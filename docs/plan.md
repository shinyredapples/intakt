# Plan: the review loop (first release)

Status: approved by the owner on 2026-10-27. The tasks are issues #5 to #35, #60, #61, #63, #64 and #67. Spec: [spec.md](spec.md). Deadline: 2026-11-22 18:00 CET.

## Conventions

- Every task is one pull request, mergeable on main with its own tests, built and reviewed as the design describes ([Choosing work](design/05-architecture/03-choosing-work.md)).
- **Waits for** names the tasks that must be merged first (they become `Waits for #n` lines when the issues exist). Tasks without a dependency between them may run in parallel.
- **Size:** S up to about 150 changed lines, M up to about 400, L above that (an L gets a plan first; split it if the plan shows two outcomes).
- **Evidence** is what the pull request must show from a running install, besides green tests.
- **Labels** on each issue, from the design's [label families](design/05-architecture/04-labels.md): `intakt` on all; `class:` and `priority:` as listed; `plan:required` on L tasks; `model:strong` only where noted.
- **PHP 8.5** lines name the 8.5 feature that fits a task (see `AGENTS.md`); use it where it makes the code clearer.
- Contracts and config shapes are not designed ahead: each task adds the contract methods and config keys it uses, and nothing more ([Left to the builder](design/08-left-to-the-builder.md)). Every user-visible task updates `docs/user/` and `docs/architecture/`.
- A task that starts or stops using a Symfony or Symfony AI feature updates its row in `docs/highlights.md` (status, task and issue, path; never the pull request number) through a new fragment in [`docs/highlights.d/`](highlights.d/), which `bin/highlights` assembles into the page (git ignores the page, so no change touches it); reviewers check it, and the `highlights` gate of `bin/check` checks the fragments, that the page is not committed, and on their assembly the status, the backticked paths, that no pull request number appears and that no row is still planned once every path it names exists; the `reproductions` gate checks that every folder under `upstream/` has a row in "Found in the beta".

## M1 Review core

### T1 Verdict schema and its validation
- **Description:** The `Review` core module's Contract gets the verdict as typed PHP objects: backed enums for verdict, severity and `fixable_by`, nested lists of findings, `resolved` and `follow_ups`, and `evidence`. These classes are the verdict's source of truth. The Platform's structured output fills them (`asObject()`, a response format naming the class) and the Validator subscriber checks their constraints; output that does not map (invalid JSON, prose, a fenced block) or fails validation becomes a failed review that says why, not a `changes` verdict ([Reviews](design/05-architecture/07-reviews.md)). The `codex` provider cannot hold the answer to a schema, and `claude_code` holds it only when its CLI returns a structured output (since #1972), so for them an answer that is text around exactly one fenced `json` block is read as that block; no block or more than one stays a failed review. T1 shipped with such output yielding `changes`; since #1823 it is asked for once more and then fails the reviewer. A JSON schema file matching the design stays as a test oracle that the classes must match.
- **Acceptance:** the design's example verdict maps to the objects; each field rule (enum, required, types) has a failing case; invalid JSON, prose and a fenced block all yield a failed review (on `claude_code` and `codex`, prose around exactly one fenced `json` block is read as that block); a test fails when the classes and the schema file disagree.
- **Evidence:** a test run listing the cases; the verdict class and schema file paths.
- **PHP 8.5:** `clone()` with property overrides for the readonly value objects; `#[NoDiscard]` on the parse result.
- **Waits for:** none. **Size:** M. **Labels:** `class:core`, `priority:high`.

### T36 A PHPStan rule: stateful services implement ResetInterface
- **Description:** A PHPStan rule next to `ParameterLimitRule`: a service class with a property that is not `readonly` must implement `ResetInterface`, so Symfony resets it between requests in worker mode and between messages in consumers. Value objects, entities, DTOs, exceptions and tests are exempt.
- **Acceptance:** a mutable service fails; with `ResetInterface` it passes; a `final readonly` service, an entity and a value object pass; the rule runs in `bin/check` and main passes.
- **Evidence:** the rule's test run and `bin/check` on main.
- **Waits for:** none. **Size:** S. **Labels:** `class:tooling`, `priority:high`.

### T83 A shrink-only ratchet list for a new PHPStan rule
- **Description:** The gate support for [Ratchet lists](design/04-constraints.md#ratchet-lists-for-a-new-rule-decided-2026-11-06), built before the next PHPStan rule part that lands with a list. A new gate (its own class and tests, appended to the gate list of `bin/check`) reads the lists from the includes of `config/gates/phpstan.neon` that point outside `config/gates/`, compares each with the target branch's version (main for a pull request) and fails when an entry is added, a `count` rises, or an entry's identifier, message pattern or path changes; deleting entries and lowering counts pass. A list absent on the target branch passes only in the change that adds its include. A list names its cleanup issue in its header. PHPStan's `reportUnmatchedIgnoredErrors` stays on, so a stale entry fails the `phpstan` gate. `docs/guide/testing-a-new-check.md` drops its "planned" mark.
- **Acceptance:** an added entry, a raised count, a widened message pattern (`#.*#`) and a changed path each fail; a deleted entry and a lowered count each pass; a new list fails without its include in the same change and passes with it; a list without a cleanup issue in its header fails; a listed violation in a moved file fails; a violation not in the list and an entry that matches nothing each fail the `phpstan` gate; `bin/check` on main passes.
- **Evidence:** the gate's test run listing the cases; `bin/check` on a temporary branch that adds a list entry (fails) and on one that deletes one (passes).
- **Waits for:** none. **Size:** M. **Labels:** `class:tooling`, `priority:high`.

### T31 `bin/instance` and `bin/probe` for reviewers and the boot gate
- **Description:** `bin/instance` boots Intakt from a clean checkout after `composer install` with the plain Symfony runtime (PHP's built-in web server on a free local port, SQLite in a scratch directory), checks that it answers, prints one JSON status line (`ready` or `failed` with the reason), and stops cleanly. `bin/probe <file>` boots the same instance and runs a reviewer's small PHPUnit test or PHP script against it, with network access cut, and prints its output and exit code. Both work offline, so the build loop can run reviewer probes and a boot gate on Intakt itself. FrankenPHP is a binary, not a Composer package, so worker mode arrives with the image in T22, which switches `bin/instance` to it inside the image.
- **Acceptance:** both commands work with the network disabled; a broken kernel config makes `bin/instance` report `failed` with the error and a non-zero exit; a probe that reaches for the network fails; the instance leaves no process or file behind; both are documented in `docs/architecture/`.
- **Evidence:** the JSON status of a clean and of a broken boot, and a probe run with its output, all without network.
- **PHP 8.5:** `#[NoDiscard]` on the instance status.
- **Waits for:** none. **Size:** M. **Labels:** `class:tooling`, `priority:high`.

### T2 Ledger: append-only events on SQLite
- **Description:** The `Ledger` core module stores events (review started, reviewer started, verdict received, judge done, usage recorded) in one append-only table through Doctrine, with a migration. No updates or deletes (one later exception, issue #2078: `intakt:demo:remove` deletes the rows replayed into the demo project). Event ids are UUIDv7 (Symfony Uid), so they sort by time; findings use the same id type when they are stored.
- **Acceptance:** appending and reading events in order works; event ids are UUIDv7; an update or delete is refused; tests are in the `persistence` group.
- **Evidence:** `bin/console doctrine:migrations:migrate` output on SQLite and the events of a test run read back with a console query.
- **PHP 8.5:** `#[NoDiscard]` on the append result, so a write that failed cannot be ignored.
- **Waits for:** none. **Size:** M. **Labels:** `class:core`, `priority:high`.

### T3 Persistence tests on MySQL, MariaDB and PostgreSQL in CI
- **Description:** A CI job with service containers runs the `persistence` group on each engine (built as a matrix; since merged into one job with a service per engine, as each job costs an ephemeral runner a full reset; the engines run at once in one step, on tmpfs data directories). Protected path: the owner approves the merge of the workflow change; it is pushed without a separate approval only when the workflow scan finds it not risky (see Merge).
- **Acceptance:** the matrix runs on the branch and is green on all three engines; the SQLite run in `bin/check` stays unchanged.
- **Evidence:** the CI run link with the three jobs.
- **Waits for:** T2. **Size:** S. **Labels:** `class:tooling`, `priority:normal`.

### T4 Providers, tiers and routing in config
- **Description:** AI Bundle configuration for at least two Platform providers (for example Anthropic and OpenAI) plus an OpenAI-compatible endpoint, keys from Symfony secrets or the environment. Intakt's own config maps capability tiers (`strong`, `standard`, `light`) to provider models per project through a model router and the AI Bundle's `model_catalog` config; several projects per install.
- **Acceptance:** the container builds with two projects that map tiers differently; a missing key disables that provider with a clear message instead of failing the boot; tests use `MockPlatformFactory` with `ScriptedResponse` (the in-memory platform no longer exists).
- **Evidence:** `bin/console debug:config ai` and an Intakt command that lists projects and their resolved tiers.
- **Waits for:** none. **Size:** M. **Labels:** `class:core`, `priority:high`.

### T5 Vendor contract and the Symfony AI Platform vendor
- **Description:** The `Vendor` plugin contract gets the one method the review needs (run a structured call for a tier). The first implementation, `Plugin/SymfonyAiVendor`, uses the Platform's structured output with the T1 verdict class (`asObject()`, checked by the Validator subscriber) and records token usage per call in the ledger (started, settled, unsettled). Per-call cost comes from the result's `getTokenUsages()` (`TokenUsage`, cached tokens included); the `remaining*` token figures a provider returns feed the budget planner.
- **Acceptance:** a structured call against `MockPlatformFactory` with a `ScriptedResponse` returns a typed verdict object; usage, cached tokens included, is recorded once per call; the `remaining*` figures reach the planner; a 429 is caught as `RateLimitExceededException` with its reset from `getRetryAfter()`, other transient errors through `RetryableExceptionInterface`, never parsed from text; the T1 schema file is the test oracle, not the call's source.
- **Evidence:** one real call per configured provider from a console command, with its usage line (keys from the owner's environment, never committed).
- **PHP 8.5:** `#[NoDiscard]` on usage reservations; the pipe operator for building the request from task, tier and verdict class.
- **Waits for:** T1, T2, T4. **Size:** M. **Labels:** `class:core`, `priority:high`.

### T6 Forge contract and the local git forge
- **Description:** The `Forge` contract gets what reading a change needs (head, base, diff, files at head). `Plugin/LocalGitForge` treats a branch of a local repository against its base as a pull request, through the Process component.
- **Acceptance:** the diff and file contents at the exact head are returned; a moved head is detected; tests use a temporary repository.
- **Evidence:** a console command printing the change summary of a sample branch.
- **PHP 8.5:** the pipe operator for turning `git diff` output into changed files.
- **Waits for:** none. **Size:** M. **Labels:** `class:core`, `priority:high`.

### T7 One reviewer agent with read-only repository tools
- **Description:** A reviewer is a Symfony AI Agent with tools to read a file, list a directory and search at the exact head (tool effect hints: read-only), a prompt per role and the task text. It returns the T1 verdict through the T5 vendor; the conversation is kept per round in an Agent message store (`MessageStoreInterface`, the agent's `message_store` option; the Doctrine DBAL store in production). The reviewer prompt includes the rubric of [How code reads](design/02-principles.md#how-code-reads): story readability, needless abstraction, duplication of knowledge and what-comments, each finding citing the rule it breaks.
- **Acceptance:** with `MockPlatformFactory` and `ScriptedResponse` scripted to call tools, the agent reads files at the head and returns a verdict; a tool call outside the repository is refused; a malformed tool call ends as a failed review (asked again once, then parked; no review cycle), not a crash; round two reads cached tokens (a test on the recorded usage). Tests assert through the AI Bundle's `AiAssertionsTrait` (`assertToolCalled`, `assertPlatformCallCount`). A sample change with a what-comment and a single-implementation interface gets findings that cite those rules.
- **Evidence:** a real review of a sample branch by one provider: the verdict JSON and the tool calls it made.
- **Symfony AI:** Anthropic prompt caching on; tools run in a `FaultTolerantToolbox`, so a failing tool answers the model with an error; a `ToolCallRequested` listener denies tool calls whose arguments escape the checkout.
- **Prompt safety:** this task brings the fencing helper of the [threat model](design/05-architecture/14-threat-model.md#third-party-text); the task text, the diff and tool results reach the prompt only through it.
- **Waits for:** T5, T6. **Size:** M. **Labels:** `class:core`, `priority:high`.

## M2 Panel and rounds

### T8 Review panel and quorum policy
- **Description:** A panel is configured per project: reviewers (role, tier, provider, prompt, budget), a quorum policy (all, majority, one strong plus one) and rules choosing a panel by change (size, paths, `review:full`).
- **Acceptance:** each policy has passing and failing cases; a panel of one, two and three reviewers works; the panel is chosen from config alone.
- **Evidence:** two configs producing two different panels for the same change, shown by a dry-run command.
- **PHP 8.5:** closures in constant expressions for the built-in quorum policies.
- **Waits for:** T4, T7. **Size:** M. **Labels:** `class:core`, `priority:high`.

### T9 Parallel reviewers through Messenger
- **Description:** A review round dispatches one message per reviewer; workers run them in parallel and the round completes when all verdicts or failures are in. State lives in the database, so a restarted worker resumes. This is the first task with message handlers, so it also installs Messenger with a command bus and a query bus, and adds the typed handler attributes with their first use: a small `Core/Platform` module's `Contract` gets a backed enum `Bus` and `AsCommandHandler` and `AsQueryHandler`, each extending Symfony's `AsMessageHandler`, fixing `bus: Bus::X->value` and passing `handles`, `method` and `priority` through. A PHPArkitect rule lets nothing in `src/` but that `Contract` depend on `AsMessageHandler`; first prove with a fixture that PHPArkitect counts attribute uses, and if it does not, a guard test parses `src/` for a direct `#[AsMessageHandler]` (aliases included) and names the attribute to use.
- **Acceptance:** a forced-order test proves the round completes correctly whichever reviewer finishes first; a killed worker's reviewer is retried once and then counts as `blocked`. A command handler is not callable on the query bus, and the reverse; the boundary rule (or guard test) fails on a fixture that uses `AsMessageHandler` directly, including through an alias; a handler that does not read its message declares it with `handles:`.
- **Evidence:** a round of three reviewers with their start and end times overlapping in the ledger.
- **Symfony:** the Workflow component is the state machine of the round and of each reviewer, with its Graphviz diagram in `docs/architecture/`. A rate-limited reviewer message is retried after the provider's reset: the exception implements `RecoverableExceptionInterface` and `getRetryDelay()` returns `getRetryAfter()`. A message that reaches the failure transport means the reviewer is `blocked`. A Semaphore per vendor account caps its parallel calls.
- **Waits for:** T8. **Size:** L. **Labels:** `class:core`, `priority:high`, `plan:required`.

### T10 Persistent finding ids across rounds
- **Description:** Round two and later pass the open findings to each reviewer; verdicts list `resolved` ids and mark `repeat`. A new P1 or P2 from round two on that is neither a regression nor cites a requirement is lowered to P3.
- **Acceptance:** ids stay stable over three rounds; resolved findings close; the goalpost rule is enforced in code, not only in the prompt.
- **Evidence:** two real rounds on a sample branch, the second after a fixing commit, with the finding table of both.
- **PHP 8.5:** `array_first()` and `array_last()` for the first and latest round of a finding.
- **Waits for:** T9. **Size:** M. **Labels:** `class:core`, `priority:high`.

### T11 Verdict identity
- **Description:** Each verdict records head, base, task revision, check command and panel policy. A change to any of them makes it stale; a clean merge of the base or a docs-only change keeps it for the untouched parts, but never its class of the protected part, which counts only for the head it was given on (D1 of #1072).
- **Acceptance:** each identity field invalidates on change; the two exceptions are covered.
- **Evidence:** a stale verdict shown as stale after a new commit on the sample branch.
- **Waits for:** T9. **Size:** S. **Labels:** `class:core`, `priority:normal`.

### T12 Judge step
- **Description:** A judge agent on a light tier marks each finding act, defer or reject against the task's acceptance criteria and non-goals, using structured output. A deferred P3 finding becomes a follow-up. A P1 or P2 finding stays on the builder's act list even when the judge marks it `defer` or `reject`, with the judge's reason kept beside it as a note.
- **Acceptance:** the judge's output is a typed object through structured output, checked by the Validator; an invalid judge answer means every blocking finding is `act`; the builder-facing list holds only `act` findings.
- **Evidence:** a real judge result on the T10 rounds.
- **Waits for:** T10. **Size:** M. **Labels:** `class:core`, `priority:high`.

### T13 `intakt:review` console command
- **Description:** One command reviews a change end to end (`--project`, change reference, `--round`) and prints the outcome, the act list and the cost, or JSON with `--format=json`.
- **Acceptance:** exit codes distinguish approve, changes and blocked; the JSON output validates against a documented schema.
- **Evidence:** the command's output on the sample repository with two providers.
- **Symfony:** Console 8.1 input mapping for the arguments and options; tests use `CommandTester` assertions (the round is scripted at the vendor contract, so no platform call is made for `AiAssertionsTrait` to assert).
- **Waits for:** T12. **Size:** S. **Labels:** `class:feature`, `priority:high`.

### T14 Provider limits and substitutes
- **Description:** A rate-limited or failing provider puts its account in cooldown until the reset time; the reviewer moves to the next account of the same vendor and role by priority, and only when every such account is out does the panel substitute a reviewer from the same tier on another provider and record that a catch-up review is owed.
- **Acceptance:** cooldown is per account, shared by all reviewers on it; a same-vendor account is tried before another provider and owes no catch-up review; substitution follows config; an outage of every provider ends the round as `blocked` with the reason.
- **Evidence:** a round with one provider's key revoked, showing the substitute and the owed catch-up; and a round with one of two same-vendor accounts out, showing the move to the other account and no catch-up owed.
- **Symfony:** provider failover through `FailoverPlatform`, wrapped by Intakt's own class that records the switch and does not rely on it alone; per-account cooldowns as RateLimiter windows aligned to the vendor's reset; Scheduler ticks for usage probes and deadlines.
- **Catch-up:** the owed record only; the catch-up review itself is T66.
- **Waits for:** T9. **Size:** M. **Labels:** `class:core`, `priority:normal`.

## M3 Agents and memory

### T15 MCP server for agents
- **Description:** The MCP Bundle exposes tools to start a review, read its status, read verdicts and the act list, and list projects, plus resources for a round's findings. Read tools are marked read-only.
- **Acceptance:** an MCP client test (PHP MCP SDK client) calls every tool; starting a review needs the configured token; errors are MCP errors, not stack traces.
- **Evidence:** an agent CLI connected over MCP starting a review of the sample branch and reading the act list (transcript excerpt), with the tool calls scripted in the builder's sandbox, which has no model login; the same transcript with a logged-in model choosing the calls (owner provides).
- **PHP 8.5:** closures in attributes where an MCP tool's input needs a check.
- **Tool safety:** every tool carries the MCP SDK's annotations (`readOnlyHint`, `destructiveHint`); whether a tool may write is decided by a Symfony Security voter on Intakt's own config, never by the model's arguments. A contract test checks that a tool without parameters encodes them as `"properties": {}` and that the protocol version is negotiated correctly with Claude Code; a failure is an upstream report under `upstream/`.
- **MCP:** the owner's MCP Bundle server and, since T16 part 1, the per-review one, with `session.lock` on. Tool authorization goes through `#[IsGrantedTool]` backed by Intakt's voter; long tools send progress notifications.
- **Worker:** the MCP server runs in its own named FrankenPHP worker (see T22), so streamed MCP responses can't starve the dashboard's worker threads.
- **Waits for:** T13. **Size:** M. **Labels:** `class:feature`, `priority:high`.

### T16 Reviewer tools over MCP
- **Description:** The read-only repository tools of T7 are served by an Intakt MCP Bundle server per review, and reviewers reach them through the agent's built-in MCP client tool (`ai.agent.<name>.tools` with an `mcp_server` entry), not hand-written client code, so any MCP-capable reviewer can use the same tools.
- **Acceptance:** a review with tools over MCP gives the same verdict path as the in-process tools in tests; the server serves only the head under review.
- **Evidence:** a real review whose tool calls appear in the MCP server's log.
- **Tool safety:** every tool carries the MCP SDK's annotations (`readOnlyHint`, `destructiveHint`); whether a tool may write is decided by a Symfony Security voter on Intakt's own config, never by the model's arguments. A contract test checks that a tool without parameters encodes them as `"properties": {}` and that the protocol version is negotiated correctly with Claude Code; a failure is an upstream report under `upstream/`.
- **MCP:** the per-review server runs with `session.lock` on; tool authorization goes through `#[IsGrantedTool]` backed by Intakt's voter; long tools send progress notifications.
- **Waits for:** T7, T15. **Size:** M. **Labels:** `class:core`, `priority:normal`.

### T17 Project memory with the Store
- **Description:** After each completed review, resolved findings and their causes are indexed with the Symfony AI Store (an embedded store that works on SQLite); each reviewer's briefing retrieves the entries relevant to the files under review, with a size cap. Indexing uses the `DocumentIndexer`, retrieval the `Retriever`, and the briefing reaches the agent as a fenced user message of its own (not through `MemoryInputProcessor`, whose fixed preamble ranks memory above the system prompt). A reranker is added only when a configured provider supports reranking.
- **Acceptance:** indexing and retrieval are tested with an in-memory store; the briefing respects its cap; memory is read-only to reviewers.
- **Evidence:** a second review on the sample repository whose briefing cites an earlier finding.
- **Store backend:** `symfony/ai-sqlite-store` (SQLite FTS5 plus vector similarity computed in PHP, needs only `pdo_sqlite`) behind Intakt's own small retrieval contract; the in-memory store in tests. It loads all vectors into PHP memory for a query, which is fine at the size of one install's memory (one store for every project, its notes kept apart by project); `docs/architecture/` says so.
- **Waits for:** T12. **Size:** M. **Labels:** `class:feature`, `priority:normal`.

### T18 GitHub forge plugin
- **Description:** `Plugin/GitHubForge` reads a pull request (head, base, diff, files at head) with a token from the environment and posts the outcome as one review comment carrying the round's one-time token. It calls GitHub through a scoped HttpClient wrapped in `RetryableHttpClient`. Before a review body and its findings are posted, the values of every credential mounted or injected into that job are redacted and the secret scan runs over the text; a hit is not posted and is a failed review (asked again once, then parked; no review cycle) ([Threat model](design/05-architecture/14-threat-model.md)). Build bundles are not taken in by any task of this plan: the task that first takes in a build's hand-back carries the same step, so it is not lost when that task is planned.
- **Acceptance:** recorded HTTP responses drive the tests; a head that moved during review is detected; nothing is posted when the round is stale; a review text holding a mounted credential's value is posted redacted, and one that still trips the secret scan is not posted and is a failed review (asked again once, then parked; no review cycle).
- **Evidence:** a review of a real pull request in a test repository, with the posted comment.
- **PHP 8.5:** `Uri\Rfc3986\Uri` instead of `parse_url` for pull-request and API URLs.
- **Waits for:** T13. **Size:** M. **Labels:** `class:feature`, `priority:normal`.

### T33 A subscription reviewer through the Claude Code or Codex platform bridge
- **Description:** One reviewer role runs through `symfony/ai-claude-code-platform` or `symfony/ai-codex-platform` (BETA1) on a subscription account (its automation token where the vendor has one), behind the same vendor contract as the API providers. Its stream parsing is exercised on purpose, including a stream that ends early (`IncompleteStreamException`). The package is a new dependency the owner approves.
- **Acceptance:** recorded streams drive the tests; a complete stream yields a typed verdict; a truncated stream raises `IncompleteStreamException` and the reviewer ends as `blocked` with the reason, its usage counted once; the setup shows which plans the vendor's terms allow for this use.
- **Evidence:** a real review of the sample branch by the subscription reviewer, with its verdict and usage line.
- **Waits for:** T7. **Size:** M. **Labels:** `class:feature`, `priority:normal`.

## M4 Live dashboard

### T20 Dashboard of reviews
- **Description:** A small server-rendered dashboard (Twig) lists projects and reviews; a review page shows each round, its reviewers, verdicts, findings with ids, the judge's call, tokens and cost. A button starts a review of a listed change.
- **Acceptance:** pages render from the ledger alone (since #677, apart from the forge budget on `/reviews`, read from the forge's recorded readings without a forge call); functional tests cover each page; no page polls.
- **Evidence:** screenshots of a completed two-round review.
- **Waits for:** T13. **Size:** M. **Labels:** `class:feature`, `priority:high`.

### T21 Live updates with streaming and Mercure
- **Description:** Reviewer progress and round state are published through Mercure as Turbo Streams as they happen, served by FrankenPHP's built-in Mercure hub; the review page updates without reloads. Progress comes from the agent's streaming `Progress` updates (tool calls, streamed text). A stop button on a running reviewer calls `Execution::cancel()`.
- **Mercure:** the built-in hub (FrankenPHP 1.13 and later) is configured with `publisher` and `issuer` keys, and symfony/mercure mints the tokens. Messenger consumers publish through the hub endpoint; the web side may use `mercure_publish()`, checked with `function_exists()` at runtime (it is absent in the CLI, so its existence is never cached at container build). The `bolt` transport keeps history, so a client that reconnects catches up with `Last-Event-ID`. The hub's route is excluded from `encode` in the Caddyfile.

### T47 Work intake from GitHub issues
- **Description:** `Plugin/WorkSource` for GitHub issues: eligible when open, carrying the project's eligibility label and not `idea`, written and last edited by an account with write access (checked when it becomes eligible and before each build), and not blocked. `Waits for #n` holds a task until every named issue is closed and every named pull request is merged into main, except a line naming the task's own pull request (or the pull request of its branch), which is no wait (the build hands over, see T59); a target that is a pull request counts as the task that pull request closes (its branch or closing keyword) for that task's failure and stall, but is released only by the confirmed merge of that pull request into main, never by that task closing: this holds for every pull-request target, a follow-up's wait on its original's pull request included, so intake does not tell such lines apart ([Choosing work](design/05-architecture/03-choosing-work.md), step 5); a task that failed for good holds its dependents with the reason. The state of every waited-for issue comes from the tick's one listing (or the stored state of an unchanged item, read conditionally), never one read per reference; only a complete, successful listing can mark a waited-for issue closed, and after a partial or failed listing every wait keeps its stored state. The one exception is a waited-for pull request: while the listing shows it open nothing is read, and once a complete listing no longer shows it open it is read once by its number and the answer stored (merged into main releases the wait; closed without a merge, or merged into another branch, releases nothing); a failed read stores nothing and is retried on the next tick (after three failed reads in a row at most once a day, and the wait stays held), a read that finds it open again stores nothing and keeps the wait held, a stored "closed without a merge" is dropped as soon as a listing shows the pull request open again, and while a wait stays held on it that pull request is read again at most once a day. A worker that will not take work this tick reads nothing from the forge. Order: `urgent` first, then open pull requests, then the milestone's due date (no milestone, or one without a due date, last; distinct milestones with the same due date, or with none, are tied, and their tasks are ordered together by the keys that follow), then effective priority (the label's `high`, `normal`, `low`, none is `normal`, raised one band per `aging_days` and by the open pull requests that wait on the task, as [Choosing work](design/05-architecture/03-choosing-work.md), step 5, specifies), then the number of queued tasks that wait on the task through the whole `Waits for` chain (more first), then the issue number; within the open pull requests the same order holds, and that count never moves a task across a priority or a milestone (milestones tied on their due date count as one). A blocked task, or one that waits on another, is passed over for the next task in this order; a skip for files in flight stays within the first candidate's milestone, priority and class (T56). A follow-up queued from a non-blocking finding joins the next open milestone after its original's (its original's when there is none), one that carries a blocking finding a reviewer raised as a follow-up item and every split part keep their original's, and the follow-up's body names its original's milestone ([Choosing work](design/05-architecture/03-choosing-work.md), step 5); next-milestone routing is the default, and the owner can list it for bounded tuning (T96). Whenever a task is queued (also after a hand-over is settled or a hold is released), its open pull request is read from the forge by the task's branch, and a task that has one is queued as a rework of that pull request, never as a fresh build. Queue state lives in the database; status labels mirror it (T19).
- **Reference:** `test_github.py` (idea issues skipped), `test_unblock.py` (trusted notes only, every referenced issue closed), `test_priority.py`, `test_queue.py`, `test_projects.py` (share order; a project at share 0 is paused for builds and reviews).
- **Acceptance:** each rule above has a case on recorded responses; an edit by an untrusted account makes the task ineligible until a trusted account confirms it; a forced-order test settles a hand-over on a task with an open pull request after its queue record is gone, and the task is queued as a rework of that pull request; a wait on several issues makes no per-reference read, a listing that comes back short releases no wait, a task that closes while its pull request is still open leaves the follow-up that waits on that pull request held and causes no read of it, a waited-for pull request that left the open listing is read exactly once and releases its waits only when it was merged into main (closed without a merge releases none, and a pull request retargeted to another branch and merged there releases none), a forced-order case where that read fails stores nothing and reads again on the next tick, a case where the read fails on three ticks in a row reads that pull request at most once a day after that and keeps the wait held, a forced-order case where the pull request is reopened between the listing and that read stores nothing, keeps the wait held, and releases it when a later listing no longer shows the pull request open and the next read finds it merged, a pull request stored as closed without a merge that is reopened and merged between two ticks releases its wait within a day of ticks that read the forge for intake with a complete listing (a tick of a worker that will not take work, or one whose listing came back short, does not count) with at most one read of it in that day, and a worker that will not take work this tick makes no forge call; forced-order cases for the order: a `normal` task of an earlier milestone is picked before a `high` task of a later milestone, an `urgent` task of a later milestone is picked first, priority decides within one milestone, of two tasks in distinct milestones with the same due date (and of two in distinct milestones with no due date) the `high` one is picked before the `normal` one whatever their milestones' numbers, of two tasks of one priority in distinct milestones with the same due date, the one with more queued tasks waiting on it is picked over an older one whatever their milestones' numbers, a blocked task is passed over for the next one, and a skip for files in flight never picks a task of a later milestone (with no free task left in the band, the first candidate is built); of two tasks with one priority, milestone and class that tie on the critical path (neither is a chain head of it), the one with more queued tasks waiting on it through the whole chain is picked over an older one, also when its own chain is shorter (one task with three short branches waiting beats an older task with one chain of two), and a lower-priority task with more waiting tasks is never picked first; A hit in the pull request text follows the same rule, on each of the two paths with a test: (order) the text is scanned before the commits leave the quarantine or are pushed, which changes both paths as built today (the round scans the text after the bundle's objects were moved into the repository, and the build task's text is scanned only by the forge plugin after the branch push, since `HandBackChecks` takes no text), and the forge's own scan stays as a second barrier; (hold, D1) whenever work is held, the text is held with the commits in the same quarantine, whether the hit was in the commits or in the text (tested for a commit-only hit as well as a text hit), never written to the ledger, a comment, the forge or a model; (retention and record, D2) the same limit applies and its end deletes the text with the objects, and the finding's record names "pull request text", the line and the rule, never the value; (release, D3) the kept commits and the kept text are both scanned again, and the work goes on with the kept text, without a new build session; (deletion, D4) a finding judged real, or not judged in time, deletes the text too. (expiry, D4) the retention limit ends the hold whatever the state of the judgement: its end deletes the held commits and text and sends the task back to build with the sanitized finding (file, line and rule) as feedback, also when the finding was judged false and its rule or allowlist change has already landed but the new scan has not yet passed, with a test; a rule or allowlist change for the finding still open at its end adds a `Waits for` line naming that change to the task, with a test. (pre-push) the build task's pre-push check runs `CheckHandBack` only on a bundle the hand-back check already accepted, so it scans the same bytes under the same rules and cannot produce the first hit while its scan scope is unchanged; `CheckHandBack` resolves the pushed branch and main from the mirror again, so a rewrite of either between the two checks can bring an object the first check excluded into scope, and a hit on it is handled as any refusal below; if it refuses anyway, the build fails closed, nothing is pushed, and the hold applies to the bundle as on the other paths. The never-moved guarantee (D1) covers objects that no scan has accepted: the objects the first check accepted and moved into the mirror, named by no ref, are only those the accepted head reaches beyond the pushed branch and main, which are the objects the scan read, so they have passed the scan under the same rules (this requires the (moved objects) case below: as built today the check moves the whole unbundled pack, commits as shipped and unreached objects included, so this clause holds only once every object the first check moves is one its scan read, and the (moved objects) tests are its precondition), a pre-push refusal does not delete them and nothing tries to isolate them; they stay on the orchestrator's machine only, are never pushed and reach no model. The bundle the first check received is held in the quarantine with the text for judgement, as on the other paths, and the build clone, which already holds the accepted head, is removed: this task adds that cleanup, because as built today the build task returns on a pre-push refusal and leaves the clone in place. Its test: a pre-push refusal pushes nothing and leaves the bundle and the text held. (moved objects) an accepted check moves into the mirror only the objects the accepted head reaches beyond the pushed branch and main, which changes the check as built today (it moves the whole unbundled pack, so `docs/architecture/hand-back.md` says the commits as shipped stay beside the rewritten ones, and this task corrects that sentence): a commit as shipped that the check wrote again (a stripped trailer, a redacted credential in its message) and any pack object the accepted head does not reach never leave the quarantine, each with a test. The scan is not widened to the whole pack instead, because a commit with a mounted credential in its message would then be refused instead of redacted. ### T57 Review lane through CI
- **Description:** The review lane takes pushed heads, never one of a project at weekly share 0 (owner decision 6: such a project gets no reviews, open pull requests included, until its share is raised): a head with pending CI goes back to its queue with a time to look again and holds nothing; heads with finished CI go first, one pending for 30 minutes is admitted by age; among heads of one priority, the one whose task more queued tasks wait on (through the whole chain) is reviewed first, then by age, never across a priority. ### T59 Rework feedback, scoped re-reviews and holds
- **Description:** A send-back gives the builder the judge's act list (open findings merged across reviewers, P1 first, one per place) and the published pull request text. A build that leaves the head unchanged while a finding needs something outside the change goes on hold and is released by an event that could change the outcome: a move of main releases an outside-change or red-CI hold into a merge-main build, never into a review of the unchanged head; a deploy alone releases into one review; the fruitless-release count and its hand-over stay. ### T63 Watchdog over main
- **Description:** A new `Core/Watchdog` checks main's new commits before every step and merge by how each arrived, never by its signature ([Merge](design/05-architecture/08-merge.md#watching-main)): a merge Intakt recorded passes; a commit the forge reports as part of a pull request merged into main by an account with write access, and one a person with write access pushed to main, are info events (a direct push also shows on the dashboard as "pushed without the gate", and main's CI result on it is watched as for any merge). A rewrite of main's history, a commit the forge cannot attribute to a merged pull request or to a write-access pusher, a merger or pusher without write access, a direct push by a bot or App account, and a commit Intakt's own identity (its App or the maintainer agent's) pushed or merged that Intakt's record lacks halt the project with an owner card that names the commit and the reason and that only the owner clears. A merge attempt records the pull request, the head, main's commit it lands on and which of Intakt's identities makes the call, before the call, and covers every merge call made under it. Before every watchdog run recovery reads each open attempt's pull request back: it records the landing as Intakt's merge only when the attempt's head landed on main by the identity the attempt recorded, read by the attempt's one landing form (for a forge merge call, the forge reports the pull request merged with that head, into main, by that identity, and main contains the merge commit the forge reports, which can differ from the head; for T62's ref update, main's ref moved from the recorded commit to exactly that head by a push the forge attributes to that identity, which is then Intakt's merge and never a direct push by an App, whatever the forge later reports as the pull request's merger); it closes the attempt without a merge only on a definitive outcome: for a forge merge call, the pull request is closed unmerged, its head changed, or another account or another base merged it (that commit is judged by the ordinary rules); for a ref update, never on the pull request's state, only once main no longer holds the recorded commit and was not moved to the head by the recorded identity's push (a push the forge has not yet attributed is no outcome); in both, a definitive refusal while no earlier call under the attempt is still unresolved (timed out or unanswered); otherwise (a forge merge call's pull request open on that head, a ref update's main still on the recorded commit or at the head with the push's attribution pending) the attempt stays open. The watchdog reads an open attempt back once more before it halts a commit by Intakt's own identity. A commit by Intakt's own identity that an open attempt could still explain (for a forge merge call, its pull request still reported open on that head; for a ref update, main holding the attempt's head, whatever the forge reports of the pull request, which it can report closed or merged before it attributes the push) is held as pending (not accepted, not halted, no merge meanwhile) and read again on the next pass; not attributed within 10 minutes, it halts as unrecorded. ### T65 Pull requests Intakt did not build
- **Description:** A pull request opened by the owner's or the maintainer's identity is reviewed on every new head without a label; anyone else's only after a person with write access labels it (a dependency bot's is taken without a label, T97). Findings go back as one comment and labels stay; without `take-over` Intakt never reworks it. Once CI and every review pass, an unprotected head merges and a protected one asks the owner once; a dependency bot's pull request is the exception: it never merges without the owner's one approval, whatever paths it touches (T97). Such a pull request merges by the forge's merge call with the project's merge method, so the forge closes it and its author keeps the credit, and the resulting commit is recorded as Intakt's merge ([Merging others' pull requests](design/05-architecture/08-merge.md#merging-others-pull-requests)). An `urgent` or `high` label counts only from the owner or the maintainer.
  An oversized one is split, not only a task ([The maintainer agent](design/05-architecture/09-maintainer-agent.md)): a head past the split tier on a pull request opened by the owner's or the maintainer agent's identity goes to the maintainer agent as a split with no `take-over` (these identities are trusted, so building from their head is safe); anyone else's gets one comment saying it is past the size limit and asking the author to split it, and is split once a person with write access sets `take-over`. The agent records the split plan first (resumable, no part created twice), and plain code checks every changed path or hunk of the diff from the merge base to `<sha>` against it before it is recorded. Each part is a task naming `Source: <branch>@<sha>` of the original head, cut along files where possible, each under the split tier, with its merge order when it links to another part. Once every part's pull request is open or merged, plain code applies each part's head as its pull request was opened, in merge order, to the merge base, which must give the tree of `<sha>`; a part closed without merging counts as missing. The same check reads each open part's current head and each merged part's merged change, which must carry exactly its share (nothing dropped, nothing added) and still give that tree in merge order; until every part has merged, a part head that drops or adds an edit is refused before review, and a part closed without merging after the original was closed reopens the original. On a mismatch or a missing part the original stays open and goes back to the maintainer agent and, the second time, to the owner; otherwise Intakt records the verified head in the split plan, closes the original with a comment naming the parts, reads the head again and reopens the original to extend the split if it moved during the close, never force-pushes or deletes its branch, and updates open issues naming the original to name the parts, as the maintainer agent's edit. Commits after `<sha>` add parts checked against the diff from the old `<sha>` to the new head, and the close check becomes the tree of the new head.
  It also covers handing items between a person and Intakt ([Labels](design/05-architecture/04-labels.md#who-drives-an-item)). `hands-off` from a person with write access stops everything on any issue or pull request: nothing starts, a running job ends at its next step, nothing it produced after the label is pushed or posted (unpushed work is kept as a bundle), a merge re-checks the label right before publishing, and it beats every other label and rule. Removing it, or setting `take-over`, on anything but a dependency bot's pull request makes the current head the task's head: commits made by hand are listed for the builder (writers' commits as its own, others fenced), the head gets one full review by every reviewer, earlier findings are checked against it, and hand-made commits use no review cycle; on a dependency bot's pull request removing `hands-off` only puts it back on the bot path and `take-over` is refused (both T97), so nothing is listed for the builder. `take-over` on a pull request Intakt did not build, other than a dependency bot's, makes it an Intakt task (reworked and reviewed like Intakt's own; on its original branch it lands by the forge merge call, as any pull request Intakt did not open); such a fork it cannot push to that is within the size limit is carried over to an Intakt branch and a new pull request linking the original, which is Intakt's own and lands by the ref update, with a `Co-authored-by` trailer per original author and one comment on the original. A pull request touching protected paths is not taken over (Intakt says so once, naming the files); nor is a dependency bot's, which T97 refuses once with a comment and keeps on the bot path (the bot rebases, the owner approves, a red check becomes a task). `take-over` on an issue by someone without write access stands in for the authorship check, with the text fenced, and an edit after it needs the label again.

### T93 Updates without pausing every lane
- **Description:** The update flow of the design ([Updates](design/05-architecture/11-setup.md#updates)), issue #968. A new version is installed side by side as a new immutable image pinned by digest, and runs the build-path self-check (#930, D1) on the default branch while the old version keeps scheduling. Its result is compared failure by failure with the running version's last result on the same commit, reused when the commit, the locked dependencies and the check configuration are unchanged. A test failure is identified by the test's name, its failure kind (assertion failure, error or timeout), its failure message or diagnostic with times, durations and paths removed, and the source location of the failing assertion from the report or else the stack trace; a finding is identified by its rule and location. A test failure without a location is matched on its whole normalized output including the trace, and one with neither counts against the update. A failure both versions show with the same identity is reported and does not block, any other fails the update, including the same test failing at a different assertion or with a different message, and this verdict lets the update go on. One build slot then switches to the new version (its jobs run from the new image, started and recorded by the running orchestrator, which stays the only writer), and the others switch together after that slot's first build finishes without an environment failure (#930, D2), or after a fixed number of minutes with no failure; a running job finishes on the version it started on. Only the slot being switched waits, with a deadline per slot after which its job is checkpointed as for a no-progress stop and resumed on the new version. Last, the orchestrator cuts over: the new one takes the next owner generation only through a takeover grant naming the expected current generation, checked and consumed in the transaction that raises it, and writes with it; a rollback revokes the grant in the transaction in which the old orchestrator takes the next generation, a write with an older generation is refused, and running reviews keep running and are collected by the new orchestrator; an old orchestrator that has not exited by a deadline of seconds is stopped by force, and a new one that does not take over by its own deadline gives way to the old version again. An update that declares stored state the old version cannot read pauses all lanes through T69's drain, copies the database and `/data`, and is rolled back from that copy only before the lanes resume. Non-urgent updates wait for the owner's update windows, at most a few a day; an urgent release and a version the owner picks start at once. Any other failure rolls back and alerts on the first one; a failure after a declared incompatible update has resumed the lanes cannot roll back: it pauses the lanes, alerts the owner and is fixed by a newer release. The old version stays installed until the post-update check and the next jobs' outcomes look right.
- **Reference:** the build loop's four self-updates of 2026-11-05 (30 to 80 minutes paused each, and one blocked on a test that failed the same way on the old version).
- **Acceptance:** forced-order tests with a controlled clock: a self-check failure the running version shows on the same commit is reported and the canary slot switches, and one only the new version shows rolls back with one alert; the same test failing at a different assertion with the same message on the new version fails the update; a test failure with neither a location nor a trace fails the update; a report that does not validate fails the update; an old orchestrator that hangs at the cut-over after writing the takeover grant is stopped at its deadline and admission resumes on the new one; an old orchestrator that hangs before writing the grant is stopped at its deadline, the new one takes nothing, and at the new one's deadline the old version is started again, takes the next generation and resumes admission; a new orchestrator that starts after the rollback is refused and takes nothing, and the old one keeps writing; a declared update that fails after the lanes resumed pauses the lanes with one alert and is not rolled back; two claimers racing for one queue item during the update leave it claimed once, and a write of the old orchestrator after the cut-over is refused; a review running at the cut-over finishes and is recorded once; a declared update that fails before the lanes resume is restored from its copy; a stored result is reused only while commit, dependencies and check configuration are unchanged; the other slots switch after the canary slot's first build without an environment failure, or after the set minutes; an environment failure on the canary slot rolls every slot back; a job running when its slot switches finishes on its old version; a job past its slot's deadline is checkpointed with its commits kept and resumes on the new version; ### T95 Check slots per host
- **Description:** The [check slots](design/05-architecture/01-overview.md#check-slots) of the design, issue #1781: an install runs at most `check_slots` jobs running checks at once on its host (a job's checks share one slot), for every project and whatever its tools. D1 a host-wide counting lock around each check: `check_slots` lock files taken with `flock`, freed by the kernel when the holder ends; no daemon, no queue state; the lock directory is the whole state and covers every project of the install; only the orchestrator holds slots, and the lock directory is never mounted into a job. D2 the default is the usable processors (affinity list capped by the own cgroup's `cpu.max`) divided by 6, at least 1, and fewer when memory is short, by the lowest numeric `memory.max` or `memory.high` across the install's own cgroup and its ancestors, read as `bin/check` reads them; a configured `check_slots` wins; `0` turns the limit off. D3 the builder only wraps the project's configured check and test commands; no tool's settings change: check containers take a slot for their run, and in a build job a slot wrapper from the job image asks the orchestrator for a slot through a slot channel of that job only, which the orchestrator treats as untrusted input. Enforcement is the job's CPU quota: the base is today's fixed 2 CPUs, raised to the slot's share (the usable processors divided by `check_slots`, never below the base; 6 for 12 processors and 2 slots) only while the job holds a slot; memory stays at 4 GiB; with `check_slots` at 0 every job keeps 2 CPUs and 4 GiB, never raised; the cap counts jobs above the base, and when the share is not above the base it is a courtesy among wrapped checks. The wrapper is the job's own cooperation, not a boundary: a check outside it, or on a grant the job wrote itself, gets only the job's current quota. D4 a waiting check shows "waiting for a check slot, N running" on its card (N the jobs holding a slot), and the progress stop (T60) does not count a step waiting for a slot as a step without progress. This task designs the slot protocol and records it in `docs/architecture/`, with the wait ceiling, the hold ceiling, the channel's limits and the per-check memory figure of D2 (at no less than a job's 4 GiB). Invariants:
  - At most `check_slots` jobs run above the base at any moment, also when an orchestrator crashes or restarts and while a call to the container engine is still in flight.
  - A lost holder is lowered to the base and never granted a slot again.
  - A check that sizes itself sees the limits it will run under: the check command of a check container sizes itself from the slot's share, not from the base it started at.
  - A check whose quota was lowered while it ran, and that fails, is not the Developer's failure: it ends as stalled, and a wrapped check says in its output that its slot was lost.
  - A raise still in flight in the engine when the holder dies never leaves a job above the base after recovery.

  Requirements on the protocol:
  - Channel entries count only as regular files, opened without following links and without blocking, with a bounded count and bounded scans per job, in a channel of fixed size, so a job that floods its channel delays only itself.
  - The waiting order is measured by the orchestrator's own clock from when it first saw a job ask, never from anything the job wrote; a job holds at most one slot, shared by its wrapped commands at once; a killed wrapper's request stops counting without waiting for the hold ceiling.
  - Recovery acts on runs, not jobs, so a retry of the same job keeps its place and its grant.
  - A held job lock (the orphan sweep's, a retry's) earns no grant.
  - A normal release lowers the job to the base before it frees the lock.
- **Reference:** the measured table of the design section (two checks at once give the most checks per minute on 12 cores; five at once with tool defaults failed every Rector run).
- **Acceptance:** each invariant and each requirement above has a test, and each crash or race order the `docs/architecture/` record names has a forced-order test that fails on an implementation without its guard. With every slot held, the next check waits and starts as soon as one is freed; checks of two projects share the same slots; `0` admits every check at once; a configured value overrides the default. Quotas: with 12 usable processors and `check_slots` at 2, a build job has 2 CPUs without a slot and 6 with one, and the memory limit is 4 GiB in each case; with `check_slots` at 0 every job has 2 CPUs and 4 GiB and no quota is ever raised. The default is 2 for 12 usable processors, 1 for 4, and lower when the memory limit is short; `max` or an unreadable limit sets no cap; with the install's own `memory.max` at `max` and a parent cgroup's numeric limit, the parent's limit lowers the default. A build whose steps wait for a slot for more than the progress stop's number of steps is not stopped for lack of progress; a wait at its ceiling ends as stalled. The card shows "waiting for a check slot, N running" while a check waits.
- **Evidence:** the build logs of three parallel builds on the test repository with `check_slots` at 2: the third check's wait line and its start once a slot was freed.
- **Waits for:** T49, T51, T56, T60, T94. **Size:** L. **Labels:** `class:core`, `priority:high`, `plan:required`.

### T92 Flaky tests: rerun once, never a send-back, one urgent task each
- **Description:** The flaky-test rule of the design ([Reviews](design/05-architecture/07-reviews.md)). The `tests` gate of the protected check runner reruns only the failed tests, once, on the same checkout and in the same environment, in CI and, only where a project's pre-push command runs tests (Intakt's static gates run none), pre-push; when every failed test passes its rerun and every other gate passed, the gate passes and the check job is green, so the head is not sent back. Intakt never reruns a whole CI job and holds no head for a flaky test, and the red-CI rule (T57) and the merge rules (T62) stay unchanged. A test that fails its run and its rerun is a failure of that run under the usual rules, also when the ledger already knows it as flaky, and the hand-back names its flaky-test task. A skipped, incomplete, risky or missing result on the rerun counts as no pass, and a test the head adds or changes is never marked flaky. The orchestrator records each test's result in the ledger from the gate's per-test report (its JUnit reports) with an environment key (Intakt's constant for the pre-push check, a number Intakt assigns per distinct CI job and matrix leg) and the tree the run tested (for a pull request's CI run, the tree of the commit the run checked out, from the forge's run metadata, never from the report), and compares results only by that tree and key, never by the head's SHA alone or a label's text. A test is flaky when it failed and passed in one environment on one tree: it passed its rerun, or it failed on one head and passed on another head whose tested tree is identical; a result from another head counts toward detection and the task's count, never toward green. Every test the rule kept from a send-back is listed, by ledger number with its environment, in the head's review panel context. Plain code keeps one task per flaky test, labelled `priority:urgent` by Intakt (the eligibility label stays a person's), titled only by its ledger number, with the test's name, its latest failure output and the CI environment's label inside a redacted and scanned `<!-- external -->` block, fenced in every prompt (text from a CI report only when the workflow scan clears the head's runners; else the task, the status and the hand-over name the test and the environment by ledger number and say the text was withheld), the environment it flaked in and how often it flaked, updated and reopened rather than duplicated, asking for a fix proved by a forced-order test, never by repetition. Conventions, in addition to the ones above:

- A check that needs a tool beyond PHP and Composer is opt-in per project (off by default, so the simplest install stays simple) and on for Intakt's own repository. On Intakt it is a new gate of `bin/check` (gate work grows by addition: its own class, test file and fixtures, one appended registry entry, a protected change); for a project the check job runs it once the project opts in. The one exception is the running-application scan (T87): it needs a booted install, so it runs nightly against the install the journey suite boots, never in `bin/check` or the check job, and its findings reach the Security engineer's audit, not a head's status.
- A check result or scan report reaches a model session (a layer review, the monthly audit) only after Intakt has redacted the values of every credential mounted or injected into the job that produced it and run the secret scan over it; a report with a hit is withheld, the session gets only Intakt's note that it was withheld, and the dashboard shows it. Scan output can print what a response or an image exposes, so this runs before the model reads it, not only before a task is filed.
- A check that adds an external command updates `docs/architecture/requirements.md`, and each family updates `docs/architecture/quality-gates.md` and the guide [Why the AI can't wreck your project](guide/why-the-ai-cant-wreck-your-project.md#checking-the-security-of-what-is-built).
- Dependency advisories for Composer already exist (the `audit` gate, and T77 for protected changes); no task here repeats them.

### T84 Backend security checks
- **Description:** Taint analysis from untrusted input (request data, forge and model output, files a job hands back) to dangerous sinks (queries, process calls, file paths, outgoing URLs, unserialize); rules for authentication and session handling (every route under an access rule or explicitly public, session cookies `Secure`, `HttpOnly` and `SameSite`, CSRF on every state-changing form); a response built from untrusted text outside the template engine's escaping is refused.
- **Acceptance:** each rule has a fixture it refuses and a neighboring one it allows, written in the shapes the repository uses (`final readonly` services, controllers with attributes); a taint path through a helper method and through a constructor-injected service is found; the project switch is off by default and a project without it runs none of these checks.
- **Evidence:** the gate's output on a fixture project with one finding per rule, and on Intakt's own tree.
- **Waits for:** T51. **Size:** L. **Labels:** `class:tooling`, `priority:normal`, `plan:required`.

### T85 Frontend security checks
- **Description:** A test requests every route of the app and asserts a strict content security policy (no `unsafe-inline`, no `unsafe-eval`, scripts only from the app's own origin or by nonce) and the security headers (frame, content type, referrer, HSTS behind TLS); inline scripts and inline event handlers in templates, and Twig's `|raw`, are refused; frontend package advisories through `importmap:audit`.
- **Acceptance:** a route added without the headers fails the test; an inline script, an `onclick` attribute and `|raw` in a template each fail, a script tag with `src` and an escaped variable pass; a package with an advisory in a recorded `importmap:audit` answer fails, a clean answer passes.
- **Evidence:** the headers of the dashboard's pages from a running install, and the gate's output for a template with `|raw`.
- **Waits for:** T51. **Size:** M. **Labels:** `class:tooling`, `priority:normal`.

### T86 Infrastructure security checks
- **Description:** A Dockerfile lint; a vulnerability scan of the built image and of its configuration (Dockerfile, compose files, the reverse-proxy config); an assertion that every container runs as a user other than root with a read-only root file system and only declared writable volumes; checks of the TLS and reverse-proxy settings (TLS on outside localhost in the reverse-proxy config the repository ships, while an owner who publishes the dashboard on a trusted network without HTTPS takes the accepted risk of [Who can act](design/05-architecture/13-dashboard.md#who-can-act) and fails no check; current protocol versions only, forwarded headers trusted only from the proxy, no admin port published).
- **Acceptance:** each check has a failing fixture (a root `USER`, a writable root, a published admin port, an outdated TLS version, an image package with a recorded advisory) and the repository's own files pass; the scan runs against a recorded vulnerability database in tests.
- **Evidence:** the checks' output on the repository's `Dockerfile`, `compose.yaml` and `Caddyfile`; a scan against the live database `(owner provides)`.
- **Waits for:** T22, T51. **Size:** L. **Labels:** `class:tooling`, `priority:normal`, `plan:required`.

### T87 Nightly baseline scan of the running application
- **Description:** Every night, a baseline scan (passive, no attack payloads) runs against the install the journey suite boots, offline and on its own address only; its report is redacted and secret-scanned before it is kept (see the conventions above), its findings and their trend are kept for the Security engineer's monthly audit, and a new finding raises one notice.
- **Acceptance:** the scan reaches no address but the booted install; a page that drops a security header or sets a cookie without its flags is reported; a finding already reported is not reported again; a planted credential value in a scanned response is redacted in the kept report, and a report with a secret-scan hit is withheld; the scan stops what it started.
- **Evidence:** a scan report of a booted install with one planted finding.
- **Waits for:** T85. **Size:** M. **Labels:** `class:tooling`, `priority:normal`.

### T88 The Security engineer's layer reviews and monthly audit
- **Description:** Per layer (backend, frontend, infrastructure) a path trigger and a focus file, both protected paths, add the Security engineer as a blocking specialist with that layer's focus and the layer's check results, redacted, scanned and fenced; a monthly audit reads the scan trends and the threat model, each report redacted, scanned and fenced, and files each finding as a task with its text inside an `<!-- external -->` block, redacted and scanned, built only once a person with write access labels it. The audit runs from the month T88 lands, whatever checks have landed by then: it reads the trends of the checks that have results and reports each layer or check without results as not covered yet, never as clean. The threat model page lists both sessions.
- **Acceptance:** a change matching one layer gets that layer's review, one matching two gets one review with both focus files, one matching none gets none; a trigger never removes a reviewer; a check result holding a planted credential value reaches the review redacted, and one with a secret-scan hit is withheld with Intakt's note; with `MockPlatformFactory`, a scripted audit files one task per finding, a secret-scan hit files nothing, an audit with no results for a layer reports that layer as not covered yet, and a filed task is not built until labeled: a label from an account without write access leaves it unbuilt, one from an account with write access makes it eligible.
- **Evidence:** the panel chosen for three changes (one per layer) by a dry-run command, and a scripted audit's filed tasks on a temporary repository.
- **Waits for:** T8, T66. **Size:** L. **Labels:** `class:core`, `priority:normal`, `plan:required`.

## AI engineer (#865)

### T102 The AI engineer: token measures and experiments
- **Description:** Every model call records cached-read, fresh-input and output tokens, turns and its largest tool outputs (size metadata only, never their bodies); the dashboard shows tokens per merged task by role and model, cache-read share and context growth per turn. The AI engineer owns role prompts, focus files, skills, context limits and model routing as experiments with a holdout, kept only when the measure they target improves (tokens per merged task, or check runs or check CPU per merged task recorded outside the job; the check-run and check-CPU targets apply only once journey scoring is built, a separate task (T103), so until then this task's experiments target tokens per merged task only and it can be delivered without journey scoring) while tokens per merged task do not rise and send-backs, escaped defects and red main do not worsen, else reverted automatically; plain code keeps a change on its own only when every figure was recorded outside the job (tokens only for API calls reported to the Platform), and where an arm's tokens come from a subscription CLI's own log a change that would be kept is held for the owner; prompt and skill changes go through the approval of protected changes; a weekly session reads a deterministic report (the daily journey review is a separate part of the design), and findings outside its settings are filed as follow-ups written to pass triage, through the follow-up inbox, fenced, redacted and scanned, and a task filed from one is built only once a person with write access labels it. Panel experiments never shrink the core panel or drop a triggered specialist, every arm of a routing experiment still starts sensitive paths, an earlier failed attempt and a `model:strong` label on the strong tier, routing changes go through the approval of protected changes, and the role's rule replaces the plan option's 15% allowance. Design: [the AI engineer](design/05-architecture/06-budget-and-model-planner.md#the-ai-engineer-planned), [Dashboard](design/05-architecture/13-dashboard.md).
- **Acceptance:** a recorded call holds the token split and the sizes of the largest tool outputs, never their bodies; a change that cuts tokens but worsens a counter-metric is reverted by plain code; a candidate prompt, focus file or skill reaches no live job, the trial arm of an experiment included, and reaches main, only after protected approval of its exact text; a task filed from the session's finding carries no steering label and is not built until a person with write access labels it, and an edit of it by an account without write access makes it ineligible; a finding whose text holds an external marker, filed as a task or merged into an open one, stays inside its external block; the role cannot change review strictness, checks, approval rules or its own limits.
- **Evidence:** the dashboard's measures on a running install, and a scripted experiment kept and one reverted.
- **Waits for:** T60, T69. **Size:** L. **Labels:** `class:core`, `priority:normal`, `plan:required`.

### T103 Journey scoring: collector, scorecard, daily review and transcript store
- **Description:** The AI engineer's [journey scoring](design/05-architecture/06-budget-and-model-planner.md#journey-scoring). At each Developer and Code reviewer session's hand-back the orchestrator copies its transcript into a store no job can read or write, and a collector with no model, in a separate process without the orchestrator's credentials, from regular files only and under limits on size, time and memory, records that session's figures (check and test invocations by kind, repeated runs, the checks' CPU seconds, turns, tool output size: counts, durations and sizes, never transcript text), beside the figures the slot's process accounting records outside the job: every check and test process the job starts, by kind (the full suite, the fast check, a single gate, and a direct test runner or static analyser run), with its CPU seconds, and the runs and CPU of a review job's probe sandbox, attributed to that review. Only these independent figures, never transcript figures, count toward an experiment's decision, so moving repeated work from the check runner to a direct run cannot make an arm look cheaper. After every merge plain code totals the task's recorded figures and scores the journey (efficiency, procedure compliance, verbosity, rounds and send-backs) against the project's rolling median, posts the scorecard on the merged pull request as an essential forge call and shows it on the [dashboard](design/05-architecture/13-dashboard.md#journey-scorecards). A session without transcript figures is marked "transcript figures unavailable" with the reason, never scored as zero. A daily AI engineer session reads the worst-scoring journeys, the rubric and each transcript redacted, secret-scanned and fenced ([Threat model](design/05-architecture/14-threat-model.md#the-ai-engineers-session-planned)), and drafts proposals that run as T102's experiments, ended by merge count. A finding only a change outside the role's settings can fix (check runner caching, test suite speed) does not go through the follow-up inbox: plain code files it directly as a ready task of its own, with no steering label, its numbers (runs, CPU seconds, the merges they come from) written by plain code from the recorded figures and the session's text in an `<!-- external -->` block, redacted and secret-scanned; a scan hit files the numbers only. A transcript is deleted once the last review that could read it has run, and at the latest after the retention period counted from its hand-back. The settings (scorecard and its comment on, review depth daily, five journeys, 20 merged tasks per arm, 14 days of retention, the review's model) are project settings with those defaults, part of the role's limits, shown on the dashboard and applied at the next merge or review without a restart. Once this lands, T102's experiments may also target check runs and check CPU per merged task.
- **Acceptance:** a session's figures are recorded at its hand-back, so a transcript deleted before the merge leaves the scorecard complete; a transcript the collector cannot read within its limits marks that session "transcript figures unavailable" with the reason, and its values stay out of the rolling median; no figure, scorecard, comment or dashboard view holds transcript text; no job can read or write the store; a transcript is deleted after the last review that could read it, and at the end of the retention period whatever state the pull request is in; with the scorecard and the review both off no transcript is kept; with the review off no journey session runs and the scorecards still land; the scorecard comment is posted even while the forge's reserve holds routine reads back; with `MockPlatformFactory`, the daily review reads at most the configured number of worst journeys, a transcript holding a planted credential value reaches it redacted and one with a secret-scan hit is withheld, and every proposal names its transcript evidence; a finding outside the role's settings is filed directly as a task with the recorded numbers and no steering label, never through the follow-up inbox, and when its text has a secret-scan hit the task holds the numbers only; a direct test runner run, a static analyser run and a review's probe run are each counted, with their CPU seconds, in the arm's check runs and check CPU, so an arm that moves runs out of the check runner does not score cheaper; transcript figures never decide a start, a merge, a ceiling or an experiment's keep; the role cannot change these settings.
- **Evidence:** the scorecard of a scripted merge, as a comment on a fake forge and on the dashboard of a running install, and the proposal of a scripted daily review.
- **Waits for:** T102. **Size:** L. **Labels:** `class:core`, `priority:normal`, `plan:required`.

## Designer (#863)

The Designer shapes and reviews user-facing work, and only for a user-facing task of a project with a user interface ([Reviews](design/05-architecture/07-reviews.md#the-designer-planned)). Its scoring has three layers ([Designer scoring layers](design/05-architecture/15-designer-scoring.md)): objective checks that block, a rubric with evidence, and taste learned by blind pairwise comparison; the dashboard shows the scores, regressions and agreement ([Dashboard](design/05-architecture/13-dashboard.md#designer-scores)). One task per layer. Conventions, in addition to the ones above:

- The tools (axe-core, Lighthouse, a headless browser with its screenshot reader) are opt-in per project and run in the check environment, never in the Designer's session; a check is a gate under the Product security conventions (its own class, test file and fixtures, one appended registry entry, a protected change), and an external command updates `docs/architecture/requirements.md`. Without a tool, what needs it is "not run", never passed, except for the screenshot reader, which the scan below needs: with the reader off, every screenshot is withheld and a build that adds or changes a committed reference fails the hand-back, never "not run".
- Every model input these tasks add is scanned against the [revision's credential set](design/05-architecture/15-designer-scoring.md#the-credential-set-of-a-revision) before it leaves and fenced before the Designer reads it, and the [Designer's session](design/05-architecture/14-threat-model.md#the-designers-session-planned) in the threat model lists it. A value of the set that cannot be read counts as a hit. The scan depends on the input:
  - **Check results** are text: every value in the set is redacted and the secret scan runs; a result with a hit is withheld whole.
  - **Screenshots and committed references** are images, so nothing is redacted in them: the [screenshot reader](design/05-architecture/15-designer-scoring.md#the-three-scans), a process without network or credentials, extracts their text and decodes any machine-readable code (a QR code or barcode), and that text is matched against every value in the set and secret-scanned. A hit, or an image the reader could not read within its limits, withholds the whole image (a committed reference fails the hand-back instead); the Designer gets Intakt's note that it was withheld and the dashboard shows the gap.

### T99 The Designer's objective checks
- **Description:** Layer 1 of the [scoring](design/05-architecture/15-designer-scoring.md#layer-1-objective-checks-that-block): accessibility (no serious or critical axe-core violation, passing contrast), layout at phone, tablet and desktop width, design tokens only, the project's Lighthouse thresholds, and screenshots against main's references under the mechanical reference rule; the page list and thresholds live in protected files; screenshots and committed references pass the screenshot reader and the scan before they leave.

- **Waits for:** T51. **Size:** L. **Labels:** `class:tooling`, `priority:normal`, `plan:required`.

### T100 The Designer's rubric and score history
- **Description:** Layer 2: the Designer scores each screen a change touches against the fixed heuristics, every score citing a screenshot region; a low score is a review finding, never a gate; scores are kept per screen over time and a drop shows as a regression on the dashboard, with gaps ("not run", withheld, no browser) shown as gaps.
- **Acceptance:** with `MockPlatformFactory`, a score without evidence is an invalid answer; a low score reaches the change as a finding and fails no check; a lower score than the screen's previous one shows as a regression, and a drop to a score that is not low raises no finding; without the browser the review records "rubric scores unavailable: no browser" and the history shows a gap, never a zero.
- **Evidence:** a scripted review's scores and one regression on the dashboard of a running install.
- **Waits for:** T99, T58. **Size:** L. **Labels:** `class:core`, `priority:normal`, `plan:required`.

### T101 The Designer's taste ladder and agreement
- **Description:** Layer 3: for a visible design choice the Designer writes typed variants, isolated build jobs implement each as a kept, unpushed commit, render jobs screenshot them, and the Designer ranks them in pairs; the owner votes blind on a sample in an order plain code picks at random; agreement is measured and shown on the dashboard, and choices with character go to the owner as options while it is low.
- **Acceptance:** a variant build and a render job get no project credential and no external dependency's address; a variant failing the hand-back checks is dropped and shown; the pair order does not follow the Designer's preference; agreement with no votes or without the browser counts as low and shows as not measured; fewer choices are asked as agreement rises.
- **Evidence:** a scripted ladder with owner votes and the agreement shown on a running install.
- **Waits for:** T100. **Size:** L. **Labels:** `class:core`, `priority:normal`, `plan:required`.
