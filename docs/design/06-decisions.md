# Decisions

1. License: MIT.
2. Orchestrator: PHP and Symfony (see Platform).
3. Several projects per install in v1: new projects through a spec and a plan, existing projects through their tickets or issues; a fixed weekly budget share per project, editable on the dashboard, with unused share flowing to the others.
4. Job images: the project's devcontainer or Dockerfile, a generated one, or an owner-supplied prebuilt image.
5. Default protected paths for projects without gates: strict (CI definitions, hook configuration, the check command, agent instructions, dependency manifests, Intakt's own project file).
6. Bundled dependencies that are Intakt projects: tested against their main by default, switchable to their last release per dependency.
7. Plan approval: adaptive (on after a rejected change, off after five clean merges), with size as the starting default.
8. Overlap forecasts: measured (forecast against actual overlap is logged); serialization only at high forecast confidence, only among tasks of one milestone and priority not started yet, never for work on an open pull request (see Choosing work, step 6).
9. Commit signing under the App: merges are created through the forge API, so they are verified as the App and the owner does not vouch for each merge; branch protection can require verified commits.
10. Forges and trackers in v1: GitHub and Gitea; Jira is the first tracker plugin after v1.
11. Spec and plan live in the repository (`docs/spec.md`, `docs/plan.md`), versioned and reviewed; the plan's tasks are created as issues.
12. Vendor accounts: subscriptions, personal and company API keys and cloud sessions, equally configurable per vendor, with priorities, roles and paid overflow after the subscriptions, whose cap is optional (2026-11-04; see Budget and model planner).
13. One owner per install in v1; collaborators work through the forge's own permissions.
14. Distribution: a Docker image (Intakt is an application, not a library).
15. The name stays Intakt.
16. PHP 8.5 and its features (decided 2026-10-26, replacing 8.4): minimum 8.5.12, the release that fixes PHP2Shell (CVE-2026-109618 and CVE-2026-109619, unauthenticated remote code execution). CI refuses an older runtime.
17. FrankenPHP worker mode (decided 2026-10-26): the dashboard, the local API and the MCP server run in FrankenPHP worker mode with its built-in Mercure hub for live updates; the Messenger consumers and the Scheduler run as separate long-running processes from the same image. Symfony Runtime's own `FrankenPhpWorkerRunner` (symfony/runtime 7.4 and later, detected automatically; Intakt runs 8.2) serves worker mode, so no extra runtime package is needed. This deliberately runs Symfony AI in a long-lived process, to find leaks and state bugs in the beta while they can still be fixed.
18. Intakt maintains itself (decided 2026-10-28; formerly "the orchestrator is the maintainer"): the Maintainer decides every hand-over it can, plain code approves protected changes on the spot (mechanical checks, then the Security engineer's security review and penetration test), the orchestrator holds tasks that wait on something outside their change and releases them on its own, and the owner is asked only for a decision Intakt cannot make, for a change a Code reviewer classes as loosening, and for the two hard floors: the approval system itself, and secrets and permissions (see the Maintainer's page and Merge).
19. Recurring blocking findings teach the Developer (decided 2026-10-31): a P1 or P2 finding that was fixed feeds the list of recurring blocking findings in the Developer's briefing, so the same kind of finding is caught before the push (see Shared project memory and Reviews).
20. A task whose review cycles run out is re-planned (decided 2026-10-31): the Maintainer splits it, rewrites its acceptance or retries it once on the strong tier instead of handing it to the owner, who is asked only for a product decision, Code reviewers who disagree on what the task requires, a P1 on security, secrets or data integrity, or a failed strong-tier retry that cannot be split (see The Maintainer).
21. Rework is the main cost to cut (decided 2026-11-02): the Developer checks the change against the Definition of Done before it pushes (the project's fast checks, the task's Evidence list, the docs the change touches) and fixes a miss in the same build; a finding kind that recurs on several changes is proposed as a check (a gate rule, a docs-impact check or a Developer checklist line), built only once a person labels it; the dashboard shows tokens per merged change and the rework share per project (see Principles, Overview, Reviews and Dashboard).
22. A new gate rule lands at once (decided 2026-11-06): a rule whose cleanup needs more than one build lands with a shrink-only ratchet list of today's violations, one checked-in file per rule outside `config/gates/` (a PHPStan baseline file for a PHPStan rule), and any new violation fails at once; the list's cleanup issue has the rule's milestone and priority, and the rule's umbrella closes only when the list is empty and deleted. A cleanup that fits one build lands with the rule and no list (see Constraints and Choosing work).
23. The team (decided 2026-11-13): the model roles carry traditional team titles users recognize, seven of them plus the Product owner (the person; decision 28 later adds the opt-in Test engineer, and decision 31 the Technical writer): Tech lead (formerly the sizer, triage and the planner), Designer (new), Developer (formerly the builder), Code reviewers (formerly the review panel, with the judge as their verdict step), Security engineer (new; formerly the gatekeeper's security reviewer and attacker, now the penetration tester), AI engineer (new) and Maintainer (formerly the maintainer agent). Machinery keeps technical names (orchestrator, scheduler, watchdog, checks, dashboard), and the approval of protected changes is plain code. The Definitions of Ready and Done are stated once, in Intent, and every readiness and self-check rule points to them (see Intent and Overview).
24. Work is picked milestone by milestone (decided 2026-11-18, replacing priority first): tasks not started yet go `urgent` first, then by the milestone's due date (none last), then by priority, then the critical path and the class order, then by the number of tasks waiting on it and the issue number (decision 26); work on open pull requests goes before them, `urgent` tasks included (decision 32); a skip for files in flight stays within the first candidate's milestone, priority and class; the review queue keeps priority first (see Choosing work, steps 5 and 6).
25. Security across all layers (decided 2026-11-04): the Security engineer covers the security of the product being built, across infrastructure, backend and frontend, with checks first (opt-in per project where a tool is needed, on for Intakt's own repository) and the role for what checks cannot judge: reviews per layer triggered by paths, each with its own focus file, and a monthly audit. For protected changes it supplies the security review and the penetration test; the approval stays plain code with the owner's two floors (see Threat model, Reviews and Merge).
26. Dependencies and follow-ups in the queue (decided 2026-11-18): within one priority and milestone, the task that more queued tasks wait on (the whole chain counted) goes before the issue number, so the order is `urgent`, milestone due date, priority, critical path and class, waiting-task count, issue number; the review queue applies the same count within one priority; a follow-up from a non-blocking finding joins, by default, the next open milestone after its original's (it keeps the original's when none is later), while one carrying a blocking finding a reviewer raised as a follow-up item and split parts keep their original's, and it names the original's milestone (see Choosing work, step 5).
27. Coding rules live in gates (decided 2026-11-04): a coding guideline a tool can check is a gate rule whose failure message explains it, and prose (`AGENTS.md`, How code reads) keeps only judgement; `AGENTS.md` lists each enforced rule as one line naming its gate; a recurring checkable finding kind becomes a proposed check under decision 21, never new prose; reviewers do not send a change back for a rule a gate enforces and passes, and a case the gate misses gets a gate issue (see Principles, Constraints and Reviews).
28. The Test engineer (decided 2026-11-10, #1297): an opt-in role that joins the team of decision 23 and owns the test suite as a whole, so the suite stays lean and fast without losing what it proves; see [the Test engineer](05-architecture/07-reviews.md#the-test-engineer-planned).
29. Background jobs on Health (decided 2026-11-12, #1532): every job Intakt runs on a schedule declares its purpose, schedule, owning role and expected token cost per run, and is shown as a row of the Health page with its last and next run, broken after repeated failures, and switched off or on and run now as owner controls under the dashboard's `Host` and CSRF rules, never through a door Intakt gives agents and jobs; see [Background jobs](05-architecture/13-dashboard.md#background-jobs).
30. Priority aging (decided 2026-11-18, #1733): ready issues and open pull requests gain one priority band per `aging_days` of waiting (per project, default 5, 0 off), `low` to `normal` to `high` and never to `urgent`, counted from when the runner first saw the issue `ready` (its own state, no extra forge calls; losing `ready` resets it, except for a task whose open pull request is held in its place, decision 32) or a pull request's current head first entered the queue (a new head starts again); aging never moves the order of tasks not started yet across milestones (the rework order of open pull requests and the review queue have no milestone grouping, so there an aged pull request passes lower bands of any milestone, never an `urgent` one), labels stay as set and the dashboard shows the effective priority and why; an issue an open pull request waits on ranks at least at that pull request's effective priority, capped at `high`, inside its own milestone; ready issues with no milestone are listed for the owner, never given one automatically (see Choosing work, step 5, and Dashboard).
31. The Technical writer (decided 2026-11-22, #3433): a role that joins the team of decision 23 and owns the docs people read; triggered like the Designer by paths and labels, it reviews the docs part of a change for its audience and can send it back like a Code reviewer, proposes the user guide's structure and the docs gate's limits for the owner to decide, never judges whether docs are true to the code and never edits code; see [the Technical writer](05-architecture/07-reviews.md#the-technical-writer-planned).
32. Finish before start (decided 2026-11-13, #2709; it replaces the part of decision 24 that let `urgent` tasks go before open pull requests): an approved head goes first in every lane, oldest approval first, for whatever it still needs before it merges; the build lane then takes `urgent` reworks and continuations, the other work on open pull requests by priority, `urgent` tasks not started yet, and the other ready tasks by milestone and priority; taking `ready` off a task whose pull request is open holds that pull request in its place, with its reviews and its age, until `ready` comes back (see Choosing work, step 5, and Merge).
33. Updates let running jobs finish on their version (decided 2026-11-18, issue #1092, replacing the drain of each switching slot): a job runs from the image it started with, recorded on the job, to its end; new jobs take the new version, no slot drains in a normal update; the orchestrator restarts once, at the cut-over, and picks the running jobs up again, reading on return what happened during the restart; the job contract is versioned and a result is accepted across exactly one update step, an older job being redone, never guessed at; a release whose notes declare a drain still drains and says why; a failed update rolls the orchestrator back on the same data inside a declared rollback window, leaves jobs on the older version alone and redoes the failed version's jobs; the board shows the jobs on an older version until none are left (D1 to D7 in [Setup](05-architecture/11-setup.md#updates), on top of the side-by-side, canary-first flow of #968; see Principles, Dashboard and the Threat model).
