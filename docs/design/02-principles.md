# Principles

Kept:
- **Lanes.** Review workers (as many as the configuration allows) and N build slots run independently and chain into each other, instead of one round at a time; merges stay one at a time ([Reviews](05-architecture/07-reviews.md)).
- **Ledger.** An append-only event log (starts, reserves, ends, merges) from which budget, history and recovery are derived. The one exception is the compose demo's replay project: the rows a recording played into it can be removed with it, because they record no work done on this install.
- **Code reviewers from different vendors**, with a substitute when one is out of budget and a later catch-up review.
- **Kept commits.** A build that fails the pre-push check keeps its commits for the next cycle instead of starting over.
- **Pre-push check in a clean place.** The Developer's own run of the checks is never trusted. The clean place may start from a dependency install Intakt's own process saved for the same lock files and platform, never from anything the Developer installed.
- **Evidence by construction.** Races are proven with forced-order tests, not repeated runs.

Changed:
- **No prose parsing for decisions.** A loop that parses reviewer prose for findings has to harden that parser again and again (fences, quotes, case, list items, Unicode line breaks). Intakt requires a structured verdict (typed objects filled through structured output and validated) and treats anything else as a failed review, which never approves (see [Reviews](05-architecture/07-reviews.md)). One bounded exception: the `codex` provider cannot hold an answer to a schema, and `claude_code` holds it only when its CLI returns a structured output, so for them exactly one plain top-level `json` block in the answer is read as the verdict, an answer that is bare JSON (surrounding whitespace aside) is read as it is, and anything else (prose with no such block, a second `json` fence opening anywhere, a block in another form or nested in another fence) is still a failed review. That block is then mapped and validated like any verdict, and an approval from these providers still counts only when the review had the review-server access and a confirmed read through it.
- **Isolation by container, not by home-directory hygiene.** Developer agents that share a Unix user and a long-lived worktree need every piece of state reset by hand, and every reset (dotfiles, CLAUDE.md, git config, commondir, index, symrefs, Composer cache) was a new denylist item found by review. Intakt gives every job a fresh container from a read-only image, with the repo cloned fresh from the orchestrator's bare mirror. Nothing a job writes survives it except the bundle it hands back.
- **Measured budgets, not estimated ones.** A ledger estimate refused a second Developer for hours while the vendor measured 4% use. Intakt asks the vendor (usage probe or API billing) first and uses its own estimates only as a fallback.
- **One process owns state.** Host scripts, container scripts and timers that all touch pause, drain and locks race each other. In Intakt, only the orchestrator writes state; the CLI and dashboard talk to it.
- **A hand-over never stops the loop.** A loop that halted every lane, reviews included, when a hand-over left nothing else to build, left the pull request that resolved it unreviewed for hours. In Intakt a hand-over parks one task; only real faults (a watchdog finding, repeated failures, a crash) stop the loop.
- **Queue state lives in the database, not in labels.** With the queue kept in forge labels, a split that labeled parts `blocked` without `ready` left 18 issues that nothing would ever build. Intakt's queue is a table; forge labels only steer it (as input from people with write access) or mirror it for people (see "Labels").
- **No flat budget per round.** One fixed token figure stopped productive large builds and let stuck small ones burn their allowance. Intakt sizes the allowance from the task and stops on lack of progress (see the [model planner](05-architecture/06-budget-and-model-planner.md)).
- **Updates fail loud and safe.** An update failed four times on a step that behaved differently in its drained form, left the loop stopped for hours and alerted only after the third failure. Intakt updates roll back on a failure (one case cannot: after a release that declared stored state the old version cannot read has resumed the lanes, a failure pauses them until a newer release), alert on the first, and run the same way they were tested. A rollback swaps the image only and keeps everything recorded since the update: each release names the oldest release it may be installed from directly and is proved, before it is published, to roll back to every release from there on, on data it wrote itself, and an older install takes the releases in between first. A rollback leaves jobs on the older version alone and stops and redoes the jobs on the failed version ([Updates](05-architecture/11-setup.md#updates)).
- **An update does not stop the work in progress.** The earlier loop drained for every update: four self-updates in one day each drained every lane and ran the project's full check twice, pausing builds and reviews for 30 to 80 minutes per update, and one whose check failed on a test that failed the same way on the old version kept everything paused until the next update. With builds of up to half an hour, a drain stops new work until the longest job ends, so owners would update less often than they should. Intakt checks a new version beside the running one, compares its result failure by failure with the running version's on the same commit (a failure both show is the project's, reported but not blocking), and starts it on one build slot first. No slot waits: a running job finishes on the image it started with (recorded on the job), new jobs take the new version, and the orchestrator is away for one restart, after which it picks up the running jobs and reads what happened meanwhile. The job contract is versioned, and a result is accepted across exactly one update step; a job too old for the new orchestrator is redone, never guessed at. A drain is only for a release that declares it, with the reason (it changes the job contract beyond one step, how jobs are isolated, or stored state the old version cannot read), and a security release stops the jobs it lists. The board shows which jobs run on an older version until none are left ([Updates](05-architecture/11-setup.md#updates)).
- **One loop change at a time.** Five fixes to the loop itself shipped in one day, two went live together, and a deploy mode that had never run end to end stopped the loop. Intakt rolls out its own changes one version at a time and checks each in production (one build slot first, a scripted post-update check, then the next jobs' outcomes) before the next; non-urgent releases wait for the owner's update windows, where the newest one is installed.
- **Rework is the cost to cut.** Over 190 issues and 128M tokens, rework (build cycles after a send-back, with their re-reviews) took 51% of all tokens, first builds 40% and first reviews 9%; 87 issues needed rework and 33 of them three or four cycles. One rework cycle costs about four reviews. In a sample of 300 blocking findings, docs disagreeing with code were 31%, edge and failure paths 24%, missing or weak tests and evidence 15%, a missed requirement 10%, project rules 9% and security 9%, and about 29% (docs, tests and evidence, project rules) could have been caught by a deterministic check or a checklist the Developer runs itself. Intakt therefore moves that part in front of the Code reviewers: the Developer checks the change against the [Definition of Done](01-intent.md#definition-of-done) before it pushes ([Overview](05-architecture/01-overview.md)), and finding kinds that recur become checks ([Reviews](05-architecture/07-reviews.md)). This matters most for an owner with one account, where every rework cycle is taken from new work.
- **Quality gates generate their own work.** Most of a busy day's rejected pull requests and follow-up issues came from the project's own gates and gate edge cases, and every new gate made every later build heavier. Intakt treats gate and tooling work as lower priority than the project's own core, and a new gate needs an escaped defect it would have caught. The one exception is the product's security checks per layer, which the owner decided on 2026-11-04 ([decision 25](06-decisions.md)); a check family beyond those still needs its escaped defect.
- **Protected changes are decided at once.** About a quarter of the merged pull requests (32 of 120) waited for the owner, several only for edited comments or an official Symfony package, and those waits were about a fifth of all waiting. Intakt approves a protected change on the spot when the mechanical checks, the Security engineer's security review and penetration test clear it, and otherwise asks the owner with the reason; only changes to the approval system itself and to secrets and permissions always go to the owner. A request never resolves itself (no timer, no veto window), and no model lowers a floor (see [Merge](05-architecture/08-merge.md#approving-protected-changes)).
- **The bot is not the owner.** A loop that posts as the owner's own account cannot tell "approved by the owner" from its own comments. Intakt acts as its own forge identity.
- **Changing identity is one step.** Moving a running loop from the owner's token to its own App took a drain, a recorded switch moment, a config change, a deploy and two host-side patches in one window, and the update resumed the loop on its own before the host side was patched, so the dependent host jobs had to be paused by hand. Intakt has its own identity from setup, and a later change of identity (another App, a rotated key) is one orchestrator command: it drains, records the moment (what the old identity did before it stays the loop's own), switches every component together and resumes only after all of them check out.
- **Setup is tested by running it.** An App creation script failed on its first real use: the program read its input from a stream that was already its own source, and the only test checked the script's text for that very line. Intakt's setup steps have end-to-end tests against a fake forge, and text checks never stand in for running the step.
- **Tests do not read the deployed config.** When a shipped config switched to the App, eight tests broke because they built on it and assumed the old identity. Intakt's test fixtures start from the built-in defaults; one test pins the shipped values. Tests do not write live state either: the suite refuses any path of a running install, because a test run beside a live loop once deleted a file the review in flight needed.
- **Add, don't move, on upgrade.** Moving existing state into a new layout during an update made the update and its rollback the riskiest code in the release: writers outside the program kept using the old paths, a rollback stopped half-way, and every outside reader had to change at the same moment. Intakt adds new state beside the old instead of moving it, and an older version ignores what it does not know, so rolling back is redeploying. The same holds for values: a release writes a new value (a job status, an enum value, a stored-class shape, a message type) only once every release it may roll back to can read it, or when those releases read an unknown value through a fallback they already have; otherwise the release declares a drain ([Updates](05-architecture/11-setup.md#updates)).
- **A wait has a ceiling, and a stalled wait is repaired by plain code.** A review step waited about 50 minutes for CI that could never start (the pull request conflicted with main, and the forge runs no pull request workflow then). It held the review lane the whole time: six heads waited and both build slots stopped at the review cap. No check noticed, because the progress stop covered builds only and the stuck notice covered parked work only after two days; a person found it. In Intakt every waiting phase ends after a set time (see [Merge](05-architecture/08-merge.md#waiting-for-ci)), and a wait at its ceiling is classified from what Intakt can read, without a model: a conflict with main takes the conflict path, no CI run takes the missed-CI path, and a run queued for lack of a runner parks the head (it holds no lane) and shows runner capacity on the dashboard. Anything else ends the job as stalled, the task goes back to its queue with its place kept, and the lane is free for the next one. The owner hears only about a repair that keeps failing: the same task stalling three times in a row raises one notice naming the phase and what was read. Every stall and its class is in the ledger, so a recurring class can get its own repair.
- **Coding rules live in gates, prose holds judgement (decided 2026-11-04).** A rule that lives only in prose is applied by reviewers after the build, which costs a rework cycle; a gate fails before the push. So a coding guideline a tool can check is a gate rule, and its failure message explains the rule well enough to fix the finding without `AGENTS.md`. Prose is for judgement only: SOLID, DRY, no overengineering, naming a tool cannot judge, and comments that give a reason ([How code reads](#how-code-reads)). `AGENTS.md` lists each enforced rule as one line naming its gate. A recurring finding kind that a tool can check becomes a proposed check ([decision 21](06-decisions.md), [Reviews](05-architecture/07-reviews.md)), never a new line of prose in `AGENTS.md`.
- **Intakt repairs its own known failure states.** Failures the loop had seen before and could have fixed by itself still waited for the owner: a CI run cancelled by a newer push was read as red CI and handed a pull request over although nothing had failed. A known failure state with a safe mechanical repair is repaired by Intakt itself and recorded in the ledger: an orphaned job container, a stale lock, a forge write whose result can be read back, a CI run cancelled with nothing to replace it. The owner gets a notice only when no safe repair exists, or when the same repair failed three times in a row, so a repair that does not hold never loops unseen. A repair never decides anything that needs the owner and never merges.

## How code reads

These hold for Intakt's own code, and reviewers check them on every change (see [Reviews](05-architecture/07-reviews.md)). They are the judgement half of the code rules; what a tool can check is a gate rule instead (see "Coding rules live in gates" above).

- **Storytelling.** A use case's entry method reads as a short story of named steps in domain words, top-down. The public method comes first, then its helpers in the order they are called. A newcomer can follow a flow from its door (command, controller, handler, MCP tool) to the result without jumping through layers of indirection.
- **SOLID, pragmatically.** One reason to change per class. Depend on a module's `Contract`, not its insides. An interface exists only at a module boundary or when a second implementation exists today, never for a single implementation inside a module. No factories, strategies, abstract base classes or generic frameworks until a second real case needs them.
- **DRY without speculation.** Duplicated knowledge (a rule, a format, a decision) has one home. Similar-looking code is extracted on the third occurrence, not the second, and never into a shared "utils".
- **No overengineering.** A module gets its `Domain/`, `UseCase/` and `Infrastructure/` folders only when they hold code. No config option, column, parameter or extension point without a caller today. Plain PHP and Symfony features before custom abstractions.
- **Comments say why, never what.** Names and small methods carry the meaning. A comment may only give a reason (a constraint, a trade-off, a link to an upstream bug) on one line; no commented-out code, no TODOs (except `TODO(#<issue>): <reason>`, naming an open issue). Docblocks hold types only (`@param`, `@return`, `@var`, `@template`, `@throws`). The `comments` gate checks this with a heuristic (a line comment must contain a reason word such as *because*, *so*, *otherwise* or *must*, or a link; a docblock with prose fails); it nudges, it does not prove, and reviewers are the backstop.
