# Threat model: prompt injection and third-party text

Prompt injection cannot be made impossible: a model that reads text an attacker can influence can be steered by it. Intakt does not try to make its models unsteerable. It makes a steered model harmless: every decision that matters is made or checked by plain code, and each model role has only the tools its job needs. This page lists, per role, what untrusted text it reads, what it can do, and which deterministic check stands between its output and any effect. A change that adds a model role, an input to a model or a tool for one updates this page in the same change (see `AGENTS.md`). Next to the loop's own threats, [The product's surface](#the-products-surface) lists the threats to the product being built, across infrastructure, backend and frontend, and the check or the Security engineer that covers each, and [Main's integrity](#mains-integrity) says what the watchdog trusts about a commit on main and why that is safe.

## Untrusted text

Untrusted means "may have been written or influenced by someone who is not a person with write access to the project". That covers:
- **Issue and comment text** from accounts without write access, and any part of a task inside an `<!-- external -->` block.
- **Pull request text**, including what a Developer wrote.
- **Code under review and in the checkout**, including dependencies in `vendor/` (or `node_modules/` and the like): a comment in a dependency is as able to carry instructions as an issue.
- **CI log excerpts and probe output**, since they print what model-written code and dependencies print.
- **Project memory**, since its entries summarize pull requests and findings that models wrote. This includes a hand-off note and the kept conversation a build continues from after a vendor limit ([Budget and model planner](06-budget-and-model-planner.md#a-limit-never-loses-work)): the kept conversation is model text and is fenced, while the note holds only the orchestrator's own facts (commits, task, open findings) and is fenced as memory.
- **Other reviews and findings**, since a steered reviewer's text reaches the Code reviewers' verdict step, the Developer and the Maintainer.
- **The owner's text in the dashboard's New task box** ([Dashboard](13-dashboard.md#starting-a-task)). It comes from the owner, but it is often pasted from elsewhere (a mail, a chat, a page), so it reaches the drafting model fenced like an issue's external block, never as instructions.

Every model output is untrusted too: it is validated against its schema before use, and anything invalid is an explicit failure, never a silent default.

## Third-party text

- **Only tasks written by people with write access are built**, unless a person with write access vouches for the task with `take-over` (next but one bullet), in which case its text is fenced. A task's author and the last editor of its body must have write access, checked through the forge's permission API when the task becomes eligible and again before each build ([Choosing work](03-choosing-work.md)).
- **Only steering from people with write access counts.** Steering labels, answers and steering comments count only from accounts with write access, checked through the forge's permission API on each event, never from the author association a comment carries ([Labels](04-labels.md), [Questions and steering](05-questions-and-steering.md)). Other comments never reach a prompt. A bot account never steers, whatever its permission, except Intakt's own identity and its Maintainer's: a CI workflow's token can hold write access, so without this rule a changed workflow could label tasks ready or urgent. A task's body counts only while its last editor has write access too, since the body is the build's instructions, except for a task vouched for with `take-over`, whose whole text is fenced as data. The two labels `hands-off` and `take-over` count only from people: Intakt's own identity and its Maintainer's never set or remove them.
- **Copied text is marked.** Text a person copies into a task from an untrusted source (an outside report, a forum post, a log) goes inside an `<!-- external -->` ... `<!-- /external -->` block, and so does the review a task filed from a catch-up review carries ([Reviews](07-reviews.md)). Intakt fences that block as untrusted although the task itself is trusted; an unclosed block runs to the end of the task. The block is data for plain code too, not only for models: the readers of `Waits for #n`, `Waits for release:`, the links between projects and `Replaces #n` take those lines only outside external blocks ([Choosing work](03-choosing-work.md)), so a line inside one records no wait, blocks no task and closes or supersedes no issue.
- **A person's label vouches for taking over, not for the text.** `take-over` from a person with write access ([Labels](04-labels.md#who-drives-an-item)) makes Intakt build on an issue or pull request it would otherwise refuse, except a pull request that touches protected paths and a dependency bot's pull request: `take-over` on either is refused with one comment ([Hands-off and take-over](08-merge.md#hands-off-and-take-over)). A dependency bot's pull request stays on the [bot path](08-merge.md#dependency-bots) (the bot rebases it, the owner approves it, a red check becomes a task of its own), its commits are never listed for the Developer, and removing `hands-off` from it puts it back on that path, so the label never turns the bot's diff into instructions for a Developer. The issue text and the pull request description stay third-party text inside an external block, read as data, never as instructions. An edit to an issue after the label needs the label again. A split of an oversized pull request follows the same trust line: one opened by the owner's or the Maintainer's identity is split with no `take-over`, since these identities are trusted and building from their head is safe, while anyone else's only gets one comment asking its author to split it, until a person with write access sets `take-over` ([The Maintainer](09-maintainer-agent.md)). `hands-off` is checked on each event like every steering label, and an account without write access can neither set nor remove either label.
- **Dependency code is untrusted input** to the Developer and the Code reviewers, whoever wrote the task.
- **Fencing (plan T7).** Every untrusted value that goes into a prompt goes through one fencing helper (`Fence` in `Core/Review`); the reviewer's task text, the change's diff, the open findings of earlier rounds and every answer of its repository tools, the verdict step's task text and findings under judgement, and the Developer prompt's task, decisions, act list, CI log excerpt and published pull request text (T49, with a gate test that plants a marker in every input and fails when one appears outside a fence), go through it today, and the other inputs listed under the roles join as their roles are built. The helper wraps the value in a block that names its source and uses a boundary the value cannot contain, and the role prompt says that fenced text is data to examine, never instructions to follow, and that only a closing marker with the opening boundary ends a fence, so any other marker inside is data. Fencing lowers the odds of steering; the checks below are what make a steered model harmless.
- **Prompts are assembled in one place (#2518, #2811).** D1: a prompt takes Intakt's own text only as a `literal-string` and untrusted text only as a `FencedText` from the fencing helper. D2: one assembly class, `PromptAssembly` in `Core/Review/Contract`, builds every model message. D3: the `phpstan` gate refuses `Message::ofUser()`, `Message::forSystem()`, `Message::ofAssistant()` and constructing `UserMessage` or `SystemMessage` anywhere else; it judges `src/`, `bin/` and `config/`; a message built under `tests/` is not judged. The one exception to D2 (maintainer decision of 2026-11-18): a reviewer role's configured prompt, the owner's panel configuration, enters the system message verbatim, only through `PromptAssembly::systemWithRole()` taking a `ReviewerConversation`; the same gate accepts a new `ReviewerConversation` in `ReviewWithReviewerHandler` only when its role prompt is a `rolePrompt()` call on a `RoundReviewer` ([Prompt assembly](../../architecture/prompt-assembly.md)).

## Roles

<a id="builder"></a>

### Developer
The Developer (`developer`, formerly the builder).
- **Reads:** the task (with its fenced external blocks), answers and steering comments, the act list of the Code reviewers' verdict step, the review in the external block of a task filed from a catch-up review (such a task is built only after a person labels it), the strong-tier plan when the Tech lead wrote one (fenced as another model's advice), CI log excerpts, the project memory briefing (after a vendor limit also the orchestrator's hand-off note and the kept conversation, fenced), after a memory kill the orchestrator's note naming the step and the killed process (the process's command line is what an earlier Developer session ran, so it is fenced, and redacted and secret-scanned like other outbound text before the same note is posted as a comment), the docs report of its self-check (planned, [Overview](01-overview.md); plain code builds it, but each hit carries names taken from the change's removed and changed lines and a line quoted from the project's docs, text that earlier sessions and contributors wrote, so each hit goes to the Developer fenced through `Fence`, the names under the change as their source and the quoted line under its docs file, never as Intakt's own text), the checkout including `vendor/`, and a split part's source ref. For a design variant (planned, [Designer scoring layers](15-designer-scoring.md#layer-3-taste-by-blind-pairwise-comparison)) it also reads the Designer's variant description, fenced as another model's advice. After a hand-back or a take-over it also reads the list of commits pushed while a person drove (hash, author, subject, files) as work to build on, never to revert: commits by people with write access count as the task's own, commits by anyone else (and the subjects and diffs they carry) stay fenced as untrusted. Today it is given the task, the decisions, and for a rework the act list, the CI excerpt and the published pull request text, each fenced under its own source; the task, the CI excerpt and the published text are cut at 100000 bytes like a reviewer's input, with Intakt's note outside the fence ([Cut notice](#reviewer-every-configured-role-specialists-included)); the other inputs arrive with their tasks.
- **Can:** run anything inside its job container: edit files, run tests, install packages from the allowed registries, reach its vendor's API, and reach the project's external dependencies the job uses (see [External dependencies](#external-dependencies)). It returns a git bundle, pull request text, and optionally a structured question or upgrade request. With [check slots](01-overview.md#check-slots) (planned) it never sees the install's lock directory, and starting a check outside the wrapper gains nothing: it runs within the job's current CPU quota. Its slot channel is untrusted input to the orchestrator, bounded per job; T95 hardens it.
- **Holds:** the credential of the one subscription account it runs on, when it runs on a subscription (an automation token, or a login file mounted read-only), because the vendor CLI needs it ([Security model](../04-constraints.md#security-model)); the project's credentials only when the owner opts in for build jobs ([New and existing projects](12-new-and-existing-projects.md)), and never for a design variant (planned), which also reaches no external dependency ([External dependencies](#external-dependencies)).
- **Checks:** the job holds no forge token, signing key or vendor API key, has an egress allowlist (its vendor's API, the package registries and the address of each external dependency the job uses, and, planned, never the dashboard port on any host address, see [Dashboard](13-dashboard.md#who-can-act); today only the internal job network and the egress proxy, which opens nothing but `CONNECT` tunnels to port 443 of allowlisted names (it checks the name, the port and the method, not that TLS runs inside the tunnel), keep jobs off it, so that holds with the default binding, the host's loopback address on a port other than 443, and not for a dashboard published on port 443 at an address an allowlisted name resolves to) and a read-only root. What it does to an external dependency happens before any check below; that path has its own [section](#external-dependencies). A credential it holds can leave the job only through that allowlist or in what it hands back, and before Intakt pushes or posts anything a job returned, it redacts the values of every credential mounted or injected into that job and runs the secret scan; a hit fails the hand-back. A build that fails the scan for the last allowed time does not lose its commits, on every path that runs the scan (the hand-back round and the build task's own hand-back check): they are kept unpublished on the orchestrator's machine until the finding is judged or its retention limit ends ([A hit of the secret check](#where-model-output-authorizes-something)). The pull request text is part of that work: on both paths it is scanned before the commits leave the quarantine or are pushed (the forge's own scan of the title and body stays as a second barrier), and it is held with the commits in their quarantine. In the build task, the pre-push check runs `CheckHandBack` only on a bundle the hand-back check already accepted (the run stops at the first failed step), so it scans the same bytes under the same rules and cannot produce the first hit while its scan scope is unchanged (`CheckHandBack` resolves the pushed branch and main from the mirror again, so a rewrite of either between the two checks can bring an object the first check excluded into scope, and a hit on it is handled as any refusal); if it refuses anyway, the build fails closed, nothing is pushed, and the hold applies to the bundle as on the other paths. The never-moved guarantee of the hold covers objects that no scan has accepted. An accepted check moves into the mirror only the objects the accepted head reaches beyond the pushed branch and main, which are the objects the scan read: a commit as shipped that the check wrote again (a stripped trailer, a redacted credential in its message) and any pack object the accepted head does not reach never leave the quarantine, and the scan is not widened to the whole pack instead, because a commit with a mounted credential in its message would then be refused instead of redacted. This restriction applies to the objects moved into the mirror: a refused bundle starts no check job, and a passing check still gives the job the original bundle. The guarantee below rests on that restriction: as built today the check moves the whole unbundled pack (commits as shipped and unreached objects included), so it holds only once every object the first check moves is one its scan read (plan T50, "(moved objects)"). The objects the first check moved into the mirror, named by no ref, have therefore passed the scan under the same rules: a pre-push refusal does not delete them and nothing tries to isolate them. They stay on the orchestrator's machine only, are never pushed and reach no model. The bundle the first check received is held in the quarantine with the text for judgement, as on the other paths, and the build clone, which already holds the accepted head, is removed (plan T50 adds that cleanup: as built today the build task returns on a pre-push refusal and leaves the clone in place). Keeping them is safe because the kept objects, the held text and every matched value stay private to the orchestrator's machine, and the forge, a job and a model get none of them: the Maintainer and a build session receive only the sanitized finding record. The commits stay in the check's quarantine, named by no ref, and no object of theirs that no scan has accepted is ever moved into the repository's objects, so no checkout, build clone, mirror fetch, job or review reads one (after a pre-push refusal the mirror holds only the objects the first check accepted, as above); the held text lies in that quarantine beside them and is never written to the ledger, a comment, the forge or a model; nothing kept is pushed, the scan still fails closed before any push, only a passing new scan of the commits and the text moves them out of the quarantine, the limit's end deletes the quarantine's objects and the text with the hold, and the finding's record names only the file (or "pull request text"), the line and the rule, never the value, with a file path that itself holds a hit redacted. The hand-back is data: the bundle must build on the expected base and is re-signed by the orchestrator; a check job runs the project's pre-push gates in a fresh container before the push (for Intakt only its static gates, which do not run the change's code), and the full check command runs after the push as the head's check run ([Overview](01-overview.md)); secrets are scanned before every push; protected paths and dependency changes are held by the merge rules and the dependency policy; the change then needs its Code reviewers, green CI on its exact head and the [merge](08-merge.md) steps. A question only parks the task; an upgrade request is one signal to the model planner, which picks the model.

### Code reviewers (every reviewer of the panel, specialists included)
The Code reviewers (`code_reviewer`, formerly the review panel): each reviewer of the panel, including a specialist, which is a panel setting and not a role of its own.
- **Subscription path (plan T33):** a tier on the `claude_code` provider runs the vendor CLI instead of Intakt's toolbox. The CLI's own file tools would bypass the checkout's path checks and the fence, so it gets no built-in tool (`--tools ""`, and `--disallowed-tools` naming each built-in: shell, file reads and writes, web fetch and search, sub-agents), no project or user settings, and no checkout: it runs in its own empty directory (`var/claude-code/`, also its home), never in Intakt's install or the checkout. A review call that has a round also gets the per-review MCP server (#1277): an MCP configuration naming only that server and the round's review credential as a bearer, `--strict-mcp-config` so no other server is loaded, and an allow-list of exactly its three read-only tools. That credential is a new secret the CLI holds for the length of the call; it reads only the head of its own round, and it reaches the CLI in a file only the install's user can read (in the CLI's directory, removed when the run has been read), never on the command line, which a timeout message would carry into the log. The allow-list is a second fence only: the server's `ToolAccessVoter` still decides every call, so a CLI that ignored its allow-list could still call only read-only tools of that one head. The CLI calls the server itself and does not use Intakt's toolbox, so the server fences every answer of its tools before it sends it (an answer reaches the CLI fenced but not cut at 100000 bytes); the prompt still says that only the fenced text and tool answers may be cited, and an answer can still not pass a change on its own. Plain code counts its `approve` only for a call that was given that server and whose own stream (never the model's text) reports a call of one of its tools on that server with a result that is no tool error (#1278, #1894); any other call (no round, no read, or only failed reads or reads elsewhere) has its `approve` turned into `blocked`, so a blind answer cannot pass a change. A steered answer from a call with the server can approve like an API-key reviewer's, and the Code reviewers' quorum and their verdict step decide the round as for any other reviewer. In its environment only `PATH`, `HOME` and the login token have a value; every other inherited variable, other providers' keys and the decryption secret included, is emptied, and the environment is read again for every call, so a variable a long-running worker gains later is emptied too. Tool uses the CLI reports are dropped, never run by Intakt; its answer passes through the same typed verdict checks, and a cut-off stream (no final result, whether the CLI exited, was killed or timed out) ends as `blocked`. A tier on the `codex` provider (plan T39) gets the same treatment from the same reasons: a review call that has a round gets the same per-review MCP server (#1835) as its one MCP server, given as command-line settings for that call only (its settings file stays unread), allowed exactly the three read-only tools and required to start; the round's credential reaches it in an environment variable, never on the command line. Its `approve` counts only for a call that was given that server and whose own events (never the model's text) show a completed call of one of its tools on that server whose result is no tool error, and is otherwise turned into `blocked`, so an answer that read nothing cannot pass a change; its prompt tells it to read the files it needs through those tools before its verdict, the tool uses it reports are dropped, and a stream without `turn.completed` ends as `blocked`. The Codex CLI enables many tools by default, so each is switched off by name on every call (shell and command execution, apps, plugins, browsers, computer use, other agents, image tools, hooks) and web search is disabled; it runs in its read-only sandbox, without a saved session and without reading a settings or rules file. Only Intakt's own options become its flags: an option or payload key of the caller never does. Its one prompt carries every user message of the reviewer, each fenced as for any other reviewer, because the bridge alone keeps only the last. The CLI refuses an unknown feature name, so a release that renames a tool fails every call instead of leaving it on. It runs in the account's own call home with a read-only copy of that account's login, never the kept login or another account's, with only `PATH`, `HOME` and `CODEX_HOME` set, plus `INTAKT_REVIEW_SERVER_BEARER` for a call in a round. Text that only claims a limit is a failed review, never a cooldown, so a steered answer cannot take an account out.
- **Cut notice:** a task, diff or tool answer over 100000 bytes is cut before it is fenced, and Intakt's own note about the cut follows the closing marker, outside the fence, so untrusted text cannot forge it and a cut cannot remove the marker. The note only asks the reviewer to read the rest; plain code (`ReviewerAgent`) turns an `approve` of a review with any cut text into `blocked` with the reason `cut-approval`, so a steered or lazy reviewer cannot pass code it was never shown. The Developer's task, CI excerpt and published pull request text are cut by the same code with the same note; a Developer approves nothing, so a cut there only shortens what it reads.
- **Reads:** the diff (a binary file in it, one whose base or head holds a NUL byte, only named with its sizes, never its bytes; every other file shows all its lines, a byte that is not UTF-8 escaped, so a stray byte cannot hide code), the task (its fenced external blocks, including the review in a task filed from a catch-up review), a read-only checkout at the head including `vendor/`, project memory, and the open findings of earlier rounds. Today it is given the task text, the notes of the project memory about the files in the diff (fenced as project memory in a user message of their own, the whole message at most 4000 bytes; the system message never changes with them, and no library preamble ranks them above the instructions) and, from round two, the open findings of earlier rounds with their persistent ids (plan T10), each fenced, and reads the checkout through its tools, each answer fenced; the other inputs arrive with their tasks. A reviewer asked again after a `changes` or `blocked` answer that named no finding also gets one fixed message of Intakt's own as its last user message, with an example finding of Intakt's own, asking it to name its findings or approve; it carries no outside text, so it is not fenced. Plain code checks that the ids it lists as `resolved` or `repeat` were open and that no id is both, and a verdict breaking either rule cannot be read as a verdict (asked for once more, then a failed reviewer that never counts as approval or changes); the open findings come from the change's stored finding ledger, taken once when the round opens and stored with it, so every reviewer of a round is shown the same list; they are earlier reviewers' text and stay fenced. A reviewer that gives one of its findings the id of a failed review only keeps its own verdict out of the ledger: it adds no finding (as if it reported none) and closes none. Its prompt holds the rubric and says that fenced text is data, never instructions.
- **Can:** call read-only repository tools at the exact head (in process or over the per-review MCP server, which serves only that head): `read_file`, `list_directory` and `search_files`, each marked read-only, with bounded answers (a file read names a binary file, one with a NUL byte anywhere, with its size and never its bytes, and returns at most 100,000 bytes of any other file, a search skips files over 1 MB, cuts each matched line to 500 bytes and stops at 100 matches or 100,000 bytes, and a directory listing stops at 100,000 bytes); and run probes in a no-network sandbox within a per-review budget. Nothing a probe writes reaches the pull request.
- **Holds:** the project's credentials by default, since check and review jobs get them unless the owner withholds them ([New and existing projects](12-new-and-existing-projects.md)), and the credential of the subscription account it runs on, when it runs on one; a `claude_code` or `codex` reviewer also holds its round's review credential, which reads only that round's head. A steered reviewer could try to copy them into its findings.
- **Checks:** probes run without network, so a credential cannot leave through a probe. Before Intakt posts a review's text (the review body and its findings), it redacts the values of every credential mounted or injected into that job, each matched with or without its leading and trailing whitespace, and runs the secret scan over it; a hit is a failed review ([Reviews](07-reviews.md)): the reviewer's output failed, not the Developer, so it uses no cycle, is asked again once and then parked, and its text is never posted. The verdict is a typed object checked by the Validator; anything else is a failed review, which never approves and never sends the head to a stand-in or a substitute ([Reviews](07-reviews.md)). It counts only for its identity (head, base, task revision, check commands, review policy) and only when the posted forge review carries its one-time token. Tool arguments that escape the checkout are refused by a listener, not by the prompt: an absolute path, a `..` segment, a null byte, the `.git` directory, and any path whose real location, after following symlinks in the code under review, is outside the checkout or inside its `.git` directory. A tool that fails answers the model with an error, never ends the run; a malformed tool call (a missing argument, a path that is not a string, an unknown tool) also makes the answer unreadable (asked for once more, then a failed reviewer), whatever the model answers after it, and the arguments are validated before the path is denied, so an escaping path cannot hide a missing argument. A reviewer that keeps calling tools without answering is stopped after 30 rounds of tool calls (a round is one model answer, however many calls it carries), which makes the answer unreadable like any other (asked for once more, then a failed reviewer). From the second round, a new blocking finding must be a regression or cite a requirement, enforced in code; both are claims the reviewer makes (a reviewer-set `regression` flag and a free-text requirement), so a steered reviewer can make them, and they only decide whether a finding keeps its severity. An approval counts toward the quorum, and a merge still needs green CI and the merge steps.

### Stand-in reviewer
- **Reads and can:** as a reviewer, on an intermediate head.
- **Checks:** its approval is never the last word (the scarcer vendor reviews the same head), it is never used on a head whose last change is a merge of main, and it never stands in for either Security engineer session: a role that is not configured sends a protected change to the owner, and an outage holds it without a decision ([Merge](08-merge.md#independent-security-review)).

### Substitute and catch-up reviewer
- **Reads and can:** a substitute is a reviewer of another vendor's same tier that reviews the final head when every account of the reviewer's vendor is out; unlike a stand-in, its verdict can be the last one at merge, and a catch-up review is owed. The catch-up reviewer is that reviewer once its vendor is back: it reads the merged change (the diff against main as it merged), the task and a read-only checkout at the merge commit, with the same tools and probes as a reviewer, and never the substitute's review.
- **Holds:** what a reviewer holds, since it runs the same probes at the merge commit.
- **Checks:** a substitute never stands in for a Security engineer session (a role that is not configured sends a protected change to the owner, and an outage holds it without a decision, [Merge](08-merge.md#independent-security-review)); this guard comes with those sessions, since today a substitute is the first configured one with a free account. The catch-up's verdict never reverts or blocks a merge: a rejection only files a task, the review inside an external block, that inherits no steering label and is built only once a person labels it ([Reviews](07-reviews.md)). The filed task's body is redacted and scanned like any review text before it is posted (see [Reviewer](#reviewer-every-configured-role-specialists-included)); a hit is a failed catch-up that files nothing and is shown on the dashboard.

### The AI engineer's session (planned)
Its weekly session reads a report built by plain code from the ledger, fenced as data, and proposes prompt, skill, context-limit and routing changes ([the AI engineer](06-budget-and-model-planner.md#the-ai-engineer-planned)). The ledger holds a tool output only as size metadata (tool name, turn, size), never its body, so the report carries no file content, command output or credential. Its journey review (daily by default, [Journey scoring](06-budget-and-model-planner.md#journey-scoring)) reads more: the rubric and the transcripts of at most the configured number of worst-scoring journeys (five by default). The orchestrator copies the transcripts at hand-back into its own store, which no job can read or write and only the collector and the journey review read, and deletes them once the last review that could read them has run, at the latest after the retention period (14 days by default), counted from the session's hand-back. The collector records a session's figures (counts, durations and sizes only) at hand-back, before its transcript can expire, and at the merge only totals them; a session without transcript figures is marked "transcript figures unavailable" on the scorecard and the dashboard, with the reason, and is never scored as zero; transcript availability for the review is shown separately: a session whose transcript was deleted after its figures were recorded keeps its scorecard values, is shown as "transcript deleted" for the review only, and is skipped by the review, as is a session whose transcript was not kept, while a transcript the collector could not read within its limits stays kept and available to the review. A transcript holds tool output, code, command output and text a steered agent wrote, so it is untrusted input: plain code redacts and secret-scans each transcript before the session sees it, a transcript with a scan hit is left out of the review and the gap shown on the dashboard, and the rubric and each transcript go into the prompt fenced as data, separately. The collector and the per-merge scorecard use no model: plain code parses the transcripts in a separate process without the orchestrator's credentials, and the scorecard and its pull request comment carry numbers and labels only, never transcript text. Both sessions have read tools only and no forge or merge permission. Plain code keeps an experiment on its own only on figures recorded outside the job. Tokens are such a figure only for API calls, whose usage the vendor reports to the Platform; a subscription CLI's tokens come from the log the job wrote, and the vendor's window reading is per account and cannot be split between arms, so where an arm's tokens rest on a job's log a change that would be kept is held for the owner and never kept automatically ([Budget and model planner](06-budget-and-model-planner.md#journey-scoring)). The other figures: the slot's process accounting records every check and test process the job starts by kind (the full suite, the fast check, a single gate, and a direct test runner or static analyser run) with its CPU seconds, so a steered job cannot hide repeated runs by leaving them out of its transcript; re-reads and verbosity are transcript-only and never decide an experiment. A figure from a job's log can still fail an experiment, which only restores the old approved version. A weekly-session finding goes to the follow-up inbox redacted, secret-scanned and inside an external block, with no steering label; a scan hit files nothing. A journey-review finding is filed directly as a task of its own by the filing step (plain code), never through the follow-up inbox or the Tech lead, under the same external-block, steering-label and boundary rules; on a scan hit, only the numbers plain code wrote are filed. No build starts without a person's label: a task filed from such a finding is built only once a person with write access sets the steering label, checked through the forge's permission API, and neither the session nor the Tech lead can make it eligible. Intakt's authorship satisfies only the author and last-editor check, never the label, and an edit by an account without write access makes the task ineligible as usual. Plain code writes the block and neutralizes any external marker inside the session's text, so the text cannot end its own block; when the Tech lead merges the finding into an open task, the text is appended as an external block of its own and is not a trusted edit of that task's body. The append does not change the task's trust status: plain code runs the author and last-editor check on the body revision it appends to and appends only if the body is still that revision (otherwise it checks again), and the append never counts as the last edit or as a confirmation, so a task last edited by an account without write access stays ineligible until a trusted account edits or confirms it. A change to a prompt, focus file or skill is a protected change and goes through approval like any other, before any live job uses it, the trial arm of an experiment included; a model's answer never keeps or reverts an experiment (plain code compares the measures), and the role never changes review strictness, checks, approval rules or its own limits.

### The Test engineer's session (planned)
The opt-in Test engineer ([Reviews](07-reviews.md#the-test-engineer-planned)) runs one scheduled audit session per project.
- **Reads:** the audit report, built by plain code from the `tests` gate's results (the gate's elapsed time, `tests/durations.json`, the test files' paths, counts and lines, the sandbox runs per gate test, the `serial` group), and the test files of the folders the report flags, read at main. Test names and test code are written by Developers, so the report and the files reach the model fenced as untrusted data; before they do, Intakt redacts the values of every credential mounted or injected into the job that produced them and runs the secret scan, and a report with a hit is withheld, as for a Security engineer layer review. The same holds for every result of its repository tools: plain code redacts and scans each read and each search result before the model sees it, and fails closed. A result with a hit, or one the scan could not complete, is withheld whole: the tool answers with Intakt's note that it was withheld, never with part of the result, and the dashboard shows it. Test files can hold a planted value, so this runs on every tool call, not only on the report.
- **Can:** read-only repository tools (read, search) at main within a turn cap, each result redacted and scanned as above; no writes, no shell, no forge access, no network beyond its vendor, no credentials of the project or the forge. It cannot run a test or CI.
- **Checks:** its output is a typed list of findings, validated against its schema; an invalid answer is a failed audit that files nothing and is shown on the dashboard, never a silent empty list. Plain code files each finding as a task with the session's text inside an `<!-- external -->` block, redacted and secret-scanned (a hit files nothing), with no steering label, exactly as for the AI engineer's findings above: no build starts until a person with write access sets the steering label, checked through the forge's permission API, and neither the session nor the Tech lead can make it eligible. The build that follows is checked and reviewed like any other: a removal or merge must name, for each removed case, the test that still proves it, the reviewers check that test, coverage of `src/` must not drop, and a time claim needs CI measurements before and after. A change to a CI workflow stays a protected change, and the role never changes a gate's strictness, the checks or the approval rules, so a steered audit can only propose tasks that a person labels and the same gates judge.

### The Designer's session (planned)
The Designer ([Reviews](07-reviews.md#the-designer-planned)) runs only for a user-facing task of a project with a user interface, and plain code decides that from the project's path and label trigger rules, which live in protected files, never the model.
- **Reads:** the task and its plan, fenced as untrusted like any issue text. For its scoring ([Designer scoring layers](15-designer-scoring.md)) it also reads the screenshots and check results of the head and the screenshots of rendered variants, all taken in the check environment from model-written code, so they are untrusted: text in a screenshot or a result is data, never an instruction. The check results are text and go through the fencing helper (`Fence`) under their own source, after Intakt redacts every value in the checked revision's credential set and runs the secret scan, since that code can print a credential only its Developer held. The set is the same for check results, screenshots and committed references ([The credential set of a revision](15-designer-scoring.md#the-credential-set-of-a-revision)): the credentials of the job that produced the output (a render job holds none; a check job holds the project's credentials unless the owner withholds them) and of every build job whose commits the revision contains beyond main (each one's subscription credential and, on the owner's opt-in, the project's: the builds of the head, plus the variant build for a variant); a revision with a commit the orchestrator did not record adds every credential any build job of the project can hold and keeps the producing job's own (a check job's project credentials withheld from build jobs stay in the set); and when a value in the set cannot be read the scan counts as a hit, never runs against a partial set. A result with a hit is withheld whole and the gap shown on the dashboard, as for the Test engineer. A screenshot is an image, which the text helper cannot wrap, so plain code sends each one as an image part of a user message of its own, after Intakt's fixed note naming its source (head or variant, screen, width) and saying that it is untrusted evidence, never instructions; the fencing gate covers both inputs ([Tests of the defenses](#tests-of-the-defenses)). A render job is a job of its own in the check environment: unlike a check job, which gets the project's credentials by default ([External dependencies](#external-dependencies)), it gets none of them and no subscription credential, so rendering cannot read a live credential, and like a variant build it reaches no external dependency. That does not make every screenshot free of one: the rendered code was written by Developers that each hold their subscription credential and, on the owner's opt-in, the project's. So no screenshot leaves the check environment, for the Designer's vendor, the dashboard, the owner's pair view or a committed reference, before plain code has read its text and machine-readable codes and matched them against every value in the rendered revision's credential set, and the secret scan; a hit, an unreadable image or an unreadable credential value withholds it whole, and a reference image a build commits is read the same way, as committed, against the set of the head it would push, by the hand-back check, which fails on a hit or an unreadable value so the commits stay unpublished ([Screenshots leave only after a scan](15-designer-scoring.md#screenshots-leave-only-after-a-scan), [Residual risk](#residual-risk)).
- **Can:** add the Ready additions to the task's plan, answer rubric scores, describe design variants and rank rendered variants in pairs; no code, no labels, no shell and no network beyond its vendor. Its opt-in tools run in the check environment, not in its session. A variant description is a typed answer (the choice, the screen, what differs); a build job implements it as code, and that job's Developer reads the description fenced as another model's advice, like the Tech lead's plan, never as the task.
- **Checks:** its additions are a typed answer validated against its schema; an invalid answer adds nothing and the task stays not *Ready* ([Definition of Ready](../01-intent.md#definition-of-ready)). It cannot make a task eligible to build: the steering label stays a person's, as for every task. Its rubric scores are a typed answer too, each citing a screenshot region; an invalid answer is a failed review, never a silent pass. A steered score can add or drop a finding but cannot pass a failing objective check, since those are plain-code checks. Its variant descriptions and pair rankings are typed answers as well; an invalid one creates or ranks nothing. A variant's build job gets none of the project's credentials whatever the owner's opt-in for build jobs and no external dependency on its allowlist, only bundled sidecars of its own, so a steered variant Developer reaches no shared instance even before the hand-back checks run ([External dependencies](#external-dependencies)). A variant's commits pass the same hand-back checks as any build and are never pushed to the change's branch or merged, so a steered variant can only show the owner a screenshot; the choice it informs reaches the change only through a build that is checked and reviewed like any other. Its agreement with the owner is measured by plain code from the owner's votes, never reported by the model.

### The Security engineer's sessions
The Security engineer (#864; team names in #862) covers the security of the product across infrastructure, backend and frontend: checks first, and the role for what checks cannot judge ([The product's surface](#the-products-surface)). It runs two model sessions of its own for a protected change: the security review and the penetration test (the former gatekeeper sessions). The approval itself is plain code that runs the steps in order and approves only when all pass, with the owner's two floors. Its other sessions, the layer reviews and the monthly audit, are listed after these bullets.
- **Reads:** the diff of a protected change, main's version of every protected file it touches, and the results of the hard floors and mechanical checks; never the Developer's pull request text or reasoning, so a Developer cannot argue its own change past them. The diff and main's files are code, fenced as untrusted.
- **Can:** the security review's read-only repository tools at the head. The penetration test also returns fixtures, as data in its typed verdict.
- **Checks:** both run in sessions of their own, apart from the Code reviewers. Their verdicts are typed objects. A session that ran without a valid verdict, or a role that is not configured, sends the change to the owner; a valid verdict wins over any limit wording in its text, which can quote the diff. A session that could not run (the vendor's limit or login error, a crash, a timeout, a cut stream, read from the run and never from the model's text) is an outage: it gives no verdict and no decision, the head waits, plain code tries again after a wait and stops trying for every head while the role is out, the owner gets one notice per outage only when it outlasts a set time, asking the owner to add or free an account for the role and clearing by itself when a session of that role runs again, and held heads do not count toward the owner cap ([Merge](08-merge.md#independent-security-review)). Waiting never approves: a steered session that fakes an outage can only delay the change, never pass it, and text that only claims a limit is no verdict and goes to the owner. They can only hold back an approval the plain checks would give, never give one the checks refuse: the floors run first and no model output lowers them. The fixtures run in a check container without network against main's gate and the head's gate; plain code compares the two results, and a fixture only the head's gate accepts sends the change to the owner. A steered penetration test that writes no fixture loses one check, which is why the floors, the no-weaker proof, the canaries and the owner's switch stand beside it ([Merge](08-merge.md#approving-protected-changes)).
- **Why two floors stay with the owner:** the approval system and secrets and permissions are the two changes the Security engineer cannot be trusted to judge. It reads text an attacker can shape, so a steered session could clear a change that widens its own approvals, and a leaked credential cannot be reverted the way a merge can.
- **Layer reviews:** on a change whose paths match a layer's triggers ([Reviews](07-reviews.md#the-security-engineer)), the role reviews as a specialist reviewer with that layer's focus file. It reads, can and holds what a [reviewer](#reviewer-every-configured-role-specialists-included) does, the layer's check results included as fenced input, and its verdict passes the same checks. Check results and scan reports can print what a response, an image or a configuration exposes, so before one reaches the model Intakt redacts the values of every credential mounted or injected into the job that produced it and runs the secret scan over it; a report with a hit is withheld, the session gets only Intakt's note that it was withheld, and the dashboard shows it. Triggers only add it; its approval counts like a specialist's and never lowers a gate or replaces a core code reviewer.
- **Monthly audit:** reads the trend of the scan results of every layer, the threat model and the scan findings, all fenced (scan output prints what the product and its dependencies hold), and each report redacted and scanned before it reaches the model, as for a layer review. Until a layer's checks land, the audit reports that layer as not covered yet, never as clean. It can only propose: each finding becomes a task Intakt files with the audit's text inside an `<!-- external -->` block, redacted and scanned like a task filed from a catch-up review, and built only once a person with write access labels it; a proposed change to this page is such a task too. It holds no write access to the repository and no credentials of the project.

### The Code reviewers' verdict step
The model call of the Code reviewers' verdict step (formerly the judge), which marks the findings of a round.
- **Reads:** the reviewers' findings, the task's acceptance criteria and non-goals, and the list of files the change touches (the paths of the round's diff, fenced as data, read by plain code from the diff headers, so the verdict step can tell a file the change touches from one outside it). The review inside the external block of a task filed from a catch-up review is never read as an acceptance criterion.
- **Can:** mark each P3 finding act, defer or reject; no tools. A P3 finding that is a local edit in a file the change already touches and needs no new design is act, and defer is only for a finding that needs its own design or tests, or files outside the change. A steered verdict step can therefore widen the act list of a planned polish round with P3 edits, which stays harmless: the polish round is limited to that list, blocks on nothing but a P1, and when it fails the approved head merges without it. Its mark for a P1 or P2 is not applied: plain code (`JudgedFindings::of`) puts every P1 and P2 the verdict step was given on the act list whatever the verdict step marked, and the prompt and the answer schema say so (`JudgePrompt`, `JudgedFinding`). It can give its reason for a `defer` or `reject` of a P1 or P2 (`note`): plain code keeps the note only for such a mark (`JudgedFindings::of`), it never takes the finding off the act list or decides anything, and it is stored with the finding in `judge_done` redacted (credential shapes and the credentials the install holds) and trimmed (`RoundLedger`), because it is model text that may quote a secret. It can also link a finding to another it was given as one cause (`same_cause_as`); plain code refuses a link to the finding itself or to an id it was not given, and keeps a link only when both findings are in one hunk of one file of the round's diff and at most five lines apart (`CausesInOneHunk`), and merges linked findings only when the whole group, with the findings that share its lines, stays in one file and within five lines (`OnePerPlace`), so links cannot be chained past that bound; a merged entry keeps the higher severity and the merged ids, so a steered verdict step cannot drop a finding's id or severity, and cannot fold a defect more than five lines away into another entry. Within that window it can: the entry keeps the first finding's text only.
- **Before it:** plain code, not a model, drops a finding before the verdict step sees it only when the finding quotes code and none of its quoted code is in the change (`QuotesInChange`); a finding without a quote, or with any quote found in the change, reaches the verdict step. A dropped finding is on no list, whatever its severity. The risk: a real finding that quotes only code absent from the change (a name the fix still has to add, written without any name the change holds) is dropped and does not reach the Developer. Its reason is recorded with the round (`dropped` in `judge_done`), with the changed lines nearest to each quote (`NearestChangedLines`, plain code, at most three short lines per quote; taken from the checked-out file and redacted as the judge's note is, over the whole file, so a private key is found by its `BEGIN` line wherever it is; a file that cannot be read from the checkout, a symbolic link or a file under one (its target may be a file the change does not touch), a file that is not the same regular file when it is opened as when it was checked (it is opened once and read only from that open file), a file in which a redacted part spans a line break, or a path the redaction changes gives no line), so the drop can be seen and checked. Those lines are code of the change and go into no prompt of Intakt's.
- **Checks:** its output is a typed list over the finding ids it was given, read through structured output and checked by the Validator and by plain code (`JudgeAgent`); an unknown id, a repeated id, a missing mark or a mark that is not act, defer or reject is a failure, and a failure (also a cut-off stream) marks every P1 and P2 finding `act`, so a broken verdict step leaves every blocking finding on the Developer's list. A steered verdict step that answers well-formed can only defer or drop P3 findings, and only the ids it was given: a `defer` or `reject` it gives a P1 or P2 is ignored, so it cannot hide a blocking finding from the Developer. Its marks never change a reviewer's verdict or count toward the quorum. The task text, the changed-file list and the findings reach it only through the fence (`UntrustedSource::Task`, `ChangedFiles` and `FindingsToJudge`). It runs on the light tier through `Vendor::judge`. It decides only what the next build works on: it never turns a reviewer's `changes` into an approval, because the quorum counts the reviewers' own verdicts on the exact head.

### Tech lead: strong-tier plan for a cheaper build
The Tech lead (`tech_lead`, formerly the planner) writing a plan for a build on a cheaper tier.
- **Reads:** the task text with its fenced external blocks and the review in the external block of a task filed from a catch-up review, and the code at main; both are untrusted.
- **Can:** read-only repository tools (read, search) within a turn cap; no writes, no network beyond its vendor, no credentials of the project or the forge.
- **Holds:** the credential of the one account it runs on only (an automation token, or a login file mounted read-only).
- **Checks:** its output is a plan capped in size, which reaches the Developer fenced as another model's advice, never as the task ([Budget and model planner](06-budget-and-model-planner.md)). It is advice only: it cannot pick a model, make a task eligible or approve anything, and the build it informs is checked, reviewed and merged like any other, so a steered plan can only produce a build that the same gates judge.

### Tech lead: readiness and sizing
The Tech lead's tool-less call (formerly triage and the sizer) that checks a task against the [Definition of Ready](../01-intent.md#definition-of-ready) and sizes it.
- **Reads:** the task text with its fenced external blocks and the review in the external block of a task filed from a catch-up review, and items of the follow-up inbox. For the validity check ([Choosing work](03-choosing-work.md), step 3) also the evidence plain code gathers: the numbers and titles of open and recently closed issues, whether the paths, commands and names the task cites exist on main with the latest commit that touched each, and the decisions added since the task was last edited; issue titles and commit subjects are untrusted, and each source is fenced on its own.
- **Can:** say whether the task is ready, propose a class, estimate a size, propose a validity disposition with its evidence by reference (which by itself closes nothing), and merge, queue or expire follow-ups; no tools.
- **Checks:** it cannot make a task eligible (eligibility is the write-access check and a steering label from a person). It cannot close a task either. A `holds` answer lets the task go on through sizing, so valid work reaches Ready. Plain code closes a task only on a link it reads from the forge itself and that a person with write access made: for a done disposition, the cited commit is on main, newer than the task's last edit and part of a merged pull request that names the task, which was not reopened since; for a superseded one, the later issue, written and last edited by an account with write access, carries a `Replaces #n` line for the task. The link goes into a comment and a ledger event. A done or superseded answer without such a link, a contradicted or unclear one and an invalid one send the task to the Product owner with the call's evidence, unbuilt and open. So a steered call cannot close a task: at worst it points plain code at a task that a merged pull request or a trusted `Replaces` line already names, or parks valid tasks with the Product owner, which costs the owner a look at each and closes nothing. A proposed class fills the row only when no label sets one. The size sets a start model and an allowance, both bounded by the owner's routing, the sensitive-path rule (sensitive paths start on the strong tier whatever the size) and the budget caps. A parked task costs one comment.

### Task drafting (Tech lead)
- **Reads:** the owner's text from the New task box, fenced as untrusted ([Dashboard](13-dashboard.md#starting-a-task)), and the chosen project's repository and plan, read-only, with the titles of its open tasks, which the orchestrator takes from its forge listing; all of it is untrusted.
- **Can:** read-only repository tools (read, search) within a turn cap; no writes, no forge access, no network beyond its vendor, no credentials of the project or the forge.
- **Checks:** its output is a draft task, validated against its schema; an invalid draft is an explicit failure shown in the draft view, never a filed issue. Nothing it writes is filed or queued: the owner sees the whole draft, can edit it, and only an approval in the dashboard (a request that passes its `Host` and CSRF checks, [Who can act](13-dashboard.md#who-can-act)) files it, and the filing is plain code that writes exactly the approved text with the labels a ready task carries, under Intakt's own forge identity. The owner's text and the drafts are shown on the dashboard to whoever can open it, never in a JSON API response. The filed issue then enters intake like any task ([Choosing work](03-choosing-work.md#tasks-drafted-from-the-dashboard)) and is checked, reviewed and approved as usual, so a steered draft can only propose a task that the owner reads before filing and the same gates judge after.

### Escalation
- **Reads and can:** a stronger model rebuilding a recurring finding is a Developer; an escalation review is a reviewer on a stronger tier; a job's upgrade request is model output.
- **Escalation review prompt (#3300):** it reads the one finding, fenced as `escalated finding`, and the round's diff with the files the finding cites first, fenced as `diff`; it has no tools. Plain code refuses to build the prompt when none of the cited files is in the diff or their sections alone are over 100000 bytes, so the model never judges a finding without its code.
- **Escalation review call (#3301):** it runs on the strong tier with no toolbox and no message store, and holds no credential of the project. Its answer is a structured `confirmed` or `rejected` with reasons, validated against its schema; anything else is a failed escalation with Intakt's own reason that keeps no verdict, never a rejection. The reasons are redacted before they are returned to be kept.
- **Checks:** a job never picks its own model; the model planner escalates on structured signals (the same check failing twice, a P1, a stall, a request with its reason) within the owner's routing and budget caps ([Budget and model planner](06-budget-and-model-planner.md)).

### Maintainer
The Maintainer (`maintainer`, formerly the maintainer agent).
- **Reads:** blocked verdicts, findings, questions, recurring failures, task and pull request text, the design documents, and the weekly flow and quality report (figures from plain code; the task titles, ledger text and the names of checks and tests in it fenced). Check and test names come from the checks' output on code Developers wrote, and a test name can carry a data-provider value, so before the report reaches the model Intakt redacts the values of every credential mounted or injected into the jobs whose output it read and runs the secret scan over the whole report; a report with a hit, or one the scan could not complete, is withheld, the session gets only Intakt's note that it was withheld, and the gap is shown on the dashboard, as for the Test engineer's report. The dashboard takes the check and test names it shows (the slowest tests of the codebase health) from that same redacted and scanned data, never from the checks' raw output, and shows the figures without the names when the report was withheld ([Dashboard](13-dashboard.md)). For the backlog sweep it also reads the issue listings (the numbers and titles of open and recently closed issues) and the evidence plain code gathers from main, which arrive through the same per-source fencing as sizing ([Readiness and sizing](#triage-and-sizing)).
- **Can:** comment, answer questions, write decisions into task descriptions, label, split tasks and oversized pull requests (the owner's, its own, or one with `take-over`), resolve conflicts on a branch, write the summaries of approval requests ([Merge](08-merge.md)) and, for a stall whose cause is a protected or environment change, open a pull request of its own that carries that change (protected files, the shared image's definition, workflow edits), through a fixed tool list with a step limit ([The Maintainer](09-maintainer-agent.md)). That list belongs to the hand-over sessions only. The weekly review session has its own tool list with read tools only (the report and the design documents): it cannot comment, label, split a task, write a task description, change a branch or open a pull request, and its job holds no forge credential. It can only return a typed answer: findings, each with a cause, a change and a check (a finding may ask for a value of a flow setting the owner listed, see below), and for a missed forecast a recommendation naming one of the card's options. The backlog sweep, a separate monthly background job whose results the weekly review reads, runs as the same kind of read-only session, and its typed answer is where it can propose closing a ready task: closed only by plain code, on the merged pull request or `Replaces #n` line that [Readiness and sizing](#triage-and-sizing) requires, never on the sweep's answer.
- **Checks:** it runs as its own narrow forge identity in a job container, and the forge, not its prompt, denies it merging, pushing main, approving, changing protections and editing config. A decision it writes changes the task's revision, so earlier verdicts stop counting and the next build is checked and reviewed like any other. It cannot give an owner approval, in a comment or in a summary: its forge identity is never the owner's account, so a review or `approve <sha>` it posts is not the owner's ([Merge](08-merge.md)), and a post guard blocks it as the second barrier. Its pushes leave its job as a bundle through the orchestrator's hand-back and push guard, which refuses main, non-fast-forward pushes and CI changes other than taking main's exactly, except on that pull request of its own ([The Maintainer](09-maintainer-agent.md)). That pull request is written from stall context a Developer wrote, so it gets no trust from its author: it builds on the current main on a new branch, a workflow edit in it passes the CI definition scan and a risky one stays local until the owner approves its push, and it goes through the Code reviewers and the protected-change approval like any build's ([Merge](08-merge.md#approving-protected-changes)), so the agent can propose such a change but never land or run one alone. Its weekly review applies nothing, by its tool list and not by its prompt: the session reads names that come from code Developers wrote, so a steered one must find no tool to act with. Plain code validates the session's typed answer against its schema, and an answer that does not validate files nothing, attaches nothing and counts as a failed session. A finding's text is model output from a session that read names Developers wrote, so it is filed the way the AI engineer's weekly-session findings (above) and the proposed checks (below) are: plain code writes the task's frame (the title and a line naming the weekly review and the report week) and puts the model's cause, change and check inside one `<!-- external -->` block, after neutralizing any external marker inside that text so it cannot end its own block. The Developer and the Code reviewers read that block as data and judge the change against the design documents. Plain code reads it as data too: the filed task is ready and written by Intakt's identity, so its body is trusted, but the readers of `Waits for #n`, `Waits for release:`, the links between projects and `Replaces #n` take those lines only outside external blocks ([Third-party text](#third-party-text), [Choosing work](03-choosing-work.md)), and an unclosed block runs to the end of the task. Such a line in a finding's text therefore records no wait, does not block the filed task and closes or supersedes no issue. No steering label is asked for: every finding of this review becomes a ready task, except a tuning the orchestrator applies (below). The outbound scan fails closed: plain code redacts each finding and the recommendation, and files the finding as a ready task, applies a tuning a finding asks for and records its text in the ledger, or attaches the recommendation to the owner card plain code opened for the missed forecast, only after a secret scan of that text completed with no hit. A hit, or a scan that did not complete, files, applies, records or attaches nothing, the session counts as failed for that item, and the gap is shown on the dashboard (the card stays open with the measured forecast). No model decides to file a task or to change a card, task, label or branch. A steered answer that validates can at most file ready tasks with a frame plain code wrote and the model's text inside one external block, each built, checked and reviewed like any other task, ask for a tuning that moves a listed setting only within the owner's bounds, and word a recommendation on a card only the owner decides. A tuning a finding asks for is applied by the orchestrator, not the session, and only for a flow setting on the owner's list and within its bounds, at most one experiment per setting; anything else is refused and filed as a ready task. Plain code undoes a tuning when the quality counter-metric worsens, and a tuned value never outlives the owner's rules: when the value in effect differs from the value in the owner's config, the setting must be on the list and the value within its current bounds, checked in the same step as every owner write and every tuning write, and otherwise the owner's value is restored in that step ([Bounded tuning](06-budget-and-model-planner.md#bounded-tuning)). The review never reaches review strictness, checks, the approval rules, its own powers or the owner floors, and no finding can widen the owner's list. Ruling a hit of the secret check a false positive never releases a push on its own: kept work goes on only after the owner's rule change and a new scan (see below). Every action is in the ledger and on the dashboard.

### Agents over MCP
- **Outside agents** (an owner's agent CLI) reach Intakt's MCP server. They send tool arguments and read verdicts and act lists, which carry text derived from code under review. Starting a review needs the configured token; whether a tool may write is decided by a Symfony Security voter on Intakt's own config, never by the model's arguments; read tools are marked read-only. No MCP tool changes an owner control (a ceiling, a pause, a share, a back-off, an account): those change only through a request to the dashboard port, which no job can reach with the default binding, the host's loopback address on a port other than 443; a dashboard published on port 443 at an address an allowlisted name resolves to is reachable until the planned deny rule exists (see the [Developer](#builder) checks and [Dashboard](13-dashboard.md#who-can-act)). An outside agent that itself runs where the port is reachable (an agent CLI on the owner's computer, with the default loopback binding) is a dashboard client like any other program there and can act; that is part of the accepted risk under [Residual risk](#residual-risk).
- **Built so far (T15, #508, #509, #510):** the owner's server answers `list_projects`, `review_status`, `review_verdicts` and `review_act_list` and serves a round's findings as a resource, all read tools, and has one write tool, `start_review` (not read-only, destructive-hinted), which reviews a branch of a local repository whose path and name the agent sends; it runs only when the config allows writes and the request carries the owner's bearer token (checked by the `access_token` authenticator, never read from tool arguments), and it takes no instruction from the agent beyond the task text, which reaches the reviewers as untrusted input; the finding text they return comes from code under review and is data for the client. The verdict step's note on an act list entry (its reason for a rejected or deferred P1 or P2, #2754) is a model's text too, so `review_act_list` and `start_review` return it inside the fence (`Review\Contract\ActEntryAnswer`). Every tool must carry `#[IsGrantedTool]`; a tool without it, or whose check names a subject built from the call's arguments, never runs, and `ToolAccessVoter` refuses `Write` while Intakt's config forbids writes (the default), whatever the arguments say.
- **Reviewers** reach their repository tools as MCP clients of a per-review server that serves only the head under review, read-only.
- **Built so far (T16, #580):** reviewers reach those tools as MCP clients, with the credential of their own round in the bearer header of every request, so the head they can read is fixed by plain code on the server and not by anything the model sends; the model still sees only the three read tools (renamed `review_*` by the client), and the tool results still pass through the fence (the server fences each answer and each refusal, for a client that has no toolbox of Intakt's; the reviewer's toolbox takes the text out of the server's fence only when the boundary is the one that text gets, then measures, cuts and fences it as any tool answer). A reviewer that gets no tools (the server cannot be reached) is not asked at all, and a review whose server is lost during a tool call, or answers it with anything but the tool's result or a refusal of the call (an HTTP error, an unreadable body, an internal error), ends there: either review is blocked, so a reviewer cannot approve code it could not read.
- **Built so far (T16, #578):** the review server's tools take no round: the round is fixed by a credential Intakt signs for it with `APP_SECRET` and the client sends as a bearer header, checked by a Security firewall before any tool runs, so a steered reviewer cannot name another review's head and a client without a credential is refused. None is issued or accepted while `APP_SECRET` is empty, and none is issued for a judged round. The credential is a secret for as long as its round is under review.

## Where model output authorizes something

- **Approval on the spot** ([Merge](08-merge.md#approving-protected-changes)): the security review's agreement and the penetration test's empty result let Intakt approve a protected change. Safeguards: deterministic hard floors that no model lowers (exactly two: the approval system, and secrets and permissions); a mechanical check that passes for every protected file (comment-only, dependency policy, gate code no weaker, harness from main with main's isolation probes), with an uncovered file going to the owner; reviewer sessions that never see the Developer's text; a code reviewer's loosening or missing class on the current head sends it to the owner; no stand-in, and no substitute in either Security engineer session's place (a substitute among the Code reviewers is allowed, see [Order of use](06-budget-and-model-planner.md#order-of-use)); green CI. A project's automatic approval is switched on by the owner only once every canary (at least three per kind of protected change) has reached the owner and a replay of past owner approvals agrees on at least 20 heads; it turns off on its own when a canary is missed or the owner overrules. A failing canary on main reverts the merge when exactly one automatic approval can be the cause and no later merge touched its files, and otherwise asks the owner, there is no daily cap, and every such approval is listed on the dashboard for a week (information, not a notice). The protected-path list and the approval rules live in the owner's config, not the repository. A request to the owner never resolves itself.
- **Finding the protected paths of a change** ([Merge](08-merge.md)): a crafted merge (first parent the branch, second parent an old main commit) could revert or delete a protected file without it showing in that merge commit's diff against one parent. Safeguards: protected paths are read from the full diff between the merge base with the current main and the exact head being merged, combined with the per-commit lists (the paths each commit between the merge base and the head touches, each commit compared against each of its parents; the commits between the merge base and the head are the commits reachable from the head and not from the merge base, so a merge's second-parent commits count unless main already contains them; a path a commit holds exactly as the current main holds it is left out of that commit's list, so a merge of main does not list what main added, while a revert to an old main is listed), never from one parent's diff; a shallow history counts as unreadable, so as protected; submodule entries and `.gitmodules` count as protected.
- **The Maintainer's decisions** ([The Maintainer](09-maintainer-agent.md)): answers, decisions in task descriptions, labels, splits and the summaries of approval requests (a summary never counts as an approval). Safeguards: its forge identity's permissions, the task revision in every verdict's identity, the post guard on owner approvals, escalation to the owner for preference, money, tax, pricing and legal choices, and the ledger. When a task's review cycles run out, the agent re-plans it, but a rewrite of the acceptance or a split never defers or drops an open P1, and a P1 on security, secrets or data integrity goes to the owner. A split of an oversized pull request is checked by plain code, not taken on the agent's word: the plan is checked before it is recorded (every changed path or hunk of the diff from the merge base to `<sha>` held by exactly one part), and the parts are checked before the close (their heads as their pull requests were opened, applied in merge order to the merge base, must give the tree of `<sha>`, or of the new head after commits past `<sha>`, whose extra parts are checked against the diff from the old `<sha>` to the new head; each open part's current head and each merged part's merged change must also carry exactly its share, so a part pushed to after it opened cannot merge a different change, and until every part has merged a part head that drops or adds an edit is refused before review). On a mismatch or a missing part the original stays open, goes back to the agent and, the second time, to the owner. The close records the verified head first and reads the head again after it, reopening the original and extending the split if the head moved; a part closed without merging after the close also reopens the original. The split never force-pushes or deletes the original branch.
- **A hit of the secret check** ([The Maintainer](09-maintainer-agent.md#a-secret-scan-hit-keeps-the-work)): when a build fails the scan for the last allowed time, on the hand-back round or on the build task's own hand-back check, its commits are kept unpublished on the orchestrator's machine instead of being discarded, until the Maintainer or the owner judges the finding. They stay quarantined: their objects stay in the check's quarantine, named by no ref, and no object that no scan has accepted is ever moved into the repository's objects, so no normal checkout, build clone, mirror fetch, job or review reads one until a passing new scan moves it in. The one case where the mirror already holds objects of held work is a pre-push refusal: those are only the objects the first check accepted, the ones its scan read ([Developer](#builder)). The pull request text is covered the same way. Order: on both paths the text is scanned before the commits leave the quarantine or are pushed, so a hit in the text is found while the objects are still quarantined; the forge's own scan of the title and body before it writes a pull request stays as a second barrier. Hold: whenever work is held, the pull request text is held with the commits in the same quarantine, as a file beside the objects, whether the hit was in the commits or in the text; the held text is the one kept artifact that can hold the matched value outside the commits, so it is never written to the ledger, a comment, the forge or a model, and neither agent reads it. The finding's record names the file, the line and the rule, never the value, and for a hit in the text it names "pull request text" in place of the file; a file path is scanned and redacted like any outbound text before it is recorded or sent to either agent, so a path that holds a credential or a scan hit is recorded as `[redacted]` with the object's id instead. The kept work has a retention limit: when it ends, the quarantine's objects and the held text are deleted with the hold, not only the hold, whatever the state of the judgement, and the task goes back to build with the finding as feedback, also when a finding judged false has its rule change landed but the new scan has not yet passed. A finding judged false releases the work only through the scan: the rule or allowlist change it needs goes through the secrets floor to the owner like any change to the scan ([Merge](08-merge.md)), and then the kept commits and the kept text are both scanned again under the changed rules and the work goes on from there with the kept text, without a new build session, so neither skips the scan. A finding judged real, or not judged within the limit, deletes the kept work, the text too, and the task goes back to build with the finding (file, line and rule) as feedback; a build session never gets the value. Safeguards: the Maintainer's ruling alone releases nothing, since only the owner's rule change and a passing scan do; the scan is fail-closed before every push, its rules and allowlist are protected paths and the owner's (the scan never reads a rule or allowlist file from the build's commits, its checkout or its environment), and inline allow directives are refused. A ruling can also become a decision in the task description for the next build (for example, replace the fixture value that looks like a key), which that build's head must pass under the unchanged scan.
- **Reviewer approvals** count toward the quorum. Safeguards: the quorum policy (by default two reviewers from different vendors), verdict identity, green CI and the merge steps.

## Writing project memory

Once a review round completes, a worker indexes the findings it resolved into project memory. This is plain code, not a model role: which findings count is decided by the change's finding ledger (a resolved claim from a failed review, or one another reviewer of the round reported again, does not count), and the text, cause and probe output of each are kept with the round when it completes. Reviewers never reach the indexing side; they only read memory, fenced, through the briefing.
- **New model input:** that text, written by reviewers (often of another vendor), is sent to the embedding model (OpenAI's `text-embedding-3-small`, through the enabled OpenAI account). This is what leaves the install for memory: the finding's text, its cause (the requirement it names) and its probe output, and nothing of the checkout. The embedding call has no tools and returns only a vector, so steered text cannot make it act; at worst it places a note poorly in search.
- **Stored text stays untrusted:** a note is model text, so when the briefing gives it to a later reviewer it is fenced as project memory ([Untrusted text](#untrusted-text)).
- **Kept to its project:** one install serves several projects from one store, so each note carries the project of the round that wrote it, and retrieval filters on the project under review; one project's findings never reach another project's reviewer.
- **Proposed checks:** when the index shows a finding kind recurring, plain code files a task proposing a check ([Reviews](07-reviews.md)); no model decides to file it. The example findings it quotes are reviewer text, so they go inside an `<!-- external -->` block, redacted and scanned before the task is filed, and every role reads them as it reads the review in a task filed from a catch-up review. The task is built only once a person with write access labels it.
- **No OpenAI account:** nothing is sent; the indexing message completes with one `info` log line (the reason, no trace), is not retried and does not reach the failure transport.

## Checking a provider key

Before a key typed in the browser is kept, plain code checks it with one call to its provider (`SymfonyAiKeyCheck`). This is not a model role: no untrusted text goes in and nothing that comes out decides more than accepted, refused or not checked.
- **Input:** the prompt is a constant of Intakt's own (`Answer with the single word: ok`), sent to the light-tier model the owner maps to the key's provider (or the model its descriptor names) with the smallest answer cap its provider accepts; the call has no tools.
- **Credential:** the key goes only to the provider whose descriptor's key pattern alone it fits (Anthropic, OpenAI, or Hugging Face's router), at that descriptor's base URL, in that provider's own header, through the bridge the descriptor names; `ProviderKey::secret()` is read for this call and, once the key is accepted, to write the kept file.
- **Output:** the answer is dropped unread beyond its success; only an authentication failure counts as a refusal, and any other failure leaves the key not checked, so a provider's text cannot mark a key good or bad.
- **Storage:** an accepted key is kept in the data volume in a file only the app user can read (`KeptProviderKeyFile`); it never reaches a log, an exception message or trace, or the browser, which gets the provider and at most its last four characters. The file is read back as outside input: a key without the form of its stored provider is refused, not shown.
- **Failures:** a provider's error text can echo the request, the key included, so it is never kept: the outcome is an enum, the only log of a check that failed for another reason than authentication is a fixed warning naming the provider and the exception's class, and the exceptions `KeepProviderKey` throws have fixed messages and no previous exception.
- **Door:** the dashboard has no login (whoever reaches the port can act, see [Dashboard](13-dashboard.md#who-can-act)), so the route that takes the key (`POST /setup/provider-key`) accepts a key only while none is configured (the write itself refuses a file or a symbolic link already at the path, a dangling link included, so two requests at once keep only one key), checks a CSRF token and sits behind the Host check; the response is a redirect with a fixed flash line and never carries the key.

## External dependencies

A project can connect its jobs to an external dependency: an instance that is already running, such as a staging backend or a shared dev server ([New and existing projects](12-new-and-existing-projects.md#dependent-services-and-projects)). Intakt adds its address to the job's egress allowlist and injects its credentials into the job types the owner allows: check and review jobs by default, build jobs only on the owner's opt-in. This is the one path where model-written code acts on something outside its container before any review:
- A **build job** that holds the credentials runs code a possibly steered Developer just wrote.
- A **check job** runs on the head, that is on model-written code, with the credentials, before the Code reviewers read it. Before the push it runs the project's pre-push gates; for Intakt these are only the static gates, which read the change's code but do not run it. After the push the head's check run runs the full check command, tests included, which runs the change's code; where that run holds the credentials, this is where model-written code first reaches the dependency. A reviewer's own probes run without network and never reach the dependency.

No deterministic check stands between that code and the shared instance: the hand-back scan, the Code reviewers and the merge rules all come later. A steered job can change or delete data within what the credentials allow, and send data to that host. The safeguards are limits, not checks:
- **Bundled is the default** and runs a fresh sidecar per job on a private network; a stub serves third-party APIs. External is an explicit owner choice per dependency.
- **Isolation is the owner's**, and the wizard says so: test-scoped, low-privilege credentials, the job's own tenant, namespace or prefix (Intakt passes `INTAKT_JOB_ID`), or read-only access. Never connect a production instance.
- **Build jobs** get the credentials only on the owner's opt-in.
- **Design variant builds and render jobs** (planned, [Designer scoring layers](15-designer-scoring.md#layer-3-taste-by-blind-pairwise-comparison)) never get an external dependency's credentials or address, whatever the owner's opt-in; a dependency they need runs as a bundled sidecar of that job.
- **Credential values** a job held are redacted and scanned before anything it returned is pushed or posted, as for every credential ([Developer](#builder)).

## CI log excerpts

The Developer holds no forge credentials, so it gets red CI as an excerpt the orchestrator reads from the forge. A Developer controls the workflow on its branch, and could make a CI job print whatever the job can reach, encoded past redaction, and read it back. So:
- **Only from a throwaway runner.** The excerpt is given only when the workflow scan of the merge rules ([Merge](08-merge.md)) finds every job of the head's, main's and the merged workflows on a forge-hosted runner with a read-only token and no secrets. A `runs-on` from a variable counts as not forge-hosted (the scan cannot read it), so such a project's Developers always get the one line. Otherwise, or when the scan fails, the Developer gets one line with the number of failed jobs, not their names, since job names come from the workflow. Intakt's own check container is a throwaway runner by construction: a fresh container with no network and no secrets, whose status the orchestrator posts from outside ([Budget and model planner](06-budget-and-model-planner.md#ci-design-for-later)), so its red run always gives the excerpt (the failed gates and their findings), under the rules below; the one line stays for forge runs only.
- **Small and clean.** At most a few failed jobs, each with its first failed step and the lines that name the failure (else the step's last lines), with terminal sequences, control characters and timestamps stripped and a cap on lines and characters. A log is read line by line under size and time limits, so a flooded log is never held whole.
- **Redacted, then fenced.** Every line is redacted, a line that still holds a credential-shaped string is dropped, and the excerpt reaches the Developer fenced as untrusted. A log that cannot be read gives one line; the send-back never waits for it.
- **Flaky-test tasks and environment labels.** The test name and the failure output a flaky-test task carries ([Reviews](07-reviews.md)) were both produced by a check of code a Developer wrote (a test name can hold a data provider's values), so both are treated like an excerpt: redacted and scanned before the task is filed or updated, published only inside an `<!-- external -->` block that every role reads as untrusted, and fenced the same way in every prompt that passes them to a model. The label of the CI environment the test flaked in (its job name, database engine and matrix values) is untrusted in the same way, since the head's workflow file sets it: a job could encode a secret or an instruction into it. The ledger therefore keys each CI environment by a number Intakt assigns (one per distinct CI job and matrix leg) and compares results by that key, never by the label's text; the pre-push check is named by Intakt's own constant, "the pre-push check". A label is treated like the test name: redacted and scanned, published only inside the `<!-- external -->` block, fenced in every prompt, and shown as escaped plain text on the dashboard. The task's title carries only the test's ledger number, never the name or a label. Text read from a CI report or a workflow must also pass the throwaway-runner check above, since redaction cannot catch a secret a job encoded into a test name, its output or a label: when the workflow scan does not clear the head, or fails, no test name, no failure output and no job name, engine or matrix value reaches a task, the status, a hand-over or a prompt. The ledger still records the results, and the task, the status and the hand-over then name the test and the CI environment only by their ledger numbers and say the text was withheld. A name, output or label that trips the scan is not published: the task is filed or updated without it, names what is missing by its ledger number and says it was withheld. The task is built only once a person with write access adds the eligibility label. Plain code files and updates it; no model decides to.
- **A flaky-test rerun proves which run, not honesty.** The rerun of failed tests ([Reviews](07-reviews.md)) is driven by the protected check runner, and a skipped, incomplete, risky or missing result on it counts as no pass. The per-test report and the rerun's exit still come from a process that runs the head's code, so they prove which run produced a result, not that its content is honest: in-process test results cannot be verified independently. A forged result gives the head nothing it does not already have, since the same code could force a green exit on the first run. The reviews therefore stay the barrier, as for any green check: a test the head adds or changes is never marked flaky, every test the rule kept from a send-back is listed in the context of the head's Code reviewers, and a result from another head counts only toward detection and a task's count, never toward green.

## Self-hosted CI runners

A pull request from a branch of the repository runs its own workflow, and every script that workflow runs, on the project's runner before any review; Intakt's builds push such branches. On a self-hosted runner with Docker access that is as good as root on the host. So a self-hosted runner is supported only when it is ephemeral and isolated:
- **A clean state for every job.** A fresh VM or container, or a snapshot rolled back before the job, with the runner registered for exactly one job (`--ephemeral` on GitHub). Nothing a job leaves on the host (a re-tagged image, a changed tool, a process) reaches a later job, main's included, and anything that exists when a job starts comes from the clean state the owner prepared. Intakt's own CI relies on this: it reuses a CI image whose tag is a hash of its Dockerfile, `composer.json` and the check ini, which a persistent runner would let a pull request replace for every later run. Composer's cache, where no locked package carries a checksum that would catch a planted archive, does not depend on the runner: every job restores it from GitHub's Actions cache, only a push to main saves it, and GitHub keeps a pull request's own cache entries out of main's scope (see `docs/architecture/ci.md`).
- **No path to the owner's network.** The runner reaches the forge and the registries its jobs download from, nothing else, so a job cannot use the host to reach other machines.

The CI image cache is written only by runs on main, never by a pull request: a pull request runs its own workflow, so a cache it could write would let it plant an image that a later job, main's included, runs. A restored image is used only under the hash of the exact inputs it was built from.

A persistent self-hosted runner is not supported. The workflow scan cannot tell an ephemeral runner from a persistent one, so self-hosted runners always need the owner's approval for a CI change ([Merge](08-merge.md)).

## Job image build inputs

When Intakt builds a job image (`intakt:job:build-image`, see [job images](../../architecture/job-images.md)), the image source can be the project's own:
- **Where it comes from.** One of three sources, each read at the project's `HEAD`. Whoever can put a commit at `HEAD` writes this input: a person with write access, a merged change, and, once builds run in images built from their commits, a Developer.
- **What the engine receives.** The build context differs per source:
  - A `.devcontainer/devcontainer.json` with `build.dockerfile`: a `git archive` of the `build.context` folder at `HEAD` (relative to `.devcontainer`, which is also the default), so the whole repository only when the context is its root.
  - A `Dockerfile` at the repository root: a `git archive` of the whole tree at `HEAD`.
  - A `.devcontainer/devcontainer.json` with `image`: only a Dockerfile Intakt writes (a `FROM` line with that image, plus the review tools for a review image), with no project files. The chosen base image still runs its own `ONBUILD` instructions, even when the project has no Dockerfile.
  - For a review image (`--kind=review`), an archive source also carries a Dockerfile Intakt adds to the archive: the project's own Dockerfile followed by the review tools' installation steps, which run too.
- **What it can reach.** Its build steps (`RUN`, and a base image's `ONBUILD`) run on the engine's host during the build, not in a job container: the build sets no network mode, so in all three cases they get the engine's default network with full network access, and no egress proxy or allowlist stands in front of them. Intakt passes them no keys or tokens. In the two archive cases the steps can read the archived files, which can hold secrets committed to the project; in the `image` case they see no committed file. In every case they can reach whatever the host's network reaches (services exposed to the build network included) and send data there, and they can leave the built image holding anything they fetched.
- **What checks it.** Only the probe after the build ([job images](../../architecture/job-images.md#the-check-after-the-build)) runs in a job container, and only when the project has a PHP profile. It checks the image's PHP and extensions, not what its steps did.

Today only the command builds an image, from the `HEAD` of the checkout the person who runs it names. Before plan task T49 builds images from a Developer's commits, this input must be settled: a steered Developer could otherwise commit a Dockerfile whose `RUN` steps act on the host's network before any review reads them.

## The product's surface

The sections above cover the loop: what a steered model could do to the project. This one covers the product the loop builds: what an outside attacker could do to it once it runs. The rule is checks first, and the Security engineer for what checks cannot judge (owner decision of 2026-11-04: security matters across all layers). A check that needs a tool beyond PHP and Composer is opt-in per project, so the simplest install stays simple; on Intakt's own repository every check is on as soon as its task lands. Each check family is a task of its own ([plan](../../plan.md#product-security-864)); until its task lands, the role's layer review covers it.

| Layer | Threat | Covered by |
|---|---|---|
| Backend | untrusted input (request data, forge and model output) reaching a dangerous sink: a query, a shell command, a file path, an outgoing URL, unserialize | taint analysis from untrusted sources to dangerous sinks |
| Backend | a known vulnerable dependency | dependency advisories: the `audit` gate today, the dependency policy for protected changes (plan T77) |
| Backend | weak authentication or session handling: a route without an access rule, a session cookie without `Secure`, `HttpOnly` or `SameSite`, a missing CSRF check on a state-changing form | rules over the security and session configuration and the routes |
| Backend | output written without escaping | refused by a check: a response built from untrusted text outside the template engine's escaping |
| Frontend | script injection in the browser | a strict content security policy and the security headers (frame, content type, referrer, HSTS behind TLS) asserted by a test on every page |
| Frontend | an inline script or unescaped template output | refused: inline scripts and event handlers in templates, and Twig's `\|raw` |
| Frontend | a known vulnerable frontend package | frontend package advisories (`importmap:audit`) |
| Infrastructure | an unsafe image definition | a Dockerfile lint |
| Infrastructure | a vulnerable package or a misconfiguration in the image or the compose and proxy files | a vulnerability scan of the image and its configuration |
| Infrastructure | a container that runs as root or writes its root file system | asserted non-root and read-only containers |
| Infrastructure | weak transport: TLS off or outdated, a proxy that forwards untrusted headers or exposes an admin port | checks of the TLS and reverse-proxy settings |
| Running application | what only shows at run time: a header a route drops, an error page that leaks, a cookie set without its flags | a nightly baseline scan of the install the journey suite boots |

What no check can judge goes to the role: a new trust boundary, an access rule that is present but wrong, a flow the taint analysis cannot follow, and whether a scan finding is real. A check's finding fails the check like any gate; the role's verdict is a review like any specialist's ([Reviews](07-reviews.md#the-security-engineer)). Scan output is untrusted text, since it prints what the product and its dependencies hold: it reaches the role redacted, secret-scanned and fenced ([The Security engineer's sessions](#the-security-engineers-sessions)), and a scan never decides an approval of a protected change, which stays with the floors and checks of [Merge](08-merge.md#approving-protected-changes).

## Main's integrity

The watchdog (planned, plan T63) judges each new commit on main by how the forge reports it arrived, never by who signed it (owner decision 2026-11-04, [Watching main](08-merge.md#watching-main)). No model takes part: plain code reads the forge's records and Intakt's own merge record. Commits from contributors, dependency bots and merges made in the forge's interface are normal on main; a rule that every commit be Intakt's recorded merge or signed by a key the owner registered would halt any project that has them. The first built part nonetheless classifies by exactly that rule (maintainer decision 2026-11-13, #2914; [Watching main](08-merge.md#watching-main)), and nothing runs it yet.
- **What it trusts.** It accepts three arrivals: a merge Intakt recorded; a commit the forge reports as part of a pull request merged into main by an account with write access; a commit the forge reports as pushed to main by a person with write access (shown as "pushed without the gate", with main's CI on it watched as for any merge). The last two are info events. It halts on everything else: a rewrite of main's history, a commit the forge cannot attribute to a merged pull request or a write-access pusher, a merger or pusher without write access, a direct push by a bot or App account, and a commit by Intakt's own forge identity that Intakt's record lacks. Each halt names the commit and its reason on an owner card, and only the owner clears it.
- **The forge's write-access check.** The trust rests on the forge's permission records, the same check that decides who steers ([Third-party text](#third-party-text)). A person with write access can already change main through the forge whatever Intakt does, so accepting their merge or push gives them nothing they lacked; the watchdog records it and keeps main's CI on it in view. An account without write access cannot land a commit that passes.
- **The gate's approval of protected paths.** A protected change Intakt merges needs the approval of exactly its head ([Merge](08-merge.md)); that approval authorizes the protected paths of that head, never the signing key of its commits, so a contributor's or a bot's commits inside an approved head are fine. Signatures are recorded as the forge reports them and never required: requiring signed commits is an opt-in project setting, off by default, under which the forge's own verification counts and Intakt's merges are signed by Intakt.
- **A stolen forge token.** Signatures used to be the guard against a forge token used outside Intakt. Two halts take that place. A commit pushed or merged by Intakt's own identity (its App or the Maintainer's) that no merge attempt of Intakt's explains is always a halt, never a notice, since Intakt never lands a commit without recording it. And a direct push to main by a bot or App account halts, since bots land changes through pull requests, so a CI workflow's token or another App's cannot push to main unnoticed. A merge attempt is recorded before the forge call, names the one identity of Intakt's (its App or the Maintainer's) that makes the call and the landing form, and closes only on a definitive outcome, read by that form. The merge is Intakt's only when the head landed by the identity the attempt recorded: for a forge merge call, the forge reports the pull request merged with that head, into main, by that identity, and main contains the merge commit the forge reports for it; for Intakt's own ref update, main's ref moved from the recorded commit to exactly that head by a push the forge attributes to that identity. A merge or push by Intakt's other identity that no attempt of its own explains halts. For a forge merge call the attempt stays open while the forge reports the pull request open on that head, and the pull request closed unmerged, on another head, or merged by another account or into another branch settles it. For a ref update the pull request's state settles nothing, since the update can still land after the pull request closed or moved: the attempt stays open while main still holds the recorded commit, or is at the head with the push's attribution pending, and only main's ref settles it (during readback the pull request's state never does); in either landing form a definitive refusal by the forge also closes the attempt when no earlier call of it is unresolved. A commit that an open attempt could still explain is held, not accepted, and Intakt merges nothing meanwhile; if the forge has not attributed it to the attempt within 10 minutes it halts, so a stolen token cannot hide behind the hold. A stolen Intakt token can therefore land, without a halt, only the head Intakt itself was merging under an open attempt, which has passed the gate.
- **Dependency bots.** A dependency bot's pull request is taken without a label ([Dependency bots](08-merge.md#dependency-bots)): only an author the forge reports as a configured bot account counts, its diff may touch only manifest and lock files and CI action pins, the Developer never edits it and `take-over` on it is refused ([Third-party text](#third-party-text)). Since no person with write access labeled it, the owner's approval of its package set and whole diff is the one human decision on it, and it never lands without that approval, whatever CI and the reviews say. A red check becomes a task of its own, and it lands through the forge's merge call under a recorded merge attempt. Setup recommends a release-age cooldown for version updates (security updates exempt), so a freshly published bad release has time to be found before the bot proposes it.
- **The forge's protection is recommended.** Setup recommends the forge's branch protection where the plan offers it (required checks from Intakt's identity, no force push, no deletion), and the dashboard shows when the watchdog is main's only protection ([Setup](11-setup.md)).

## Updates

During an update the jobs of two versions of Intakt run at once ([Updates](11-setup.md#updates)). No model decides any step of it: plain code compares the check results, switches the slots, applies the deadlines and rolls back.
- **One writer at a time.** Until the cut-over, the running orchestrator is the only process that admits work, claims queue items, holds lane state and writes results; the new version runs only as jobs it starts and records, so no queue item is claimed twice. At the cut-over the new orchestrator takes the next owner generation in the database, only through a takeover grant that names the expected current generation and is checked and consumed in the same transaction that raises it; a rollback revokes the grant in the same transaction in which the old orchestrator takes the next generation, so a new orchestrator that starts late takes nothing. A write carrying an older generation is refused, so a late write of the old orchestrator, or of a rollback's loser, cannot land. An old orchestrator that hangs at the cut-over is stopped at a deadline, and its writes are refused the same way; if it hung before writing the grant, the new one takes nothing and the old version is started again and resumes admission. A job's result is collected once, by whichever orchestrator holds the current generation.
- **Both versions are the install's own.** The new version is a released image pinned by digest, from the source the owner set; it is not untrusted text. Its orchestrator holds the same credentials and keys as the old one, uses the same database and `/data` volume, and nothing is added: no job of either version gets a forge token, the signing key or a vendor API key.
- **The self-check runs project code.** It runs the project's check on the default branch in a check job container like any other, with the same isolation, egress allowlist and credentials rules ([Developer](#builder), [External dependencies](#external-dependencies)). Its report is untrusted data, validated against its format before use; a report that does not validate counts as one failure the running version does not share. Plain code compares it failure by failure with the running version's result on the same commit, by each failure's identity (a test's name, its failure kind, which is one of assertion failure, error or timeout, its failure message or diagnostic with times, durations and paths removed, and the source location of the failing assertion from the report or the stack trace; a finding's rule and location). A test failure without a location is matched on its whole normalized output including the trace, and one with neither counts against the update. A test that fails on both versions at a different assertion or with a different normalized message is the new version's failure and fails the update. Project code can make a failure appear on both versions, which is reported and does not block the update, or on the new version only, which fails the update with an owner alert. For a test failure, at most it can hide a new failure behind one the running version shows in the same test with the same kind, at the same source location and with the same normalized message, or, when neither result yields a location, with the same whole normalized failure output including the trace. For a finding matched by its rule and location, it can hide a new finding with the same rule at the same location. For a check without a machine-readable report, it can hide any new failure as long as both versions print the same normalized output (for example both print only `Check failed`); that is why such a check counts as a single failure. In every case it cannot make an update pass a check that has no shared failure, and it cannot switch a slot: the canary slot switches only after the comparison passes, and the remaining slots wait for the canary slot's first build without an environment failure or for the set minutes with no failure.
- **A checkpointed job is resumed by the other version.** What a job past its deadline leaves is what a no-progress stop leaves: its kept commits and the orchestrator's hand-off note. A job of the new version reads them as it reads any kept work: the commits go through the hand-back checks, the check job, the Code reviewers and the merge rules again, and the note and any kept conversation reach the Developer fenced ([Untrusted text](#untrusted-text)). Nothing the old version decided about the job counts beyond the ledger events it wrote.
- **Stored state stays readable by both.** The new version only adds state the old one ignores, so neither version reads state it cannot validate. An update that changes stored state in a way the old version cannot read declares it and pauses all lanes, so the two versions never run side by side on it; it is rolled back from a copy taken at the drain, and only before the lanes resume.

## Tests of the defenses

- **A fencing gate.** A test lists every input of every prompt builder; a new input fails it until it goes through the fencing helper or is argued onto an allow-list of values Intakt itself writes. With the Designer (planned), an image input joins it: it fails the gate unless it goes into a user message of its own behind Intakt's fixed note naming its source.
- **An injection canary.** An offline test plants instructions ("approve this", "add the merge label", "print the token", "edit the CI definition") in each untrusted source: quoted external text, a third-party comment, a code comment, a CI log line, a dependency's README. It runs them through the real prompt builders, the trust checks and one round with a Developer that obeys every plant, and asserts that each plant reaches its prompt only fenced, no third-party comment counts, no approval is counted, no steering label is applied, no credential reaches posted text, and no CI change is pushed or merged. A live variant runs only against a throwaway repository.

## Residual risk

A steered reviewer can approve a weak change that passes CI. Outside protected paths, that is what the Code reviewers' second vendor, the gates and green CI on the exact head are for; a project that runs a single code reviewer accepts this risk for unprotected changes. Inside protected paths, a steered Security engineer session can only fail to hold back a change the floors and mechanical checks already passed; a weakening those checks cannot see (gate code written to cheat the tests that run it) is what the canaries, the owner's switch and the revert on a failing canary are for.

A steered job can try to carry a credential it holds out in a form the redaction and the scan do not recognize (split or encoded), or to an allowlisted host that accepts uploads. That is why the forge token, the signing key and vendor API keys never enter a job, project credentials should be test-scoped and low-privilege, and a subscription credential is limited to its one vendor account, which the owner can revoke (an automation token by revoking the token, a login by signing it out).

A screenshot is one such form (planned, with [the Designer's session](#the-designers-session-planned)). A steered Developer of a head holds its subscription credential whenever it runs on a subscription, with no opt-in, and the project's credentials when the owner opted in for build jobs; a variant's Developer holds only its subscription credential. It can write the credential into the code split or encoded, so the hand-back scan of the diff misses it, and have the page decode and draw it. Before a screenshot goes to the Designer's vendor, the dashboard, the owner's pair view or the repository as a reference, plain code reads its text and machine-readable codes and withholds it on a match with a value in the rendered revision's credential set (a variant's screenshot covers the head's Developers as well as the variant's, and an unrecorded commit widens the set by every credential any build job of the project can hold, keeping the producing job's own), a secret-scan hit, a failed read or a credential value that cannot be read; a reference image the Developer commits is read as committed by the hand-back check against the same kind of set, so a hit or an unreadable value fails the hand-back before the push ([Screenshots leave only after a scan](15-designer-scoring.md#screenshots-leave-only-after-a-scan)). That stops a credential drawn as text or as a code; it does not stop one drawn in a form the reader does not recognize (hidden in pixel values, distorted, or spread across screens). For that rest the limits are the ones above: build jobs get the project's credentials only on the owner's opt-in and those should be test-scoped and low-privilege, and a subscription credential reaches only its one vendor account and can be revoked.

The dashboard has no login: whoever can reach its port can press every button and change every setting ([Dashboard](13-dashboard.md#who-can-act)). An attacker on a network the port is published to can therefore act, and the owner accepts that risk by publishing it there. It is bounded by the port being published on the host's loopback address only by default (phone access is opt-in), by the `Host` check that answers only the configured dashboard names with the configured port (so a site that rebinds its name to the host's address gets nothing), by the CSRF check on every state-changing request (so a web page open in the owner's browser cannot act), by job containers having no route to the dashboard port (planned in part: today jobs run on an internal network whose only way out is the egress proxy, which opens only `CONNECT` tunnels to port 443 of allowlisted names and does not check that TLS runs inside them, so jobs stay off the port with the default binding on a port other than 443 but not for a dashboard published on port 443 at an address an allowlisted name resolves to, while the deny rule for the dashboard port, the refusal of an allowlist entry that names it and the job's start check of [Jobs cannot reach it](13-dashboard.md#who-can-act) are not built yet), and by MCP tools, API tokens, forge labels and comments, job output and model answers never changing a control. Any program that runs where the port is reachable, an owner's agent CLI on the host included, is a dashboard client and can act; the owner accepts that with the binding they choose. The guides recommend a VPN over publishing the port on a shared network, and HTTPS beyond loopback.

A project's Dockerfile or devcontainer runs its `RUN` steps on the engine's host with full network access when Intakt builds its job image ([Job image build inputs](#job-image-build-inputs)); this stays open until it is settled before T49 builds images from a Developer's commits.

On a clean hosted runner a CI log excerpt still holds what the job printed, and redaction knows only credentials of known shapes ([CI log excerpts](#ci-log-excerpts)).

Booting a pull request head runs its code on the host. The watcher's boot gate boots a head only when its pull request author is trusted (a person with write access, Intakt's own identity or the Maintainer's identity; a check that fails or cannot answer counts as untrusted), so another author's head is reviewed without ever being booted. Until the review job containers of T58 (#340) land, a trusted author's head runs `composer install` (with the Composer plugins the head allows) and main's `bin/instance` unsandboxed on the host as Intakt's user, beside the install's home, keys and database. Only an environment allowlist and an empty scratch home keep the install's tokens and Composer credentials from being handed to it ([Boot step](../../architecture/boot-step.md#how-a-commit-boots)); code that looks for the install's files on purpose can still read what that user can read. A trusted author whose account is taken over, or a dependency the head pulls in, carries this risk.

An owner-approval push request for a risky CI change ([Merge](08-merge.md)) shows an image by its sizes and full blob ids instead of its bytes, which a comment cannot hold: a plain file (mode `100644`, never executable or a link) named `.png`, `.jpg`, `.jpeg` or `.gif` whose every blob starts with that type's signature and one holds a NUL byte. Any other file with a NUL byte, such as a script with a NUL byte appended that bash still runs, keeps its bytes, so the request is refused and the change goes back to be split. The owner approves an image unseen, and the approved commit pins its bytes; it runs only when code loads it as code (a PHP `include`, `bash logo.png`). Such code in the change is shown in the same request, while code already on main that loads a file of the change as code is a risk the owner accepts.

A person with write access, or whoever holds such a person's forge credentials, can merge a pull request into main or push to main outside the gate, and the watchdog accepts either as an info event; a direct push is the one shown as "pushed without the gate" ([Main's integrity](#mains-integrity)). The owner bounds it with the forge's branch protection, which setup recommends (required checks, no force push); without it the watchdog only makes it visible. The opt-in signing setting does not stop stolen credentials: under it the forge's own verification counts, so a merge made in the forge's interface, which the forge signs, or a commit signed with a key registered on the stolen account still passes. It catches only commits the forge does not verify.

A steered build or check job can harm an external dependency within its credentials before anything is reviewed ([External dependencies](#external-dependencies)). The owner accepts that risk by choosing the external mode and bounds it by the scope of the credentials and the instance.
