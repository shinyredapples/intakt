# Reviews

- **The Code reviewers' panel is configured, not fixed** (formerly the review panel): any number of reviewers, each a setting of the panel (a model tier from a vendor, a prompt, its probes and its budget), not a role of the team of its own ([Overview](01-overview.md#the-team)), with a quorum policy per project (for example all must approve, a majority, or one strong reviewer plus one other) and rules for which changes get which panel (more reviewers for protected paths or large changes). The default is two reviewers from different vendors when both are available, on every head, documentation and test changes included. With one reviewer (a one-account install, see [Budget and model planner](06-budget-and-model-planner.md)), the panel adds a second review, another model tier of the same vendor, only for protected paths, security-relevant changes and large changes; other changes get one review, because there is no second vendor to ask. A stand-in or substitute reviewer, catch-up reviews and the verdict step work with any panel size.
- **Each reviewer setting can carry its own skill.** A reviewer setting names a focus file in the project (for example a security, framework, test or documentation reviewer): a checklist of what to look for and recipes for the probes to run, added to that reviewer's prompt. The panel rules choose which reviewers see which change (the [Security engineer](#the-security-engineer) for changes that match a layer's triggers, a documentation reviewer for user-facing pages). Skill files are protected paths, so a change cannot weaken the reviewers that judge it.
- **A fixed core panel plus specialists the change calls for.** The project's core panel reviews every pull request under its quorum rule. Specialists (settings of the panel, not roles of the team) are added on top when a trigger matches: the changed paths (for example input handling or security configuration), a `review:<specialist>` label on the task, the task's class or size, or the Tech lead's reading of the task's text (for example "parses user input" adds the Security engineer's backend review). Each specialist is blocking (it must approve like the core panel) or advisory (its findings become follow-ups), and judges only what its skill covers. Triggers only ever add reviewers, never remove one or shrink the core panel; the trigger rules are protected like the skill files. For a protected change every blocking reviewer classifies its protected part on each head it reviews, and a loosening or missing class on the current head sends it to the owner (a class from an older head counts for neither); the Security engineer's security review and penetration test judge it apart from the panel, and a second vendor is never required ([Merge](08-merge.md#approving-protected-changes)).
- **A stand-in reviewer only when it saves something.** Replacing the scarcer vendor on an intermediate head with a cheaper reviewer pays off only when that vendor's window is tight and only if the stand-in rejects; when both approve, the scarcer vendor still has the last word on the same head and the stand-in's review was pure cost. Intakt therefore uses a stand-in only when the scarcer vendor's measured use is near its ceiling on every account of that vendor the reviewer's role may use (another account of the same vendor is a move, not a stand-in), never to a head whose last change is a merge of main, and records each superseded stand-in approval so its cost is visible. A stand-in is not a substitute: when every account of the scarcer vendor is out, a substitute of another vendor reviews the final head instead, its verdict can be the last one, and a catch-up review is owed (below).
- **The core panel reviews a head in parallel.** No reviewer waits for another's approval, and a rejection by one reviewer does not cancel the others on the same head, so the Developer gets every finding in one rework. Gating the scarcer reviewer behind a cheaper one saves its review on every head the first rejects, but each blocking finding only the scarcer reviewer would raise then costs an extra build cycle once the first approves, and a build cycle costs several reviews. Measured on 465 heads that two reviewers of different vendors reviewed in parallel: both approved 212, only the cheaper rejected 108, only the scarcer rejected 29, both rejected 116. A gate would have skipped the scarcer reviewer on 224 heads (about 48% of its reviews), but on 75 of the 116 heads both rejected (65%) it raised blocking findings the other did not (117 of its 240, 23 of them P1). With a build cycle at about four times one review (about 195k against 48k tokens), the skipped reviews would save about 10.8M tokens, while each extra cycle costs a build plus the review it triggers (about 243k), so the 75 extra cycles cost about 18M, plus a round-trip per head. Gating pays only while one reviewer's unique blocking findings appear on few of the heads both reject (here below about 38%); the panel's measured overlap on those heads is what would justify revisiting this rule.
- **Review capacity follows build capacity.** Reviews run in as many parallel review workers as the configuration allows, each claiming a different head, so two workers never review the same head and a head's panel still runs as one review round. Merges stay one at a time across the whole install: every worker hands an approved head to the one landing step ([Merge](08-merge.md), one path for landing), which lands a single head at a time under one install-wide lock, so two workers never merge at once, whichever project their heads belong to. Measured: in a build loop running beside Intakt, one review worker for three Developers left the Developers idle 158 times in a day at the cap on heads waiting for review, while the review models ran only about 5 hours of that day.
- **A catch-up review runs by itself and its findings become tasks.** When a head merged with a substitute's verdict in a reviewer's place (every account of that reviewer's vendor was out, so another vendor's reviewer of the same tier reviewed the final head; see [Order of use](06-budget-and-model-planner.md#order-of-use)), Intakt queues that reviewer's catch-up review of the merged change (the diff against main as it merged) and runs it on its own once the reviewer's vendor has room again, merges touching sensitive paths first, then oldest, never ahead of a live head waiting for that reviewer. The reviewer gets the task and the change, not the substitute's review, so its verdict stays independent. A rejection is filed as a new task naming the merged pull request, with the whole review inside an `<!-- external -->` block (see [Threat model](14-threat-model.md#untrusted-text)): Intakt is the task's author, but the review it carries is model output that read steerable code, so it stays fenced as untrusted however the task is later edited or labelled, and the text Intakt writes around it (the pull request, the reviewer, the merged commit) gives no instructions of its own. The task body is redacted and scanned like any review text before it is filed; a hit files nothing and counts as a failed catch-up. The task takes no steering label from the merged task: like any task, it is built only once a person with write access labels it, so a review that read steerable code never starts a build on its own. An approval's follow-up items go to the follow-up inbox like any review's follow-ups (below); a clean approval closes the catch-up. A catch-up that returns `blocked` or no valid verdict is tried once more on another account of the same vendor; when that fails too, it goes to the Maintainer as a hand-over and shows as failed. Every run counts as an attempt (the first, the retry, and each run the Maintainer starts); after three failed attempts in all it is given up with one owner notice naming the merged pull request (plan T66). A failed catch-up never blocks or reverts the merge. A pull request still open when the reviewer is back needs no catch-up: the reviewer reviews its current head as usual. The queue, each catch-up's state and a catch-up that keeps failing are on the dashboard.
- **Reviewers can run code.** Each review job may write small tests or scripts and run them against the exact head in a no-network sandbox, within a per-review budget (files, calls, time), through the same narrow, checked path for every vendor. A finding should carry its probe's output; nothing a probe writes reaches the pull request. On the first day with probes, about a quarter of the reviewer's findings carried that evidence (2% before), and they caught real bugs the Developer's tests and CI had passed (an edge value still accepted after a fix, a setting lost after a reconnect), in rounds where the reviewer without probes approved. The verdict schema has an `evidence` field per finding (probe file and output), so the verdict step can weigh a demonstrated finding over a read one. A probe that shows a defect goes back to the Developer with its finding, fenced as reviewer output and cut to a size limit, with the instruction to add it as a regression test that fails before the fix.
- The verdict is a typed object (enums, nested lists) that the Platform's structured output fills and the Validator checks; anything else is a failed review (below), which never approves. The `codex` provider cannot hold an answer to a schema, and `claude_code` holds it only when its CLI returns a structured output (otherwise its answer is the result text), so for them alone exactly one plain top-level `json` block in the answer (three backticks and `json` at the start of a line, closed by a line of three backticks, not inside another fence) is read as the verdict before it is mapped and validated, and an answer that is bare JSON from its first to its last character is still read as it is; any other answer (no `json` fence opening and not bare JSON, more than one opening anywhere, or one block in another form) is still a failed review. An approval from these providers still counts only when the review had the review-server access and also reports a confirmed read through it; otherwise it is turned into a blocked verdict. On a head that touches protected paths it also classifies the protected part (`protected`, with a reason; a missing or invalid class counts as loosening; the class counts only for the head it was given on and never carries to a later head; the schema file and the verdict class gain these fields with the review task), which the merge rules read (see [Merge](08-merge.md)). Its JSON shape, which a schema file mirrors as a test oracle (the classification fields join the schema file with the review task):
  ```json
  {"verdict": "approve" | "changes" | "blocked",
   "findings": [{"id": "F3", "severity": "P1" | "P2" | "P3", "file": "...", "line": 12, "symbol": "...",
                 "text": "...", "fixable_by": "builder" | "owner", "repeat": false, "requirement": "...",
                 "evidence": {"probe": "...", "output": "..."}, "regression": false}],
   "resolved": ["F1", "F2"],
   "follow_ups": ["..."],
   "protected": "tightens" | "neutral" | "loosens", "protected_reason": "..."}
  ```
  A reviewer is asked for `approve` or `changes` only: a problem that must stop the change is a P1 finding, not a verdict. A reviewer that still answers `blocked` and names at least one finding is recorded as `changes` with those findings, so every view shows it as a request for changes and the quorum counts it like any `changes` (see the verdict step below). `blocked` is recorded only from Intakt itself: the verdicts it gives when a reviewer could not review or its approval is refused (no tools, stopped, a cut stream, an approval of a change it could not read or was not shown whole). A reviewer's `blocked` without a finding is asked once more and then fails, like `changes` without one. A reviewer's answer of any verdict that gives a finding one of the ids reserved for Intakt's own failed reviews is invalid output: it is asked once more and then fails, also when the diff was cut, so it never counts as a vote whose findings the ledger drops.
  `blocked` means the review could not judge the change (a broken environment, a missing product decision). It does not use up a build cycle: a broken environment goes to the Maintainer (which repairs or re-queues it, and escalates to the owner only what it cannot), a change waiting on something outside it is held and released automatically (see [The Maintainer](09-maintainer-agent.md)), and only a missing product decision the Maintainer cannot make reaches the owner. `fixable_by: owner` findings take the same route.
- **A failed review is no verdict.** A review that returns no valid verdict (invalid output, a crash, a timeout, a cut stream, a text that trips the secret scan) never approves. It also uses no review cycle and never sends an unchanged head back to the Developer: counted as "changes", failed reviews used up cycles on heads nobody had judged. The same reviewer is asked once more at once; a second failure parks the head for that reviewer as unavailable, with one notice, and a later wake asks it again. It never hands the head to a stand-in or a substitute, because a Developer could provoke the failure (a diff or output that breaks the reviewer) and so pick its reviewer. A failed review next to another reviewer's rejection is only recorded; the rejection goes to the Developer.
- **Feedback goes to the Developer only when the Developer can act on it on its branch.** A Developer on a pushed pull request can change its branch and nothing else: it cannot split its task, open another task or change anything outside the repository. Anything else is never sent to the Developer first, because a Developer sent back with work it cannot do spends a build and leaves the change waiting. A split goes straight to the Maintainer as a hand-over. A change outside the repository follows the hold rules instead: the task is put on hold and released on the event that could change the outcome (a move of main releases it into a build that merges main, never into a review of the unchanged head), and only after a few fruitless releases does it reach the Maintainer (see [The Maintainer](09-maintainer-agent.md)).
- **A head that needs main is rebuilt or split, never reviewed again unchanged.** An open finding that names a conflict with main or an update the branch needs from main is no reason to review the same head again, however often main moves: each such review spends the whole panel, the finding stays open, and the head is held again. A conflict only in registry files is merged by Intakt without a build ([Merge](08-merge.md)); otherwise the head goes once to a build from current main (a build that merges main) if the task has build cycles left, otherwise to the Maintainer as a hand-over. When that build leaves the finding open, the task goes to the Maintainer instead of back into a hold that every move of main would release.
- **A second hand-over of the same task is a split.** When the Maintainer gets the same task handed over a second time, whatever the cause of either hand-over and however the first one ended, it splits the task instead of re-queuing it, since the task already stalled once after a hand-over and the next re-queue would most likely end the same way. A task first handed over for a broken environment and later for a finding that needs main is split on that second hand-over, not re-queued. The owner routes of [the Maintainer](09-maintainer-agent.md) stand: when the task cannot be split, it goes to the owner. A branch over the review size limit (below) is never queued again for a build or a review: the Maintainer splits it on its first hand-over. The one exception is a head whose moved text the move check takes out of the measure (below): what it measures within the contract is reviewed, not split.
- **An oversized head goes to the Maintainer, not to the reviewers.** Every pushed head is measured again against the size contract (see [Choosing work](03-choosing-work.md)), from the changed lines in the forge's diff and without a model call, after the move check (next rule) has taken out the text it proves moved. A head past the split tier is not reviewed, since a review of it would cost more than its size contract allows, and it is not sent back to the Developer, which cannot split a pushed pull request. It goes to the Maintainer, which splits the task, or the pull request when there is no task and it was opened by the owner's or the Maintainer's identity or carries `take-over` (anyone else's oversized pull request gets one size-limit comment instead; see "Pull requests Intakt did not build" below), with the existing split and `Source:` rules; the hand-over names the head's size and the tier it passed. A change that can be split takes the split route of [#944](https://github.com/shinyredapples/intakt/issues/944) and [the Maintainer](09-maintainer-agent.md); the next rule is for a change a split does not fit.
- **A head that only moves text is measured without the move.** A deterministic move check, plain code with no model call, compares the removed and the added lines of the whole change (the diff between the merge base and the head). A removed line that reappears byte-identical among the added lines counts as moved, also when the only difference is a link rewritten to point at the text's new page, and both its removal and its addition leave the size measure. The matching is one to one: each match consumes one removed occurrence and one added occurrence, so two identical removed paragraphs need two added copies, and a removed or added occurrence left without a partner counts toward the size like any other changed line. A line the merge of main carried into the moved text ([Merge](08-merge.md#a-head-that-moves-text)) never counts as moved, so a carried edit is never hidden as a move. The size contract then applies to what is left: a head whose remainder is within it gets a normal review of that remainder only, and every verdict on it states that the moved text was checked by the move check and not read. A head whose remainder is still past the split tier goes to the Maintainer as above. The check covers text files under `docs/` only: code is never measured this way, because a moved line of code can change behavior through what surrounds it (another scope, another order, another import), so every changed line of code counts toward the size. For every run of moved lines the check puts its enclosing Markdown context on the old page and on the new page in the remainder, even when those lines are moved or unchanged: the heading path (the nearest heading above the run, with the headings it sits under) and every ancestor line of the run in the Markdown structure (the parent list item at each indent level, the line that opens an enclosing block quote, the header row of an enclosing table, the opening line of an enclosing fenced block). This is needed because a context line can itself match as moved, or exist unchanged on both pages, and still frame different text after the move, as when a line moves between two parent list items under the same heading. When the two contexts differ, the reviewers read both and judge whether the moved text still means the same in its new place. When they are the same, the reviewers see that the context did not change. The check proves only that the moved text is unchanged and that its structural context is shown: a sentence elsewhere on the page that qualifies the moved text is not part of that structure, a risk accepted because the check covers only `docs/` and the reviewers still read the whole remainder. Every hand-over and every approval request for a head in this route names each step still needed for its merge (the owner's approval, any label, the merge of main that carries edits into the moved text; see [Merge](08-merge.md#a-head-that-moves-text)), so the owner never has to find one by reading code. Reason: measured on 2026-11-07, a task that split one large architecture README into topic pages produced a 710 thousand character diff, far past the review limit and moved text by design. Splitting a single move leaves pages half moved, so it was reviewed by hand: one review cost a full Maintainer session on text that had not changed, and the owner approved it, but it could not merge without a label nothing had mentioned.
- **Red CI comes before any reviewer.** CI runs on the pushed head first, and red CI sends it back to the Developer with a CI log excerpt as its findings (see [Threat model](14-threat-model.md#ci-log-excerpts)), so no review is spent on it. The pre-push check runs only the project's pre-push gates (for Intakt its static gates), so CI is where the rest of the check runs ([Overview](01-overview.md), the head's check run is the Developer's check). A red run of Intakt's own check container (a fresh container with no network and no secrets, whose status the orchestrator posts from outside, see [Where checks run](06-budget-and-model-planner.md#ci-design-for-later)) goes back with the failed gates and their findings, redacted and fenced like any CI excerpt. A red forge run names them only when the workflow scan clears the head's runners; otherwise, or when the scan fails, it carries only the number of failed jobs, as the threat model sets. CI can also fail for what no check of the Developer covers (another database engine, a runner fault), so two red-CI send-backs in a row are free within a cycle and the third counts as one; a reviewer's verdict starts the count again.
- **A flaky test is no send-back.** The rerun lives inside the check job only. Wherever the tests run (in CI, and in the pre-push check of a project whose pre-push command runs tests; Intakt's pre-push gates run none), the tests gate (for Intakt, the `tests` gate with its JUnit reports) reruns only the failed tests, once, on the same checkout and in the same environment, never the whole suite and never more than once. When every failed test passes its rerun and every other gate passed, the tests gate passes, so the check job itself is green: such a head is never sent back, and red CI keeps the rule above unchanged, since a green job is not red CI. Intakt never reruns a whole CI job for a flaky test and never holds a head for one. Green comes only from a pass on the rerun: a test that fails both its run and its rerun is a failure of that run under the usual rules (in CI, the red-CI rule above), also when the ledger already knows it as flaky; the hand-back then names its flaky-test task, so the Developer does not chase it.
  The orchestrator records each test's result in the ledger from the tests gate's per-test report, with the environment it ran in and the tree that run tested. The environment is the pre-push check or one CI job and matrix leg (for example a job on another database engine): the ledger keys each CI environment by a number Intakt assigns, one per distinct CI job and matrix leg, and the pre-push check by Intakt's own constant. A CI environment's label (its job name and matrix values) is written in the head's workflow file, so it is untrusted text like a test's name: the ledger keeps it only to recognize the same environment again. The tree is the one the run checked out: for the pre-push check the tree of the commit the check runner checked out, and for a pull request's CI run the tree of the commit the run checked out (on GitHub the merge commit of the pull request with its base), read from the forge's run metadata, never from the report. Results are compared only by that tree and that environment key, never by the head's SHA alone and never by a label's text, since another run on the same head can test another merge tree once the base moved. A test is flaky when it failed and passed in the same environment on the same tree: it passed its rerun, or it failed on one head and passed on another head whose tested tree is identical. A pass in one environment never makes a failure in another flaky, in either direction: a test that passes the pre-push check and fails in a CI job on another database engine is not flaky by that. Results on another head with an identical tree count toward detecting a test as flaky and toward its task's count, never toward turning a run green.
  The reviews stay the barrier, as for any green check. The rerun is driven by the protected check runner (for Intakt, `bin/check` and `config/gates/`, which are protected paths), not by the head's code, and a skipped, incomplete, risky or missing result on the rerun counts as no pass. A test the head adds or changes can never be marked flaky: its failure goes back to the Developer under the usual rules, rerun pass or not. Every test the rule kept from a send-back is listed, by ledger number and with its environment, in the context of the head's Code reviewers. The report and the rerun's exit still come from a process that runs the head's code: the runner and the forge's metadata prove which run produced a result, not that its content is honest. A forged result gives the head nothing it does not already have, since the same code could force a green exit on the first run, so that judgment belongs to the reviews.
  For each flaky test, plain code keeps one task labelled `priority:urgent` that carries the test's name, the environment it flaked in, its latest failure output and how often it flaked: a later flake updates that task (its count and latest output) and reopens it when it was closed, never opening a second one. The environment is named as "the pre-push check" (Intakt's own words) or by the CI environment's ledger number, with its label beside the test's name. The test's name and its failure output both come from code a Developer wrote (a test name can hold a data provider's values), and a CI environment's label comes from the head's workflow file, so all three go into an `<!-- external -->` block, redacted and scanned before the task is filed or updated, and a label or text from a CI report is used only when the workflow scan clears the head's runners, else the task carries none of them, names the test and the environment by their ledger numbers and says the text was withheld; the task's title names the test only by its ledger number and never holds a label, and the task is built only once a person with write access adds the eligibility label, like a task proposing a check (below; [Threat model](14-threat-model.md#ci-log-excerpts)). The task asks for a fix that proves the cause with a forced-order test that fails on the old code, never by repeated runs ([Principles](../02-principles.md)). The dashboard lists a flaky test until a fix is verified: a pull request built from its task has merged, and after that merge the test has passed, on a tree that holds the fix, in every environment it flaked in, without flaking since. A merge alone never clears it, since the test may not have run there yet, and a test that did not run counts as no pass. A fix that removes the test on purpose is verified instead when the merged pull request says so, its panel approved it, and the test is absent from a complete run of the tests gate in each such environment on a tree that holds the fix (never a rerun of failed tests, a filtered run or a run that stopped early, where an absent test proves nothing). A task closed without that merge leaves the test listed ([Dashboard](13-dashboard.md)).
- **The Developer checks where CI runs.** The Developer's sandbox, the pre-push check and CI run the same image, built from one definition, so the Developer's own check and CI see the same tools. A test that needs a tool declares it in the requirements page (for Intakt, `docs/architecture/requirements.md`), and the pre-push check looks each declared tool up before it runs anything: a missing one fails the check with the cause `environment`, never first in CI. That cause is not the Developer's to fix, since the image's definition is protected: the head is not sent back to the Developer and takes the environment route instead ([The Maintainer](09-maintainer-agent.md)). Reason: a test needed a tool the CI image lacked while the Developer's sandbox had it, so the Developer's check passed, every rebuild failed CI the same way, and the Developer could not change the image.
- **A review step never waits without a ceiling.** Waiting for CI, for a reviewer slot or on a merge of main ends after a set time (for example 20 minutes), so one head that can never proceed cannot hold a review worker while others queue. A wait at its ceiling is classified and repaired without a model, or ends as stalled and the head goes back to its queue with its place kept; the details are in [Merge](08-merge.md#waiting-for-ci).
- **A cancelled CI run is no verdict.** A new push cancels the run of the head it replaces, and a review that started on the old head once read that cancellation as red CI and handed the pull request over, although nothing had failed. A cancelled run is therefore never red CI: it is ignored when a newer run of the same event and the same pull request exists on the same head, and a remaining cancelled run is waited on like unfinished CI, never a send-back and never a merge. The exception covers waiting and the missed-CI recovery only: when Intakt cancelled a run itself because it could no longer matter, that run is recorded as Intakt's cancel and nothing waits on it ([Merge](08-merge.md#waiting-for-ci)). When nothing restarts a cancelled run Intakt did not make, it takes the missed-CI path of [Merge](08-merge.md#waiting-for-ci): a closed or merged pull request goes to the Maintainer, a head that conflicts with main gets the checked registry-file merge or else the route of a head that needs main (above), except on a dependency bot's pull request, which waits for the bot's next head, and any other head gets one re-trigger and goes to the Maintainer once only if CI still does not start.
- **A file that loses most of its content is stopped before review.** The pre-push check compares each changed file with main: a file that shrinks to a small fraction of its size (for example under a fifth, and more than 50 lines lost) fails the check with the file named, unless the task's plan names that file as removed or rewritten. A Developer once replaced two documentation files with the single line `1`, and only the merge conflict it caused brought it to light.
- **A build tries its own change before it asks for a review.** The [Definition of Done](../01-intent.md#definition-of-done) stays the one statement of done; this bullet adds what the Developer tries first. (1) For each acceptance item the build states the measured result, and a build with an unmet item says so instead of asking for a review. (2) The build checks each docs sentence it changed against the code and searches the docs for the same claim elsewhere. (3) A build that adds a rule, parser or gate tries the other forms of its input, and tests each error path and each limit boundary it adds. (4) These are instructions to the Developer: they change no review, no gate and no merge rule, and a reviewer does not send a change back only because a build lacks such a statement. Reason: measured on 2026-11-07 across the builds since 2026-11-01, both reviewers approved the first reviewed head of about 42% of merged issues and a merged issue took about 2.2 reviewed heads, and a sample of the 225 P1 and P2 findings on the last 90 merged pull requests read as real defects of these kinds (acceptance not met or not measured, docs that state what the code does not do, a rule or parser that handles one form of its input, error paths and limits never exercised).
- **The head must boot where main boots.** For a project with a boot command (the app starts offline, answers and stops), every head is booted once before any reviewer runs. A head that fails while main boots goes back to the Developer, counted like red CI. Main's result is cached per main commit and per fingerprint of the boot and probe tools, so a broken tool is told apart from a broken head: when main fails too, the gate is off for that head and the tool is an infrastructure alert, never a send-back.
- **A canary checks the probe path.** After a passing boot, one fixed probe of Intakt's own runs through the same path as a reviewer's probes and must print its known line. A failure is compared with main's canary; a broken probe path is an infrastructure alert and the reviewers run with probes marked unavailable, so a broken tool never reads as a finding against the head.
- **Reviewers check how the code reads.** Besides correctness, every reviewer checks the principles of [How code reads](../02-principles.md#how-code-reads) explicitly: story readability (does the entry method read as named steps, can a newcomer follow the flow), needless abstraction (an interface, factory or base class without a second real case), duplication of knowledge, and comments that say what instead of why. Such a finding cites the rule it breaks in `requirement`.
- **Findings keep their ids across rounds.** A reviewer copies the open ids, lists the fixed ones under `resolved`, and marks a finding that came back as `repeat`. From the second round on, a new blocking finding must be a regression (the reviewer sets `regression`) or cite a requirement of the task; anything else is lowered to P3 in code, before the verdict is stored, so the panel and the ledger see the same severity; a repeat keeps the severity it was first stored with. Reviewers cannot move the goalposts.
- **Re-reviews see what changed.** A reviewer gets the full diff the first time, then a scoped re-review: its own earlier verdicts and the delta from the head it last reviewed, without what a merge of main brought in. After its own approval it judges only that delta and reopens untouched code only for a P1; a new P2 or P3 on code it already saw is a follow-up. It falls back to the full diff when the old head is not an ancestor, the delta conflicts or is too large, or it touches generated, vendored or lock files. Saved earlier reviews only choose what a reviewer is shown; they never count as a verdict on the new head.
- **Reviewers do not re-flag what `bin/check` passes.** A reviewer does not send a change back for a rule a `bin/check` gate enforces and passes (for example a constructor with more than three parameters, which the parameter limit exempts on purpose), also when the gate is wrong or misses a case: that gap gets a gate issue, not a send-back and not prose for `AGENTS.md` ([Principles](../02-principles.md)), so the reviewer reports it at most as a [P3] that names the gate in `requirement`.
- **Owner-proved evidence is the owner's.** An Evidence item the task marks owner-proved (`(owner provides)`) is never a reason to send a change back, since the Developer cannot produce it: a finding that asks for it is not blocking. Such items are listed for the owner, who proves them before the merge. Sizing already sends back a task with an unproducible item that lacks the mark ([Definition of Ready](../01-intent.md#definition-of-ready), [Choosing work](03-choosing-work.md), step 3).
- **Reviewers cross-check each other.** In a re-review each reviewer gets the other reviewers' open P1 and P2 findings, fenced as untrusted, and confirms or disputes each in a `cross_check` list of its verdict (the schema gains it with the task that brings cross-checks). A finding is shared only when every counted reviewer raised or confirmed it, so the verdict step passes it on without a model call (next bullet); a finding one counted reviewer confirms and another disputes is not shared and goes to the verdict step's model call, and a finding disputed while its holder still holds it on the same head goes to the escalation review instead of the Developer.
- **The Code reviewers' verdict step** (formerly the judge) sits between the reviewers and the next build, and it is plain code when the reviewers agree. When every counted reviewer approves, plain code records the approval with no model call; when that round also carries a finding that may be deferred (a P3 or a follow-up), one model call still runs, only to mark those findings, and the approval stands whatever it marks (an act mark can start the polish round below). When every blocking finding is shared (every counted reviewer raised or confirmed it, none disputed it), plain code applies the escalation rule first (see Escalation on recurrence below): a shared P1 that recurs in the same place goes to the escalation review, and only the other shared blocking findings go to the Developer as act, with no model call. A shared blocking finding never goes through the model, also when the same round carries a finding that may be deferred: the model call that round still needs marks only the deferrable findings. A model call runs only for disagreements and deferrals: a blocking finding that not every counted reviewer shares, and a finding that may be deferred (a P3 or a follow-up). That one cheap call marks each such finding act, defer or reject, against the task's acceptance criteria and its stated non-goals. A `defer` turns only a P3 or a reviewer's own follow-up item into a follow-up task. A blocking P1 or P2 that the model marks `defer` or `reject` stays on the act list, with the model's reason kept beside it as a note: the model sorts, merges and judges P3 findings and can never remove a P1 or P2. The model only suggests which findings share a cause; plain code keeps such a link only when both findings sit in one hunk of one file, a few lines apart, before it merges their act-list entries. Today one model call marks every finding of a round; the plain-code part is planned. A P3 finding that is a local edit in a file the change already touches and needs no new design (docs or guide wording, a name, a comment, a missing assertion or test case for behavior the change adds) is act; defer is only for a finding that needs its own design or tests, or files outside the change. The Developer only sees what to act on. The round's outcome and its act list agree: once the verdict step is done, a reviewer's `changes` counts for the quorum as changes only when one of its findings is on the act list, as that reviewer's approval with follow-ups when all its findings are P3 and the verdict step marked every one defer or reject, and otherwise as `blocked` (a finding the quote check dropped, a P3 left without a mark, a failed review), so a round that ends as `changes` always names what to change and the Developer is never sent back with nothing to act on. Only the counted vote changes: the reviewer's verdict is shown and stored as it gave it. A round judged before votes were counted keeps the verdicts as given.
- **A polish round** (planned, plan task T59) comes when every counted reviewer approved a round and the verdict step marked findings act: the change gets one polish rework, limited to the act list, before the merge. Its re-review covers only the polish delta, by one reviewer, and blocks only on a P1. The verdict step's marks of a polish round are not filed, so no follow-up starts from it. The rework has its own budget: one attempt, about 5 minutes without a new commit, instead of the build's no-progress limit. If the polish rework fails, CI is red or the delta review blocks, the approved head merges without the polish commits and the act items become one follow-up task, so a polish round never costs a change its approval; on a pull request that builds a follow-up task the act items are listed in the merge note and dropped instead (next bullet). A per-project setting, on by default, turns the polish round off.
- **No follow-ups from follow-up pull requests.** A pull request that builds a follow-up task files no new follow-up task, so review follow-ups stop breeding further ones (in a week of 302 merged pull requests, 44 of 159 traceable follow-ups came from a pull request that itself fixed a follow-up, each costing a full build, CI and two reviews for polish-level change). Its approvals' act items still go through the polish round before the merge as for any change. Its deferred P3 items are listed in the merge note and dropped: not filed and not sent to the follow-up inbox. A P2 a reviewer itself raised as a follow-up item (a re-review's new P2 on code it already saw) is filed as today.
- **Fixed blocking findings teach the next Developer.** A P1 or P2 finding that was fixed feeds the list of recurring blocking findings in the Developer's briefing, so the same kind of finding is caught before the push instead of in another round (see [Shared project memory](10-shared-project-memory.md)).
- **Findings that recur become checks.** A briefing line only asks the Developer to look; a check makes sure. When the project memory's resolved-findings index (see [Threat model](14-threat-model.md#writing-project-memory)) shows the same kind of finding on several changes (for example three), plain code files a task proposing a check for that kind: a gate rule, a docs-impact check (a statement left stale, a required docs update left out) or a line in the Developer's checklist. At most one proposal per kind is open, and a kind whose proposal a person closed is not proposed again. The task names the kind and the changes it came from, and quotes example findings inside an `<!-- external -->` block, redacted and scanned like a task filed from a catch-up review, since they are model output that read steerable code. Like any task it is built only once a person with write access labels it, so accepting a proposed check stays the owner's choice, and the rules on gates still apply (a new gate needs the escaped defects it would have caught, which the proposal lists; see [Principles](../02-principles.md)).
- P1 and P2 block. Deferred P3s and follow-ups go to a follow-up inbox, not straight to the task list, except those of a pull request that builds a follow-up task: its deferred P3s never reach the inbox, also when they come from a catch-up approval after the merge note was published (they are added to that note and dropped). A P2 follow-up item a reviewer raised on such a pull request still goes to the inbox; a P1 or P2 finding the verdict step marks `defer` never does, because it stays on the act list. The inbox works like this: the Tech lead's next call over the inbox merges each one into an open task it belongs to, queues it with a priority, or lets it expire after a set time. A follow-up queued from a non-blocking finding joins the next open milestone after its original's, skipping closed ones (its original's when no later one is open), one that carries a blocking finding a reviewer raised as a follow-up item keeps its original's, and each names its original's milestone so a person can move it back ([Choosing work](03-choosing-work.md), step 5). Next-milestone routing is the default; the owner can list it for [bounded tuning](06-budget-and-model-planner.md#bounded-tuning). Open follow-ups never pile up unseen.
- **Escalation on recurrence.** The ledger counts, per (file, symbol), how many rounds flagged it. A P1 flagged in the same place in two rounds, or a disputed finding, goes to an escalation review: a reviewer on a stronger tier judges that one finding on the head. If it confirms, the next build runs on a stronger model and the reviewer that raised it re-reviews; if it rejects, the holder re-reviews with the escalation's reasons attached. The escalation's verdict is kept per finding, keyed by a hash of the finding's text and a hash of every file it names at the head, and the same finding on unchanged files reuses it instead of asking again, which could give a second, contradictory verdict. A finding that names no file, or a path that is not a regular file in the checkout, gets no key and is judged again. A third time goes to the Maintainer, which decides it and asks the owner only for a decision it cannot make. The same check or test failing in two rounds in a row also goes to the Maintainer, instead of spending the rest of the round.
- **A verdict counts only for what it reviewed.** Each verdict carries an identity: the head commit, the base commit, the task's revision, the check commands and the review policy. If any of them changes, the verdict no longer counts. Two exceptions save review budget: a merge of main into the branch without conflicts, and a change that touches only documentation, keep the verdict for the parts they did not touch; only the touched parts are reviewed again. A kept verdict never keeps its class of the protected part: on the new head every blocking reviewer classifies the protected part again, and until it does, that head has no valid class from it ([A panel reviewer's class](08-merge.md#hard-floors)).
- **The forge shows the same review the orchestrator counted.** Each review job gets a one-time token that its posted review must contain; the orchestrator matches the forge review to the verdict it received before counting it.
- **Pull requests Intakt did not build.** One opened by the owner's or the Maintainer's identity goes through the same panel on every new head, without a label. Anyone else's pull request is reviewed only after a person with write access labels it, since its author is not trusted. The one exception is a pull request whose author the forge reports as one of the project's dependency bots: it is taken without a label, and only a diff in the manifest and lock files and the CI action pins is reviewed ([Merge](08-merge.md#dependency-bots)). A dependency bot's pull request is never taken over: `take-over` on it is refused once with a comment, as for a pull request that touches protected paths, and it stays on the bot path (the bot rebases it, the owner approves it, a red check becomes a task of its own); it never becomes an Intakt task, the builder never edits its branch and its commits are never listed for the builder ([Merge](08-merge.md#hands-off-and-take-over)). Without `take-over` the others keep this rule: reviewed, findings as one comment, never reworked. With `take-over` from a person with write access on any other such pull request, it becomes an Intakt task: the Developer reworks the open findings on it and it is reviewed and approved like Intakt's own, and on its original branch it lands by the forge merge call ([Merge](08-merge.md#hands-off-and-take-over)). The label is what vouches for building on it, because the reason for not reworking was an untrusted author.
  - *An oversized one is split by who opened it.* A head past the split tier on a pull request opened by the owner's or the Maintainer's identity is not reviewed: it goes to the Maintainer as a split, with no `take-over` needed, since these identities are trusted and building from their head is safe. Anyone else's oversized pull request is not split: it gets one comment saying it is past the size limit and asking the author to split it, and once a person with write access sets `take-over`, it is split the same way ([The maintainer agent](09-maintainer-agent.md)). The Maintainer records the split plan first, and plain code checks every changed path or hunk of the diff from the merge base to `<sha>` against it before it is recorded. Each part is a task naming `Source: <branch>@<sha>` of the original head, cut along files where possible, each under the split tier, stating its merge order when it links to another part. Once every part's pull request is open or merged, plain code checks that the parts add up to the pinned diff: each part's head as its pull request was opened, applied in merge order to the merge base, must give the tree of `<sha>`. A part whose pull request was closed without merging counts as missing. The same check also reads each part as it stands now: an open part's current head and a merged part's merged change must carry exactly its share, nothing dropped and nothing added, and applied in merge order they must still give that tree; until every part has merged, a new head of a part that drops or adds an edit is refused before review, and a part closed without merging after the original was closed reopens the original. With a missing part or a mismatch the original stays open and goes back to the Maintainer and, the second time, to the owner; when the check passes, Intakt records the verified head in the split plan, closes the original with a comment naming the parts and that head, never force-pushes its branch and never deletes it, reads the head again right after the close and reopens the original to extend the split if it moved, and updates open issues whose text names the original to name the parts, as the Maintainer's edit. Commits on the original branch after `<sha>` get more parts, checked against the diff from the old `<sha>` to the new head, not against hunks of the merge-base diff, and the close check stays that all parts, applied in order, give the tree of the new head.
  - *Never skipped in silence.* Intakt never skips a pull request opened by the owner's or the Maintainer's identity without saying so. When any rule except `hands-off` keeps it from reviewing or merging one (`hands-off` still takes precedence and Intakt posts nothing on the pull request; for example a branch it may not push to, a path it may not touch, a missing approval), it posts one comment on that pull request naming the rule and what would let it proceed, once per head, and shows the pull request under [Waiting on you](../mocks/waiting.html) when a person has to act. A pull request by anyone else without the label stays unanswered, as before: an untrusted author gets no comment, except the one size-limit comment on a head past the split tier (above). Why: a build loop running beside Intakt silently skipped branch names outside its accepted prefixes, and a pull request the owner opened sat for an hour with green CI and no review.
  - *Send-backs move no labels.* Findings go back as one comment, and the pull request keeps the labels people gave it, so a review round never undoes a person's steering.
  - *The owner is asked once, at the end:* a dependency bot's pull request always needs that one approval, whatever paths it touches ([Merge](08-merge.md#dependency-bots)). The owner is asked when CI is green on the head, every review approves and the head merges cleanly with main; a head still in review or sent back asks nothing, except an owner decision plain code reads from the head, which is asked when it first appears ([Merge](08-merge.md)). A dependency bot's approval is never such an early question: it is asked only at the end, also while its lock files or action pins are protected paths, so the owner never approves a bot head whose red check is about to become a task. The approval follows the merge rules ([Merge](08-merge.md)); on the owner's own pull request, where the forge does not let an author review, it is the `approve <sha>` comment.
  - *Priority is the owner's or the Maintainer's.* A `priority:urgent` or `priority:high` label counts on such a pull request only when its latest label event came from the owner or the Maintainer; anyone else's counts as normal. An urgent one goes before every task head; a high one ranks like a high task. Without a counted priority, these pull requests and task heads take turns, so neither starves. A priority label orders work that is due anyway; it never authorizes a review or a merge.
  - *A limit mid-review:* a review cut off by a vendor limit before its answer starts streaming starts again on another account of the same vendor and is never continued by another vendor; when no account of that vendor has room, the stand-in and catch-up rules apply ([Budget and model planner](06-budget-and-model-planner.md#a-limit-never-loses-work)). One cut off by a limit or an outage after its first answer delta has streamed is not started again: its verdict is `blocked` with the cut stream as its reason. A stream that ends early without a limit or an outage behind it is tried once more without streaming, and the reviewer ends `blocked` only when that try is cut too.
  - *An unchanged pull request costs no reads:* it is read again only when its head or update time changed, or after a set interval.

## The Security engineer

The Security engineer (#864) covers the security of the product being built, across infrastructure, backend and frontend. Checks come first, and the role reviews what checks cannot judge: a new trust boundary, an access rule that is present but wrong, a flow the taint analysis cannot follow, whether a scan finding is real. The checks per layer and the threats they cover are in [The product's surface](14-threat-model.md#the-products-surface); a check that needs a tool is opt-in per project and on for Intakt's own repository.
- **A review per layer, triggered by paths.** Each layer has its own path triggers and its own focus file, and a change whose paths match a layer's triggers gets that layer's review, as a blocking specialist on top of the core panel. The triggers are the project's, for example for Intakt:
  - *Backend:* input handling, controllers and routes, security and session configuration, forge and model clients, anything that runs a process or builds a query. Focus: taint from untrusted input to a sink, authentication and session handling, unescaped output.
  - *Frontend:* templates, assets and the import map, response headers. Focus: the content security policy and the security headers, inline scripts, Twig's `|raw`, frontend packages.
  - *Infrastructure:* the Dockerfile, the compose files, the reverse-proxy config, the boot harness. Focus: image contents, non-root and read-only containers, TLS and proxy settings, exposed ports.

  A change that matches several layers gets one review with each matching focus file. The focus files and the triggers are protected paths like every skill file and trigger rule (above), so a change cannot weaken the review that judges it. The review gets the results of the layer's checks on the head, redacted, secret-scanned and fenced ([Threat model](14-threat-model.md#the-security-engineers-sessions)), so it judges what they cannot instead of repeating them; it does not re-flag what a passing check covers (above).
- **A monthly audit.** Once a month the role reads the trend of every layer's scan results (new, fixed and recurring findings, the nightly baseline scans of the running application included, each report redacted and secret-scanned before the model reads it; a layer whose checks have not landed yet is reported as not covered, never as clean), checks that the [threat model](14-threat-model.md) still matches the product, and files each finding as a task: a scan finding nobody fixed, a threat the model lacks, a check family a recurring finding calls for. Like a task from a catch-up review, the task carries the audit's text inside an `<!-- external -->` block and is built only once a person with write access labels it; a check family beyond those of decision 25 still needs the escaped defect it would have caught ([Principles](../02-principles.md)).
- **Protected changes.** For a protected change the role runs the security review and the penetration test the approval needs, formerly the gatekeeper's security reviewer and attacker sessions (the attacker is now the penetration tester), apart from the panel; the approval itself stays plain code with the owner's two floors ([Merge](08-merge.md#approving-protected-changes)).
- **Handing an item back.** This covers Intakt's own tasks as well as a pull request given `take-over`. It never covers a dependency bot's pull request: `take-over` on it is refused (above), and removing `hands-off` from it puts it back on the bot path with nothing given to the Developer ([Merge](08-merge.md#hands-off-and-take-over)). When `hands-off` is removed, or `take-over` is set, the head as it now stands is the task's head. The head gets one full review by every reviewer; earlier findings are checked against it rather than carried over, since the code under them changed. Commits made by hand use up no review cycle, because the cycle limit guards the Developer's loop, not a person's work. The Developer is given the commits pushed while a person drove (hash, author, subject, files) as work to build on, never to revert ([Threat model](14-threat-model.md#builder)).

## The Designer (planned)

The Designer (`designer`, #863, [Overview](01-overview.md#the-team)) shapes and reviews user-facing work: flows, states, copy, layout across screen widths and accessibility. Without it, user-facing quality rests on Code reviewers reading diffs, and nothing in the design covers accessibility, usability or user flows. Nothing in this section is built yet.

- **Active only where there is a user interface.** The role runs only for a project with a user interface, and there only for a task whose paths or labels touch it. The triggers are the project's, like the Security engineer's layer triggers (above): path triggers (for example templates, assets, styles and the controllers that render pages) and a label on the task. The role runs before the build, when there is no diff yet, so a path trigger is matched against the files named in the task's plan ([Choosing work](03-choosing-work.md), step 4). A project without a user interface, or a task that touches none of it, never calls the role, so it costs nothing there. Like every trigger rule, the Designer's trigger rules live in protected files.
- **It adds to Ready before the build.** For a task its triggers match (a user-facing task), before the build starts, the Designer adds to the task's plan what *Ready* needs for it ([Definition of Ready](../01-intent.md#definition-of-ready), point 3): the flows; every state (empty, loading, error, success); the copy; the layout at the three widths (phone, tablet, desktop); and the accessibility needs. The Tech lead still owns *Ready*; a task the triggers match is not *Ready* until the plan carries these additions, so neither an approval of the plan nor `plan:skip` starts its build before then. A task the triggers do not match, in any project, needs none of them.
- **Tools are opt-in.** The tools the role can use (axe-core, Lighthouse, a headless browser) are opt-in per project and run in the check environment, never in the role's own session, so the simplest install needs none of them.
- **How it scores.** The Designer judges user-facing work in three layers: objective checks that block, a rubric with evidence whose low scores are review findings, and taste learned from the owner by blind pairwise comparison ([Designer scoring layers](15-designer-scoring.md)).

## The Test engineer (planned)

The Test engineer (`test_engineer`, #1297, [Overview](01-overview.md#the-team)) keeps the test suite and the CI pipeline lean and fast without losing what the tests prove. Every other role sees one change at a time: the Developer writes the tests of a change, the Code reviewers judge the tests in a diff, and the Maintainer settles hand-overs. Nobody owns the suite as a whole. Measured on this repository (30 green CI runs to 2026-11-10): 389 test files and 3451 test methods; one file (`tests/Application/InstanceTest.php`, 121 s median) bounds the wall time of the `tests` gate, and the gate tests start 33 separate `bin/check --only=phpstan` sandbox runs where 13 would prove the same. Two test pull requests merged on 2026-11-09 each moved tests worth a few seconds out of the `serial` group while the files that cost minutes per run stayed as they were. Nothing in this section is built yet.

- **Opt-in.** The role joins the team of #862 as an opt-in role: a new project starts without it, so the simplest first install needs none of it.
- **What it owns.** A time budget for the `tests` gate and for each test file (measured by the gate's elapsed time in CI and by every file's time in `tests/durations.json`; the gate line's `slowest` list names only the ten slowest files, so it points at them but is not the measure, see [Quality gates](../../architecture/quality-gates.md#the-test-time-budget-planned)), redundant and low-value tests, the split between unit, integration, gate and journey tests, flaky tests (#860), the journeys (#859) and the speed of the CI workflows. It does not own a change's own tests (the Developer) or the review of a diff's tests (the Code reviewers).
- **A scheduled audit, never an edit.** On a schedule, plain code builds a deterministic report: the gate's elapsed time and every file's time (slowest first), test count and lines per folder, `bin/check` sandbox runs per gate test and the tests in `serial`. A model pass then reads the folders the report flags. Each finding, whatever its kind (a budget overrun, a redundant or low-value test, a misplaced test, a flaky test, a slow journey or CI workflow), becomes a `ready` task: one written to meet the [Definition of Ready](../01-intent.md#definition-of-ready). Like a task from the Security engineer's audit, it carries the audit's text inside an `<!-- external -->` block and is built only once a person with write access labels it ([Threat model](14-threat-model.md#the-test-engineers-session-planned)). The role never edits a test itself.
- **No coverage is lost.** A task that removes or merges a test names, for each removed case, the test that still proves the behavior; a behavior with no other proof is not removable. Coverage of `src/` must not drop. A claim about time is measured in CI before and after, never estimated alone.
- **Limits.** A change to a protected path, such as a CI workflow, keeps the approval of protected changes ([Merge](08-merge.md#approving-protected-changes)). The role never changes a gate's strictness, the checks or the approval rules.
