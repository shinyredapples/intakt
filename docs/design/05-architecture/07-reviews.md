# Reviews

- **The review panel is configured, not fixed:** any number of reviewers, each a role (a model tier from a vendor, a prompt, its probes and its budget), with a quorum policy per project (for example all must approve, a majority, or one strong reviewer plus one other) and rules for which changes get which panel (more reviewers for protected paths or large changes, one for docs). The default is two reviewers from different vendors when both are available. With one reviewer (a one-account install, see [Budget and model planner](06-budget-and-model-planner.md)), the panel adds a second review, another model tier of the same vendor, only for protected paths, security-relevant changes and large changes; docs-only and test-only changes get one review. A stand-in or substitute reviewer, catch-up reviews and the judge step work with any panel size.
- **Each reviewer role can carry its own skill.** A role names a focus file in the project (for example a security, framework, test or documentation reviewer): a checklist of what to look for and recipes for the probes to run, added to that role's prompt. The panel rules choose which roles see which change (a security role for changes to input handling or secrets, a documentation role for user-facing pages). Skill files are protected paths, so a change cannot weaken the reviewers that judge it.
- **A fixed core panel plus specialists the change calls for.** The project's core panel reviews every pull request under its quorum rule. Specialist roles are added on top when a trigger matches: the changed paths (for example input handling or security configuration), a `review:<role>` label on the task, the task's class or size, or the triage step's reading of the task's text (for example "parses user input" adds the security role). Each specialist is blocking (it must approve like the core panel) or advisory (its findings become follow-ups), and judges only what its skill covers. Triggers only ever add reviewers, never remove one or shrink the core panel; the trigger rules are protected like the skill files. For a protected change every blocking reviewer classifies its protected part, and a loosening or missing class sends it to the owner; the security reviewer and the attacker judge it apart from the panel, and a second vendor is never required ([Merge](08-merge.md#approving-protected-changes)).
- **A stand-in reviewer only when it saves something.** Replacing the scarcer vendor on an intermediate head with a cheaper reviewer pays off only when that vendor's window is tight and only if the stand-in rejects; when both approve, the scarcer vendor still has the last word on the same head and the stand-in's review was pure cost. Intakt therefore uses a stand-in only when the scarcer vendor's measured use is near its ceiling on every account of that vendor the reviewer's role may use (another account of the same vendor is a move, not a stand-in), never to a head whose last change is a merge of main, and records each superseded stand-in approval so its cost is visible. A stand-in is not a substitute: when every account of the scarcer vendor is out, a substitute of another vendor reviews the final head instead, its verdict can be the last one, and a catch-up review is owed (below).
- **The core panel reviews a head in parallel.** No reviewer waits for another's approval, and a rejection by one reviewer does not cancel the others on the same head, so the builder gets every finding in one rework. Gating the scarcer reviewer behind a cheaper one saves its review on every head the first rejects, but each blocking finding only the scarcer reviewer would raise then costs an extra build cycle once the first approves, and a build cycle costs several reviews. Measured on 465 heads that two reviewers of different vendors reviewed in parallel: both approved 212, only the cheaper rejected 108, only the scarcer rejected 29, both rejected 116. A gate would have skipped the scarcer reviewer on 224 heads (about 48% of its reviews), but on 75 of the 116 heads both rejected (65%) it raised blocking findings the other did not (117 of its 240, 23 of them P1). With a build cycle at about four times one review (about 195k against 48k tokens), the skipped reviews would save about 10.8M tokens, while each extra cycle costs a build plus the review it triggers (about 243k), so the 75 extra cycles cost about 18M, plus a round-trip per head. Gating pays only while one reviewer's unique blocking findings appear on few of the heads both reject (here below about 38%); the panel's measured overlap on those heads is what would justify revisiting this rule.
- **A catch-up review runs by itself and its findings become tasks.** When a head merged with a substitute's verdict in a reviewer's place (every account of that reviewer's vendor was out, so another vendor's reviewer of the same tier reviewed the final head; see [Order of use](06-budget-and-model-planner.md#order-of-use)), Intakt queues that reviewer's catch-up review of the merged change (the diff against main as it merged) and runs it on its own once the reviewer's vendor has room again, merges touching sensitive paths first, then oldest, never ahead of a live head waiting for that reviewer. The reviewer gets the task and the change, not the substitute's review, so its verdict stays independent. A rejection is filed as a new task naming the merged pull request, with the whole review inside an `<!-- external -->` block (see [Threat model](14-threat-model.md#untrusted-text)): Intakt is the task's author, but the review it carries is model output that read steerable code, so it stays fenced as untrusted however the task is later edited or labelled, and the text Intakt writes around it (the pull request, the reviewer, the merged commit) gives no instructions of its own. The task body is redacted and scanned like any review text before it is filed; a hit files nothing and counts as a failed catch-up. The task takes no steering label from the merged task: like any task, it is built only once a person with write access labels it, so a review that read steerable code never starts a build on its own. An approval's follow-up items go to the follow-up inbox like any review's follow-ups (below); a clean approval closes the catch-up. A catch-up that returns `blocked` or no valid verdict is tried once more on another account of the same vendor; when that fails too, it goes to the maintainer agent as a hand-over and shows as failed. Every run counts as an attempt (the first, the retry, and each run the maintainer agent starts); after three failed attempts in all it is given up with one owner notice naming the merged pull request (plan T66). A failed catch-up never blocks or reverts the merge. A pull request still open when the reviewer is back needs no catch-up: the reviewer reviews its current head as usual. The queue, each catch-up's state and a catch-up that keeps failing are on the dashboard.
- **Reviewers can run code.** Each review job may write small tests or scripts and run them against the exact head in a no-network sandbox, within a per-review budget (files, calls, time), through the same narrow, checked path for every vendor. A finding should carry its probe's output; nothing a probe writes reaches the pull request. On the first day with probes, about a quarter of the reviewer's findings carried that evidence (2% before), and they caught real bugs the builder's tests and CI had passed (an edge value still accepted after a fix, a setting lost after a reconnect), in rounds where the reviewer without probes approved. The verdict schema has an `evidence` field per finding (probe file and output), so the judge step can weigh a demonstrated finding over a read one. A probe that shows a defect goes back to the builder with its finding, fenced as reviewer output and cut to a size limit, with the instruction to add it as a regression test that fails before the fix.
- The verdict is a typed object (enums, nested lists) that the Platform's structured output fills and the Validator checks; anything else is a failed review (below), which never approves. On a head that touches protected paths it also classifies the protected part (`protected`, with a reason; a missing or invalid class counts as loosening; the schema file and the verdict class gain these fields with the review task), which the merge rules read (see [Merge](08-merge.md)). Its JSON shape, which a schema file mirrors as a test oracle (the classification fields join the schema file with the review task):
  ```json
  {"verdict": "approve" | "changes" | "blocked",
   "findings": [{"id": "F3", "severity": "P1" | "P2" | "P3", "file": "...", "line": 12, "symbol": "...",
                 "text": "...", "fixable_by": "builder" | "owner", "repeat": false, "requirement": "...",
                 "evidence": {"probe": "...", "output": "..."}, "regression": false}],
   "resolved": ["F1", "F2"],
   "follow_ups": ["..."],
   "protected": "tightens" | "neutral" | "loosens", "protected_reason": "..."}
  ```
  `blocked` means the reviewer could not judge the change (a broken environment, a missing product decision). It does not use up a build cycle: a broken environment goes to the maintainer agent (which repairs or re-queues it, and escalates to the owner only what it cannot), a change waiting on something outside it is held and released automatically (see [The maintainer agent](09-maintainer-agent.md)), and only a missing product decision the maintainer agent cannot make reaches the owner. `fixable_by: owner` findings take the same route.
- **A failed review is no verdict.** A review that returns no valid verdict (invalid output, a crash, a timeout, a cut stream, a text that trips the secret scan) never approves. It also uses no review cycle and never sends an unchanged head back to the builder: counted as "changes", failed reviews used up cycles on heads nobody had judged. The same reviewer is asked once more at once; a second failure parks the head for that reviewer as unavailable, with one notice, and a later wake asks it again. It never hands the head to a stand-in or a substitute, because a builder could provoke the failure (a diff or output that breaks the reviewer) and so pick its reviewer. A failed review next to another reviewer's rejection is only recorded; the rejection goes to the builder.
- **Feedback goes to the builder only when the builder can act on it on its branch.** A builder on a pushed pull request can change its branch and nothing else: it cannot split its task, open another task or change anything outside the repository. Anything else is never sent to the builder first, because a builder sent back with work it cannot do spends a build and leaves the change waiting. A split goes straight to the maintainer agent as a hand-over. A change outside the repository follows the hold rules instead: the task is put on hold and released on the event that could change the outcome (a move of main releases it into a build that merges main, never into a review of the unchanged head), and only after a few fruitless releases does it reach the maintainer agent (see [The maintainer agent](09-maintainer-agent.md)).
- **An oversized head goes to the maintainer agent, not to the reviewers.** Every pushed head is measured again against the size contract (see [Choosing work](03-choosing-work.md)), from the changed lines in the forge's diff and without a model call. A head past the split tier is not reviewed, since a review of it would cost more than its size contract allows, and it is not sent back to the builder, which cannot split a pushed pull request. It goes to the maintainer agent, which splits the task with the existing split and `Source:` rules; the hand-over names the head's size and the tier it passed.
- **Red CI comes before any reviewer.** CI runs on the pushed head first, and red CI sends it back to the builder with a CI log excerpt as its findings (see [Threat model](14-threat-model.md#ci-log-excerpts)), so no review is spent on it. CI can fail for what the pre-push check does not cover (another database engine, a runner fault), so two red-CI send-backs in a row are free within a cycle and the third counts as one; a reviewer's verdict starts the count again.
- **A review step never waits without a ceiling.** Waiting for CI, for a reviewer slot or on a merge of main ends after a set time (for example 20 minutes), so one head that can never proceed cannot hold the review lane while others queue. A wait at its ceiling is classified and repaired without a model, or ends as stalled and the head goes back to its queue with its place kept; the details are in [Merge](08-merge.md#waiting-for-ci).
- **A cancelled CI run is no verdict.** A new push cancels the run of the head it replaces, and a review that started on the old head once read that cancellation as red CI and handed the pull request over, although nothing had failed. A cancelled run is therefore never red CI: it is ignored when a newer run of the same event and the same pull request exists on the same head, and a remaining cancelled run is waited on like unfinished CI, never a send-back and never a merge. When nothing restarts it, it takes the missed-CI path of [Merge](08-merge.md#waiting-for-ci): one re-trigger, then the head goes to the maintainer agent once.
- **A file that loses most of its content is stopped before review.** The pre-push check compares each changed file with main: a file that shrinks to a small fraction of its size (for example under a fifth, and more than 50 lines lost) fails the check with the file named, unless the task's plan names that file as removed or rewritten. A builder once replaced two documentation files with the single line `1`, and only the merge conflict it caused brought it to light.
- **The head must boot where main boots.** For a project with a boot command (the app starts offline, answers and stops), every head is booted once before any reviewer runs. A head that fails while main boots goes back to the builder, counted like red CI. Main's result is cached per main commit and per fingerprint of the boot and probe tools, so a broken tool is told apart from a broken head: when main fails too, the gate is off for that head and the tool is an infrastructure alert, never a send-back.
- **A canary checks the probe path.** After a passing boot, one fixed probe of Intakt's own runs through the same path as a reviewer's probes and must print its known line. A failure is compared with main's canary; a broken probe path is an infrastructure alert and the reviewers run with probes marked unavailable, so a broken tool never reads as a finding against the head.
- **Reviewers check how the code reads.** Besides correctness, every reviewer checks the principles of [How code reads](../02-principles.md#how-code-reads) explicitly: story readability (does the entry method read as named steps, can a newcomer follow the flow), needless abstraction (an interface, factory or base class without a second real case), duplication of knowledge, and comments that say what instead of why. Such a finding cites the rule it breaks in `requirement`.
- **Findings keep their ids across rounds.** A reviewer copies the open ids, lists the fixed ones under `resolved`, and marks a finding that came back as `repeat`. From the second round on, a new blocking finding must be a regression (the reviewer sets `regression`) or cite a requirement of the task; anything else is lowered to P3 in code, before the verdict is stored, so the panel and the ledger see the same severity; a repeat keeps the severity it was first stored with. Reviewers cannot move the goalposts.
- **Re-reviews see what changed.** A reviewer gets the full diff the first time, then a scoped re-review: its own earlier verdicts and the delta from the head it last reviewed, without what a merge of main brought in. After its own approval it judges only that delta and reopens untouched code only for a P1; a new P2 or P3 on code it already saw is a follow-up. It falls back to the full diff when the old head is not an ancestor, the delta conflicts or is too large, or it touches generated, vendored or lock files. Saved earlier reviews only choose what a reviewer is shown; they never count as a verdict on the new head.
- **Reviewers cross-check each other.** In a re-review each reviewer gets the other reviewers' open P1 and P2 findings, fenced as untrusted, and confirms or disputes each in a `cross_check` list of its verdict (the schema gains it with the task that brings cross-checks). A confirmed finding goes to the judge as before; a finding disputed while its holder still holds it on the same head goes to the escalation review instead of the builder.
- **A judge step** sits between the reviewers and the next build: one cheap call marks each finding act, defer (a follow-up task) or reject, against the task's acceptance criteria and its stated non-goals. The builder only sees what to act on.
- **Fixed blocking findings teach the next builder.** A P1 or P2 finding that was fixed feeds the list of recurring blocking findings in the builder's briefing, so the same kind of finding is caught before the push instead of in another round (see [Shared project memory](10-shared-project-memory.md)).
- **Findings that recur become checks.** A briefing line only asks the builder to look; a check makes sure. When the project memory's resolved-findings index (see [Threat model](14-threat-model.md#writing-project-memory)) shows the same kind of finding on several changes (for example three), plain code files a task proposing a check for that kind: a gate rule, a docs-impact check (a statement left stale, a required docs update left out) or a line in the builder's checklist. At most one proposal per kind is open, and a kind whose proposal a person closed is not proposed again. The task names the kind and the changes it came from, and quotes example findings inside an `<!-- external -->` block, redacted and scanned like a task filed from a catch-up review, since they are model output that read steerable code. Like any task it is built only once a person with write access labels it, so accepting a proposed check stays the owner's choice, and the rules on gates still apply (a new gate needs the escaped defects it would have caught, which the proposal lists; see [Principles](../02-principles.md)).
- P1 and P2 block. P3s and follow-ups go to a follow-up inbox, not straight to the task list: the next triage call merges each one into an open task it belongs to, queues it with a priority, or lets it expire after a set time. Open follow-ups never pile up unseen.
- **Escalation on recurrence.** The ledger counts, per (file, symbol), how many rounds flagged it. A P1 flagged in the same place in two rounds, or a disputed finding, goes to an escalation review: a reviewer on a stronger tier judges that one finding on the head. If it confirms, the next build runs on a stronger model and the reviewer that raised it re-reviews; if it rejects, the holder re-reviews with the escalation's reasons attached. The escalation's verdict is kept per finding, keyed by a hash of the finding's text and a hash of every file it names at the head, and the same finding on unchanged files reuses it instead of asking again, which could give a second, contradictory verdict. A finding that names no file, or a path that is not a regular file in the checkout, gets no key and is judged again. A third time goes to the maintainer agent, which decides it and asks the owner only for a decision it cannot make. The same check or test failing in two rounds in a row also goes to the maintainer agent, instead of spending the rest of the round.
- **A verdict counts only for what it reviewed.** Each verdict carries an identity: the head commit, the base commit, the task's revision, the check commands and the review policy. If any of them changes, the verdict no longer counts. Two exceptions save review budget: a merge of main into the branch without conflicts, and a change that touches only documentation, keep the verdict for the parts they did not touch; only the touched parts are reviewed again.
- **The forge shows the same review the orchestrator counted.** Each review job gets a one-time token that its posted review must contain; the orchestrator matches the forge review to the verdict it received before counting it.
- **Pull requests Intakt did not build.** One opened by the owner's or the maintainer agent's identity goes through the same panel on every new head, without a label. Anyone else's pull request is reviewed only after a person with write access labels it, since its author is not trusted. Without `take-over` these keep this rule: reviewed, findings as one comment, never reworked. With `take-over` from a person with write access, the pull request becomes an Intakt task: the builder reworks the open findings on it and it is reviewed, approved and merged like Intakt's own ([Merge](08-merge.md#hands-off-and-take-over)). The label is what vouches for building on it, because the reason for not reworking was an untrusted author.
  - *Send-backs move no labels.* Findings go back as one comment, and the pull request keeps the labels people gave it, so a review round never undoes a person's steering.
  - *The owner is asked once, at the end:* when CI is green on the head, every review approves and the head merges cleanly with main; a head still in review or sent back asks nothing. The approval follows the merge rules ([Merge](08-merge.md)); on the owner's own pull request, where the forge does not let an author review, it is the `approve <sha>` comment.
  - *Priority is the owner's or the maintainer agent's.* A `priority:urgent` or `priority:high` label counts on such a pull request only when its latest label event came from the owner or the maintainer agent; anyone else's counts as normal. An urgent one goes before every task head; a high one ranks like a high task. Without a counted priority, these pull requests and task heads take turns, so neither starves. A priority label orders work that is due anyway; it never authorizes a review or a merge.
  - *A limit mid-review:* a review cut off by a vendor limit starts again on another account of the same vendor and is never continued by another vendor; when no account of that vendor has room, the stand-in and catch-up rules apply ([Budget and model planner](06-budget-and-model-planner.md#a-limit-never-loses-work)).
  - *An unchanged pull request costs no reads:* it is read again only when its head or update time changed, or after a set interval.
- **Handing an item back.** This covers Intakt's own tasks as well as a pull request given `take-over`. When `hands-off` is removed, or `take-over` is set, the head as it now stands is the task's head. The head gets one full review by every reviewer; earlier findings are checked against it rather than carried over, since the code under them changed. Commits made by hand use up no review cycle, because the cycle limit guards the builder's loop, not a person's work. The builder is given the commits pushed while a person drove (hash, author, subject, files) as work to build on, never to revert ([Threat model](14-threat-model.md#builder)).
