# The maintainer agent

The orchestrator is the maintainer: it settles every hand-over it can decide itself, through its maintainer agent, and asks a person only for a decision it cannot make. Most hand-overs never need the owner: a re-queue after a transient failure, a split of an over-size change, a merge conflict, a reviewer misreading, a finding already fixed on the current head, a hit of the secret check (judged while the work is kept, and never settled by skipping the scan; see below and [Threat model](14-threat-model.md#where-model-output-authorizes-something)), a wrong label, reviewers who disagree, a decision the design documents already make. The maintainer agent decides those on the merits and writes the decision into the task description, so the owner sees only what needs a person.
- **It runs as its own identity**, a second, narrower App, never the owner's and never the loop's (one shared bot would make the maintainer's actions count as the loop's own, and let it set the loop's statuses); it runs as a job container that holds only its own credentials, so it cannot reach the orchestrator's forge token or signing key (an empty forge config, a separate git config and tool deny-lists are not enough where it shares a user with them: git and similar tools run commands named in repository config, which the session can write, and anything it launches runs with the same access): it can comment, answer questions, write maintainer decisions into task descriptions (issue bodies), label, split tasks, resolve conflicts on a branch, write the summaries of approval requests (see [Merge](08-merge.md)) and open its own pull request for a stall's protected or environment change (below), but it has no permission to merge, push main, approve, change protections or edit config, and the forge enforces that, not its prompt.
- **Its pushes go through the hand-back.** A conflict resolution leaves its job as a bundle, like a build. The orchestrator checks that it builds on the branch, refuses main and a non-fast-forward push, and tells a merge of main apart from an edit of the CI definition. A merge of main may bring in main's own workflow content: the pushed tree's workflows must equal main's or the branch base's, and each merge commit's workflows must equal one of its parents'. Any other change to a workflow is an agent-authored edit and is refused, since the forge would run it on the project's runners before anyone looked. The one exception is the agent's own pull request for a protected or environment change (see "Every stall gets a cause and a route" below): it has no branch yet, so its bundle must build on the current main and goes to a new branch of its own, never to a task's branch, and its workflow edits follow the CI definition rules of [Merge](08-merge.md), so a risky one stays local until the owner approves its push. Then it re-signs and pushes it. That push guard, not an instruction, is the barrier, because the agent works in a checkout whose content a builder wrote.
- **A usage limit is a wait, not a failure.** A session refused by its vendor's structured usage-limit answer counts no attempt, escalates nothing and runs again once the account has room. Counting it as a failure turned one exhausted window into false "the maintainer failed twice" cards for the owner. The maintainer runs on the same account selection as the jobs, so one switch of account moves it too.
- **Its absence is noticed.** When the maintainer agent has not finished a session for a set time while items wait, or its sessions keep failing, that is an infrastructure alert, and past a grace period an owner card. Items it would have settled stay parked, never dropped.
- **Short-lived and narrow:** one session per batch of new items, a fixed tool list, a step limit, and no shell tools that could reach the forge another way.
- **It decides by default and escalates as a decision.** It asks the owner only when the options are balanced and the choice is a matter of the owner's preference, for money, tax, pricing or legal rules, and for what a bounded number of its own attempts did not resolve. An escalation names the options, its recommendation and why it could not choose, in the owner's "Waiting on you" column. Protected-path changes follow the merge rules (see [Merge](08-merge.md)), not an escalation.
- **It leaves ideas to the owner.** An issue labelled `idea` is for discussion only: the maintainer agent never sizes, triages, splits, labels it as work or answers it as a decision, even when the eligibility label is also set (see [Labels](04-labels.md)).
- **An open pull request never waits on a large task.** When a finished pull request is held only for a part that needs another, larger task (a screenshot of a dashboard not built yet, a recording of a feature still planned), the maintainer splits that part into a follow-up that waits for the larger task, narrows the original task's acceptance to what it delivers now, and releases the hold. Pulling the large task forward instead would let one small pull request reorder the plan.
- **A task that waits on something outside its change is held, not reworked.** When a round leaves the code unchanged because the open finding needs something outside the pull request, the task is put on hold instead of being reviewed again. A hold on another task (`Waits for #n`) releases when that task closes. A wait whose target is a pull request is resolved to the task that pull request closes (its branch or its closing keyword), so the stall of the task that pull request closes is reported with that task's own cause and route (see "Every stall gets a cause and a route" below). A `Waits for` line that names the task's own pull request, or the pull request of its branch, is not a wait: Intakt creates no hold, and the build ends as a hand-over with the builder's reason, routed by its stall cause (for an owner-only file, the protected change route). Any other hold releases on an event that could change the outcome. A hold whose reason is something outside the change, or whose open finding is red CI, is released by a move of main into a build that merges main first (a merge-main rework), never into a review of the unchanged head, because the head can only change through such a build. A deploy of Intakt alone releases into one review of the same head, which returns to hold if nothing changed. The count of fruitless releases stays: only after a few does the task reach the maintainer agent. A finding that names a conflict with main or an update needed from main is the exception: it gets one build from current main if the task allows it, otherwise it goes to the maintainer agent at once, and a build that leaves it open also goes to the maintainer agent rather than back on hold (see [Reviews](07-reviews.md)). When a hand-over of the same task for this same cause (a finding that needs main, or an over-size branch) ended in a re-queue, its next hand-over is a split, never another re-queue. This does not change the owner routes of the re-plan bullet below (a product decision, an open P1 on security, secrets or data integrity, or a retry on the strong tier that fails when the task cannot be split), and an unrelated earlier hand-over, such as a transient failure or a memory kill, does not count. A hand-over that cites red CI follows the CI excerpt rules of the [threat model](14-threat-model.md): when the workflow scan does not clear the head, it gives the number of failed jobs, never their names, since job names come from the branch's workflow. This hold is for work outside the pull request only: a head past the split tier is not held, it goes straight to the maintainer agent for a split (see [Reviews](07-reviews.md)).
- **Every stall gets a cause and a route.** A head or a chain of work (a task and the tasks that wait on it) that has not moved for a set time (for example two hours with no new head, verdict or merge) gets exactly one of five causes, recorded in the ledger and shown on its card, and each cause has a route that runs without the owner watching:
  - *Builder-fixable:* the open finding or the red CI is the builder's to fix on its branch, so it goes back to the builder.
  - *Needs a protected change:* the fix lies in a protected path the builder may not change. The maintainer agent prepares that change as a pull request of its own, which goes through the review panel and the merge rules like any protected change ([Merge](08-merge.md#approving-protected-changes)); the stalled task is held, and that merge releases it like any move of main (above).
  - *Needs the environment:* a tool the check needs is missing from the image the builder and CI share ([Constraints](../04-constraints.md#security-model)), which the pre-push check reports with the cause `environment` ([Reviews](07-reviews.md)). The maintainer agent prepares the image change as its own pull request for the panel, the same way.
  - *Needs an owner decision:* a package outside the trusted vendors, a protected change the floors send to the owner, or a product decision. It goes to the owner, asked when it first appears ([Merge](08-merge.md)), and is never settled by a default or a timeout.
  - *Waits for another issue:* the `Waits for` line is rechecked against the rule that it names only the work the task builds on ([Choosing work](03-choosing-work.md)). When it names a whole umbrella and one part suffices, the maintainer agent narrows the line to that part; otherwise the wait stays, and the stall of the task it waits for is the one that is routed.

  The cause is read without a model where Intakt can (the pre-push check's `environment` cause, an open owner question, an open `Waits for` line, the builder's hand-over reason), and the maintainer agent decides the rest on the merits. An owner question that is already out does not name the stall when another cause also holds, because its route is already running. A route that keeps failing (the same task stalling three times in a row with the same cause, whatever heads its rebuilds pushed) raises the one notice of the principle "A wait has a ceiling" ([Principles](../02-principles.md)). Reason: one pull request held the critical path of two milestones (12 issues, the demo included) for hours and nobody was told. Its CI lacked a tool the builder's sandbox had, so every rebuild failed the same way, the owner was never asked about its new packages, and every lane looked busy with other work.
- **A task whose review cycles run out is re-planned, not handed to the owner.** In one stretch of the loop's records, 36 of 48 hand-overs were review cycles running out with changes still requested, and each waited on the maintainer. The maintainer agent reads the findings still open and decides on the merits: it splits the task along them (the done part merges if it passes on its own, the rest becomes a new task), rewrites the task's acceptance when the findings show it was unclear, or sends it back once more on the strong tier when one finding blocks it. It writes the decision into the task description. The owner is asked only when an open finding needs a product decision, the reviewers disagree on what the task requires, an open P1 touches security, secrets or data integrity, or the retry on the strong tier still fails and the task cannot be split. A rewrite or split never defers or drops an open P1, and a P1 on security, secrets or data integrity goes to the owner, because the agent reads model-written findings and a steered one could otherwise rewrite the acceptance until the finding no longer counts. The retry on the strong tier is the last one: if the head still comes back with changes requested, the agent splits the task along the findings that remain or, when it cannot, the task goes to the owner as the bounded number of unresolved attempts above. The earlier steps stay as they are (see [Reviews](07-reviews.md)).
- **A secret scan hit keeps the work until it is judged.** <a id="a-secret-scan-hit-keeps-the-work"></a>When a build fails the secret scan for the last allowed time, its commits stay unpublished on the orchestrator's machine, not discarded, and the hand-over comes to the maintainer agent, which judges the finding or passes it to the owner. The finding's record names the file, the line and the rule, never the value, and the kept work has a retention limit, after which it is deleted. A finding judged false releases the work: the scan rule or allowlist change goes through the secrets floor to the owner as usual ([Merge](08-merge.md)), then the kept commits are scanned again and go on from there; they never skip the scan, and the agent's ruling alone releases nothing. A finding judged real, or not judged within the limit, deletes the kept work, and the task goes back to build with the finding as feedback. A build session's feedback never carries the finding's value. Reason: a required `"ext-tokenizer": "*"` line in `composer.json` matched a rule for a sensitive key set to a real value, the hand-over discarded the commits, and once the rule was corrected the task was built again from nothing, at 470 thousand tokens on the strongest model for its last build step alone, though nothing was wrong with the work. Keeping the work costs little and does not weaken the rule, since the commits stay local and the scan still fails closed before any push ([Threat model](14-threat-model.md#builder)).
- **A task killed for memory twice comes to it, not to another attempt.** The first memory kill is told to the next attempt; a second kill of the same task is handed over, since a third attempt would most likely run the same command again ([Security model](../04-constraints.md#security-model)). It decides on the merits (a narrower task, a decision for the builder written into the task, a task that raises the limit in the project file), and the owner is asked only when it cannot resolve it.
- **Everything it does is recorded** in the ledger with the item it acted on, so the dashboard can show what it settled and what it passed on.
