# The maintainer agent

The orchestrator is the maintainer: it settles every hand-over it can decide itself, through its maintainer agent, and asks a person only for a decision it cannot make. Most hand-overs never need the owner: a re-queue after a transient failure, a split of an over-size change, a merge conflict, a reviewer misreading, a finding already fixed on the current head, a false positive of the secret check (settled by a rework that passes the unchanged scan, never by skipping it; see [Threat model](14-threat-model.md#where-model-output-authorizes-something)), a wrong label, reviewers who disagree, a decision the design documents already make. The maintainer agent decides those on the merits and writes the decision into the task description, so the owner sees only what needs a person.
- **It runs as its own identity**, a second, narrower App, never the owner's and never the loop's (one shared bot would make the maintainer's actions count as the loop's own, and let it set the loop's statuses); it runs as a job container that holds only its own credentials, so it cannot reach the orchestrator's forge token or signing key (an empty forge config, a separate git config and tool deny-lists are not enough where it shares a user with them: git and similar tools run commands named in repository config, which the session can write, and anything it launches runs with the same access): it can comment, answer questions, write maintainer decisions into task descriptions (issue bodies), label, split tasks, resolve conflicts on a branch and write the summaries of approval requests (see [Merge](08-merge.md)), but it has no permission to merge, push main, approve, change protections or edit config, and the forge enforces that, not its prompt.
- **Its pushes go through the hand-back.** A conflict resolution leaves its job as a bundle, like a build. The orchestrator checks that it builds on the branch, refuses main and a non-fast-forward push, and tells a merge of main apart from an edit of the CI definition. A merge of main may bring in main's own workflow content: the pushed tree's workflows must equal main's or the branch base's, and each merge commit's workflows must equal one of its parents'. Any other change to a workflow is an agent-authored edit and is refused, since the forge would run it on the project's runners before anyone looked. Then it re-signs and pushes it. That push guard, not an instruction, is the barrier, because the agent works in a checkout whose content a builder wrote.
- **A usage limit is a wait, not a failure.** A session refused by its vendor's structured usage-limit answer counts no attempt, escalates nothing and runs again once the account has room. Counting it as a failure turned one exhausted window into false "the maintainer failed twice" cards for the owner. The maintainer runs on the same account selection as the jobs, so one switch of account moves it too.
- **Its absence is noticed.** When the maintainer agent has not finished a session for a set time while items wait, or its sessions keep failing, that is an infrastructure alert, and past a grace period an owner card. Items it would have settled stay parked, never dropped.
- **Short-lived and narrow:** one session per batch of new items, a fixed tool list, a step limit, and no shell tools that could reach the forge another way.
- **It decides by default and escalates as a decision.** It asks the owner only when the options are balanced and the choice is a matter of the owner's preference, for money, tax, pricing or legal rules, and for what a bounded number of its own attempts did not resolve. An escalation names the options, its recommendation and why it could not choose, in the owner's "Waiting on you" column. Protected-path changes follow the merge rules (see [Merge](08-merge.md)), not an escalation.
- **It leaves ideas to the owner.** An issue labelled `idea` is for discussion only: the maintainer agent never sizes, triages, splits, labels it as work or answers it as a decision, even when the eligibility label is also set (see [Labels](04-labels.md)).
- **An open pull request never waits on a large task.** When a finished pull request is held only for a part that needs another, larger task (a screenshot of a dashboard not built yet, a recording of a feature still planned), the maintainer splits that part into a follow-up that waits for the larger task, narrows the original task's acceptance to what it delivers now, and releases the hold. Pulling the large task forward instead would let one small pull request reorder the plan.
- **A task that waits on something outside its change is held, not reworked.** When a round leaves the code unchanged because the open finding needs something outside the pull request, the task is put on hold instead of being reviewed again. A hold on another task (`Waits for #n`) releases when that task closes. A wait whose target is a pull request is resolved to the task that pull request closes (its branch or its closing keyword), so the stall of the task that pull request closes is reported with that task's own cause and route (the causes and routes are defined by #595). A `Waits for` line that names the task's own pull request, or the pull request of its branch, is not a wait: Intakt creates no hold, and the build ends as a hand-over with the builder's reason, routed by its stall cause (for an owner-only file, the protected change route). Any other hold releases on an event that could change the outcome. A hold whose reason is something outside the change, or whose open finding is red CI, is released by a move of main into a build that merges main first (a merge-main rework), never into a review of the unchanged head, because the head can only change through such a build. A deploy of Intakt alone releases into one review of the same head, which returns to hold if nothing changed. The count of fruitless releases stays: only after a few does the task reach the maintainer agent. A hand-over that cites red CI follows the CI excerpt rules of the [threat model](14-threat-model.md): when the workflow scan does not clear the head, it gives the number of failed jobs, never their names, since job names come from the branch's workflow. This hold is for work outside the pull request only: a head past the split tier is not held, it goes straight to the maintainer agent for a split (see [Reviews](07-reviews.md)).
- **A task whose review cycles run out is re-planned, not handed to the owner.** In one stretch of the loop's records, 36 of 48 hand-overs were review cycles running out with changes still requested, and each waited on the maintainer. The maintainer agent reads the findings still open and decides on the merits: it splits the task along them (the done part merges if it passes on its own, the rest becomes a new task), rewrites the task's acceptance when the findings show it was unclear, or sends it back once more on the strong tier when one finding blocks it. It writes the decision into the task description. The owner is asked only when an open finding needs a product decision, the reviewers disagree on what the task requires, an open P1 touches security, secrets or data integrity, or the retry on the strong tier still fails and the task cannot be split. A rewrite or split never defers or drops an open P1, and a P1 on security, secrets or data integrity goes to the owner, because the agent reads model-written findings and a steered one could otherwise rewrite the acceptance until the finding no longer counts. The retry on the strong tier is the last one: if the head still comes back with changes requested, the agent splits the task along the findings that remain or, when it cannot, the task goes to the owner as the bounded number of unresolved attempts above. The earlier steps stay as they are (see [Reviews](07-reviews.md)).
- **A task killed for memory twice comes to it, not to another attempt.** The first memory kill is told to the next attempt; a second kill of the same task is handed over, since a third attempt would most likely run the same command again ([Security model](../04-constraints.md#security-model)). It decides on the merits (a narrower task, a decision for the builder written into the task, a task that raises the limit in the project file), and the owner is asked only when it cannot resolve it.
- **Everything it does is recorded** in the ledger with the item it acted on, so the dashboard can show what it settled and what it passed on.
