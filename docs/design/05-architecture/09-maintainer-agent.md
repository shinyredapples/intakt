# The maintainer agent

The orchestrator is the maintainer, with two duties: it settles every hand-over it can decide itself, through its maintainer agent, and asks a person only for a decision it cannot make; and it reviews the loop's flow and quality every week (see "A weekly flow and quality review" below). Most hand-overs never need the owner: a re-queue after a transient failure, a split of an over-size change, a merge conflict, a reviewer misreading, a finding already fixed on the current head, a hit of the secret check (judged while the work is kept, and never settled by skipping the scan; see below and [Threat model](14-threat-model.md#where-model-output-authorizes-something)), a wrong label, reviewers who disagree, a decision the design documents already make. The maintainer agent decides those on the merits and writes the decision into the task description, so the owner sees only what needs a person.
- **It does not tune model use.** Role prompts, skills, context limits and model routing belong to the AI engineer, who changes them only as measured experiments ([the AI engineer](06-budget-and-model-planner.md#the-ai-engineer-planned)). The maintainer agent settles hand-overs and may file a task about a cost it sees.
- **It leaves the test suite to the Test engineer.** The maintainer's weekly review keeps its remit of flow and quality in general; the health of the test suite as a whole (its time budget, redundant tests, flaky tests, the journeys and the CI workflows' speed) moves out of it to the opt-in Test engineer ([the Test engineer](07-reviews.md#the-test-engineer-planned)). A project without that role has no owner of the suite's health.
- **It runs as its own identity**, a second, narrower App, never the owner's and never the loop's (one shared bot would make the maintainer's actions count as the loop's own, and let it set the loop's statuses); it runs as a job container that holds only its own credentials, so it cannot reach the orchestrator's forge token or signing key (an empty forge config, a separate git config and tool deny-lists are not enough where it shares a user with them: git and similar tools run commands named in repository config, which the session can write, and anything it launches runs with the same access): it can comment, answer questions, write maintainer decisions into task descriptions (issue bodies), label, split tasks, resolve conflicts on a branch, write the summaries of approval requests (see [Merge](08-merge.md)) and open its own pull request for a stall's protected or environment change (below), but it has no permission to merge, push main, approve, change protections or edit config, and the forge enforces that, not its prompt.
- **Its pushes go through the hand-back.** A conflict resolution leaves its job as a bundle, like a build. The orchestrator checks that it builds on the branch, refuses main and a non-fast-forward push, and tells a merge of main apart from an edit of the CI definition. A merge of main may bring in main's own workflow content: the pushed tree's workflows must equal main's or the branch base's, and each merge commit's workflows must equal one of its parents'. Any other change to a workflow is an agent-authored edit and is refused, since the forge would run it on the project's runners before anyone looked. The one exception is the agent's own pull request for a protected or environment change (see "Every stall gets a cause and a route" below): it has no branch yet, so its bundle must build on the current main and goes to a new branch of its own, never to a task's branch, and its workflow edits follow the CI definition rules of [Merge](08-merge.md), so a risky one stays local until the owner approves its push. Then it re-signs and pushes it. That push guard, not an instruction, is the barrier, because the agent works in a checkout whose content a builder wrote.
- **A usage limit is a wait, not a failure.** A session refused by its vendor's structured usage-limit answer counts no attempt, escalates nothing and runs again once the account has room. Counting it as a failure turned one exhausted window into false "the maintainer failed twice" cards for the owner. The maintainer runs on the same account selection as the jobs, so one switch of account moves it too.
- **Its absence is noticed.** When the maintainer agent has not finished a session for a set time while items wait, or its sessions keep failing, that is an infrastructure alert, and past a grace period an owner card. Items it would have settled stay parked, never dropped.
- **Short-lived and narrow:** one session per batch of new items, with a fixed tool list, a step limit, and no shell tools that could reach the forge another way. A weekly review (below) is a session of its own with its own, smaller tool list, separate from the hand-over sessions': read tools only (the report and the design documents) and the same step limit. It has no tool to comment, label, split a task, write a task description, change a branch or open a pull request, and its job holds no forge credential, so the forge actions of the identity bullet above are out of its reach. All it can do is return a typed answer, which plain code handles (see "What becomes of a finding" below).
- **It decides by default and escalates as a decision.** It asks the owner only when the options are balanced and the choice is a matter of the owner's preference, for money, tax, pricing or legal rules, for a milestone whose forecast misses its due date (there plain code opens the owner card and attaches the agent's recommendation to it, below), and for what a bounded number of its own attempts did not resolve. An escalation names the options, its recommendation and why it could not choose, in the owner's "Waiting on you" column. Protected-path changes follow the merge rules (see [Merge](08-merge.md)), not an escalation.
- **It leaves ideas to the owner.** An issue labelled `idea` is for discussion only: the maintainer agent never sizes, triages, splits, labels it as work or answers it as a decision, even when the eligibility label is also set (see [Labels](04-labels.md)).
- **An open pull request never waits on a large task.** When a finished pull request is held only for a part that needs another, larger task (a screenshot of a dashboard not built yet, a recording of a feature still planned), the maintainer splits that part into a follow-up that waits for the larger task, narrows the original task's acceptance to what it delivers now, and releases the hold. Pulling the large task forward instead would let one small pull request reorder the plan.
- **A task that waits on something outside its change is held, not reworked.** When a round leaves the code unchanged because the open finding needs something outside the pull request, the task is put on hold instead of being reviewed again. A hold on another task (`Waits for #n`) releases when that task closes. A wait whose target is a pull request is resolved to the task that pull request closes (its branch or its closing keyword), so the stall of the task that pull request closes is reported with that task's own cause and route (see "Every stall gets a cause and a route" below). A `Waits for` line that names the task's own pull request, or the pull request of its branch, is not a wait: Intakt creates no hold, and the build ends as a hand-over with the builder's reason, routed by its stall cause (for an owner-only file, the protected change route). Any other hold releases on an event that could change the outcome. A hold whose reason is something outside the change, or whose open finding is red CI, is released by a move of main into a build that merges main first (a merge-main rework), never into a review of the unchanged head, because the head can only change through such a build. A deploy of Intakt alone releases into one review of the same head, which returns to hold if nothing changed. The count of fruitless releases stays: only after a few does the task reach the maintainer agent. A finding that names a conflict with main or an update needed from main is the exception: it gets one build from current main if the task allows it, otherwise it goes to the maintainer agent at once, and a build that leaves it open also goes to the maintainer agent rather than back on hold (see [Reviews](07-reviews.md)). When a hand-over of the same task for this same cause (a finding that needs main, or an over-size branch) ended in a re-queue, its next hand-over is a split, never another re-queue. This does not change the owner routes of the re-plan bullet below (a product decision, an open P1 on security, secrets or data integrity, or a retry on the strong tier that fails when the task cannot be split), and an unrelated earlier hand-over, such as a transient failure or a memory kill, does not count. A hand-over that cites red CI follows the CI excerpt rules of the [threat model](14-threat-model.md): when the workflow scan does not clear the head, it gives the number of failed jobs, never their names, since job names come from the branch's workflow. This hold is for work outside the pull request only: a head past the split tier is not held, it goes straight to the maintainer agent for a split (see [Reviews](07-reviews.md)).
- **A wait for an outside change is written as a typed line.** Whenever the maintainer agent parks a task on a change in another repository (an upstream fix, a release of a tool Intakt runs on), it writes a `Waits for release: <owner>/<repo>#<n>` line into the task description. The line is all it writes: Intakt reads it, records the task as blocked in its row and mirrors that as the `blocked` status label, so plain code can lift the wait ([Choosing work](03-choosing-work.md)). A wait stated only in prose (for example "queued again once deployed") is a defect: nothing would ever lift it. Plain code cannot read prose, so it finds the defect by what is missing: a task that left the queue with no typed reason shows as an untracked wait with the stalled work ([Dashboard](13-dashboard.md)). The maintainer agent also receives the external waits plain code cannot settle: an external issue closed with no merged change, an external state Intakt cannot read for a day, and a wait no plugin can answer. Its own judgment lifts nothing: a reference is recorded as satisfied only on verified evidence, which is a plugin answer that comes in later, another change the agent names in the task (an upstream pull request or a release) that plain code then checks with the same two questions, or the owner's decision recorded on the task. Without one of these it asks the owner, and the wait stays until the owner answers; it never lapses.
- **Every stall gets a cause and a route.** A head or a chain of work (a task and the tasks that wait on it) that has not moved for a set time (for example two hours with no new head, verdict or merge) gets exactly one of five causes, recorded in the ledger and shown on its card, and each cause has a route that runs without the owner watching:
  - *Builder-fixable:* the open finding or the red CI is the builder's to fix on its branch, so it goes back to the builder.
  - *Needs a protected change:* the fix lies in a protected path the builder may not change. The maintainer agent prepares that change as a pull request of its own, which goes through the review panel and the merge rules like any protected change ([Merge](08-merge.md#approving-protected-changes)); the stalled task is held, and that merge releases it like any move of main (above).
  - *Needs the environment:* a tool the check needs is missing from the image the builder and CI share ([Constraints](../04-constraints.md#security-model)), which the pre-push check reports with the cause `environment` ([Reviews](07-reviews.md)). The maintainer agent prepares the image change as its own pull request for the panel, the same way.
  - *Needs an owner decision:* a package outside the trusted vendors, a protected change the floors send to the owner, or a product decision. It goes to the owner, asked when it first appears ([Merge](08-merge.md)), and is never settled by a default or a timeout.
  - *Waits for another issue:* the `Waits for` line is rechecked against the rule that it names only the work the task builds on ([Choosing work](03-choosing-work.md)). When it names a whole umbrella and one part suffices, the maintainer agent narrows the line to that part; otherwise the wait stays, and the stall of the task it waits for is the one that is routed.

  The cause is read without a model where Intakt can (the pre-push check's `environment` cause, an open owner question, an open `Waits for` line, the builder's hand-over reason), and the maintainer agent decides the rest on the merits. An owner question that is already out does not name the stall when another cause also holds, because its route is already running. A route that keeps failing (the same task stalling three times in a row with the same cause, whatever heads its rebuilds pushed) raises the one notice of the principle "A wait has a ceiling" ([Principles](../02-principles.md)). Reason: one pull request held the critical path of two milestones (12 issues, the demo included) for hours and nobody was told. Its CI lacked a tool the builder's sandbox had, so every rebuild failed the same way, the owner was never asked about its new packages, and every lane looked busy with other work.
- **A task whose review cycles run out is re-planned, not handed to the owner.** In one stretch of the loop's records, 36 of 48 hand-overs were review cycles running out with changes still requested, and each waited on the maintainer. The maintainer agent reads the findings still open and decides on the merits: it splits the task along them (the done part merges if it passes on its own, the rest becomes a new task), rewrites the task's acceptance when the findings show it was unclear, or sends it back once more on the strong tier when one finding blocks it. It writes the decision into the task description. The owner is asked only when an open finding needs a product decision, the reviewers disagree on what the task requires, an open P1 touches security, secrets or data integrity, or the retry on the strong tier still fails and the task cannot be split. A rewrite or split never defers or drops an open P1, and a P1 on security, secrets or data integrity goes to the owner, because the agent reads model-written findings and a steered one could otherwise rewrite the acceptance until the finding no longer counts. The retry on the strong tier is the last one: if the head still comes back with changes requested, the agent splits the task along the findings that remain or, when it cannot, the task goes to the owner as the bounded number of unresolved attempts above. The earlier steps stay as they are (see [Reviews](07-reviews.md)).
- **A secret scan hit keeps the work until it is judged.** <a id="a-secret-scan-hit-keeps-the-work"></a>When a build fails the secret scan for the last allowed time, on the hand-back round or on the build task's own hand-back check, its commits stay unpublished on the orchestrator's machine, not discarded, and the hand-over comes to the maintainer agent, which judges the finding or passes it to the owner. The kept objects stay in the check's quarantine, named by no ref, and no object that no scan has accepted is moved into the repository's objects, so no checkout, job or review reads one before a passing new scan (after a pre-push refusal the mirror holds only objects the first check's scan accepted, [Threat model](14-threat-model.md#builder)). The pull request text is kept the same way: on both paths it is scanned before the commits leave the quarantine or are pushed (the forge's own scan stays as a second barrier), and whenever work is held, the text is held with the commits in the same quarantine, whether the hit was in the commits or in the text, never written to the ledger, a comment, the forge or a model, so the agent judges from the finding's record and never reads the held text. The finding's record names the file (or "pull request text"), the line and the rule, never the value, and a file path that itself holds a credential or a scan hit is redacted before it is recorded or sent to either agent. The kept work has a retention limit, after which the quarantine's objects and the held text are deleted with the hold. A finding judged false releases the work: the scan rule or allowlist change goes through the secrets floor to the owner as usual ([Merge](08-merge.md)), then the kept commits and the kept text are both scanned again and the work goes on from there with the kept text; they never skip the scan, and the agent's ruling alone releases nothing. A finding judged real, or not judged within the limit, deletes the kept work, the text too, and the task goes back to build with the finding as feedback. The retention limit is the end whatever the state of the judgement, also while a release is pending: its end deletes the held commits and text and sends the task back to build with the sanitized finding (file, line and rule) as feedback, also when the finding was judged false and its rule or allowlist change has already landed but the new scan has not yet passed; if a rule or allowlist change for that finding is still open when it ends, the task gets a `Waits for` line naming that change, so the rebuild runs under the corrected rule. A build session's feedback never carries the finding's value. Reason: a required `"ext-tokenizer": "*"` line in `composer.json` matched a rule for a sensitive key set to a real value, the hand-over discarded the commits, and once the rule was corrected the task was built again from nothing, at 470 thousand tokens on the strongest model for its last build step alone, though nothing was wrong with the work. Keeping the work costs little and does not weaken the rule, since the commits stay local and the scan still fails closed before any push ([Threat model](14-threat-model.md#builder)).
- **A task killed for memory twice comes to it, not to another attempt.** The first memory kill is told to the next attempt; a second kill of the same task is handed over, since a third attempt would most likely run the same command again ([Security model](../04-constraints.md#security-model)). It decides on the merits (a narrower task, a decision for the builder written into the task, a task that raises the limit in the project file), and the owner is asked only when it cannot resolve it.
- **A weekly flow and quality review.** Hand-overs show what is stuck now; they do not show what makes the loop slow or its output worse over weeks. Reason: in one owner session on this repository (2026-11-03 to 2026-11-04), rework was the largest cost (about 60% of build rounds), checks and builds ran on different PHP settings, follow-ups refilled the current milestone, and serial chains left build slots idle. A person found each of these by reading the ledger; the review makes that a duty of the maintainer.
  - *Plain code computes the report.* From the ledger and the queue, without a model: lead time per stage, send-backs per task and their kinds, idle build slots and why they were idle, waits, task inflow and outflow, tokens per merged task, checks that fail only in CI (the second, independent run of the checks), and per milestone its ready work, throughput, inflow and a forecast against its due date. The same report carries the quality counter-metric and, once a month, the codebase's health ([Dashboard](13-dashboard.md)); the test suite's own health stays the Test engineer's (above). The model reads the report; it never counts, and it never reads prose to compute a figure.
  - *When it runs.* One maintainer session reads the report each week, and at once, without waiting for the weekly run, when a milestone's forecast misses its due date or a metric moves past a threshold the owner set.
  - *What becomes of a finding.* The session applies nothing itself, and its tool list, not its prompt, makes that so: it holds none of the hand-over sessions' tools ("Short-lived and narrow" above). It returns one typed answer: a list of findings, each with the measured cause, the change it proposes and how its effect is checked (the figure and the review date), and, in a session a missed forecast started, a recommendation that names one of the card's options and why. Plain code validates the answer against its schema, and an answer that does not validate files nothing, attaches nothing and counts as a failed session. From a valid answer plain code redacts and secret-scans each finding and files it as a ready task whose description carries the cause, the change and the check; a finding with a scan hit is not filed. No model decides to file, label or change a task. Model routing, prompts and context limits are the AI engineer's (#865), not the maintainer's. It never changes review strictness, checks, the approval rules, its own powers or the owner floors.
  - *A missed milestone is the owner's decision.* When plain code finds that a milestone's forecast misses its due date, it opens the owner card itself, as a decision with the options (cut scope, move the date, add capacity) and the measured forecast; the card does not depend on the agent choosing to escalate. The session it starts returns a recommendation in its typed answer, and plain code attaches it to that card after validating, redacting and secret-scanning it; an invalid answer or a scan hit attaches nothing, and the card stays open with the measured forecast. The card is never settled by a default or a timeout, and the session has no tool that could close or change it.
- **The review sweeps the backlog.** The flow and quality review includes a backlog sweep, which runs on its own schedule as a background job, monthly by default and not every week ([Dashboard](13-dashboard.md), Background jobs): every ready issue not in flight (no pushed branch, no open pull request) is checked against main and against the titles of recent and open issues, for issues already done and for duplicates and replacements. It answers each issue in the Tech lead's typed form, with its evidence cited by reference, and the same plain-code rule ([Choosing work](03-choosing-work.md), step 3) decides what is closed: a done case only when the cited commit is on main, newer than the issue's last edit and part of a merged pull request that names the issue, a superseded case only when the later issue, written and last edited by an account with write access, carries a `Replaces #n` line for it, each with that link in a comment. The sweep's own answer closes nothing: the rest, done or superseded answers without such a link included, and contradicted and unclear ones, are listed for the Product owner with the sweep's evidence. It complements the Tech lead's check when an issue is sized ([Choosing work](03-choosing-work.md), step 3), which catches an issue only when it is sized or sized again. Measured on 2026-11-12: 213 issues checked, 1 done and 1 superseded found and closed, 4 unclear, for about 0.9M tokens on a smaller model.
- **Everything it does is recorded** in the ledger with the item it acted on, so the dashboard can show what it settled and what it passed on.
