# The maintainer agent

The orchestrator is the maintainer: it settles every hand-over it can decide itself, through its maintainer agent, and asks a person only for a decision it cannot make. Most hand-overs never need the owner: a re-queue after a transient failure, a split of an over-size change, a merge conflict, a reviewer misreading, a finding already fixed on the current head, a false positive of the secret check (settled by a rework that passes the unchanged scan, never by skipping it; see [Threat model](14-threat-model.md#where-model-output-authorizes-something)), a wrong label, reviewers who disagree, a decision the design documents already make. The maintainer agent decides those on the merits and writes the decision into the task description, so the owner sees only what needs a person.
- **It runs as its own identity**, a second, narrower App, never the owner's and never the loop's (one shared bot would make the maintainer's actions count as the loop's own, and let it set the loop's statuses); it runs as a job container that holds only its own credentials, so it cannot reach the orchestrator's forge token or signing key (an empty forge config, a separate git config and tool deny-lists are not enough where it shares a user with them: git and similar tools run commands named in repository config, which the session can write, and anything it launches runs with the same access): it can comment, answer questions, write maintainer decisions into task descriptions (issue bodies), label, split tasks, resolve conflicts on a branch and write the summaries of approval requests (see [Merge](08-merge.md)), but it has no permission to merge, push main, approve, change protections or edit config, and the forge enforces that, not its prompt.
- **Its pushes go through the hand-back.** A conflict resolution leaves its job as a bundle, like a build. The orchestrator checks that it builds on the branch, refuses main and a non-fast-forward push, and tells a merge of main apart from an edit of the CI definition. A merge of main may bring in main's own workflow content: the pushed tree's workflows must equal main's or the branch base's, and each merge commit's workflows must equal one of its parents'. Any other change to a workflow is an agent-authored edit and is refused, since the forge would run it on the project's runners before anyone looked. Then it re-signs and pushes it. That push guard, not an instruction, is the barrier, because the agent works in a checkout whose content a builder wrote.
- **A usage limit is a wait, not a failure.** A session refused by its vendor's structured usage-limit answer counts no attempt, escalates nothing and runs again once the account has room. Counting it as a failure turned one exhausted window into false "the maintainer failed twice" cards for the owner. The maintainer runs on the same account selection as the jobs, so one switch of account moves it too.
- **Its absence is noticed.** When the maintainer agent has not finished a session for a set time while items wait, or its sessions keep failing, that is an infrastructure alert, and past a grace period an owner card. Items it would have settled stay parked, never dropped.
- **Short-lived and narrow:** one session per batch of new items, a fixed tool list, a step limit, and no shell tools that could reach the forge another way.
- **It decides by default and escalates as a decision.** It asks the owner only when the options are balanced and the choice is a matter of the owner's preference, for money, tax, pricing or legal rules, and for what a bounded number of its own attempts did not resolve. An escalation names the options, its recommendation and why it could not choose, in the owner's "Waiting on you" column. Protected-path changes follow the merge rules (see [Merge](08-merge.md)), not an escalation.
- **A task that waits on something outside its change is held, not reworked.** When a round leaves the code unchanged because the open finding needs something outside the pull request, the task is put on hold instead of being reviewed again. A hold on another task (`Waits for #n`) releases when that task closes; any other hold releases on an event that could change the outcome (the orchestrator deploys a new version, or main moves) for one review of the same head, and returns to hold if nothing changed. Only after a few fruitless releases does it reach the maintainer agent.
- **Everything it does is recorded** in the ledger with the item it acted on, so the dashboard can show what it settled and what it passed on.
