# The Maintainer

The Maintainer (`maintainer`, formerly the maintainer agent; see [the team](01-overview.md#the-team)) is the model role through which the orchestrator keeps the loop moving, with two duties: it settles every hand-over it can decide itself and asks a person only for a decision it cannot make; and it reviews the loop's flow and quality every week (see "A weekly flow and quality review" below). A third duty is planned: drafting a journey entry at each milestone close (see "A journey entry at each milestone close" below). Most hand-overs never need the owner: a re-queue after a transient failure, a split of an over-size change, a merge conflict, a reviewer misreading, a finding already fixed on the current head, a hit of the secret check (judged while the work is kept, and never settled by skipping the scan; see below and [Threat model](14-threat-model.md#where-model-output-authorizes-something)), a wrong label, reviewers who disagree, a decision the design documents already make. The Maintainer decides those on the merits and writes the decision into the task description, so the owner sees only what needs a person.
- **It does not tune model use.** Role prompts, skills, context limits and model routing belong to the AI engineer, who changes them only as measured experiments ([the AI engineer](06-budget-and-model-planner.md#the-ai-engineer-planned)). The Maintainer settles hand-overs, asks only for tunings of the flow settings the owner listed ([Bounded tuning](06-budget-and-model-planner.md#bounded-tuning)) and may file a task about a cost it sees.
- **It leaves the test suite to the Test engineer.** The Maintainer's weekly review keeps its remit of flow and quality in general; the health of the test suite as a whole (its time budget, redundant tests, flaky tests, the journeys and the CI workflows' speed) moves out of it to the opt-in Test engineer ([the Test engineer](07-reviews.md#the-test-engineer-planned)). A project without that role has no owner of the suite's health.
- **It runs as its own identity**, a second, narrower App, never the owner's and never the loop's (one shared bot would make the Maintainer's actions count as the loop's own, and let it set the loop's statuses); it runs as a job container that holds only its own credentials, so it cannot reach the orchestrator's forge token or signing key (an empty forge config, a separate git config and tool deny-lists are not enough where it shares a user with them: git and similar tools run commands named in repository config, which the session can write, and anything it launches runs with the same access): it can comment, answer questions, write the Maintainer's decisions into task descriptions (issue bodies), label, split tasks, resolve conflicts on a branch, write the summaries of approval requests (see [Merge](08-merge.md)) and open its own pull request for a stall's protected or environment change (below), but it has no permission to merge, push main, approve, change protections or edit config, and the forge enforces that, not its prompt.
- **Its pushes go through the hand-back.** A conflict resolution leaves its job as a bundle, like a build. The orchestrator checks that it builds on the branch, refuses main and a non-fast-forward push, and tells a merge of main apart from an edit of the CI definition. A merge of main may bring in main's own workflow content: the pushed tree's workflows must equal main's or the branch base's, and each merge commit's workflows must equal one of its parents'. Any other change to a workflow is an agent-authored edit and is refused, since the forge would run it on the project's runners before anyone looked. The one exception is the agent's own pull request for a protected or environment change (see "Every stall gets a cause and a route" below): it has no branch yet, so its bundle must build on the current main and goes to a new branch of its own, never to a task's branch, and its workflow edits follow the CI definition rules of [Merge](08-merge.md), so a risky one stays local until the owner approves its push. Then it re-signs and pushes it. That push guard, not an instruction, is the barrier, because the agent works in a checkout whose content a Developer wrote.
- **A usage limit is a wait, not a failure.** A session refused by its vendor's structured usage-limit answer counts no attempt, escalates nothing and runs again once the account has room. Counting it as a failure turned one exhausted window into false "the maintainer failed twice" cards for the owner. The Maintainer runs on the same account selection as the jobs, so one switch of account moves it too.
- **Its absence is noticed.** When the Maintainer has not finished a session for a set time while items wait, or its sessions keep failing, that is an infrastructure alert, and past a grace period an owner card. Items it would have settled stay parked, never dropped.
- **Short-lived and narrow:** one session per batch of new items, with a fixed tool list, a step limit, and no shell tools that could reach the forge another way. A weekly review (below) is a session of its own with its own, smaller tool list, separate from the hand-over sessions': read tools only (the report and the design documents) and the same step limit. It has no tool to comment, label, split a task, write a task description, change a branch or open a pull request, and its job holds no forge credential, so the forge actions of the identity bullet above are out of its reach. All it can do is return a typed answer, which plain code handles (see "What becomes of a finding" below).
- **It decides by default and escalates as a decision.** It asks the owner only when the options are balanced and the choice is a matter of the owner's preference, for money, tax, pricing or legal rules, for a milestone whose forecast misses its due date (there plain code opens the owner card and attaches the agent's recommendation to it, below), and for what a bounded number of its own attempts did not resolve. An escalation names the options, its recommendation and why it could not choose, in the owner's "Waiting on you" column. Protected-path changes follow the merge rules (see [Merge](08-merge.md)), not an escalation.
- **It leaves ideas to the owner.** An issue labelled `idea` is for discussion only: the Maintainer never sizes, triages, splits, labels it as work or answers it as a decision, even when the eligibility label is also set (see [Labels](04-labels.md)).
- **An open pull request never waits on a large task.** When a finished pull request is held only for a part that needs another, larger task (a screenshot of a dashboard not built yet, a recording of a feature still planned), the Maintainer splits that part into a follow-up that waits for the larger task, narrows the original task's acceptance to what it delivers now, and releases the hold. Pulling the large task forward instead would let one small pull request reorder the plan.
- **A task that waits on something outside its change is held, not reworked.** When a round leaves the code unchanged because the open finding needs something outside the pull request, the task is put on hold instead of being reviewed again. A hold on another task (`Waits for #n`) releases when that task closes. A wait whose target is a pull request is resolved to the task that pull request closes (its branch or its closing keyword), so the stall of the task that pull request closes is reported with that task's own cause and route (see "Every stall gets a cause and a route" below). Such a wait, a follow-up's wait on its original's pull request included, does not release when that task closes: it releases only when the forge confirms that pull request merged into main ([Choosing work](03-choosing-work.md), step 5). A `Waits for` line that names the task's own pull request, or the pull request of its branch, is not a wait: Intakt creates no hold, and the build ends as a hand-over with the Developer's reason, routed by its stall cause (for an owner-only file, the protected change route). Any other hold releases on an event that could change the outcome. A hold whose reason is something outside the change, or whose open finding is red CI, is released by a move of main into a build that merges main first (a merge-main rework), never into a review of the unchanged head, because the head can only change through such a build. A deploy of Intakt alone releases into one review of the same head, which returns to hold if nothing changed. The count of fruitless releases stays: only after a few does the task reach the Maintainer. A finding that names a conflict with main or an update needed from main is the exception: a conflict only in registry files is first merged by Intakt without a build ([Merge](08-merge.md)), and only when that does not resolve it, or for any other conflict or update from main, it gets one build from current main if the task allows it, otherwise it goes to the Maintainer at once, and a build that leaves it open also goes to the Maintainer rather than back on hold (see [Reviews](07-reviews.md)). The second hand-over of the same task is a split, never another re-queue, whatever the cause of either hand-over (a finding that needs main, an over-size branch, a broken environment, a transient failure, a memory kill) and however the first one ended. This does not change the owner routes of the re-plan bullet below (a product decision, an open P1 on security, secrets or data integrity, or a retry on the strong tier that fails when the task cannot be split): a task that cannot be split goes to the owner. A hand-over that cites red CI follows the CI excerpt rules of the [threat model](14-threat-model.md): when the workflow scan does not clear the head, it gives the number of failed jobs, never their names, since job names come from the branch's workflow. This hold is for work outside the pull request only: a head past the split tier is not held, it goes straight to the Maintainer for a split (see [Reviews](07-reviews.md)).
- **An oversized pull request with no task is split too.** Splitting is not only for tasks. A head past the split tier on a pull request opened by the owner's identity or the Maintainer's identity goes to the Maintainer as a split, with no `take-over` needed: these identities are trusted, so building from their head is safe, and `take-over` exists for untrusted authors. A pull request from anyone else is not split. It gets one comment saying it is past the size limit and asking the author to split it; a person with write access can set `take-over`, and then the rules of this bullet apply to it.
  - *The plan comes first.* The agent records the split plan before any part exists, as it does for a task, so the split can resume and no part is created twice. Each part is a task that names `Source: <branch>@<sha>` of the original head, so the Developer applies the source's own diff and writes nothing new. Parts are cut along files where possible, each stays under the split tier, and a part that links to another states its merge order.
  - *The plan is checked before it is recorded.* Plain code checks every changed path or hunk of the diff from the merge base to `<sha>` against the plan: a path or hunk that no part holds, or that two parts hold, refuses the plan, and the agent writes it again.
  - *The parts are checked before the close.* Once every part's pull request is open or merged, plain code checks that the parts' heads add up to the pinned diff. It takes each part's head as its pull request was opened and applies them in merge order to the merge base, which must give the tree of `<sha>`. A part whose pull request was closed without merging counts as missing. A part that waits for another can never be open at the same time as the part it waits for, which is why a merged part counts as present. The same check also reads each part as it stands now: an open part's current head and a merged part's merged change must carry exactly its share, nothing dropped and nothing added, because a part can be pushed to after it opened and then merge with a different change than its share of the original. Applied in merge order to the merge base, these current heads and merged changes must still give the tree of `<sha>` (or of the new head after an extension, below). A part that dropped any of its share, or added any other edit, counts as a mismatch. On a mismatch, or with a missing part, the original stays open and goes back to the Maintainer and, the second time, to the owner.
  - *The close.* When the check passes, Intakt records the verified head in the split plan and then closes the original pull request with a comment naming the parts and the head the check verified. It never force-pushes the original branch and never deletes it. Right after the close, it reads the original's head again: if the head moved past the verified one in between, Intakt reopens the original and extends the split as below, so a push during the close never leaves changes unsplit. After a restart, a recorded close whose follow-up read of the head has not run does that read first, and reopens and extends the split if the head moved. Until every part has merged, each new head of a part is checked against its share the same way, and a head that drops any of it or adds any other edit is refused before review; a part closed without merging reopens the original.
  - *The close follows the head.* If commits land on the original branch after `<sha>`, the split is extended with more parts, recorded in the plan first like the others. The diff from the old `<sha>` to the new head gets as many parts as it needs, each under the split tier and with its place in the merge order, so a large later push still has a valid split. These parts are checked against that diff by path or hunk, as in the plan check (every changed path or hunk of it held by exactly one of them, so a single file past the split tier can be cut by hunk), not against hunks of the merge-base diff, because a later commit can overwrite a line an earlier part already added, so the exact-hunk rule of the plan check does not apply to the extended diff. The close check stays that all parts, applied in order, give the tree of the new head.
  - *Issues that name the original are repointed.* Open issues whose text names the original pull request are updated to name the parts, and the edit shows in the issue's history as the Maintainer's. Right before writing, Intakt reads the issue again; right after, it checks the edit history. If another edit landed in between and the agent's edit is still the latest, Intakt rewrites the body as that other edit's text with only the references replaced, and reads and checks again in the same way. If a newer edit than the agent's exists, or the second try collides too, Intakt stops writing to that issue and posts one comment that names the parts and the overwritten edit, so a person can reconcile it. Intakt never knowingly writes older text over a newer edit. Where the forge has no write that is conditional on the revision read (GitHub's issue edit, for one), this read, write and check is how the body is repointed, and an edit that lands between the read and the write can still be overwritten: the history check catches it, and the one comment names that edit so a person can restore it. Where the forge offers such a conditional write, Intakt uses it for the same flow. If the write is refused, Intakt reads the latest revision, builds the body again from that text with only the references replaced, and tries one more conditional write; if that is refused too, it stops writing to the issue and posts the one comment, which names the parts and says the body was left unchanged.

  Reason: an owner pull request of design mocks (326k characters of diff against a 200k limit) was sent back once and then waited a day, because a pull request Intakt did not build was only reviewed and never reworked. A session split it by hand into three pull requests with disjoint files, each under the limit, together exactly the original tree.
- **A wait for an outside change is written as a typed line.** Whenever the Maintainer parks a task on a change in another repository (an upstream fix, a release of a tool Intakt runs on), it writes a `Waits for release: <owner>/<repo>#<n>` line into the task description. The line is all it writes: Intakt reads it, records the task as blocked in its row and mirrors that as the `blocked` status label, so plain code can lift the wait ([Choosing work](03-choosing-work.md)). A wait stated only in prose (for example "queued again once deployed") is a defect: nothing would ever lift it. Plain code cannot read prose, so it finds the defect by what is missing: a task that left the queue with no typed reason shows as an untracked wait with the stalled work ([Dashboard](13-dashboard.md)). The Maintainer also receives the external waits plain code cannot settle: an external issue closed with no merged change, an external state Intakt cannot read for a day, and a wait no plugin can answer. Its own judgment lifts nothing: a reference is recorded as satisfied only on verified evidence, which is a plugin answer that comes in later, another change the agent names in the task (an upstream pull request or a release) that plain code then checks with the same two questions, or the owner's decision recorded on the task. Without one of these it asks the owner, and the wait stays until the owner answers; it never lapses.
- **Every stall gets a cause and a route.** A head or a chain of work (a task and the tasks that wait on it) that has not moved for a set time (for example two hours without movement) gets exactly one of five causes, recorded in the ledger and shown on its card, and each cause has a route that runs without the owner watching. Movement is a merge, or a new head or verdict that changes the outcome; plain code reads it from the structured results, never from text:
  - *A repeated failure is no movement.* Plain code keeps a record of the blockers each task has already shown: every gate, test and CI step a head of the task failed on (by the forge's job and step results and the check's gate and cause), every file a round's blocking findings named (the paths in each typed finding, [Reviews](07-reviews.md)), and the lowest number of blocking findings a round had. A new head or round is compared with that whole record, never only with the head or round before it, and the record outlives a reset of the timer: a blocker that reset the timer once stays in the record, so it cannot reset it a second time. A head that passes every check does not empty the record: each failed gate, test and step stays in it, marked cleared once a head passes it, and a check that fails again after it was cleared stays cleared, so it can neither reset the timer as a new failure nor clear a second time. The files and the count are emptied when a round approves. A new head whose CI or pre-push check fails only on gates, tests or steps already in the record, or whose review round again does not approve, changes nothing: it does not reset the stall's timer, so rebuilds that keep hitting the same failures, in any order, leave the stall running while the milestone stays blocked. Heads that fail step X, then Y, then X again reset the timer once, at Y, and never after. A failing head is movement only when it fails on a gate, test or step the record does not hold. A head that passes every check is movement only when the record holds at least one failed gate, test or step not yet cleared, which that head then clears. A head that passes every check while the record holds no uncleared failure clears nothing, so it is not movement on its own: heads pushed every hour that all pass their checks while each review round returns the same blocking finding in `A.php` leave the stall running, and so do heads that alternate between failing step X and passing every check under that same finding, which reset the timer once, when X is first cleared, and never after. A review is read by its combined outcome, the blocking findings of every reviewer of the round together, never one verdict at a time: a reviewer that approves each new head while another returns the same blocking findings moves nothing, since the round still does not approve. A round that does not approve is movement only when its blocking findings name a file the record does not hold, or when it has fewer blocking findings than the lowest number in the record, so a task that clears its findings one at a time keeps moving. Rounds that alternate between a blocking finding in `A.php` and one in `B.php` reset the timer once, when `B.php` is first named, and never after, and a count that only swings back and forth resets nothing.
  - *Anything else is movement:* a merge, a head that fails on a gate, test or step the record does not hold, a head that passes every check and clears at least one failure the record holds that no head cleared before, a round that approves (every required reviewer approves the head), and an answer from the owner.
  - *Developer-fixable:* the open finding or the red CI is the Developer's to fix on its branch, so it goes back to the Developer.
  - *Needs a protected change:* the fix lies in a protected path the Developer may not change. The Maintainer prepares that change as a pull request of its own, which goes through the Code reviewers and the merge rules like any protected change ([Merge](08-merge.md#approving-protected-changes)); the stalled task is held, and that merge releases it like any move of main (above).
  - *Needs the environment:* a tool the check needs is missing from the image the Developer and CI share ([Constraints](../04-constraints.md#security-model)), which the pre-push check reports with the cause `environment` ([Reviews](07-reviews.md)). The Maintainer prepares the image change as its own pull request for the Code reviewers, the same way.
  - *Needs an owner decision:* a package outside the trusted vendors, a protected change the floors send to the owner, or a product decision. It goes to the owner, asked when it first appears ([Merge](08-merge.md)), and is never settled by a default or a timeout.
  - *Waits for another issue:* the `Waits for` line is rechecked against the rule that it names only the work the task builds on ([Choosing work](03-choosing-work.md)). When it names a whole umbrella and one part suffices, the Maintainer narrows the line to that part; otherwise the wait stays, and the stall of the task it waits for is the one that is routed. Plain code follows that route from task to waited-for task (a pull request resolved to the task it closes, as above) and records each task it passes; when the route reaches a task it already passed, the waits form a cycle, and the route stops there instead of going round. Plain code follows every `Waits for` line of a task, so a task that waits on two tasks which both wait on it is found in two cycles. Each cycle is known by its own tasks and lines, and each is a stall of its own on every task in it, routed once to the Maintainer with the tasks and the `Waits for` lines that close it: the Maintainer rechecks each of those lines against the rule above and narrows or removes one that names more than its task builds on, or splits the part two tasks both need into a task of its own that each waits on, and writes the decision into the task descriptions. When no line can be narrowed and no split breaks the cycle, it asks the owner as a decision naming the tasks and the lines, which is never settled by a default or a timeout. Plain code checks each recorded cycle again on every pass, one by one, from the open tasks and their `Waits for` lines as they stand: while the same tasks and lines still form it, it stays one stall and raises no new route. Once a cycle's own tasks and lines no longer form it, whatever broke it (a line changed, a task of the cycle closed, or a waited-on pull request merged), plain code retires that cycle's stall, withdraws its open Maintainer route and any owner request it raised, with one comment on the request saying the cycle is gone. Every other cycle is left as it is: when A waits on B and on C, both wait on A, and B closes, the stall and the request of the cycle of A and B are retired, while the cycle of A and C keeps its stall, its route and its request. A task's own stall timer starts when the last cycle it is in is retired. A different cycle that forms later is a new stall.

  The cause is read without a model where Intakt can (the pre-push check's `environment` cause, an open owner question, an open `Waits for` line, the Developer's hand-over reason), and the Maintainer decides the rest on the merits. An owner question that is already out does not name the stall when another cause also holds, because its route is already running. A route that keeps failing (the same task stalling three times in a row with the same cause, whatever heads its rebuilds pushed) raises the one notice of the principle "A wait has a ceiling" ([Principles](../02-principles.md)). Reason: one pull request held the critical path of two milestones (12 issues, the demo included) for hours and nobody was told. Its CI lacked a tool the Developer's sandbox had, so every rebuild failed the same way, the owner was never asked about its new packages, and every lane looked busy with other work.
- **A task whose review cycles run out is re-planned, not handed to the owner.** In one stretch of the loop's records, 36 of 48 hand-overs were review cycles running out with changes still requested, and each waited on the Maintainer. The Maintainer reads the findings still open and decides on the merits: it splits the task along them (the done part merges if it passes on its own, the rest becomes a new task), rewrites the task's acceptance when the findings show it was unclear, or sends it back once more on the strong tier when one finding blocks it. It writes the decision into the task description. The owner is asked only when an open finding needs a product decision, the reviewers disagree on what the task requires, an open P1 touches security, secrets or data integrity, or the retry on the strong tier still fails and the task cannot be split. A rewrite or split never defers or drops an open P1, and a P1 on security, secrets or data integrity goes to the owner, because the agent reads model-written findings and a steered one could otherwise rewrite the acceptance until the finding no longer counts. The retry on the strong tier is the last one: if the head still comes back with changes requested, the agent splits the task along the findings that remain or, when it cannot, the task goes to the owner as the bounded number of unresolved attempts above. A task sent back for the third time comes here earlier, once, for a split along its open findings ([Choosing work](03-choosing-work.md), step 6). If this is the task's second hand-over, whatever the cause of the first, the rewrite and the strong-tier retry are not offered: the task is split along the open findings, and when it cannot be split it goes to the owner, as the owner routes above say. The earlier steps stay as they are (see [Reviews](07-reviews.md)).
- **A secret scan hit keeps the work until it is judged.** <a id="a-secret-scan-hit-keeps-the-work"></a>When a build fails the secret scan for the last allowed time, on the hand-back round or on the build task's own hand-back check, its commits stay unpublished on the orchestrator's machine, not discarded, and the hand-over comes to the Maintainer, which judges the finding or passes it to the owner. The kept objects stay in the check's quarantine, named by no ref, and no object that no scan has accepted is moved into the repository's objects, so no checkout, job or review reads one before a passing new scan (after a pre-push refusal the mirror holds only objects the first check's scan accepted, [Threat model](14-threat-model.md#builder)). The pull request text is kept the same way: on both paths it is scanned before the commits leave the quarantine or are pushed (the forge's own scan stays as a second barrier), and whenever work is held, the text is held with the commits in the same quarantine, whether the hit was in the commits or in the text, never written to the ledger, a comment, the forge or a model, so the agent judges from the finding's record and never reads the held text. The finding's record names the file (or "pull request text"), the line and the rule, never the value, and a file path that itself holds a credential or a scan hit is redacted before it is recorded or sent to either agent. The kept work has a retention limit, after which the quarantine's objects and the held text are deleted with the hold. A finding judged false releases the work: the scan rule or allowlist change goes through the secrets floor to the owner as usual ([Merge](08-merge.md)), then the kept commits and the kept text are both scanned again and the work goes on from there with the kept text; the one exception is the held bundle of an unfinished build, which has no pull request text: its release pushes nothing, and the build takes the ordinary unfinished-build path of [Choosing work](03-choosing-work.md), step 3, from the turn-limit status and redacted stop report kept with the hold: re-sized after a recorded turn-limit status, built again at the same size as a first unfinished build without one, handed over as the second; they never skip the scan, and the agent's ruling alone releases nothing. A finding judged real, or not judged within the limit, deletes the kept work, the text too, and the task goes back to build with the finding as feedback. The retention limit is the end whatever the state of the judgement, also while a release is pending: its end deletes the held commits and text and sends the task back to build with the sanitized finding (file, line and rule) as feedback, also when the finding was judged false and its rule or allowlist change has already landed but the new scan has not yet passed; if a rule or allowlist change for that finding is still open when it ends, the task gets a `Waits for` line naming that change, so the rebuild runs under the corrected rule. A build session's feedback never carries the finding's value. Reason: a required `"ext-tokenizer": "*"` line in `composer.json` matched a rule for a sensitive key set to a real value, the hand-over discarded the commits, and once the rule was corrected the task was built again from nothing, at 470 thousand tokens on the strongest model for its last build step alone, though nothing was wrong with the work. Keeping the work costs little and does not weaken the rule, since the commits stay local and the scan still fails closed before any push ([Threat model](14-threat-model.md#builder)).
- **A task killed for memory twice comes to it, not to another attempt.** The first memory kill is told to the next attempt; a second kill of the same task is handed over, since a third attempt would most likely run the same command again ([Security model](../04-constraints.md#security-model)). It decides on the merits (a narrower task, a decision for the Developer written into the task, a task that raises the limit in the project file), and the owner is asked only when it cannot resolve it.
- **A weekly flow and quality review.** Hand-overs show what is stuck now; they do not show what makes the loop slow or its output worse over weeks. Reason: in one owner session on this repository (2026-11-03 to 2026-11-04), rework was the largest cost (about 60% of build rounds), checks and builds ran on different PHP settings, follow-ups refilled the current milestone, and serial chains left build slots idle. A person found each of these by reading the ledger; the review makes that a duty of the Maintainer.
  - *Plain code computes the report.* From the ledger and the queue, without a model: lead time per stage, send-backs per task and their kinds, idle build slots and why they were idle, waits, task inflow and outflow, tokens per merged task, checks that fail only in CI (the second, independent run of the checks), and per milestone its ready work, throughput, inflow and a forecast against its due date. The same report carries the quality counter-metric and, once a month, the codebase's health ([Dashboard](13-dashboard.md)); the test suite's own health stays the Test engineer's (above). The model reads the report; it never counts, and it never reads prose to compute a figure.
  - *When it runs.* One Maintainer session reads the report each week, and at once, without waiting for the weekly run, when a milestone's forecast misses its due date or a metric moves past a threshold the owner set.
  - *What becomes of a finding.* The session applies nothing itself, and its tool list, not its prompt, makes that so: it holds none of the hand-over sessions' tools ("Short-lived and narrow" above). It returns one typed answer: a list of findings, each with the measured cause, the change it proposes and how its effect is checked (the figure and the review date), and, in a session a missed forecast started, a recommendation that names one of the card's options and why. Plain code validates the answer against its schema, and an answer that does not validate files nothing, attaches nothing and counts as a failed session. From a valid answer plain code files each finding as a ready task, except a tuning the orchestrator applies (next item). The finding's text is model output from a session that read names Developers wrote, so plain code writes the task's frame (the title and a line naming the weekly review and the report week) and puts the model's cause, change and check inside one `<!-- external -->` block, after neutralizing any external marker inside that text so it cannot end its own block, as for the AI engineer's findings ([Threat model](14-threat-model.md#maintainer-agent)). The Developer and the Code reviewers read that block as data and judge the change against the design documents. Plain code reads it as data too: it takes `Waits for #n`, `Waits for release:`, the links between projects and `Replaces #n` only outside external blocks ([Choosing work](03-choosing-work.md), step 1), so such a line in a finding's text records no wait, does not block the filed task and closes or supersedes no issue. Plain code redacts the text and files the finding, or applies a tuning it asks for and records its text, only after a secret scan of it completed with no hit; a hit, or a scan that did not complete, files, applies and records nothing, counts the session as failed for that finding and shows the gap on the dashboard. No model decides to file, label or change a task. Model routing, prompts and context limits are the AI engineer's (#865), not the Maintainer's. It never changes review strictness, checks, the approval rules, its own powers or the owner floors.
  - *What it may apply.* Through the orchestrator, never by a tool of its own: a finding may ask for a value of a flow setting the owner listed with bounds in the owner's config, for example follow-up routing or pick weights. The orchestrator applies it only when the setting is on the list and the value within its bounds, as a recorded experiment with a review date, at most one per setting, and plain code undoes it when the quality counter-metric worsens. A tuned value stays only while the setting is on the owner's list and within its current bounds; otherwise the orchestrator restores the owner's value, and any owner write to the setting's value, its bounds or its place on the list ends the experiment as superseded ([Bounded tuning](06-budget-and-model-planner.md#bounded-tuning)). A request outside the list or its bounds is refused and filed as a ready task like any other finding, and no finding can widen the owner's list.
  - *A missed milestone is the owner's decision.* When plain code finds that a milestone's forecast misses its due date, it opens the owner card itself, as a decision with the options (cut scope, move the date, add capacity) and the measured forecast; the card does not depend on the agent choosing to escalate. The session it starts returns a recommendation in its typed answer, and plain code attaches it to that card after validating and redacting it, and only after a secret scan of it completed with no hit; an invalid answer, a scan hit or a scan that did not complete attaches nothing, counts the session as failed for that recommendation, shows the gap on the dashboard, and the card stays open with the measured forecast. The card is never settled by a default or a timeout, and the session has no tool that could close or change it.
- **The backlog sweep is a job of its own.** The backlog sweep is a separate background job, monthly by default ([Dashboard](13-dashboard.md), Background jobs); it is not part of the weekly session, which reads its results. Every ready issue not in flight (no pushed branch, no open pull request) is checked against main and against the titles of recent and open issues, for issues already done and for duplicates and replacements. It runs as a read-only session like the weekly review, with no forge credential ([Threat model](14-threat-model.md#maintainer-agent)), and answers each issue in the Tech lead's typed form, with its evidence cited by reference, and the same plain-code rule ([Choosing work](03-choosing-work.md), step 3) decides what is closed: a done case only when the cited commit is on main, newer than the issue's last edit and part of a merged pull request that names the issue, a superseded case only when the later issue, written and last edited by an account with write access, carries a `Replaces #n` line for it, each with that link in a comment. The sweep's own answer closes nothing: the rest, done or superseded answers without such a link included, and contradicted and unclear ones, are listed for the Product owner with the sweep's evidence. It complements the Tech lead's check when an issue is sized ([Choosing work](03-choosing-work.md), step 3), which catches an issue only when it is sized or sized again. Measured on 2026-11-12: 213 issues checked, 1 done and 1 superseded found and closed, 4 unclear, for about 0.9M tokens on a smaller model.
- <a id="journey-entries"></a>**A journey entry at each milestone close (planned, #1741).** When a milestone closes on a project whose Journey page is on ([Dashboard](13-dashboard.md#journey-page)), plain code starts one drafting session. It runs as a read-only session like the weekly review, with no forge credential, and is charged to the project's weekly share. Reason: writing Intakt's own `docs/journey.md` by hand showed that figures can be generated, but the story needs judgment.
  - *What it reads.* The milestone's issues with their Decisions sections, the owner's decisions, the stalls with their causes, and the send-back patterns (finding kinds per task), each fenced as untrusted ([Threat model](14-threat-model.md#journey-entries)).
  - *What it returns.* One typed entry: the date and a list of claims, each with the issue or pull request it rests on. A claim without a link is not a claim. Plain code validates the answer, checks that every link names an issue or pull request of this project, redacts the text and runs the secret scan; anything that fails publishes nothing and shows as a gap.
  - *Who publishes it.* The Product owner sees the draft as a "Waiting on you" card, may edit it, and approves it in the dashboard. Only then does plain code write the approved text into `docs/journey.md` and open the pull request, which is reviewed and merged like any change. No model decides to publish.
- **Everything it does is recorded** in the ledger with the item it acted on, so the dashboard can show what it settled and what it passed on.
