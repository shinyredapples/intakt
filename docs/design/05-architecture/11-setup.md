# Setup

```
docker run -d --name intakt -v intakt:/data -v /var/run/docker.sock:/var/run/docker.sock -p 127.0.0.1:7781:7781 ghcr.io/shinyredapples/intakt
```

This is the planned one-command start, in which the first-run wizard below writes the config and the `/data` layout below holds Intakt's state. Today's image does not start from it yet: it needs `INTAKT_CONFIG` set to a file on its data volume (it makes and keeps its startup secrets next to that file) and the volume mounted at `/app/var/data`, as `compose.yaml` does.

Then open the dashboard. The port is published on loopback only. The dashboard's port setting is the port published on the host, not the one inside the container: it defaults to 7781, the port the image listens on, and an owner who publishes another one (for example `-p 127.0.0.1:8080:7781`) sets it to that port (8080), because the dashboard checks it in the `Host` header (see [Dashboard](13-dashboard.md#who-can-act)). That separate setting is planned: today the port is `DASHBOARD_PORT`, which the image's health check and start message also call inside the container, so setting it to another port than the one the server listens on makes the container report unhealthy; today's image is published on host port 7781 (#2615). The dashboard has no login, no owner secret and no setup code: whoever can reach the port can act, which on loopback is whoever is on the host. Phone access is opt-in and planned: the owner will publish the port to a network they trust and add that name to the dashboard names; until then the dashboard answers only its loopback names (see [Dashboard](13-dashboard.md#who-can-act)). The first-run wizard:
1. asks for the repository URL and detects the forge;
2. creates Intakt's own forge identity: on GitHub a GitHub App through the manifest flow (one confirmation by the owner; Intakt stores the App's private key, never a personal token), owned by the account that owns the repositories (a private App installs only there), installed only on the chosen repositories with the narrowest permissions (including the workflows permission, without which the forge refuses any push that touches CI files, even a merge of main into a branch); on Gitea a bot user with a scoped token. Before anything uses it, the wizard mints a token, reads the installation back and compares its repositories and permissions with the manifest, and offers to copy the private key to the owner's secret store. It then recommends the forge's protection for the main branch where the plan offers it (required status checks from that identity, no force push, no deletion) and says what the owner may still bypass; requiring signed commits is an opt-in project setting, off by default, under which the forge's own verification counts ([Merge](08-merge.md#watching-main)). When the forge's protection is off, the dashboard shows that the watchdog is main's only protection;
3. adds each vendor account, one or more per vendor: for a subscription, the vendor's automation token, which the owner creates with the vendor's CLI (the wizard shows the command, for example `claude setup-token`) and pastes in, or a device-flow login for a vendor without such a token; or an API key;
4. reads the project (see "New and existing projects") to propose the toolchain, job image and check command, and runs the check once, recording its memory peak for the default runtime memory limit ([Security model](../04-constraints.md#security-model)); on a host that cannot give a job nested memory groups it says once that a runaway command can end the whole job there; an empty repository goes to the foundation flow instead;
5. proposes defaults (one build slot, at most two built heads waiting for review, so builds cannot outrun reviews, label `intakt`), and writes one config file that the owner can edit later.

The `intakt` volume at `/data` survives an image update; during an update the jobs of both versions run against it, while only one orchestrator at a time writes it ([Updates](#updates)). Among Intakt's state it holds `/data/secrets` (the runtime secrets vault for credentials saved in the admin area, see [Dashboard](13-dashboard.md#accounts)) and `/data/keys` (the forge App's private key, the signing key and the runtime vault's decryption key, readable by the orchestrator's user only and never mounted into a job).

Podman works through its Docker-compatible socket. Rootless mode is the default where available.

## The starting team

A new project starts with four model roles of [the team](01-overview.md#the-team): the Tech lead (`tech_lead`), the Developer (`developer`), the Code reviewers (`code_reviewer`) and the Maintainer (`maintainer`). The Designer (`designer`), the Security engineer (`security_engineer`) and the AI engineer (`ai_engineer`) are opt-in per project, off until the owner turns one on, and so is every tool they need: the security scanners, the accessibility and page-quality tools, and the scan of the running app. The Test engineer (`test_engineer`) is opt-in the same way. The wizard proposes none of them, so the simplest first install needs none of them, nor their tools. A project without the Security engineer still has the approval of protected changes: with the role not configured, every protected change goes to the owner ([Merge](08-merge.md#independent-security-review)).

## Updates

An update replaces Intakt's own version while the lanes keep working: the new version is checked beside the old one, starts on one build slot first, and only the slot being switched waits, with a deadline. Only an update the old version could not run beside pauses every lane. Measured in the build loop Intakt is distilled from (2026-11-05): four self-updates in one day each drained every lane and ran the target project's full check before and after, which paused builds and reviews for 30 to 80 minutes per update, and one update whose check failed on a test that failed the same way on the old version kept everything paused until the next update.

1. **Side by side, one writer.** A new version is installed as a new immutable version (its own image, pinned by digest) beside the running one, and neither changes the other's files. The running orchestrator keeps scheduling while the new version is checked: builds and reviews start, merges go on. It stays the only process that admits work, claims queue items, holds lane state and writes results ([One process owns state](../02-principles.md)) until the cut-over in item 4. Before it, the new version runs only as jobs that this orchestrator starts from the new image and records like any other job: the self-check and the switched slots' builds. A slot's version is the image its jobs run from.
2. **Its self-check is compared with the running version's, failure by failure.** The new version runs the [build-path self-check](#the-build-path-self-check) on the project's default branch. Its result is compared with the running version's last result on the same commit, which is reused when the commit, the locked dependencies and the check configuration are unchanged since it was taken; otherwise the running version runs the check on that commit too. The comparison is per failure, not per check: each failing test or finding is identified from the check's machine-readable report (a test's name, its failure kind, which is one of assertion failure, error or timeout, its failure message or diagnostic, and the source location of the failing assertion, its file relative to the repository and its line, read from the report or, when the report has none, from the failure's stack trace; a finding's rule and location), and a check without such a report counts as one failure identified by its failure output. Messages, diagnostics, traces and report-less output are normalized the same way before they are compared: times, durations and paths are removed. Both results are on the same commit, so a location is stable; a test failure whose location can be read from neither the report nor a trace is matched on its whole normalized failure output including the trace, and one with neither a location nor a trace counts against the update. A failure the running version shows with the same identity is the project's own: it is reported, does not block the update, and the project's own urgent task handles it (issue #860). Any other failure is the new version's and fails the update: a new failure in a check that already failed, and also a test that fails on both versions with the same name and kind but at a different assertion or with a different normalized message (for example an exit-status assertion where the running version failed an output assertion, even when both print the same message, such as `Failed asserting that false is true.`). The rule fails closed: a failure that cannot be matched in full counts against the update. This comparison's verdict, not a clean pass, is what lets the update go on.
3. **One slot first.** Once the comparison finds no failure of the new version's own, one build slot switches to the new version (the canary slot). When a build on the canary slot finishes without a stop the [shared-failure canary](06-budget-and-model-planner.md#shared-failure-canary) counts, or after a fixed number of minutes in which it shows no failure, the other slots switch together. One task's counted stop there neither switches the other slots nor rolls back, because it may be that task's own failure: the canary slot goes on with its next build. An environment failure needs corroboration: counted stops of 2 different tasks on the canary slot within an hour with the same normalized error, which no build of the old version showed in that hour. It rolls every slot back. The canary slot also has a deadline, a fixed time counted from its switch, so the rollout cannot stay on one slot: when builds on it keep ending in counted stops with different normalized errors, no build finishes without one, no interval stays free of failures and no two tasks corroborate one error. The deadline ends as soon as the switch of the other slots is decided (a build finished without a counted stop, or the failure-free minutes passed), even while those slots are still finishing their running jobs: from then each of them has only its own slot deadline (item 5), so the canary deadline never rolls back a rollout that already qualified. If neither the switch nor a rollback has been decided by that deadline, the update rolls back: the canary slot returns to the old version between jobs, the owner is alerted once with the stops seen, and the version is not tried again until a newer one exists or the owner retries it. The stops themselves are handled per task as usual. When the other slots switch, each does so as soon as its running job finishes or reaches its deadline (item 5). A slot switches between jobs: a running job finishes on the version it started on.
4. **The cut-over.** Once every build slot runs the new version, the orchestrator itself switches, and with it the review lane, the Scheduler and the dashboard. The old orchestrator writes a takeover grant naming the current owner generation, stops admitting work, finishes its pending writes and exits; the new one starts, takes the next owner generation in the database and writes with it. It may take the generation only through that grant: the grant is checked against the generation it names and consumed in the same database transaction that raises the generation, and without a valid grant the new orchestrator takes nothing and exits. A write carrying an older generation is refused, so a late write of the old orchestrator cannot land after the cut-over. The wait for the old orchestrator has a deadline of seconds: one that has not exited by then is stopped by force, and the new one starts and takes the generation through the grant all the same (an old orchestrator that hung before writing the grant leaves the new one nothing to take, and the rollback below applies). The generation makes that safe: whatever the hung or stopped process still tries to write is refused, and a write it did not finish is recovered as after any crash, from the database. If the new orchestrator has not taken the generation by a deadline of its own, the old version's orchestrator is started again and, in one transaction, revokes the grant and takes the next generation (the rollback below), so a new orchestrator that starts late finds no valid grant, takes nothing and exits; the owner is alerted, so admission never stays stopped behind a process that hangs. No lane drains for it: admission stops only for the seconds the switch takes, and a review or check job still running keeps running in its container; the new orchestrator collects its result as after any restart (all state is in the database, see [Overview](01-overview.md)), so a review is neither interrupted nor waited for, and is recorded once. New reviews start on the new version.
5. **Only the slot being switched waits, with a deadline.** A slot about to switch takes no new job while its running job finishes; the other slots and the review lane go on. Each slot has a deadline: a job still running at it is checkpointed (its work saved as for a no-progress stop, its commits kept, see [Budget and model planner](06-budget-and-model-planner.md)), its task keeps its place, and it resumes on the new version.
6. **Stored state stays readable by both.** Under [Add, don't move](../02-principles.md), a new version adds state beside the old and the old version ignores what it does not know, so the old orchestrator keeps reading results that new-version jobs leave, and rolling back stays redeploying. An update that changes stored state in a way the old version cannot read declares it with its release. Only such a declared update pauses all lanes: it drains them (no new jobs, running ones finish or are checkpointed at the deadline), copies the database and the `/data` volume, switches everything at once, and runs the start checks and the post-update check while the lanes stay paused. A failure until then restores the copy and the old version: nothing was accepted since the drain, so no work is lost. Once the lanes resume, the old version can no longer read the state and the update is no longer rolled back to it: a later failure pauses the lanes, alerts the owner on the first one, and is fixed forward by a newer release.
7. **Update windows.** Non-urgent updates are batched: the owner's settings set at most a few update windows a day, and a version that waits for a window is installed at the next one, as the newest release published by then. With auto-update on, a new release starts an update when it appears, or at the next window when windows are set. Windows apply only to non-urgent releases: a release its notes mark urgent (a security fix, or a fix for a failure that stops lanes) starts at once, and so does a version the owner picks.

Any other failure rolls back through the same steps in reverse: switched slots go back to the old version between jobs (a job past its deadline is checkpointed and resumed there), and after the cut-over the old orchestrator takes the next owner generation back. The old version stays installed until the update is done, and the owner is alerted on the first failure, not after retries. The old version is removed only once the update's scripted post-update check of what it changed (for example a job writing its probe file under the new rules) and the next jobs' outcomes look right, and the next update waits until then, so Intakt's own changes still roll out one version at a time ([One loop change at a time](../02-principles.md)). The installer runs in one fixed environment whatever starts it (clean variables, fixed PATH, defined signal handling), because an inherited difference (a restored SIGPIPE that killed a listing piped into an early-exiting match, a sudo variable that made a helper refuse) made the same install pass one way and fail another; its checks read a command's output first and then match it, and print what they read when they fail. A version that failed to install is not tried again until a newer one exists or the owner retries it, and a rollback that could not restore every part blocks the next update until a check shows the install whole.

### The build-path self-check

Before the new version schedules any build of a project, it runs one self-check per project. Reason: a runner update can break the path every build takes (for example which OS user runs the project's checks), and in the build loop Intakt is distilled from such a break cost about 6 hours, 37 builds and no merge before anyone noticed.

1. **The real build path.** The self-check is a build job from the new image: the builder's command wrapper runs, as the OS user builds run as, in a build job's environment, on the project's default branch. It is not only the check command.
2. **Check and commit.** It runs the project's check command and makes one commit on a scratch branch inside the job. The branch is never pushed, and the job gets no forge token or signing key, like any job.
3. **Failures.** A wrapper, user or commit step that fails counts as one failure, identified by its step and normalized output. The check's failures are identified as in item 2 above.
4. **Two verdicts, for two questions.** What a result is compared with depends on the question:
   - **Rollout verdict** (may the update go on?): the comparison of item 2 with the running version's result on the same commit, and nothing else. A project test that broke since an earlier self-check fails on both versions and does not block the update. A failure of the new version's own rolls the update back and alerts the owner once; that project's builds never start on the new version.
   - **Pause-recovery verdict** (may a [shared-failure pause](06-budget-and-model-planner.md#shared-failure-canary) end?): it passes only on a clean result: the wrapper, user and commit steps succeed and the check shows no failure. Only a clean result is the project's known-good result. No failure is carried over from an earlier self-check as accepted, and a rollout pass never makes a result known good, because a failure saved once would let a later self-check clear a pause with nothing fixed. A project without a known-good result follows the same rule: only a clean self-check passes, so a first result cannot seed one with failures. A failure the running version also shows does not count as passed here, because a break that both versions share is exactly what a pause can stand for. A result with any failure keeps the pause, however often the self-check is repeated; the alert names the failures, and the owner resumes the project when they are the project's own.

   The owner can start a self-check on the installed version; it gets only the pause-recovery verdict. An update's self-check on a paused project gets both: the rollout verdict decides whether the update goes on, the pause-recovery verdict whether the pause ends, so one result can let the update go on and keep the pause. A new failure that both versions show passes the rollout verdict and fails the pause-recovery verdict, and it fails that verdict again on every later self-check while it is still there.

   A pause-recovery pass ends the pause only for the version that passed it, the image the self-check ran from. The project's builds then start only on slots running that version: during an update, a slot still on the old version starts no build of the paused project, and if the update rolls back, the pause stays in force on the old version, which has not passed a self-check, so a rollback never resumes builds in the environment the pause was raised in. A later version clears the pause only with a pass of its own.
