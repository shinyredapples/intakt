# Setup

```
docker run -d --name intakt -v intakt:/data -v /var/run/docker.sock:/var/run/docker.sock -p 127.0.0.1:7781:7781 ghcr.io/shinyredapples/intakt
```

This is the planned one-command start, in which the first-run wizard below writes the config and the `/data` layout below holds Intakt's state. Today's image does not start from it yet: it needs `INTAKT_CONFIG` set to a file on its data volume (it makes and keeps its startup secrets next to that file) and the volume mounted at `/app/var/data`, as `compose.yaml` does.

Then open the dashboard. The port is published on loopback only. The dashboard's port setting is the port published on the host, not the one inside the container: it defaults to 7781, the port the image listens on, and an owner who publishes another one (for example `-p 127.0.0.1:8080:7781`) sets it to that port (8080), because the dashboard checks it in the `Host` header (see [Dashboard](13-dashboard.md#who-can-act)). The setting is `DASHBOARD_PORT`; the image's health check and start message call the port the server listens on (`SERVER_PORT`) with that `Host`. The dashboard has no login, no owner secret and no setup code: whoever can reach the port can act, which on loopback is whoever is on the host. Phone access is opt-in and planned: the owner will publish the port to a network they trust and add that name to the dashboard names; until then the dashboard answers only its loopback names (see [Dashboard](13-dashboard.md#who-can-act)). The first-run wizard:
1. asks for the repository URL and detects the forge;
2. creates Intakt's own forge identity: on GitHub a GitHub App through the manifest flow (one confirmation by the owner; Intakt stores the App's private key, never a personal token), owned by the account that owns the repositories (a private App installs only there), installed only on the chosen repositories with the narrowest permissions (including the workflows permission, without which the forge refuses any push that touches CI files, even a merge of main into a branch); on Gitea a bot user with a scoped token. Before anything uses it, the wizard mints a token, reads the installation back and compares its repositories and permissions with the manifest, and offers to copy the private key to the owner's secret store. It then recommends the forge's protection for the main branch where the plan offers it (required status checks from that identity, no force push, no deletion) and says what the owner may still bypass; requiring signed commits is an opt-in project setting, off by default, under which the forge's own verification counts ([Merge](08-merge.md#watching-main)). When the forge's protection is off, the dashboard shows that the watchdog is main's only protection;
3. adds each vendor account, one or more per vendor: for a subscription, the vendor's automation token, which the owner creates with the vendor's CLI (the wizard shows the command, for example `claude setup-token`) and pastes in, or a device-flow login for a vendor without such a token; or an API key;
4. reads the project (see "New and existing projects") to propose the toolchain, job image and check command, and runs the check once, recording its memory peak for the default runtime memory limit ([Security model](../04-constraints.md#security-model)); on a host that cannot give a job nested memory groups it says once that a runaway command can end the whole job there; an empty repository goes to the foundation flow instead;
5. proposes defaults (one build slot, at most two built heads waiting for review, so builds cannot outrun reviews, label `intakt`), and writes one config file that the owner can edit later.

The `intakt` volume at `/data` survives an image update; during an update the jobs of both versions run against it, while only one orchestrator at a time writes it ([Updates](#updates)). Among Intakt's state it holds `/data/secrets` (the runtime secrets vault for credentials saved in the admin area, see [Dashboard](13-dashboard.md#accounts)) and `/data/keys` (the forge App's private key, the signing key and the runtime vault's decryption key, readable by the orchestrator's user only and never mounted into a job).

Podman works through its Docker-compatible socket. Rootless mode is the default where available.

## The starting team

A new project starts with four model roles of [the team](01-overview.md#the-team): the Tech lead (`tech_lead`), the Developer (`developer`), the Code reviewers (`code_reviewer`) and the Maintainer (`maintainer`). The Designer (`designer`), the Security engineer (`security_engineer`) and the AI engineer (`ai_engineer`) are opt-in per project, off until the owner turns one on, and so is every tool they need: the security scanners, the accessibility and page-quality tools, and the scan of the running app. The Test engineer (`test_engineer`) is opt-in the same way. The wizard proposes none of them, so the simplest first install needs none of them, nor their tools. A project without the Security engineer still has the approval of protected changes: with the role not configured, every protected change goes to the owner ([Merge](08-merge.md#independent-security-review)).

## Updates

An update replaces Intakt's own version without stopping the work in progress ([decision 32](../06-decisions.md)): the new version is checked beside the old one and starts on one build slot first, a running job finishes on the image it started with, new jobs take the new version, and the orchestrator is away only for one restart. No slot drains in a normal update; only a release that declares a drain has one (item 8). Jobs already run in their own containers from an image, so a running job shares no tree with the orchestrator and needs no versioned install folders or helper changes to stay on its version. Measured in the build loop Intakt is distilled from (2026-11-05): four self-updates in one day each drained every lane and ran the target project's full check before and after, which paused builds and reviews for 30 to 80 minutes per update, and one update whose check failed on a test that failed the same way on the old version kept everything paused until the next update.

1. **Side by side, one writer.** A new version is installed as a new immutable version (its own image, pinned by digest) beside the running one, and neither changes the other's files. The running orchestrator keeps scheduling while the new version is checked: builds and reviews start, merges go on. It stays the only process that admits work, claims queue items, holds lane state and writes results ([One process owns state](../02-principles.md)) until the cut-over in item 5. Before it, the new version runs only as jobs that this orchestrator starts from the new image and records like any other job: the self-check and the switched slots' builds. A slot's version is the image its jobs run from.
2. **A job keeps its image to its end (D1).** When a job starts, the image it runs from (by digest), the Intakt release of the orchestrator that started it and the version of the job contract it speaks (item 7) are recorded on the job. The job runs from that image until it exits; an update never swaps or restarts a running job's container. Only a failed update (item 10) or a security release ([Threat model](14-threat-model.md#jobs-on-an-older-image-during-an-update)) stops one. A job the old orchestrator starts from the new image (the self-check, the switched slots' builds) speaks the contract version of the orchestrator that started it, and that version is what is recorded on it; a release whose jobs cannot speak the running orchestrator's contract changes the contract beyond item 7 and declares a drain (item 8).
3. **Its self-check is compared with the running version's, failure by failure.** The new version runs the [build-path self-check](#the-build-path-self-check) on the project's default branch. Its result is compared with the running version's last result on the same commit, which is reused when the commit, the locked dependencies and the check configuration are unchanged since it was taken; otherwise the running version runs the check on that commit too. The comparison is per failure, not per check: each failing test or finding is identified from the check's machine-readable report (a test's name, its failure kind, which is one of assertion failure, error or timeout, its failure message or diagnostic, and the source location of the failing assertion, its file relative to the repository and its line, read from the report or, when the report has none, from the failure's stack trace; a finding's rule and location), and a check without such a report counts as one failure identified by its failure output. Messages, diagnostics, traces and report-less output are normalized the same way before they are compared: times, durations and paths are removed. Both results are on the same commit, so a location is stable; a test failure whose location can be read from neither the report nor a trace is matched on its whole normalized failure output including the trace, and one with neither a location nor a trace counts against the update. A failure the running version shows with the same identity is the project's own: it is reported, does not block the update, and the project's own urgent task handles it (issue #860). Any other failure is the new version's and fails the update: a new failure in a check that already failed, and also a test that fails on both versions with the same name and kind but at a different assertion or with a different normalized message (for example an exit-status assertion where the running version failed an output assertion, even when both print the same message, such as `Failed asserting that false is true.`). The rule fails closed: a failure that cannot be matched in full counts against the update. This comparison's verdict, not a clean pass, is what lets the update go on.
4. **One slot first, and no slot waits (D2).** Once the comparison finds no failure of the new version's own, one build slot switches to the new version (the canary slot). When a build on the canary slot finishes without a stop the [shared-failure canary](06-budget-and-model-planner.md#shared-failure-canary) counts, or after a fixed number of minutes in which it shows no failure, the other slots switch together. One task's counted stop there neither switches the other slots nor rolls back, because it may be that task's own failure: the canary slot goes on with its next build. An environment failure needs corroboration: counted stops of 2 different tasks on the canary slot within an hour with the same normalized error, which no build of the old version showed in that hour. It rolls every slot back. The canary slot also has a deadline, a fixed time counted from its switch, so the rollout cannot stay on one slot: when builds on it keep ending in counted stops with different normalized errors, no build finishes without one, no interval stays free of failures and no two tasks corroborate one error. The deadline ends as soon as the switch of the other slots is decided (a build finished without a counted stop, or the failure-free minutes passed), so the canary deadline never rolls back a rollout that already qualified. If neither the switch nor a rollback has been decided by that deadline, the update rolls back: the canary slot returns to the old version between jobs, the owner is alerted once with the stops seen, and the version is not tried again until a newer one exists or the owner retries it. The stops themselves are handled per task as usual. A slot switches at once, without a pause: a job it is running keeps the image it started with to its end (item 2), and the slot's next job takes the new version. So a normal update has no drain: admission goes on throughout, and the only gap in new work is the cut-over's restart.
5. **The cut-over is the one restart (D3).** Once every build slot runs the new version, the orchestrator itself switches, and with it the review lane, the Scheduler and the dashboard. The old orchestrator writes a takeover grant naming the current owner generation, stops admitting work, finishes its pending writes and exits; the new one starts, takes the next owner generation in the database and writes with it. It may take the generation only through that grant: the grant is checked against the generation it names and consumed in the same database transaction that raises the generation, and without a valid grant the new orchestrator takes nothing and exits. A write carrying an older generation is refused, so a late write of the old orchestrator cannot land after the cut-over. The wait for the old orchestrator has a deadline of seconds: one that has not exited by then is stopped by force, and the new one starts and takes the generation through the grant all the same (an old orchestrator that hung before writing the grant leaves the new one nothing to take, and the rollback below applies). The generation makes that safe: whatever the hung or stopped process still tries to write is refused, and a write it did not finish is recovered as after any crash, from the database. If the new orchestrator has not taken the generation by a deadline of its own, the old version's orchestrator is started again and, in one transaction, revokes the grant and takes the next generation (the rollback below), so a new orchestrator that starts late finds no valid grant, takes nothing and exits; the owner is alerted, so admission never stays stopped behind a process that hangs. This is the update's one restart, and no lane drains for it: admission stops only for the seconds the switch takes. Job containers are not the orchestrator's child processes, so every job carries on through it, on whichever version it runs: a job writes its output directory and exits as usual, and the container runtime keeps the exit status. On start, the new orchestrator lists the job containers through the socket, matches them to the jobs the database holds as running, and takes each up again: a job still running is watched again, and a job that exited during the restart is read as if its exit had just been seen. Queued Messenger messages are kept in the database with the rest of the state, a deadline that passed fires on return, and forge changes are read by the next poll, so anything that happened during the restart is read on return, not lost. A review is therefore neither interrupted nor waited for, and is recorded once. The test that proves it forces the order instead of repeating runs: it starts a job, stops the orchestrator, lets the job write its result and exit while the orchestrator is down, starts the orchestrator on the next version, and asserts that the job's result is read and recorded exactly once (one end event in the ledger) and its task moves on as if no restart had happened. A second case keeps the job running across the restart and asserts it is watched again and ends normally.
6. **Live, then on trial.** The new orchestrator is *live* once it holds the owner generation and its start checks passed (the forge and the vendors answer). From then on it admits work, every job it starts takes the new version's images, the review lane included, and the old version's orchestrator starts nothing. It is on trial until its scripted post-update check passed and the first job of each kind it started ended with a result it could accept; a failure until then rolls back (item 10).
7. **A versioned job contract, one step of tolerance (D4).** What a job reads (its mounted inputs) and what it hands back (the bundle and pull request text, the verdict JSON, the check result) is a contract with a version number, recorded on the job (item 2). Two releases in a row can speak the same contract, so the version alone cannot bound the age: an orchestrator accepts a result only when both hold, the job's recorded release is its own or the release this install was updated from (exactly one update step; a step passes over releases only inside the rollback window of item 9), and the job's contract version is its own or the one before it. A result from a job started two or more update steps back, from an older contract, or one whose release or contract version it cannot read, is not interpreted or guessed at: the job's work is done again on the new version (a build is rebuilt, keeping its commits where the bundle can still be read as a bundle; a check or review runs again), with the reason in the ledger.
8. **A drain is the exception (D5).** A release drains only when its release notes declare it, with the reason, which the update's record and the dashboard show; without that declaration an update never drains. A release declares a drain when it changes the job contract by more than item 7 allows (its jobs cannot speak the running orchestrator's contract, item 2), changes how jobs are isolated (container, mounts, network, egress), or changes stored state the old version cannot read (item 9). Work that only waits, for CI or for a person, does not hold a drain up.
   - *Contract or isolation.* Each slot drains when it switches: it takes no new job while its running job finishes, the other slots and the review lane go on. Each slot has a deadline: a job still running at it is checkpointed (its work saved as for a no-progress stop, its commits kept, see [Budget and model planner](06-budget-and-model-planner.md)), its task keeps its place, and it resumes on the new version. The cut-over waits until no job of the old version runs; a review or check job still running at the deadline is stopped and run again on the new version.
   - *Stored state the old version cannot read.* Such a release pauses all lanes: it drains them (no new jobs, running ones finish or are checkpointed at the deadline), copies the database and the `/data` volume, switches everything at once, and runs the start checks and the post-update check while the lanes stay paused. It has no rollback window (item 9): a failure until then restores the copy and the old version, and nothing was accepted since the drain, so no work is lost. Once the lanes resume, the old version can no longer read the state and the update is no longer rolled back to it: a later failure pauses the lanes, alerts the owner on the first one, and is fixed forward by a newer release.
9. **Stored state stays readable by both, so a rollback keeps live state.** Under [Add, don't move](../02-principles.md), a new version adds state beside the old and the old version ignores what it does not know, so the old orchestrator keeps reading results that new-version jobs leave, and rolling back stays redeploying: a rollback swaps the image only; it never restores a backup, so nothing recorded after the update (ledger events, merges, job results) is lost. The rule covers values as well as layout: a release writes a new value (a new job status, enum value, stored-class shape or message type) only once every release in its rollback window can read it, so the reader ships one release before the writer, or the older releases read the unknown value through a fallback they already have; otherwise the release declares a drain (item 8). The release an install rolls back to is the one it ran before the update, which is not always the one published just before, so the rule is stated over a *rollback window*:
   - *Declared.* Each release declares the oldest release it may be installed from directly. Its rollback window is every release from that one up to the release published just before it.
   - *Proved for the whole window, with the data the new release writes.* Before a release is published, its CI migrates a copy of the database with it and runs the new release on that copy, writing every kind of record it adds or changes (a new job status, enum value, stored-class shape or message type, for example by running its journeys on it). Then it starts the image of every release in its window, not only the one just before it, on that copy, and checks that each reads and writes it. A release that fails for any of them is not published; it fixes the migration or the value, or declares a shorter window. The forced-order test of the rollback: a release writes a new job status during its trial, fails its post-update check, and the restored release loads that job.
   - *Removal follows the window.* A column or table is removed only once no release inside the removing release's window reads it. A release that A reads, B stopped reading and C wants to drop can drop it only if C's window starts at B or later.
   - *Enforced by the installer.* An install older than the target's window is refused the direct update, whether the owner picked the version or auto-update found it. It takes the intermediate releases first, in order, always the newest release whose window holds the version it runs. Each is a full update with its own restart, trial and post-update check, and the next one starts only when the one before passed; the owner is shown the reason and the path. So an install never rolls back to a release outside the window the failed release was proved against.

   So no release needs a restore to roll back, except one that declares stored state the old version cannot read (item 8). The owner's own copy of the data stays a recovery for a broken volume, not a step of the rollback.
10. **A failed update rolls the orchestrator back (D6).** An update fails before the cut-over (a failure of the new version's own in the comparison, a corroborated environment failure or the canary deadline (item 4), a new orchestrator that does not take over by its deadline) or on trial (item 6: a failed post-update check, or a first job of a kind that fails its start check or hands back a result the new version cannot read). Either way it rolls back (a release that declared stored state the old version cannot read follows item 8 instead) through the same steps in reverse: switched slots go back to the old version between jobs, and after the cut-over the old orchestrator takes the next owner generation back and resumes admission. Jobs on the older version are not touched and finish as they would have. Jobs running from the failed version's image are stopped and their work is done again on the restored version, each recorded in the ledger with the reason. A security hold the release wrote stays ([Threat model](14-threat-model.md#jobs-on-an-older-image-during-an-update)).
11. **Shown until done (D7).** The board shows which running jobs are on an older version until none are left ([Dashboard](13-dashboard.md)).
12. **Update windows.** Non-urgent updates are batched: the owner's settings set at most a few update windows a day, and a version that waits for a window is installed at the next one, as the newest release published by then. With auto-update on, a new release starts an update when it appears, or at the next window when windows are set. Windows apply only to non-urgent releases: a release its notes mark urgent (a security fix, or a fix for a failure that stops lanes) starts at once, and so does a version the owner picks.

The old version stays installed until the update is done, and the owner is alerted on the first failure, not after retries. The old version is removed only once the trial (item 6) passed, that is, the update's scripted post-update check of what it changed (for example a job writing its probe file under the new rules) and the first job of each kind look right, and no job on it is still running; the next update waits until the trial passed, so Intakt's own changes still roll out one version at a time ([One loop change at a time](../02-principles.md)). The installer runs in one fixed environment whatever starts it (clean variables, fixed PATH, defined signal handling), because an inherited difference (a restored SIGPIPE that killed a listing piped into an early-exiting match, a sudo variable that made a helper refuse) made the same install pass one way and fail another; its checks read a command's output first and then match it, and print what they read when they fail. A version that failed to install is not tried again until a newer one exists or the owner retries it, and a rollback that could not restore every part blocks the next update until a check shows the install whole.

### The build-path self-check

Before the new version schedules any build of a project, it runs one self-check per project. Reason: a runner update can break the path every build takes (for example which OS user runs the project's checks), and in the build loop Intakt is distilled from such a break cost about 6 hours, 37 builds and no merge before anyone noticed.

1. **The real build path.** The self-check is a build job from the new image: the builder's command wrapper runs, as the OS user builds run as, in a build job's environment, on the project's default branch. It is not only the check command.
2. **Check and commit.** It runs the project's check command and makes one commit on a scratch branch inside the job. The branch is never pushed, and the job gets no forge token or signing key, like any job.
3. **Failures.** A wrapper, user or commit step that fails counts as one failure, identified by its step and normalized output. The check's failures are identified as in item 3 above.
4. **Two verdicts, for two questions.** What a result is compared with depends on the question:
   - **Rollout verdict** (may the update go on?): the comparison of item 3 with the running version's result on the same commit, and nothing else. A project test that broke since an earlier self-check fails on both versions and does not block the update. A failure of the new version's own rolls the update back and alerts the owner once; that project's builds never start on the new version.
   - **Pause-recovery verdict** (may a [shared-failure pause](06-budget-and-model-planner.md#shared-failure-canary) end?): it passes only on a clean result: the wrapper, user and commit steps succeed and the check shows no failure. Only a clean result is the project's known-good result. No failure is carried over from an earlier self-check as accepted, and a rollout pass never makes a result known good, because a failure saved once would let a later self-check clear a pause with nothing fixed. A project without a known-good result follows the same rule: only a clean self-check passes, so a first result cannot seed one with failures. A failure the running version also shows does not count as passed here, because a break that both versions share is exactly what a pause can stand for. A result with any failure keeps the pause, however often the self-check is repeated; the alert names the failures, and the owner resumes the project when they are the project's own.

   The owner can start a self-check on the installed version; it gets only the pause-recovery verdict. An update's self-check on a paused project gets both: the rollout verdict decides whether the update goes on, the pause-recovery verdict whether the pause ends, so one result can let the update go on and keep the pause. A new failure that both versions show passes the rollout verdict and fails the pause-recovery verdict, and it fails that verdict again on every later self-check while it is still there.

   A pause-recovery pass ends the pause only for the version that passed it, the image the self-check ran from. The project's builds then start only on slots running that version: during an update, a slot still on the old version starts no build of the paused project, and if the update rolls back, the pause stays in force on the old version, which has not passed a self-check, so a rollback never resumes builds in the environment the pause was raised in. While the pause is still in force, a later version clears it only with a pass of its own (for example: B rolled back, C is tried next).

   The pause is retired for the project, for every version, once the version that passed the pause-recovery verdict is final: every build slot and the orchestrator run it, and the update can no longer roll back to the version the pause was raised on. A clean self-check the owner starts on the installed version outside an update retires the pause at once, because only one version exists then. After retirement, a later update starts unpaused: its self-check gets only the rollout verdict, and only a new trip of the canary pauses the project again. So after B's clean self-check and completed rollout, an update to C whose self-check shows a failure B also shows passes the rollout verdict, and the project's builds start on C.
