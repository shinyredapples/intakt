# Setup

```
docker run -d --name intakt -v intakt:/data -v /var/run/docker.sock:/var/run/docker.sock -p 127.0.0.1:7780:7780 ghcr.io/shinyredapples/intakt
```

Then open the dashboard. The port is published on loopback only. The dashboard's port setting is the port published on the host, not the one inside the container: it defaults to 7780, and an owner who publishes another one (for example `-p 127.0.0.1:8080:7780`) sets it to that port (8080), because the dashboard checks it in the `Host` header (see [Dashboard](13-dashboard.md#only-the-owner)). Phone access is opt-in (see [Dashboard](13-dashboard.md#only-the-owner)). Before anything else, the first-run wizard asks for the one-time setup code the first start printed to the container's log (`docker logs intakt`), then creates the owner secret or registers a passkey (for `localhost`; phone access pairs a passkey of its own, see [Dashboard](13-dashboard.md#only-the-owner)), which every change from the dashboard needs (a card's buttons and the admin area alike). Then it:
1. asks for the repository URL and detects the forge;
2. creates Intakt's own forge identity: on GitHub a GitHub App through the manifest flow (one confirmation by the owner; Intakt stores the App's private key, never a personal token), owned by the account that owns the repositories (a private App installs only there), installed only on the chosen repositories with the narrowest permissions (including the workflows permission, without which the forge refuses any push that touches CI files, even a merge of main into a branch); on Gitea a bot user with a scoped token. Before anything uses it, the wizard mints a token, reads the installation back and compares its repositories and permissions with the manifest, and offers to copy the private key to the owner's secret store. It then offers the forge's protection for the main branch (required status checks from that identity, signed commits, no force push, no deletion) and says what the owner may still bypass;
3. adds each vendor account, one or more per vendor: for a subscription, the vendor's automation token, which the owner creates with the vendor's CLI (the wizard shows the command, for example `claude setup-token`) and pastes in, or a device-flow login for a vendor without such a token; or an API key;
4. reads the project (see "New and existing projects") to propose the toolchain, job image and check command, and runs the check once, recording its memory peak for the default runtime memory limit ([Security model](../04-constraints.md#security-model)); on a host that cannot give a job nested memory groups it says once that a runaway command can end the whole job there; an empty repository goes to the foundation flow instead;
5. proposes defaults (one build slot, at most two built heads waiting for review, so builds cannot outrun reviews, label `intakt`), and writes one config file that the owner can edit later.

The `intakt` volume at `/data` survives an image update, and both versions read and write it while they run side by side during an update ([Updates](#updates)). Among Intakt's state it holds `/data/secrets` (the runtime secrets vault for credentials saved in the admin area, see [Dashboard](13-dashboard.md#accounts)) and `/data/keys` (the forge App's private key, the signing key and the runtime vault's decryption key, readable by the orchestrator's user only and never mounted into a job).

Podman works through its Docker-compatible socket. Rootless mode is the default where available.

## Updates

An update replaces Intakt's own version while the lanes keep working: the new version is checked beside the old one, starts on one build slot first, and only the slot being switched waits, with a deadline. Only an update the old version could not run beside pauses every lane. Measured in the build loop Intakt is distilled from (2026-11-05): four self-updates in one day each drained every lane and ran the target project's full check before and after, which paused builds and reviews for 30 to 80 minutes per update, and one update whose check failed on a test that failed the same way on the old version kept everything paused until the next update.

1. **Side by side.** A new version is installed as a new immutable version (its own image, pinned by digest) beside the running one, and neither changes the other's files. The running version keeps scheduling while the new one is checked: builds and reviews start, merges go on.
2. **Its self-check is compared with the running version's.** The new version runs the build-path self-check (issue #930, D1) on the project's default branch. Its result is compared with the running version's last result on the same commit, which is reused when the commit, the locked dependencies and the check configuration are unchanged since it was taken; otherwise the running version runs the check on that commit too. A failure the running version shows as well is the project's own: it is reported, does not block the update, and the project's own urgent task handles it (issue #860). A failure only the new version shows fails the update.
3. **One slot first.** Once the self-check passes, one build slot switches to the new version (the canary slot). The other slots switch when that slot's first build finishes without an environment failure (issue #930, D2), or after a fixed number of minutes in which the slot shows no failure. A slot switches between jobs: a running job finishes on the version it started on. The review lane, the Scheduler and the dashboard switch after the last build slot.
4. **Only the slot being switched waits, with a deadline.** A slot about to switch takes no new job while its running job finishes; the other slots and the review lane go on. Each slot has a deadline: a job still running at it is checkpointed (its work saved as for a no-progress stop, its commits kept, see [Budget and model planner](06-budget-and-model-planner.md)), its task keeps its place, and it resumes on the new version.
5. **Stored state stays readable by both.** Under [Add, don't move](../02-principles.md), a new version adds state beside the old and the old version ignores what it does not know, so both versions use one database while they run side by side, and rolling back stays redeploying. An update that changes stored state in a way the old version cannot read declares it with its release. Only such a declared update pauses all lanes: it drains them (no new jobs, running ones finish or are checkpointed at the deadline), switches everything at once and resumes.
6. **Update windows.** Non-urgent updates are batched: the owner's settings set at most a few update windows a day, and a version that waits for a window is installed at the next one, as the newest release published by then. An update starts when the owner picks a version or, with auto-update on, when a new release appears; with windows set, auto-update starts it at the next window.

Any failure rolls back: switched slots go back to the old version, which stays installed until the update is done, and the owner is alerted on the first failure, not after retries. The old version is removed only once the update's scripted post-update check of what it changed (for example a job writing its probe file under the new rules) and the next jobs' outcomes look right, and the next update waits until then, so Intakt's own changes still roll out one version at a time ([One loop change at a time](../02-principles.md)). The installer runs in one fixed environment whatever starts it (clean variables, fixed PATH, defined signal handling), because an inherited difference (a restored SIGPIPE that killed a listing piped into an early-exiting match, a sudo variable that made a helper refuse) made the same install pass one way and fail another; its checks read a command's output first and then match it, and print what they read when they fail. A version that failed to install is not tried again until a newer one exists or the owner retries it, and a rollback that could not restore every part blocks the next update until a check shows the install whole.
