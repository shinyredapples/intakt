# Choosing work

How a task (its issue on the forge) becomes a build. Every step is cheap and runs before any build tokens are spent.

1. **Eligible.** Open, labeled for the loop and not labeled `idea` (which wins, see [Labels](04-labels.md)), written by a trusted author and last edited by one (an account with write access, checked through the forge's permission API when the task becomes eligible and again before each build; the body is the build's instructions, so an edit by anyone else makes the task ineligible until a trusted account edits or confirms it), not blocked. Text a task copies from an untrusted source sits in an `<!-- external -->` block that Intakt fences as untrusted (see [Threat model](14-threat-model.md#third-party-text)). Plain code skips that block as well: it reads the lines of this step (`Waits for #n`, `Waits for release:` and the links between projects) and the `Replaces #n` line of step 3 only outside external blocks, and an unclosed block runs to the end of the task, so such a line inside a block records no wait, blocks nothing and replaces nothing. Dependencies are `Waits for #n` lines (or the forge's native blocked-by links where it has them). A `Waits for` line names only the work the task builds on: the one part of an umbrella that suffices, never the whole umbrella, because a wait on an umbrella holds the task until every part closes and lines the chain up in single file. The [Tech lead](01-overview.md#the-team) (formerly the planner) checks this when it writes the line, and a stall rechecks it ([The Maintainer](09-maintainer-agent.md)). A wait releases when every named issue is closed and every named pull request is merged into main. A target that is a pull request is resolved to the task that pull request closes (its branch or its closing keyword), and one that names the task's own pull request is no dependency (see [The Maintainer](09-maintainer-agent.md)). Resolving it tells Intakt which task's failure or stall the wait follows; it is not what releases the wait. A wait whose target is a pull request, a follow-up's wait on its original's pull request included, releases only when the forge confirms that pull request merged into main, never because the task it closes is closed (step 5, "A follow-up waits for the pull request it follows to merge"). When a task fails for good, the tasks that wait on it are held with the reason, instead of being built on a missing base.
   **A wait for a change in another repository is typed too.** A task that waits for a change outside its own repository (an upstream fix, a release of a tool Intakt runs on) carries a line `Waits for release: <owner>/<repo>#<n>`, with one or more references after the colon. The line by itself blocks the task: when Intakt reads it from a trusted author, it records each reference in the task's row, keyed by `<owner>/<repo>#<n>`, with its own state (waiting or satisfied), records the task as blocked, and mirrors that blocked state as the `blocked` status label ([Labels](04-labels.md)). Nobody sets that label by hand, and nothing below reads it: the row is the state. Lifting the wait clears the blocked state, which the label then follows, but keeps the reference records. Reading the same line again after the lift blocks nothing; only a reference that is new on the line (one with no record yet) blocks the task again. The `Waits for #n` reading takes only references before the colon, so it never reads these references and never lifts such a task early. As for `Waits for #n`, only a line from a trusted author counts. When the other repository is a project Intakt builds itself and the task needs only that change merged, the link between projects (`Waits for billing#12`, see [New and existing projects](12-new-and-existing-projects.md)) is the form to use; `Waits for release:` is for a repository Intakt does not build, or for a change the task needs released or deployed, not only merged. A task that also has a dependency of this step (a `Waits for #n` line for a task of its own repository, a link between projects, or a native blocked-by link of the forge) is lifted by the normal unblocking, not by the check below: the check only records each `Waits for release:` reference as satisfied, and the normal unblocking lifts the task once every such dependency is closed and every `Waits for release:` reference is recorded as satisfied, so closing the local wait never lifts a task whose outside change has not shipped, and a shipped outside change never lifts a task whose local dependency is still open. Reason: a task with about eight others behind it sat outside every queue for three days, because the wait for a fix in the tool that runs the builds was only a sentence in a decision; no label and no `Waits for` line told the unblocking or the Maintainer's check for unexplained blocks about it, and the fix had shipped the same day.
   **A dependency bot's pull request is taken without a label.** A pull request whose author the forge reports as one of the project's dependency bots (a project setting naming the bot logins, on by default for the forge's own bot) is admitted for review without the loop's label or a `take-over`; it is reviewed and checked as [Merge](08-merge.md#dependency-bots) describes and never merges without the owner's one approval, whatever paths it touches, and a diff outside the manifest and lock files and the CI action pins (protected paths) is refused there.
2. **Ready.** A tool-less call of the Tech lead (formerly the sizer and triage) checks the first point of the [Definition of Ready](../01-intent.md#definition-of-ready): that the task states an observable result, an acceptance condition and a single outcome. The other points are covered elsewhere on this page: what the task waits for and its source in step 1; size, evidence and the check against today's main in step 3; and the plan in step 4, where the Tech lead also names the docs the change will touch. A task is Ready only when it meets the whole definition. A task that fails this first check is parked with one comment listing what is missing; it costs no build.
3. **Sized.** The same call estimates the change in changed lines against a size contract with tiers: small tasks are merged with siblings when that saves a review, large ones must be split, and the size also sets the starting default for posting the plan for approval (step 4). Each part of a split is mergeable on main with its own tests and repeats the decisions that apply to it. Each part is written as one line of the form title, done-when, verify, files, depends on, and a plain-code check caps a chain of parts (each depending on the one before) at two; a split that needs a longer chain is re-cut, because a part is never split again. The tier that forces a split is lower when the pool is small (see [Budget and model planner](06-budget-and-model-planner.md)), because rework on a large change costs the most. A new gate rule whose cleanup needs more than one build is split so that the first part lands the rule with its ratchet list and the cleanup becomes one or more `ready` parts with the rule's milestone and priority, not blocked by the rule part; a rule issue that fits one build keeps the rule and its whole cleanup in one change, with no list (see [Ratchet lists](../04-constraints.md#ratchet-lists-for-a-new-rule-decided-2026-11-06)). The same call also judges each Evidence item of the task: producible in the Developer's sandbox (no network beyond the model provider and the package registries, no forge access, no real credentials) or not. A task with an unproducible item that it does not mark as owner-proved (`(owner provides)`) goes back to its author before any build, with one comment naming those items, like a task that is not ready; it costs no build. Measured on this repository, about 15% of blocking findings were evidence the Developer's sandbox could not produce (a running container, a real provider call, a hand check). An item marked owner-proved stays in the task: reviewers do not send a change back for it, and it is listed for the owner ([Reviews](07-reviews.md)). This is the target for the sizing prompt, which belongs to the build loop's configuration outside this repository; the prompt does not say it yet.
   **An issue is checked against today's main before it is built.** The validity check is part of getting an issue to Ready ([Definition of Ready](../01-intent.md#definition-of-ready)). When the Tech lead sizes an issue, it also judges, with evidence, whether the issue is done on main already, superseded by another issue, or contradicted by a later decision. The sizing call stays tool-less: plain code gives it the evidence, each part fenced as untrusted under its own source ([Threat model](14-threat-model.md#triage-and-sizing)): the numbers and titles of the open issues and of the issues closed in the last 30 days, from the forge's listing; for each path, command or name the issue cites, whether it exists on today's main and the latest commit on main that touched it; and the entries of the decisions page ([Decisions](../06-decisions.md)) added since the issue was last edited. The call answers with a typed disposition (holds, done, superseded, contradicted or unclear) that cites its evidence by reference (a commit on main, an issue number, a decision number), validated against its schema; an invalid answer is unclear. An issue that holds goes on through sizing as before, so valid work reaches Ready.

   **The model's answer never closes an issue by itself.** A reference that merely exists proves nothing: a formatting commit touches the cited file, and an unrelated later issue is still a later issue. So plain code closes an issue only on a link that plain code can read and that a person with write access made, and it looks that link up on the forge itself, never in the model's answer:
   - *Done:* the cited commit is on main, is newer than the issue's last edit, and belongs to a merged pull request that names this issue (its closing keyword, or its branch when the branch is this task's work branch), and the issue was not reopened after that merge. A commit older than the issue's last edit, or one whose pull request does not name the issue, confirms nothing.
   - *Superseded:* the other issue exists, is not this one, was opened after it, was written and last edited by an account with write access (the check of step 1), and its text names this issue as replaced on a line of its own, `Replaces #n`, the one form plain code reads, and only outside an external block (step 1): a `Replaces #n` line inside one, which holds copied or model-written text, is no link a person made and confirms nothing. A later issue that does not carry that line confirms nothing, however similar its title.
   - *Everything else goes to the Product owner:* a done or superseded answer without such a link, with the model's evidence attached; a contradicted issue, with the decision it contradicts (plain code checks that the decision exists and is newer than the issue's last edit); and an unclear one. A fix that landed through another issue's pull request, and an issue edited after its fix, go there too, on purpose. None of these is built and none is closed.

   An issue closed this way gets the link in a comment and a ledger event, so the owner can reopen it. "Confirmable" therefore means what plain code can confirm; the model only points to where to look. An issue sized more than 7 days ago is sized again, with this check, before its first build. Work already in flight (a pushed branch, an open pull request) is never judged again: it is finished, reworked or handed over by the rules for open pull requests (step 5). The Maintainer's backlog sweep (monthly by default) checks the ready issues not in flight the same way ([The Maintainer](09-maintainer-agent.md)). Reason: ready issues piled up faster than they were built (in a build loop running beside Intakt, 444 opened against 303 closed in one week), and an older one may be done already, replaced by a later issue or contradicted by a later decision, so building it as written spends a build on work nobody needs. Like the rest of this step, this is a target for the sizing prompt outside this repository.
   **Every pushed head is sized again.** A head can outgrow the contract after sizing, through a rework or fixes for findings, so the size check runs again on every pushed head: the changed lines come from the forge's diff of the pull request, with no model call, after a deterministic move check has taken out text under `docs/` that only moved. A head past the split tier is not reviewed; it goes to the Maintainer for a split (see [Reviews](07-reviews.md), which also has the move check).

   **A build that runs out of turns sends its task back to sizing, once.** After a task's first build that ended at the turn limit, the next step is not another build at the same size but the sizing call again, with that build's evidence. The sizing call may split the task, or keep it whole and state why; a kept task is built again with that reason in its plan. A part of an earlier split is never split again (T48), so its re-size can only keep it whole with a reason.
   - *What goes into the re-size.* The files the build touched and the lines it changed so far, which plain code reads from its bundle once the hand-back accepted it (an unfinished build's bundle goes through the hand-back's bundle checks and secret scan too, for these counts only, and nothing of it is pushed; with no commits they are marked unavailable, not zero, and a bundle the checks refuse takes the hand-back's refusal path below), and where it stopped, from the build's own report, redacted and secret-scanned like the pull request text before it goes into the call (a hit leaves the report out). The file paths are redacted and secret-scanned the same way before prompt assembly, deleted paths included: the bundle's secret scan covers only the objects the bundle adds, and a deleted path comes from the base tree. A path with a hit is left out and only counted.
   - *Which builds count, and the hand-over.* Only an unfinished build (no pull request text, or no commits) is re-sized or counted. Pull request text titled as blocked is the exception and comes first: with commits or without, the build keeps the blocked-output path ([Architecture overview](01-overview.md), build job), pushes nothing and sends the task to the owner, and it is neither re-sized nor counted as unfinished. The hand-back's refusal comes first: a bundle its checks refuse, the secret scan included, takes the hand-back's own path (back to the Developer once with the reason, held for judgement at the last secret-scan hit, handed over the second time) whatever the turn-limit status, and that build is neither re-sized nor counted here. When the hold on an unfinished build's bundle is released (the finding judged false and the kept commits pass a new scan), nothing of it is pushed either, because there is no pull request text for the work to go on with: the build then counts as an unfinished build whose bundle the hand-back accepted, so it is re-sized or handed over like any other, and the kept bundle is deleted once plain code has taken its counts. Because the release can come after the build job has ended, the hold keeps the build's parsed turn-limit status and its stop report, already redacted and scanned, beside the kept commits, and the re-size uses them. A build that handed back pull request text and an accepted bundle is finished whatever its turn-limit status and keeps the path every finished build has: pull request text titled as blocked keeps its commits unpublished and sends the task to the owner ([Architecture overview](01-overview.md), build job), and any other goes on to the pre-push check, CI and review as usual, and a failed pre-push check sends it back to the Developer under that check's own rule; the task's build cycles and the per-task total of the progress stop (T60) bound those rounds, as they bound every build. A second build of the same task that runs out of turns is not sized or built again: plain code, counting the task's out-of-turns builds in the ledger, hands it to the Maintainer or the owner. The turn-limit status read from `build.log` is untrusted ([Threat model](14-threat-model.md)), so plain code also counts unfinished builds from what it saw itself and hands the task over at the second. A build that ends with an accepted structured question parks its task and is not counted (a bundle handed back beside the question is dropped unread, so nothing of it is counted or pushed), and both counts start over when a person or the Maintainer sends a handed-over task back to building.
   - *Calibration.* Sizing also calibrates on the project's recent out-of-turns builds, only those plain code also counted as unfinished: plain code gives the call their files, characters and changed lines next to those of recent tasks that fit, so the estimate learns what ran out on this project. Builds with unavailable counts are left out of the file and line figures. Because a builder can forge the status on an unfinished build of its own, the sample's influence is bounded: it takes at most one build per task, only figures plain code counted from an accepted bundle (never figures a builder reported), and only a fixed number of the most recent builds. A skewed sample can only move estimates, which the size tiers, the size check on every pushed head, the owner's routing and the budget caps still bound; it starts no build, merge or close by itself. Even a window filled with forged builds of distinct tasks stays bounded: the figures are numbers plain code counted, not text; the tasks that fit come only from finished builds; and the size tiers and the size check on every pushed head are plain code that never reads the sample, so a poisoned sample can at worst make the call split other tasks more often, or keep a too-large task whole for at most two unfinished builds, the bound this rule gives every task: its first out-of-turns build is re-sized, and a second out-of-turns or unfinished build hands it over even if the re-size kept it whole. A finished build's failed pre-push checks are bounded by the task's build cycles and the per-task total of the progress stop, as for every task, and a head it pushes past the split tier goes to the Maintainer through the size check. So the sample adds no build beyond the bounds every task has, and it never lets a head past the split tier. Each forged sample also costs its own task one of the two unfinished builds that hand it over.

   Reason: on a build loop running beside Intakt, 16 builds in four days ran out of turns, 13% of all tokens, and 7 of those tasks never merged; one task ran out four times after sizing called it a fit, because a build of the same task usually runs out at the same place. Like the rest of this step, this is a target for the sizing prompt outside this repository.
4. **Planned.** Every task has a plan before its build (files, approach, risks) and names the docs the change will touch, as the [Definition of Ready](../01-intent.md#definition-of-ready) requires; the Tech lead writes the plan and names those docs with it. For a task of a project with a user interface whose planned files or labels match the Designer's triggers, the plan also needs the Designer's additions (flows, states, copy, widths, accessibility; [The Designer](07-reviews.md#the-designer-planned)): until it carries them the task is not Ready, so neither an approval of the plan nor `plan:skip` below starts its build. What is optional, per project, is posting that plan back as a comment before the build starts and waiting for its approval. With plan approval on, only an owner approval of that plan starts the build; the approved plan becomes part of the task. Plan approval is adaptive: size sets the starting default (off for small tasks, on for large ones), a rejected change turns it on for the project, and five clean merges turn it off again. The `plan:` label overrides that default for one task: `plan:required` posts the plan and waits for approval, `plan:skip` starts the build without waiting (see [Labels](04-labels.md)). The plan itself stays required for every task; only posting it and waiting for approval depend on the default and the label.
   **The plan carries a brief for the first build.** Before a task's first build the Tech lead adds a brief to the plan: the change in at most eight lines, the files and interfaces it touches (file and line), the exact command that verifies it, and a done-when that a check or a reviewer can observe. A plain-code check refuses a brief with no verify command, no done-when or more than eight lines of change, and the task is not Ready until it passes. The brief is issue-derived text, so it reaches the builder fenced like the task ([Threat model](14-threat-model.md)). Reason: measured on the loop that builds this repository, about 57% of the tokens on merged work went to rework after the first build and review, and about half of the first reviewed heads were sent back; a build that starts from a stated change and a stated check has less to guess.
5. **Prioritized.** Every queued task has an explicit priority (owner-set, or inherited: split parts and follow-ups take their original's; their milestone follows the rule below; a flaky-test task Intakt files is `urgent`, see [Reviews](07-reviews.md), and so is the task for a dependency bot's red check, below), and work is picked milestone by milestone. Tasks not started yet are ordered `urgent` first, then by the due date of the task's milestone (a task with no milestone, or whose milestone has no due date, last; a ready task with no milestone is also listed for the owner, below), then by effective priority (the priority label, `high`, `normal`, `low`, raised by aging, below; a task without a priority label counts as `normal`), then the critical path and the class order (below), then by the number of queued tasks that wait on it (below), then by issue number (the critical path ranks chain heads within a milestone and priority). Distinct milestones with the same due date, or with no due date, are tied: their tasks are ordered together, by effective priority first and then by the keys that follow, and a chain head on the critical path of any of the tied milestones counts as on the critical path. So, among tasks not started yet, every ready task of a milestone due earlier is built before any task of a milestone due later (a task an earlier milestone waits on is placed with that milestone, "The critical path goes first within its milestone" below), and a later milestone only gets the build time an earlier one cannot use; two exceptions come first: an `urgent` task is picked before any milestone, and work on an open pull request (below) goes ahead of every task not started yet, whatever its milestone. A task that is blocked or waits on another is passed over for the next task in this order. The reason: with priority first, a `high` task of a later milestone was built before a `normal` task of the milestone due next, so a milestone due soon slipped behind later work whose labels happened to be higher, and keeping the stages in order took relabelling. Process work (fixes to the loop's own flow) can be put ahead of features on purpose, never by accident. Work is also classed as core, feature or tooling (gates, developer tools, docs tooling); class orders work only within one milestone (or milestones tied on their due date) and priority, and by default core comes first and tooling last, and tooling that does not fix an observed failure is not queued without the owner. When several slots are free, the highest-priority ready class gets them first; a lower class only takes a slot that would otherwise sit idle. One `priority:urgent` build may start while the heads waiting for review are at their cap.

   **Two limits hold the builders, and they count different heads.** The review cap counts only heads waiting for a reviewer or in review; a head waiting for CI, for a CI runner or for landing does not count, because no reviewer can move it. The limit on heads in flight counts every pushed head not merged yet, whatever it waits for, and is higher: twice the review cap by default. A build starts only while both admit it, except that one `priority:urgent` build may start past the review cap, as above, and a rework of an open pull request replaces a head already counted, so it starts at the in-flight limit too: otherwise a limit filled with heads that need rework would hold the very builds that let them merge. Only a fresh build is held by the in-flight limit. The count is the number of pushed heads not merged yet, including heads awaiting owner approval, on hold or queued for rework, not only the heads in a waiting phase. Reason: the review cap alone keeps builders from outrunning the reviewers, but it once counted heads waiting for CI and stopped the builders while the review worker had nothing to review; counting only reviewable heads fixes that, and leaves the heads waiting for CI or landing unbounded. Those heads still conflict with each other on merge and each needs a CI run, so the second, higher limit bounds merge conflicts and CI load without stopping builders while reviews are due.
   **Open pull requests come first.** Work on a task whose pull request is already open (a rework, a merge of main, a fix after a hand-over, a continuation) goes ahead of any task not started yet, whatever their milestones and priorities; only an `urgent` task goes before it. Within each group the order above holds (milestone, then priority, then the tasks waiting on it, then number). Finished work waiting on a small step is cheaper to land than new work, and an open pull request ages: main moves under it and conflicts grow.
   **The pull request is read, not remembered.** Whenever a task is queued (when it becomes ready, after a hand-over is settled, after a hold is released), Intakt reads the open pull request of the task's branch from the forge, and a task that has one is queued as a rework of that pull request, never as a fresh build. A settled hand-over can drop the task's queue record, so the record is never what tells Intakt that a pull request exists. A step that writes to a pull request reads it again first; when the pull request it expects cannot be found, the task goes to the Maintainer, never to a write.
   **The critical path goes first within its milestone.** Intakt keeps the dependency graph of each milestone (its open tasks and their `Waits for` lines) and that graph's critical path: the longest chain of open tasks, by their size estimates, that still has to merge before the milestone is done. The graph follows every `Waits for` line out of the milestone: an open task of another milestone, or of none, that a task of the milestone waits on, directly or further down the chain, is a prerequisite of the milestone and joins its graph, so it counts on that milestone's critical path and in its forecast ([Dashboard](13-dashboard.md)), and its delay shows there. In the order of this step such a prerequisite is placed with the milestone due first among those whose graph it joins, when that milestone comes before its own place (a later milestone, or none); its milestone label stays as it is, and Intakt writes none. Otherwise a task of a later milestone would be built only after every task of the milestone that waits on it, and one with no milestone would wait at the end of the order, while the milestone due first could not finish without it. A chain head is the first open task of a chain, whose own waits are all closed. A wait cycle ([The Maintainer](09-maintainer-agent.md), "Waits for another issue") has no chain head and no end, so plain code finds it in the graph and never forecasts past it: the critical path counts each task of the cycle once and stops there, and a milestone whose graph reaches a cycle shows no forecast date but "cannot finish: wait cycle" with the cycle's tasks, until the cycle is gone. It does not open the missed-forecast card, because the cycle already has its own route to the Maintainer and then the owner. Within each group above (open pull requests, then the rest), each milestone (or milestones tied on their due date) and each priority, the chain heads on the critical path of that milestone are picked first, then the rest. The class order (core, feature, tooling) still decides which class a free slot goes to first, so the critical path ranks tasks within a class and never moves a lower class ahead of a higher one. A stalled chain head gets its cause and route ([The Maintainer](09-maintainer-agent.md)) and shows on the board as a forecast slip ([Dashboard](13-dashboard.md)). Reason: Developers kept busy with other ready work while the one head on two milestones' critical path stood still, so every lane looked healthy and the chain did not move.
   **Then the task that unblocks the most, then age.** "By dependencies" means: among tasks of one priority (and one milestone, where milestones order the queue) that the rules above leave tied, the task that more queued tasks wait on goes first, counting every task behind it through the whole chain of `Waits for` lines, not only the direct ones; equal counts go by age, oldest (lowest issue number) first. The same tie-break orders the review of heads that share a priority; the review queue does not group by milestone, so there it counts only within a priority. For builds it ranks tasks only inside one milestone (or milestones tied on their due date) and priority and never moves one across either; for reviews it ranks only inside one priority and never moves one across it. It never outranks the critical path or the class order. Reason: picks within one priority went by age only, so a task three others waited on sat behind unrelated older ones, and the build slots idled on chains that could have been opened.
   **Waiting work ages one band per `aging_days`.** Wherever this step orders by priority, for builds and for reviews, it uses the effective priority: the label's band, raised one band for every full `aging_days` the work has waited. `aging_days` is set per project, 5 by default, and 0 turns aging off. A band goes from `low` to `normal` to `high` and never to `urgent`, so aging never moves work ahead of an `urgent` task. An issue's age counts from when the runner first saw it `ready`, from the runner's own state and never from extra forge calls (such as reading its label history): the tick's one listing (below) shows the label, and the runner records the first tick that showed it. When an issue loses `ready`, its age resets, and it counts again from the next time it is seen `ready`. An open pull request ages the same way for the rework and review order, counted from when its current head first entered the queue: a new head (a rework, a merge of main) starts its count again. An issue that an open pull request waits on (through a `Waits for` line) ranks at least at that pull request's effective priority, capped at `high`, inside the issue's own milestone (for a prerequisite of an earlier milestone, the milestone the critical path rule above places it with, so the two rules add up: the critical path picks its milestone, and this rule its band there), so an old pull request's blockers go first. The cap holds also when the pull request is `urgent`: a blocker never becomes `urgent` this way, so only an `urgent` label puts a task ahead of every milestone, and the blocker keeps its place among the other tasks of its own milestone. In the build and rework order, aging changes the band only inside the order of one milestone (or of milestones tied on their due date, which priority orders together): it never moves work across milestones with different due dates, and the milestone due date still orders that queue before any band. The review queue does not group by milestone (above), so there an aged head is reviewed before heads of a lower effective band whatever their milestones, still never before an `urgent` head; this changes only the review order, never which task is built or reworked next. Labels stay as the owner set them; Intakt writes no priority label for aging, and the dashboard shows each task's effective priority and why ([Dashboard](13-dashboard.md)). A ready issue with no milestone is never given one automatically (the task for a dependency bot's red check, below, is the one exception): it is listed for the owner on the dashboard, and it waits at the end of the order until the owner places it, unless a milestone waits on it, which places it with that milestone (the critical path rule above). Reason: measured on this repository on 2026-11-13, 37 of the 47 ready `priority:high` M7 issues were filed since 2026-11-11, and the M7 plan tasks from 2026-10-31 at `normal` sat below all of them until they were raised by hand; inside one milestone the order counted age only as the last tie-break.
   **Follow-ups join the next milestone.** A follow-up queued from a non-blocking finding (a P3 or an advisory specialist's note, see [Reviews](07-reviews.md)) joins the next open milestone after its original's; when there is no later open milestone, it keeps its original's. A follow-up that carries a blocking finding a reviewer raised as a follow-up item keeps its original's milestone, and so do split parts (a ratchet cleanup part included). Each follow-up names its original's milestone in its body, so a person can move it back. Reason: when follow-ups took their original's milestone, the milestone being finished kept refilling with its own follow-ups while the next stages waited. Next-milestone routing is the default; the owner can list it for [bounded tuning](06-budget-and-model-planner.md#bounded-tuning).
   **A follow-up waits for the pull request it follows to merge.** When Intakt files a follow-up while its original's pull request is still open, it writes a `Waits for` line naming that pull request, and the follow-up is passed over like any waiting task until that pull request merges. This wait is on the pull request itself, not on the task step 1 resolves it to, and the same holds for every `Waits for` line whose target is a pull request (other than the task's own, which is no wait): intake does not tell a follow-up's line from one a person wrote, because both release the same way, only when the forge confirms that pull request merged into main. A task that closes, or drops out of the open-issue listing, while its pull request is still open releases nothing. The merge is learned without a read per tick: the tick's one listing (below) carries the open pull requests, and while it shows that pull request open, nothing is read and nothing is released. Once a complete listing no longer shows it open, Intakt reads that pull request once by its own number and stores the answer: merged into main releases the wait; closed without a merge, or merged into another branch after a retarget, releases nothing. A read that fails stores nothing and is retried on the next tick; after three failed reads in a row it is retried at most once a day, like a held answer below, and the wait stays held. A read that finds the pull request open (it was reopened between the listing and the read) stores nothing and releases nothing: the wait stays held, and the listings watch that pull request again, so its later merge or close is learned by the same steps. A stored "closed without a merge" answer is dropped as soon as a listing shows the pull request open again, and while a wait stays held on such an answer, Intakt reads that one pull request again at most once a day, so a reopen and merge between two ticks is learned within a day of reading time, with no read per reference on every tick. Reading time is a tick on which the worker reads the forge for intake and its listing comes back complete: no read happens while the worker will not take work, while the reserve of the forge budget pauses routine reads, or after a listing that came back short, so those hours delay the day (below). A follow-up filed after the merge waits for nothing. When the pull request closes without a merge, the wait follows the task step 1 resolved it to: if that task failed for good, the waiting task is held with the reason, as step 1 holds every task that waits on a failed one; otherwise the wait is a stall with that task's cause and route ([The Maintainer](09-maintainer-agent.md)), for example a task that landed through a replacement pull request, whose wait the Maintainer points at the replacement or removes. Reason: a follow-up edits the files of the change it follows, so a build started while that change was still open worked on a base without it and met it again as a conflict with main.
   **A dependency bot's red check is urgent.** The task Intakt files when CI fails on a dependency bot's pull request ([Merge](08-merge.md#dependency-bots)) is `urgent`, so it is picked before any milestone, and it carries the earliest open milestone, so it counts toward that milestone's progress. When the bot closes or supersedes the pull request, Intakt closes the task with a comment naming the replacement (the bot's newer pull request, read from the forge), or saying there is none. Reason: seen on 2026-11-05, such tasks without a milestone sat behind 98 milestoned tasks, and one for a superseded pull request stayed ready.
6. **Scheduled.** Each plan or size estimate carries a forecast set of files or areas (the task's expected files). When the forecast is confident, a task not started yet whose forecast overlaps a head in flight (a build still running, or a pushed head not merged yet) is built after it, within the limits below (forecast against actual overlap is logged to measure that); the rest run in parallel across the build slots. A project can choose a serial mode (one build at a time, in dependency order) for small setups.
   **A slot skips work whose files are in flight, unless nothing else in its band (milestone, priority and class) is ready.** When a slot is free, the first candidate in the order of step 5 sets the band: its milestone, its priority and its class. If its forecast is confident and overlaps a head in flight, only a candidate of the same milestone, priority and class that is free of overlap may take the slot in its place; if there is none, the first candidate is built anyway, so a skip never leaves a slot idle, never crosses into a later milestone and never lets lower-priority work ahead. A chain head on the critical path (step 5) is not skipped for an overlap either. This differs from a blocked or waiting task (step 5), which is passed over for the next task in the whole order, because it cannot be built at all. Work on an open pull request is never skipped or delayed for an overlap: its files are already in flight, and holding it back only lets the conflict grow. The rule applies only to tasks not started yet. Reason: measured on this repository, 49 merges brought 14 cycles for a conflict with main, most of them in the lock file, the bundles list and the guide's index, and each of those cycles was a build spent on files another head was already changing. Also measured: a task heading the critical path waited almost two hours as a fresh pick behind one shared documentation file, and two high-priority tasks were held back while two normal-priority ones took their slots.
   **A third send-back goes to a split, once.** A send-back is a head returned to the Developer with findings: a review round that requests changes, or red CI as [Reviews](07-reviews.md) counts it (two red-CI send-backs in a row are free within a cycle and the third counts as one). A merge of main is no send-back, and neither is Intakt's own merge of a conflict only in registry files ([Merge](08-merge.md)). When one task is sent back for the third time, no slot starts its next rework: the task goes to the Maintainer, which splits it along its open findings with the split and `Source:` rules (the done part merges if it passes on its own, see [The Maintainer](09-maintainer-agent.md)). This happens once per task: after a task has been split this way, a later third send-back of it or of one of its parts takes the normal rework and re-planning rules, never a second split by this rule. When the open findings give no split, the Maintainer takes the other routes of re-planning (a rewrite of the acceptance, or one retry on the strong tier). Reason: a task sent back three times has shown that it is too large or too unclear for one build, and a smaller task costs less than a fourth rework of the same scope.

**Outside events are re-checked early.** Internal hand-offs (a build that ends, a review that is judged) start the next step at once, because they are events. An outside event (CI, an approval, a new head of a bot pull request, the default branch's CI) is only seen by polling, so a step that leaves one pending arms one early re-check of its lane, backing off 30 s, 60 s, 120 s, 240 s and then the normal interval. A delay is used only while it is shorter than the lane's normal interval, and any work on the lane resets the backoff. Each pending event keeps one due time in the queue, the only schedule for reading it: every read that finds the event still pending, early or by the lane's normal run, advances the backoff and sets the due time to that read plus the smaller of the next delay and the normal interval, and the normal run skips an event whose due time has not come. With a 5-minute normal interval the reads fall 30 s, 90 s, 210 s and 450 s after the step, then every 300 s; with a 1-minute interval at 30 s, then every 60 s. One timer per lane is armed at a time, for the earliest due time, also one at the normal interval, so a due time between two of the project's ticks is read when it comes. A reset never moves a read later: each due time becomes the earlier of its stored value and 30 s after the work. A due time that passed while the lane's lock was held is read as soon as that run ends, and the lane's lock keeps the re-check from running beside the lane's normal run. Below a configured share of the forge's hourly budget only the early re-checks give way: the event's due time is then one normal interval after its last read, and the lane's timer stays set for that read, because it is essential. Pending-aware re-checks are an owner setting, on by default ([Merge](08-merge.md#waiting-for-ci), pending-aware re-checks). Webhooks stay the optional last step.

**Waits and intake read from the one listing.** The state of every waited-for issue of a project Intakt manages (a `Waits for #n` line, or a link between projects) comes from the tick's one listing of the forge (see [Merge](08-merge.md#waiting-for-ci), one listing per forge per tick), or from the stored state of an item the listing shows unchanged, read conditionally; it is never one read per reference. Only a complete, successful listing can mark a waited-for issue closed: an issue of a listed project that such a listing does not return as open counts as closed. A listing that comes back short (a page that failed, was rate-limited or came back empty midway, a page cap that was reached, or a search that hit its result cap) closes nothing, and every wait keeps its stored state until a complete listing comes. A wait whose target is a pull request (step 5) is the one exception to "never one read per reference", and a bounded one: the listing shows that a pull request is no longer open, not whether it merged, so once a complete listing stops showing a waited-for pull request open, Intakt reads that pull request once by its number and stores the answer. That is one read per waited-for pull request, not one per tick or per waiting task (plus a retry of a failed read on the next tick, at most once a day after three failures in a row, and at most one read a day while a wait stays held on a "closed without a merge" answer, step 5); a pull request the listing still shows open, and a listing that comes back short, cause no read and release nothing. The pick follows the same rule: the order of step 5 (`urgent` first, then open pull requests, then milestone due date, priority and the other ties down to issue number) is computed over the complete listing, every page of it read in the same tick, before anything is sorted, and never over the first page of a listing. A listing that comes back short picks nothing that tick, just as it closes no wait. The comments and label history of a waiting task are read again only when its update time moved or, because an edit in the same second keeps the update time, when the listing shows other labels or other numbers in its body (its waits and closing keywords) than the last read did, and then only for a task the intake rules need a history for. A worker that will not take work this tick (no free slot, paused, draining or held by the budget) makes no forge call for intake: it neither lists nor re-reads the ready issues the listing returned. Measured: about 85% of the forge calls of a build loop were such routine re-reads, repeated on every tick of every worker (the waits of 35 blocked issues, each waited-for issue read one by one, and a re-read of every ready issue, also by workers about to skip), and they used up the hourly forge budget the essential steps need.

**A wait for another repository is lifted by plain code.** Intakt lifts a `Waits for release:` wait itself, without a model, once every issue it names is closed and the change that closed each one has reached what the project runs: deployed, for a tool Intakt runs on, or released and taken into the project's lock file, for a dependency. Two plugin questions decide it ([Plugins](02-plugins.md)): the forge plugin answers which merged change closed the issue, and the language or deployment plugin answers whether that change is in what the project runs. The listing above does not cover a repository Intakt does not manage, so the forge plugin reads each named issue directly: its state and the merged change that closed it (the forge's closing link, for example a pull request whose closing keyword names the issue and that was merged). It reads only the waiting references of blocked tasks, by the blocked state stored in the task's row and never by the label, at most once per reference per hour, conditionally where the forge allows it, and as a routine read that waits while the reserve of the forge budget is in force. A read that fails or comes back incomplete changes nothing: the reference keeps its stored state. This check itself lifts only a task with none of the dependencies of step 1 (no `Waits for #n` line, no link between projects such as `Waits for billing#12`, and no native blocked-by link of the forge, open or closed): such a task is lifted when its last reference is recorded satisfied. Just before such a task is lifted, by this check or by the normal unblocking of step 1, the language plugin checks every satisfied dependency reference once more against the lock file in effect, a local read with no forge call: a reference whose change is no longer in it goes back to waiting, and the task stays blocked. Nothing is rechecked after the lift: a rollback after the task was queued is not this check's job. The deployed case needs no recheck here, because it goes to the Maintainer (below). Where neither plugin can answer, as for the deployed case while no deployment plugin exists ([Plugins](02-plugins.md)), the wait goes to the Maintainer ([The Maintainer](09-maintainer-agent.md)); it is never lifted by default, by a timeout or on a model's judgment. An issue closed with no merged change, or a state Intakt cannot read for a day, also goes to the Maintainer instead of staying hidden.

**A `hands-off` item is never admitted.** Step 1 treats it like a closed one, whatever its other labels, `urgent` included; removing the label gives it back ([Labels](04-labels.md#who-drives-an-item)).

## Tasks drafted from the dashboard

The owner can describe new work in plain words in the dashboard's New task box ([Dashboard](13-dashboard.md#starting-a-task)). Drafting is a Tech lead job on the chosen project: it reads the owner's text, fenced as untrusted input like every other ([Threat model](14-threat-model.md#task-drafting-tech-lead)), and has read-only access to that project's repository and plan. It writes a draft task: the title, outcome, decisions, acceptance, a size estimate, the milestone and priority it proposes, and a `Waits for` line for each open task the work builds on (the rule for `Waits for` lines in step 1 applies). The call is charged to the project's weekly share like any job, and it waits while the share or the pool has no room.

Nothing reaches intake before the owner approves the draft. "The owner" names the role: the dashboard has no login, so whoever can act on it ([Who can act](13-dashboard.md#who-can-act)) holds it, any approval request that passes the `Host` and CSRF checks counts, and the ledger records the dashboard as the approval's source, not a verified person. Approval files the draft, as the owner edited it, as an issue on that project's forge with the labels a ready task carries, and a draft that must be split is filed as its parts together. Intakt's own forge identity creates the issue and applies the labels, as it does for split parts ([Labels](04-labels.md)), so step 1's author check sees an account with write access. Later edits follow step 1's rule: an edit by any account with write access (the owner's own forge account, for example) keeps the task eligible, and an edit by an account without write access makes it ineligible until a trusted account edits or confirms it. From there the filed issue is a task like any other: it enters at step 1 and is checked for eligibility, readiness and size, planned, prioritized and scheduled as above, then built, checked, reviewed and approved as usual. The issue is the record; the draft is not a second queue, and the dashboard never queues a build itself.

## Taking over an issue Intakt would not build

An issue written or last edited by someone without write access is not eligible (step 1). When a person with write access sets `take-over`, the label stands in for the authorship check: that person has read the issue and vouches for building on it. The reason is that people outside the project report real work, and refusing it until someone retypes it wastes the writer's time. The issue's text stays inside an external block, so the Developer reads it as data, never as instructions ([Threat model](14-threat-model.md#third-party-text)). Edits to the issue after the label make it ineligible again until the label is set again, because the label vouched for the text as it was. The other steps (ready, sized, planned, prioritized, scheduled) apply as for any task.

A part split from a larger change can name a source: a line `Source: <branch>@<sha>`, honored only from a trusted author. The orchestrator checks that the commit is on that branch and gives the job that one ref, read-only; the Developer applies the source's own diff, not whole files.

**A split happens once.** The split plan is recorded before any part is created. After a crash the split resumes from the record, and a part whose create answer was lost is found by its part marker before anything is created, so no part exists twice. When the original is an issue, it stays open as an umbrella that is never built, and closes on its own once every part is closed.

**An oversized pull request with no task is split too.** Splitting is not only for tasks. A head past the split tier on a pull request opened by the owner's or the maintainer agent's identity goes to the Maintainer as a split, with no `take-over` needed: these identities are trusted, so building from their head is safe, and `take-over` exists for untrusted authors. Anyone else's oversized pull request is not split: it gets one comment saying it is past the size limit and asking the author to split it, and once a person with write access sets `take-over`, it is split like the owner's ([The maintainer agent](09-maintainer-agent.md)). The split plan is recorded first, as above, and plain code checks every changed path or hunk of the diff from the merge base to `<sha>` against it before it is recorded. Each part is a task naming `Source: <branch>@<sha>` of the original head, so the Developer applies the source's own diff and writes nothing new; parts are cut along files where possible, each stays under the split tier, and a part that links to another states its merge order. The original pull request is closed, not left as an umbrella, and only once every part's pull request is open or merged and the parts check passes: each part's head as its pull request was opened, applied in merge order to the merge base, must give the tree of `<sha>`. A part whose pull request was closed without merging counts as missing, so the original stays open. The same check also reads each part as it stands now: an open part's current head and a merged part's merged change must carry exactly its share, nothing dropped and nothing added, and applied in merge order they must still give that tree, so a part pushed to after it opened cannot merge a different change; until every part has merged, a new head of a part that drops or adds an edit is refused before review, and a part closed without merging after the original was closed reopens the original. With a missing part or a mismatch, the original goes back to the maintainer agent and, the second time, to the owner. When the check passes, Intakt records the verified head in the split plan and closes the original with a comment naming the parts and that head, then reads the head again: if it moved during the close, Intakt reopens the original and extends the split as below. Intakt never force-pushes the original branch and never deletes it, and open issues whose text names the original pull request are updated to name the parts, an edit shown in the issue's history as the Maintainer's. Commits on the original branch after `<sha>` extend the split with more parts: they are checked against the diff from the old `<sha>` to the new head, not against hunks of the merge-base diff, and the close check stays that all parts, applied in order, give the tree of the new head.
