# Choosing work

How a task (its issue on the forge) becomes a build. Every step is cheap and runs before any build tokens are spent.

1. **Eligible.** Open, labeled for the loop and not labeled `idea` (which wins, see [Labels](04-labels.md)), written by a trusted author and last edited by one (an account with write access, checked through the forge's permission API when the task becomes eligible and again before each build; the body is the build's instructions, so an edit by anyone else makes the task ineligible until a trusted account edits or confirms it), not blocked. Text a task copies from an untrusted source sits in an `<!-- external -->` block that Intakt fences as untrusted (see [Threat model](14-threat-model.md#third-party-text)). Dependencies are `Waits for #n` lines (or the forge's native blocked-by links where it has them). A target that is a pull request is resolved to the task that pull request closes (its branch or its closing keyword), and one that names the task's own pull request is no dependency (see [The maintainer agent](09-maintainer-agent.md)). When a task fails for good, the tasks that wait on it are held with the reason, instead of being built on a missing base.
2. **Ready.** A tool-less triage call checks that the task states an observable result, an acceptance condition and a single outcome. A task that does not is parked with one comment listing what is missing; it costs no build.
3. **Sized.** The same call estimates the change in changed lines against a size contract with tiers: small tasks are merged with siblings when that saves a review, large ones must be split, and a band in between gets a plan first. Each part of a split is mergeable on main with its own tests and repeats the decisions that apply to it. The tier that forces a split is lower when the pool is small (see [Budget and model planner](06-budget-and-model-planner.md)), because rework on a large change costs the most.
   **Every pushed head is sized again.** A head can outgrow the contract after sizing, through a rework or fixes for findings, so the size check runs again on every pushed head: the changed lines come from the forge's diff of the pull request, with no model call. A head past the split tier is not reviewed; it goes to the maintainer agent for a split (see [Reviews](07-reviews.md)).
4. **Planned (optional, per project).** The builder writes back what it will do (files, approach, risks) as a comment before it starts. With plan approval on, only an owner approval of that plan starts the build; the approved plan becomes part of the task. Plan approval is adaptive: size sets the starting default (off for small tasks, on for large ones), a rejected change turns it on for the project, and five clean merges turn it off again.
5. **Prioritized.** Every queued task has an explicit priority (owner-set, or inherited: split parts and follow-ups take their original's), and the queue is ordered by it, then by dependencies and age. Process work (fixes to the loop's own flow) can be put ahead of features on purpose, never by accident. Work is also classed as core, feature or tooling (gates, developer tools, docs tooling); by default core comes first and tooling last, and tooling that does not fix an observed failure is not queued without the owner. When several slots are free, the highest-priority ready class gets them first; a lower class only takes a slot that would otherwise sit idle. One `priority:urgent` build may start while the heads waiting for review are at their cap.
   **Open pull requests come first.** Work on a task whose pull request is already open (a rework, a merge of main, a fix after triage, a continuation) goes ahead of any task not started yet, whatever their priorities; only an `urgent` task goes before it. Within each group the priority order holds. Finished work waiting on a small step is cheaper to land than new work, and an open pull request ages: main moves under it and conflicts grow.
   **The pull request is read, not remembered.** Whenever a task is queued (when it becomes ready, after a hand-over is settled, after a hold is released), Intakt reads the open pull request of the task's branch from the forge, and a task that has one is queued as a rework of that pull request, never as a fresh build. A settled hand-over can drop the task's queue record, so the record is never what tells Intakt that a pull request exists. A step that writes to a pull request reads it again first; when the pull request it expects cannot be found, the task goes to the maintainer agent, never to a write.
6. **Scheduled.** Each plan or size estimate carries a forecast set of files or areas. When the forecast is confident, a task not started yet whose forecast overlaps a head in flight is built after it, within the limits below (forecast against actual overlap is logged to measure that); the rest run in parallel across the build slots. A project can choose a serial mode (one build at a time, in dependency order) for small setups.
   **Avoiding files in flight only reorders work of one priority.** When a slot is free, the first candidate in the order of step 5 sets the band: its priority and class. If it overlaps a head in flight, only a candidate of the same priority and class that is free of overlap may take the slot in its place; if there is none, the first candidate is built anyway, so a skip never lets lower-priority work ahead. Work on an open pull request is never skipped or delayed for an overlap: its files are already in flight, and holding it back only lets the conflict grow. The rule applies only to tasks not started yet. Measured: a task heading the critical path waited almost two hours as a fresh pick behind one shared documentation file, and two high-priority tasks were held back while two normal-priority ones took their slots.

**A `hands-off` item is never admitted.** Step 1 treats it like a closed one, whatever its other labels, `urgent` included; removing the label gives it back ([Labels](04-labels.md#who-drives-an-item)).

## Taking over an issue Intakt would not build

An issue written or last edited by someone without write access is not eligible (step 1). When a person with write access sets `take-over`, the label stands in for the authorship check: that person has read the issue and vouches for building on it. The reason is that people outside the project report real work, and refusing it until someone retypes it wastes the writer's time. The issue's text stays inside an external block, so the builder reads it as data, never as instructions ([Threat model](14-threat-model.md#third-party-text)). Edits to the issue after the label make it ineligible again until the label is set again, because the label vouched for the text as it was. The other steps (ready, sized, planned, prioritized, scheduled) apply as for any task.

A part split from a larger change can name a source: a line `Source: <branch>@<sha>`, honored only from a trusted author. The orchestrator checks that the commit is on that branch and gives the job that one ref, read-only; the builder applies the source's own diff, not whole files.

**A split happens once.** The split plan is recorded before any part is created. After a crash the split resumes from the record, and a part whose create answer was lost is found by its part marker before anything is created, so no part exists twice. The original stays open as an umbrella that is never built, and closes on its own once every part is closed.
