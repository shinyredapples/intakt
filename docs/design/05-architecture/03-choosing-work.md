# Choosing work

How a task (its issue on the forge) becomes a build. Every step is cheap and runs before any build tokens are spent.

1. **Eligible.** Open, labeled for the loop and not labeled `idea` (which wins, see [Labels](04-labels.md)), written by a trusted author and last edited by one (an account with write access, checked through the forge's permission API when the task becomes eligible and again before each build; the body is the build's instructions, so an edit by anyone else makes the task ineligible until a trusted account edits or confirms it), not blocked. Text a task copies from an untrusted source sits in an `<!-- external -->` block that Intakt fences as untrusted (see [Threat model](14-threat-model.md#third-party-text)). Dependencies are `Waits for #n` lines (or the forge's native blocked-by links where it has them). A `Waits for` line names only the work the task builds on: the one part of an umbrella that suffices, never the whole umbrella, because a wait on an umbrella holds the task until every part closes and lines the chain up in single file. The planner (the Tech lead) checks this when it writes the line, and a stall rechecks it ([The maintainer agent](09-maintainer-agent.md)). A target that is a pull request is resolved to the task that pull request closes (its branch or its closing keyword), and one that names the task's own pull request is no dependency (see [The maintainer agent](09-maintainer-agent.md)). When a task fails for good, the tasks that wait on it are held with the reason, instead of being built on a missing base.
2. **Ready.** A tool-less triage call checks that the task states an observable result, an acceptance condition and a single outcome. A task that does not is parked with one comment listing what is missing; it costs no build.
3. **Sized.** The same call estimates the change in changed lines against a size contract with tiers: small tasks are merged with siblings when that saves a review, large ones must be split, and a band in between gets a plan first. Each part of a split is mergeable on main with its own tests and repeats the decisions that apply to it. The tier that forces a split is lower when the pool is small (see [Budget and model planner](06-budget-and-model-planner.md)), because rework on a large change costs the most. A new gate rule whose cleanup needs more than one build is split so that the first part lands the rule with its ratchet list and the cleanup becomes one or more `ready` parts with the rule's milestone and priority, not blocked by the rule part; a rule issue that fits one build keeps the rule and its whole cleanup in one change, with no list (see [Ratchet lists](../04-constraints.md#ratchet-lists-for-a-new-rule-decided-2026-11-06)). The same call also judges each Evidence item of the task: producible in the builder's sandbox (no network beyond the model provider and the package registries, no forge access, no real credentials) or not. A task with an unproducible item that it does not mark as owner-proved (`(owner provides)`) goes back to its author before any build, with one comment naming those items, like a task that is not ready; it costs no build. Measured on this repository, about 15% of blocking findings were evidence the builder's sandbox could not produce (a running container, a real provider call, a hand check). An item marked owner-proved stays in the task: reviewers do not send a change back for it, and it is listed for the owner ([Reviews](07-reviews.md)). This is the target for the sizing prompt, which belongs to the build loop's configuration outside this repository; the prompt does not say it yet.
   **Every pushed head is sized again.** A head can outgrow the contract after sizing, through a rework or fixes for findings, so the size check runs again on every pushed head: the changed lines come from the forge's diff of the pull request, with no model call, after a deterministic move check has taken out text under `docs/` that only moved. A head past the split tier is not reviewed; it goes to the maintainer agent for a split (see [Reviews](07-reviews.md), which also has the move check).
4. **Planned (optional, per project).** The builder writes back what it will do (files, approach, risks) as a comment before it starts. With plan approval on, only an owner approval of that plan starts the build; the approved plan becomes part of the task. Plan approval is adaptive: size sets the starting default (off for small tasks, on for large ones), a rejected change turns it on for the project, and five clean merges turn it off again.
5. **Prioritized.** Every queued task has an explicit priority (owner-set, or inherited: split parts and follow-ups take their original's; their milestone follows the rule below; a flaky-test task Intakt files is `urgent`, see [Reviews](07-reviews.md)), and work is picked milestone by milestone. Tasks not started yet are ordered `urgent` first, then by the due date of the task's milestone (a task with no milestone, or whose milestone has no due date, last), then by priority (`high`, `normal`, `low`; a task without a priority label counts as `normal`), then the critical path and the class order (below), then by the number of queued tasks that wait on it (below), then by issue number (the critical path ranks chain heads within a milestone and priority). So every ready task of an earlier milestone is built before any task of a later one, and a later milestone only gets the build time an earlier one cannot use. A task that is blocked or waits on another is passed over for the next task in this order. The reason: with priority first, a `high` task of a later milestone was built before a `normal` task of the milestone due next, so a milestone due soon slipped behind later work whose labels happened to be higher, and keeping the stages in order took relabelling. Process work (fixes to the loop's own flow) can be put ahead of features on purpose, never by accident. Work is also classed as core, feature or tooling (gates, developer tools, docs tooling); class orders work only within one milestone and priority, and by default core comes first and tooling last, and tooling that does not fix an observed failure is not queued without the owner. When several slots are free, the highest-priority ready class gets them first; a lower class only takes a slot that would otherwise sit idle. One `priority:urgent` build may start while the heads waiting for review are at their cap.
   **Open pull requests come first.** Work on a task whose pull request is already open (a rework, a merge of main, a fix after triage, a continuation) goes ahead of any task not started yet, whatever their milestones and priorities; only an `urgent` task goes before it. Within each group the order above holds (milestone, then priority, then the tasks waiting on it, then number). Finished work waiting on a small step is cheaper to land than new work, and an open pull request ages: main moves under it and conflicts grow.
   **The pull request is read, not remembered.** Whenever a task is queued (when it becomes ready, after a hand-over is settled, after a hold is released), Intakt reads the open pull request of the task's branch from the forge, and a task that has one is queued as a rework of that pull request, never as a fresh build. A settled hand-over can drop the task's queue record, so the record is never what tells Intakt that a pull request exists. A step that writes to a pull request reads it again first; when the pull request it expects cannot be found, the task goes to the maintainer agent, never to a write.
   **The critical path goes first within its milestone.** Intakt keeps the dependency graph of each milestone (its open tasks and their `Waits for` lines) and that graph's critical path: the longest chain of open tasks, by their size estimates, that still has to merge before the milestone is done. A chain head is the first open task of a chain, whose own waits are all closed. Within each group above (open pull requests, then the rest), each milestone and each priority, the chain heads on the critical path of that milestone are picked first, then the rest. The class order (core, feature, tooling) still decides which class a free slot goes to first, so the critical path ranks tasks within a class and never moves a lower class ahead of a higher one. A stalled chain head gets its cause and route ([The maintainer agent](09-maintainer-agent.md)) and shows on the board as a forecast slip ([Dashboard](13-dashboard.md)). Reason: builders kept busy with other ready work while the one head on two milestones' critical path stood still, so every lane looked healthy and the chain did not move.
   **Then the task that unblocks the most, then age.** "By dependencies" means: among tasks of one priority (and one milestone, where milestones order the queue) that the rules above leave tied, the task that more queued tasks wait on goes first, counting every task behind it through the whole chain of `Waits for` lines, not only the direct ones; equal counts go by age, oldest (lowest issue number) first. The same tie-break orders the review of heads that share a priority; the review queue does not group by milestone, so there it counts only within a priority. For builds it ranks tasks only inside one milestone and priority and never moves one across either; for reviews it ranks only inside one priority and never moves one across it. It never outranks the critical path or the class order. Reason: picks within one priority went by age only, so a task three others waited on sat behind unrelated older ones, and the build slots idled on chains that could have been opened.
   **Follow-ups join the next milestone.** A follow-up queued from a non-blocking finding (a P3 or an advisory specialist's note, see [Reviews](07-reviews.md)) joins the next open milestone after its original's; when there is no later open milestone, it keeps its original's. A follow-up that carries a deferred blocking finding keeps its original's milestone, and so do split parts (a ratchet cleanup part included). Each follow-up names its original's milestone in its body, so a person can move it back. Reason: when follow-ups took their original's milestone, the milestone being finished kept refilling with its own follow-ups while the next stages waited.
6. **Scheduled.** Each plan or size estimate carries a forecast set of files or areas. When the forecast is confident, a task not started yet whose forecast overlaps a head in flight is built after it, within the limits below (forecast against actual overlap is logged to measure that); the rest run in parallel across the build slots. A project can choose a serial mode (one build at a time, in dependency order) for small setups.
   **Avoiding files in flight only reorders work of one milestone and priority.** When a slot is free, the first candidate in the order of step 5 sets the band: its milestone, its priority and its class. If it overlaps a head in flight, only a candidate of the same milestone, priority and class that is free of overlap may take the slot in its place; if there is none, the first candidate is built anyway, so a skip never crosses into a later milestone and never lets lower-priority work ahead. A chain head on the critical path (step 5) is not skipped for an overlap either. This differs from a blocked or waiting task (step 5), which is passed over for the next task in the whole order, because it cannot be built at all. Work on an open pull request is never skipped or delayed for an overlap: its files are already in flight, and holding it back only lets the conflict grow. The rule applies only to tasks not started yet. Measured: a task heading the critical path waited almost two hours as a fresh pick behind one shared documentation file, and two high-priority tasks were held back while two normal-priority ones took their slots.

**Outside events are re-checked early.** Internal hand-offs (a build that ends, a review that is judged) start the next step at once, because they are events. An outside event (CI, an approval, a new head of a bot pull request, the default branch's CI) is only seen by polling, so a step that leaves one pending arms one early re-check of its lane, backing off 30 s, 60 s, 120 s, 240 s and then the normal interval. A delay is used only while it is shorter than the lane's normal interval, and any work on the lane resets the backoff. Each pending event keeps one due time in the queue, the only schedule for reading it: every read that finds the event still pending, early or by the lane's normal run, advances the backoff and sets the due time to that read plus the smaller of the next delay and the normal interval, and the normal run skips an event whose due time has not come. With a 5-minute normal interval the reads fall 30 s, 90 s, 210 s and 450 s after the step, then every 300 s; with a 1-minute interval at 30 s, then every 60 s. One timer per lane is armed at a time, for the earliest due time, also one at the normal interval, so a due time between two of the project's ticks is read when it comes. A reset never moves a read later: each due time becomes the earlier of its stored value and 30 s after the work. A due time that passed while the lane's lock was held is read as soon as that run ends, and the lane's lock keeps the re-check from running beside the lane's normal run. Below a configured share of the forge's hourly budget only the early re-checks give way: the event's due time is then one normal interval after its last read, and the lane's timer stays set for that read, because it is essential. Pending-aware re-checks are an owner setting, on by default ([Merge](08-merge.md#waiting-for-ci), pending-aware re-checks). Webhooks stay the optional last step.

**Waits and intake read from the one listing.** The state of every waited-for issue comes from the tick's one listing of the forge (see [Merge](08-merge.md#waiting-for-ci), one listing per forge per tick), or from the stored state of an item the listing shows unchanged, read conditionally; it is never one read per reference. Only a complete, successful listing can mark a waited-for issue closed: an issue of a listed project that such a listing does not return as open counts as closed. A listing that comes back short (a page that failed or was rate-limited midway, or a search that hit its result cap) closes nothing, and every wait keeps its stored state until a complete listing comes. The comments and label history of a waiting task are read again only when its update time moved. A worker that will not take work this tick (no free slot, paused, draining or held by the budget) makes no forge call for intake: it neither lists nor re-reads the ready issues the listing returned. Measured: about 85% of the forge calls of a build loop were such routine re-reads, repeated on every tick of every worker (the waits of 35 blocked issues, each waited-for issue read one by one, and a re-read of every ready issue, also by workers about to skip), and they used up the hourly forge budget the essential steps need.

**A `hands-off` item is never admitted.** Step 1 treats it like a closed one, whatever its other labels, `urgent` included; removing the label gives it back ([Labels](04-labels.md#who-drives-an-item)).

## Tasks drafted from the dashboard

The owner can describe new work in plain words in the dashboard's New task box ([Dashboard](13-dashboard.md#starting-a-task)). Drafting is a Tech lead job on the chosen project: it reads the owner's text, fenced as untrusted input like every other ([Threat model](14-threat-model.md#task-drafting-tech-lead)), and has read-only access to that project's repository and plan. It writes a draft task: the title, outcome, decisions, acceptance, a size estimate, the milestone and priority it proposes, and a `Waits for` line for each open task the work builds on (the rule for `Waits for` lines in step 1 applies). The call is charged to the project's weekly share like any job, and it waits while the share or the pool has no room.

Nothing reaches intake before the owner approves the draft. Approval files the draft, as the owner edited it, as an issue on that project's forge with the labels a ready task carries, and a draft that must be split is filed as its parts together. Intakt's own forge identity creates the issue and applies the labels, as it does for split parts ([Labels](04-labels.md)), so step 1's author check sees an account with write access. Later edits follow step 1's rule: an edit by any account with write access (the owner's own forge account, for example) keeps the task eligible, and an edit by an account without write access makes it ineligible until a trusted account edits or confirms it. From there the filed issue is a task like any other: it enters at step 1 and is checked for eligibility, readiness and size, planned, prioritized and scheduled as above, then built, checked, reviewed and approved as usual. The issue is the record; the draft is not a second queue, and the dashboard never queues a build itself.

## Taking over an issue Intakt would not build

An issue written or last edited by someone without write access is not eligible (step 1). When a person with write access sets `take-over`, the label stands in for the authorship check: that person has read the issue and vouches for building on it. The reason is that people outside the project report real work, and refusing it until someone retypes it wastes the writer's time. The issue's text stays inside an external block, so the builder reads it as data, never as instructions ([Threat model](14-threat-model.md#third-party-text)). Edits to the issue after the label make it ineligible again until the label is set again, because the label vouched for the text as it was. The other steps (ready, sized, planned, prioritized, scheduled) apply as for any task.

A part split from a larger change can name a source: a line `Source: <branch>@<sha>`, honored only from a trusted author. The orchestrator checks that the commit is on that branch and gives the job that one ref, read-only; the builder applies the source's own diff, not whole files.

**A split happens once.** The split plan is recorded before any part is created. After a crash the split resumes from the record, and a part whose create answer was lost is found by its part marker before anything is created, so no part exists twice. The original stays open as an umbrella that is never built, and closes on its own once every part is closed.
