# Merge

Only the orchestrator merges. Right before merging it:
1. re-reads the task and the pull request, and stops if either is blocked, closed or changed since the verdicts. Intakt re-reads the pull request's base right before the call and merges only when it is main; where the forge's merge call can pin the base, Intakt pins it. A head merged elsewhere is reported on the task, and the issue stays open;
2. requires green CI on exactly the head it is about to merge, and waits when CI has not registered that head yet (a head it pushed a moment ago);
3. records the merge attempt (the pull request and that head) before the call, then merges only that head: the forge call names the head commit, so a push in between makes the merge fail instead of riding the earlier approval, and a merge whose answer is lost, or that the forge finishes late, is still Intakt's: the attempt stays open until the outcome is definitive ([Watching main](#watching-main));
4. reads the result back (the merge commit and its tree) and only then closes the issues and records the merge.

Landing order:
- **A head ready to land goes before new reviews.** On each tick the review worker first lands any head that needs no model call: every required verdict exists for its exact patch, CI is green on it, the owner's approval is there where the change needs one, and it merges cleanly with main. Only then does it start a review. Priority orders reviews and builds, never finished work. Reason: a low-priority head with green CI, two approving reviews and the owner's approval waited behind several normal-priority reviews of 20 to 40 minutes each. The merge costs no tokens and takes a few minutes, while every hour of waiting lets main move on, which adds merges of main, CI runs, conflict risk and a new head that needs the owner's approval again.
- **One path for landing.** The same no-model landing step serves this rule and the [budget back-off](06-budget-and-model-planner.md) (where only merges run). A head that turns out to need more than a merge goes back to its place in the review queue and is not tried again for a short while. Reason: two landing paths would drift apart, and a head that cannot land must not block the queue or be retried on every tick.

- **A head that fails backs off alone.** An unexpected failure while reviewing, landing or merging one head sets that head's next try time and records the cause in the ledger and on its card, and the tick goes on to the next head; after a few failures in a row the head goes to the maintainer agent ([Budget](06-budget-and-model-planner.md)). Reason: a head that fails on every try must not stop the review and merge of every other head.

Protected paths (gates, CI config, agent instructions, dependency policy, the boot harness) need an approval, and a protected change gets one of exactly two outcomes, decided at once when its head has green CI and its panel's verdicts ([Approving protected changes](#approving-protected-changes)), while an owner decision plain code can already read from a pushed head is asked on that head (below):
- **Intakt approves on the spot** when no hard floor is hit, every mechanical check passes, the Security engineer's security review agrees and its penetration test finds no way around the change.
- **Otherwise the owner reviews.** The request names the floor or the check that sent it. It never resolves itself: no timer, no veto window, no "approve unless stopped", no one-tap shortcut.
- **Protected paths are read from the whole change.** Whether a head touches a protected path is decided from the full diff between the merge base with the current main and the exact head being merged, combined with the per-commit lists (the paths each commit between the merge base and the head touches, each commit compared against each of its parents; the commits between the merge base and the head are the commits reachable from the head and not from the merge base, so a merge's second-parent commits count unless main already contains them; a path a commit holds exactly as the current main holds it adds nothing to main and is left out of that commit's list, so a merge of main does not list what main added, while a revert to an old main still differs and is listed; a shallow history counts as unreadable), never from a merge commit's diff against one parent, because a crafted merge (first parent the branch, second parent an old main commit) could otherwise revert or delete a protected file without it being listed. Submodule entries and `.gitmodules` count as protected.
What goes to the owner follows these rules:
- **Same flow as any change.** A build that touches protected paths is pushed and opened as a normal pull request, gets CI, its review panel and reworks on its own branch; it is never exported as a patch for someone to re-apply (patches go stale and every rejection meant a rebuild from scratch). When CI and its review panel pass, it parks with "waiting for the owner" and notifies once, unless the owner's answer to an early question (below) already covers it.
- **A risky change to the CI definition is never pushed before the owner approved it.** A forge runs the workflow taken from the pushed commit, so a build that edits it would run its own workflow on the project's runners before anyone looked. A change is pushed without that approval only when a scan of the workflows (the head's, main's, and the two merged) shows they can reach no more than a forge-hosted, throwaway runner with a read-only token and no secrets: hosted runner labels only, read-only permissions, no secrets beyond the read-only token, no triggers that run with the base repository's rights; anything the scan cannot read counts as risky. A `runs-on` taken from a variable or an expression is unreadable, since the variable can change without a commit, so it counts as risky even while the variable is unset: every CI change of that project waits for the owner, and its builders get no CI log excerpts ([Threat model](14-threat-model.md#ci-log-excerpts)). The scan reads the files the workflows run from the repository as part of the CI definition: a change to one of them is a CI change, since it runs on the runner as the workflow does. Self-hosted runners always ask, and must be ephemeral ([Threat model](14-threat-model.md#self-hosted-ci-runners)). Merging a CI change follows the approval rules below: a workflow that reads a repository secret, raised permissions, a new trigger or a runner change always goes to the owner (a hard floor), and any other CI edit, like a file a workflow runs, is approved on the spot only when it clears every floor and check. A risky change stays local; the owner approves the exact diff and commit first, and only then is it pushed. That request shows the whole change, not only the CI files (an approved one-line workflow edit can run a script nobody was shown); an image in it (a plain, non-executable file whose name and first bytes agree on PNG, JPEG or GIF) is named by its sizes and full blob ids instead of its bytes, which a comment cannot hold and which the approved commit pins, while any other file with a NUL byte keeps its bytes, so the request is refused, since a script can run with one ([Threat model](14-threat-model.md#residual-risk)). A change too large to show in full is sent back to be split, never approved from a file list. Approving the push does not approve the merge: the owner is asked again, with the full list of protected changes, when the head is ready to merge.
- **The owner is asked only for a reviewed change.** Before the push request reaches the owner, the review panel reviews the held diff with a security brief: triggers that run with the base repository's rights, permissions, runners, secrets, untrusted text (titles, bodies, branch names) put into a script through an expression instead of an environment variable, unpinned actions, and what a later push of the branch could run. A rejection goes back to the builder without asking the owner; an approval travels with the request, so the owner confirms a reviewed change instead of reading a workflow cold. The envelope that needs no approval stays narrow on purpose: a token that may write issues could rewrite a task's body, which is the build's instructions, so any write scope keeps needing the owner.
- **The approval names the head.** It is a normal forge review by the owner's account (possible because the pull request's author is Intakt's identity, not the owner), or a comment `approve <sha>` by it, which no job can write (jobs have no forge credentials) and Intakt's own identity never writes. A new push needs a new approval, except where the answer to an early question carries (next rule).
- **An owner decision is asked when it first appears.** When plain code can read from a pushed head that the change needs the owner (a new package outside the trusted vendors or another change the dependency policy sends to the owner, a protected change that hits a hard floor or that no mechanical check covers), the owner is asked on that first head, in parallel with any CI fix or review round, not after them. The question names the decision, not the head: the package set (each new package with its version and source) or the protected change (the diff of every protected path). The answer covers that decision and carries to every later head that keeps it unchanged, so a rework, a CI fix or a clean merge of main asks nothing new; a head that changes the package set or the protected diff is asked again about what changed. Merging still needs green CI and every verdict on the exact head; the owner's answer never stands in for them. It stays a real answer from the owner's own account (above): no default, no timeout, no veto window. A need the checks can only see later (a reviewer's loosening class, a security review that does not agree) is asked when that verdict arrives. Reason: a pull request that added packages needing the owner kept failing CI for an unrelated reason, and since the owner was asked only after green CI and every approval, the owner was never asked while it held a milestone's critical path for hours.
- **An early approval counts once its head passes.** An approval given before CI and the reviews finish stays: it counts once that same head passes, and a push after it voids it, except the clean merge of main, the generated-files resolution described below and an answer to an early question, which carries as above. Intakt never removes or re-asks it because of a review or CI round.
- **The owner can send a head back.** A comment `changes <sha>` by the owner's account, or a review requesting changes on that head, when it is the owner's newest decision there, sends the head back with the owner's note fenced: to the builder for a task's head, to the maintainer agent for its own pull request. The head is no longer asked about and stops counting toward the owner-wait cap. Only a later approval from the owner's own account overrides the owner's send-back, never anything the maintainer agent or Intakt's identity posts, so a helper cannot overrule the owner.
- **The owner is asked only about a head that merges.** Before a protected head is offered for approval it must merge cleanly with main; a real conflict goes back to the builder, not to the owner or the maintainer. An early question (above) is the exception: it asks about the decision, not the head, so it goes out on the first pushed head even when that head conflicts with main, in parallel with the conflict's fix, and its answer carries to the resolved head when that head keeps the decision unchanged; the merge approval itself still waits for a head that merges. While a head waits, main moving costs nothing (no rebuild, review or new notice); a conflict that appears only in generated files is resolved by Intakt itself after the approval (merge main, regenerate the generated files, and let the approval carry when the protected change is byte-identical and the extra commits touch only generated files), and a real conflict withdraws the request once, but parks the approval instead of dropping it. When the resolved head is a merge of main onto the parked head, made by Intakt's builder or maintainer agent through the hand-back, with the protected change byte-identical, the parked approval carries to it once its review and CI pass; any other new head drops it with one comment and is asked again. Intakt's own recorded merges stay recognized across hand-backs, so an owner is never asked twice for the same change because of Intakt's bookkeeping.
- **An approval is informed and unforgeable.** The request lists every protected change of that head and says plainly when the change modifies the checks that judged it (green CI then means the head's own gates passed). Only the owner's own account can give it, through a channel no agent of Intakt's can write: Intakt's identity never posts it, and helper agents acting for the owner (the maintainer agent, which writes the summaries of approval requests and triages) run under a forge identity that is never the owner's account, so a review or `approve <sha>` they post is not the owner's, and a post guard blocks them from it as a second barrier, not by an instruction. A clean merge of main into an approved head that leaves its protected changes identical keeps the approval, so a busy main does not mean asking again every hour.
- **Only a few heads wait for the owner at once** (a cap per install, three by default), so the owner's queue stays short enough to act on. Only real waits count: a head with green CI and every review passed that waits for the merge approval, and a held CI change that waits for its push approval. A head still in review, sent back or on hold does not count, and a wait Intakt cannot classify counts (fail closed). An early question (above) is asked whatever the cap and does not count toward it, because holding it back is the very wait it exists to remove. A head that is ready while the cap is full is queued for the owner with no label, comment or notice and holds no slot; the queue is ordered by priority, then age, so a newer head never takes a freed place ahead of an older one of the same priority. A freed place is reserved under the same lock that read the count, before the owner is asked, so two workers cannot both take it, and a failed ask gives it back. At the cap, builds of tasks known to need the owner wait, with one notice; a task's own rework is never blocked.
- **Main is merged in last.** A head gets CI and its reviews as it was pushed. Intakt merges main into the branch only when the head is ready to merge (green CI, every verdict, any owner approval it needs) or when the forge reports a conflict with main. A clean merge keeps the verdicts and the owner's approval (above), and CI runs once more on the merged head before the merge. Merging main into every open branch whenever main moved restarted CI on all of them: one pull request ran CI 19 times in a day, and a single self-hosted runner fell an hour behind.

## Approving protected changes

On this repository 32 of 120 merged pull requests waited for the owner; about 6 of those only edited comments in the boot harness, most dependency approvals added official Symfony packages, and waiting for approvals was about 20% of all waiting in the loop. Of 57 pull requests that asked the owner for approval, 52 merged, 5 were closed and none was rejected: an approval that is always given filters nothing while every protected change waits for a person. So Intakt approves on the spot what its checks and the Security engineer ([Threat model](14-threat-model.md#the-security-engineers-sessions)) clear, and asks the owner for what touches the approval system itself or secret handling and workflow permissions, at once and with the reason. This replaces approval by class, which needed at least two reviewers from different vendors classifying a change as tightening or neutral. The approval is plain code that runs the steps below in order and approves only when all pass; the first step that fails ends it with a request to the owner that names that step. Its two model sessions, the security review and the penetration test, are run by the Security engineer.

### Hard floors

Exactly two hard floors remain. They are deterministic rules over the whole change (read as protected paths are, above). No model output lowers them, and a hit always goes to the owner:
- **The approval system:** the protected-path list, the floors, the checks that apply them, the Security engineer's prompts and the canary corpus (below), so Intakt can never widen its own approvals.
- **Secrets and permissions:** any change to how secrets or credentials are stored, read, injected, redacted or scanned, including the secret scan's rules and its allowlist; a workflow that reads a repository secret; raised workflow permissions, new triggers or a runner change.

Other CI edits, gate tests, agent instructions and the boot harness are not floors: they go through the mechanical checks, the security review and the penetration test. They are approved on the spot only where a mechanical check covers the change (gate tests and the harness by their checks); a workflow file or an agent instructions file that no check covers still goes to the owner. One rule besides the floors still sends a change to the owner: a panel reviewer that classifies the protected part as loosening, or gives no valid class ([Reviews](07-reviews.md)). A classification never approves on its own.

### Mechanical checks

Every protected file the change touches must be covered by a mechanical check that passes; a file no check covers goes to the owner. The checks are plain code. What differs per language comes from a `language` plugin ([Plugins](02-plugins.md)), PHP first.
- **Comment-only.** The old and the new file parse to the same syntax tree once comments and whitespace are dropped, through tree-sitter or the language's own tokenizer (for PHP, `PhpToken`). A comment a tool reads counts as code: docblocks (static analysis reads their types), suppression and ignore markers, and inline allow directives. Where a language has no parser, the check does not apply.
- **Dependency policy.** One adapter per ecosystem reads the old and new manifest and lock file (Composer first; npm, PyPI, Go and Cargo by plugin). The old files are read at the merge base of the head with main, never at main's tip, as for the protected paths below, and so for every owner decision about a change (packages, protected paths, workflow changes): a branch behind main that only adds one package is asked about that package alone, not about packages main added since. The rules are written once over language-neutral sources: OSV.dev for advisories and deps.dev for release dates and use. A change passes only when every new package, transitive ones included, comes from an allowed vendor in the owner's config, has no open advisory, and has a release older than the minimum age in the owner's config, and when no install script, plugin or package source changes (for Composer: `scripts`, `allow-plugins`, `repositories`, `config`, binaries and autoload files). The orchestrator queries the sources, never a job; an unreachable source or an unknown answer goes to the owner.
- **Gate code is no weaker.** Main's gate tests run unchanged against the head's gate code, and so does the violation corpus: every violation the gates have ever caught, kept as a fixture that must still be caught. Both run through the project's check command, so the proof is language-neutral, in their own check container and as their own user, with the result leaving through a channel the code under test cannot rewrite. A check that runs the candidate's code cannot detect code written to cheat it, which is why the security review and the penetration test follow.
- **Harness from main.** The boot gate runs main's trusted harness (`bin/instance`, `bin/probe`) against the head, so a harness change cannot certify itself. Booting proves only that the head still boots, so main's isolation probes also run through the head's harness: a probe that reaches the network, writes outside its folder, reads a credential or runs as another user must still be stopped. A harness change passes only when both hold.

### Independent security review

The Security engineer (#864) runs two separate model sessions on the protected part: a **security review** and a **penetration test**, each with its own role and prompt ([Threat model](14-threat-model.md#the-security-engineers-sessions)). They get the diff, main's version of every protected file and the floor and check results, never the builder's pull request text or reasoning, and their verdicts are typed objects checked like any other. The security review must agree that the change keeps or tightens the rules. A second AI vendor adds confidence when one is available and is never required. Missing capacity (no account free, a failed session, a stand-in, or a substitute in either session's place) sends the request to the owner, never waits it out.

### Penetration test

The penetration test tries to write a fixture that main's gate rejects and the head's gate accepts. Plain code runs each fixture against both, in a check container without network. A fixture that gets through is proof of weakening: the change goes to the owner with the fixture, and the fixture joins the violation corpus once the owner confirms it. Finding nothing is not proof of safety; it is one more check that must pass.

### Earned autonomy

There is no per-category dry-run mode and no per-category count. A project's automatic approval can be switched on once both hold:
- every **canary change** reaches the owner: canaries are owner-known changes that run through the pipeline regularly and must be sent to the owner, at least three per kind of protected change (comment-only, dependency, gate code, harness, and the floors: a workflow that reads a repository secret, an edited approval rule, an edited secret scan); and
- a replay of the repository's past owner approvals agrees with the computed decision on at least 20 heads.

The owner's one switch in the owner's config then turns it on, since turning it on widens the approval rules. A missed canary or an owner overrule turns it off for the project until both hold again. There is no daily cap on automatic approvals: a cap only sent routine approvals back to the owner.

### Containment

- **Automatic revert.** When main's canaries or violation fixtures fail, Intakt looks at the automatic approvals merged since they last passed. When there is exactly one and no later merge touched any file it changed, Intakt reverts that merge at once: the revert restores those files to main's version before it, byte for byte, so it needs no approval. Otherwise (several automatic approvals, or a later merge on the same files) Intakt reverts nothing on its own and asks the owner, naming every candidate merge, and no automatic approval is given in that project until the owner answers. In both cases automatic approval is off for the project until both conditions of earned autonomy hold again, and the owner is notified.
- **Visible afterwards.** Every automatic approval says so on the pull request in one line (the head, each check that passed), and is listed on the dashboard for a week with that line, so a wrong call is seen without anything waiting on a person; it is information, not a notice.

## Waiting for CI

- **A wait for CI holds nothing.** A head whose CI is pending holds no slot and no lock: its step ends, the head goes back to its queue with its place by age and a time to look again, and the lane takes a head whose CI has finished. A head pending for a set time (for example 30 minutes) is admitted by age anyway, so a slow pipeline is not starved by fast ones. A drain does not wait for parked heads.
- **Every waiting phase has a ceiling.** A step that waits for CI, for a reviewer slot or on a merge of main ends after a set time (for example 20 minutes), also when it still holds the lane (a head admitted by age after the set time above, or a step waiting on a merge of main). Jobs that call a model keep their progress stop instead. A wait at its ceiling is classified and repaired without a model, as the [principles](../02-principles.md) describe: a conflict with main takes the merge-main path, no CI run takes the missed-CI path below, a run queued for lack of a runner parks the head (it holds no lane) and shows runner capacity on the dashboard, and anything else ends the job as stalled. The task goes back to its queue with its place kept and the lane is free for the next one. The same task stalling three times in a row raises one notice naming the phase and what was read; every stall and its class goes in the ledger, so a recurring class can get its own repair. For the reason, see the principle "A wait has a ceiling" in the [principles](../02-principles.md).
- **A head waiting for CI is not a head waiting for review.** The cap on built heads waiting for review counts only heads whose CI has finished. Heads still waiting for CI count against the CI capacity instead ([Budget and model planner](06-budget-and-model-planner.md#ci-design-for-later)): when more heads wait for CI than the runners can clear in a set time, new builds wait, and the dashboard shows "waiting for CI" apart from "waiting for review". A review cap filled with heads whose CI had not started kept the build slots closed while nothing was being reviewed.
- **Polling first, webhooks last and optional.** Intakt reads the forge by polling and works fully without webhooks, which need an endpoint the forge can reach (a public URL or a tunnel) and so add setup and attack surface. A webhook is a later, optional addition for installs that already have a public endpoint; it only makes a change visible sooner and never replaces the poll. The poll is cheap by five rules:
  - **Conditional requests.** Each read sends the last ETag or If-Modified-Since value; GitHub answers "not modified" without counting it against the rate limit.
  - **One listing per forge per tick.** A tick lists the open issues and open pull requests of all projects on one forge once (for example one search over their repositories) instead of reading each item or each project, and skips re-reading the body of any item whose update time (and, for a pull request, head) did not change. New eligible tasks, steering labels and owner answers in comments are found this way, since a label or a comment moves the issue's update time. The listing carries no CI results, and a finished check run changes neither the head nor the pull request's update time, so this skip never covers CI.
  - **CI is read per waiting head.** Each head waiting for CI has its check status read on its own, by commit, as a conditional request on the short interval, until CI has finished for that head. The poll then stops reading CI for that head; the merge step still reads CI on the exact head right before merging (above), so a rerun that changed the result after the poll stopped is seen there and never rides the earlier green.
  - **Adaptive intervals.** Long (for example 15 minutes) when the project is idle, short (for example 1 minute) otherwise, so a running build keeps the short interval even with no head waiting. A project is idle when it has no head waiting for CI or a review and no build or review job running, which plain code reads from the queue and the running jobs. An idle project runs only the long listing poll, and a waiting state's own deadline still wakes it.
  - **Rate-limit aware.** A refusal makes that project wait for the reset time the forge names (on GitHub a 403 with `X-RateLimit-Remaining: 0`, or a 403 or 429 with `Retry-After`, or a GraphQL answer of any status with `X-RateLimit-Remaining: 0`; the forge raises it as a typed rate-limit result, makes no call with the installation's token in the same rate-limit pool (on GitHub `core` for REST, `graphql` for GraphQL) before the latest reset any answer of that pool named, and records every REST answer's remaining budget and reset per installation in the cache the workers share); other projects go on. A refused shared listing holds the projects on that forge only; projects on other forges go on.
  - **A reserve for essential calls.** Each installation keeps a share of its hourly budget (20% by default, owner-configurable) for the calls the loop cannot do without: the CI of a waiting head and of the default branch, merges, pushes, review posts and owner notices. Below the reserve, by the latest recorded reading, routine reads pause until the reading's reset: listings beyond each project's one per tick, wait and intake scans, and dashboard refreshes. Essential calls always go on; only the forge's own refusal above stops them, and a head whose essential read it stopped waits for the reset as a waiting head, never as a failing one. Routine re-reads on every tick of every worker once spent a whole hour's budget, and the check of a red default branch was skipped.
- **A missed CI start is detected.** A forge can miss a push: the branch moves, the pull request keeps the old head and no run starts. After a set time (for example 10 minutes) with no run for the head, or with the pull request on another head, Intakt reads the pull request once. Closed or merged: the head leaves the queue and goes to the maintainer agent. A conflict with main (the forge starts no run then): a merge-main rework for the builder. Otherwise Intakt nudges the forge once (for example by closing and reopening the pull request) and, if that starts nothing, hands the head to the maintainer agent once. No head waits for CI forever.
- **A cancelled run is waited on, not judged.** A new push cancels the run of the head it replaces (the workflow's concurrency group), so a cancelled run says nothing about the head; read as red CI, it once handed a pull request over although nothing had failed. A cancelled run is ignored when a newer run of the same event and the same pull request exists on the same head. A remaining cancelled run counts as unfinished CI: the head waits, is never sent back for it and never merges on it. When nothing restarts it within the missed-start time, it takes the missed-CI path above: one re-trigger, then the head goes to the maintainer agent once ([Reviews](07-reviews.md), [Principles](../02-principles.md)).
- **No runner is not a wait.** A run that cannot start because the plan's CI minutes are spent or no runner takes it is recorded with that cause and shown on the board, never as an endless "pending" (see [Budget and model planner](06-budget-and-model-planner.md#ci-design-for-later)).

## Hands-off and take-over

The labels are defined in [Labels](04-labels.md#who-drives-an-item); this is what they mean for the merge flow.
- **A `hands-off` item does not merge.** The first step of the list above also re-reads the label, right before publishing, so a label set while the merge was about to run stops it. A push or a post a job produced after the label is not published; its unpushed work is kept as a saved bundle.
- **A taken-over pull request merges like Intakt's own.** After `take-over`, the builder reworks the open findings, the panel reviews the head and the rules above apply unchanged, protected-path rules included.
- **A fork Intakt cannot push to is carried over.** Intakt applies the change on an Intakt branch and opens a new pull request that links the original. Every original author is kept as a `Co-authored-by` trailer on Intakt's signed commits, so credit survives. The original gets one comment pointing to the new pull request, and nothing else is written to it.
- **A pull request that touches protected paths is not taken over.** The builder may not change protected paths, so Intakt says so once, naming the files, and leaves the pull request to people. The reason is that a taken-over pull request would otherwise be a way to push a protected change through the builder. A dependency bot's pull request is not taken over either: it is reviewed and merged as it is ([Dependency bots](#dependency-bots)).

## Pull requests Intakt did not open

- **Merged through the forge.** Intakt merges a pull request it did not open (a contributor's, a dependency bot's, the owner's) through the forge's merge API with the project's merge method, not by moving main itself, so the forge closes it and its author keeps the credit. The steps at the top of this page apply unchanged (the attempt is recorded before the call, the merge call names the head), and Intakt records the resulting commit as its own merge. This holds for every pull request Intakt did not open, a contributor's as much as a bot's.
- **Protected paths are approved by the head, not by a key.** A protected change is authorized by the approval of exactly its head (above), never by the signing key of the commits in it. A contributor's or a bot's commits in an approved head are fine.

## Dependency bots

- **Taken without a label.** A pull request from a dependency bot (Dependabot, Renovate) is work without the eligibility label ([Choosing work](03-choosing-work.md#dependency-bot-pull-requests)). A project setting names the bot logins; it is on by default for the forge's own bot. Only an author the forge authenticates as one of those bot accounts counts.
- **Manifest and lock files only.** A diff that touches anything besides manifest and lock files (and CI action pins, which are protected) is refused with one comment naming the files.
- **Checked like any change.** Review, CI and the dependency-policy adapter run as for any change. Manifests and lock files are protected paths, so the owner approves the head once.
- **Only the owner's approval of the exact head counts.** For a bot's pull request this rule takes precedence over the carry and automatic rules above: no on-the-spot approval by Intakt, no answer to an early question carried to a later head, and no approval kept across a merge of main. Intakt never pushes to a bot's branch; the bot's own push (a rebase after main moved, a newer version) is a new head that voids the approval and is asked again once its review and CI pass. Reason: the bot, not Intakt's builder, makes every head, so nothing Intakt checked links the new head to the approved one.
- **Intakt writes the Evidence.** For such a pull request whose diff only touches the manifest and lock file, Intakt writes the Evidence itself: the version changes, the upstream release notes, the lock file's consistency, the dependency audit and CI on the head. Reviewers are told not to ask the bot for an Evidence section ([Reviews](07-reviews.md)); dependency-bot pull requests on this repository were sent back for exactly that.
- **A red check becomes one task.** When CI fails on the bot's head, Intakt files one task with the failing excerpt and the packages that moved. It is `urgent`, so it is picked before any milestone, and it carries the earliest open milestone for counting ([Choosing work](03-choosing-work.md#dependency-bot-pull-requests)). The bot's pull request is checked again after that task merges. When the bot closes or supersedes the pull request, Intakt closes the task with a comment naming the replacement. Seen on 2026-11-05: such tasks without a milestone sat behind 98 milestoned tasks, and one for a superseded pull request stayed ready.
- **Merged in place**, through the forge's merge API ([above](#pull-requests-intakt-did-not-open)).
- **Cooldown and grouping are recommended at setup.** Setup recommends a release-age cooldown for version updates (Dependabot `cooldown`, Renovate `minimumReleaseAge`): about 3 days for patch and minor releases and longer for major ones, with security updates exempt and handled at once. Related packages are grouped, a framework's packages together.

## Watching main

Main's integrity rests on how a commit arrived, never on whose key signed it (owner decision 2026-11-04). The earlier rule, that every commit on main must be a merge Intakt recorded or be signed by a key the owner registered, halts any project with outside contributors, a dependency bot or people who merge in the forge's interface. On this repository the first two dependency-bot pull requests could not merge: the bot's commits carry the forge's signature, which counted as unknown, and lock files took only maintainer-signed commits. Before every step and merge, the watchdog reads main's new commits and how the forge reports each one arrived:
- **Accepted:** a commit Intakt merged and recorded; a commit the forge reports as part of a pull request merged into main by an account with write access (an info event); a commit the forge reports as pushed to main by a person with write access (an info event, shown on the dashboard as "pushed without the gate", and main's CI result on it is watched as for any merge).
- **Halts:** a rewrite of main's history; a commit the forge cannot attribute to a merged pull request or to a write-access pusher; a commit whose merger or pusher lacks write access; a direct push to main by a bot or App account, since bots land changes through pull requests; and a commit Intakt's record lacks that Intakt's own forge identity (its App or the maintainer agent's) pushed or merged. The last is always a halt, never a notice: Intakt never lands a commit without recording it, so such a commit means its token was used outside Intakt. A merge whose answer was lost (a timeout, a restart) is not such a commit (next point). Only a commit no merge attempt explains halts. Each halt names the commit and the reason on an owner card, and only the owner clears it, after checking the commit.
- **A merge attempt stays open until its outcome is definitive.** Intakt records each merge attempt (the pull request, the head, and which of Intakt's identities, its App or the maintainer agent's, makes the call) before it calls the forge. An attempt covers every merge call made under it, retries included. Before every watchdog run, recovery reads each open attempt's pull request back:
  - *Recorded as Intakt's merge* only when the forge reports all three: the pull request is merged with exactly that head, into main, by the same Intakt identity the attempt recorded. The attempt then closes with the resulting commit. A merge by Intakt's other identity that no attempt of its own explains is still a halt (the own-identity case above).
  - *Closed without a merge* only on an answer that cannot change: the forge refused a call with a definitive answer (not a timeout or a server error) and no earlier call under the same attempt is still unresolved (timed out or unanswered; otherwise the attempt stays open as below), the pull request is closed unmerged, its head is no longer the attempt's head (the merge call names the head, so it can no longer succeed), or the pull request was merged by another account or into another branch. In the last case the commit is not Intakt's merge and the watchdog judges it by the rules above: a merger with write access is an info event.
  - *Kept open* while the forge reports the pull request open on that head, for as long as that lasts: a merge that timed out can still finish after the read, so an open pull request is no outcome. A later pass that merges the same head again does so under the same attempt.
  - *Read once more before a halt.* A merge can also finish between recovery's read and the watchdog's read of main. So before the watchdog halts a commit by Intakt's own identity, it reads back the open attempt for that commit's pull request, if there is one, and applies the same three conditions.
  - *Held while the forge reports late.* When main has a commit by Intakt's own identity and an open attempt exists for a pull request the forge still reports open on that head, the watchdog holds that commit as pending: not accepted, not halted, and Intakt merges nothing meanwhile. It reads the commit again on the next pass. If the forge has not attributed it to the attempt within 10 minutes, it halts as the own-identity case. The hold is bounded so a stolen token cannot hide behind it.
- **Signatures are recorded, never required.** Each commit's signature is recorded as the forge reports it. Requiring signed commits is an opt-in project setting, off by default to keep the [simplest first install](../../guide/setting-up-intakt.md); when it is on, the forge's own verification counts, and Intakt's merges are signed by Intakt.
- **The forge's protection is recommended, not assumed.** Setup recommends the forge's branch protection where the plan offers it (required checks from Intakt's identity, no force push, no deletion), and the dashboard shows when the watchdog is main's only protection.

## Branch cleanup

Branch cleanup is Intakt's job, so a busy loop does not leave hundreds of branches behind. It is limited on purpose:
- **Only Intakt's own branches by default.** Cleanup touches only branches Intakt created (its branch prefix). It never touches the default branch, protected branches or release branches. Cleaning up other people's branches is opt-in per project.
- **Merged pull request:** its branch is deleted once the forge reports the pull request merged, read back right after the move of main, and setup turns on the forge's own auto-delete where it exists. The forge marks the pull request merged a moment after main moves, and deleting the branch before that can close a merged pull request as unmerged. If the forge has not reported the merge within a short bound, the branch is kept and the pull request gets one comment naming the head that landed on main. Cleanup deletes the branch once the forge reports it merged.
- **Closed, unmerged pull request:** the branch is kept for 30 days, then deleted. A `keep` label on the pull request exempts it.
- **Branch with no pull request:** after 30 days without commits it is listed as stale; after 60 days it is deleted unless claimed. A branch is claimed when a person (not Intakt's identity) has committed to it, or when it is named in the `keep-branches` list of the project file. The `keep` label does not apply here, since there is no pull request to carry it.
- **Warning first:** a weekly job lists what it will delete a week before it does (a dashboard chore and one notice), then deletes.
- **Nothing is lost:** the orchestrator keeps every deleted branch's head in its own mirror as an archive ref, so a deleted branch can be restored. Archive refs are never pushed to the forge.
