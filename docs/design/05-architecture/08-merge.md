# Merge

Only the orchestrator merges. Right before merging it:
1. re-reads the task and the pull request, and stops if either is blocked, closed or changed since the verdicts; it re-reads the pull request's base right before the call and merges only when it is main, and where the forge's merge call can pin the base, Intakt pins it (a head merged into another branch is reported on the task, and the issue stays open);
2. requires green CI on exactly the head it is about to merge, and waits when CI has not registered that head yet (a head it pushed a moment ago);
3. records the merge attempt (the pull request, that head, main's commit it lands on, and which of Intakt's identities makes the call: its App or the Maintainer's) before the call, then lands only that head: a forge merge call names the head and fails if the pull request's head moved; the update of main's ref that [T62](../../plan.md#t62-merge-signed-fast-forward-of-the-exact-head) plans names main's expected commit and the recorded head, so it fails if main moved at all, even forward to an ancestor of the head (a fast-forward check alone would let it land), and a push to the pull-request branch after step 1's read is never landed: only the recorded, approved head lands (the approval names the head), and the newer commits stay on the open pull request and need verdicts of their own as a new head. A pull request Intakt did not open always lands by the forge merge call, never by the ref update ([Merging others' pull requests](#merging-others-pull-requests)). A landing whose answer is lost, or that the forge reports late, is still Intakt's ([Watching main](#watching-main));
4. reads the result back (the merge commit and its tree) and only then closes the issues and records the merge.

Landing order:
- **An approved head goes first, in every lane.** What an approved head still needs before it can merge (a polish build, a merge of main, the CI wait, a short re-review, the landing) goes before everything else in the lane that does it, `urgent` work included; among approved heads, the oldest approval goes first. The build lane's side is in [Choosing work](03-choosing-work.md), step 5. On each tick the review worker takes the approved heads in the order of their approval, oldest first, and gives each the step it needs: the landing, when it needs no model call (every required verdict exists for its exact patch, CI is green on it, the owner's approval is there where the change needs one, and it merges cleanly with main), its due CI read, or its short re-review. So a newer approved head that is ready to land waits behind an older one whose short re-review can start, and a due CI read of an older approved head goes before one of a newer head, whichever finished CI first. Only then does a new review start. Priority orders reviews and builds, never finished work. Reason: a low-priority head with green CI, two approving reviews and the owner's approval waited behind several normal-priority reviews of 20 to 40 minutes each. The merge costs no tokens and takes a few minutes, while every hour of waiting lets main move on, which adds merges of main, CI runs, conflict risk and a new head that needs the owner's approval again.
- **One path for landing.** The same no-model landing step serves this rule and the [budget back-off](06-budget-and-model-planner.md) (where only merges run). A head that turns out to need more than a merge goes back to its place in the review queue and is not tried again for a short while. Every review worker hands its approved heads to this one step, which lands a single head at a time across the whole install under one lock, whichever worker or project a head comes from ([Reviews](07-reviews.md), review capacity follows build capacity). Reason: two landing paths would drift apart, and a head that cannot land must not block the queue or be retried on every tick.

- **A head that fails backs off alone.** An unexpected failure while reviewing, landing or merging one head sets that head's next try time and records the cause in the ledger and on its card, and the tick goes on to the next head; after a few failures in a row the head goes to the Maintainer ([Budget](06-budget-and-model-planner.md)). Reason: a head that fails on every try must not stop the review and merge of every other head.

Protected paths (gates, CI config, agent instructions, dependency policy, the boot harness) need an approval, and a protected change gets one of exactly two outcomes, decided at once when its head has green CI and its Code reviewers' verdicts ([Approving protected changes](#approving-protected-changes)), while an owner decision plain code can already read from a pushed head is asked on that head (below). The one exception is an outage of the Security engineer's sessions: a head whose security review or penetration test could not run gets no outcome yet, neither an approval nor an owner request, and waits until a session runs ([Independent security review](#independent-security-review)):
- **Intakt approves on the spot** when no hard floor is hit, every mechanical check passes, the Security engineer's security review agrees and its penetration test finds no way around the change.
- **Otherwise the owner reviews.** The request names the floor or the check that sent it. For a floor hit the request and the owner's notice (a phone push included) each name, in plain words, the floor and each path that hit it (for example "secrets floor: `src/Core/HandBack/UseCase/CheckHandBack/BundleSecretScan.php`, the scan of a build's commits for secrets, changed"), and reads as a decision to make, never as a security incident; a bare label like "secret handling" is not enough. It never resolves itself: no timer, no veto window, no "approve unless stopped", no one-tap shortcut.
- **Protected paths are read from the whole change.** Whether a head touches a protected path is decided from the full diff between the merge base with the current main and the exact head being merged, combined with the per-commit lists (the paths each commit between the merge base and the head touches, each commit compared against each of its parents; the commits between the merge base and the head are the commits reachable from the head and not from the merge base, so a merge's second-parent commits count unless main already contains them; a path a commit holds exactly as the current main holds it adds nothing to main and is left out of that commit's list, so a merge of main does not list what main added, while a revert to an old main still differs and is listed; a shallow history counts as unreadable), never from a merge commit's diff against one parent, because a crafted merge (first parent the branch, second parent an old main commit) could otherwise revert or delete a protected file without it being listed. Submodule entries and `.gitmodules` count as protected.
What goes to the owner follows these rules:
- **Same flow as any change.** A build that touches protected paths is pushed and opened as a normal pull request, gets CI, its Code reviewers and reworks on its own branch; it is never exported as a patch for someone to re-apply (patches go stale and every rejection meant a rebuild from scratch). When CI and its Code reviewers pass, it parks with "waiting for the owner" and notifies once, unless the owner's answer to an early question (below) already covers it.
- **A risky change to the CI definition is never pushed before the owner approved it.** A forge runs the workflow taken from the pushed commit, so a build that edits it would run its own workflow on the project's runners before anyone looked. A change is pushed without that approval only when a scan of the workflows (the head's, main's, and the two merged) shows they can reach no more than a forge-hosted, throwaway runner with a read-only token and no secrets: hosted runner labels only, read-only permissions, no secrets beyond the read-only token, no triggers that run with the base repository's rights; anything the scan cannot read counts as risky. A `runs-on` taken from a variable or an expression is unreadable, since the variable can change without a commit, so it counts as risky even while the variable is unset: every CI change of that project waits for the owner, and its Developers get no CI log excerpts ([Threat model](14-threat-model.md#ci-log-excerpts)). The scan reads the files the workflows run from the repository as part of the CI definition: a change to one of them is a CI change, since it runs on the runner as the workflow does. Self-hosted runners always ask, and must be ephemeral ([Threat model](14-threat-model.md#self-hosted-ci-runners)). Merging a CI change follows the approval rules below: a workflow that reads a repository secret, raised permissions, a new trigger or a runner change always goes to the owner (a hard floor), and any other CI edit, like a file a workflow runs, is approved on the spot only when it clears every floor and check. A risky change stays local; the owner approves the exact diff and commit first, and only then is it pushed. That request shows the whole change, not only the CI files (an approved one-line workflow edit can run a script nobody was shown); an image in it (a plain, non-executable file whose name and first bytes agree on PNG, JPEG or GIF) is named by its sizes and full blob ids instead of its bytes, which a comment cannot hold and which the approved commit pins, while any other file with a NUL byte keeps its bytes, so the request is refused, since a script can run with one ([Threat model](14-threat-model.md#residual-risk)). A change too large to show in full is sent back to be split, never approved from a file list. Approving the push does not approve the merge: the owner is asked again, with the full list of protected changes, when the head is ready to merge. A rework of a held change that is still held needs a new push approval of its own exact commit, even when its floor paths are unchanged (the carry of a floor approval, below, applies only to pushed heads).
- **The owner is asked only for a reviewed change.** Before the push request reaches the owner, the Code reviewers review the held diff with a security brief: triggers that run with the base repository's rights, permissions, runners, secrets, untrusted text (titles, bodies, branch names) put into a script through an expression instead of an environment variable, unpinned actions, and what a later push of the branch could run. A rejection goes back to the Developer without asking the owner; an approval travels with the request, so the owner confirms a reviewed change instead of reading a workflow cold. The envelope that needs no approval stays narrow on purpose: a token that may write issues could rewrite a task's body, which is the build's instructions, so any write scope keeps needing the owner.
- **The approval names the head.** It is a normal forge review by the owner's account (possible because the pull request's author is Intakt's identity, not the owner), or a comment `approve <sha>` by it, which no job can write (jobs have no forge credentials) and Intakt's own identity never writes. A new push needs a new approval, except for the pushes that keep it, listed in full under "An early approval counts once its head passes" (below): the clean merge of main, the generated-files resolution, the answer to an early question, and the owner's floor approval of a head parked "waiting for the owner", which a conflict fix of any form keeps on the same terms. The push approval of a held CI change never carries: it names one commit. The approval authorizes the protected paths of exactly that head, never the signing key of the commits in it, so a contributor's or a bot's commits in an approved head are fine.
- **An owner decision is asked when it first appears.** When plain code can read from a pushed head that the change needs the owner (a new package outside the trusted vendors or another change the dependency policy sends to the owner, a protected change that hits a hard floor or that no mechanical check covers), the owner is asked on that first head, in parallel with any CI fix or review round, not after them. The question names the decision, not the head: the dependency change or the protected change (the diff of every protected path). A dependency change is everything the [dependency policy](#mechanical-checks) reads that can send it to the owner, not only the package names: each new or changed package with its version and source, the locked identity of each such package's artifact (for Composer, the lock file's `dist` and `source` entries: type, URL, reference and checksum), and every change to install scripts, plugins, package sources and the package manager's own settings (for Composer: `scripts`, `allow-plugins`, `repositories`, `config`, binaries and autoload files). The answer covers that decision and carries to every later head that keeps it unchanged, so a rework, a CI fix or a clean merge of main asks nothing new; a head that changes any part of the dependency change (a new registry or script with the same packages, or a package locked to another artifact at the same version, included) or the protected diff is asked again about what changed. For a floor hit this is exact: the owner's floor approval of a head held for the owner (the early question or the merge approval of a head parked "waiting for the owner") carries to a rework only when the rework hits the same floors on the same paths, no more and no fewer, and every one of those paths keeps the file entry of the approved head (the same bytes and the same mode: the executable bit, a symlink, a submodule entry; a path deleted or renamed is changed), whatever else the rework changes (a test stub, a line of docs); a rework that hits another floor or another path, or changes such an entry in any way, needs a new approval. This carry never covers the push approval of a held CI change (above): that approval names one commit, because the push runs the head's workflow and whatever the workflow runs, so a revised held change is shown again, whole diff and exact commit, before it is pushed; the request says which floor paths are unchanged since the owner's last answer, so the owner reads only what changed. Once pushed, its floor approval carries as above. Merging still needs green CI and every verdict on the exact head; the owner's answer never stands in for them. It stays a real answer from the owner's own account (above): no default, no timeout, no veto window. A need the checks can only see later (a reviewer's loosening class, a security review that does not agree) is asked when that verdict arrives, about the head it judged; a reviewer's class never carries to a later head ([A code reviewer's class](#hard-floors)). A dependency bot's pull request is the exception to both: its one owner approval is asked neither on the first head nor when a verdict arrives, but at the end ([Dependency bots](#dependency-bots)). Reason: a pull request that added packages needing the owner kept failing CI for an unrelated reason, and since the owner was asked only after green CI and every approval, the owner was never asked while it held a milestone's critical path for hours.
- **An early approval counts once its head passes.** An approval given before CI and the reviews finish stays: it counts once that same head passes, and a push after it voids it, except the clean merge of main, the generated-files resolution described below, an answer to an early question and the owner's floor approval of a parked head, which carry as above. An approval to push a held CI change never becomes an approval to merge, before or after the push: the merge is asked about on its own, with the full list of protected changes (above). Intakt never removes or re-asks it because of a review or CI round.
- **The owner can send a head back.** A comment `changes <sha>` by the owner's account, or a review requesting changes on that head, when it is the owner's newest decision there, sends the head back with the owner's note fenced: to the Developer for a task's head, to the Maintainer for its own pull request. The head is no longer asked about and stops counting toward the owner-wait cap. Only a later approval from the owner's own account overrides the owner's send-back, never anything the Maintainer or Intakt's identity posts, so a helper cannot overrule the owner.
- **The owner is asked only about a head that merges.** Before a protected head is offered for approval it must merge cleanly with main; a real conflict goes back to the Developer, not to the owner or the Maintainer (a conflict only in registry files is first merged by Intakt, below). A dependency bot's pull request is the exception to the conflict rules of this bullet: Intakt never pushes to its branch, so a conflict of any kind, in generated or lock files included, is neither sent to the Developer nor resolved by Intakt; the head waits for the bot's next head, and the owner's answer carries to that head only when it keeps the same package set and the same diff ([Dependency bots](#dependency-bots)). An early question (above) is the exception: it asks about the decision, not the head, so it goes out on the first pushed head even when that head conflicts with main, in parallel with the conflict's fix, and its answer carries to the resolved head when that head keeps the decision unchanged; the merge approval itself still waits for a head that merges. While a head waits, main moving costs nothing (no rebuild, review or new notice); a conflict that appears only in generated files is resolved by Intakt itself after the approval (merge main, regenerate the generated files, and let the approval carry when the protected change is byte-identical and the extra commits touch only generated files), and a real conflict withdraws the request once, but parks the approval instead of dropping it. When the resolved head is a merge of main onto the parked head, made by Intakt's Developer or Maintainer through the hand-back, with the protected change byte-identical, the parked approval carries to it once its review and CI pass. A resolved head of any other form (a rebase, or a merge of main with further edits), made through the hand-back, keeps the owner's floor approval, and only that, under the floor carry of the early-question rule (above): it must hit the same floors on the same paths, no more and no fewer, with each of those paths keeping the file entry of the approved head (the same bytes and the same mode), and the approval counts once review and CI pass on the resolved head. Everything else is dropped with one comment and asked again: on such a head, an approval given for another reason (a protected change no mechanical check covers, a reviewer's loosening class), and any resolved head that changes, adds or removes a floor path. The push approval of a held CI change never carries to a resolved head, whatever its form (above). Intakt's own recorded merges stay recognized across hand-backs, so an owner is never asked twice for the same change because of Intakt's bookkeeping.
- **An approval is informed and unforgeable.** The request lists every protected change of that head and says plainly when the change modifies the checks that judged it (green CI then means the head's own gates passed). Only the owner's own account can give it, through a channel no agent of Intakt's can write: Intakt's identity never posts it, and helper agents acting for the owner (the Maintainer, which writes the summaries of approval requests and sorts hand-overs) run under a forge identity that is never the owner's account, so a review or `approve <sha>` they post is not the owner's, and a post guard blocks them from it as a second barrier, not by an instruction. A clean merge of main into an approved head that leaves its protected changes identical keeps the approval, so a busy main does not mean asking again every hour.
- **Only a few heads wait for the owner at once** (a cap per install, three by default), so the owner's queue stays short enough to act on. Only real waits count: a head with green CI and every review passed that waits for the merge approval, and a held CI change that waits for its push approval. A head still in review, sent back or on hold does not count, nor does a head held by an outage of the Security engineer's sessions ([Independent security review](#independent-security-review)), since nobody can act on it yet, and a wait Intakt cannot classify counts (fail closed). An early question (above) is asked whatever the cap and does not count toward it, because holding it back is the very wait it exists to remove. A head that is ready while the cap is full is queued for the owner with no label, comment or notice and holds no slot; the queue is ordered by priority, then age, so a newer head never takes a freed place ahead of an older one of the same priority. A freed place is reserved under the same lock that read the count, before the owner is asked, so two workers cannot both take it, and a failed ask gives it back. At the cap, builds of tasks known to need the owner wait, with one notice; a task's own rework is never blocked.
- **Main is merged in last.** A head gets CI and its reviews as it was pushed. Intakt merges main into the branch only when the head is ready to merge (green CI, every verdict, any owner approval it needs) or when the forge reports a conflict with main that is only in registry files (below; any other conflict takes the route of a head that needs main: back to the Developer while the task has build cycles left, otherwise to the Maintainer). A clean merge keeps the verdicts and the owner's approval (above), but not a reviewer's class of the protected part, which the merged head gets anew ([A code reviewer's class](#hard-floors)), and CI runs once more on the merged head before the merge. Merging main into every open branch whenever main moved restarted CI on all of them: one pull request ran CI 19 times in a day, and a single self-hosted runner fell an hour behind.
- **A conflict only in registry files is merged by Intakt.** Registry files are files that many changes each add an entry to (for example the lock file, the bundles list and the guide's index). They are named in a list in the owner's config in Intakt, never in the repository, so no build can widen the list. When merging main into a pushed head conflicts only in files on that list, Intakt merges main itself, with no build and no model call: the language plugin regenerates a lock file from the merged manifest, keeping every other locked version, and a list file keeps the entries both sides added. Being on the list only allows the attempt: Intakt resolves a conflict in a list file only when each side's change is a pure addition of whole entries that the other side does not touch, and a lock file only when the merged manifest names each package once. When both sides edit, delete or reorder the same entry, add the same entry with different content, or the resolver cannot otherwise keep both sides' changes without choosing between them, the conflict is not resolved this way and takes the fallback below (the route of a head that needs main). The merged head is checked before it goes anywhere: it passes the hand-back checks and the pre-push check like a build's hand-back, and only a head that passes is pushed, as a new head that gets CI and its reviews like any other. Intakt pushes such a head only to a branch it may write to: the branch of its own pull request, or of a taken-over pull request it can push to ([Hands-off and take-over](#hands-off-and-take-over)), never the branch of a pull request it only reviews. Right before the push it re-reads `hands-off`, as the first step of the merge list does, and pushes only when the branch is still on the head it merged; a `hands-off` label or a branch that moved pushes nothing, and the merged head is dropped. When the merge leaves a conflict in a file not on the list, a conflict on the list cannot be resolved as above, the regeneration fails or the check fails, nothing is pushed and the head takes the route of a head that needs main ([Reviews](07-reviews.md)): a merge-main rework for the Developer if the task has build cycles left, otherwise a hand-over to the Maintainer, as before. A dependency bot's pull request is never merged this way: Intakt never pushes to its branch, so its conflict waits for the bot's next head ([Dependency bots](#dependency-bots)). For a protected head, approvals carry only as the rule on heads that merge (above) says for a resolved head of its form; this rule adds no carry. Reason: measured on this repository, 49 merges brought 14 cycles for a conflict with main, most of them in the lock file, the bundles list and the guide's index, and each such cycle spent a build on a conflict plain code can resolve.

## A head that moves text

A change too large for review that only moves text under `docs/` is reviewed without the moved text, as [Reviews](07-reviews.md) describes (the move check and what is left of the size measure). A change that can be split takes the split route of [#944](https://github.com/shinyredapples/intakt/issues/944) instead; an oversized pull request with no task is split too when the owner's or the Maintainer's identity opened it or a person with write access set `take-over`, as [the Maintainer](09-maintainer-agent.md) describes (anyone else's gets one comment saying it is past the size limit and stays with its author), and its original is closed only once its parts' pull requests add up to its head, never merged itself. The merge side of the route:
- **An approved move lands before new work on the same file.** Once every verdict and any owner approval it needs are there, a head in this route has merge priority over new work on a file it moves text out of: the landing step lands it ahead of any other head that edits that file, whatever their priority, and a build of a new task that would edit that file starts only after it landed, so the build works on the new place. Reason: a long-lived move conflicts with everything that edits the old file; measured on 2026-11-07, two merges touched the old file within one hour of a move, and each needed the same edit carried into a topic page by hand.
- **The merge of main carries edits into the moved text.** When main changed a line the head moved, the build that merges main applies that edit to the line at its new place as a step of the build, never by hand, in a commit of its own that holds only the carried edits. The move check then runs again on the merged head and never counts a line that commit added as moved: after the merge the edited line is removed from the old page and added byte-identical at the new one, so without that exclusion the check would match the pair and hide the edit. A carried deletion leaves no line in the change: when main deleted a line the head moved, the build removes it from the new page as well, and since main already removed it from the old page, the line is in neither main nor the head. A missed or wrong carry does show: the line main changed or deleted stays at the new page in its old form, with no partner among the lines removed from main, so it is an unmatched line in the remainder the reviewers read.
- **The request names every step to the merge.** The hand-over and the owner's approval request of such a head list each step still needed before it merges (the approval itself, any label the merge needs, a pending merge of main and its carried edits), so the owner never has to find one by reading code. Reason: an owner approved such a move, and it still could not merge without a label nothing had mentioned; that was found by reading the code.

## Approving protected changes

On this repository 32 of 120 merged pull requests waited for the owner; about 6 of those only edited comments in the boot harness, most dependency approvals added official Symfony packages, and waiting for approvals was about 20% of all waiting in the loop. Of 57 pull requests that asked the owner for approval, 52 merged, 5 were closed and none was rejected: an approval that is always given filters nothing while every protected change waits for a person. So Intakt approves on the spot what its checks and the Security engineer ([Threat model](14-threat-model.md#the-security-engineers-sessions)) clear, and asks the owner for what touches the approval system itself or secret handling and workflow permissions, at once and with the reason. This replaces approval by class, which needed at least two reviewers from different vendors classifying a change as tightening or neutral. The approval is plain code that runs the steps below in order and approves only when all pass; the first step that fails ends it with a request to the owner that names that step. An outage of one of its model sessions is not a failed step: it holds the head without a decision ([Independent security review](#independent-security-review)). Its two model sessions, the security review and the penetration test, are run by the Security engineer.

### Hard floors

Exactly two hard floors remain. They are deterministic rules over the whole change (read as protected paths are, above). No model output lowers them, and a hit always goes to the owner:
- **The approval system:** the protected-path list, the floors, the checks that apply them, the Security engineer's prompts and the canary corpus (below), so Intakt can never widen its own approvals.
- **Secrets and permissions:** any change to how secrets or credentials are stored, read, injected, redacted or scanned, including the secret scan's rules and its allowlist; a workflow that reads a repository secret; raised workflow permissions, new triggers or a runner change.

How the secrets floor tells a change to secret handling from any other change:
- **A named list, not a word in a name.** The floor is a list of named paths and code areas that do this work (the secret scan's rules and allowlist, the code that stores, injects or redacts credentials), kept in the project's configuration in Intakt beside the protected-path list and protected like the floor it serves: a change to the list is a hit of the approval-system floor. A path joins the list only by being named there, never because its name contains a word like "secret", "token" or "credential".
- **A test counts only when the list names it.** The list decides alone, so the result is one: a test the list does not name never hits the floor, whatever its edit, and a test the list names hits it with any edit, its input or its assertion of a version included, like every other path on the list (plain code does not judge what an edit means). An edit to a test's input or to its assertion of a version is not a change to how secrets are handled, so the list names a test only when the test itself decides how secrets are handled (for example a file the secret scan reads as its rules), never a test only because it exercises that code.
- **Deterministic.** Whether a change hits the floor is decided by plain code from the list and the change; no model output raises or lowers it.

Reason: on 2026-11-07 a dependency change that edited one regular expression in a test whose file name contains "Secrets" was sent to the owner four times in one night, by phone push, once for each rework, including one that changed only a test stub and a line of docs. No secret, rule or scanner behavior changed in any of them.

Other CI edits, gate tests, agent instructions and the boot harness are not floors: they go through the mechanical checks, the security review and the penetration test. They are approved on the spot only where a mechanical check covers the change (gate tests and the harness by their checks); a workflow file or an agent instructions file that no check covers still goes to the owner. One rule besides the floors still sends a change to the owner: a code reviewer that classifies the protected part as loosening, or gives no valid class ([Reviews](07-reviews.md)). A classification never approves on its own.

**A code reviewer's class** (formerly a panel reviewer's class) counts only for the head it judged:
- **A class belongs to the head it was given on.** Only the classes given on the current head decide; a loosening class on an older head does not send a later head to the owner.
- **A missing class is never filled from an older head.** A current head without a valid class from a code reviewer goes to the owner, as above, even when an older head had one, and in either direction: an older tightening or neutral class does not clear it, and an older loosening class does not decide it.
- **A loosening notice names its head.** A request or notice that says a reviewer classed the change as loosening names that head and quotes that reviewer's reason (`protected_reason`), fenced as untrusted text ([Threat model](14-threat-model.md#untrusted-text)).

Reason: a host job that looked for a loosening class in every comment on a pull request told the owner that a reviewer had classed a change as loosening, although both reviewers classed the current head neutral or tightening and approved; the loosening classes were from seven older heads, each for a real finding that was then fixed.

### Mechanical checks

Every protected file the change touches must be covered by a mechanical check that passes; a file no check covers goes to the owner. The checks are plain code. What differs per language comes from a `language` plugin ([Plugins](02-plugins.md)), PHP first.
- **Comment-only.** The old and the new file parse to the same syntax tree once comments and whitespace are dropped, through tree-sitter or the language's own tokenizer (for PHP, `PhpToken`). A comment a tool reads counts as code: docblocks (static analysis reads their types), suppression and ignore markers, and inline allow directives. Where a language has no parser, the check does not apply.
- **Dependency policy.** One adapter per ecosystem reads the old and new manifest and lock file (Composer first; npm, PyPI, Go and Cargo by plugin). The old files are read at the merge base of the head with main, never at main's tip, as for the protected paths below, and so for every owner decision about a change (packages, protected paths, workflow changes): a branch behind main that only adds one package is asked about that package alone, not about packages main added since. The rules are written once over language-neutral sources: OSV.dev for advisories and deps.dev for release dates and use. A change passes only when every new package, transitive ones included, comes from an allowed vendor in the owner's config, has no open advisory, and has a release older than the minimum age in the owner's config, and when no install script, plugin or package source changes (for Composer: `scripts`, `allow-plugins`, `repositories`, `config`, binaries and autoload files). The orchestrator queries the sources, never a job; an unreachable source or an unknown answer goes to the owner.
- **Gate code is no weaker.** Main's gate tests run unchanged against the head's gate code, and so does the violation corpus: every violation the gates have ever caught, kept as a fixture that must still be caught. Both run through the project's check command, so the proof is language-neutral, in their own check container and as their own user, with the result leaving through a channel the code under test cannot rewrite. A check that runs the candidate's code cannot detect code written to cheat it, which is why the security review and the penetration test follow.
- **Harness from main.** The boot gate runs main's trusted harness (`bin/instance`, `bin/probe`) against the head, so a harness change cannot certify itself. Booting proves only that the head still boots, so main's isolation probes also run through the head's harness: a probe that reaches the network, writes outside its folder, reads a credential or runs as another user must still be stopped. A harness change passes only when both hold.

### Independent security review

The Security engineer (#864), the role that also reviews the product's security per layer ([Reviews](07-reviews.md#the-security-engineer)), runs two separate model sessions on the protected part, the former gatekeeper sessions: a **security review** and a **penetration test**, each with its own role and prompt ([Threat model](14-threat-model.md#the-security-engineers-sessions)). They only supply verdicts: the decision stays the plain code above, and no verdict lowers the owner's two floors. They get the diff, main's version of every protected file and the floor and check results, never the Developer's pull request text or reasoning, and their verdicts are typed objects checked like any other. The security review must agree that the change keeps or tightens the rules. A second AI vendor adds confidence when one is available and is never required. When a session gives no verdict, what follows depends on why:
- **A role that is not configured sends the change to the owner.** With no Security engineer configured for the project, the request goes to the owner at once, naming the missing role. A stand-in or a substitute never takes either session's place.
- **An outage holds the change.** A session that could not run (the vendor's usage-limit or login error, a crash, the session's timeout, a stream cut before its final result) gives no verdict and no decision: the head stays waiting for the approval, nothing is recorded as decided, and nothing is sent to the owner for it. An outage is read from the run itself, as for the [budget](06-budget-and-model-planner.md) ("only structured signals count"), never from the model's text. Plain code tries again after a wait; while the role is known to be out (no account of it can run), it stops trying at once for every waiting head and tries one session after the wait, and only when that one runs do the other heads go on.
- **A session that ran without a valid verdict sends the change to the owner.** It is not an outage: the run finished and its answer is not a verdict that passes the checks, so that head goes to the owner, naming the session. A valid verdict in the output wins over any limit wording in its text, because the text can quote the diff; text that only claims a limit is no verdict, so it goes to the owner too, never holds the head.
- **The owner hears once per outage.** One notice per outage, not per head, and only when it outlasts a set time (for example 2 hours). It names the role and says what the owner can do: add an account for it or free one. It resolves by itself when a session of the role runs again, and the held heads go on through the steps above without an owner request for the outage.
- **No verdict is never an approval.** Waiting out an outage decides nothing: a held head is approved only by the steps above once both sessions have run, or by the owner. The request rule above stands (no timer, no veto window), and no stand-in or substitute replaces either session during an outage.
- **The hold applies before and after the switch.** Before [earned autonomy](#earned-autonomy) switches a project on, every protected head still ends with the owner. A head that reaches a Security engineer session and meets an outage is held as above, with no owner request and no recorded decision, and the request follows with the computed decision when the sessions run. A head that never reaches a session (the role is not configured, or an earlier check fails) goes to the owner at once. After the switch, a held head that then passes every step is approved without the owner, provided the canaries (which run through the same pipeline and resume after an outage with the held heads) each still reach the owner; a missed canary turns automatic approval off, and before the switch it keeps the switch off. Sending a held head to the owner before the switch would bring back the incident below, which happened before any project was switched on.

Measured on 2026-11-06 and 11-07: the account of the security sessions reached its usage limit for about 5 hours, every session answered with the limit, and a job that read that as "no valid verdict" sent the owner one notice per head (9 in that time) and recorded each head as decided, so none was tried again. The owner's queue filled with heads nobody had judged and builds waited behind them; of the seven heads re-run once the account was back, six needed no owner. That case is an outage under the rules above: the vendor signaled the limit in its structured error (for Codex, `src/Core/Ai/Infrastructure/CodexAccountFailure.php` already recognizes it), so the heads are held. Limit wording that appears only in the text of a finished answer is no such signal, and that head goes to the owner.

### Penetration test

The penetration test tries to write a fixture that main's gate rejects and the head's gate accepts. Plain code runs each fixture against both, in a check container without network. A fixture that gets through is proof of weakening: the change goes to the owner with the fixture, and the fixture joins the violation corpus once the owner confirms it. Finding nothing is not proof of safety; it is one more check that must pass.

### Earned autonomy

Until the switch below, every protected head ends with the owner with its computed decision; a Security engineer outage still holds it first, as [above](#independent-security-review). There is no per-category dry-run mode and no per-category count. A project's automatic approval can be switched on once both hold:
- every **canary change** reaches the owner: canaries are owner-known changes that run through the pipeline regularly and must be sent to the owner, at least three per kind of protected change (comment-only, dependency, gate code, harness, and the floors: a workflow that reads a repository secret, an edited approval rule, an edited secret scan); and
- a replay of the repository's past owner approvals agrees with the computed decision on at least 20 heads.

The owner's one switch in the owner's config then turns it on, since turning it on widens the approval rules. A missed canary or an owner overrule turns it off for the project until both hold again. There is no daily cap on automatic approvals: a cap only sent routine approvals back to the owner.

### Containment

- **Automatic revert.** When main's canaries or violation fixtures fail, Intakt looks at the automatic approvals merged since they last passed. When there is exactly one and no later merge touched any file it changed, Intakt reverts that merge at once: the revert restores those files to main's version before it, byte for byte, so it needs no approval. Otherwise (several automatic approvals, or a later merge on the same files) Intakt reverts nothing on its own and asks the owner, naming every candidate merge, and no automatic approval is given in that project until the owner answers. In both cases automatic approval is off for the project until both conditions of earned autonomy hold again, and the owner is notified.
- **Visible afterwards.** Every automatic approval says so on the pull request in one line (the head, each check that passed), and is listed on the dashboard for a week with that line, so a wrong call is seen without anything waiting on a person; it is information, not a notice.

## Waiting for CI

- **A wait for CI holds nothing.** A head whose CI is pending holds no slot and no lock: its step ends, the head goes back to its queue with its place by age and a time to look again, and the lane takes a head whose CI has finished. A head pending for a set time (for example 30 minutes) is admitted by age anyway, so a slow pipeline is not starved by fast ones. A drain does not wait for parked heads.
- **Every waiting phase has a ceiling.** A step that waits for CI, for a reviewer slot or on a merge of main ends after a set time (for example 20 minutes), also when it still holds the lane (a head admitted by age after the set time above, or a step waiting on a merge of main). Jobs that call a model keep their progress stop instead. A wait at its ceiling is classified and repaired without a model, as the [principles](../02-principles.md) describe: a conflict with main takes the same path as in the missed-CI rule below (the registry-file merge when the conflict is only in registry files, otherwise the route of a head that needs main; on a dependency bot's pull request, a wait for the bot's next head), no CI run takes the missed-CI path below, a run queued for lack of a runner parks the head (it holds no lane) and shows runner capacity on the dashboard, and anything else ends the job as stalled. The task goes back to its queue with its place kept and the lane is free for the next one. The same task stalling three times in a row raises one notice naming the phase and what was read; every stall and its class goes in the ledger, so a recurring class can get its own repair. For the reason, see the principle "A wait has a ceiling" in the [principles](../02-principles.md).
- **A head waiting for CI is not a head waiting for review.** The cap on built heads waiting for review counts only heads waiting for a reviewer or in review. Heads waiting for CI, for a runner or for landing count against the limit on all heads in flight ([Choosing work](03-choosing-work.md), step 5), and a head stays in that count while it waits for landing; heads still waiting for CI also count against the CI capacity ([Budget and model planner](06-budget-and-model-planner.md#ci-design-for-later)): when more heads wait for CI than the runners can clear in a set time, new builds wait, and the dashboard shows "waiting for CI" apart from "waiting for review". A review cap filled with heads whose CI had not started kept the build slots closed while nothing was being reviewed.
- **Polling first, webhooks last and optional.** Intakt reads the forge by polling and works fully without webhooks, which need an endpoint the forge can reach (a public URL or a tunnel) and so add setup and attack surface. A webhook is a later, optional addition for installs that already have a public endpoint; it only makes a change visible sooner and never replaces the poll. The poll is cheap by six rules:
  - **Conditional requests.** Each read sends the last ETag or If-Modified-Since value; GitHub answers "not modified" without counting it against the rate limit.
  - **One listing per forge per tick.** A tick lists the open issues and open pull requests of all projects on one forge once (for example one search over their repositories) instead of reading each item or each project, and skips re-reading the body of any item whose update time (and, for a pull request, head) did not change. New eligible tasks, steering labels and owner answers in comments are found this way, since a label or a comment moves the issue's update time. The listing carries no CI results, and a finished check run changes neither the head nor the pull request's update time, so this skip never covers CI.
  - **CI is read per waiting head.** Each head waiting for CI has its check status read on its own, by commit, as a conditional request when its due time comes (the short interval after its last read, or sooner while a pending-aware re-check backs off, below), until CI has finished for that head. The poll then stops reading CI for that head; the merge step still reads CI on the exact head right before merging (above), so a rerun that changed the result after the poll stopped is seen there and never rides the earlier green.
  - **Adaptive intervals.** Long (for example 15 minutes) when the project is idle, short (for example 1 minute) otherwise, so a running build keeps the short interval even with no head waiting. A project is idle when it has no head waiting for CI or a review and no build or review job running, which plain code reads from the queue and the running jobs. An idle project runs only the long listing poll, and a waiting state's own deadline still wakes it.
  - **Pending-aware re-checks.** When a step of a lane ends with an outside event pending (CI of a head, an approval, a new head of a bot pull request, the default branch's CI), the Scheduler arms an early re-check of that lane, so the event is read again sooner than the lane's normal interval. The normal interval is the one the rule above gives the project: short while a head waits for CI or a build runs, long when the project is idle (for example while it waits only for an approval). The re-checks back off: 30 s after the step, then 60 s, 120 s and 240 s after each read that finds the event still pending, then the lane's normal interval again. A delay is used only while it is shorter than the lane's normal interval: the backoff ends at the first delay that is not, and the normal interval takes over from there. Each pending event has one due time, and it is the only schedule for reading that event. The step that leaves the event pending sets it to 30 s later. Every read that finds the event still pending, whether the early re-check or the lane's normal run made it, is not work: it advances the backoff one step and sets the due time to the time of that read plus the smaller of the next delay and the normal interval. The lane's normal run skips an event whose due time has not come, so it neither reads the event a second time nor advances its backoff before the armed re-check does; it reads an event whose due time has come, which also covers a timer that was lost. Once the backoff has ended, each read sets the due time one normal interval later, and those reads are the event's essential reads at the normal interval. With a 5-minute normal interval the reads fall 30 s, 90 s, 210 s and 450 s after the step (delays of 30 s, 60 s, 120 s and 240 s), then every 300 s; with a 1-minute short interval they fall at 30 s, then every 60 s; with a 15-minute long interval all four delays are used, as with 5 minutes. These times do not depend on where the project's tick falls. Any work on the lane (a step that acts on what it read, such as a review that starts because CI finished, or a hand-off into or out of the lane) resets the backoff of the lane's pending events, so they start again as after the step: each event's due time becomes the earlier of its stored due time and 30 s after the work, and the read after that is followed by the 60 s delay. A reset never moves a read later, so a due time that has already passed stays passed and is read when the run ends (below). Each pending event keeps its backoff step and its due time with its head's place in the queue, so a wait never lives only in a timer. Only one early re-check per lane is armed at a time: its timer is set for the earliest due time among the lane's pending events, and arming replaces that timer instead of adding a second. The timer covers every due time, also one a normal interval after the last read once the backoff has ended, so the timer, not the project's tick, is what wakes the lane at a due time between two ticks: due at 750 s with the project's ticks at 600 s and 900 s, the tick at 600 s skips the event, the timer reads it at 750 s, and the tick at 900 s skips it again (next due at 1050 s). The re-check runs under the same lock the lane's normal run takes, so a re-check and a normal run never run that lane in parallel. A re-check that finds the lock taken reads nothing, and the run holding the lock sets the lane's timer again from the stored due times when it ends, so a head that still waits keeps its wait while the lane works on another head. A due time that has already passed when that run ends is not dropped and not moved: the event is read at once, as the lane's next run under the lock, and its next due time counts from that read (due at 30 s with the lock held until 40 s: read at 40 s, next due at 100 s). This holds also when that run did work that resets the backoff: the reset comes first and keeps the passed due time, then the read follows, so the two rules give one schedule (due at 30 s, the lock holder finishes a hand-off for another head at 40 s: read at 40 s, next due at 100 s, not a new 30 s delay first). A read that comes sooner than one normal interval after the event's last read is a call that reading at the normal interval alone would not make, so it gives way first: below a configured share of the installation's hourly calls (an owner setting, at or above the reserve for essential calls below), by the latest recorded reading, no early re-check is armed, and the event's due time is one normal interval after its last read (after the step, when it has not been read yet); the lane's timer is still set for that due time, because that read is essential. The share is read again when a re-check comes due, and one that comes due below it reads nothing, leaves the backoff step as it is and moves the due time in the same way, so an allowance another lane spent in between is seen; the lane then waits for its normal interval. With the setting off, every due time is one normal interval after the last read. Pending-aware re-checks are an owner setting, on by default. Internal hand-offs need no re-check, because they are events already ([Choosing work](03-choosing-work.md)). Measured on this repository over three days, 629 reviews were postponed while CI ran and the next look came on average 4.4 minutes later, about 46 task-hours, most of it after CI had already finished.
  - **Rate-limit aware.** A refusal makes that project wait for the reset time the forge names (on GitHub a 403 with `X-RateLimit-Remaining: 0`, or a 403 or 429 with `Retry-After`, or a GraphQL answer of any status with `X-RateLimit-Remaining: 0`; the forge raises it as a typed rate-limit result, makes no call with the installation's token in the same rate-limit pool (on GitHub `core` for REST, `graphql` for GraphQL) before the latest reset any answer of that pool named, and records every REST answer's remaining budget and reset per installation in the cache the workers share); other projects go on. A refused shared listing holds the projects on that forge only; projects on other forges go on.
  - **A reserve for essential calls.** Each installation keeps a share of its hourly budget (20% by default, owner-configurable) for the calls the loop cannot do without: the CI of a waiting head and of the default branch, merges, pushes, review posts, owner notices and (planned) the scorecard comment of a merge ([Journey scoring](06-budget-and-model-planner.md#journey-scoring)). Below the reserve, by the latest recorded reading, routine reads pause until the reading's reset: listings beyond each project's one per tick, wait and intake scans, and dashboard refreshes. Essential calls always go on; only the forge's own refusal above stops them, and a head whose essential read it stopped waits for the reset as a waiting head once that reset time is stored: a forge refusal is ordinary waiting. If storing the reset time fails, that head alone fails and goes through the ordinary per-head back-off of a failed head, while the other heads of the tick go on. Routine re-reads on every tick of every worker once spent a whole hour's budget, and the check of a red default branch was skipped.
- **A missed CI start is detected.** A forge can miss a push: the branch moves, the pull request keeps the old head and no run starts. After a set time (for example 10 minutes) with no run for the head, or with the pull request on another head, Intakt reads the pull request once. Closed or merged: the head leaves the queue and goes to the Maintainer. A conflict with main (the forge starts no run then): on a dependency bot's pull request, a wait for the bot's next head ([Dependency bots](#dependency-bots)); on any other, Intakt merges it itself when the conflict is only in registry files (above), and otherwise, or when that merge fails, the head takes the route of a head that needs main (a merge-main rework for the Developer while the task has build cycles left, else a hand-over to the Maintainer). Otherwise Intakt nudges the forge once (for example by closing and reopening the pull request) and, if that starts nothing, hands the head to the Maintainer once. No head waits for CI forever.
- **A failed run is retried only when the failure looks transient.** Plain code classifies a failed run from the forge's structured job and step results; for the registry case it may also match a fixed list of network errors in the failed step's log. No model reads the log ([Principles](../02-principles.md)):
  - **Transient means no result from the code.** A failure is transient only when it shows no result from the project's code: the forge reports the runner lost, a job never started, the checkout timed out, or the step that fetches dependencies failed with one of a fixed list of network errors reaching a registry. Anything else, and anything the code cannot classify, is not transient.
  - **A named failure goes straight back.** A failure that names a failed gate, test or step of the project is not transient. It is never retried automatically, with one exception: a test the flaky record names (below). The head goes back to the Developer at once as red CI with the failed step and its log lines, under the excerpt rules of red CI (the failed gates and their findings, redacted and fenced, always from Intakt's check container and from a forge run only when the workflow scan clears the head's runners; a forge run the scan does not clear, or any forge run when the scan fails, gives only the count of failed jobs; [Threat model](14-threat-model.md#ci-log-excerpts)). On a dependency bot's pull request, which the Developer never edits, the same excerpt goes into the one task filed for its red check instead ([Dependency bots](#dependency-bots)). No runner slot or wait is spent on a run that cannot pass. Seen on 2026-11-07: a smoke test that called a command with a descriptor missing failed every time, was run again automatically, and the head waited in the runner queue for a result already known.
  - **One automatic retry per head.** A transient failure gets one automatic retry; a second failure on the same head is the result and is judged as red CI, as above. The retry starts the per-head CI read again, so the head waits on the retried run. The missed-CI nudge above is no retry: it starts a run where none exists, and no run failed.
  - **Flakiness needs a recorded suspect.** A test known as flaky keeps its own record and rule. A failed test is retried for flakiness only when that record names it, never on a guess; a test it does not name is a named failure, as above. This is the only exception to the named-failure rule, and it draws on the same single retry per head: a flaky retry and a transient retry are not both allowed on one head, and a second failure is the result.
  - **The reason is recorded.** Every decision to retry or not, with the class read and the job and step it was read from, goes in the ledger and on the task's timeline.
- **A run Intakt cancelled is not waited on.** When the orchestrator knows a queued or running run can no longer matter (its head went back to the Developer, was replaced or left the queue), it may cancel that run. It records the cancel as its own, with the head and the reason, so nothing waits on that run: it never holds the head, never takes the missed-CI path and is never judged red.
- **A cancelled run Intakt did not make is waited on, not judged.** A new push cancels the run of the head it replaces (the workflow's concurrency group), so a cancelled run says nothing about the head; read as red CI, it once handed a pull request over although nothing had failed. A cancelled run is ignored when a newer run of the same workflow, for the same event and the same pull request, exists on the same head; only such a run replaces it, and a newer run of another workflow, event or pull request does not. Of two runs the forge stamps with the same creation second, the later-numbered one is the newer, except for runs of a pull-request event whose pull request the forge does not name, which such a tie never orders. A cancelled run of a pull-request event whose pull request the forge does not name keeps the earlier rule: a run of the same workflow and event, whose pull request the forge does not name either, replaces it when the forge stamps it with a later creation second, while one from the same second leaves the cancelled run unfinished. A remaining cancelled run that Intakt did not cancel itself (above) counts as unfinished CI: the head waits, is never sent back for it and never merges on it. When nothing restarts it within the missed-start time, it takes the missed-CI path above: a closed or merged pull request goes to the Maintainer, a head that conflicts with main gets the registry-file merge or the route of a head that needs main (on a dependency bot's pull request, a wait for the bot's next head), and any other head gets one re-trigger and goes to the Maintainer once only if that starts nothing ([Reviews](07-reviews.md), [Principles](../02-principles.md)). The same rule covers a run that never started: the forge can create a run that never reaches a runner and stays queued with no jobs, a run that can be neither cancelled nor deleted. A run that has not started is ignored when a newer run of the same origin (the same workflow, event and pull request) exists on the same head, like a replaced cancelled run, so the head is judged on the newer run; only such a run replaces it. A not-started run of a pull-request event whose pull request the forge does not name is not ignored, because two runs with an unknown pull request are not shown to share one origin. A run that is still running is never ignored and keeps the head pending, because it may still finish red; a requested rerun of a run counts as running. A replaced cancelled run is ignored whether it started or not. A not-started run with no newer run stays unfinished CI and takes the missed-start path above, unchanged. A failed run makes the head red even while another run is still going (queued, running or a cancelled run that stays), so red CI is never waited on.
- **No runner is not a wait.** A run that cannot start because the plan's CI minutes are spent or no runner takes it is recorded with that cause and shown on the board, never as an endless "pending" (see [Budget and model planner](06-budget-and-model-planner.md#ci-design-for-later)).

## Hands-off and take-over

The labels are defined in [Labels](04-labels.md#who-drives-an-item); this is what they mean for the merge flow.
- **A `hands-off` item does not merge.** The first step of the list above also re-reads the label, right before publishing, so a label set while the merge was about to run stops it; once the dashboard's planned `hands-off` control exists, the same re-read also reads its state in Intakt's own records ([Labels](04-labels.md)). A push or a post a job produced after the label is not published; its unpushed work is kept as a saved bundle.
- **A taken-over pull request is reworked and reviewed like Intakt's own.** After `take-over` on a pull request that is not a dependency bot's, the Developer reworks the open findings, the Code reviewers review the head and the rules above apply unchanged, protected-path rules included. It lands as a pull request Intakt did not open: on its original branch by the forge merge call ([Merging others' pull requests](#merging-others-pull-requests)), not by the ref update of step 3; only a fork carried over to an Intakt branch (below) becomes Intakt's own pull request and keeps the ref update.
- **A taken-over fork Intakt cannot push to is carried over.** Intakt applies the change on an Intakt branch and opens a new pull request that links the original. Every original author is kept as a `Co-authored-by` trailer on Intakt's signed commits, so credit survives. The original gets one comment pointing to the new pull request, and nothing else is written to it. When the taken-over fork is past the split tier and split instead ([The Maintainer](09-maintainer-agent.md)), the split's comment naming the parts, its close and its reopen (after a late commit, or when a part closes without merging) are all the take-over writes to the original.
- **A pull request that touches protected paths is not taken over.** The Developer may not change protected paths, so Intakt says so once, naming the files, and leaves the pull request to people. The reason is that a taken-over pull request would otherwise be a way to push a protected change through the Developer.
- **A dependency bot's pull request is not taken over.** Like a protected-path change, `take-over` on it is refused: Intakt says so once in a comment, and the pull request stays on the [bot path](#dependency-bots) (the bot rebases it, the owner approves it, a red check becomes a task of its own). It never becomes an Intakt task, its commits are never listed for the Developer and it is never carried over to an Intakt branch; removing `hands-off` from it puts it back on the same bot path. The reason is that the bot owns its branch and its diff, and the owner's approval covers exactly the bot's package set and diff.

## Merging others' pull requests

A pull request Intakt did not open (a person's pull request reviewed after its label, or a dependency bot's, below) merges after the same checks as Intakt's own, but lands differently (owner decision 2026-11-04):
- **Through the forge's merge call.** Intakt merges it with the forge's merge API, using the project's merge method, never by moving main's ref. The forge then closes the pull request as merged and its author keeps the credit. None of its commits needs Intakt's or the owner's signature: signatures are [recorded, never required](#watching-main). Intakt's own heads keep the ref update of step 3.
- **Recorded as Intakt's merge.** The merge attempt (step 3) names the forge merge call as its landing form, and recovery records the resulting commit (the forge's merge commit) as Intakt's merge by the rules of [Watching main](#watching-main), so every commit the landing brought onto main is covered by it.

Reason: the first two dependency-bot pull requests on this repository could not merge, because their commits carried the forge's signature and touched lock files, and one had to be replayed by hand as an owner-signed pull request.

### Dependency bots

A dependency bot's pull request (Dependabot, Renovate) is work Intakt takes on its own ([Choosing work](03-choosing-work.md)):
- **Taken without a label.** A project setting names the bot logins whose pull requests Intakt takes; it is on by default for the forge's own bot (on GitHub, Dependabot). Only an author the forge reports as that bot account counts, never a user account with a similar name.
- **Manifest, lock files and CI action pins only.** A diff that touches anything besides the ecosystem's manifest and lock files and the CI action pins (which are protected paths) is refused with one comment naming the files, and Intakt does nothing more with it.
- **Checked like any change.** Its Code reviewers, CI and the [dependency-policy](#mechanical-checks) adapter run as for any change, and the Developer never edits the pull request. Intakt pushes nothing to the bot's branch, so the rule "Main is merged in last" (above) does not apply to it: a branch behind main or in conflict is left to the bot, which rebases it into a new head.
- **The owner approves once, whatever the paths.** Every admitted bot pull request needs one approval from the owner's own account before it merges, a diff that touches only a manifest included (a project without a committed lock file, a widened version range). The approval comes from the bot's authorship, not from the protected-path list: nobody with write access labeled the pull request, so the owner's answer is the only human decision on it, and Intakt never approves a bot head on the spot. Lock files and CI action pins are usually protected paths as well, which is the common reason the owner is asked, never the condition. The owner is asked at the end, as "The owner is asked once, at the end" in [Reviews](07-reviews.md) says: once CI is green on the head, every review approves and the head merges cleanly with main, so the owner never approves a head whose red check is about to become a task. The question covers the package set and the pull request's whole diff, and the answer carries to a later head of the bot that keeps the same package set and the same diff; a head that changes either is asked again.
- **A red check becomes one task.** When CI fails on the bot's head, Intakt files one task with the failing excerpt (under the excerpt rules of [red CI](#waiting-for-ci)) and the packages that moved, and checks the pull request again after that task merges. How that task is ordered, and when it closes, is in [Choosing work](03-choosing-work.md).
- **Evidence written by Intakt.** A pull request from an authenticated dependency bot whose diff touches only the manifest and lock file gets its Evidence from Intakt: the version changes, the upstream release notes, the lock file's consistency, the dependency audit and CI on the head. Reviewers are told not to ask the bot for an Evidence section, since such pull requests were sent back for exactly that.
- **Merged in place.** Once CI, every review and the owner's approval pass on its head, it lands by the forge merge call (above). Without the owner's approval it never lands, green CI and every review notwithstanding.
- **Setup recommends a cooldown.** Setup recommends a release-age cooldown for version updates (Dependabot `cooldown`, Renovate `minimumReleaseAge`): about 3 days for patch and minor updates and longer for major ones, with security updates exempt and handled at once. It also recommends grouping related packages (a framework's packages together).

## Watching main

Main's integrity rests on whether a change went through a gate, never on who signed its commits (owner decision 2026-11-04): commits from contributors, dependency bots and the forge's own merges are normal on main. Reason: requiring every commit to come from Intakt or carry the owner's signature would halt any project with outside contributors, a dependency bot or people who merge in the forge's interface. Before every step and merge, the watchdog reads main's new commits and how the forge reports each one arrived:
- **Accepted:** a commit Intakt merged and recorded; a commit the forge reports as part of a pull request merged into main by an account with write access (an info event); a commit the forge reports as pushed to main by a person with write access (an info event, shown on the dashboard as "pushed without the gate", and main's CI result on it is watched as for any merge).
- **Halts:** a rewrite of main's history; a commit the forge cannot attribute to a merged pull request or to a write-access pusher; a commit whose merger or pusher lacks write access; a direct push to main by a bot or App account, since bots land changes through pull requests; and a commit Intakt's record lacks that Intakt's own forge identity (its App or the Maintainer's) pushed or merged. The last is always a halt, never a notice: Intakt never lands a commit without recording it, so such a commit means its token was used outside Intakt. A merge whose answer was lost (a timeout, a restart) is not such a commit (below); only a commit no merge attempt explains halts. Each halt names the commit and the reason on an owner card, and only the owner clears it, after checking the commit.
- **A merge attempt stays open until its outcome is definitive.** The attempt is recorded before the forge call (step 3 above) and covers every merge call made under it: a later pass that merges the same head again does so under the same attempt. Before every watchdog run, recovery reads each open attempt's pull request back:
  - *Recorded as Intakt's merge* only when the attempt's head landed on main by the identity the attempt recorded, in the attempt's landing form (an attempt lands in one form, and its outcome is read by that form): for a forge merge call, the forge reports the pull request merged with that head as its head, into main, by that identity, and main contains the merge commit the forge reports for it (a merge commit or a squash is a new commit, not the head; step 4 reads its tree back); for a ref update, main's ref moved from the attempt's recorded commit to exactly that head, by a push the forge attributes to that identity. The attempt then closes with the resulting commit (the forge's merge commit, or the head), and every commit the landing brought onto main is covered by it. A ref update that matches its attempt is Intakt's merge (the first accepted case), never a direct push by an App; whether and by whom the forge later reports the pull request merged is read only for [branch cleanup](#branch-cleanup). A merge or push by Intakt's other identity that no attempt of its own explains is not Intakt's merge: it halts as an unrecorded commit of Intakt's own identity.
  - *Closed without a merge* only on an answer that cannot change, read by the landing form. For a forge merge call the pull request's state settles it: the pull request is closed unmerged, its head is no longer the attempt's head (the merge call names the head, so it can no longer succeed), or it was merged by another account or into another branch. For a ref update the pull request's state settles nothing, since the update targets main directly and can still land after the pull request closed or moved: only main's ref settles it, once main no longer holds the recorded commit and was not moved to that head by the recorded identity's push (the update names the recorded commit as main's expected value, so it can no longer succeed). A ref update whose push the forge has not yet attributed is no outcome: main at the head with the attribution pending closes nothing. In both forms, a definitive refusal of a call (not a timeout or a server error) closes the attempt when no earlier call under it is still unresolved (timed out or unanswered). A head merged by another account is not Intakt's merge, and the watchdog judges that commit by the rules above: a merger with write access is an info event.
  - *Kept open* otherwise: for a forge merge call while the forge reports the pull request open on that head, for a ref update while main still holds the recorded commit or main is at the head with the push's attribution pending, in both for as long as that lasts, and while an earlier call under the attempt is unresolved: a landing that timed out can still finish after the read, so an open pull request, an unmoved main or an unattributed push is no outcome. After a ref update the forge can report the pull request open, closed or merged before it attributes the push: the attempt stays open and the commit is held as below, and the ref match above records it once the forge attributes the push to the recorded identity.
  - *Read once more before a halt.* A merge can also finish between recovery's read and the watchdog's read of main, so before the watchdog halts a commit by Intakt's own identity, it reads back the open attempt for that commit's pull request, if there is one, and applies the same conditions.
- **A late forge record is held, for a bounded time.** When main has a commit by Intakt's own identity and an open attempt could still explain it, the watchdog holds that commit as pending: not accepted, not halted, and Intakt merges nothing meanwhile. For a forge merge call that is an open attempt for a pull request the forge still reports open on that head. For a ref update it is main holding the attempt's head while the attempt is open, whatever the forge reports of the pull request, since the forge can report it closed or merged before it attributes the push. It reads the commit again on the next pass. If the forge has not attributed it to the attempt within 10 minutes, it halts as an unrecorded commit of Intakt's own identity. Reason: the bound keeps a stolen token from hiding behind the hold.
- **Signatures are recorded, never required.** Each commit's signature is recorded as the forge reports it. Requiring signed commits is an opt-in project setting, off by default to keep the [simplest first install](../../guide/setting-up-intakt.md); when it is on, the forge's own verification counts, and Intakt's merges are signed by Intakt.
- **The forge's protection is recommended, not assumed.** Setup recommends the forge's branch protection where the plan offers it (required checks from Intakt's identity, no force push, no deletion), and the dashboard shows when the watchdog is main's only protection.
- **Signature rules built first (maintainer decision 2026-11-13, #2914).** The first built part of the watchdog classifies by Intakt's record and by signature: a recorded merge head, and every commit reachable from it and not from its recorded base, passes before any signature check, a commit signed by a key the owner registered passes, a commit signed by a peer loop's key (`--peer-key`, #2988) passes as an info event with no notice, and an unsigned commit, an unknown key and a rewrite of main's history are violations ([Watchdog over main](../../architecture/watchdog.md)). The forge-based rules above are still planned; how they and these rules combine is the owner's to settle. The signature rules run only by hand so far (`intakt:watchdog:check`, #1790, and `intakt:watchdog:guard`, which halts with an owner card that only the owner clears with `intakt:watchdog:clear`, #1690); nothing runs either set on its own yet.

## Branch cleanup

Branch cleanup is Intakt's job, so a busy loop does not leave hundreds of branches behind. It is limited on purpose:
- **Only Intakt's own branches by default.** Cleanup touches only branches Intakt created (its branch prefix). It never touches the default branch, protected branches or release branches. Cleaning up other people's branches is opt-in per project.
- **Merged pull request:** its branch is deleted once the forge reports the pull request merged, read back right after the move of main, and setup turns on the forge's own auto-delete where it exists. The forge marks the pull request merged a moment after main moves, and deleting the branch before that can close a merged pull request as unmerged. If the forge has not reported the merge within a short bound, the branch is kept and the pull request gets one comment naming the head that landed on main. Cleanup deletes the branch once the forge reports it merged.
- **Closed, unmerged pull request:** the branch is kept for 30 days, then deleted. A `keep` label on the pull request exempts it.
- **Branch with no pull request:** after 30 days without commits it is listed as stale; after 60 days it is deleted unless claimed. A branch is claimed when a person (not Intakt's identity) has committed to it, or when it is named in the `keep-branches` list of the project file. The `keep` label does not apply here, since there is no pull request to carry it.
- **Warning first:** for a closed, unmerged pull request's branch and a branch with no pull request, a weekly job lists what it will delete a week before it does (a dashboard chore and one notice), then deletes. A merged pull request's branch needs no warning (owner decision of 2026-11-24 on #3839).
- **Nothing is lost:** the orchestrator keeps every deleted branch's head in its own mirror as an archive ref, so a deleted branch can be restored. Archive refs are never pushed to the forge.
