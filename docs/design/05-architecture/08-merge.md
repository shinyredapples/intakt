# Merge

Only the orchestrator merges. Right before merging it:
1. re-reads the task and the pull request, and stops if either is blocked, closed or changed since the verdicts;
2. requires green CI on exactly the head it is about to merge, and waits when CI has not registered that head yet (a head it pushed a moment ago);
3. merges only that head: the forge call names the head commit, so a push in between makes the merge fail instead of riding the earlier approval;
4. reads the result back (the merge commit and its tree) and only then closes the issues and records the merge.

Protected paths (gates, CI config, agent instructions, dependency policy, the boot harness) need an approval, and a protected change gets one of exactly two outcomes, decided at once when its head has green CI and its panel's verdicts ([Approving protected changes](#approving-protected-changes)):
- **Intakt approves on the spot** when no hard floor is hit, every mechanical check passes, the independent security review agrees and the attacker test finds no way around the change.
- **Otherwise the owner reviews.** The request names the floor or the check that sent it. It never resolves itself: no timer, no veto window, no "approve unless stopped", no one-tap shortcut.
- **Protected paths are read from the whole change.** Whether a head touches a protected path is decided from the full diff between the merge base with the current main and the exact head being merged, combined with the per-commit lists (the paths each commit between the merge base and the head touches, each commit compared against each of its parents; the commits between the merge base and the head are the commits reachable from the head and not from the merge base, so a merge's second-parent commits count unless main already contains them), never from a merge commit's diff against one parent, because a crafted merge (first parent the branch, second parent an old main commit) could otherwise revert or delete a protected file without it being listed. Submodule entries and `.gitmodules` count as protected.
What goes to the owner follows these rules:
- **Same flow as any change.** A build that touches protected paths is pushed and opened as a normal pull request, gets CI, its review panel and reworks on its own branch; it is never exported as a patch for someone to re-apply (patches go stale and every rejection meant a rebuild from scratch). When CI and its review panel pass, it parks with "waiting for the owner" and notifies once.
- **A risky change to the CI definition is never pushed before the owner approved it.** A forge runs the workflow taken from the pushed commit, so a build that edits it would run its own workflow on the project's runners before anyone looked. A change is pushed without that approval only when a scan of the workflows (the head's, main's, and the two merged) shows they can reach no more than a forge-hosted, throwaway runner with a read-only token and no secrets: hosted runner labels only, read-only permissions, no secrets beyond the read-only token, no triggers that run with the base repository's rights; anything the scan cannot read counts as risky. A `runs-on` taken from a variable or an expression is unreadable, since the variable can change without a commit, so it counts as risky even while the variable is unset: every CI change of that project waits for the owner, and its builders get no CI log excerpts ([Threat model](14-threat-model.md#ci-log-excerpts)). The scan reads the files the workflows run from the repository as part of the CI definition: a change to one of them is a CI change, since it runs on the runner as the workflow does. Self-hosted runners always ask, and must be ephemeral ([Threat model](14-threat-model.md#self-hosted-ci-runners)). Merging a CI change follows the approval rules below: a workflow file always goes to the owner, and a file a workflow runs is approved on the spot only when it clears every floor and check. A risky change stays local; the owner approves the exact diff and commit first, and only then is it pushed. That request shows the whole change, not only the CI files (an approved one-line workflow edit can run a script nobody was shown), and a change too large to show in full is sent back to be split, never approved from a file list. Approving the push does not approve the merge: the owner is asked again, with the full list of protected changes, when the head is ready to merge.
- **The owner is asked only for a reviewed change.** Before the push request reaches the owner, the review panel reviews the held diff with a security brief: triggers that run with the base repository's rights, permissions, runners, secrets, untrusted text (titles, bodies, branch names) put into a script through an expression instead of an environment variable, unpinned actions, and what a later push of the branch could run. A rejection goes back to the builder without asking the owner; an approval travels with the request, so the owner confirms a reviewed change instead of reading a workflow cold. The envelope that needs no approval stays narrow on purpose: a token that may write issues could rewrite a task's body, which is the build's instructions, so any write scope keeps needing the owner.
- **The approval names the head.** It is a normal forge review by the owner's account (possible because the pull request's author is Intakt's identity, not the owner), or a comment `approve <sha>` by it, which no job can write (jobs have no forge credentials) and Intakt's own identity never writes. A new push needs a new approval.
- **An early approval counts once its head passes.** An approval given before CI and the reviews finish stays: it counts once that same head passes, and a push after it voids it, except the clean merge of main and the generated-files resolution described below. Intakt never removes or re-asks it because of a review or CI round.
- **The owner can send a head back.** A comment `changes <sha>` by the owner's account, or a review requesting changes on that head, when it is the owner's newest decision there, sends the head back with the owner's note fenced: to the builder for a task's head, to the maintainer agent for its own pull request. The head is no longer asked about and stops counting toward the owner-wait cap. Only a later approval from the owner's own account overrides the owner's send-back, never anything the maintainer agent or Intakt's identity posts, so a helper cannot overrule the owner.
- **The owner is asked only about a head that merges.** Before a protected head is offered for approval it must merge cleanly with main; a real conflict goes back to the builder, not to the owner or the maintainer. While a head waits, main moving costs nothing (no rebuild, review or new notice); a conflict that appears only in generated files is resolved by Intakt itself after the approval (merge main, regenerate the generated files, and let the approval carry when the protected change is byte-identical and the extra commits touch only generated files), and a real conflict withdraws the request once, but parks the approval instead of dropping it. When the resolved head is a merge of main onto the parked head, made by Intakt's builder or maintainer agent through the hand-back, with the protected change byte-identical, the parked approval carries to it once its review and CI pass; any other new head drops it with one comment and is asked again. Intakt's own recorded merges stay recognized across hand-backs, so an owner is never asked twice for the same change because of Intakt's bookkeeping.
- **An approval is informed and unforgeable.** The request lists every protected change of that head and says plainly when the change modifies the checks that judged it (green CI then means the head's own gates passed). Only the owner's own account can give it, through a channel no agent of Intakt's can write: Intakt's identity never posts it, and helper agents acting for the owner (the maintainer agent, which writes the summaries of approval requests and triages) run under a forge identity that is never the owner's account, so a review or `approve <sha>` they post is not the owner's, and a post guard blocks them from it as a second barrier, not by an instruction. A clean merge of main into an approved head that leaves its protected changes identical keeps the approval, so a busy main does not mean asking again every hour.
- **Only a few heads wait for the owner at once** (a cap per install, three by default), so the owner's queue stays short enough to act on. Only real waits count: a head with green CI and every review passed that waits for the merge approval, and a held CI change that waits for its push approval. A head still in review, sent back or on hold does not count, and a wait Intakt cannot classify counts (fail closed). A head that is ready while the cap is full is queued for the owner with no label, comment or notice and holds no slot; the queue is ordered by priority, then age, so a newer head never takes a freed place ahead of an older one of the same priority. A freed place is reserved under the same lock that read the count, before the owner is asked, so two workers cannot both take it, and a failed ask gives it back. At the cap, builds of tasks known to need the owner wait, with one notice; a task's own rework is never blocked.
- **Main is merged in last.** A head gets CI and its reviews as it was pushed. Intakt merges main into the branch only when the head is ready to merge (green CI, every verdict, any owner approval it needs) or when the forge reports a conflict with main. A clean merge keeps the verdicts and the owner's approval (above), and CI runs once more on the merged head before the merge. Merging main into every open branch whenever main moved restarted CI on all of them: one pull request ran CI 19 times in a day, and a single self-hosted runner fell an hour behind.

## Approving protected changes

On this repository 32 of 120 merged pull requests waited for the owner; about 6 of those only edited comments in the boot harness, most dependency approvals added official Symfony packages, and waiting for approvals was about 20% of all waiting in the loop. So Intakt approves what plain code can prove harmless, and asks the owner for everything else, at once and with the reason. This replaces approval by class, which needed at least two reviewers from different vendors classifying a change as tightening or neutral. The order below is the order of the decision; the first step that fails ends it with a request to the owner that names that step.

### Hard floors

Hard floors are deterministic rules over the whole change (read as protected paths are, above). No model output lowers them, and a hit always goes to the owner:
- **Secrets and credentials:** any change to how secrets or credentials are stored, read, injected, redacted or scanned, including the secret scan's rules and its allowlist.
- **CI:** every workflow file (`.github/` and the like), and therefore raised permissions, new triggers, a runner change and a workflow that reads a repository secret. Code ownership lives there too.
- **Gate tests:** a deleted, renamed or edited test, fixture or configuration of an existing gate. New tests and fixtures are not a floor.
- **The protected-path list and the approval rules,** including the code that applies these rules and the canary corpus (below), so Intakt can never widen its own approvals.
- **Agent instructions:** `AGENTS.md` and every file a model reads as its rules (skill and focus files, role prompts).
- **A panel reviewer's class.** A panel reviewer that classifies the protected part as loosening, or gives no valid class ([Reviews](07-reviews.md)), sends the change to the owner. A classification never approves on its own.

### Mechanical checks

Every protected file the change touches must be covered by a mechanical check that passes; a file no check covers goes to the owner. The checks are plain code. What differs per language comes from a `language` plugin ([Plugins](02-plugins.md)), PHP first.
- **Comment-only.** The old and the new file parse to the same syntax tree once comments and whitespace are dropped, through tree-sitter or the language's own tokenizer (for PHP, `PhpToken`). A comment a tool reads counts as code: docblocks (static analysis reads their types), suppression and ignore markers, and inline allow directives. Where a language has no parser, the check does not apply.
- **Dependency policy.** One adapter per ecosystem reads the old and new manifest and lock file (Composer first; npm, PyPI, Go and Cargo by plugin). The rules are written once over language-neutral sources: OSV.dev for advisories and deps.dev for release dates and use. A change passes only when every new package, transitive ones included, comes from an allowed vendor in the owner's config, has no open advisory, and has a release older than the minimum age in the owner's config, and when no install script, plugin or package source changes (for Composer: `scripts`, `allow-plugins`, `repositories`, `config`, binaries and autoload files). The orchestrator queries the sources, never a job; an unreachable source or an unknown answer goes to the owner.
- **Gate code is no weaker.** Main's gate tests run unchanged against the head's gate code, and so does the violation corpus: every violation the gates have ever caught, kept as a fixture that must still be caught. Both run through the project's check command, so the proof is language-neutral, in their own check container and as their own user, with the result leaving through a channel the code under test cannot rewrite. A check that runs the candidate's code cannot detect code written to cheat it, which is why the security review and the attacker test follow.
- **Harness from main.** The boot gate runs main's trusted harness (`bin/instance`, `bin/probe`) against the head, so a harness change cannot certify itself. Booting proves only that the head still boots, so main's isolation probes also run through the head's harness: a probe that reaches the network, writes outside its folder, reads a credential or runs as another user must still be stopped. A harness change passes only when both hold.

### Independent security review

Separate reviewer sessions judge the protected part: a **security reviewer** and an **attacker**, each with its own role and prompt ([Threat model](14-threat-model.md#security-reviewer-and-attacker)). They get the diff, main's version of every protected file and the floor and check results, never the builder's pull request text or reasoning, and their verdicts are typed objects checked like any other. The security reviewer must agree that the change keeps or tightens the rules. A second AI vendor adds confidence when one is available and is never required. Missing reviewer capacity (no account free, a failed review, a stand-in) sends the request to the owner, never waits it out.

### Attacker test

The attacker tries to write a fixture that main's gate rejects and the head's gate accepts. Plain code runs each fixture against both, in a check container without network. A fixture that gets through is proof of weakening: the change goes to the owner with the fixture, and the fixture joins the violation corpus once the owner confirms it. Finding nothing is not proof of safety; it is one more check that must pass.

### Earned autonomy per category

Each category (comment-only, dependency, gate code, harness) starts in **shadow mode**: the decision is computed and logged while the owner still approves, starting with a replay of the repository's past approvals. Owner-known **canary changes** run through the pipeline regularly and must be sent to the owner. Each category has canaries of its own, and detection is measured per category over only those, so a category with no canaries cannot reach 100% by default:
- *comment-only:* a changed statement among edited comments, an edited docblock type, an added ignore marker;
- *dependency:* a malicious dependency, a package from another vendor, a new install script;
- *gate code:* a weakened gate, a gate that skips a file it used to read;
- *harness:* a harness edit that drops the isolation of `bin/probe` (network, folder, credentials or user), one that skips a boot step;
- *hard floors:* a workflow that reads a repository secret, an edited gate test, an edited agent instruction.

A category with fewer canaries than a set minimum (for example 3) stays in shadow mode. A category qualifies for automatic approval only at 100% detection of its own canaries and agreement with the owner over a set number of real cases (for example 20); the owner then switches it on in the owner's config, since turning it on widens the approval rules. It switches back to shadow mode on its own when a canary is missed or the owner overrules a computed decision.

### Containment

- **Automatic revert.** When main's canaries or violation fixtures fail, Intakt looks at the automatic approvals merged since they last passed. When there is exactly one and no later merge touched any file it changed, Intakt reverts that merge at once: the revert restores those files to main's version before it, byte for byte, so it needs no approval. Otherwise (several automatic approvals, or a later merge on the same files) Intakt reverts nothing on its own and asks the owner, naming every candidate merge, and no automatic approval is given in that project until the owner answers. In both cases the categories involved go back to shadow mode and the owner is notified.
- **A daily cap** on automatic protected approvals per project (for example 3); past it, the next one goes to the owner.
- **Visible afterwards.** Every automatic approval says so on the pull request in one line (the head, the category, each check that passed), and is listed on the dashboard for a week with that line, so a wrong call is seen without anything waiting on a person; it is information, not a notice.

## Waiting for CI

- **A wait for CI holds nothing.** A head whose CI is pending holds no slot and no lock: its step ends, the head goes back to its queue with its place by age and a time to look again, and the lane takes a head whose CI has finished. A head pending for a set time (for example 30 minutes) is admitted by age anyway, so a slow pipeline is not starved by fast ones. A drain does not wait for parked heads.
- **A head waiting for CI is not a head waiting for review.** The cap on built heads waiting for review counts only heads whose CI has finished. Heads still waiting for CI count against the CI capacity instead ([Budget and model planner](06-budget-and-model-planner.md#ci-design-for-later)): when more heads wait for CI than the runners can clear in a set time, new builds wait, and the dashboard shows "waiting for CI" apart from "waiting for review". A review cap filled with heads whose CI had not started kept the build slots closed while nothing was being reviewed.
- **Webhooks first, a read as backstop.** CI results arrive as forge webhooks. A head waiting longer than expected is read directly, and a fallback read skips items whose head and update time did not change, to spare the forge's rate limit.
- **A missed CI start is detected.** A forge can miss a push: the branch moves, the pull request keeps the old head and no run starts. After a set time (for example 10 minutes) with no run for the head, or with the pull request on another head, Intakt reads the pull request once. Closed or merged: the head leaves the queue and goes to the maintainer agent. A conflict with main (the forge starts no run then): a merge-main rework for the builder. Otherwise Intakt nudges the forge once (for example by closing and reopening the pull request) and, if that starts nothing, hands the head to the maintainer agent once. No head waits for CI forever.
- **No runner is not a wait.** A run that cannot start because the plan's CI minutes are spent or no runner takes it is recorded with that cause and shown on the board, never as an endless "pending" (see [Budget and model planner](06-budget-and-model-planner.md#ci-design-for-later)).

## Branch cleanup

Branch cleanup is Intakt's job, so a busy loop does not leave hundreds of branches behind. It is limited on purpose:
- **Only Intakt's own branches by default.** Cleanup touches only branches Intakt created (its branch prefix). It never touches the default branch, protected branches or release branches. Cleaning up other people's branches is opt-in per project.
- **Merged pull request:** its branch is deleted at once, and setup turns on the forge's own auto-delete where it exists.
- **Closed, unmerged pull request:** the branch is kept for 30 days, then deleted. A `keep` label on the pull request exempts it.
- **Branch with no pull request:** after 30 days without commits it is listed as stale; after 60 days it is deleted unless claimed. A branch is claimed when a person (not Intakt's identity) has committed to it, or when it is named in the `keep-branches` list of the project file. The `keep` label does not apply here, since there is no pull request to carry it.
- **Warning first:** a weekly job lists what it will delete a week before it does (a dashboard chore and one notice), then deletes.
- **Nothing is lost:** the orchestrator keeps every deleted branch's head in its own mirror as an archive ref, so a deleted branch can be restored. Archive refs are never pushed to the forge.
