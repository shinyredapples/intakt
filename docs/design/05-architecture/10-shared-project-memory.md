# Shared project memory

The goal is a memory that helps every vendor's agents, without letting any one of them poison it.
- **Written only by the orchestrator**, from accepted events: a merged pull request's summary, a review finding that was fixed, a recurring check failure and its cause. The one other entry is the task-scoped [hand-off note](#hand-off-at-a-limit) when a job stops at a vendor limit, which the orchestrator builds only from its own facts.
- **Read-only to jobs**, mounted as a short markdown digest per project and role, regenerated after each merge, with a size cap.
- **Reviewed by the owner** in the dashboard: entries can be pinned, edited or deleted.
- **Fresh or flagged.** An entry that explains code records a content hash of the files it describes. When main changes them, the entry is flagged stale in the digest and on the dashboard until a job re-describes it, so no job reads an outdated explanation as fact.
- **Settled findings.** A finding the judge or an escalation review rejected is kept with the text, the reason it was rejected, the file and symbol, and a content hash of the code it points at, so later reviewers do not raise the same intentional pattern again. It counts only while the code under it is unchanged: when main changes that code its hash no longer matches, the entry is flagged stale, as above, and is no longer given to reviewers as settled. Like every entry only the orchestrator writes it, from the judge's reject of a finding (a P3; a P1 or P2 keeps its veto and stays on the act list) or a rejecting escalation review, with the hash of the finding's file taken from the reviewed checkout, and the owner can delete it; a deleted entry is not returned. Each reviewer's briefing lists the settled findings on the files in the diff whose code the head under review still holds unchanged, under their own heading ("already settled, do not raise again unless this code changed"), fenced as project memory and within the briefing's size cap, ahead of the other notes. A reviewer may still raise one when it shows the reason no longer holds; the finding then cites the settled entry, and the judge decides on it as on any other finding.
- **Briefing at job start.** Each job starts with a short briefing: what the project is, what is in flight, recent merges and decisions, and the gotchas for the files it will touch.
- <a id="hand-off-at-a-limit"></a>**Hand-off at a limit.** When a job stops at a vendor limit, the orchestrator writes a hand-off note for the task: what was done, what is left and the open findings. The note is built only from facts the orchestrator holds: the job's pushed commits (what was done), the task and the findings it holds (what is left, the open findings). The job's own words reach the next account only through the kept conversation, which is fenced. The next account that continues the task reads the note and the kept conversation through `MemoryInputProcessor` (plan T43), fenced like the rest of the memory. Open for T43: the processor's fixed preamble tells the model that memory outweighs the system prompt, which would rank the fenced note and conversation above it, so T43 replaces or avoids that preamble (the reviewer's briefing sends its notes as a user message for this reason). The note is scoped to its task and is not part of the digest other tasks read. It is dropped when the task merges. See [a limit never loses work](06-budget-and-model-planner.md#a-limit-never-loses-work).
- **Recurring blocking findings in the briefing.** The orchestrator groups the P1 and P2 findings fixed in the project's recent rework rounds by reviewer role and kind, and the Developer's briefing lists the most frequent kinds with one short example each, within the digest's size cap. Checking the change against the list before the hand-back is point 4 of the [Definition of Done](../01-intent.md#definition-of-done), and that definition is the only statement of the rule. The list comes only from accepted events (fixed findings), and like every entry, the hand-off note included, it is written only by the orchestrator, so no job can write to it. The reason: rework, not review capacity, slows pull requests down. In one stretch of the loop's records, 62 of 111 merged pull requests were approved on their first head, 13% needed three or more rework rounds, and one reviewer blocked many heads for the same kinds of finding on different tasks. Each extra round costs a wait for a free build slot, a build and another review (see [Reviews](07-reviews.md)). A kind that keeps recurring despite the briefing is proposed as a check of its own ([Findings that recur become checks](07-reviews.md)).
