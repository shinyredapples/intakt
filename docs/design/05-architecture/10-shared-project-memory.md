# Shared project memory

The goal is a memory that helps every vendor's agents, without letting any one of them poison it.
- **Written only by the orchestrator**, from accepted events: a merged pull request's summary, a review finding that was fixed, a recurring check failure and its cause.
- **Read-only to jobs**, mounted as a short markdown digest per project and role, regenerated after each merge, with a size cap.
- **Reviewed by the owner** in the dashboard: entries can be pinned, edited or deleted.
- **Fresh or flagged.** An entry that explains code records a content hash of the files it describes. When main changes them, the entry is flagged stale in the digest and on the dashboard until a job re-describes it, so no job reads an outdated explanation as fact.
- **Briefing at job start.** Each job starts with a short briefing: what the project is, what is in flight, recent merges and decisions, and the gotchas for the files it will touch.
- **Recurring blocking findings in the briefing.** The orchestrator groups the P1 and P2 findings fixed in the project's recent rework rounds by reviewer role and kind, and the builder's briefing lists the most frequent kinds with one short example each, within the digest's size cap. The builder checks its change against the list before it pushes and says in the pull request text which items it checked. The list comes only from accepted events (fixed findings), like the rest of the memory, so no job can write to it. The reason: rework, not review capacity, slows pull requests down. In one stretch of the loop's records, 62 of 111 merged pull requests were approved on their first head, 13% needed three or more rework rounds, and one reviewer blocked many heads for the same kinds of finding on different tasks. Each extra round costs a wait for a free build slot, a build and another review (see [Reviews](07-reviews.md)).
