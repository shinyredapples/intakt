# Plugins

Each plugin is a PHP class behind a small interface, shipped in the image, and selected in config.

| Kind | Interface (sketch) | v1 implementations |
|---|---|---|
| Forge | list work, read issue, open or update pull requests, read CI status, merge, comment | GitHub, Gitea |
| Vendor | run build, run review, probe usage, price/limits | Claude Code (subscription or API key), Codex (subscription or API key), one API-only vendor (OpenAI-compatible endpoint) |
| Gate | command plus protected paths | project command (`bin/check`, `make check`, ...) |
| Language | compare two versions of a file without comments and whitespace, read a package manifest and lock file into the dependency policy's neutral form ([Merge](08-merge.md#mechanical-checks)), set the runtime memory limit of the processes a job starts ([Security model](../04-constraints.md#security-model)) | PHP (`PhpToken`, Composer), planned |
| Work source | which tasks are eligible, in what order | forge issues with a label, plus dependencies ("Waits for #n"); see "Choosing work" |
| Notifier | deliver a notice (kind, item, link, urgency), report delivery, test | browser push (Web Push over HTTPS, from the dashboard as an installable app), Home Assistant (webhook or mobile app notify), ntfy, generic webhook, email |

Vendor plugins declare their models with a cost class and strengths (build, review, triage), so the planner can choose without vendor-specific code.

**A check reuses a trusted dependency snapshot per lock file.** The dependency step of a check belongs to the language's gate plugin: it names the lock files (for Composer `composer.json` and `composer.lock`; the PHP version comes with the job image) and how to install from them alone with no package's own code (scripts and plugins off) and no file that depends on the tree. The runner keeps a snapshot store keyed by a hash of those inputs and the job image's immutable ID (never a tag, which a rebuild can move). Only the runner writes it: a miss installs in a job of its own that sees the lock files and none of the builder's tree, and saves the result writable by the runner alone; a check job mounts its snapshot read-only and copies the installed folder into its own clone, only where the head leaves that path free, so neither a builder nor the code under test can change what a later check of another head gets, and the snapshot never replaces a file of the change under check. A check holds its snapshot until its job ended, so the store never removes one in use. Files that depend on the tree (for Composer the autoloader and the runtime files) are still made by each check from its own tree. The store keeps the least recently used snapshots up to a configurable count (10 by default). A language whose plugin names no such install installs on every check. See [Check job](../../architecture/check-job.md#dependency-snapshots).

**Notifications go through Intakt, never around it.** Every notice (an approval waiting, a question, an escalation, a halt, a failed update) is an event in the orchestrator, delivered by the notifier plugins the owner enabled: none of the loop's parts (jobs, the maintainer agent) send their own pushes. Routing is in the owner's config: which kinds go to which notifiers (for example approvals and halts to the phone, email as the fallback), quiet hours, and a fallback notifier when the first one fails. Each notice is sent once per item and state change, carries a link to the item on the dashboard or the forge (an approval notice also carries the exact head to approve), and its delivery result is recorded, so a notifier that fails is itself shown on the dashboard. Notices carry no secrets and no approval power: an approval the owner gives stays a forge action by the owner's account. Browser push needs the dashboard served over HTTPS (the wizard offers a certificate from the forge's or a local CA); a notifier's credentials (webhook URL, token) live in the owner's config like other credentials, and every notifier has a "send test" button in the wizard.
