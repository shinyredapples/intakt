# Plugins

Each plugin is a PHP class behind a small interface, shipped in the image, and selected in config.

| Kind | Interface (sketch) | v1 implementations |
|---|---|---|
| Forge | list work, read issue, open or update pull requests, read CI status, merge, comment, name the merged change that closed an issue (also in another repository) | GitHub, Gitea |
| Vendor | run build, run review, probe usage, price/limits | Claude Code (subscription or API key), Codex (subscription or API key), one API-only vendor (OpenAI-compatible endpoint) |
| Gate | command plus protected paths | project command (`bin/check`, `make check`, ...) |
| Language | compare two versions of a file without comments and whitespace, read a package manifest and lock file into the dependency policy's neutral form ([Merge](08-merge.md#mechanical-checks)), set the runtime memory limit of the processes a job starts ([Security model](../04-constraints.md#security-model)), say whether a change of a dependency is released and taken into the project's lock file, name the dependency step of a check (below) | PHP (`PhpToken`, Composer), planned; the dependency step is built in the PHP gate until this kind exists |
| Work source | which tasks are eligible, in what order | forge issues with a label, plus dependencies ("Waits for #n", and `Waits for release: <owner>/<repo>#<n>` for a change in another repository); see "Choosing work" |
| Notifier | deliver a notice (kind, item, link, urgency), report delivery, test | browser push (Web Push over HTTPS, from the dashboard as an installable app), Home Assistant (webhook or mobile app notify), ntfy, generic webhook, email |

Vendor plugins declare their models with a cost class and strengths (build, review, sizing), so the [model planner](06-budget-and-model-planner.md#planning) can choose without vendor-specific code.

**The dependency step of a check belongs to the language plugin.** It names the lock inputs of the dependency install (for Composer: `composer.json`, `composer.lock` and the PHP version of the job image) and how to install the locked packages from them in a clean environment, with scripts and plugins off. The install installs from the lock or fails: a head whose install would not read the lock (for Composer: no `composer.lock`, or a `composer.json` whose `config.lock` is set to anything other than `true`) or whose lock file is not the same after the install (Composer resolved the dependencies anew, as it does for a lock file without a `packages` key, such as `{}`) has no locked install and installs every time. Only an install whose lock inputs pin its contents may be reused (the trust rule). For Composer the install refuses, before Composer runs, a lock that holds a path package, an archive without a checksum (unless its `https` URL ends in its own locked commit id), a source reference that is not a full commit id, a malformed checksum, mirrors, a local or unknown address, a Composer plugin or installer other than `symfony/runtime`, a root script for a package event or for `pre-install-cmd` (a check that copied an install would run it with the packages already in place), or a vendor folder that is absolute or resolves outside the folder Composer runs in, or to that folder itself (nothing of that install would be left to keep). A refusal exits with a status Composer's own failures do not use and a message that names the package, file or script, so that the check installs every time and does not fail. After Composer, the install refuses in the same way a package Composer installed from source whose checkout, found where Composer recorded installing it, is not at the locked commit or is not a plain git clone. Files that depend on the tree (for Composer: the autoload and runtime files and the root package's metadata) are made by a separate command from each check's own tree, with the tree's own plugins and the scripts of the events that command raises (the root package's package-install and package-update events never run in this split, nor do plugins that act on them; plugins that choose install paths are off during the locked install and act only in the generation, after the packages are already in place; the trust rule decides whether such a tree may reuse an install), so an install of the locked packages could serve every head with the same lock inputs. The step also names the platform probe and the install a check runs when it has no shared install (for Composer: the gate's own `composer install`). A language without this support names no lock inputs and installs every time, as a project's own check command does. The lock guards of the trust rule, the source guard after Composer and the store of installs (below) are in place, and a check reuses a saved install when its lock inputs match.

**Trusted installs live in a bounded store that only Intakt writes.** The store is owned by Intakt's runner and keyed by a hash of the lock inputs; only the orchestrator's own process writes it. A build job gets no mount of it, and a check job reaches a snapshot only as a read-only bind of that snapshot's folder, so neither a builder nor the code under test can change what a later check reuses. A snapshot is published under its key in one atomic rename after every entry was made read-only, so a key never names a partial or writable copy. The store keeps the least recently used snapshots up to a configured count (10 by default), trimmed on every save and every lease, never the snapshot being saved or leased. A check holds a shared pin on its snapshot while it mounts it, and an eviction must take that pin exclusively, so a leased snapshot is never removed; a finished install is still published when no room can be made, so while snapshots are leased the store holds at most the count or the active leases plus one, whichever is larger. That overflow can last until the next save or lease after the leases end, because only a save or a lease trims the store. An eviction first renames the snapshot away from its key, so a removal stopped half-way never leaves a partial copy under a key. The check that reuses a snapshot holds its lease as long as it uses the mount, or copies the snapshot out first ([Check job](../../architecture/check-job.md#the-dependency-snapshot-store)).

**A wait for another repository asks two questions.** A `Waits for release:` line ([Choosing work](03-choosing-work.md)) is lifted from two answers, never from a model: the forge plugin answers "which merged change closed this issue", and the language or deployment plugin answers "is that change in what the project runs" (released and taken into the lock file, for a dependency; deployed, for a tool Intakt runs on). The table has no deployment kind yet: no v1 plugin answers the deployed case, so a wait for a tool's deployment goes to the [Maintainer](09-maintainer-agent.md) until a deployment plugin exists. A wait that no plugin can answer goes to the Maintainer and is never lifted by default.

**Notifications go through Intakt, never around it.** Every notice (an approval waiting, a question, an escalation, a halt, a failed update) is an event in the orchestrator, delivered by the notifier plugins the owner enabled: none of the loop's parts (jobs, the Maintainer) send their own pushes. Routing is in the owner's config: which kinds go to which notifiers (for example approvals and halts to the phone, email as the fallback), quiet hours, and a fallback notifier when the first one fails. Each notice is sent once per item and state change, carries a link to the item on the dashboard or the forge (an approval notice also carries the exact head to approve), and its delivery result is recorded, so a notifier that fails is itself shown on the dashboard. Notices carry no secrets and no approval power: an approval the owner gives stays a forge action by the owner's account. Browser push needs the dashboard served over HTTPS (the wizard offers a certificate from the forge's or a local CA); a notifier's credentials (webhook URL, token) live in the owner's config like other credentials, and every notifier has a "send test" button in the wizard.
