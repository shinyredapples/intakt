# Budget and model planner

For each vendor account Intakt keeps a budget model:
- **Subscription:** rolling windows (for example five hours and weekly), each with a measured used fraction from the vendor's own usage probe, and a reset time.
- **API key:** paid overflow, spend tracked from the vendor's billing or token counts. A weekly spend cap per account or per install is an optional owner setting; with none, the account's balance at the vendor is the limit (owner decision of 2026-11-04: API console credit serves reviews and builds after the subscriptions, uncapped, until the balance is gone).
- **Overage:** whether the account bills extra usage past its subscription (asked at setup, kept in the dashboard's admin area). With overage on, a subscription window behaves like an API key past its limit: every guard below that fails open on a subscription (a missing usage reading, a call already in flight past the ceiling) must fail closed instead, and the owner's spend cap applies if one is set.
- **Accounts are a list, not a choice.** Per vendor the owner can enter subscriptions, API keys, or both, equally: personal keys, company or organization keys (with their workspace, spend limits and admin-visible usage), and cloud execution where the vendor offers it (for example Claude Code cloud sessions, which run a job on the vendor's infrastructure instead of a local container). Each account has a role (which jobs it may run), a priority and its own budget model, so a project can say "subscription first, then the company API key when the subscription's window is spent, never more than its spend cap" or "until its balance is gone". Falling over to a paid account is a planner decision shown on the dashboard, within the owner's cap if one is set; it never happens silently. Symfony AI's Platform provides the API side for every provider it supports; subscription CLIs and cloud sessions are vendor plugins of their own. The owner adds, orders and removes accounts in the dashboard's admin area, in a vendor-neutral model of kinds, usage windows, overage, credit pools, vendor-side blocks and roles (see [Dashboard](13-dashboard.md#accounts)).
  - *Several subscriptions of one vendor.* The list may hold more than one subscription of the same vendor (for example two personal plans), each with its own windows, readings and cooldown. A job runs on one account at a time; the next job can start on another, and a job that hits a limit continues on another ([a limit never loses work](#a-limit-never-loses-work)).
  - *One pool, used at once.* Every configured account of every vendor is in the pool for the roles the owner allows it (build, review, light work), unless the owner excludes the account or a model. Jobs run on different accounts at the same time. The reason (the owner's rule of 2026-10-31: every available resource is used unless the owner configures it out): running the loop showed the binding limit was one account's short window (it backed off at 60%, later ran at 95% by midday) while a second subscription sat idle, and a weekly window ran out with days left on another.
  - *Automation credentials before interactive logins.* Where the vendor offers a long-lived automation token for a subscription (Claude: `claude setup-token`), that token is the account's credential: the owner creates it with the vendor's CLI, and the orchestrator passes it to each job on that account. Interactive logins refresh their credentials inside the CLI's configuration directory, and account switchers that swap that directory conflict with a job's fresh per-session configuration, so neither is used for a vendor that has a token. A vendor with only an interactive login (Codex today) keeps the login file per account in the orchestrator, refreshed there, and mounted read-only into the job, never a writable config dir.
  - *Readings belong to their account.* Every usage reading, cached probe, measured limit and outage record carries its account, and a reading is never applied to another account. A newly used account needs its own reading before the planner trusts it.
  - <a id="accounts-differ"></a>*Accounts differ, even of one vendor.* The planner learns each account's room (how fast a window fills under load, which window binds) from that account's own readings and measured rate, and never assumes two accounts of one vendor are alike, whatever their plan names say. Reason, measured on 2026-11-13 by the build loop Intakt is distilled from: on one account a five-hour window lasted five Developers about 90 minutes; on another of the same vendor it never filled and only the weekly window counted.
  - *Usage readings for the ranking (planned).* The Codex vendor plugin reads a subscription account's usage (plan, whether it is allowed now, each window's used percent, length and reset time) from the endpoint Codex itself uses. The read costs no model call, runs inside the account's own job identity and egress like any vendor call, and its token is never logged. It is an internal endpoint, so the read is best-effort: a failed read (an HTTP error, a changed shape, an expired token) falls back to the vendor's limit signals from real calls, and the plugin records when it stops answering. While an account is out until a stated reset, the reading is repeated (for example every 30 minutes), so an upgraded plan or an early reset is used at once.
- **Ceilings are the owner's to move.** The ceiling of each window (the default stop at 90% of the five-hour window, the weekly one the pace aims at) can be raised or lowered by the owner from the dashboard, always with an expiry; a raised ceiling never passes the plan limit of an account that bills overage. A project's share, a pause and a back-off are the owner's in the same way (see [Owner controls](13-dashboard.md#controls)).

## Order of use

The order is a ranking made at each job start over the whole pool, not a chain that waits for the first account to run out. Accounts that are spent, blocked at the vendor or backing off, or not allowed for the job's role, are left out. The rest are ranked, within each account's cap (where one is set) and roles, by step first:
1. subscription credit that expires soon or can only be spent on certain work, while it can be (a credit pool counts as expiring soon when it ends before the subscription's next weekly reset); credit on a paid account (an API key or overage) ranks in step 3 however soon it expires, so it is never spent while a subscription has room;
2. subscription windows, within Intakt's share of them;
3. paid usage, overage or API keys, after every subscription with room: up to the owner's weekly cap per account or per install where one is set, otherwise until the balance is gone.

Within a step the ranking spends what would expire first:
- **Soonest reset first.** An account with room in a window that resets in an hour ranks before one whose window resets in four days. Room left near a reset is lost, so it is spent rather than saved. A window at its ceiling has no room, however soon it resets.
- **Then the cheapest tier that fits the job**, then the owner's order as the last tie-break.
- **A paid account never ranks above a subscription with room** for the job's role: the step comes before the reset time, so a build never pays while any subscription still has room for it.

The ranking is run again at every start, so jobs on different accounts run at the same time and an account that comes back (a reset, a lifted block) is used from the next start. The planner sizes parallelism the same way:
- **Parallelism follows the room.** The number of jobs that start follows the total room across the pool, capped by the host's memory, the CI runners and the review capacity, so more Developers never just queue for review or CI. Two limits on pushed heads hold new builds: the review cap on heads waiting for a reviewer or in review, and a higher limit on all heads in flight (twice the review cap by default) that bounds merge conflicts and CI load ([Choosing work](03-choosing-work.md), step 5). The readings, the caps and the resulting number are shown on the dashboard (later).
- **CPU is shared by priority, not by a start gate (owner decision 2026-11-12, issue #1641).** The host reading (memory and CPU per job) gives a baseline count of Developers the host runs comfortably: the CPU part of that reading sets the baseline, while the memory part is the start cap of the bullet above. Every job container gets a CPU weight by its role (cgroup v2 `cpu.weight`, set through the container runtime's CPU shares option): reviews and the merge path high (400), the Developers within the baseline count normal (100), and Developers above it low (25). A check or probe job takes the weight of the work it serves: a build's own check its Developer's weight (100 or 25), a check of a head for review or merge 400, and a probe job 100, because it runs tests like a Developer. A Developer above the baseline may still start as long as memory allows, because memory, not CPU, is what a start must not overrun, and it needs no queue or waiting logic. A weight is a share under contention, not a ban: a low-weight Developer gets all the CPU the others leave idle, and while every job wants CPU, its container as a whole (however many processes it runs) gets 25 parts against a baseline Developer's 100 and a review's 400. So extra Developers mostly run on idle CPU, and on a saturated host they slow the others only by their small share: with three baseline Developers and two extra ones all busy, each baseline Developer keeps 100 of 350 parts, 86% of what it had without them. A review gets everything it asks for while that is within its share: with those five Developers busy, one review holds 400 of 750 parts of the host's processors, far more than a review that waits on model APIs most of the time uses. These shares hold only for jobs with enough runnable work to use them: a job uses at most as many processors as it has runnable processes, so a review with one busy thread uses at most one processor whatever its share, and what a job leaves unused goes to the others. When it asks for more than its share, it is held to it: on a single processor against one busy baseline Developer that is 400 of 500 parts, about 80%. The reason, measured on a build loop running beside Intakt: three Developers used 8.6 of 12 cores running their tests (7 to 8 test processes at once, each a full core) while the review workers used 0.06 cores, waiting on model APIs, with memory and IO pressure near zero; two more Developers would have asked for about 14 cores. The three weights are settings with these defaults, and setup asks for nothing new. Where the host gives no CPU weights, the baseline count is a start cap as before ([Constraints](../04-constraints.md#security-model)).

When an account is spent, blocked at the vendor or backing off while a job runs on it, the job hands off, in a way that depends on the job:
- *A build or any other job but a review* continues on the account the ranking picks next over the whole pool, as above (any vendor, within the tiers its role allows), with no preference for its own vendor. A change of model across vendors is recorded on the task.
- *A review stays with its vendor, and is never continued by another vendor:* a review cut off by a limit before its answer starts streaming starts again on another account of the same vendor its role may use, in the order of use, paid ones included, and only when all of them are out does the panel substitute a reviewer from the same tier of another vendor, with a catch-up review owed ([Reviews](07-reviews.md), as below). Among the substitutes vendor diversity comes first, then the order of use: a vendor not yet reviewing the head is taken first, its paid accounts included, before a subscription of a vendor already on the panel. When every other vendor is already on the panel (the default panel of two vendors), the substitute comes from one of them, in the order of use; the round then has fewer vendors than reviewers, which does not by itself send a protected change to the owner, since approving one on the spot never requires a second vendor ([Merge](08-merge.md#independent-security-review)). When no other vendor has an account the role may use, the round ends `blocked` with the reason. A review cut off by a limit or an outage after its first answer delta has streamed is not started again: its verdict is `blocked` with the cut stream as its reason (an `incomplete-stream` finding), and the usage of the cut call is recorded once as unsettled. A stream that ends before its answer is complete without a limit or an outage behind it is tried once more without streaming, recorded in the ledger like the first try; only when that try is cut too is the verdict `blocked` with the first cut as its reason.

When nothing is allowed, work waits and the board shows each account's cause (a spent window, a vendor-side block, a back-off); when it ends is a reset time and shows only in the admin area ([Owner controls](13-dashboard.md#controls)).

### A limit never loses work

A job that hits a vendor limit (a structured signal, see Limits and accounting) stops at a clean point and its work moves on:
- Its commits are pushed to its work branch, its conversation is kept in the message store (`symfony/ai-doctrine-message-store`), and a hand-off note (what was done, what is left, the open findings) goes to the [shared project memory](10-shared-project-memory.md#hand-off-at-a-limit). The note is written by the orchestrator only, from its own facts (the pushed commits, the task and the findings it holds).
- The next account the ranking allows continues it at once, with the history and the note through the agent's memory input (`MemoryInputProcessor`, plan T43, which still has to replace or avoid the processor's preamble that ranks memory above the system prompt; see [hand-off at a limit](10-shared-project-memory.md#hand-off-at-a-limit)). It does not wait for the first account's reset.
- The reason: a limit is the account's, not the task's, and waiting for a reset while another account has room wastes both the room and the work already paid for.
- A build may continue on another vendor's account within the tiers its role allows, and the model change is recorded on the task. A review is never continued by another vendor: it starts again on another account of the same vendor, and when none has room the substitute and catch-up rules of [Reviews](07-reviews.md) apply.

## Planning


The model planner (machinery, not a role of the team; the [AI engineer](#the-ai-engineer-planned) owns model routing) runs before each job and picks a model and a pace:
- It has the task sized first (the Tech lead's cheap sizing call, formerly the triage call), then chooses the cheapest model that is fit for that size and role. The same call judges each Evidence item of the task as producible in the Developer's sandbox or not ([Definition of Ready](../01-intent.md#definition-of-ready)), and a task with an unproducible item it does not mark as owner-proved (`(owner provides)`) goes back to its author before any build ([Choosing work](03-choosing-work.md), step 3).
- **Auto model choice: the planner decides, a job can ask.** The start model comes from what is known before the job runs: the size estimate and kind of change (docs, a test fix, a new module), whether it touches protected or sensitive paths, earlier failed attempts on the task, and the measured budget and weekly pace. During the run the planner escalates on signals (the same check failing twice, no progress for a set time, a P1 from a reviewer, or a structured upgrade request from the job with its reason) and steps down for mechanical follow-ups (regenerated files, a docs-only rework). A job never picks its own model: left to itself it would pick the strongest one, and a task's text could steer it. Every outcome is recorded per model and size class (cycles to merge, tokens, review rejections), and the planner learns from it which model is enough for which kind of work. A backtest on a loop's first week (150 issues) showed what the start rule should and should not use: the stronger model barely did better on first builds at any size, while it did fix review blockers more often, so the cheaper model starts by default (a project's default start tier becomes strong only through the strong-start rule of the plan option below, "Strong starts against plans"; while the pool has expiring room, first builds without a `model:` label start on the strong tier anyway, see "Expiring room starts first builds on the strong tier" below), a blocking finding or a stall escalates the next rework, a round with only minor findings is reworked on the cheaper model, and size alone is a weak trigger (the size estimate barely predicted the real diff). While that default is the cheaper tier, only sensitive paths, an explicit label, an earlier failed attempt and, for a first build without a `model:` label, expiring room in the pool (below) start on the stronger model. Because past data cannot show what the other model would have done, a small random share of starts goes to the other model, so the gain is measured instead of assumed. That share never includes a start that touches a sensitive or protected path: such a start always runs on the strong tier, because the safety rule comes before any holdout.
- **The routing is the owner's configuration, not code.** Models are named by capability tier per vendor (for example `strong`, `standard`, `light`), and the owner's config maps the tiers to whatever models each account has: an install with one model per vendor collapses the tiers, one with a reasoning model adds a tier. Routing rules are declarative conditions on the facts the planner already has (an issue label such as `model:strong`, kind of change, size estimate, sensitive path patterns, an earlier failed attempt, the previous round's findings, the pacing level), each naming the tier it asks for, with the order and the defaults set per project on top of a global policy. The escalation triggers, the step-down cases, the holdout share and the pacing levels are part of the same policy, so a project can be stricter or cheaper without code changes, and the wizard proposes a policy from the models the logged-in accounts actually offer.
- **A strong-tier plan for a cheaper build, as a measured option.** About a third of the tasks whose first build ran on a cheaper model were later escalated, and a strong build costs about twice a cheaper one. Per project, off by default, the model planner (machinery) schedules one read-only strong-tier call of the Tech lead (read tools only, a turn cap) before a task's first build on a cheaper tier. The Tech lead writes a short plan (the approach, the files, the tests as sentences, the evidence and how to produce it, the pitfalls in the task and its decisions), which the Developer gets fenced as another model's advice, never as the task. It is kept per task revision: a send-back reuses it, a changed task gets a new one, and a build on the strong tier drops the strong-tier call. It is charged to the task, and the strong-tier call is skipped when its reserve does not fit or the window would not admit it. It is the same Tech lead plan as step 4 of [Choosing work](03-choosing-work.md), written on a stronger tier; when the strong-tier call is dropped or skipped, the Tech lead still writes that plan on the regular tier. Either way, posting it for approval still follows step 4, and to the Developer it stays advice.
  - *Arms.* Every first cheaper build records its arm: `plan` when it got one, `control` when it did not. Every first build on the strong tier records the arm `strong`.
  - *Quality trend.* A report per start model and arm (`plan`, `control` and `strong`), with first builds started on expiring room shown apart (their path, see "Expiring room starts first builds on the strong tier" below): builds and send-backs per task, the share escalated to a stronger model, P1 and P2 findings per 100 changed lines, merges without escalation, and tokens per merged task, plan calls included.
  - *Decision rule.* After about 40 tasks in the `plan` arm, keep the plans if their escalated share is at least a third lower than `control`'s and their tokens per merged task at most 15% higher; otherwise turn them off. The strong-start rule below takes precedence: while it has made the project's default start tier strong, this rule never turns the plans off, so the holdout's cheaper first builds keep both arms, `plan` and `control`, and the plan arm stays measured; the rule applies again once the default start tier is back on the cheaper tier. The thresholds are policy, set per project.
  - *Strong starts against plans.* The report and the rule also compare the `plan` arm with the `strong` arm, because comparing `plan` with `control` alone cannot show whether a strong start is as cheap per merged task. When strong starts cost at most the `plan` arm's tokens per merged task and have fewer send-backs per task, the planner's default start tier for that project becomes strong, and a holdout share of first builds stays on the cheaper tier (with and without a plan, which the decision rule above does not turn off meanwhile) so every arm stays measured and the rule can turn back. Measured on this repository over 135 merged issues: strong-tier first builds had 1.01 send-backs per task, 9% escalated and about 780k tokens per merged task; cheaper builds with a strong-tier plan had 1.18 send-backs, 29% escalated and about 800k tokens. The thresholds and the holdout share are policy, set per project.
  - *Once the AI engineer lands.* The decision rule and the strong-start rule above hold until [the AI engineer](#the-ai-engineer-planned) is built (plan T102). From then on, the plan option and the default start tier are routing experiments of that role and its rule governs both ("Every change is an experiment" under [the AI engineer](#the-ai-engineer-planned)): a plan or strong-start experiment targets tokens per merged task, so it is kept when those fall against the arm it replaces without the quality counter-metric worsening (or held for the owner where an arm's tokens come from a job's own log), and the 15% allowance and the "at most the same tokens" condition no longer apply.
- **It spends expiring room on delivery.** Room that would expire unused buys an extra build slot and strong first builds, under the two rules below ("An extra build slot runs on expiring room" and "Expiring room starts first builds on the strong tier"). Reason, measured over 24 hours with two Developers in the build loop Intakt is distilled from: the build slots were busy 78% of the time and the review lane 53%, about half of one account's week would have expired unused, and first builds on the strong model drew 0.67 send-backs per issue against 1.16 on the default model.
- **Build slots and panel size follow the install, derived at each start.** The planner derives the number of build slots and the size of the Code reviewers' panel from the pool and the host: the accounts, the five-hour room and the free memory per job (a single build can need about 5 GB, so a small host cannot run two). A one-account install runs one Developer and one Code reviewer unless the owner raises them, in the owner's controls next to the other budget settings. Reason: a second reviewer from another vendor catches real defects, but with one account it doubles review cost on the same window, and rework is about half of all spend. How a one-reviewer panel adds a second review is in [Reviews](07-reviews.md); the lower split tier on a small pool is in [Choosing work](03-choosing-work.md).
- **A Developer's checks share the host with the other build slots.** Intakt sizes a Developer's gates at once as `max(2, processors / slots)`, at most 8, where the division rounds down (`intdiv`: 11 processors and 3 slots give 3). The processors are the host's online processors; the slots are a setting of the install (`intakt.build.slots`, 1 by default) until the planner derives them. Once extra Developers run on CPU weights (plan T94), the slots in this division are the baseline build slots only: an extra Developer gets the same count as a baseline one, and its low weight, not a smaller count, keeps its gates from crowding the baseline Developers, so starting extra Developers never cuts a baseline Developer's count. The count is a ceiling, never a raise: a build job hands it to its Developer's `bin/check` through `INTAKT_GATE_SLOTS` only when there is more than one slot and the count is below the default `bin/check` sizes from the job's CPU and memory limits (the CPUs, and the 2 GiB memory shares the test workers leave). Otherwise, and always with a single slot, the job hands over nothing and leaves the variable as the job's environment has it (unset unless the job image sets it), so one Developer alone keeps today's default. `bin/check` takes a handed count as it is, so a count above its default would run more gates than the job's memory holds. With today's fixed job limits (2 CPUs, 4 GiB) that default is 1 and the floor of the count is 2, so `intakt.build.slots` does not change a build job's check: the job's CPU limit is what keeps Developers apart, and the count takes effect once jobs get larger limits (no plan task sets them yet). *Planned with [check slots](01-overview.md#check-slots) (T95, #1781):* the job's CPU limit then has two values. The base is these same 2 CPUs, and it is what keeps Developers apart outside a check. The slot's share (the usable processors divided by `check_slots`, never below the base) applies only while the job holds a check slot, and at most `check_slots` jobs have it at once. Memory stays at 4 GiB in both, and with `check_slots` at 0 every job keeps the fixed 2 CPUs and 4 GiB. `bin/check` reads its limits when it starts, so a check with a slot sizes itself from the slot's share and one started without a slot from the base. The count above is still sized from the host's processors and the build slots; only the `bin/check` default it is compared with is then the one sized from the slot's share and 4 GiB, the limits a check with a slot runs under. Under 4 GiB that default is 1 at either value, so the count still hands over nothing. The CPU weight of the job's role (plan T94) applies at both values: the slot raises the job's limit, the weight sets its share when the host is busy. T95 changes only the CPU limit and waits, among other tasks, for T60 and T94 (the full list is in the plan; it waits for T60 for the progress stop); larger memory limits, which would let the count take effect, are no part of it. Reason, measured on Developers that ran without per-job limits: three Developers on 12 processors, each running 8 gates at once, loaded the host to 22 to 28 and took 7 to 9 minutes for one `bin/check --fast`; checks past the agent's 10-minute tool limit went to the background and were polled, and over 12 builds the Developers waited 146 minutes on their own checks against 15 minutes on the model.
- **A Developer's checks end inside their own tool call.** Intakt starts each Developer's agent session with a tool time limit above the slowest expected `bin/check --fast`, set where Intakt starts the session, never by the Developer: a setting of the install (`intakt.build.tool_time_limit_seconds`, 25 minutes by default, below the session's allowance), which a Claude Code session gets as both `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`. Reason: the same measurement as above; checks took 7 to 9 minutes on a shared host, and the runs that went past the agent's 10-minute default tool limit were moved to the background and polled, so the Developers waited on their own checks instead of working.
- **Measured use decides whether a job starts, estimates only what it runs on.** A start is refused when the vendor's measured use is at its ceiling (for example 90% of the five-hour window), never because the planner's estimate of a big job would not fit: that rule left a large rework waiting forever with the window at 5%, and the estimate-based ledger read a window as full that the vendor measured at 5%. A second parallel start needs a margin below the ceiling and a fresher reading. A share stays reserved for reviews so builds cannot starve them.
- **The week is paced, not only each window.** On or behind the weekly pace, each short window may run to its ceiling; ahead of pace, the short-window ceiling drops, so the week's limit is not spent by day three and the owner's own sessions on the same account are not locked out.
- **No reading is not a free pass.** A usage reading is trusted for a limited age (shorter for a second parallel start). While none is trusted, one build runs at a time; after an outage of a few hours the planner's own token accounting refuses again and the owner is notified once.
  - *A window missing from an answer is unused, not a broken reading.* A vendor's usage answer can leave out a window that has seen no use in its current period (observed: after five idle hours the answer carried only the weekly window). A missing window counts as 0% used with no reset time. The check that drops a frozen or wrong reading (a reset time already past, or further ahead than the window's length) applies only to windows present in the answer. An answer with no window at all is no reading, and the rule above applies. Reason: dropping the whole answer left an idle account without a trusted reading; the planner ranks such an account last, so it was never used again and never got the window back, while it had a full fresh week.
  - *A kept reading shows its age.* When the latest probe brought no usable reading and the dashboard falls back to the last one, it shows when that reading was taken. Reason: a stale 100% kept after a reset must be visible as stale, not read as the current state.
- **The pool has expiring room** when the room that would expire unused adds up to more than one typical build. For each account in the pool the build role may use, the planner projects its weekly window to its reset at the account's measured rate of use, and takes the room still left at that reset; the rooms of all these accounts, each counted in typical builds (the share of that account's week a median build used), are summed, and the pool has expiring room while the sum is above one.
- **An extra build slot runs on expiring room.** A build slot beyond the first starts only while both hold: the pool has expiring room (above), and the second vendor's projected week stays below 0.95; when the room is short, it also yields to strong first builds (next rule). A second vendor is a panel vendor other than the build account's: every extra build brings extra reviews from each of them, so a slot that would run one of their weeks out is not started. When the panel has several such vendors (a build on vendor C, reviewers from A and B), each of them is a second vendor and each one's projected week must stay below 0.95: with A at 0.90 and B at 0.97, no extra slot starts. When the panel's only vendor is the build account's own, that vendor stands in for the second. A vendor can have several accounts with their own windows and resets, so its projected week is the lowest of its accounts' projected weeks, over the accounts the review role may use: each account's used fraction of its weekly window, projected at its measured rate to its own reset. Below 0.95 thus means at least one of its accounts is projected to keep room to its reset, so the extra reviews have an account of their own vendor to run on ([order of use](#order-of-use)). When no account of a second vendor has a usable forecast (no trusted reading, or no measured rate yet), the condition does not hold and no extra slot starts, as no reading is not a free pass (below). The rule only adds to the start rules above: memory, the measured-use ceiling and the review share still apply, and a slot already running finishes its build when the room ends. Each second vendor's projected week is shown on the board. When that vendor runs out anyway, the provider-limits rules keep reviews going (a substitute and an owed catch-up review, see [Reviews](07-reviews.md)). This rule does not change the panel: wherever reviewers of two vendors are available, every head keeps reviewers from both, documentation and test changes included. Only an install that has one reviewer (above) is smaller, and [Reviews](07-reviews.md) says how it adds a second review.
- **Expiring room starts first builds on the strong tier.** While the pool has expiring room (above), a task's first build that carries no explicit `model:` label and that the planner would by its own choice start on a cheaper tier starts on the strong tier instead, and records the arm `strong` (as every strong first build does) together with the path `expiring-room`. The planner applies the safety rule first, then a valid `model:` label, and this path only after both ([Labels](04-labels.md): safety rules beat labels, labels beat inference). A first build with an explicit `model:` label of any tier is outside this path, because expiring room is inferred from pace, not an escalation: a build labeled for a cheaper tier (`model:light`, `model:standard`) starts on the tier its label names unless a sensitive path starts it strong, is never drawn into the holdout below, records no path `expiring-room`, is counted in neither the path's `strong` arm nor its holdout arms, and records what it records today. A first build that would start strong anyway (a sensitive or protected path, an explicit label for the strong tier, or a project default start tier that is already strong) is outside this path too: it is never drawn into the holdout below, records no path `expiring-room`, is not counted in the path's `strong` arm, and records what it records today. A random holdout of the first builds on this path stays on a cheaper tier, at the holdout share of the routing policy, and records its arm (`plan` or `control`) as usual, with the same path, so the difference between the tiers keeps being measured. Only builds that were eligible for the same random holdout differ by tier alone, so the report shows the `expiring-room` path apart and every comparison sets arms of the same path against each other: the expiring-room gain is the path's `strong` arm against its own holdout, and the decision rule and the strong-start rule count only first builds outside this path. Reason: lighter tasks can arrive in weeks with room to spare and heavier ones in tight weeks, and a pooled comparison would credit the strong tier with that difference in task mix. The holdout's tier is the cheaper tier the planner would have picked for that build. When the project's default start tier is already strong, the path holds no first build and changes nothing, and the strong-start rule's own holdout on the cheaper tier is the one that keeps measuring. This is a second path to a strong start beside the strong-start rule of [Planning](#planning): it lasts only while the room does, and changes neither the default start tier nor the decision rule that sets it. When the room is short for both, the extra build slot yields first: a slot that would need the room the strong first builds use is not started, and only when even the strong first builds no longer fit do first builds go back to the default tier. Reason: an extra slot only adds a build to a review lane that already waits, while a strong first build spends the same room on fewer send-backs.
- **A window is told by its length and its reset, never by its name.** A vendor that has one window may call it `primary`. A reading's window is the one of its stated length (`window_minutes`), or else by its reset: a reset more than five hours and at most a week ahead is the weekly window, a nearer one the five-hour window. A vendor plugin never maps windows by name.
- **A job that cannot start for a reason of its own never idles a slot:** the slot takes the next job that fits and says why the first waits.
- When an account is out, work moves as [order of use](#order-of-use) and [a limit never loses work](#a-limit-never-loses-work) say: a build continues at once on the next ranked account, a review starts again on another account of its vendor first, then on a substitute of another vendor, recording that a catch-up review is owed. Each switch is shown on the dashboard.

Pacing goal: each window should end near its ceiling. The dashboard shows the forecast, so an owner can see whether capacity is being wasted.

Allowance per task:
- **From its size.** The sizing call puts each task in a size class, and the class (times a factor for the build model) sets its token allowance. A new feature gets more than a small fix from the start.
- **Progress, not spend, ends a build.** A build over its allowance that is still making progress continues. Progress is a commit that changes content (an empty or whitespace-only commit does not count) or a change in which tests fail, compared by test name, not raw output (an output that varies by a word is the same failure). One that makes no progress for a set number of steps ends early, whatever it spent, and keeps its commits. A step waiting for a [check slot](01-overview.md#check-slots) (planned) is not a step without progress, because the wait is the host's, not the build's.
- **A ceiling as backstop**, a few times the allowance for that model, ends a runaway that the progress signal misses, plus a total per task across continuations, so a build that games the progress signal still reaches the owner. A stop for lack of progress saves the work (commits, a patch) exactly as any other hand-over.
- **A failing item backs off alone.** An unexpected failure of one item (a round, a reviewer, a task step, a head the watcher reads) sets that item's next try time and records the cause in the ledger and on its card; the other items go on in the same tick. After a few failures in a row (four, as for a failing bench) the item goes to the Maintainer. The install-wide failure back-off is kept for causes that really are install-wide and never starts from one item's failure. Reason: in the build loop Intakt is distilled from, one record that had lost its pull request failed on every try, each failure put the whole review lane into its failure back-off, and no head of any task was reviewed or merged for 40 minutes.
- **A failure every build shares pauses the project ([shared-failure canary](#shared-failure-canary)).** When builds of different tasks keep failing the same way, the cause is the environment, not the tasks: builds pause and the owner is told once.
- **Every outcome that is not a merge records its cause** (over allowance without progress, ceiling, deadline, failed checks, protected paths, review cycles, conflict, question), so the allowances and limits can be tuned from data.

Limits and accounting:
- **Only structured signals count as "out of budget":** a vendor's usage-exhausted error or an HTTP 429 with its code, never the model's own text. The reset time is parsed from the vendor's error or headers, and the cooldown is kept per quota account, not per agent, so two agents on one account wait together. A subscription plan's usage-exhausted error that names no reset (a spent Codex plan) waits until the latest reset still ahead of a window the account's measured readings show as spent (100 percent or more), else the short default pause; any other failure without a reset (an outage) keeps the short pause. Until the usage readings above are recorded for real accounts, only the demo's replay writes readings, so that wait is the short pause outside the demo.
- **A billing or credit error tells the owner once.** A paid account whose vendor answers with a structured billing or credit error (the balance is gone, a payment failed) is marked unavailable with that cause and left out of the ranking, and the owner gets one notice ("Waiting on you", see [Dashboard](13-dashboard.md#notices-and-waiting-on-you)), since only the owner can top it up. Later failed calls on the same account notify nothing new; the account comes back after the owner's top-up, once a test call or a probe succeeds.
- **A weekly share of 0 pauses the project.** The owner sets a share to 0 to spend nothing on that project: nothing new starts for it, no build and no review, not even a rework or review of an open pull request or the resumption of an interrupted build. A job already running when the share drops finishes, as with any pause, and keeps its commits. Only upkeep that calls no model keeps running: the guard on its main branch and the settling of a job that was killed, so a dead job never blocks an update or counts as running work of another project. Its tasks, branches and pull requests stay as they are and carry on when the share is above 0 again. A share of 0 that still finished open pull requests kept a paused project using both build slots while the project the owner wanted built waited.
- **The forge's hourly API budget keeps a reserve.** A forge's call budget is a budget like a vendor window, read from every answer per installation. Each installation keeps a share of its hour (20% by default, owner-configurable) for essential calls: the CI of a waiting head and of the default branch, merges, pushes, review posts, owner notices and (planned) the scorecard comment of a merge ([journey scoring](#journey-scoring)). Below that share, routine reads (listings beyond each project's one per tick, wait and intake scans, dashboard refreshes) pause until the reset, and essential calls always go on; a head whose essential read the forge's own refusal stopped waits for the reset as a waiting head once that reset time is stored: a forge refusal is ordinary waiting. If storing the reset time fails, that head alone fails and goes through the ordinary per-head back-off of a failed head, while the other heads of the tick go on ([Merge](08-merge.md), "A reserve for essential calls").
- **Budget limits stop model calls, not approved merges.** When an account's limit pauses work, the orchestrator still merges heads that already have every verdict for their exact change, green CI and any owner approval they need, because merging calls no model. It is the same landing step that runs before new reviews ([Merge](08-merge.md)).
- **Subscription CLIs are counted from their own logs.** An API call reports its usage to the Platform, but a subscription CLI in a job reports none to Intakt; it keeps per-message usage in its own session log. After the job, Intakt reads that log from the job's output and settles the job's calls in the same ledger: each message counted once by its message id (a CLI writes one record per content block, and a resumed session copies its history), or by the CLI's own per-turn token counts where it keeps those. The job wrote the log, so it is untrusted input: it is parsed in a separate process without the orchestrator's credentials, from regular files only (no symlinks or other special files), under limits on file size, line length, time and memory, and a model name outside a safe pattern is shown as `invalid`. Because a steered job could rewrite its log, these counts feed allowances, cost reports and outcome records, never a start decision or a ceiling, which come from the vendor's measured use, and never on their own the keeping of an experiment: an experiment whose token figure rests on these counts is held for the owner ("Figures recorded outside the job" under [journey scoring](#journey-scoring)).
- **Cost comes from a dated price table** in the owner's config: list price for subscription accounts (an equivalent, not a bill) and the billed price for API keys. A model missing from the table shows no price, never an estimate.
- **The usage report can be shared.** Tokens and cost per project, vendor, model and role, from the ledger; it shows no limits, plan shares or reset times.
- **Usage is recorded per vendor call** with three states: started, settled, unsettled. Prices are fixed when the call is admitted. A crash in the middle of a call is settled from the vendor's usage later, never billed twice and never lost.

### Shared-failure canary

A broken environment or a broken update of Intakt fails every build the same way. Handled one task at a time, each task is parked, the owner gets one question per task and the budget keeps burning: in the build loop Intakt is distilled from, about 6 hours, 37 builds and no merge. The canary turns that into one pause and one alert.

- **What counts.** A build that fails with an error, and also a stop without one: a no-progress stop (no new commit within the limit) and a stop because the same check failed 3 times. The 2026-11-05 incident began as about 25 such stops across 10 tasks before any build failed with an error.
- **The same error.** Each counted stop gets a normalized error: the error text, or the stop cause for a stop without one, with paths, ids and numbers masked.
- **Held for an hour first.** A counted stop is held before it is handled: its task is not parked, no question or notice about it reaches the owner, nothing is charged, and the task keeps its place in the queue without a new build. A held stop is released one hour after it happened if the canary has not tripped on its error by then, and is then handled like any stop (parked, asked about, charged), at most an hour late. A trip needs its 3 stops within one hour, so every stop it counts is still held when it trips.
- **When it trips.** Builds of at least 3 different tasks of one project fail within an hour with the same normalized error.
- **What it does.** It pauses builds for that project and alerts the owner once. The held stops with that error are never handled: their tasks stay queued, unparked and uncharged, the attempt counts against no allowance, send-back or stall rule, and the owner gets no notice per task, only the one alert. Reviews and merges go on.
- **How it clears.** Only a self-check that passes the [pause-recovery verdict](11-setup.md#the-build-path-self-check) on that project (the next update runs one, and the owner can start one) or the owner's resume ends it, never a timer. A self-check's pass ends it only for the version that passed it: builds resume only on slots running that version, and a rolled-back update leaves the pause in force. Once that version is final (every build slot and the orchestrator run it, and the update can no longer roll back to the version the pause was raised on), the pause is retired for every version; a clean self-check the owner starts outside an update retires it at once. A later update then starts unpaused: its self-check gets only the rollout verdict, and only a new trip of the canary pauses the project again.

Unlike the install-wide failure back-off above, the canary is per project, watches the build lane, and stays until it is cleared. It decides nothing else ([Threat model](14-threat-model.md#updates)).

## Bounded tuning

The maintainer's weekly review ([The maintainer agent](09-maintainer-agent.md)) may tune the loop's flow, never its rules:
- **Only what the owner listed, within its bounds.** The owner's config lists the flow settings that may be tuned and the bounds of each (for example follow-up routing and pick weights). The maintainer agent asks for a value; the orchestrator applies it only when the setting is on the list and the value within its bounds, and refuses anything else. The agent cannot edit that list or the config. Model routing, prompts and context limits are not on it: they belong to [the AI engineer](#the-ai-engineer-planned) (#865).
- **Every tuning is an experiment.** It is recorded in the ledger with the setting, the value before and after, the measured cause, the figure it should move and a review date, and it shows on the dashboard ([Dashboard](13-dashboard.md)). A setting has at most one experiment in effect: the orchestrator refuses a tuning of a setting whose experiment has not ended (kept, undone or superseded), so an undo restores the value in effect before the experiment (the owner's, or one a kept experiment left), never the trial value of another experiment still in effect.
- **Its text is scanned before it is kept.** The cause and the other text of a tuning are model output from a session that read names builders wrote, so plain code redacts them and applies the tuning and records that text only after a secret scan of it completed with no hit; a hit, or a scan that did not complete, applies and records nothing, counts the session as failed for that finding and shows the gap on the dashboard, as for a filed finding ([Threat model](14-threat-model.md#maintainer-agent)).
- **Quality undoes it.** The weekly quality counter-metric has five signals: fixes to recently merged code, reverts, red main, catch-up findings, bugs filed against merged tasks. A bug report counts only once someone with write access to the repository has confirmed it against a merged task, under the confirmation rule of [the dashboard's quality figures](13-dashboard.md#quality-beside-speed), because anyone can open an issue, and an unconfirmed report must not undo a tuning. When a tuning starts, plain code records each signal's baseline, its mean over the four weeks before, with the experiment. Each week the tuning is in effect, plain code compares each signal's count with its own baseline; the counter-metric worsens when any one signal rises above its baseline by more than the margin the owner set for it. Signals are never netted: one that worsens undoes the tuning even when the others improve, because a drop in reverts does not pay for a rise in red main. At the review date the next review keeps it or undoes it from the measured figures.
- **A tuned value never outlives the owner's rules.** The owner's value of a setting is the value in the owner's config: the last value the owner wrote. Only the owner and the orchestrator's tuning write a listed setting, so a value in effect that differs from the owner's value was set by a tuning. One invariant holds: when the value in effect differs from the owner's value, the setting is on the list and the value is within its current bounds. The orchestrator checks it in the same step as every owner write to the setting's value, its bounds or the list, and every tuning write (a trial value or an undo). When the check fails, it restores the owner's value in that step, which is always allowed, and the ledger records it. The check looks only at the value in effect, the owner's value, the list and the bounds, never at which write set the value. An owner write that sets the value makes it the owner's value, so it stands, also when the same write changes the bounds or takes the setting off the list.
  - *The owner's write ends the experiment.* The orchestrator records every owner write to a listed setting's value, its bounds or its place on the list in the ledger, also one that sets the value it already has. Any such write since an experiment started ends it as superseded by the owner, also a write that sets the trial value again, because an owner who changed the value and set it back has decided on it; no quality or review-date undo runs for it. What stays in effect after that follows from the invariant alone: a value still allowed stays, anything else becomes the owner's value.
  - *An undo restores the value before.* A quality undo, or an undo at the review date, of an experiment the owner did not supersede restores the value in effect before the experiment (the owner's, or one a kept experiment left), and the invariant is checked in the same step.
  - *One step, one experiment.* The orchestrator, as the only writer of state, makes the check and the restore as one step, so an owner write that arrives between them is never overwritten: it either comes first and supersedes the experiment, or comes after the restore and stands. A setting has at most one experiment in effect. Every undo, every undo left out and every restore is recorded.
- **What it never touches:** review strictness, checks, the approval rules, the maintainer's own powers and the owner floors. A finding about them, or about any setting not on the list, becomes a ready task.

## The AI engineer (planned)

Model use is Intakt's main cost. Measured on this repository over 72 hours to 2026-11-04: builds used 85% of tokens, reviews 12% and plans 3%, and about 60% of build rounds were rework. The records hold one token total per call, so it cannot be seen whether a build is expensive because of long sessions, large tool outputs or prompt size. Tokens are not the only waste: over 3 days to 2026-11-09 (84 merged pull requests), Developer sessions ran 5,179 check and test commands, about 62 per merged task, and review sessions another 684, on a host whose checks kept most of its cores busy. The AI engineer (`ai_engineer`, [Overview](01-overview.md#the-team)) keeps model and token use as low as it can go without hurting quality: it measures where tokens and check runs go, tunes what it owns as controlled experiments, and keeps only changes that improve the measure they target without raising tokens per merged task, while the quality counter-metric holds (the rule is under "Every change is an experiment" below). Nothing in this section is built yet.

- **Measures.** Every model call records its cached-read, fresh-input and output tokens, its turns and its largest tool outputs, next to the single total it records today. A tool output is recorded as size metadata only (the tool's name, the turn and the output's size in tokens and bytes), never its body, so no file content, command output or credential a tool returned reaches the ledger, the dashboard or the role's weekly report; only the daily journey review below reads transcripts, redacted and fenced. The dashboard shows tokens per merged task by role and model, the cache-read share and context growth per turn ([Dashboard](13-dashboard.md#trends-and-token-measures)).
- **Build measures.** Per project the role also measures the share of first reviewed heads approved, the review rounds to merge and the verify-command runs per task, each over its own cohort so that work which never merges still counts: first reviewed heads approved over every task whose first head was reviewed, merged, closed or abandoned; rounds to merge over the merged tasks, shown beside the count of reviewed tasks closed or abandoned unmerged and their review rounds; and verify-command runs over every build, of any outcome. The brief and the split line ([Choosing work](03-choosing-work.md), steps 3 and 4) are compared before and after they took effect: a task falls before or after a rule by when its first build started. Targeted verify, the two-failure stop and the approach note ([How a build verifies](01-overview.md#how-a-build-verifies)) start with the build job that counts verify-command runs, so they have no "before" and are compared with and without the rule instead: the build job records per build which of the three its instructions carried, and the "without" cohort is the holdout arm of an AI engineer experiment on that one rule (builds whose instructions leave it out), the holdout of "Every change is an experiment" below. Verify-command runs exist only once a brief names a verify command, so they are compared for those three rules only. They are counted by the build job from the build's session log after the job (plan T49) and recorded per build, from the first build that runs under T49; they come from the transcript, so, like every transcript figure, they show trends and never decide an experiment ([journey scoring](#journey-scoring)): the holdout's decision rests on the other measures.
- **What it owns.** The role prompts, focus files and skills; the context limits (turn caps, tool output caps, the scope of a re-review, the size of a briefing); and model routing: the start tier per role and kind of task, escalation, and the size of the Code reviewers' panel by risk. Panel experiments are bounded by [Reviews](07-reviews.md): they only add reviewers on top of the project's fixed core panel or choose among the reviewers added by risk, and never shrink the core panel, lower its quorum, drop the second vendor where both are available, or remove a specialist a trigger calls for; the trigger rules stay protected, so a change to them goes through protected approval. Tuning these moves here from the Maintainer ([The Maintainer](09-maintainer-agent.md)). The routing policy of [Planning](#planning) stays the form the choices take; the role changes its values, and the owner's configuration stays the default. Those values live in the owner's routing configuration of [Planning](#planning), and the role changes them only through the approval of protected changes ([Merge](08-merge.md#approving-protected-changes)), the same as a prompt: routing is part of the role's limits, which it cannot change on its own. Every arm of a routing experiment keeps the strong-start rule of [Planning](#planning) and the [Threat model](14-threat-model.md#triage-and-sizing) (Checks): sensitive paths start on the strong tier whatever `model:` says, an earlier failed attempt still starts there (it counts as an escalation, which can raise a `model:` label's tier), on any other task an explicit `model:*` label still sets the tier it names (so `model:strong` starts there, [Labels](04-labels.md)), and no experiment can change that rule or its order.
- **Every change is an experiment.** A change runs with a holdout that keeps the old prompt or route, as the planner's plan option does above. It is kept only when the measure it targets improves (tokens per merged task, or a journey measure Intakt records outside the job, check runs or check CPU per merged task, see [journey scoring](#journey-scoring)), tokens per merged task do not rise, and the quality counter-metric does not worsen: send-backs per task, escaped defects and red main. Otherwise it is reverted automatically, by plain code that reads the report, not by the role. Plain code keeps a change on its own only when every figure the rule reads was recorded outside the job; where an arm's tokens come from a subscription CLI's own log, a change that would be kept is held for the owner instead ("Figures recorded outside the job" under [journey scoring](#journey-scoring)). The thresholds, the holdout share and the sample size (the minimum merged tasks per arm) are policy, set per project.
- **Protected, and bounded.** Prompts, focus files and skills are protected agent instructions, so a change to one goes through the approval of protected changes ([Merge](08-merge.md#approving-protected-changes)) like any other, and a cheaper prompt cannot drop a safety rule. The approval comes before any use: a candidate prompt, focus file or skill is given to no live job, the trial arm of an experiment included, until its exact text is approved as a protected change, so an experiment only chooses between approved versions. The role never changes review strictness, the checks, the approval rules or its own limits, and it never approves its own change.
- **A weekly session over a deterministic report.** The role has two kinds of session: this weekly one over the token report, and the review of the worst journeys ([journey scoring](#journey-scoring), daily by default). Plain code builds the report from the ledger (the measures above, per arm); the session reads it fenced as data and proposes experiments inside its settings. A finding outside its settings (a check that is slow, a tool that returns too much, a design question) is filed as a follow-up written to meet the [Definition of Ready](../01-intent.md#definition-of-ready), not made as a change by the session. It goes to the follow-up inbox like a review's follow-up ([Reviews](07-reviews.md)), with the session's text redacted, secret-scanned and inside an `<!-- external -->` block ([Threat model](14-threat-model.md#untrusted-text)); a scan hit files nothing. The Tech lead's next call over the inbox files it as a task of its own, merges it into an open task or lets it expire.
  - *Only a person's label starts a build.* A task filed from such a follow-up carries no steering label and inherits none. Like a task from a catch-up review, it is built only once a person with write access sets the label that makes it eligible, checked through the forge's permission API like any steering ([Choosing work](03-choosing-work.md), step 1). Neither the session nor the Tech lead can make it eligible, so the session's text never reaches a build with only model calls in between. Intakt's authorship satisfies only the author and last-editor check of step 1, never the label, and it vouches for nothing the block holds. An edit by an account without write access makes the task ineligible as usual, until a trusted account edits or confirms it.
  - *The block's boundary is kept by plain code.* The filing step, not a model, writes the block: it neutralizes any opening or closing external marker inside the session's text before filing, so the text cannot end its own block, and when a role reads the task the fence around the block uses a boundary the text cannot contain. When the Tech lead merges the follow-up into an open task, plain code appends the text to that task as an external block of its own, never as part of the task's own text. The append does not change the task's trust status: plain code runs the author and last-editor check of [Choosing work](03-choosing-work.md) step 1 on the body revision it appends to, and appends only if the body is still that revision (otherwise it checks again). Intakt's append never counts as the last edit or as a confirmation, so if an account without write access made the last edit before the append, the task stays ineligible until a trusted account edits or confirms it. The merged text is not a trusted edit of that task's body: it adds no instruction, acceptance criterion or decision, changes neither the task's eligibility nor its labels, and every role reads it as data however the task is later edited or labelled.

### Journey scoring

The token ledger shows what a task cost, not how the agents worked. Journey scoring adds that: plain code scores every merged task's journey (every build and review session that led to the merge), and the role reviews the worst of them. These measures stand beside the token ledger and the flow and test-time measures, and replace neither.

- **A collector with no model: each session at hand-back, the task after every merge.** Plain code reads the transcript of each of the task's Developer and Code reviewer sessions (first build, reworks, polish, every review round) when the session hands back and its transcript is copied into the store below, so a session's figures are recorded before its transcript can expire, however long the pull request then waits for a rework or an owner's approval. When the pull request merges, plain code reads no transcript again: it totals the recorded figures of the task's sessions and scores the journey. The figures, per session and for the task, are: check and test invocations by kind (the full suite, the fast check, a single gate, a direct test runner), repeated runs (the same invocation on a tree no edit changed since its last run), the CPU seconds of checks from the check runner's own timing, turns, and tool output size. It records counts, durations and sizes, never transcript text. A transcript is job output, so it is read like a subscription CLI's session log above: in a separate process without the orchestrator's credentials, from regular files only, under limits on size, time and memory. A steered job could rewrite its transcript, so these figures feed scores, the review's choice of journeys and trends, never a start decision, a merge, a ceiling or an experiment's keep decision.
- **Figures recorded outside the job.** Beside the transcript figures, Intakt keeps figures the job cannot rewrite: the slot's process accounting records every check and test process the job starts, by kind (the full suite, the fast check, a single gate, and a direct test runner or static analyser run, that is any of the project's configured check and test commands), with its CPU seconds, into the slot's record and not into any file the job can write, so check CPU includes the CPU of direct test runner and static analyser runs. The slot's process accounting also covers the probe sandbox of a review job ([Reviews](07-reviews.md)), and its runs and CPU are attributed to the review that started it. Rounds and send-backs come from the orchestrator's records. Only independent figures let plain code keep an experiment, so moving repeated work from the check runner to a direct test runner cannot make an arm look better. A measure only a transcript shows (re-reads, verbosity) ranks journeys and shapes proposals, but no experiment can target it, so a job that leaves its repeated runs out of its transcript cannot make its arm look better.
  - *Tokens are independent only on API accounts.* The token source depends on the kind of account. For a call on an API account, the vendor's answer reports the call's usage to the Platform and the orchestrator records it in the ledger, outside the job. A subscription CLI job reports no usage to Intakt: its tokens are read from the session log the job wrote ("Subscription CLIs are counted from their own logs" above), which a steered job could rewrite. The vendor's measured use of a subscription is a used fraction of a window per account, which several jobs and the owner's own sessions can share, so it cannot be split between tasks or arms and is not used to attribute tokens.
  - *Without independent tokens, no automatic keep.* An arm's tokens per merged task are independent only when every model call of its merged tasks, in every build and review session, was reported to the Platform. When that holds for both arms, plain code decides the experiment under the rule above. When it does not hold for an arm (any install that builds or reviews on a subscription), the log-based token figure can still fail the experiment, so a change whose target does not improve, whose tokens rise or whose counter-metric worsens is reverted automatically as usual. It can never keep one: a change that would be kept is taken out of use like a reverted one, and plain code raises one "Waiting on you" card ([Dashboard](13-dashboard.md#notices-and-waiting-on-you)) with each arm's figures and the source of each (process accounting, the orchestrator's records, usage reported to the Platform, or a job's log). The change comes into force only when the owner keeps it there; if the owner drops it, it stays reverted. This holds whether tokens are the experiment's target or only its "do not rise" guard, so an arm that under-reports its tokens gains nothing without the owner.
- **Transcripts are kept apart, and only as long as a review needs them.** At hand-back, the orchestrator copies each Developer and Code reviewer session's transcript out of the job's output into its own store, which no job can read or write. Only the collector process and the AI engineer's journey review (after redaction and the secret scan, fenced) read it; it is never posted, shown on the dashboard or given to another job. It is deleted once the last review that could read it has run (with the model review off, once its figures are recorded), and at the latest after the retention period (14 days by default, a setting below), which runs from the session's hand-back and not from the merge, whatever state the pull request is in; the recorded counts, durations and sizes stay. With the per-merge scorecard and the model review both off, no transcript is kept.
  - *Missing coverage is shown, never scored as zero.* The figures are recorded at hand-back, so a transcript that expires before the merge costs the scorecard nothing. A session can still lack transcript figures: no transcript was kept (both settings were off at its hand-back), or the collector could not read it within its limits. Such a session is marked "transcript figures unavailable" on the scorecard and the dashboard, with the reason (no transcript kept, or a read limit hit). This is a measurement status only: a transcript the collector could not read within its limits is still kept and stays available to the review. The session's transcript-based values (repeated runs, re-reads, verbosity, turns, tool output size) are shown as missing, the journey's values are marked incomplete with the number of sessions they cover, and an incomplete value does not enter the rolling median. The figures recorded outside the job are not affected. A session whose transcript was deleted after its figures were recorded, before the scheduled review, is a different case: its scorecard values stay as they are, complete and in the rolling median. Only its transcript is unavailable. A session that hit the read limit keeps its "transcript figures unavailable" status after deletion, and its missing values stay out of the rolling median. The dashboard shows each session's transcript availability for the review separately from the scorecard's measurement status ("transcript kept", "transcript not kept", "transcript deleted" or "scan hit"); for a deleted one the review skips that session, reads the journey's other transcripts and is told which sessions are missing, and the dashboard shows the gap, as it does for a transcript with a scan hit.
- **A scorecard per merge, in plain code.** From those figures plain code, with no model and no tokens, scores the journey on efficiency (redundant check runs, re-reads of an unchanged file, idle waits), procedure compliance (the role's skill steps followed, as far as code can tell, for example the checks run once after the change rather than after every edit), verbosity (tool output and the session's own text per turn), and rounds and send-backs. Each value shows against the project's rolling median of merged tasks. Within a minute of the merge the scorecard is posted as a comment on the merged pull request and shown on the dashboard ([Dashboard](13-dashboard.md#journey-scorecards)). The comment holds numbers and labels only, never transcript text, and is an essential forge call like a review post (one per merge), so the reserve of the forge's hourly budget never holds it back. Only the forge's own refusal (the hour's budget fully spent) can delay it; it is then posted at the reset, and the dashboard still shows the scorecard at once.
- **A daily review of the worst journeys.** Once a day (the default depth, see the settings below) one AI engineer session reads the worst-scoring journeys merged since its last review in depth, at most the configured number of journeys (five by default), and judges what code cannot: why a run was repeated, whether a skill step was skipped on purpose. The rubric and each transcript reach it fenced as data, the transcripts redacted and secret-scanned first ([Threat model](14-threat-model.md#the-ai-engineers-session-planned)). It drafts proposed changes to prompts, skills and the checks' procedure, each naming its transcript evidence (the session, the turns and what happened there). Proposals come only from those worst-scoring sessions.
- **Proposals are experiments, decided by merge count.** A proposal runs as an experiment with a holdout, as above, and a prompt or skill change goes through the approval of protected changes before any arm uses it. An experiment ends by merge count, not by calendar: once each arm has at least the minimum number of merged tasks (20 by default), so a difference is measurable and one noisy merge never flips a prompt. Plain code keeps it only when the measure it targets, one of the figures recorded outside the job, improves under the rule above, and holds it for the owner instead where an arm's tokens are not such a figure. The role never loosens the checks, review strictness or approval rules to save work: fewer check runs come from repeating a check less, never from checking less on the head that is reviewed.
- **Findings outside its settings become tasks with the numbers.** A cause only a change outside the role's settings can fix (check runner caching, test suite speed, which the opt-in [Test engineer](07-reviews.md#the-test-engineer-planned) also audits where a project enables it) becomes a ready task with the measured numbers. Unlike the weekly session's findings it does not go through the follow-up inbox, so the Tech lead can neither merge it into another task nor let it expire: the filing step (plain code) files it directly as a task of its own, written to meet the [Definition of Ready](../01-intent.md#definition-of-ready), its numbers (runs, CPU seconds, the merges they come from) written by plain code from the recorded figures and the session's text in an `<!-- external -->` block, redacted and secret-scanned (a scan hit files the numbers only), with the boundary rules above. "Ready" means complete for a build, not eligible for one: like every task filed from a session's text, it carries no steering label and is built only once a person with write access sets the label that makes it eligible (*Only a person's label starts a build* above).
- **Settings, with defaults that need no setup.** Every cadence and size is a project setting, kept with the experiment policy above in the owner's configuration, so a first install needs no setup: the per-merge scorecard (on) and its pull request comment (on); the depth of the model review (after every merge, daily, weekly or off; daily); how many worst journeys it reads (five); the minimum merged tasks per experiment arm (20); how long a transcript is kept at most (14 days); and the model for the review (the role's model from routing). With the review off, no journey review session runs and no proposal comes from journeys; the scorecards, if on, still land, and the dashboard shows the review as off. The dashboard shows every setting, and a change takes effect at the next merge or review without a restart. They are part of the role's limits, so the role cannot change them.

## CI (design for later)

Not in the first release. What a merge needs is an independent second run of the checks, on a machine the Developer does not control; the forge's CI is one way to get it, not a requirement. A loop on a private repository's hosted runners spent a month's included minutes in under two days.
- **Where checks run is a per-project setting, and the default needs no setup.** The default is Intakt's own check container: for each head the orchestrator starts a fresh container from the job image, with the project's sidecars (databases) and no network or secrets, runs the project's check command there, and posts the result to the pull request as a commit status itself, from outside the container, so the code under test cannot write its own result. A fresh install therefore needs no CI plan, runner or forge workflow. Opt-in: the forge's CI (hosted runners, or the owner's self-hosted ones), alone or as well, for example for pull requests from outside contributors. When more than one is set, each is a required status.
- **Forge CI capacity is a budget** like a vendor window, when the forge's CI is in use:
  - **Minutes are a budget input.** Per project, the plan's included minutes, their reset date and the used share are read from the forge's billing API where it has one; for self-hosted runners, their count and busy share. The planner treats CI like a vendor window: a forecast that runs out before the reset slows the admission of new builds first, before the reviews of heads already pushed.
  - **Fewer runs per change.** Each push costs a run, so a newer push cancels the runs of the head it replaces, red-CI send-backs are capped (see [Reviews](07-reviews.md)), and the pre-push check catches what it can before a push. A failed run is retried only when its failure looks transient, at most once per head, and a failure that names a gate, test or step goes back to the Developer with no retry (a test the flaky record names shares the head's one retry); Intakt may cancel a run that can no longer matter, and a run it cancelled itself is not waited on ([Merge](08-merge.md#waiting-for-ci)). An automatic retry counts against this budget like any run; a missed-CI nudge starts the run the head never got, not a second one.
  - **Spent minutes are a cause, not a wait.** A run refused for spent minutes, or with no runner to take it, is recorded with its cause. Heads wait without a slot, and the owner gets one card (raise the limit, add a runner, or wait for the reset) with the reset date.
  - **Paid minutes are capped:** minutes billed past the plan count against the owner's CI spend cap and never start silently. Unlike paid vendor accounts, CI minutes have no uncapped mode.
  - **The dashboard shows** minutes used, the forecast at reset and minutes per merge.
