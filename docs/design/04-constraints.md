# Constraints

## Platform (decided 2026-10-26)

- **PHP and Symfony.** Intakt is built on PHP 8.5 (8.5.12 or later) and Symfony: Messenger workers and Scheduler for the lanes and timers (all state in the database, so workers restart freely), the Process component and the Docker Engine API (over its socket, through HttpClient) for jobs, FrankenPHP with Mercure for the live dashboard, and Symfony AI (Platform, Agent, the MCP SDK) for Intakt's own model calls, the API-only vendor and MCP access for agents. Performance is not a constraint: the orchestrator mostly waits on jobs, the forge and git. Intakt uses every Symfony AI component it can, deliberately and early, to find the beta's bugs while they can still be fixed before 1.0: the Platform with several real providers at once (the model catalog, streaming, structured output for verdicts, token usage for the budget, error and rate-limit handling), the Agent for every role (tools, tool effect hints, the message store), the Store for project memory, the AI Bundle for configuration, Mate where it fits, and the MCP Bundle and PHP MCP SDK as both server and client. Edge cases are exercised on purpose (long runs, parallel calls, provider outages, oversized contexts, malformed tool calls). Intakt keeps its own small vendor interface on top, so a provider or the library can still be swapped, and pins exact versions.
- **A long-lived kernel.** The HTTP side (dashboard, local API, MCP server) runs in FrankenPHP worker mode, one booted kernel serving many requests; Messenger consumers and the Scheduler are separate long-running processes. Services keep no per-request state, and anything that must be cleared between requests implements `ResetInterface`; process-wide settings (`umask()`, `setlocale()`) are never changed per request, and `$_ENV` is treated as not reset between requests; Doctrine's entity manager is reset after every request and message; workers restart after a set number of requests and when they pass a memory ceiling. A test sends many requests through one booted kernel and checks that nothing leaks between them.
- **Upstream bugs are reported, with the owner's OK.** A job that hits a likely Symfony AI or MCP SDK bug writes a minimal reproduction (a failing test or a short script) and a draft report with the exact versions into `upstream/`; the dashboard shows it as a chore, and it is posted to the upstream tracker only after the owner approves that report (and a small, clear fix may go upstream as a pull request the same way). Each new pre-release is run against the collected reproductions to see what was fixed. Plugins are PHP classes behind the same small interfaces.
- **First release: the review loop** as a standalone Symfony app (the Symfony AI & MCP Hackathon entry, with a public sample project and API keys rather than subscriptions).

## Security model

- **Secrets stay in the orchestrator.** The forge token, signing key and vendor API keys never enter a job. A subscription account reaches a job only as that one account's credential: its vendor's automation token where the vendor offers one, passed by the orchestrator, otherwise its login file mounted read-only, never a writable config dir ([Budget and model planner](05-architecture/06-budget-and-model-planner.md)).
- **Cached credentials stay private.** Short-lived tokens the orchestrator or the dashboard caches live in a directory only their own user can read, never under a directory a web server serves, and are read with symlink and owner checks.
- **Jobs are disposable.** A fresh container per job, read-only root filesystem, a tmpfs work area, no host mounts beyond its inputs, resource limits, and an egress allowlist.
- **Every job has its own memory limit inside the shared one.** A build or CI job that runs away is killed alone, by its own limit, and recorded with cause `oom`, instead of exhausting a shared limit and taking unrelated jobs with it (one runaway test killed a CI job and a Developer job together). A job's limit is set from measured peaks, overcommitted on purpose, with the shared limit as the outer bound.
- **A runaway command fails fast, and a memory kill is told.** A job's own limit is not enough: a Developer's test printed exception traces with their arguments, the traces held the test framework's whole object graph and grew past 2 GB in seconds, and with no limit in the runtime the job's limit killed the test and the agent with it. The only record was a ledger line, so the next attempt continued the saved work, ran the same test and was killed again, each kill losing the whole session. So:
  - *Commands have their own memory group.* Inside each job, the agent's commands run in a memory group of their own below the job's limit. A runaway command is killed alone; the agent survives and gets the kill as the command's result, with the killed process named.
  - *The runtime has a limit by default.* A `language` plugin ([Plugins](05-architecture/02-plugins.md)) sets a runtime memory limit for the processes it starts (`memory_limit` for PHP, `--max-old-space-size` for Node; none for a runtime without such a limit), so a runaway usually ends with the runtime's own error before any group is reached. The default is the larger of 512 MB and twice the memory peak of the project's first green check on main, measured at setup, so it needs no setup and grows with a large project instead of failing it (Intakt's own check passes under 256 MB, with 179 MB for its test run). A limit the project sets itself (in its test runner config, a tool option) wins; a setting in the project file overrides the default; the dashboard shows the value in use. The runtime limit alone does not cover every command, since some tools lift it themselves (Rector, PHPArkitect and Composer for PHP); the memory group does.
  - *A memory kill is told and handed over.* A job killed for memory posts one comment on its task naming the process and the step, and the next attempt gets that note. A second memory kill of the same task goes to the [Maintainer](05-architecture/09-maintainer-agent.md) instead of another attempt; the owner is alerted only when the Maintainer cannot resolve it. On the dashboard it is status, not an owner action.
  - *A host without nested groups.* Where the host cannot give a job nested memory groups (no cgroup v2 delegation, some desktop container hosts), the commands share the job's own limit, so a runaway command ends the whole job. The runtime limit, the comment, the note and the hand-over still apply, and setup says once that on this host a runaway command can end the whole job.
- **Extra builders mostly use idle CPU.** Each job container gets a CPU weight by its role, so builders above the host's baseline count run mainly on CPU the baseline builders and the reviews leave idle; when every job wants CPU, an extra builder gets only a small share (25 against a baseline builder's 100 and a review's 400), so it slows the others only a little ([Budget and model planner](05-architecture/06-budget-and-model-planner.md)).
  - *A host without CPU weights.* Where the host gives no CPU weights (no cgroup v2 delegation, as for nested groups above), Intakt falls back to the start cap of before: no builder starts above the baseline count. Setup says so once, and asks for nothing.
- **Credentials settle before use.** A freshly issued forge token can be refused for a moment (a forge's git endpoint answered "repository not found" for about a second after each App token was minted, and a fetch that triggered the refresh halted the loop every hour): tokens are rotated early, the previous valid token is used until the new one is confirmed, and a first token is probed before use. Transient network failures of git and of forge API calls are retried a few times and keep the tool's own error text (redacted): a git failure that outlasts the retries fails the job, not the whole loop; a forge API failure (a network error or HTTP 5xx on a request that is safe to repeat) is retried for about a minute, and one that outlasts that makes only its project wait a short back-off, like a rate limit, with no halt, no owner notification and the other projects going on; a 4xx answer or a request that is not safe to repeat fails at once. Only a long outage (on the order of 30 minutes for one project), not a single failure, halts that project and notifies the owner with the last error, redacted; only integrity failures halt at once.
- **Projects are isolated by allow-list, not deny-list.** Several projects on one install never share a job user, a temporary directory or a readable path. Each project's files are readable only by that project's own users (owner and group, nothing for others), and setup fails if any path of one project is readable by another project's users. A deny list fails open: a check that listed the paths other projects must not read missed a release directory and a repository mirror that every user could read, so a public project's build could have copied a private project's source into its pull request.
- **A job's scope is fixed for its whole run.** Which project a review job serves is decided once, under the same lock that runs the job, and checked again at every privileged step against the calling user. A mismatch fails the job; it never counts as a check that was "off". In a loop where a timer could rewrite the shared "current project" while a review ran, the review's checks were refused and the boot check read as off, so changes could have merged without it.
- **Test databases for every supported engine.** A project that supports several databases gets an isolated, least-privilege test database per job slot on each engine, reset before each job (data, settings and engine-level objects such as roles' settings and large objects); a database server that is down at an update is skipped with a warning, never a reason to roll the update back.
- **Hand-back is data, not code.** The orchestrator reads a git bundle and a JSON file. It verifies the bundle's commits build on the expected base, re-signs them itself, and holds changes to protected paths (gates, CI, agent instructions, dependency policy) for an approval: Intakt approves on the spot when the mechanical checks pass and the Security engineer's security review and penetration test clear the change, and otherwise asks the owner; a change that hits one of the two hard floors (the approval system itself, and secrets and permissions) always goes to the owner (see [Merge](05-architecture/08-merge.md#approving-protected-changes)).
- **Dependency changes are policy-checked**, per package ecosystem (Composer, npm, Go modules, Python, Cargo, ...), by a plugin that reads the manifest and the lock file:
  - *Routine, merged like any change:* version bumps within the same source; new packages from **trusted vendors** (Composer vendors such as `symfony/` and `doctrine/`, npm scopes such as `@angular/`, Go module path prefixes), resolved from the trusted registries with lock entries that pass the same source checks; and the wiring for a module the same change adds (for example an autoload namespace pointing at that module's own new directory), when it matches the project's module pattern and touches nothing the gates load.
  - *Owner approval through the pull-request flow:* any other new package, a changed or removed source, registry or autoload entry, scripts and install hooks, and every other manifest setting. The pull request lists the new packages and their sources at the top, so the approval is a glance.
  - *Where it is set:* trusted vendors and registries are set **globally** in the owner's config (they hold for every project) and **per project** (added to the global list, or replacing it for a project that needs a stricter set). The module pattern is per project. Like all routing, these live in the owner's config, never in the repository, so a build cannot widen them. A vendor match is exact on the vendor segment (`symfony/` never matches `symfony-evil/`). Trust in a vendor is not trust in a commit either: forges serve a fork's commits through the upstream repository's URLs, so a new package's locked commit must be that of an upstream release tag for its version. The repository's owner must be the vendor exactly (a look-alike account such as `sym-fony` is not `symfony`), the download URL must be the forge's archive of exactly that commit (a lock change that only swaps the URL is checked like a new version), and the same tag check applies to every version bump. Trust in a vendor is not trust in what a package loads: a new package counts as routine only if its own autoloading stays inside its vendor's namespace and runs no code on load (no autoloaded files, no class maps), because the checks and gates load the project's autoloader in-process; a module's own wiring is routine only when a static read of the wired file shows nothing but that module's class.
- **The check runs in its own container** and a fresh clone (it may copy a saved install with the same lock files and platform into it) and no access to the build job's files.
- **One image for the builder and CI.** The builder's sandbox, the pre-push check and the CI jobs that run the check run the same image, built from one definition (on the forge's hosted or self-hosted runners those jobs run the check inside that image as a container, not on the runner's own tools), so a check that passes before the push does not fail in CI for a missing tool. A test that needs a tool declares it in `docs/architecture/requirements.md` (another project, in its own requirements page), and a missing tool fails the builder's pre-push check with the cause `environment`, never first in CI ([Reviews](05-architecture/07-reviews.md)).
- **Two kinds of config.** The owner's config in the orchestrator holds credentials, vendors, models, prompts, the check commands and the protected paths. A project file in the repository may set delivery policy (labels, size limits, plan approval, serial mode) and the runtime memory limit of its jobs' commands (see above), and nothing else: a key in it that would route credentials, models or prompts makes the project refuse to run until the owner removes it. A change to the check commands is always an owner change.
- **Project text is config, with neutral defaults.** Text Intakt sends to a project's jobs or posts on its forge (prompts, send-backs, the command that regenerates generated files, the files quoted to the Code reviewers, the Tech lead's readiness and sizing notes, design notes) comes from that project's config, and every default names no project. A test renders each prompt and template for each configured project and fails when one project's names or values appear in another's, since such text steers jobs toward files that do not exist and leaks one project into another.
- **Local setup is opt-in.** Jobs never load the owner's own hooks, settings or keys. A project can opt in to named, read-only pieces of a local setup (for example a hooks directory) for its jobs, after the wizard has shown what that exposes.

## Vendor terms

Some vendors' consumer subscriptions restrict automated or unattended use. Intakt will document, per vendor plugin, which plans its terms allow for this kind of use, show it at setup next to each account, and leave the choice to the owner: subscriptions and API keys are equally configurable, and the wizard never hides one of them. For ChatGPT plans, check OpenAI's sign-in route for third-party apps, which has per-app usage caps; if it applies, those caps are one more budget input for the model planner.

## Code standards

- **Gates start from the owner's existing PHP gate code** (MIT): code style, PHPStan at max with strict rules and no baseline; a shrink-only ratchet list per new rule while its cleanup runs (see [Ratchet lists](#ratchet-lists-for-a-new-rule-decided-2026-11-06)), Rector, module boundaries (PHPArkitect: modules meet only through their `Contract` namespace), the comment rule, `composer audit`, gitleaks on files and on the change's commits, Conventional Commit subjects and the long-dash check.
- **A lean start.** The first set is style, static analysis, Rector, module boundaries, the comment rule, tests, audit, secrets, commit subjects and long dashes. The comment rule joined the first set on 2026-10-27, so that "comments say why, never what" is enforced from the first task, not only asked for. The documentation, index and diagram gates come once there are docs to protect. Any later gate needs an escaped defect it would have caught (see Lessons), except the product's security checks per layer, which the owner decided on 2026-11-04 ([decision 25](06-decisions.md)).
- **Coding rules are gate rules (decided 2026-11-04).** A coding guideline a tool can check is enforced by a gate of `bin/check`, with a failure message that explains the rule; prose in `AGENTS.md` and [How code reads](02-principles.md#how-code-reads) is for judgement only (SOLID, DRY, no overengineering, naming a tool cannot judge, comments that give a reason). A recurring checkable finding kind becomes a proposed check, not prose (see [Principles](02-principles.md)).
- **Modules with contracts.** Each plugin kind (forge, vendor, notifier, work source, gate) and each core area is a module whose `Contract` namespace is its only public surface, listed in one module list.
- **Tasks follow the loop's own conventions from the first task:** acceptance criteria and an Evidence section, `Waits for #n` dependencies, `Source:` lines for split parts, the owner's decisions in the description, the size contract, all checked by the [Definition of Ready](01-intent.md#definition-of-ready).
- **Protected paths have a code owner.** Today `.github/CODEOWNERS` names the owner for `config/gates/`, `.github/` (CI), `bin/check`, `bin/instance`, `bin/probe` and `AGENTS.md`, so every one of those needs the owner's review once the branch ruleset requiring code-owner review is on (it is turned on when the repository goes public; a private repository on the free plan cannot enforce it). The owner narrows it to the owner-only files in the task that implements approval on the spot (plan T80, see [Merge](05-architecture/08-merge.md#approving-protected-changes)); only then does approval on the spot apply under the ruleset. The protected-path list and the approval rules are not files in the repository: they live in the owner's config in the orchestrator (see "Two kinds of config"), and the code that applies the approval rules joins the protected paths in that task.
- **Portable storage:** SQLite by default, with the persistence tests also run on MySQL, MariaDB and PostgreSQL.
- **Done means exercised on a running install**, with the evidence in the pull request (see the [Definition of Done](01-intent.md#definition-of-done)).
- **Releases:** Conventional Commits, release notes generated from commit types, semantic versions, signed tags. Actions pinned to commit SHAs; a fail-closed secret scan before every push.
- **The design becomes a folder** (`docs/design/`: intent, principles, goals and non-goals, constraints, architecture, decisions, design calls open to correction, left to the Developer) when the repository is bootstrapped; this file is its source.

## Ratchet lists for a new rule (decided 2026-11-06)

A new gate rule is switched on the day it lands, also while the repository still breaks it in places, so that new work cannot add violations while the old ones are fixed. "No baseline" still holds: Intakt never computes the known findings from the target branch on each run and fails only on new ones, because then the debt is listed nowhere and never has to be paid. Instead:

- **A list per rule, only while its cleanup runs.** A rule whose cleanup needs more than one build may land with a ratchet list: the exact violations on the default branch when the rule lands (file, identifier, message), one checked-in file per rule, outside `config/gates/`. A cleanup that fits in one build still lands with the rule and no list (for example: fix every deprecated use in the same change).
- **PHPStan rules first.** The rules waiting for a list are PHPStan rules, so a list is a PHPStan baseline file per rule, generated with `--generate-baseline` (entries with `identifier`, `path`, the message pattern and `count`) and included from `config/gates/phpstan.neon`. PHPStan already fails on an entry that matches nothing (`reportUnmatchedIgnoredErrors`, on by default); the gate adds only the shrink-only check. Another tool gets a list only when one of its rules needs one.
- **Shrink-only.** The gate fails on a violation not in the list, on a list entry that no longer matches anything, and on any list change that is not a shrink: compared with the target branch's list, no entry may be added, no `count` may rise, and no message pattern or path may change (a widened pattern such as `#.*#` would let anything in). Only deleting entries and lowering counts passes. A list arrives only with its rule, in the change to `config/gates/phpstan.neon` that adds the rule, which is protected anyway; after that the list needs no protected path, and a cleanup pull request that deletes entries needs no owner approval.
- **Moving a file means fixing it.** Moving or renaming a file with a listed violation makes the old entry stop matching and the moved violation count as new, so the move fixes it.
- **The cleanup is planned with the rule.** Every rule with a list has one open cleanup issue, named in the list file's header, with the rule's milestone and priority, never a later one, so the cleanup is picked with the rule's own work and the list cannot become a permanent baseline. When the Tech lead splits a rule issue, the first part lands the rule with its list, and the cleanup becomes one or more `ready` parts that are not blocked by the rule part; their pull requests only change `src/` and delete list entries (a cleanup part that merges before the rule part only fixes code, and the rule part's list holds what is left). A rule issue that fits one build keeps the rule and the whole cleanup in one change and gets no list ([Choosing work](05-architecture/03-choosing-work.md)). This split rule is the target for the Tech lead's sizing prompt, which belongs to the build loop's configuration outside this repository and does not state it yet. The rule's umbrella closes only when its list is empty and deleted, together with its include, which only tightens the rules.

## Documentation

Intakt documents itself the way it asks projects to be documented, in the same change as the code:
- **Two audiences.** Every user-visible feature has a plain user guide page (`docs/user/`: what it does, how to set it up, what to do when it goes wrong, for an owner who is not a developer) and a technical page (`docs/architecture/`: how it works, the data it keeps, its limits, with a flow diagram where the flow is not obvious). A task that adds or changes such a feature names both pages in its description, and a review checks they were written or updated.
- **Same change, no drift.** A pull request that changes behavior updates the pages that describe it; a documentation gate fails when code names (commands, config keys, events, routes) referenced by the docs no longer exist, or new public ones are undocumented.
- **Verified claims.** Docs state only what the code does; examples are run (commands with their real output, config that loads), and statements about limits or numbers cite where they come from.
- **Plain style:** US English, short sentences, no filler, no em-dashes.
- **Generated indexes** of modules, commands, config keys and docs pages are kept in the repository for agents and readers, regenerated by a command and checked by the gate.
- **The README** takes a newcomer from `git clone` to a running demo in five minutes and links the user guide and the technical pages; the docs are published as a site from `docs/` at the public release.
