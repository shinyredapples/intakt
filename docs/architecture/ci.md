## CI

`.github/workflows/ci.yml` runs on every pull request and every push to main, with a read-only token and no secrets. Its four jobs are `check` (`bin/check`), `changes` (whether a pull request touches persistence), `persistence` (the engines, see [Persistence](persistence.md)) and `image` (`docker build --tag intakt:ci .`, nothing pushed, then `docker/smoke-test.sh intakt:ci` on the host, which prints both digests; see [Container image](container-image.md)). The workflow fails when any of its jobs fails; the `image` job fails when the build fails or the script exits non-zero (a failed check or a wrong call).

`.github/workflows/first-start.yml` also runs on every pull request and every push to main, with a read-only token and no secrets. Its one job, `first-start`, runs `docker/verify-first-start.sh`, a smoke check of the demo's first start ([The demo with docker compose](demo-with-docker-compose.md)). It shares the runner and fork guard below. It runs the script directly on the host, not in the CI image, so the CI image and job-container bullets are about `ci.yml` only.

- **Runner:** every job of both workflows has `runs-on: ${{ fromJSON(vars.CI_RUNS_ON || '"ubuntu-24.04"') }}`. With the repository variable `CI_RUNS_ON` unset, CI runs on GitHub's `ubuntu-24.04`. Set to a JSON label list, for example `["self-hosted","linux","x64","intakt-ci"]`, it runs on that self-hosted runner. A self-hosted runner must be ephemeral (a clean machine state for every job, registered `--ephemeral`) with no network path to the owner's other machines, and its host needs Docker for the runner's user, unprivileged user namespaces and no AppArmor profile blocking mount; a persistent self-hosted runner is not supported ([setup and reasons](../user/self-hosted-ci.md)). A `runs-on` taken from a variable is one the planned workflow scan cannot read, so for this repository it counts as risky ([Merge](../design/05-architecture/08-merge.md)).
- **Fork guard:** every job's `if` in both workflows is exactly `github.event.pull_request.head.repo.full_name == github.repository || github.event_name == 'push'`, so a pull request from a fork never runs, on either kind of runner. The guard is kept to this one exact form, with no other job condition, so a workflow scan can verify it line by line; the other conditions therefore live in the steps: `changes` answers `true` on a push, and `persistence` skips its steps and starts no database service (an empty service image) when the answer is not `true`. A failing `changes` job skips the engines and fails the run.
- **The CI image:** the `image` job is an exception, as `first-start` is: it builds the application image from the repository's `Dockerfile` and runs `docker/smoke-test.sh` on the host, not in the CI image; `changes` also runs `.github/ci/persistence-needed.sh` directly on the host. Only the `check` and `persistence` jobs run Intakt's code in the image built from `.github/ci/Dockerfile` (`dunglas/frankenphp:1.13.4-php8.5-trixie` pinned by digest, frankenphp without file capabilities, plus git, jq, unzip, python3, iproute2, the `ext-*` entries of `composer.json` that the base lacks, `pdo_mysql` and `pdo_pgsql` (only the persistence group uses them), Composer 2.11.1 and gitleaks 8.30.1, copied from stages built on the `composer` image and gitleaks' GHCR image, each pinned by tag and digest, and a uid 1000 user). It loads `config/gates/php/check.ini` as `zz-check.ini` in its `conf.d`, so the jobs run with the check-time settings (`memory_limit=-1`, `zend.assertions=1`, `E_ALL`); there is no separate CI ini. Its build fails below PHP 8.5.12 or if any extension of the profile is still missing, and checks frankenphp, PHP, `pdo_mysql`, `pdo_pgsql`, Composer and gitleaks. The `docker` entry of `.github/dependabot.yml` updates the `FROM` images of this Dockerfile and the app's `Dockerfile` weekly (prefix `build`), tag and digest together, once a release is 3 days old (7 for a major); a gitleaks update also needs `PINNED_VERSION` in `config/gates/src/GitleaksGate.php` moved, or the `secrets` gate and its test fail. `.github/ci/build-image.sh` builds it with the checkout as context (`--file .github/ci/Dockerfile .`) and tags it by a hash of the Dockerfile, `composer.json` and the check ini, and builds only when no image of that tag exists, so a clean runner state that already holds the image reuses it, while a profile change builds a new image and an image of an older profile is not reused. The reuse is safe only because a self-hosted runner is ephemeral: a pull request's job could tag any image with main's hash, and only a clean state for every job keeps that from reaching a later one. The jobs run it with `--user 1000:1000` and the checkout mounted read-only; `.github/ci/run-on-copy.sh` installs the locked dependencies on a copy in the home directory and runs the command there. No job has a job container, and no container gets the Docker socket.
- **`check`:** runs `bin/check` in the CI image, with `--base` set to the pull request's target branch, or to `origin/main` on a push, so a pull request that leaves the gate code alone skips the slow gate tests and every push to main runs them. The gate tests run processes in a new user namespace and mount a fresh `/proc` there, so the container gets `.github/ci/seccomp-userns.json` (Docker's default seccomp profile plus `unshare` only with `CLONE_NEWUSER`, and `mount`) and `systempaths=unconfined` (the kernel refuses a new `/proc` in a user namespace while Docker's masks cover parts of the old one). On GitHub-hosted runners only, it also gets `apparmor=unconfined` (Docker's AppArmor profile forbids mount) and the job sets the `kernel.apparmor_restrict_unprivileged_userns=0` sysctl (those runners are discarded after the job).
- **Job containers:** the `check` job and each persistence engine run with `/home/ci` (the working copy and `vendor/`) and `/tmp` on tmpfs, so nothing they write touches the runner's disk, and with Composer's cache (`COMPOSER_CACHE_DIR=/composer-cache`) on the runner's `intakt-composer-cache` Docker volume, mounted read-only with `COMPOSER_CACHE_READ_ONLY=1` (without that setting Composer ignores a cache it cannot write). The volume is empty unless the runner's clean state provides it filled for the default branch's lock; Composer then downloads what it lacks, as before, and caches nothing. No locked package carries a checksum (`"shasum": ""` in `composer.lock`), so a planted archive in the cache would be installed unchecked by a later job, main's included. The guard is the runner's clean state per job: whatever a job writes to the volume is gone before the next job starts. The read-only mount only keeps main's own jobs from writing to it by accident; a pull request runs its own `ci.yml` and could drop it.
- **`persistence`:** one job with a service container per engine, each database's data directory on a tmpfs (the databases are throwaway, so disk syncs only cost time). One step runs the three engines at once (`.github/ci/persistence-engines.sh`, covered by `tests/Gates/PersistenceEnginesTest.php`), each in the CI image on the network the runner creates for the job's services (`job.services.<engine>.network`), reaching its database by the service name `mysql`, `mariadb` or `postgresql`; no port is published. The step runs only once the CI image was built; every engine runs to its end even when another fails, its output in its own log group, and the step fails when any engine failed. One job rather than a matrix, because each job on an ephemeral runner is a full machine reset and takes a runner of its own.
