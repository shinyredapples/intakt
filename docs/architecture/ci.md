## CI

`.github/workflows/journeys.yml` runs the journeys on main, nightly and on demand (`gh workflow run journeys.yml`), never on a pull request, and a red run files or updates one urgent task ([Journeys](journeys.md)). Its `journeys` job uses the runner and CI image below; its `alarm` job uses the CI image on GitHub's runner (the `journeys.yml` bullet).

`.github/workflows/ci.yml` runs on every pull request and every push to main, with a read-only token and no secrets except the optional read-only Docker Hub login below. Its four jobs are `check` (`bin/check`), `changes` (whether a pull request touches persistence), `persistence` (the engines, see [Persistence](persistence.md)) and `image` (`docker build --tag intakt:ci .`, nothing pushed, then `docker/smoke-test.sh intakt:ci` on the host, which prints both digests, see [Container image](container-image.md), and `docker/verify-first-start.sh intakt:ci`, a smoke check of the demo's first start, see [The demo with docker compose](demo-with-docker-compose.md), and when needed the upgrade check below). The app image is built once per run: no other job or workflow that runs on a pull request or a push to main builds it. The first-start check also runs after a failed smoke test, so a run reports both, and is skipped when the build failed. The workflow fails when any of its jobs fails; the `image` job fails when the build fails or any of its scripts exits non-zero (a failed check or a wrong call). `tests/Gates/AppImageWorkflowTest.php` checks the single build, the scripts on `intakt:ci` in the `image` job only, the conditions of the first-start and upgrade steps, the upgrade decision and the fork guard.

**The upgrade check** (`docker/verify-upgrade.sh <head image> <base commit>`) proves that a new version starts on data the version before it wrote, and that going back works the way [Your data](../guide/your-data.md#upgrading) tells users. It builds the base's image from `git archive` of the base commit, starts it on a fresh volume seeded exactly as the first-start check seeds it (it sources that script's functions), waits until Docker reports the container healthy and records the facts the head must still read: the sample project's panel, the project file and the MCP owner token. It then copies the volume, starts `intakt:ci` on the copy (the migrations run in the entrypoint; `doctrine:migrations:up-to-date` must pass, the container must become healthy and the facts must read the same), and finally starts the base's image again on the untouched original and reads the facts once more. The base never starts on a volume the head migrated, because migrations only go forward. A step of the `image` job decides whether the check runs, so the job reports on every pull request: on a pull request the base is the merge base and `.github/ci/upgrade-needed.sh` answers yes when the change touches `migrations/`, a class with a Doctrine attribute (`#[ORM\`) on either side, the `Dockerfile`, `docker/` or `composer.lock` (`tests/Gates/UpgradeNeededTest.php`). Any other change, for example a stored enum value used through `enumType:` or the Doctrine configuration under `config/`, is not checked on its pull request, only on main after the merge: every push to main runs the check, with the head's first parent (`HEAD~1`) as the base. It runs after a failed smoke test too and is skipped when the build failed; it needs no secret. `tests/Core/Dashboard/Infrastructure/VerifyUpgradeScriptTest.php` runs it with a fake `docker` and `git`. The checkout fetches the full history for the base, and the job's limit is 35 minutes for the second build and the three starts.

`.github/workflows/highlights.yml` publishes the assembled highlights page to GitHub Pages on every push to main and by hand; it is no check and never runs for a pull request, and its `if:` guard limits both jobs to this repository and to main ([The published highlights page](highlights-page.md)). Its `build` job runs on GitHub's `ubuntu-24.04` without the Docker Hub login. It also runs Intakt's code (`bin/highlights`) in the CI image, which it gets through `.github/actions/ci-image`, as the `check`, `persistence` and `journeys` jobs do.

`.github/workflows/release-image.yml` runs when a release tag `v*` is pushed, and on demand for an existing tag (`gh workflow run release-image.yml -f tag=v0.1.0`), never on a pull request. Its `image` job checks out the workflow's own revision and, apart in `release/`, the tag; logs in to Docker Hub as the other jobs do; and runs `.github/ci/release-image.sh` from the workflow's revision with `CONTEXT=release`. The script refuses a tag that is not `vX.Y.Z` and a checkout that is not the tag's commit, builds the image from `release/` with the OCI labels `source`, `version` and `revision`, runs `docker/smoke-test.sh`, and only then pushes it to `ghcr.io/shinyredapples/intakt` as the version (`0.1.0`). Its `latest` job then runs `.github/ci/release-latest.sh` on GitHub's `ubuntu-24.04` (for `gh` and `docker buildx`), one run at a time across all tags (concurrency group `release-image-latest`, nothing cancelled): it reads the tags as they are now (`gh api`), and points `latest` at the highest release tag's image once that is on the registry (only buildx's "not found" for that exact reference or the registry's `MANIFEST_UNKNOWN` counts as not pushed yet; any other inspect error, a 404 from the token endpoint included, fails the job), never at its own run's tag, so overlapping releases cannot move `latest` back and a waiting run GitHub drops changes nothing. Both jobs have `packages: write` for their own token beside `contents: read`. `tests/Gates/ReleaseImageTest.php` runs both scripts with a fake `docker` (and `gh`) and checks the triggers, the dispatch input, the two checkouts, the serialized `latest` job and the permissions.

`.github/workflows/ci-image.yml` publishes the CI image to `ghcr.io/shinyredapples/intakt-ci:<hash>`, the hash `.github/ci/build-image.sh --print-hash` names it by, so a build loop can run `bin/check` in exactly CI's environment (thread-safe PHP 8.5 from the FrankenPHP image, the same extensions, ini profile and tools) instead of a local PHP that can behave differently. It runs on a push to main that changes one of the image's inputs, and on demand; its one job runs only on main (`if: github.ref == 'refs/heads/main'`), never for a pull request, since a pull request runs its own workflow and could plant an image a loop then trusts. `.github/ci/publish-ci-image.sh` leaves an image already published for the hash as it is, builds and pushes only when the registry confirms it missing (buildx's not found for that exact reference, or the registry's `manifest unknown` message; an answer with only the code `MANIFEST_UNKNOWN` fails closed), and fails on any other registry error. The job has `packages: write` beside `contents: read`; on a self-hosted runner it would publish an `intakt-ci:<hash>` image already on the runner, which is one more reason the runner must be ephemeral ([setup and reasons](../user/self-hosted-ci.md)). `tests/Gates/CiImagePublishTest.php` runs the script with a fake `docker` and checks the triggers and permissions.

- **Runner:** every job of `ci.yml`, the `journeys` job of `journeys.yml`, the `image` job of `release-image.yml` and the `publish` job of `ci-image.yml` have `runs-on: ${{ fromJSON(vars.CI_RUNS_ON || '"ubuntu-24.04"') }}`; the `alarm` job of `journeys.yml` and the `latest` job of `release-image.yml` always run on GitHub's `ubuntu-24.04`. With the repository variable `CI_RUNS_ON` unset, CI runs on GitHub's `ubuntu-24.04`. Set to a JSON label list, for example `["self-hosted","linux","x64","intakt-ci"]`, it runs on that self-hosted runner. A self-hosted runner must be ephemeral (a clean machine state for every job, registered `--ephemeral`) with no network path to the owner's other machines, and its host needs Docker for the runner's user, unprivileged user namespaces and no AppArmor profile blocking mount; a persistent self-hosted runner is not supported ([setup and reasons](../user/self-hosted-ci.md)). A `runs-on` taken from a variable is one the planned workflow scan cannot read, so for this repository it counts as risky ([Merge](../design/05-architecture/08-merge.md)). A hosted runner service that starts every job on a new VM and discards it afterwards (for example Ubicloud) registers its runners as self-hosted; with the repository variable `CI_DISPOSABLE_RUNNER` set to `true`, the jobs prepare that VM as they do GitHub's runners (the sysctl and `apparmor=unconfined` below). Leave it unset for any other self-hosted runner.
- **Fork guard:** every job's `if` in `ci.yml` is exactly `github.event.pull_request.head.repo.full_name == github.repository || github.event_name == 'push'`, so a pull request from a fork never runs, on either kind of runner. The guard is kept to this one exact form, with no other job condition, so a workflow scan can verify it line by line; the other conditions therefore live in the steps: `changes` answers `true` on a push, and `persistence` skips its steps and starts no database service (an empty service image) when the answer is not `true`. A failing `changes` job skips the engines and fails the run. `journeys.yml` has no fork guard: it starts only from its schedule or by hand (`workflow_dispatch`), never from a pull request.
- **The CI image:** the `image` job of `ci.yml` is an exception: it builds the application image from the repository's `Dockerfile` and runs `docker/smoke-test.sh`, `docker/verify-first-start.sh` and `docker/verify-upgrade.sh` on the host, not in the CI image; `changes` also runs `.github/ci/persistence-needed.sh` directly on the host. Only the `check` and `persistence` jobs of `ci.yml`, the `journeys` and `alarm` jobs of `journeys.yml` and the `build` job of `highlights.yml` run Intakt's code in the image built from `.github/ci/Dockerfile` (`dunglas/frankenphp:1.13.4-php8.5-trixie` pinned by digest, frankenphp without file capabilities, plus git, jq, unzip, python3, iproute2, a fixed list of extensions (`intl`, `pcntl`, `zip`, and `pdo_mysql` and `pdo_pgsql`, which only the persistence group uses) installed before `composer.json` and the check ini are copied in, so an edit of either reuses that layer, Composer 2.11.1 and gitleaks (the version `GitleaksGate::PINNED_VERSION` names), copied from stages built on the `composer` image and gitleaks' GHCR image, each pinned by tag and digest, and a uid 1000 user).
- **CI image settings and build checks:** the CI image loads `config/gates/php/check.ini` as `zz-check.ini` in its `conf.d`, so the jobs run with the check-time settings (`memory_limit=-1`, `zend.assertions=1`, `E_ALL`); there is no separate CI ini. Its build fails below PHP 8.5.12 or, after the copy, when the same script as the app image's finds that `composer.json` does not parse, has no `require` object or names an `ext-*` the image does not load (each missing one is named), and checks frankenphp, PHP, `pdo_mysql`, `pdo_pgsql`, Composer, gitleaks and zizmor.
- **Dependabot for the CI image:** the `docker` entry of `.github/dependabot.yml` updates the `FROM` images of `.github/ci/Dockerfile` and the app's `Dockerfile` weekly (prefix `build`), tag and digest together, once a release is 3 days old (Dependabot has no separate, longer wait for a major in this ecosystem), except the images on GitHub's container registry (`ghcr.io`), such as the gitleaks image: Dependabot has no verified publish date there, so its cooldown does not hold and an update of such an image can arrive with no wait. A gitleaks bump is the `FROM` line in `.github/ci/Dockerfile` plus `GitleaksGate::PINNED_VERSION` in `config/gates/src/GitleaksGate.php` (the gate test reads it from there); without that edit the `secrets` gate fails. So the gitleaks image has a `gitleaks` group of its own, listed before the entry's `images` group, which holds every other image and leaves the gitleaks image out (`exclude-patterns`): its update opens as a pull request of its own and cannot hold back the others until that edit is made (`tests/Gates/DependabotImageGroupsTest.php` checks the group and the exclusion against the image the CI Dockerfile names, and that the exclusion holds that image and nothing else).
- **Building and reusing the CI image:** `.github/ci/build-image.sh` builds the CI image with the checkout as context (`--file .github/ci/Dockerfile .`) and tags it by a hash of the Dockerfile, `composer.json` and the check ini, and builds only when no image of that tag exists, so a clean runner state that already holds the image reuses it, while a profile change builds a new image and an image of an older profile is not reused. The reuse is safe only because a self-hosted runner is ephemeral: a pull request's job could tag any image with main's hash, and only a clean state for every job keeps that from reaching a later one.
- **CI image cache:** the `check`, `persistence` and `journeys` jobs and the `build` job of `highlights.yml` get the image through `.github/actions/ci-image`: it reuses an image already on the runner, else restores the copy that a run on main saved in GitHub's Actions cache under `intakt-ci-image-<hash>` (the hash `build-image.sh --print-hash` prints, the same that names the image) and loads it, else builds it; only a run on main that had to build saves it (`actions/cache/save`), never a pull request, because a pull request runs its own workflow and could otherwise plant an image a later job would run. A hosted runner service such as Ubicloud starts every job on a fresh VM, so without the cache each of these jobs compiles the image (about a minute). Composer's downloads are cached separately, see Job containers.
- **Running the CI image:** the jobs run the CI image with `--user 1000:1000` and the checkout mounted read-only; `.github/ci/run-on-copy.sh` installs the locked dependencies on a copy in the home directory and runs the command there. No job has a job container, and no container gets the Docker socket.
- **`check`:** runs `bin/check` in the CI image, with `--base` set to the pull request's target branch, or to `origin/main` on a push, so a pull request that leaves the gate code alone skips the slow gate tests and every push to main runs them. The gate tests run processes in a new user namespace and mount a fresh `/proc` there, so the container gets `.github/ci/seccomp-userns.json` (Docker's default seccomp profile plus `unshare` only with `CLONE_NEWUSER`, and `mount`) and `systempaths=unconfined` (the kernel refuses a new `/proc` in a user namespace while Docker's masks cover parts of the old one). On runners discarded after the job only (GitHub-hosted, or `CI_DISPOSABLE_RUNNER` set to `true`), it also gets `apparmor=unconfined` (Docker's AppArmor profile forbids mount) and the job sets the `kernel.apparmor_restrict_unprivileged_userns=0` sysctl.
- **Docker Hub login:** before a job pulls from Docker Hub (the `check`, `persistence`, `image` and `journeys` jobs), `.github/ci/docker-hub-login.sh` logs Docker in with the repository secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` when they are set, and does nothing when they are not. A hosted runner service shares its IP addresses among its customers, and Docker Hub allows few anonymous pulls per address; GitHub's own runners are not limited this way. The token must be read-only, because a same-repository pull request's job can read it. The `persistence` job's database services pull their images anonymously: GitHub rejects a job whose service `credentials` are empty, so they cannot take the optional secrets.
- **`journeys.yml`:** the `journeys` job checks out main and runs `bin/check --journeys` in the CI image with the `check` job's container options (the seccomp profile, `systempaths=unconfined`, the Docker Hub login, and on discarded runners `apparmor=unconfined` and the sysctl) and `/home/ci` and `/tmp` on tmpfs, but without Composer's cache.
  It pipes the output through `tee` into the runner's temporary folder.
  It keeps the output as the `journeys-output` artifact when the step fails or ends `cancelled`.
  A job stopped at `timeout-minutes` ends `failure` with its journeys step `cancelled`.
  It passes the step's outcome and the checked-out commit to `alarm`.
  Its limit of 40 minutes holds the image build and, one after another, each journey file's run: the gate's 300 seconds cover one file's whole contained run (`bin/instance`'s boot and stop plus the PHPUnit run of that file), not each journey test in it.
  One run at a time (`concurrency: journeys`, never cancelled).
  The `alarm` job needs `journeys`.
  It runs only when its journeys step failed, or ended `cancelled` while `failure()` is true (a timeout).
  A run cancelled by hand ends the `journeys` job `cancelled`, so `failure()` is false and `alarm` is skipped.
  It runs on GitHub's `ubuntu-24.04`, never on `CI_RUNS_ON`, because it uses that runner's `gh`, which the CI image lacks.
  It checks out the same commit, downloads the artifact, builds or reuses the CI image and runs `bin/journey-alarm --run=<run link>` on the saved output in it, with the host's `gh` mounted read-only at `/usr/local/bin/gh`.
  When the journeys step ended `cancelled`, it adds `--timed-out`.
  It does not use the shared container rules: `/home/ci` is on tmpfs, but `/tmp` is not, and it gets no seccomp profile or other security option.
  The top-level token is `contents: read`; the whole `alarm` job holds `issues: write` (GitHub has no per-step permissions), and only its last step puts the token in its environment (`GH_TOKEN`, passed into the container with `GITHUB_REPOSITORY`).
  `tests/Gates/JourneysWorkflowTest.php` pins the triggers, the permissions, the upload's and the alarm's conditions and where `GH_TOKEN` appears.
- **Job containers:** the `check` job and each persistence engine run with `/home/ci` (the working copy and `vendor/`) and `/tmp` on tmpfs, so nothing they write touches the runner's disk. No locked package carries a checksum (`"shasum": ""` in `composer.lock`), so a planted archive in Composer's cache would be installed unchecked by a later job, main's included.
- **Composer's cache in the `check` job:** a hosted runner starts every job on a fresh VM, and without a cache Composer downloads every dist from GitHub unauthenticated, where a slow or refused download failed the job. The job restores Composer's cache from GitHub's Actions cache (`actions/cache/restore`, pinned by commit) into a directory under the runner's temporary folder, keyed `composer-<runner OS>-<hash of composer.lock>`, falling back to the newest `composer-<runner OS>-` entry, and mounts it as `COMPOSER_CACHE_DIR=/composer-cache`. On a pull request the directory is readable by the container's uid 1000 and mounted read-only with `COMPOSER_CACHE_READ_ONLY=1` (without that setting Composer ignores a cache it cannot write), and nothing is saved. Only a push to main mounts it writable and, when the lock's key was not an exact hit, saves it afterwards (`actions/cache/save`), so a pull request cannot plant an archive that a later main run reads; GitHub also keeps a pull request's own cache entries out of main's scope. A self-hosted runner uses the same Actions cache. The cache adds no secret and no token to the container.
- **Composer's cache in the persistence engines:** each engine mounts the runner's `intakt-composer-cache` Docker volume read-only with `COMPOSER_CACHE_READ_ONLY=1`. The volume is empty unless the runner's clean state provides it filled; Composer then downloads what it lacks and caches nothing. The guard is the runner's clean state per job: whatever a job writes to the volume is gone before the next job starts.
- **`persistence`:** one job with a service container per engine, each database's data directory on a tmpfs (the databases are throwaway, so disk syncs only cost time). One step runs the three engines at once (`.github/ci/persistence-engines.sh`, covered by `tests/Gates/PersistenceEnginesTest.php`), each in the CI image on the network the runner creates for the job's services (`job.services.<engine>.network`), reaching its database by the service name `mysql`, `mariadb` or `postgresql`; no port is published. The step runs only once the CI image was built; every engine runs to its end even when another fails, its output in its own log group, and the step fails when any engine failed. One job rather than a matrix, because each job on an ephemeral runner is a full machine reset and takes a runner of its own.
- **Database images:** the `persistence` job's services take their images from `.github/ci/databases.Dockerfile` (never built), one `FROM <image> AS <service>` line per service; the `changes` job reads them with Bash builtins and fails unless each service has exactly one. Dependabot updates them in the `images` group (see the [index](README.md) for their missing digest; each `image:` line in `ci.yml` carries a `zizmor: ignore[unpinned-images]` for it).
- **zizmor in the CI image:** the image also holds zizmor, the version pinned by the zizmor stage in `.github/ci/Dockerfile`, copied from a stage on its GHCR image, pinned by tag and digest like the other tool stages; the build checks `zizmor --version`. Dependabot keeps it current with them (`images` group). The `workflows` gate calls it.
