## Vendor

`Plugin/Vendor/Contract/Vendor` has three methods. `mapsAModelTo(project, tier)` tells whether the project maps a model to the tier: `SymfonyAiVendor` asks `TierResolver::configured()`, the same mapping that throws `Core/Ai/Contract/TierNotMapped` on a call, and answers false for that exception only; the answer covers only the mapping, not whether a provider is available, so a tier whose own provider is disabled still counts as mapped, also when no substitute is configured and the call then fails with `TierProviderDisabled`, and a project that is not configured throws `ProjectNotConfigured`. `AccountLimitedVendor` passes the wrapped vendor's answer on, and the test doubles that implement `Vendor` answer true (`JudgeCallingVendor` asks the vendor it wraps, and `ScriptedJourneyVendor` the vendor it answers with). `ReviewChange::start()` asks it for every tier a round needs before the round opens, see [Review flow](review-flow.md#refused-before-it-starts) (tests: `tests/Plugin/SymfonyAiVendor/SymfonyAiVendorTierMappingTest.php`, `tests/Plugin/SymfonyAiVendor/Infrastructure/AccountLimitedVendorTest.php`). `review(project, tier, ReviewRequest)` returns a `VendorReview` (`#[NoDiscard]`): the `Verdict` and the substitute `Provider`, null unless another provider than the tier's own answered. `judge(project, JudgeRequest)` returns a `Judgement` on the light tier (see "Judge"), on the model `TierInvoker::answering()` chooses, in the same account place and with the same usage rows and provider errors as a review, and turns a cut-off stream into the judgement that marks every blocking finding `act`; a judgement records no substitute. `Plugin/SymfonyAiVendor/Infrastructure/SymfonyAiVendor` implements it: it asks `TierInvoker::answering()` for the review's model, then wraps the `TierInvoker` in a `TierRoutedPlatform` (a `PlatformInterface` that sends every round to that one model, whatever model name the agent passes, and keeps every round's `DeferredResult`) and hands that platform to the `Reviewer` of `Core/Review` (see [Reviewer agent](reviewer-agent.md)), which runs the agent and returns the parsed verdict. The schema sent to the model is derived from the `Verdict` class, and `StrictVerdictSubscriber` and the Validator check the answer; the T1 schema file (`tests/Core/Review/Contract/verdict.schema.json`) is the test oracle, not the call's source. An answer that is not a valid verdict comes back as `VerdictUnreadable` (never a verdict); a failed call stays an exception. `review` first reserves the call in the ledger through `UsageLedger` (`reserve` is `#[NoDiscard]`; the `call` id is a UUIDv7 built from the injected `ClockInterface`), then settles it once the verdict is parsed, with the usage of every round of the agent (`UsageLedger::settle()` takes the rounds and lists the usages of all of them), or leaves it unsettled when the call throws (the exception still propagates), with the usage of every round that can be read. A `claude_code` or `codex` review for which no review server access can be issued (`NoReviewServerAccess`) makes no call: it settles with no usages and returns `Verdict::noTools()` (see [AI providers](ai-providers.md)). `retriedOnce()` runs a review once more with more room after a Platform `MaxOutputTokensException` or a `VerdictUnreadable`: the stopped call is left `unsettled` with that class (an unreadable answer is `settled` with its tokens, because the call ended with an answer), and the review runs once more with a new reservation, twice the tier's output limit and a new conversation id from the same `ClockInterface`; when that call is stopped or unreadable too, the exception propagates and the reviewer ends `failed` (see [Review flow](review-flow.md)), shown as "stopped at its output limit" or "the reviewer's answer could not be read as a verdict" by `FailureInWords` (the latter followed by its reason when the reason is key-safe). A review whose verdict is `changes` or `blocked` with no finding (`Verdict::withholdsApprovalWithoutFinding()`) is not a valid verdict: its call is settled, `ChangesWithoutFindings` is thrown, and `retriedOnce()` runs the review once more with a new reservation and a new conversation id at the same output limit, the conversation marked `askedToNameFindings` so the prompt shows the reviewer an example finding and asks it to name its findings or approve; when that verdict is again `changes` or `blocked` with no finding, the exception (declared on `Vendor::review`) propagates and the reviewer ends `failed`. A call that cannot reach the model endpoint (an HTTP client `TransportExceptionInterface`, which Symfony's client raises as the answer is read, or `Core/Ai/Contract/EveryEndpointUnreachable`, which `AccountFailoverPlatform` throws when every account the call was sent to threw a transport error while sending, see [AI providers](ai-providers.md)) is left `unsettled`, typed as `Plugin\Vendor\Contract\ProviderUnreachable` (declared on `Vendor::review` and `Vendor::judge`), and `retriedOnce()` runs the review once more with a new reservation and a new conversation id at the same output limit; when that call cannot reach it either, the reviewer ends `failed`, shown as "the model endpoint could not be reached" by `FailureInWords`. Every row is a `usage_recorded` event with a JSON payload: `started` (`call` UUID, `project`, `tier`, and `round`, the review round's id, on a reviewer call made for a round, carried on `ReviewerConversation::$round`, and on every judge call, carried on `JudgeRequest::$round`; a reviewer call outside a round carries none; and `model`, the model the tier resolved to and that answers the call, a substitute's model when a substitute answers, passed to `UsageLedger::reserve()` with the tier as `Infrastructure/AnsweringTier`, because Claude Code and Codex answers name no model and API answers name a dated snapshot; a retried review reserves under the same model; rows written before it was kept have none), `settled` (the same `call` and `usages`, one entry per `TokenUsage` of the result's `token_usage` metadata, an aggregation split into its parts: `model`, `prompt`, `completion`, `thinking`, `tool`, `cached`, `cache_creation`, `cache_read`, `total` and the `remaining`, `remaining_minute`, `remaining_month` figures; empty when the provider reported none) or `unsettled` (the same `call`, the `failure` class and the `usages` of every round whose usage can be read; empty when none can; a round whose usage cannot be read is left out and logged once at warning level, and the other rounds keep theirs). The three payloads are the readonly classes `UsageStarted` (`tier` held as the `Tier` enum, `round` and `reviewer` left out of the JSON when null; a reviewer call's started row, reserved with `UsageLedger::reserveForReviewer()`, names the reviewer's id from its `ReviewerConversation::$reviewerId`, the judge's names none, and `RoundLedgerReading::figuresOfReviewers()` adds up each reviewer's calls and names the models they ran on, see [Sample repository](sample-repository.md#reviewing-one-bench-change)), `UsageSettled` and `UsageUnsettled`, each usage entry a `TokenUsageRow` whose unreported figures stay `null` in the JSON, all in `Plugin/SymfonyAiVendor/Contract/` (so `Core/Review`'s `RoundLedgerReading` reads them back) and written by `UsageLedger` through the `stored` serializer (see "Stored JSON"); the keys and values are the ones written before (`tests/Plugin/SymfonyAiVendor/Contract/UsagePayloadsTest.php`). An answer that is not a valid verdict still settles with its tokens, because they were spent: when mapping fails the result has no metadata, so `UsageLedger` reads the usage with the converter's `TokenUsageExtractor` from the raw result, or from the converted result an in-memory raw result carries (`MockPlatformFactory`). When reading the usage throws (an extractor failing on the raw answer), the call is left `unsettled` with the class of the first unreadable round's exception and the usages of its rounds that can still be read; each round is read once (`UsageLedger` collects the usages and the failures in one pass, so a failing extractor runs once), each unreadable round is logged once at warning level with the call id and its round index, and `review` still returns a readable verdict and still throws `VerdictUnreadable` for an answer that is no verdict. A ledger that refuses an append throws `Plugin/Vendor/Contract/UsageNotRecorded` (declared on `Vendor::review`) after logging the row at error level: a refused `started` row stops the call before it is sent, a refused `settled` row fails the call instead of returning the verdict, and a refused `unsettled` row keeps the call's exception as the previous one. Provider limits are typed errors, never read from a model's text (the Codex CLI's own error messages are turned into them before, see [AI providers](ai-providers.md)): `SymfonyAiVendor` turns a Platform `RateLimitExceededException` into `Plugin/Vendor/Contract/ProviderRateLimited`, carrying `retryAfterSeconds` from `getRetryAfter()` (null when the provider sent none, a negative value clamped to zero so the reset is never in the past, a value above one day clamped to 86400 seconds so the reset stays meaningful) and `resetsAt($now)` (the caller passes its clock's moment, null without a reset), and any other `RetryableExceptionInterface` (such as a `ServerException`) into `ProviderFailedTransiently`; the original is the previous exception, and the call is still left `unsettled` with the original class. Both are declared on `Vendor::review`. With the review's model chosen, `SymfonyAiVendor` takes a place in the Semaphore of that model's provider (`VendorAccountLimit`, keyed by the provider that answers, so a substitute counts against its own provider's limit and not the tier's, and every account of a provider shares one limit, since the account is chosen only inside the call; Symfony Semaphore over a `LockStore` on a `LockFactory` with a `FlockStore` in `var/locks` (in the test environment `%kernel.cache_dir%/locks`, one per test worker), because the other Semaphore store needs Redis and every worker runs on this host), without waiting; at the limit (`intakt.vendor_account_parallel_calls` in `config/services.yaml`, 3) it throws `Plugin/Vendor/Contract/VendorAccountBusy` before reserving any usage, and the place is released when the review ends or fails. `SymfonyAiVendor` turns `EveryAccountCoolingDown` into `ProviderRateLimited` with its wait (the exception stays its cause, so `AccountLimitedVendor` reads that wait, which includes a pinned router provider's pause, before the account windows), `EveryProviderOut` into `Plugin/Vendor/Contract/NoProviderLeft` (the message is the reason) and an `AuthenticationException`, `EveryKeyRejected` included, into `ProviderRejectedTheKey` (no provider text); the substitute is the chosen model's provider when it is not the tier's own (`TierResolver::configured()`, so a disabled own provider counts too), never read from text, and an approval (or a `changes` of only P3 findings, which the quorum can count as approval: `Verdict::mayCountAsApproval()`, which judges a reviewer's `blocked` with findings as the `changes` it is recorded as) counts only when that provider reads the checkout or the call carried `ReviewServerAccess::OPTION` (a `claude_code` or `codex` call given the per-review MCP server, decided per attempt, so a retry at the output limit is judged on its own options), and only when one of the attempt's rounds also reports a completed read through that server (`Core/Ai/Contract/ReviewServerReads`, see [AI providers](ai-providers.md)); otherwise it is `Verdict::unreadApproval()`. The `Vendor` service is `AccountLimitedVendor`, which wraps `SymfonyAiVendor` (in the test environment it is the journeys' `ScriptedJourneyVendor`, which answers as `JourneyVendor` unless a process has a script directory and then is `SymfonyAiVendor` itself, see [Journeys](journeys.md); tests of these classes build them directly). When a tier has substitutes (`TierResolver::hasSubstitutes()`, asked first, so a disabled own provider is never resolved), it throws `VendorAccountOut` for `ProviderRateLimited`, `ProviderFailedTransiently` and `ProviderRejectedTheKey` even when every account of the provider is out, so a review cut off before its first answer delta starts again from the beginning, in a new conversation, on whichever provider `answering()` chooses then, or ends in `NoProviderLeft`. Without substitutes, a `ProviderRejectedTheKey` throws `VendorAccountOut` only when its previous exception is `Core/Ai/Contract/KeyRejected`, which `AccountFailoverPlatform` throws while another account of the provider is free; any other rejection (`EveryKeyRejected`, or the provider's own, also on a provider not listed under `accounts:`, which has its one `default` account) is rethrown and ends the reviewer as `failed`, because only `KeyRejected` proves that another account is free and a cooldown reading is not that proof, so a rejected key is never called again at once. When the call fails with `ProviderRateLimited` or `ProviderFailedTransiently`, the failing account is cooling down by then, and `AccountLimitedVendor` uses the wait of an `EveryAccountCoolingDown` in the cause chain; only when the chain carries none does it ask `AccountCooldowns::secondsUntilAnAccountIsFree()`, where zero means another account of the provider is free, and it throws `Plugin/Vendor/Contract/VendorAccountOut` (declared on `Vendor::review`); otherwise both are thrown as `ProviderRateLimited` with that wait (until the first account is free, not the failed account's own reset), so the handler hands the reviewer back to wait out the shared cooldown instead of recording a failure. A call whose accounts all failed with a limit while an account is free again carries a wait too, instead of the failover's generic error counting as a failure (see "Cooldowns and failover" in [AI providers](ai-providers.md)): one second when the free account is one the call never sent to, so the reviewer is handed back for a second and the retry reaches that account; for a pinned model whose limited accounts are free because the pin already ended or no window was saved, the shortest wait those limits named (one second after a one-second reset, 120 seconds after a 120-second one). Each entry of a `settled` or `unsettled` row's `usages` carries `account`, the key of the account the call ran on (null when the result carries none). Tests: `tests/Plugin/SymfonyAiVendor/Infrastructure/VendorAccountLimitTest.php`, `tests/Plugin/SymfonyAiVendor/Infrastructure/AccountLimitedVendorTest.php`, and `tests/Core/Review/UseCase/RunReviewRound/SameVendorAccountFailoverTest.php` (a round on two accounts of one provider whose first is limited: the reviewer moves to the other account and the round completes with its verdict; a transient failure while every account cools down leaves the reviewer `queued`). A stream that breaks off mid-text after a tool round (a scripted `StreamResult` per round) leaves the call with one `started` and one `unsettled` row whose `usages` hold both rounds, once, with `StreamEndedEarly` (the `IncompleteStreamException` the streamed answer raises, see [Review verdicts](review-verdicts.md)) as the `failure`. A transient error once the stream has yielded an answer delta, not only usage or metadata (a `ServerException`, also a server error event, or a `RateLimitExceededException`) reaches the vendor as the `IncompleteStreamException` that `StreamedAnswer` makes of it, with the provider's exception as the previous one (see [Review verdicts](review-verdicts.md)): the vendor returns `Verdict::incompleteStream()` at once (blocked, P1, with the reason `The provider failed after the answer had started streaming.`) and does not retry it, because the outage has cooled the account down. A cut without such a previous exception (the stream itself ended early) is run once more without streaming (see [Review flow](review-flow.md)), and when that try is cut too, the vendor returns `Verdict::incompleteStream()` with the first cut's message as the reason. The finding's `Evidence` names the call (`probe`: `the call to <provider>, model <model>`, the model that answered) and, for a `StreamEndedEarly`, its `described()` lines as the `output` (who cut it, the chunk count and the last chunks); any other cut, such as a subscription CLI's, has the output `cut by: platform, outside a counted stream` (`CutStreamRetryVendorTest`). `AccountLimitedVendor` passes either verdict on, and the round stores it as the reviewer's blocked verdict. A transient error before the stream's first answer delta (also after the usage a provider sends on opening the message) stays `ProviderFailedTransiently` and goes through `AccountLimitedVendor` as above (`tests/Plugin/SymfonyAiVendor/SymfonyAiVendorTest.php`, `tests/Core/Review/UseCase/RunReviewRound/RunReviewRoundTest.php`). Handing the `remaining*` figures to a budget planner is not done yet (no planner exists). Tests: `tests/Plugin/SymfonyAiVendor/SymfonyAiVendorTest.php` (`MockPlatformFactory` with the application's event dispatcher, and `InMemoryLedger` for the recorded rows; each test boots a kernel of its own for that dispatcher in `setUp()` and shuts it down in `tearDown()`, and a test runs a review on it, which calls the listeners the container declares, and finds none of them called after its `services_resetter` ran; the `persistence` test that gets the vendor from the container boots its own).

### Sizing

The sizing call is not a method of `Vendor`: `SizingVendor::size(project, SizingRequest)` is its own interface in the same `Contract/`, implemented by `SymfonyAiSizingVendor` (standard tier, no account failover wrapper yet), so the test doubles of `Vendor` need no sizing method. Its `started` usage row names the task (`UsageStarted::$task`), see [Task sizing](task-sizing.md).

### Token figures

`TokenUsageRow::figures()` turns one usage entry into a `TokenFigures` (`Plugin/SymfonyAiVendor/Contract/`): `prompt`, `cacheRead`, `cacheWrite`, `cached`, `completion`, and `total()`, always `prompt + completion`, never the vendor's `total` (Anthropic reports none, so a total read from the vendor was 0). `prompt` holds every input token, cached ones included, but the vendors count them differently, so the rule follows the provider the entry's `account` key names (`Account::providerOfKey()`, the part before the dot of `Account::key()`): for a provider whose `Provider::countsCacheApartFromPrompt()` is true (`anthropic` and `claude_code`, whose `input_tokens` leaves the cache out) `prompt` is the vendor's prompt plus `cache_read` and `cache_creation`, shown as `cacheRead` and `cacheWrite`, plus the part of the combined `cached` beyond those two (never below 0), shown as `cached`: all of it when only the combined figure is reported (the Claude Code bridge adds the two up), none when it equals their sum (the Anthropic bridge). For any other provider (`openai`, `openai_compatible` and `codex` count cached tokens within the prompt) and for an entry without an account key or with an unknown provider, `prompt` is the vendor's prompt as reported, `cacheRead` is `cache_read`, else `cached`, and `cacheWrite` is `cache_creation`. A figure the vendor did not report counts as 0 in the token figures; a round's cost does not price an entry without `prompt` as 0 but shows it as unknown (see [Round cost](round-cost.md)). `RoundLedgerReading::tokensOf()` (the console's `intakt:review`) and the dashboard's `LedgerTokens` both add up these figures, so they show the same numbers for a round (`tests/Plugin/SymfonyAiVendor/Contract/TokenUsageRowTest.php` feeds recorded usage answers through the Anthropic, Claude Code and Generic bridges' extractors).

### Judge

Plan task T12, part 1 (design: [Reviews](../design/05-architecture/07-reviews.md), [threat model](../design/05-architecture/14-threat-model.md#judge)). `Core/Review/Contract` has the `Judge` interface (`judge(JudgeRequest, PlatformInterface, model): Judgement`, `#[NoDiscard]`), `JudgeRequest` (the task text, `list<Finding>`, the `round` id, which `JudgeRoundHandler` sets and the vendor records on the call's usage, and `changedFiles`, the paths of the round's diff from `DiffPaths` as a `Git\Contract\Paths`, which `JudgePrompt` sends in a fence of its own, source `changed files`, one JSON-encoded path per line so a newline in a name cannot read as a second file, so the judge can tell a file the change touches from one outside it), `Judgement` (a `#[Valid]` list `marks` of `JudgedFinding`: an `id` that is not blank, a `Mark`, the backed enum `act`, `defer`, `reject`, and an optional `same_cause_as`, the id of another given finding with the same cause, see [Review flow](review-flow.md), and an optional `note`, the judge's reason for a `defer` or `reject` of a P1 or P2). Property names are the JSON field names, as for `Verdict`.

- **Agent:** `JudgeAgent` runs a Symfony AI `Agent` with no toolbox and no message store on the given platform, with `PlatformSubscriber::RESPONSE_FORMAT => Judgement::class`, so the schema comes from the class and the Validator checks the answer.
- **Prompt:** `JudgePrompt` holds the fixed instructions in the system message (the marks, where a P1 or P2 stays on the act list whatever its mark and the judge marks it `defer` or `reject` with a one-sentence `note` when it disagrees, a P3 that is a local edit in a file the change already touches and needs no new design is `act` and `defer` is for a finding needing its own design or tests or files outside the change; and `same_cause_as` for a finding that reports the same change as an earlier one in the same file and part of the diff); the task, the changed files and the findings (id, severity, place, requirement, text) are three user messages, each through `Fence::wrap` (`UntrustedSource::Task`, `UntrustedSource::ChangedFiles`, `UntrustedSource::FindingsToJudge`), and all four messages are built by `PromptAssembly` (see Prompt assembly under [Reviewer agent](reviewer-agent.md)).
- **Invalid answer:** a Validator violation, an answer that is not JSON or not a `Judgement`, an unknown mark, an id that was not given, a repeated id or a finding left unmarked gives `Judgement::everyBlockingFindingActs()`: every P1 and P2 finding is `act`. A P3 finding then gets no mark, so it is not on the act list. A failed call is not an answer and stays an exception.
- **Vendor:** `SymfonyAiVendor::judge()` (and `AccountLimitedVendor::judge()`) always uses `Vendor::JUDGE_TIER`, the light tier; `ReviewChange` asks for the same constant before a round starts (see [Review flow](review-flow.md#refused-before-it-starts)).
- **Act list and follow-ups (part 2):** `JudgedFindings::of(Judgement, list<Finding>)` (Contract) matches marks to findings by id: `actList` holds every P1 and P2 finding whatever its mark (a `defer` or `reject` for one is not applied, #1891) and the P3 findings marked `act` (also a small local P3 edit in a touched file), `followUps` a `FollowUp` (wrapping the finding) per P3 marked `defer`; a gate-gap P3 (`Finding::$gate_gap`, #3319) is never on `actList`: marked `act` or `defer` it is a follow-up, marked `reject` it is in `rejected`, and without a mark it is on neither, while a gate-gap P1 or P2 stays on `actList` like any other; another P3 marked `reject` or without a mark is on neither, and `rejected` holds the P3 findings marked `reject`, apart from the ones without a mark, because only a P3 the judge marked `defer` or `reject` lets a `changes` verdict count as approval (`Domain\CountedVote`, see [Review flow](review-flow.md)). `JudgePrompt` and the `mark` schema description (`#[Schema]` on `JudgedFinding`) state the rule. A judged finding may carry the judge's reason (`note` on `JudgedFinding`, null by default); `JudgedFindings::$notes` (a `Contract/JudgeNotes`, see [Review verdicts](review-verdicts.md)) keeps it, as the judge gave it and by finding id, only for a P1 or P2 marked `defer` or `reject` (#2685), and the finding stays on the act list. `UseCase/JudgeRound/QueueJudgingOfCompletedRound` (a Workflow `AsCompletedListener` on the `complete` transition) dispatches `JudgeRound` (routed to `async`) inside the transaction that completes a round, once, because only the completing step passes the guard; the Doctrine queue shares that transaction, and the vendor call itself runs later in `JudgeRoundHandler`, outside the round's lock. The handler loads the round through `JudgedRounds` and returns at once when it is `judged` already (a redelivered message asks the model nothing). Otherwise it takes the findings the round reported (`StoredFindings::reportedIn()`, from the round's `reported_findings` column, migration `Version20261101120000`; none for a round completed before it). They are kept when the round completes, in the step that records its verdicts: the verdicts are recorded on the change's finding ledger under its lock, and the open findings whose latest round is this round (`FindingLedger::openReportedIn()`) are stored as JSON with the round, under the ledger's ids `F1`, `F2`, ..., so two reviewers that give different findings the same id of their own both reach the judge, and a later round that reports a finding again does not take it from this round's judge. A round that completes after a newer round of the change was recorded keeps its findings the same way, from the ledger with its verdicts added, but that ledger is not stored, so its verdicts do not undo the newer ones; its ledger comes from `FindingLedger::apartFor()`, so a new finding of such a round gets an id under the round's own prefix (`R<round>-F<n>`, for example `R1-F2`) that the stored ledger, which hands out `F<n>`, never gives to another finding. It drops each finding the quote check refuses (see Quote check in [Review flow](review-flow.md#quote-check)), then calls `Vendor::judge()` with the round's task and the findings it kept and builds the `JudgedFindings` from those; a round that reported no findings, or whose every finding was dropped, skips the call and is recorded with an empty judgement (no act ids, no follow-ups). `JudgedRounds::record()` then locks the round row (`ReviewRounds::withLockedRound()`) and the change's finding row (`StoredFindings::lockChangeOf()`), applies `judge` (complete to judged) and lets `RoundLedger::judgeDone()` append a `judge_done` event (JSON: `round`, `act` ids, `follow_ups` ids, and `findings`, every finding the judge was given as `id`, `severity` and `text`, kept in `JudgedFindings::$findings`, so the dashboard can show what each id stands for from the ledger alone, and `dropped`, each finding the quote check dropped as `id`, `severity`, `text`, `file`, `line`, the `reason` it was dropped for and its `gate_gap` mark (false when a row written before reads back), kept in `JudgedFindings::$dropped`, and `same_cause`, the judge's links between findings of one cause that `Domain/CausesInOneHunk` kept (both in one hunk of one file of the round's diff, at most five lines apart), kept in `JudgedFindings::$sameCause`; each entry of `findings` also holds `judge_note` (`JudgeDoneFinding::$judgeNote`), the note `JudgedFindings::$notes` kept for it passed through `trim()` of the `Platform` `Redactor`'s redaction, so a held credential quoted in it is stored as `[redacted]`, and null for every other finding, for a note left empty by that, and for a row written before notes were recorded), and `gate_gap` (`JudgeDoneFinding::$gateGap`), the reviewer's gate-gap mark (see Gate gap in [Review verdicts](review-verdicts.md); false for a row written before it was recorded), in the same transaction, followed there by a `recurring_p1_found` event for each P1 that recurs on another head (see [A recurring P1](review-flow.md#a-recurring-p1)); a worker that finds the round judged meanwhile records nothing, so a round has one `judge_done`. A `ProviderRateLimited`, `VendorAccountBusy`, `ProviderFailedTransiently` or `VendorAccountOut` from the vendor becomes `JudgeLimited`, a `RecoverableMessageHandlingException` (retry delay from the provider's reset, none for an account out, otherwise the retry strategy's), so the message comes back instead of reaching the failure transport. A `JudgeRound` message that fails for another reason and will not be retried (`WorkerMessageFailedEvent::willRetry()` is false) is not parked: the `DispatchOnFailureStamp` of the judging makes Messenger dispatch `RecordFailedJudging`, whose handler appends `judging_failed`, queues the publication and logs the failure (it does so only when the round is still `complete` and `FailedJudgings::isRecorded()` finds no failure recorded; when the failure cannot be recorded, Messenger falls back to parking the judging in the failure transport), so the round stays `complete`, unjudged; `intakt:review` reads that record to stop waiting (see the review command in [Forge contract](forge-contract.md)). Follow-ups are not stored beyond that event yet; the inbox and a command that reads the act list are later tasks.

### Escalation review

Plan task T61, issue #3301 (design: [threat model](../design/05-architecture/14-threat-model.md#escalation)); the prompt and the flow are in [Review flow](review-flow.md#the-escalation-call).

- **Port:** `Plugin/Vendor/Contract/EscalationReviews::escalate(project, round, MessageBag): ?EscalationVerdict`, its own contract apart from `Vendor`, with `TIER` set to `Tier::Strong`.
- **Vendor:** `SymfonyAiVendor\Infrastructure\SymfonyAiEscalationReviews` resolves the strong tier with `TierInvoker::answering()` and runs the call inside the provider account's limit (`VendorAccountLimit`).
- It runs a Symfony AI `Agent` with no toolbox and no message store, with `PlatformSubscriber::RESPONSE_FORMAT => EscalationVerdict::class`.
- A Validator violation (an outcome other than `confirmed` or `rejected`, `reasons` blank or only white space, form feeds, Unicode spaces or other invisible characters), an answer that is not JSON or not an `EscalationVerdict` returns null, never a rejection.
- The answer's text is then read again with the serializer, extra fields refused and every field required, as the schema sent to the model says; an answer with a field the schema does not hold, or without `reasons`, returns null too.
- The call is recorded in the usage ledger under the round's id: settled after an answer; after a failed call left unsettled.
- A failed call, and a strong tier whose accounts all cool down or whose providers are all out, is thrown as the vendor's typed error (`TypedProviderFailure::of()`, the mapping `SymfonyAiVendor` uses too: `ProviderRateLimited` with its delay, `ProviderRejectedTheKey`, `ProviderFailedTransiently`, `ProviderUnreachable`, `NoProviderLeft`), so the queue tries the escalation again.
- A ledger that cannot take the unsettled row is logged, and the provider's error is still thrown, so its delay is kept.
- That log names the call's id and the failure's class only, never the exception chain, which can hold a provider error that echoes part of a key.
- `reasons` needs a letter, digit, punctuation mark or symbol; combining marks, variation selectors and the Hangul and Braille fillers that render blank do not count.
- **Tests:** `tests/Plugin/SymfonyAiVendor/SymfonyAiEscalationReviewsTest.php` (the strong tier's model with no tools, the usage row on the strong tier with the round, answers that are no verdict, Unicode spaces around visible reasons, a rate limit typed with its delay and left unsettled, a rejected key, every account cooling down before the call, a ledger that cannot take the unsettled row).

`php bin/console intakt:vendor:probe` (`Plugin/SymfonyAiVendor/UseCase/ProbeProviders`) makes one real call (prompt `Answer with the single word: ok`, one user message built by `Review/Contract/PromptAssembly::notice()`) through `TierInvoker::invoke()` on the tier's own model, never a substitute, for each provider that some configured project and tier maps and whose keys are set; the first project and tier that maps a provider is used. It prints `<provider>: model, prompt, completion, cached, total, remaining` from the result's `token_usage` metadata, read into a `ProbeUsage` and normalized by the application's default serializer (`n/a` for a figure the provider did not report; `ProbeUsageTest`), and for a provider whose call or usage reading throws, an error line `<provider>: the call failed with <exception class>` (only the class, because a provider's message can echo a key), then goes on with the next provider; it exits with 1 when any provider failed. It does not write to the ledger and records no usage reading. So it checks only whether the providers reached through the projects' configured tiers answer: a provider no project tier maps is never called, and an answer says nothing about whether usage readings of a given account resumed. Each call is paid, so the dashboard's Waiting on you page does not offer it (see [Dashboard](dashboard.md)). Tests: `tests/Plugin/SymfonyAiVendor/UseCase/ProbeProvidersCommandTest.php` (`MockPlatformFactory` behind a stubbed `TierInvoker`).
