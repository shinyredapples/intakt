## Development diagnostics (Mate)

`symfony/ai-mate` and `symfony/ai-symfony-mate-extension` are `require-dev` packages pinned to one version, so `composer install --no-dev` (the install the container image of plan task T22 is to use) leaves them out; `tests/Application/MateDevOnlyTest.php` guards that and that nothing under `src/` uses Mate. Their Composer plugin stays disabled (`config.allow-plugins` is unchanged), so `vendor/bin/mate discover` is run by hand. The project's Mate files live in `mate/` (`config.php`, loaded through `extra.ai-mate.includes` in `composer.json`, pins the invocation `vendor/bin/mate` and PHP 8.5; `extensions.php` enables the two packages; `AGENT_INSTRUCTIONS.md` is what `discover` writes from the extensions' instructions, together with the marked block in `AGENTS.md` that points to it). No project tools exist, so there is no scan folder, and `mate.env_file` keeps its default (none), so Mate loads no env file of its own. `discover` also writes skill copies to `.agents/skills/` and `.claude/skills/` and a root `CLAUDE.md` that imports `AGENTS.md`; `.gitignore` keeps out `/.agents/`, `/.claude/skills/` and `/CLAUDE.md` (`tests/Application/MateGeneratedFilesTest.php` checks it). It rewrites the committed `mate/extensions.php` (adding per-skill state) and `mate/AGENT_INSTRUCTIONS.md` as well; those rewrites are not committed. Mate lists the packages from `vendor/composer/installed.json`, so without that file, or without `symfony/ai-mate` in it, it finds no tools either. `vendor/bin/mate tools:list` shows six tools: `server-info`, `symfony-dotenv-check`, `symfony-services`, `symfony-service-detail`, `symfony-profiler-list` and `symfony-profiler-get`. `framework.profiler` collects in `dev` (see the profiler section below); `symfony/web-profiler-bundle` is not installed, so there is no profiler toolbar or web page. The container tools read the app's compiled dev container under `var/cache/` (they ask for `bin/console cache:warmup` when there is none) and the dotenv check reads the app's `.env*` files, so they report what the app really has, not a guess from the code. `tests/Application/MateInvocationTest.php` runs `vendor/bin/mate` and checks that the tool list offers `server-info`, `symfony-services` and `symfony-dotenv-check` and that `server-info` reports this PHP. Mate takes the project root from the real path of `vendor/autoload.php`, so a `vendor/` that is a symlink to a folder elsewhere leaves it without `installed.json` and `mate/extensions.php`, and it finds no tools; `upstream/ai-mate-symlinked-vendor-root/` reproduces this. The CLI is the entry point; no MCP server is configured. `AGENTS.md` says when to use it.

## Development diagnostics (profiler)

FrameworkBundle's profiler (`framework.profiler` in `config/packages/framework.yaml`, no extra package) measures what a request does, so a query count or a list of dispatched messages is read from a running request instead of from the code.

- `dev` collects every request (`collect: true`). Profiles go to FrameworkBundle's default file store, `var/cache/dev/profiler/`, and each response names its profile in the `X-Debug-Token` header; the Doctrine (`db`), Messenger (`messenger`), Twig, security and the framework's own collectors fill them.
- `test` holds the profiler with `collect: false`, so a request collects a profile only after the test client's `enableProfiler()`, and the suite collects nothing it does not ask for. `tests/Core/Dashboard/UseCase/ListReviewsQueriesTest.php` counts the queries of the reviews page for three rounds on the SQLite ledger (15: six page reads plus three per unjudged round, which asks for its judging failures on its own) and checks that a request without `enableProfiler()` leaves no profile; `tests/Core/Dashboard/UseCase/StartReviewMessagesTest.php` lists the messages a start of the next round dispatches on the application's buses.
- `prod` has no `profiler` key, so its container holds no `profiler` and no `profiler_listener` service; `tests/Application/ProfilerOutsideProdTest.php` asks the prod container in a process of its own (`debug:container`, `APP_DEBUG=0`) and checks that the test container does hold it. The image runs `APP_ENV=prod`, and no profiler package is installed in any environment.
- A saved profile holds no secret of the environment. The request's server bag also carries every environment variable (`APP_SECRET`, provider keys, `MCP_OWNER_TOKEN`), so `RedactRequestProfilesPass` (registered by `Kernel::addApplicationPasses`, a no-op where FrameworkBundle registers no request collector, as in `prod`) swaps the class of `data_collector.request` for `Intakt\Core\Server\Infrastructure\RedactedRequestDataCollector`. Before the collector's data is frozen it replaces with `******` the value of every server variable that is not a request variable (an allow-list: `HTTP_*` but `HTTP_AUTHORIZATION`, `REQUEST_*`, `SERVER_*`, `REMOTE_*`, `SCRIPT_*`, `CONTENT_*`, `QUERY_STRING`, `PATH_INFO` and the like), every value of the collector's dotenv list, and the `Authorization` header, also inside the collector's curl command. `tests/Core/Server/Infrastructure/RedactedRequestDataCollectorTest.php` checks that a saved profile holds neither a canary environment value nor a bearer token, and still shows the request URI and host.
