## Development diagnostics (Mate)

`symfony/ai-mate` and `symfony/ai-symfony-mate-extension` are `require-dev` packages pinned to one version, so `composer install --no-dev` (the install the container image of plan task T22 is to use) leaves them out; `tests/Application/MateDevOnlyTest.php` guards that and that nothing under `src/` uses Mate. Their Composer plugin stays disabled (`config.allow-plugins` is unchanged), so `vendor/bin/mate discover` is run by hand. The project's Mate files live in `mate/` (`config.php`, loaded through `extra.ai-mate.includes` in `composer.json`, pins the invocation `vendor/bin/mate` and PHP 8.5, and points the profiler tools at `$APP_CACHE_DIR/dev/profiler` when `APP_CACHE_DIR` is set; `extensions.php` enables the two packages; `AGENT_INSTRUCTIONS.md` is what `discover` writes from the extensions' instructions, together with the marked block in `AGENTS.md` that points to it). No project tools exist, so there is no scan folder, and `mate.env_file` keeps its default (none), so Mate loads no env file of its own. `discover` also writes skill copies to `.agents/skills/` and `.claude/skills/` and a root `CLAUDE.md` that imports `AGENTS.md`; `.gitignore` keeps out `/.agents/`, `/.claude/skills/` and `/CLAUDE.md` (`tests/Application/MateGeneratedFilesTest.php` checks it). It rewrites the committed `mate/extensions.php` (adding per-skill state) and `mate/AGENT_INSTRUCTIONS.md` as well; those rewrites are not committed. Mate lists the packages from `vendor/composer/installed.json`, so without that file, or without `symfony/ai-mate` in it, it finds no tools either. `vendor/bin/mate tools:list` shows six tools: `server-info`, `symfony-dotenv-check`, `symfony-services`, `symfony-service-detail`, `symfony-profiler-list` and `symfony-profiler-get`. The profiler tools list and read the profiles the dev install saves (see the profiler section below); `symfony/web-profiler-bundle` is not installed, so there is no toolbar and no `/_profiler` page. The container tools read the app's compiled dev container under `var/cache/` (they ask for `bin/console cache:warmup` when there is none) and the dotenv check reads the app's `.env*` files, so they report what the app really has, not a guess from the code. Reading a profile through Mate works against a running dev instance: a request answers with `X-Debug-Token`, `symfony-profiler-list` then lists the profile and `symfony-profiler-get --token=<token>` returns its URL, status code and the four collectors with a `symfony-profiler://profile/<token>/<collector>` URI each. The tools read `var/cache/dev/profiler/` (the extension's default), or `$APP_CACHE_DIR/dev/profiler/` when `APP_CACHE_DIR` is set, which is where the kernel then saves them. `bin/instance` keeps the app's cache in its scratch folder and passes `APP_CACHE_DIR` to the command it runs, so Mate reads an instance's profiles when it runs as that command, for example `APP_ENV=dev php bin/instance -- sh -c 'curl -si "$INTAKT_INSTANCE_URL/"; vendor/bin/mate tools:call symfony-profiler-list --format=json'`; the scratch folder and its profiles are removed when the instance stops. The only Mate extension published for a bundle Intakt could use is `symfony/ai-monolog-mate-extension`, and Intakt has no Monolog; none exists for Doctrine or Messenger, so no further extension is installed. `tests/Application/MateInvocationTest.php` runs `vendor/bin/mate` and checks that the tool list offers `server-info`, `symfony-services`, `symfony-dotenv-check` and both profiler tools, that `server-info` reports this PHP, and that `symfony-profiler-list` lists a profile saved under the cache `APP_CACHE_DIR` names. Mate takes the project root from the real path of `vendor/autoload.php`, so a `vendor/` that is a symlink to a folder elsewhere leaves it without `installed.json` and `mate/extensions.php`, and it finds no tools; `upstream/ai-mate-symlinked-vendor-root/` reproduces this. The CLI is the entry point; no MCP server is configured. `AGENTS.md` says when to use it.

## Symfony profiler

FrameworkBundle's profiler (`framework.profiler` in `config/packages/framework.yaml`) is defined in two environments only:

- `dev`: it collects on every request, answers with an `X-Debug-Token` header and saves the profile in the default file storage under `var/cache/dev/profiler/`. The collectors that fill a profile are `db` (Doctrine DBAL's queries), `messenger` (the messages dispatched), `time` and `memory`, and no others, also with `APP_DEBUG=0`: Messenger defines its collector only in debug, so `config/services.yaml` defines `data_collector.messenger` again under `when@dev` and reuses that one definition under `when@test` through a YAML anchor, and `config/packages/doctrine.yaml` sets `dbal.profiling: true` under `when@dev` and `when@test`, whose default (`%kernel.debug%`) would leave `db` without its queries (`tests/Application/ProfilerAllowListTest.php` boots `dev` with and without debug).
- `test`: the profiler is defined with `collect: false`, so a request saves a profile only when its test client called `enableProfiler()`; the rest of the suite saves none (`tests/Application/SavedProfileSecretsTest.php`). Such a profile holds the same four collectors, and `db` counts the queries, also with `APP_DEBUG=0` (`tests/Application/ProfilerAllowListTest.php` boots `test` without debug). Two tests in the `persistence` group measure a request this way, on the SQLite ledger and the container's own buses: `tests/Core/Dashboard/UseCase/ReviewsPageQueriesTest.php` writes three rounds and asserts that `/reviews` runs 16 queries: reads of `ledger_event` (six, plus three per round) and the shell's one read of the owner notices for the You count, and `tests/Core/Dashboard/UseCase/StartReviewMessagesTest.php` presses the start of the next round and asserts the messages the post dispatches: `ReplayMarkOfRound` on `query.bus`, then `StartReview`, `RunReviewRound`, `RoundOpened` and one `ReviewWithReviewer` per reviewer on `command.bus`. Both reset the `profiler` service before the measured request, because a client that does not reboot its kernel would otherwise also count what the test's setup ran.
- `prod` sets no `profiler` key, so its container defines neither `profiler` nor `profiler_listener`. `tests/Application/ProfilerOutsideProdTest.php` boots `new Kernel('prod', false)` in the test process with a cache folder of its own and checks both are absent while `router` is there. No profiler package is installed in any environment: the profiler is part of `symfony/http-kernel` and FrameworkBundle, and `symfony/web-profiler-bundle` is not required, so there is no toolbar and no `/_profiler` page.

**A saved profile holds no secret.** Profiles are kept free of secrets with an allow-list of collectors, not by masking values, following the logging rule in [Conventions](conventions.md) (nothing secret in what the app writes down). `src/Core/Server/Infrastructure/ProfileOnlyRequestMeasuresPass.php`, registered in `Kernel::addApplicationPasses()` before optimization at priority 10 (after the autoconfiguration at 100 has tagged collectors, before FrameworkBundle's `ProfilerPass` at 0 reads the tags), removes the `data_collector` tag from every service whose tag `id` is not `db`, `messenger`, `time` or `memory`, also from a collector tagged without an `id`. The service itself stays defined, and since its tracing decorators (such as the serializer's) still feed it while only the profiler resets the collectors it registered, the pass tags it `kernel.reset` (method `reset`) unless it already has that tag, so no request sees the data of the one before (`tests/Application/SymfonyAiResetTest.php`). Where no `profiler` is defined (`prod`) it does nothing. So the request collector (headers such as `Authorization`, cookies, the session, server and environment variables, the body), the config, logger, security, HTTP client, AI and MCP collectors and every other one are never registered, and a collector that is never registered puts nothing into a saved profile: a new kind of credential needs no new rule. `tests/Application/ProfilerAllowListTest.php` checks that a saved dev profile's collectors are exactly the four; `tests/Application/SavedProfileSecretsTest.php` sends a rejected `/mcp/review` request with an environment variable, a `SERVER_` variable, an `Authorization: Bearer` header, a session cookie and a POST body field as canaries and finds none of them in the saved profile file. Beside the collectors, the profiler writes each profile's metadata (method, URL, client address, status code, time) into the profile file and the storage's `index.csv`. `src/Core/Server/Infrastructure/PathOnlyProfilerStorage.php` decorates `profiler.storage` (`#[AsDecorator]` with `IGNORE_ON_INVALID_REFERENCE`, so it is removed where no profiler is defined) and, before each write, parses the URL as a `Uri\Rfc3986\Uri`, saves it without its query and fragment, and drops the client address, because a query string can carry a credential such as an `access_token`. A profile without a URL keeps none, and a URL that does not parse is saved as none rather than raw, since its query could not be found and removed. `tests/Application/SavedProfileSecretsTest.php` sends a query canary and a client address and finds neither in the saved profile; `tests/Core/Server/Infrastructure/PathOnlyProfilerStorageTest.php` also reads `index.csv`. The `db` collector keeps each query with its bound values and the `messenger` collector each dispatched message; no query or message of a profiled request is known to carry a credential. Adding a collector to the allow-list needs its own test that it saves no credential.
