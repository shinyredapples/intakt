## Measured use

Plan task T40, part 1 (design: [Budget and model planner](../design/05-architecture/06-budget-and-model-planner.md)). `src/Core/Budget/` keeps, per account, the latest measured use of each subscription window, so the start ceiling ([below](#start-ceiling-and-admission)) decides from what the vendor measured, never from an estimate.

- `Contract/` holds the typed surface: `MeasuredUse` (`record(WindowReading): ReadingOutcome`, marked `#[NoDiscard]`, and `of(Account, UsageWindow): ?WindowUse`), `UsageWindow` (backed enum `five-hour` and `weekly`, with each window's length in seconds; `UsageWindow::told()` names a vendor's window by its stated length in minutes or else by its reset, never by the vendor's own name for it: a reset more than five hours and at most a week ahead is the weekly window), `Usage` (the used percent and the reset time, or none), `WindowReading` (the `Account` from `Core/Ai/Contract`, the window and its `Usage`), `WindowUse` (the `Usage`, `takenAt` and `ageInSeconds`) and `ReadingOutcome` (`recorded`, `reset-already-passed`, `reset-beyond-window`).
- A used percent that is negative, not a number or infinite is refused when the `Usage` is built (`UsedPercentOutOfRange`); above 100 is kept as reported.
- `Infrastructure/DoctrineMeasuredUse` stamps a reading with the clock's moment (`ClockInterface`) as `takenAt` and refuses a frozen or wrong one: a reset time at or before now is `reset-already-passed`, one further ahead than the window's length is `reset-beyond-window`. A refused reading stores nothing, so the last good reading of that window stays. A reading without a reset time is kept without one.
- A reading belongs to one account and one window: rows are found by provider, account name and window as separate columns, so a reading is never applied to another account of the same provider, to the same account name of another provider, or to the account's other window. `of()` returns the latest reading (latest `taken_at`, then highest `position` within one second) with its age on the clock at the moment of the call, or null when the window has none.
- Readings are appended, never updated: `Domain/WindowReadingRecord` in the table `budget_window_reading` (`position` auto-increment primary key, `provider`, `account`, `usage_window`, `used_percent`, `resets_at` nullable and `taken_at` in UTC through `utc_datetime_immutable`, index `budget_window_reading_window`; migration `Version20261101160000`). After an insert the older rows of that account and window are deleted in the same transaction (issue #3226, below), so two workers recording one window at once need no lock of their own: a cleanup deletes only rows with an earlier `taken_at`, or the same `taken_at` and a lower position, so a worker whose cleanup runs after another worker recorded never deletes that newer reading, and a reading stamped earlier but stored after a fresher one (issue #2920) deletes nothing fresher; its own stale row stays until the next reading's cleanup, and `of()` passes over it. Two first readings of one window stamped in one second may both finish their cleanup before either commits on a read-committed engine (PostgreSQL, MySQL), each missing the other's uncommitted row, so both rows stay; `of()` reads the one with the higher position and the next reading's cleanup drops the other.
- `DoctrineMeasuredUse` checks a reset time with `UsageWindow::refusalOfReset(resetsAt, now)`, which the cooldown below shares.
- Not yet: nothing records a reading or a usage limit, and nothing asks the guard (below) before a call or a merge; the vendor plugins that turn Claude's rate-limit events and Codex's token counts into readings and usage-limit answers into recorded usage limits (a Codex usage-limit error already cools its account down through `AccountCooldowns`, see [AI providers](ai-providers.md)), and the owner controls that place a pause, are later tasks.
- `Contract/InstallWideFailures` (task #994, part 1) decides when `SharedHold::FailureBackOff` starts, from the causes Budget itself knows: `databaseFailed()`, `lockStoreFailed()`, `forgeCredentialsRefused()` and `handOverFailed()` (task #996) each start it, and `itemFailed(item, failure)` starts it for a full disk or when a second, different item fails with the same error within an hour; any other item failure is only recorded, so one item's failure never starts it alone. `Infrastructure/DoctrineInstallWideFailures` places the hold for 15 minutes through `Holds::hold()` and logs the cause as an error with the exception. It appends the item's failure first (`Domain/ItemFailureRecord`, table `budget_item_failure`, migration `Version20261106100000`; rows older than an hour are deleted on the next record) and reads the others after, so of two items failing at once at least one sees the other, without a lock. The error key is a SHA-256 hash of the exception class and message, each length-prefixed. `Domain/FullDisk` matches the system's disk-full text (`No space left on device`, `database or disk is full`) only on a Symfony Filesystem `IOException` or a DBAL exception anywhere in the chain, never on the message of another exception, because that can carry pull request text. `Watcher`'s `FailedHeads` calls `itemFailed()`, `forgeCredentialsRefused()` and `handOverFailed()` for a failed head and its `HeadLocks` calls `lockStoreFailed()` when taking or giving back a head lock fails (see [`Core/Watcher/UseCase/WatchPullRequests`](forge-contract.md)); nothing calls `databaseFailed()` yet. Tests: `tests/Core/Budget/Infrastructure/DoctrineInstallWideFailuresTest.php` (a second worker commits the other item's row between this item's insert and its read, forced by a `postFlush` listener).
- Tests: `tests/Core/Budget/Infrastructure/DoctrineMeasuredUseTest.php` (`persistence` group, a `MockClock`; a second worker on its own connection and entity manager records in the same second after the first worker read its clock and before its transaction, and the first worker's reading, stored last with the higher position, is the one that stays (a second worker's reading written on the same connection just before the cleanup, through the test middleware `AnotherWorkerWritesBeforeTheCleanup`, stands for a commit between the insert and the cleanup on a read-committed engine: the cleanup does not delete it); a worker whose clock is read before another worker stores a fresher reading stores its own last, and the fresher one stays the measured use until the next reading leaves one row) and `tests/Core/Budget/Contract/UsageTest.php`.

### Start ceiling and admission

Plan task T40, part 2. `Contract/StartGuard::decide(Account, int $callsRunning): StartDecision` (marked `#[NoDiscard]`) answers whether one more call may start on an account; it takes no estimate, so measured use alone decides. `StartDecision` is a backed enum: `start`, `at-ceiling`, `no-trusted-reading`, `reading-not-fresh-enough`, `no-margin-for-parallel-start`, and the holds of part 3 ([below](#cooldowns-shared-holds-and-outage-notices)) `cooling-down`, `budget-backed-off`, `paused`, `failure-backed-off`, `draining`, and `halted` for a watchdog halt (#1690); `admits()` is true for `start` only.

- `Domain/CeilingStartGuard` holds the measured-use rules; `Domain/BudgetGuard`, the alias of `StartGuard`, asks it once no hold refuses (part 3). It reads `MeasuredUse::of()` for the account's own two windows only, so a reading of another account, of the same or another provider, never counts. A reading whose reset time is at or before the clock's moment (`ClockInterface`) is dropped, since its window has reset; a reading without a reset time is dropped once its age reaches `UsageWindow::seconds()`, since its window has reset at least once by then.
- Rules, in order: any kept reading, of any age short of its reset, at or above its window's ceiling is `at-ceiling` (use only grows until the reset, so an old reading is a lower bound); with no call running, `start`; a window without a reading, or one older than `TRUSTED_FOR_SECONDS` (1800), is `no-trusted-reading`; one older than `PARALLEL_TRUSTED_FOR_SECONDS` (300) is `reading-not-fresh-enough`; a window at or within `PARALLEL_MARGIN` (10 points) of its ceiling is `no-margin-for-parallel-start`; otherwise `start`.
- A window's ceiling is a chain with the pipe operator: the owner's ceiling, then (five-hour only) the weekly pace, then the margin for a parallel start. The pace is the weekly ceiling times `min(1, (elapsed + 5 h) / 7 d)`, the elapsed part of the week taken from the weekly reading's reset time; while the weekly use is above the pace, the five-hour ceiling is multiplied by pace / weekly use. Without a weekly reset time there is no pace.
- Ceilings are owner config: `config/packages/ai.php` takes the `budget` key off the root of `config/intakt.yaml` (so the projects tree never sees it) and processes it with `Infrastructure/BudgetConfiguration` (`budget.ceilings.<UsageWindow value>`, a float from 1 to 100, default `DEFAULT_CEILING` 90, keys not normalized, unknown keys refused; a NaN is turned into a string before normalization so the type check refuses it, because Symfony Config before 8.2.0-BETA2 skipped every check for NaN, a bug fixed upstream, see `upstream/config-nan-skips-validation/`; the step is kept as a workaround) into the parameter `intakt.budget.ceilings`, keyed by `UsageWindow` value.
- The ceilings of the removed shadow mode are gone (issue #1477, part 2 of #1433): the tree has no `shadow_ceilings` key, so a file that still sets `budget.shadow_ceilings` is refused as an unknown key and stops the boot (see [Mode per project](capability-tiers.md#mode-per-project)).
- Tests: `tests/Core/Budget/Domain/CeilingStartGuardTest.php` (one rule per test on a `MockClock`, with `tests/Core/Budget/ReadingsInMemory.php`), `tests/Core/Budget/ScriptedDayTest.php` (`persistence` group: a day of readings in `DoctrineMeasuredUse` and the decision at each step), `tests/Core/Budget/Infrastructure/BudgetConfigurationTest.php`, and cases in `tests/Application/ProjectTiersTest.php` (the file's ceilings reach the parameter; 120 stops the boot; a `shadow_ceilings` section stops the boot).

### Cooldowns, shared holds and outage notices

Plan task T40, part 3 (design: [Budget and model planner](../design/05-architecture/06-budget-and-model-planner.md), [Owner controls](../design/05-architecture/13-dashboard.md#controls)). `Contract/Holds` keeps what holds work back besides measured use; `Infrastructure/DoctrineHolds` is its alias.

- `coolDown(Account, DateTimeImmutable $resetsAt): ReadingOutcome` (marked `#[NoDiscard]`) is for a vendor's structured usage-limit answer only. The reset time is checked against `UsageWindow::longest()` (the week, found from the cases' lengths, since the answer names no window): at or before the clock's moment is `reset-already-passed`, further ahead than the week is `reset-beyond-window`, and either cools nothing down. A kept one is appended to `budget_account_cooldown` (`position`, `provider`, `account`, `until`, `placed_at`; index on provider and account). `isCoolingDown(Account)` is true while any row of that provider and account name lies ahead of the clock, so a later limit never shortens a running cooldown, and another account of the same or another provider is never held. Unlike the one-day cooldown of `Core/Ai` after a provider's rate limit ([AI providers](ai-providers.md)), it lasts until the reset, a week at most.
- `hold(SharedHold, DateTimeImmutable $until)` appends to `budget_shared_hold` (`position`, `hold`, `until`, `placed_at`); `sharedInEffect()` lists the holds with a row ahead of the clock, in the order of the `SharedHold` cases: `drain`, `failure-back-off`, `pause`, `budget-back-off`. `SharedHold::holdsMerges()` is true for `drain` and `failure-back-off`. A shared hold holds every account.
- `Domain/BudgetGuard::decide()`: a watchdog halt first, `halted` while `Watchdog/Contract/Halts::standing()` lists any owner card, of any project, because a start names no project yet ([Watchdog over main](watchdog.md#the-halt-and-the-owner-card)); else the first shared hold in effect gives its decision (`draining`, `failure-backed-off`, `paused`, `budget-backed-off`); else an account in cooldown is `cooling-down`; else `CeilingStartGuard` decides. `decideMerge(): StartDecision` (on `StartGuard`, marked `#[NoDiscard]`) is `halted` on the same condition, else the first shared hold that holds merges, else `start`: an approved head lands through a budget back-off, a pause (as the design's pause control says) and any cooldown, never through a watchdog halt, a drain or a failure back-off. `intakt:budget:replay` builds its guard with the install's `Halts`, so a card standing on the install now shows as `halted` in a replay of any day, whatever cards the scripted day had. `DayReplay` is the only caller of `decide()` and `decideMerge()` so far; no step or merge consults them yet.
- Outage notice: on each `decide()` the guard asks `Domain/OutageWatch::watch(Account)`; when the newest reading of the account's windows by its stored moment (`MeasuredUse::of()`, reset or not; the latest `takenAt` wins, not the smallest `ageInSeconds`, since each window's age is sampled at its own clock reading) is at least `OutageWatch::OUTAGE_SECONDS` (3 hours) old, it dispatches `Domain/UsageReadingsStayedAway` (the account, the `takenAt` of that reading, the clock's moment) through the event dispatcher. An account with no reading has no outage. `Infrastructure/DoctrineOutageNotices::noticeOnce()` (`#[AsEventListener]`) takes the lock `budget-outage-notice-<account key>` without waiting (busy means another worker is noticing it), and unless `budget_outage_notice` (`position`, `provider`, `account`, `last_reading_at`, `noticed_at`; unique index `budget_outage_notice_outage` on provider, account and last reading) already holds that outage, logs at warning level `No usage of account {account} has been read since {since}, so only one call at a time runs on it.` and then stores it. A warning that fails stores nothing, so the next `decide()` tries it again; a crash between the warning and the row repeats the warning once. One outage gives one notice; a new reading followed by a new outage gives another. Notices do not go through `Plugin/Notifier` yet (plan T67). The planner's own token accounting refusing after an outage is not built.
- Owner notices in force (issue #2892): `Contract/OwnerNotices::stillRunningOldestFirst(): list<OutageNotice>` lets other modules read the owner notices still in force without the Budget tables; `Infrastructure/DoctrineOwnerNotices` is its alias. Until the owner notice records of plan task T67 (#349) exist, the only owner notices are the outage notices: a `budget_outage_notice` row is listed while its `ended_at` is empty and no `budget_window_reading` row of the same provider and account name has a `taken_at` after its `last_reading_at` (a `NOT EXISTS` subquery), ordered by `noticed_at`, then `position`. Comparing with the reading the outage started from, not with `noticed_at`, keeps a reading that lands while the outage is being noticed, or one stamped earlier but stored later, from leaving the outage listed. `OutageNotice` holds the `Account`, `lastReadingAt` and `noticedAt`. Nothing is deleted: a page that lists them drops the item on its next load. A notice with a saved end never returns to the list, even once the reading that ended it is removed. Only a notice with no saved end (one that ended before the column below existed) depends on the readings alone: it is listed again if the newer reading of its account is later removed. The cleanup of old readings never does that, since it removes a reading only for one of the same window stamped no earlier, which ends the outage as well, even when the older-stamped reading is stored last. A reading of the same account name at another provider, or of another account, ends nothing. The board page calls it on each load; the Waiting on you page reads the same notices through the one read below.
- Owner notices ended (issue #3225): the nullable column `budget_outage_notice.ended_at` (`OutageNoticeRecord::$endedAt`, migration `Version20261121110000`) keeps the moment of the reading that ended the outage, because only the latest reading of a window stays stored. `DoctrineMeasuredUse::record()` sets it, in one `UPDATE` with no lock after the reading is stored and the older readings are dropped, on every notice of the reading's provider and account name whose `last_reading_at` is before the reading's `taken_at`, whose `ended_at` is empty or later, and whose `last_reading_at` is not before the latest other reading of that account taken before this one (read before the cleanup drops it). So the earliest reading wins when a slow writer stores an earlier one late, and a notice an earlier reading already ended keeps its end. When a reading of that account taken after this one is already stored, only notices with a saved end are moved to this reading's moment: that fresher reading ended every outage before it when it was stored, so a notice it left with no end is from before the column existed, and a reading stored late gives it none, also when no earlier reading of the account is stored to guard by (issue #3226).
- Stored and ended together (issue #3226): `DoctrineMeasuredUse::record()` stores the reading, drops the older readings and ends the outages in one transaction of the connection (`Connection::transactional()`, not `wrapInTransaction()`, which closes the entity manager on a failure). A failed end rolls the reading and the dropped readings back too, so the notice stays waiting, the earlier reading stays the latest, and the next reading ends the outage; the rolled-back reading is detached from the entity manager, because the database may give its `position` to the next one. Only after the commit, only when an `UPDATE` ended or moved at least one notice, and not when the caller already holds a transaction (its rollback could erase an end a listener heard of, so its owner announces; the budget replay never does), it dispatches `Contract/OwnerNoticesChanged` (no fields; a listener reads the notices again through `OwnerNotices`) through Symfony's event dispatcher; a failed end dispatches nothing. `DoctrineOutageNotices` dispatches it too (#3369), once it stored a new notice and looked for its end (below), and the same way only when no caller holds a transaction, so the budget replay never does; an outage already noticed, or a worker that finds the notice lock taken, dispatches nothing. The dashboard's `LiveWaitingPage` listens to it and pushes the Waiting on you page ([Live updates](live-updates.md)). `DoctrineOutageNotices`, once the new notice row is flushed, looks for a reading after its last reading and ends the notice with the earliest one in the same kind of `UPDATE`, then looks again until the earliest reading is the same as the one it just ended with (also when a competing writer saved that end first and its own `UPDATE` moved no row), so a reading stored at any moment before the notice, also one stored while the end is being saved (which skips a notice with no end yet, as it cannot tell it from one that predates ends being kept), still gives the earliest end. A reading whose own `UPDATE` ran before the notice row existed but that commits only after the writer's last look (possible on a read-committed engine) is covered by the reading itself: outside a caller's transaction, after its commit, `DoctrineMeasuredUse` runs the same `UPDATE` once more, limited to notices with a saved end, and moves a later end to its moment (a notice with no end yet is left to its writer, which now sees the reading, or is from before ends were kept); a move it makes also dispatches `OwnerNoticesChanged`. Inside a caller's transaction this second `UPDATE` does not run. Two known limits remain on a read-committed engine, both left to #3293, which plans a per-account lock shared by both writers (SQLite serializes writers, so neither happens there): (a) when the account's only recovery reading runs its `UPDATE` before the notice row exists and commits after the notice writer's last look, the notice has no end for the second `UPDATE` to move, so it leaves the waiting list (the reading is after its last reading) but is missing from the notices ended that day; (b) when the second `UPDATE` fails after the commit, the reading and any ends the transaction saved stay committed, the error reaches the caller, and `OwnerNoticesChanged` is still dispatched for the ends the transaction saved, so a later end it would have moved stays. A notice ended before the column existed keeps no end and is only left out of the running list by its newer reading: a later reading does not end it, because the reading that ended it, or a newer one, is still the latest of its window. An outage whose recovery reading a late write removed before the upgrade is ended by the first reading after the upgrade, at that reading's moment, since before the upgrade it was already listed as waiting again. `Contract/OwnerNotices::endedOnTheDayOf(DateTimeImmutable): list<EndedOutageNotice>` (`account`, `endedAt`) lists the notices whose `ended_at` falls on the UTC day of the moment, newest first, then by `position` descending. Nothing calls it yet; the Waiting on you page's panels that show it are later parts of #3200.
- Waiting and ended in one read (issue #3227): `Contract/OwnerNotices::waitingAndEndedOnTheDayOf(DateTimeImmutable): OwnerNoticesOfTheDay` (`waitingOldestFirst: list<OutageNotice>`, `endedNewestFirst: list<EndedOutageNotice>`) returns both lists above from one `SELECT` over `budget_outage_notice`, because a recovery committed between two queries would list one outage as both waiting and ended. The statement selects columns, not entities, and keeps the rows whose `ended_at` is empty with no later reading (the same `NOT EXISTS` subquery as the running list) or whose `ended_at` falls on the UTC day of the moment, ordered by `noticed_at`, then `position`; PHP splits them: a row with no end is waiting, in that order, and a row with an end is ended, sorted by `ended_at`, then `position`, both descending. So each list matches the read of its own above, and a notice ended on another day, or one with no end whose newer reading is stored (from before ends were kept), is in neither. The Waiting on you page calls it once on each load, for its items and its "You handled today" panel (#3201, see [Dashboard](dashboard.md)).
