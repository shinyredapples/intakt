## MCP server for the owner

Module `Core/Mcp` (plan task T15, part #508) wires the MCP Bundle's server `owner` (`config/packages/mcp.yaml`): HTTP at `/mcp/owner` (route type `mcp` in `config/routes/mcp.yaml`), name `intakt`, file session store with `session.lock` on, and the tools of the namespaces `Core\Ai\UseCase\ListProjects`, `Core\Review\UseCase\ReadRound` and `Plugin\LocalGitForge\UseCase\ReviewChange` in its registry (listed by namespace because a prefix of all Intakt would also serve the review server's tools; the bundle fails the build for a pattern that matches nothing, so the test environment adds the test tools' namespace). Over HTTP the bundle needs a PSR-17 implementation, which `guzzlehttp/psr7` supplies. The SDK's default DNS rebinding protection stays: only the hosts `localhost`, `127.0.0.1` and `[::1]` are accepted.

**Review server (plan task T16, part #578).** A second server, `review` (name `intakt-review`), is served at `/mcp/review` with its own file session store (the bundle refuses two servers that share one) and `session.lock` on. Its registry is the namespace `Core\Review\UseCase\ServeReviewTools` and nothing else: `read_file`, `list_directory` and `search_files`, each with the SDK annotations `readOnlyHint: true`, `destructiveHint: false`, and `#[IsGrantedTool(ToolAccess::Read)]` because `AuthorizedToolCalls` wraps every server and refuses a tool without one (the voter decides for this server as for the owner's, see Tool safety below). The round comes from the request's credential, never from a tool argument: no tool takes a round. `ReviewCredential` (an `AccessTokenHandlerInterface`) issues a credential `<round id>.<HMAC-SHA256 of a purpose label and the round id, keyed with %kernel.secret%>` and accepts only one whose round is a UUID and whose signature matches (`hash_equals`); with an empty `APP_SECRET` it issues none and accepts none. `config/packages/security.yaml` has a stateless firewall `mcp_review` on `^/mcp/review` with the `access_token` authenticator and that handler, which logs the round in as a user named after the round id with `ReviewCredential::REVIEWER_ROLE`, and an `access_control` entry that requires that role on `^/mcp/review`, so a request without a valid credential, the owner token included, gets 401; from Symfony 8.2 the access-token authenticator is the firewall's entry point, so a request without any credential gets that 401 with a `WWW-Authenticate: Bearer` challenge (`ReviewServerContractTest::testARequestWithoutACredentialIsAnsweredWithABearerChallenge`). `php bin/console intakt:review:issue-credential <round>` (`IssueReviewCredentialCommand`) prints the path and the credential of a round under review and refuses an unknown or judged one; the reviewers' MCP client gets the credential from `ReviewServerHttpClient` (below). `ReviewedRepository` takes the round id from the Security user (only with the reviewer role), loads the stored round, refuses an unknown or judged round (the snapshot of a judged round is removed) with an MCP tool error, and builds the `Checkout` of that round's snapshot, which refuses paths outside it and `.git`; a snapshot that is gone (`Contract\CheckoutNotADirectory`) is the tool error `The head of this round is not available.` A tool call is refused as an MCP tool error only for the failures the tools name: `PathNotInCheckout` and `PathOutsideCheckout` from `Checkout::resolve()`, `Infrastructure\Repository\PathNotReadable` (a path that is no file or no directory, is not UTF-8 text, or cannot be read, listed or searched, such as a pipe) and `SearchTextEmpty`; any other exception passes through and fails the request. It wraps every answer in `Fence` as `UntrustedSource::ToolResult` (a refusal too, because its text can name the path the reviewed code chose, as in `"<path>" is not a file.`), because the `claude_code` and `codex` CLIs call the server themselves and put the answer into their prompt as it comes; it does not cut an answer. Once the round's head is resolved, it records every call it answers, a refusal included, as a row of `round_tool_call` (`RoundToolCalls`, under the tool's name from the tool's `NAME` constant, which its `#[McpTool]` attribute uses too), with the path only for a `read_file` it answered with the file, relative to the checkout as the checkout resolved it (`Checkout::relative()`), so `README.md` and `./README.md` record one path. After each recorded call `ReviewedRepository` calls `RoundUpdates::summaryChanged()` (see Summary updates in [Live updates](live-updates.md)). `read_file` resolves the path once (`Checkout::resolve()`) and reads that resolved file (`ReadFile::contentAt()`) as well as records it, so the file read and the file recorded cannot differ. Recording is best effort: when the insert fails (a DBAL or ORM exception), `RoundToolCalls` logs the error "A tool call of the review server was not recorded; it is answered anyway." with the `round`, the `tool` and the `exception`, and the call keeps its answer, or its refusal; the session summary counts the rows (see Session summary under [Reviewer agent](reviewer-agent.md)). A call refused before that (no credential, an unknown or judged round, an unavailable head) is not recorded. The tools run the same `ReadFile`, `ListDirectory` and `SearchFiles` classes as the in-process toolbox, with the same arguments (`search_files` takes `text` and an optional `path`). `search_files` sends an MCP progress notification (when the call carries a `progressToken`) after every tenth file searched, through the optional `$fileSearched` callback of `SearchFiles`. Reviewers reach the server as described in Reviewers over MCP below. Tests: `tests/Core/Review/UseCase/ServeReviewTools/ReviewServerContractTest.php` (group `persistence`) talks to the kernel over HTTP with a round's credential: the listing, the annotations, reads at the head, the fence around every answer and around a refusal that names its path, refused paths, one session that names another round in its arguments and still sees only its own, another round's credential that sees that round, 401 without a credential, with a signature of another round and with the owner token, an unknown and a judged round, and the progress notifications; `ReviewedRepositoryTest` (group `persistence`) calls `ReviewedRepository` with a signed-in round: a gone snapshot, the named refusals other than a path outside the checkout (`PathOutsideCheckout` is covered by the refused paths of `ReviewServerContractTest`), and an unexpected exception from a search or from loading the round for its head passing through instead of becoming a tool error; `IssuedReviewServerAccessesTest` shows that only the missing secret blocks an access and any other exception passes through; `SearchFilesTest` covers the empty text and a pipe that cannot be searched, and `SearchFilesVanishingFileTest` a file whose size cannot be read; `ReviewCredentialTest` and `IssueReviewCredentialCommandTest` cover the credential and the command.

**Reviewers over MCP (plan task T16, part #580).** `config/packages/mcp.yaml` configures the MCP Bundle client `reviewer` (client name `intakt-reviewer`) with one HTTP server, `review`, at `%env(REVIEW_MCP_BASE_URL)%/mcp/review` (the parameter `ReviewServices::MCP_URL`, set in `mcp.yaml` and given to the connection in `config/packages/ai.php`, because YAML could name it only by spelling it; the `claude_code` and `codex` reviewers get the same parameter through `IssuedReviewServerAccesses`, whose `ReviewServerAccess` `IsolatedClaudeCodeCli` and `IsolatedCodexCli` turn into each CLI's MCP server; default `http://localhost:7780` in `.env`; the image sets `http://localhost:7781`, its `SERVER_PORT`; outside the image, set it to the address the web server listens on, for example `http://localhost:8000` with `php -S localhost:8000 -t public`). `config/packages/ai.php` configures the AI Bundle agent `reviewer` with the tool entry `mcp_server: reviewer.review` and the prefix `review_` (`ReviewerMcpToolboxFactory::TOOL_PREFIX`), so the bundle builds the `McpToolbox` (package `symfony/ai-mcp-tool`) service `ai.toolbox.reviewer.mcp.reviewer.review` with the tools `review_read_file`, `review_list_directory` and `review_search_files`. Only that toolbox is used: `ReviewerAgent` still builds the `Agent` of each review on the platform and model of its tier, so the configured agent's platform is `PlatformChosenPerReview`, which throws when called. A configured connection takes fixed headers, and the credential names one round, so the connection's `http_client` is `ReviewServerHttpClient`: it adds `Authorization: Bearer` with `ReviewCredential::issueFor()` for the round that `during($round, $call)` sets for the length of one call (`reset()` clears it too), and refuses (`LogicException`) a request outside such a call. `ReviewerMcpToolboxFactory::create(ReviewRequest)` returns `ToolsOfRound`, which lists and calls the tools inside `during()` for the round of `ReviewerConversation::round`; a request without a round is refused with a `LogicException`. One connection serves every review of a process (the bundle closes it on kernel reset), which shows no review another's head, because the server takes the round from the credential of each request. The rest of the reviewer path is unchanged: `FaultTolerantToolbox`, the fence around tool results and the verdict checks. `DenyPathsOutsideCheckout` runs only in the in-process twin, because the server already refuses paths outside the head. `MalformedToolCalls` also counts an invalid-params error of the server (a missing or wrongly typed argument) as a malformed call, so such a review still ends as a `VerdictUnreadable`. When the server cannot be reached, `McpToolbox` logs the failure, lists no tools and skips the server for 60 seconds; `ReviewerAgent` then returns `Verdict::noTools()` before the model is asked: a `blocked` verdict whose finding `no-tools` (fixable by the owner) gives the reason, a failed review that adds nothing to the ledger. The tool list stays cached once listed, so a server lost later fails only the calls: `ToolsOfRound` passes on only what the server answers about the call (a `ToolErrorException` of the tool, or a `RemoteCallException` carrying a `RequestException` with the invalid-params code `-32602`, the server's answer to an unknown tool or invalid arguments) and turns any other failure of a call into `ReviewServerLost`, including the protocol errors the SDK client makes of an HTTP error status (`401`, `500`), an unreadable body or the server's internal error, which is neither a tool execution failure nor a `RuntimeException`, so neither `FaultTolerantToolbox` hands it to the model nor `VerdictParser` reads it as an unreadable answer; `ReviewerAgent` ends that review as `Verdict::noTools()` as well. The 60-second skip applies to listing only: after a failed call the next call goes to the server at once. `tests/Core/Review/Infrastructure/ReviewerOverMcpTest.php` takes the factory from the container with a second kernel as the HTTP server (the kernel under test resets its services, `ReviewServerHttpClient` included, before each request it handles), runs one scripted model through both toolboxes and compares the verdicts, checks that every request carries the credential of its own round and that none is sent outside a review, that an unreachable server and a server lost after listing its tools block the review, that the next review after a failed call reaches the server again without waiting, and that a tool error the server answers stays with the model.

- **Tool safety:** tools carry the AI Bundle's `#[IsGrantedTool]` (`Symfony\AI\AiBundle\Security\Attribute\IsGrantedTool`) with a `ToolAccess` value (`mcp_tool_read` or `mcp_tool_write`, from `Core/Mcp/Contract`) as its attribute. The AI Bundle checks that attribute only in its agent toolbox, on `ToolCallArgumentsResolved` events, which an MCP tool call never raises, so Intakt checks it itself. `AuthorizeToolCallsPass` (added by `Kernel::addApplicationPasses()` after the bundle's own pass; `Kernel::build()` and the test kernels `WorkerKernel`, `UnrestoredKernel`, `AiPlatformKernel` and `ToolTimeLimitKernel` (`tests/Core/Build/UseCase/RunBuildJob/ToolTimeLimitKernel.php`) all call it, so they share one list of the application's compiler passes) wraps the SDK's reference handler of every server, also one without a handler locator, in `AuthorizedToolCalls`. It reads every `#[IsGrantedTool]` on the tool's class and method and asks `security.authorization_checker` about each, never passing a subject. A tool without the attribute, one whose attribute names a subject (a subject is built from the call's arguments), or one that is refused does not run. Each decision goes to the `logger` service: a granted call at info (`Tool call {tool} granted.`, with the handler as `tool` and the attribute as `access`), a refusal at warning (`Tool call {tool} refused: ...`); the arguments are never logged, because a model chose them. A review credential carries only `ReviewCredential::REVIEWER_ROLE`, so on the review server `Write` is refused even when `$highestAllowed` allows it, and arguments naming the owner role change nothing (`ToolAccessVoterTest`). `ReviewServerContractTest` also pins the review server's protocol negotiation (the version of Claude Code echoed, an unknown version answered with one the server speaks) and that no tool schema encodes `properties` as `[]`. `ToolAccessVoter` grants `Read` always and `Write` only when its constructor argument `$highestAllowed` is `ToolAccess::Write`; it receives no tool arguments, so a model cannot argue its way to a write. `Write` additionally needs the token of the request: the voter grants it only when the Security token carries `OwnerTokenHandler::OWNER_ROLE`. For the owner server, `config/packages/security.yaml` has the stateless firewall `mcp_owner` on `^/mcp/owner`, with the `access_token` authenticator (bearer header) and `OwnerTokenHandler`, which compares the header with `MCP_OWNER_TOKEN` through `hash_equals` and refuses everything while that variable is empty. There is no `access_control`, so a request without a header reaches the read tools unauthenticated; a wrong token fails the whole request (401). `$highestAllowed` is `%env(enum:...ToolAccess:MCP_OWNER_ACCESS)%` (`mcp_tool_read` by default in `.env`). The token never comes from tool arguments, and the voter still receives none.
- **Review skill:** `skills/intakt-review/SKILL.md` is a Markdown skill for Claude Code and Codex that runs the review loop through the owner server; it adds no runtime code. Its `## Tools` section lists each tool with its argument names, and `tests/Core/Mcp/Contract/ReviewSkillMatchesServerTest.php` (group `persistence`) checks them, and every tool name in the skill's text, against the server's `tools/list` (the arguments of `start_review` sit inside its `review` object) and that every required argument is named.
- **Route name:** the bundle names the owner server's route `_mcp_endpoint_owner`; no page links to it (the first-run page shows no MCP address since #3330).
- **Errors:** a refusal is a `ToolCallException`, which the SDK sends as a tool result with `isError`; any other exception in a tool is sent as an internal error with a short fixed message. Neither carries a stack trace (the details go to the log).
- **`list_projects`** (`Core/Ai/UseCase/ListProjects`) returns the names from `TierResolver::projects()` as `{"projects": [{"name": "alpha", "mark": "live"}, ...]}` (`ListedProject`, `#[Exclude]`d), where `mark` is the `ReplayMark` that the `ReplayMarkOfProject` query of Review's `Contract/` answers over the query bus for each name, annotated `readOnlyHint: true`, `destructiveHint: false`, with `#[IsGrantedTool(ToolAccess::Read->value)]`. It has no parameters and the SDK encodes that as `"properties":{}`.
- **Tests:** `tests/Core/Mcp/Contract/` talks to the kernel as an agent does: initialize with Claude Code's revision `2025-11-25` gets it back, an unknown revision gets one the server speaks, `tools/list` carries `"properties":{}` and the read-only annotations, `list_projects` answers (the round tools below have their own contract test), and an unknown tool is an error without a trace. `ToolAuthorizationContractTest` calls a write tool that only the test kernel serves (`tests/Core/Mcp/services.yaml`) and gets the refusal as an MCP error, so the wrapper is proven in the running server. `tests/Core/Mcp/Infrastructure/` covers the voter, the wrapper and the pass.
- **Round reads** (`Core/Review/UseCase/ReadRound`, part #509; the registry in `config/packages/mcp.yaml` lists `resource_templates` as well as `tools`): three tools, each read-only (`readOnlyHint: true`, `destructiveHint: false`) with `#[IsGrantedTool(ToolAccess::Read->value)]`, taking one `roundId` string that the listing describes as `UUID of the review round.` (the MCP SDK's `#[Schema]` on the parameter). The answers they build per call (`RoundStatus`, `RoundIdentity`, `ReviewerStatus`, `ReviewerIdentity`, `RoundVerdicts`, `GivenVerdict`, `RoundActList`) are `#[Exclude]`d from the container. Each of the three also carries `mark`, the round's `ReplayMark` (`live` or `replay`, from `ReviewRound::replayMark()`), so a recording played back shows as one. `review_status` returns a `RoundStatus`: `round` (a `RoundIdentity` of id, change and number), the round's `state` and `reviewers`, each a `ReviewerStatus` of `reviewer` (a `ReviewerIdentity` of role and tier), `state` and `failure`, and `dropped`, the `Review\Contract\DroppedFinding`s (`id`, `severity`, `text`, `file`, `line`, `reason`, `gateGap`, the dropped finding's gate-gap mark, and `nearest`, a list of `QuoteNearLines` of `quote` and `lines`, each a `NearLine` of `file`, `line` and `text`; see [Review flow](review-flow.md)) the quote check dropped before the judge: once the round is `judged`, `RoundStatusTool` reads them from the round's `judge_done` ledger event with `RoundLedgerReading::droppedOf()`; before that the list is empty, and a `judge_done` row written before drops were recorded reads as none. `review_verdicts` returns the `PanelVerdict`s stored by `StoredVerdicts::of()`, each as a `GivenVerdict` of `tier` and `verdict`, the reviewer's answer document (`Infrastructure/ReviewerAnswer/Verdict::fromVerdict()`), so `resolved` and `follow_ups` are lists of strings as the reviewer wrote them; it applies no standing rule, because that needs the forge's head move (`UseCase/ReadVerdicts` does that for callers that have it). `review_act_list` returns a `RoundActList`: once the round is `judged`, the reported findings (`StoredFindings::reportedIn()`) whose ids the `judge_done` ledger event lists under `act` (read with `RoundLedgerReading::judgeDoneOf()` and built by `StoredFindings::actListOf()`, the same list as `ReviewChange`); before that `judged` is false and the list empty. An entry for a P1 or P2 the judge rejected or deferred carries `judge_note`, the judge's reason as recorded in `judge_done`, wrapped in the fence (`<<<UNTRUSTED act list fence-...>>>`) because it is a model's text; an entry that merged other findings (at its place or by a cause link) keeps its own note, otherwise the first note of a finding it merged (`OnePerPlace`), so it carries at most one; an entry without a note has no such key (`RoundActList` and `StartedReview` write their entries through `Review\Contract\ActEntryAnswer`, see Judge note in [Review verdicts](review-verdicts.md)). The resource template `intakt://rounds/{roundId}/findings` (`RoundFindingsResource`, `application/json`, also behind `IsGrantedTool`, which the wrapper checks for resources too) returns the reported findings as JSON. `ReadableRounds` loads the round through `ReviewRounds::stored()` and turns `RoundNotFound` into a `ToolCallException` (an MCP tool error with the message) or, for the resource, a `ResourceNotFoundException`; neither carries a stack trace. Tests: `tests/Core/Review/UseCase/ReadRound/ReadRoundToolsTest.php` (real rounds, judged by a scripted judge) and `tests/Core/Mcp/Contract/RoundReadContractTest.php` (the same through the kernel as a client calls it: annotations, the `roundId` description, answers, resource listing and read, errors); both are in the `persistence` group.
- **`start_review`** (`Plugin/LocalGitForge/UseCase/ReviewChange/StartReviewTool`, part #510; it lives in the forge plugin like `intakt:review`, because core Review may not read a local repository): `readOnlyHint: false`, `destructiveHint: true`, `#[IsGrantedTool(ToolAccess::Write->value)]`. Input is one object argument, `review`, because the repository allows at most three parameters and the SDK does not map objects (its `#[Schema]` declares `project`, `task`, `change`, `repository`, `base`, `round`); the tool checks the values itself, and an empty one or a round below 1 is a `ToolCallException`, as is any `ReportableFailure` (for example `RoundNotNext`, or `RoundTierNotMapped` for a project that maps no model to a tier the round needs, see [Review flow](review-flow.md#refused-before-it-starts)). The snapshot, request and review path is `LocalChangeReview`, shared with `ReviewChangeCommand`, which also owns the stop-signal cleanup. The tool waits for the round, because the snapshot is removed when the call returns, and answers with a `StartedReview` (round id and number, decision, act list with a fenced `judge_note` on an entry that has one, as in `review_act_list`, reasons and `end`, the `ChangeReview::$end` value of `Review\Contract\RoundEnds`: `judged`, `judging_failed` or `no_outcome_in_time`). `ChangeReviews::review()` takes a `ReviewProgress` (default `IgnoredProgress`) and `ReviewChange` reports a `RoundProgress` (reviewers started, reviewers finished, reviewers, judged) on every poll. `ForwardedProgress` sends it through the SDK's `ClientGateway::progress()` (a no-op without a `progressToken`) when the step moved: reviewers finished, plus one for the judge, out of reviewers plus one.
- **SDK client test:** `tests/Core/Mcp/Contract/OwnerServerSdkClientTest.php` (group `persistence`) uses the MCP SDK's own `Mcp\Client` over `HttpTransport` with a PSR-18 client (`KernelHttpClient`) that hands the requests to the kernel. It lists and calls every tool and reads the findings resource, and covers the start tool with the token, reading the started round's act list back through `review_act_list`, the progress notifications, the refusals (no token, wrong token, token with config at read, token as an argument) and the MCP errors. In the test's own setup (it swaps the doubles into its container after each boot, so no other kernel test gets them; they are defined in `tests/Core/Mcp/services.yaml`) `ChangeReviews` is the real `ReviewChange` on a stored round, with a panel of one (`OnePanel`), a scripted vendor (`OneFindingVendor`) and a clock (`WorkersOnSleep`) whose every sleep hands the queued reviewer and judge messages to their handlers, so no worker process is needed. `ToolAccessVoterTest` and `OwnerTokenHandlerTest` cover the rule and the handler.
- **Worker:** the `mcp` worker of the container image serves `/mcp/*` (see [Container image](container-image.md)).
