# Build task

Plan task T56, parts 1 (#2037) and 2 (#2025). `php bin/console intakt:build:task <project> <issue> --remote=<remote> --branch=<branch> --directory=<folder> --image=<image>` (`BuildTaskCommand`) calls `UseCase/BuildTask/BuildTask::run(BuildTaskRequest): BuildTaskOutcome` (marked `#[NoDiscard]`) in `Core/Build`. The build lane (#1568) will call the same use case; it holds no slot, queue, admission, schedule or state machine, and one run builds one task. The remote, the branch, the folder and the job image are options the caller gives, as the single commands take them as arguments; no naming scheme derives them.

## The steps

1. **Task:** `IssueReads::listOpen(<project>, null)` (the GitHub forge's contract) lists the open issues and the run takes the one numbered `<issue>`. The caller names the issue, so the eligibility and order rules of intake do not apply. A pull request of that number is no task; a forge read that fails (`ForgeReadFailed`, `ForgeRateLimited`) or an issue the listing lacks ends the run here. The result holds the `ListedIssue` (title and body, untrusted text) for the steps that come later.
2. **Mirror:** `BuildCheckout::updateMirror(<project>, <remote>)`, the Git module's contract for [`intakt:mirror:update`](mirror.md).
3. **Clone:** `BuildCheckout::makeClone(<project>, <branch>, <folder>)`, the contract for [`intakt:build:clone`](build-clone.md), without a source line (whether the task's author may name one is not read here).
4. **Build job:** `RunBuildJob::run(BuildJob)`, the use case of [`intakt:build:run`](build-job.md), in `<folder>` on `<branch>` with `<image>`. The tier is the routing rules' choice: `BuildRouting::tierFor(<project>, BuildFacts::fromLabels(<the issue's labels>, []))`, so a `model:<tier>` label of the issue counts, with no paths and no setback (a first build has no file forecast and no earlier round). The brief is the issue's title, a blank line and its body, with no decisions and no rework; `BuilderPrompt` fences it. The step passes when the job hands back a bundle and the pull request text (`BuildVerdict::Built`); any other verdict fails it with `BuildVerdict::reason()` as its message (for example `the build made no commit on the task's branch`). A project without routing rules (`BuildRoutingNotConfigured`), a tier that does not resolve or is not on `claude_code` (`TierResolutionFailure`, `BuilderNotOnClaudeCode`), a clone that is no folder, a job the runner refuses (`JobRefused`), a failing engine (`DockerEngineFailed`), a job event the ledger did not record (`JobEventNotRecorded`) and a filesystem error fail it with their message. What the job hands back (the bundle, the pull request text and the log) is untrusted and goes nowhere yet; only the verdict reaches the ledger.

`Git/Infrastructure/GitBuildCheckout` implements `BuildCheckout` by calling `UpdateMirror::update()` and `MakeBuildClone::make()`; every failure of either (an invalid project or branch name, `MirrorNotUpdated`, `NetworkGitFailed`, `BuildCloneNotMade`, `RepositoryAttributesRefused`, a filesystem error, and for the mirror a failure of Symfony Lock such as a lock that cannot be acquired) becomes one `BuildCheckoutFailed` with the same message, so Build never imports a use case of Git. A failure of Symfony Process in either step (a local git call that is killed by a signal, runs into the 60 seconds a local call gets, or cannot run) becomes a `BuildCheckoutFailed` with fixed words (`git was killed by signal <n>`, `git timed out after <n> seconds`, `git could not run`; `BuildCheckoutFailed::stopped()`) and without the caught exception as its cause, because that exception's message holds the whole command line. Each of these is therefore a failed step with its event in the ledger, never an exception that leaves the run.

`run()` reads the task first, then runs the `BuildStep` cases in their declared order, so the enum is the one list of the steps. The run stops at the first step that fails, with that step's own message in `BuildTaskOutcome` (`last`, `failure`, `task`; `passedSteps()` lists the steps before it), and runs no later step. A run whose steps all pass ends after the build job, with `last` the `build_job` step and no failure. Nothing is retried here: a failure is recorded and the run ends. The steps after the build job (the hand-back check, the pre-push check, the signed push and the pull request) are later parts.

## The ledger

Each step appends one `LedgerEventKind::BuildStepEnded` (`build_step_ended`) event with the JSON payload `project`, `task` (the issue number as text), `step` (`task`, `mirror`, `clone` or `build_job`, a `Build/Contract/BuildStep` case), `outcome` (`passed` or `failed`, a `Build/Contract/BuildStepOutcome` case) and `failure` (the message, or null). The issue's title and body are never in the payload. A ledger that does not record an event stops the run with `BuildStepNotRecorded` before the next step. `intakt:status` shows the last of these events of each task in `lanes.build` (see [Status read model](status.md)), and the dashboard's task page `/tasks/<project>/<task>` shows the steps of the task's latest run (see [Dashboard](dashboard.md)).

## The door

The command prints `<step> passed` for each step that passed, then `title <title>` once the task was read, and for a failing step an error block `<step> failed: <message>` and exit code 1. An issue number that is not a whole number from 1 to 999999999, a missing `--remote`, `--branch`, `--directory` or `--image`, and a step the ledger did not record fail with a message and exit code 1.

The title is untrusted text, so it is never printed as it is: each control character (`\p{Cc}`: C0 such as ESC and BEL, DEL, and C1 such as CSI) is printed as `?`, because it would drive the operator's terminal, and the console formatter's tags are escaped (`OutputFormatter::escape()`). A title that is not UTF-8 keeps only its printable ASCII (`0x20` to `0x7E`), every other byte printed as `?`.

`GitHubIssueReads` is the container's `IssueReads` in `dev` and `prod`; in the test environment `tests/Core/Build/services.yaml` replaces it with `RecordedIssues`, which serves the file `BUILD_RECORDING` names (a JSON list of issues in GitHub's shape), so the command runs on an install without GitHub. The same file gives `RunBuildJob` the `ScriptedJobRunner` instead of `ContainerJobRunner`: it serves the files of the folder `BUILD_JOB_OUTPUT` names as the job's output (exit code 0), so the build job step runs without a container engine or a model. The review and check jobs keep the container runner.

Tests: `BuildTaskTest` (a failure at each step, a mirrors folder that cannot be created, a refused attributes file in the mirror step and in the clone step, a mirror lock that cannot be acquired, a git call killed by a signal in the mirror step and in the clone step, a pull request of the number, a ledger that does not record, a build job without a commit or without pull request text, a job the runner refuses, a project without routing rules, a failed clone that runs no job, the clone, branch, image and fenced brief the job gets, a `model:strong` label choosing the tier, all steps passing, over a local git remote with the scripted job runner), `BuildCheckoutFailedTest` (the fixed words of a process failure), `BuildTaskCommandTest` (the title's control characters, a failed build job and a missing `--image` among them).
