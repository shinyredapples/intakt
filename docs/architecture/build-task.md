# Build task

Plan task T56, parts 1 (#2037), 2 (#2025), the hand-back check (#2116), the pre-push check (#2117) and the push step (#2352, not yet in the order of steps). `php bin/console intakt:build:task <project> <issue> --remote=<remote> --branch=<branch> --directory=<folder> --image=<image>` (`BuildTaskCommand`) calls `UseCase/BuildTask/BuildTask::run(BuildTaskRequest): BuildTaskOutcome` (marked `#[NoDiscard]`) in `Core/Build`. The build lane (#1568) will call the same use case; it holds no slot, queue, admission, schedule or state machine, and one run builds one task. The remote, the branch, the folder and the job image are options the caller gives, as the single commands take them as arguments; no naming scheme derives them.

## The steps

1. **Task:** `IssueReads::listOpen(<project>, null)` (the GitHub forge's contract) lists the open issues and the run takes the one numbered `<issue>`. The caller names the issue, so the eligibility and order rules of intake do not apply. A pull request of that number is no task; a forge read that fails (`ForgeReadFailed`, `ForgeRateLimited`) or an issue the listing lacks ends the run here. The result holds the `ListedIssue` (title and body, untrusted text) for the steps that come later.
2. **Mirror:** `BuildCheckout::updateMirror(<project>, <remote>)`, the Git module's contract for [`intakt:mirror:update`](mirror.md).
3. **Clone:** `BuildCheckout::makeClone(<project>, <branch>, <folder>)`, the contract for [`intakt:build:clone`](build-clone.md), without a source line (whether the task's author may name one is not read here).
4. **Build job:** `RunBuildJob::run(BuildJob)`, the use case of [`intakt:build:run`](build-job.md), in `<folder>` on `<branch>` with `<image>`. The tier is the routing rules' choice: `BuildRouting::tierFor(<project>, BuildFacts::fromLabels(<the issue's labels>, []))`, so a `model:<tier>` label of the issue counts, with no paths and no setback (a first build has no file forecast and no earlier round). The brief is the issue's title, a blank line and its body, with no decisions and no rework; `BuilderPrompt` fences it. The step passes when the job hands back a bundle and the pull request text (`BuildVerdict::Built`); any other verdict fails it with `BuildVerdict::reason()` as its message (for example `the build made no commit on the task's branch`). A project without routing rules (`BuildRoutingNotConfigured`), a tier that does not resolve or is not on `claude_code` (`TierResolutionFailure`, `BuilderNotOnClaudeCode`), a clone that is no folder, a job the runner refuses (`JobRefused`), a failing engine (`DockerEngineFailed`), a job event the ledger did not record (`JobEventNotRecorded`) and a filesystem error fail it with their message. What the job hands back (the bundle, the pull request text and the log) is untrusted: only the verdict reaches the ledger, and only the bundle goes on, to the next step; the pull request text and the log go nowhere yet.
5. **Hand-back check:** `UseCase/BuildTask/HandBackCheck` has `UseCase/BuildTask/HandBackFile` write the bundle to a file of its own (`Filesystem::tempnam()` in `var/hand-backs`, made with mode `0700`), calls `HandBackChecks::check(HandBack)`, the HandBack module's contract for the check of [`intakt:hand-back:check`](hand-back.md) (implemented by `CheckHandBack`), and `HandBackFile` removes the file after the check, whatever its result, also when writing the bundle into it failed. The `HandBack` names the project's mirror (`BuildCheckout::mirrorOf(<project>)`), because the check needs a bare repository whose `HEAD` names main and the clone's `HEAD` names the task's branch; `<branch>`; the file; no merge of main asked (a first build has no rework that asks for one); and an empty `JobCredentials`, because the build job mounts no credential yet. An `AcceptedHandBack` leaves its objects in the mirror, named by no ref, and then `BuildCheckout::takeCheckedHead(<project>, BranchHead(<branch>, <head>), <folder>)` moves the clone's branch to the accepted head, because the job committed in a clone of its own in the container, so `<folder>` holds the checked build only after this. The step passes once the clone took the head. A `RefusedHandBack` fails it with the refusal's fixed text (`HandBackRefusal::reason()`, for example `the bundle cannot be read as a git bundle`), so no text of the bundle reaches the ledger. A check that cannot run (`HandBackNotChecked`, for example when gitleaks is missing), an invalid branch (`InvalidArgumentException`), a refused attributes file (`RepositoryAttributesRefused`), a project name that is no folder name (`BuildCheckoutFailed`), a bundle file that cannot be written (`IOException`) and a clone that cannot take the head (`BuildCheckoutFailed`) fail it with their message. A bundle file that cannot be removed after the check (`IOException` of `Filesystem::remove()`) fails the step with its message, which names the file's path and nothing of the bundle, in place of the check's own result: also after an accepted bundle whose head the clone already took, because the untrusted bundle is then still on disk. A failure of Symfony Process during the check (git or gitleaks killed by a signal, past its timeout, or unable to run) fails it with fixed words (`the hand-back check was killed by signal <n>`, `the hand-back check timed out after <n> seconds`, `the hand-back check could not run`), never with the exception's message, which holds the whole command line. The pull request text is not checked here, and a failure is not sent back to the builder (that is the round of `RouteHandBack`, which this step does not run).
6. **Pre-push check:** `UseCase/BuildTask/PrePushCheck` has `HandBackFile` write the same bundle to a new file and build the same `HandBack`, then calls `CheckJobs::run(CheckJob)`, the HandBack module's contract for the [check job](check-job.md) of `intakt:check:run` (implemented by `RunCheckJob`), with `<image>`, no configured command (so the gate's own steps run: `composer install` and `bin/check --fast` for the PHP gate) and no path named by the plan, because neither a project's check command nor plan approval is configured yet. `RunCheckJob` runs `CheckHandBack` again on the same bundle and mirror, which accepts it again, because the hand-back check moved no ref of the mirror; then the lost-content check and the check job, which clones the mirror and applies the bundle itself. The step passes when the outcome is `CheckVerdict::Passed`. Any other verdict fails it with `CheckVerdict::reason()`, with ` (exit code <n>)` for a failed step (for example `the check command failed (exit code 2)`); the check's log never reaches the ledger or the output, because it holds what the code under test printed. A `RefusedHandBack` fails it with the refusal's fixed text. A check that cannot run (`HandBackNotChecked`), an invalid branch (`InvalidArgumentException`), a refused attributes file (`RepositoryAttributesRefused`), a job the runner refuses (`JobRefused`), a failing engine (`DockerEngineFailed`), a job event the ledger did not record (`JobEventNotRecorded`), a project name that is no folder name (`BuildCheckoutFailed`) and a bundle file or check script that cannot be written or read (`IOException`) fail it with their message; a bundle file that cannot be removed after the check fails it as in the hand-back check. A failure of Symfony Process during the check fails it with fixed words (`the pre-push check was killed by signal <n>`, `the pre-push check timed out after <n> seconds`, `the pre-push check could not run`). After a passed pre-push check, `<folder>` holds the checked head on `<branch>`, ready for the signed push, which is not part of this command. A failure is not retried and not sent back to the builder.

## The push step

`UseCase/BuildTask/PushStep::failureOf(BuildTaskRequest, AcceptedHandBack, ChangeText): ?string` (#2352, part 1 of #2315) pushes the task's branch signed. It is not yet one of the `BuildStep` cases, so `run()` does not call it and no `build_step_ended` event names it; putting it into the order of steps, its ledger event and its line in the command's output are part 2. It builds a `BranchPushRequest` of `<project>`, the project's mirror (`BuildCheckout::mirrorOf(<project>)`, the bare repository the hand-back check left the accepted head's objects in, where the signing writes its commits), `<remote>`, `<branch>`, the `AcceptedHandBack` and the pull request text, and calls `BranchPush::push()`, the Git module's contract (implemented by `PushBranch`, see [Branch push](branch-push.md)). Like `PrePushCheck`, it returns null when the branch is pushed (`PushedBranch`) and a failure text otherwise:

- a `RefusedPush` gives its `reason`, the outcome `PushBranch` recorded as `push_refused` (for example `the remote refused the push of task (git push exited with 1)`);
- a `MainConflicts` gives the fixed text `the branch conflicts with main, so nothing was pushed (conflicting paths: <n>)`, with the number of paths and none of their names, because the builder chose them;
- a mirror that cannot be named (`BuildCheckoutFailed`), a push that fails (`BranchNotPushed`, for example a ledger that did not record `push_intended`), an unsigned commit (`UnsignedCommitRefused`), a pull request text that trips the secret scan (`ChangeTextHoldsSecret`) and a forge write that fails (`ForgeWriteFailed`) give their message.

The step records nothing itself, because `PushBranch` already writes the push's ledger events and asks the forge for the pull request. A failure is not retried and not sent back to the builder, also not a conflict with main; nothing here merges, reviews or labels.

`Git/Infrastructure/GitBuildCheckout` implements `BuildCheckout` by calling `UpdateMirror::update()`, `MakeBuildClone::make()` and `TakeCheckedHead::take()`, and answers `mirrorOf()` with `Mirrors::pathOf()` (`var/mirrors/<project>.git`). `Git/Contract/BranchHead` refuses a head that is no lowercase object id (`InvalidArgumentException`), because a refspec takes a ref name or an option as readily; `TakeCheckedHead` then runs `git fetch --quiet --no-tags --no-write-fetch-head --update-head-ok -- <mirror> +<head>:refs/heads/<branch>` over `file` only and `git reset --hard --quiet` in the clone; a failed call is a `CheckedHeadNotTaken`. Every failure of these (an invalid project, branch or head, `MirrorNotUpdated`, `NetworkGitFailed`, `BuildCloneNotMade`, `CheckedHeadNotTaken`, `RepositoryAttributesRefused`, a filesystem error, and for the mirror a failure of Symfony Lock such as a lock that cannot be acquired) becomes one `BuildCheckoutFailed` with the same message, so Build never imports a use case of Git. A failure of Symfony Process in any of them (a local git call that is killed by a signal, runs into the 60 seconds a local call gets, or cannot run) becomes a `BuildCheckoutFailed` with fixed words (`git was killed by signal <n>`, `git timed out after <n> seconds`, `git could not run`; `BuildCheckoutFailed::stopped()`) and without the caught exception as its cause, because that exception's message holds the whole command line. Each of these is therefore a failed step with its event in the ledger, never an exception that leaves the run.

`run()` reads the task first, then runs the `BuildStep` cases in their declared order, so the enum is the one list of the steps. The run stops at the first step that fails, with that step's own message in `BuildTaskOutcome` (`last`, `failure`, `task`; `passedSteps()` lists the steps before it), and runs no later step. The bundle of the build job reaches the hand-back check and the pre-push check as a local of the run, never a property, because a worker keeps the service between runs. A run whose steps all pass ends after the pre-push check, with `last` the `pre_push_check` step and no failure. Nothing is retried here: a failure is recorded and the run ends. The steps after the pre-push check (the signed push and the pull request) are later parts.

## The ledger

Each step appends one `LedgerEventKind::BuildStepEnded` (`build_step_ended`) event with the JSON payload `project`, `task` (the issue number as text), `step` (`task`, `mirror`, `clone`, `build_job`, `hand_back_check` or `pre_push_check`, a `Build/Contract/BuildStep` case), `outcome` (`passed` or `failed`, a `Build/Contract/BuildStepOutcome` case) and `failure` (the message, or null). The issue's title and body are never in the payload. A ledger that does not record an event stops the run with `BuildStepNotRecorded` before the next step. `intakt:status` shows the last of these events of each task in `lanes.build` (see [Status read model](status.md)), and the dashboard's task page `/tasks/<project>/<task>` shows the steps of the task's latest run (see [Dashboard](dashboard.md)).

## The door

The command prints `<step> passed` for each step that passed, then `title <title>` once the task was read, and for a failing step an error block `<step> failed: <message>` and exit code 1. An issue number that is not a whole number from 1 to 999999999, a missing `--remote`, `--branch`, `--directory` or `--image`, and a step the ledger did not record fail with a message and exit code 1.

The title is untrusted text, so it is never printed as it is: each control character (`\p{Cc}`: C0 such as ESC and BEL, DEL, and C1 such as CSI) is printed as `?`, because it would drive the operator's terminal, and the console formatter's tags are escaped (`OutputFormatter::escape()`). A title that is not UTF-8 keeps only its printable ASCII (`0x20` to `0x7E`), every other byte printed as `?`.

`GitHubIssueReads` is the container's `IssueReads` in `dev` and `prod`; in the test environment `tests/Core/Build/services.yaml` replaces it with `RecordedIssues`, which serves the file `BUILD_RECORDING` names (a JSON list of issues in GitHub's shape), so the command runs on an install without GitHub. The same file gives `RunBuildJob` the `ScriptedJobRunner` instead of `ContainerJobRunner`: it serves the files of the folder `BUILD_JOB_OUTPUT` names as the job's output (exit code 0), so the build job step runs without a container engine or a model. It gives `RunCheckJob` the same runner, so the pre-push check reads `check-result` and `check.log` from that folder too; the review jobs keep the container runner. The hand-back check is the real `CheckHandBack` in every environment, so a scripted bundle must be one the mirror accepts.
