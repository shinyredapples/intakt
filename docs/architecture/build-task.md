# Build task

Plan task T56, parts 1 (#2037), 2 (#2025), the hand-back check (#2116), the pre-push check (#2117), its pull request text round (#2677) and the push step (#2352, put into the order of steps by #2353). `php bin/console intakt:build:task <project> <issue> --remote=<remote> --branch=<branch> --directory=<folder> --image=<image>` (`BuildTaskCommand`) calls `UseCase/BuildTask/BuildTask::run(BuildTaskRequest): BuildTaskOutcome` (marked `#[NoDiscard]`) in `Core/Build`. The build lane (#1568) will call the same use case; it holds no slot, queue, admission, schedule or state machine, and one run builds one task. The remote, the branch, the folder and the job image are options the caller gives, as the single commands take them as arguments; no naming scheme derives them.

## The steps

Before step 1, `PushRemoteCheck` compares `<remote>` with the project's configured GitHub repository, read through `ConfiguredRepositories::nameOf()` (the GitHub forge's contract, implemented by `WatchedRepositories`; the forge contract carries no git detail). A project with a `github` entry needs `<remote>` to be `https://github.com/<owner>/<name>` (optional `.git` and trailing slash; host, owner and name case-insensitive; the scheme written `https` in lower case, because git matches it case-sensitively against the push's protocol allowlist and refuses `HTTPS`; user info such as a token is allowed, because Intakt supplies no git credentials of its own; no port, query or fragment; ssh, a path, a `file://` URL and another host are refused; the path is read normalized as in RFC 3986 by PHP's `Uri\Rfc3986\Uri`, so dot segments and percent-encoded letters name the same repository, and a doubled leading slash is trimmed like the outer slashes), because the ownership check and the pull request write use the configured repository while `git push` uses the remote. A mismatch throws `PushRemoteRefused` naming both, before the forge is read, with no ledger event, no step reported as passed and nothing pushed; the command prints its message and exits with 1. The remote is shown without its user info, query and fragment, and a remote without a host that holds an `@` or `:` (an ssh address) is not shown, because either can carry a token. A project without a `github` entry accepts any remote. Tests: `PushRemoteCheckTest` and `BuildTaskTest`.

1. **Task:** `IssueReads::readOpen(<project>, <issue>)` (the GitHub forge's contract) reads the one issue numbered `<issue>` with a single request, never the listing of every open issue. The caller names the issue, so the eligibility and order rules of intake do not apply. A forge read that fails (`ForgeReadFailed`, `ForgeRateLimited`) ends the run here with the failure's message, and an issue the read answers as none (closed, missing, transferred, a pull request or an answer for another number) with `project "<project>" has no open issue <issue>`. The result holds the `ListedIssue` (title and body, untrusted text) for the steps that come later. `run()` reads the issue and records this step's row while it holds the task's start lock (Symfony Lock, `BuildRun::startLockKey()`: `build-run-start-` and the SHA-256 of the length-prefixed project and the issue number, no TTL), so a run that started earlier records its `task` row before a run that started later; runs of other tasks never touch it. The lock is taken without waiting (`acquire(blocking: false)`), so a stalled holder never blocks the next run: while another run of the same task holds it, this step fails with the fixed words `another run of this task is starting` (`BuildTask::START_BUSY`), and a failure of the lock store fails it with `the start of the run could not be locked` (`BuildTask::START_NOT_LOCKED`); either way the run reads no issue and runs no other step. That failed `task` row is recorded outside the lock, so the holder can record its own `task` row after it; the task page then shows the holder, which is right, because it is the run that goes on.
2. **Mirror:** `BuildCheckout::updateMirror(<project>, <remote>)`, the Git module's contract for [`intakt:mirror:update`](mirror.md). Below a [disk floor](disk-floors.md) of the mirrors folder, or on a disk whose free space cannot be read, the update throws `MirrorNotUpdated`, which `GitBuildCheckout` turns into `BuildCheckoutFailed`, so the step is recorded as failed with that reason and no clone is made.
3. **Clone:** `BuildCheckout::makeClone(<project>, <branch>, <folder>)`, the contract for [`intakt:build:clone`](build-clone.md), without a source line (whether the task's author may name one is not read here). Below a disk floor of `<folder>`'s parent, or on a disk that cannot be read, the clone throws `BuildCloneNotMade`, so the step is recorded as failed the same way and `<folder>` is not made. A hold is recorded as an ordinary failure for now.
4. **Build job:** `RunBuildJob::run(BuildJob)`, the use case of [`intakt:build:run`](build-job.md), in `<folder>` on `<branch>` with `<image>`. The tier is the routing rules' choice: `BuildRouting::tierFor(<project>, BuildFacts::fromLabels(new Labels(<the issue's labels>), new Paths()))`, so a `model:<tier>` label of the issue counts, with no paths, no setback and no escalation outcome (a first build has no file forecast and no earlier round). The brief is the issue's title, a blank line and its body, with no decisions and no rework; `BuilderPrompt` fences it. Before the job runs, an issue labeled `bug` (`Contract/TaskKind::fromLabels(Labels)` gives `TaskKind::Bug`) is checked by plain code, never a model: `Domain/BugReport::fromBody()` reads the four parts **When**, **Today**, **Expected** and **Must keep working**, and `missingParts()` lists the absent or empty ones in that order. It first removes fenced code blocks (```` ``` ```` or `~~~`), the text between `<!-- external -->` and `<!-- /external -->` and every HTML comment, so none of them starts, fills or ends a part. A four-space indented code block is not removed: it is read like any other text. It reads these in the order they open: a fence counts when it is indented at most three columns past the content of the list item it is in, or at most three spaces outside a list (four or more make it indented code), and ends at its closing fence, which counts only when it is indented at most three columns past the same container (a tab counts as four columns, so a closer four columns deeper is the code's own text), or, inside a list item, at the first line indented less than that item's content; an external block's or a comment's closer ends it at any indentation; a fence opened inside a comment does not hide the text after the comment, and a comment opened inside a fence ends with the fence; inline code spans (backtick runs of equal length) are skipped when looking for `<!--`, so a `<!--` between backticks opens no comment; a line of three backticks followed by more backticks on the same line is an inline code span, not a fence. A part starts at a heading whose text is exactly the part's name (any letter case, an optional colon, optional closing `#`s, also after list markers such as `- ## When`; an underlined heading, a paragraph followed by a line of `=` or `-`, counts the same, but only outside a list) or at a line that starts with the part's name in bold (`**When**` or `**When:**`, also as a bulleted or numbered list item such as `1. **When:**`), whose text after the label on the same line counts. A part ends at any heading and at any line that starts with a bold label, one of the four or not; a plain `Word:` line does not end it. When a part is missing, no job runs: `run()` parks the task with `BuildQuestion::forMissingBugParts()`, a question that names the missing parts and offers "Add the missing parts to the task" (recommended) and "Remove the bug label", through the same `park()` below, so the step is recorded as `asked`; the clone has been made by then and is left alone, and a failed mirror or clone fails the run before the check as for every task. A bug task with all four parts, and a task without the label, go on. The step passes when the job hands back a bundle and the pull request text (`BuildVerdict::Built`) and `ParkedTasks::clear(<the run>)` removed the task's parked row, if it has one that this run or a run that started before it parked (see [The parked-task record](#the-parked-task-record)); a row the database does not remove (`ParkedTaskNotCleared`) fails the step with that exception's fixed words. A job that ends with a question that passes the question rule (`BuildVerdict::Asked`, with its `BuildQuestion`) parks the task: `run()` calls `ParkedTasks::park(<the run>, <question>)` (a `BuildRun` with the project, the issue and the run id), which records this step as `asked` (see [The parked-task record](#the-parked-task-record)), and the run ends there without a failure and runs no later step; a parking that fails (`TaskNotParked`) fails the step with that exception's fixed words. A question that breaks the rule (`BuildVerdict::QuestionRefused`) and any other verdict fail it with `BuildVerdict::reason()` as its message (for example `the build made no commit on the task's branch`). A project without routing rules (`BuildRoutingNotConfigured`), a tier that does not resolve or is not on `claude_code` (`TierResolutionFailure`, `BuilderNotOnClaudeCode`), a clone that is no folder, a job the runner refuses (`JobRefused`), a failing engine (`DockerEngineFailed`), a job event the ledger did not record (`JobEventNotRecorded`) and a filesystem error fail it with their message. What the job hands back (the bundle, the pull request text and the log) is untrusted: only the verdict reaches the ledger; the bundle goes on to the hand-back check and the pre-push check, the pull request text to the push step, and the log nowhere.
5. **Hand-back check:** `UseCase/BuildTask/HandBackCheck` has `UseCase/BuildTask/HandBackFile` write the bundle to a file of its own (`Filesystem::tempnam()` in `var/hand-backs`, made with mode `0700`), calls `HandBackChecks::check(HandBack)`, the HandBack module's contract for the check of [`intakt:hand-back:check`](hand-back.md) (implemented by `CheckHandBack`), and `HandBackFile` removes the file after the check, whatever its result, also when writing the bundle into it failed. The `HandBack` names the project's mirror (`BuildCheckout::mirrorOf(<project>)`), because the check needs a bare repository whose `HEAD` names main and the clone's `HEAD` names the task's branch; `<branch>`; the file; no merge of main asked (a first build has no rework that asks for one); and an empty `JobCredentials`, because the build job mounts no credential yet. An `AcceptedHandBack` leaves its objects in the mirror, named by no ref, and then `BuildCheckout::takeCheckedHead(<project>, BranchHead(<branch>, <head>), <folder>)` moves the clone's branch to the accepted head, because the job committed in a clone of its own in the container, so `<folder>` holds the checked build only after this. The step passes once the clone took the head, and `HandBackCheck::check()` then returns the `AcceptedHandBack` (its `base` and `head`) for the push step instead of a failure text. A `RefusedHandBack` fails it with the refusal's fixed text (`HandBackRefusal::reason()`, for example `the bundle cannot be read as a git bundle`), so no text of the bundle reaches the ledger. A check that cannot run (`HandBackNotChecked`, for example when gitleaks is missing), an invalid branch (`HandBackBranchRefused`), a head that is no object id (`InvalidArgumentException` of `BranchHead`), a refused attributes file (`RepositoryAttributesRefused`), a project name that is no folder name (`BuildCheckoutFailed`), a bundle file that cannot be written (`IOException`) and a clone that cannot take the head (`BuildCheckoutFailed`) fail it with their message. A bundle file that cannot be removed after the check (`IOException` of `Filesystem::remove()`) fails the step with its message, which names the file's path and nothing of the bundle, in place of the check's own result: also after an accepted bundle whose head the clone already took, because the untrusted bundle is then still on disk. A failure of Symfony Process during the check (git or gitleaks killed by a signal, past its timeout, or unable to run) fails it with fixed words (`the hand-back check was killed by signal <n>`, `the hand-back check timed out after <n> seconds`, `the hand-back check could not run`), never with the exception's message, which holds the whole command line. The pull request text is not checked here, and a failure is not sent back to the builder (that is the round of `RouteHandBack`, which this step does not run).
6. **Pre-push check:** `BuildTask` first calls `BuildCheckout::updateMirror(<project>, <remote>)` again, as the mirror step does, because main can move while the build job runs and the check job merges the branch into current main (the mirror's `HEAD`); a failed update fails this step with its message and starts no check job. That includes an update held by a disk floor of the mirrors folder. Then `UseCase/BuildTask/PrePushCheck` has `HandBackFile` write the same bundle to a new file and build the same `HandBack`, then calls `CheckJobs::run(CheckJob)`, the HandBack module's contract for the [check job](check-job.md) of `intakt:check:run` (implemented by `RunCheckJob`), with `<image>`, no configured command (so the gate's own steps run: `composer install` and `bin/check --fast` for the PHP gate, with an empty Composer cache; a saved install of the checked tree's lock files and platform ([when a check reuses one](check-job.md#in-short)), made through the gate's [dependency step](check-job.md#the-gate-plugin), may be copied in first, but it replaces neither step: `composer install` and `bin/check --fast` still run after the copy, and the install makes the generated files for the check's own clone) and no path named by the plan, because neither a project's check command nor plan approval is configured yet. `RunCheckJob` runs `CheckHandBack` again on the same bundle and the updated mirror. The hand-back check moves no ref of the mirror, but neither it nor `RunCheckJob` holds the mirror's lock (`UpdateMirror` takes `git-mirror-<project>` only to publish a new mirror), so another operation on the same mirror, for example another run's update of the project's mirror, can move its refs between the two checks. Apart from the update this step itself runs first (its effect is described next), the second check always judges the bundle again against the mirror as it then is (main as its `HEAD` names it and the task's branch as it then stands), so it can refuse a bundle the first check accepted; any refusal fails the step as below. When the update fetched the task's branch (a concurrent push since the mirror step) and that fetched branch is not an ancestor of the bundle's head (the push holds other commits), the check refuses the bundle with `HandBackRefusal::NotFastForward`, and the step fails with that refusal's fixed text and starts no check job. When the fetched branch is an ancestor of the bundle's head (for example a branch created on the remote at the main commit the build started from), the bundle still passes and the check job runs. After a passed check come the lost-content check and the check job, which clones the mirror, applies the bundle itself and, when main moved since the branch last merged it, runs the steps on the branch merged into current main, as CI does. The step passes when the outcome is `CheckVerdict::Passed`; for a `bug` task that outcome is only the prerequisite of the regression check at the end of this step, and a regression refusal fails the step before the pull request text round, so it records no text line. A merge with current main that conflicts is the conflict route: `CheckVerdict::ConflictsWithMain` fails the step with `the branch conflicts with current main, so the check ran no step`, the conflicting paths stay in the check's log, and nothing is pushed, as with the push step's conflict below. A merge that fails without git reporting a conflict (git refused it, its commit failed or it left no merge commit) is `CheckVerdict::NotMerged` and fails the step with `git refused to merge the branch with current main without a conflict, so the check ran no step`. Any other verdict fails it with `CheckVerdict::reason()`, with ` (exit code <n>)` for a failed step (for example `the check command failed (exit code 2)`); the check's log never reaches the ledger or the output, because it holds what the code under test printed. A `RefusedHandBack` fails it with the refusal's fixed text. A check that cannot run (`HandBackNotChecked`), an invalid branch (`HandBackBranchRefused`), a refused attributes file (`RepositoryAttributesRefused`), a job the runner refuses (`JobRefused`), a failing engine (`DockerEngineFailed`), a job event the ledger did not record (`JobEventNotRecorded`), a project name that is no folder name (`BuildCheckoutFailed`) and a bundle file or check script that cannot be written or read (`IOException`) fail it with their message; a bundle file that cannot be removed after the check fails it as in the hand-back check. A failure of Symfony Process during the check fails it with fixed words (`the pre-push check was killed by signal <n>`, `the pre-push check timed out after <n> seconds`, `the pre-push check could not run`). After a passed check job, `UseCase/BuildTask/PullRequestTextCheck` runs the [pull request text round](check-job.md#the-pull-request-text-round) through the HandBack contract `PullRequestTextRound::route(PullRequestTextTask::resolved(<the project's mirror>, <branch>), <the issue's body>, <the body of the build's text>)`, the body split from the title as the push step splits it. Only a head that passed the check job is counted, so a failed check job records no text line. A first miss fails the step with `the pull request text is sent back to the builder: <reason>` and `; missing: E2, E3` when items are missing (never the text), and nothing is pushed; the commits stay in `<folder>` and the mirror. A second miss in a row is `PullRequestTextRoute::ToReviewers`: the step passes and the head goes on to the push, so the reviewers see the gap. A mirror path that cannot be named (`BuildCheckoutFailed`), a task the round refuses (`InvalidArgumentException`) and a line the ledger does not take, a lock store that fails and a ledger that cannot be read (each a `PullRequestTextRoundNotRecorded`) fail the step with their message, and nothing is pushed. After a passed pre-push check, `<folder>` holds the checked head on `<branch>`, ready for the push step. A failure is not retried. No code re-runs the builder or resumes from the kept head yet (T56), and a second run needs a new folder. For a task labeled `bug`, once the check job passed, `PrePushCheck` also calls `RegressionTests::run(CheckJob)` and logs its result (the test paths and how each run ended); a head with no new test (`the head of a bug adds no regression test`) or whose new test also passes on the base (`the new test of a bug also passes on the base, so it proves nothing`) fails the step like a red check and nothing is pushed, and every other result leaves the verdict as the check job gave it. When the pair was read and the step passed (and the pull request text round did not stop the head), `PrePushCheck::resultOf()` hands the `RegressionRuns` back in its `PrePushResult`, `BuildTask` keeps them as the step's result, and the push step builds the pull request body through `Domain/RegressionEvidence`, which adds three lines (`- Regression tests: <paths>`, `- On the base: <result>`, `- On the head: <result>`) at the end of the body's first `## Evidence` section, or a new `## Evidence` heading at the end of the body when it has none. The section starts at the first heading whose text is the word `Evidence` (any letter case, followed by a colon, a space or nothing) and ends before the next heading of the same or a higher level, so a subheading such as `### E1` stays inside it. `Domain/ReadableLines` finds the headings: ATX headings, and setext headings (a paragraph underlined with `=` is level 1, with `-` level 2, and the heading starts at the paragraph's first line). It also reads code fences, indented code (a line indented four or more columns that does not continue a paragraph, where a tab moves to the next multiple of four columns, so `\tEvidence` is code too), thematic breaks and list item lines, so no heading is read inside a fence or indented code, and a `---` under a list item or after a blank line is no underline. Inside a paragraph, an ordered item whose number's value is not 1 (`2.`, `02.`) and an empty item (a marker followed only by spaces, tabs or the line's end, such as `1.` or `-`) are paragraph text, so `---` under them underlines the paragraph (`Follow-ups`, `1.`, `---` is a level 2 heading); an ordered item whose one to nine digits have the value 1 (`1.`, `01.`, `001)`) followed by text starts a list, so a `---` under it is a thematic break. A paragraph that started directly below a list item line (no blank line between) is that item's wrapped text: there an ordered item with any number ends it (`1. E1: the test`, `   passes`, `2. E2: shown`), so a `---` under that next item is a thematic break. Container blocks are not read: a `---` under the continuation line of a list item (`- E1: the test`, `  passes`) is still taken as an underline. Other Markdown (block quotes, lazy continuation lines, HTML blocks) is not read. The body is read with LF, CRLF and CR line endings alike and is written back with LF. A fence closes only on the same marker character repeated at least as often as the opening line, a heading inside a fence is not taken, and a fence left open at the end of the body is closed before the lines are added. The lines hold fixed words and the test paths read from the diff (a path with characters outside letters, digits and `_./@+ -` is not shown), never a log or the builder's text; a head of any other kind is pushed with its body as written ([regression tests of a bug](check-job.md#regression-tests-of-a-bug)).
7. **Push:** the signed push of the accepted head, described in the next section.

## The push step

`UseCase/BuildTask/PushStep::failureOf(BuildTaskRequest, AcceptedHandBack, ChangeText): ?string` (#2352, part 1 of #2315) pushes the task's branch signed; #2353 (part 2) made it the last `BuildStep` case, `push`, after the pre-push check. `run()` hands it the `AcceptedHandBack` the hand-back check returned and the build job's pull request text as a `ChangeText`: the first line, trimmed, is the title, and the rest, trimmed, is the body, the form `BuilderPrompt` asks the builder to write (a title, a blank line, the body); for a bug head whose regression runs the pre-push check handed back, the body also gets the [Evidence lines of those runs](#the-steps) from `Domain/RegressionEvidence` (a head of any other kind keeps its body as written). A text whose first line is blank fails the step with the fixed text `the pull request text has no title on its first line`, and nothing is pushed. It builds a `BranchPushRequest` of `<project>`, the project's mirror (`BuildCheckout::mirrorOf(<project>)`, the bare repository the hand-back check left the accepted head's objects in, where the signing writes its commits), `<remote>`, `<branch>`, the `AcceptedHandBack` and the pull request text, and calls `BranchPush::push()`, the Git module's contract (implemented by `PushBranch`, see [Branch push](branch-push.md)). Like `PrePushCheck`, it returns null when the branch is pushed (`PushedBranch`) and a failure text otherwise:

- a `RefusedPush` gives its `reason`, the outcome `PushBranch` recorded as `push_refused` (for example `the remote refused the push of task (git push exited with 1)`);
- a `MainConflicts` gives the fixed text `the branch conflicts with main, so nothing was pushed (conflicting paths: <n>)`, with the number of paths and none of their names, because the builder chose them;
- a mirror that cannot be named (`BuildCheckoutFailed`), a push that fails (`BranchNotPushed`, for example a ledger that did not record `push_intended`), an unsigned commit (`UnsignedCommitRefused`), a pull request text that trips the secret scan (`ChangeTextHoldsSecret`) and a forge write that fails (`ForgeWriteFailed`, also a branch the forge refuses before the push because it has an open pull request another account opened) give their message.

The step writes no event of its own beyond its `build_step_ended`, because `PushBranch` already writes the push's ledger events (`push_intended`, `branch_pushed` or `push_refused`, `change_intended`, `change_opened`) and asks the forge (`ChangeOpening`), before the push, to refuse a branch with an open pull request another account opened, and after it to open or update the pull request of the branch with the title and body; those events come before the step's `build_step_ended`. A failure is not retried and not sent back to the builder, also not a conflict with main; nothing here merges, reviews or labels.

`Git/Infrastructure/GitBuildCheckout` implements `BuildCheckout` by calling `UpdateMirror::update()`, `MakeBuildClone::make()` and `TakeCheckedHead::take()`, and answers `mirrorOf()` with `Mirrors::pathOf()` (`var/mirrors/<project>.git`). `Git/Contract/BranchHead` refuses a head that is no lowercase object id (`ObjectIdMalformed`, an `InvalidArgumentException`), because a refspec takes a ref name or an option as readily; `TakeCheckedHead` then runs `git fetch --quiet --no-tags --no-write-fetch-head --update-head-ok -- <mirror> +<head>:refs/heads/<branch>` over `file` only and `git reset --hard --quiet` in the clone; a failed call is a `CheckedHeadNotTaken`. Every failure of these (a refused project name or branch, `ProjectNameRefused` or `BranchNameRefused`, `MirrorNotUpdated`, `NetworkGitFailed`, `BuildCloneNotMade`, `CheckedHeadNotTaken`, `RepositoryAttributesRefused`, a filesystem error, and for the mirror a failure of Symfony Lock such as a lock that cannot be acquired) becomes one `BuildCheckoutFailed` with the same message, so Build never imports a use case of Git. A failure of Symfony Process in any of them (a local git call that is killed by a signal, runs into the 60 seconds a local call gets, or cannot run) becomes a `BuildCheckoutFailed` with fixed words (`git was killed by signal <n>`, `git timed out after <n> seconds`, `git could not run`; `BuildCheckoutFailed::stopped()`) and without the caught exception as its cause, because that exception's message holds the whole command line. Each of these is therefore a failed step with its event in the ledger, never an exception that leaves the run. A Symfony Process exception that extends `InvalidArgumentException` is a failure of Symfony Process like the others and becomes `BuildCheckoutFailed::stopped()`; any other `InvalidArgumentException` from inside these calls is a programming error and passes through `GitBuildCheckout` unchanged.

`run()` reads the task first (after the remote check above), then runs the `BuildStep` cases in their declared order, so the enum is the one list of the steps. The run stops at the first step that fails, with that step's own message in `BuildTaskOutcome` (`last`, `failure`, `task`; `passedSteps()` lists the steps before it), and runs no later step. A parked task stops at the build job too, with no failure: `BuildTaskOutcome::parked()` is true for an outcome without a failure whose `last` is not the final step, and `passedSteps()` then lists the steps before the build job. The bundle and the pull request text of the build job and the `AcceptedHandBack` of the hand-back check reach the later steps as locals of the run, never properties, because a worker keeps the service between runs. A run whose steps all pass ends after the push, with `last` the `push` step and no failure. Nothing is retried here: a failure is recorded and the run ends. Refusing a second run for an issue with an open pull request is a later part.

## The ledger

Each step appends one `LedgerEventKind::BuildStepEnded` (`build_step_ended`) event with the JSON payload `project`, `task` (the issue number as text), `run` (a random UUID v4 in RFC 4122 form, taken once per `run()` by `UseCase/BuildTask/BuildRun::startedFor()` before the issue is read, so every step row of one run carries the same id and the task page can keep two overlapping runs of a task apart; which run is the latest is the order of their first rows (the `task` row) in the ledger, which the start lock of the task step keeps in the order the runs recorded their `task` step, never the order of the ids or the clock; `BuildRun::stepPayload()` writes this payload for `run()` and for `ParkedTasks::park()`), `step` (`task`, `mirror`, `clone`, `build_job`, `hand_back_check`, `pre_push_check` or `push`, a `Build/Contract/BuildStep` case), `outcome` (`passed` or `failed`, a `Build/Contract/BuildStepOutcome` case; its third case, `asked`, is written only by `ParkedTasks::park()`, for the `build_job` step of a parked task, in place of the event `run()` would append (see [The parked-task record](#the-parked-task-record))) and `failure` (the message, or null). The issue's title and body, and the pull request's, are never in the payload. A ledger that does not record an event stops the run with `BuildStepNotRecorded` before the next step. `intakt:status` shows the latest of these events of each task's latest run in `lanes.build`, a parked task as `build_job` `asked` with its parked question (see [Status read model](status.md)), and the dashboard's task page `/tasks/<project>/<task>` shows the steps of the task's latest run and the question of a parked one (see [Dashboard](dashboard.md)). Both show the push step like any other: a run through the push as `push` `passed` (the page says `Every step passed.`), a run stopped at it as `push` `failed` with the step's failure text, redacted (the page says `Stopped at push: <failure>`).

## The parked-task record

Issue #2961 (part 1 of #2673) stores the question a build ends with; #2962 (part 2) has `BuildTask` call it when the build job's outcome carries an accepted question, and #3552 when a bug task misses a part (see [the build job step](#the-steps)). `BuildTask` opens no transaction around the run, so `park()` never meets one of the caller's. `UseCase/BuildTask/ParkedTasks::park(BuildRun, BuildQuestion)` writes a `Domain/ParkedTaskRecord` row to the table `build_parked_task` (mapping `Build` in `config/packages/doctrine.yaml`, migrations `Version20261120110000` and `Version20261125190000`): `project` and `task` (the issue number, an integer) as the primary key, so a task has at most one row, the accepted question's `question` (a JSON string), `choices` (a JSON list of strings) and `recommendation` (a JSON string), `parked_at` (the clock's time in UTC) and `run` (the id of the run that parked it; null only for a row parked before the column existed, which no reader shows and any run replaces or clears). The texts are stored as JSON, because `BuildQuestion` keeps a NUL character inside a text, which PostgreSQL's `text` cannot store and a JSON escape (`\u0000`) can. A task parked again replaces its row, unless a run that started later parked it: two runs of a task can overlap, so an older run's parking then leaves the newer run's question and only records its own `asked` step and `task_parked` event. Which run started later is the order of their first `build_step_ended` rows in the ledger; a stored run without such a row counts as earlier. The row and the order are read before the transaction, and the replaced row is deleted only as it was read (by its `run`), so a parking whose row another run wrote in between meets that row's primary key, rolls back, reads the row again and decides again by the same order (an earlier run's row is replaced, a later run's is kept); after three such conflicts it throws `TaskNotParked`. `park()` refuses to run inside a transaction the caller opened (`TaskNotParked`, before any write and without touching that transaction), because there its commit would only release a savepoint and the caller could still roll the question and the event back. In the same transaction it appends the `build_step_ended` event of the `build_job` step with the run's `run` id, the outcome `asked` and the failure null, then a `LedgerEventKind::TaskParked` (`task_parked`) event (#2674, part 3 of #1696) with the payload `project`, `task` (the issue number as text) and `run` (the id of the run that parked it); like every step's payload, both name the task by number and hold no question text. The row is written with one insert on the connection (`Connection::insert()`, after a `delete()` of the row it replaces), not through the entity manager, because the row then stays out of the entity manager's identity map, which `resetManager()` throws away after a failed parking (see below).

A parking that fails stores neither the row nor the event and throws `UseCase/BuildTask/TaskNotParked` with fixed words and no cause (`Issue <n> of project "<project>" was not parked: the database did not store its question`), because the database's message may quote the question. This covers a database that cannot be opened, a failed insert, an event the ledger did not record and a commit the database refused. On SQLite a commit is refused (`database is locked`) when another connection holds a read transaction; DBAL then counts the transaction as ended while the driver keeps it open (`upstream/dbal-failed-commit-leaves-transaction-open/`), so `rollBackWhatTheRefusedCommitLeftOpen()` rolls back the PDO connection when it is still in a transaction (only PDO drivers) and then closes the DBAL connection, which opens again on its next use. The close resets DBAL's count of open transactions, which can also outlive a transaction the database rolled back itself (an SQLite `RAISE(ROLLBACK)` during the ledger's insert left DBAL counting two levels with no transaction open); on a driver other than PDO, an open transaction ends with the connection the close drops. It returns at once when the connection is not open, and swallows a failure of the rollback (`Doctrine\DBAL\Exception` or `PDOException`), so the caller always gets `TaskNotParked`. After every failed parking `park()` calls `ManagerRegistry::resetManager()`, because the default entity manager still holds the `asked` event record the rollback took back, and the next append would collide with it. The reset is an accepted trade-off: the default entity manager is shared, so it also throws away every change that another holder of that manager had not yet flushed.

`ParkedTasks::clear(BuildRun)` (#2674) deletes the task's row on the connection when the given run or a run that started before it parked it; a question of a run that started later stays, and a task without a row is no failure. `BuildTask` calls it when a later run's build job built (the question it parked with no longer says where the task stands), before that step's `build_step_ended` is appended, and writes no event of its own: the `passed` build job step records it. A delete the database refuses throws `UseCase/BuildTask/ParkedTaskNotCleared` with fixed words and no cause (`Issue <n> of project "<project>" is still parked: the database did not remove its question`), which fails the build job step.

The readers of the row go through the Build contract: `Contract/ParkedQuestions::of(project, task): ?ParkedQuestion` (implemented by `Infrastructure/StoredParkedQuestions`, which reads the row on the connection, decodes the three JSON texts itself, to objects so that `{"0":"a"}` is no list, and uses the connection's type conversion only for `parked_at`) gives the `question`, `choices`, `recommendation` `parkedAt` and `run` of a parked task, and null without a row or for a row outside the shape the parking writes (`BuildQuestion::fromStored()` applies the rules an accepted question passed: a question or recommendation that is no JSON text, is empty or is not trimmed, choices that are no non-empty JSON array of such texts or name one twice, a recommendation that is not one of the choices; texts whose shortest hand-back (the three keys as JSON, escaped only where JSON must escape) is longer than `BuildQuestion::MAX_BYTES`, which no accepted hand-back can hold; also a time that does not convert and a `run` that is no UUID). The status (`lanes.build`, see [Status read model](status.md)) and the task page (see [Dashboard](dashboard.md)) read it only for a task whose latest step is `asked`, through `Dashboard/Infrastructure/ParkedQuestionTexts`, which takes the ledger's task text only as the plain digits of a whole number from 1 (no space, sign or leading zero), gives the question only when its `run` is the run the reader shows and redacts every text with `Platform/Contract/Redactor`, because the builder wrote them.

## The door

The command prints `<step> passed` for each step that passed, then `title <title>` once the task was read, and for a failing step an error block `<step> failed: <message>` and exit code 1. A parked task prints the steps before the build job, the title and a warning block `build_job asked: the task is parked until its question is answered`, and exits with 0, because the run did what it should; the question itself is never printed, because the builder wrote it. An issue number that is not a whole number from 1 to 999999999, a missing `--remote`, `--branch`, `--directory` or `--image`, a `--remote` outside the configured GitHub repository (`PushRemoteRefused`, printed with no `<step> passed` line) and a step the ledger did not record fail with a message and exit code 1.

The title is untrusted text, so it is never printed as it is: each control character (`\p{Cc}`: C0 such as ESC and BEL, DEL, and C1 such as CSI) is printed as `?`, because it would drive the operator's terminal, and the console formatter's tags are escaped (`OutputFormatter::escape()`). A title that is not UTF-8 keeps only its printable ASCII (`0x20` to `0x7E`), every other byte printed as `?`.

`GitHubIssueReads` is the container's `IssueReads` in `dev` and `prod`; in the test environment `tests/Core/Build/services.yaml` replaces it with `RecordedIssues`, which serves the file `BUILD_RECORDING` names (a JSON list of issues in GitHub's shape, `milestone.due_on` included; a file of the form `{"fails": "<message>"}` fails every read with `ForgeReadFailed`), so the command runs on an install without GitHub (`intakt:queue:show` lists the same file, see [Work intake](work-intake.md#the-intaktqueueshow-command)). The same file gives `RunBuildJob` the `ScriptedJobRunner` instead of `ContainerJobRunner`: it serves the files of the folder `BUILD_JOB_OUTPUT` names as the job's output (exit code 0), so the build job step runs without a container engine or a model. It gives `RunCheckJob` and `DependencyJobs` the same runner, so the pre-push check reads `check-result` and `check.log` from that folder too, and a folder without a `platform` file leaves the check without a dependency snapshot; the review jobs keep the container runner. The hand-back check is the real `CheckHandBack` in every environment, so a scripted bundle must be one the mirror accepts. The push is the real `PushBranch` too, so the test environment needs the signing key at `var/data/keys/signing_key` and a `<remote>` it can push to (a local git repository); only its `ChangeOpening` is replaced, by `tests/Core/Build/LocalChangeOpening`, which opens nothing, refuses no branch in `refuseForeignChange()` and answers `<project>:<branch>` as the change, opened as `Created`.
