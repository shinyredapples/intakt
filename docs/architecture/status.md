# Status read model

The status is one JSON document per install that reports, per project, the review lane, the build lane, the watcher's guard decisions, the changes waiting for the owner, the Needs-you items and the last outcomes, plus the install-wide holds and the message queues. The owner's dashboard reads it until Intakt's own dashboard replaces it (plan T68). The read model, its schema and the `intakt:status --format=json` command are built; the local endpoint is the next part of T68.

- **Schema:** `docs/user/status.schema.json` (JSON Schema draft-07). `StatusReadModelTest` validates every document it builds against it with `justinrainbow/json-schema`, and checks that the schema's enums for `holds`, a step's `progress` and an outcome's `decision` list exactly the cases of `Budget/Contract/SharedHold`, `Dashboard/Domain/ReviewerProgress` and `Review/Contract/Decision` (plus `null`), and that the enums for a build task's `step` and `outcome` list exactly the cases of `Build/Contract/BuildStep` and `Build/Contract/BuildStepOutcome`, and the `mark` enum (`definitions.mark`) exactly the cases of `Review/Contract/ReplayMark`.
- **Entry:** `Dashboard/UseCase/ShowStatus/StatusReadModel::json()` encodes `generated_at` (the `ClockInterface` moment, `DATE_ATOM`), `holds` (`Budget/Contract/Holds::sharedInEffect()`, by value, in the order they win; never an end, because an end can be a vendor's reset time, see [Measured use](measured-use.md)), `queues` and `projects` with `json_encode()` (`JSON_THROW_ON_ERROR`).
- **No queued message:** nothing is sent to a transport; the only dispatches are Review's `ReplayMarkOfProject` and `ReplayMarkOfRound` queries on the synchronous `query.bus` (through `Dashboard/Infrastructure/ReplayMarks`), answered in the same process from the database, and every other part reads the database or the transport's own store, so a stopped `messenger:consume` still yields a status.
- **Queues:** `Dashboard/Infrastructure/MessageQueues` gets every Messenger transport through `#[AutowireIterator('messenger.receiver', indexAttribute: 'alias')]`, so the list follows `config/packages/messenger.yaml` (`async`, `failed`), and reports `getMessageCount()` for a transport that implements `MessageCountAwareInterface` (the Doctrine transport, and the `in-memory://` transport of the test environment) and `null` for a transport without it.
- **Projects:** `Dashboard/UseCase/ShowStatus/ProjectStatuses` builds each section grouped by project and joins them per name; the names are the watcher's projects (`WatcherServices::PROJECTS`) and every project a section names, as strings, sorted with `SORT_STRING`, so a watched project without events is listed with empty sections. Each project carries `mark`, its `ReplayMark` value (`live` or `replay`, from `ReplayMarks::ofProject()`, so a watched project flagged before its first review is already `replay`), and each entry of `lanes.review`, `waiting_for_owner` and `last_outcomes` carries the `mark` of its board card (`Review::$mark`, see Replay mark in [Dashboard](dashboard.md)); the schema's `definitions.mark` enum lists exactly the cases of `ReplayMark`. It reads the ledger once (`readInOrder()`) and hands that one snapshot to every section (`LedgerReviewPages::boardOf()`, `LedgerFailingHeads::in()`, `LedgerWaitingHeads::in()`, `LedgerBuildSteps::in()`), so a watcher line written while the status is read cannot show one head both waiting and failed.
  - `lanes.review`: the board's cards in In review, newest first; each latest round with its change, round id, number, start, `reviewers` (the panel size from `review_started`) and one step per reviewer the ledger has a row for (role, tier, `ReviewerProgress` value). A reviewer's free-text failure or block reason is left out.
  - `lanes.build`: `Dashboard/Infrastructure/LedgerBuildSteps` keeps the latest `build_step_ended` event of each task (nested keys: project, then task), because a run of `intakt:build:task` stops at its first failed step and a new run starts again at `task`. Each task reports `task`, `step`, `outcome`, `failure` (redacted) and `ended_at` (the event's `recordedAt`), the task whose latest step is newest first. A row is left out when its `project` or `task` is no string, its `step` or `outcome` is no case of `BuildStep` or `BuildStepOutcome`, or a `failed` outcome has no failure text (or a `passed` one has one). Nothing here adds a slot, a queue or a state: the lane is only the ledger's events.
  - `guard_decisions`: `Dashboard/Infrastructure/LedgerWaitingHeads` keeps the latest watcher line per project and pull request (nested keys), as `LedgerFailingHeads` does, and reports `pending` for `head_pending` and `red` for `head_red` with `read_again_at` parsed as `DATE_ATOM` (a malformed moment reads as `null`); a later `round_queued`, `head_forgotten` or failure line ends it. `LedgerFailingHeads` adds each failing head that is not handed over as `failed`, with its cause, failures and `retry_at` as `read_again_at`.
  - `waiting_for_owner`: the board's Waiting on you cards (change and latest round id); nothing places a card there yet, so it is empty.
  - `needs_you`: the handed-over heads of `LedgerFailingHeads` (change, cause, failures).
  - `last_outcomes`: the `lastJudgedRound()` of every board card, newest judgment first, at most `ProjectStatuses::LAST_OUTCOMES` (10) per project, with the round's `outcome` (`null` without a recorded quorum, as on the review page) and `judgedAt`.
- **Command:** `Dashboard/UseCase/ShowStatus/ShowStatusCommand` (`intakt:status`, an invokable command) writes `StatusReadModel::json()` as one line with `OutputInterface::OUTPUT_RAW`, so text in a cause or a change name that looks like console markup is printed as recorded. `--format` is the backed enum `StatusFormat` (only `json`, the default), resolved by the Console's `#[Option]` enum support, which refuses any other value with `InvalidOptionException` before the command runs. It exits with `Command::SUCCESS`.
- **No secrets:** every failure cause goes through `Platform/Contract/Redactor` (the held credentials and the secret shapes, like a log line); round ids, change names, roles and tiers are Intakt's own values.

Tests: `tests/Core/Dashboard/UseCase/ShowStatus/StatusReadModelTest.php` (a ledger in memory, a stubbed `Holds`, `Redactor` and transports, the replay marks through `tests/Support/ReplayMarkBus`, a `MockClock`; a flagged project and its reviews marked `replay`, a live one `live`, a watched flagged project without events; a forced order in which the watcher records a failed head pending between two reads of the ledger, reported once; a task stopped at the mirror and one stopped at the clone, a task built again, malformed build rows); `tests/Core/Dashboard/UseCase/ShowStatus/ShowStatusCommandTest.php` (the command through the kernel on SQLite: its output validates against the schema, also with a message queued and no consumer, `json` is the default and `yaml` is refused).
