# Status read model

## In short

`StatusReadModel::json()` builds one JSON document per install, valid against `docs/user/status.schema.json`: the install-wide holds, the message queues and, per project, its replay mark, the review and build lanes, the watcher's guard decisions, the changes waiting for the owner, the Needs-you items and the last outcomes. It reads the ledger once and hands that snapshot to every section, and sends nothing to a transport (its only dispatches are synchronous queries), so a stopped `messenger:consume` still yields a status. Failure causes are redacted. `intakt:status --format=json` prints it as one line, and `GET /status` answers the same bytes on the loopback-only dashboard port.

## Details

The status is one JSON document per install that reports, per project, the review lane, the build lane, the watcher's guard decisions, the changes waiting for the owner, the Needs-you items and the last outcomes, plus the install-wide holds and the message queues. The owner's dashboard reads it until Intakt's own dashboard replaces it (plan T68). The read model, its schema, the `intakt:status --format=json` command and the local endpoint are built.

- **Schema:** `docs/user/status.schema.json` (JSON Schema draft-07). `StatusReadModelTest` validates every document it builds against it with `justinrainbow/json-schema`, and checks that the schema's enums for `holds`, a step's `progress` and an outcome's `decision` list exactly the cases of `Budget/Contract/SharedHold`, `Dashboard/Domain/ReviewerProgress` and `Review/Contract/Decision` (plus `null`), and that the enum for a build task's `step` lists exactly the cases of `Build/Contract/BuildStep` and the one for its `outcome` exactly the cases of `Build/Contract/BuildStepOutcome` (`asked` included since #2674); the `mark` enum (`definitions.mark`) exactly the cases of `Review/Contract/ReplayMark`; and an outcome's `end` enum exactly the cases of `Review/Contract/RoundEnds`.
- **Entry:** `Dashboard/UseCase/ShowStatus/StatusReadModel::json()` encodes `generated_at` (the `ClockInterface` moment, `DATE_ATOM`), `holds` (`Budget/Contract/Holds::sharedInEffect()`, by value, in the order they win; never an end, because an end can be a vendor's reset time, see [Measured use](measured-use.md)), `queues` and `projects` with `json_encode()` (`JSON_THROW_ON_ERROR`).
- **No queued message:** nothing is sent to a transport; the only dispatches are Review's `ReplayMarkOfProject` and `ReplayMarkOfRound` queries on the synchronous `query.bus` (through `Dashboard/Infrastructure/ReplayMarks`), answered in the same process from the database, and every other part reads the database or the transport's own store, so a stopped `messenger:consume` still yields a status.
- **Queues:** `Dashboard/Infrastructure/MessageQueues` gets every Messenger transport through `#[AutowireIterator('messenger.receiver', indexAttribute: 'alias')]`, so the list follows `config/packages/messenger.yaml` (`async`, `failed`), and reports `getMessageCount()` for a transport that implements `MessageCountAwareInterface` (the Doctrine transport, and the `in-memory://` transport of the test environment) and `null` for a transport without it.
- **Projects:** `Dashboard/UseCase/ShowStatus/ProjectStatuses` builds each section grouped by project and joins them per name; the names are the watcher's projects (`WatcherServices::PROJECTS`) and every project a section names, as strings, sorted with `SORT_STRING`, so a watched project without events is listed with empty sections. Each project carries `mark`, its `ReplayMark` value (`live` or `replay`, from `ReplayMarks::ofProject()`, so a watched project flagged before its first review is already `replay`), and each entry carries the `mark` of the round it names, never one mark of its review (`ReviewedRound::replayMark()`, see Replay mark in [Dashboard](dashboard.md)): `lanes.review` and `waiting_for_owner` that of the card's latest round, `last_outcomes` that of the last ended round, so a replay round opened after a live round of the same change is `replay` in the review lane while the live round's outcome stays `live`; the schema's `definitions.mark` enum lists exactly the cases of `ReplayMark`. It reads the ledger once (`readInOrder()`) and hands that one snapshot to every section (`LedgerReviewPages::boardOf()`, `LedgerFailingHeads::in()`, `LedgerWaitingHeads::in()`, `LedgerBuildSteps::in()`), so a watcher line written while the status is read cannot show one head both waiting and failed.
  - `lanes.review`: the board's cards in In review whose `Review::activeRound()` is a round (the latest round neither judged nor ended, see End states on the review page in [Dashboard](dashboard.md)), newest first; each such round with its change, round id, number, start, `reviewers` (the panel size from `review_started`) and one step per reviewer the ledger has a row for (role, tier, `ReviewerProgress` value). A reviewer's free-text failure or block reason is left out.
  - `lanes.build`: `Dashboard/Infrastructure/LedgerBuildSteps` keeps the latest `build_step_ended` event of each task's latest run (nested keys: project, then task), because a run of `intakt:build:task` stops at its first failed step and a new run starts again at `task`. The latest run is told by `LatestBuildRun`, the rule the task page (`latestRunOf`) uses too (see [Dashboard](dashboard.md)), so when two runs of a task overlap, a step the older run writes later changes neither the row nor its place, and a task whose latest run has no well-formed row is left out. Each task reports `task`, `step`, `outcome`, `failure` (redacted), `ended_at` (the event's `recordedAt`) and `question`, the task whose latest step is newest first. A row is left out when its `project` or `task` is no string, its `step` or `outcome` is no case of `BuildStep` or `BuildStepOutcome`, a `failed` outcome has no failure text (or another outcome has one), an `asked` outcome belongs to a step other than `build_job`, or its `run` is given but no UUID, by `latestRunOf` for the task page as well. `intakt:build:task` writes `asked` for the `build_job` step of a parked task (through `ParkedTasks::park()`, see [Build task](build-task.md#the-parked-task-record)), so a parked task shows `build_job` `asked` as its latest step (#2674). For such a task only, `ProjectStatuses` asks `Dashboard/Infrastructure/ParkedQuestionTexts` for the parked row through the Build contract's `ParkedQuestions`, and `question` holds its `text`, `choices` and `recommendation`, each redacted, and `parked_at` (`DATE_ATOM`); it is `null` for every other outcome and for an `asked` step whose row is gone, malformed or parked by another run than the step's. The pull request step is the last `BuildStep` case, so a task whose latest row is `push` `failed` stopped at the push with the reason the push step recorded, one whose latest row is `pull_request` `passed` went through every step, and one whose latest row is `push` `passed` is either between the two steps or a run recorded before the pull request step existed, which went through every step of its time. The board and the task page tell the two apart by the row's `next` key (see [Dashboard](dashboard.md)); `lanes.build` reports neither `next` nor `final`, so it does not. Nothing here adds a slot, a queue or a state: the lane is only the ledger's events.
  - `guard_decisions`: `Dashboard/Infrastructure/LedgerWaitingHeads` keeps the latest watcher line per project and pull request (nested keys), as `LedgerFailingHeads` does, and reports `pending` for `head_pending` and `red` for `head_red` with `read_again_at` parsed as `DATE_ATOM` (a malformed moment reads as `null`: one holding a NUL byte, and one that does not format back to the stored text, such as an impossible calendar date like `2026-02-30T00:00:00+00:00`, included); a later `round_queued`, `head_forgotten` or failure line ends it. `LedgerFailingHeads` adds each failing head that is not handed over as `failed`, with its cause, failures and `retry_at` as `read_again_at`.
  - `waiting_for_owner`: the board's Waiting on you cards (change and latest round id); nothing places a card there yet, so it is empty.
  - `needs_you`: the handed-over heads of `LedgerFailingHeads` (change, cause, failures).
  - `last_outcomes`: the last ended round of every board card: its newest round that is judged or has an ending (`ReviewedRound::hasEnded()`, the `RoundEnding` `LedgerRounds` got from the Review contract's `RoundEndings`), so a round running after it does not hide it; newest first by `judgedAt`, else by the ending's `endedAt` (when the ledger recorded the failed judging, or when the upper wait ran out), else by `startedAt` (a judging parked without a ledger record), at most `ProjectStatuses::LAST_OUTCOMES` (10) per project. Each has `end`, the `RoundEnds` value (`judged` for a judged round, `judging_failed` for a judging that failed for good, `no_outcome_in_time`; the schema's enum lists exactly its cases), the round's `outcome` as `decision` (`null` without a recorded quorum, as on the review page, and for a round ended without the judge's call) and `judgedAt` (`null` for such a round). A judging that failed for good is shown from its ledger event `judging_failed` (see [Review flow](review-flow.md#a-judging-that-failed-for-good)), since its `DispatchOnFailureStamp` keeps it out of the `failed` transport that `queues` counts.
- **Command:** `Dashboard/UseCase/ShowStatus/ShowStatusCommand` (`intakt:status`, an invokable command) writes `StatusReadModel::json()` as one line with `OutputInterface::OUTPUT_RAW`, so text in a cause or a change name that looks like console markup is printed as recorded. `--format` is the backed enum `StatusFormat` (only `json`, the default), resolved by the Console's `#[Option]` enum support, which refuses any other value with `InvalidOptionException` before the command runs. It exits with `Command::SUCCESS`.
- **Endpoint:** `Dashboard/UseCase/ShowStatus/ShowStatusController` (`dashboard_show_status` at `GET /status`, `DashboardRoutes::SHOW_STATUS`) answers `StatusReadModel::json()` unchanged through `JsonResponse::fromJsonString()` (`Content-Type: application/json`), so the body is the command's line without its line break and is never decoded and encoded again. Reachability is local because the dashboard port is bound to loopback; the route's name starts with `DashboardRoutes::PREFIX`, so `Dashboard/Infrastructure/RefuseForeignHost` additionally answers `400` before the controller runs unless the requested `Host` names loopback and `DASHBOARD_PORT` (it validates the name and the port, not the peer address; see [Dashboard](dashboard.md)). Symfony also routes `HEAD` to a `GET` route, so `HEAD /status` answers `200` with the headers and an empty body; any other method gets `405`. It needs no consumer, for the reasons under No queued message.
- **No secrets:** every failure cause goes through `Platform/Contract/Redactor` (the held credentials and the secret shapes, like a log line); round ids, change names, roles and tiers are Intakt's own values.
