## Reviewer repository tools

Plan task T7, part 1 (design: [Reviews](../design/05-architecture/07-reviews.md), [threat model](../design/05-architecture/14-threat-model.md)). `Core/Review` gives a reviewer agent three read-only tools over one checkout of the head under review: `read_file`, `list_directory` and `search_files` (`src/Core/Review/Infrastructure/Repository/`). Each is a Symfony AI `#[AsTool]` with the effect hints `readOnlyHint`, `destructiveHint: false`, `idempotentHint` and `openWorldHint: false`. Since plan task T16, part #580, a reviewer no longer calls them in process: it reaches the same tools over the per-review MCP server (see Reviewers over MCP under [MCP server for the owner](mcp-server.md)), and `ReviewerToolboxFactory` is the in-process twin that tests use to prove both paths give the same verdict.

- **Checkout:** `Contract/Checkout` is built from the directory of the checkout and is the only place that decides what is inside it. `resolve($path)` refuses (with `PathOutsideCheckout`) an absolute or drive path, a null byte, a `..` segment, any `.git` segment and, after `realpath`, a location outside the root or with a `.git` segment below it, so a symlink in the code under review can lead neither out nor into the git directory. A path that does not exist is `PathNotInCheckout`.
- **Toolbox:** `ReviewerToolboxFactory::inCheckout($checkout)` (and `create($request)` for the checkout of a `ReviewRequest`) returns a `Toolbox` with the three tools and an event dispatcher holding `DenyPathsOutsideCheckout`; the reviewer agent wraps it in a `FaultTolerantToolbox`. A tool that throws (a missing file, a directory read as a file) answers the model with `An error occurred while executing tool "<name>".` instead of ending the run. The classes are built per review, so `config/services.yaml` excludes the `Repository/` folder from service registration.
- **Listener:** `DenyPathsOutsideCheckout` listens to `ToolCallRequested` and denies a call whose `path` argument escapes the checkout, before any tool runs; the denial reason is the model's answer. A `path` that is not a string is refused with an `InvalidToolCallArgumentsException` (answered to the model as `The path must be a string.`) rather than denied, because the toolbox's resolver would coerce it and the reviewer agent counts an invalid argument as a malformed call. Before it decides on the path, the listener runs the toolbox's own `ToolCallArgumentResolver` (one instance, shared with the `Toolbox` by the factory) on the call, so a call that misses another required argument (`search_files` without `text`) is refused as an invalid argument even when its path escapes the checkout: a denial stops the toolbox before its own resolver runs, and only a complete call is denied. All three tools name that parameter `path`, which a test checks for each tool.
- **Limits:** `read_file` answers a binary file (one with a NUL byte anywhere, read in chunks of 1 MiB to its end, not only the part an answer shows, the rule the diff applies) with `Binary file, not shown: <n> bytes`, its size, instead of its bytes; it returns at most 100,000 bytes of any other file, cut on a UTF-8 character boundary, and fails for one that is not valid UTF-8; `search_files` matches text literally and case-sensitively, skips symlinks, `.git`, files over 1 MB (also when the path names the file) and files that are not valid UTF-8, fails with `PathNotReadable` for a file whose size cannot be read (one removed after the walk found it; the stat's warning is silenced, so the refusal is the same under a debug kernel, whose error handler throws warnings), cuts each matched line to 500 bytes on a UTF-8 character boundary (marked `[line cut]`), and stops at 100 matches or before the answer passes 100,000 bytes; `list_directory` stops before its answer passes 100,000 bytes (marked `[more entries not shown]`). `list_directory` and `search_files` replace invalid UTF-8 in file names. `search_files` skips an unreadable subdirectory (`RecursiveIteratorIterator::CATCH_GET_CHILD`) and still returns the matches in the rest; a call whose `path` names an unreadable directory gets the tool error answer (`An error occurred while executing tool "search_files".`) from the `FaultTolerantToolbox`. Every answer is valid UTF-8 because it reaches the provider as JSON, outside the `FaultTolerantToolbox`.
- **Tests:** `tests/Core/Review/Contract/CheckoutTest.php` covers `Checkout::resolve` on a fixture checkout (escaping paths, links into the git directory, a missing path, a root that is not a directory); `tests/Core/Review/Infrastructure/Repository/ReviewerAgentTest.php` runs a real `Agent` on a `TraceablePlatform` around `MockPlatformFactory`, whose script (a `ScriptedResponse` closure) asks for tool calls, with a `TraceableToolbox` around a `FaultTolerantToolbox`. They assert through the AI Bundle's `AiAssertionsTrait` (`assertToolCalled`, `assertPlatformCallCount`): the test overrides `getAiDataCollector()` to build the bundle's `DataCollector` from that platform and toolbox, since the toolbox is built per review and is not a container service a profiled request would collect. `tests/Core/Review/UseCase/JudgeRound/BinaryFileReadReviewTest.php` (group `persistence`) runs a scripted review whose reviewer reads a PNG the change adds with `read_file`, through the real agent, worker and judge, and checks the provider gets the binary file's name and size and the verdict is recorded.
