# Job images

`Core/Job/UseCase/BuildJobImage` builds the image a project's jobs run in (plan task T45) and checks that the image has the project's PHP. The doors are `intakt:job:build-image <directory> <tag>` (`BuildJobImage`: plan, build, probe) and `intakt:job:plan-image <directory>` (the plan alone, with the generated Dockerfile or where the project's Dockerfile is built, no engine call); both take `--kind=review` for [the review job image](#the-review-job-image) (`JobImageKind::Review`, passed to `BuildJobImage::build()` and `JobImagePlanner::planFor()`; the default is `project`, the image as its source gives it, and another value is refused by the console with the values there are), and `plan-image` then prints the Dockerfile Intakt writes and, for a project tree, where it is built. No lane builds an image or starts a job from one yet (the build job arrives with T49). The jobs themselves run as described in [Job containers](job-containers.md).

## Where the image comes from

`JobImagePlanner` reads the commit at `HEAD` of the checkout, never its working tree (`ProjectFiles`, through the [hardened git call](requirements.md#the-hardened-git-call): `ls-tree` to find a file, `cat-file blob` to read it, `archive` for a build context). Only a regular file counts (mode `100644` or `100755`), so a symlink or a submodule named `Dockerfile` is no source. The directory must hold `.git` itself: git would otherwise find the repository of a parent folder and read that project's files. The first source that exists wins:

| Source | Plan | Build context |
|---|---|---|
| `.devcontainer/devcontainer.json` with `build.dockerfile` | that Dockerfile; `build.context` (default `.`) and `build.dockerfile` are relative to `.devcontainer/` | `git archive HEAD:<context>` |
| `.devcontainer/devcontainer.json` with `image` | a one-line Dockerfile `FROM <image>` | that Dockerfile alone |
| `Dockerfile` at the root | that Dockerfile, used as it is | `git archive HEAD` |
| `composer.json` alone | a generated Dockerfile (below) | that Dockerfile alone |

`devcontainer.json` is read as JSON with comments: `//` and `/* */` comments and trailing commas are removed outside strings before `json_decode`. It is refused (`JobImageNotBuilt`) when it uses `dockerComposeFile`, names neither `image` nor `build.dockerfile`, names a context outside the repository (absolute, or `..` past the root) or a Dockerfile outside its context, or an `image` that is not an image reference (Docker's grammar in short: lowercase path parts, an optional port, tag and `sha256` digest, so no space or line break reaches the `FROM` line). Other devcontainer keys (`build.args`, `build.target`, features) are not read. Because the context comes from `git archive`, it holds the committed files only; `.dockerignore` is not applied.

## The project's PHP

`PhpProfile` reads `composer.json` at `HEAD` before any source is chosen:

- `config.platform.php` (a version of two or three numbers) and `require.php` (a Composer constraint, parsed with `composer/semver`). With neither, every source is refused (`composer.json names no PHP version ...`), also beside a Dockerfile: a job never gets an image with some other PHP. A platform version that does not meet `require.php` is refused too.
- The rule an image must meet: the platform version exactly when it has three numbers, every patch of that minor when it has two (`8.4` means `8.4.*`), and `require.php` as well.
- The extensions: every `ext-*` key of `require` and `require-dev`, lowercased as Composer does. A name that is not `a-z`, `0-9`, `_` and `-` is refused.

A project without `composer.json` gets its devcontainer or Dockerfile image unchecked; one without any of the four sources is refused.

## The generated Dockerfile

`GeneratedDockerfile` writes, in order:

1. `FROM php:<version>-cli`, from the platform version's minor when there is one, otherwise from the newest of the minors 8.5, 8.4, 8.3 and 8.2 for which some patch meets the rule (`PhpProfile::imageVersionIn`, given the minor's newest known released patch from `GeneratedDockerfile::RELEASED_PATCHES`, for example `8.4.25`): the minor alone (`php:8.4-cli`, a tag that moves with the patches) only when one range the rule admits contains that released patch and runs to the minor's end with no gap (`^8.4`, `>=8.4.3 <8.5`; for a minor without a known released patch, when the rule's last range in it runs to the minor's end), otherwise a pinned patch: the highest patch the rule admits at or below the released one (`8.4.25` for `^8.4 !=8.4.9999` or `>=8.4.0 <8.5 !=8.4.26`, `8.4.24` for `>=8.4.0 <8.5 !=8.4.25`, `8.4.19` for `>=8.4.1 <8.4.20`), else the lowest patch it admits above it (`8.4.30` for `>=8.4.30 <8.5`, `8.4.31` for `>8.4.30 <8.5`); without a known released patch, the highest patch the rule admits in that minor. A three-number platform version therefore always becomes the image's version. A minor where no range admits a patch (`>8.4.1 <8.4.2`) is skipped. A rule no candidate meets is refused.
2. Composer from `composer:2.11.1`, by the release image's digest, and `install-php-extensions` from `mlocati/php-extension-installer:2.13.2`.
3. `ca-certificates`, `curl`, `git`, `unzip`, `nodejs` and `npm` from Debian: `curl` for the [start check](job-containers.md#start-check), `git` for the checkout.
4. `npm install --global <package>@<version> ...` for each dependency of the [CLI manifest](#the-cli-versions), in its order: Claude Code (`@anthropic-ai/claude-code`) and Codex (`@openai/codex`).
5. For each extension: skipped when `php -m` lists it already (spelled as Composer spells it), otherwise `install-php-extensions <name>`; still missing afterwards, the step prints `missing PHP extension: <name>` and fails the build.

Steps 3 and 4 are the job tools (`JobTools::steps()`), which [the review job image](#the-review-job-image) adds to a project's own Dockerfile too.

## The review job image

A review job will run a reviewer's CLI with `git` in the image, and a project's own Dockerfile or devcontainer image need not hold them. `JobImagePlanner::planFor()` with `JobImageKind::Review` therefore plans the image as above and then:

- a generated image is planned unchanged, since it holds the job tools already;
- for a devcontainer `image`, the one-line `FROM <image>` Dockerfile gets the job tools;
- for a devcontainer `build.dockerfile` or a root `Dockerfile`, the project's Dockerfile is read at `HEAD` (a missing file or a symlink is refused: `The Dockerfile <path> is not a file at HEAD, ...`), and Intakt writes it, followed by the job tools, as `.intakt-review.Dockerfile` at the top of the build context (`ReviewDockerfile::PATH`), which is the project's tree as before; the build names that file, so the project's own Dockerfile is sent as it is committed. `git archive --add-file` appends it to the tar git writes (`ProjectFiles::archiveAdding`), so long paths, modes and symlinks of the tree stay as committed. A project file of that name comes first in the tar and the later entry wins when the engine unpacks it (`BuildJobImageCommandTest` lists the sent tar and finds the added entry last).

`ReviewDockerfile::after()` writes the project's Dockerfile with its trailing white space removed, a blank line, `# Added by Intakt for a review job.`, `USER root` (the project's last stage may end as another user, who could not install packages) and the job tools, so they apply to the last stage, which is the image built. It refuses (`The project's Dockerfile cannot get the review job's tools: ...`) a Dockerfile whose parser directives at the top set another escape character than the backslash (`# escape=` followed by a backtick, case and spaces as Docker allows them, read with BuildKit's directive pattern, so an earlier directive whose value holds spaces, such as `# check=skip=all; error=true`, does not end the scan, while a line that is not a known directive (`syntax`, `escape`, `check`), such as `# maintainer=Example Team`, is a comment and ends it; also after a UTF-8 byte order mark, which Docker strips before it reads the directives; the same line after an instruction, a comment or a blank line is a comment), because the added steps continue their lines with a backslash, and one whose last line that is not blank or a comment ends with a backslash that continues it (one standing alone, or following another character than a backslash, as Docker's parser reads it; an escaped backslash, `\\`, stays a literal and ends the line), because Docker would join the added steps to it. The job tools install with `apt-get`, so a review image needs a last stage with Debian's or Ubuntu's package tools; on another base the build fails with the engine's error. The image is then built and its PHP probed as any job image.

The image only holds the tools: which hosts a review job reaches is the job's egress allowlist ([Egress](job-containers.md#egress)), so a reviewer reaches its vendor only through the job's proxy. The job's command, `docker/job/review.sh`, and `ReviewJob`, which runs a job in the image a project's `review_job.image` names, are described in [Review job](review-job.md). The review flow starts a review job for each reviewer when the install has a container engine ([Where a reviewer runs](review-flow.md#where-a-reviewer-runs)); nothing builds the image on its own.

## The CLI versions

`docker/job/cli/package.json` is the one place the Claude Code and Codex versions live: its `dependencies` name both CLIs at exact versions, and `docker/job/cli/package-lock.json`, written by `npm install --package-lock-only`, locks them. No PHP code or test repeats a version. `CliManifest` reads the manifest each time a Dockerfile is generated (the release image holds it, since its `Dockerfile` copies the repository) and refuses it (`JobImageNotBuilt`, `The CLI manifest <path> cannot be used: <reason>.`) when it cannot be read, is not JSON, has no non-empty `dependencies` object, or names a package that is not an npm package name (lowercase, an optional `@scope/`) or a version that is not exact (three numbers and an optional pre-release; no range, tag or URL), because both end up in the `RUN` line.

The versions are bumped by Dependabot pull requests that change the manifest and its lock together and go through normal review and CI like any dependency pull request (no auto-merge). The `npm` entry of `.github/dependabot.yml` for `/docker/job/cli` checks weekly (prefix `build` with scope), waits until a release is 3 days old, and puts both CLIs in one group (`job-image-cli`), so one update round opens one pull request and rebuilds the image once (`tests/Gates/DependabotImageGroupsTest.php` checks the entry and that its one group matches every CLI the manifest lists). A bump by hand is an edit of `package.json` followed by `npm install --package-lock-only` in `docker/job/cli/`.

`tests/Gates/JobImageCliVersionsTest.php` fails when the generated Dockerfile installs another version of a CLI than the manifest names, or leaves one out (it also checks that a Dockerfile with a changed version fails), when the manifest names other packages than the two CLIs, and when the lock file locks other versions than the manifest.

## The build

`BuildContext::of` writes the context as a tar named `context.tar` into a new folder only its owner can enter (mode `0700`, named `intakt-image-<random>` under the system temporary directory). `BuildContext::upload` turns that file into the request body: a closure that hands out the tar in the chunks the HTTP client asks for (the curl client sends them chunked), so it is never held in memory as one string and a large repository need not fit in it. When the client has read the last byte, the closure closes the file and removes the folder, so the tar leaves the disk once it is sent and not when the build ends. `BuildJobImage` removes the folder again once the request is over, for a request that broke off before the end of the tar or never started (engine unreachable, connection reset). `BuildContext::remove` refuses (`LogicException`) a path that is not a `context.tar` in an `intakt-image-` folder directly under the system temporary directory, since it deletes the whole folder. `DockerEngine::build` sends that body to `POST /build` with `t=<tag>`, `dockerfile=<path in the context>`, `rm` and `forcerm`, waits up to 600 seconds without output and 3600 seconds in all, and reads the answer line by line (`EngineAnswer::built`): `stream` lines are the output, an `error` line is the failure, and the `aux.ID` line names the built image (`sha256:` and 64 hex digits). A line that is no JSON object, or whose `stream` or `error` is not text or whose `aux.ID` is no such id, is `DockerEngineFailed`, and so is an answer with neither an `error` nor an image id (an empty or cut-off answer), so only a build the engine finished counts. A failed build is `JobImageNotBuilt` with the engine's error and the last 20 lines of output, so a missing extension names itself. The tag must be an image reference without digest.

## The check after the build

Whenever there is a `PhpProfile`, `PhpInImage` runs a probe job in the new image through `JobRunner`, by the image id the build named rather than the tag, so a build that runs at the same time and moves the tag cannot make this one check its image (job id `image-probe-<hash of the image id>-<16 random hex digits>`, so two builds that end in the same image id probe it under their own job ids and container names; no network, no inputs, 256 MiB, one CPU, 60 seconds). It runs `php -r` and writes `PHP_VERSION` and the loaded extensions (lowercased, a space as `-`) to `php.json` in its output directory. The image is refused when the probe does not exit with 0, writes no version of three numbers or no list of names, has a PHP the rule does not allow (`The image <tag> has PHP 8.4.19, which does not meet >=8.5.12.`), or lacks an extension (`The image <tag> lacks the PHP extensions pdo_sqlite.`). This also covers a devcontainer or Dockerfile image, and the moving minor tag of a generated one. The probe is a job like any other, so an image that declares volumes is refused there (`JobRefused`).

## Limits

- Images are built on demand by the command; nothing caches them per commit or rebuilds them when `composer.json` or the Dockerfile changes yet.
- `POST /build` sets no network mode, so the `RUN` steps of a project's Dockerfile or devcontainer run on the engine's host with its default network and no egress proxy. The threat model names this input ([Job image build inputs](../design/05-architecture/14-threat-model.md#job-image-build-inputs)); it must be settled before builds run on a builder's commits (plan T49).
- A compose file and an owner-supplied prebuilt image ([decision 4](../design/06-decisions.md)) are not image sources yet.
- Intakt's own job image is its release image: the `Dockerfile` at its root, with PHP 8.5.12 and every `ext-*` of `composer.json`, but no Claude Code or Codex CLI (its review job image adds them). That `Dockerfile` declares no `VOLUME`, so its probe is not refused (`JobImagePlannerTest::testIntaktsOwnSourcesPlanItsRootDockerfileWhichDeclaresNoVolume`); `/app/var/data` is mounted by whoever runs it. Intakt has no `.devcontainer/devcontainer.json`, which would come first.
