## Quality gates

`bin/check` runs every gate below and prints one JSON line per gate, then a result line. CI runs the same command. The `journeys` gate is not one of them: it runs only alone, with `bin/check --journeys` (see [Journeys](journeys.md)).

Each selected gate runs in a child process of its own (`GateChildren`, through `ProcessRunner::runToItsEnd()`, stopped after 3600 seconds, keeping what it printed before, also when a signal kills it; it needs the `posix` extension, else it fails with `cannot run ...: the PHP posix extension is missing`). The child runs in a session of its own (`setsid`, never a PID or user namespace, so the gate's tools see the real user and processes), and its whole process group is killed with signal 9 when it ends. When the child runs past its deadline (the runner's own clock, not Symfony's `Process` timeout, which would send TERM and KILL at once), and when `bin/check` gets SIGHUP, SIGINT or SIGTERM (`StopSignalForwarding`), the group first gets SIGTERM, then SIGKILL as soon as it is gone or after 2 seconds (`ProcessGroup::STOP_GRACE_SECONDS`); a signal then ends `bin/check` with that same signal. A contained run the child starts through `ProcessRunner::runWithin()` lives in a session of its own, which a signal to the child's group does not reach, so `runWithin()` forwards the same three signals too: the child kills its contained run's group with signal 9 and then dies of the signal, which is why the parent asks before it kills. A child that dies of signal 9 (the OOM killer, an outside `kill -9`, or the parent's SIGKILL after the 2-second grace) runs no handler, so a contained run it started through `runWithin()` may keep running. The child is `php config/gates/run-gate.php <gate> <the arguments of bin/check>`, which runs in `bin/check`'s working directory; its launcher (`setsid`, then `sh`) starts in the workspace root (`--root`, else the repository) and changes to that directory just before it runs the child, so a relative or empty `PATH` entry finds `setsid` and `sh` where the preflight looked for them (`ProcessRunner::runToItsEndWithToolsFrom()`, which otherwise runs as `runToItsEnd()`). The child calls `CheckCommand::runGate()`, finds the gate in the selection those arguments make (a gate they leave out is an unknown gate, exit code 2), runs that one gate and prints its result line, exiting with 0 when it passes and 1 when it fails. The child entry sends PHP's warnings and notices to stderr (`display_errors=stderr`), so a PHP without its own `php.ini`, whose CLI prints them on stdout, cannot spoil the result line; the parent writes each child's stderr to its own stderr as the child finishes. The children run one after another, in the gate order of the table below. Once all of them have finished, the parent prints their result lines in that order, then the result line. A child's line counts only when its output is exactly one line followed by one newline, with no other byte before or after, that line is byte for byte what `json_encode()` with the flags of `GateResult::toJson()` (`GateResult::JSON_FLAGS`) writes for the object it decodes to (so a repeated key, a `findings` object, an escaped slash or a stray NUL byte or space fails), it is a JSON object of that gate with no fields beyond `gate`, `ok`, `findings`, `omitted`, `note` and `slowest`, `ok` agrees with its findings and omitted count, and the exit code agrees with `ok` (`GateReport`); a child that crashes, times out or prints anything else fails its gate with the finding `gate process ended with exit code <n> and no valid result line: <its output, then its error output>`, of which only the end is kept, after `...`, when it does not fit the finding's 300 characters (`GateResult::MAXIMUM_FINDING_LENGTH`), so a timeout or signal stays named. Missing tools are checked in the parent before any child starts (exit code 2), and so are the `pcntl` and `posix` extensions (`RequiredTools::missingToRunEachInItsOwnProcess()`): a child in a session of its own gets no Ctrl-C from the terminal, so without them an interrupted `bin/check` would leave it running. Tests: `tests/Gates/GateChildrenTest.php` (a slow passing gate and a fast failing gate reported in gate order, a crashing child, a child's stderr passed on, all through a home whose child entry is a fixture; a PHP warning of the real child entry stays off its result line), `tests/Gates/GateReportTest.php` (lines that count and lines that fail the gate), `tests/Gates/GateReportExactLineTest.php` (NUL bytes, a space, a vertical tab, a repeated key, a `findings` object, no newline or two fail the gate; the line `GateResult::toJson()` writes, plus one newline, passes), `tests/Gates/GateReportLongOutputTest.php` (a long output keeps its end, a short one stays whole), `tests/Gates/GateChildTreeTest.php` (a program a child started is stopped when the child times out, when it ends, and when `bin/check` is interrupted; a contained run started through `runWithin()` is stopped when the child times out and when `bin/check` is interrupted), `tests/Gates/GateChildTimeoutTest.php` (a timed-out child fails its gate with its output and error output), `tests/Gates/GateChildCrashTest.php` (a child killed by a signal fails its gate with its output, its error output and `... was killed by signal <n>`), `tests/Gates/GateChildRelativePathTest.php` (with `PATH=tools` and the tools under the workspace root, a run from another directory passes its gate; without `setsid` there it stops with exit code 2 before any gate).

| `ratchet` | the shrink-only check of the [ratchet lists](../design/04-constraints.md#ratchet-lists-for-a-new-rule-decided-2026-11-06) (`RatchetListsGate`), in the fast run too. A ratchet list is a PHPStan baseline file of one new rule: every include of the checked tree's `config/gates/phpstan.neon` (each a plain relative path of letters, digits, `_`, `.`, `/` and `-` on its own `- path` line of a block `includes:` key with nothing after its colon, resolved from `config/gates/`; the item may be indented or, as NEON allows, sit at the key's own indentation; an absolute path, a path above the repository root, a `%placeholder%`, a flow list such as `includes: [...]`, a comment after the key, a configuration whose first line is indented (its top-level keys cannot be told apart) or another form of include fails the gate) that points outside `config/gates/` and `vendor/` (`PhpStanIncludes`). With no list the gate passes with the note `no ratchet lists` and reads no git; a tree without git skips it. Each list must name its cleanup issue in its header (a line `# Cleanup issue: #<number>` among the comment lines above the first other line) and hold nothing but `parameters:` with `ignoreErrors:` (an empty `ignoreErrors: []` passes, so the last entry can be deleted) (`RatchetListFile`, read by indentation), so a list cannot set another parameter, include a file or register a service. `IgnoredErrorsReader` reads the entries with PHPStan's own `dump-parameters --json`, once per list and version, side by side, on a copy at the list's path in a scratch directory with `reportUnmatchedIgnoredErrors: false` (the copy has no code next to it); every entry needs exactly `identifier`, `path` (inside the repository), a positive `count` and one of `message` or `rawMessage`. The working tree's list is compared with the list at the merge base with the target branch (`--base`, read with `git show`): an entry whose identifier, path or message pattern is not on the target branch's list (an added entry, a widened pattern such as `#.*#`, a moved file) and a `count` above the target branch's fail; deleting entries and lowering counts pass. A list absent on the target branch passes only when its include is absent there too, so it arrives in the change that adds its include to the protected configuration. A violation the list does not hold, and an entry that matches nothing (`reportUnmatchedIgnoredErrors` stays on) or names a file that no longer exists, fail the `phpstan` gate instead. Tests: `tests/Gates/RatchetListsGateTest.php`, and `tests/Gates/RatchetListStaticAnalysisTest.php` for the `phpstan` side |

The gates start `git` only through `Workspace::git()`, which runs the [hardened call](requirements.md#the-hardened-git-call) built by their own protected copy, `config/gates/src/HardenedGitCall.php`; the gitleaks gates start gitleaks with the hardened `git` environment. When the repository's `.git/info/attributes` exists, the call refuses it and `CheckCommand::runGate()` reports every gate that reads git as failed with that reason.

Options: `--fast` (changed PHP files only), `--journeys` (see [Journeys](journeys.md)), `--only=<gate,...>`, `--skip=<gate,...>`, `--base=<ref>` (the base of the change, default `origin/main`).
