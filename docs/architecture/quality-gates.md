## Quality gates

### In short

`bin/check` is the command that checks a change. It runs a fixed list of gates, from coding standards and static analysis to tests, secret scans and commit subjects, and prints one JSON line per gate, then a result line. CI runs the same command with the pull request's arguments, so a local run and a CI run check the same things. Each gate runs in a child process of its own, which `bin/check` stops as a whole when it runs too long or when `bin/check` gets a stop signal.

Worth knowing:

- `--fast`, `--only=<gate,...>` and `--skip=<gate,...>` narrow a run; `--base=<ref>` sets the base of the change (by default `origin/main`).
- The `journeys` gate is not part of a normal run; it runs only with `bin/check --journeys`.
- No gate can be weakened inline: the `comments` gate refuses suppression directives such as `@phpstan-ignore*`.
- Before any gate runs, `bin/check` looks up the tools the selected gates need and names the missing ones.

The rest of this page is the detailed reference.

`bin/check` runs every gate below and prints one JSON line per gate, then a result line, unless `--reuse` asked it to reuse the passed result of an identical tree (see below), when it prints the `audit` line, if that gate is selected, and the result line alone. CI runs the same command, without `--reuse`. The `journeys` gate is not one of them: it runs only alone, with `bin/check --journeys` (see [Journeys](journeys.md)).

Each selected gate runs in a child process of its own (`GateChildren`, started through `ProcessRunner::startToItsEndWithToolsFrom()` and polled through `ProcessRunner::endOf()`, stopped after 3600 seconds, keeping what it printed before, also when a signal kills it; it needs the `posix` extension, else it fails with `cannot run ...: the PHP posix extension is missing`). The child runs in a session of its own (`setsid`, never a PID or user namespace, so the gate's tools see the real user and processes), and its whole process group is killed with signal 9 when it ends. When the child runs past its deadline (the runner's own clock, not Symfony's `Process` timeout, which would send TERM and KILL at once), and when `bin/check` gets SIGHUP, SIGINT or SIGTERM (`StopSignalForwarding`), the group first gets SIGTERM, then SIGKILL as soon as it is gone or after 2 seconds (`ProcessGroup::STOP_GRACE_SECONDS`); a signal then ends `bin/check` with that same signal. A contained run the child starts through `ProcessRunner::runWithin()` lives in a session of its own, which a signal to the child's group does not reach, so `runWithin()` forwards the same three signals too: the child kills its contained run's group with signal 9 and then dies of the signal, which is why the parent asks before it kills. A child that dies of signal 9 (the OOM killer, an outside `kill -9`, or the parent's SIGKILL after the 2-second grace) runs no handler, so a contained run it started through `runWithin()` may keep running. The child is `php config/gates/run-gate.php <gate> <the arguments of bin/check>`, which runs in `bin/check`'s working directory; its launcher (`setsid`, then `sh`) starts in the workspace root (`--root`, else the repository) and changes to that directory just before it runs the child, so a relative or empty `PATH` entry finds `setsid` and `sh` where the preflight looked for them (`ProcessRunner::startToItsEndWithToolsFrom()`, which otherwise starts the child as `runToItsEnd()` does; `ProcessRunner::endOf()` then checks a `RunningChild` without waiting and stops it at its deadline). The child calls `CheckCommand::runGate()`, finds the gate in the selection those arguments make (a gate they leave out is an unknown gate, exit code 2), runs that one gate and prints its result line, exiting with 0 when it passes and 1 when it fails. The child entry sends PHP's warnings and notices to stderr (`display_errors=stderr`), so a PHP without its own `php.ini`, whose CLI prints them on stdout, cannot spoil the result line; the parent writes each child's stderr to its own stderr as the child finishes. The children run at the same time, at most N at once (`GateSlots`): N is the number of processors `bin/check` may use (`Processors`: the affinity list, capped by the cgroup v2 CPU quota `cpu.max` of its own cgroup, the same count the `tests` gate starts from), capped by the lowest cgroup v2 memory limit of its own cgroup, every parent cgroup and the root of its cgroup namespace (`memory.max` and `memory.high`, read through `OwnCgroup::fileAndAncestors()`, which walks from the own path in `/proc/self/cgroup` up to and including `/`, so a process at the root of a private cgroup namespace, `0::/`, reads its container's own limits there, and `cpu.max` too): that limit holds one 2 GiB share per test worker first, then one per gate, so the cap is the shares minus the test workers plus one (2 GiB is PHPStan's `--memory-limit`, `StaticAnalysisGate::MEMORY_LIMIT_GIB`, the most any gate asks for; `max` or an unreadable file sets no cap; at least 1), or the number `INTAKT_GATE_SLOTS` names (1 to 999; any other value stops `bin/check` with `{"error":"INTAKT_GATE_SLOTS names no number of gates to run at once from 1 to 999"}` and exit code 2 before any gate starts). The gates that run the change's code (`tests`, `container`, `journeys` and `phpstan`, which boots the change's kernel to dump the test container, each implementing `RunsTheChangesCode`) start only once every static gate (all the others) has ended, because a test of the change, running on the same writable checkout as the same user, could otherwise alter the tools or inputs of a static gate while that gate judges the head (`GateSlots::launchOrder()` puts the static gates first, `GateChildren` holds back a gate that runs the change's code while a static gate waits or runs). The static gates start in the gate order of the table below as slots free up; then the `tests` gate starts first of the others, so it never waits for a slot, and the rest follow in gate order. The `tests` gate takes as many slots as it runs test workers (the parent sizes them as the gate does, with `TestWorkerCount`; a refused `INTAKT_TEST_WORKERS` counts as one), but at most N - 1, so one other gate still runs beside it; every other gate takes one slot. Only when the `tests` gate is among the selected gates and N is above 1 does the parent ask the other children that run the change's code, the only ones that run beside it, to lower their priority (`LowPriority::environmentFor()` sets `INTAKT_GATE_LOW_PRIORITY` to `1` for each of them and removes the variable for every other child, so no child keeps an ask it inherited); a static gate, and a child started any other way (without the `tests` gate, with N = 1, or by a nested `bin/check` such as the gate tests start), keeps its priority. An asked child lowers its own priority to niceness 19 before it runs its gate (`LowPriority`: `proc_nice()`, and its session's `/proc/self/autogroup` where that file is writable, because where the kernel shares the processors between sessions a process's own niceness counts only inside its session), so the gates beside the `tests` gate, and the tools they start, get only the processor time its workers leave idle. With N = 1 the children run one after another, the static gates first. When `bin/check` gets SIGHUP, SIGINT or SIGTERM, every running child's group gets SIGTERM before the grace of any of them starts. Once all of them have finished, the parent prints their result lines in that order, then the result line. A child's line counts only when its output is exactly one line followed by one newline, with no other byte before or after, that line is byte for byte what `json_encode()` with the flags of `GateResult::toJson()` (`GateResult::JSON_FLAGS`) writes for the object it decodes to (so a repeated key, a `findings` object, an escaped slash or a stray NUL byte or space fails), it is a JSON object of that gate with no fields beyond `gate`, `ok`, `findings`, `omitted`, `note` and `slowest`, `ok` agrees with its findings and omitted count, and the exit code agrees with `ok` (`GateReport`); a child that crashes, times out or prints anything else fails its gate with the finding `gate process ended with exit code <n> and no valid result line: <its output, then its error output>`, of which only the end is kept, after `...`, when it does not fit the finding's 300 characters (`GateResult::MAXIMUM_FINDING_LENGTH`), so a timeout or signal stays named. Before the children start, the parent (`CheckCommand`, through `GateChildren::scratchOutsideTheTree()`, which it then hands to `GateChildren::reportsOf()`) creates one scratch folder with mode `0700` under the system temp directory (`ScratchDirectory`, named `intakt-gate-results-<16 hex digits>`; `ScratchDirectory::create()` silences `mkdir()`, so a missing or read-only temp directory gives no folder and no PHP warning on stdout, also under `display_errors=1`) and hands each child the file `<gate>.json` in it through `INTAKT_GATE_FULL_RESULT` (`GateChildren::FULL_RESULT_VARIABLE`); when the folder cannot be created, or would lie inside the checked tree (a temp directory under `--root`, where the next gate would scan the earlier gates' files), no child gets the variable (it is unset in each child's environment, even when `bin/check` itself was started with it) and the folder is removed again. The child takes the variable out of its own environment (`putenv()`) and out of `$_ENV` and `$_SERVER` before its gate runs (Symfony Process passes those arrays on too, for example under `variables_order=EGPCS`), so nothing the gate starts inherits it, and after it prints its line it creates that file (it never writes over or through anything already in its place, a link included) and writes its whole result into it (`GateResult::toFullJson()`: the keys of the line, but every finding, neither cut nor folded, and `omitted` 0); a child started without the variable writes nothing. Each finding, in the line and in the whole result, first goes through `GateResult::scrubbed()`, which replaces a broken UTF-8 byte (`mb_scrub()`, so mbstring's substitute character; without mbstring, U+FFFD) before the line folds its whitespace, so the line and the whole result start from the same text. Once the children have ended, the parent reads each file and keeps it on the gate's `GateReport` (`kept`) only when the gate's line came from the child itself (`GateLine::Printed`; a crash, a timeout, a missing or invalid line or a wrong exit code gets the line `GateReport::fromChild()` builds (`GateLine::Built`), which names why the child stopped, and never a kept result, even one the child saved before it crashed) and the file is JSON of that gate whose `ok` is the line's verdict, whose `omitted` is 0 and whose findings are a list of strings (a `{"0": ...}` object decodes as one) that, cut as the line cuts them (`GateResult::toJson()`), give the line's own `findings` and `omitted`; anything else (no file, another gate, another or no `ok`, an `omitted` other than 0, findings under other keys, other findings) leaves the gate with its line alone. Then it removes the folder, also when starting a child or the collection throws, and when `bin/check` gets SIGHUP, SIGINT or SIGTERM, once the children are stopped (`ScratchDirectory::discard()`, which catches Symfony's `IOException`: a folder with an entry that cannot be removed stays in the system temp directory, and the run keeps its gate lines, verdict, report and exit code). `GateReport::lineIsCut()` tells whether the line lost something: an omitted count above 0, or a finding that `GateResult::isCut()` counts as cut, one whose display width (`mb_strwidth()`, the measure `mb_strimwidth()` cuts by, both told UTF-8 whatever mbstring's internal encoding is; the character count without mbstring) is at least 297 columns (`MAXIMUM_FINDING_LENGTH - 3`), so an uncut finding that long counts as cut too; whitespace the line folds to single spaces is no cut. Collecting the whole results changes no line. After it has printed the gate lines and taken the verdict and the `failed` list from them (`CheckCommand::reportOn()`), the parent writes the full report (`FullReport`): one JSON document `{"whole":<bool>,"gates":[...]}` holding, in gate order, each gate's kept whole result, or its line when nothing was kept, copied byte for byte rather than decoded and encoded again (so an empty object, numbered keys, a NUL-prefixed key and a number too large for a float keep their shape; `FullReport::ascii()` checks it with `json_validate()`, and a gate whose JSON fails that check would leave the run with no report), and `whole` true only when no gate listed with its line has a cut line (`GateReport::lineIsCut()`). It goes to `var/check/report-<16 hex digits>.json` in the checked tree (`--root`, else the repository; `FullReport::FOLDER`, created when missing with the mode the umask gives; a check that loses the race to create it to another check in the same tree still writes into it), under a fresh random name opened exclusively (`fopen()` mode `x`), so it never writes over an earlier report; a `var/` or `var/check` that is a link is refused (`is_link()` before and after `mkdir()`), and so is a folder whose `realpath()` is not inside the checked tree's. The file keeps the mode the umask gives. Only after a whole write does `FullReport::pruneOlderReportsIn()` keep the 20 newest generated reports: it lists the literal folder with `scandir()` (never a `glob()` pattern, which would read a tree named like `tree[a]` as a pattern), keeps only names that are exactly `report-` plus 16 lowercase hex digits and `.json` (`FullReport::GENERATED`, ended by `\z`, so a name with a trailing newline does not match), skips the file just written, links and anything that is not a plain file, sorts the rest by `filemtime()` newest first and removes all past the 19 newest with warnings suppressed. So a hand-made `report-manual.json` is never removed, and this run's report stays even when 19 others are dated in the future. Two checks of the same tree at once may prune each other's report; nothing locks against that. Each character past ASCII is replaced by the `\u` escape `json_encode()` writes for it by default (a surrogate pair past U+FFFF), so the report is ASCII only: Intakt's own `.gitignore` leaves out `var/`, and the ASCII-only report keeps a tree whose gates do scan `var/` passing (no long dash or broken byte in it). The result line then gets a `report` key naming the file relative to the checked tree; when no report can be written, the result line has no `report` key: when there is no scratch folder (none could be created, or it would lie inside the checked tree, so no gate could keep its whole result and `CheckCommand` writes no report at all), when the folder is refused or cannot be created, when the file cannot be opened, and when the write fails or stops short (`FullReport::writtenAs()`: `fwrite()` wrote fewer bytes than the report holds or `fclose()` failed; the partly written file is removed, and the silenced calls print no PHP notice between the gate lines and the result line). The report never changes the verdict, the `failed` list or the exit code, which are taken before it is written. The scrub before the fold and the cut in UTF-8 can change the text a child prints for a broken byte, but never its verdict: the verdict, the `failed` list and the exit code come from the lines alone. Missing tools are checked in the parent before any child starts (exit code 2), and so are the `pcntl` and `posix` extensions (`RequiredTools::missingToRunEachInItsOwnProcess()`): a child in a session of its own gets no Ctrl-C from the terminal, so without them an interrupted `bin/check` would leave it running. ### Reusing a passed result

A passed result is reused for an identical tree (`PassedTree`, `TreeFingerprint`), but only when the run asks for it with `--reuse` (`Options::$reuse`, refused beside `--journeys`). The record is a file the checked code and the caller can write as well, so it proves nothing about who ran the gates: a run without `--reuse`, as in CI and every gating step, never reads it and runs every selected gate as before.

#### The fingerprint

After the options, the slots and the missing tools are checked, and before any child starts, `CheckCommand` takes the fingerprint of the run, on every run: a SHA-256 over length-prefixed parts, so no value can pass for the boundary between two parts. The parts are the `HEAD` commit, the base tip and the merge base the run's `Workspace` finds (`Workspace::baseTip()`, `Workspace::mergeBase()`), and the content of the repository's shallow file (found with `git rev-parse --git-path shallow`; its absence is a value of its own, and an unreadable one gives no fingerprint), because the commit subjects and the history secrets judge commits, not the tree, and deepening a shallow checkout shows them commits they did not see; the staged index as `git ls-files --stage -z` lists it (mode, object id and path of each entry), because the fast run takes its files from the index too; every file and folder under the checked folder, ignored or not (`vendor/`, `.env.*.local` and `phpunit.xml` count), found by a PHP directory walk (`TreeWalk`), each with its path, its `lstat()` mode, size, modification and change times and inode, and for a file the SHA-256 of its bytes; a link counts with its target text and with what is behind it (the file, or the whole folder walked the same way, since the gates open paths through a link such as a `vendor/` that points at a shared install), and a link that leads back into a folder the walk is already inside of gives no fingerprint; and, when the home of `bin/check` is another folder, the same for its `bin/check`, `config/gates/`, `composer.lock` and `vendor/`; the options (mode, `--only`, `--skip`, `--base`, `--test-merge`, not `--reuse`, so a pass of a run that did not ask serves one that does); the running PHP (`PHP_VERSION`, the loaded extensions, `ini_get_all()`); and the whole environment except `_`, `OLDPWD` and `SHLVL`, which a new shell sets anew.

#### What the walk leaves out

The walk leaves out `.git` (the commits and the index are parts of their own) and what the check itself writes while its gates run (`TreeFingerprint::WRITTEN_BY_THE_CHECK`: `var/` with the report and the record, `.phpunit.cache/`, and the `config/reference.php` and `config/schema.json` a debug kernel writes), but a path under those names is left out only while the gates' own file listing does not name it: `TreeFingerprint` asks `Scope::repositoryFiles()`, the call the gates take their files from (the index plus the untracked files the committed `.gitignore` leaves in), and every path it lists there (a tracked `var/tracked.md` or `config/reference.php`, an untracked file under a `var/` that is not ignored) counts like any other file, together with the folders above it up to the checked folder (`TreeWalk::folderAlone()`: their `lstat()` data, without what they hold, and for a folder that is a link also the `lstat()` data of every folder and link inside the checked folder that its route passes, followed one name at a time rather than through `realpath()`, so a link part way along the route counts too, then of the folder it leads to and of that folder's ancestors inside the checked folder; a route that leads nowhere or passes more than 40 links gives no fingerprint; a listed path that is itself a link to a file or a folder counts the folders and links on its route and the ancestors of where it leads the same way, through `TreeWalk::foldersOnTheRoute()`), so moving such a folder, or a link on its route, away and back while the gates ran records nothing. A tree that does not ignore `var/check` therefore has the report and the record among its gate inputs and keeps no record: the report changes the second fingerprint, and `recordPass()` takes the fingerprint once more after writing the record and removes the record when it no longer matches.

#### Files read, choices and failures

Apart from that listing the walk reads files itself, so git's ignore rules (`.gitignore`, `.git/info/exclude`, the global excludes) hide nothing from it, and nothing is written to the index or the object store. The issue asked for the tree hash, the lock file and the gate configuration; the commits, the ignored files, the PHP and the environment are this change's choice, so that a reused result stands only for inputs that would give the same verdict. A tree without `.git`, a failed git call, an unreadable file or folder or a refused `info/attributes` gives no fingerprint, and the gates run.

#### Reusing and recording a pass

When the run asked for `--reuse` and `var/check/passed.json` (`PassedTree::RECORD`, refused when it, `var/` or `var/check` is a link, and read only up to one byte past the expected length, so a record of any size costs no memory) holds exactly `{"fingerprint":"<that fingerprint>"}` and a newline, `bin/check` starts no gate but the `audit` one when it is selected (`ComposerAuditGate`, since a new advisory can hit an unchanged lock file), prints its line, writes a report of it and ends with the result line plus `"reused":"var/check/passed.json"`; without `audit` it prints only `{"result":"pass","failed":[],"reused":"var/check/passed.json"}`, exit code 0. Otherwise the gates run as before, and only when every gate passed and the full report was written does `PassedTree::recordPass()` take the fingerprint again and, when it is unchanged and no file or folder in it changed (its change time) in or after the second the run started (`PassedTree::before()` reads the start through Symfony's `ClockInterface`), and `var/check` is a folder inside the checked tree that no link leads to, write the record to a temporary name created exclusively and `rename()` it over `passed.json`, so only the latest pass is kept and no half-written record is ever read. A file edited and changed back while the gates ran keeps a newer change time, so it records nothing, and the start-second rule covers two such changes inside the very second the first fingerprint was taken, which the times cannot tell apart, the same way git treats a racily clean index entry. Because a folder counts with its own times and inode, a file that came and went and a folder moved away and back while the gates ran record nothing either. A gate that rewrites a file the walk covers, or adds or removes one in a folder it covers, therefore leaves nothing to reuse: the run that first creates `var/`, `.phpunit.cache/` or `config/reference.php` changes the folder they are in and records nothing, and so does a run that first creates `var/check` (or another folder) in a folder counted above a listed path, such as the `var/` of a tracked `var/tracked.md`; the next run of the unchanged tree does. A run that reused a pass records nothing. `hasPassed()` takes the fingerprint once more after it found a matching record and reuses the pass only while that fingerprint is unchanged, so a file edited between the first fingerprint and the lookup runs the gates. A gate child (`CheckCommand::runGate()`) never reads or writes the record.

## The test time budget (planned)

Planned, not built (#1297): the Test engineer ([design](../design/05-architecture/07-reviews.md#the-test-engineer-planned)), an opt-in role, will hold a time budget for the `tests` gate and for each test file. The gate's budget is measured by its elapsed time in CI, which `bin/check` does not report yet; a file's budget by its time in `tests/durations.json`, which holds every test file. The `slowest` list on the gate's line is not the measure: it names only the ten slowest files, and each time there is the sum of the file's tests over all passes, not the wall time it adds to the gate. A budget overrun is one kind of finding; the role's scheduled audit also files a task for each redundant or low-value test, misplaced test, flaky test and slow CI workflow it finds, and never edits a test itself. A task that removes or merges a test names the test that still proves each removed case, the coverage of `src/` must not drop, and a time claim is measured in CI before and after. The role never changes a gate's strictness, the checks or the approval rules, and a change to a CI workflow stays a protected change.
