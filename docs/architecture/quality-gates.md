## Quality gates

`bin/check` runs every gate below and prints one JSON line per gate, then a result line. CI runs the same command. The `journeys` gate is not one of them: it runs only alone, with `bin/check --journeys` (see [Journeys](journeys.md)).

Each selected gate runs in a child process of its own (`GateChildren`, started through `ProcessRunner::startToItsEndWithToolsFrom()` and polled through `ProcessRunner::endOf()`, stopped after 3600 seconds, keeping what it printed before, also when a signal kills it; it needs the `posix` extension, else it fails with `cannot run ...: the PHP posix extension is missing`). The child runs in a session of its own (`setsid`, never a PID or user namespace, so the gate's tools see the real user and processes), and its whole process group is killed with signal 9 when it ends. When the child runs past its deadline (the runner's own clock, not Symfony's `Process` timeout, which would send TERM and KILL at once), and when `bin/check` gets SIGHUP, SIGINT or SIGTERM (`StopSignalForwarding`), the group first gets SIGTERM, then SIGKILL as soon as it is gone or after 2 seconds (`ProcessGroup::STOP_GRACE_SECONDS`); a signal then ends `bin/check` with that same signal. A contained run the child starts through `ProcessRunner::runWithin()` lives in a session of its own, which a signal to the child's group does not reach, so `runWithin()` forwards the same three signals too: the child kills its contained run's group with signal 9 and then dies of the signal, which is why the parent asks before it kills. A child that dies of signal 9 (the OOM killer, an outside `kill -9`, or the parent's SIGKILL after the 2-second grace) runs no handler, so a contained run it started through `runWithin()` may keep running. The child is `php config/gates/run-gate.php <gate> <the arguments of bin/check>`, which runs in `bin/check`'s working directory; its launcher (`setsid`, then `sh`) starts in the workspace root (`--root`, else the repository) and changes to that directory just before it runs the child, so a relative or empty `PATH` entry finds `setsid` and `sh` where the preflight looked for them (`ProcessRunner::startToItsEndWithToolsFrom()`, which otherwise starts the child as `runToItsEnd()` does; `ProcessRunner::endOf()` then checks a `RunningChild` without waiting and stops it at its deadline). The child calls `CheckCommand::runGate()`, finds the gate in the selection those arguments make (a gate they leave out is an unknown gate, exit code 2), runs that one gate and prints its result line, exiting with 0 when it passes and 1 when it fails. The child entry sends PHP's warnings and notices to stderr (`display_errors=stderr`), so a PHP without its own `php.ini`, whose CLI prints them on stdout, cannot spoil the result line; the parent writes each child's stderr to its own stderr as the child finishes. The children run at the same time, at most N at once (`GateSlots`): N is the number of processors `bin/check` may use (`Processors`: the affinity list, capped by the cgroup v2 CPU quota `cpu.max` of its own cgroup, the same count the `tests` gate starts from), capped by the lowest cgroup v2 memory limit of its own cgroup, every parent cgroup and the root of its cgroup namespace (`memory.max` and `memory.high`, read through `OwnCgroup::fileAndAncestors()`, which walks from the own path in `/proc/self/cgroup` up to and including `/`, so a process at the root of a private cgroup namespace, `0::/`, reads its container's own limits there, and `cpu.max` too): that limit holds one 2 GiB share per test worker first, then one per gate, so the cap is the shares minus the test workers plus one (2 GiB is PHPStan's `--memory-limit`, `StaticAnalysisGate::MEMORY_LIMIT_GIB`, the most any gate asks for; `max` or an unreadable file sets no cap; at least 1), or the number `INTAKT_GATE_SLOTS` names (1 to 999; any other value stops `bin/check` with `{"error":"INTAKT_GATE_SLOTS names no number of gates to run at once from 1 to 999"}` and exit code 2 before any gate starts). The gates that run the change's code (`tests`, `container`, `journeys` and `phpstan`, which boots the change's kernel to dump the test container, each implementing `RunsTheChangesCode`) start only once every static gate (all the others) has ended, because a test of the change, running on the same writable checkout as the same user, could otherwise alter the tools or inputs of a static gate while that gate judges the head (`GateSlots::launchOrder()` puts the static gates first, `GateChildren` holds back a gate that runs the change's code while a static gate waits or runs). The static gates start in the gate order of the table below as slots free up; then the `tests` gate starts first of the others, so it never waits for a slot, and the rest follow in gate order. The `tests` gate takes as many slots as it runs test workers (the parent sizes them as the gate does, with `TestWorkerCount`; a refused `INTAKT_TEST_WORKERS` counts as one), but at most N - 1, so one other gate still runs beside it; every other gate takes one slot. Only when the `tests` gate is among the selected gates and N is above 1 does the parent ask the other children that run the change's code, the only ones that run beside it, to lower their priority (`LowPriority::environmentFor()` sets `INTAKT_GATE_LOW_PRIORITY` to `1` for each of them and removes the variable for every other child, so no child keeps an ask it inherited); a static gate, and a child started any other way (without the `tests` gate, with N = 1, or by a nested `bin/check` such as the gate tests start), keeps its priority. An asked child lowers its own priority to niceness 19 before it runs its gate (`LowPriority`: `proc_nice()`, and its session's `/proc/self/autogroup` where that file is writable, because where the kernel shares the processors between sessions a process's own niceness counts only inside its session), so the gates beside the `tests` gate, and the tools they start, get only the processor time its workers leave idle. With N = 1 the children run one after another, the static gates first. When `bin/check` gets SIGHUP, SIGINT or SIGTERM, every running child's group gets SIGTERM before the grace of any of them starts. Once all of them have finished, the parent prints their result lines in that order, then the result line. A child's line counts only when its output is exactly one line followed by one newline, with no other byte before or after, that line is byte for byte what `json_encode()` with the flags of `GateResult::toJson()` (`GateResult::JSON_FLAGS`) writes for the object it decodes to (so a repeated key, a `findings` object, an escaped slash or a stray NUL byte or space fails), it is a JSON object of that gate with no fields beyond `gate`, `ok`, `findings`, `omitted`, `note` and `slowest`, `ok` agrees with its findings and omitted count, and the exit code agrees with `ok` (`GateReport`); a child that crashes, times out or prints anything else fails its gate with the finding `gate process ended with exit code <n> and no valid result line: <its output, then its error output>`, of which only the end is kept, after `...`, when it does not fit the finding's 300 characters (`GateResult::MAXIMUM_FINDING_LENGTH`), so a timeout or signal stays named. Missing tools are checked in the parent before any child starts (exit code 2), and so are the `pcntl` and `posix` extensions (`RequiredTools::missingToRunEachInItsOwnProcess()`): a child in a session of its own gets no Ctrl-C from the terminal, so without them an interrupted `bin/check` would leave it running.
