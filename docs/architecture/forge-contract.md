## Forge contract and the local git forge

### In short

The forge is where changes live. The Forge contract gives the rest of Intakt typed reads of a change: its commits, its diff, a file as it is at the head, and whether and how the head moved. Writes (review comments and the verdict status on a head) sit in a separate contract, so a read-only forge implements none of them. The local git forge, where a local branch against the base branch is the pull request, and the GitHub forge both implement the reads. The page also covers the forge budget, author trust, the open pull request and issue listings, and the verdict identity.

Worth knowing:

- The local git forge runs git with an argument list, no shell, hardened settings and a 60-second timeout.
- Failures are typed: `ChangeNotFound`, `FileNotFoundAtHead` and `ForgeReadFailed`.
- A changed task, check command or panel policy makes a recorded verdict stale.
- `intakt:change:summarize` prints a summary of a local branch's change.

The rest of this page is the detailed reference.

`Plugin/Forge/Contract` holds what reading a change needs, as typed objects only:

- `Forge::change(ChangeId)` returns a `Change`: the id, the `commits` (`CommitRange`: `base` and `head` as `CommitId`, full hashes) and the `diff` (`Diff`: the unified `patch` text and the `files`, a `ChangedFiles` collection of `ChangedFile`: path and `FileStatus` added, modified or deleted; a rename shows as a delete and an add).
- `Forge::hasHeadMoved(Change)` is true when the change's branch now points at another commit than the `Change` was read at (`#[NoDiscard]`).
- `Forge::headMoveSince(CommitId $earlier, Change)` returns a `HeadMove`: how the change's head moved since the earlier head (`HeadMoveKind`: `unmoved`, `clean-merge-of-base`, `commits` or `rewritten`) and the `paths` that differ between the two heads (a `Git\Contract\Paths`, empty for `unmoved` and `rewritten`).
- `Forge::fileAtHead(Change, path)` returns a `FileContent` as it is at the `Change`'s head hash, not at the branch tip, so a branch that moved on does not change what is read; both forges build it with `FileContent::ofBytes()`, which names a binary file (a NUL byte anywhere, `BinaryFiles::isBinary()`) by its size with the text `FileContent::binaryText()` writes (step 2 below, and [GitHub App identity](github-app-identity.md)).
- Failures are typed: `ChangeNotFound`, `FileNotFoundAtHead` and `ForgeReadFailed` (git could not run, timed out, failed or printed something unexpected).

`Plugin/LocalGitForge` implements it for a local repository (`LocalRepository`: path and base branch). A local branch (`refs/heads/<id>`, never a tag) against the base branch is the pull request. Every call is a `GitCall` (a `GitCommand`, the absolute directory and a `GitEnvironment`) built by `Core/Git/Contract/HardenedGit` and runs through the Process component with that command's argument list (no shell) in the repository, with a 60-second timeout; the hardened call (no replace objects or grafts, no lazy fetch or transport, an absolute pinned work tree, literal pathspecs, no repository hooks, fsmonitor, attributes, filters, textconv, external diff, signature checks or output encodings, no inherited `GIT_*` variables, no system or user config) is described in [Requirements](requirements.md#the-hardened-git-call). A Process failure (a missing directory, a timeout) becomes a `ForgeReadFailed`, and so does a NUL byte in a path or change id, which is refused before git starts, and a repository whose `.git/info/attributes` exists, which the hardened call refuses (`RepositoryAttributesRefused`).

1. The head is the branch's commit (`git check-ref-format` on `refs/heads/<id>`, then `git show-ref`; an invalid branch name or a missing branch is `ChangeNotFound`, any other git failure `ForgeReadFailed`); the base is the merge base of the base branch and the head, so what the base branch gained after the branch was cut is not in the diff.
2. The diff is `git diff` between those two hashes, without colors, renames, external diff drivers or text conversion, with every file shown as text (`--text`, so neither an attribute nor git's binary detection replaces a change by `Binary files differ`), with `--full-index` and `-c core.quotePath=true` (a name that is not ASCII is written in escapes), and with `--ignore-submodules=none`, so a changed submodule commit shows even when the repository sets `diff.ignoreSubmodules`. `BinaryFiles` (in `Plugin/Forge/Contract`, so the GitHub forge's held change uses it too, see [Workflow risk scan](workflow-risk-scan.md#holding-the-push)) then reads both blobs of each file's `index` line (`git cat-file blob`; a submodule's commits are not read) and decides what is binary from all their bytes, not only the lines shown: a file with a NUL byte anywhere in either blob keeps its header up to the `index` line, and its lines are replaced by `Binary file, not shown: <size> at the base, <size> at the head`, each size `<n> bytes` (the blob's length; `1 byte` for a blob of one byte) or `absent` (an all-zero id). A mode-only change (such as `chmod +x` on a committed PNG) keeps its `old mode` and `new mode` lines and gets no binary label, because git shows no `index` line and no content for it. Every other file keeps all its lines, so a stray byte cannot hide code; in a file whose part of the diff is not valid UTF-8, each byte that starts no UTF-8 character becomes the replacement character U+FFFD followed by the byte in hex in braces (for example `�{E9}`), and a replacement character of that part itself becomes `�{EFBFBD}`, so an escape always stands for one set of bytes. So the diff is valid UTF-8 and a binary file's bytes never reach a prompt or a stored conversation; a binary file adds no lines to `addedLines()` or `removedLines()`. A file that shows no `index` line but holds a NUL byte or bytes that are not UTF-8 is a `ForgeReadFailed`. `BinaryFiles::named()` does all of this; `withImagesNamed()` names only a binary file that is a plain image (every mode `100644`, a `.png`, `.jpg`, `.jpeg` or `.gif` name, quoted by git or not, and every blob starting with that type's signature) and leaves every other file as git printed it, unescaped and unchecked, for a reader that refuses what is not UTF-8 or holds a NUL byte itself (the GitHub forge's push request, where any other binary file could be a script the owner would approve unseen). `fileAt` and `fileAtHead` apply the same rule to the one blob they read: a file with a NUL byte anywhere comes back as `FileContent::binary()`, whose `binaryBytes` is the blob's length and whose `content` is `Binary file, not shown: <n> bytes` (`1 byte` for a blob of one byte), never its bytes; every other file's `content` is its bytes as committed and `binaryBytes` is `null`. `InstanceBoot` refuses a binary harness as `crashed` (see [Boot step](boot-step.md)). The changed files come from `git diff --name-status -z` with the same options and hashes; `NameStatusParser` turns that output into `ChangedFiles` with the pipe operator (split on NUL, pair status with path, map to objects). An unknown status or a status without a path is a `ForgeReadFailed`. Because `-z` gives each path's raw bytes, `LocalGitForge` then refuses a change (and a head move) that adds, changes or deletes a path that is not valid UTF-8 with `ForgeReadFailed`, whose message names the path escaped as a text file's lines are in the patch (`BinaryFiles::escaped()`: `caf\xE9.txt` is named `caf�{E9}.txt`), so every path in `ChangedFiles`, and in a `HeadMove`'s `paths`, is valid UTF-8 and kept as committed. Builder's choice: refused rather than escaped, because an escaped path is itself a valid file name (`caf�{E9}.txt` can be committed beside `caf\xE9.txt`), so a listed path would name another file for `fileAtHead`.
3. A file is looked up with `git ls-tree -z <head hash> -- <path>` and read with `git cat-file blob <blob hash>`. A path that is not a file (missing, a directory or a submodule) at the head is `FileNotFoundAtHead`; a head that cannot be read is `ForgeReadFailed`.
4. A head move since an earlier head: the same hash is `unmoved`. An earlier commit that is not in the repository (`git cat-file -e <hash>^{commit}` fails) or is not an ancestor of the head (`git merge-base --is-ancestor`, exit 1) is `rewritten`; any other exit is `ForgeReadFailed`. Otherwise the head is a `clean-merge-of-base` when it is a merge commit with exactly two parents (`git rev-list --parents --max-count=1`), the first is the earlier head, the second is an ancestor of the base branch, and its tree is exactly the tree `git merge-tree --write-tree` computes for those two parents without conflicts (with `core.attributesFile` naming `src/Plugin/LocalGitForge/Infrastructure/builtin-merge.gitattributes`, whose `* merge` makes git use its own text merge, so no merge driver from the repository's config runs), so a resolved conflict or an edit hidden in the merge is not clean; anything else is `commits`. The paths come from `git diff --name-status -z` between the two heads, with the options of step 2.

`php bin/console intakt:change:summarize <branch> [--repository=.] [--base=main]` (`Plugin/LocalGitForge/UseCase/SummarizeChange`, plan task T6) builds a `LocalGitForge` from the input (`SummarizeChangeInput`, mapped with `#[MapInput]`), reads the `Change` of the branch and prints the branch and base names, the first 12 characters of the base and head hashes, the file count with the `+` and `-` lines (`Diff::addedLines()` and `Diff::removedLines()`, counted from the patch inside `@@` hunks only, so the `+++` and `---` file headers are excluded and a changed line starting with `++` or `--` is counted), and one `status path` line per changed file. Branch names and paths are escaped with `OutputFormatter::escape()` before they reach the console, so a name containing a formatter tag such as `<info>` prints literally. Before that, `Infrastructure\VisiblePath` prints every control character in a path (bytes 0x00 to 0x1F and 0x7F, and the UTF-8 encoded U+0080 to U+009F) as `\xNN` per byte and a backslash as `\\`, so a file name holding an escape sequence cannot rewrite the terminal; branch names need no such step, because git refuses control characters in ref names. The file count reads `1 file changed` for one file and `N files changed` otherwise. `ChangeNotFound`, `ForgeReadFailed`, a `--repository` that is not a directory (`RepositoryNotFound`), an empty `--base` (`LocalRepositoryIncomplete`) and an empty branch (`ChangeIdEmpty`) print the message as an error and exit with 1. The command lives in the plugin's own module because it needs the plugin's `Infrastructure`, which other modules may not use.

### Forge writes

`Plugin/Forge/Contract/ForgeWrites` holds what Intakt writes to a forge, apart from the reads, so a read-only forge implements none of it: `postReview(project, Change, ReviewComment)` and `publishVerdict(project, ChangeId, PublishedVerdict)`. A `PublishedVerdict` is the head (`CommitId`), a `HeadStatus` (`success`, `failure`, `error`, or `pending` for an approved protected head handed to Intakt that waits for the owner, see [Pull requests handed to Intakt](handed-to-intakt.md#intakts-review-counts)), a non-blank description, an optional non-blank comment (`comments()` returns `CommentBodies` holding none or that one as given, not redacted again: the Review module's `LoopReviewComment` redacts each finding line whole and alone, and a second pass over the whole text could carry a redaction with no end, such as a header named in the file and an unclosed `[` in the text, into the verdict block), the round's `ReviewToken`, which the forge posts as a marker with the comment so a retry finds it, and the owner ask's parts (`ownerAsks`, a `CommentBodies`, empty unless the head waits for the owner), each posted as a comment of its own with a marker of its own; `publishVerdict()` returns `false` when the forge writes nothing by its configuration (no GitHub App) and `true` once it wrote; a round of a reviewer-for-loop project or of a pull request handed to Intakt publishes it (see [Reviewer-for-loop mode](capability-tiers.md#reviewer-for-loop-mode), which also holds what `GitHubForge` sends). A `ReviewComment` is a non-blank body, the round's one-time `ReviewToken` (16 to 128 letters, digits, `_` or `-`, so it cannot close the marker it is posted in) and the `JobCredentials` of the jobs that wrote the body (their non-empty values, possibly none, read only by iterating it); an invalid one is an `InvalidArgumentException`. `ReviewComment::redactedBody()` delegates to `Core/Platform/Contract/Redaction`, the one redaction shared by posted text, log records (`Core/Platform/Infrastructure/RedactedJsonFormatter`, see the Logging convention) and stored text (`Core/Platform/Contract/Redactor`, the interface for text a module stores or shows, implemented by `Core/Platform/Infrastructure/HeldCredentialRedactor`, which passes `HeldCredentials::values()` read at each call, as the formatter does; so far the watcher's failure cause): it replaces every held value with `[redacted]`, and also its `trim()`med form when that form is non-empty and differs (so a value stored with a trailing newline is redacted where it is quoted without it), each form matched by one pattern that allows every character as itself (with any run of backslashes before `"`, `\` and `/`) and, only for the characters `json_encode` may escape (control characters, non-ASCII, `"`, `\`, `/`, `<`, `>`, `&`, `'`), also as a JSON short escape (`\n`, `\t`, `\r`, `\b`, `\f`) or as `\u` escapes (UTF-16 units, either case), each escape after any run of backslashes, so JSON encoding at any depth and with the `JSON_HEX_*` flags is covered while a credential of thousands of plain characters stays within PCRE's pattern size; then it redacts credential header values (plain, quoted, shell-quoted, JSON, `print_r`/`var_export` scalars and lists, Digest parameters; a quoted value may hold the other quote character; a `var_export` or short-array list ends at its matching bracket, skipping quoted strings, and the text after that bracket is kept only for a list that is the value of a quoted key (the header name directly after `"` or `'` and directly followed by the same quote after any backslashes, as in JSON `"authorization": [...]` and `var_export` `'Authorization' => [...]` or `array (`; a quoted key after an unquoted credential header name on the same line, as in `Cookie: x; 'authorization': [...]`, sits inside that header's value and does not count) and is list-shaped: its first element is quoted, keyed (`0 =>`), nested or missing, and a `,`, closing bracket or line end follows its closing bracket; any other bracket after a credential header name (an unquoted name such as `Cookie: [a]; sid=...`, `Authorization: ['Bearer x'] ...`, `-H 'Cookie: [] ...'` or `cookie=[...]`, whatever follows the bracket) is replaced with `[redacted]` up to its matching end, and the value pass then redacts it with the rest of the value, to the end of its line or quote, as it does a `[redacted]` already in the text and a value that holds a list opening later on; a `print_r` list is redacted to the end of the text, because `print_r` does not quote values and its end cannot be told apart from a value; a list without a found end is redacted to the end of the text), the userinfo of URLs (also with JSON's `\/` separator), and secret shapes. Every pass finds its parts by position in the original text (a part an earlier pass found is masked byte for byte, so positions stay), and all parts are replaced at the end (`RedactedSpans`, one integer per part, so a one-character held value matching every byte of a long text stays within memory). The header, userinfo and secret-shape passes run twice, on the original text and with the held values masked (their line breaks kept): a held value that is also a header name, a URL scheme or `Bearer`, or that ends right before one, still lets its header, userinfo or token be found. Parts that overlap (a value and its trimmed form, two held values sharing characters) become one `[redacted]` carrying the replacement of the part that reaches furthest (so an unterminated quoted header value keeps its closing quote), while parts that only touch keep one each. A text that still trips the secret scan after redaction throws `ReviewTextHoldsSecret` (its message holds no part of the text) and posts nothing; a post whose round is stale throws `RoundStale` and posts nothing; a failed post, including a failed read of the head just before it and a secret scan that cannot run, is `ForgeWriteFailed`. `GitHubForge` implements it (see [GitHub App identity](github-app-identity.md)); opening the pull request of a pushed branch is a separate contract, `ChangeOpening`, described in [Branch push](branch-push.md#the-pull-request); nothing calls `postReview()` yet, because no live round posts its outcome so far. No guard decorates the forge writes: `publishVerdict()` is called only by `PublishVerdictHandler`, for a reviewer-for-loop project or a pull request handed to Intakt (see [Pull requests handed to Intakt](handed-to-intakt.md),  [Mode per project](capability-tiers.md#mode-per-project) and [Reviewer-for-loop mode](capability-tiers.md#reviewer-for-loop-mode)).

### Forge budget

`Plugin/Forge/Contract/ForgeBudgets::thisHour()` (#677, decision D4 of #668) returns one `ForgeBudget` per forge installation the install calls as: its `installation` id, the calls `used` and `remaining` this hour and `reserveInForce`, whether routine reads wait for the reserve. `used` and `remaining` are both null when no answer of this hour reported the budget (`isRead()` is false). It is built from what earlier answers reported and makes no call. `GitHubForge`'s `Infrastructure/GitHubForgeBudgets` implements it (see [GitHub App identity](github-app-identity.md)); `LocalGitForge` has no budget and does not. The dashboard shows it on `/reviews` ([Dashboard](dashboard.md)).

### Pull request author trust

`Plugin/Forge/Contract/AuthorTrust::isAuthorTrusted(ChangeId)` (issue #1974, part 1 of #1828, decision 1; `#[NoDiscard]`) answers whether the author of a change is trusted, because booting a head runs its code on the host ([Threat model](../design/05-architecture/14-threat-model.md)): an author with write access, Intakt's own identity or the maintainer's identity. A check that fails or cannot answer is `false`, never `true`, and the method throws nothing. `GitHubForge`'s `Infrastructure/GitHubAuthorTrust` implements it with the classification of the steering trust check (see [GitHub App identity](github-app-identity.md), "Pull request author trust"), and only for a head whose `head.repo.full_name` in the same pull request answer is the base repository: a head in a fork (also a deleted one, whose `head.repo` is null) is untrusted without a permission lookup, because the fork's owner can push under the author's name, and an answer without `head.repo` is invalid and counts as untrusted. `LocalGitForge` answers `true` for every branch without running git, because a local branch is the owner's own. The two implementations are separate services; the container's `AuthorTrust` is `GitHubAuthorTrust` (`config/services.yaml`), because the watcher lists pull requests through `GitHubWatchReads`, and the test environment binds it to `tests/Core/Watcher/RecordedPullRequests`. The watcher's `BootGate` asks it before it boots a head (issue #1975, see [Boot step](boot-step.md#the-gate-decision)). Tests: `tests/Plugin/GitHubForge/GitHubAuthorTrustTest.php`, `AuthorTrustOnTheContainerTest.php` and `tests/Plugin/LocalGitForge/LocalGitForgeAuthorTrustTest.php`.

`Plugin/Forge/Contract/ChangeAuthorship::isCreatedByIntakt(ChangeId)` (issue #3001) answers whether Intakt's own App created a change, from the author the forge sets; unlike `AuthorTrust`, a read that fails throws `ForgeReadFailed` (or `ForgeRateLimited`) instead of answering. `GitHubForge`'s `Infrastructure/GitHubChangeAuthorship` is its only implementation; the watcher asks it only for an open pull request whose opening records predate openings or that has no opening record at all, never for one with a recorded `change_handed_to_intakt` or `change_not_handed_to_intakt` line, and leaves a pull request whose author it cannot read for the next tick ([Pull requests handed to Intakt](handed-to-intakt.md)). Tests: `tests/Plugin/GitHubForge/GitHubChangeAuthorshipTest.php`.

### Open pull request listing

`Plugin/Forge/Contract/OpenChanges::listOpen(project, ?validator)` (plan task T38, part 1) lists the open changes of a project and returns an `OpenChangeListing`: either `unchanged` (the forge answered that the list is the one the validator came from, as GitHub does with a `304` to `If-None-Match`, which costs no rate limit) or the `changes` (`OpenChange`: `ChangeId`, head `CommitId` and `updatedAt`) with the new `validator`. A failed read is `ForgeReadFailed`; a listing the forge holds back for its rate limit is `ForgeRateLimited`. `LocalGitForge` does not implement it. `Plugin/GitHubForge/Infrastructure/GitHubWatchReads` does (plan task T18): it reads `GET /repos/{owner}/{name}/pulls?state=open&per_page=100` through `GitHubCalls::asInstallation()` with the installation token, and sends the earlier validator as `If-None-Match`; a `304` is `unchanged` and ends the read. Before the first page it asks `BudgetReserve`, which below the installation's reserve lets one listing per tick through and throws `ForgeRateLimited` for the others ([GitHub App identity](github-app-identity.md), "Reserve for essential calls"). Each pull request becomes an `OpenChange` of its `html_url` (the address `PullRequestAddress` accepts, so the forge's other reads take it), its `head.sha` and its `updated_at` in UTC. A listed pull request that cannot be built into an `OpenChange` is `ForgeReadFailed` with the cause chained, for exactly three causes: `ChangeNotFound` (an address that is not a `https://github.com` pull request: another host or scheme, credentials, a port, or another path), `ChangeIdEmpty` (a blank address) and `CommitIdMalformed` (a head that is no commit id); any other exception propagates. A full page of 100 triggers a read of the next pages (`page=2` and on, at most 10 pages, else `ForgeReadFailed`), and a listing whose first page is full returns no validator, also when the next page is empty, because the `ETag` of page one says nothing of the others (a reopened older pull request can fill page two without changing page one). Pages can shift between two reads, so a pull request that comes on two pages is listed once, at its first place (by its `ChangeId`). A refused or failed read (any status outside 2xx, a `404` too, an unreachable GitHub, an answer that is not JSON or not the expected shape, such as a listing page that is a JSON object instead of a list, `{}` included) is `ForgeReadFailed`, with `ForgeCredentialsRefused` as the cause for a `401`; the client's own exception is not chained, because its trace holds the bearer token. The GitHub repository of a project is the `github` key (`owner/name`, optional, validated by `WatchConfiguration`) of its `watch` section (which also takes the optional `eligibility_label`, `intakt` when left out, validated by `WatchConfiguration` and read by `CompleteListing` of the work source, see [Work intake](work-intake.md)), read by `WatchedRepositories` from the parameter `intakt.watcher.projects`; a project without one is `ForgeReadFailed`. Tests: `GitHubWatchReadsTest` (recorded answers in `tests/Plugin/GitHubForge/Fixtures/`); the tests of the watcher use `RecordedForge` (`tests/Core/Watcher/UseCase/FindChangedPullRequests/`), which answers like GitHub's conditional listing.

### Open issue listing

`Plugin/GitHubForge/Contract/IssueReads::listOpen(project, ?validator)` (plan task T47 of #329, via #1600, part 1) lists the open issues and pull requests of a project in one call and returns an `IssueListing`: `unchanged` (a `304` to the validator; a `304` to a listing without one fails with `ForgeReadFailed`) or the `ListedIssue`s (number, title, body, labels as `IssueLabels`, author, `updatedAt`, milestone due date, whether it is a pull request). `Infrastructure\GitHubIssueReads` reads every page in that call, 100 issues each, and checks the `Link` header only for whether it names a next page, then asks for the next page number itself: only a page that names none ends the listing. It reads `rel` as an RFC 8288 link parameter: optional whitespace around `=`, a quoted or unquoted value, a quoted value unescaped (a quoted-pair such as `\x` stands for its character, RFC 9110) and split on whitespace into relation types compared case-insensitively as whole tokens (only the first `rel` of a link counts), so `rel = "next"` and `rel="prev next"` name a next page and `rel="next-page"`, or `rel=next` inside another parameter's quoted value, does not. A `Link` header that is not a list of `<...>` links with such parameters fails with `GitHub answered a Link header this forge cannot read.`, because reading it as naming no next page would end the listing early. That includes a list with an empty element (`, ,`), which RFC 9110 list syntax allows: a known limit that fails closed.

An `anchor` parameter (in any letter case) sets the context of a link's relations, which can be another resource (RFC 8288 section 3.2) or the requested page itself, so a link with `next` among its relations and an `anchor` fails the listing with the same message unless the anchor is provably the page just requested: the empty reference `""`, or a relative reference without scheme, host or fragment without control characters or spaces, whose path is absent or the requested path and whose query, split on `&` into raw pairs and sorted, equals the request's (so `"?page=1&state=open&per_page=100"` matches, and `"?state=closed&state=open&per_page=100&page=1"` does not). An absolute anchor fails even when it names this very page. GitHub sends no anchors, so failing stays visible and never ends a listing early or follows another resource's next page. A link without `next` is read whatever its anchor's value, while an `anchor` without a value is an unreadable Link on any link.

Only a `200` (or a `304` to a validator) is read: any other status, also another 2xx such as `206 Partial Content`, fails with `GitHub answered <status> to a read.`. A listing that comes back short fails with `ForgeReadFailed` (or `ForgeRateLimited`) and returns nothing: a page that failed, was rate-limited, is not a list, is empty or short while a next link is still named, or the tenth page still naming a next one. After the last page of a listing of several pages, every page before it is asked for again with its own `ETag` as `If-None-Match`, and anything but a `304` fails the listing: a rate-limited confirmation raises `ForgeRateLimited`, a refused one or another status fails with `ForgeReadFailed` (`GitHub answered <status> to a read.`), and a `200` fails with `ForgeReadFailed` (`GitHub did not confirm that page <n> of the open issues stayed the same while the later pages were read.`): an issue that closes or opens on a page already read moves the later pages by one, so an issue at a page boundary would be read twice or never. Because those `304`s come one at a time, an issue that opens ahead of a page boundary for one page's read and is gone again for every confirmation would pass them; it lists the next page's first issue a second time, so a listing that holds an issue number twice fails first with `GitHub listed issue #<n> on two pages, so the open issues moved while they were read.` (the opposite, a gap, needs an issue that a page listed to close and reopen, which changes its `updated_at` and so that page's `ETag`). An `ETag` that is not an RFC 9110 entity tag (`"..."` or `W/"..."`, for example `*`, which would match any page as `If-None-Match`) fails the listing with `GitHub answered a validator that is not an entity tag.`, also on a single page. Any edit to an issue on an earlier page (a comment, a label) while the later pages are read also gives that page a new `ETag`, so on a busy repository such a listing fails and the next tick lists again. Because a `304` compares representations and `updated_at` counts whole seconds, an issue closed and reopened within the second its page was served would leave that page looking unchanged; so every page before the last must carry a `Date` header (else `GitHub answered page <n> of open issues without a Date.`, and a `Date` that does not read strictly as an HTTP date (one that does not format back to the same text, such as second 99 or a weekday that does not match its day) gives `GitHub answered a Date this forge cannot read.`), and an issue on it updated 5 seconds or less before that `Date` (the slack allows for GitHub's servers' clocks) fails the listing with `ForgeReadFailed` (`Issue #<n> on page <p> of the open issues changed in the seconds GitHub served the page, ...`). A single-page listing is not asked for again. Only a single-page listing carries the first page's validator. The listing takes its own `BudgetReserve::admitListing` slot (`issues:<project>`), apart from the watcher's.

`IssueReads::readOpen(project, number)` (#2073) reads one issue for `intakt:build:task` ([Build task](build-task.md)) and returns its `ListedIssue`, or null when there is no open issue of that number. `GitHubIssueReads` makes one request, `GET /repos/{owner}/{name}/issues/{number}`, through the same `GitHubCalls`, bearer and failure rules as the listing, and maps the answer with `IssueFields`, the same code that maps a listed issue, so labels, title and body come out the same way. The request follows no redirect (`max_redirects` 0), because GitHub answers an issue transferred to another repository with a `301` to it. It answers null for a `404` or a `301`, for a `closed` issue, for a pull request (an answer with `pull_request`) and for an answer whose `number` is not the one asked for. A `state` that is missing or neither `open` nor `closed` fails with `ForgeReadFailed` (`GitHub answered an issue whose state is neither open nor closed.`). A rate-limited read raises `ForgeRateLimited`; any other status (a `304` too) fails with `ForgeReadFailed` (`GitHub answered <status> to a read.`, with `ForgeCredentialsRefused` as the cause for a `401`), and an answer that is not a JSON object with `GitHub answered an issue that is not an object.`. It takes no `BudgetReserve` slot, because the reserve paces the routine listings of a tick and a build reads its one task once. Tests: the single-read cases of `GitHubIssueReadsTest`.

`Infrastructure\GitHubIssueHistories::of(project, number, listedAt)` (part 2; `Contract\IssueHistories`, the door `GitHubWorkSource` reads it through) reads the history of one issue or pull request with one GraphQL query on `repository.issueOrPullRequest` (`GitHubCalls::query()`, counted and paused in GitHub's `graphql` pool, apart from the REST reads), so an open pull request with a closing keyword is read like an issue. `Core/Watcher/UseCase/WatchPullRequests` is the Scheduler tick (plan task T38, part 3). `WatcherSchedule` (`#[AsSchedule('watcher')]`, run by `messenger:consume scheduler_watcher`) holds one `RecurringMessage` per project that has a `watch` section, every minute (`Core/Watcher/Contract/WatchTick::INTERVAL`, which the GitHub reserve counts in too), each a `WatchPullRequests(project)` handled on `command.bus` by `WatchPullRequestsHandler`. a line the ledger refuses fails the tick inside that transaction, so the rows and the listing's record come back and the next tick forgets them again; a head is read again from here even when the listing answers unchanged, and a head that is not yet due is not read. `PendingHeads::dueFor()`, `StartedRounds::notYetRecorded()` and `StartedRounds::openRoundsBefore()` read each listed row again by its key (the row detached, then `find()`), because a worker keeps its entity manager, and skip a row another worker deleted in between (a `refresh()` of a deleted row keeps its old values). `LookAtHeads` then takes the due heads: `HeadLocks` tries the lock `watcher-change-<hash of project and change>` for each without waiting, skips a busy one (it stays due for the next tick), reads each held head again from `watcher_pending_head` (`PendingHeads::stillDue()`: a head another tick settled between the read and the lock is dropped, a newer head queued meanwhile replaces the one read) and holds the locks from the stale check to the round start. Every head's lock lives in the one lock store, so a store failure is no head's own: when taking a head lock fails (`LockAcquiringException`; a busy lock is no failure) or giving one back fails (`LockReleasingException`), `HeadLocks` reports it to `Budget/Contract/InstallWideFailures::lockStoreFailed()`, which starts the install-wide failure back-off, and fails the tick, so the heads stay due. It gives back every held lock, also after one failed, and reports the store failure once (the failed take, else the first failed release); it then rethrows the failure that ended the tick when there was one (the release failure is only reported, which logs it with its trace), else the first failed release. A report that fails itself (`lockStoreFailed()` throws, for example because the hold cannot be written) is logged as an error with both exceptions and contained, so the same failure is still the one rethrown. The head locks are created without auto-release, because a lock's destructor would ask a store that is still down and its exception would replace the one rethrown. `HeadDecisions` decides each held head on its own (`AdmitHeads`) and orders the decisions (`AdmissionDecision::order()`), and `SettleHeads::settleEach()` settles each through `SettleHead`: a green one first passes its `HeadGate` (`BootGate`, which boots the head only when its pull request author is trusted and otherwise appends `head_boot_skipped` and lets the round start; a trusted author's head that fails to boot while main boots is settled like a red one, with `cause` `boot_failed` in its `head_red` line and the round already started on that head withdrawn, see [Boot step](boot-step.md#in-the-watcher)), then checked by `StaleVerdicts` against the change's rounds on other heads and then starts a round (`RoundStarts`); a pending head is recorded as `head_pending` and its read-again time set with one `UPDATE` that names the head in its condition (so a newer head the listing queued meanwhile stays due now), a red one is recorded as `head_red`, and only then does `StaleVerdicts` check them, so a new head whose commit is not fetched yet (the identity query fails) is still recorded and then backs off; a red head is removed only after its check succeeded (a pending one has its failure count reset by `PendingHeads::clearFailures()` then), so one whose check failed stays queued and is read again (and recorded `head_red` again) once its back-off has passed. A head that fails backs off alone ([Budget](../design/05-architecture/06-budget-and-model-planner.md)): `HeadBackOff::tryAlone()` runs the decision and the settling of each head and catches any failure (a forge read, the stale check, the round start), so the tick goes on to the next head and records the owed `round_queued` lines without failing. A CI read the forge refuses for its rate limit (`ForgeRateLimited`, thrown before any request by the forge's own pause, see [GitHub App identity](github-app-identity.md), "Rate limits") is caught in its own clause and is no failure: `HeadBackOff` logs one info line (`project`, `change`, `head`, `resets_at`) and moves the head's read-again time to the refusal's `resetsAt` through `PendingHeads::waitUntil()` (one `UPDATE` that names the head in its condition, as `keep()` does, which delegates to it; the failure count stays), with no `head_failed` line, no failure counted and no report to `InstallWideFailures`, so a pause of several ticks hands no head over and starts no install-wide back-off, and the head is read again once the pause has ended; a pause that starts between the listing and the CI reads is covered the same way. For the failed head it logs one error with the exception (`project`, `change`, `head`) and, when the failure closed the entity manager (a failed flush closes it for every holder), resets it through `ManagerRegistry::resetManager()`, so the back-off and the next head do not fail with `EntityManagerClosed`. `FailedHeads` then, in one database transaction, sets the head's next try with one `UPDATE` that names the head and its update time in its condition (`PendingHeads::backOff()`: `read_again_at` and `failures`; it returns whether the row changed), so the same commit the listing queued again meanwhile stays due with no failures, and only when the row changed appends `head_failed` (with `cause`, the exception class and its message, bytes that are not UTF-8 replaced by `?` and then redacted like a log line through `Core/Platform/Contract/Redactor`, the held credentials included, because the cause is stored and shown on a card; `failures` in a row and `retry_at`); the next try is 60 seconds after the first failure in a row, twice as long after each further one, and at most 30 minutes. The `UPDATE` takes the row's write lock first, so a listing that closes the pull request (`forgetClosed()`, which takes no head lock) waits for it or has already removed the row; a head closed while its step was in flight thus gets no failure line after its `head_forgotten`, and no card. The fourth failure in a row appends `head_handed_over` instead of `head_failed` (the hand-over to the maintainer agent, which is planned), once; the head stays queued and is tried again at its next try, so a fault that clears lets it start its round without its pull request changing; a head the listing names again counts its failures anew. The dashboard shows the latest failure of each head as a card on `/reviews` (`LedgerFailingHeads` in [Dashboard](dashboard.md)). A failure of that report (for example the Budget table locked or the connection lost; a closed entity manager cannot be the cause, because `HeadBackOff` resets it first) is logged as an error with the exception and contained: when the report's failed flush closed the entity manager, `FailedHeads` resets it through `ManagerRegistry::resetManager()`, so the head still backs off alone and the tick goes on with the next head. A connection lost while the round was queued ends the transaction, and DBAL would reconnect in autocommit; a commit past DBAL (a native one, or MySQL's implicit commit) leaves DBAL's own transaction count at one. So `startOnce` checks that its transaction is still active, by DBAL's count and, on a PDO connection, by `PDO::inTransaction()`, before it inserts the row and otherwise discards the round and throws `RoundTransactionLost`, writing neither the row nor the removal of the pending head, so the head stays due; `Plugin/LocalGitForge/UseCase/ReviewChange/DiscardQueuedRoundHandler` removes the snapshot through `KeptSnapshots`, as `RemoveKeptSnapshot` does after the judge. A start that fails itself removes its snapshot in `LocalChangeReview` and sends no discard. `RoundStarts` then records `round_queued` for every round of the project whose `queued_recorded` flag is unset (`StartedRounds::recordOnce`: one transaction that sets the flag with one conditional `UPDATE` and appends the line through the ledger, which writes on the same connection, so a failed append rolls the flag back and two workers record a round once); `SettleHeads::settleEach()` does the same at the end of every tick, so a line whose append failed after the round was committed is written by a later tick even when no head is due. `Plugin/LocalGitForge/UseCase/ReviewChange/StartReviewAtHeadHandler` starts the round through `LocalChangeReview::startAt()`, which reads the change at that head (`LocalGitForge::changeAt()`, merge base against the base branch; a head missing from the repository is `ForgeReadFailed`), so the round reviews the commit whose CI was read, whatever the local branches point at. `StaleVerdicts` asks on `query.bus` first `Contract\IdentityAtHead` (handled by `IdentityAtHeadHandler` in the same plugin through `LocalChangeReview::identityAt()`: as `Contract\HeadIdentity`, the `VerdictIdentity` the same start would record at the new head, with the project's task, the default check command `bin/check` and the panel `Panels` chooses, and the `HeadMove` from the round's head, both read from the repository the round was read from), then `Contract\VerdictsOfRound` with both; when Review answers `stale`, `StartedRounds::markStaleOnce` runs one transaction in which one `UPDATE` sets the row's `stale` flag only where it is unset (the verdict query clears the entity manager, so a loaded row would no longer be written), and `verdicts_stale` is appended only when that update changed the row, so a round is reported once, and a failed append rolls the flag back, so a later tick checks the round again and records the line. A move that keeps the verdicts (for example documentation only) changes nothing. A head that returns to one whose round is stale (A, then B, then A) gets a fresh round: the old round was reported stale once and its verdicts no longer count, so `isStarted` ignores a stale row and the start transaction deletes it with one conditional `DELETE` (the key holds one row per head) before it inserts the new row, which starts unstale and owing its `round_queued` line; a failed start rolls the delete back, so the stale row stays. A stale row whose `round_queued` line is still owed keeps its head started until the line is recorded, so the line is not lost, and its head stays pending, so a later tick starts the fresh round once the line is recorded, also on an unchanged listing. Both decisions, whether the round starts and whether the head stays pending, come from one read of the row at the start of the transaction, because the listing lock is released before the heads are looked at and a second tick of the same project records owed lines meanwhile: a second read could find the line taken and forget the head whose start was just suppressed. Because the replacement keeps the key, the conditional `UPDATE`s of `recordOnce` and `markStaleOnce` also name the round id, so a delayed worker holding the old round neither claims the fresh round's `round_queued` line nor marks the fresh round stale. A round that stands (a move that kept the verdicts) is never replaced, so that head starts no second round. The new head gets a round only when its CI is green. The ledger kinds `head_pending`, `head_red`, `round_queued`, `verdicts_stale`, `head_failed` and `head_handed_over` carry JSON with project, change and head (and the round id, the read-again time, the cause, the failures in a row, the next try). The tables are `watcher_started_round` and `watcher_pending_head` (migration `Version20261102100000`; `Version20261104100000` adds the pending head's `failures`, default 0; `Version20261114100000` adds the started round's `withdrawal_owed` and `withdrawal_requested`, both default false; `Version20261124100000` adds its `labels`, a nullable JSON list, so a release before it still stores its rounds after a rollback; null reads as no labels, see [Labels on reviewed changes](#labels-on-reviewed-changes)). `GitHubWatchReads` is the container's `OpenChanges` and `HeadChecks` in `dev` and `prod`; in the test environment `tests/Core/Watcher/services.yaml` replaces both with `RecordedPullRequests`, which serves the file `WATCHER_RECORDING` names (pull requests and workflow runs in GitHub's shape). ### Verdict identity

`Core/Review/Contract/VerdictIdentity` (plan task T11) is what a verdict was given on: the `commits` (`CommitRange`, head and base) and the `ReviewTerms`: the task revision, the check command and the panel policy, each a SHA-256 hash (`ReviewTerms::of(task, checkCommand, Panel)`: the task text, the command line, and the JSON of the quorum policy with every reviewer's role name, prompt, tier, provider and budget in panel order). Builder's choice: the task revision is the hash of the task text, because a local branch has no task revision of its own, and the hashes keep a recorded identity free of the task text and the command line. `recorded()` writes the five parts as `head.base.task-revision.check-command.panel-policy` (a dot never occurs in a hash); `VerdictIdentity::fromRecorded()` reads that form back and refuses any other shape with a named exception next to its thrower: `RecordedIdentityMalformed` for a count of parts other than five, `ReviewTermMalformed` (from `ReviewTerms`) for a term that is no SHA-256 hash, and `Forge/Contract/CommitIdMalformed` (from `CommitId`, which refuses anything but a full lowercase hash) for a head or base that is no commit id. All three extend `InvalidArgumentException` and are not `ReportableFailure`s, because a stored identity reaches them too. `GitHubForge` and `LocalGitForge` catch `CommitIdMalformed` (never the SPL class) where they read a hash and turn it into `ForgeReadFailed`; `GitHubWatchReads` turns `ChangeNotFound`, `ChangeIdEmpty` and `CommitIdMalformed` from a listed pull request into `ForgeReadFailed`, and lets any other exception propagate.

`standingAt(VerdictIdentity $current, HeadMove $move)` returns a `VerdictStanding`: its `Standing` (`current`, `kept-for-untouched-parts` or `stale`), the `IdentityField`s that `changed`, and the paths to `reviewAgain` (a `Git\Contract\Paths`, empty unless the verdict is kept). No change is `current`. A changed task revision, check command or panel policy is always `stale`. When only the head and base changed, a `clean-merge-of-base` move keeps the verdict, and so does a `commits` move that left the base unchanged and touched only paths under `docs/` (builder's choice: documentation is the root `docs/` folder only, so a `README.md` elsewhere or a `docs/` folder below the root is code to review); the move's paths are then the ones to review again. Any other move (`rewritten`, or commits touching other paths) is `stale`.

Every review round records the identity it was started on (`RunReviewRound` carries it, the `verdict_identity` column of `review_round`, migration `Version20261031140000`); `ReviewRounds::open()` refuses one whose task revision or panel policy is not that of the round's task and panel (`IdentityNotOfRound`, through `ReviewTerms::describes()`). Its verdicts are read with the query `Contract/VerdictsOfRound` (round id, current identity, the `HeadMove` from the round's head), handled on `query.bus` by `VerdictsOfRoundHandler`: it clears the entity manager, loads the round (an unknown id is `RoundNotFound`), takes the standing from `ReviewRound::standingAt()` and returns a `Contract/RoundVerdicts` with that standing and the verdicts that still count (`counting`, one `PanelVerdict` per reviewer with a verdict, deserialized from its stored JSON): none when the standing is `stale` or the round is a replay (`ReviewRound::replayMark()`, [Review flow](review-flow.md#a-replay)), all of them otherwise, whatever the project's mode (see [Mode per project](capability-tiers.md#mode-per-project)), with the standing's `reviewAgain` paths. A round stored before the column has no identity and is `stale` in every field; a round marked stale with `MarkVerdictsStale` is `stale` in `head` whatever identity it is asked about ([Review flow](review-flow.md#a-round-marked-stale)). The Watcher dispatches it when a head moves during a round (see [Open pull request listing](#open-pull-request-listing)); the quorum decision over stored verdicts is a later task.

`php bin/console intakt:verdict:identity <project> <branch> <task> <check-command> [--reviewed=IDENTITY] [--repository=.] [--base=main]` (`Plugin/LocalGitForge/UseCase/CheckVerdictIdentity`) reads the branch's `Change`, asks the review module's `Contract\Panels` (implemented by `ConfiguredPanels`) for the project's panel for that change (its changed lines and paths, no labels), and prints `identity <recorded form>`. With `--reviewed` it reads the head move from the recorded head and prints the standing, then `changed` fields after a colon (`stale: head changed`), and one `review again <path>` line per path, escaped like the summary's paths. An unknown branch, a git failure, a project without a panel, a glob that cannot be evaluated (`GlobCannotBeEvaluated`, now in the review module's `Contract`) and a recorded identity of another shape (the command turns those three named exceptions of `fromRecorded()` into `RecordedIdentityUnreadable` with the message `--reviewed is not a recorded verdict identity: ` and the refusal, because only there is the identity typed by a person; any other `InvalidArgumentException` passes through as a programming error) print the message as an error and exit with 1.

**Review command.** `php bin/console intakt:review <branch> --project=P --task=T [--round=N] [--format=text|json] [--repository=.] [--base=main] [--check-command=bin/check]` (`Plugin/LocalGitForge/UseCase/ReviewChange`, in the forge plugin because it reads the change from a local repository, which the core review module may not reach) reads the branch's `Change`, asks `Contract\Panels` for the panel, builds the `VerdictIdentity` like `intakt:verdict:identity`, and hands a `Contract\ChangeReviewRequest` to `Contract\ChangeReviews` inside `LocalGitForge::withSnapshotOf()`: a detached worktree of the head commit (`git worktree add --detach`, through the hardened call, so no hook or filter of the repository runs, with `-c core.autocrlf=false -c core.eol=lf -c core.sparseCheckout=false -c core.sparseCheckoutCone=false`, so neither a line-ending conversion nor a sparse checkout of the repository reaches the snapshot) in a fresh directory `intakt-review-<random>` under `sys_get_temp_dir()`, whose real path is the request's `checkoutRoot`, removed in a `finally` (`LocalGitForge::removeSnapshot()`, `git worktree remove --force`, skipped when the directory is already gone) once the round ends or the review fails; the reviewers read the head's files whatever happens in the user's checkout meanwhile, and the checkout itself is never touched. The command implements the Console component's `SignalableCommandInterface` for SIGINT and SIGTERM (when `SignalRegistry::isSupported()`, that is with `pcntl`): while the round runs, `CleanupOnStop` (a `ResetInterface` service) holds the snapshot's removal, and `handleSignal()` runs it and returns 128 plus the signal (130, 143), so a stopped command, which skips the `finally`, leaves no worktree; only SIGKILL can. The change name and the optional expected round number travel as one `Contract\RequestedRound` on the request and on `RunReviewRound`. `Core/Review/UseCase/ReviewChange/ReviewChange` implements the contract: it first refuses a round whose project maps no model to a tier the round needs with `RoundTierNotMapped` (each reviewer's tier and the judge's, see [Review flow](review-flow.md#refused-before-it-starts)), then dispatches `RunReviewRound` on the command bus with the `RequestedRound`, whose number `ReviewRounds::open()` compares with the number it takes under the change's `change_findings` lock and refuses with `RoundNotNext` inside the transaction (so a round another caller opened first is seen, and the refused round is rolled back; `ReviewChange` gets it as itself, because `command.bus` unwraps a handler's exception, see [Conventions](conventions.md)), and reads the round id from the `HandledStamp`, then polls the stored round once a second through `ClockInterface::sleep()` until it is `judged`, its judging failed for good, or the upper wait passes (`UseCase/ReviewChange/UpperWait::secondsFor()`: `RoundReviewer::REVIEW_CEILING_SECONDS`, 3600, for each reviewer of the panel, added up because one worker runs them one after another, plus `UpperWait::JUDGE_SECONDS`, the same 3600 for the judge's one call; 10800 for a panel of two; builder's choice: the sum rather than the longest, so a single worker never has a healthy round cut); a judging failed for good when the round is `complete` and `UseCase/JudgeRound/FailedJudgings::hasFailed()` finds a `judging_failed` ledger event of the round (`Contract\JudgingFailed`, appended by `RecordFailedJudgingHandler` for the `RecordFailedJudging` message that the judging's `DispatchOnFailureStamp` dispatches, see [Review flow](review-flow.md)) or, when that message could not be dispatched, a `JudgeRound` message of the round in the failure transport (`messenger.transport.failed`, read with `ListableReceiverInterface::all(FailedJudgings::PARKED_MESSAGES_READ)`, at most 500 messages in no set order, which leaves the message in place; a transport that cannot be listed shows no failure), and the review is then `blocked` with the reason `the judging failed` (`RoundEndReasons::JUDGING_FAILED`, end `RoundEnds::JudgingFailed`) and an empty act list, while the round stays unjudged; the workers (`messenger:consume async`) do the reviewing and the judging, the command only waits. `Contract\ChangeDecision` (in the contract, because the dashboard decides a judged round's outcome with it too) decides from the quorum policy and the stored verdicts (read with `UseCase/ReadVerdicts/StoredVerdicts`, which `VerdictsOfRoundHandler` uses too; the standing rules are not applied, since the round was started on the current identity and reviewed in a snapshot of its head): `approve` when `QuorumPolicy::isMet()`, else `changes` when any verdict is `changes`, else `blocked`; a reviewer without a verdict votes as `blocked`, a round whose `ReviewRound::replayMark()` is `Replay` is `blocked` without asking `ChangeDecision`, with the reason `RoundEndReasons::REPLAY` first in `reasons` for a judged round ([Review flow](review-flow.md#a-replay)), and a round that is not judged at the upper wait is `blocked` with the reason `no outcome in time` (`RoundEndReasons::NO_OUTCOME_IN_TIME`, end `RoundEnds::NoOutcomeInTime`, followed by the seconds waited and the hint to start a worker). The act list is the round's reported findings whose ids the `judge_done` ledger event lists under `act`, one entry per place and per cause the judge linked (`StoredFindings::actListOf()`, see [Review flow](review-flow.md)), and the text output prints a merged entry's ids joined with `+`, while the JSON row carries them under `merged`. `RoundLedgerReading::tokensOf()` sums the tokens of the calls whose `started` `usage_recorded` row carries the round's id under `round` (each reviewer call of the round and its judge call), wherever in the ledger they sit: the `settled` or `unsettled` row with the same `call` id carries the `usages`, and a call started without a round id counts for no round, so rounds of one project running at once each count only their own calls; it adds up each usage's `TokenUsageRow::figures()` into `RoundTokens` (calls, prompt, cache read, cache write, cached, completion, total; see [Vendor](vendor.md#token-figures)), and the text's token line names the cache parts that are not 0 in parentheses after the prompt. `RoundLedgerReading::costOf()` prices the same calls by their model into a `Budget/Contract/Cost`, printed as the `cost:` line after the token line and as `cost` in the JSON (see [Round cost](round-cost.md)). ### Labels on reviewed changes

Plan task T19. `Infrastructure\TrustedPullRequestLabels::of(project, PullRequestAddress, listedAt)` refuses a pull request outside the project's configured repository (`ChangeNotFound`; `PullRequestAddress::isIn()` compares owner and repository without regard to case, as GitHub does, and `GitHubStatusLabels` refuses the same way), because the history and the trust are read for that repository, then reads the pull request's `IssueHistory`, drops a label that is no longer on it, asks `SteeringTrustCheck` about each account that applied one (one answer per account per read) and keeps only labels from a writer, Intakt's own identity or the Maintainer. A trust check that fails fails the read (`TrustNotChecked`), so an unchecked label never steers. The result is a `Domain\TrustedLabels`: the steering `Core\Review\Contract\Labels` and the outvoted values. `Domain\LabelFamilies` keeps one value in each one-value family of the design (`priority:`, `class:`, `model:`, `plan:`), the one applied last, and names the trusted values applied earlier as outvoted; any other prefix (`review:`, `status:`, a project's own such as `area:`) and a label without a colon is no such family, so none of its labels is removed. `Plugin\Forge\Contract\ChangeLabels::steeringOf(project, OpenChange)` is the read the watcher calls when it queues a round; `Infrastructure\GitHubChangeLabels` implements it and, when the read fails, logs a warning and answers no labels, so a failed read is never a decision. It hands the outvoted values to `Infrastructure\OutvotedLabels`, which removes each (`DELETE .../issues/{n}/labels/{label}`, a 404 counts as removed) and posts one comment naming them; a failed write is logged and dropped. Both label writes go through `Infrastructure\GitHubLabelWrites`. `RoundStarts` passes the labels to `WatchedProject::startAt()`, so they ride `StartReview::$labels` and `ReviewChangeInput::$labels` into `LocalChangeReview::describe()`, and back in `QueuedRound::$labels` to the `labels` column of `watcher_started_round`. `StaleVerdicts` asks for the identity at a moved head with the labels kept on the round (`StartedRound::labels()`; a row stored before the column has none), so it reads no labels and a failed read cannot change the identity. In `ConfiguredPanels`, `review:full` adds the reviewers of every rule and `model:<tier>` (parsed by `Tier::fromLabel()`, also used by `BuildFacts::fromLabels()`) sets the tier of every reviewer, except that under a quorum that needs a strong vote (`QuorumPolicy::needsStrongVote()`, `one-strong-plus-one`) a reviewer configured as strong stays strong; a value naming no tier changes nothing. `Plugin\Forge\Contract\StatusLabels` is the write side, apart from `Forge` because only a forge with labels has one. Its one step, `reconcile(project, change)`, takes no status from the caller: the status comes from Intakt's own stored round (`Core\Review\Contract\LatestRoundStatus`, implemented by `StoredLatestRoundStatus` over `ReviewRounds::latestStateOf()`, which reads the state of the pull request's newest round as an array, so a worker's identity map cannot hand it an old state). A round collecting or complete gives `status:in-review`, a judged round gives `status:waiting-on-you` (its verdict is published right after its judging; no publication is stored), and no round gives no status label. `RoundStatusMirror::reconcile()` wraps the step, does nothing for a forge without it and logs and drops any failure, so the next watcher pass reconciles again. `RoundStarts` reconciles after `StartedRounds::startOnce()` committed (also when the head already had a round, because a label change makes the head due again) and from `RoundStarts::restoreIfStarted()` when the head now starts no round (its CI turned pending or red, or its boot failed) on a pull request that had a round at this or an earlier head (`StartedRounds::hasRoundOf()`); `PublishVerdictHandler` reconciles after a verdict is published. `Infrastructure\GitHubStatusLabels` takes the lock `intakt.status-label.<hash of the pull request's owner and repository in lower case and its number>` (two spellings of one address share it) without waiting: a writer that finds it held skips its write and logs it at info level, and never writes without it. Because the holder reads the stored round while it holds the lock, and every later watcher pass reconciles again, a skipped write leaves a wrong label for at most one pass; there is no wait and no read to confirm a write. Under the lock it reads the stored round, then the labels on the pull request (`Infrastructure\GitHubStatusReads::labelsOn()`, `GET .../issues/{n}/labels`, up to 10 pages of 100), and `Domain\StatusReconciliation` names the `status:` labels to remove and the one to add. Only when that changes something does it read the label events (`GitHubStatusReads::of()`, `GET .../issues/{n}/events`, kept to `status:` labels), and only to decide the comment: when the latest event on a `status:` label came from someone other than Intakt's own identity, it posts one comment through `GitHubIssueComments` after its writes. Every read comes before the first write, so a failed read writes nothing. A second pass finds the labels right and writes and comments nothing. The local git forge has no labels, so its rounds carry none.
