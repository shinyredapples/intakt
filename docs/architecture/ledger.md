## Ledger

### In short

The ledger is Intakt's append-only event log, one table `ledger_event` (an auto-increment `position`, a UUIDv7 `id`, the `kind`, the `payload` text, `recorded_at` in UTC and an optional indexed `subject`). Other modules use only its contract: `Ledger::append()` returns an `AppendResult` instead of throwing, and the reads return `RecordedEvents` in append order: all events (`readInOrder()`), one kind (`readOfKind()`), one kind with exactly a given subject (`readOfKindAbout()`), one kind stored with no subject at all (`readOfKindWithoutSubject()`), the events whose payload mentions any of some texts (`readMentioning()`), and the same narrowed to some kinds in the query (`readOfKindsMentioning()`). `PayloadFields` reads untyped payloads by typed field. Stored events are never changed or deleted: a Doctrine listener and SQLite triggers refuse it, with one exception for the replayed demo rows.

### Details

`src/Core/Ledger/` keeps the append-only event log in one table, `ledger_event` (`position` auto-increment integer primary key, `id` UUIDv7 through Symfony Uid's Doctrine type `uuid` with the unique index `ledger_event_id`, `kind`, `payload` text, `recorded_at` in UTC, and the nullable `subject`, a `VARCHAR(255)` with the index `ledger_event_subject` on `(kind, subject, position)`). The migration `Version20261027120000` creates it through the schema API, so it is not tied to SQLite. `Version20261122110000` (#2554) adds `subject` with a plain `ALTER TABLE ... ADD`, because the schema diff rebuilds an SQLite table to alter it and would drop the append-only triggers, then creates the index; on an existing ledger the stored rows keep a null subject, since rows are never back-filled, and its way back drops the index and the column.

- `LedgerEventKind` also has `escalation_reviewed` and `escalation_failed`, the kinds for an escalation review's verdict and its failure, which `EscalateRecurringP1Handler` appends, and `RecordFailedEscalationHandler` for an escalation parked after its retries (see [The escalation review](review-flow.md#the-escalation-review)).
- `append` is marked `#[NoDiscard]` on the interface and on `DoctrineLedger`, because PHP checks the method that runs. A database failure, or an entity manager that an earlier failure closed (`EntityManagerClosed`), is returned as `AppendResult::failed($reason)` (`succeeded()` is false, `id` is null, the reason names the exception class but not its message), not thrown; success carries the `id` of the stored event. After a failure the ledger resets the entity manager through the `ManagerRegistry`, so the next append works. The ledger owns the default entity manager: `append` flushes every pending change in it and the reset discards them, so a second entity needs its own manager or a flush of only the ledger record.
- `Domain/EventRecord` is the Doctrine entity; `Infrastructure/DoctrineLedger` implements the contract. The moment comes from the clock, converted to UTC. The column keeps it without an offset, so `recorded_at` is mapped to the DBAL type `utc_datetime_immutable` (`Infrastructure/UtcDateTimeImmutableType`, registered in `config/packages/doctrine.yaml`): it writes the UTC wall clock and parses the stored text as UTC, never in PHP's default time zone, so a moment inside a daylight-saving gap of that zone is read back unchanged. A stored value that is not a wall clock, or names a date or time that does not exist (PHP reports a warning and would roll it over), is refused with a conversion exception. The id is a `UuidV7` generated from the same clock moment, so it carries the time the event was stored. Events are read ordered by `position`, which the database assigns on insert, not by `id`: ids do not follow append order when the clock steps back or when two processes append in the same millisecond. `position` stays inside the module; the contract exposes only the id.
- `tests/Core/Ledger/DoctrineLedgerTest.php` is in the `persistence` group, and so is `tests/Core/Ledger/DoctrineLedgerOnACaseInsensitiveSubjectTest.php` (a `subject` column with SQLite's `COLLATE NOCASE`: `R1` reads nothing stored as `r1`); `tests/Core/Ledger/UtcDateTimeImmutableTypeTest.php` tests the type without a database.
- Updates and deletes are refused twice. `Infrastructure/RefuseChangesToStoredEvents` is a Doctrine `onFlush` listener (registered by `#[AsDoctrineListener]`) that throws `Contract/LedgerEventsAreAppendOnly` (a `LogicException`) when the unit of work holds a scheduled update or deletion of an `EventRecord`. Before throwing it clears the entity manager, so the refused change, and anything else pending in it, is not carried into the next flush: the code that flushes the change gets the exception, and later appends in the same worker are stored. When a refused change is still pending as `append` flushes, the refusal reaches `append` instead: it returns `AppendResult::failed` naming `LedgerEventsAreAppendOnly`, its own event is not stored, and the code that made the change gets no exception, because its change was discarded. The migration `Version20261028120000` adds the SQLite triggers `ledger_event_no_update` and `ledger_event_no_delete`, which abort with `ledger_event is append-only` and so also stop DQL bulk statements and raw SQL, and `ledger_event_no_replace`, a `BEFORE INSERT` trigger that aborts an insert whose `position` or `id` is already stored, because `INSERT OR REPLACE` removes the conflicting row without firing delete triggers unless `recursive_triggers` is on; on other platforms the migration does nothing, so there only the listener applies.
- One exception removes rows (issue #2078): `Contract/RemoveReplayedEvents` (a list of event ids), handled on the command bus by `UseCase/RemoveReplayedEvents/RemoveReplayedEventsHandler`, deletes those rows through the DBAL connection, not the unit of work, so the listener above stays as it is for every other path. On SQLite it reads the `ledger_event_no_delete` trigger's statement from `sqlite_master`, drops it, deletes the rows by `id` and creates the trigger again from that statement, all in one transaction: SQLite lets no other writer in while it is held, and a failure rolls the drop back, so the trigger is never missing for another connection. Only `intakt:demo:remove` sends it, with the rows replayed into the demo project after checking that project is flagged as a replay, because the ledger knows no projects ([The demo recording](demo-recording.md#removing-the-demo-project)). `tests/Core/Ledger/RemoveReplayedEventsHandlerTest.php` (`persistence` group, with the migration's triggers through `AppendOnlyTriggers` beside it): only the named rows go, an empty list keeps every row, and afterwards a raw delete is still refused by the trigger and an ORM delete by the listener.
- `UseCase/ReadEvents/ReadEventsCommand` is `intakt:ledger:events`: it reads `Ledger::readInOrder()` and prints one line per event of a known kind (`recorded_at` in UTC, id, kind, payload) through `OutputFormatter::escape`, so formatter tags in a payload print as stored, and a count; rows of a removed kind stay stored, are skipped by `DoctrineLedger` and are not counted. It has no run filter because events carry no run reference yet.
- `tests/Core/Ledger/AppendOnlyLedgerTest.php` (`persistence` group) has one test per refused operation, at the Doctrine level and in the database; `DoctrineLedgerTest` checks that an append after a Doctrine refusal, or after another failure closed the manager, is stored, and that `readOfKindAbout()` reads only the kind's events of the exact subject (none for a prefix of a stored subject) and `readOfKindWithoutSubject()` only those appended without one, in append order; `tests/Application/MigrationsMatchMappingTest.php` (`persistence` group) empties the database, runs `doctrine:migrations:migrate` and asserts that `doctrine:schema:validate --skip-mapping` finds no difference from the mapping, since the other tests build their schema from the mapping; `tests/Core/Ledger/ReadEventsCommandTest.php` covers the command with a stub ledger.
