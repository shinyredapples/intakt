## Sample repository

`fixtures/sample-repository/` is data, not code; the demo's seed builds a git repository from it (see [The demo](demo-with-docker-compose.md)). `base/` is the tree of the base commit; `pull-request/` holds only the files the branch adds or changes. `issues.json` lists each deliberate issue (`id`, `kind` of bug, missing-test or security, `file`, `description`, and an `evidence` line that appears as an added line in the change). `SampleRepositoryTest` builds the repository with the test `TemporaryRepository` (base on `main`, then the overlay on `sample-change`) and checks that every listed issue is in the diff. It is JavaScript so the PHP gates do not scan it.


### The bench repository

`fixtures/sample-repository/bench/` grows from the same `base/` and holds the changes of the review bench (issue #1938; the data and the plain code that scores a run, then the command that reviews one change and the command that runs the whole bench into a result file, below; repeated runs, the comparison of runs and the report come later). There are eight changes, each in `bench/<change>/` with a `tree/` (the files the branch adds or changes, the same layout as `pull-request/`), a `task.md` and an `expectations.json`. `BenchRepositoryTest` builds each as its own branch `bench/<change>` on top of `main`. The demo seed reads only `base/` and `pull-request/`, so it is unchanged.

`expectations.json` is a list of planted defects: `id`, `file`, `lines` (`from` and `to`, inclusive, 1-based), `description` and `severity` (`P1`, `P2` or `P3`, what the defect deserves). Five changes plant one defect each (an acceptance item not met, an error path never handled, input that runs commands, an off-by-one boundary, docs that state what the code does not do); three plant none (`[]`), so false alarms are measured. `Expectations::fromJson` refuses with `InvalidExpectations` a file whose top level is not a JSON list (an object such as `{}` too), an entry that is not an object, a missing or reversed range, an unknown severity and an `id` listed twice. The test checks that every planted line is a `+` line of the change's diff (unchanged context lines do not count); `ScriptedBenchRunTest` classifies every bench change with scripted reviewer findings and checks the figures.

Matching and counting are plain code in `src/Core/Bench/` (`Domain/`, with the results in `Contract/`) and never ask a model:

- `DefectMatcher`: a finding matches a defect when it names the same file and a line inside the range. A finding without a file or line never matches, and there is no tolerance for a nearby line.
- `RunClassifier`: unmatched findings on a defect-free change are false alarms. Unmatched findings on a change with defects are listed in the verdict, not counted.
- Every missed defect gets a cause (`FailureCause`): `harness` when the run failed (a provider or tool failure, `RunOutcome::failed()`), `bench` when the expectation cannot hold (its file is not in the change or its range ends past the file's last line, checked with `ChangeFiles`), otherwise `reviewer` (the model missed it). The range is checked before matching, so a finding never catches a defect whose expectation cannot hold: that defect is `bench`, and the finding is listed as unmatched (a false alarm on a defect-free change cannot arise, as it has no defects).
- `BenchFigures`: the detection rate (caught over planted) and the false alarm rate (clean runs with at least one false alarm over clean runs) leave out harness failures, which are listed with their reasons. A rate with nothing to count is `null`, not zero.

### Reviewing one bench change

`php bin/console intakt:bench:review <change> --project=<project>` runs one bench change through the normal review path and prints the result; it calls the project's paid models, so it runs only when asked and nothing in `bin/check` or CI calls it. `BenchChangeCheckout` builds a git repository of its own for the run (the `base/` commit on `main`, then the change's `tree/` as `bench/<change>`, with a fixed author and moment) in a folder under the system's temporary folder (`sys_get_temp_dir()`) and removes it afterwards, also when the review fails. It asks the project's panel for the change's size and paths (`Panels`), and the request names a round change of its own for every run (`bench/<change>-<random>`), because rounds of one change share a finding ledger and a second run must not see the findings of the first. A name that is not a folder of `bench/` (or is not lowercase letters, digits and hyphens) is refused with `There is no bench change named "<name>".`, and the command exits with 1, as it does without `--project`.

`ReviewBenchChange` sends the request through `Review\Contract\ChangeReviews`, the same panel, judge and ledger that `intakt:review` uses, and classifies each reviewer's own verdict with `RunClassifier`. `BenchReview` holds the round's decision, the judge's act list (for the whole round, because the judge merges the reviewers' findings) and one `BenchReviewerResult` per reviewer: its role and tier, the `RunVerdict` (the defects caught, the misses with their cause, the false alarms on a defect-free change, the unmatched findings and the harness failure), the tokens and the duration. A reviewer that failed, was stopped, or gave no verdict is a harness failure with the failure in plain words, so its misses are `harness` and never counted against the reviewer.

The per-reviewer figures are read back from the ledger by `RoundLedgerReading` and carried on `ChangeReview::$reviewers` as `ReviewerOutcome`. Tokens are the usage rows whose `usage_recorded` started row names the reviewer (`UsageStarted::$reviewer`, set by `SymfonyAiVendor` from the conversation; rows written before it existed name none and count for no reviewer, though they still count for the round). The duration is in milliseconds, from the reviewer's first `reviewer_started` to its last `verdict_received`, `reviewer_failed` or `reviewer_stopped` row, by the ledger's clock; it is empty while the reviewer has no end.

The provenance is the Intakt version, a hash of each prompt and a hash of the bench repository, which `ReadBenchProvenance` reads, the command prints and the result file below names: the version (and commit when Composer knows it) of the install; `Review\Contract\ReviewPrompts` (`HashedReviewPrompts`), the SHA-256 of the reviewer's and the judge's instruction text (`ReviewerPrompt::INSTRUCTIONS`, `JudgePrompt::INSTRUCTIONS`; a role's own prompt is part of the project's panel and already in a round's panel policy hash); and the SHA-256 over every file of `base/` and `bench/` by path and content, hidden files (such as a `.gitignore`) included, because the checkout copies them into the reviewed repository. Tests: `ReviewBenchChangeTest` (scripted vendor on SQLite: the figures per reviewer, a false alarm, a failed reviewer), `HashedReviewPromptsTest` (stable, and changed by a changed text), `ReadBenchProvenanceTest`, `BenchChangeCheckoutTest` and `ReviewBenchChangeCommandTest`.

### Running the whole bench

`php bin/console intakt:bench --project=<project>` (`src/Core/Bench/UseCase/RunBench/`) runs every bench change through the same path; like `intakt:bench:review` it calls the project's paid models, so it runs only when asked and nothing in `bin/check` or CI calls it. Without `--project` it exits with 1 before any checkout is built. `RunBench` takes the changes from `BenchChangeCheckout::names()` (every folder of `bench/` with an `expectations.json`, in name order) and reviews each with `ReviewBenchChange` in a checkout of its own under the system's temporary folder, removed after each change, also when its review fails. A `ReportableFailure` of any review ends the run: the command prints it, exits with 1 and writes no file. Otherwise it prints one line per change (`<change>: decision <decision>, measured <n> act list findings`) and per reviewer (`<role> (<tier>), measured: <n> caught, <n> missed, <n> false alarms, <n> prompt tokens, <n> completion tokens, <n> calls, <n> ms` or `no end`, then the harness failure if there is one), and the path of the result file.

`BenchResultFile` writes the result file with `Filesystem::dumpFile()` to `var/bench/<moment>-<random>.json`, the moment from the `ClockInterface` in UTC (`Ymd\THis\Z`) and six random hex digits, so two runs in the same second keep both files. The JSON object holds `intakt_version`, `ran_at` (ISO 8601, UTC), `project`, `prompts` (`reviewer`, `judge`), `bench_repository` and `changes`, one entry per change with `change`, `decision`, `act_list` and `reviewers`. Each reviewer has `role`, `tier`, `caught` (defect ids), `missed` (a list of `id` and `cause`, `reviewer`, `bench` or `harness`), `false_alarms`, `unmatched`, `harness_failure` (`null` when the run completed), `tokens` (`calls`, `prompt`, `completion`, `total`) and `milliseconds` (`null` while the reviewer has no end). A finding is written as `id`, `severity`, `file`, `line` and `text`. Tests: `BenchResultFileTest` (each field), `RunBenchCommandTest` (no project, one file and its path, every change once in name order, every figure labeled as measured, a failed review) and `RunBenchTest` (scripted vendor on SQLite: the figures per reviewer and a false alarm in the result file).
