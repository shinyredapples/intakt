## Persistence

SQLite by default (`DATABASE_URL` in `.env`). MySQL, MariaDB and PostgreSQL are supported targets: the `persistence` job in `.github/workflows/ci.yml` runs `vendor/bin/phpunit --group persistence` on MySQL, MariaDB and PostgreSQL, in the versions `.github/ci/databases.Dockerfile` pins (one job with a service container per engine, its data directory on a tmpfs, and one step that runs the three engines at once through `.github/ci/persistence-engines.sh`, each reached by its service name `mysql`, `mariadb` or `postgresql`, no password; one job instead of a three-entry matrix because each job costs an ephemeral runner a full reset; the test environment appends `_test` to the database name, so the URL names `intakt` and the service creates `intakt_test`). On a pull request the engines run only when the `changes` job finds the change touches persistence: a path under `src/Core/Ledger/`, `src/Core/Platform/` (the database platform and server version), `migrations/`, `tests/Core/Ledger/`, `tests/Core/Platform/`, Doctrine's configuration, the Composer files, `phpunit.dist.xml`, `tests/Application/MigrationsMatchMappingTest.php`, the test SQLite middleware (`tests/Support/UnsyncedSqlite.php`, `tests/Support/UnsyncedSqliteDriver.php` and `tests/Support/services.yaml`, which tags it for every engine), `.github/workflows/` or `.github/ci/`, an added line naming Doctrine in `src/`, or a test it adds, removes or edits in the `persistence` group (a changed line or file under `tests/` naming `Group('persistence')`); `.github/ci/persistence-needed.sh` decides, with rename detection off so a renamed file counts under its old path too, and its diffs are saved and must succeed first, so a failure fails the `changes` job and the run rather than reading as untouched. A full push run on main always runs them. A push to main whose commit passed `ci.yml` as the head of a pull request into main skips them (see the `main` bullet of [CI](ci.md)), so a change a pull-request filter misses is caught by the nightly full run on main (#2126), and until that lands by the next direct push or release commit. `bin/check` still runs the whole suite on SQLite. In the test environment every SQLite connection of the container runs `PRAGMA synchronous = OFF` when it connects (`tests/Support/UnsyncedSqlite.php`, a DBAL middleware that `tests/Support/services.yaml` tags `doctrine.middleware`; a connection to another engine is left as it is), so a test does not wait for the disk after each statement on its scratch database file. A persistence test starts from `EmptyDatabase::rowsIn()` (`tests/Application/EmptyDatabase.php`), which on SQLite keeps the mapped tables of the scratch database and deletes their rows (children first is not needed, foreign keys are off during the delete and back to their earlier setting afterwards, also when a delete fails, and the identity counters restart), instead of dropping and creating the 27 tables for every test; it rebuilds the schema when the current mapping's create statements (`SchemaTool::getCreateSchemaSql()`) or the table and index definitions in `sqlite_master` differ from those of its last build, whose fingerprint of both it keeps in the file's `PRAGMA user_version` (a new file, a changed mapping, a dropped column, a schema a migration test left); it quotes the table and trigger names it deletes from and drops through the platform, and on MySQL, MariaDB and PostgreSQL it always drops and creates the schema, as before; the migration tests still start from `EmptyDatabase::in()`, the full drop. No wrapping transaction is used, so a test of a rollback sees a real one. `doctrine.dbal.server_version` comes from the `postgresql_server_version` env var processor (`src/Core/Platform/Infrastructure/PostgreSqlServerVersion.php`) applied to `DATABASE_URL`: a PostgreSQL URL (driver `pdo_pgsql`, or `pgsql` through `?driver=pgsql`) gets `12`, the version of DBAL 4's newest PostgreSQL platform, and any other URL none, so MySQL, MariaDB and SQLite detect the server on the first connection. DoctrineBundle picks a platform before it connects and refuses an empty PostgreSQL version (`upstream/doctrine-bundle-postgresql-empty-server-version`); `tests/Core/Platform/PostgreSqlServerVersionTest.php` builds the test connection for both PostgreSQL drivers and for MySQL. `migrations/` is in Composer's `autoload-dev` (`DoctrineMigrations\`), so tests and static analysis name a migration class directly; the migrations bundle still finds migrations by path. `config/packages/doctrine.yaml` sets the ORM's `use_schema_editor_api` to true: Doctrine ORM 3.8 deprecates schema generation without the schema editor API (`tests/Application/KernelTest.php` checks that the entity manager's `SchemaTool` triggers no such deprecation).
