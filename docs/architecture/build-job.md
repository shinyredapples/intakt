# Build job

Plan task T49, the job itself (#1709; design: [overview](../design/05-architecture/01-overview.md), [threat model](../design/05-architecture/14-threat-model.md#builder)). A build job runs the Claude Code CLI on the [builder prompt](builder-prompt.md) in a [job container](job-containers.md) of its own, and returns a git bundle and the pull request text, or a question. The session is bounded by a turn limit and an allowance, and a cut session keeps its commits (#1710); the allowance is a fixed constant until T60 sizes it per task. A build that needs a decision ends with a structured question, checked by its refusal rule and carried in the outcome (#2672); `BuildTask` parks the task on an accepted question; not built yet: posting the question; the builder's own check tool in the job; reading usage from the session log; the account credential in the job (the job holds none yet, so a real build cannot sign in to the vendor).

`php bin/console intakt:build:run <project> <clone> <branch> <task> <image> <bundle> [--tier=<tier>] [--decision=<text> ...]` (`RunBuildJobCommand`) calls `UseCase/RunBuildJob/RunBuildJob::run(BuildJob)` (marked `#[NoDiscard]`) in `Core/Build`. [`intakt:build:task`](build-task.md) calls it too, as its build job step, with the tier the routing rules choose. Nothing calls it from another module yet: the build lane (T56) will.

## The steps

1. **Model:** `TierResolver::resolve(<project>, <tier>)` picks the model from the project's tier map ([Capability tiers](capability-tiers.md)); the tier is the caller's choice (`--tier`, `standard` by default, for `intakt:build:run`; the routing rules' choice for `intakt:build:task`). A tier on any provider but `claude_code` is `BuilderNotOnClaudeCode`, because the job runs the Claude Code CLI and holds no vendor API key; a tier that cannot be resolved (`TierResolutionFailure`) is thrown as it is. No job starts in either case.
2. **Clone:** `<clone>` is a [build clone](build-clone.md) made with `intakt:build:clone` (resolved with `realpath`); a path that is no folder is a `BuildCloneIsNoFolder`. The job gets the build clone, never the mirror, so it sees main, the task's branch and a verified source and no other branch.
3. **Prompt:** `BuilderPrompt::textFor()` of the `BuildBrief`, written to a file of its own, `var/prompts/prompt-<random>.md` (mode 0600), which is removed after the job, also when the job throws.
4. **Job** (`JobRunner::run()`):
   - the image given, as the project's job image ([Job images](job-images.md));
   - two read-only inputs, the build clone at `/input/clone` and the prompt file at `/input/prompt.md`, and no mount of the [dependency snapshot store](check-job.md#the-dependency-snapshot-store), which only the orchestrator's own process writes, so a builder cannot change an install a later check reuses;
   - the command `/bin/sh -c <docker/job/build.sh> intakt-build /input/clone /input/prompt.md <branch> <model> <max turns> <allowance seconds> <gates at once> <tool time limit seconds>` (100 turns and 3000 seconds, builder's choice until T60), the script's text read from the project folder for each job;
   - `<tool time limit seconds>` is the parameter `intakt.build.tool_time_limit_seconds` (`BuildServices::TOOL_TIME_LIMIT`, 1500 in `config/services.yaml`), injected into `RunBuildJob` with `#[Autowire(param: ...)]`. The constructor refuses a value that is not an integer (a YAML boolean, a string or a float), below 1, or not below the allowance (3000) with an `InvalidArgumentException`, because a tool call that outlives the session is cut with it anyway. The reason for 25 minutes: a `bin/check --fast` on a host shared by three builders took 7 to 9 minutes, and checks past the CLI's 10-minute default tool limit went to the background and were polled (#1140, [Budget and model planner](../design/05-architecture/06-budget-and-model-planner.md));
   - `<gates at once>` is `Domain/GatesAtOnce::loweringTheDefaultOfAJobWith()` for the job's CPUs and memory: the count only when there is more than one build slot and the count is below `Domain/GatesByDefault::$count`, so the script sets `INTAKT_GATE_SLOTS` to it; empty otherwise (a single slot, or a count equal to or above that default), so the script leaves `INTAKT_GATE_SLOTS` as the job's environment has it (unset in Intakt's own images, see step 3 of [In the container](#in-the-container)), and only then does `bin/check` size its gates at once from the job's cgroup ([Quality gates](quality-gates.md)). The count only ever lowers, because `bin/check` takes `INTAKT_GATE_SLOTS` as it is: a higher count would admit more gates than the job's memory holds. `GatesByDefault` states the check's own rule for a job (`GateSlots::byDefault()`; the application cannot load the gates' code, so `GatesByDefaultTest` compares the two over a grid of limits): the usable processors are the job's CPUs rounded up, at most the host's processors; the test workers are one per usable processor, at most 4; the default is `max(1, min(usable processors, intdiv(memory, 2 GiB) - test workers + 1))`. With today's limits (2 CPUs, 4 GiB) the two test workers hold both memory shares and the default is 1, below `GatesAtOnce::FEWEST`, so the argument is always empty and `intakt.build.slots` does not change a build job's check: the job's CPU limit is what keeps builders on one host apart. A job of 8 CPUs and 32 GiB has a default of 8, which 3 slots on 12 processors would lower to 4. The count (#2587) is `GatesAtOnce::$count`, `min(8, max(2, intdiv(processors, slots)))` (`GatesAtOnce::MOST`, the 8 gates at once of the measured checks; `GatesAtOnce::FEWEST`, so one gate still runs beside the `tests` gate), where fewer than one processor or slot is an `InvalidArgumentException`. The container builds it through the factory `Infrastructure/HostProcessors::gatesAtOnce()` when the service is first needed, not when the container is compiled: the processors are the host's online processors (`posix_sysconf(POSIX_SC_NPROCESSORS_ONLN)`, at least 1), the slots the parameter `intakt.build.slots` (`BuildServices::SLOTS`, 1 in `config/services.yaml`), because there is no build lane yet to count them. The reason, measured on the build loop that developed Intakt with builders that had no per-job limits: three builders on 12 processors, each running 8 gates at once, loaded the host to 22 to 28 and took 7 to 9 minutes for one `bin/check --fast` ([Budget and model planner](../design/05-architecture/06-budget-and-model-planner.md));
   - an allowlist of `api.anthropic.com` and the gate's registry hosts (`Gate::registryHosts()`), because the builder installs the project's dependencies itself (only a [check](check-job.md#in-short) reuses a saved install);
   - the limits 4 GiB of memory, 2 CPUs and 3600 seconds (the allowance plus 600 seconds for the script's cleanup and bundle, so the runner's kill, which keeps no output, never comes first), and the job id `build-<first 40 hex digits of the SHA-256 of the length-prefixed project and the branch>`, so a second build of the same branch of the same project while one runs is refused as already running.
5. **Outcome:** read from the job's output directory only (`JobResult::$output`). The container's exit code says one thing only: `RunBuildJob::OUTPUT_NOT_CLEARED` (3), the script's code for files the builder planted in the output (`build.log` included), or a failed bundle left, that it could not remove; the builder cannot set the script's exit code. `BuildJobOutcome` holds a `BuildVerdict` (a backed enum whose `reason()` is fixed text), the bundle's bytes, the pull request text, `build.log` and the `BuildQuestion` or null:
   - `MemoryKilled` or `TimedOut` when the engine stopped the job, whatever its output says, with no bundle and no text;
   - `NoResult` when the runner refuses the output (`JobOutputRefused`: a folder that could not be listed, a link, a folder in it, a file that could not be read, too many files, more than 16 MiB in all, the bundle included), with the orchestrator's fixed line `no result: the runner refused the job's output: it could not be listed, or an entry in it is not a plain file or could not be read, or it passed the limit on entries or bytes` as its log, one line for every case because the exception does not say which it was (the `JobOutputRefused` message is not used, because it quotes a name the builder chose, which could hold a line break such as U+2028), or when the job exited with `OUTPUT_NOT_CLEARED`, whatever its output says, with `no result: the build script could not clear the job's output` appended on a line of its own to whatever `build.log` it could read;
   - `Asked` with the question when `question.json` (`RunBuildJob::QUESTION`) is there and passes the [question rule](#the-question), with no bundle and no text, whatever else the output holds; `QuestionRefused` when it breaks the rule, with no question and `question refused: <QuestionRefused message>` appended to the log;
   - otherwise `NoCommits` without `handback.bundle`, `NoPullRequestText` without `pull-request.md`, otherwise `Built`.

Both the bundle and the text are untrusted: the [hand-back check](hand-back.md) reads the bundle before anything trusts it ([`intakt:build:task`](build-task.md) runs it right after the job), and the checks of the text are plan tasks T50 and T51.

## In the container

`docker/job/build.sh` (POSIX `sh`, with `git`, `setsid`, `sleep`, `sha256sum`, `timeout`, `readlink`, `find` and `claude`) runs as the job's command after the [start check](job-containers.md#start-check):

1. The branch must pass `git check-ref-format --branch` with the name itself as the answer.
2. `git init --initial-branch=<branch> --object-format=<the build clone's>` in `$TMPDIR/clone` (`/work/clone`), then `git fetch --no-tags --no-write-fetch-head --update-head-ok` of the build clone's `refs/heads/*` and `refs/source/*`, and `git checkout --force <branch>`. The clone therefore holds what the build clone holds and no remote. Its git identity is `Intakt builder <builder@intakt.invalid>` (builder's choice), because the job has no git configuration and the orchestrator signs the commits before a push. A step that fails ends the job with no bundle and no text, and the CLI does not run. The script then tries the image's `timeout` (looked up only in the fixed system folders `/usr/local/sbin`, `/usr/local/bin`, `/usr/sbin`, `/usr/bin`, `/sbin` and `/bin`, never through the `PATH` the job starts with) in the form step 6 uses, on a command that does nothing (`timeout -k 5 30 true`): when it fails (no `timeout` in the image, one the script refuses, or one that rejects `-k`), the script writes `the image's timeout cannot bound the bundle step` to `build.log` and exits with 1, and the CLI does not run either. Found only in step 6, such a `timeout` would spend the session and then leave its commits without a bundle; the script never bundles without the limit instead. The script refuses a `timeout` when any part of the way to its file is, or lies in, a folder the builder can write: the clone, `$TMPDIR`, `$HOME` or the output folder, each as it is named and as its real path. `system_command()` walks that way one name at a time from the path found, as the kernel resolves it, reads each link with `readlink` (at most 40 links, the kernel's own bound) and checks every hop: the path found, each link of a chain, each folder on a link's target that is itself a link, and the file at the end, which must be an executable regular file. So a link in a system folder that reaches its file through a link in the work area is refused although both ends are outside it, and so is a link into the output folder. The script then calls the path found and not the file at the end, because a binary that serves several commands (such as BusyBox) picks the command by the name it is called with. It resolves `git` for step 6 the same way; when that fails, it writes `the image's git is not in its system folders` to `build.log` and exits with 1 before the CLI runs.
3. `claude -p --model <model> --max-turns <max turns> --output-format json --dangerously-skip-permissions --settings <time limit settings>` in the clone, in a session of its own (`setsid`), the prompt file on its standard input, with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, because the allowlist lets only the vendor's API through, and, when `<gates at once>` is not empty, with `INTAKT_GATE_SLOTS=<gates at once>`, the variable the builder's `bin/check` reads for the number of gates it runs at once ([Quality gates](quality-gates.md)); the job spec carries no environment, so the script exports it. An empty argument leaves the variable as the script inherited it: unset, unless the job's environment (the job image) already sets `INTAKT_GATE_SLOTS`, which `bin/check` then reads; a given count replaces an inherited value. It also exports `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`, both `<tool time limit seconds>` times 1000, replacing any inherited value, so one command of the session runs up to that limit by default, and passes the same two values as `<time limit settings>`, the JSON object `{"env":{"BASH_DEFAULT_TIMEOUT_MS":"<ms>","BASH_MAX_TIMEOUT_MS":"<ms>"}}` with both values as strings. The exports alone are not the last word, because Claude Code applies the `env` of the clone's `.claude/settings.json` and `.claude/settings.local.json` after it starts; command-line settings rank above those files, so the builder cannot ask for more than the limit. The script does not pass `--setting-sources`, so the clone's other project settings still apply. The container is the sandbox, so the CLI asks for no permission. Its output and errors go to `build.log`, followed by `claude exited with <status>`. A watchdog in a session of its own sleeps for the allowance and then kills the CLI's session (`SIGKILL` to its process group), never the script. When the CLI ends first, the script ends the watchdog (`SIGKILL` to its process group). When the CLI ended by `SIGKILL` (status 137), that may be the watchdog's own cut or a kill from elsewhere (such as the out-of-memory killer), so the script sends the watchdog `SIGTERM` instead and waits for it, without waiting out the allowance: before its kill, the watchdog answers `SIGTERM` by killing its own process group (its sleep and itself), which is no cut; it ignores `SIGTERM` from just before it sends its kill, so a watchdog that has cut still reports the cut. The watchdog sends its kill only while the session's leader is alive and not a zombie (`kill -0` and the `State:` line of `/proc/<pid>/status`, which the script reads with shell builtins; not `/proc/<pid>/stat`, where a name the builder gives the leader with a line break could put a false state on the first line; a leader in state `Z` whose `Threads:` line shows more than 1 is a leader thread that ended while another thread of the process still runs, so it is cut), so a leader killed from elsewhere and not yet reaped, whose surviving child the watchdog could otherwise kill before the script's `SIGTERM` arrives, is no cut. The watchdog reports a cut by its exit status (0 only when its kill reached the session), not by a file the builder could write or block, and the script then logs `claude cut after <n> seconds, its commits are kept`. The CLI also ends by itself at the turn limit. Either way the steps below run, so the bundle holds what was committed before the cut.
4. After the CLI exits, the script sets `PATH` to the fixed system folders of step 2, so every command it runs from then on comes from there and none from a folder of the starting `PATH` (a relative entry, or one in `$HOME`) where the builder could have planted one. No process of the builder is left running, because one could write into the output after the next step. In the container the script is the first process (PID 1) of the job's own process namespace, so it sends `SIGKILL` to every other process there (`kill -s KILL -1`), also one that left the CLI's session. Run as any other process, as in the tests, it kills the CLI's session only (`kill -s KILL -- -<session>`), because the user's other processes cannot be told apart from the builder's. Then the script gives its user read, write and search permission on the output directory again (`chmod u+rwx`, which the builder can take away), and removes a `build.log` that is no longer a regular file the script may write (a named pipe would make the append wait, a link would write elsewhere, a file without write permission would fail the append), so the log starts again without the CLI's output. A folder there first gets read, write and search permission back for its user on itself and on every folder in it (`find <folder> -type d -exec chmod u+rwx`, each folder before `find` reads it), because a recursive removal cannot empty a folder it may not read. Only folders are changed: a file in it may be a hard link to a file elsewhere in the output, whose mode `chmod` would change too, and `find` follows no link, so a link there is removed without being followed. Directly after the removal the script checks the log's place (`[ -e ]` or `[ -L ]`, the second for a link to nothing), whatever status the removal ended with: when anything still stands there, it writes `the build log could not be started again` to its standard error and exits with 3 before any append, so a pipe that survived cannot make the append wait and a link that survived is not written through. Then it appends `claude exited with <status>` to `build.log`. When that append fails (the log cannot be created), the script writes the same line and exits with 3 too, since a failed redirection would skip every later command, the bundle's too. That line is for whoever reads the container's log: the runner keeps only the [start check](job-containers.md#start-check)'s lines of a job's standard error, because the builder can write there too. When a folder, a pipe or a link still stands in the log's place, the runner refuses the output (`JobOutputRefused`), and `RunBuildJob` ends the build as `NoResult` with a fixed reason of the orchestrator's own as its log, `no result: the runner refused the job's output: it could not be listed, or an entry in it is not a plain file or could not be read, or it passed the limit on entries or bytes`, which names no file, so the caller learns what stopped the bundle from the orchestrator and not from the builder. From here on git reads no global or system settings (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`): the builder could have written them, for example an include that waits on a pipe. Git does not search for its repository either: `GIT_DIR=.git` and `GIT_WORK_TREE=.` name the clone, relative to the clone folder the script is in, because without them git searches upward from a `.git` it cannot use and would find a repository the builder made in the work area above the clone (`git init "$TMPDIR"`). Nor does git read the clone's own settings as the builder left them: before any further git command the script requires `.git` to be a folder and not a link (a link would take the removal and the new files outside the clone), requires `.git/objects` and `.git/objects/info` not to be links either (and gives its user read, write and search permission on them when they are folders), removes `.git/config`, `.git/commondir` (a file that would point git at another folder's settings), `.git/objects/info/alternates` and `.git/objects/info/http-alternates` (files that tell git where else to read objects, for example a named pipe that holds the bundle, or objects the builder moved out of the clone, which then leave no bundle) and `.git/HEAD`, writes `.git/HEAD` again as `ref: refs/heads/<branch>` (so a removed or unreadable HEAD does not make `.git` no repository), and writes a minimal `.git/config` itself, with `printf` and not with git, which would read the old one: `[core]` with `repositoryformatversion = 0` and `bare = false`, or, for a build clone that is not SHA-1, `repositoryformatversion = 1` and `[extensions]` `objectformat = <format>`, the format read in step 2, a shell variable the builder cannot change. It first gives its user read, write and search permission on `.git` again (not on a link, which `chmod` would follow). When the settings cannot be replaced, the script writes `no bundle is handed back: the clone's git settings could not be replaced` to `build.log`, runs no git command and, after step 5, exits with 0 without a bundle (so the job ends as `NoCommits`, or `Asked` with a question) instead of holding its slot until it is timed out.
5. Any `pull-request.md`, `handback.bundle` or `question.json` already in the output directory is removed: the builder can write there too, so only the files the script writes next are handed back. The builder can also take permissions away, so the script first gives its user read, write and search permission on a planted folder and every folder in it (the output directory itself got them back in step 4), the same way as for a folder at `build.log` in step 4 (folders only, never through a link). When any of them is still there afterwards, the script writes `the output folder could not be cleared` to `build.log` and exits with 3 without writing anything else. `PR.md` in the clone's root, when it is a regular file and not a link, is copied to `pull-request.md`, and `QUESTION.json` the same way to `question.json`, but only when its bytes differ from the ones the checkout held when the session started. The script reads them after the checkout of step 2 and before it starts the CLI in step 3 (`sha256sum < QUESTION.json` of a regular file, empty when there is none or it is a link) into a shell variable, which the builder cannot write, and compares the same command's answer after the session with it. The digest is `sha256sum`'s and not git's, because `git hash-object` in the clone follows the clone's git settings, which the builder can write: a session that switches the clone's object format (`extensions.objectFormat`) would give the same bytes another hash, and a clean filter named there would run after the session. `sha256sum` reads only the file's bytes, so no git setting of the clone reaches the comparison. A hash that could not be taken is never a change: when the command fails or prints nothing before the session (while the file is there), the question is not handed back and `build.log` gets `QUESTION.json is not handed back: it could not be hashed before the session`, also when the builder removed the file since; when it fails or prints nothing after the session, the question is not handed back either and the line ends in `after the session`. So a question the branch already held and the builder left untouched is not handed back, also when the checkout converts its line endings (`eol=crlf` in `.gitattributes`) and so holds other bytes than the commit, and also when the builder broke or changed the clone's git settings (an invalid line in `.git/config`; another object format).
6. `git bundle create <output>/handback.bundle refs/heads/<branch> ^<the branch's commit before the CLI ran>`: the task's branch by its full name, whatever the builder checked out, with the starting commit as the prerequisite. Git refuses an empty bundle, so a build without a new commit leaves none. The command runs as the `git` step 2 resolved, under the `timeout` step 2 resolved, as `timeout -k 5 30` (coreutils; the short option, because a project image may carry a `timeout` without long ones): repository state the builder left that is not a setting, such as a named pipe at `.git/refs/heads/<branch>`, `.git/packed-refs` or `.git/shallow`, could make git wait until the job is timed out and so hold its slot, while a bundle of the branch's new commits takes seconds. A git still running after 30 seconds gets `SIGTERM`, and `SIGKILL` 5 seconds later; the script reads status 124 (`timeout`'s own for a cut), 137 (the kill) and 143 (a `timeout` that reports the status of the git its `SIGTERM` ended) as a cut, then writes `no bundle is handed back: git bundle create was cut after 30 seconds` to `build.log` and treats the cut as a failed bundle. When git fails or is cut, whatever it left at `handback.bundle` and `handback.bundle.lock` (the lock file a killed git leaves) is removed (`rm -f`); when `handback.bundle` is still there, the script writes `the output folder could not be cleared` to `build.log` and exits with 3.

Otherwise the script exits with 0, whatever the CLI's status (which `build.log` holds), so the CLI can never end the job with the code that means an output not cleared. It exits with 1 when the clone cannot be prepared or the image's `timeout` cannot bound the bundle step or its `git` is not in the system folders (step 2), all before the CLI runs. `HOME` and `TMPDIR` are the job's own tmpfs work area.

## The question

The [builder prompt](builder-prompt.md) tells the builder to write `QUESTION.json` (`Domain/BuildQuestion::FILE`) in the checkout root, and no `PR.md`, when it needs a decision the task does not cover. The text is untrusted, so `BuildQuestion::fromHandedBack(string)` is the refusal rule, plain code that throws `Domain/QuestionRefused`, named after the broken rule, with one fixed message per rule: more than `BuildQuestion::MAX_BYTES` (8192) bytes (`the question is longer than 8192 bytes`); not a JSON object, or more than 7 arrays or objects nested in one another counting the object itself, also under an ignored key (`json_decode` with a depth of 8, which counts each array or object as one level and one more for its contents) (`the question is not a JSON object`; decoded to objects, not associative arrays, so a JSON object such as `{"0":"a"}` never passes for a list); `question` missing, not a text or blank after trimming (`the question text is empty`); `choices` missing, empty, not a list (`the question has no list of choices`); a choice that is not a text or blank (`a choice is not a non-empty text`); two choices equal after trimming (`two choices are the same`, so the reader can always tell which choice the recommendation names); `recommendation` not exactly one of the trimmed choices (`the recommendation is not one of the choices`). An accepted question holds the trimmed `question`, the `choices` (a non-empty list of texts) and the `recommendation`. Other keys are ignored, also one that starts with an escaped NUL (`"\u0000..."`), which PHP decodes no object with: before decoding, `BuildQuestion` gives each such key the first character U+0001 instead, which leaves it unknown; it matches every JSON string whole, so a value is never changed. `BuildTask` stores the question a build job hands back through `ParkedTasks::park()`; nothing posts it yet. `Build/Contract/BuildStepOutcome` has the case `Asked` (`asked`) for it, written only by `ParkedTasks::park()`, which stores the question as a parked-task record (see [Build task](build-task.md#the-parked-task-record)) and which `BuildTask` calls from the build job step when the outcome carries an accepted question (see [Build task](build-task.md#the-steps)); the status schema comes with part 3 of #1696.

## The console door

The command reads `<task>` as the task's text and each `--decision` as one decision, in order; it runs first builds only (a rework's act list and CI excerpt have no console form). A `Built` outcome writes the bundle to `<bundle>`, prints `bundle <bundle>`, `pull request text:` and the text (escaped for the console), and exits with 0. An `Asked` outcome prints `question: <question>`, one `choice: <choice>` line per choice and `recommendation: <recommendation>` (in each, every character of `\p{C}` (controls, format characters such as a zero-width space, unassigned and private-use code points), `\p{Zl}`, `\p{Zp}`, every `\p{Zs}` space other than U+0020 and every code point of Unicode's `Default_Ignorable_Code_Point` property (`RunBuildJobCommand::DEFAULT_IGNORABLE`, its ranges from `DerivedCoreProperties.txt` of Unicode 16.0, because PCRE has no class for it; among them U+034F, the variation selectors and the Hangul fillers) is printed as `\u{<code point in hex>}` and a backslash as two, so the builder's text cannot forge a line and two choices that differ only in such a character print differently (visible lookalike letters, such as Latin and Cyrillic "a", print as they are); then the text is escaped for the console), writes no bundle and exits with 0. Any other verdict, `QuestionRefused` included, prints the last 40 lines of `build.log` and `failed: <reason>` in an error block, writes no bundle and exits with 1. An unknown tier (`TierNotKnown`), a clone that is no folder, a task file that cannot be read, a tier that cannot be resolved or is not on `claude_code`, a job the runner refuses (`JobRefused`) and a `ReportableFailure` (for example `DockerEngineFailed` without a Docker socket) print their message and exit with 1. Any other exception, an `InvalidArgumentException` included, is left to the console as a programming error.
