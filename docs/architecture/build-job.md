# Build job

Plan task T49, the job itself (#1709; design: [overview](../design/05-architecture/01-overview.md), [threat model](../design/05-architecture/14-threat-model.md#builder)). A build job runs the Claude Code CLI on the [builder prompt](builder-prompt.md) in a [job container](job-containers.md) of its own, and returns a git bundle and the pull request text. The session is bounded by a turn limit and an allowance, and a cut session keeps its commits (#1710); the allowance is a fixed constant until T60 sizes it per task. Not built yet: the structured question that parks a task; the builder's own check tool in the job; reading usage from the session log; the account credential in the job (the job holds none yet, so a real build cannot sign in to the vendor).

`php bin/console intakt:build:run <project> <clone> <branch> <task> <image> <bundle> [--tier=<tier>] [--decision=<text> ...]` (`RunBuildJobCommand`) calls `UseCase/RunBuildJob/RunBuildJob::run(BuildJob)` (marked `#[NoDiscard]`) in `Core/Build`. [`intakt:build:task`](build-task.md) calls it too, as its build job step, with the tier the routing rules choose. Nothing calls it from another module yet: the build lane (T56) will.

## The steps

1. **Model:** `TierResolver::resolve(<project>, <tier>)` picks the model from the project's tier map ([Capability tiers](capability-tiers.md)); the tier is the caller's choice (`--tier`, `standard` by default, for `intakt:build:run`; the routing rules' choice for `intakt:build:task`). A tier on any provider but `claude_code` is `BuilderNotOnClaudeCode`, because the job runs the Claude Code CLI and holds no vendor API key; a tier that cannot be resolved (`TierResolutionFailure`) is thrown as it is. No job starts in either case.
2. **Clone:** `<clone>` is a [build clone](build-clone.md) made with `intakt:build:clone` (resolved with `realpath`); a path that is no folder is an `InvalidArgumentException`. The job gets the build clone, never the mirror, so it sees main, the task's branch and a verified source and no other branch.
3. **Prompt:** `BuilderPrompt::textFor()` of the `BuildBrief`, written to a file of its own, `var/prompts/prompt-<random>.md` (mode 0600), which is removed after the job, also when the job throws.
4. **Job** (`JobRunner::run()`):
   - the image given, as the project's job image ([Job images](job-images.md));
   - two read-only inputs, the build clone at `/input/clone` and the prompt file at `/input/prompt.md`;
   - the command `/bin/sh -c <docker/job/build.sh> intakt-build /input/clone /input/prompt.md <branch> <model> <max turns> <allowance seconds> <gates at once> <tool time limit seconds>` (100 turns and 3000 seconds, builder's choice until T60), the script's text read from the project folder for each job;
   - `<tool time limit seconds>` is the parameter `intakt.build.tool_time_limit_seconds` (`BuildServices::TOOL_TIME_LIMIT`, 1500 in `config/services.yaml`), injected into `RunBuildJob` with `#[Autowire(param: ...)]`. The constructor refuses a value below 1 or not below the allowance (3000) with an `InvalidArgumentException`, because a tool call that outlives the session is cut with it anyway. The reason for 25 minutes: a `bin/check --fast` on a host shared by three builders took 7 to 9 minutes, and checks past the CLI's 10-minute default tool limit went to the background and were polled (#1140, [Budget and model planner](../design/05-architecture/06-budget-and-model-planner.md));
   - `<gates at once>` is `Domain/GatesAtOnce::loweringTheDefaultOfAJobWith()` for the job's CPUs and memory: the count only when there is more than one build slot and the count is below `Domain/GatesByDefault::$count`, so the script sets `INTAKT_GATE_SLOTS` to it; empty otherwise (a single slot, or a count equal to or above that default), so the script leaves `INTAKT_GATE_SLOTS` as the job's environment has it (unset in Intakt's own images, see step 3 of [In the container](#in-the-container)), and only then does `bin/check` size its gates at once from the job's cgroup ([Quality gates](quality-gates.md)). The count only ever lowers, because `bin/check` takes `INTAKT_GATE_SLOTS` as it is: a higher count would admit more gates than the job's memory holds. `GatesByDefault` states the check's own rule for a job (`GateSlots::byDefault()`; the application cannot load the gates' code, so `GatesByDefaultTest` compares the two over a grid of limits): the usable processors are the job's CPUs rounded up, at most the host's processors; the test workers are one per usable processor, at most 4; the default is `max(1, min(usable processors, intdiv(memory, 2 GiB) - test workers + 1))`. With today's limits (2 CPUs, 4 GiB) the two test workers hold both memory shares and the default is 1, below `GatesAtOnce::FEWEST`, so the argument is always empty and `intakt.build.slots` does not change a build job's check: the job's CPU limit is what keeps builders on one host apart. A job of 8 CPUs and 32 GiB has a default of 8, which 3 slots on 12 processors would lower to 4. The count (#2587) is `GatesAtOnce::$count`, `min(8, max(2, intdiv(processors, slots)))` (`GatesAtOnce::MOST`, the 8 gates at once of the measured checks; `GatesAtOnce::FEWEST`, so one gate still runs beside the `tests` gate), where fewer than one processor or slot is an `InvalidArgumentException`. The container builds it through the factory `Infrastructure/HostProcessors::gatesAtOnce()` when the service is first needed, not when the container is compiled: the processors are the host's online processors (`posix_sysconf(POSIX_SC_NPROCESSORS_ONLN)`, at least 1), the slots the parameter `intakt.build.slots` (`BuildServices::SLOTS`, 1 in `config/services.yaml`), because there is no build lane yet to count them. The reason, measured on the existing loop with builders that had no per-job limits: three builders on 12 processors, each running 8 gates at once, loaded the host to 22 to 28 and took 7 to 9 minutes for one `bin/check --fast` ([Budget and model planner](../design/05-architecture/06-budget-and-model-planner.md));
   - an allowlist of `api.anthropic.com` and the gate's registry hosts (`Gate::registryHosts()`), because the builder installs the project's dependencies;
   - the limits 4 GiB of memory, 2 CPUs and 3600 seconds (the allowance plus 600 seconds for the script's cleanup and bundle, so the runner's kill, which keeps no output, never comes first), and the job id `build-<first 40 hex digits of the SHA-256 of the length-prefixed project and the branch>`, so a second build of the same branch of the same project while one runs is refused as already running.
5. **Outcome:** read from the job's output directory only (`JobResult::$output`). The container's exit code says one thing only: `RunBuildJob::OUTPUT_NOT_CLEARED` (3), the script's code for files the builder planted in the output, or a failed bundle left, that it could not remove; the builder cannot set the script's exit code. `BuildJobOutcome` holds a `BuildVerdict` (a backed enum whose `reason()` is fixed text), the bundle's bytes, the pull request text and `build.log`:
   - `MemoryKilled` or `TimedOut` when the engine stopped the job, whatever its output says, with no bundle and no text;
   - `NoResult` when the runner refuses the output (`JobOutputRefused`: a link, too many files, more than 16 MiB in all, the bundle included), or when the job exited with `OUTPUT_NOT_CLEARED`, whatever its output says;
   - `NoCommits` without `handback.bundle`, `NoPullRequestText` without `pull-request.md`, otherwise `Built`.

Both the bundle and the text are untrusted: the [hand-back check](hand-back.md) reads the bundle before anything trusts it ([`intakt:build:task`](build-task.md) runs it right after the job), and the checks of the text are plan tasks T50 and T51.

## In the container

`docker/job/build.sh` (POSIX `sh`, with `git`, `setsid`, `sleep` and `claude`) runs as the job's command after the [start check](job-containers.md#start-check):

1. The branch must pass `git check-ref-format --branch` with the name itself as the answer.
2. `git init --initial-branch=<branch> --object-format=<the build clone's>` in `$TMPDIR/clone` (`/work/clone`), then `git fetch --no-tags --no-write-fetch-head --update-head-ok` of the build clone's `refs/heads/*` and `refs/source/*`, and `git checkout --force <branch>`. The clone therefore holds what the build clone holds and no remote. Its git identity is `Intakt builder <builder@intakt.invalid>` (builder's choice), because the job has no git configuration and the orchestrator signs the commits before a push. A step that fails ends the job with no bundle and no text, and the CLI does not run.
3. `claude -p --model <model> --max-turns <max turns> --output-format json --dangerously-skip-permissions` in the clone, in a session of its own (`setsid`), the prompt file on its standard input, with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, because the allowlist lets only the vendor's API through, and, when `<gates at once>` is not empty, with `INTAKT_GATE_SLOTS=<gates at once>`, the variable the builder's `bin/check` reads for the number of gates it runs at once ([Quality gates](quality-gates.md)); the job spec carries no environment, so the script exports it. An empty argument leaves the variable as the script inherited it: unset, unless the job's environment (the job image) already sets `INTAKT_GATE_SLOTS`, which `bin/check` then reads; a given count replaces an inherited value. It also exports `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`, both `<tool time limit seconds>` times 1000, replacing any inherited value, so one command of the session runs up to that limit by default and cannot ask for more. The container is the sandbox, so the CLI asks for no permission. Its output and errors go to `build.log`, followed by `claude exited with <status>`. A watchdog in a session of its own sleeps for the allowance and then kills the CLI's session (`SIGKILL` to its process group), never the script. When the CLI ends first, the script ends the watchdog, except when the CLI ended by `SIGKILL` (status 137): that may be the watchdog's own cut, so the script waits for the watchdog, which ends at the allowance at the latest. The watchdog reports a cut by its exit status (0 only when its kill reached the session), not by a file the builder could write or block, and the script then logs `claude cut after <n> seconds, its commits are kept`. The CLI also ends by itself at the turn limit. Either way the steps below run, so the bundle holds what was committed before the cut.
4. After the CLI exits, no process of the builder is left running, because one could write into the output after the next step. In the container the script is the first process (PID 1) of the job's own process namespace, so it sends `SIGKILL` to every other process there (`kill -s KILL -1`), also one that left the CLI's session. Run as any other process, as in the tests, it kills the CLI's session only (`kill -s KILL -- -<session>`), because the user's other processes cannot be told apart from the builder's. From here on git reads no global or system settings (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`): the builder could have written them, for example an include that waits on a pipe.
5. Any `pull-request.md` or `handback.bundle` already in the output directory is removed: the builder can write there too, so only the files the script writes next are handed back. The builder can also take permissions away, so the script first gives its user read, write and search permission on the output directory again, and on a planted folder and everything in it (`chmod -R u+rwx`, never on a link, which `chmod` would follow). When either file is still there afterwards, the script writes `the output folder could not be cleared` to `build.log` and exits with 3 without writing anything else. `PR.md` in the clone's root, when it is a regular file and not a link, is copied to `pull-request.md`.
6. `git bundle create <output>/handback.bundle refs/heads/<branch> ^<the branch's commit before the CLI ran>`: the task's branch by its full name, whatever the builder checked out, with the starting commit as the prerequisite. Git refuses an empty bundle, so a build without a new commit leaves none. When git fails, whatever it left at `handback.bundle` is removed (`rm -f`); when that file is still there, the script writes `the output folder could not be cleared` to `build.log` and exits with 3.

Otherwise the script exits with 0, whatever the CLI's status (which `build.log` holds), so the CLI can never end the job with the code that means an output not cleared. It exits with 1 when the clone cannot be prepared. `HOME` and `TMPDIR` are the job's own tmpfs work area.

## The console door

The command reads `<task>` as the task's text and each `--decision` as one decision, in order; it runs first builds only (a rework's act list and CI excerpt have no console form). A `Built` outcome writes the bundle to `<bundle>`, prints `bundle <bundle>`, `pull request text:` and the text (escaped for the console), and exits with 0. Any other verdict prints the last 40 lines of `build.log` and `failed: <reason>` in an error block, writes no bundle and exits with 1. An unknown tier, a clone that is no folder, a task file that cannot be read, a tier that cannot be resolved or is not on `claude_code`, and a `ReportableFailure` (for example `DockerEngineFailed` without a Docker socket) print their message and exit with 1.

## Tests

`tests/Core/Build/BuildScriptTest.php` runs the real `docker/job/build.sh` with `sh -c` on a temporary build clone, with a scripted `claude` on the path that commits and writes `PR.md`, so a scripted CLI returns a bundle and the text, and a scripted CLI that commits and then sleeps past a 3 second allowance still returns a bundle of its commit, also when it put a folder where a cut marker file would go, and a scripted CLI sees the gates at once it was given as `INTAKT_GATE_SLOTS`, and none when it was given an empty argument (or the value its environment already set, which a given count replaces), and a scripted CLI sees a tool time limit of 1800 seconds as `1800000` in both `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS`, also when its environment set another value; `tests/Core/Build/Domain/GatesAtOnceTest.php` checks the count (12 processors with 1, 2 and 3 slots: 8, 6 and 4; 2 processors with 3 slots: the floor of 2; 18 processors with 2 slots: the ceiling of 8; no processor or no slot refused) and what is handed over (4 and 6 for 3 and 2 slots on 12 processors with a job of 8 CPUs and 32 GiB; nothing for 1 slot, for a job of 2 CPUs and 4 GiB with any slots, for a count equal to the job's default or above what its memory holds), `GatesByDefaultTest` the job's default and that it equals the check's own `GateSlots::byDefault()` over a grid of processors, CPUs and memory, `HostProcessorsTest` the factory on the host; `RunBuildJobTest` (an empty argument with 1 slot on 12 processors, and with 2 or 3 slots on 12 processors and 3 slots on 2 processors, because the job's limits give a default of 1; the configured tool time limit as the last argument, with 1, 1800 and 2999 passed and 0, -1, 3000 and 3001 refused) and `RunBuildJobCommandTest` run the use case and the command with a stubbed `JobRunner` and `TierResolver`, because the build sandbox has no Docker daemon. No build job has run against a live engine yet.
