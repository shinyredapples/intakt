## Dashboard

### In short

The dashboard is the web interface of Intakt: server-rendered Twig pages under `src/Core/Dashboard/`. It shows the board, the review list and each review, Waiting on you, a task's build steps, Trends, search, the setup wizard, Add a project and a demo. Its pages read what happened from the ledger. It uses other modules only through their `Contract/` classes and reads no repository. A few buttons act: start a review, stop one reviewer, stop a running round. Running work reaches an open page without a reload through the Mercure hub, described in [Live updates](live-updates.md).

Worth knowing:

- There is no login, by design. Every dashboard route refuses a request unless its host is `localhost`, `127.0.0.1` or `[::1]` on the `DASHBOARD_PORT` (`RefuseForeignHost`).
- Every form that acts posts a CSRF token, which `FormPress` checks.
- `/status` is not a page: it answers the status JSON ([Status read model](status.md)).
- `/components` shows every shared component in the light and the dark theme.

The rest of this page is the detailed reference.

Plan task T20, parts 1 to 3 (design: [Dashboard](../design/05-architecture/13-dashboard.md)). `src/Core/Dashboard/` is a server-rendered Twig dashboard (`symfony/twig-bundle`, `templates/dashboard/`, `config/packages/twig.yaml`) that reads the ledger, through `Ledger::readInOrder()` of the Ledger contract (`readOfKind()` and `readMentioning()` where one review or one kind is enough, and `readOfKindAbout()` with `readOfKindWithoutSubject()` for a round's reviewer starts) and reads its payloads with the contract's `LedgerPayloads`, and, for the forge budget on `/reviews`, `Plugin/Forge/Contract/ForgeBudgets` (below); other modules it uses only through their `Contract/`: Review (`StartReview`, `ChangeSource` for the start button, `ChangeDecision` and `FailureInWords` for a round's outcome and a failed reviewer's words, and the round ledger's payload classes with their `Ai` and `ReviewerForLoop` enums), the vendor plugin's usage payload classes and, for the setup wizard (below), Ai (`TierResolver`, `EnabledAccounts`, `KeptProviderKeys`, `AiServices::DISABLED_PROVIDERS`), Review (`Panels`, and `SampleChange` with `StartReview` for the first-review step), Watcher (`FailingMains`, for the check step) and it reads no repository.

- `Infrastructure/RoundPayloads` reads the round ledger's rows into the Review module's payload classes in its `Contract/` (`ReviewStarted`, `ReviewerStarted`, `VerdictReceived`, `ReviewerFailed`, `ReviewerBlocked`, `ReviewerStopped`, `CatchUpOwed`, `JudgeDone` with its `JudgeDoneFinding` list, `ReviewerFindingsRecorded`) and the `usage_recorded` rows into the vendor plugin's `Contract/` classes (`UsageStarted`, and `UsageSettled` or `UsageUnsettled` as the row's `phase` says), through `Ledger\Contract\LedgerPayloads::of()` and the `stored` serializer. A row that does not deserialize (not JSON, a key missing, a value of another type or outside its enum, such as an unknown `tier` or `decision`, or a token count that is not a number) is skipped whole, so one bad row does not take the pages down (the skipping rule itself, with `entriesOf()` and the defaults below, is tested in `tests/Core/Ledger/Contract/LedgerPayloadsTest.php`). Two keys are read apart, as the array reader did: a `verdict_received` whose `mode` is unknown or not a string is read again without it as `Live` (`LedgerPayloads::ofWithout()`, which leaves a key unread through `AbstractNormalizer::IGNORED_ATTRIBUTES`), so its reviewer still shows as answered; and `judge_done` is read for its marks without `findings` and `dropped`, whose entries `LedgerPayloads::entriesOf()` deserializes one by one into `JudgeDoneFinding`, leaving out an unreadable entry (no `text`, an unknown `severity`, a number too large to encode again) while its id keeps the judge's call, so the round stays judged. A `review_started` row's `replay_factor` (written only by a demo replay) is read on its own into `Infrastructure/ReplayedStart`, so a factor that does not read leaves the round readable without one (see Replay mark below). Keys that rows written before them lack take the value the pages always showed for such a row (`LedgerPayloads::of()` takes them as a `PayloadDefaults`, named by the payload's constructor parameters (a positional value throws `InvalidArgumentException`), and passes them as `AbstractNormalizer::DEFAULT_CONSTRUCTOR_ARGUMENTS`, which apply only to an absent key): a `review_started` without `change` or `task` reads them as empty and one without `number`, or with a null `number`, has no number (it is read into `Infrastructure/UnnumberedStart`, whose `number` is optional, so a `number` that is no integer still skips the row), a `review_started` without `quorum` has none (`ReviewStarted::$quorum` is null, while an unknown `quorum` value skips the row), a `reviewer_started` without `model` has none (`ReviewerStarted::$model` is null), a `verdict_received` without `mode` is `Live`, and a `judge_done` without `findings` (or with `findings` that is not a list) has no recorded finding text. A `findings` entry without `merged` (every one written before act entries were recorded) reads with none, through the default of `JudgeDoneFinding::$merged`.
- The Ledger contract's `PayloadFields::of()` is a bounded decode (depth 8) shared by exactly six readers: `LedgerFailingHeads`, `LedgerWaitingHeads` and `LedgerBuildSteps` here, the Watcher's `FailingMains` and `HandedOverChanges`, and the Review module's `OwnerAsks`. It reads a line by typed field (`text()`, `number()`, `has()`, `lacks()`); a line with invalid JSON or a payload that is not an object has no fields. `LedgerBuildSteps` uses `has()` to tell a `run` written as `null` (left out) from a row written before runs were named.
- `Infrastructure/LedgerReviews::newestFirst()` reads the lists (`/reviews`, the project filter's `FilterProjects` and search's `SearchIndex`) from `LedgerReviewPages::listedRoundsInStartOrder()`, which feeds the ledger to a fresh `LedgerRounds` (below) and returns `LedgerRounds::listedInStartOrder()`: every round, its reviewers, findings, ending and state decided by the same code as on its review page, in the ledger order of its first readable `review_started`, but without its cost, tokens or replay mark, which the lists do not show, so a list read asks `RoundCosts` and `ReplayMarks` nothing (#2418; test `LedgerReviewsTest`). Each `Domain/ReviewedRound` makes a `Domain/ReviewSummary` (#2217, part 1 of #2210, decisions D1 and D2 in part) with its `round` id, `project`, `reviewers`, `startedAt` and `state` (`judged` once a `judge_done` row of the round has readable marks, else `in progress`), its `change` and round `number` from the start (empty and null for a start written before the ledger recorded them), its `outcome` (a `Domain/ReviewOutcome` from `ReviewOutcome::of()`, the vocabulary the review page uses: Failed for a round whose judging failed or whose reviewers all failed, Blocked for a round that ended without an outcome in time, else (a judged ending included) Approved, Changes requested or Blocked from the decision `ChangeDecision` gives a judged round with a recorded quorum; null for a round not judged or started without a quorum) and its `findingCount` (the number of the round's `RoundFinding` rows once judged, so a finding an act entry stands for is not counted again and a round judged before finding text was recorded counts the ids the judge marked; null while the round is not judged, so 0 means a judged round without findings). `/reviews` shows these fields (#2218, part 2 of #2210, below). An event of another kind and a row that does not deserialize are skipped. The first readable `review_started` of a round counts; a later one for the same round, readable or not, changes nothing. Rounds are listed newest first by the ledger order of their first readable `review_started`; an unreadable one before it takes no place. Tests: `ReviewSummaryTest`, `LedgerReviewsTest`.
- `Infrastructure/LedgerFailingHeads::now()` reads the watcher's lines for the failed-head cards on `/reviews`: per project and pull request (nested keys), the latest of `head_failed`, `head_handed_over`, `head_pending`, `head_red`, `round_queued` and `head_forgotten` counts. A failure line with a string `cause`, an integer `failures` and a `retry_at` readable as `DATE_ATOM` (not one holding a NUL byte, and one that formats back to the stored text, so an impossible calendar date such as `2026-02-30T00:00:00+00:00` is unreadable) makes a `Domain/FailingHead` (project, change and a `Domain/HeadFault`); any other latest line, an unreadable failure line included, shows no card, so the card goes when the head is read again, its round is queued or its pull request is closed. The `cause` is shown as the watcher stored it, redacted against the held credentials like a log line. A card is marked handed over while the lines since the `head_handed_over` line are of the same commit and none of them is a `round_queued` or `head_forgotten`: a `head_pending` or `head_red` is written before the stale check, which may fail again and keeps the failure count, so it keeps the mark.

- `Infrastructure/LedgerReviewPages::reviewOf(round)` reads the review page without reading the whole ledger (#2418): it feeds the `review_started` rows (`Ledger::readOfKind()`) to a fresh `Infrastructure/LedgerRounds`, which names the rounds of the review (`roundsOfTheReviewOf()`, `null` when there are none), then the rows whose payload names one of those round ids, then the rows that name the calls their `usage_recorded` started rows tie to them (`callsOf()`, because a settled call's row names only its call), both through `Ledger::readMentioning()`, each row once. The same review page and the judged-state live update (below) read it so. `LedgerRounds` collects per round and joins at the end, because a reviewer's, the judge's or a call's event can sit anywhere relative to its round's start. The first readable `review_started` (as in [Review rounds](review-rounds.md), with its `change` and `number`) makes a `Domain/ReviewedRound` (from `RoundStart` and `Domain/RoundPlace`). Readable `reviewer_started`, `verdict_received`, `reviewer_failed`, `reviewer_blocked`, `reviewer_stopped` and `catch_up_owed` rows make one `Domain/ReviewerOutcome` per reviewer id, which the latest readable row sets (`ReviewerProgress`: `running`, `verdict` with `decision`, the `findings` count and the `mode`, `failed` with the `failure` as `Review\Contract\FailureInWords` words it, so the note reads `stopped at its output limit` and never an exception's class name, `blocked` with `reason`; `catch_up_owed` adds the `substitute` provider value); `ReviewerOutcome::$model` is the `model` of the reviewer's latest `reviewer_started` row (`ReviewerOutcome::restarted()`), null when that row has none or the reviewer has no readable start (#2266), replaced by the `model` of a later `catch_up_owed` row when that row names one (`ReviewerOutcome::substitutedBy()`), so the model and `substitute` always describe the same provider (#2425; a `catch_up_owed` row without a `model` keeps the start's), and the review page's reviewer table and current state block show it (#2267, below), a live round update included (#2534, below); `ReviewerOutcome::$mode` is the `ReviewerForLoop\Contract\ProjectMode` of the `verdict_received` row, `Live` when `mode` is absent, unknown (the removed `shadow` included) or not a string; the review page shows every verdict without a mark; a start begins the row again, and a row that does not deserialize leaves the reviewer as it was. The first `judge_done` of a round whose marks are readable marks it judged with its readable `findings` entries as `Domain/RoundFinding`s (an unreadable entry is left out), each with a `Domain/JudgeCall` (act, follow-up, or rejected or unmarked, by whether its id is under `act`, under `follow_ups` or neither), which `JudgeCall::inWords()` renders in plain words as listed further down. An entry's `merged` ids (an act list entry that stands for findings reported at the same place, see [Review flow](review-flow.md)) go to `RoundFinding::$merged`, and the findings they name get no card of their own, so the act list names each place and each cause once; the finding cards and the open findings of the state block show one finding number per entry, its own id (`F1`), and a card whose entry merged others names them below its place as secondary text (`Also reported as F4`, the `.fc-merged` line of `templates/dashboard/_judged_round.html.twig`), while the card's anchor stays `round-<id>-finding-<finding id>` and its `data-finding` lists every id (`RoundFinding::ids()`) (tests: `LedgerRoundsTest`, `ShowReviewControllerTest`, `MergedActEntryPageTest`, and `ReviewPageLiveUpdatesTest`, whose page is opened before its round starts and receives the judged round only as a live update). An id under `act` or `follow_ups` with no entry in `findings` still becomes a `RoundFinding` with its call and a null severity and text (shown as `not recorded`); a `judge_done` without a `findings` list (written before the field existed) marks the round with `ReviewedRound::judgedFromMarksOnly()`, so `findingTextRecorded` is false and the page says the findings were not recorded instead of that there were none. A judged round whose start recorded a `quorum` (`ReviewedRound::$quorum`) gets `ReviewedRound::$outcome` from `Review\Contract\ChangeDecision`, the rule `intakt:review` decides with: each answered reviewer votes its `decision`, and every other one (failed, blocked, stopped, still running, or counted in `reviewers` but never started) votes `blocked`, so a failed reviewer never helps a quorum; an unjudged round, or one started before the quorum was recorded, has no outcome. Like `intakt:review`, the page counts each answered reviewer's vote as the round's `judge_done` row records it under `votes` (a `changes` verdict of only P3 findings the judge deferred or rejected votes `approve`, one whose findings are on no list votes `blocked`), and the decision its `verdict_received` row records when the judge row holds no vote for it (a row written before votes were counted); the reviewer's own row still shows its own decision (see [The outcome and the act list agree](review-flow.md)). `ReviewedRound::failedReviewers()` counts the `failed` ones. `Infrastructure/LedgerTokens` adds up the `TokenUsageRow::figures()` (a `TokenFigures` of the vendor plugin's `Contract/`: prompt with cache reads and writes included, cache read, cache write, cached, completion and their summed total, see [Vendor](vendor.md#token-figures)) of the `usages` of every call whose `started` `usage_recorded` row names the round, the rule `RoundLedgerReading` follows, so the page and `intakt:review` show the same figures; the table has the columns Prompt, Cache read, Cache write, Cached, Completion, Total and Cost. The `Domain/Review` holds the round asked for and every round with the same `project` and a non-empty `change` naming the same change (`Review\Contract\ChangeAddress::sameChange()`, so a pull request's start rows in two letter cases are one review, see [One address per pull request](review-flow.md#one-address-per-pull-request); when two of those rounds have the same number, two spellings were stored apart with a numbering each, and only the rounds of the asked round's exact spelling are its review, `Infrastructure/LedgerRounds::oneSequenceOf()`; a legacy review kept apart so, whose spelling differs from its own canonical form, is history only: `Review::nextNumber()` is null and its page shows no Start round, because new rounds start from the canonical review), ordered by `number`; a round started without a `change` (before the ledger recorded it) is a review of its own. A round the ledger never started readably is `null`.
