# Pull requests handed to Intakt

While Intakt runs beside the build loop that developed Intakt, Intakt opens its pull requests under its own GitHub App identity and the loop leaves every pull request that identity opened (owner decision 2 of 2026-10-31 in `docs/plan.md`). Plan task T71 (issue #3001, part 1 of #353) makes Intakt recognize those pull requests as handed over to it, so later parts treat them as counted. Part 2 (issue #3002) posts Intakt's review of those pull requests with the round's one-time token and asks the owner for protected heads ([below](#intakts-review-counts)); the merge through Intakt alone, and keeping the loop off them, are planned (part 3 of #353). The weekly report on the loop's own heads ([Weekly report](weekly-report.md)) reads nothing of it and is unchanged.

## What counts as handed over

A pull request counts as handed to Intakt when Intakt's own ledger holds a `change_opened` line for it with `opening` `created`: the line `PushBranch` appends after the GitHub App opened the pull request with `POST /pulls`, or after a retry found it open with this App's own bot account as its author ([Branch push](branch-push.md)), with the same `project` and the same `change` (the pull request's address, which is also the change id the listing returns). `ChangeOpening::openOrUpdate()` answers an `OpenedChange` (the `ChangeId` and its `Opening`: `Created` or `Updated`), and `PushRecords::open()` writes the `Opening`'s value as `opening`. The GitHub opener answers only `Created`: a branch with an open pull request another account opened (the loop's included) is refused with `ForgeWriteFailed` before the push and again before the write ([Branch push](branch-push.md#the-pull-request)), so Intakt neither pushes to such a pull request's branch nor writes to it (except for the accepted check-to-push window: one another account opens between the check and `git push` moves with the push, and the second look-up then refuses the write), and `updated` remains only in lines written before that refusal. It also counts when its `change_opened` lines of the project carry no `opening` at all (written before openings were recorded) and the forge answers that Intakt's App created it (`Plugin/Forge/Contract/ChangeAuthorship::isCreatedByIntakt(ChangeId)`, below). And it counts when it has no `change_opened` line of the project at all (a push that stopped after `POST /pulls` and before its record, also when the branch moved since) and the forge answers the same. The watcher never decides from what a listing reports: title, body, labels and branch are text others can shape. Only GitHub's own `user.login` is read as the author, compared with the App's bot account as GitHub names it (`GET /app`), which no person or other App can take.

`GitHubForge`'s `Infrastructure/GitHubChangeAuthorship` implements `ChangeAuthorship` (the container's only implementation, so its alias): it parses the `ChangeId` with `PullRequestAddress`, reads `GET /repos/{owner}/{repo}/pulls/{n}` through `TrustAnswers::ofInstallation()` with the token of `CheckedInstallationTokens::current()` and answers `true` only when `user.login` is a bot account and `SteeringIdentities::isOwn()` matches it (the slug from `GET /app` with the App's JWT; a person's login asks no `GET /app`). An address that is no GitHub pull request, a refused or unreachable read (a `404` too), an answer without the author's login or with an empty one, a failed token mint, a refused installation check and a failed `GET /app` are `ForgeReadFailed`; a read the installation's rate-limit pause refuses stays `ForgeRateLimited`.

The addresses are compared without letter case, because the push builds the address from the configured `github` value (`owner/name`) and the listing takes GitHub's `html_url`, which spells the owner and repository as GitHub does, and GitHub does not tell them apart by case. A repository renamed after the pull request was opened is not followed: its listed address no longer matches.

Not handed over:

- a pull request with no `change_opened` line of the project, such as one the loop opened, when the forge answers that someone other than this App created it. The answer is recorded as a `change_not_handed_to_intakt` line, because the author GitHub sets never changes, so the forge is asked once per pull request and not again; a rate limit stops the author reads of that tick (below);
- a pull request whose `change_opened` lines all say `updated`: an earlier push found an open pull request of the branch that someone else, the loop included, opened, and only updated its text (a push now refuses such a branch instead);
- a pull request whose `change_opened` lines all lack `opening` (written before this rule existed) when the forge answers that someone other than this App created it, the loop included. That answer is recorded as a `change_not_handed_to_intakt` line too, and the forge is not asked again. A push of its branch cannot record it as `created`: while it is open, `refuseForeignChange()` refuses the push ([Branch push](branch-push.md#the-pull-request)). A created opening still decides before that line. A retry of a push whose only record lacks `opening` also asks the forge again, even for the same head and text (`PushRecords::openedChange()` takes no such record as done), so it records `created`, or is refused when the open pull request is another account's;
- a `change_opened` line of another project with the same address, because projects are told apart;
- a pull request that someone else opened at a head Intakt's push only intended (a `change_intended` with no `change_opened`): the forge answers another author. When the process stopped after GitHub created the pull request, the next tick asks the forge and recognizes it without another push; a later push also finds it open with this App's bot account as its author, updates it when it targets the change's base (otherwise opens a new one) and records `created`. A push whose look-up finds an open pull request of the branch without a `user.login` text, or with an empty one, throws `ForgeWriteFailed` before anything is pushed or written, so nothing is recorded for an author GitHub did not name and the push can be retried. A head that moved after the stopped push (someone pushed to the branch) does not matter: the forge is asked for every open pull request without a `change_opened` line, whatever its head.

## Intakt's review counts

`Core/Watcher/Contract/HandedOverChanges::isHandedToIntakt(project, change)` answers from the `change_handed_to_intakt` lines alone (`Ledger::readOfKind()`), with the same project and the address compared without letter case, as the tick compares it; a line that is not valid JSON is skipped. The Review module reads it through that contract only.

`Review/UseCase/PublishVerdict/PublishVerdictHandler` publishes a judged round when the project is `reviewer-for-loop` or when its change is handed to Intakt, whatever the mode, so in a `live` project only the handed-over pull requests get a status and a comment; the loop's own heads stay with the weekly report. The publication is the one [Capability tiers](capability-tiers.md) describes: `VerdictForTheLoop` decides the `PublishedVerdict`, its `ReviewToken` is the round's id, and `GitHubForge::publishVerdict()` ends the comment with `<!-- intakt-verdict: <round id> -->` and posts it once, found again by that marker on a retry.

**Asking the owner for a protected head.** `OwnerAsks::askFor(round, verdict)` returns an `OwnerAsk` only for a verdict with status `success` (Intakt approves) of a handed-over change whose head touches a protected path: it asks `Git/Contract/ProtectedHeads::of(project, head)` ([Protected paths](protected-paths.md)), and an unreadable answer counts as protected. The `OwnerAsk` holds the `ProtectedChanges` and a new `PublishedVerdict` for the same head and token: `HeadStatus::Pending` with the description `Intakt approves this head; it touches protected paths and waits for the owner.`, never `success`, the review comment unchanged, and the ask in `PublishedVerdict::$ownerAsks`, a list of parts. The first part is `**Waiting for the owner** (head <full head>)`, the line `This head touches protected paths, so it merges only once the owner has approved this head.`, then `Intakt could not read which paths this head changes, so it counts as protected.` for an unreadable answer (git's reason is not posted, as it may name folders of the host) and `Protected paths:` with `- <code>path</code>` for every path. A part holds at most 60000 bytes (below GitHub's 65536 characters per comment, with room for the marker); the paths that do not fit go on in further parts headed `**Waiting for the owner** (head <full head>), continued`, and a part ends only after a path. Each path has control characters and backslashes spelled out (`addcslashes`), invalid UTF-8 replaced (`mb_scrub`), then every character of ``&<>"'`\*_#[]~|!()`` written as a numeric entity, so a file name cannot add a line, open a hidden comment, end the code span or turn into markdown (GitHub renders markdown inside `<code>`). A `changes` or `error` verdict, a head that touches no protected path and a change not handed over ask nothing.

`GitHubForge::publishVerdict()` posts the review comment (marker `<!-- intakt-verdict: <round id> -->`), then each part of the ask as a comment of its own ending with `<!-- intakt-owner-ask: <round id> <digest> part <n> -->`, where the digest is the SHA-256 of the JSON list of all the ask's parts, each posted only when no comment of this App ends with its marker, and then the status. The secret scan covers the parts too, as GitHub shows them: each part with its tags stripped and its entities decoded (`html_entity_decode(strip_tags(...))`), because the escaped file name inside `<code>` would hide a key from gitleaks's rules; a hit is `ReviewTextHoldsSecret`, so nothing is posted and the handler publishes only the `error` status. So a retry whose review comment is already on the pull request still posts an ask the earlier try did not carry (its protected answer changed in between), a part an earlier try did not reach, and, when the protected paths changed between the tries, the whole changed ask under new markers, so the comments show the paths the `owner_asked` line records. `ForgeWrites::publishVerdict()` returns whether the forge wrote: `false` when no GitHub App is configured.

`PublishVerdictHandler` publishes the ask's verdict in place of the round's, and only after a forge write that returned `true` calls `OwnerAsks::record()`, which appends one `owner_asked` line (`project`, `change`, `head`, `round`, `paths`, `unreadable`) unless the ledger already holds one of the same project, head and change, the change compared without letter case (`Ledger::readMentioning([head])`). The read and the append run under the change's publication lock (`ChangePublications`, keyed by the project and the change's canonical address without letter case, `strtolower(ChangeAddress::canonical($change))`), which every publication of the change holds, so a retried publication or a second round of the same head, also one naming the pull request in another letter case or with an old fragment, query or trailing slash, records no second line. A line the ledger refuses throws `OwnerAskNotRecorded` after the forge write, so Messenger's retry posts only the status again (the comments are found by their markers) and appends the line. Without a GitHub App the forge writes nothing, as for any publication, and no line is recorded. The ask approves nothing: reading the owner's approval and the merge are part 3.

**A round judged before the hand-over.** A round judged while its pull request was not yet recorded as handed over is acknowledged without a publication. So when `ChangesHandedToIntakt` appends a `change_handed_to_intakt` line, it also appends a `hand_over_publication_queued` line (project, change, head) and dispatches `Review/Contract/PublishHandedOverChange(project, change, head)` on the command bus, the head the forge listed. It does the same, once, for a listed pull request that already has a `change_handed_to_intakt` line but no `hand_over_publication_queued` line of its project (both compared without letter case), so a pull request recognized before publications were queued, whose head was judged then and published nothing, gets that head published after an upgrade. The message is routed to the `async` transport (`config/packages/messenger.yaml`), so it is stored in the tick's transaction and a worker handles it only after the hand-over line committed. `PublishHandedOverChangeHandler` then queues `PublishVerdict` for the latest judged round of that head (`ReviewRounds::latestJudgedAt()`: the change in its canonical form, `Contract\ChangeAddress::canonical()`, under which every round of a pull request is stored and numbered in one sequence whatever letter case the forge lists, and of its judged rounds at that head the highest round number, never the newest id, so it is the round `ReviewRounds::judgedAfter()` does not drop as superseded even when the clock went back between two rounds; only when no round of that sequence judged the head, a round an older install left under another spelling, which migration `Version20261122100000` kept apart, is looked up among the judged rounds stored under another address whose `ChangeAddress::canonical()` is the listed change's (so an alias with a suffix is found and a local branch differing only in letter case is not), the highest number deciding and never an id; and `judgedAfter()` treats such an old-spelling round as superseded by any judged round of the canonical sequence at the same head, so a verdict queued from the old round is not published over a canonical one: `HandedOverRoundLookupTest`), which then publishes it as above; a change without a judged round of that head queues nothing. A judging that commits after the worker's lookup checks the hand-over after the line committed, so it publishes itself, and a later head's judging does the same. Rounds opened now store the pull request's address in its canonical lowercase form (`StoredFindings::openRound()`, see [One address per pull request](review-flow.md#one-address-per-pull-request)), so the rounds and the hand-over name one pull request alike and its rounds are one sequence whatever letter case named them; migration `Version20261122100000` moved the rounds stored before under one spelling to that form. Known limit: when two old spellings that the migration kept apart both judged a head and no round of the canonical sequence did, the highest round number decides between sequences whose numbers do not compare, so the lookup can pick the round of either spelling.

## Where it happens

`Core/Watcher/UseCase/WatchPullRequests/ChangesHandedToIntakt::recognizeAmong()` runs in each watch tick ([Forge contract](forge-contract.md), the Scheduler tick), inside `ChangedHeads`' database transaction, after the listing and before the changed pull requests are queued. The transaction runs under the project's listing lock (`FindChangedPullRequests::whileListing()`), which is released only after it committed or rolled back, so an overlapping tick of the same project stops with `ListingInProgress` instead of reading the ledger before this tick's `change_handed_to_intakt` lines are committed and appending them a second time. It is given every open pull request of the project as the last completed listing saw it (`FindChangedPullRequests::openOf()`, the `watcher_seen_change` rows), not only the changed ones, so a pull request listed before its `change_opened` line was written is recognized on the next tick even when the listing is unchanged (HTTP 304). It reads the `change_opened`, `change_handed_to_intakt` and `change_not_handed_to_intakt` lines (`Ledger::readOfKind()`), keeps those of the tick's project (a line that is not valid JSON is skipped), and decides each open pull request in this order: a created `change_opened` line or a `change_handed_to_intakt` line means handed over; otherwise an updated `change_opened` line or a `change_not_handed_to_intakt` line means not handed over, and the forge is not asked; only when there is none of these is `ChangeAuthorship` asked. It appends one `change_handed_to_intakt` line (`project`, `change`, `head`: the address and head the listing named) through `WatcherLedger` for each open pull request handed over that has no such line yet, and one `change_not_handed_to_intakt` line of the same shape for each one whose author the forge answered is not this App. Each open pull request handed over without a `hand_over_publication_queued` line of the project, also one whose `change_handed_to_intakt` line an earlier tick wrote, gets that line and a `PublishHandedOverChange`, once ([A round judged before the hand-over](#intakts-review-counts)). So each pull request's author is read at most once over its lifetime, also on an unchanged (304) listing. It decides first and appends afterwards: every open pull request is decided, the forge's author reads included, before the first line is appended, because a failure behind an append would roll the transaction back under a line the entity manager still holds. Only a definite answer is recorded: an author the forge cannot read (`ForgeReadFailed`) records nothing and leaves that pull request unrecognized on this tick, logs a warning (`The author of {change} in {project} could not be read, so it is checked again on the next tick: {reason}`) and goes on with the others; a `ForgeRateLimited` author read does the same and asks no further author on this tick. The listing's record, the other recognitions and the queueing of the changed heads stand, and the next tick asks again, because it is given every open pull request. A line the ledger refuses throws `WatcherEventNotRecorded`, which rolls the transaction back with the listing's record, so the next tick tries again.

The lines are facts, not states: a second `change_handed_to_intakt` or `change_not_handed_to_intakt` line for the same pull request (two workers both recognizing it) says the same thing, and readers treat the lines as a set.
