## Doctor

#3865, part 2 of #3826; the web server and workers checks are #3827, part 2 of #1625. `php bin/console intakt:doctor` (`src/Core/Server/UseCase/Doctor/DoctorCommand`) runs the infrastructure health checks from the terminal, so an owner can see what is wrong with an install even when the dashboard does not start. In the shipped compose stack: `docker compose exec intakt php bin/console intakt:doctor`.

- Same checks, same code (decision D1): it reads `Contract/ServerStatus::read()` once and judges the reading with `Contract/InfrastructureChecks::of()`, whose hub check is the shared `Contract/HubVerdict`. It has no judgement of its own; the checks and their fix texts are described in [Server status](server-status.md).
- Read-only (D3): the reading is three `GET` requests to FrankenPHP's admin API (`/frankenphp/threads`, `/metrics`, `/mercure/health/ready`), one `GET /status` to the dashboard and a read of the process list. It writes nothing, dispatches no message, starts nothing and calls no model.
- The checks, in this order, each with its display name: `web server` (`Infrastructure/WebServerCheck`), `worker threads` (`InfrastructureChecks->threads`), `server metrics` (`->metrics`), `Mercure hub` (`->hub`), `workers` (`Infrastructure/ConsumerProcessesCheck`) and `forge` (`GitHubForge/Contract/ForgeConnection::run()`, implemented by `Infrastructure/ForgeConnectionCheck`, #3866, part 3 of #3826). The two checks of #3827 cover what the dashboard cannot report about itself (D2) and answer with `Infrastructure/DoctorCheckVerdict`, a pass or a problem with its fix.
- Output (D4): one line per check, `pass: <name>`, or `fail: <name>: <problem>; fix: <fix>`. Every line goes through one helper that turns each control character (`\p{Cc}`, so line breaks, tabs, escape and C1 codes) and each Unicode line or paragraph separator into a space, after `mb_scrub()` replaces bytes that are not UTF-8 with `?`. Lines are written raw, so a reason that looks like console markup is printed as it is.
- Exit code: 0 only when every check passes, otherwise 1.
- A piece that is down (D5): each admin API call has the 2-second timeout and limit of `Infrastructure/AdminApi`, so a stopped or hanging web server makes each check fail with `<source> down (<path> did not answer)` within a few seconds instead of hanging. A `FRANKENPHP_ADMIN_URL` that `AdminApi` refuses (not plain `http` on `localhost`, `127.0.0.1` or `[::1]`) sends nothing; every check then fails as `cannot run (<message>)` with the fix `set FRANKENPHP_ADMIN_URL to plain http on localhost, for example http://localhost:2019`.

`WebServerCheck` sends `GET http://localhost:<SERVER_PORT>/status` (`SERVER_PORT` defaults to `7781` in `config/services.yaml`, as in the Caddyfile) with `Host: localhost:<DASHBOARD_PORT>`, because `Dashboard/Infrastructure/DashboardHost` answers only a request named that way; `docker/healthcheck.sh` probes the same server the same way. It asks `/status`, not the board, because a board load can wait up to 15 seconds on the forge check. It follows no redirect, bypasses any proxy and has a 4-second timeout and `max_duration`, so a hung server fails the line (D5). Failure texts:

- No answer: `web server down (/status did not answer on port <port>)`, fix `check that FrankenPHP is running and listens on SERVER_PORT (in the compose stack, docker compose restart intakt starts it again)`. The transport's message is not shown.
- Any status outside 2xx: `web server answered /status with status <code>`, fix `check the FrankenPHP log and var/log for the error the page ends on`.
- A port that is not digits from 1 to 65535: `cannot run (SERVER_PORT or DASHBOARD_PORT is not a port number)`, fix `set SERVER_PORT and DASHBOARD_PORT to port numbers between 1 and 65535 where this install gets its environment (.env.local, or the env file or variables given to the container)`, without a request. A value with anything after its digits, a line feed included, is refused the same way. The check reads both ports as text and checks them itself, so a bad port fails this line and the other checks still run.

`ConsumerProcessesCheck` reads `/proc/<pid>/cmdline` of every process and looks for one that is PHP (its program name contains `php`) running this install's `bin/console` (the argument right before `messenger:consume`) with the receiver after `messenger:consume`, so a `grep` or `ps` that searches for those words does not count. The script must resolve (`realpath()`) to `bin/console` under `%kernel.project_dir%`: an absolute path is resolved as it is, a relative one from the process's working directory (`/proc/<pid>/cwd`). Another program's script named `console` and another install's consumer do not count. Each process is sorted by `Infrastructure/WorkerProcess`: this install's, `Unverifiable` (PHP running a relative script ending in `bin/console` with the receiver, whose working directory the doctor may not read, such as a process of another user) or other. A receiver with no consumer of this install but an unverifiable one fails as `cannot run (the doctor may not read the working directory of a process that may be the <receiver> worker)`, fix `run the doctor as the user that runs the workers, so it may read their working directory (in the compose stack: docker compose exec intakt php bin/console intakt:doctor)`; it is reported as stopped only when no such process exists. The doctor leaves its own process (`getmypid()`) out of the list, because under `hidepid` its own command line stays readable while the others are hidden. It looks for at least one `async` consumer and one `scheduler_watcher` consumer, as `docker/entrypoint.sh` starts them. Inside the container the process list is the container's own. Failure texts, one per failing receiver joined with `; ` (and their fixes joined the same way): `no async worker is running, so no review or build moves` and `the scheduler worker is not running, so pull requests are not watched`, fix `restart the container with docker compose restart intakt; outside the container, start them with messenger:consume async and messenger:consume scheduler_watcher scheduler_retention`. A process list that is missing, unreadable, lists no process or lets the doctor read none of its command lines fails as `cannot run (the process list under /proc cannot be read)`, fix `run the doctor inside the container: docker compose exec intakt php bin/console intakt:doctor`. A consumer the entrypoint is restarting at that moment (after its hour-long time limit, about a second) shows as missing.

The forge check is one class, and the board shows it too: `ShowBoardController` shows its verdict as the "Forge" figure of the infrastructure row, through `Dashboard/Infrastructure/RememberedForgeVerdict`, which runs the check at most once a minute and in one board load at a time (D1, see [Dashboard](dashboard.md)); the doctor runs it on every call. Its `Contract/ForgeConnectionVerdict` is a pass (`configured` is false when no App is set) or a problem with a fix. It reads the App installation back with `InstallationReadBack` and compares it with `GITHUB_APP_PERMISSIONS` and `GITHUB_APP_REPOSITORIES`. It is read-only (D3): it builds its own rate-limit readings over an in-memory cache and lock store and its own installation token, so the live readings and pauses stay untouched, and it writes nothing. It only reads the live pause (`RateLimitReadings::refuseWhileLimited()` for the installation's `core` pool) before the read-back, so it sends no request while GitHub asked the forge to wait. Its GitHub client has a 5-second timeout and no retries, and `Infrastructure/DeadlineHttpClient` gives the whole run (token, installation and every repository page) one 15-second deadline: each request gets the time left as its `max_duration`, never more than the 15 seconds, and a request after the deadline fails as a transport error, so the check ends as `cannot run` (D5). The time spent is measured on Symfony's `MonotonicClock` (wired in `config/services.yaml`), so a system clock set back during the run does not lengthen the deadline. The request options are `#[SensitiveParameter]`, so the bearer token is not among the trace arguments of that error. Failure texts (the `<problem>` part; the fix follows `fix:`):

- Half-cleared App: `GITHUB_APP_ID is empty while GITHUB_APP_INSTALLATION_ID or GITHUB_APP_PRIVATE_KEY is still set`. An empty App ID fails when either the installation ID or the private key is still set; with all three empty (the demo) the check passes without a request, as not configured. An App ID that is not digits (after trimming) fails as `GITHUB_APP_ID is not a number`, and an App ID with an empty installation ID fails as `GITHUB_APP_INSTALLATION_ID is empty`. `AppJwt` signs the trimmed App ID as the issuer, so an ID with spaces around it is sent to GitHub as the number alone.
- Unreadable settings: `the App settings cannot be read (<message>)` when `GITHUB_APP_PERMISSIONS` is not `name:level` pairs (or names one permission twice), or when either setting is an empty list. `GITHUB_APP_REPOSITORIES` is read as a comma-separated list of names, which the read-back compares with the installation's repositories as they are; their `owner/repo` form is not checked here. No request is sent.
- Local key error: `the private key cannot sign (it cannot be read or is not an RSA key)`. `AppJwt` signs only with an RSA key, because GitHub refuses another key type's signature under RS256. The JWT is signed before any request, so this needs no GitHub.
- Installation mismatch: `the installation does not match the configuration (<differences>)`, naming the permissions and repositories that differ.
- Cannot run: `cannot run (<reason>)` when GitHub refuses the token exchange or the read-back (a wrong installation ID answers 404), does not answer within the deadline, answers in an unusable shape or is rate limited, and, without a request, while the live forge is paused for a rate limit. It counts as a failure.

A stopped web server prints:

```
fail: web server: web server down (/status did not answer on port 7781); fix: check that FrankenPHP is running and listens on SERVER_PORT (in the compose stack, docker compose restart intakt starts it again)
fail: worker threads: worker threads down (/frankenphp/threads did not answer); fix: check that FrankenPHP is running and that FRANKENPHP_ADMIN_URL points at its admin API
fail: server metrics: server metrics down (/metrics did not answer); fix: check that the Caddyfile's global options turn on metrics and that FRANKENPHP_ADMIN_URL points at the admin API
fail: Mercure hub: hub down (/mercure/health/ready did not answer); fix: check that FrankenPHP runs with the Caddyfile's mercure block and that FRANKENPHP_ADMIN_URL points at its admin API
pass: workers
pass: forge
```

Tests: `tests/Plugin/GitHubForge/ForgeConnectionCheckTest` covers each forge failure text, a key that is not RSA, an App ID that is not UTF-8, an App ID with spaces around it (the issuer of the tokens sent is the number alone), a refused token exchange, a paused live forge (no request), a rate-limited check that leaves the live forge unpaused and the deadline across repository pages (on both sides); `tests/Plugin/GitHubForge/DeadlineHttpClientTest` covers a clock set back during the run and the bearer token kept out of the trace arguments; `tests/Core/Dashboard/Infrastructure/RememberedForgeVerdictTest` covers the minute a verdict is kept and two overlapping board loads running the check once; `tests/Core/Server/Infrastructure/WebServerCheckTest` covers a 200, no answer, a 5xx, a redirect, a timeout, the request it sends and the ports it refuses without a request (a line feed after the digits among them); `tests/Core/Server/Infrastructure/ConsumerProcessesCheckTest` covers both consumers running, each one missing, both missing, a receiver name before `messenger:consume`, a `grep` for the worker, an unrelated script named `console`, another install's consumer, a working directory that cannot be read (`cannot run` for a relative `bin/console`, stopped for any other script, a pass beside a verified consumer), the doctor's own readable command line beside hidden ones, and a missing, unreadable or empty process list (a `FakeProcessRoot` folder); `tests/Core/Server/DoctorCommandTest` replays the recorded admin API answers (`RecordedAdminApi`): a healthy install, each check failing with its fix text, a stopped web server, the web server or the workers alone failing (exit 1), a refused URL, a reason with line breaks and escape codes, bytes that are not UTF-8, and a reason that looks like console markup.
