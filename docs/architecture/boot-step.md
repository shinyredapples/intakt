# Boot step

The boot step boots one commit of a project once with `bin/instance` ([Instance and probes](instance-and-probes.md)) and reports the outcome (plan task T58, part 1). It is the harness side of the boot gate in [Reviews](../design/05-architecture/07-reviews.md). `BootGate` ([below](#the-gate-decision)) decides from it whether a head goes back. The watcher passes every head whose CI is green through `BootGate` before that head's round starts, and boots the head only when its pull request author is trusted ([In the watcher](#in-the-watcher)).

## Contract

In `src/Core/Review/Contract/`:

- `BootAt`: the repository and base (`ChangeSource`) and the exact commit (`CommitId`) to boot.
- `BootHarness`: a query that boots `BootAt` with the `bin/instance` that commit carries itself, as main is booted.
- `BootHarnessAtMain`: a query that boots the head in `BootAt` with the `bin/instance` of main's commit, so a head that changes the harness does not certify itself ([Merge](../design/05-architecture/08-merge.md), "Harness from main").
- `BootOutcome`: the answer to both, a `BootState` (`booted`, `failed`, `crashed`) and a reason (empty when booted).

`failed` is the commit's own result: its harness reported `{"status":"failed","reason":"..."}`, or `composer install` failed in it. `crashed` is the boot step's: no status could be read, or the step itself failed (the repository or the commit is missing, main has no `bin/instance`, git or a process could not run, or a process passed its time limit). A crash is an outcome, never an exception, so a crashing boot step can never stop the review it gates.

## Main's cached result

`BootResults::ofMain(BootKey, ChangeSource)` in `src/Core/Watcher/UseCase/WatchPullRequests/` (part 2) answers main's boot result from the table `watcher_boot_result` and boots only on a miss. `BootKey` is the project, main's commit and a tool fingerprint (a string the caller passes; nothing computes one yet), so main's result is reused while both stay the same and recomputed when either changes. On a miss it asks the query bus with `BootHarness`, stores the row of a `BootRecord` (the state, the reason and the moment, from `ClockInterface`) and appends the ledger event `boot_result_computed` (project, main commit, tool fingerprint, state, reason). A cache hit appends a line only when the board shows otherwise: `WatcherLedger::failingMainOf()` reads the project's boot lines (`readOfKindsMentioning` with the kinds `boot_result_computed` and `main_boot_failed` and the text `"project":<the JSON-encoded project>`) and applies the board's own rule to them (`FailingMains` in `src/Core/Watcher/Contract/`, which the board uses too, see [Dashboard](dashboard.md)), so a line the board passes over (a late computed `booted` line of a pair already seen) is passed over here as well. A stored `booted` result while the board shows the project's banner, or a stored `failed` result while the board shows no banner or the banner of another main commit and tool fingerprint pair, appends `boot_result_computed` with the same payload plus `read_from` `store` (`WatcherLedger::bootResultReadFromStore()`), after any pending alert is claimed, so the board follows main when it or the tools go back to a pair whose result is stored. The read and the append run while holding a Symfony Lock named after the project (`watcher-main-boot-` and the SHA-256 of the project), so two hits that read the board at once record the change once; the lock is tried without waiting, and a hit that finds it busy appends nothing. The board then ends as if the dropped hit had come just before the holder's, and the next hit of the current main reads the board again and corrects it. Repeated hits of the same state, and a stored crash, append nothing; a ledger that refuses the line, or a lock store that fails, is logged (`Main's stored boot result could not be recorded in the ledger.`) and the stored outcome is still answered. This line never raises a second alert: the alert stays once per pair. A `crashed` outcome is stored too, but only for a back-off of 5 minutes (`BootRecord::CRASH_BACK_OFF`, counted from the row's moment): inside it `ofMain` answers the stored crash without booting and appends no ledger line, so a boot step that keeps crashing (for example `composer` cannot run) does not run main's `composer install` for every green head; once it has passed, `ofMain` reads the row again from the database (another worker may have stored a fresh result over it meanwhile, and that one answers); a crash that is still expired counts as a miss, main boots again and the new result replaces the crashed row (a new crash starts a new back-off, a `booted` or `failed` result is kept for good). When the stored result is `failed`, its row is stored with `alert_pending` true (migration `Version20261114120000`), and the owner alert `main_boot_failed` (the same payload without the state) is appended by the worker that claims it: one conditional update sets `alert_pending` from true to false, so of two workers only the one whose update changed the row appends it. The update and the append run in one transaction on the entity manager's connection, which the ledger writes through too, so the claim and the ledger line are committed together or not at all. The worker that stored the row claims it at once; a cache hit claims it only while the row still says pending. A ledger that refuses the alert, a claim that cannot be written and a commit that fails are logged and roll the transaction back; the entity manager is then reset through `ManagerRegistry::resetManager()`, as `DoctrineLedger` does after a failed flush, because a ledger line flushed before the rollback would stay managed although the database no longer holds it. A cache hit forgets its row after the claim, so the next ask reads the row again. A worker that stops before the commit loses the transaction with its connection: `alert_pending` stays true and a later ask of the same key appends the alert, so it comes once per main commit and tool fingerprint, also after a ledger failure or a killed worker. The migration sets `alert_pending` to true on every `failed` row stored before it, because none of them has raised the alert yet, so the first ask of such a key after the upgrade appends it; a `crashed` outcome raises none. Main's outcome is returned in every case. A head is then reviewed as if the gate were not there (`BootGate` returns the green decision when main does not boot), and the board shows the alert as a banner for the project until a `booted` result is recorded for a main commit and tool fingerprint pair the project has not booted or failed before (a late `booted` line of an older main does not clear it), or a `boot_result_computed` line marked `read_from` `store` says `booted`; a marked line that says `failed` shows the banner again with its reason. A crash is the boot step's fault and not main's, so it is never trusted for good, and the gate lets the review through on it as before; a query bus that throws is turned into a `crashed` outcome with the exception's class and message. Before the reason is stored, logged in the ledger or returned, bytes that are not UTF-8 are replaced with `?` and it is redacted through the `Redactor` as a log line is, so a token in a tool's output or an exception message is neither stored nor shown.

The record is read through the entity manager but written with one insert on the connection, inside a savepoint, and its `alert_pending` with one conditional update on the connection (in the transaction that also holds the alert's append), never with a flush of the record: the default entity manager is the ledger's, and a failed flush would close it. When two workers miss the same key at once, the one whose insert loses (a unique constraint violation) still returns its own outcome. Nothing in `ofMain` throws: a cache that cannot be read is treated as a miss, a result that cannot be stored or a ledger line that cannot be written is logged as an error, and main's outcome, computed or stored, is returned in every case. `BootResults::ofHead(BootAt, CommitId main)` boots a head with `BootHarnessAtMain` through the same dispatch, crash and scrubbing steps, and stores and records nothing.

## The gate decision

`BootGate::admit(WatchedProject, HeadDecision)` in `src/Core/Watcher/UseCase/WatchPullRequests/` takes the decision of a head whose CI is green and answers the decision the head gets after its boot. It implements `HeadGate` and is the install's gate (`#[AsAlias(HeadGate::class)]`, [In the watcher](#in-the-watcher)). For every watched project:

1. it asks `Plugin/Forge/Contract/AuthorTrust::isAuthorTrusted()` for the head's change (issue #1975, decision 1), because booting runs the head's code on the host ([Threat model](../design/05-architecture/14-threat-model.md)). When the author is not trusted (`NonWriter` or `ForeignBot` in GitHub's classification, or a check that fails or cannot answer, which the contract answers `false`; a check that throws anyway counts as untrusted too and logs the warning `The pull request author counts as untrusted, because the trust check failed.`), it boots nothing, neither main nor the head, appends `head_boot_skipped` (project, change, head and `cause` `boot_skipped_untrusted_author`, `BootGate::UNTRUSTED_AUTHOR`) through `WatcherLedger::headBootSkipped()`, and answers the green decision unchanged, so the round still starts: failing closed means never running the code, not never reviewing. A `head_boot_skipped` line the ledger refuses is a failure of the gate (below), so the head is still not booted. The install's `AuthorTrust` is `GitHubAuthorTrust` (`config/services.yaml`), because the watcher lists pull requests through `GitHubWatchReads`; the test environment binds it to `tests/Core/Watcher/RecordedPullRequests` (below);
2. it asks the query bus for `MainCommit(ChangeSource)`, the commit the base branch points at, answered by the local git forge's `MainCommitHandler` (`git show-ref` of the base branch in the project's `repository` path);
3. it asks `BootResults::ofMain` for main's result under the `BootKey` of the project, that commit and the constant `BootGate::TOOL_FINGERPRINT` (nothing computes a fingerprint of the boot tools yet, so one constant stands for them);
4. only when main is `booted`, it boots the head with `BootResults::ofHead`.

| main | head | decision |
| --- | --- | --- |
| not booted | not booted (author not trusted) | the green decision unchanged, with a `head_boot_skipped` line: the round may start |
| booted | failed | `HeadDecision::sentBackFor(FailedBoot)`: `HeadAdmission::FailedBoot` with the redacted reason in `FailedBoot`; it starts no round, like red CI |
| booted | booted or crashed | the green decision unchanged: the round may start |
| failed or crashed | not booted | the green decision unchanged: the gate is off for the head |

A project without `bin/instance` has the gate off: main's boot crashes because main has no harness (before any `composer install`), and a crash is stored only for its 5-minute back-off, so main's tree is read for `bin/instance` again once it has passed. Any `Throwable` from the gate (also a `MainCommit` answer that is not a commit) is logged as the error `The boot gate failed, so the review starts without it.` and the green decision is returned, so a crashing gate never stops the review.

Tests: `tests/Core/Watcher/UseCase/WatchPullRequests/BootGateTest.php` (`persistence` group; also an untrusted author's head booted neither with main nor alone, also when it would fail to boot, its `head_boot_skipped` line, a trust check that throws booting nothing, a skipped boot the ledger refuses booting nothing, a trusted author's head booted, and the container's `HeadGate` being `BootGate`), `tests/Core/Watcher/Domain/HeadDecisionTest.php` and the main commit case of `tests/Plugin/LocalGitForge/BootHeadHandlersTest.php`.

## In the watcher

`SettleHead` (plan task T58, part 2) passes every head whose CI is green through its `HeadGate` before anything else. In the install that gate is `BootGate` (`#[AsAlias(HeadGate::class)]`), which boots a head only when its pull request author is trusted ([above](#the-gate-decision)); any other author's head goes to review unbooted, with a `head_boot_skipped` line. A trusted author's head runs `composer install` (with the plugins the commit allows) and main's `bin/instance` as the install's user, beside the install's home, keys and database ([below](#how-a-commit-boots)), unsandboxed until the boot runs in an isolated job container (the review job containers of #340); the [Threat model](../design/05-architecture/14-threat-model.md#residual-risk) records that risk. In the test environment `AuthorTrust` is `tests/Core/Watcher/RecordedPullRequests`, which answers trusted only for a recorded pull request with `"author_trusted": true`, so a recording without the key (as the journeys write) boots nothing.

The rest of this section is what `SettleHead` does with `BootGate` as its gate, as `WatchPullRequestsHandlerTest` wires it, for a trusted author's head. A head boots before its round starts and no reviewer runs on a head that fails while main boots. A pending or red head is not booted. A head that already has a round is booted again whenever the listing names it again, because a head that stopped booting must lose that round's approvals. The boot runs inside the tick, while the head's lock is held.

A `FailedBoot` decision goes back like red CI (`HeadDecision::goesBack()` is true for both):

1. `HeadsWithoutRound` records it, and `WatcherLedger` writes it as `head_red` with `read_again_at` `null`, `cause` `boot_failed` (`FailedBoot::CAUSE`) and the redacted `reason`, so a reader tells it from red CI.
2. `StaleVerdicts::noteRefusedHead()` takes the round already started on the refused head itself (`StartedRounds::roundAt()`). It runs before the check of the earlier heads and reads no repository, only the round's row, so the withdrawal is owed and sent even when step 3 then throws; otherwise a next boot that passes or crashes would leave the approval on the forge. `StartedRounds::oweWithdrawalOnce()` runs one transaction: one `UPDATE` sets `stale` where it is unset, and `verdicts_stale` is written only when that changed the row; a second `UPDATE` sets `withdrawal_requested` and `withdrawal_owed` where `withdrawal_requested` is unset (migration `Version20261114100000`). So the withdrawal is owed once per round, also when a move already found the round stale before its head returned (A, then B, then A failing to boot), whose approval may still be on the forge, and that round's `verdicts_stale` is not written a second time. Then `StaleVerdicts::withdrawOwed()` sends Review's `MarkVerdictsStale(roundId)` on the command bus for every round of the pull request that still owes its withdrawal, which withdraws an approval already published on the forge ([Review flow](review-flow.md#a-round-marked-stale)), and clears `withdrawal_owed` only after Review took it. So an approved head that does not boot keeps no approval, neither in Review nor as a status on the forge.
3. `StaleVerdicts::noteMovedHead()` checks the rounds of the change's earlier heads with Review, as for any head that moved; those heads booted, so they are not withdrawn. It asks `IdentityAtHead` for each of those rounds, and a repository read that fails there (`ForgeReadFailed`) throws.
4. `HeadsWithoutRound::settled()` removes the pending head, so it is read again only when the listing names the pull request again.

Any failure in steps 1 to 3 (for example a `MarkVerdictsStale` that throws) leaves the head due and backs it off alone through `HeadBackOff`. A `MarkVerdictsStale` that throws is rethrown as `VerdictsWithdrawalRefused` (in `src/Core/Watcher/UseCase/WatchPullRequests/`, the original kept as its previous exception), so the `cause` of the `head_failed` line, and of `head_handed_over` after four failures in a row, reads `Intakt\Core\Watcher\UseCase\WatchPullRequests\VerdictsWithdrawalRefused: Review refused to withdraw the verdicts of the head's round:` followed by Review's own exception class and message; for the command bus's `HandlerFailedException` that is its first wrapped exception (for example Review's `RoundNotFound`). The message leaves out the round id, so the same refusal on two pull requests still reads as the same error to Budget's install-wide failure check. A withdrawal Review did not take stays owed on the round's row, whatever the next boot says: `SettleHead` calls `StaleVerdicts::withdrawOwed()` first on every try for that pull request (a head that boots again, a crashed boot, a head that moved), before the boot and the round start, and a refusal again leaves the head due without a fresh round. A head whose round was withdrawn this way and that later boots gets a fresh round, as a head that returns to a stale round does. Main's boot result and `boot_result_computed` come from `BootResults` as above.

Tests: `tests/Core/Watcher/UseCase/WatchPullRequests/WatchPullRequestsHandlerTest.php` (`persistence` group: a green head booted with main's harness before its round starts, an untrusted author's green head never booted while its round still starts after its `head_boot_skipped` line, a trust check that fails booting nothing while the round starts, a trusted author's head booted with no `head_boot_skipped` line, a pending or red head not booted, a head that fails to boot recorded `head_red` with its reason and forgotten, not read again until its pull request changes, a failed boot withdrawing the round already started on that head, a withdrawal that fails sent again on the next try also when the head then boots, crashes or moved, no fresh round while it is still refused, a refused withdrawal named as the `head_failed` cause with Review's reason, also through the command bus's wrapper, and as the `head_handed_over` cause after four refusals, a withdrawal taken once not sent again, also when the head fails to boot again, a head that returns (A, B, A) and fails to boot withdrawing its round a move already found stale with no second `verdicts_stale`, that returning head withdrawn although the stale check of the head between throws on a repository read, staying due, and withdrawn once when its next boot crashes or passes, a moved head that fails to boot leaving the earlier head's round to the stale check, a fresh round once the head boots again, a crashed head boot, a main that does not boot, and a gate that throws all still starting the round).

## How a commit boots

The handlers `BootHarnessHandler` and `BootHarnessAtMainHandler` (query bus) live in the local git forge, in `src/Plugin/LocalGitForge/UseCase/BootHead/`, and both call `InstanceBoot`:

1. It reads `bin/instance` at the harness commit (the commit itself for `BootHarness`, main's for `BootHarnessAtMain`). A harness the forge names as binary (a NUL byte anywhere) is `crashed` with `bin/instance is a binary file of <n> bytes, not a harness.`, because the forge hands over its size, not its bytes.
2. It takes a detached worktree of the commit in the temp directory, as a review snapshot is taken ([Forge contract](forge-contract.md)), and removes it after the boot, whatever the outcome.
3. It runs `composer install --no-interaction --no-progress --no-scripts` in the snapshot (at most 600 seconds). Composer plugins the commit allows still run, because `symfony/runtime` writes `vendor/autoload_runtime.php` as a plugin and `bin/instance` needs that file; a plugin is the commit's own code, as is the code `bin/instance` boots, and it runs with the same allowlisted environment and scratch home (below). When `composer` cannot be found or executed (exit code 127 or 126), the outcome is `crashed` with `composer could not run: ` and the shell's error output, because that is the boot step's fault, not the commit's. Any other failure is `failed` with `composer install failed: ` and Composer's error output.
4. Then it places the harness at `bin/instance` in the snapshot, so nothing the install wrote there (a Composer plugin of the commit, or a package binary when the commit sets `bin-dir` to `bin`) replaces it. A `bin/instance` the snapshot holds (also a symbolic link) is removed first, so writing never follows a link out of the snapshot; a `bin` that is a symbolic link or a file is `failed` without writing anything.
5. It runs `php bin/instance` through `sh -c 'exec "$@" 3>&1 1>&2'` (at most 180 seconds), so the status line of descriptor 3 arrives on standard output and the server log on standard error, where no log line can pass for the status.

Both commands get only an allowlist of the boot install's environment variables: `PATH`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TZ`, `TMPDIR`, `COMPOSER_CACHE_DIR` and the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, also in lower case). Every other variable, including those Dotenv loaded into `$_ENV`, `APP_ENV`, `APP_SECRET` and `COMPOSER_AUTH`, is unset, so the commit boots with the defaults of `bin/instance` and gets no token of the booting install from its environment. `HOME` and `COMPOSER_HOME` are not inherited either: both commands get one empty scratch directory beside the snapshot (the snapshot's path plus `-home`, mode 0700) as `HOME` and `COMPOSER_HOME`, removed with the snapshot. Without it Composer would load the booting install's `auth.json` (from `COMPOSER_HOME`, or from `~/.composer` or `~/.config/composer` under `HOME`) and a Composer plugin of the commit would read its tokens through Composer's config. The package cache is still shared when the install sets `COMPOSER_CACHE_DIR`; without it Composer caches inside the scratch home, so each boot downloads afresh.

6. Exactly `{"status":"ready"}` or `{"status":"ready","mode":"worker"}` (the two lines `bin/probe` accepts) with exit code 0 is `booted`; `{"status":"failed","reason":"..."}` or `{"status":"failed","mode":"worker","reason":"..."}` with a non-empty reason is `failed` with that reason; no status line, more than one line, any other status, key or mode (also `ready` with an undefined mode or an extra key), or `ready` with another exit code is `crashed`.

What this does not do: the install and the commit's code run as the install's user with no filesystem isolation, so a plugin or `bin/instance` that computes the real home (for example through `posix_getpwuid`) can still read files there. The allowlist and the scratch home remove only what the environment and Composer hand over; keeping head code away from the install's files is the job sandbox of #340 (review job containers), not built yet, which is why the watcher's `BootGate` boots only a trusted author's head ([In the watcher](#in-the-watcher)).
