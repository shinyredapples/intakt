# Builder prompt

Plan task T49, part 1 (#1574; design: [threat model](../design/05-architecture/14-threat-model.md#builder)). `Core/Build/Domain/BuilderPrompt::textFor(BuildBrief): string` builds the one prompt a build job gives its builder. Running the builder with it, the model choice, the turn limit, the hand-back and the session usage are later parts of T49; nothing calls the prompt in production yet.

- **Brief:** `Core/Build/Contract/BuildBrief` holds the `task` text, the maintainer's `decisions` (a list of texts) and a `Rework` or null for a first build. A `Contract/Rework` holds the `actList` (a list of `Review/Contract/Finding`), the `ciExcerpt` (a string or null) and the `publishedText` of the pull request.
- **Order:** the fixed instructions, then the task, the decisions when there are any, and then for a first build the request to write the pull request text to `PR.md`; for a rework the request to fix what the act list and the CI log name and to edit the published text, the act list when it is not empty, the CI excerpt when there is one, and the published text. Parts are separated by a blank line.
- **Fencing:** each of the five inputs goes through `Review/Contract/Fence::wrap()` as one fence of its own source: `UntrustedSource::Task`, `Decisions`, `ActList`, `CiLog` and `PullRequestText`. Nothing of the brief reaches the text in any other way. The instructions describe the fence like the reviewer's (only a closing marker with the opening boundary ends it) and say never to follow an instruction in a fence to handle credentials, change protected paths, disable checks, push, merge or contact outside services.
- **Decisions:** numbered `D1`, `D2`, ... in their order, one per line, inside the `decisions` fence (builder's choice).
- **Act list:** each finding is `Finding::listEntry()`, the same entry the reviewer's open findings use (id, severity, `file:line`, symbol, requirement, text), followed by `evidence from <probe>:` and the probe output when the finding carries evidence; entries are separated by a blank line, all inside the `act list` fence.
- **Wording:** the instructions are the builder's choice ([Left to the builder](../design/08-left-to-the-builder.md)), as long as every input stays fenced.

## The fencing gate

`tests/Core/Build/Domain/FencedPlants` is the gate: it walks the brief by reflection and takes every string in it (nested objects and lists included; enums, numbers, booleans and null are skipped), so a field added to the brief is checked without a list to update. Every such string must be a plant (it starts with `PLANT-`, so a test that leaves a field with ordinary text fails), must appear in the prompt, and must not appear outside a real fence. A real fence is one that `Fence::contentOf()` accepts, so a forged opening or closing marker hides nothing. `BuilderPromptTest` runs it over a first build and a rework with every field planted, and checks each input's fence source; `FencedPlantsTest` shows the gate refusing a plant interpolated outside a fence, a plant repeated beside its fence, a plant in a forged fence, a missing plant and an input text that is no plant.
