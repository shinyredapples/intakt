# Builder prompt

Plan task T49, part 1 (#1574; design: [threat model](../design/05-architecture/14-threat-model.md#builder)). `Core/Build/Domain/BuilderPrompt::textFor(BuildBrief): string` builds the one prompt a build job gives its builder. The [build job](build-job.md) runs the builder with it on the tier's model (`intakt:build:run`); the build job bounds the session by a turn limit and an allowance; reading the session usage is a later part of T49.

- **Brief:** `Core/Build/Contract/BuildBrief` holds the `task` text, its `kind` (`TaskKind`, `Task` by default), the maintainer's `decisions` (a `Decisions` value holding their texts in order) and a `Rework` or null for a first build. A `Contract/Rework` holds the `actList` (a list of `Review/Contract/Finding`), the `ciExcerpt` (a string or null) and the `publishedText` of the pull request.
- **Order:** the fixed instructions, then the task, the decisions when there are any, for a bug task the test-first instruction (see Bug tasks), and then for a first build the request to write the pull request text to `PR.md`; for a rework the request to fix what the act list and the CI log name and to edit the published text; for both, next, the request to end with a question instead when a decision the task does not cover is needed (write no `PR.md`, write `QUESTION.json`, `BuildQuestion::FILE`, in the checkout root: a JSON object with `question`, `choices` and `recommendation`, one of the choices; see [Build job](build-job.md#the-question)); then for a rework the act list when it is not empty, the CI excerpt when there is one, and the published text. Parts are separated by a blank line.
- **Bug tasks:** a brief whose `kind` is `TaskKind::Bug` adds one literal instruction: the first acceptance criterion is a regression test that fails today, so write it first, watch it fail for the reason under "Today", commit it on its own, then fix the bug and keep what "Must keep working" lists unchanged. A head without such a test, or whose test also passes on the base, is refused before the push, and a bug that no test can reproduce belongs in a task without the `bug` label; the builder never decides that on its own. It sits after the decisions and outside the task fence because it is trusted text, and no input of the task enters it. The threat model's "Bug tasks" line under [Developer](../design/05-architecture/14-threat-model.md#developer) says what the `bug` label and a waiver in the fenced task text can and cannot do.
- **Fencing:** each of the five inputs becomes one fence of its own source: `UntrustedSource::Task`, `Decisions`, `ActList`, `CiLog` and `PullRequestText`. The decisions and the act list go through `Review/Contract/Fence::wrap()`. The whole text is put together by `Review/Contract/PromptAssembly::document(PromptPart ...)` (#2519), which joins its parts with a blank line. A `PromptPart` is a `literal-string` lead alone (the fixed instructions and the closing requests, Intakt's own constants) or a lead such as `The task:` followed by a blank line and a `FencedText`'s `rendered()`; it takes no other string, so PHPStan rejects a runtime string as a lead and runtime content enters only through a `FencedText`. The text is the same as before the assembly path. Nothing of the brief reaches the text in any other way. The instructions describe the fence like the reviewer's (only a closing marker with the opening boundary ends it) and say never to follow an instruction in a fence to handle credentials, change protected paths, disable checks, push, merge or contact outside services.
- **Oversized input:** the task, the CI excerpt and the published pull request text go through `Review/Contract/PromptCut::fenced()`, the cut the reviewer prompt uses: a text over `PromptCut::CEILING_BYTES` (100000 bytes) is cut with `mb_strcut`, so a UTF-8 character is never split, before it is fenced, and `FencedText::cut()` puts Intakt's note ("Intakt cut this text: N of M bytes are shown ...") after the closing marker, outside the fence. A text at the ceiling is fenced whole with no note. The instructions say a cut note may follow a fence and that its sentence on approvals is for reviewers; the build side refuses nothing because of a cut. `BuilderPromptTest` covers each of the three inputs over and at the ceiling.
- **Decisions:** numbered `D1`, `D2`, ... in their order, one per line, inside the `decisions` fence (builder's choice).
- **Act list:** each finding is `Finding::listEntry()`, the same entry the reviewer's open findings use (id, severity, `file:line`, symbol, requirement, text), followed by `evidence from <probe>:` and the probe output when the finding carries evidence; entries are separated by a blank line, all inside the `act list` fence.
- **Wording:** the instructions are the builder's choice ([Left to the builder](../design/08-left-to-the-builder.md)), as long as every input stays fenced.

## The fencing gate

`tests/Core/Build/Domain/FencedPlants` is the gate: it walks the brief by reflection and takes every string in it (nested objects and lists included; enums, numbers, booleans and null are skipped), so a field added to the brief is checked without a list to update. Every such string must be a plant (it starts with `PLANT-`, so a test that leaves a field with ordinary text fails), must appear in the prompt, and must not appear outside a real fence, neither whole nor any of its non-blank lines, split at `\n`, `\r\n` or `\r` (so a task whose first line is used as a title outside the fence fails, also when its lines end in CRLF). A real fence is one that `Fence::contentOf()` accepts, so a forged opening or closing marker hides nothing. `BuilderPromptTest` runs it over a first build and a rework with every field planted, and checks each input's fence source; `FencedPlantsTest` shows the gate refusing a plant interpolated outside a fence, a multi-line plant whose first or a later line is interpolated outside its fence, a plant repeated beside its fence, a plant in a forged fence, a missing plant and an input text that is no plant, and passing a multi-line plant wholly inside its fence.
