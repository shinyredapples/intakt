# Work intake from GitHub issues

Plan task T47. `Plugin/WorkSource` is the contract. No implementation of it exists yet and nothing calls it; `Plugin/GitHubWorkSource` holds the parts of the GitHub one built so far: its rules (`Domain\IntakeRules`), its stored state and the listing sync that fills it (below), which nothing calls yet either. The rules are those of [Choosing work](../design/05-architecture/03-choosing-work.md) (step 1, eligible, and step 5, prioritized) and [Labels](../design/05-architecture/04-labels.md).

## Contract (`Plugin/WorkSource/Contract`)

- `WorkSource::nextWork(project, WorkerState)` answers a `WorkPick`: a `Task` (number, title, and `reworkOf`, the number of its open pull request or null) or a `NothingPicked` reason. A worker state other than `free` (`no-free-slot`, `paused`, `draining`, `held-by-budget`) is meant to return before any forge read, so an idle worker makes no forge call.
- `WorkSource::queue(project)` answers a `WorkQueue`: the ready tasks in pick order and the held ones (`HeldTask`, with a reason), or `incomplete`. `TaskNotQueued` is the failure for a task that is not in the queue.
- `WorkSource::failedForGood(project, number, reason)` records that a task failed for good, so the tasks that wait on it are held with that reason.

## The `eligibility_label` key

The `watch` section of a project takes the optional `eligibility_label`: the issue label that makes a task eligible; when the key is left out it is unset, and no code reads it yet (the implementation arrives in part 2 of #1602). `WatchConfiguration` refuses a blank value, including one of only Unicode whitespace such as a no-break space, with the same check as the `repository`, `base` and `task` keys. Test: `tests/Core/Watcher/Infrastructure/WatchConfigurationTest.php`.

## Stored state (`work_source_issue`, `work_source_validator`, `work_source_failure`)

Issue #2906, part 1 of #2666. Three Doctrine entities in `Plugin/GitHubWorkSource/Domain`, mapped as the `GitHubWorkSource` entry of `config/packages/doctrine.yaml`, with migration `Version20261120100000`:

- `StoredIssue` (`work_source_issue`, key project and number): what the last complete listing showed of one open issue or pull request. It keeps the title (cut to 255 characters), labels, author, update time and milestone due date (text in UTC with microseconds, `Y-m-d H:i:s.u`, because a datetime column keeps whole seconds and an edit within the same second would go unseen), whether it is a pull request, the `Waits for` numbers, the `Waits for` lines that could not be read and the numbers a pull request closes, and what its history said once read (`vouch()`): whether author and last editor had write access, and the labels whose last application was by such an account. `trusted` is null until the history was read. The body is not kept, because only the numbers it names steer the queue. `queued()` gives the row back as the `QueuedIssue` the rules take (with an empty body, and untrusted when the history was not read).
- `IntakeValidator` (`work_source_validator`, one per project): the validator of the last complete listing.
- `TaskFailure` (`work_source_failure`, key project and number): the reason a task failed for good. It is a table of its own, so removing the row of a closed task keeps its reason and its dependents stay held.

`Infrastructure\IntakeStore` persists them:

- `record(project, issues, ?validator)` makes the project's rows those of one complete listing in one flush: a stored item is updated in place (`StoredIssue::replaceWith`), a new one is added, a stored item the listing no longer shows loses its row, and the validator is stored, replaced, or removed when the forge sent none, so the next listing is a full one. An issue of another project is an `InvalidArgumentException`, and nothing is written. Failures are never touched.
- `recordIfStill(project, issues, Domain\ValidatorChange)` does the same as `record()`, storing the change's `to`, only while the stored validator is still the change's `from` (the one the listing was requested with, `null` for none), and answers whether it recorded. It reads the validator row with `LockMode::PESSIMISTIC_WRITE` in the same transaction as the write, so a competing writer waits on that row where the database supports row locks.
- `issuesOf(project)` and `validatorOf(project)` read them back.
- `failForGood(project, number, reason)` stores or replaces the reason, only for a task the stored rows show (`TaskNotQueued` otherwise); `failuresOf(project)` answers the reasons by number.

Every method works in a new entity manager of its own, built on the shared one's connection, configuration and event manager, and nothing keeps that manager when the method ends. The rows of a project are loaded with a query on that manager (`createQueryBuilder()`), never through `getRepository()`: the shared configuration's repository factory keeps every manager it built a repository for, with the rows that manager loaded, for the life of the worker (a test runs 50 ticks of `issuesOf()`, `failuresOf()` and `record()` and finds no manager alive afterwards). A worker keeps the shared entity manager between ticks, so reading through it could answer rows another worker has replaced since. A write that flushed the shared one would also write another caller's pending work (a test persists a validator of another project in the shared manager, and `record()` leaves it unwritten). A failed write must leave no scheduled removal behind for a later flush (a test hides the validator table so `record()` fails after it scheduled a removal, flushes the shared manager, and the row is still there). `record()`, `recordIfStill()` and `failForGood()` run in a transaction (`wrapInTransaction`), so a failed write changes no row. The store takes no lock apart from the validator row in `recordIfStill()`: the pick that calls `failForGood()` and takes the lock is another part of #329. Test: `tests/Plugin/GitHubWorkSource/Infrastructure/IntakeStoreTest.php` (group `persistence`, SQLite); `tests/Application/MigrationsMatchMappingTest.php` checks the migration against the mapping.

## Listing sync (`Infrastructure\CompleteListing`)

Issue #2908, part 3 of #2666. `CompleteListing::sync(project, IntakeRules)` reads one complete listing per tick and makes the stored rows those of that listing; it answers a `Domain\SyncedListing`: `complete` with every listed item as a `QueuedIssue`, or `short` with a reason and no items. The caller passes the rules, because the eligibility label is the project's setting; nothing reads the `eligibility_label` key yet.

1. It reads the listing once through `Contract\IssueReads::listOpen(project, validator)` with the stored validator (`IntakeStore::validatorOf`). `GitHubIssueReads` reads every page in that call before it returns ([Forge contract](forge-contract.md#open-issue-listing)), so the order of the rules is computed over the whole listing, never over its first page.
2. A listing the forge answers unchanged (`304`) is answered from the stored rows (`IntakeStore::issuesOf`). A listed one becomes fresh rows: every listed field, the milestone due date included, comes from the listing, also for an item whose update time did not move, because a due date changes without it. The `Waits for` and closing numbers are read from the listed body with `Domain\IssueReferences`.
3. Every row, also after a `304`, goes through `IntakeRules::itemsNeedingHistory()` with the rules of this tick, so a change of the eligibility label makes the items it now names candidates although their update time did not move. A row that needs its history and has no stored vouching gets it: `Contract\IssueHistories::of(project, number)` and `Contract\SteeringAccounts::steers(project, account)` (asked once per account per tick) give a `Vouching`. A listed item whose update time equals its stored row's keeps that row's vouching (`StoredIssue::vouchingWhileUnchanged()`), so its history is not read again; one whose update time moved is read again when it needs it.
4. `IntakeStore::recordIfStill()` stores the rows, with the listing's validator (the stored one after a `304`), only while the stored validator is still the one this tick sent. When another sync stored a listing while this tick's request was in flight, nothing is written, so an older validator never labels newer rows, and the sync answers the rows that sync stored (a test runs a second sync inside the first one's request). A row the listing no longer shows goes; its failed-for-good reason stays in `work_source_failure`, so its dependents stay held.

A wait on several issues is answered from the listing or the stored rows: no read per reference is made (a test sees one listing request and no other). A listing read that fails (`ForgeReadFailed`, a later page included), is rate limited (`ForgeRateLimited`), or a history or trust read that fails (`TrustNotChecked` too) makes the tick short: nothing is recorded, the rows and the validator stay as they were, so no wait closes and nothing is picked, and a warning `The listing of project {project} came back short, so nothing is picked and no wait closes this tick: {reason}` is logged with the exception. Test: `tests/Plugin/GitHubWorkSource/CompleteListingTest.php` (group `persistence`, SQLite), with `RecordedIssueReads`, `RecordedIssueHistories`, `GrantedAccounts` and, for the paging cases, `GitHubIssueReads` on `RecordedIssueApi`.
