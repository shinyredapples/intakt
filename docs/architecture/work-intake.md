# Work intake from GitHub issues

Plan task T47. `Plugin/WorkSource` is the contract. `Plugin/GitHubWorkSource` holds the GitHub implementation, `Infrastructure\GitHubWorkSource`: its rules (`Domain\IntakeRules`), its stored state, the complete-listing sync that keeps that state and the pick (all below). Nothing calls it yet. The rules are those of [Choosing work](../design/05-architecture/03-choosing-work.md) (step 1, eligible, and step 5, prioritized) and [Labels](../design/05-architecture/04-labels.md).

## Contract (`Plugin/WorkSource/Contract`)

- `WorkSource::nextWork(project, WorkerState)` answers a `WorkPick`: a `Task` (number, title, and `reworkOf`, the number of its open pull request or null) or a `NothingPicked` reason. A worker state other than `free` (`no-free-slot`, `paused`, `draining`, `held-by-budget`) returns `NothingPicked::WorkerNotTakingWork` before any forge call, so an idle worker makes none.
- `WorkSource::queue(project)` answers a `WorkQueue`: the ready tasks in pick order and the held ones (`HeldTask`, with a reason), or `incomplete`. `TaskNotQueued` is the failure for a task that is not in the queue.
- `WorkSource::failedForGood(project, number, reason)` records that a task failed for good, so the tasks that wait on it are held with that reason.

## The `eligibility_label` key

The `watch` section of a project takes the optional `eligibility_label`: the issue label that makes a task eligible. When the key is left out it is `intakt` (issue #3291, part 1 of #2987), so a project beside the earlier loop builds only what carries its own label: `IntakeRules` counts a task as a candidate only when it carries the label it was built with, so a task carrying only the loop's label is not eligible and its history is not read (test: `tests/Plugin/GitHubWorkSource/Domain/IntakeRulesTest.php`). The default has one home, `Plugin/GitHubWorkSource/Contract/WorkLabels::ELIGIBILITY`. `CompleteListing` takes the processed watch sections (`WatcherServices::PROJECTS`) and builds the project's `IntakeRules` from its `eligibility_label` at the start of each listing, so each project plans, queues and picks only the tasks carrying its own label; a project without a watch section names no label, so its listing is short before any forge call (tests: `CompleteListingTest::testEachProjectPlansOnlyTheTasksCarryingTheLabelItsWatchNames`, `testAProjectWithoutAWatchSectionLeavesTheListingShortWithoutAForgeCall`, and through `GitHubWorkSource`, `GitHubWorkSourceTest::testATaskCarryingOnlyTheLoopsLabelIsNeitherQueuedNorPicked` and `testATaskCarryingTheLabelTheProjectNamesIsQueuedAndPicked`). The container wires no caller of `GitHubWorkSource` yet (#2667), so a running install does not list issues by the label so far. `WatchConfiguration` refuses a blank value, including one of only Unicode whitespace such as a no-break space, with the same check as the `repository`, `base` and `task` keys. Test: `tests/Core/Watcher/Infrastructure/WatchConfigurationTest.php`.

## Wait lines (`Domain\IssueReferences`)

`IssueReferences` reads the numbers a body names: `waitsFor()` and `unreadableWaits()` from its `Waits for` lines, `closedBy()` from a pull request's closing keywords (`Closes`, `Fixes`, `Resolves` and their forms, then `#n`).

- **A wait line** is a line of its own that starts with the words `Waits for`, in any case. Before the words it may hold spaces, blockquote markers (`>`, repeated, with spaces or not) and one list marker (`-`, `*`, `+`, `1.` or `1)`, then a space). The words may carry the same `**`, `__`, `*` or `_` on both sides, with the colon inside or outside (`**Waits for:** #9`, `**Waits for** : #9`). Anything but a letter, a digit or `_` may follow the words, so `Waits for#9` and `**Waits for**#9` are wait lines, and `Waits for, #9` is one whose numbers cannot be read. A word joined to the words (`Waits for_example`), emphasis that does not close the way it opened, and prose that mentions a wait (`this waits for #9`) are not wait lines.
- **The numbers** after the words (and an optional colon) are a list of `#n` joined by commas, `and` or `&` (`#9, #10 and #11`). The `n` is ASCII digits (`0` to `9`): a `#` followed by a digit of another script (`Waits for #9 and #１０`, `Waits for #1２`) makes the whole line unreadable, and no number is taken from it. A note may follow the list but must hold no `#` and no digit of any script, so `Waits for #9 then 10` or `Waits for #9 then １０` names no number a wait could miss.
- **An unreadable wait** is a wait line whose numbers are not such a list (`Waits for billing#12`, `**Waits for** the base`, `Waits for #9 and 10`, or text that is not UTF-8). `unreadableWaits()` answers the line as written, its markers included and without the spaces around it, and `waitsFor()` takes no number from it; `IntakeRules` holds the task with `unreadable wait: "<line>"`. A line the pattern cannot finish (PCRE gives up) is held as unreadable too, never dropped.
- **External blocks.** A line inside an `<!-- external -->` ... `<!-- /external -->` block is neither a wait nor an unreadable wait, because the threat model counts copied text as untrusted even in a trusted task. A line holding only `<!-- external -->` (spaces or tabs around it allowed) opens the block, a line holding only `<!-- /external -->` closes it, and a block that is never closed runs to the end of the text. Closing keywords are read from the whole body.

Test: `tests/Plugin/GitHubWorkSource/Domain/IssueReferencesTest.php`.

## Stored state (`work_source_issue`, `work_source_validator`, `work_source_failure`)

Issue #2906, part 1 of #2666. Three Doctrine entities in `Plugin/GitHubWorkSource/Domain`, mapped as the `GitHubWorkSource` entry of `config/packages/doctrine.yaml`, with migration `Version20261120100000` (and `Version20261120120000` for the sync generation, issue #3063):

- `StoredIssue` (`work_source_issue`, key project and number): what the last complete listing showed of one open issue or pull request. It keeps the title (cut to 255 characters), labels, author, update time and milestone due date (text in UTC with microseconds, `Y-m-d H:i:s.u`, because a datetime column keeps whole seconds and an edit within the same second would go unseen), whether it is a pull request (`isPullRequest()`), the `Waits for` numbers, the `Waits for` lines that could not be read and the numbers a pull request closes, and what its history said once read (`vouch()`): whether author and last editor had write access, and the labels whose last application was by such an account. `trusted` is null until the history was read (`isVouched()` says whether it was), and `keepVouchingOf(stored)` copies what a stored row's history said onto a fresh reading of the same item only while its update time, its label set and the numbers its body names are all unchanged. `forgetVouching()` sets `trusted` back to null and drops the vouched labels. The body is not kept, because only the numbers it names steer the queue. `queued()` gives the row back as the `QueuedIssue` the rules take (with an empty body, and untrusted when the history was not read).
- `IntakeValidator` (`work_source_validator`, one per project): the sync state of the project, written by the first recorded listing and never removed: the validator of the last recorded listing (null when the forge sent none, as for a listing of several pages) and the sync generation, 1 for the first recorded listing and one more for each later one. `state()` answers both as a `Domain\SyncState`; a project without a row answers `SyncState::neverSynced()` (no validator, generation 0). Going back to a release older than `Version20261120120000` needs its down migration first (`doctrine:migrations:execute --down 'DoctrineMigrations\Version20261120120000'`), because the older mapping cannot load a sync state row without a validator; the down migration drops those rows and the generation column.
- `TaskFailure` (`work_source_failure`, key project and number): the reason a task failed for good. It is a table of its own, so removing the row of a closed task keeps its reason and its dependents stay held.

`Infrastructure\IntakeStore` persists them:

- `recordIfStill(project, readBefore, ListingRows)` (`#[NoDiscard]`) makes the project's rows those of one complete listing in one flush, compare-and-set on the sync generation (decision 2 of #2908, issue #3063), so it holds without a forge validator: in its transaction it reads the project's sync state row with a pessimistic write lock (`LockMode::PESSIMISTIC_WRITE`, a row lock where the platform has one), and when its generation is no longer that of `readBefore`, the `SyncState` read before the listing, another worker stored a newer listing meanwhile, so it writes nothing and answers false. Otherwise a stored item is updated in place (`StoredIssue::replaceWith`), a new one is added, a stored item the listing no longer shows loses its row, the generation advances and the validator of `Domain\ListingRows` is stored (null when the forge sent none, so the next listing is a full one), and it answers true. The first sync of a project finds no row to lock and inserts it; when another worker committed the row after it was read, the write fails with DBAL's `UniqueConstraintViolationException` (or `LockWaitTimeoutException`, when SQLite in WAL mode refuses a write on the stale read snapshot), the transaction is rolled back, and it reads the sync state again: when the generation advanced, it answers false instead of throwing; otherwise no newer listing was stored and the `UniqueConstraintViolationException` is thrown. A write that overlaps a writer that has not committed yet is a different case, for a first sync and for an already synced project alike: while the other worker sits between its write and its commit, the database refuses this write with one of DBAL's `RetryableException`s (`LockWaitTimeoutException`, which SQLite raises at once as "database is locked" on its default journal and in WAL mode, or `DeadlockException`), and the sync state read again still shows the old generation, because the other write is not committed and may still roll back. That is not a lost write, so the store does not answer false: it throws `Domain\ProjectHeldByAnotherWriter` with the refusal as its previous exception, and nothing is written. The same exception follows when the re-read of the sync state is itself refused with a `RetryableException` (on SQLite's default journal, another worker whose commit waits for this one's read lock keeps a pending lock that refuses new reads), and when SQLite refuses this write's own `COMMIT` as busy because another worker holds a read transaction. SQLite keeps a transaction open after a refused `COMMIT` while DBAL already counts it as ended, on both of DBAL's SQLite drivers (`sqlite://` through PDO, `sqlite3://` through the native `SQLite3` extension), so before the re-read the store rolls back a native transaction still open on the connection (`PDO::rollBack()` when `PDO::inTransaction()` says one is open; for `SQLite3`, which cannot say so, a `ROLLBACK` whose "no transaction is active" refusal is expected): the re-read never sees this write's own uncommitted generation as another worker's, and the next call on the connection writes normally. The store runs this transaction itself instead of through the entity manager's `wrapInTransaction()`, because a server that aborts a deadlock victim's transaction itself (InnoDB does) refuses the rollback that follows, and that refusal would replace the `DeadlockException`: the store ignores a refused rollback and throws the failure that ended the write. The flush still runs its statements in a nested transaction of its own (a savepoint), and when a statement there is refused after the server aborted the whole transaction, the unit of work's rollback to that savepoint is refused too and thrown in place of the statement's refusal, which PHP keeps at the end of its chain of previous exceptions. So the store looks through that chain for a `RetryableException` and continues with it, and it brings the connection's transaction nesting level back to where the write started (a nested level whose savepoint is gone is left through a commit, which DBAL counts as ended even when the release is refused, before the level above is rolled back). A deadlock is therefore named as held whether it is raised before the flush's nested transaction or on a statement inside it, with the `DeadlockException` as the previous exception, nothing written and no transaction left open. The development requirements in `composer.json` include `ext-sqlite3`, so the native driver's tests run on every development install. An issue of another project is an `InvalidArgumentException`, and nothing is written. Failures are never touched.
- `issuesOf(project)` and `syncStateOf(project)` read them back.
- `failForGood(project, number, reason)` stores or replaces the reason under the same row lock on the sync state as `recordIfStill()` (on SQLite, under the database's write lock, taken first), only for a task the stored rows show: a number with no stored row, or one whose stored row is a pull request (the listing stores pull requests for the rules, never as tasks), throws `TaskNotQueued` and records nothing, checked inside the locked transaction; `failuresOf(project)` answers the reasons by number, and `failuresUnderTheListingLock(project)` the same under that lock (used by the pick). On SQLite's default journal another connection's open read lets the lock's write through and refuses only the `COMMIT` of either method as busy: the store then rolls back the native transaction SQLite keeps open (the same cleanup as in `recordIfStill()`) before the refusal leaves, as DBAL's `RetryableException` from `failForGood()` and as `Domain\ProjectHeldByAnotherWriter` from `failuresUnderTheListingLock()`. So no transaction stays open on the shared connection, a failure whose commit was refused is not read back as recorded, and the next call works normally (tests on both SQLite drivers: `testAPickReadWhoseCommitAReaderRefusedLeavesNoTransactionOpenAndTheNextOneReads`, `testAFailureWhoseCommitAReaderRefusedIsNotReadBackAndCanBeRecordedAgain`).
- `forgetVouchingOf(project, number)` (used by the pick, issue #3310) runs under the same lock as `failForGood()`: it calls `forgetVouching()` on the item's row, when there is one, and advances the sync state with no validator (`IntakeValidator::advance(null)`), so the next listing is a full one and a listing read before it loses its write. A refusal with a `RetryableException` throws `Domain\ProjectHeldByAnotherWriter`.
- A read of `issuesOf()`, `syncStateOf()` or `failuresOf()` that the database refuses with a `RetryableException` throws `Domain\ProjectHeldByAnotherWriter` with the refusal as its previous exception: on SQLite's default journal, another worker whose commit waits for a third one's read lock keeps a pending lock that refuses every new read until it commits.

Every method works in a new entity manager of its own, built on the shared one's connection, configuration and event manager, and nothing keeps that manager when the method ends. The rows of a project are loaded with a query on that manager (`createQueryBuilder()`), never through `getRepository()`: the shared configuration's repository factory keeps every manager it built a repository for, with the rows that manager loaded, for the life of the worker (a test runs 50 ticks of `issuesOf()`, `failuresOf()` and `recordIfStill()` and finds no manager alive afterwards). A worker keeps the shared entity manager between ticks, so reading through it could answer rows another worker has replaced since. A write that flushed the shared one would also write another caller's pending work (a test persists a validator of another project in the shared manager, and `recordIfStill()` leaves it unwritten). A failed write must leave no scheduled removal behind for a later flush (a test makes the flush fail with an `onFlush` listener after a removal was scheduled, flushes the shared manager, and the row is still there).

- **Deadlocks.** `recordIfStill()`, `failForGood()`, `failuresUnderTheListingLock()` and `forgetVouchingOf()` run in the transaction the store runs itself, not the entity manager's `wrapInTransaction()`, so a deadlock whose transaction the server aborted leaves no transaction level open on the shared connection and is not replaced by the refused rollback: `failForGood()` throws the `DeadlockException` itself, while `recordIfStill()` (with the generation unmoved), `failuresUnderTheListingLock()` and `forgetVouchingOf()` name it as `Domain\ProjectHeldByAnotherWriter`, with the `DeadlockException` as the previous exception.
- **Refused commits.** A failed write changes no row, also when SQLite refuses the `COMMIT` and keeps the transaction open: the store rolls it back.
- **One lock.** The store takes one lock, the pessimistic write lock on the project's sync state row, in `recordIfStill()`, `failForGood()`, `failuresUnderTheListingLock()` and `forgetVouchingOf()` (see [Pick, queue and failure](#pick-queue-and-failure-infrastructuregithubworksource)). Only a server database enforces that row lock; on SQLite the ORM renders it as nothing and the store relies on SQLite's database-wide write lock instead. Three tests (`testRecordingAFailureReadsTheSyncRowWithAWriteLock`, `testThePickReadOfTheFailuresReadsTheSyncRowWithAWriteLock`, `testForgettingAnItemReadsTheSyncRowWithAWriteLock`) prove that `failForGood()`, `failuresUnderTheListingLock()` and `forgetVouchingOf()` ask for the lock: they run the store on SQLite behind a test DBAL middleware (`tests/Plugin/GitHubWorkSource/WriteLockOfAServer.php`) that names a MySQL platform, so the ORM appends `FOR UPDATE` to the sync row's read, records each statement and strips the clause before SQLite runs it. They fail when the lock mode is removed from that read; they do not show a server holding the lock.

Test: `tests/Plugin/GitHubWorkSource/Infrastructure/IntakeStoreTest.php` and `tests/Plugin/GitHubWorkSource/Infrastructure/NativeSqliteRefusedCommitTest.php` (the native `sqlite3` driver) (group `persistence`, SQLite); `tests/Application/MigrationsMatchMappingTest.php` checks the migration against the mapping, and `tests/Application/IntakeGenerationMigrationTest.php` that `Version20261120120000` plans in one dry run with the migration creating the table (it writes both table shapes out instead of reading the database) and keeps a stored validator up and back down.

## Complete-listing sync (`Infrastructure\CompleteListing`)

Issue #3062, part 1 of #2908. `CompleteListing::planOf(project)` (`#[NoDiscard]`) makes one complete listing per tick and answers the `IntakePlan` of `IntakeRules::planOf()` over the resulting rows and the stored failures, or null when the listing came back short. It uses `Plugin/GitHubForge` only through its contract: `IssueReads::listOpen()`, `IssueHistories::of()` and `SteeringAccounts::steers()`. `GitHubWorkSource` calls it (below); the container wires no caller of that yet.

- **Every page, then sort** (owner decision of 2026-11-11). The listing is asked with the stored validator, and `IssueReads` answers every page or fails, so the next task is chosen from the complete open-issue listing. A `ForgeReadFailed` or `ForgeRateLimited` (a later page that fails, too) and a history read or trust check that fails (`ForgeReadFailed`, `ForgeRateLimited`, `TrustNotChecked`) make the listing short: nothing is written, no row is removed, so no wait closes and nothing is picked, and a warning is logged with the project and the failure's message as `reason`.
- **Unchanged items from the stored rows.** A `304` answers every row from the store. An item whose `updated_at`, label set and body numbers (`Waits for`, unreadable `Waits for` lines, closing keywords) equal its stored row's keeps that row's history (`StoredIssue::keepVouchingOf()`); one where any of them changed loses that history, because an edit in the second of the earlier listing keeps `updated_at`, and has it read again only when `IntakeRules::itemsNeedingHistory()` names the row (see the next item). A history is read for the `updated_at` the row was listed with (`IssueHistories::of(project, number, listedAt)`), pull requests included; an item GitHub updated after the listing fails that read, so the listing is short and no history is stored for text or labels the listing does not hold. Because `updated_at` has whole seconds, `CompleteListing` also compares the history's `body` and `currentLabels` with the row (`StoredIssue::isListedAs(history, references)`): the labels as a set (sorted as strings, so `1` and `01` stay apart) and the numbers the body names (`Waits for`, unreadable `Waits for` lines, closing keywords), not the text, since a row answered from a `304` keeps no body. Any difference fails with `ForgeReadFailed` ("GitHub holds #n with other text or labels than it was listed with, ..."), so the listing is short; an edit that keeps those numbers and labels is vouched for by its editor. Waits are answered from the rows by `IntakeRules::planOf()` (a number the listing does not show open counts as closed), never by a read per referenced issue.
- **Fields that change without `updated_at`** (decision 4 of #2908). Every other field of a row, the milestone due date among them, is taken from each listing that is not a `304`. `IntakeRules::itemsNeedingHistory()` runs over every row of every listing, a `304` too, and every row it names whose history was never read gets it read, so after a change of the configured eligibility label a stored row that became a candidate is vouched and written, even when GitHub answers `304`.
- **Write.** The sync state (`IntakeStore::syncStateOf()`) is read before the listing, which is asked with its validator. A `304` that read no history writes nothing. Otherwise the rows go through `IntakeStore::recordIfStill()` with that sync state and the listing's validator (the stored one again after a `304`), so of two overlapping syncs only the first to record wins, a first-ever sync of the project and listings without a validator included. When it answers false, the plan is answered from the rows the other worker stored, after `IntakeRules::itemsNeedingHistory()` of this sync's own rules ran over them and every row it names whose history was never read had it read (decision 3 of #3063, issue #3188), so a change of the eligibility label is not missed for a tick. Those rows are not written again; a history read or trust check that fails there makes the listing short, as above. The sync state is read again before those rows and once more after their histories and the failed-for-good reasons (`failuresOf()`) were read, the last reads the plan is answered from; when its generation moved in between, a third worker committed a newer listing meanwhile, so the listing is short for this tick (`ListingReplacedMeanwhile`: warning logged, null answered, nothing written, no retry), because answering from the older rows could release a wait the newest listing holds. When the write, or any read of the store during the sync (the sync state before the listing included), is refused because another worker has written and not committed yet (`ProjectHeldByAnotherWriter`), the listing is short too: the warning names that reason, no exception leaves `planOf()`, and the next tick reads the rows the other worker committed. Nothing is written when the refusal comes before this sync's write won; when this sync's write won and the `failuresOf()` read of the plan after it is refused, the written rows stay, because they are the newest committed listing, and only this tick's plan is skipped (the next tick plans from them).
- **Closed failures** (decision 3 of #2908). Removing the row of a closed issue keeps its failed-for-good reason, because failures live in `work_source_failure`, so its dependents stay held.

Tests: `tests/Plugin/GitHubWorkSource/Infrastructure/CompleteListingTest.php` (group `persistence`, SQLite; the paging cases run `GitHubIssueReads` and `GitHubIssueHistories` over recorded GitHub answers).

## Pick, queue and failure (`Infrastructure\GitHubWorkSource`)

Issue #3308, part 1 of #2667. The container wires no caller of it yet.

- **`nextWork`** returns `WorkerNotTakingWork` for a worker that will not take work first, before any forge call or store read, then takes the `IntakePlan` of `CompleteListing::planOf()`; a short listing (`null`, its reason already logged) is `ListingIncomplete`. It walks the ready tasks in order. For each (`GitHubWorkSource::isStillSteered()`) it asks again whether the author has write access (`SteeringAccounts::steers()`), because access may have been withdrawn since the row was vouched, then reads the history from `IssueHistories::of()` for the update time the task was listed with. Each account is asked once per task (the author, the last editor and those who applied the labels are often the same). Because `updated_at` has whole seconds, an edit in the second of the listing keeps it, so the pick compares that history with the plan in two steps. First `QueuedIssue::isListedAs(history, references)`: the current labels as a set and the numbers the body names (`Waits for`, unreadable `Waits for` lines, closing keywords), each compared as a set, so the same references in another order pass; a change to the wording alone passes. Then it builds `Vouching::of()` from the history and compares it with the plan's through `QueuedIssue::isVouchedAs()`: whether author and last editor have write access, and, of the labels the task carries, those an account with write access applied last. The priority labels (`Priority::labelsIn()`) are compared in the order they were applied, because `Priority::of()` takes the one applied last; every other label is compared as a set, so two labels a writer applies again in the other order still pick the task. A label removed and applied again by an account without write access leaves the label set as planned and is caught only by this second step. An author or last editor that no longer steers skips that task (an info record names it). A difference in either step throws `ItemNotAsPlanned` ("GitHub holds #n with other labels, waits or closing references than it was planned with, ..." or "The labels of #n are no longer applied by the accounts with write access the plan counted, ..."). It is logged as a warning that the task is not the item it was planned with and ends the tick with `TrustNotChecked`, so a task behind it is not picked in its place. That tick also calls `IntakeStore::forgetVouchingOf()`: under the listing lock it drops the row's stored vouching and the project's validator and advances the generation, so the next listing is a full one, reads the item and its history again and vouches it from scratch (a listing read before the forget loses its write). A refused forget (`ProjectHeldByAnotherWriter`) is logged as a second warning, and the tick still ends with `TrustNotChecked`. Any check that fails (`ForgeReadFailed`, `ForgeRateLimited`, `TrustNotChecked`) is logged as a warning that the write-access check failed, not as an untrusted account, ends the tick with `TrustNotChecked` and forgets nothing.
- **Failure re-read under the lock.** Before returning a task, the pick reads the failure records with `IntakeStore::failuresUnderTheListingLock()`: a lock on the project's sync row (`work_source_validator`), the row `recordIfStill()` and `failForGood()` lock too. SQLite has no row lock and, in WAL mode, reads from the snapshot of a transaction's first read, so the re-read and `failForGood()` first send an `UPDATE` of that table that matches no row: it takes SQLite's write lock before anything is read, and a server database ignores it and relies on the row lock. A task, or a task it waits for, that failed for good since the plan was made is skipped. The tasks it waits for are the ones the plan resolved (`IntakePlan::$dependsOn`), so a wait on a trusted pull request counts the tasks that pull request closes. The pick is ordered before any failure that commits after that read. When another writer holds the database and the read is refused (`ProjectHeldByAnotherWriter`), the reason is logged and the tick ends with `ListingIncomplete`; nothing is thrown out of the contract.
- **`queue`** answers the plan's ready and held tasks (`reworkOf` from the open pull request that closes the task), or `incomplete` for a short listing. **`failedForGood`** is `IntakeStore::failForGood()`, which takes the sync row's lock before it writes and refuses a listed pull request with `TaskNotQueued`, as it refuses a number the listing does not show.
- **Pages.** The listing reads every page before anything is sorted, so the issue that sorts first on the last page is picked; a later page that fails leaves the listing short, so nothing is picked and the reason is logged.

Tests: `tests/Plugin/GitHubWorkSource/GitHubWorkSourceTest.php` (group `persistence`, SQLite), including the forced order of a failure recorded between the plan and the pick (also of a task a waited-for pull request closes) and a failure another connection tries to record on a WAL file while the pick reads the failures (refused, not missed). The steering check at the pick has a case each for a wait added and for wording changed alone, for an eligibility label and a priority label applied again by an account without write access, and for two priority labels and two other labels a writer applies again in the other order. After a difference, a case for each step shows the next full listing reading the item again: a changed wait picks the task behind it, and a label put back by an account without write access holds the task as not eligible and picks the next one; a refused forget is logged and still picks nothing, and a failed history read forgets nothing.
