# Work intake from GitHub issues

Plan task T47. `Plugin/WorkSource` is the contract. No implementation of it exists yet and nothing calls it; `Plugin/GitHubWorkSource` holds the parts of the GitHub one built so far: its rules (`Domain\IntakeRules`), its stored state and the complete-listing sync that keeps that state (both below), which nothing runs yet either. The rules are those of [Choosing work](../design/05-architecture/03-choosing-work.md) (step 1, eligible, and step 5, prioritized) and [Labels](../design/05-architecture/04-labels.md).

## Contract (`Plugin/WorkSource/Contract`)

- `WorkSource::nextWork(project, WorkerState)` answers a `WorkPick`: a `Task` (number, title, and `reworkOf`, the number of its open pull request or null) or a `NothingPicked` reason. A worker state other than `free` (`no-free-slot`, `paused`, `draining`, `held-by-budget`) is meant to return before any forge read, so an idle worker makes no forge call.
- `WorkSource::queue(project)` answers a `WorkQueue`: the ready tasks in pick order and the held ones (`HeldTask`, with a reason), or `incomplete`. `TaskNotQueued` is the failure for a task that is not in the queue.
- `WorkSource::failedForGood(project, number, reason)` records that a task failed for good, so the tasks that wait on it are held with that reason.

## The `eligibility_label` key

The `watch` section of a project takes the optional `eligibility_label`: the issue label that makes a task eligible; when the key is left out it is unset, and no code reads it yet (the implementation arrives in part 2 of #1602). `WatchConfiguration` refuses a blank value, including one of only Unicode whitespace such as a no-break space, with the same check as the `repository`, `base` and `task` keys. Test: `tests/Core/Watcher/Infrastructure/WatchConfigurationTest.php`.

## Stored state (`work_source_issue`, `work_source_validator`, `work_source_failure`)

Issue #2906, part 1 of #2666. Three Doctrine entities in `Plugin/GitHubWorkSource/Domain`, mapped as the `GitHubWorkSource` entry of `config/packages/doctrine.yaml`, with migration `Version20261120100000`:

- `StoredIssue` (`work_source_issue`, key project and number): what the last complete listing showed of one open issue or pull request. It keeps the title (cut to 255 characters), labels, author, update time and milestone due date (text in UTC with microseconds, `Y-m-d H:i:s.u`, because a datetime column keeps whole seconds and an edit within the same second would go unseen), whether it is a pull request, the `Waits for` numbers, the `Waits for` lines that could not be read and the numbers a pull request closes, and what its history said once read (`vouch()`): whether author and last editor had write access, and the labels whose last application was by such an account. `trusted` is null until the history was read (`isVouched()` says whether it was), and `keepVouchingOf(stored)` copies what a stored row's history said onto a fresh reading of the same item only while its update time is unchanged. The body is not kept, because only the numbers it names steer the queue. `queued()` gives the row back as the `QueuedIssue` the rules take (with an empty body, and untrusted when the history was not read).
- `IntakeValidator` (`work_source_validator`, one per project): the validator of the last complete listing.
- `TaskFailure` (`work_source_failure`, key project and number): the reason a task failed for good. It is a table of its own, so removing the row of a closed task keeps its reason and its dependents stay held.

`Infrastructure\IntakeStore` persists them:

- `recordIfStill(project, askedWith, ListingRows)` (`#[NoDiscard]`) makes the project's rows those of one complete listing in one flush, compare-and-set on the forge validator: in its transaction it reads the stored validator with a pessimistic write lock (`LockMode::PESSIMISTIC_WRITE`, a row lock where the platform has one), and when that is no longer `askedWith`, the validator the listing was asked with, another worker stored a newer listing meanwhile, so it writes nothing and answers false. Otherwise a stored item is updated in place (`StoredIssue::replaceWith`), a new one is added, a stored item the listing no longer shows loses its row, the validator of `Domain\ListingRows` is stored, replaced, or removed when the forge sent none, so the next listing is a full one, and it answers true. When no validator is stored there is no row to lock, so two workers that both asked without one can both write; the per-project sync generation that closes this gap is part 2 of #2908. An issue of another project is an `InvalidArgumentException`, and nothing is written. Failures are never touched.
- `issuesOf(project)` and `validatorOf(project)` read them back.
- `failForGood(project, number, reason)` stores or replaces the reason, only for a task the stored rows show (`TaskNotQueued` otherwise); `failuresOf(project)` answers the reasons by number.

Every method works in a new entity manager of its own, built on the shared one's connection, configuration and event manager, and nothing keeps that manager when the method ends. The rows of a project are loaded with a query on that manager (`createQueryBuilder()`), never through `getRepository()`: the shared configuration's repository factory keeps every manager it built a repository for, with the rows that manager loaded, for the life of the worker (a test runs 50 ticks of `issuesOf()`, `failuresOf()` and `recordIfStill()` and finds no manager alive afterwards). A worker keeps the shared entity manager between ticks, so reading through it could answer rows another worker has replaced since. A write that flushed the shared one would also write another caller's pending work (a test persists a validator of another project in the shared manager, and `recordIfStill()` leaves it unwritten). A failed write must leave no scheduled removal behind for a later flush (a test makes the flush fail with an `onFlush` listener after a removal was scheduled, flushes the shared manager, and the row is still there). `recordIfStill()` and `failForGood()` run in a transaction (`wrapInTransaction`), so a failed write changes no row. Apart from the validator lock of `recordIfStill()`, the store takes no lock: the pick that calls `failForGood()` is another part of #2666 and of #329. Test: `tests/Plugin/GitHubWorkSource/Infrastructure/IntakeStoreTest.php` (group `persistence`, SQLite); `tests/Application/MigrationsMatchMappingTest.php` checks the migration against the mapping.

## Complete-listing sync (`Infrastructure\CompleteListing`)

Issue #3062, part 1 of #2908. `CompleteListing::planOf(project)` (`#[NoDiscard]`) makes one complete listing per tick and answers the `IntakePlan` of `IntakeRules::planOf()` over the resulting rows and the stored failures, or null when the listing came back short. It uses `Plugin/GitHubForge` only through its contract: `IssueReads::listOpen()`, `IssueHistories::of()` and `SteeringAccounts::steers()`. Nothing runs it yet: no `WorkSource` implementation calls it and the container wires no caller.

- **Every page, then sort** (owner decision of 2026-11-11). The listing is asked with the stored validator, and `IssueReads` answers every page or fails, so the next task is chosen from the complete open-issue listing. A `ForgeReadFailed` or `ForgeRateLimited` (a later page that fails, too) and a history read or trust check that fails (`ForgeReadFailed`, `ForgeRateLimited`, `TrustNotChecked`) make the listing short: nothing is written, no row is removed, so no wait closes and nothing is picked, and a warning is logged with the project and the failure's message as `reason`.
- **Unchanged items from the stored rows.** A `304` answers every row from the store. An item whose `updated_at` equals its stored row's keeps that row's history (`StoredIssue::keepVouchingOf()`); one whose `updated_at` moved has its history read again. A history is read for the `updated_at` the row was listed with (`IssueHistories::of(project, number, listedAt)`), pull requests included; an item GitHub updated after the listing fails that read, so the listing is short and no history is stored for text or labels the listing does not hold. Because `updated_at` has whole seconds, `CompleteListing` also compares the history's `body` and `currentLabels` with the row (`StoredIssue::isListedAs(history, references)`): the labels as a set and the numbers the body names (`Waits for`, unreadable `Waits for` lines, closing keywords), not the text, since a row answered from a `304` keeps no body. Any difference fails with `ForgeReadFailed` ("GitHub holds #n with other text or labels than it was listed with, ..."), so the listing is short; an edit that keeps those numbers and labels is vouched for by its editor. Waits are answered from the rows by `IntakeRules::planOf()` (a number the listing does not show open counts as closed), never by a read per referenced issue.
- **Fields that change without `updated_at`** (decision 4 of #2908). Every other field of a row, the milestone due date among them, is taken from each listing that is not a `304`. `IntakeRules::itemsNeedingHistory()` runs over every row of every listing, a `304` too, and every row it names whose history was never read gets it read, so after a change of the configured eligibility label a stored row that became a candidate is vouched and written, even when GitHub answers `304`.
- **Write.** A `304` that read no history writes nothing. Otherwise the rows go through `IntakeStore::recordIfStill()`, asked with the validator the listing was asked with (the stored one again after a `304`). When it answers false, the plan is answered from the rows the other worker stored.
- **Closed failures** (decision 3 of #2908). Removing the row of a closed issue keeps its failed-for-good reason, because failures live in `work_source_failure`, so its dependents stay held.

Tests: `tests/Plugin/GitHubWorkSource/Infrastructure/CompleteListingTest.php` (group `persistence`, SQLite; the paging cases run `GitHubIssueReads` and `GitHubIssueHistories` over recorded GitHub answers).
