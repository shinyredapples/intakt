## The weekly report: the loop's reviews and Intakt's

Module `Core/ReviewerForLoop` (plan task T42 and the weekly report of #1432). It holds the project mode (see [Capability tiers](capability-tiers.md)) and the report that compares, in `reviewer-for-loop` mode, the loop's GPT review with Intakt's published review on the same heads. Nothing fetches comments from a forge yet; the report reads recorded pull requests.

**Reading the loop's reviews.** `Domain/LoopReviewReader::read(loopIdentity, head, comments)` takes `Contract\PullRequestComment` objects (author, head commit, body) and returns `Contract\LoopReviews`: one `LoopReview` per comment whose author is the given identity and whose head is the given head, with the reviewer name, a `LoopVerdict` (`approve`, `changes` or `unreadable`) and the `LoopFinding` list (file, line, `Severity`). It exists only for this report; Intakt's own reviews never parse prose. Reading rules (builder's choice for what the issue leaves open; `test_agents.py` is not in this repository):
- The reviewer is the text of a `Reviewer: <name>` line (`unknown` without one).
- The verdict is the last JSON candidate: a fenced block whose info string starts with `json` (whatever it holds), or a line starting with `{`. Its `verdict` must be `approve` or `changes`; a missing, malformed or unknown verdict, a final candidate that is no JSON object, or a comment without JSON, is `unreadable`, never approval. An `approve` with an open P1 or P2 finding counts as `changes`; a P3 finding keeps the approval. Open means a P1 anywhere, or a P2 that does not come after an unfenced, unquoted line `Follow-ups:` (the loop files a P2 of a re-review there and still approves); a filed P2 is still listed among the findings.
- A finding is a line `[P1|P2|P3] file:line ...` (optional bullet `-`, `*`, `+` or numbered `1.`/`1)` marker, optional backticks around the location). Lines inside a fence and lines starting with `>` are neither findings nor verdicts. A fence opens with three or more backticks or tildes, any indentation and any info string, and closes only with a line of the same character at least as long; an unclosed fence runs to the end. CRLF line endings are read like LF.

**Matching findings.** `Domain/ReviewComparison::matchedSpots(loopReviews, intaktReviews)` is generic over `LoopFinding` and `Finding`. First each side is merged on its own into spots (`Domain/MergedSpot`): sorted by file and line, a finding joins the spot before it when it is in the same file, comes from a review that has no finding in that spot yet, and the spot's span (lowest to highest line) stays at most `ReviewComparison::LINE_WINDOW` (3) lines with it, whatever their severities. Findings on the same file and line are placed together: every one the spot before admits joins it before any of them opens a new spot, so the spots do not depend on the reviewers' order. One review's own findings therefore never merge with each other, and a chain of nearby findings splits into spots no wider than the window. A spot keeps its span and its most severe finding as representative; a finding without file or line is never merged. Then a loop spot matches an unused Intakt spot of the same file whose span is at most `LINE_WINDOW` lines from its own span, the closest one. The representatives are the match; the rest are `loopOnly` or `intaktOnly`, and an Intakt finding without file or line never matches. Test: `tests/Core/ReviewerForLoop/Domain/ReviewComparisonTest.php`.

**The report.** `UseCase/WeeklyReport/WeeklyReportCommand` (`intakt:reviewer-for-loop:weekly-report <folder> [--until=<moment>]`) lists the folder literally with `Infrastructure/RecordedFolder::jsonFiles()`, which uses `scandir()` (not `glob()`, which takes `[`, `*` or `?` in the folder name as a pattern), and reads each regular file ending in `.json`, in name order, with `Infrastructure/RecordedPullRequestFile` into `Domain/RecordedPullRequest` (number, loop identity, Intakt identity, `Domain/PostedComment` list: a `PullRequestComment` and its `postedAt`, parsed by `Infrastructure/RecordedMoment` in GitHub's format `Y-m-d\TH:i:sp`; an impossible date such as February 30 is refused, not rolled over, and so is text holding a null byte). `Domain/Week::endingAt(until)` is the half-open range of the seven days before `--until` (the `ClockInterface` now without it). `Domain/PublishedComparison::report(list<RecordedPullRequest>, Week)` first keeps only the reviews (`RecordedPullRequest::keepingReviews()`): a comment by the loop identity whose `Reviewer:` line names `gpt` (any case, `LoopReviewReader::reviewerNamedIn()`), and a comment by the Intakt identity that holds a verdict block, a JSON line or a json fence even a broken one (`LoopReviewReader::holdsVerdict()`); the loop's other reviewers, a bot's ordinary messages and other authors are ignored. `RecordedPullRequest::headsReviewedIn(Week)` then keeps the heads whose last such review lies in the week, so both sides of a head land in one report. The report reads each side with `LoopReviewReader` (Intakt's decisions are named `intakt`, the loop's by their `Reviewer:` line), matches findings with `matchedSpots()`, and returns `Contract/WeeklyReport` (the week and one `Contract/PublishedHead` per head: decisions, `Contract/Agreement`, matched count, `loopOnly` and `intaktOnly` findings). A side has no verdict when it has no reviews or one of them is unreadable, even beside a `changes` review; otherwise it is `changes` when any of its reviews is, and `approve` when none is. Both sides `changes` or both `approve` is `agree`, one of each `disagree`, and a side without a verdict `incomplete`, so an unreadable review never counts as agreement. The table has one row per head and a summary line (`WeeklyReport::withAgreement()`, `matched()`, `loopOnly()`, `intaktOnly()`). An unreadable `--until`, a missing folder or an unreadable file exits with 2 and names it. Recorded set: `tests/Fixtures/ReviewerForLoop/weekly/`, and `tests/Fixtures/ReviewerForLoop/loop-review-comments.json` for the reader; tests: `LoopReviewReaderTest`, `PublishedComparisonTest`, `WeeklyReportCommandTest`.
