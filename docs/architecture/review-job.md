# Review job

Plan task T58, the review job's script (#1923, part 2 of #1861) and its runner (#1862, part 2 of #1840; design: [overview](../design/05-architecture/01-overview.md), [reviews](../design/05-architecture/07-reviews.md)). A review job runs one reviewer in a [job container](job-containers.md) built from [the review job image](job-images.md#the-review-job-image), against a read-only checkout of the exact head, reaching only its vendor through the job's proxy ([Egress](job-containers.md#egress)). `ReviewJob` runs one; `ReviewerInJob` calls it for each `claude_code` reviewer on an install whose `INTAKT_CONTAINER_ENGINE` names an engine, on a clone of the head of its own (#2017, part A of #2012). Every other reviewer, and every reviewer of an install without an engine, reviews in the app's own process. A Codex review in a job is not built yet: the job's Codex has its shell off, which is the only way it reads files, so each of its approvals would be blocked as unread. Turning each job failure into a reviewer failure of its own is part B of #2012.

The job holds one credential: the login token of the account its call runs on (`AccountLogins::claudeCode()`, the first free account in the owner's order), never another account's. It is a read-only input file of its own, `/input/login` (mode 0600 under `var/prompts/`, removed after the job), which `review.sh` reads into the CLI's environment only. Its value is redacted from the CLI's events and from the log before anything in them is parsed, stored or posted.

## The job

`Core/Review/Infrastructure/ReviewJob::run(ReviewJobRequest)` (marked `#[NoDiscard]`) returns a `ReviewJobAnswer` or throws `ReviewJobFailure` (a `ReportableFailure`). The request (`Core/Review/Contract/ReviewJobRequest`) holds the project, the checkout's path, the head, the reviewer's role name, the resolved model (`ResolvedModel`: provider and model) and the prompt text, which is passed as it is, so its untrusted parts are fenced by whoever writes it.

1. **Provider:** `claude_code` allows `api.anthropic.com`, `codex` allows `chatgpt.com` (the host of a Codex subscription login), each alone (builder's choice): the review image installs nothing and the CLI talks to no other host. Any other provider is `No review job runs a reviewer on the provider <provider>` before anything else.
2. **Image:** `ReviewJobImages::imageFor(<project>)` reads the project's `review_job.image` from the owner's configuration (`ReviewJobConfiguration`, its own tree beside the projects tree, set by `config/packages/ai.php` as the parameter `ReviewServices::JOB_IMAGES`); a project without one is `The project "<project>" has no review job image`. The image is the one `intakt:job:build-image --kind=review` tagged ([Job images](job-images.md#the-review-job-image)); nothing checks here that it is one.
3. **Checkout:** resolved with `realpath`; a path that is no folder is an `InvalidArgumentException`. It must be a clone with a `.git` folder of its own (a worktree's `.git` file is refused by the script), made read-only by the job's mount.
4. **Prompt:** written to a file of its own, `var/prompts/review-<random>.md` (mode 0600), removed after the job, also when it throws. A worker that is killed removes nothing, so before a job stages its files it removes the `login-*` and `review-*` files in `var/prompts/` that are older than the job's time limit plus one minute, which no running job can still use.
5. **Job** (`JobRunner::run()`): the image; the read-only inputs, the checkout at `/input/checkout`, the prompt at `/input/prompt.md` and, for a job with a login, the login at `/input/login`; the command `/bin/sh -c <docker/job/review.sh> intakt-review /input/checkout <head> /input/prompt.md <provider> <model>` (and `/input/login` with a login), the script's text read from the project folder for each job; the allowlist of step 1; the limits 4 GiB of memory, 2 CPUs and 1800 seconds (builder's choice until T60); the job id `review-<first 40 hex digits of the SHA-256 of the length-prefixed project, head, reviewer and provider>`, so a second run of the same reviewer on the same head while one runs is refused as already running.
6. **Outcome**, read from the job's output only:
   - `The review job ran out of memory.` or `ran out of time.` when the engine stopped it, and `left an output the runner refuses to read.` for `JobOutputRefused`, whatever the output says;
   - an exit code other than 0 is `The review job refused to run the reviewer: <reason>.`, with the text of the last `refused: ` line of `review.log` (or `it exited with <code>`): the script sets that code only for a refusal before the CLI ran, and the CLI cannot set it;
   - otherwise the last `<provider> exited with <status>` line of `review.log`, which the script writes after the CLI ended, must say 0 (`The reviewer's CLI <provider> exited with <status>.`, or `did not report how ...` without one);
   - then `ReviewJobAnswer::read()` reads `answer`: for `claude_code` an event stream (`--output-format stream-json`) whose every line is a JSON object, whose answer is the last event with `type` `result`, when it has `is_error` false and a non-empty text `result`; for `codex` an event stream whose every line is a JSON object, whose answer is the text of the last completed `agent_message` item, and only when the turn holding that item ended with `turn.completed` (a `turn.failed`, a new `turn.started` or the end of the stream before it refuses the answer, and a later turn's `turn.completed` does not count). Anything else is `The reviewer's CLI <provider> gave no answer the review job can read.` The answer's text is untrusted: only its shape is checked here. Beside the text, the answer holds what the CLI's own events show, never the model's text: `readFiles`, the paths of `claude_code`'s reads: a `Read` call of a path under `/input/checkout` with no `..`, `.` or `.git` segment that got a `tool_result` whose `is_error` is missing or `false` (a string such as `"true"` does not count); `ReviewerInJob` counts a read only when one of these paths is a regular file (mode `100644` or `100755`) in the head's tree (`HeadClones::holdsARegularFileOf()`), so a link, a submodule or a path the head does not hold does not count; and `usage`, the usage of `claude_code`'s final `result` or of each `codex` `turn.completed`, read by the bridges' own extractors. An event whose usage has no figures, or a token count (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `cached_input_tokens`) that is not a whole number of zero or more, counts as no usage, so its call stays unsettled instead of being settled as zero or below what it spent;
   - a failure after the CLI ran (out of memory, out of time, no exit line, a failing exit, an unreadable answer) carries the usage the events report (`ReviewJobFailure::$usage`), which settles the call; with none, the call stays unsettled with `JobReportedNoUsage`. A refusal, a missing CLI or an output the runner refuses keeps its own reason. When the read check itself fails, the read counts as not confirmed and the usage still settles the call.

## In the container

`docker/job/review.sh <checkout> <head> <prompt file> <provider> <model> [<login file>]` (POSIX `sh`, with `env`, `sed`, `grep`, `find`, `git` and `claude` or `codex`) runs as the job's command after the [start check](job-containers.md#start-check). It writes `review.log` (each refusal as `refused: <reason>`, git's and the CLI's errors, then `<provider> exited with <status>`) and `answer` (the CLI's standard output as it wrote it) into `INTAKT_JOB_OUTPUT`. Any refusal exits with 1 before the CLI runs, and leaves no `answer`; otherwise the script exits with 0 whatever the CLI's status, so the CLI can never end the job with the code of a refused checkout. Five arguments are needed, and a sixth names the login file (`refused: usage: ...` otherwise).

1. **Environment.** Every exported `GIT_*` variable is unset before the first git call (the image may set `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_CONFIG_COUNT` and the like), and so is `NODE_OPTIONS`, which would load code into the CLI. Only `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1` and `GIT_ATTR_NOSYSTEM=1` are set, so git reads no global or system settings and no system attributes file.
2. **Proxy only.** `NO_PROXY`, `no_proxy`, `ALL_PROXY` and `all_proxy` are unset, so no request of the CLI bypasses the proxy. `HTTPS_PROXY` must be set, and `https_proxy`, `HTTP_PROXY` and `http_proxy` must equal it (`the job has no egress proxy`); `INTAKT_JOB_EGRESS` must not be empty (`the job has no egress allowlist`); and a job in its reduced mode is refused (`the start check failed: <INTAKT_REDUCED_MODE>`). The job's internal network has no way out but its proxy, which lets through only the allowlist.
3. **Provider and prompt.** `claude_code` or `codex`; any other value is `no reviewer CLI for the provider <provider>`. The prompt file must be a readable regular file (`the prompt cannot be read`), and a given login file a readable one that is not empty (`the login cannot be read`); with a login, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_BASE_URL` of the image are unset for the CLI.
4. **Git 2.40 or later.** `git --version` must print `git version <major>.<minor>...` with 2.40 or later (`the checkout checks need git 2.40 or later, found: <what it printed>`), because step 8 runs `status --attr-source`, which an older git refuses as an unknown option. Debian 12 (git 2.39) and Ubuntu 22.04 (git 2.34) install an older git, so a review image whose last stage is one of them is refused for every review; Debian 13 and Ubuntu 24.04 install 2.40 or later.
5. **Read-only.** `<checkout>` must not be a link (`the checkout is a link`), because `find` does not descend into a link it is given, so a link to a folder would hide every writable entry in it; the job mounts a real folder. `<checkout>/.git` must be a folder, not a link (`the checkout has no .git folder of its own`), and no file or folder in the checkout, its `.git` included, may be writable for the job's user (`the checkout is writable`), as on a read-only mount: `find <checkout> -exec` tests each entry with `[ -w ]`, which follows a link to its target, and an entry `find` cannot read refuses the checkout too. A writable file stays writable inside a read-only folder, so checking the two folders alone is not enough.
6. **Clone settings only.** `.git/commondir`, `.git/config.worktree`, `.git/objects/info/alternates` and `.git/info/attributes` are refused (`the checkout has .git/<file>`); `git clone` writes none of them, and attributes such as `ident` would let a changed file compare equal to the head. And `.git/config` must be a regular file. `git config --file .git/config --list` may hold only what `git clone` or `git init` writes on Linux: `core.repositoryformatversion` 0 or 1, `core.filemode=true`, `core.bare=false`, `core.logallrefupdates=true`, `extensions.objectformat` `sha1` or `sha256`, `remote.origin.url`, `remote.origin.fetch`, `branch.<name>.remote` and `branch.<name>.merge`; any other setting or value (an fsmonitor, a hooks path, a filter, an include, `core.filemode=false`) is `the checkout has a setting a clone does not write`, and git never runs it. A non-empty `.git/info/exclude` is not refused, because `git clone` writes one with comment lines.
7. **Exact head.** `<head>` must be a full commit id (40 or 64 lowercase hex digits, `the head is not a commit id`), and `rev-parse --verify --quiet HEAD^{commit}` of the checkout must print it (`the checkout is not at <head>`).
8. **No change.** Every git call on the checkout is pinned to it (`checkout_git`: `git --git-dir=<checkout>/.git --work-tree=<checkout> --no-replace-objects --no-optional-locks -c core.untrackedCache=false -c core.hooksPath=$TMPDIR/review-hooks -c core.attributesFile=$TMPDIR/review-attributes`), so a replace ref (`refs/replace/<head>`) cannot make git compare the checkout against another commit's tree, and nothing is written into the checkout. Before the first of these calls the script makes `$TMPDIR/review-hooks` an empty folder and `$TMPDIR/review-attributes` an empty file, anew (`the job folder cannot hold the empty hooks folder and attributes file` if it cannot): so no hook in the checkout's `.git/hooks` runs (`read-tree HEAD` would run a `post-index-change` hook), while the `*.sample` files `git clone` writes there are not refused; and git reads no attributes file outside the repository (`core.attributesFile` otherwise defaults to `$XDG_CONFIG_HOME/git/attributes` or `$HOME/.config/git/attributes`, read even with `GIT_CONFIG_GLOBAL` set), where `* text eol=lf` or `* ident` would let a changed tracked file compare equal. Its index is not trusted either, because flags such as `skip-worktree` or crafted file times could hide a change: `read-tree HEAD` writes a fresh index to `$TMPDIR/review-index`, which every check below uses (through `GIT_INDEX_FILE` on those calls only) and which is removed afterwards.
   - Every folder the head holds as a submodule (a gitlink: mode `160000` in `-c core.quotePath=false ls-files --stage` of the fresh index) must be a real folder, not a link, with no entry in it (`find <folder>/. ! -name . -prune -print` prints nothing), which is what a clone leaves there (`the checkout has a submodule folder that is not an empty folder`). This is checked before `status` runs, because `status` starts git inside a repository it finds in such a folder, and that git runs the nested repository's own settings (an fsmonitor), which step 6 does not read; and neither `status` nor `ls-files --others` looks at a file in such a folder, so a planted one would stay hidden. A submodule path git prints quoted (one with a control character, a double quote or a backslash) is refused (`the head has a submodule path with a character git quotes`), because the quoted form is not the folder's name and an empty folder with the quoted name could stand in for the real one.
   - `status --porcelain --untracked-files=no --ignore-submodules=none` must print nothing: a changed, deleted or added tracked file is `the checkout differs from the head`. It runs with `--attr-source=<empty tree>` (the id `hash-object -t tree --stdin` gives for the repository's object format), so the head's `.gitattributes` cannot normalize a change away either (`ident` hiding text inside `$Id: ... $`, `eol` hiding carriage returns). In turn a head whose attributes rewrite content on checkout (`ident` with a `$Id$` keyword, `eol=crlf`, `working-tree-encoding`, or a `filter` such as a Git LFS smudge filter that rewrote the files when the checkout was made) is refused even when unchanged; `text` with `eol=lf` on Linux is not, as it writes the content unchanged.
   - `ls-files --others --exclude-per-directory=.gitignore` must print nothing (`the checkout has untracked files`). It reads only the `.gitignore` files in the checkout, never `.git/info/exclude` or a global excludes file, so `*` in `info/exclude` hides nothing; a file the head's `.gitignore` ignores, such as `vendor/`, is allowed.
   - A `.gitignore` the head does not hold could ignore itself and what it hides, so `ls-files --others --ignored --directory --exclude-per-directory=.gitignore` must list no `.gitignore` (`the checkout has a .gitignore the head does not hold`). An ignored folder such as `vendor/` is listed as one entry, so a package's own `.gitignore` in it is allowed.
9. **The CLI** runs in the checkout (entered in a subshell whose input, output and error files are opened first, so relative paths keep naming the same files) with the prompt file on its standard input:
   - `claude_code`: `claude -p --model <model> --output-format stream-json --verbose --tools Read,Grep,Glob --permission-mode dontAsk --allowedTools 'Read(//input/checkout/**)' --disallowedTools <rules> --setting-sources '' --strict-mcp-config --no-session-persistence`, with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`: only reads of the checkout (a read rule covers `Grep` and `Glob` too), because `dontAsk` refuses what no rule allows, a committed link out of the checkout included. The `--disallowedTools` rules are `Read` rules for the login and prompt files, the output folder, `HOME`, `/proc`, `/dev` and `/sys`. And no user, project or local settings and no MCP server. `stream-json` with `--verbose` writes each event as a line, so the answer shows the CLI's `Read` calls and their results, and the usage of its final `result`.
   - `codex`: `codex exec --json --sandbox read-only --ephemeral --ignore-user-config --ignore-rules --disable <feature>... --model <model> --config web_search="disabled" -`, the same features switched off as for the in-process Codex reviewer (`IsolatedCodexCli`): `shell_tool`, `unified_exec`, `apps`, `plugins`, `browser_use`, `in_app_browser`, `computer_use`, `multi_agent`, `image_generation`, `view_image` and `hooks`.

`HOME` and `TMPDIR` are the job's own tmpfs work area.

## Open

These are decided by the runner's issue (part 2 of #1650), not here: how a `codex` reviewer reads the checkout while its shell tools are off; whether `--setting-sources ''` keeps a `CLAUDE.md` or `.claude/` folder of the head out of Claude Code's prompt; how far Claude Code's `Read` tool reaches outside the checkout; and the statement that the review image is built from main's tree, not from the head under review.

## Tests

`tests/Core/Review/ReviewScriptTest.php` runs the real `docker/job/review.sh` with `sh -c` on a temporary clone made read-only by removing every write permission bit (skipped for the superuser, who ignores them), with scripted `claude` and `codex` on the path. It covers the CLI's arguments, folder, input and answer for each provider (the Codex features compared with `IsolatedCodexCli`'s list), each refusal above with the CLI not running, a stand-in `git` reporting 2.39.5, 1.50.0 or no version (refused) and 2.40.0 or 3.0.1 (allowed), a writable tracked file and a writable folder inside a read-only checkout, a link to a read-only checkout holding a writable tracked file, `* ident` in `info/attributes`, carriage returns under `* text eol=lf` in `$XDG_CONFIG_HOME/git/attributes` and a changed `$Id: ... $` under `* ident` in `$HOME/.config/git/attributes`, executable `post-index-change` and `post-checkout` hooks in `.git/hooks` that never run (the review allowed), a changed `$Id: ... $` under the head's own `* ident` and carriage returns under its own `eol=lf` (an unchanged checkout under `eol=lf` allowed, one under `* ident` refused), a replace ref for the head pointing at a commit whose tree matches a changed checkout, `*` in `info/exclude` with a planted untracked file, a planted self-ignoring `.gitignore`, a `skip-worktree` flag hiding a change, a head with a submodule (an unchanged clone allowed, also with a space and a non-ASCII letter in the submodule's path; refused: a repository planted in the submodule folder, whose fsmonitor command never runs, a planted file, a link in place of the folder, a missing folder, and a path git quotes), an fsmonitor whose command never runs, exported git variables that do not reach git, and the CLI's environment without `GIT_*` variables (but the three settings), `NODE_OPTIONS` or a proxy bypass.

`tests/Core/Review/Infrastructure/ReviewJobTest.php` runs `ReviewJob` with a stubbed `JobRunner`, because the build sandbox has no Docker daemon: the inputs, command, image, allowlist per provider, job id (also that `ab`/`c` and `a`/`bc` give two ids), the prompt file's removal, and each failure above. `ReviewJobInContainerTest` runs `ReviewJob` through the real `ContainerJobRunner`, `DockerEngine` client and `EgressProxy` against the scripted engine `tests/Core/Job/FakeDockerEngine.php`: the checkout is a read-only bind mount under a read-only root, the job sits only on its internal network, its proxy's Squid configuration allows `api.anthropic.com` alone and denies the rest, and a refused tunnel to another host in the proxy's log is recorded as `JobEgressRefused`. `ReviewJobAnswerTest` covers each answer shape refused for both CLIs, `ReviewJobConfigurationTest` the configuration tree and the images, and `tests/Application/ProjectTiersTest.php` the `review_job` section through the booted container. No review job has run against a live engine yet.
