## Container image

CI builds the image and runs its smoke test (below) on main and on every pull request that changes more than `docs/`, `tests/` or `upstream/`: the `image` job ([CI](ci.md)).

Every release publishes the image to `ghcr.io/shinyredapples/intakt` ([releasing](../releasing.md#the-container-image)).

Plan task T22, part 1. `Dockerfile` (multi-stage) builds on `dunglas/frankenphp:1.13.4-php8.5-trixie` (ZTS), pinned by digest (`DockerfileTest` fails for a FrankenPHP below 1.13.4 here and in `.github/ci/Dockerfile`), fails to build below PHP 8.5.12, installs with `composer install --no-dev`, warms the `prod` cache and runs as user 10001. `docker/entrypoint.sh` takes `APP_SECRET` and `MERCURE_JWT_SECRET` from the environment, or makes an empty one once and keeps it beside `INTAKT_CONFIG` on the data volume (see [the demo](demo-with-docker-compose.md); with neither a value nor `INTAKT_CONFIG` it names the missing one and stops; nothing secret is in an `ENV` line or a layer) and `MERCURE_JWT_ISSUER`, which the Dockerfile defaults to `http://localhost:7781` and the Caddyfile reads without a default, naming a missing one; it runs `doctrine:migrations:migrate`, then, on every start that is not the demo's (which rebuilds around its seed), rebuilds the container: it removes the kernel's cache folder (`var/cache/<environment>`, or `$APP_CACHE_DIR/<environment>` when that is set, a relative one under `/app`) and, when `APP_BUILD_DIR` is set, `$APP_BUILD_DIR/<environment>`, where the kernel then compiles the container, then runs `cache:warmup` in a new process. The environment and both folders are read with an inline `php -r` that boots Symfony Runtime's `SymfonyRuntime` with the runtime options `bin/console` gets (`APP_RUNTIME_OPTIONS`, so a `dotenv_path` is followed), the working folder as the project folder: a value in the environment wins, and a folder or an `APP_ENV` named in a dotenv file (such as `.env.prod.local`) counts too. The environment is always `APP_ENV`, also when an `env_var_name` runtime option names another variable, because `bin/console` passes `APP_ENV` to the kernel. The read prints the three values as `NAME=value` lines, and the start ends before anything is removed or warmed up when a dotenv file cannot be parsed, when the environment is empty or holds a `/`, when `APP_ENV`, `APP_CACHE_DIR` or `APP_BUILD_DIR` holds a control character (U+0000 to U+001F or U+007F, so a newline, a carriage return, a tab or a NUL byte from `.env.local.php`; the read names the variable and prints nothing, because a line break would read as two values and bash drops a NUL byte, so either would name another folder), or when bash does not get exactly those three lines in that order. It does so on every start, not only on one with a project file, because `config/packages/ai.php` reads the project file only while the container is compiled: the image compiled its own without one, and a restart after the file was changed or removed would otherwise keep the projects the last start compiled. A failed rebuild ends the start (`EntrypointSampleSeedTest`: with `INTAKT_CONFIG`, with the default file, after the file was removed, with `APP_BUILD_DIR`, with a relative `APP_CACHE_DIR`, with either one set in `.env.test.local`, with `APP_BUILD_DIR` in the file a `dotenv_path` runtime option names, with `APP_ENV` and `APP_BUILD_DIR` set in `.env.local`, with the environment's `APP_BUILD_DIR` winning over the dotenv file's, with an `env_var_name` runtime option beside `APP_ENV`, a dotenv file that cannot be parsed, an `APP_CACHE_DIR` or `APP_ENV` of two lines, an `APP_BUILD_DIR` with a carriage return, a read that prints other than the three named lines, and a failed warmup); then `frankenphp validate --config Caddyfile --adapter caddyfile` (so a rejected Caddyfile prints its reason), then starts the processes below. `.dockerignore` keeps `.git`, `var/`, `vendor/`, `.env.local`, `.env.local.php`, every `.env.*.local` and `intakt.env` out of the context. SQLite and the hub's Bolt file are in `/app/var/data`, which every documented run mounts as a volume; the image declares no `VOLUME`, because it is also Intakt's own job image and the job runner refuses an image that declares one ([Job images](job-images.md#limits)).

- **Workers:** the Caddyfile's `php_server` declares `app` (`public/index.php`) and `mcp` (`public/mcp.php`, `match /mcp/*`, `max_threads`). Both set `FRANKENPHP_WORKER=1`, which makes Symfony Runtime pick `FrankenPhpWorkerRunner`. `public/mcp.php` only returns `public/index.php`, because FrankenPHP refuses two workers on one file.
- **Per-worker limits:** FrankenPHP 1.13.4 has `max_wait_time` only in the global `frankenphp` block, so it is shared by both workers; `num` and `max_threads` are the mcp worker's own. A `match` worker can only be declared inside `php_server`.
- **Admin API:** `localhost:2019` (the `CADDY_ADMIN` default), unpublished; the Caddyfile's global `metrics` option is on, because FrankenPHP adds its `frankenphp_*` series to the admin API's `/metrics` only then. `CaddyfileTest` checks the adapted `admin.listen` and `apps.http.metrics`; `AdminApiExposureTest` checks the shipped files: the Caddyfile's one `admin` line defaults to `localhost:2019`, no `Dockerfile`, `compose.yaml`, `.env`, `.env.dist` or `docker/entrypoint.sh` sets `CADDY_ADMIN`, the image exposes only 7781, compose publishes only `127.0.0.1:7781:7781`, and `.env`'s `FRANKENPHP_ADMIN_URL` is `http` on a loopback host. The Caddyfile hands `CADDY_ADMIN` to Caddy as it is, and Caddy binds a bare port such as `:2019` on every interface, so `docker/entrypoint.sh` stops the start, before anything else runs, unless the value is unset, empty or `<host>:<port>` with the host `localhost`, `127.0.0.1` or `[::1]`; it prints `intakt: CADDY_ADMIN must be a port on localhost, 127.0.0.1 or [::1] (for example localhost:2019); the value set was refused`, without the value itself, because a pasted URL may carry a password (`EntrypointSampleSeedTest`). **Development installs:** FrankenPHP run directly on the Caddyfile, without the entrypoint, has no such guard and binds `CADDY_ADMIN` as given, so keep it unset or on loopback there.
- **PHP extensions:** the base stage has no list of its own: it copies `composer.json` and installs, with `install-php-extensions`, each `ext-*` entry under `require` that the base image does not load, plus `opcache`, which is no profile entry and is there for serving. The build fails when the copied `composer.json` does not parse or its `require` is missing or a plain value instead of an object (the script that lists the extensions exits non-zero, and the build assigns its output to a variable before the install so `set -eu` stops it), and when a profile extension or `opcache` is still not loaded after the install. The CI image instead installs a fixed list before it copies `composer.json`, then runs the same script once after the copy as a check: its build fails on the same broken `composer.json` and when a profile extension is not loaded, naming each one ([CI](ci.md)). The image keeps PHP's production settings and does not load `config/gates/php/check.ini`. `DockerfileTest.php` checks that the install names only `opcache` beside the profile, runs the image's script against a sample `composer.json` (it names each required extension that is not loaded, and nothing else, and exits non-zero on broken JSON or a `require` that is missing or a plain value), checks that this image runs that script in a plain assignment before the install and again before the re-check and that the CI image runs it in a plain assignment before its check, and checks both build failures, that the profile has `pcntl` and that the check ini is not copied in.
- **Tests:** `tests/Core/Dashboard/Infrastructure/CaddyfileTest.php` adapts the Caddyfile and checks both workers; `CaddyfileWorkersTest.php` beside it (group `hub`) runs FrankenPHP on the Caddyfile with a migrated scratch database and reads the request counts per worker file from the admin API's `/frankenphp/threads`, polled for up to 10 seconds because FrankenPHP counts a request only when the worker has finished it, after its answer is sent: on one server, `GET /projects` answers 200 from the `app` worker and then `POST /mcp/owner` is served by the `mcp` worker (the home of the app-worker fact; the memory-ceiling test keeps a server of its own). `DockerignoreTest.php` checks that the env files stay out of the build. `EntrypointTest.php` runs `docker/entrypoint.sh` with `bash`, as the container does, and checks that a missing required value (`MERCURE_JWT_ISSUER` as the case) is named on stderr with a non-zero exit and nothing on stdout, and that it checks every value the Caddyfile reads without a default; `ComposeDemoTest` proves the env template lists the secrets the entrypoint requires.
- **Restarts (part 2):** the `Dockerfile` sets `FRANKENPHP_LOOP_MAX=500`, which Symfony Runtime's `FrankenPhpWorkerRunner` reads, so a worker leaves its loop after that many requests. `Core/Server/Infrastructure/EndWorkerOnMemoryCeiling` is a `kernel.terminate` listener (priority -1024, after the response is sent and the other listeners ran): inside a worker (`FRANKENPHP_WORKER` in the request's server bag) it ends the worker when `memory_get_usage(true)` is above `WORKER_MEMORY_CEILING_MB` (exactly at it keeps serving). The end is `exit(0)`, which FrankenPHP replaces without counting a failure, so `max_consecutive_failures` (default 6, not set in the Caddyfile) is only for crashes. The reading and the exit are constructor closures a test replaces; the listener keeps no state. `CaddyfileWorkersTest` proves against a running FrankenPHP (ceiling 1 MB) that repeated requests all answer 200, the server keeps running and the worker is replaced: the admin API's `/frankenphp/threads` then reports that it holds less than the ceiling (`MemoryUsage`, a new worker before its first request), where a kept worker holds its booted kernel. The thread's `RequestCount` is not the sign: since Symfony Runtime 8.1.11 runs `terminate` inside FrankenPHP's request callback, a worker that exits there is never counted.
- **Health check:** `HEALTHCHECK` runs `docker/healthcheck.sh` (installed as `intakt-healthcheck`) every 30 seconds from the working directory `/app`; it runs `php bin/console intakt:server:health` (see [Server status](server-status.md), with `FRANKENPHP_ADMIN_URL` always set from the listener, `http://$CADDY_ADMIN` or `http://localhost:2019` when `CADDY_ADMIN` is unset or empty, overriding any `FRANKENPHP_ADMIN_URL`, so the check reads the listener of its own server; a bare port such as `:2019` becomes `localhost:2019`) and asks `curl` for the dashboard at `http://localhost:$SERVER_PORT/` (default 7781) with the header `Host: localhost:$DASHBOARD_PORT`, because the dashboard checks the port the owner publishes while the server listens on `SERVER_PORT`, and when `INTAKT_SAMPLE_REPOSITORY` is set it also needs `var/sample-ready`, which the entrypoint removes at every start and writes after the seed. Three failures make the container `unhealthy`. `HealthcheckScriptTest` runs it with stand-ins for `curl` and `php`; `HealthcheckHubTest` (group `hub`) runs it from the project root against a running FrankenPHP and expects `healthy`. The restart policy is a `docker run` flag (`--restart unless-stopped`), not part of the image.
- **Restart tests:** `tests/Core/Server/Infrastructure/EndWorkerOnMemoryCeilingTest.php` forces the memory reading with a stub (below, at and above the ceiling, and outside a worker); `tests/Core/Dashboard/Infrastructure/DockerfileTest.php` checks the loop maximum, the ceiling and that the health check runs the script.
- **Processes (part 3):** `docker/entrypoint.sh` (bash, PID 1) starts `frankenphp run --config Caddyfile --adapter caddyfile`, `MESSENGER_CONSUMERS` (`Dockerfile`: 3) `messenger:consume async` and one `messenger:consume scheduler_watcher scheduler_retention` (the watcher tick and the conversation retention task, see the conversation store in [Reviewer agent](reviewer-agent.md)), each consumer with `--memory-limit=${WORKER_MEMORY_CEILING_MB}M --time-limit=3600 --quiet`. `--quiet` drops Symfony's start banner (the `[OK] Consuming messages` line on stdout and its comments on stderr), which nothing lets the script wait for and which followed the dashboard address line (`EntrypointSampleSeedTest`); an error the command throws is still printed. The consumers run with plain `php`, not `frankenphp php-cli`, until T28's SIGTERM probe (#35) passes on 1.13.4. A loop that sleeps one second and then checks every child with `kill -0` starts an ended consumer or scheduler again within a second, whatever its exit status, taking the status with `wait <pid>`; it does not block on `wait -n`, because bash reaps a child killed by a signal while a command runs and `wait -n` then no longer knows it ("no such job") and blocks on the live children, so a consumer ending while another is started again, or several ending together, are all started again (`EntrypointProcessesTest` forces both orders). It logs `intakt: <transport> ended with status <n>, starting it again` on stderr. When `frankenphp` ends, the script stops the others and exits with its status, so Docker's restart policy restarts the container. On SIGTERM or SIGINT it stops every child and exits 0. Stopping takes the children from bash's job table (`jobs -p`), not from the script's own list of recorded pids, because bash runs the trap between starting a child and recording its pid, and a child missed there would get no signal and hang the final `wait` past Docker's stop timeout. It sends SIGTERM, waits up to 8 seconds (inside Docker's 10 second stop timeout; a deadline taken from `/proc/uptime`, which a wall clock step cannot move, checked between pauses of a tenth of a second, because a count of pauses grew past the stop timeout on a loaded machine: `EntrypointSampleSeedTest` forces it with a `sleep` stand-in that makes the stop's pauses take three times as long) and then sends SIGKILL to what still runs, because a consumer ignored an early SIGTERM (one that arrived before its worker existed) until 8.2.0-BETA2 (`upstream/messenger-consume-ignores-early-sigterm`, fixed by Intakt's pull request symfony/symfony#67912); the lock now has the fix and the script keeps the SIGKILL as a safeguard; the image installs `pcntl`, so a running worker finishes its current message first. Bash runs the trap only after a foreground command ends, so the poll's `sleep 1` and the demo's readiness calls run as jobs the script waits for (`as_job`), and the stop starts at once (see [the demo](demo-with-docker-compose.md)). Supervisor was not used: the image would need Python, and the loop is all that is needed.
- **Process tests:** `tests/Core/Dashboard/Infrastructure/EntrypointProcessesTest.php` runs the real entrypoint against stand-ins for `php` and `frankenphp` in `PATH` (bash scripts that loop over `sleep` without `exec`, so `/proc` keeps their arguments, beside a `sleep` stand-in that runs the entrypoint's one second poll for a tenth of a second and leaves its 0.1 second stop steps, so the 8 second grace stays; they end on SIGTERM and can be stopped with SIGSTOP; the `php` stand-in ends the migration, the start's inline `php -r` that reads the kernel's environment and folders (it prints `APP_ENV=test`, `APP_CACHE_DIR` with the test's folder and an empty `APP_BUILD_DIR`), and the start's `cache:warmup` at once, and `APP_CACHE_DIR` points into the test's own folder, so the rebuild removes nothing in the checkout; no database, migration or `frankenphp` binary is needed) and reads its children from `/proc`: the web server, two `async` consumers and the scheduler run, the consumers under `php` (one test, both facts); a consumer or the scheduler killed with SIGKILL is replaced; SIGTERM ends every child and exits 0, also when a consumer cannot act on it (stopped with SIGSTOP), and also when it lands between starting the first child and recording its pid (forced with a bash `DEBUG` trap over the sourced entrypoint); a killed `frankenphp` stops the others and the entrypoint exits 137. `DockerfileTest.php` checks `MESSENGER_CONSUMERS` and `pcntl`.
- **Worker-mode state (plan task T29, part 1):** `tests/Application/WorkerModeTest.php` (group `persistence`) boots one kernel and never reboots it, sends requests through `tests/Application/WorkerBrowser.php`, a `KernelBrowser` with `disableReboot()` (it terminates the kernel after each request, as the worker loop does), and reads what the services hold with `WorkerState` after running the kernel's `services_resetter` itself, which is what the next `handle()` does after a terminate (so it also resets after a reviewer run, which is not a request). It shows that the user of a bearer-token request (`security.token_storage`), the entities in the entity manager's identity map (`doctrine`), another browser's flash messages (one session per browser) and the messages of an earlier reviewer conversation (`ReviewerRuns` over the `reviewer_conversation` store, a scripted platform) do not reach the next request. No application service needed a new `ResetInterface`: the `intakt.statefulService` rule keeps them stateless. One test per runner mode (one kept kernel, a kernel cloned per request) shows that a request's umask, locale and environment variable do not reach the next request, and a negative test with `UnrestoredKernel` shows they do without `ProcessSettings`. Three tests run `tests/Application/WorkerKernel.php`, a kernel built like Intakt's (the same compiler passes, from `Kernel::addApplicationPasses()`) with the `kernel.reset` tag removed from `doctrine` or `security.token_storage` (`KeepStateOf`), and show the leak appears without that reset: the entities, the user, and the user again after a reviewer run. The Symfony AI services are part 3, below.
- **Process settings and kernel reset modes (plan task T29, part 2):** `umask()`, the locale and `$_ENV` belong to the worker process, so they outlive a request, also when `FRANKENPHP_RESET_KERNEL=1` makes `FrankenPhpWorkerRunner` clone the kernel after each request (the clone boots a container of its own, but shares the process). `Intakt\Kernel` takes a `Core/Server/Infrastructure/ProcessSettings` (umask, `setlocale(LC_ALL, '0')`, the whole `$_ENV`) at its first `boot()`, once per worker before the first request and after the bundles booted (FrameworkBundle's `boot()` adds `DOCTRINE_DEPRECATIONS` to `$_ENV`), and restores it in `terminate()` after the terminate listeners, also when one throws; the runner terminates before it clones, and a clone carries the same snapshot, so the next request starts clean in both modes. It is a kernel property, not a `kernel.reset` service, because a service would be built anew in a cloned kernel's container, after the leak. `WorkerBrowser` reads `FRANKENPHP_RESET_KERNEL` once from `$_SERVER`, as the runner does, and clones its kernel after each request when it is true. The user, review credential and identity map tests and the process tests run in both modes (`runnerModes`: one kept kernel, a kernel cloned per request); the rest run with the kept kernel only: the flash tests replace container services that a clone does not carry, the reviewer runs are not requests, and a clone would hide the leaks the `WorkerKernel` tests show. The process tests change the umask, the locale or an `$_ENV` entry inside one request and read them inside the next: `WorkerBrowser::requestRunning()` puts a step on its next request as a request attribute, and `tests/Application/RunRequestStep.php`, a `kernel.request` listener (`#[AsEventListener]`, priority 4096) that `tests/Support/services.yaml` autoconfigures in the test container, runs it ahead of every other listener (a listener added to the compiled dispatcher at runtime is deprecated since Symfony 8.2). `tests/Application/UnrestoredKernel.php`, Intakt's kernel without the restore, shows all three leaks in both modes. The image sets no `FRANKENPHP_RESET_KERNEL`, because the clone would hide the leaks of services this test looks for.
- **Symfony AI reset probe (plan task T29, part 3):** `tests/Application/SymfonyAiResetTest.php` (group `persistence`) runs reviewer work twice in one kernel and runs the kernel's `services_resetter` in between, as the next request would. `tests/Application/AiPlatformKernel.php` is Intakt's configuration plus one generic platform (`ai.platform.generic.probe`) whose HTTP client answers from `ProviderAnswers`, which keeps every request body, because the test install has no account and so no bundle platform. Two `ReviewerRuns` agents on that platform, the first with `model-a?temperature=0.2`, a tool `first_tool` and its own stored conversation, the second with `model-b`, `second_tool` and another conversation: the second call carries only its own model, tools and messages, and no temperature. Two review rounds list their tools through the container's MCP toolbox (`ai.toolbox.reviewer.mcp.reviewer.review`) against a second kernel that serves `/mcp/review`: each round connects afresh and lists the tools itself (`server/discover`, `tools/list`). With the `kernel.reset` tag removed (`WorkerKernel`), the second round reuses the first one's connection (`mcp.client.reviewer.server.review`) or gets the first one's tool list without asking the server (the toolbox). `AiServiceState` walks every object behind the container's Symfony AI and MCP services (definitions with a `Symfony\AI\` or `Mcp\` class, or an `ai.` or `mcp.` id, read from the container the framework serializes beside its debug dump; lazy proxies are initialized), records each property by content under every path from a service that reaches its object (service id, then property names and array keys; an object is skipped only while it is an ancestor on the current path), so an object a reset put in place is compared with the one it replaced, and an object two references share and a reset replaced behind one of them is still compared behind the other. A property only one of the two walks recorded counts as changed too (new or gone), at a path only that walk reached (for example a cycle replaced by an object of the same class that holds state) as well as at a path both reached (for example an object replaced by one that keeps its properties and adds one holding a message), because two equal rounds with a reset between them reach the same objects. The test compares a reviewer run with an MCP tool listing before and after a second one: what differs after the reset is the list of state a request leaves behind. It holds two judged entries: `Mcp\Client\State\ClientState::$requestIdCounter` (counts on across connections; JSON-RPC ids only have to be unique) and `Symfony\AI\Platform\Provider::$resolvedModel`, a leak at v1.0.0-BETA1 (`upstream/ai-platform-provider-keeps-resolved-model/`, fixed on `main`) that Intakt does not reach, because its router calls `supports()` right before `invoke()`. A new entry fails the test until it is judged. The same walk also lists every property a request could write, also on paths the two runs do not take (structured output): each non-static, non-readonly property of a reached object that does not implement `ResetInterface`. The test holds that list with a judgment for each: set up from configuration, a cache with the same content for every request, the reviewer's MCP connection (closed by `ServerConnection::reset()` and written afresh by the next connect), cleared by the library when the call ends or the next one starts (`PlatformSubscriber::$outputType` and `$objectToPopulate`, the MCP server's per-request maps), written afresh by every `getTools()` (`ChainToolbox::$owners`), a harmless counter, or the `Provider::$resolvedModel` leak. A property missing from the list, or listed but no longer found, fails the test. `tests/Application/AiServiceStateTest.php` checks the walk itself. No Intakt service changed.

- **Smoke test:** build the image (`docker build -t intakt:local .`), then run `docker/smoke-test.sh intakt:local` (any image reference works).
