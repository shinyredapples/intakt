## The demo recording

Issue #2056 (part 1 of #1944). A recording is one file that holds the ledger events and the live dashboard updates of one real review of a change, with the moment the review started, the models it called and the Intakt version that wrote it. The demo project it is replayed into exists on the compose demo, `intakt:demo:remove` removes it with the replayed rows (below), and the replay writes its ledger events there and publishes its live updates through the dashboard's publisher (both below); the `/demo` page plays it from the dashboard with a caption of each stage (issue #2058, below). The flag that marks a project and its rounds as a replay is stored by the Review module ([Review flow](review-flow.md#a-replay)).

### Capturing the live updates

The ledger holds no live updates, so they are captured while the review runs. `Core/Dashboard/Infrastructure/CapturingLiveUpdates` decorates `Core/Dashboard/Contract/LiveUpdates` (`#[AsDecorator]`; `MercureLiveUpdates` is the alias it decorates, `#[AsAlias]`). With `INTAKT_LIVE_CAPTURE` empty (`.env` sets it so) every update goes to the hub as before and nothing is written. When the variable names a file, the capture waits for the Symfony Lock `dashboard-live-capture` and, holding it, sends the update to the hub and then appends it to the file as one JSON line (`at`, `topic`, `data`: the moment from the clock, the topic and the Turbo stream) with Symfony Filesystem's `appendToFile()`. One lock across both steps, because every web and queue worker publishes and appends, and two workers stepping between each other's publish and append would capture their updates in the other order than the hub received them. A lock that cannot be taken or a capture that cannot be written logs the warning `A live dashboard update was not captured.` and the update is still published, so the work that published goes on, as for a hub that is down; a lock that cannot be released logs `The live capture lock was not released.`

### Writing the recording

`Core/Dashboard/UseCase/RecordDemo/RecordDemoCommand` (`intakt:demo:record <project> <change> <recording>`):

1. `Infrastructure/ReplayedReviewRows::of()` (shared with `intakt:demo:remove` below) reads the ledger in order. The rounds are the `review_started` rows (read through the dashboard's `RoundPayloads::startOf()`) of that project and change. A row belongs to the review when its payload's `round` is one of them, or, when it has no `round` key, its `call` is a model call whose `usage_recorded` row of phase `started` names one of them (a settled usage names only its call). The models are the distinct non-empty `model` values of those started calls, in the order first called.
2. With no round, it prints `No review round of change <change> in project <project> is in the ledger.` and exits 1.
3. `CapturedUpdates` reads the capture file `INTAKT_LIVE_CAPTURE` names and keeps the updates whose topic is a round's topic (`MercureRoundUpdates::topicOf()`, `review/rounds/<round>`), in capture order. It exits 1 without writing when the variable is empty (`Set INTAKT_LIVE_CAPTURE to the file the live updates were captured in.`), the file cannot be read, a line is not a captured update (`Line <n> of <file> is not a captured live update.`, empty lines are skipped) or a round has no update (`<file> holds no live update of review round <round>.`, checked per round, so a capture started after the first round is refused rather than recorded without that round's live stream).
4. The recording is written with Filesystem's `dumpFile()` (a temporary file renamed into place); a file that cannot be written exits 1 with the reason. It prints `Recorded <n> ledger events and <n> live updates of <n> review rounds into <file>.`

### The format

`RecordingFormat` is the one home of both formats; it uses the `stored` serializer (snake_case keys) and writes every moment as `Y-m-d\TH:i:s.uP` in UTC, so rows and updates of one second keep their order. The recording is pretty-printed JSON with a trailing newline:

| Key | Holds |
|---|---|
| `reviewed_at` | the moment of the first round's `review_started` row |
| `intakt_version` | Composer's root package version, with `@<commit>` when Composer knows the commit (`dev-main@<sha>` in a checkout) |
| `models` | the models the rounds called |
| `project`, `change` | as given to the command |
| `events` | each row as `id`, `kind` (the `LedgerEventKind` value), `payload` (the stored text, unchanged) and `recorded_at` |
| `updates` | each captured update as `at`, `topic` and `data` |

`RecordingFormat::read()` turns a file that is not a recording (not JSON, a missing key, an unknown event kind, a model that is not text, a moment in another form) into `RecordingIsMalformed`; a recording read back writes the same text again.

### The demo project

Issue #2301 (part 1 of #2077). `Core/Dashboard/UseCase/CreateDemoProject/CreateDemoProjectCommand` (`intakt:demo:create`) creates the project recordings are to be replayed into: `CreateDemoProjectCommand::NAME`, `demo-replay`, separate from the seeded `sample` project. A project exists in Intakt only through the rows that name it, so creating it means marking it: the command dispatches Review's `Contract\FlagProjectAsReplay` on the command bus, which stores the existing replay flag and adds no table or column of its own; a second run finds the project flagged and stores nothing. It prints `The demo project demo-replay is marked as a replay: its reviews never count as a verdict.` and exits 0.

It runs only on the compose demo, recognized by a non-empty `INTAKT_COMPOSE_SERVICE` (`compose.yaml` sets it; `.env` sets it empty for every other install). `INTAKT_SAMPLE_REPOSITORY` is not the signal, because a plain `docker run` of the image sets it too (the CI smoke start in `docker/verify-first-start.sh`). With the variable empty it prints `The demo project is created only on the compose demo, and INTAKT_COMPOSE_SERVICE is empty on this install.`, dispatches nothing and exits 1. `docker/entrypoint.sh` calls it in the demo branch after the second container rebuild, only when `INTAKT_COMPOSE_SERVICE` is set ([Demo with docker compose](demo-with-docker-compose.md)).

### Replaying the ledger events

Issue #2302 (part 2 of #2077), with the live updates from issue #2373 (part 1 of #2303). `Core/Dashboard/UseCase/ReplayDemo/ReplayDemoCommand` (`intakt:demo:replay <recording> [--factor=<n>]`, `--factor` a float, default 1):

1. With `INTAKT_COMPOSE_SERVICE` empty it prints `A recording is replayed only on the compose demo, and INTAKT_COMPOSE_SERVICE is empty on this install.` and exits 1, the same signal `intakt:demo:create` reads, so a replay writes only on the install where the demo project exists. A factor that is not finite or not above 0 prints `The factor must be a number above 0.` and exits 1; a value that is no number is refused by the Console's float option itself.
2. It reads the file with Filesystem's `readFile()` and `RecordingFormat::read()`; a file that cannot be read or is malformed exits 1 with the reason.
3. `ReplaysRecording::replay()` takes the Symfony Lock `dashboard-demo-replay` without waiting and without a lease (`ttl: null`, since a replay at the recorded pace can outlast any lease) and holds it to the last step; a busy lock is `ReplayIsRefused` (`Another replay is running; start this one when it has ended.`). Holding it, it first refuses when the demo project is not flagged as a replay (read through `Infrastructure/ReplayMarks::ofProject()`; `The demo project demo-replay is not marked as a replay, so nothing is replayed; create it with intakt:demo:create first.`), because rows replayed after `intakt:demo:remove` took the flag away would read as a live review; then a recording with a captured update whose topic is blank (`Captured update <n> of this recording has no topic, so nothing is replayed.`), because the live event would throw partway through; then it reads the ledger's `review_started` rows and refuses a recording whose `review_started` row names a `round` the ledger already holds (`The ledger already holds review round <round> of this recording, so it is not replayed again.`), before any append: a second replay would merge into the first one's review pages, and a round stored live on the recording install would keep its live mark, because the dashboard reads a stored round's own mark before its project's ([Review flow](review-flow.md#a-replay)); then it reads the ledger's `usage_recorded` rows and refuses a recording whose `usage_recorded` row names a `call` the ledger already holds (`The ledger already holds model call <call> of this recording, so it is not replayed.`), because a call's settled usage names only its call, so another project's usage would count as the demo project's and go with it on removal.
4. It plays one timeline: the recorded events (by `recorded_at`) and the captured updates (by `at`) merged, each list kept in its own recorded order, and an event before an update of the same moment, so the page an update changes already finds that row. Each step is due at the replay's start (the clock's moment when the steps begin) plus the time between the timeline's first moment and its own, in microseconds, divided by the factor. Before each step it calls `ClockInterface::sleep()` with only the time still left until that moment, so the time an append takes is not added to the gaps after it; the first waits 0, and a step whose moment has already passed (an earlier append took longer, or it was recorded before the first step) follows at once. An event is appended through `Ledger\Contract\Ledger::append()`; the ledger stamps each row with its own clock, so the replayed rows carry the replay's moments at the recorded pace. After each appended event it calls `Infrastructure/TourCaptionUpdates::publishTheStage()`, which publishes the caption of the demo run's current stage (below). An update is published through `Dashboard\Contract\LiveUpdates::publish()` as a `LiveEvent` of its recorded `topic` and `data`, unchanged: the same publisher (the capture decorator around the Mercure hub, [Live updates](live-updates.md)), topics and Turbo streams a live review sent, so an open review page goes through the same states, with no page or template of its own. Like every publish it never throws, so a hub that is down does not stop the replay.
5. A payload whose top-level `project` is the recording's `project` is decoded and encoded again with only that key set to `CreateDemoProjectCommand::NAME` (`json_encode` with `JSON_PRESERVE_ZERO_FRACTION`, the stored serializer's options, so the escapes and the key order stay); in a review's rows that is the `review_started` row and the `usage_recorded` rows of phase `started`. A rewritten `review_started` row also gets the key `replay_factor` (`Infrastructure/ReplayedStart::KEY`) holding the factor as a float (`4.0` for `--factor=4`, issue #2374, part 2 of #2303), because a review page loaded later has no other way to know the pace; no other row gets it. Every other payload is appended as its stored text. The replay stores no Review round, so the dashboard reads each replayed round's mark from the demo project, which is flagged as a replay.
6. A failed append is `ReplayStopped` (`The replay stopped after <n> of <total> ledger events: the <kind> row was not appended (<reason>).`). Once at least one event is written the message goes on `The events it wrote stay in the ledger: remove them with intakt:demo:remove, then run intakt:demo:create, before replaying this recording.`, because the rows already written keep their round in the ledger and step 3 refuses the recording while they stay. When the first append fails it goes on `Nothing was written, so replay this recording again.` instead, because nothing of the recording is in the ledger, so a plain retry is not refused, and `intakt:demo:remove` would also delete every earlier replay in the demo project. Later events and updates are not played and the command exits 1. Otherwise it prints `Replayed <n> ledger events and <n> live updates of change <change> into the demo project demo-replay, <factor> times as fast as recorded.`

The ledger publishes no live update on an append, so the replayed updates are what an open page receives; a page opened later reads the replayed rows when it loads. The review page shows each replayed round's factor in its round heading ([Dashboard](dashboard.md), Replay mark); the recorded updates carry no factor, so an open page shows it once it is loaded again after the round's `review_started` row is written.

Tests: `tests/Core/Dashboard/UseCase/ReplayDemo/ReplaysRecordingTest.php` (a recording written and read back through `RecordingFormat` appended as the same kinds and payloads in recorded order, the project rewritten only in the `review_started` and started `usage_recorded` rows with the escapes kept, the factor stored in the `review_started` row only, a whole factor stored as `4.0`, the moments of each append under a `MockClock` at factor 4 through `ClockedLedger` beside it, the forced order where the third append fails and the clock already stood at its moment while the second row carries the moment before, an event recorded earlier following at once, a failed append stopping later rows, the stop message naming `intakt:demo:remove` and `intakt:demo:create` after a written row, a stop at the first append asking for a plain retry without naming `intakt:demo:remove`, that retry replaying in full beside an earlier replay, a round the ledger holds refused before any append, a model call the ledger holds under another project's round refused before any append, a demo project that is no replay refused before any append, another round replayed beside an earlier replay, a held lock refused, and the lock free after a replay; for the updates, through `ClockedLiveUpdates` beside it, which notes the clock's moment and the ledger's row count at each publish: every update published with its recorded topic and stream in capture order, each at its moment at factor 4, each after the rows recorded up to its moment including one of the same moment, an update overrun by slow appends published at once, an update captured before the first row published at the start, no update after a failed append, and none for a held round or a held lock) and `ReplayDemoCommandTest.php` beside it (refused outside the compose demo with nothing published, the rows, the published update and the summary on it, factors 8 and 0.5 on the clock, 0, -2 and `1e400` refused, a word refused by the Console, a malformed and a missing file, a second replay of one recording, a failed append reported, a demo project that is no replay refused with nothing appended). ### Removing the demo project

Issue #2078 (part 3 of #2057). `Core/Dashboard/UseCase/RemoveDemoProject/RemoveDemoProjectCommand` (`intakt:demo:remove`, no arguments) removes the demo project with every ledger row replayed into it:

1. With `INTAKT_COMPOSE_SERVICE` empty it prints `The demo project is removed only on the compose demo, and INTAKT_COMPOSE_SERVICE is empty on this install.`, removes nothing and exits 1.
2. It takes the replay's lock `ReplaysRecording::LOCK` without waiting, because rows a running replay appends after the read below would stay behind; a busy lock prints `A replay is running; remove the demo project when it has ended.`, removes nothing and exits 1. The lock is released when the command ends.
3. Holding it, it asks `Infrastructure/ReplayMarks::ofProject()` for `demo-replay`. A project of that name that is not flagged as a replay keeps all its rows: the command prints `The project demo-replay is not marked as a replay, so nothing is removed.` and exits 0, so a second removal succeeds and changes nothing.
4. `Infrastructure/ReplayedReviewRows::ofProject()` reads the ledger once and returns the project's rows of every change, by the rule `of()` uses for one change: the `review_started` rows naming the project give the rounds, a row belongs when its `round` is one of them or, naming no round, its `call` is a model call started in one of them. A row that names another round stays, even when its `call` is one of the demo project's.
5. It sends Ledger's `Contract\RemoveReplayedEvents` (the rows' ids) and then Review's `Contract\UnflagReplayProject(demo-replay)` on the command bus, the flag last, so a removal that stops partway still finds a replay and the next run finishes it. The replay stores no Review round, so the flag is the project's only row outside the ledger. It prints `Removed the demo project demo-replay with its <n> ledger rows.` and exits 0.
6. After it lets the lock go (also after step 3), it calls `Infrastructure/LiveBoardHeadline::publishTheBoard()`, which publishes the board headline stream as a round update does (see Board headline in [Live updates](live-updates.md)), because no round follows a removal and a board left empty would otherwise keep its waiting octopus hidden on an open page until a reload (#2437). A failed publish is logged and changes nothing of the removal.

Rows of another project are never read as the demo project's: a replay refuses a round or a model call id the ledger already holds, so each replayed round and call id is the demo project's own, and a row naming another round is kept even if its call id matches. `intakt:demo:create` (the next compose start runs it) creates the project again; until then `intakt:demo:replay` refuses, because the project is no replay.

Tests: `tests/Core/Dashboard/UseCase/RemoveDemoProject/RemoveDemoProjectCommandTest.php` (`persistence` group, the container's buses, ledger and the migration's triggers: the demo project's rows and its mark removed, the count in the output, the rows of the live `sample` project and of another flagged project and that project's mark kept, a `sample` row that names a demo call id under its own round kept, refused outside the compose demo and while a replay holds the lock with nothing removed, a project of the demo name that is no replay keeping its rows, a second removal succeeding with nothing removed, the lock free afterwards, the board pushed after removing the only replayed review holding the waiting octopus, nothing pushed when refused outside the compose demo).

The automatic close is armed for the caption element of the last stage, kept in a `WeakSet` inside `captionTour()` and not in the DOM: when its 8 seconds pass it closes only if that same element is still shown, so a caption a live update or Back put in meanwhile (another round, the same stage again, or the copy Turbo restores from its cache) arms its own full 8 seconds, and if it is paused then, **Resume** arms a fresh 8 seconds. That close also stores the round in `intakt-tour-ended`, and a caption of any other round, at whichever stage a page first shows it, opens the tour again; a **Close** by the visitor stays for the tab. Only the page a started run's redirect reached follows the tour: the server renders `[data-tour-follow]` only on the `/demo` response that takes the `PlayDemoController::STARTED` flash (a refused Play, a later visit, or a request that picked up another form's success line has none), and that page follows to the review with `location.assign` once a stage that is not the last arrives, and only while the tour is neither closed nor paused. The mark does not outlive that page: `takePlay()` removes `data-tour-follow` from the element when it takes the page, so a page Turbo restores with Back is not taken again, and the flash lines in `base.html.twig` carry `data-turbo-temporary`, so Turbo leaves them out of the page it caches. From then on the script follows by the taken page's body alone. A later visit to `/demo` stays there and shows its readiness line.
