## Review verdicts

The `Core/Review` module's `Contract` holds the verdict a reviewer returns (plan task T1, design: [Reviews](../design/05-architecture/07-reviews.md)).

- **Classes are the source of truth:** `Verdict` (`verdict`, a `Decision`: `approve`, `changes` or `blocked`; `findings`; `resolved`; `follow_ups`), `Finding` (`id`, `severity` a `Severity` P1 to P3, `file`, `line`, `symbol`, `text`, `fixable_by` a `FixableBy` builder or owner, `repeat`, `requirement`, `evidence`) and `Evidence` (`probe`, `output`). They are final and readonly, the closed sets are backed enums, and the property names are the JSON field names, because Symfony AI's structured output ignores serializer name mapping. Validator constraints: `id`, `text` and `probe` are not blank, `line` is at least 1, and findings and evidence are validated as nested objects.
- **Stored JSON:** verdicts (`round_reviewer.verdict`) and findings (`review_round` `open_findings`, `reported_findings` and `resolved_findings`, `change_findings.findings`) are written and read with the named serializer `stored` (`framework.serializer.named_serializers` in `config/packages/framework.yaml`, injected with `#[Target('stored')]`), configured once with the snake_case name converter, so the stored keys stay as they were written before (`fixable_by`, `follow_ups`). It is a named serializer because a name converter on the application's default one would change how the model's answer is read. The properties keep their snake_case names for now, because Symfony AI's schema factory ignores name converters and the model must still be asked for `fixable_by` (`tests/Core/Review/Contract/FindingSchemaTest.php`); `Verdict::isFailedReview()` and `TrackedFinding::isOpen()` are `#[Ignore]`d so the stored shape is the one `json_encode` wrote. `RoundReviewer` (Domain) takes the finished JSON and never serializes. `ReviewTerms` and the schema instruction of the confined Claude Code client keep `json_encode`, because their bytes must be stable. The `usage_recorded` and `account_cooled_down` ledger payloads are written through their payload classes with the same serializer (see "Cooldowns and failover" and the vendor's usage rows); so are the round ledger's events, which `UseCase/RunReviewRound/RoundLedger` writes from one readonly class per kind (`ReviewStarted`, `ReviewerStarted`, `VerdictReceived`, `CatchUpOwed`, `ReviewerFailed`, `ReviewerBlocked`, `ReviewerStopped`, `JudgeDone` with its `JudgeDoneFinding` list in the Review module's `Contract/`, because the Dashboard reads them too; `ShadowRoundHeld`, which no other module reads, next to `RoundLedger`), closed sets as their backed enums (`Tier`, `Decision`, `ProjectMode`, `Severity`, `Provider`, and `QuorumPolicy` for the `quorum` of `review_started`) and the keys and stored values as before (`tests/Core/Review/UseCase/RunReviewRound/RoundLedgerPayloadsTest.php`). Inside the Review module the round ledger's rows are read back through the same classes by the Ledger module's `Contract/LedgerPayloads::of(row, class)`, which deserializes a row with the `stored` serializer and returns null for a row that does not deserialize (not JSON, a key missing, a value outside its enum), so the reader skips it as it skipped an unreadable array row before: `judge_done` by `UseCase/ReviewChange/RoundLedgerReading::actIdsOf()`, `usage_recorded` by `RoundLedgerReading::tokensOf()` and `costOf()` (into the vendor plugin's `Contract/` classes `UsageStarted`, and `UsageSettled` or `UsageUnsettled` as the row's `phase` says, so a usage entry with a token count that is not a number skips its whole row), `verdict_received` by `UseCase/ReadVerdicts/ShadowRounds` and `reviewer_stopped` by `Infrastructure/StopRequests` (`tests/Core/Review/UseCase/ReviewChange/RoundLedgerReadingTest.php`, `tests/Core/Review/UseCase/ReadVerdicts/VerdictsOfRoundTest.php`, `tests/Core/Review/Infrastructure/ReviewerStoppingTest.php`). The Dashboard reads the round ledger and usage rows through the same classes (`Dashboard/Infrastructure/RoundPayloads`, see Dashboard). Rows without a payload class are still read as arrays: the dashboard's `reviewer_stop_requested` in `StopRequests`, and the watcher's lines in the Dashboard's `LedgerFailingHeads`. Command output goes through the serializer too: `intakt:review --format=json` writes `ReviewOutput` with the `stored` serializer (see "Review command"), and `intakt:vendor:probe` normalizes a `ProbeUsage` with the application's default serializer for its usage line. Tests that build a ledger writer or reader without the container use `tests/Support/StoredSerializerFactory.php`, pinned to the container's `serializer.stored` by `tests/Support/StoredSerializerFactoryTest.php`. Tests: `tests/Core/Review/Stored/StoredJsonTest.php` (round trips, and rows in the format written before).
- **Mapping:** a caller invokes the Platform with `response_format` set to `Verdict::class`; the structured-output subscriber sends the schema it derives from the classes, and the Validator subscriber checks the constraints. `StrictVerdictSubscriber` (`Infrastructure`, a `ResultEvent` subscriber at priority 10, ahead of structured output) fills the objects for exactly that response format: `StrictVerdictConverter` maps the reply text with the application's serializer, refusing unknown fields (`ALLOW_EXTRA_ATTRIBUTES` false) and left-out fields, nullable ones too (`REQUIRE_ALL_PROPERTIES`), as the schema does, and decoding JSON objects as objects (`JsonDecode::ASSOCIATIVE` false), so an object never passes as a list. The serializer passes an object on as a list of findings, and the constructor's `TypeError` is turned into a mapping failure (`upstream/serializer-object-collection-accepts-any-object`). A streamed answer (`StreamResult`) is passed on as a new stream over the bridge's deltas with a `StreamedAnswer` and a `StrictVerdictStreamListener`. `StreamedAnswer` lets each text delta stream on as it comes, but hides it from the listeners after it (Symfony AI's `PartialObjectStreamListener`, which the structured output adds, would otherwise read the narration before a tool call as the answer and fail on it); when a round ends without asking for tools, it hands those listeners the whole answer text once, as a delta that is not streamed again. `StrictVerdictStreamListener` maps that text by the same rules when the stream ends (a round that asked for tools is left alone), so a streamed verdict is refused where an unstreamed one would be. The Anthropic bridge streams two text blocks as one run of text deltas, so the converter hands the bridge the raw result through `AnthropicTextBlocks`, which counts the `content_block_start` events of type `text`; an answer whose text spans two blocks is refused like an unstreamed answer with two text parts. For a provider whose raw stream has no such events, the count stays 0 and nothing is refused on it. An unstreamed answer in several parts (a provider that thinks before it answers sends the thinking beside the text) is kept as parts with the one text part mapped to the `Verdict` and checked against the constraints by the converter itself, because Symfony AI's Validator subscriber checks only an object result, never one among parts; `ReviewerPrompt::verdictIn()` reads the verdict from that part. Two text parts, or none, are refused. An unstreamed round that asks for tools drops its narration text before Symfony AI's structured output can read it as the answer, and keeps the thinking and the calls, so the next request replays them; a streamed one keeps its narration in the conversation, hidden from the structured output as above (`tests/Core/Review/Infrastructure/StreamedAnswerTest.php`; `tests/Core/Review/Infrastructure/AnthropicToolUsingReviewerTest.php` replays recorded Anthropic answers, unstreamed and streamed, through the real agent, toolbox and bridge with only the HTTP client mocked). A stream that ends cleanly without any answer text, or on an unfinished JSON document (a string, object or array is still open, and Symfony AI's `PartialJsonParser` reads it as a prefix), raises `IncompleteStreamException`, like a stream the provider reports as cut off, so the reviewer's call fails as an incomplete answer and never becomes a verdict; a closed document that does not validate (a trailing comma) is mapped like the same unstreamed answer. Before it, a `FinalStreamedUsage` listener sets the stream's `token_usage` to one usage holding, for each figure, the last value any of its usage events reported, also when the stream is cut off, because Symfony AI adds up every usage event while a provider repeats figures it already reported; a figure no event reports stays null (unknown), never 0. Anthropic's bridge reports the input and cache tokens on `message_start` and only the output tokens on `message_delta`, so the row keeps both (`tests/Plugin/SymfonyAiVendor/AnthropicUsageTest.php` replays a recorded tool-use stream and its final text from `tests/Plugin/SymfonyAiVendor/Fixtures/anthropic/`); the vendor's usage row then counts the call once, because `UsageLedger` reads a consumed `StreamResult`'s `token_usage` before the other sources. `VerdictParser::parse()` takes that `DeferredResult` and returns a `Verdict`, marked `#[NoDiscard]`.
- **Invalid output** becomes a `changes` verdict with one finding: id `invalid-output` (`Verdict::INVALID_OUTPUT`), severity P1, fixable by the builder, no place, the design's rule as `requirement`, and a text that says why: the first violation (`findings[0].id: This value should not be blank.`) or the mapping error (`... Syntax error`, `The type of the "line" attribute ...`, `... requires the following parameters to be present : "$id"`, `Extra attributes are not allowed ("findings[0].note" is unknown).`). This covers output that is not JSON, any fenced code block (also one whose body is a valid verdict, which Symfony AI's structured output would unwrap), a JSON value of the wrong shape or type, a left-out or unknown field, an enum value outside its set, and an answer that is not a single text (a reply in several parts that holds two texts or none, or a tool call handed to `parse()`; the [reviewer agent](reviewer-agent.md) takes a tool call as a step of its loop instead, so there only the final answer must be a verdict). Any other failure of the call, such as a rate limit, stays an exception.
- **Schema oracle:** `tests/Core/Review/Contract/verdict.schema.json` is the schema Symfony AI derives from the classes. `VerdictSchemaTest` fails when the two differ, and checks with `justinrainbow/json-schema` (a development dependency) both directions: the file accepts every verdict the classes accept (`AcceptedVerdicts`) and refuses every broken field rule the classes refuse (`BrokenFieldRules`). The parser tests run on the application's event dispatcher, so the subscribers and their order are the real ones.
