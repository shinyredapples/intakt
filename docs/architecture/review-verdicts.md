## Review verdicts

The `Core/Review` module's `Contract` holds the verdict a reviewer returns (plan task T1, design: [Reviews](../design/05-architecture/07-reviews.md)).

- **Classes are the source of truth:** `Verdict` (`verdict`, a `Decision`: `approve`, `changes` or `blocked`; `findings`; `resolved`; `follow_ups`), `Finding` (`id`, `severity` a `Severity` P1 to P3, `file`, `line`, `symbol`, `text`, `fixable_by` a `FixableBy` builder or owner, `repeat`, `requirement`, `evidence`, `regression`, and `merged`, below) and `Evidence` (`probe`, `output`). They are final and readonly, the closed sets are backed enums, and the property names are the JSON field names, because Symfony AI's structured output ignores serializer name mapping. The reviewer's answer format is not the contract `Verdict` itself but the answer document `Infrastructure/ReviewerAnswer/Verdict` (#3419): the same four fields with the same types (`findings` a list of the contract's `Finding`, validated as nested objects; `resolved` and `follow_ups` lists of strings), and no origin. It keeps the short name `Verdict` because Symfony AI names the schema after the class, so the schema the reviewers get is the one the contract `Verdict` gave (`tests/Core/Review/Infrastructure/ReviewerAnswerTest.php` compares it with `fixtures/verdict-schema.json`, taken from main before the document existed). `toVerdict()` maps it to the contract `Verdict` with origin `Reviewer`; it is the only mapping, so the contract can later change its types without changing the schema or the stored rounds. Validator constraints: `id`, `text` and `probe` are not blank, `line` is at least 1, and findings and evidence are validated as nested objects.
- **Stored JSON:** verdicts (`round_reviewer.verdict`) and findings (`review_round` `open_findings`, `reported_findings` and `resolved_findings`, `change_findings.findings`) and the ledger ids a round resolved (`review_round.resolved_finding_ids`) are written and read with the named serializer `stored` (`framework.serializer.named_serializers` in `config/packages/framework.yaml`, injected with `#[Target('stored')]`), configured once with the snake_case name converter (and `StoredFindingNormalizer` for a finding's merged ids and judge note, and `StoredFindingIdsNormalizer` for the other lists of finding ids and the judge's same-cause links, below), so the stored keys stay as they were written before (`fixable_by`, `follow_ups`). It is a named serializer because a name converter on the application's default one would change how the model's answer is read. The properties keep their snake_case names for now, because Symfony AI's schema factory ignores name converters and the model must still be asked for `fixable_by` (`tests/Core/Review/Contract/FindingSchemaTest.php`); `Verdict::isFailedReview()` and `TrackedFinding::isOpen()` are `#[Ignore]`d so the stored shape is the one `json_encode` wrote. `RoundReviewer` (Domain) takes the finished JSON and never serializes. A contract `Verdict` is written as it is, and a stored verdict is read back as the answer document and mapped with `toVerdict()` (`UseCase/ReadVerdicts/StoredVerdicts`, `UseCase/RunReviewRound/StoredFindings`), so the stored JSON keeps the answer format (`StoredJsonTest` pins a row written on main and the JSON a verdict is written as). `ReviewTerms` and the schema the confined Claude Code client passes as `--json-schema` keep `json_encode`, because their bytes must be stable. The `usage_recorded`, `account_cooled_down` and `account_error_reported` ledger payloads are written through their payload classes with the same serializer (see "Cooldowns and failover" and the vendor's usage rows); so are the round ledger's events, which `UseCase/RunReviewRound/RoundLedger` writes from one readonly class per kind (`ReviewStarted`, `ReviewerStarted`, `VerdictReceived`, `CatchUpOwed`, `ReviewerFailed`, `ReviewerBlocked`, `ReviewerStopped`, `JudgeDone` with its `JudgeDoneFinding` list, its `DroppedFinding` list (`dropped`: each finding the quote check dropped before the judge, with its `reason`; a row written before the list existed reads with none) and `fallback` (true when the judge left a finding without its mark, as the fallback for an unreadable answer does; absent on rows written before, which read as null), `ReviewerFindingsRecorded` with `severities` (each reported id with the severity of the reviewer's stored verdict; absent on rows written before, which read as null) in the Review module's `Contract/`, because the Dashboard reads them too; `RoundLedger::reviewerStarted()` adds the `model` the reviewer's tier resolves to through `Ai\Contract\TierResolver::resolve()`, so the dashboard can name the reviewer by it, and leaves the key out when the tier does not resolve, because the reviewer's own call then fails on its usual path, so such a row reads like one written before the key existed; `RoundLedger::catchUpOwed()` adds after `substitute` the `model` of the tier's first substitute on that provider from `TierResolver::substitutes()`, so the dashboard names a substituted reviewer by the model that answered, and leaves it out the same way when none matches or the tier does not resolve), closed sets as their backed enums (`Tier`, `Decision`, `ProjectMode`, `Severity`, `Provider`, and `QuorumPolicy` for the `quorum` of `review_started`) and the keys and stored values as before (`tests/Core/Review/UseCase/RunReviewRound/RoundLedgerPayloadsTest.php`). Inside the Review module the round ledger's rows are read back through the same classes by the Ledger module's `Contract/LedgerPayloads::of(row, class)`, which deserializes a row with the `stored` serializer and returns null for a row that does not deserialize (not JSON, a key missing, a value outside its enum), so the reader skips it as it skipped an unreadable array row before: `judge_done` by `UseCase/ReviewChange/RoundLedgerReading::judgeDoneOf()`, `usage_recorded` by `RoundLedgerReading::tokensOf()` and `costOf()` (into the vendor plugin's `Contract/` classes `UsageStarted`, and `UsageSettled` or `UsageUnsettled` as the row's `phase` says, so a usage entry with a token count that is not a number skips its whole row) and `reviewer_stopped` by `Infrastructure/StopRequests` (with `verdict_received`, `reviewer_failed` and `reviewer_blocked` for `stoppedIn()`) (`tests/Core/Review/UseCase/ReviewChange/RoundLedgerReadingTest.php`, `tests/Core/Review/Infrastructure/ReviewerStoppingTest.php`). The Dashboard reads the round ledger and usage rows through the same classes (`Dashboard/Infrastructure/RoundPayloads`, see Dashboard). Rows without a payload class are still read as arrays: the dashboard's `reviewer_stop_requested` in `StopRequests`, and the watcher's lines in the Dashboard's `LedgerFailingHeads`. Command output goes through the serializer too: `intakt:review --format=json` writes `ReviewOutput` with the `stored` serializer (see "Review command"), and `intakt:vendor:probe` normalizes a `ProbeUsage` with the application's default serializer for its usage line. Tests that build a ledger writer or reader without the container use `tests/Support/StoredSerializerFactory.php`, pinned to the container's `serializer.stored` by `tests/Support/StoredSerializerFactoryTest.php`. Tests: `tests/Core/Review/Stored/StoredJsonTest.php` (round trips, and rows in the format written before).
- **Judge note:** the private `Finding::$judge_note` (a string, null by default, read with `judgeNote()`, set with `withJudgeNote()`) holds the judge's reason for a rejected or deferred P1 or P2 that stays on the act list; `StoredFindings::actListOf()` sets it on an act list entry from the round's `judge_done` row (see [Review flow](review-flow.md)). It is `#[Ignore]`d like `merged`, so the schema never asks a reviewer for it (`FindingSchemaTest`). `StoredFindingNormalizer` writes the key `judge_note` after `merged` only when the note is set and the caller's `attributes` and `ignored_attributes` context allow it, so a finding without a note is stored as before; a row without the key or with `null` reads with no note, and a note that is not a string fails to read (`StoredJsonTest`, `StoredFindingNormalizerTest`). The findings resource of the MCP server therefore shows `judge_note` only when set. Because the property is private, `json_encode` leaves it out of a finding. The answers of `review_act_list` (`RoundActList`) and `start_review` (`StartedReview`), which the MCP SDK encodes with `json_encode`, are `JsonSerializable` and write each act list entry through `Review\Contract\ActEntryAnswer`: its public fields as before, then `judge_note` only when the entry has a note, wrapped in the fence as act list text (`Fence::wrap(UntrustedSource::ActList, ...)`), because it is a model's text (`ActEntryAnswerTest`, `ReadRoundToolsTest`, `StartReviewToolTest`).
- **Merged ids:** `Finding::$merged` (a `Contract/FindingIds`, the finding ids in order, empty by default, set with `withMerged()`) names the findings an act list entry stands for besides its own id. It is `#[Ignore]`d, so Symfony AI's schema never asks a reviewer for it (`FindingSchemaTest`, and `verdict.schema.json` is unchanged) and a reviewer's answer that names it is refused as an unknown field (`BrokenFieldRules`). Only the `stored` serializer writes and reads it, through `Infrastructure/StoredFindingNormalizer` (tagged for that serializer alone): it writes the key `merged` after the other fields, also when the list is empty, unless the caller's `attributes` context leaves it out or its `ignored_attributes` names it (the review command's act list rows name it in `ReviewOutput::FIELDS`, so they carry it); a row without the key, as every row stored before, reads with no merged ids, and a `merged` that is not a list of strings fails to read, an object such as `{"0":"B"}` included, because the stored serializer's own JSON encoder (`Infrastructure/StoredJsonEncoder`, tagged for that serializer alone) keeps an object under `merged` as an object instead of decoding it to an array (`StoredJsonTest`, `StoredFindingNormalizerTest`). The findings resource of the MCP server, which writes with the same serializer, now shows `merged` too. `FindingIds` is the Review contract's one value for a list of finding ids (`Finding::$merged`, `JudgeDone::$act` and `$followUps`, `JudgeDoneFinding::$merged`), a final readonly class callers build directly (`new FindingIds('F1', 'F2')`): it iterates its ids in the order given (`contains()` asks for one) and `json_encode` writes it as a plain JSON list, so the MCP answers that encode findings keep their shape (`FindingIdsTest`, `ReadRoundToolsTest`). On the `stored` serializer, `Infrastructure/StoredFindingIdsNormalizer` (tagged for that serializer alone) writes it as a list of strings and reads an array of strings back in order (an id list stored under keys, such as `{"1":"F3"}`, reads in order and is written back as a list; the code never wrote one keyed, and a stored finding's `merged` under keys is refused by `StoredFindingNormalizer`), and refuses a value that is not an array or holds anything but strings, so a `judge_done` row or a stored finding written before the ids were one value reads back and is written again byte for byte (`RoundLedgerPayloadsTest`, `StoredJsonTest`, `StoredFindingIdsNormalizerTest`). `SameCause` is the Review contract's one value for the judge's same-cause links (`JudgedFindings::$sameCause`, `JudgeDone::$sameCause`, empty by default), from a finding id to the id of the finding it names as its cause: `with(finding, cause)` returns a copy with the link (a later link of the same finding replaces the earlier one) and refuses an empty id or a finding named as its own cause, `causeOf()` gives the cause of one finding or null, and it iterates the links in the order added, a numeric id as a string (`SameCauseTest`); `JudgedFindings::of()` keeps no link of a finding to itself (`JudgedFindingsTest`). On the `stored` serializer, `StoredFindingIdsNormalizer` writes it as a JSON object from finding to cause, no links as `[]` as before, and reads such an object back, refusing a value that is not an array, a cause that is not a string and an empty id, but keeping a finding stored as its own cause by an older writer (`withStored()`), so a `judge_done` row written before the links were one value reads back and is written again byte for byte (`RoundLedgerPayloadsTest`, `StoredFindingIdsNormalizerTest`); a stored `same_cause` whose keys are consecutive numbers starting at `0` decodes as a JSON list and is written back as a list, as it was before the links were one value; `OnePerPlace` takes the links as a map from finding to cause. `JudgeNotes` is the Review contract's one value for the judge's notes (`JudgedFindings::$notes`, empty by default), from a finding id to the note the judge gave for it: `with()` returns a copy with one more note, refuses an empty id and keeps the note as given (an empty or untrimmed note too), `noteOf()` gives the note of one finding or null, and it iterates the notes in the order added, a numeric id as a string (`JudgeNotesTest`). It is never serialized: `RoundLedger::judgeDone()` reads each finding's note through `noteOf()` into `judge_note`, so `judge_done` rows and the MCP act answers keep their shape (`RoundLedgerPayloadsTest`). `Domain/OnePerPlace::actList(reported, actIds, sameCause)` is the merge rule (design: one entry per place, from plan task T59, and one entry per cause, #2336): of the reported findings, in panel order, it keeps those whose ids are among the act ids, and groups them before it builds any entry: act findings at the same `file` and `line` are one group, and a link the judge gave (`sameCause`, either direction) joins the whole groups of its two findings, so a finding linked to one entry that sits at the place of another makes the two one entry, whichever of them comes first in panel order. A link joins two groups only when the joined group stays in one file and at most `CausesInOneHunk::NEARBY_LINES` (five) lines from its lowest line to its highest; otherwise that link is ignored and both groups stay entries, so a chain of links (lines 3, 8 and 13) keeps the finding at line 13 as an entry of its own, with its text. The links are tried in the panel order of the linking finding, so the result is the same on every run; grouping by place is never undone. Each group becomes one entry: the id and text of its first finding in panel order, the highest severity (P1 over P2 over P3) and the ids of the others, in panel order, in `merged`. The line range is the change's own: the judge names the cause, and before anything is recorded `Domain/CausesInOneHunk` keeps a link only when both findings have a line in one file and both lines are inside one hunk of the round's diff (the new-side lines each `@@` header names, read by `Infrastructure/DiffHunks`) and at most `CausesInOneHunk::NEARBY_LINES` (five) lines apart, so a steered judge cannot fold a defect further away into another entry, even in a new file, whose diff is one hunk, and `OnePerPlace` holds the same bound for the whole group, so links that are each within five lines cannot be chained past it; because the entry keeps only the first finding's text, a linked finding within that window can still lose its own text; a link it drops leaves the judge's mark as it was (`CausesInOneHunkTest`, `DiffHunksTest`). A finding without a file or without a line is never merged, and only a P3 the judge marked defer or reject stays out of an act entry (a P1 or P2 is always among the act ids, whatever the judge marked). Places are keyed by file, then line, never by a joined string. A merged entry keeps its own judge note, or else the first note of a finding it merged (`OnePerPlaceTest`). `UseCase/RunReviewRound/StoredFindings::actListOf()` applies it to every act list a round produces, publishes and reads back (see [Review flow](review-flow.md)) (`tests/Core/Review/Domain/OnePerPlaceTest.php`).
- **Mapping:** a caller invokes the Platform with `response_format` set to the answer document's class (`Infrastructure\ReviewerAnswer\Verdict::class`); the structured-output subscriber sends the schema it derives from the classes, and the Validator subscriber checks the constraints. `StrictVerdictSubscriber` (`Infrastructure`, a `ResultEvent` subscriber at priority 10, ahead of structured output) fills the objects for exactly that response format: `StrictVerdictConverter` maps the reply text with the application's serializer, refusing unknown fields (`ALLOW_EXTRA_ATTRIBUTES` false) and left-out fields, nullable ones too (`REQUIRE_ALL_PROPERTIES`), as the schema does, and decoding JSON objects as objects (`JsonDecode::ASSOCIATIVE` false), so an object never passes as a list. Before 8.2.0-BETA2 the serializer passed an object on as a list of findings and the constructor's `TypeError` ended the mapping (`upstream/serializer-object-collection-accepts-any-object`, fixed by Intakt's pull request symfony/symfony#67913); the lock now has the fix, and the converter keeps turning that `TypeError` into a mapping failure. For a `ClaudeCode` or `Codex` model (`StrictVerdictSubscriber::formOf()` passes `AnswerForm::ProseAroundBlock`, otherwise `AnswerForm::Json`, to the converter), whose answer may be prose around the verdict (a `Codex` model cannot hold its answer to a schema; a `ClaudeCode` one gets the schema through the CLI's `--json-schema` option, and its answer held to it is read from the CLI's `structured_output`, so its result text is read only when the CLI leaves that field out or null, see [AI providers](ai-providers.md)), `verdictFrom()` first takes the body of the one fenced `json` block (`fencedBlockOf()`), by a rule that is deliberately simpler than Markdown and fails closed: every `json` fence opening anywhere in the answer counts (three or more backticks or three or more tildes, optional spaces or tabs, then `json` in any case as a whole word, whatever comes before it on the line, so indentation, `>`, a list marker or a mention in the prose all count), and exactly one is required; that one must be a plain top-level block (a line that starts with exactly ```` ```json ````, the body, and the next line holding exactly ```` ``` ````, each with trailing spaces or tabs allowed and a Windows line ending accepted), and it must not sit inside another fence: an odd count of fence lines before it (any line holding three backticks or three tildes), or a fence opened before it (a line of three or more backticks or tildes after only spaces, tabs, `>` or list markers) that is still open, refuses it. A fence is closed only by a later fence line with no info string, of its character, at least as long, and with the same prefix (`FenceLine::closes()`; up to three spaces of indentation count as no prefix, as in Markdown): only a fence line without a prefix closes a fence opened without one, because inside an open block a quoted, listed, tab-indented or four-space-indented fence line is content, and a bare fence line after a quoted opening starts a new block instead of closing the quoted one. A closed block of another language beside it, such as a `php` block, is allowed. An ambiguous answer is refused rather than guessed: with no opening, several, a block in another form or a nested one, the text is mapped as it is, so it fails as before; bare JSON is mapped as it is too, and everything after the mapping (constraints, finding ids, the goalpost rule, the judge) is unchanged. Every other provider keeps the strict reading. A streamed answer (`StreamResult`) is passed on as a new stream over the bridge's deltas with a `StreamedAnswer` and a `StrictVerdictStreamListener`. `StreamedAnswer` lets each text delta stream on as it comes, but hides it from the listeners after it (Symfony AI's `PartialObjectStreamListener`, which the structured output adds, would otherwise read the narration before a tool call as the answer and fail on it); when a round ends without asking for tools, it hands those listeners the whole answer text once, as a delta that is not streamed again. A transient Platform error (`RetryableExceptionInterface`: a `ServerException`, also a server error event, or a rate limit) thrown once the bridge's stream has yielded an answer delta (any delta but a `TokenUsageInterface` or a `MetadataDelta`, which a provider reports on opening the message, often right before an overload error) is rethrown as an `IncompleteStreamException` with the message `The provider failed after the answer had started streaming.` and the error as its previous exception, because a provider cannot resume a broken stream; one thrown before the first answer delta, also after only usage or metadata, and any other error, passes unchanged. Every cut the streamed answer raises is a `Review\Contract\StreamEndedEarly`, a subclass of `IncompleteStreamException`, so every caller handles it as before: a `StreamTally` shared by `StreamedAnswer` and `StrictVerdictStreamListener` counts each delta of the bridge's stream and keeps the last five, each as its class short name, a `TextDelta` or `ThinkingDelta` with the first 80 characters of its text as a JSON string, a `MetadataDelta` with its key and its value as JSON (only the type when the value is not a scalar). The exception carries that count and those chunks with `StreamCutBy`, which says who raised it: `provider-failure-mid-stream` (the transient error above), `platform` (the bridge's own `IncompleteStreamException`, rethrown with its message and its previous exception, so the retry rules and the account's cooldown read it as before) or `unfinished-answer` (the listener below); `described()` writes them as lines `cut by:`, `chunks:` and `last chunks:` (`none` when no delta came). `StrictVerdictStreamListener` maps that text by the same rules when the stream ends (a round that asked for tools is left alone), so a streamed verdict is refused where an unstreamed one would be. The Anthropic bridge streams two text blocks as one run of text deltas, so the converter hands the bridge the raw result through `AnthropicTextBlocks`, which counts the `content_block_start` events of type `text`; an answer whose text spans two blocks is refused like an unstreamed answer with two text parts. For a provider whose raw stream has no such events, the count stays 0 and nothing is refused on it. An unstreamed answer in several parts (a provider that thinks before it answers sends the thinking beside the text) is kept as parts with the one text part mapped to the answer document and checked against the constraints by the converter itself, because Symfony AI's Validator subscriber checks only an object result, never one among parts; `ReviewerPrompt::verdictIn()` reads the answer document from that part, or from the object result, and maps it with `toVerdict()`; anything else is refused with an `UnexpectedResultTypeException` that still names the contract `Verdict`, as the converter's deserialization message and the serializer's detail it carries do (the converter writes the contract class name in place of the answer document's), so the refusal texts stay as they were. Two text parts, or none, are refused. An unstreamed round that asks for tools drops its narration text before Symfony AI's structured output can read it as the answer, and keeps the thinking and the calls, so the next request replays them; a streamed one keeps its narration in the conversation, hidden from the structured output as above (`tests/Core/Review/Infrastructure/StreamedAnswerTest.php`, `tests/Core/Review/Infrastructure/StrictVerdictStreamListenerTest.php`; `tests/Core/Review/Infrastructure/AnthropicToolUsingReviewerTest.php` replays recorded Anthropic answers, unstreamed and streamed, through the real agent, toolbox and bridge with only the HTTP client mocked; `tests/Core/Review/UseCase/JudgeRound/ToolUsingReviewerJudgedTest.php` carries the same replay through a round's worker to the judge, which is asked about the findings of a changes answer and not asked after an approval). The Symfony AI behavior these steps work around (the narration converted or decoded as the answer, the object among the parts left unvalidated) is reproduced in `upstream/ai-structured-output-multi-part-answers/`. A stream that ends cleanly without any answer text, or on an unfinished JSON document (a string, object or array is still open, and Symfony AI's `PartialJsonParser` reads it as a prefix), raises `IncompleteStreamException`, like a stream the provider reports as cut off, so the reviewer's call fails as an incomplete answer and never becomes a verdict; a closed document that does not validate (a trailing comma) is mapped like the same unstreamed answer. Before it, a `FinalStreamedUsage` listener sets the stream's `token_usage` to one usage holding, for each figure, the last value any of its usage events reported, also when the stream is cut off, because Symfony AI adds up every usage event while a provider repeats figures it already reported; a figure no event reports stays null (unknown), never 0. Anthropic's bridge reports the input and cache tokens on `message_start` and only the output tokens on `message_delta`, so the row keeps both (`tests/Plugin/SymfonyAiVendor/AnthropicUsageTest.php` replays a recorded tool-use stream and its final text from `tests/Plugin/SymfonyAiVendor/Fixtures/anthropic/`); the vendor's usage row then counts the call once, because `UsageLedger` reads a consumed `StreamResult`'s `token_usage` before the other sources. `VerdictParser::parseWith()` takes a closure that reads the verdict (in the reviewer agent, `ReviewerPrompt::verdictIn()`'s) and returns a `Verdict`, marked `#[NoDiscard]`; it has no method that reads a `DeferredResult` itself, because the contract cannot name the answer document in `Infrastructure`.
- **Invalid output** is no verdict: `VerdictParser` throws `VerdictUnreadable` (in the Review `Contract`), whose message says why after `The reviewer's answer could not be read as a verdict: `; the vendor settles the call's usage, asks once more with twice the output room, and a second one fails the reviewer (`FailureInWords`: `the reviewer's answer could not be read as a verdict`, followed by the reason when it is key-safe, see [Vendor](vendor.md) and [Review flow](review-flow.md)), so no verdict with an `invalid-output` finding is made any more; `Verdict::INVALID_OUTPUT` stays among the ids of `Verdict::isFailedReview()` because rounds recorded before hold it, so those still read as failed reviews. The reason is the first violation (`findings[0].id: This value should not be blank.`) or the mapping error (`... Syntax error`, `The type of the "line" attribute ...`, `... requires the following parameters to be present : "$id"`, `Extra attributes are not allowed ("findings[0].note" is unknown).`). This covers output that is not JSON, any fenced code block (also one whose body is a valid verdict, which Symfony AI's structured output would unwrap), except for a `claude_code` or `codex` answer that holds exactly one fenced `json` block, which is read as that block (two such blocks, or a block of another language, stay invalid), a JSON value of the wrong shape or type, a left-out or unknown field, an enum value outside its set, and an answer that is not a single text (a reply in several parts that holds two texts or none, or a tool call read as the answer; the [reviewer agent](reviewer-agent.md) takes a tool call as a step of its loop instead, so there only the final answer must be a verdict). Any other failure of the call, such as a rate limit, stays an exception.
- **Changes without findings:** a verdict that withholds approval names at least one finding. `Verdict::withholdsApprovalWithoutFinding()` (`#[Ignore]`d, like `isFailedReview()`) tells a `changes` or `blocked` verdict with an empty `findings` list; the schema and the parser still accept it, and the vendor refuses it after the call with `ChangesWithoutFindings`, asks the same reviewer once more, telling it to name its findings or approve, and records the reviewer as failed when the second verdict names nothing either (see [Review flow](review-flow.md)).
- **Blocked with findings (#2757):** the reviewer prompt asks for `approve` or `changes` only (a P1 finding stops a change, not the verdict), but the schema keeps `blocked`, because Intakt's own failure verdicts use it. `Verdict::asRecorded()` returns a reviewer's `blocked` verdict that names at least one finding as `changes` with the same findings, resolved ids and follow-ups; a `blocked` without findings and every failure verdict Intakt gives itself (`Verdict::noTools()`, `reviewerStopped()`, `cutApproval()`, `unreadApproval()`, `incompleteStream()`) stay `blocked`. The origin decides, not the finding id: these named constructors set `origin` to `VerdictOrigin::Intakt`, a private constructor parameter that defaults to `VerdictOrigin::Reviewer` and is `#[Ignore]`d, so the schema does not ask for it, the stored JSON does not hold it, a model's answer that names it is refused as an unknown field (`tests/Core/Review/Contract/BrokenFieldRules.php`), and `withFindings()` keeps it. A reviewer's answer can therefore never pass as a failure verdict, and it never becomes a counted vote under a failure id either (#2787): `Verdict::claimedFailureIds()` (`#[Ignore]`d) returns, as `FindingIds`, the reserved ids (`invalid-output`, `incomplete-stream`, `unread-approval`, `no-tools`, `cut-approval`, `reviewer-stopped`) that a verdict of origin `Reviewer` names as finding ids, and none for a verdict of origin `Intakt`; `ReviewerAgent` refuses a verdict that claims any, whatever its decision, with the key-safe `VerdictUnreadable` reason `the verdict names finding ids reserved for failed reviews: <ids>.`, before it replaces an approval of cut text with `Verdict::cutApproval()` and before it checks the open ids, so an `approve` on a cut diff is refused too and the vendor asks once more in a new conversation and a second such answer fails the reviewer like any unreadable answer (`ReviewerVerdictTest`, `ReviewerRetryVendorTest`, `StopReviewerTest`). Without that refusal a reviewer's `changes`, or a `blocked` recorded as `changes`, would count as a changes vote while the finding ledger and `StoredFindings` drop its findings. `isFailedReview()` still goes by the ids, because stored verdicts carry no origin: Intakt's own failure verdicts and rounds stored before, a `changes` verdict with a reserved finding id included, still read as failed reviews, and the finding ledger (`FindingLedger::recordVerdict()`) and the resolved ids `StoredFindings` reads still omit their findings and resolutions. Such a legacy verdict stored as `changes` counts as `blocked` for a round judged with counted votes: `CountedVote::of()` checks `isFailedReview()` first, so the builder is never sent back with nothing to act on. Only a round with no stored vote for that reviewer (judged before votes were counted) falls back to the verdict as given, so it can keep its changes outcome while the ledger skips that verdict's findings and resolutions; no new verdict of this shape is stored. `ReviewWithReviewerHandler` applies it to the vendor's verdict before the goalpost rule and `ReviewerLeases::recordVerdict()`, so the stored verdict, the `verdict_received` ledger event and everything read from them (the dashboard's reviewer rows, its Now box, the round's Reviewers table, the quorum decision and `intakt:review`) say `changes`. The live log shows the answer as the model gave it (`ReadAnswer` is published by `LiveProgress` before the verdict is recorded), so its `blocked` stays visible there (`tests/Core/Review/Contract/VerdictTest.php`, `tests/Core/Dashboard/UseCase/BlockedWithFindingsPageTest.php`).
- **Blocked names its reason (#2758):** `blocked` stays only for a reviewer that did not deliver a usable review: one the round moved to the `blocked` state (no provider left, a stopped worker, a failed message), whose reason is the `reviewer_blocked` event's `reason`, or one whose recorded verdict is a `blocked` verdict Intakt gave, whose reason is `Verdict::blockedReason()` (the text of its one finding, `#[Ignore]`d; null for any other verdict). `RoundLedger::verdictReceived()` writes that reason into `verdict_received` as `reason` (left out when null). A `blocked` row written before the reason was recorded has none, so `LedgerRounds` notes `Reason not recorded: this verdict was written before Intakt kept the reason of a blocked verdict.` instead (the Blocked chip never shows without a note). The dashboard shows it as the muted note after the **Blocked** chip in the reviewer's row of the round's Reviewers table and in the Now box (the same partial for the page load and the live stream), and `ReviewChange` writes `reason: <role> reviewer blocked, <reason>` for `intakt:review`, keeping `failed` for a failed reviewer (`tests/Core/Dashboard/UseCase/BlockedReviewerReasonPageTest.php`, `ReviewPageLiveUpdatesTest`, `LedgerRoundsTest`, `ReviewChangeTest`, `VerdictTest`).
- **Schema oracle:** `tests/Core/Review/Contract/verdict.schema.json` is the schema Symfony AI derives from the reviewer answer document and the contract's `Finding` and `Evidence`. `VerdictSchemaTest` fails when the two differ, and checks with `justinrainbow/json-schema` (a development dependency) both directions: the file accepts every verdict the classes accept (`AcceptedVerdicts`) and refuses every broken field rule the classes refuse (`BrokenFieldRules`). The parser tests run on the application's event dispatcher, so the subscribers and their order are the real ones, and read each answer through `ScriptedReviewer::verdictFor()`, which maps the answer document and parses it as `ReviewerPrompt::verdictIn()` does.
