## Conventions

- **Named arguments** follow the rule in `AGENTS.md`: positional by default, named only where a value does not explain itself at the call site (a bare boolean, `null`, an unclear literal, several scalars of the same type in a row, skipped optional parameters); a call with two or more named arguments puts each argument on its own line with a trailing comma; they are no fix for a long parameter list, which is split or has values that form a real concept grouped into a readonly value object (never an artificial parameter object, as the parameter-limit gate says); calls into a `Contract/` interface or across a plugin boundary use none, since a parameter name would become public API. The `cs` gate enforces the layout of calls with two or more named arguments (attributes are left out); reviewers check the rest.
- **Container ids and parameter names** under `intakt.` are written once: each module that registers one has a final class of constants in its `Contract/` (`AiServices`, `BudgetServices`, `ReviewServices`, `ReviewerForLoopServices`, `WatcherServices`, `OutageServices`, `GitHubForgeServices`, `SymfonyAiVendorServices`, and `PlatformServices` for `intakt.gitleaks`, the scanner both the GitHub forge's scan and the hand-back's scan run), and `config/`, `src/` and `tests/` reference those constants (`#[Autowire(param: AiServices::ACCOUNTS)]`; YAML keys use `!php/const`; an argument YAML would have to spell as `%name%` is bound in `config/packages/ai.php` instead). The names derived from a provider come from `Contract\Provider` (`platformId()`, `cliId()`, `accountsId()`, `configKey()`, `parameter()`, or the case's `value`, as for the bundle's `anthropic` and `openai` platform keys in `config/packages/ai.php` and the sample project's models), so the platform factories keep no name constant of their own; the `phpstan` gate's `intakt.reSpelledName` reports a literal under `src/` or `config/` that re-spells either kind; `parameter()` is the only place that builds `intakt.ai.codex`, so `config/packages/ai.php` binds it to `UseCase/ProbeCodexLogin/ProbeCodexLoginCommand` (an attribute cannot call it). Those classes and `Budget/Domain/CeilingStartGuard` are left out of the resource scan in `config/services.yaml`, because it runs after `config/packages/` and would replace their definitions.
- **Logging** is structured (context arrays, no interpolated secrets). `config/services.yaml` defines `logger` as Symfony's `HttpKernel\Log\Logger` (minimum level from `INTAKT_LOG_LEVEL`, output `php://stderr`, the service output the journal reads) with `Core/Platform/Infrastructure/RedactedJsonFormatter` as its formatter; no Monolog is installed. The level goes through the `log_level` env var processor `Core/Platform/Infrastructure/LogLevelFromEnvironment` (`%env(log_level:INTAKT_LOG_LEVEL)%`, and `.env` sets `warning`): any of the eight `Psr\Log\LogLevel` values, `warning` when the variable is not set at all, and any other value (an empty one and a level in capitals included) throws when the container builds `logger`, which is at boot, with a message naming the variable and the accepted levels but not the value, since the value could be a credential set in the wrong variable and the message reaches the terminal unredacted (`tests/Core/Platform/Infrastructure/LogLevelFromEnvironmentTest.php`). The formatter, and so the redaction below, is the same at every level; no setting turns it off. The formatter writes one JSON line per record (`time` from the clock, `level`, `message` with `{placeholders}` filled, `context`); a `Throwable` in the context, under `exception` or anywhere else, becomes `class`, `message`, `at`, `trace` and its `previous` chain, and an object becomes `[object Class]`. The `trace` is built from `getTrace()` as PHP prints it but without arguments: one `#n file(line): Class->function()` per frame (`[internal function]` without a file) and `{main}` last, for the previous exceptions too. `getTraceAsString()` is never used, because it writes string arguments cut to `zend.exception_string_param_max_len` characters (15 by default, with `zend.exception_ignore_args` off, the engine defaults the image runs with, since it copies no `php.ini`), and the redaction matches a held credential only as its whole value (with or without its leading and trailing whitespace), so a cut argument would reach the log as the credential's prefix. Before the record is encoded, every string in it (the message, each context value and key, each exception's message and trace) passes through `Redaction::redact()` on its own, so a redaction never cuts into the JSON or into another field: a private key without its end line takes the rest of its own string, never the trace. A context key that names a header (the redaction would redact a value written after it, as for `Authorization` or `Cookie`) has its whole value, a list included, written as `[redacted]`, and its `{placeholder}` in the message is filled with `[redacted]` too. A redacted key never overwrites another: when its redacted name is already taken in the same map (a key equal to a held credential beside a key named `[redacted]`), it gets the first free name with a counter appended (`[redacted] 2`, `[redacted] 3`, ...), so every value stays in the line. The held credentials come from `Core/Platform/Infrastructure/HeldCredentials`, read when the record is written from the environment (the process environment of `getenv()`, `$_ENV` and `$_SERVER`, each source on its own, so a name that holds another value in each source holds every value) and then from the secrets vault (`secrets.vault`): the values of `APP_SECRET`, `MERCURE_JWT_SECRET`, `MCP_OWNER_TOKEN`, `GITHUB_APP_PRIVATE_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENAI_COMPATIBLE_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` and `HF_TOKEN`, and of every variable that is one of these names followed by `_` and more, as an account's variables are (`ANTHROPIC_API_KEY_TEAM`). The key kept from the browser (`KeptProviderKeys::read()`, none when the file is missing or unreadable) is held too. An unset or empty one is skipped, and a vault secret that cannot be decrypted is skipped instead of stopping the logger. URL userinfo, authorization headers and secret shapes are redacted too. A caller that logs a failure passes the exception itself under `exception`, never only its class or message, and the item the failure belongs to (`reviewer`, `round`, `call`, `project`, `account`, `installation`) as a context key. `SymfonyAiKeyCheck` is an exception: it logs only the class under `exception_class`, because the key it checks is not held yet and a provider's text can echo it ([AI providers](ai-providers.md)). Tests: `tests/Core/Platform/Infrastructure/RedactedJsonFormatterTest.php`, `tests/Core/Platform/Infrastructure/HeldCredentialsTest.php`, `tests/Application/HuggingFaceTokenRedactionTest.php`.
- **Deprecations in tests:** `phpunit.dist.xml` fails the run on every deprecation (`failOnDeprecation`) and keeps `ignoreIndirectDeprecations="true"` only for the ones PHPUnit rates as indirect, a vendor package calling another, which Intakt cannot fix. A deprecated vendor method that Intakt reaches through a vendor wrapper is rated indirect too, so the gate does not see it: with `APP_DEBUG=1` a test adding a listener to the container's `event_dispatcher` (a `TraceableEventDispatcher` around the `CompiledEventDispatcher`, whose `addListener()` and `removeListener()` Symfony 8.2 deprecates) passed it. The suite runs with `APP_DEBUG=0`, where that call is direct and fails the gate, so the test environment decorates `event_dispatcher` with Symfony's `ScopedEventDispatcher` (`tests/Support/services.yaml`): a listener a test adds at runtime (`DemoReviewLogTest`, `ShowErrorOutsideDashboardTest`, `DashboardPageTestCase`) goes to that wrapper and lives as long as the test's kernel. A class that triggers its deprecation while it loads is included by Composer's autoloader, so PHPUnit's default resolver names the autoloader as the caller and would rate every such deprecation indirect, whoever loaded the class. `tests/Support/Deprecation/LoadTimeDeprecationResolver` (registered under `issueTriggerResolvers`) finds the innermost frame that calls a registered autoloader and names the code that needed the class instead: the file of that frame, or, when an internal function such as `interface_exists()` asked for the class, the file of the next frame. It does so only when the loading itself raised the deprecation, that is when every frame between the deprecation and the autoloader call runs inside that autoloader (`tests/Support/Deprecation/RegisteredAutoloader`: the frame's file is the autoloader's own file, as for the include of the class file and Composer's include closure, or the frame has no file and its class is the autoloader's class). Any other frame before the autoloader call is code that called a deprecated symbol while the file loaded, and it stays the caller: an Intakt file whose load-time code calls a deprecated vendor function is rated direct even when vendor code asked for the class, and a vendor file whose load-time code calls another vendor's deprecated function stays indirect even when the test asked for it (`LoadTimeDeprecationResolverTest` runs both as real tests). It matches the frames against every callable in `spl_autoload_functions()` when the deprecation is raised (methods, functions, invokable objects and closures alike), because Symfony's `DebugClassLoader`, once enabled, replaces Composer's autoloader and includes the class file itself, and a closure loader's own file may lie outside the source (`LoadTimeDeprecationResolverTest` runs a real test that loads a deprecated vendor class with `DebugClassLoader` enabled, and one through a closure loader written outside the checkout). The resolver handles the autoloaders Intakt runs, Composer's `ClassLoader` and Symfony's `DebugClassLoader`, plus a plain closure loader; a test-registered loader that hands the `require` to a helper function in another file is not covered. A vendor class that extends a deprecated vendor class stays the caller, so that case stays indirect. Its `<source>` includes both `src/` and `tests/`, because PHPUnit rates a caller as Intakt's own only when it is in the source or is the running test's own file: so a test, a test helper under `tests/` (a builder, a base class) or a `src/` class that loads a deprecated vendor class or calls a deprecated vendor method is rated direct and fails the gate (`LoadTimeDeprecationResolverTest` runs a real test that does so, and one that does so through a helper). Including `tests/` also makes `restrictNotices` and `restrictWarnings` report the notices and warnings that test helpers raise. `phpunit.gates.xml` (the gates pass of the `tests` gate) registers the same resolver and the same `deprecationTrigger` block, and its `<source>` includes `tests/Gates/` beside `config/gates/src/`, so a gate test or a gate test helper that loads a deprecated vendor class fails the gates pass too (`LoadTimeDeprecationResolverTest` runs `tests/Gates/Deprecation/LoadsADeprecatedClassGateFixture` and the helper fixture beside it under that configuration). The `deprecationTrigger` block makes PHPUnit start the trace at the `trigger_deprecation` call, so the callee the resolver sees is the deprecated vendor file; without `tests/Gates/` in the source a helper under it is third-party code, so only the test's own file counts as the caller.
- **Logs in tests:** `tests/Support/services.yaml` (imported by `config/services.yaml` in the test environment) decorates `logger` with `RecordingLoggerFactory::create()`. In a PHPUnit run it returns a `RecordingLogger` that appends each record to a file the `UnassertedErrorLogExtension` (registered in `phpunit.dist.xml`) creates and names in `INTAKT_TEST_LOG_RECORDS`; anywhere else, for example an instance `bin/instance` serves in the test environment, it keeps the configured logger (the redacted JSON lines above), which writes to stderr and so to the server log. The `RecordingLogger` fills each `{key}` placeholder of the message from the context before it records it, by PSR-3 placeholder interpolation: a scalar or `Stringable` value replaces it, any other value leaves the placeholder as it is. A record whose context holds a `Throwable` (which the service log prints with its trace) gets `"traced": true`, and `LogRecords::all()` reads every record of the test without removing it, so a test can check the whole log of what it ran, below error level too (`tests/Application/DemoReviewLogTest.php`). A test that expects an error asserts it with `AssertsLoggedErrors::assertLoggedError()` (level and the filled-in message, without the ` at File line N` of an uncaught exception), which removes the record. A Dashboard page test asserts an uncaught client error (4xx) with `assertLoggedError(LogLevel::WARNING, ...)`, the level Symfony 8.2 logs it at. `ReviewServerContractTest` expects the uncaught 401 of a request without a credential to `/mcp/review` only while `tests/Support/SymfonyRelease::isAtLeast('8.2')` is false, because Symfony 8.2 makes the access-token authenticator the firewall's entry point, which answers 401 without an exception to log. Kernel tests extend `tests/Support/KernelTestCase` or `tests/Support/WebTestCase`, which use the trait; its `assertPostConditions()` takes the records left at error level or above and fails the test itself, naming each record (level and message). Both bases also declare `getContainer()` to return Symfony's `TestContainer`, the container a test kernel hands out, so the `phpstan` gate lets a helper given it read private services. `tests/Support/Log/KernelTestCasesFailOnUnassertedErrorsTest` checks that every kernel test class gets that hook. As the backstop for a test without the trait, after each test the extension takes the remaining records and reports each one at error level or above as a PHPUnit warning naming the record, which `failOnWarning` turns into a failed run; warnings and lower levels stay allowed. A record left when a test class finishes (logged in `tearDownAfterClass`) is reported as a PHPUnit test runner warning naming that class, and one left when the run finishes as a runner warning of its own, before the file is deleted; PHPUnit fails a run with a runner warning by default. Removing or taking records holds one file lock from the read to the rewrite, so a record another process appends meanwhile is kept. A test in a separate process gets its own records file and is checked in that process; a command a test starts inherits the variable, so its errors count for that test. Tests: `tests/Support/Log/` (`UnassertedErrorLogExtensionTest` runs fixtures in a subprocess, one of them isolated; `TestLoggerWiringTest` boots a kernel outside PHPUnit and reads the error from stderr).
- **Clock in tests (#2295):** `tests/Support/services.yaml` also decorates `clock` with `PinnableClockFactory::create()`. In a PHPUnit run (the same `INTAKT_TEST_LOG_RECORDS` check) it returns a `PinnableClock`, which reads and sleeps on the framework's clock until a test pins it, and from then on on a `MockClock` at that moment (its `sleep()` moves the moment without waiting); anywhere else, for example an instance `bin/instance` serves in the test environment, the framework's clock stays. A web test sets the moment with `WebTestCase::clockAt()`, which pins the clock the container already holds instead of replacing it with `set()`, because `set()` throws "already initialized" once anything has created the clock. `PinnableClock::workOnEachSleep()` hands it work to run at the start of each `sleep()` (not again for a sleep inside that work, also through a `withTimeZone()` view, which runs the work through the clock it came from), so a kernel test runs `messenger:consume` while `intakt:review` waits, as a worker process runs beside the command on an install (`JudgingFailedForGoodStatusTest`). Tests: `tests/Support/PinnableClockTest.php` (one boots a kernel outside PHPUnit and reads the clock's class), `tests/Core/Dashboard/UseCase/DashboardPageTestCaseTest.php` (creates the clock before the page setup).
- **An empty env loader in tests (#2232):** `tests/Support/services.yaml` also registers `intakt.test.empty_env_var_loader`, a `tests/Core/Ai/Infrastructure/FixedEnvVars` with no variables tagged `container.env_var_loader`, so it changes no value. The framework drops its secrets vault loader where no `config/secrets/` folder exists, as in a checkout, so this loader is what shows that the kept provider key's loader is handed every other env loader (`KeptProviderKeyVariablesWiringTest`, [AI providers](ai-providers.md)). The test expects exactly that one loader (#2434): a container compiled while `config/secrets/` exists keeps the framework's loader for good, so `AiProvidersTest` removes the `config/secrets/` folder its vaults leave empty after each test and runs in the `serial` group, where no other worker compiles a container while the folder exists. `VaultTestsLeaveNoVaultFolderBehindTest` (also `serial`) runs `AiProvidersTest` and then the wiring test in one PHPUnit process, and checks that `AiProvidersTest` leaves no `config/secrets/` behind; it checks the same for `KeptKeyBuildWarningTest`, which removes the folder the same way.
- **Scratch files in tests skip the disk flush:** the git repositories that tests build (`tests/Gates/Sandbox.php` and `tests/Core/Git/TemporaryRepository.php`) run git with `-c core.fsync=none`, and the test container's SQLite connections run `PRAGMA synchronous = OFF` (see [Persistence](persistence.md)), because nothing reads these files after a crash and the test workers of the `tests` gate otherwise wait on each other's flushes.
- **Doctrine mapping** uses attributes with the `ORM` alias, and each module's entities and mapping live in that module.
- **Dependencies:** official Symfony and Doctrine packages first. Any other package needs a release within the last 12 months and a clean `composer audit`, and the owner approves it; a new official Symfony or Doctrine package is routine under the build loop's composer policy. The release rule applies to the packages Intakt requires directly. A package those pull in is judged together with its parent: it needs a clean `composer audit`, and an older release is accepted when the parent requires it and is itself current (for example `marc-mabe/php-enum` under `justinrainbow/json-schema`); list such packages under `## New dependencies` too. Two release cooldowns apply to PHP dependencies, each deciding something else. The `cooldown` block of the `composer` entry in `.github/dependabot.yml` (3 days, 7 for a major) decides only when Dependabot opens its pull requests. A release the reviews found unsafe is skipped by name and exact version in that entry's `ignore` list (rector/rector 2.8.4, which removed a conditional assignment with side effects, review of #1285), so the next release is reviewed again. The `github-actions` entry waits 7 days before it opens a pull request for a new action release, while the `docker` and `composer` entries keep 3 days, each with a `# zizmor: ignore[dependabot-cooldown]` that cites the 3-day composer cooldown. `config.policy.cooldown` in `composer.json` (period `3 days`, `block` true, `audit` `fail`, which needs Composer 2.11 or later) decides what any `composer update` or `composer require` may lock, whoever runs it, and what the `audit` gate fails on: a locked release published less than 3 days ago (`tests/Application/ComposerCooldownPolicyTest.php`). An exception is written in `config.policy.cooldown.ignore` as a package pattern with a `constraint` and a `reason`, and the `audit` gate names every exception Composer applies to the audit. The only one is the owner's one-time decision of 2026-11-13: `symfony/*` at `8.2.0-BETA2` (released 2026-11-13 17:29 UTC). It is removed again once that release is older than the 3-day cooldown, and no other package gets one. The JavaScript packages of `importmap.php` follow the same rule through two AssetMapper 8.2 settings in `config/packages/asset_mapper.yaml` (forwarded from `framework.asset_mapper` to the `AssetMapperBundle`): `minimum_release_age: 259200` (3 days in seconds, the Composer period) makes `ImportMapUpdateChecker` read npm's full metadata and offer only the newest stable version published at least that long ago (a version exactly 3 days old is eligible), so `importmap:update` keeps a younger one out and `importmap:outdated` names it as withheld; `importmap_integrity_algorithms: [sha384]` makes `ImportMapGenerator` add a sha384 hash of each module's served file to the rendered import map and its `modulepreload` links, and `asset-map:compile` stores it in `importmap.json`, so the browser refuses a module whose bytes changed after compilation (`tests/Application/ImportMapPolicyTest.php`, which also checks the age against `config.policy.cooldown.period`). The hash is computed from the local file, so it does not check what `importmap:install` downloads from jsDelivr; AssetMapper 8.2 has no per-entry hash in `importmap.php`. Intakt runs on Symfony 8.2: `composer.json` requires the Symfony components and bundles at `^8.2` (Symfony AI, Flex, UX and the Mercure bundle have versions of their own) and PHP at `>=8.5.12`. 8.2 is a beta until 8.2.0 is released, so `minimum-stability` is `beta` (with `prefer-stable`), and the lock holds `8.2.0-BETA2`.
- **Message handlers** use Intakt's `AsCommandHandler` and `AsQueryHandler` (in the platform module's `Contract`, with a `Bus` enum), which extend Symfony's `AsMessageHandler` and fix the bus. `config/packages/messenger.yaml` defines two buses, `command.bus` (the default) and `query.bus`, and two transports, `async` and the failure transport `failed` (see [Review rounds](review-rounds.md)); a handler is registered on its attribute's bus only. Each bus also sets Messenger's 8.2 `messages` option (issue #2881) to its marker interface, `CommandMessage` on `command.bus` and `QueryMessage` on `query.bus`, so the bus refuses a message of the other kind when the application dispatches it, before any middleware runs, with Messenger's `InvalidArgumentException` ("This bus only dispatches messages of type ..."); a message a worker receives from a transport (it carries a `ReceivedStamp`) is not checked, as Messenger documents. `command.bus` sets Messenger's `unwrap_exceptions` (issue #2696): when one handler fails, the code that dispatched the command gets that handler's own exception instead of a `HandlerFailedException`, also when the failing handler ran in a command dispatched by another handler, since each dispatch unwraps its one level; several failing handlers still arrive as a `HandlerFailedException`, and so does every failure on `query.bus` and in a worker (`tests/Core/Platform/CommandBusUnwrapTest.php`). A handler that does not read its message takes no parameter and names the message with `handles:`. A handler method takes exactly one message class as its parameter (or none, with `handles:`): `HandledMessagesNameTheirBusTest` (below) fails a union-typed parameter on purpose ("names its message as one class") instead of checking each member of the union. Every message handled through `AsCommandHandler` or `AsQueryHandler` implements the empty marker interface of the bus that attribute names, `CommandMessage` for `command.bus` and `QueryMessage` for `query.bus` (both in the platform module's `Contract`), wherever the message class lives (a module's `Contract/` or the use case's own folder), and never the other marker, so no message is handled on both buses (the unwrap test sends the command `RefuseThing` and the query `FindRefusedThing`). `RoundOpened` is handled on `command.bus`, so it is a `CommandMessage` although its name reads as an event. Through the `messages` option the markers decide which bus accepts a message: a message without a marker is refused on both buses when the application dispatches it. `HandledMessagesNameTheirBusTest` stays: it fails at test time a handler whose message lacks its bus's marker, which the bus option would only refuse when that message is dispatched. `tests/Core/Platform/HandledMessagesNameTheirBusTest.php` reflects every class in a file of `src/` or `tests/Core/Platform/Handler/` that names `AsCommandHandler` or `AsQueryHandler` (so an attribute grouped with another one is found too), takes its message from each such attribute's `handles:` or the handler method's parameter, and fails for a message without its bus's marker or with both markers. `tests/Core/Platform/BusSeparationTest.php` proves the routing, the refusal of a query on `command.bus` and of a command on `query.bus`, and the refusal of a message with no marker (a plain `stdClass`) on both buses, with handlers in `tests/Core/Platform/Handler/`, which `tests/Core/Platform/services.yaml` registers (imported by `config/services.yaml` in the test environment only, skipped when `tests/` is absent). The `architecture` gate refuses `AsMessageHandler` anywhere else in `src/`, the kernel included, also through an alias or in another capitalization (`config/gates/src/Architecture/MessageHandlerOnlyThroughContractAttributes.php`). The failure transport and the retry strategy of `async` are described under [Review rounds](review-rounds.md).
- **Expected failures** implement `Core/Platform/Contract/ReportableFailure` (extends `Throwable`): a failure whose message is written for the person running the command. `ChangeNotFound`, `ChangeIdEmpty`, `ForgeReadFailed`, `PanelConfigurationFailure` (so `PanelNotConfigured`), `GlobCannotBeEvaluated`, `RoundNotNext`, `RepositoryNotFound`, `LocalRepositoryIncomplete` and `RecordedIdentityUnreadable` implement it. The console commands `intakt:review`, `intakt:verdict:identity`, `intakt:change:summarize` and `intakt:review:panel` catch `ReportableFailure` only, print its message and exit with 1; any other exception, an `InvalidArgumentException` from inside a review round included, is a programming error and escapes. `LocalRepository::existingAt()` refuses a `--repository` that is not a directory with `RepositoryNotFound` before a forge is built.
