## Capability tiers per project

`Intakt\Core\Ai\Contract\Tier` is the closed set `strong`, `standard`, `light`. Intakt's own config is a file apart from the AI Bundle's: `config/packages/ai.php` reads the YAML file named by `INTAKT_CONFIG` (else `config/intakt.yaml`, git-ignored; `config/intakt.example.yaml` shows two projects), validates it with `Infrastructure\ProjectsConfiguration` (Symfony Config: project names kept as written, dashes included; tier names; provider names from the `Provider` enum; a string model that is valid UTF-8 and not blank, where blank means only whitespace, Unicode whitespace included, matched with `/^\s*$/u`) and sets the parameter `intakt.projects`. An invalid file fails the container build with the path of the bad key; no file means no projects. The file is read when the container is built, so a change needs `cache:clear`.

A project's optional `review` section is split off before that tree runs (it refuses unknown keys); a `projects` value that is not an array is passed on unchanged, so that tree refuses it. The section is validated by the Review module's `Infrastructure\PanelConfiguration` (`quorum` from the `QuorumPolicy` values; `reviewers` a list, not a map, of at least one, each with a `role` and `prompt` that are valid UTF-8 and not blank, `tier` from `Tier`, `provider` from `Provider`, an integer `budget` of at least 1; unknown keys refused). `PanelConfiguration` takes the provider of each project tier from the validated projects tree and refuses a reviewer whose `provider` differs from the one its project maps its `tier` to, or whose tier the project does not map; it then builds each `Panel` through `ConfiguredPanels` and turns a `Contract\PanelConfigurationFailure` into a config error naming the project. The result is the parameter `intakt.review.panels`. `Infrastructure\ConfiguredPanels::panelFor(string $project)` builds the typed `Contract\Panel` (a non-empty list of `Contract\PanelReviewer`, plus the `QuorumPolicy`) from it, or throws `Contract\PanelNotConfigured`. A `PanelReviewer` holds a `Contract\ReviewerRole` (name and prompt), a `Contract\ReviewerModel` (`Tier` and `Provider`) and the budget. A `Panel` without reviewers throws `Contract\PanelWithoutReviewers`; a `Panel` whose policy `QuorumPolicy::isMet()` refuses even when every reviewer approves (for `one-strong-plus-one`, fewer than two reviewers or none on the strong tier) throws `Contract\PanelCannotReachQuorum`. 
A project's `review` section may also hold `rules`, a list (not a map) of rules that only add reviewers to the core panel. A rule has `min_lines` (an integer of at least 1), `paths` (a list, not a map, of non-empty strings that are valid UTF-8, so a number or a boolean is refused), or both, and `reviewers` in the same shape as above, checked against the same tier-provider mapping. A rule with neither trigger is refused. `Contract\ChangeDescription` (lines changed, changed paths, labels) describes a change; `ConfiguredPanels::panelForChange(string $project, ChangeDescription $change)` returns the core reviewers followed by the reviewers of every rule that matches, under the project's own quorum policy. A rule matches when the change has at least `min_lines` lines or touches a path that matches one of its globs; the label `review:full` (`ChangeDescription::FULL_REVIEW_LABEL`) matches every rule. `Contract\PathGlob` anchors a glob on the whole path: `*` and `?` stay inside one folder, `**` crosses folders and matches any byte, newline included, and `/**/` and a leading `**/` also match no folder, as in gitignore (glob and path are both read with a leading slash, and a run of `**/` segments counts as one, so `src/**/**/Security/**` matches `src/Security/Door.php`); a path that is valid UTF-8 is matched by character (`/u`), any other path by byte, so a file name with other bytes still meets its rule. At boot both the core panel and the largest panel (every rule added) are built, so a panel the quorum policy can never meet for some change is refused: rules only add reviewers, so these two bound every panel a change can get. `panelFor($project)` is the core panel alone. `UseCase\ChoosePanel\ChoosePanelCommand` (`intakt:review:panel <project> [--lines=N] [--path=P ...] [--label=L ...]`) prints the quorum and each chosen reviewer (role, tier, provider, budget); it reads only the configuration, calls no model and fails with the panel-not-configured message for an unknown project and refuses a negative `--lines`; a path glob the regular-expression engine cannot evaluate (a backtrack limit, say) fails the choice with `GlobCannotBeEvaluated` instead of being skipped, and the command prints that error, which names the glob, and fails instead of letting the exception escape. `intakt:review` runs the chosen panel (see Review command under [Verdict identity](forge-contract.md#verdict-identity)); the labels of the dry run come from the command line, not from a forge.

For each enabled provider, `Infrastructure\ProjectModelCatalog` adds to the AI Bundle's `model_catalog.models` every model a project maps to it that the bridge's own catalog does not list, with the bridge's model class (`Claude`, `Gpt`, or the generic `CompletionsModel`) and the capabilities `input-messages`, `output-text`, `output-structured` and `tool-calling`; a listed model keeps the bridge's entry. `config/packages/ai.php` registers the service locator `intakt.ai.provider_platforms`, which holds the account failover platform of each enabled provider (`intakt.ai.accounts.<provider>`, see [AI providers](ai-providers.md)) under its `Provider` value. The service `Infrastructure\TierPlatform` implements the contract `Contract\TierInvoker`, which other modules use instead of the class, with two methods. `answering(project, tier)` chooses the `ResolvedModel` a call runs on (a resolution failure throws its `TierResolutionFailure`). A tier without substitutes (`TierResolver::hasSubstitutes()` false) resolves its own model through `resolve()`, so a disabled provider throws `TierProviderDisabled`; when every account of its provider cools down from a rejected key (`AccountCooldowns::isEveryAccountRejected()`) it throws `Contract\EveryKeyRejected`, an `AuthenticationException` naming only the provider, and when its provider is otherwise out it throws `EveryAccountCoolingDown`. A tier with substitutes configured (true even when every substitute is on a disabled provider) takes its own model from `configured()` and returns the first of it and `TierResolver::substitutes()` whose provider can answer: not disabled (`isDisabled()`), not every account rejected, and an account free for that model, which for an `AccountFailoverPlatform` means neither the account's window nor its pinned router provider is cooling (`ModelWaits::secondsUntilFree()` is zero, see [AI providers](ai-providers.md)), else `AccountCooldowns::secondsUntilAnAccountIsFree()` is zero. Only the first model listed on a provider is judged (the tier's own model, else its first substitute there); a later substitute on a provider already judged is skipped. A switch is logged at info level (`Provider {own} is out, so the review goes to the substitute {substitute}.`). The choice reads the configuration and the cooldowns only, never a failed call, so a refused request cannot pick its reviewer. When none can answer it throws `Contract\EveryProviderOut` with a `Contract\ProviderOutage` per provider it tried, its own and the enabled substitutes, each with a fixed reason: `disabled`, `keys rejected`, or the wait (`for 60 s`); the message holds provider names and those reasons only. `invoke(ResolvedModel, TierRequest)` (`TierRequest` keeps the input and the Platform options to itself and sends them with `invokeOn()`; `of()` takes a text or object input, `ofParts()` with `withPart()` builds an array input one key at a time so its keys and order stay as given, and `withDefaults()` adds options, where one already set wins) invokes that model name on its provider's bundle platform, whose Symfony AI `CatalogBasedModelRouter` finds the model in the bundle's model catalog; it never moves a failed call to another provider (another account of that provider is still tried by `AccountFailoverPlatform`). `SymfonyAiVendor` asks `answering()` once per review and builds a `TierRoutedPlatform` on that `ResolvedModel`, which runs every round of the agent on it, so a review that went to a substitute is never continued by another provider; unread approvals and the parallel-call limit are judged on the provider that answered (see [Vendor](vendor.md)). Recording a substitute's review and the catch-up review it owes are planned.

`Contract\TierResolver` (`projects()`, `resolve(project, tier)`, `configured(project, tier)`, `isDisabled(provider)`, `substitutes(project, tier)`, `hasSubstitutes(project, tier)`) is implemented by `Infrastructure\ConfiguredTierResolver` and returns a `ResolvedModel` (provider and model name); `configured()` returns the tier's own model also on a disabled provider, which `resolve()` refuses; `substitutes()` returns the tier's optional `substitutes` list of `ProjectsConfiguration` (default empty) as `ResolvedModel`s in configured order, leaving out those on a disabled provider, `hasSubstitutes()` tells whether that list is configured at all, disabled ones included, and `ProjectModelCatalog` adds their models to the catalog too. A failure is a `TierResolutionFailure`: `ProjectNotConfigured`, `TierNotMapped`, or `TierProviderDisabled`, which carries the provider's disabled message from `intakt.ai.disabled_providers`, so a tier pointing at a switched-off provider is reported when resolved, never at boot. `php bin/console intakt:ai:tiers` (`UseCase/ListProjectTiers`) prints every project with each tier's provider and model, or the problem. Tests: `tests/Core/Ai/Infrastructure/ConfiguredTierResolverTest.php`, `ProjectsConfigurationTest.php`, `ProjectModelCatalogTest.php`, `TierPlatformTest.php` (two `MockPlatformFactory` platforms with scripted answers, and stubbed cooldowns for the choice of substitute), `tests/Core/Ai/UseCase/ListProjectTiersCommandTest.php` and `tests/Application/ProjectTiersTest.php` (the kernel boots with two projects that map tiers differently, and the locator holds only the enabled provider, whose bundle platform finds a project's model in its model catalog).

**Output limit.** `ProjectsConfiguration` gives each tier an integer `max_output` (minimum 1, default `Tier::defaultMaxOutput()`: 16000 strong, 8000 standard, 4000 light), kept at the tier level so its substitutes share it. `ConfiguredTierResolver` puts it into `ResolvedModel::$maxOutput` (null when a mapping carries none, which sends no limit), and `TierPlatform::invoke()` adds it to the Platform options as `PlatformOptions::MAX_OUTPUT_TOKENS`, which the Anthropic and generic bridges map to their own parameter; an option the caller already set wins, and a provider with `Provider::limitsOutput()` false (`claude_code`, `codex`) gets none. A reviewer's retry after a stop at the limit runs on `ResolvedModel::withMaxOutput()` with twice that limit, so it needs no setting of its own (see [Review flow](review-flow.md)). Tests: `TierPlatformTest.php` (the limit of each tier reaches the vendor call of that tier through a recording platform) and `ProjectsConfigurationTest.php`.

### Mode per project

A project's optional `mode` key is split off like its `review` section and validated by the ReviewerForLoop module's `Infrastructure\ProjectModeConfiguration` (a value of the `Contract\ProjectMode` enum, `live` or `reviewer-for-loop`); the result is the parameter `intakt.reviewer_for_loop.modes` (project name to mode, only the projects that set one), which `Infrastructure\ConfiguredProjectModes` reads behind the contract `Contract\ProjectModes` (`of(project): ProjectMode`, `live` for a project without a mode). The shadow mode is gone (issue #1478, part 3 of #1433): `ProjectMode` has no `shadow` case, so a file that sets `mode: shadow` stops the boot as an unknown value, and no decorator guards `Plugin/Forge/Contract/ForgeWrites` by mode any more: the container's `ForgeWrites` is `GitHubForge` itself (see [Forge writes](forge-contract.md#forge-writes)). Two places read the mode. `Review/UseCase/PublishVerdict/PublishVerdictHandler` publishes the loop's own pull requests only for a `reviewer-for-loop` project (see [Reviewer-for-loop mode](#reviewer-for-loop-mode)), and a pull request handed to Intakt in any mode (see [Pull requests handed to Intakt](handed-to-intakt.md#intakts-review-counts)), and `Review/UseCase/RunReviewRound/RoundLedger::verdictReceived()` writes the project's mode at that moment into every `verdict_received` row (`"mode":"reviewer-for-loop"` or `"mode":"live"`; rows written before the mode was recorded have no `mode`, and rows written while the shadow mode existed keep `"mode":"shadow"`, which the dashboard reads as `live`). The mark is a record only (issue #1476, part 1 of #1433): `RunReviewRoundHandler` opens every round alike, through `RoundOpening::open()`, without asking a ceiling, and `VerdictsOfRoundHandler` returns a round's stored verdicts as `counting` whenever its standing is not `stale` and the round is not a replay ([Review flow](review-flow.md#a-replay)), whatever the project's mode or the marks of the round's rows. The Budget module has no shadow ceilings and no shadow start guard (issue #1477, part 2 of #1433): `BudgetConfiguration` has no `shadow_ceilings` key, so a file that still sets `budget.shadow_ceilings` stops the boot as an unknown key (`tests/Core/Budget/Infrastructure/BudgetConfigurationTest.php`, `tests/Application/ProjectTiersTest.php`). Part of the [reviewer for the loop](../plan.md#reviewer-for-the-loop-issue-1251) stage: the watcher starts a round for every green head (T38) whatever the project's mode; nothing merges yet, so a verdict is counted in three places only, `VerdictsOfRoundHandler`, `intakt:review` (`ReviewChange`) and the reviewer-for-loop publication (`VerdictForTheLoop`), and each leaves a replay out ([Review flow](review-flow.md#a-replay)); the dashboard's review page shows the decision a round's ledger rows give, a replay's too, and counts it for nothing. Tests: `tests/Application/ProjectTiersTest.php` (the container reads `reviewer-for-loop` for a project that sets it and `live` for one without a mode; `mode: shadow` and any other unknown mode stop the boot) and `tests/Core/Review/UseCase/RunReviewRound/RoundLedgerPayloadsTest.php` (the mode written into a `verdict_received` row).

### Reviewer-for-loop mode

Issue #1251, parts 1 and 2 of 3. A project whose `mode` is `reviewer-for-loop` has Intakt's panel review the heads the build loop that developed Intakt pushes, in place of the loop's own Claude reviewer, while the loop keeps building, merging and asking the owner. The mode filters no head: the watcher starts a round for every green head of the project's open pull requests, as for any watched project, and `RunReviewRoundHandler` opens it like any other round. `RoundLedger::verdictReceived()` marks each `verdict_received` row `"mode":"reviewer-for-loop"`, and `VerdictsOfRoundHandler` counts its verdicts as a live project's, and the review page shows them without a mark. The published verdict is the only thing it writes: nothing calls `ForgeWrites::postReview()`, and `PublishVerdictHandler` is the only caller of `publishVerdict()`, so Intakt never merges, pushes, labels or approves a protected head in this mode (D2).

**Publishing the verdict** (issue #1251, part 2, D1). The judge transition of the `review_round` workflow runs inside `JudgedRounds::record()`'s transaction, once per round; `Review/UseCase/PublishVerdict/QueuePublicationOfJudgedRound` (`#[AsCompletedListener]` on `judge`) dispatches `PublishVerdict(roundId)` there, routed to the `async` transport, so a judged round is queued once with its judge record and a redelivered judging queues nothing. A round that never reaches `judge` still gets a status: when a `JudgeRound` message fails for good (for example after `TierNotMapped` exhausted the retries), Messenger dispatches the `RecordFailedJudging` message its `DispatchOnFailureStamp` carries (see [Review flow](review-flow.md#a-judging-that-failed-for-good)), and its handler queues `PublishVerdict(roundId)` once; no listener of Intakt's own watches worker failures for it. A round whose reviewer messages are parked reaches `judge` anyway, because `BlockReviewerOfFailedMessage` blocks those reviewers and completes the round. `PublishVerdictHandler` reads the round and the project's mode at that moment and returns for any mode but `reviewer-for-loop` unless the round's change is handed to Intakt (`Watcher/Contract/HandedOverChanges`, see [Pull requests handed to Intakt](handed-to-intakt.md#intakts-review-counts)), and also when a later round of the change that reviewed the same head commit is already judged (`ReviewRounds::judgedAfter()`; that check and the forge write run under the change's publication lock `ChangePublications`, and a round marked stale publishes a withdrawal, see [Review flow](review-flow.md#a-round-marked-stale)); the marks of the round's `verdict_received` rows are not read, so a round reviewed before the project was switched to `reviewer-for-loop` publishes its verdict like any other. `VerdictForTheLoop` decides like `intakt:review`: `ChangeDecision` over the quorum recorded on the round's `review_started` row (`RoundLedgerReading::quorumOf()`; a row without one decides `blocked`) and each reviewer's vote as the judge step recorded it in `judge_done` (`RoundLedgerReading::votesOf()`; one without a verdict votes `blocked`; a `changes` verdict of only P3 findings the judge deferred or rejected votes `approve`, one whose findings are on no list `blocked`, see [Review flow](review-flow.md)), and it builds a `Plugin/Forge/Contract/PublishedVerdict` for the round's reviewed head (`ReviewRound::identity()`), carrying the round's id as its `ReviewToken`: a round whose `ReviewRound::replayMark()` is `Replay` is `Error` with the description `Intakt does not count a replay as a review of this head.` and no comment, before any vote is read and before the withdrawal of a stale round, so a replay round marked stale keeps that `Error`; a round not in the `judged` state (only a judging that failed for good publishes one) and a `blocked` decision are `Error` with the description `Intakt could not review this head.` and no comment, because the comment's verdict is only `approve` or `changes`; otherwise the status follows `LoopReviewComment::verdict()`, `approve` as `HeadStatus::Success` and `changes` as `Failure`, both with the comment, so the status and the comment cannot disagree. That verdict is the decision, except that an `approve` whose act list holds a P1 becomes `changes`, because the loop reads an open P1 as changes whatever the JSON says (`ReviewerForLoop/Domain/LoopReviewReader`); under an `approve` the findings follow a `Follow-ups:` line, below which the loop does not count a P2 as blocking. `LoopReviewComment` writes the comment in the shape of the loop's own reviewer comments: the heading `**Review by Intakt** (head <first 12 hex of the head>)`, a blank line, under an approval the `Follow-ups:` line, one `[P1|P2|P3] file:line: text` line per finding of the judge's act list (the same list `intakt:review` prints; builder's choice: a finding without a line is `file: text`, one without a file `(no file): text`, and every run of whitespace in the place and text becomes one space, so a model's line break can open neither a fence nor a finding line; then the whole finding line, and only it, is run through the shared `Redaction` with no job credentials, because a header can start in the place and end in the text, and a redaction that finds no end, such as an unclosed `Authorization: [`, takes the rest of its text, which must not be the verdict block; after the redaction every `<!--` in the finding line becomes `&lt;!--` (#1415), because GitHub hides everything after an HTML comment opener, the verdict block too, and a finding that quotes another round's marker must not carry it into the App's comment; the heading, the `Follow-ups:` line and the block hold no reviewer text and are not redacted), a blank line when there are findings, then a fenced `json` block holding `{"verdict":"approve"|"changes","head":"<40 hex>","summary":"<a> of <n> reviewers approve; findings to act on: <k>."}` (builder's choice for the summary). The handler calls `ForgeWrites::publishVerdict(project, ChangeId of the round's change, verdict)`. `GitHubForge::publishVerdict()` runs only through `Plugin/GitHubForge/Infrastructure/GitHubAppSetting::whenConfigured()` (issue #2162, D1): while `GITHUB_APP_ID` is empty or only spaces (the demo), it returns before any scan, lock, token or request, so the message succeeds and nothing is retried. A Messenger worker's start (`GitHubAppSetting::onWorkerStarted()`, an `#[AsEventListener]` on `WorkerStartedEvent`, so also a worker of a `live` project like the demo's, whose handler never reaches the forge for the loop's own pull requests; a pull request handed to Intakt gets its review published in any mode, see [Pull requests handed to Intakt](handed-to-intakt.md#intakts-review-counts)) or, in a process without a worker, the first such call logs one info record that verdicts are not published to GitHub (a marker the service keeps, never reset between messages, so one line per start; the review page and MCP show the verdict). Otherwise it refuses an address that is no GitHub pull request (`ChangeNotFound`, which the handler logs as a warning and drops, since a round of a local branch has nothing to publish on), takes the comment as `LoopReviewComment` redacted it (`PublishedVerdict::comments()`, none or one, not redacted a second time) and scans it with `SecretScan`; a hit throws `ReviewTextHoldsSecret` before any request, and the handler then publishes the same head as `Error` with the description `Intakt could not publish its review of this head.` and no comment. Otherwise `Plugin/GitHubForge/Infrastructure/VerdictLocks` takes the `LockFactory` lock `intakt.verdict.<round id>` (`GitHubForgeServices::VERDICT_LOCK_PREFIX`) without waiting (the file lock store all workers share); a busy lock is `ForgeWriteFailed`, so that delivery is retried, and the lock is held from the read of the comments to the status post and released also when a post fails. When there is a comment, `Plugin/GitHubForge/Infrastructure/PostedComments::notYetPosted()` reads the pull request's comments (`issues/<n>/comments`, 100 per page, at most 30 pages, a full 30th page fails the write) for one whose `performed_via_github_app.id` is the App's `GITHUB_APP_ID`, which GitHub alone sets, and whose body, trailing whitespace removed, ends with the marker `<!-- intakt-verdict: <round id> -->` (where the post puts it), so a person's or another App's comment with the marker suppresses nothing, and neither does this App's comment of another round that quotes the marker inside a finding (#1415); when none holds it, the comment goes to `issues/<n>/comments` with the marker after a blank line, and then the status goes to `statuses/<head>` with `context` `intakt/review`, `state` the `HeadStatus` value and a fixed description, both through the never-retried `post()`, so a head never shows the status without its comment. It reads no head first: the status and the comment name the head they judge. A failed read or write is `ForgeWriteFailed` and escapes the handler, so Messenger retries the message by the `async` transport's strategy; a retry finds the comment an earlier attempt posted, also one GitHub stored while answering an error, by its marker and posts only the status, so a round leaves one comment. The App needs write access to commit statuses (`statuses:write`) and to pull requests. **Rollback:** the loop switches back to its own Claude reviewer, and the project's mode goes back to `live` (which publishes nothing on the loop's own pull requests; a pull request handed to Intakt still gets its review published, see [Pull requests handed to Intakt](handed-to-intakt.md#intakts-review-counts)).
