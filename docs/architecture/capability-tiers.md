## Capability tiers per project

`Intakt\Core\Ai\Contract\Tier` is the closed set `strong`, `standard`, `light`. Intakt's own config is a file apart from the AI Bundle's: `config/packages/ai.php` reads the YAML file named by `INTAKT_CONFIG` (else `config/intakt.yaml`, git-ignored; `config/intakt.example.yaml` shows two projects), validates it with `Infrastructure\ProjectsConfiguration` (Symfony Config: project names kept as written, dashes included; tier names; provider names from the `Provider` enum; a string model that is valid UTF-8 and not blank, where blank means only whitespace, Unicode whitespace included, matched with `/^\s*$/u`) and sets the parameter `intakt.projects`. An invalid file fails the container build with the path of the bad key; no file means no projects. The file is read when the container is built, so a change needs `cache:clear`.

A project's optional `review` section is split off before that tree runs (it refuses unknown keys); a `projects` value that is not an array is passed on unchanged, so that tree refuses it. The section is validated by the Review module's `Infrastructure\PanelConfiguration` (`quorum` from the `QuorumPolicy` values; `reviewers` a list, not a map, of at least one, each with a `role` and `prompt` that are valid UTF-8 and not blank, `tier` from `Tier`, `provider` from `Provider`, an integer `budget` of at least 1; unknown keys refused). `PanelConfiguration` takes the provider of each project tier from the validated projects tree and refuses a reviewer whose `provider` differs from the one its project maps its `tier` to, or whose tier the project does not map; it then builds each `Panel` through `ConfiguredPanels` and turns a `Contract\PanelConfigurationFailure` into a config error naming the project. The result is the parameter `intakt.review.panels`. `Infrastructure\ConfiguredPanels::panelFor(string $project)` builds the typed `Contract\Panel` (a non-empty list of `Contract\PanelReviewer`, plus the `QuorumPolicy`) from it, or throws `Contract\PanelNotConfigured`. A `PanelReviewer` holds a `Contract\ReviewerRole` (name and prompt), a `Contract\ReviewerModel` (`Tier` and `Provider`) and the budget. A `Panel` without reviewers throws `Contract\PanelWithoutReviewers`; a `Panel` whose policy `QuorumPolicy::isMet()` refuses even when every reviewer approves (for `one-strong-plus-one`, fewer than two reviewers or none on the strong tier) throws `Contract\PanelCannotReachQuorum`. 
A project's `review` section may also hold `rules`, a list (not a map) of rules that only add reviewers to the core panel. A rule has `min_lines` (an integer of at least 1), `paths` (a list, not a map, of non-empty strings that are valid UTF-8, so a number or a boolean is refused), or both, and `reviewers` in the same shape as above, checked against the same tier-provider mapping. A rule with neither trigger is refused. `Contract\ChangeDescription` (lines changed, changed paths, labels) describes a change; `ConfiguredPanels::panelForChange(string $project, ChangeDescription $change)` returns the core reviewers followed by the reviewers of every rule that matches, under the project's own quorum policy. A rule matches when the change has at least `min_lines` lines or touches a path that matches one of its globs; the label `review:full` (`ChangeDescription::FULL_REVIEW_LABEL`) matches every rule. `Infrastructure\PathGlob` anchors a glob on the whole path: `*` and `?` stay inside one folder, `**` crosses folders and matches any byte, newline included, and `/**/` and a leading `**/` also match no folder, as in gitignore (glob and path are both read with a leading slash, and a run of `**/` segments counts as one, so `src/**/**/Security/**` matches `src/Security/Door.php`); a path that is valid UTF-8 is matched by character (`/u`), any other path by byte, so a file name with other bytes still meets its rule. At boot both the core panel and the largest panel (every rule added) are built, so a panel the quorum policy can never meet for some change is refused: rules only add reviewers, so these two bound every panel a change can get. `panelFor($project)` is the core panel alone. `UseCase\ChoosePanel\ChoosePanelCommand` (`intakt:review:panel <project> [--lines=N] [--path=P ...] [--label=L ...]`) prints the quorum and each chosen reviewer (role, tier, provider, budget); it reads only the configuration, calls no model and fails with the panel-not-configured message for an unknown project and refuses a negative `--lines`; a path glob the regular-expression engine cannot evaluate (a backtrack limit, say) fails the choice with `GlobCannotBeEvaluated` instead of being skipped, and the command prints that error, which names the glob, and fails instead of letting the exception escape. `intakt:review` runs the chosen panel (see Review command under [Verdict identity](forge-contract.md#verdict-identity)); the labels of the dry run come from the command line, not from a forge.

For each enabled provider, `Infrastructure\ProjectModelCatalog` adds to the AI Bundle's `model_catalog.models` every model a project maps to it that the bridge's own catalog does not list, with the bridge's model class (`Claude`, `Gpt`, or the generic `CompletionsModel`) and the capabilities `input-messages`, `output-text`, `output-structured` and `tool-calling`; a listed model keeps the bridge's entry. `config/packages/ai.php` registers the service locator `intakt.ai.provider_platforms`, which holds the account failover platform of each enabled provider (`intakt.ai.accounts.<provider>`, see [AI providers](ai-providers.md)) under its `Provider` value. The service `Infrastructure\TierPlatform` implements the contract `Contract\TierInvoker`, which other modules use instead of the class, with two methods. `answering(project, tier)` chooses the `ResolvedModel` a call runs on (a resolution failure throws its `TierResolutionFailure`). A tier without substitutes (`TierResolver::hasSubstitutes()` false) resolves its own model through `resolve()`, so a disabled provider throws `TierProviderDisabled`; when every account of its provider cools down from a rejected key (`AccountCooldowns::isEveryAccountRejected()`) it throws `Contract\EveryKeyRejected`, an `AuthenticationException` naming only the provider, and when its provider is otherwise out it throws `EveryAccountCoolingDown`. A tier with substitutes configured (true even when every substitute is on a disabled provider) takes its own model from `configured()` and returns the first of it and `TierResolver::substitutes()` whose provider can answer: not disabled (`isDisabled()`), not every account rejected, and a free account (`AccountCooldowns::secondsUntilAnAccountIsFree()` is zero). A switch is logged at info level (`Provider {own} is out, so the review goes to the substitute {substitute}.`). The choice reads the configuration and the cooldowns only, never a failed call, so a refused request cannot pick its reviewer. When none can answer it throws `Contract\EveryProviderOut` with a `Contract\ProviderOutage` per provider it tried, its own and the enabled substitutes, each with a fixed reason: `disabled`, `keys rejected`, or the wait (`for 60 s`); the message holds provider names and those reasons only. `invoke(ResolvedModel, TierRequest)` (`TierRequest` holds the input and the Platform options) invokes that model name on its provider's bundle platform, whose Symfony AI `CatalogBasedModelRouter` finds the model in the bundle's model catalog; it never moves a failed call to another provider (another account of that provider is still tried by `AccountFailoverPlatform`). `SymfonyAiVendor` asks `answering()` once per review and builds a `TierRoutedPlatform` on that `ResolvedModel`, which runs every round of the agent on it, so a review that went to a substitute is never continued by another provider; unread approvals and the parallel-call limit are judged on the provider that answered (see [Vendor](vendor.md)). Recording a substitute's review and the catch-up review it owes are planned.

`Contract\TierResolver` (`projects()`, `resolve(project, tier)`, `configured(project, tier)`, `isDisabled(provider)`, `substitutes(project, tier)`, `hasSubstitutes(project, tier)`) is implemented by `Infrastructure\ConfiguredTierResolver` and returns a `ResolvedModel` (provider and model name); `configured()` returns the tier's own model also on a disabled provider, which `resolve()` refuses; `substitutes()` returns the tier's optional `substitutes` list of `ProjectsConfiguration` (default empty) as `ResolvedModel`s in configured order, leaving out those on a disabled provider, `hasSubstitutes()` tells whether that list is configured at all, disabled ones included, and `ProjectModelCatalog` adds their models to the catalog too. A failure is a `TierResolutionFailure`: `ProjectNotConfigured`, `TierNotMapped`, or `TierProviderDisabled`, which carries the provider's disabled message from `intakt.ai.disabled_providers`, so a tier pointing at a switched-off provider is reported when resolved, never at boot. `php bin/console intakt:ai:tiers` (`UseCase/ListProjectTiers`) prints every project with each tier's provider and model, or the problem. Tests: `tests/Core/Ai/Infrastructure/ConfiguredTierResolverTest.php`, `ProjectsConfigurationTest.php`, `ProjectModelCatalogTest.php`, `TierPlatformTest.php` (two `MockPlatformFactory` platforms with scripted answers, and stubbed cooldowns for the choice of substitute), `tests/Core/Ai/UseCase/ListProjectTiersCommandTest.php` and `tests/Application/ProjectTiersTest.php` (the kernel boots with two projects that map tiers differently, and the locator holds only the enabled provider, whose bundle platform finds a project's model in its model catalog).

**Output limit.** `ProjectsConfiguration` gives each tier an integer `max_output` (minimum 1, default `Tier::defaultMaxOutput()`: 16000 strong, 8000 standard, 4000 light), kept at the tier level so its substitutes share it. `ConfiguredTierResolver` puts it into `ResolvedModel::$maxOutput` (null when a mapping carries none, which sends no limit), and `TierPlatform::invoke()` adds it to the Platform options as `PlatformOptions::MAX_OUTPUT_TOKENS`, which the Anthropic and generic bridges map to their own parameter; an option the caller already set wins, and a provider with `Provider::limitsOutput()` false (`claude_code`, `codex`) gets none. A reviewer's retry after a stop at the limit runs on `ResolvedModel::withMaxOutput()` with twice that limit, so it needs no setting of its own (see [Review flow](review-flow.md)). Tests: `TierPlatformTest.php` (the limit of each tier reaches the vendor call of that tier through a recording platform) and `ProjectsConfigurationTest.php`.

### Shadow mode per project

A project's optional `mode` key is split off like its `review` section and validated by the Shadow module's `Infrastructure\ProjectModeConfiguration` (a value of the `Contract\ProjectMode` enum, `live` or `shadow`); the result is the parameter `intakt.shadow.modes` (project name to mode, only the projects that set one), which `Infrastructure\ConfiguredProjectModes` reads behind the contract `Contract\ProjectModes` (`of(project): ProjectMode`, `live` for a project without a mode). `Infrastructure\ShadowGuardedForgeWrites` decorates the service `Plugin/Forge/Contract/ForgeWrites` (see [Forge writes](forge-contract.md#forge-writes)): for a project whose mode is `shadow` each write returns without reaching the forge; any other project, one without a mode included, writes through the decorated forge. It is defined in `config/services.yaml` (`decorates` with `decoration_on_invalid: ignore`) and left out of the resource scan, because the scan would alias `ForgeWrites` to the guard itself when it is the only class implementing it; it decorates `GitHubForge`, the only forge that writes, and with no forge that writes it would be dropped from the container. A shadow project's round runs its whole panel and judge like a live one's, and `ReviewChange` returns its decision as for a live one. Two more places read the mode. `Review/UseCase/RunReviewRound/RoundLedger::verdictReceived()` writes the project's mode at that moment into every `verdict_received` row (`"mode":"shadow"` or `"mode":"live"`; rows written before this change have no `mode`). `Review/UseCase/ReadVerdicts/ShadowRounds::isShadow(round)` is true when the round's project is in shadow mode now or any `verdict_received` row of the round carries `"mode":"shadow"` (it reads only the `verdict_received` events, through `Ledger::readOfKind()`, each as a `Contract\VerdictReceived`; a row that does not deserialize, one written without `mode` included, marks nothing), and then `VerdictsOfRoundHandler` returns no `counting` verdicts, whatever the standing: a verdict recorded in shadow mode never counts for a merge, also after the project is switched to live, and a project switched to shadow counts none of its earlier verdicts. The handler reads the round's verdicts before the ledger: a reviewer's verdict and its `verdict_received` row commit in one transaction, so the ledger read after the verdicts holds the mark of every verdict it returns, also when a worker commits a verdict between the two reads. **Shadow ceiling** (plan task T41, part 3). `Review/UseCase/RunReviewRound/RunReviewRoundHandler` reads the project's mode through `ProjectModes` and, for a project whose mode is `shadow`, calls `ShadowRoundHold::refuseAboveTheCeiling()` before `RoundOpening::open()` stores the round, its `review_started` event and its messages in one transaction. The hold asks `Budget/Contract/ShadowStartGuard::decide(provider)` for each distinct provider the round may spend: every reviewer's own provider and the providers of `Ai/Contract/TierResolver::substitutes(project, tier)` for its tier (a substitute on a disabled provider is left out by the resolver, since it never answers), because `TierPlatform::answering()` moves a review to a substitute as soon as its own provider is out, and the judge's providers, `TierResolver::configured(project, light)` and the substitutes of the light tier, because a reviewer's findings make the round call the judge on that tier (a project without a light tier adds none, since its judge fails with `TierNotMapped` before it reaches an account); the list is deduplicated, so the guard is asked once per provider, and `shadow_round_held` names the provider that held the round. A reviewer's tier the resolver cannot resolve fails the start with its `TierResolutionFailure`. Its implementation `Budget/Domain/EveryAccountShadowGuard` asks the shadow `BudgetGuard::decide(account, 0)` for every enabled account of the provider (`Ai/Contract/EnabledAccounts`, read from the parameter `intakt.ai.accounts` by `Infrastructure/ConfiguredAccounts`) and returns the first decision that does not admit, else `start`: a call runs on the first account outside cooldown and fails over to the next (`Ai/Infrastructure/AccountFailoverPlatform`), so every account a reviewer may reach must be below the shadow ceilings; a provider without an enabled account starts (the vendor names that failure). When a provider does not start, `RoundLedger::shadowRoundHeld()` appends `shadow_round_held` (`project`, `change`, `provider`, `reason`, the `StartDecision` value) outside the round's transaction, no round or message is stored, and `ShadowCeilingReached` (a `ReportableFailure`) is thrown, whose message says the account is not below the shadow ceiling for `at-ceiling` and, for any other decision, that it is not available for a start, with the decision in plain words and its value (`tests/Core/Review/UseCase/RunReviewRound/ShadowCeilingReachedTest.php`); `ReviewChange::start()` unwraps it from Messenger's `HandlerFailedException` like `RoundNotNext`. The shadow ceilings go to the same `CeilingStartGuard` class (so the weekly pace applies, with the shadow weekly ceiling as its base) built a second time in `config/packages/ai.php` as an inline service with the parameter `intakt.budget.shadow_ceilings`, inside a second `BudgetGuard`, the service `intakt.budget.shadow_ceiling_guard`, so the shared holds and an account's cooldown hold a shadow round too; `BudgetConfiguration` reads `budget.shadow_ceilings.<UsageWindow value>` with `DEFAULT_SHADOW_CEILING` 70 and the same checks as `budget.ceilings`. The hold is a start-time check only: it does not stop a round already stored, and a live project is never asked. Tests: `tests/Core/Review/UseCase/RunReviewRound/ShadowRoundHoldTest.php` (above the ceiling no round starts and the reason is in the ledger; below it a round starts; one account of the provider above it holds the round, whether it is the account the reviewer runs on or the one it fails over to; an account of a tier's substitute provider above it holds the round and the event names the substitute, and own and substitute accounts below it start the round; the judge's light-tier provider or its substitute above it holds the round, and below it the round starts; a live round is not asked; the caller gets the hold unwrapped), `tests/Core/Budget/Domain/EveryAccountShadowGuardTest.php`, `tests/Core/Ai/Infrastructure/ConfiguredAccountsTest.php`, `tests/Core/Budget/Infrastructure/BudgetConfigurationTest.php` and `tests/Application/ProjectTiersTest.php` (the default and the owner's value reach the parameter; at 75 percent the container's shadow guard holds a provider while its start guard starts). Part of plan task T41: the watcher starts a round for every green head (T38) whatever the project's mode, so a shadow project's panel runs on every head the watcher admits, held by the shadow ceiling above; nothing merges yet, so `VerdictsOfRound` is the only place a verdict is counted. Tests: `tests/Core/Shadow/Infrastructure/ShadowGuardedForgeWritesTest.php`, `tests/Core/Review/UseCase/ReadVerdicts/VerdictsOfRoundTest.php` (the switches in both directions, a shadow verdict committed right after the ledger read counts none once the project is live, and a shadow mode of another project leaves a round counting), `tests/Core/Shadow/ShadowRoundTest.php` (a shadow round's `verdict_received` rows carry `shadow` and its current approvals count none through the container's handler; a live round's rows carry `live` and its two count) and `tests/Application/ProjectTiersTest.php` (in the test environment `tests/Core/Shadow/services.yaml` makes `WriteRefusingForge`, which logs and refuses every write, the container's `ForgeWrites` and also public under its own class name; a shadow project's round through `ReviewChange` reaches its two-reviewer decision and its post through the container leaves the forge's write log empty, a live project's post is refused by it, a project without a mode is refused by it, and an unknown mode stops the boot).
