# Workflow risk scan

Plan task T55, part 1 of 2. Behind the GitHub forge, a change may be pushed without the owner's approval only when its workflows reach no more than a GitHub-hosted, throwaway runner with a read-only token and no secrets ([Merge](../design/05-architecture/08-merge.md)). Part 1 is the scan that decides that; part 2 (holding a build with a risky CI change local until the owner's `approve <sha>`) is not built yet, so nothing holds a push on the scan's findings so far.

## The scan

`Plugin/GitHubForge/Domain/WorkflowRiskScan::scan(WorkflowFile ...$files)` (`#[NoDiscard]`) answers a `WorkflowRisk`: its `findings` (path, line, kind, detail; line 0 is the whole file) and `isRisky()`, true when there is any finding. The caller passes the head's, main's and the merged workflows together, so a finding in any of them makes the change risky. A `WorkflowFile` whose content is `null` (it could not be read) or is not valid UTF-8 is one `unreadable` finding.

Each file is read line by line, a strict reader of the plain block YAML workflows are written in: `WorkflowLines` turns each line into a key or list item (`WorkflowNode`, its value a `WorkflowValue`), script text, or an unreadable line; `WorkflowFileScan` keeps the keys above the current line by indentation and reads what they mean; `WorkflowJobs` keeps each job's runner and token declarations until the file's end. None of them guesses: a form it does not read is an `unreadable` finding, so it can only ask the owner too often, never too rarely. The kinds (`WorkflowRiskKind`):

- `unreadable`: a `runs-on` from a variable or an expression (`${{ ... }}`, `vars.CI_RUNS_ON` included, whether or not the variable is set, and whatever fallback it names: the value can change without a commit, so an unset or unreadable variable is reported the same way); a `runs-on` on the next lines (a list or a `group`) or naming no label; a job with no `runs-on`; a job that calls a reusable workflow (`uses:`); `permissions` from an expression or with no scope; an anchor, alias, tag or merge key; a flow mapping other than `{}`; a flow list with an anchor, alias or tag item, or a quoted item holding a comma; a quoted key or a complex key (`? `); a value continued on the next line (plain or quoted), or any line under a key that already has a value; an expression that does not close on its line; a tab in the indentation; a line break other than a newline (`\r`, U+0085, U+2028, U+2029); a second document; a block scalar with an indentation indicator (`|2`); a dash with nothing after it.
- `not-hosted-runner`: a `runs-on` label that is not one of GitHub's standard hosted labels (`HostedRunnerLabel`: `ubuntu-latest`, `ubuntu-24.04`, `ubuntu-22.04`, their `-arm` forms, `windows-latest`, `windows-2025`, `windows-2022`, `windows-11-arm`, `macos-latest`, `macos-26`, `macos-15`, `macos-14`), one finding per label, also each extra label of a list (`[ubuntu-latest, gpu]`). A larger runner's label is chosen by its owner and cannot be told from a self-hosted one, so it asks too.
- `writable-token`: `permissions: write-all`, any scope set to `write`, and a job with neither its own `permissions` nor the workflow's (its token then gets the repository's default, which may write). Read-only is `{}`, `read-all`, or scopes set to `read` or `none`.
- `secret`: an expression reading `secrets` other than `secrets.GITHUB_TOKEN` (the read-only token), `toJSON(secrets)` included, also inside a script; `secrets` in an `if:`; and a `secrets:` key (passing secrets on, `inherit` included).
- `trigger`: a trigger other than `push`, `pull_request`, `merge_group`, `workflow_dispatch`, `workflow_call` and `schedule` (`BranchTrigger`), such as `pull_request_target`, `workflow_run` or `issue_comment`, in the scalar, list or key form of `on`.

Block scalar text (`run: |`) is script text: a key in it is not read as one, but every expression in it is checked for secrets. The block ends as YAML ends it (the first line not deeper than its key, or less deep than its first line), and the line after it is read again. A `#` starts a comment only outside quotes and after a space or at the start of the line.

## The CI definition

`Plugin/GitHubForge/Domain/CiDefinition::changedAmong($workflows, $changedPaths)` returns the changed paths that are part of the CI definition, so a change to one is a CI change with no workflow file changed: every path under `.github/`; every Dockerfile (`Dockerfile`, `Dockerfile.<name>`, `<name>.Dockerfile`), because a workflow can build an image from one without naming it; and every path a workflow names (`scripts/test.sh` in `run: ./scripts/test.sh` or `/workspace/scripts/test.sh`, not in `scripts/test.sh.bak` or `old-scripts/test.sh`). A file is read as named only from the workflow's text, not from the scripts the named file runs in turn. When a workflow cannot be read, every changed path counts.

## The command

`php bin/console intakt:forge:workflow-risk <checkout> [--changed=<path>]...` (`UseCase/ScanWorkflows/ScanWorkflowsCommand`) is the door until part 2 calls the scan: it reads every `*.yml` and `*.yaml` entry directly in `<checkout>/.github/workflows/` (`Infrastructure/WorkflowFiles`, with Finder and Filesystem; an entry that cannot be read, such as a folder with that name, is passed on as unreadable), prints one line per finding (`<path>:<line> <kind>: <detail>`) and then `Risky: <n> findings in <m> workflows` or `Not risky: <m> workflows, ...`. With `--changed`, it prints `CI change: <path>` for each changed path of the CI definition, or `No CI change among <n> changed paths`. It exits with success either way, and with failure when `<checkout>` is not a directory. A checkout without the folder has no workflows and is not risky.

Tests: `tests/Plugin/GitHubForge/WorkflowRiskScanTest.php`, `CiDefinitionTest.php` and `ScanWorkflowsCommandTest.php`.
