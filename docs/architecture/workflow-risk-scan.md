# Workflow risk scan

Whether one GitHub Actions workflow file stays inside the envelope a change may push in without the owner: forge-hosted runners, a read-only token, no secrets, no trigger with the base repository's rights (plan task T55, part 1; design: [Merge](../design/05-architecture/08-merge.md), [Threat model](../design/05-architecture/14-threat-model.md#ci-log-excerpts)). `Plugin/GitHubForge/Domain/WorkflowFileScan::scan($text)` (`#[NoDiscard]`) answers a list of `WorkflowFinding` (a `WorkflowRisk`, the line and a detail), empty when the file stays inside. `php bin/console intakt:forge:workflow-risk <file>` (`UseCase/ScanWorkflow/ScanWorkflowCommand`) runs it on a file read with Symfony's `Filesystem::readFile()`: exit 0 without findings, 1 with any, 2 when the file cannot be read. The head's, main's and the merged workflows are read together in [The workflows of a change](#the-workflows-of-a-change).

## The CI definition

The files a workflow runs are part of the CI definition (T55, part 2): `Domain/CiDefinition::changedAmong($workflows, $changedPaths)` (`#[NoDiscard]`) answers the changed paths that are, given the workflows as `Domain/WorkflowFile` (a path and its text, `null` with a reason from `WorkflowFile::unread()` when it could not be read). It does not resolve paths and fails closed: a changed path is part of the CI definition when any workflow's text names any trailing part of it (in effect its file name, matched as a whole word in any case, non-ASCII letters included; a file name or workflow text that is not valid UTF-8 always counts). A path under `.github/`, any Dockerfile (`Dockerfile`, `Dockerfile.<x>`, `<x>.Dockerfile`, in any case), every path under the folder of a local action (`uses: ./tools/build`, also as `"uses":` or `uses :`, folder matched in any case), and every path when a workflow cannot be read or is in a form the strict line reader (below) does not read (`Domain/WorkflowReader` throws `WorkflowFormNotRead`, for example on an escaped key or value, an anchor or a tag, which could spell a path the text does not show), or when a `uses:` value is neither a plain `./` folder nor a remote action (`owner/repo@ref` with an owner that does not start with a dot, `docker://`), count too. Files a workflow runs without naming them (Makefile targets, Composer scripts) are not found; the owner approval of a push decides those. `php bin/console intakt:forge:ci-paths <path>... --workflow=<file>` (`UseCase/ListCiChanges/ListCiChangesCommand`) prints `ci <path>` for each such path, then `CI change: yes` or `no`, and exits with 0; a workflow file it cannot read is printed as `unreadable <file>: <reason>` and makes every path a CI change.

## The workflows of a change

A risky change to the CI definition waits for the owner before its push (T55, part 3), so every workflow the forge may run is scanned: the head's (run on the push), the merged ones (run on the merge) and main's (what a changed script runs under now). `Infrastructure/MirrorWorkflows::of($repository, $head)` reads them from a git directory (a relative path is made absolute against the current directory first, since git runs inside the repository) through `Core/Git/Contract/HardenedGit`, from objects only (no checkout): main is the branch the repository's `HEAD` names (`symbolic-ref`, as for protected paths, since a mirror's `HEAD` follows the remote's default branch), and main and the head are resolved once to commits (`rev-parse --verify --end-of-options <name>^{commit}`), the merge is `git merge-tree --write-tree`, and each side's `.yml` and `.yaml` files directly in `.github/workflows/` (any case) are listed with `ls-tree` and read with `cat-file blob`. It answers `Domain/CiWorkflows` (the three lists of `WorkflowFile` and the changed paths). It fails closed: a symbolic link or submodule there, a `.github` or `.github/workflows` entry that is not a folder (each is checked with its own `ls-tree`, since a listing through a link or submodule is empty and would read as no workflows), a failed `ls-tree` or `cat-file`, and the merged side when the merge conflicts become a `WorkflowFile::unread()` with the reason. The changed paths are every path where the head differs from main (what the push runs that main does not hold, even a change main merged and then reverted, and also files main changed after the head forked, which fails closed) together with every path where the merged tree differs from main (what the change brings to main), each path once; with a conflict only the first part is there, and the unread merged side makes each of them part of the CI definition. A `HEAD` that names no branch, a name that is no commit, a failed `diff-tree` and a merge git does not try (exit other than 0 or 1, such as unrelated histories) throw `Domain/CommitNotRead`.

`Domain/CiScan::of($workflows)` (`#[NoDiscard]`) runs `WorkflowFileScan` on each file of each `Domain/WorkflowSide` (`head`, `main`, `merged`) and `CiDefinition::changedAmong()` over all three, and answers `Domain/CiScanResult`: the findings as `Domain/CiFinding` (side, path, finding; an unread file is one `unreadable` finding at line 0 with its reason) and the CI paths. `isRisky()` is true with any finding, `isCiChange()` with any CI path, and `holdsThePush()` (`#[NoDiscard]`) with both, since a change outside the CI definition runs nothing new on the runner. `php bin/console intakt:forge:ci-scan <repository> <head>` (`UseCase/ScanCiChange/ScanCiChangeCommand`) prints each finding as `<side> <path> line <n>: <risk>: <detail>` and each CI path as `ci <path>` (control characters escaped, so a file name cannot forge a line), then `risky:`, `CI change:` and `push waits for the owner:` with `yes` or `no`; it exits with 1 when the push waits, 0 otherwise and 2 on `CommitNotRead` or `RepositoryAttributesRefused`. [Holding the push](#holding-the-push) acts on `holdsThePush()`.

## Holding the push

A build whose `holdsThePush()` is true stays local until the owner approves exactly its head (T55, issue #1621; design: [Merge](../design/05-architecture/08-merge.md)). `UseCase/ApprovePush/PushGate::decide($repository, $head, $issue)` (the issue a `Domain/TaskIssue`: project and number) answers a `PushOutcome` (a `PushDecision`, the commit and the `CiScanResult`):

1. `Infrastructure/MirrorChange::of()` resolves the head once to a commit (`rev-parse --verify`) and reads the change through `HardenedGit`: the single merge base of main (the branch `HEAD` names) and the head (`merge-base --all`; none or several throw `CommitNotRead`), then `diff-tree -r -p --text --no-renames --no-color --no-ext-diff --no-textconv --full-index --ignore-submodules=none` from it to the head, so git's guess never replaces a file by "Binary files differ". `Plugin/Forge/Contract/BinaryFiles::withImagesNamed()` then names a plain image the way the local git forge names a binary file ([Forge contract](forge-contract.md), step 2): its header up to the `index` line, which carries both full blob ids, then `Binary file, not shown: <size> at the base, <size> at the head`. A plain image is a file whose every mode in the header (`new file mode`, `deleted file mode`, `old mode`, `new mode`, the `index` line's) is `100644`, whose name ends in `.png`, `.jpg`, `.jpeg` or `.gif` (any case; also when git prints the path quoted, as it does for a path with a byte outside printable ASCII such as `café.png`), and whose blobs (`cat-file blob`; a failed read throws `CommitNotRead`) each start with that type's signature, at least one holding a NUL byte. The signature check is weak: a GIF only has to start with the four bytes `GIF8`, so a script that starts with `GIF8=1; echo ran` and holds a NUL byte is named as an image (the threat model accepts that kind of polyglot). Every other file keeps the bytes git printed, unescaped, so a script with a NUL byte, an executable image or a file named like an image that is none stays for `PushRequest` to refuse. Builder's choice (issue #2033): an image in a push request is shown by its name, sizes and blob ids instead of its bytes, because a comment cannot hold bytes that are not UTF-8 text, and the owner approves the full commit id, whose tree pins those exact blobs; only images, because any other binary file could be a script a workflow runs that the owner would approve unseen (the remaining risk is in the [Threat model](../design/05-architecture/14-threat-model.md#residual-risk)). `MirrorWorkflows::of()` reads that same commit, so a branch moved meanwhile cannot put another commit under the approval.
2. Without `holdsThePush()` the decision is `Free` and GitHub is not asked: `GitHubIssueComments` is a `#[Lazy]` argument, so this path needs no GitHub settings.
3. Otherwise, under a Symfony lock `intakt.push-request.<length of the project name>:<project>.<issue>.<commit>` (`GitHubForgeServices::PUSH_REQUEST_LOCK_PREFIX`; tried without waiting, a busy lock throws `ForgeWriteFailed`), `Infrastructure/GitHubIssueComments::of()` reads every comment of the task's issue (100 per page, at most 30 pages, more fails the read) as `Domain/IssueComment` (login, a person by GitHub's `User` type with no `performed_via_github_app`, since an App acting with a person's token keeps that person's login and type, edited when `updated_at` differs from `created_at`, posted through this App by `performed_via_github_app.id`, text). Before the read, `Domain/PushRequest::for()` builds the request (the approve line, that the push approval does not approve the merge, the findings and CI paths and the complete diff, each in a fence one backtick longer than any run inside) and `SecretScan` checks it, so a change the issue cannot show (`ChangeNotShown`) stays held even when an approve for it stands. With no comment of this App, never edited, whose text equals the request just built (it ends in `PushRequest::marker()`, `<!-- intakt-push-request: <commit> -->`; a marker in another head's diff, a request whose text was replaced or edited, or one built from other findings does not count), `GitHubIssueComments::post()` posts the request once (never retried) and reads the comment GitHub answers with: unless it carries this App's `performed_via_github_app.id`, an `updated_at` equal to its `created_at` and exactly the posted text, the post throws `ForgeWriteFailed` (nothing decided), since no later run could find that comment as the request. Otherwise `Asked`. Otherwise `Domain/PushApproval::isGivenIn()`, over the comments listed after the first such request only, is `Approved` when a comment by a person whose login equals `GITHUB_OWNER_LOGIN` (any case; empty means none counts), never edited, holds exactly `approve <full commit id>` (trimmed, any case); else `StillAsked`.
4. `PushRequest` throws `Domain/ChangeNotShown` when the body exceeds `PushRequest::MAX_CHARACTERS` (65536, GitHub's limit for a comment), or when the diff is still not UTF-8 or holds a NUL byte once images are named (a text file with a byte that is not UTF-8, a binary file that is no plain image, or a file without an `index` line); `PushGate` throws it when the secret scan finds a credential. Nothing is posted: the change goes back to be split.

`php bin/console intakt:forge:push-approval <repository> <head> --project=P --issue=N` (`UseCase/ApprovePush/PushApprovalCommand`) prints the findings and CI paths as `intakt:forge:ci-scan` does and one `push:` line, and exits with 0 for `Free` and `Approved`, 1 for `Asked`, `StillAsked` and `ChangeNotShown`, and 2 on `CommitNotRead`, `RepositoryAttributesRefused`, `ForgeReadFailed`, `ForgeWriteFailed` and `ForgeRateLimited`, so a failed read never lets the push go. No build calls it yet: the push itself is plan task T53.

## A strict line reader

`Domain/WorkflowReader` (with `WorkflowInlineValue` for keys and one-line values and `WorkflowBlockValue` for block scalars) reads the text line by line into `WorkflowMapping`, `WorkflowSequence` and `WorkflowScalar` nodes (each with its line), and throws `WorkflowFormNotRead` (line and reason) for any form outside the subset it knows; the scan turns that into one `unreadable` finding. A YAML library is not used on purpose: it would accept forms (anchors and aliases, merge keys, tags, multi-line plain and quoted values, escapes) that let a runner, a permission or a secret look different to the scan than to GitHub, so the reader accepts only:

- block mappings with plain or simply quoted keys (`[A-Za-z0-9_][A-Za-z0-9_./-]*`), each key once per mapping, and block sequences, also a sequence under a key at the key's own indentation (`on:` then `- pull_request_target` keeps the items under `on`);
- one-line plain, single-quoted and double-quoted values (no backslash in a double-quoted one), and one-line flow values (`[a, b]`, `{a: b}`) whose items are plain or quoted scalars without brackets, braces or `#`;
- block scalars with the headers `|`, `>` and a chomping sign (`|-`, `>+`), whose extent is every following line indented at least as deep as the first text line, blank lines included. An indentation number, leading blank lines deeper than the text, or a later line deeper than the key but less deep than the first text line make the extent uncertain, and the file `unreadable`;
- comments, blank lines, a leading byte order mark and one leading `---`.

Everything else is `unreadable`: a tab in the indentation, a value that goes on over the next line, a line that belongs to no key or item above it, a value that starts with `&`, `*`, `!`, `@`, `` ` ``, `%`, `|`/`>` with text after the header, a nested key inside a value (`a: b: c`), text that is not UTF-8, and control characters or the YAML 1.1 line breaks (U+0085, U+2028, U+2029), since another reader would split those lines differently.

## What the scan reports

| Kind | Rule |
|---|---|
| `trigger` | each event under `on` (a name, a list or a mapping's keys) that is not a `Domain/ContainedTrigger`: `push`, `pull_request`, `workflow_dispatch`, `schedule`, `merge_group` |
| `runner` | each `runs-on` label that is not a `Domain/HostedRunnerLabel` (GitHub's standard hosted labels), looked up as parsed, before any trimming, so a label from a `\|` or `>` block (with its line breaks) is one too, and a block scalar whose parsed text exactly matches a hosted label (no trailing line break) produces no runner finding; the detail shows the label trimmed, with a line break left inside it written as `\n`, so the finding stays on one line; a `runs-on` mapping (`group`, `labels`) |
| `permissions` | a scope set to `write` or `write-all` (`Domain/TokenPermissions`), in the workflow's or a job's `permissions`; a job with no `permissions` of its own while the workflow has none, since the repository default may write |
| `secret` | every match of `secrets` as a word in any key or value, in any case, except `secrets.GITHUB_TOKEN` (`Domain/SecretReferences`); a block scalar is checked over its whole text, so `if: \|` or `run: >-` with `secrets.KEY` in a later line is a finding at the key's line; `secrets: inherit` is one too |
| `unreadable` | a form the reader refuses (above); a `runs-on` label holding `${{` (a variable, a matrix value or any expression), and each value holding `${{` anywhere in a `runs-on` mapping (its `group` or `labels`, as a name or a list), next to that mapping's `runner` finding: the scan never reads a variable, so its value is a failed read even while the variable is unset; no `on` or no `jobs` mapping; a key the scan reads by name (`on`, `jobs` and `permissions` at the top, `permissions`, `runs-on`, `uses` and `secrets` in a job) that matches only when case is ignored (`WorkflowMapping::entriesInAnotherCase()`), each spelling at its own line, with a detail naming the key and the expected spelling, also next to an exact spelling of the same key: the scan fails closed instead of settling how GitHub compares key case, and does not add the "no `on`", "no `jobs`" or "no `runs-on`" finding for it; a job that is not a mapping, has no `runs-on`, or calls another workflow (`uses:`); an empty or non-scalar trigger; an empty, whitespace-only or non-scalar runner label; a permission level other than `read`, `none` or `write`, or permissions that are neither `read-all`, `write-all` nor a mapping |

Findings are sorted by line. The `secret` rule is a word match on purpose: a false finding only asks the owner, while a reference the scan missed would push a secret-reading workflow unasked.

## Limits

- `intakt:forge:ci-scan` and `intakt:forge:push-approval` take a git directory, not a project name; no push calls them yet (T53).
- The owner's send-back (`changes <sha>`), an approval given as a forge review, and the owner-wait cap are not read here (T64).
- Only the files directly in `.github/workflows/` are read; a workflow another one calls (`uses:`) is not followed, and the calling job is `unreadable`.
- The hosted label list is fixed in code; a new GitHub label counts as `runner` until it is added.
- The scan cannot tell a self-hosted runner registered with a hosted label from GitHub's own runner.
- The CI definition reads the text as written: files a workflow runs without naming them (Makefile targets, Composer scripts) and shell-level spellings the text does not show (a backslash-newline continuation inside a `|` block, shell quoting inside a name) are not found; the owner approval of a push decides them.
