# Task sizing

Plan task T48, part 1 (#4062): the readiness check and the size estimate of one new task; part 2 (#4063): the split of an oversize task into two to four parts, once. Closing the umbrella when its parts are closed is part 3 and is not built yet.

## In short

`intakt:build:size` asks a model once, with no tools, whether a trusted task is ready and how big it is. Plain code checks the typed answer. A task that is not ready is parked with one comment. A ready task of size `split` is split: plain code checks the two to four part lines, records the plan in the ledger, files each part once with a hidden marker, the original's labels and `Waits for` lines for the parts it builds on, and leaves the original open as their umbrella. A run that stopped finishes from the plan and finds a part whose create answer was lost by its marker. A task is split once, and a part is never split again.

## The call

`intakt:build:size <project> <issue>` runs `SizeTask`, in the Build module. It takes the `LockFactory` lock `SizingRecords::keyOf(project, task)` (a length-prefixed hash of project and number) without waiting and with no TTL; a run that finds it held fails with "another sizing of it is running" and makes no call. Under the lock it reads the task and first looks for a split plan of it (see [The split](#the-split)): a task with one is finished from it and never sized again. Otherwise it looks for the latest verdict (a `parked` one on the same text only has its comment ensured). Otherwise it asks `SizingVendor::size()` once; when the answer says the task is not ready it parks it, records the answer and comments; when it says ready it removes an earlier readiness question and records the answer, or, for size `split`, splits the task; an invalid answer is only recorded.

`EligibleTasks` reads the open issue through `IssueReads::readOpen()` and applies intake's rule before any call: the issue carries the project's eligibility label (`EligibilityLabels`) and not the `idea` label (`WorkLabels::IDEA`), its author has write access (`SteeringAccounts`), its history (`IssueHistories`, as of the read's update time) holds the same body, the same set of labels and a last editor with write access, and the label was applied by an account with write access. The label set is compared because the history lists every application of a label, also of one removed since. A refused or unreadable issue fails the command with the reason and spends no tokens. The labels the issue holds go into `SizingRequest::$labels` for a split's parts and never into the prompt.

`SizingVendor` (`Plugin/Vendor/Contract/`) is its own interface, so the other implementations of `Vendor` need no sizing stub. `SymfonyAiSizingVendor` implements it: it resolves the standard tier for `SizingRequest::$project`, reserves a usage row that names the task, runs `SizingAgent` on a `TierRoutedPlatform`, then settles the row, or leaves it unsettled and rethrows the failure typed (`TypedProviderFailure`), as the judge does.

`SizingAgent` calls an agent with no tools and `PlatformSubscriber::RESPONSE_FORMAT => SizingVerdict::class`. `SizingPrompt` builds the messages only through `PromptAssembly`; the title and the body of the task are fenced as untrusted (`UntrustedSource::Task`). The prompt asks for the size the task earns by itself, never a decision to split, and for size `split` the parts in the split line form of [Choosing work](../design/05-architecture/03-choosing-work.md) (step 3). `SplitTask` splits every ready task of size `split`; a lower split boundary for a small pool is not built.

## The verdict

`SizingVerdict` holds `ready`, `missing` (a list of `ReadinessGap`: `observable_result`, `acceptance_condition`, `single_outcome`), `size` (a `SizeTier`: `small`, `medium`, `large`, `split`), `estimated_lines`, `reason` and `parts` (a list of strings, each one part in the split line form). The Validator refuses a negative line count, an empty or overlong reason, more than four parts and an empty or overlong part; plain code (`agreesWithItself()`) refuses a verdict that is not ready with nothing missing, a ready one that names a gap, a repeated gap, size `split` without parts and another size with parts. `SizingAgent` also checks the answer's JSON text against the constructor's parameters, because the mapping drops a field it does not know, keeps the last of a field written twice and takes an object for the list: an extra or a missing field, a field written twice (the field names in the text are counted, nested ones too), and a `missing` or `parts` that is not a JSON list are no verdict. Last, it reads the parts with `SplitLines::partsIn()` (`Domain/`): a split that check refuses is no verdict either.

`SplitLines::partsIn()` takes two to four lines. Each line holds the markers ` | done-when: `, ` | verify: `, ` | files: ` and ` | depends on: ` exactly once and in that order, so a field runs to the next marker and a ` | ` inside a field (a `verify` of `php app.php | wc -l`) stays in it; no field is empty. `depends on` is `none` or `part <n>` references separated by `, `, each naming an earlier part once. No part may start a chain longer than two (part 3 on part 2 on part 1 is refused, part 3 on parts 1 and 2 passes). A line with a line break (`\r`, `\n`, U+2028, U+2029), a NUL byte, bytes that are not UTF-8 or `<!--` is refused, because model text in a filed part must not start a `Waits for` line, open an external block or forge a part marker. A title longer than 256 characters (GitHub's limit) is refused before the plan is recorded, so no plan holds a part GitHub cannot file.

An answer that is not JSON, that the mapping or the Validator refuses, or that contradicts itself is no verdict: `Sizer::size()` returns `null`. A failed call (a rate limit, an unreachable endpoint) is not an answer and stays a typed provider error.

## What plain code does with it

| Verdict | Task | Recorded after |
| --- | --- | --- |
| ready | the readiness question of the latest verdict, if that one parked the task, is removed through `ParkedTasks::clear()` | `task_sized`, outcome `ready`, size and estimated lines |
| not ready | parked with one question through `ParkedTasks`, then one issue comment through `TaskComments::postOnce()` | `task_sized`, outcome `parked`, the missing items (after the park, before the comment) |
| ready, size `split` | an earlier readiness question is removed, then the task is split (see [The split](#the-split)); a part of an earlier split is kept whole instead | `task_split_planned` before any part, `task_split` last; for a kept part `task_sized`, outcome `ready`, size `split` |
| none (invalid) | not parked, not split, no comment, an earlier question stays | `task_sized`, outcome `invalid` |

The question and the comment are worded by `BuildQuestion::forMissingReadiness()` from the closed list of gaps, never from the model's text; the comment is `asComment()`: the question and its choices. The parking is the one that a builder's question and a bug task missing a part use (see [Build task](build-task.md#the-parked-task-record)).

A ready verdict clears the question as the run that parked it (the `run` of the latest `parked` line), so a question a build run stored later stays. A question that cannot be removed fails the command and records no `task_sized`.

## One comment per text

`TaskComments::postOnce()` (`Plugin/GitHubForge/Contract/`) takes a `KeyedComment` (the text and a key); `SizeTask` passes `sizing-` and the `text` hash of the record as the key. `GitHubTaskComments` first reads every comment of the issue through `GitHubIssueComments::of()`. When a comment posted through this App (`IssueComment::$byThisApp`, which GitHub alone sets) holds the line `<!-- intakt:once <key> -->`, nothing is posted. Otherwise it posts the comment with that line appended through `GitHubIssueComments::post()`. A read that fails posts nothing and fails the command. A key with other characters than lowercase letters, digits and hyphens is refused before any request.

The read comes first because GitHub can store a comment and still answer the post as failed (a 502, or an answer the forge code cannot confirm). The `parked` verdict is already on record by then, so the retry on the same text makes no model call: it words the comment again from the recorded missing items, calls `postOnce()` with the same key, finds the stored comment by its marker and posts nothing, or posts the comment when the failed run did not store it. It records nothing new and ends with `already_sized`; a failed read or post fails it as before. The issue holds one comment, and the parked question and the comment name the first verdict's items. The match is on the marker and not on the wording, so an edited task that still lacks the same item gets a comment of its own.

## The record

`task_sized` has the lock's key as its subject. For a `parked` verdict it is appended right after the park and before the comment, so `parked` means the task is parked, and the comment is ensured on every run on the same text. For `ready` and `invalid` it is appended last, so `ready` means the earlier readiness question is gone. A task that is split gets no `task_sized` line: its `task_split_planned` line holds the verdict's size, estimated lines, text and run. A failed park fails the command and records no `task_sized`; a failed comment fails the command after the `parked` record. The payload holds the project, the task number as text, the outcome, the missing items, the size, the estimated lines, `text` (a hash of the title and body) and `run` (the id the sizing parked the task under). It never holds the title, the body or the model's reason, because they are untrusted text.

## One verdict per text

Before the call, `SizingRecords::latestVerdictOf()` reads the `task_sized` lines of that subject and keeps the last one with outcome `ready` or `parked` (`RecordedSizing`; a `parked` line whose missing items are not all known gaps does not count). When its `text` hash is the task's, the run ends with outcome `already_sized` and no call; a `parked` one first ensures its comment (see [One comment per text](#one-comment-per-text)). Only the latest verdict counts: a task whose text was sized ready, edited into a text that was parked and then restored is sized again, so the restored text releases the parked question. An `invalid` line does not count, and an edited title or body is sized again. One `ready` line of size `split` on the same text is the exception: it was recorded before the split existed (#4062) and has no part lines, so a task with no plan that is not a part is sized once more and split from the new verdict (`RecordedSizing::awaitsItsSplit()`); after that its plan ends every run.

## The split

`SplitTask` runs under the sizing lock, in this order:

1. **Plan.** It appends `task_split_planned` (subject: the sizing key) and reads it back. The payload holds the project, the task number as text, the size, the estimated lines, `text`, `run`, `parts` (the part lines as the model wrote them) and `labels` (the original's labels as read); never the title, the body or the reason. No part exists before this record.
2. **Parts.** In the plan's order, each part goes through `TaskParts::fileOnce()` (`Plugin/GitHubForge/Contract/`) as a `PartIssue`: the part's title; a body `Part <n> of <m> of #<task>, split by sizing.` with its done-when, verify and files lines and one `Waits for #<number>` line per part it depends on; the marker `<!-- intakt:part <sizing key> <n> -->`; the original's labels; and the plan's moment.
3. **Umbrella.** The original stays open. `TaskComments::postOnce()` posts `This task was split into #a, #b. It stays open as their umbrella.` under the key `split-<sizing key>`.
4. **Record.** It appends `task_split` with the project, the task, the run and the part numbers in order. The command prints `outcome split`.

`GitHubTaskParts` files each part once by its marker, as [Filing split parts](forge-contract.md#filing-split-parts) describes. A failed read creates nothing.

**Resume.** A run that finds a `task_split_planned` line skips the model: with a `task_split` line it ends with `already_sized`, without one it repeats steps 2 to 4. The resume starts like any sizing run, so the original must still be open, carry the eligibility label and pass the steering check. A part whose create GitHub stored but answered as failed is then found by its marker, and the comment by its key, so each part exists once and later parts wait for the first part's real number. `SplitPlan::of()` decodes the plan with JSON objects kept apart from lists. A plan line whose project or task is not the task being sized, whose parts are not a JSON list or no longer pass `SplitLines`, or whose labels are not a JSON list of texts fails the command (`planUnreadable`) and splits nothing. A failed part filing or umbrella comment (steps 2 and 3) fails the command with `notSplit`; a refused append of `task_split_planned` or `task_split` fails it with `notRecorded`.

**Once.** The plan is read whatever the task's text, so an edited original is never sized or split again. A task is a part (`SplitTask::isPart()`) when its body holds `<!-- intakt:part `, when the forge kept its number for a part of the same project and the project's current repository (`TaskParts::isFiledPart()`, read from the `part_issue_created` lines, so from the moment a part is filed, before the split is finished), or when a `task_split` line of the same project lists its number. So an edit that removes the marker from a filed part does not make it a split candidate, also while its split is unfinished, and the same number in another project, or in another repository after the project was remapped, is not a part. A `split` verdict on a part keeps it whole and records `task_sized` with outcome `ready` and size `split`. One limit stays: whenever a part's number was not recorded (its create answer was lost, or the ledger refused the `part_issue_created` line with the number), the marker is its only identifier until a later run of the split finds it by that marker and keeps its number. A trusted author who copies the marker into a task only keeps that task whole.

## Tokens

The `started` row of the call carries the project and the task number (`UsageStarted::$task`), so a task's sizing cost is read from the ledger by its number. The call is settled when it answered, valid or not, and left unsettled when it failed.
