## GitHub App identity

`Plugin/GitHubForge` (plan task T37, part 1) is Intakt's identity on GitHub. `Infrastructure\AppJwt` signs an RS256 JWT with the App's private key (`openssl_sign`; a key that cannot be read or is not RSA, such as an elliptic-curve key, throws `InstallationTokenNotMinted` before any request; `iss` is the App id with surrounding whitespace trimmed, `iat` is 60 seconds before now and `exp` 540 seconds after, from `ClockInterface`). `InstallationTokenMinter::mint($installationId)` posts it as a bearer token to `/app/installations/{id}/access_tokens` through `HttpClientInterface` and returns an `InstallationToken` (value and UTC expiry; `#[NoDiscard]`). `InstallationTokens::current()` (configured with the installation id) is the one door for a forge call: it returns the cached token while it expires more than 60 seconds from now and mints a new one otherwise; it implements `ResetInterface`, so a worker drops it between messages. Anything but a 201 with a non-empty `token` and a parseable `expires_at`, a transport error, and a key that cannot sign throw `InstallationTokenNotMinted`; so does a freshly minted token that has expired or expires within 60 seconds. An `expires_at` that PHP parses only with a warning (a day that does not exist, such as November 31, which PHP would roll over to December 1) counts as unparseable, because a credential must not be cached on a guessed expiry. There is no other credential to fall back to, and a failed mint caches nothing. The key, the JWT and GitHub's answer are `#[SensitiveParameter]` (`AppJwt`'s constructor, the minter's exchange and its reading of the answer, which holds the minted token), so they never appear among a trace's arguments; messages hold the status or the exception class only, and log records the status or the exception with its message and trace, redacted like every record (the logged trace names the file, line, class and function of each frame and never writes an argument value, see the Logging convention). A transport error is not chained as the previous exception, because its trace carries the request options with the JWT. The three settings are the environment variables `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID` and `GITHUB_APP_PRIVATE_KEY`, wired in `config/services.yaml`. The tests (`tests/Plugin/GitHubForge/`) replay recorded GitHub answers with `MockHttpClient` and generate their RSA key at run time. `Infrastructure\InstallationReader::read()` (part 2; `#[NoDiscard]`) reads the installation back: `GET /app/installations/{id}` with the App JWT for the permissions, and `GET /installation/repositories` with the installation token, page by page (100 a page) until exactly `total_count` names are read. Both go through `Infrastructure\GitHubCalls` over `github.client`: the listing as an installation call, so it waits out the installation's rate-limit pause (see **Rate limits** below), the JWT read as an App call, which the pause does not hold. An empty page before that, more names than `total_count`, a `total_count` that changes between pages and a repository listed twice are `InstallationNotReadBack`, because an incomplete listing could hide a repository beyond the configuration. `Infrastructure\InstallationReadBack::check()` (returns the `Installation`, `#[NoDiscard]`) compares it with `Domain\ExpectedInstallation` (built from `GITHUB_APP_PERMISSIONS`, `name:level,...`, and `GITHUB_APP_REPOSITORIES`, `owner/name,...`, both required and non-empty, a permission name at most once; invalid settings are an `InvalidArgumentException`) compares exactly and names every difference: wrong level, missing, or extra permission, missing or extra repository. A difference throws `InstallationDoesNotMatchConfiguration` and logs the differences; a failed token mint, a status other than 200, a transport error, an incomplete listing or an answer in the wrong shape throws `InstallationNotReadBack` and logs its message. Both are `ReportableFailure`s with messages that hold names, statuses, counts or exception classes only. `Infrastructure\CheckedInstallationTokens::current()` is the forge's only token door: before the first token of the process it runs the check, and a failed check hands out no token, so `GitHubForge` reaches GitHub only after the installation matched; a success is kept until the service is reset (it implements `ResetInterface`, so a worker checks again after each message), a failure is checked again on the next call. `UseCase\CheckInstallation\CheckInstallationCommand` (`intakt:forge:installation`) runs the same check on its own: it exits with failure and prints the message on either exception. No orchestrator start sequence exists yet, and no console listener runs the check, so console calls that use no forge never reach GitHub. Git reaches a project's remote in two places: the mirror update (`clone --mirror`, `fetch` and `ls-remote` through `NetworkGit`, see [Bare mirror](mirror.md)) and the signed push (`ls-remote` and `push` through `BranchGit`, see [Branch push](branch-push.md)); the build clone fetches from the local mirror over `file` only and needs no credential. `HardenedGit` itself allows no transport, so both name the two protocols they need (`GIT_ALLOW_PROTOCOL=file:https`) and set `GIT_TERMINAL_PROMPT=0`, so git never asks for a credential; the system's and the user's git configuration stay switched off (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`), so no credential helper named there runs. Both take the remote's address from their caller and name it on every call, and Intakt hands git no other credential: an `https` remote that asks for authentication has to carry the credential in that address. That is why neither `NetworkGitFailed` nor `BranchNotPushed` repeats the message of a Process exception, which holds the command line and the address in it. No door hands git an installation token yet: nothing builds such an address from `InstallationTokens::current()`, the mirror command takes its remote as an argument and the only caller of the push, `PushStep` (see [The push step](build-task.md#the-push-step)), is reached by `intakt:build:task` as its last step and takes the remote from the command's `--remote` option, so that door is a follow-up.

**Trust checks** (plan task T37, part 3). `Infrastructure\SteeringTrustCheck::check($repository, $login)` (`#[NoDiscard]`) answers a `Domain\SteeringTrust`: `writer`, `own-identity` and `maintainer` steer (`steers()`), `non-writer` and `foreign-bot` do not. A repository that is not `owner/name` or a login that is not a GitHub login (a letter or digit, then letters, digits and hyphens, at most 39 characters, optionally ending in `[bot]`) is `TrustNotChecked` before any request. A login ending in `[bot]` is a bot (`Infrastructure\SteeringIdentities`): it is a candidate `maintainer` when it is `<GITHUB_MAINTAINER_APP_SLUG>[bot]` (the setting may be empty, then no bot is the maintainer; a value that is not a slug is an `InvalidArgumentException`), a candidate `own-identity` when it is the `slug` GitHub answers to `GET /app` with the App JWT followed by `[bot]` (read from GitHub, never configured, so no setting can name a foreign bot as Intakt), and `foreign-bot` otherwise, whose permission is never asked; logins compare without case. A candidate steers only after the same permission read as a person's answers `admin` or `write` with `user.type` `Bot`, and is `non-writer` otherwise, so a failed token mint or a refused installation check fails it too. Any other login is asked on each check, never cached, through `GET /repos/{owner}/{repo}/collaborators/{login}/permission` with the token of `CheckedInstallationTokens::current()`, so the installation must have matched first: `permission` `admin` or `write` (GitHub reports the maintain role as `write`) is `writer`, `read` or `none` (the triage role reports as `read`) is `non-writer`, and an account whose `user.type` is `Bot` is `foreign-bot` whatever its permission. An answer about another login, a level outside those four, a missing field, any status but 200 (a 404 too, so an unknown account or repository fails instead of reading as a decision), a transport error, a key that cannot sign, a failed token mint and a refused installation check are `TrustNotChecked` (a `ReportableFailure`; its messages hold names, statuses or exception classes only, and a transport exception is not chained); no other credential is tried. `Infrastructure\TrustAnswers` makes the reads over `github.client` through `GitHubCalls`; a rate-limit answer to the permission read is `ForgeRateLimited` instead (see **Rate limits** below). `UseCase\CheckTrust\CheckTrustCommand` (`intakt:forge:trust <owner/name> <login>`) prints `<login> on <repository>: <decision>, steers` (or `does not steer`) and exits with failure on `TrustNotChecked`. `Infrastructure\GitHubIssueHistories` reads who applied each label of an issue and in which order (see below), and `Infrastructure\ProjectSteeringAccounts` (`Contract\SteeringAccounts`) asks the check for a project's repository, and `Plugin/GitHubWorkSource/Infrastructure/CompleteListing` applies it to that history, but nothing runs that sync or reads comments yet, so no event uses the check, and decisions are not written to the ledger. Tests: `tests/Plugin/GitHubForge/SteeringTrustCheckTest.php`, `CheckTrustCommandTest.php` and `TrustOnTheContainerTest.php` (the command as the container wires it, over the recorded answers).

**Pull request author trust** (issue #1974, part 1 of #1828, decision 1). `Infrastructure\GitHubAuthorTrust` implements `Plugin/Forge/Contract/AuthorTrust::isAuthorTrusted(ChangeId)` ([Forge contract](forge-contract.md#pull-request-author-trust)). It parses the `ChangeId` with `PullRequestAddress`, reads `GET /repos/{owner}/{repo}/pulls/{n}` through `TrustAnswers::ofInstallation()` with the token of `CheckedInstallationTokens::current()`, takes the author's `user.login` and the `head.repo.full_name` from the same answer. A head whose repository is not the base repository (a fork, the author's own too, because the fork's owner can push under the author's name; a deleted fork has `head.repo` null) is untrusted with no permission lookup. Otherwise it asks `SteeringTrustCheck::check()` for that repository and login, on each call, never cached. The answer is `SteeringTrust::steers()`: `writer`, `own-identity` and `maintainer` are trusted, `non-writer` and `foreign-bot` are not. Any failure is untrusted, never trusted: an address that is no GitHub pull request (`ChangeNotFound`, before any request), a refused or unreachable read of the pull request or of the permission (a `404` too), an answer without the author's login or without a `head.repo` key, a failed token mint, a refused installation check, a read the installation's rate-limit pause refuses (`ForgeRateLimited`) and anything else thrown on the way. Each such failure logs one warning (`change` and the `exception`). It is the container's `AuthorTrust` outside the test environment, which the watcher's boot gate asks before it boots a head ([Boot step](boot-step.md#the-gate-decision)). Tests: `tests/Plugin/GitHubForge/GitHubAuthorTrustTest.php` (recorded pull requests and permissions in `RecordedTrust`) and `AuthorTrustOnTheContainerTest.php` (the service as the container wires it, through the test-only public alias `intakt.test.author_trust`).

**Reading a pull request** (plan task T18, part 1). `Infrastructure\GitHubForge` implements the `Forge` reads over the GitHub REST API. `config/packages/framework.yaml` declares the scoped client `github.client` (base URI `https://api.github.com`, the parameter `GitHubForgeServices::API_URL` set in `config/services.yaml` and given to the client in `config/packages/github_forge.php`, which the [connectivity check](outage.md) probes too; API version header, `retry_failed` with 3 retries on the listed `http_codes`, which are Symfony's defaults without 429, so Symfony wraps it in `RetryableHttpClient`: 423, 425, 502 and 503 answers are tried again for any method, 500, 504, 507, 510 and dropped connections (code 0) for idempotent methods, a 429 never); `Infrastructure\GitHubCalls` takes it with `#[Target('github.client')]`, and the forge sends every request through `GitHubCalls::asInstallation()`. Every request carries the token of `CheckedInstallationTokens::current()` as bearer, so the installation is read back and matched before the first request; an `InstallationTokenNotMinted` becomes `ForgeReadFailed`, and so do `InstallationNotReadBack` and `InstallationDoesNotMatchConfiguration`, with the difference in the message. The `ChangeId` is the pull request URL: `PullRequestAddress` parses it with `Uri\Rfc3986\Uri` (never `parse_url`) and accepts only `https://github.com/<owner>/<repo>/pull/<n>` without credentials or port, with an owner of letters, digits and hyphens and a repository that is not only dots, so the token cannot follow a crafted address to another host or out of `/repos/<owner>/<repo>` (`..`); anything else is `ChangeNotFound`, as is a 404 for the pull request. `change()` reads the pull request (head sha, base ref), takes the base as `merge_base_commit` of `compare/<base ref>...<head sha>` (the merge base, as `LocalGitForge` does) and the changed files from the `files` of that same comparison, so they belong to the head the base was taken for, then reads the diff of `compare/<base>...<head>` with `Accept: application/vnd.github.diff` (between two commits, so a head that moves meanwhile cannot mix states); `renamed` is a deletion of the old path plus an addition of the new one, `copied` an addition, `changed` a modification, an unknown status `ForgeReadFailed`. GitHub lists at most 300 files of a comparison, so a list of 300 or more files, or a comparison without `files`, fails the read with `ForgeReadFailed` instead of returning a list that may be cut off. `hasHeadMoved()` reads the pull request again and compares head shas. `headMoveSince()` is `unmoved` for the same sha; otherwise `compare/<earlier>...<head>`: status `ahead` is `commits` with the compared file paths (both paths of a rename), anything else (diverged, behind, or a 404 for an earlier head GitHub no longer knows) is `rewritten`, and so is an `ahead` comparison of 300 or more files or without `files`, because a list that may be incomplete cannot prove that only documentation changed. It never answers `clean-merge-of-base`, because the API cannot prove that a merge added nothing of its own, so a merge of the base is reviewed again as `commits`. `fileAtHead()` reads `contents/<path>?ref=<head sha>` with the raw media type, each path segment URL-encoded; a 404 is `FileNotFoundAtHead`, and the answer goes through `FileContent::ofBytes()`, so one with a NUL byte anywhere is named by its size as the local git forge names it. Any other status outside 2xx, a transport error and an answer that is not the expected JSON shape are `ForgeReadFailed`; the message names the status or exception class, never the token, and a transport exception is not chained, because its trace holds the request options with the token. **Rate limits** (plan task T18, decision D1). Every call with the installation token goes through `Infrastructure\GitHubCalls::asInstallation()` (REST: the forge's reads and its review post, the trust check's permission read, the author trust's pull request read and `GitHubChangeAuthorship`'s pull request read `GET /repos/{owner}/{repo}/pulls/{n}` (all three `TrustAnswers::ofInstallation()`) and the read-back's repository listing) or `GitHubCalls::query()` (a `POST /graphql`: the issue history read). Both ask `Infrastructure\RateLimitReadings` before each request and after each answer, for the installation of `InstallationTokens::$installationId`. Calls with the App JWT (`GitHubCalls::asApp()`: `GET /app`, `GET /app/installations/{id}`) spend the App's budget, so the pause does not hold them and their answers are not recorded. `RateLimitReadings` sits on the cache pool `intakt.github.rate_limits` (`cache.app`, so every worker and the scheduler share it; an array adapter in tests) and keeps its entries under a hash of the installation id and GitHub's rate-limit pool (a `core` pause the version before the per-pool keys stored under the installation id alone is honored, and never shortened, until it expires, so an upgrade during a pause does not resume REST calls before GitHub's reset): the latest `Domain\RateLimitReading` of the `core` pool (`X-RateLimit-Remaining`, `X-RateLimit-Limit` and `X-RateLimit-Reset` of any answer that carries all three; one whose reset has passed counts as none) and a pause marker per pool. The pool of an answer is its `X-RateLimit-Resource` header, else the pool of its request (`core` for `asInstallation()`, `graphql` for `query()`); a `graphql` answer records no reading, so it never replaces the one `BudgetReserve` and `GitHubForgeBudgets` read, and its pause holds only `query()`, while a pause of `core` holds only `asInstallation()`. An answer of 403 or 429 with a `Retry-After` header, or with `X-RateLimit-Remaining: 0`, is a rate limit, and so is a `graphql` answer of any status with `X-RateLimit-Remaining: 0`, because GitHub answers an exhausted GraphQL pool with 200 and a `RATE_LIMITED` error (a query that spent the last point is read again after the reset): the reset is `Retry-After` (seconds from now, or an HTTP date), else `X-RateLimit-Reset`, taken whole; one minute from now when none is readable or the named one is not in the future (a skewed clock). The marker is written under a Symfony Lock (`LockFactory` over the file store, waited for) and keeps the later of the stored and the new reset, so an answer in flight cannot shorten a pause; `Plugin/Forge/Contract/ForgeRateLimited` (carrying that `resetsAt`, a `ReportableFailure`, not a `ForgeReadFailed`) is thrown. While the marker lies ahead of the clock (`ClockInterface`, not the cache expiry), an installation call throws `ForgeRateLimited` without any request. Any other 403 stays `ForgeReadFailed`, `ForgeWriteFailed`, `TrustNotChecked` or `InstallationNotReadBack`. Waiting on the exception is left to the callers (plan parts 3 and 4 of the same issue); the two console commands print it as a failure.

**Reserve for essential calls** (plan task T18, decision D2 of #668, part 2). `Infrastructure\BudgetReserve::admitListing()` keeps a share of the installation's hourly budget for essential calls: the share is the parameter `intakt.github.reserve_percent` (`GitHubForgeServices::RESERVE_PERCENT`), which `config/packages/ai.php` sets from the owner's `github.reserve_percent` in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names): it takes the `github` key off the root of that file, so the projects tree never sees it, and processes it with `Infrastructure\GitHubConfiguration` (Symfony Config: an integer from 0 to 100, 20 (`GitHubConfiguration::DEFAULT_RESERVE_PERCENT`) when the key or the section is absent, unknown keys refused), so any other value fails the container build with the key's path `intakt.github.reserve_percent`; `BudgetReserve` itself still refuses a value outside 0 to 100 with an `InvalidArgumentException` when the service is built. `RateLimitReading::isBelowShare()` compares `remaining * 100` with `limit * percent`, so 999 of 5,000 is below 20% and 1,000 is not. Without a reading, or at or above the share, a listing goes on. Below it, one listing per project per watcher tick (`Core/Watcher/Contract/WatchTick::INTERVAL`, one minute, the interval `WatcherSchedule` uses) goes on, because each project's tick lists once and a slot shared by the installation would leave every project but the first unlisted until the reset: the project's slot is kept in the pool `intakt.github.rate_limits` under `BudgetReserve::slotKey()`, a hash of the length-prefixed installation id and project name, written under a Symfony Lock tried without waiting; the slot holds when the project's next listing is due, one tick after the later of the last listing's due time and the moment it ran, and lives in the pool until that due time (up to a tick and a half, not a fixed tick, so an early listing's debt is not forgotten when its slot expires), so over time no more than one listing per tick goes on, a tick handled a few seconds late behind another project's on the serial consumer does not cost the next tick its listing, and an early one adds none; a held lock, a listing half a tick or more before its due time or a due time the pool does not save throws `ForgeRateLimited` with the reading's reset, before any request. `WatchPullRequestsHandler` catches that refusal, skips the listing and still looks at the project's due heads, so their CI reads go on. The forge's own pause (**Rate limits** above) throws the same `ForgeRateLimited` from the listing, so the tick looks at the due heads then too; a CI read that pause refuses is no head failure: `HeadBackOff` moves that head's read-again time to the reset, with no failure counted, no `head_failed` line and no install-wide report, so a pause of several ticks hands no head over; only when storing that read-again time fails is the head backed off alone as a failed head, and the tick goes on to the next one ([Forge contract](forge-contract.md), the Scheduler tick). Only `GitHubWatchReads::listOpen()` asks the reserve, after the project's repository is known and before its first page; every other installation call is essential and never asks: the CI reads of `ciStateOf()`, the single issue read of `GitHubIssueReads::readOpen()`, the pull request reads, the review post and the verdict publication of `GitHubForge`, the trust check's permission read, the author trust's pull request read, `GitHubChangeAuthorship`'s pull request read (`GET /repos/{owner}/{repo}/pulls/{n}`), the labels and events reads, label writes and restoration comment of `GitHubStatusLabels`, which the watcher's status pass makes on every tick ([Forge contract](forge-contract.md#the-status-pass-of-each-watcher-tick)), and the read-back's repository listing, which every installation call needs first. The watcher tick makes `GitHubChangeAuthorship`'s read once per open pull request that has no decisive record ([Pull requests handed to Intakt](handed-to-intakt.md)): a `change_opened` line with `opening`, or a `change_handed_to_intakt` or `change_not_handed_to_intakt` line. A definite answer is recorded either way, so each pull request's author is read at most once over its lifetime, also on an unchanged (304) listing. Its `GET /app`, asked only for a bot author, is an App call, which the pause does not hold. No wait or intake scan and no dashboard refresh reads the forge yet. The dashboard's forge budget (#677, decision D4) reads no forge either: `Infrastructure\GitHubForgeBudgets` implements `Plugin/Forge/Contract/ForgeBudgets` ([Forge contract](forge-contract.md), "Forge budget") for the one configured installation (`GITHUB_APP_INSTALLATION_ID`; none when it is empty), from `RateLimitReadings::latest()`: the calls used are the limit less the remaining calls (at least 0), and the reserve is in force when `BudgetReserve::isInForce()` says so, the same test `admitListing()` applies; without a reading of this hour (none yet, or its reset has passed) the installation is shown unread. Tests of it: `GitHubForgeBudgetsTest`. Tests: `BudgetReserveTest`, `RateLimitReadingTest`, `BudgetReserveSettingTest` (the default and an owner value, as the container is built), `GitHubConfigurationTest` (the bounds and the refused values), the reserve tests of `GitHubWatchReadsTest`, `WatchPullRequestsHandlerTest::testAPendingHeadIsReadAgainWhileTheForgeHoldsTheListingBack`, its forge pause tests (`testAForgePauseOverSeveralTicksCountsNoHeadFailureAndHandsTheHeadOverToNoOne`, `testAHeadWhoseCiReadAForgePauseRefusedIsReadAgainOnceThePauseHasEndedAndNotBefore`, `testAForgePauseOnTwoHeadsOfOneTickStartsNoFailureBackOff`, `testAHeadWhoseForgePauseCannotBeStoredIsBackedOffAloneWhileTheNextHeadOfTheTickStartsItsRound`, `testAHeadWhoseForgePauseAndBackOffCannotBeStoredStaysDueWhileTheNextHeadOfTheTickStartsItsRound`) and `GitHubForgeRateLimitTest::testItPostsAReviewWithTheHourlyBudgetBelowTheReserve`. The tests replay recorded answers (`tests/Plugin/GitHubForge/Fixtures/`) with `MockHttpClient`; the retry codes are read from `framework.yaml`, so a test proves a 429 is sent once and a dropped connection of a read is tried again (`GitHubForgeRateLimitTest`, `RateLimitReadingsTest`, and the pause tests in `SteeringTrustCheckTest` and `InstallationReadBackTest`).

**Posting a review** (plan task T18, part 2). `GitHubForge::postReview()` implements `ForgeWrites` through the same scoped client. It first takes the redacted body and runs `Infrastructure\SecretScan` over it: `gitleaks stdin --no-banner --ignore-gitleaks-allow --log-level error --exit-code 3` from Symfony Process in the project directory, the binary taken from `INTAKT_GITLEAKS` as for the secrets gates (the container binds `%env(default:intakt.gitleaks:INTAKT_GITLEAKS)%`, the parameter `PlatformServices::GITLEAKS` the hand-back's secret scan shares, so `gitleaks` from the path when it is unset or empty), with `GITLEAKS_CONFIG` and `GITLEAKS_CONFIG_TOML` removed from its environment, so gitleaks's built-in rules apply and an inline allow comment the job wrote into the text is ignored. Exit 3 is a hit (`ReviewTextHoldsSecret`, no request is sent), 0 is clean, and any other exit (127 when `gitleaks` is missing, 2 when it cannot reserve the memory it asks for at start under a tight memory cap, see [requirements](requirements.md)) or a process failure is `ForgeWriteFailed`. Then it asks `hasHeadMoved()`; when the pull request's head is no longer the `Change`'s head, it throws `RoundStale` and sends no write, and a `ForgeReadFailed` or `ChangeNotFound` of that read becomes a `ForgeWriteFailed` chained to it. Otherwise it posts one review to `pulls/<n>/reviews` with `event` `COMMENT`, `commit_id` the reviewed head (so a push between the check and the post cannot attach the review to a head it did not see) and the body followed by a blank line and the marker `<!-- intakt-review-token: <token> -->`, which GitHub does not render. A status outside 2xx, a transport error, an `InstallationTokenNotMinted` and a refused installation check are `ForgeWriteFailed`, named by status or exception class and with the transport exception not chained, as for reads. The post passes the request option `max_retries: 0`, which `RetryableHttpClient` reads per request, so it is sent once: its default strategy would retry a POST on 423, 425, 429, 502 and 503, and a 502 after GitHub stored the review would post it twice. The option needs the retrying client in front, as the container wires it; a client without it refuses the option, which ends as `ForgeWriteFailed`. The `project` argument was for the project mode guard, removed with the shadow mode (issue #1478); the GitHub forge does not read it. Asking the reviewer again once and parking it after a `ReviewTextHoldsSecret` belong to the round that calls `postReview()`, which does not exist yet. `GitHubForge::publishVerdict()` posts a reviewer-for-loop round's comment and commit status `intakt/review` through the same `post()`, under the lock `intakt.verdict.<round id>`, skipping the comment when `PostedComments` finds a comment of this App (`performed_via_github_app.id` equal to `GITHUB_APP_ID`) ending with the round's marker `<!-- intakt-verdict: <round id> -->` on the pull request already (see [Reviewer-for-loop mode](capability-tiers.md#reviewer-for-loop-mode)). An owner ask's parts follow the comment, each skipped the same way by its own marker `<!-- intakt-owner-ask: <round id> <digest> part <n> -->` (the digest is the SHA-256 of the whole ask) ([Pull requests handed to Intakt](handed-to-intakt.md#intakts-review-counts)). Without an App (`GITHUB_APP_ID` empty, as in the demo) it publishes nothing, makes no request and returns `false`, and logs one info record per process start, at a Messenger worker's start or at the first skipped publication, whichever comes first (`Infrastructure\GitHubAppSetting`, issue #2162); `Domain\ExpectedInstallation` is a lazy service, so the forge, and the `PublishVerdictHandler` that holds it, can be built while `GITHUB_APP_PERMISSIONS` and `GITHUB_APP_REPOSITORIES` are empty, and the two settings are parsed only when the installation check first runs (tests: `tests/Plugin/GitHubForge/GitHubForgeWithoutAppTest.php`, `tests/Plugin/GitHubForge/GitHubAppSettingTest.php`, and `tests/Application/DemoReviewLogTest.php`, which judges a demo round and drains its queue through the application's bus, worker events and logger, then reads every record the application logged in the test (the test run's `RecordingLogger`, which marks a record whose context holds an exception) and finds no failed message, no record at warning or above, no exception in a record's context, and exactly one info notice). Tests: `tests/Plugin/GitHubForge/GitHubForgeTest.php` (the stale case reads the change, moves the recorded head, then posts; a 502 to the post is not retried; a failed read before the post; redaction; a live payment key, a shape the redaction does not know, that trips the scan), `tests/Plugin/GitHubForge/SecretScanTest.php` (runs the real `gitleaks`) and `tests/Plugin/Forge/ReviewCommentTest.php`.

**Refused credentials** (decision 1 of #681, part 2). `Plugin/Forge/Contract/ForgeCredentialsRefused` is a cause, never thrown alone: a 401 to a read or a write is a `ForgeReadFailed` or `ForgeWriteFailed` with a `ForgeCredentialsRefused` as `previous`, and a 401 to the installation token exchange is an `InstallationTokenNotMinted` with the same cause. The token exchange failure is chained through the read-back (`InstallationNotReadBack`) and through `GitHubForge`'s read and write failures, so a caller finds the cause by walking `getPrevious()`. Callers keep catching the failures they caught before; any other status carries no such cause. `InstallationTokenNotMinted` and `GitHubForge` both compare the status with `Plugin/GitHubForge/Domain/RefusedCredentials::STATUS`, so their two checks cannot drift apart. The message is fixed text, and the HTTP client's exception, whose trace holds the token, is never chained. The watcher's `FailedHeads` walks the chain of a failed head for this cause and starts the install-wide failure back-off from it (task #996, see [`Core/Watcher/UseCase/WatchPullRequests`](forge-contract.md)).

**Trust before a pick** (issue #3308, part 1 of #2667). `GitHubWorkSource::nextWork()` asks `SteeringAccounts::steers()` again for the author and the last editor of the task it is about to return. A check that fails (`TrustNotChecked`, or a `ForgeReadFailed` or `ForgeRateLimited` of the check or of the history read that names the last editor) is never a "no": the work source logs it as a failed check and picks nothing, see [Work intake](work-intake.md).
