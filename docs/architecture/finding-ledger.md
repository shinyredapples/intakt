## Finding ledger

Plan task T10, parts 1 to 3 (design: [Reviews](../design/05-architecture/07-reviews.md)). `Core/Review/Domain/FindingLedger` is the ledger of the findings of one change, built from its stored `TrackedFinding`s (an empty one for a new change). `recordRound(round, findings)` matches a finding to a tracked one by its id, but only to ids issued before that round, so a finding that returns keeps its id, gains the round and is open again even if it was resolved; several reports of one existing id in a round count once (the first one is kept as the latest `Finding`). Any other finding gets a new ledger id (`F1`, `F2`, ... in order of first sight), also when two new findings of one round share an id or one names an id issued earlier in the same round. The first round may be any number; each later round must be above the latest one `recordRound` recorded in this ledger instance, and a round equal to or below it throws `RoundNotAfterLatest` before any of its findings is tracked, so the ledger stays unchanged. `resolve(ids)` closes the named findings and ignores unknown ids; `open()` lists the findings not closed. A `TrackedFinding` holds the id, the latest `Finding`, its rounds and a `FindingStatus` (`open` or `resolved`); `firstRound()` and `latestRound()` use `array_first()` and `array_last()`. Part 2 adds `recordVerdict(round, verdict)`, which closes the `resolved` ids and keeps the id only of a finding marked `repeat` whose id is tracked (any other finding gets a new id, also when its id matches) and returns the ledger ids the verdict's findings were tracked under, in the verdict's order (none for a failed review; #2933 records them per reviewer, see [Review rounds](review-rounds.md)), and `openForReviewers()`, which lists the open findings as `Finding`s under their ledger ids for `ReviewBrief::$open`. Several verdicts of one round are recorded one after the other under the same round number; the order of rounds reaching a stored ledger is kept by `recorded_round` (below), not by `RoundNotAfterLatest`. A `resolved` id of a finding that another verdict of the same round already reported again is ignored, so a finding one reviewer repeats stays open whichever verdict is recorded first. A failed review (`Verdict::isFailedReview()`: a verdict carrying a finding with id `invalid-output`, `incomplete-stream`, `unread-approval`, `no-tools`, `cut-approval` or `reviewer-stopped`) adds nothing, because it is the reviewer's fault, not the change's. Only Intakt's own failure verdicts and rounds stored before #2787 still reach the ledger with one of these ids: the reviewer agent refuses a reviewer's answer that names one as unreadable (`Verdict::claimedFailureIds()`, see [Review verdicts](review-verdicts.md)), so no new counted `changes` vote is recorded whose findings and resolutions the ledger drops. A `changes` verdict with such an id counts as `blocked` for a round judged with counted votes (`CountedVote::of()` checks `isFailedReview()` first); only a round judged before votes were counted falls back to the stored decision, while the ledger skips its findings and resolutions. `UseCase/RunReviewRound/StoredFindings` keeps the ledger of each change in `Domain/ChangeFindings` (table `change_findings`, key `project` and `change_ref`, the count of `rounds`, the tracked findings as JSON in `findings` and the number of the latest round recorded in `recorded_round`, written and read back with the `stored` serializer; migration `Version20261031150000`); the review round numbers its rounds there, takes the open findings it tells its reviewers from it when a round opens, and feeds it (see [Review rounds](review-rounds.md)). `tests/Core/Review/Domain/FindingLedgerTest.php` covers three stable rounds, closing, reopening, repeated reports in one round, refused rounds that are repeated or earlier, both orders of a repeat and a resolve in one round, the six failed reviews, a rebuilt ledger and unknown ids.

The goalpost rule (part 3) is `Domain/GoalpostRule`: from round two on a new P1 or P2 with neither `regression: true` nor a non-blank `requirement` becomes P3 (`Finding::withSeverity()`). `ReviewWithReviewerHandler` applies it to the reviewer's verdict, after `Verdict::asRecorded()` (a reviewer's `blocked` with findings becomes `changes`, see [Review verdicts](review-verdicts.md)), (`GoalpostRule::applyToVerdict()`, with the round number and the open findings the reviewer was told) before `ReviewerLeases::recordVerdict()` stores it, so `VerdictsOfRoundHandler` hands the panel the same severities the ledger records. `ReviewerAgent` applies the same rule to its answer first, with `ReviewBrief::$round` and `ReviewBrief::$open`, so the guards that refuse an approval see those severities too (see [Reviewer agent](reviewer-agent.md)); applying it twice changes nothing. There a `repeat` of an open id takes the open finding's severity, and a `repeat` of an id the reviewer was not told counts as new. `FindingLedger::recordVerdict()` also passes every finding it starts through the rule, and `TrackedFinding::seenAgain()` keeps the severity a finding was first stored with, so a repeat can neither raise a lowered finding nor lower a blocking one. Round one and P3 findings are never changed, and the rule never raises a severity. `regression` is a reviewer-set field of `Finding` (required in the verdict schema, default false in the class); a steered reviewer can set it or name a requirement, the same trade as before, so the rule limits drift but does not replace the checks that decide a merge. `tests/Core/Review/Domain/GoalpostRuleTest.php` covers the rule, `FindingLedgerTest.php` the ledger call and `FindingsAcrossRoundsTest.php` the stored verdict the panel reads.
