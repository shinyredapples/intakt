## Upstream reproductions

`php bin/console intakt:upstream:run [directory]` (module `Core/Upstream`, plan task T26) runs every subfolder of `upstream/` (or of `directory`, relative to the project or absolute) as its own process through Symfony Process (`ReproductionRunner`), 300 seconds at most. A reproduction checks the expected behavior, so a failing run means the bug is still there. The runner does not read the `## Upstream status` section that ends each `REPORT.md`: it holds the result at the pinned versions, the result on the upstream development branch, the upstream issues found, the pull requests and commits the duplicate check found (or "none found", with the date of the check), and the decision (see `upstream/README.md`). That duplicate check comes before a new folder, in the order `upstream/README.md` gives under "Before a new folder": the existing folders, upstream's open, merged and closed pull requests, the commits on upstream's development branch since the pinned version that touch the affected files together with the changelog or upgrade notes of the next release, then upstream's open and closed issues. A lead upstream has already fixed gets no new folder; the fixing pull request or commit and the first release that contains it are recorded in the report of the existing folder it belongs to, or in the report of the task that found the bug. The `reproductions` gate requires the pull requests and commits line in a report whose status is `ready to file` (see below). A subfolder with a `reproduce.php` file is a script reproduction: `php -d auto_prepend_file=vendor/autoload.php reproduce.php`, run from the subfolder; it passes only when it exits with 0 and the last line of its standard output is `REPRODUCTION PASSES` (builder's choice: the exit code alone cannot tell a fixed script from one that never checked anything, so the script must say that it checked). Any other subfolder is a PHPUnit run: `vendor/bin/phpunit --no-configuration` with `vendor/autoload.php` as bootstrap. Only a test that ran and asserted can show a fix, so that run also fails on an empty suite, a skipped or incomplete test and a test without assertions (`--fail-on-empty-test-suite`, `--fail-on-skipped`, `--fail-on-incomplete`, `--fail-on-risky`); a subfolder with neither a script nor a test is therefore reported as `still fails`. A run that reaches the timeout is stopped, reported as `still fails` with the output `Timed out after 300 seconds.`, and the next reproduction runs. When `directory` does not exist or cannot be read, or listing it fails (no search permission on it, or a `FilesystemIterator` error while opening or reading it; the folder path is read literally, never as a glob pattern), the command prints an error and exits with 2 without running anything, so a mistyped, unreadable or unsearchable folder never reads as a clean run. The command first prints the installed `symfony/ai-*` and `mcp/*` versions, then one line per reproduction (`passes` or `still fails`) and a summary. With `-v` the output of each failing run follows its line, written raw (`OutputInterface::OUTPUT_RAW`), so console style tags in it are printed as text; a fractional timeout is printed as given (`%g`). The exit code is 1 when any reproduction still fails, otherwise 0. `tests/Core/Upstream/RunReproductionsCommandTest.php` covers a passing and a failing PHPUnit sample, a run where every reproduction passes and exits with 0, failure output shown only with `-v` (a failing script), a missing folder, an unreadable and an unsearchable folder (both skipped for the superuser, whom permission bits do not bind), failure output with a style tag, a folder with neither script nor test, skipped, incomplete and assertion-free tests, and scripts that pass, exit with an error, omit the marker line, use the project autoloader or hang before a further script. The hanging script runs at a 0.5 second timeout, which also proves the fractional timeout message; scripts and PHPUnit runs share the timeout handling (`ReproductionRunner::outcome()`), so no PHPUnit run is made to hang. The gates keep skipping `upstream/` (`Scope::EXCLUDED_PREFIXES`), so a failing reproduction never fails `bin/check`.

A `symfony/ai` folder whose decision is `ready to file` also gets a `Fix pull request` line in `## Upstream status` (`fix pull request ready`, `filed as symfony/ai#<number>` once posted, or `issue only` with the reason; a later run that finds the reproduction passing on a release records that release there) and a record of the pull request search: the open pull requests with the same component prefix, those whose changed files overlap the fix, and the pull requests merged into `main` since BETA1 on those files. A prepared fix is `fix.patch` (`git format-patch` of one commit on a scratch clone of `symfony/ai` `main`, applying to the commit named in the status) and `PR.md` (the pull request as it will be posted); `COMMENT.md` replaces `PR.md` when an open pull request already fixes the bug, and holds the comment for an open upstream issue that already covers it. A `ready to file` folder with neither holds `ISSUE.md`, the upstream issue as it will be filed (the repository's bug report template, exact versions, the reproduction inline, actual and expected behavior; for Symfony and Doctrine whether the fix looks small). A `ready to file` status needs a `Checked` line no older than 14 days and a `Pull requests and commits` line (the pull requests and commits the check found, named by a `#` number, a URL or a commit hash, or else the date of the check as `YYYY-MM-DD`, as in `none found (checked 2026-11-07)`; a line that starts with `none`, `nothing` or `no` always needs the date) in the same section, which the `reproductions` gate enforces (see [Quality gates](quality-gates.md)). After the owner's review a report gets an `Owner review` line and a `Status` line, which can also be `not filed` with the reason. The runner treats these files as it treats `REPORT.md`: only `reproduce.php` and PHPUnit tests are run. Nothing is pushed or posted from the loop; the owner approves each pull request, comment or issue (`upstream/README.md`).

Four folders are passing probes: they ask whether a library misbehaves where Intakt depends on it, and all four pass at the pinned versions, so they stay as guards and hold no `REPORT.md` (a probe that fails gets one, as the failing probe below). `ai-worker-mode-state/` boots one probe kernel with the Framework, Security, AI and MCP bundles (a generic platform over a mock HTTP client, two MCP servers with file sessions and `session.lock`, as `config/packages/mcp.yaml` has them) and sends every request through it with `handle()` and `terminate()`, as a FrankenPHP worker does, so the kernel resets its services between requests. It alternates 1,000 calls (model a, owner tool, model b, review tool): no answer, structured-output target or tool list crosses over, a session of one server is refused by the other, and memory after a warm-up of 100 calls grows by less than 16 KiB (a service keeping 20 bytes on every second call grows it by about 36 KB). The mock HTTP client keeps no record of its calls; the mock platform's client does, which would read as a leak. It does not replay an `HttpCassette` either: `CassetteHttpClient` serves the recorded interactions in order and fails once they run out, so 1,000 alternating calls would need 1,000 recorded interactions, and it checks each request against its recorded one, which would tie the probe to the call order. `ai-structured-output-enums-nested-lists/` fills an object with an enum and a nested list through the Anthropic, OpenAI and generic bridges, replayed from redacted `HttpCassette` files in `cassettes/` through `CassetteHttpClient`, which also checks each request against the recorded one. The cassettes were written through `CassetteHttpClient` from each provider's wire format over a mock client, not recorded from a live provider. A closed stream of the whole plan fills the object; a closed stream that stops in the middle of the array (stop reason `max_tokens`, `response.incomplete` with `max_output_tokens`, finish reason `length`) gives no object and raises `MaxOutputTokensException` (Anthropic, OpenAI) or the platform's `RuntimeException` with the decoder's message `Cannot json decode the streamed content.` (generic, whose `MaxOutputTokensException` covers cut tool calls only), never `IncompleteStreamException`. `mcp-parallel-tools-call-one-session/` runs three `tools/call` of one session in three PHP processes over one file session store: without `session.lock` a tool waits until all three are inside it, with the lock they run one after the other; each response and each progress token arrives once, also with the client pinned to protocol 2025-11-25, and a tool without parameters lists them as `{}`; a call with `{}` as its arguments reaches the tool as an empty array (the SDK decodes messages into arrays), which its request encodes again as `{}`. A client sending `[]` or leaving out `arguments` reaches the tool the same way as `{}`, so the probe does not check what the client sent. `ai-generic-platform-cut-stream/` (#1964) asks whether the generic bridge reads a complete OpenAI-compatible stream as cut: it sends hand-written SSE bodies in the chat completions format (the Hugging Face router's, model `openai/gpt-oss-120b:novita`) through `MockHttpClient`. A complete stream yields its text whether it ends with a usage-only chunk and `[DONE]`, without `[DONE]`, with the finish reason repeated on the usage chunk, or with keep-alive comments and CRLF line ends; an answer of reasoning only also ends complete, with no text. Only a body that ends cleanly without any `finish_reason` raises `IncompleteStreamException` (`Completions stream ended before a finish reason was received.`); a connection lost mid-body raises the HTTP client's `TransportException` instead. An in-stream error object without an `error` key (`{"object":"error",...}`) also raises `IncompleteStreamException`; the expected behavior is a provider error that carries the error's message, so a pre-release on which that test fails because another exception is raised has fixed it. Whether the router sends errors in that shape is not checked. The probe does not tell what cut the reviewer streams of the juror run of 2026-11-13: that run kept only the exception class, which Intakt's `StreamedAnswer` and `StrictVerdictStreamListener` raise too. Since #1964 a reviewer blocked by a cut stream keeps the provider, the model, which of the three raised the cut, the number of chunks and the last five as the evidence of its `incomplete-stream` finding (see [Review verdicts](review-verdicts.md)), so the next cut stream tells them apart; until one is recorded, the cause stays open. No probe uses a live provider or credentials.

`frankenphp-messenger-consume-sigterm/` is a probe that fails, so it holds a `REPORT.md`; the bug is already reported as php/frankenphp#2479 and Intakt has nothing to add there, so the folder holds no comment. `console.php` is a small kernel (Framework and Doctrine bundles, a Doctrine transport on SQLite, one handler that waits for a marker file); `MessengerConsumeSigtermTest.php` dispatches one message, starts `messenger:consume async` (no limit, so only SIGTERM stops it), waits until the handler is in flight, sends SIGTERM, releases the handler and reads the exit code, once under plain `php` (the control, exit code 0) and once under `frankenphp php-cli`. At FrankenPHP 1.13.4, 1.13.5 and 1.13.6 (checked 2026-11-21) and 1.14.0 (checked 2026-11-22) the second ends with exit code 139 (a segmentation fault), also for an idle consumer, so the consumers and the Scheduler keep running with plain `php`. The test needs the `frankenphp` binary and fails without it, as `intakt:upstream:run` counts a skip as a failure.

Two probes of plan T25 push the Platform and the Agent where providers fail; both fail at the pinned versions, so each holds a `REPORT.md`. `ai-failover-platform-deferred-rate-limit/` puts two accounts of one provider (two Generic platforms, so one class) behind a `FailoverPlatform`. The first account's 429 and the second account's answer are replayed from redacted cassettes in `cassettes/`, written through `CassetteHttpClient` from scripted HTTP answers. The 429 surfaces only when the result is read, after `FailoverPlatform` returned, so the caller gets `RateLimitExceededException` instead of the second answer; the control, the same 429 thrown inside `invoke()` by a `MockPlatformFactory` platform, fails over. A third test finds both platforms on one rate-limit key (the platform class), the bug of `ai-failover-platform-retries-a-failed-platform/`, which the open fix pull request symfony/ai#2890 addresses. The `ISSUE.md` of `ai-failover-platform-deferred-rate-limit/` is the upstream issue it was filed as (symfony/ai#2944). `ai-agent-streamed-tool-call-cut-stream/` runs an agent with a toolbox and `stream` over `MockPlatformFactory` with a `ScriptedResponse` closure: a round that streams a tool call and its usage, then a round that streams its usage and half a sentence and ends with `IncompleteStreamException`. The execution fails, the tool runs once, and each round's `StreamResult` holds its own usage once, but `Execution::getMetadata()` holds no usage after the cut, while the same run without the cut reports both rounds once. Its `COMMENT.md` is the comment posted on the open symfony/ai#2617 on 2026-11-14; that pull request counts the tool round but not the cut one. Intakt reads usage from each round's `DeferredResult` (see [Vendor](vendor.md)) and moves to another account through its own cooldowns (see [AI providers](ai-providers.md)), so neither bug changes what it records.
