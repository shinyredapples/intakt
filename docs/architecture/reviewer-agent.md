## Reviewer agent

Plan task T7, part 2 (design: [Reviews](../design/05-architecture/07-reviews.md), [threat model](../design/05-architecture/14-threat-model.md#third-party-text)). `Core/Review/Contract` has the `Reviewer` interface (`review(ReviewRequest, PlatformInterface, model): Verdict`, `#[NoDiscard]`), implemented by `Infrastructure/ReviewerAgent`; the interface exists because `Plugin/SymfonyAiVendor` may use only the module's `Contract`.

- **Request:** `ReviewRequest` holds the `Checkout` of the head, a `ReviewBrief` and a `ReviewerConversation`: the role prompt (what this reviewer looks for) and the `id`, a time-based UUID that names the conversation of that reviewer in that round (the review round makes a new one at every start of the reviewer, see [Review rounds](review-rounds.md)), and, for a reviewer of a round, the `round` id and the `reviewerId` the ledger records for it (see Stopping the reviewer under [Dashboard](dashboard.md)), and `askedAgain`, true only on a retry `SymfonyAiVendor` starts, so the live view marks where it starts (see [Live updates](live-updates.md)), and `askedToNameFindings`, true only on the retry after a `changes` or `blocked` verdict without findings, for which `ReviewerPrompt` adds `ReviewerPrompt::NAME_FINDINGS_OR_APPROVE` as the last user message. The `ReviewBrief` holds the `change`, a `ChangeUnderReview` with the round's `project`, the task text and the change's `diff`, and `open`, a list of `Finding` (empty in round one) holding the findings still open under their persistent ledger ids, and `round`, the round's number (required). `ReviewerPrompt` adds them as a user message after the task, the diff and the project memory briefing when there is one, in one fence of source `earlier findings` (id, severity, file:line, symbol, requirement and text of each), and the instructions tell the reviewer that from round two on a new P1 or P2 needs a requirement or `regression: true` and to list fixed ids under `resolved`, to report a returning finding with its id and `repeat: true`, and to use only given ids. `ReviewerAgent` then checks in plain code that every `resolved` id and every `repeat` finding id is among the open ids, that no id is both `resolved` and `repeat`, and, first, before an approval of cut text becomes `Verdict::cutApproval()`, that no finding uses an id reserved for Intakt's failed reviews (`Verdict::claimedFailureIds()`, see [Review verdicts](review-verdicts.md)), and otherwise throws `VerdictUnreadable` (never changes, never approval).
- **Agent:** `ReviewerAgent` builds a Symfony AI `Agent` per review on the given platform (through `ReviewerRuns::agent()`), with the toolbox for that review wrapped in `MalformedToolCalls`, then `FaultTolerantToolbox`, then `FencedToolbox` (through `ReviewerPrompt::fenced()`), at most 30 rounds of tool calls (`ReviewerRuns::MAX_ROUNDS`, handed to the agent's `maxToolCalls`, which counts the model answers that ask for tools, however many calls each carries; builder's choice: a review reads a handful of files and the bill grows per round). It calls the agent with the option `response_format` set to the reviewer answer document, `Infrastructure\ReviewerAnswer\Verdict::class` (see [Review verdicts](review-verdicts.md)). `StrictVerdictConverter` lets a tool call through (an unstreamed round in several parts loses only its narration text, and a streamed round's narration is never read as the answer, see Mapping in [Review verdicts](review-verdicts.md)), so the agent's loop runs; only the final answer must be a verdict. The agent's result goes through `ReviewerPrompt::verdictIn()`, which takes the verdict part of an answer in several parts (thinking beside the text), maps the answer document to the contract `Verdict` with `toVerdict()` and reads it with `VerdictParser::parseWith()`, so output that is not a valid verdict throws `VerdictUnreadable`. A reviewer that still asks for tools after the 30th round (`MaxIterationsExceededException`) throws it too instead of crashing; the vendor asks once more, and a second `VerdictUnreadable` fails the reviewer (see [Vendor](vendor.md)). That retry is the same as for any unreadable answer: `SymfonyAiVendor` settles the first call with the tokens of all its rounds, then starts a new conversation with twice the output room (`withMoreRoom()`, `RETRY_ROOM`), which may again take up to 30 rounds. So a review that hits the round limit, the longest kind of run, can cost about twice a normal run; a round that asks for 35 files is one round. The toolbox comes from a `Closure(ReviewRequest): ToolboxInterface`, wired with `#[AutowireCallable]` to `ReviewerMcpToolboxFactory::create()` (the tools over MCP, see Reviewers over MCP under [MCP server for the owner](mcp-server.md)), so a test can hand in `ReviewerToolboxFactory::create()` or a `TraceableToolbox`. A toolbox that lists no tools ends the review as `Verdict::noTools()` before the model is asked, and a `ReviewServerLost` from a tool call ends it the same way. A malformed tool call (a missing argument, a `path` that is not a string, an unknown tool name) is answered to the model by the `FaultTolerantToolbox`, and `MalformedToolCalls` (built per review, so excluded from the container) notes it on the way out, so the review throws `VerdictUnreadable` whatever the model answers afterwards, unless the reviewer was stopped later in the run: then it ends as `Verdict::reviewerStopped()`, so the stop is recorded. A path outside the repository is denied by the listener of part 1 in process and refused by the review server over MCP; that is no malformed call, and the review ends in the verdict the model answers. Failures of the call itself (rate limit, server error) stay exceptions.
- **Conversation store:** the agent gets a `MessageStoreInterface` (its `messageStore` argument, the `message_store` option of the AI Bundle) and the first messages carry the conversation's `id` as their bag id. `ReviewerAgent` saves them (`ReviewerRuns::started()`) before it calls the agent, which claims the conversation: when another review already stored messages under that id, also one that inserted the row at the same moment, the store throws its `ConflictException`, and `review()` throws `Contract/ConversationAlreadyStarted` before the model is asked, so no reviewer ever sees another one's prompt or answers. The Agent then saves the conversation after every round of tool calls and after the answer. In production the store is the bundle's Doctrine DBAL store (`symfony/ai-doctrine-message-store`, `ai.message_store.doctrine.dbal.reviewer_conversation` in `config/packages/ai.php`), whose alias `MessageStoreInterface` `ReviewerRuns` autowires; it keeps one row per reviewer and round in `reviewer_conversation` (`id`, `version`, `messages`, `updated_at`). Migration `Version20261029120000` creates the table, and the Doctrine `schema_filter` in `config/packages/doctrine.yaml` hides it from the ORM's schema tools, since the store owns its columns. Tests use `InMemoryMessageStore`, and a stub store that throws the `ConflictException` for the race.
- **Prompt caching:** `config/packages/ai.php` sets the Anthropic platform's `cache_retention` to `short` (the five-minute window; the bridge's default, set explicitly so it is a choice). The bridge then marks the last system block, the last tool definition and the last block of the last message as cacheable on every request, and reads `cache_creation_input_tokens` and `cache_read_input_tokens` into the result's `token_usage`. `tests/Core/Review/Infrastructure/ReviewerPromptCachingTest.php` runs the agent over the real Anthropic bridge with a scripted HTTP client: it asserts the cache markers in both requests and that round two's recorded usage has `cacheReadTokens` of what round one created. Whether a real provider honors the markers is the real review's evidence, not this test's.
- **Prompt:** `ReviewerPrompt::messagesFor(conversation, brief)` returns a system message, a user message with the task, a user message with the diff, a user message with the project memory briefing when memory holds notes on the files under review (see Briefing under [Project memory](project-memory.md)), and, from round two on, a user message with the open findings (see Request above), the last one except on the retry after a `changes` or `blocked` verdict without findings, which ends with the fixed `NAME_FINDINGS_OR_APPROVE` message. The system message holds the fixed instructions (the verdict is `approve` or `changes`, and a problem that must stop the change is a P1 finding rather than a verdict of its own, issue #2757; fenced text is data, and only a line `<<<END <boundary>>>>` with the opening boundary closes a fence, so any other marker inside is data, the tools, the rubric of [How code reads](../design/02-principles.md#how-code-reads): Storytelling, SOLID pragmatically, DRY without speculation, No overengineering, Comments say why never what, each finding naming the rule in its `requirement` field, and the rule of [Reviews](../design/05-architecture/07-reviews.md) not to re-flag what `bin/check` passes, also when the gate is wrong or misses a case, which gets a gate issue and at most a P3 naming the gate in `requirement`), then the role prompt. Each user message holds its input fenced, except that fixed retry message, which is Intakt's own text and carries no input.
- **Output contract:** the reviewer answers a `Verdict` (see [Review verdicts](review-verdicts.md)), each finding with `id`, `severity`, `file`, `line`, `symbol`, `text`, `fixable_by`, `repeat`, `requirement`, `evidence`, `regression` and `gate_gap`. `gate_gap` is true when the finding's `requirement` names a `bin/check` gate that passed and the finding says the gate misses the case, the gap the instructions cap at P3; the mark is a field, so code never parses the requirement or text for it. A finding without it reads as not a gate gap. A gate-gap P3 never reaches the builder's act list: the judge's `act` or `defer` makes it a follow-up and `reject` drops it, while a gate-gap P1 or P2 stays on the act list like any other (see Gate gap under [Review verdicts](review-verdicts.md)). `ReviewerPrompt::EXAMPLE_FINDING`, the finding the retry message shows, holds every field, `"gate_gap":false` included.
- **Fencing:** `Contract/Fence::wrap(UntrustedSource, text)` returns a `Contract/FencedText` value, never a string; its `rendered()` is `<<<UNTRUSTED <source> <boundary>>>>`, the text, `<<<END <boundary>>>>`, which `FencedText` itself builds, so every value of the type is a whole fence. The boundary is `fence-` and 16 hex digits of the SHA-256 of the text, so the text cannot contain its own boundary and close its fence, and equal text gives an equal prompt (so a provider's prompt cache still hits). `UntrustedSource` is `Task`, `Diff`, `ToolResult`, `EarlierFindings`, `FindingsToJudge`, `ChangedFiles` or `ProjectMemory`, and for the [builder prompt](builder-prompt.md) `Decisions`, `ActList`, `CiLog` or `PullRequestText`, and for the [escalation prompt](review-flow.md#the-escalation-prompt) `EscalatedFinding`. `FencedToolbox` wraps every tool answer (also the errors) through the same helper (an answer of the review server comes already fenced by the server, see [MCP server](mcp-server.md); `FencedToolbox` takes the text inside that fence with `Fence::contentOf()`, which accepts only a `tool result` fence whose boundary is the one its text gets and returns null for any other answer, so the 100000-byte ceiling of Oversized input is measured and cut on that text, the server's fence neither pushes an answer over the ceiling nor loses its end to a cut, and the model sees one fence; an answer that only looks fenced is fenced again and measured whole), and the open findings of earlier rounds, which earlier reviewers wrote, go through it as one `earlier findings` fence. The change's unified diff (`Diff::$patch`, cut to a size limit as described under Oversized input) goes through it as one `diff` fence, the user message after the task and before the open findings. The project memory briefing goes through it as one `project memory` fence (see [Project memory](project-memory.md)). CI log excerpts and the full text of other reviews are not inputs of the reviewer yet; each goes through `Fence` when it arrives.
- **Prompt assembly (#2518):** every prompt of the Review module is put together by `Contract/PromptAssembly`, the one class that creates Symfony AI messages: `system(instructions)` and `systemWithRole(instructions, ReviewerConversation)` give the system message, `user(lead, FencedText)` a user message of the lead, a blank line and the rendered fence, `notice(text)` a user message of Intakt's own text alone (`NAME_FINDINGS_OR_APPROVE`), `userText(lead, FencedText)` the text of such a message (so `ReviewerMemory` measures its 4000-byte cap on what is sent), and `toolAnswer(FencedText)` the string of a tool answer (`FencedToolbox`) or of an answer and a refusal of the review server (`ReviewedRepository`). Untrusted text is accepted only as `FencedText`; the instructions, leads and notice are typed `literal-string`, so the `phpstan` gate refuses a runtime string there. The role prompt is the one runtime value: it is the owner's panel configuration, so it counts as trusted, and the assembly takes it only from the `ReviewerConversation` that carries it, never as a plain string. This is the one exception to D2 of #2518: a reviewer role's `prompt` from the panel configuration (`ConfiguredPanels`) enters the system message verbatim, only through `systemWithRole()`. The `phpstan` gate enforces this ([Prompt assembly](prompt-assembly.md)): it refuses a message built outside `PromptAssembly` (`intakt.rawPromptMessage`) and, in `ReviewWithReviewerHandler`, a `new ReviewerConversation` whose role prompt is not a `rolePrompt()` call on a `RoundReviewer` (`intakt.unprovenRolePrompt`); it also limits where the role prompt's carriers are built (#2812): a `ReviewerRole` only in `ConfiguredPanels` and `SampleProject` and a `RoundReviewer` only in `ReviewRound` (`intakt.reviewerRole`), a `ReviewerConversation` only in `ReviewWithReviewerHandler` and the retries of `SymfonyAiVendor`, which copy the stopped conversation's `rolePrompt` (`intakt.reviewerConversation`), every class a class-string union names being judged (a class string bound to an interface or parent class of a carrier, such as `class-string<HasPlace>`, counting as that carrier, and an intersection bound such as `class-string<HasPlace&Countable>` unless a part of it rules the carrier out) and a trait body, used by a class or not, counting as outside, so the role prompt's chain of trust ends at the owner's panel configuration and the sample's literal roles; the gate judges `src/`, `bin/` and `config/`; a message built under `tests/` is not judged. `ReviewerPrompt`, `JudgePrompt`, `ReviewerMemory` (`briefingOn()` returns the user message or null), `FencedToolbox` and `ReviewedRepository` go through it, and the messages the model receives are byte for byte what they were before. Outside the Review module (#2519), the [builder prompt](builder-prompt.md) is one string put together by `document(PromptPart ...)`, each part a `literal-string` lead with an optional `FencedText`, and `SymfonyAiKeyCheck` and `intakt:vendor:probe` send their one fixed prompt as `notice()`; both modules use the shared class from `Review/Contract`, so no other module builds its own.
- **Oversized input:** `PromptCut` (in `Review/Contract`, because the [builder prompt](builder-prompt.md) cuts its inputs with it too) cuts the task, the diff and every tool answer to `PromptCut::CEILING_BYTES` (100000 bytes, a constant; builder's choice: a review reads files through its tools, so a larger prompt only costs tokens) with `mb_strcut`, so a UTF-8 character is never split, before the text is fenced. `PromptCut::fenced()` returns a `FencedText` too; for a cut text it is the fence of the head with `FencedText::cut()` applied, so the note "Intakt cut this text: N of M bytes are shown ..." (a constant of `FencedText`) follows the closing marker, outside the fence, so it is Intakt's text and the cut cannot drop the marker; the instructions tell the reviewer to read what it needs with its tools. Plain code does not trust that: when the task or the diff is over the ceiling (`ReviewerPrompt::cutsInputOf`) or `FencedToolbox` cut a tool answer of the review (`cutAnAnswer()`; one toolbox per review, so the mark never outlives it), `ReviewerAgent` turns an `approve`, or a `changes` of only P3 findings, which the quorum can count as approval (`Verdict::mayCountAsApproval()`; a reviewer's `blocked` with findings is judged as the `changes` it is recorded as), into `Verdict::cutApproval()`: `blocked` with the P1 finding `cut-approval` (fixable by the owner), a failed review like `no-tools`. A `changes` or `blocked` answer keeps its findings. An answer of any decision that names a reserved failure id is refused as unreadable before that, so a cut diff never turns it into `cut-approval`. The guard reads the severities the round will store: `ReviewerAgent` first applies `Domain\GoalpostRule` to the answer with the round's number (`ReviewBrief::$round`) and the open findings, and returns that verdict, so from round 2 on a `changes` whose only P1 or P2 names no requirement and no regression (or repeats an open P3) is P3-only and is refused too (`ReviewerVerdictTest`). A malformed or unknown tool call and an answer that is not a verdict throw `VerdictUnreadable`, and a reviewer that fails that way twice is recorded with that exception class as its failure, or with the reason in words when Intakt built it from its own wording (see [Review flow](review-flow.md)); an approval of a cut task (one that tries to steer included), diff or tool answer ends as `blocked` with its finding; neither is a crash; `ReviewerVerdictTest` and `PromptCutTest` cover each case, and `FencedToolboxTest` an answer the review server fenced (just under the ceiling it is not cut, over it it is cut inside one fence that still closes, and one that only looks fenced is measured whole).
- **Usage:** every round of the agent is a call on the project's tier platform; `SymfonyAiVendor` settles the call with the usage of all rounds.
- **Session summary (#1554, part 1 of #1549):** `Contract/SessionSummaries::ofRound(roundId)` returns a `Contract/SessionSummary` computed from what the round recorded, for the summary the review page pins under its live log (#1555, see [Dashboard](dashboard.md)), or null when no round is stored under the id (an unknown id or one that is no UUID, because the ledger also names rounds started before Intakt stored them): `toolCalls` (a `Contract/ToolCallCount` per tool name, ordered by name, with `kindInWords()` for the page, and `totalToolCalls()`), `cost` (the round's cost from `RoundCosts::costOf()`, see [Round cost](round-cost.md)), `filesRead` (each file once, under its path relative to the checkout as the checkout resolved it, so two spellings of one file are one entry, in the order it was first read, each passed through `Platform\Contract\Redaction` by `RoundToolCalls::filesReadIn()` because the summary is published live), and three lists of findings under the change's ledger ids: `checking` (the open findings the round was handed), `reported` (the open findings it reported, from `reported_findings`) and `resolved` (those of `checking` that the round resolved), plus `judged`, true once the stored round's state is judged, read in the same query as the rest, so the live publisher learns under its lock that the round's final summary goes out with the judged state (see Summary updates in [Live updates](live-updates.md)). `reported` and `resolved` stay empty until the round completes, because before that each reviewer's finding ids are its own. When it completes, the round keeps the ledger ids of the findings it resolved as a JSON list (`resolved_finding_ids`, migration `Version20261112110000`, written by `StoredFindings` with `resolved_findings`, which memory indexing reads; an empty list for a round overtaken by a newer recorded round of the change), and `Infrastructure/StoredSessionSummaries` lists as `resolved` the findings of `checking` whose id is in that list, matched by id only and shown as `checking` holds them, so of two open findings that read alike only the resolved one is listed, and a finding another open round of the change repeated with new text meanwhile is still listed. A round completed before that migration (the column is null) kept its resolved findings under its reviewer's ids, which can name other open findings of the ledger, so it lists none as resolved, as does a round not completed yet. Tool calls and files read come from `round_tool_call` (`Domain/RoundToolCall`, migration `Version20261112100000`: an autoincrement `position`, `round_id`, `tool`, and `file_read`, set only for a file the server answered with), which the review server writes through `Infrastructure/RoundToolCalls` (see Review server under [MCP server for the owner](mcp-server.md)). The review server records them, not the agent, because every reviewer's calls pass through it, also those of a subscription CLI whose conversation Intakt never stores; one row per call rather than counters on the round, because the reviewers of a round call tools at the same time. The credential names the round, not the reviewer, so the figures are the round's, summed over its reviewers. Tests: `tests/Core/Review/Infrastructure/StoredSessionSummariesTest.php` (group `persistence`; calls through the review server over HTTP: counted by kind, a file read twice or under two spellings listed once, a refused read counted as a call and not as a file read, a listing or a search reads no file, another round's calls not counted, the cost, the findings before and after completion, an open finding left unresolved, one of two alike findings resolved, a legacy round kept under a reviewer's id that names another ledger finding for findings that read alike and that read differently, a finding resolved after an earlier open round repeated it with new text, a round completed after a newer round of the change, no summary for an unknown round and for an id that is no UUID, and a read and a refusal whose recording fails, which keep their answer and log the error). A call whose row could not be written is missing from the summary.
- **Tests:** `tests/Core/Review/Contract/FenceTest.php` and `tests/Core/Review/Infrastructure/ReviewerVerdictTest.php` (a real `Agent` on a `TraceablePlatform` around `MockPlatformFactory` and the application's dispatcher; `assertPlatformCallCount()`, `assertToolCalled()` and `assertToolCallCount()` through `AiAssertionsTrait`, with a `TraceableToolbox` the test hands in as the toolbox closure). Because the model is scripted, the sample change (a what-comment and an interface with one implementation) proves the plumbing and the prompt (the model is shown the rubric and the files it read, and its findings reach the verdict with the rule they cite), not what a real model finds. `ReviewerConversationStoreTest` (group `persistence`) migrates an empty SQLite database, round-trips a conversation through the container's store and shows that store refusing another review's first messages under a stored id; `tests/Application/EmptyDatabase.php` empties the database for the persistence tests, including the conversation table that the schema filter hides from the schema tool.
