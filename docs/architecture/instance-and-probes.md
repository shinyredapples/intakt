## Instance and probes

Two entry points let reviewers and the boot gate exercise a running Intakt without network access, after `composer install` (plan task T31). Both exist.

- `bin/instance` boots the app from a clean checkout on a free port of `127.0.0.1` with SQLite in a scratch directory, prints one JSON status line, `ready` or `failed` with the reason, and stops cleanly. It has two modes (plan task T22): when an executable `frankenphp` is on its `PATH` (as in the container image), FrankenPHP serves the app in worker mode; otherwise PHP's built-in web server runs the plain Symfony runtime.
- `bin/probe <file>` boots the same instance and runs a reviewer's small PHPUnit test or PHP script against it, with network access cut, and prints its output and exit code.

How `bin/instance` works:

1. It needs no Composer autoloader itself, so a broken install still reports `failed`. It takes no argument, except `-- <command...>` (command mode, how `bin/probe` reuses it): once the instance is `ready` it runs that command with stdin from `/dev/null`, stdout and stderr shared, descriptor 3 closed, and `INTAKT_INSTANCE_URL` and the scratch environment set. A command still running after 60 seconds (`INTAKT_INSTANCE_COMMAND_SECONDS` when set to a positive number, fractions allowed, which the tests use) is killed with SIGKILL and its status is 124; a limit that is not finite in nanoseconds (such as `1e300`) fails the boot before the command runs. `CommandWait::exitBefore()` blocks SIGCHLD and waits for it, so the command's end wakes the wait at once; where the PHP signal functions are disabled it polls every 50 ms. Either way it reads the command's status before the clock, so a command found ended after the limit counts as timed out. Only the command itself is killed or waited for: processes it leaves behind are the caller's to contain, which `bin/probe` does with a PID namespace of its own. With `PROBE_ISOLATED=1`, the calling sandbox provides it. When the boot fails, the command does not run.
2. It creates a scratch directory under `$TMPDIR` (under `var/` when unset; a concurrent run may remove a `var/` folder between its creation and the scratch folder, so `mkdir` is tried a second time when the first left no folder; when both fail, the status reason is `cannot create the scratch directory: <operating system reason>`, or `unknown reason` when `mkdir` failed without a warning) and points the cache, log and share directories and `DATABASE_URL` into it. `APP_ENV` is taken from the environment (default `test`); `APP_DEBUG` is always `0`, because a debug kernel writes `config/reference.php` into the checkout.
3. Built-in server mode: it starts `php -d variables_order=EGPCS -S 127.0.0.1:0`, so the runtime sees that environment instead of falling back to `.env`, and the server binds a free port itself (no other process can take it between a probe and the bind). Worker mode: FrankenPHP cannot report a port it picked itself, so `bin/instance` binds `127.0.0.1:0` twice, notes both ports and closes the sockets; it writes a minimal `Caddyfile` into the scratch directory (not the repository's, which needs the Mercure settings and the `mcp` worker): a global `admin` on `127.0.0.1:<admin port>`, `metrics` (FrankenPHP adds its queue and worker-restart series to the admin API's `/metrics` only with Caddy's metrics on, and the instance's board reads them there) and a `frankenphp` block setting `num_threads 2` (FrankenPHP's default is two PHP threads per CPU, each with its own memory, so on a host with many CPUs under an address-space limit PHP exits with a bare `Out of memory` before it serves; with the fixed count FrankenPHP runs three PHP threads, two regular and the worker's, whatever the host) and `php_ini log_errors 1` (FrankenPHP runs PHP with `log_errors` off, so without it a fatal error during the boot, such as a broken kernel configuration, only reaches the response body and the failure reason would not name it), and one site `http://:<port>` with `bind 127.0.0.1` (the site names no host, because a Caddy site address also matches the `Host` header and Caddy answers a request no site matches with an empty `200` that never reaches PHP, so a request naming the dashboard's host, as the journeys send, would get an empty page; `bind` keeps the listener on loopback, without it the listener would take every interface), `root <project>/public` and a `php_server` holding one worker named `app` (`file <project>/public/index.php`, `num 1`, `env FRANKENPHP_WORKER 1`, so Symfony Runtime picks `FrankenPhpWorkerRunner`), and starts `frankenphp run --config <scratch>/Caddyfile --adapter caddyfile` with `XDG_DATA_HOME` and `XDG_CONFIG_HOME` inside the scratch directory, so Caddy writes nothing outside it. If another process takes a port in between, FrankenPHP exits and the status is `failed` with the reason from its log; there is no retry. In both modes a `sh -c 'exec "$@" 3>&-'` wrapper closes the caller's descriptor 3, and the descriptor spec holds only 0 to 2 (stdout and stderr go to a log in the scratch directory), so the server never holds the status descriptor.
4. Once the port is known (from the server log in built-in server mode; in worker mode the port was chosen up front, but it counts as known only once the log holds Caddy's `serving initial configuration` line, which Caddy prints after every listener is bound, so an unrelated process that answers on the chosen port before FrankenPHP cannot make the instance `ready`), it requests `/` on that port until the server answers, for at most 30 seconds. A status code below 500 is `ready` (any such answer shows the kernel booted; the dashboard answers `/` on a port other than `DASHBOARD_PORT`, as this one is, with `400` before the board reads any database). A status code of 500 or more, a status line it cannot parse, an early exit or no answer is `failed`. The reason is the first log line that mentions an error or exception, else the last line that is not empty and not one the built-in server writes about itself (its `Development Server ... started` line and its `Accepted`, `[<code>]: <method> <path>` and `Closing` lines for each request, which would only restate the status code; a process the system stops, such as PHP's own `Out of memory` exit, names no error), `the server log is empty` when the log holds no line, `the server log names no reason` when it holds only the built-in server's own lines, or the unparsable status line.
5. It stops the server (SIGTERM, then SIGKILL after 5 seconds) and removes the scratch directory. When `TMPDIR` is unset and the run itself created the `var/` fallback, it also removes `var/` with a plain `rmdir`, which fails quietly while another run still uses it; a `var/` that existed before the run is left alone. It prints the server log to stdout, except in command mode after a `ready` boot, where the command's output is what the caller wants. Only then does it open descriptor 3, once, and write the status line, so nothing it started can inherit a duplicate of it. A descriptor 3 that the PHP runtime opened itself counts as missing: with CLI OPcache enabled, OPcache's lock (an unlinked file) takes the first free descriptor before the script runs, so the script checks the link count of what it opened (`fstat`) and refuses zero, which a caller's file, pipe or device never has. A caller's memfd (the build loop's channel) also has no link, so it is accepted when `/proc/self/fd/3` points to a `/memfd:` name and is not exactly OPcache's own lock (`/memfd:opcache_lock (deleted)`); a caller's memfd whose name only starts with `opcache_lock` is accepted.

The server and the command get an environment built from an allowlist, not the caller's whole one: `PATH`, `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TZ` and `TMPDIR` when the caller set them, the `APP_*` variables and `DATABASE_URL` that `bin/instance` sets (`APP_ENV` and `APP_SECRET` keep the caller's value when it is set and not empty or `0`), and `INTAKT_INSTANCE_URL` for the command. The server always gets `FRANKENPHP_ADMIN_URL` (the caller's value is never passed): in worker mode its own admin address, in built-in server mode `http://admin-api.invalid`, which `AdminApi` refuses, so the board reads nothing from a listener on the default port. In worker mode the server also gets `XDG_DATA_HOME` and `XDG_CONFIG_HOME`, and the command `INTAKT_INSTANCE_ADMIN_URL` (`http://127.0.0.1:<admin port>`, FrankenPHP's admin API, for example `/frankenphp/threads`); in built-in server mode neither is set. A command therefore cannot print a token the caller had set.

Contract with the build loop: the status line is `{"status":"ready"}` or `{"status":"failed","reason":"..."}` on descriptor 3 only; in worker mode it carries `"mode":"worker"` after `status` (`{"status":"ready","mode":"worker"}`), and a line without `mode` means the built-in server; stdout and stderr are the log (or the command's output). Without a command, the exit code is 0 exactly when `ready` was reported. In command mode, a `ready` boot exits with the command's status (124 when it was killed), and a `failed` boot exits 1. When descriptor 3 is not open, or the PHP runtime opened it itself (OPcache's lock), no status is written and the exit code is 1. The status is an `InstanceStatus` marked `#[NoDiscard]`, so the script cannot drop it. The tests are split in three files, so the tests gate can run them on separate workers, and they share one boot wherever several facts come from the same run (each boot starts a server, and a boot of the real kernel compiles the container cold). `tests/Application/InstanceTest.php` covers a clean boot of a copy of the project and, from the same boot, the leftovers in `$TMPDIR` and in the project tree after it, a broken kernel configuration (reported as `failed`, its server log printed and the command not run), an unparsable status line, an HTTP 500 whose log holds only the built-in server's own lines (`HTTP 500: the server log names no reason`) and one whose front controller wrote a line to stderr (that line is the reason, not the request lines after it), the removal of a `var/` created by a boot without `TMPDIR` and the keeping of one that existed, a scratch directory that cannot be created, the kill with 124, and in one command-mode boot the passed-through exit code, the suppressed server log, the closed descriptor 3, the missing `INTAKT_INSTANCE_ADMIN_URL`, the server's `FRANKENPHP_ADMIN_URL` (`http://admin-api.invalid` although the caller set another; the stub's `/?admin` answers it) and the environment allowlist (a caller variable off the list is not visible to the command). `tests/Application/InstanceDescriptorTest.php` covers descriptor 3: the server's descriptors (read from `/proc` while it runs, with a caller holding descriptors 3 to 14), the missing descriptor (closed explicitly, since PHPUnit's own process holds Composer's bin proxy script on descriptor 3 and a child would inherit it), the descriptor OPcache takes when `opcache.enable_cli` is on (skipped where the extension is not loaded), a memfd as descriptor 3 (passed by a small Python helper, named `opcache_lock_status`), a pipe as descriptor 3, a scratch `mkdir` that loses a race with an `rmdir` once and one that fails without a warning. Both `tests/Application/InstanceTest.php` and `tests/Application/InstanceDescriptorTest.php` run `bin/instance` with a `PATH` stripped of every folder holding a `frankenphp` (through `pathWithoutFrankenphp()` in `tests/Application/InstanceTestCase.php`), so they cover the built-in server wherever they run. Only the tests whose subject is the kernel boot the real application: the clean boot (which also checks the project tree), the broken kernel configuration and the worker-mode tests (the four with a `frankenphp` stub name the real project too, but fail before any kernel boots). The launcher tests (the `var/` folder cases, the command-mode boot, the kill with 124 and every test of `tests/Application/InstanceDescriptorTest.php`) boot a stub copy of the project (`bin`, `public` and `composer.json`, made once per class through `tests/Support/ProjectCopy.php`) whose `public/index.php` answers 200, so they do not pay for the kernel's boot. The worker-mode tests in `tests/Application/InstanceWorkerModeTest.php` need `frankenphp` on the `PATH` (the CI image and the build sandbox have it) and fail without it, since the tests gate counts a skip as a failure: one boot, with `frankenphp` found through a relative `PATH` entry (`tools`) while the caller runs from another directory (`bin/instance` makes the found path absolute before the server starts from the project root), reports `{"status":"ready","mode":"worker"}`, and its command reads `/proc/net/tcp` and `/proc/net/tcp6` and finds the instance port listening on `0100007F` (loopback) only, then reads the `FRANKENPHP_ADMIN_URL` of the FrankenPHP process this run launched (the one whose `--config` lies in the test's scratch folder) from `/proc` and prints only whether it equals `INTAKT_INSTANCE_ADMIN_URL`, which it does (not the `http://localhost:2019` the caller set), then reads `/frankenphp/threads` on the admin port and finds the `app` worker thread for `public/index.php` (from the Caddyfile `bin/instance` writes) with a request served, and after it no file is left in `$TMPDIR` and no process names the scratch directory; a broken kernel configuration reports `failed` with `"mode":"worker"` and a reason that names the unrecognized option, with exit code 1; a request that names the dashboard's host (`localhost` and the `DASHBOARD_PORT` of `.env.test`) reaches the app: after its command migrates the instance's fresh database, `/projects` answers `200` with the empty projects page; in another boot, after the same migration, the board at `/` shows `Threads busy` and `Queue depth` in its infrastructure row, read from the instance's own admin API; a `frankenphp` in the caller's directory, found through an empty `PATH` entry, which the lookup reads as the shell does, also boots in worker mode; a boot reports `{"status":"ready","mode":"worker"}` and its command finds three PHP threads in `/frankenphp/threads`, whatever the number of CPUs (the test checks the count rather than a boot under an address-space limit, because the memory a boot needs also depends on how FrankenPHP and its extensions are linked). A `frankenphp` stub on the `PATH` that exits 1 with an error makes the boot report `failed` with `"mode":"worker"` and the stub's error line as the reason, leaving no process or scratch directory; a stub whose last log line is `Out of memory` reports `the server exited: Out of memory`, and one that exits without a word `the server exited: the server log is empty`. A stub that answers one request on the chosen port and then exits 1 with a bind error, as an unrelated listener in front of a FrankenPHP that cannot bind would, makes the boot report `failed` with that error, and the command does not run.

How `bin/probe` works:

1. It takes one path, `tests/Probe/NAME.php` (letters, digits, `_`, `.` and `-`, an existing file); anything else prints the usage and exits 2.
2. It starts `unshare --net --map-root-user --pid --fork --kill-child`, which gives the run a new network namespace with no route out and a new PID namespace, brings loopback up (the instance needs it) and runs `php bin/instance -- <probe command>` in it. `bin/instance` is process 1 of that PID namespace, so when it exits the kernel kills every process the probe left behind, also one that started its own session, after a normal end, a failure or the 60-second kill. If the namespaces cannot be created, no status is reported and the probe fails; it never runs with the network open. A caller that already isolates the run (the build loop's sandbox: own network namespace, own PID namespace, a seccomp filter that refuses new user namespaces) sets `PROBE_ISOLATED=1`: `bin/probe` then starts `php bin/instance -- <probe command>` directly, without `unshare` and without `ip link set lo up`, and descriptor 3 stays the status channel. It first checks that the run is offline, reading `/proc/net/dev` and connecting to a listening socket on `127.0.0.1` (sysfs shows the namespace it was mounted in, so its flags would not tell): an unreadable `/proc/net/dev`, one with no interface or a line that does not name one, a network interface other than `lo`, or a loopback that is down, makes it print the reason to stderr and exit 2 before anything starts. Any other value of the variable, or none, keeps the `unshare` path.
3. A name ending in `Test.php` runs as `vendor/bin/phpunit --no-configuration --bootstrap tests/bootstrap.php --do-not-record-test-run-history <file>`, anything else as `php <file>`. The probe sees `INTAKT_INSTANCE_URL` (the instance's base URL) and the scratch `DATABASE_URL`, cache, log and share variables.
4. The probe's output goes straight to stdout and stderr; `bin/probe` ends with the line `exit code: N` and exits with the probe's status. It accepts exactly the two ready lines, `{"status":"ready"}` and `{"status":"ready","mode":"worker"}`, so it works in both modes of `bin/instance`. When the instance is not `ready` it prints the status line to stderr and exits non-zero, also when the probe itself would have exited 0.
5. The instance stops and removes its scratch directory as `bin/instance` does, so no process or file is left. `tests/Application/ProbeTest.php` boots five instances, each holding every fact its run can show, because a namespaced boot costs seconds: a failing script (it prints the `404` the instance answers for a missing page and the result of connecting to `192.0.2.1`, which fails with `Network is unreachable`, as only a namespace without a route gives, since with a route it would time out, leaves a child and ends with 7, reported as `exit code: 7`), a PHPUnit test (in worker mode where `frankenphp` is on the `PATH`), a script against the built-in server (with `frankenphp` taken off the `PATH`), a probe that ends with 0 and leaves a child (after it the child is killed, `$TMPDIR` is empty and no process names the project's `public` folder), and a probe killed after its time with exit code 124. It also covers a refused path. The child a probe leaves running starts its own session (in the failing, the exit-0 and the killed probe; the child confirms that it runs by creating a marker file before the probe goes on, so a child that never started cannot pass as a killed one, and the kernel reaps every process of the PID namespace before `unshare` returns, so the check after the run is not a race). An `unshare` that fails is covered too: the probe never runs and `bin/probe` exits non-zero. `tests/Application/ProbeIsolationTest.php` loads `bin/probe` (it starts a probe only when run directly) and covers the three-way decision (`unshare`, isolated start, refusal) with a fake `/proc/net/dev` and an address that cannot be bound, so it needs no namespace privileges. The tests that need the namespaces are skipped on a host that refuses them, as the gate tests are.
