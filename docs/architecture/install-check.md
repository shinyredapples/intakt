# The install check

## In short

`bin/install-check [<repository address or path>]` installs the project the way a stranger does, from the README on a clean clone, and reports the first thing that breaks. Hundreds of tests had passed while a fresh install could not save its API key; only a real install found it.

## How it works

- **Reading the README.** A first `git clone -- <address>` (default `https://github.com/shinyredapples/intakt.git`) into a new folder under the system temporary folder reads the default branch's README. The current checkout is never used. An address that is empty or starts with a dash is refused; a path to an existing folder is made absolute first, so `bin/install-check .` clones the repository the caller stands in.
- **The commands.** `ReadmeInstallBlock` reads them from that README: the install block is the first code fence after the line that starts with `<!-- install-check`. The README stays the one source. Every line runs verbatim, one step each (`install: <command>`), including the README's own `git clone ... && cd intakt`: it runs in an empty `home` folder, and git's `url.<address>.insteadOf` setting (passed as `GIT_CONFIG_*` variables) points the README's GitHub address at the repository under check, so a broken address or folder name in the README fails that step. Each line runs in its own shell, followed by a line that writes the folder the shell ended in; the next install command starts there, so a `cd` in one line (also into a nested folder) carries to the next. A line that ends outside `home` leaves the next one in `home`. The walk runs in the folder the last install command ended in. `teardown` runs in the last folder inside `home` that any install command ended in, so a line that returns to `home` and fails after Compose started still stops the containers; when no line ended inside `home`, `teardown` is skipped (`no clone was made`). A README edit that breaks a command fails that step. A missing marker, a marker not followed by a code block or an unclosed block means the check could not run.
- **The walk.** After the install commands: `demo` (`bin/install-check-demo`: open `/demo`, press **Play the demo run**, wait for `#review-verdict`; no model is called), `ui-check` (`node bin/ui-check http://localhost:7781`), `demo-removal` (`docker compose exec -T intakt php bin/console intakt:demo:remove`, because the journey needs a demo run that has not been played: `/setup` shows its button only then), `journey-check` (`node bin/journey-check http://localhost:7781` when the clone has it and the removal passed, otherwise skipped naming the reason) and `keyed`. A failed install command skips the later install commands and every step after them.
- **The keyed step** runs only when `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` is set (the first one found). The container seeds the sample's reviewers from the keys it sees when it starts, so the step writes `<NAME>=<key>` to the clone's `.env.local` (mode 0600, as the README's key path does), then runs `docker compose up -d --wait && docker compose exec -T intakt php bin/console intakt:demo`. Any verdict exit of `intakt:demo` (0 approve, 10 changes, 11 blocked) passes; anything else fails. A key with characters `.env.local` cannot hold unquoted fails the step.
- **What a step sees.** `InstallProcessRunner` gives every step only `PATH`, `HOME`, `USER`, the locale, `TERM`, `TMPDIR`, `XDG_RUNTIME_DIR`, the docker, Node and Playwright location variables and the proxy settings, plus `COMPOSE_PROJECT_NAME`, `GIT_TERMINAL_PROMPT=0` and the git rewrite. No provider key and no forge token (`GH_TOKEN`, `GITHUB_TOKEN`) reaches the README's commands or the clone's scripts. Each step runs as `setsid sh -c <command>`, so it is its own process group. Each step has 1800 seconds; one that passes them fails with `stopped after 1800 seconds` (exit 124), its whole process group is killed, so nothing it started keeps running, and the check goes on to the end.
- **Redaction.** The key's value and any `Bearer <token>` (the MCP owner token `intakt:demo` prints) become `[redacted]` in every log and in the report.
- **The end.** Every run has its own `COMPOSE_PROJECT_NAME` (`intakt-install-check-<12 hex digits>`), so two runs on one docker never stop each other's containers or remove each other's volume. The last step, `teardown`, runs `docker compose down -v --remove-orphans` in the clone, also after a failed step; a failing teardown fails the check. The temporary folder is removed at the end, also when the check could not run.

## Output and exit codes

One line per step, `passed`, `failed` or `skipped`, then the last 40 lines of a failed step's log. Logs, the demo screenshot, the screenshots of `bin/ui-check` (`var/ui-check/`) and `bin/journey-check` (`var/journey-check/<run>/`) copied from the clone, and `report.json` go to `var/install-check/<date>-<time>-<6 hex digits>/`, one folder a workflow can upload. Exit 0: every step passed or was skipped, and the report reached `bin/journey-alarm` when it was asked to. Exit 1: a step failed. Exit 2: the check could not run (`InstallCheckCouldNotRun`: no `docker compose`, the first clone failed, the README block is missing), or every step passed but `bin/journey-alarm` failed.

## Reporting

When `GITHUB_REPOSITORY` is set, `bin/install-check` ends by running `bin/journey-alarm --install-check=<report.json>` (with `--run=<GITHUB_SERVER_URL>/<GITHUB_REPOSITORY>/actions/runs/<GITHUB_RUN_ID>` when those three are set) with its own environment, so `gh` gets the token; without it, the check prints `not reported: ...` and files nothing. `bin/journey-alarm` validates the report (`InstallReport::fromJson()`) and hands each step to `InstallCheckAlarm`, which uses the same `GitHubIssues` and lock as the journeys alarm. A failed step files one urgent, ready task or rewrites the open one. The marker `<!-- intakt:install-check:<hash of the step's identity> -->`, the first line of the task's body, ties the task to the step. Every lookup (the step's own task, the check after a create, and the tasks of steps a run no longer has) reads the marker from the first line only (`GitHubIssues::openIssuesOpeningWith()`) and takes the lowest number, because a body quotes a log, and a log may hold another step's marker on a line of its own. Anyone can copy a marker into an issue, so the alarm reads, edits and closes only issues opened by the account it acts as (`GitHubIssues::openedBy(GitHubIssues::account())`, where the account is the login `gh api user` answers). GitHub refuses that question to every installation token alike ("Resource not accessible by integration"), so the account is then never guessed: the environment variable `INSTALL_CHECK_ALARM_ACCOUNT` names the login (not a credential; the daily workflow of a later change sets `github-actions[bot]`), and it is read only when that question is refused. The whole value must be a login: anything else, a trailing newline included, is refused before any write and is not trimmed. Refused and unset, `bin/journey-alarm --install-check` writes nothing to GitHub and exits 2 with a line naming `INSTALL_CHECK_ALARM_ACCOUNT`; any other refusal stops the alarm with exit 1. An issue another account opened with a marker is never edited or closed, and a failing step files its own task beside it. An install step is known by its place in the README block (`install: #1`, `install: #2`, ...), every other step by its name. So fixing a broken command closes its task. Adding or removing a command moves or drops places: when every install command of a run passes, `InstallCheckAlarm` reads the open issues whose whole first line is an install-check marker with a 64-digit hash (`GitHubIssues::openIssuesOpeningWith()`), where the alarm writes it, and closes each whose marker no step of this run has; an issue that only quotes a marker further down, or an example of one, is never closed. While an install command fails, such a task stays open. After a create it reads the open issues again; when a run on another machine filed an older task for the same step meanwhile, it closes its own as a duplicate and updates the older one. A step that passes closes its open task; a skipped step changes nothing. A daily scheduled run is added by a later change.
