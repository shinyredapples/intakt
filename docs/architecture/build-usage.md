# Build usage

Plan task T49, part 3 (#1576; design: [Budget and model planner](../design/05-architecture/06-budget-and-model-planner.md), "Subscription CLIs are counted from their own logs"). A [build job](build-job.md) runs the Claude Code CLI on a subscription, which reports no usage to Intakt. After the job, Intakt reads the tokens the session spent from the job's `usage.log` and records them in the build job's ledger row, for the per-task total of the [build allowance](build-allowance.md).

## What the job hands back

The CLI runs with `--output-format stream-json --verbose`, so it writes one JSON record per line as the session runs. Each content block of a model message is one `"type":"assistant"` record carrying the message's `message.id` and `message.usage`; records that repeat an id belong to the same message. The stream also holds the CLI's other records (`system`, `user` with every tool result, the final `result`).

The build script writes the stream to `session.jsonl` in the job's work area, never into the output, and sends only the CLI's errors to `build.log`. After the session it filters the stream with the image's `node` (resolved in the system folders before the session, like `git`): for each `assistant` record it writes `{"type":"assistant","message":{"id":...,"usage":...}}` to `usage.log` in the output, and it drops every other line. So no tool result reaches `build.log`, which the console prints when a build fails, and the transcript never shares the output's byte limit with the bundle. The filter opens the stream without following a link or waiting on a named pipe and reads it only when it is a regular file; it parses no line over 64 MiB but writes a record without an id in its place, which the reader turns into `malformed`. It is bounded like the bundle step (30 seconds). When the image's `node` is missing or lies in a folder the builder can write, or the filter fails or is cut, no `usage.log` is handed back and `build.log` says why; the reading is then `not_reported`. A `usage.log` the session planted is removed before the filter writes its own.

## What is read

`Domain/SessionLog::usageIn()` counts each message once by its id (the last record of an id gives its counts) and adds the messages up. A `result` line, where one is in the file, is not added on top, because its usage repeats the messages'. Every `assistant` record must carry a non-empty text `message.id` and a `message.usage` with `input_tokens`, `output_tokens`, `cache_read_input_tokens` and `cache_creation_input_tokens`, each a whole number from 0 to 10^15 (`BuildUsage::MOST`), and the sum of each count must stay within that bound (`BuildUsage::plus()`); otherwise the usage is `malformed`, never zero. A file without any `assistant` record is `not_reported`. Other lines are skipped. No model name is read: the job's model is the one the tier chose.

The records are written as the session runs, so a session cut at its allowance or killed by the engine, which writes no `result` line, still counts the messages it logged. The file is untrusted, because the builder runs as the same user as the build script and can rewrite the stream and the output, so the figures are recorded for the allowance only; no start decision or ceiling reads them.

## The separate process

`UseCase/RunBuildJob/IsolatedSessionLog::usageIn()` reads the file in a child process:

- a file over 4 MiB (`IsolatedSessionLog::MAX_BYTES`) is `too_large` and no child starts: the whole file is refused, so every count of that build is lost, not only its tail. One filtered record takes a few hundred bytes, so this takes thousands of messages;
- the child is the PHP executable Symfony's `PhpExecutableFinder` finds, run with `-d memory_limit=64M -r`, loading only the application's autoloader (no kernel, no `.env` file) and calling `Domain/SessionLog::usageIn()` on the file, which it gets on standard input;
- every variable of the orchestrator's environment is unset for it, because that environment holds the credentials;
- it is stopped after 5 seconds (`IsolatedSessionLog::SECONDS`);
- `SessionLog` walks the file one line at a time, so a file of millions of short lines stays within the memory limit; a line over 1 MiB (`SessionLog::MAX_LINE_BYTES`) makes it `line_too_long`, and a line nested deeper than 16 levels is skipped.

The child prints one JSON line. `Domain/SessionUsage::fromAnswer()` checks it like any untrusted text: only `read` with valid counts, `not_reported`, `malformed` or `line_too_long` count; anything else, a child that fails, runs out of memory, is stopped or cannot start is `reader_failed`.

## Where it goes

`RunBuildJob` reads `usage.log` (`RunBuildJob::USAGE`) for every job the runner ran, whatever the verdict, and puts the result on `BuildJobOutcome::$usage` as a `SessionUsage`: the `UsageReading` and, when read, the `BuildUsage` counts. A job without a `usage.log` is `not_reported`; usage records in `build.log` are not counted. A job whose output the runner refused carries none (null), because nothing was read.

`BuildTask` writes it into the `usage` key of the build job step's `build_step_ended` row (`EndedStep::ofBuildJob()`, also for the `asked` row `ParkedTasks::park()` writes): `reading` and the four counts, null when not read. Every other row, and the row of a job that never ran or whose end failed, holds `usage: null`. Nothing reads the key yet; the watch of a running build (#3965) will count it into the per-task total.

## The console door

`php bin/console intakt:build:usage <log>` (`UseCase/ReadBuildUsage/ReadBuildUsageCommand`) reads a kept `usage.log`, or any file of the CLI's stream, the same way. A link, a folder, a named pipe or another file that is not regular is refused without being read. The command checks the path, opens it without waiting (so a named pipe put in its place never holds the command), and reads it only when the opened file is the one it checked (same device and inode, a regular file), so a path swapped for a link or a pipe after the check is refused as "could not be read, or was replaced after it was checked". It reads at most 4 MiB and one byte from that handle, so a file that grows after the check never reaches memory whole; the extra byte makes it `too_large`. It prints `reading read`, one `<count name> <number>` line per count and `total <sum>`, and exits with 0; otherwise it prints `usage not read: <reading>` (or why the file was not read) and exits with 1.
