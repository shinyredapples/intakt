# Branch push

The orchestrator signs the commits of an accepted hand-back with its own key, pushes the branch without force and opens or updates the pull request as the forge App with the builder's text. The use case is `Core/Git/UseCase/PushBranch/PushBranch`; other modules call it through `Core/Git/Contract/BranchPush::push(BranchPushRequest)` (marked `#[NoDiscard]` on the interface and on `PushBranch::push`, because PHP reports a discarded result only for the method that runs). `Core/Build`'s `PushStep` (see [Build task](build-task.md#the-push-step)) calls it, and `intakt:build:task` runs that step last; the build lane (T56) will call the same use case later.

`BranchPushRequest` holds the project, the bare repository that holds the accepted head (the project's [mirror](mirror.md)), the remote's address, the task's branch, the `AcceptedHandBack` ([hand-back checks](hand-back.md)) and the builder's `ChangeText` (title and body). The result is a `PushedBranch` (the signed head and the `ChangeId` of the pull request), `MainConflicts` (the conflicting paths: nothing was pushed; `intakt:build:task` records a failed `push` step and ends the run, and sending the branch back to the builder as a merge-main rework is a later task) or `RefusedPush` (the remote refused the push, see steps 5 and 6: nothing was pushed, and the outcome is recorded). A push that cannot go on is a `ReportableFailure`: `BranchNotPushed` (the reason names no remote address, also when a call was stopped instead of exiting, see [A call that does not finish](#a-call-that-does-not-finish)) or `UnsignedCommitRefused`.

## Steps

1. **One push at a time.** A lock per project and branch is tried without waiting; a busy lock is `BranchNotPushed` ("another push of this branch is running"), and the caller tries again later. The [restore of an archived head](branch-cleanup.md#restore) takes the same lock (`PushLockName`), so the two never push one branch together. A failure of the lock store (any Symfony Lock exception, while acquiring or releasing) is `BranchNotPushed` too ("the lock store failed: ..."), with the store's exception as `previous`, so no Lock exception leaves the `BranchPush` contract. The lock is created with `autoRelease: false` and released only by `PushBranch`, because Symfony's destructor would try a failed release again and throw its own exception over `BranchNotPushed`. A failed release is tried once more at once, so a store back after a short outage frees the branch then; when the second try fails too, the lock stays held until its time to live (300 seconds) ends, and calls in that time get "another push of this branch is running". A release that fails twice after the push landed is reported as not pushed as well; the next call finds the recorded push at the remote tip and returns `PushedBranch` without pushing or asking the forge again. When the push itself failed (any exception of steps 2 to 6), a failed release is not reported: the caller gets the push's own failure. Tests: `PushBranchTest::testALockStoreThatFailsToSaveIsReportedAsNotPushedAndNothingIsPushedOrRecorded`, `testALockStoreThatFailsToReleaseAfterThePushIsReportedAsNotPushed`, `testALockStoreThatFailsToReleaseAndStillHoldsTheLockIsReportedAsNotPushed`, `testALockStoreThatFailsToReleaseAndToTellWhetherTheLockIsHeldIsReportedAsNotPushed`, `testALockStoreWhoseReleaseFailsOnceReleasesTheBranchSoTheNextCallReadsThePush`, `testAFailureDuringThePushIsReportedInsteadOfAFailedLockRelease` and `testAPushWhoseLockReleaseFailedIsReportedPushedByTheNextCallWithoutPushingAgain`. Holding the lock, `PushBranch` lists the repository's address rewrites and remote sections in one call (`BranchGit::addressEntries()`: `git config --null --get-regexp '^(url\..*\.(push)?insteadof|remote\..*)$'`, includes followed). When a `url.<base>.insteadOf` or `url.<base>.pushInsteadOf` value is a prefix of the remote (an empty one is a prefix of every remote, as git applies it to every URL), or when any `remote.<remote>.*` key exists for the exact remote string (git push then takes the string as that remote's name and pushes to its `url` or `pushurl`; a section whose name only starts with the remote string is another remote), the push is refused with `BranchNotPushed` before anything is read from the remote, recorded or pushed, and the forge is not called, because git would read or push another address while the ownership check and the pull request write use the configured repository. The message does not name the remote, because it can hold a credential. A change to the mirror's config between this check and the push is out of scope: the mirror is Intakt's own repository and the check runs under the push lock, so a writer that can change its config then can change its refs and hooks as well. Tests: `PushBranchTest::testARemoteTheRepositorysConfigRewritesToAnotherRepositoryIsNeitherReadNorRecordedNorPushed`, `testARewriteOfAnotherAddressDoesNotStopThePush`, `testARemoteNamedLikeARemoteSectionOfTheRepositorysConfigIsNeitherRecordedNorPushedToEitherRepository` and `testARemoteSectionWhoseNameOnlyStartsWithTheRemoteDoesNotStopThePush`.
2. **Sign.** Each new commit (`rev-list --reverse --topo-order <head> --not <base> <main>`) is rebuilt with its parents replaced by the rebuilt ones and its signature header (`gpgsig`, or `gpgsig-sha256` in a SHA-256 repository) replaced by the orchestrator's SSH signature over the commit text, then written with `hash-object -w`. Tree, author, committer, dates and message are kept, and an ed25519 signature is deterministic, so a retry after a crash produces the same ids. The signing key must therefore be an ed25519 key: any other type (an ECDSA signature takes a fresh random nonce each time) is refused before it signs, with `BranchNotPushed`. Commits already on the pushed branch (the `base`) and main's own commits are not signed again. `ssh-keygen -Y sign` signs with the private key at the container parameter `intakt.git.signing_key` (`GitServices::SIGNING_KEY`, `var/data/keys/signing_key` under the project directory, which is `/app/var/data/keys/signing_key` in the image and so on the volume mounted at `/app/var/data`; never mounted into a job); signing is not done through git's own configuration, which `HardenedGit` switches off for good reason.
3. **Verify.** Every commit of `<head> --not <main>` must carry a signature that `ssh-keygen -Y verify` accepts against an allowed-signers file holding the orchestrator's public key alone (namespace `git`). A commit without a signature, signed by another key or changed after signing is `UnsignedCommitRefused`, and nothing is pushed.
4. **Test-merge.** The remote branch is read (`ls-remote`) on every call. Git matches the pattern `refs/heads/<branch>` against the end of every ref name, so a ref such as `refs/heads/a/refs/heads/<branch>` is listed too: only the line whose ref is exactly `refs/heads/<branch>` counts, and without one the branch is taken as not there. The branch is read also for a signed head that is already recorded as pushed, because the ledger knows nothing of a later head or of another writer that moved the branch since. Unless this signed head is already recorded as pushed or already is the remote branch's tip (a crash after the push left only its record missing, and a main that conflicts since cannot take the push back), `git merge-tree --write-tree --name-only --no-messages -z <main> <head>` runs in the repository: a clean result goes on, a conflict returns `MainConflicts` with the paths, and any other failure is `BranchNotPushed`. The paths are read NUL-delimited (`-z`), so each is the file's name byte for byte, also with a letter outside ASCII, a double quote or a line break in it (without `-z` git prints such a name as a quoted string). The merge writes objects only, never a ref or a work tree.
5. **Push.** `PushBranch` itself does not compare the remote with the forge's repository (it only refuses a remote the repository's config rewrites, step 1); `intakt:build:task` does it first (`PushRemoteCheck`, see [Build task](build-task.md)), so the pre-push ownership check and the pull request write look at the repository the push reaches. A signed head recorded as pushed (`branch_pushed`) is not pushed again. When the remote branch read in step 4 is no longer that head (a later head was pushed, another writer moved the branch, or the branch is gone), the call is refused with `BranchNotPushed` ("the remote branch `<branch>` moved since this head was pushed") before the pull request step: no `change_intended` is appended and the forge is not called, so a late retry of an earlier head neither replaces the pull request text of the head that followed it nor comes back as a `PushedBranch`. The lock of step 1 is held from that read to the pull request write. For a signed head not recorded as pushed, once the test-merge found no conflict, `ChangeOpening::refuseForeignChange(ProposedChange)` asks the forge first whether the branch has an open pull request that another account opened ([The pull request](#the-pull-request)); a refusal is `ForgeWriteFailed`, thrown before `push_intended` is appended and before `git push` runs, so nothing is recorded or pushed. A project without a `github` entry in its watch section now fails here too, in `refuseForeignChange`, before anything is pushed. When the remote branch already is the signed head, nothing is pushed. When it is neither the signed head nor the `base` the hand-back was checked against (null for a branch not pushed yet), the branch moved and the push is refused. Otherwise `git push <remote> <head>:refs/heads/<branch>` runs: never `+`, never `--force`, never retried (`NetworkGit` is for reads), so git itself also refuses anything that is not a fast-forward. When `git push` exits with any code but 0 (the remote refused the update, for example a [local git forge](forge-contract.md) repository whose work tree has the branch checked out), the result is `RefusedPush` with the fixed reason `the remote refused the push of <branch> (git push exited with <n>)`: git's error output is never read, because it may repeat the remote's address. The pull request is not written then, and no `change_intended` is appended; the forge has already been asked once, by the look-up of `refuseForeignChange()`. The push is not tried again within the call; the next call reads the remote branch as in step 4 and pushes again when it is still where the hand-back was checked. A `git push` that is stopped instead of exiting stays `BranchNotPushed` (see [A call that does not finish](#a-call-that-does-not-finish)).
6. **Record.** Before the push the ledger gets `push_intended` (`project`, `branch`, `head`: the SHA the push intends to produce); after it `branch_pushed`, or `push_refused` (the same three keys and `reason`, the text of `RefusedPush`) when `git push` failed, in which case a retry appends no second `push_intended`; before the forge is asked to open or update the pull request `change_intended` (the same three keys and nothing of the text); after the pull request `change_opened` (also `change`, `text_digest`: a SHA-256 over the title's length, the title and the body, never the text itself, and `opening`: `created` when the forge created the pull request or the open one was created by Intakt's own App; `updated`, for an open one someone else opened, is what the GitHub opener answered before it refused such pull requests, so only older lines carry it, see [Pull requests handed to Intakt](handed-to-intakt.md)). A step whose record exists for this project, branch and head is not done again (another project's record of the same branch and head counts for nothing, because projects can share history and branch names), and a step whose record is missing is checked against the outside first (the remote tip, the forge's open pull request), so a crash at any point leaves nothing to repeat and nothing to undo. The record of the push stands only while the remote branch still is that head: the remote tip read on every call decides (step 5), not the ledger alone. A ledger that refuses a record stops the push with `BranchNotPushed`; when it refuses `change_intended`, the forge is not called.

   The pull request step also depends on the text: the forge is skipped only when the last record of this project, branch and head among `change_intended` and `change_opened`, in ledger order (`Ledger::readInOrder()`), is a `change_opened` that carries the digest of the text at hand. A rework that corrects only the title or the body and keeps the commits therefore calls `openOrUpdate` again, which updates the open pull request, and appends another `change_intended` and `change_opened`. The last record decides, not the first, so a text that goes back to an earlier wording reaches the forge again; a record without a digest counts for no text, and neither does one without a known `opening` (`created` or `updated`, a line written before openings were recorded), so a retry of the same head and text asks the forge again and records how it got there ([Pull requests handed to Intakt](handed-to-intakt.md)). A `change_intended` that no `change_opened` follows marks a write whose outcome the ledger never learned (the forge failed, the record of the pull request was refused, or the process died in between): no earlier `change_opened` counts then, so the next push calls the forge with its own text, whether that is the unrecorded correction again or the text recorded before it. Every push that reaches the forge call appends its own `change_intended`, also a retry after a failed call.

## A call that does not finish

Every `git` call of the push goes through one step of `BranchGit`, and every `ssh-keygen` call of `SigningKey` (public-key extraction, signing and verification) through the same `run()` of `GuardedRun`, a stateless service injected into both. A `git` call is limited to 600 seconds and an `ssh-keygen` call to 60 (each constructor's `timeoutSeconds`, which the tests lower). Symfony Process throws for a call that hits its limit, is killed by a signal or cannot start; each becomes `BranchNotPushed` with one of three fixed reasons, where `<program>` is `git <command>` (`git push`, `git ls-remote`, `git merge-tree` and so on) or `ssh-keygen`:

- `<program> timed out after <n> seconds`
- `<program> was killed by signal <n>`
- `<program> could not start`

The message of the Process exception is never used and the exception is never chained as `previous`, because it holds the whole command line, and with it a credential in the remote's address or the signing key's file. `HardenedGit` asks git for the repository's object format before each call; when that question is stopped the same way, the reason is `git <command> could not be prepared, because the look at its repository was stopped or found no bare repository`, again without the exception; a repository whose config names a work tree (`core.worktree` beside `core.bare = false`) is refused by the bare call, so the push ends with `BranchNotPushed`. A stopped `ssh-keygen -Y verify` stops the push with `BranchNotPushed` and is not read as a signature that does not verify. Nothing is retried: after a stopped `push` the `push_intended` record stays, and the next call reads the remote branch first (step 5), so it pushes only when the stopped push did not land. Tests: `BranchGitTest` and `SigningKeyTest` (a `git` or an `ssh-keygen` first on `PATH` that is killed or hangs on one argument, `ProgramOnPath`), and `PushBranchTest::testAPushKilledByASignalIsReportedAsNotPushedAndRecordsNoPush` and `testAPushThatWasKilledIsPushedByTheNextCall`.

## Tests with the local git forge

`PushToTheLocalGitForgeTest` pushes to a repository as the local git forge serves it (a clone with its work tree on main) and reads the result back through `LocalGitForge`: a branch that passes is pushed and every commit verifies against the orchestrator's key; a forge whose work tree has the task branch checked out refuses the push, which returns `RefusedPush`, records `push_refused` after `push_intended`, asks the forge for no pull request, and is pushed by the next call once the forge's work tree is back on main; a forge whose `pre-receive` hook refuses the push and prints the forge's path gives `RefusedPush` with the same fixed reason, which never carries the hook's output; a ledger that refuses `push_refused` stops the push with `BranchNotPushed`.

## The pull request

`Plugin/Forge/Contract/ChangeOpening` has two methods, both taking a `ProposedChange` (the project, the branch, the base branch (main) and the `ChangeText`). `refuseForeignChange()` returns nothing and throws `ForgeWriteFailed` when the branch has an open pull request Intakt must leave alone; `PushBranch` calls it before the push (step 5). `openOrUpdate()` returns an `OpenedChange`: the `ChangeId` and its `Opening`, `Created` when this call created the change (`POST /pulls`) or updated an open one to the same base that Intakt's own App created (`PATCH`, a retry after a push that stopped before its record, or a corrected text). `Opening::Updated` stays in the contract for ledger lines written before foreign pull requests were refused; the GitHub opener no longer answers it.

`Plugin/GitHubForge/Infrastructure/GitHubChangeOpener` implements it as the installation (the App). Both methods resolve the project's repository first (a project without a `github` entry in its watch section is `ForgeWriteFailed`) and run the same look-up, `ownPullRequestsOf()`: `GET /pulls?head=<owner>:<branch>&state=open&per_page=100` lists the branch's open pull requests in one answer, never page by page (offset pages read one after the other can shift when a pull request closes between them and skip one that stays open throughout); an answer with 100 entries, a full page that may not be all of them, and an answer that is not a JSON list, `{}` included, are `ForgeWriteFailed`, and every listed one whose `head.ref` is the branch is checked, whatever its base, never only the first. Its author (`user.login`, which GitHub alone sets) must be this App's own bot account, `<slug>[bot]` without letter case, the slug read from GitHub's `GET /app` with the App's own JWT (`SteeringIdentities::isOwn()`). The look-up is `ForgeWriteFailed`, with nothing written, when any listed pull request of the branch was opened by another account (a person, or another App, also one listed after this App's own pull request or opened to another base), has no `user.login` text (no `user`, or a login that is no text or empty), has an author that cannot be checked (a `GET /app` that fails), or has no readable `head.ref` (missing, no text, or empty: the listing is of this branch, so such an entry may be another account's pull request of it). Only when every match is this App's own does it answer them, by number with their `base.ref`. `openOrUpdate()` then picks the one whose `base.ref` is the change's base and updates only that one, never one opened to another base; when none of them has that base it opens a new one with `POST`, and an own match without a readable `base.ref` before that pick is `ForgeWriteFailed`. `openOrUpdate()` scans the title and body for secrets first (`ChangeTextHoldsSecret`, nothing written), then runs the look-up again, because another account can open a pull request of the branch between the check and the write, and then (GitHub offers no way to tie a listing to a push, so a pull request another account opens between the check and `git push` still moves with the push; the second look-up then refuses the write and leaves its text alone; this window is accepted) `PATCH /pulls/<number>` updates the picked one's title and body, or `POST /pulls` opens one with its `head` and `base`. The `PATCH` sends no `base`, so a pull request someone retargets after the look-up keeps its new base instead of being moved back. The writes are never retried. A call the installation's rate-limit pause refuses (`ForgeRateLimited` from `GitHubCalls`) is `ForgeWriteFailed` with the `ForgeRateLimited` chained as its previous exception, so the time of the reset survives. An answer that is not JSON, a pull request without a number and a refused call are `ForgeWriteFailed` too. The local git forge has no pull requests to open and does not implement it; `tests/Core/Build/LocalChangeOpening` refuses nothing. Tests: `GitHubChangeOpenerTest`, `PushBranchTest::testTheForeignChangeCheckRunsBeforeAnythingIsRecordedOrPushed` and `testABranchWithAForeignOpenPullRequestIsNeitherRecordedNorPushed`, `PushToAStubbedGitHubTest` (a real push through `GitHubChangeOpener` against a scripted GitHub) and `PushToAStubbedGitHubOnSqliteTest` (the same push on the install's Doctrine ledger on SQLite, read back with `intakt:ledger:events`).

## What is not here

The pre-push check job (T51) runs before this use case is called, and `intakt:build:task` calls it as its push step ([Build task](build-task.md)). The workflow approval (T55) is not yet in that command's path: the command pushes without it. The merge itself (T62) and the build lane (T56) come later. GitHub does not show these commits as "Verified": it checks an SSH signature against a signing key registered on a user account whose verified email is the commit's committer email, a GitHub App's account holds no SSH signing keys, and the push keeps the builder's committer. The signatures verify with git itself against the orchestrator's public key (`gpg.ssh.allowedSignersFile` and `git log --format=%G?`), which is what step 3 checks.
