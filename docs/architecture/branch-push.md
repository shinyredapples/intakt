# Branch push

The orchestrator signs the commits of an accepted hand-back with its own key, pushes the branch without force and opens or updates the pull request as the forge App with the builder's text. The use case is `Core/Git/UseCase/PushBranch/PushBranch`; other modules call it through `Core/Git/Contract/BranchPush::push(BranchPushRequest)` (marked `#[NoDiscard]` on the interface and on `PushBranch::push`, because PHP reports a discarded result only for the method that runs). No console command calls it yet: the build lane (T56) will.

`BranchPushRequest` holds the project, the bare repository that holds the accepted head (the project's [mirror](mirror.md)), the remote's address, the task's branch, the `AcceptedHandBack` ([hand-back checks](hand-back.md)) and the builder's `ChangeText` (title and body). The result is a `PushedBranch` (the signed head and the `ChangeId` of the pull request) or `MainConflicts` (the conflicting paths: nothing was pushed, and the caller sends the branch back to the builder as a merge-main rework). A push that cannot go on is a `ReportableFailure`: `BranchNotPushed` (the reason names no remote address) or `UnsignedCommitRefused`.

## Steps

1. **One push at a time.** A lock per project and branch is tried without waiting; a busy lock is `BranchNotPushed` ("another push of this branch is running"), and the caller tries again later.
2. **Sign.** Each new commit (`rev-list --reverse --topo-order <head> --not <base> <main>`) is rebuilt with its parents replaced by the rebuilt ones and its signature header (`gpgsig`, or `gpgsig-sha256` in a SHA-256 repository) replaced by the orchestrator's SSH signature over the commit text, then written with `hash-object -w`. Tree, author, committer, dates and message are kept, and an ed25519 signature is deterministic, so a retry after a crash produces the same ids. The signing key must therefore be an ed25519 key: any other type (an ECDSA signature takes a fresh random nonce each time) is refused before it signs, with `BranchNotPushed`. Commits already on the pushed branch (the `base`) and main's own commits are not signed again. `ssh-keygen -Y sign` signs with the private key at the container parameter `intakt.git.signing_key` (`GitServices::SIGNING_KEY`, `/data/keys/signing_key`, never mounted into a job); signing is not done through git's own configuration, which `HardenedGit` switches off for good reason.
3. **Verify.** Every commit of `<head> --not <main>` must carry a signature that `ssh-keygen -Y verify` accepts against an allowed-signers file holding the orchestrator's public key alone (namespace `git`). A commit without a signature, signed by another key or changed after signing is `UnsignedCommitRefused`, and nothing is pushed.
4. **Test-merge.** Unless this signed head is already recorded as pushed or already is the remote branch's tip (a crash after the push left only its record missing, and a main that conflicts since cannot take the push back), `git merge-tree --write-tree --name-only --no-messages <main> <head>` runs in the repository: a clean result goes on, a conflict returns `MainConflicts` with the paths, and any other failure is `BranchNotPushed`. It writes objects only, never a ref or a work tree.
5. **Push.** The remote branch is read (`ls-remote`). When it already is the signed head, nothing is pushed. When it is neither the signed head nor the `base` the hand-back was checked against (null for a branch not pushed yet), the branch moved and the push is refused. Otherwise `git push <remote> <head>:refs/heads/<branch>` runs: never `+`, never `--force`, never retried (`NetworkGit` is for reads), so git itself also refuses anything that is not a fast-forward.
6. **Record.** Before the push the ledger gets `push_intended` (`project`, `branch`, `head`: the SHA the push intends to produce); after it `branch_pushed`; after the pull request `change_opened` (also `change`, and `text_digest`: a SHA-256 over the title's length, the title and the body, never the text itself). A step whose record exists for this project, branch and head is not done again (another project's record of the same branch and head counts for nothing, because projects can share history and branch names), and a step whose record is missing is checked against the outside first (the remote tip, the forge's open pull request), so a crash at any point of the three leaves nothing to repeat and nothing to undo. A ledger that refuses a record stops the push with `BranchNotPushed`.

   The pull request step also depends on the text: the forge is skipped only when the latest `change_opened` record of this project, branch and head carries the digest of the text at hand. A rework that corrects only the title or the body and keeps the commits therefore calls `openOrUpdate` again, which updates the open pull request, and appends another `change_opened`. The latest record decides, not the first, so a text that goes back to an earlier wording reaches the forge again; a record without a digest counts for no text. A correction that reached the forge while its record was refused is sent again by the retry of the same push. The ledger knows nothing of such an unrecorded correction, so a next push that carries the earlier recorded text instead is skipped as already there.

## The pull request

`Plugin/Forge/Contract/ChangeOpening::openOrUpdate(ProposedChange)` returns the `ChangeId`; a `ProposedChange` is the project, the branch, the base branch (main) and the `ChangeText`. `Plugin/GitHubForge/Infrastructure/GitHubChangeOpener` implements it as the installation (the App): the title and body are scanned for secrets first (`ChangeTextHoldsSecret`, nothing written), then `GET /pulls?head=<owner>:<branch>&state=open` looks for the branch's open pull request, and `PATCH /pulls/<number>` updates its title, body and base, or `POST /pulls` opens one. The writes are never retried. An answer that is not JSON, a pull request without a number, a refused call and a project without a `github` entry in its watch section are `ForgeWriteFailed`. The local git forge has no pull requests to open and does not implement it.

## What is not here

The pre-push check job and the workflow approval (T51, T55) run before this use case is called, and the merge itself (T62) and the build lane that calls the push (T56) come later. GitHub does not show these commits as "Verified": it checks an SSH signature against a signing key registered on a user account whose verified email is the commit's committer email, a GitHub App's account holds no SSH signing keys, and the push keeps the builder's committer. The signatures verify with git itself against the orchestrator's public key (`gpg.ssh.allowedSignersFile` and `git log --format=%G?`), which is what step 3 checks.
