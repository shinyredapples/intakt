# Branch push

The orchestrator signs the commits of an accepted hand-back with its own key, pushes the branch without force and opens or updates the pull request as the forge App with the builder's text. The use case is `Core/Git/UseCase/PushBranch/PushBranch`; other modules call it through `Core/Git/Contract/BranchPush::push(BranchPushRequest)` (marked `#[NoDiscard]`). No console command calls it yet: the build lane (T56) will.

`BranchPushRequest` holds the project, the bare repository that holds the accepted head (the project's [mirror](mirror.md)), the remote's address, the task's branch, the `AcceptedHandBack` ([hand-back checks](hand-back.md)) and the builder's `ChangeText` (title and body). The result is a `PushedBranch` (the signed head and the `ChangeId` of the pull request) or `MainConflicts` (the conflicting paths: nothing was pushed, and the caller sends the branch back to the builder as a merge-main rework). A push that cannot go on is a `ReportableFailure`: `BranchNotPushed` (the reason names no remote address) or `UnsignedCommitRefused`.

## Steps

1. **One push at a time.** A lock per project and branch is tried without waiting; a busy lock is `BranchNotPushed` ("another push of this branch is running"), and the caller tries again later.
2. **Sign.** Each new commit (`rev-list --reverse --topo-order <head> --not <base> <main>`) is rebuilt with its parents replaced by the rebuilt ones and its signature header (`gpgsig`, or `gpgsig-sha256` in a SHA-256 repository) replaced by the orchestrator's SSH signature over the commit text, then written with `hash-object -w`. Tree, author, committer, dates and message are kept, and an ed25519 signature is deterministic, so a retry after a crash produces the same ids. Commits already on the pushed branch (the `base`) and main's own commits are not signed again. `ssh-keygen -Y sign` signs with the private key at the container parameter `intakt.git.signing_key` (`GitServices::SIGNING_KEY`, `/data/keys/signing_key`, never mounted into a job); signing is not done through git's own configuration, which `HardenedGit` switches off for good reason.
3. **Verify.** Every commit of `<head> --not <main>` must carry a signature that `ssh-keygen -Y verify` accepts against an allowed-signers file holding the orchestrator's public key alone (namespace `git`). A commit without a signature, signed by another key or changed after signing is `UnsignedCommitRefused`, and nothing is pushed.
4. **Test-merge.** Unless this signed head is already recorded as pushed, `git merge-tree --write-tree --name-only --no-messages <main> <head>` runs in the repository: a clean result goes on, a conflict returns `MainConflicts` with the paths, and any other failure is `BranchNotPushed`. It writes objects only, never a ref or a work tree.
5. **Push.** The remote branch is read (`ls-remote`). When it already is the signed head, nothing is pushed. When it is neither the signed head nor the `base` the hand-back was checked against (null for a branch not pushed yet), the branch moved and the push is refused. Otherwise `git push <remote> <head>:refs/heads/<branch>` runs: never `+`, never `--force`, never retried (`NetworkGit` is for reads), so git itself also refuses anything that is not a fast-forward.
6. **Record.** Before the push the ledger gets `push_intended` (`branch`, `head`: the SHA the push intends to produce); after it `branch_pushed`; after the pull request `change_opened` (also `change`). A step whose record exists for this branch and head is not done again, and a step whose record is missing is checked against the outside first (the remote tip, the forge's open pull request), so a crash at any point of the three leaves nothing to repeat and nothing to undo. A ledger that refuses a record stops the push with `BranchNotPushed`.

## The pull request

`Plugin/Forge/Contract/ChangeOpening::openOrUpdate(project, branch, base, ChangeText)` returns the `ChangeId`. `Plugin/GitHubForge/Infrastructure/GitHubChangeOpener` implements it as the installation (the App): the title and body are scanned for secrets first (`ChangeTextHoldsSecret`, nothing written), then `GET /pulls?head=<owner>:<branch>&state=open` looks for the branch's open pull request, and `PATCH /pulls/<number>` updates its title, body and base, or `POST /pulls` opens one. The writes are never retried. An answer that is not JSON, a pull request without a number, a refused call and a project without a `github` entry in its watch section are `ForgeWriteFailed`. The local git forge has no pull requests to open and does not implement it.

## What is not here

The pre-push check job and the workflow approval (T51, T55) run before this use case is called, and the merge itself (T62) and the build lane that calls the push (T56) come later. The GitHub "Verified" badge needs the public key registered with the App's account, which only the owner can do.
