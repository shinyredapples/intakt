# Branch push

The orchestrator signs the commits of an accepted hand-back with its own key, pushes the branch without force and opens or updates the pull request as the forge App with the builder's text. The use case is `Core/Git/UseCase/PushBranch/PushBranch`; other modules call it through `Core/Git/Contract/BranchPush::push(BranchPushRequest)` (marked `#[NoDiscard]` on the interface and on `PushBranch::push`, because PHP reports a discarded result only for the method that runs). `Core/Build`'s `PushStep` (see [Build task](build-task.md#the-push-step)) calls it, and `intakt:build:task` runs that step last; the build lane (T56) will call the same use case later.

`BranchPushRequest` holds the project, the bare repository that holds the accepted head (the project's [mirror](mirror.md)), the remote's address, the task's branch, the `AcceptedHandBack` ([hand-back checks](hand-back.md)) and the builder's `ChangeText` (title and body). The result is a `PushedBranch` (the signed head and the `ChangeId` of the pull request), `MainConflicts` (the conflicting paths: nothing was pushed; `intakt:build:task` records a failed `push` step and ends the run, and sending the branch back to the builder as a merge-main rework is a later task) or `RefusedPush` (the remote refused the push, see steps 5 and 6: nothing was pushed, and the outcome is recorded). A push that cannot go on is a `ReportableFailure`: `BranchNotPushed` (the reason names no remote address, also when a call was stopped instead of exiting, see [A call that does not finish](#a-call-that-does-not-finish)) or `UnsignedCommitRefused`.

## Steps

1. **One push at a time.** A lock per project and branch is tried without waiting; a busy lock is `BranchNotPushed` ("another push of this branch is running"), and the caller tries again later.
2. **Sign.** Each new commit (`rev-list --reverse --topo-order <head> --not <base> <main>`) is rebuilt with its parents replaced by the rebuilt ones and its signature header (`gpgsig`, or `gpgsig-sha256` in a SHA-256 repository) replaced by the orchestrator's SSH signature over the commit text, then written with `hash-object -w`. Tree, author, committer, dates and message are kept, and an ed25519 signature is deterministic, so a retry after a crash produces the same ids. The signing key must therefore be an ed25519 key: any other type (an ECDSA signature takes a fresh random nonce each time) is refused before it signs, with `BranchNotPushed`. Commits already on the pushed branch (the `base`) and main's own commits are not signed again. `ssh-keygen -Y sign` signs with the private key at the container parameter `intakt.git.signing_key` (`GitServices::SIGNING_KEY`, `var/data/keys/signing_key` under the project directory, which is `/app/var/data/keys/signing_key` in the image and so on the volume mounted at `/app/var/data`; never mounted into a job); signing is not done through git's own configuration, which `HardenedGit` switches off for good reason.
3. **Verify.** Every commit of `<head> --not <main>` must carry a signature that `ssh-keygen -Y verify` accepts against an allowed-signers file holding the orchestrator's public key alone (namespace `git`). A commit without a signature, signed by another key or changed after signing is `UnsignedCommitRefused`, and nothing is pushed. Then, on every call and before anything is recorded or pushed, `ChangeOpening::refuseForeignChange(project, branch)` asks the forge whether every open pull request of the branch is this App's own (see [The pull request](#the-pull-request)): any pull request of the branch another account opened, or one whose owner cannot be checked, ends the call with `ForgeWriteFailed`, so the remote branch stays where it is and no `push_intended` or `branch_pushed` is appended, because new commits on the branch would move that pull request's head.
4. **Test-merge.** The remote branch is read (`ls-remote`) on every call. Git matches the pattern `refs/heads/<branch>` against the end of every ref name, so a ref such as `refs/heads/a/refs/heads/<branch>` is listed too: only the line whose ref is exactly `refs/heads/<branch>` counts, and without one the branch is taken as not there. The branch is read also for a signed head that is already recorded as pushed, because the ledger knows nothing of a later head or of another writer that moved the branch since. Unless this signed head is already recorded as pushed or already is the remote branch's tip (a crash after the push left only its record missing, and a main that conflicts since cannot take the push back), `git merge-tree --write-tree --name-only --no-messages -z <main> <head>` runs in the repository: a clean result goes on, a conflict returns `MainConflicts` with the paths, and any other failure is `BranchNotPushed`. The paths are read NUL-delimited (`-z`), so each is the file's name byte for byte, also with a letter outside ASCII, a double quote or a line break in it (without `-z` git prints such a name as a quoted string). The merge writes objects only, never a ref or a work tree.
5. **Push.** A signed head recorded as pushed (`branch_pushed`) is not pushed again. When the remote branch read in step 4 is no longer that head (a later head was pushed, another writer moved the branch, or the branch is gone), the call is refused with `BranchNotPushed` ("the remote branch `<branch>` moved since this head was pushed") before the pull request step: no `change_intended` is appended and the forge is not called, so a late retry of an earlier head neither replaces the pull request text of the head that followed it nor comes back as a `PushedBranch`. The lock of step 1 is held from that read to the pull request write. For a signed head not recorded as pushed: when the remote branch already is the signed head, nothing is pushed. When it is neither the signed head nor the `base` the hand-back was checked against (null for a branch not pushed yet), the branch moved and the push is refused. Otherwise `git push <remote> <head>:refs/heads/<branch>` runs: never `+`, never `--force`, never retried (`NetworkGit` is for reads), so git itself also refuses anything that is not a fast-forward. When `git push` exits with any code but 0 (the remote refused the update, for example a [local git forge](forge-contract.md) repository whose work tree has the branch checked out), the result is `RefusedPush` with the fixed reason `the remote refused the push of <branch> (git push exited with <n>)`: git's error output is never read, because it may repeat the remote's address. Nothing reaches the forge then, and no `change_intended` is appended. The push is not tried again within the call; the next call reads the remote branch as in step 4 and pushes again when it is still where the hand-back was checked. A `git push` that is stopped instead of exiting stays `BranchNotPushed` (see [A call that does not finish](#a-call-that-does-not-finish)).
6. **Record.** Before the push the ledger gets `push_intended` (`project`, `branch`, `head`: the SHA the push intends to produce); after it `branch_pushed`, or `push_refused` (the same three keys and `reason`, the text of `RefusedPush`) when `git push` failed, in which case a retry appends no second `push_intended`; before the forge is asked to open or update the pull request `change_intended` (the same three keys and nothing of the text); after the pull request `change_opened` (also `change`, `text_digest`: a SHA-256 over the title's length, the title and the body, never the text itself, and `opening`: `created` when the forge created the pull request or the open one was created by Intakt's own App, `updated` when it updated an open one someone else opened, which the GitHub opener never does because it leaves such a pull request alone ([The pull request](#the-pull-request)), see [Pull requests handed to Intakt](handed-to-intakt.md)). A step whose record exists for this project, branch and head is not done again (another project's record of the same branch and head counts for nothing, because projects can share history and branch names), and a step whose record is missing is checked against the outside first (the remote tip, the forge's open pull request), so a crash at any point leaves nothing to repeat and nothing to undo. The record of the push stands only while the remote branch still is that head: the remote tip read on every call decides (step 5), not the ledger alone. A ledger that refuses a record stops the push with `BranchNotPushed`; when it refuses `change_intended`, the forge is not called.

   The pull request step also depends on the text: the forge is skipped only when the last record of this project, branch and head among `change_intended` and `change_opened`, in ledger order (`Ledger::readInOrder()`), is a `change_opened` that carries the digest of the text at hand. A rework that corrects only the title or the body and keeps the commits therefore calls `openOrUpdate` again, which updates the open pull request, and appends another `change_intended` and `change_opened`. The last record decides, not the first, so a text that goes back to an earlier wording reaches the forge again; a record without a digest counts for no text, and neither does one without a known `opening` (`created` or `updated`, a line written before openings were recorded), so a retry of the same head and text asks the forge again and records how it got there ([Pull requests handed to Intakt](handed-to-intakt.md)). A `change_intended` that no `change_opened` follows marks a write whose outcome the ledger never learned (the forge failed, the record of the pull request was refused, or the process died in between): no earlier `change_opened` counts then, so the next push calls the forge with its own text, whether that is the unrecorded correction again or the text recorded before it. Every push that reaches the forge call appends its own `change_intended`, also a retry after a failed call.

## A call that does not finish

Every `git` call of the push goes through one step of `BranchGit`, and both `ssh-keygen` calls of `SigningKey` through the same `GuardedRun::of()`. A `git` call is limited to 600 seconds and an `ssh-keygen` call to 60 (each constructor's `timeoutSeconds`, which the tests lower). Symfony Process throws for a call that hits its limit, is killed by a signal or cannot start; each becomes `BranchNotPushed` with one of three fixed reasons, where `<program>` is `git <command>` (`git push`, `git ls-remote`, `git merge-tree` and so on) or `ssh-keygen`:

- `<program> timed out after <n> seconds`
- `<program> was killed by signal <n>`
- `<program> could not start`

The message of the Process exception is never used and the exception is never chained as `previous`, because it holds the whole command line, and with it a credential in the remote's address or the signing key's file. `HardenedGit` asks git for the repository's object format before each call; when that question is stopped the same way, the reason is `git <command> could not be prepared, because the look at its repository was stopped or found no bare repository`, again without the exception; a repository whose config names a work tree (`core.worktree` beside `core.bare = false`) is refused by the bare call, so the push ends with `BranchNotPushed`. A stopped `ssh-keygen -Y verify` stops the push with `BranchNotPushed` and is not read as a signature that does not verify. Nothing is retried: after a stopped `push` the `push_intended` record stays, and the next call reads the remote branch first (step 5), so it pushes only when the stopped push did not land. Tests: `BranchGitTest` and `SigningKeyTest` (a `git` or an `ssh-keygen` first on `PATH` that is killed or hangs on one argument, `ProgramOnPath`), and `PushBranchTest::testAPushKilledByASignalIsReportedAsNotPushedAndRecordsNoPush` and `testAPushThatWasKilledIsPushedByTheNextCall`.

## Tests with the local git forge

`PushToTheLocalGitForgeTest` pushes to a repository as the local git forge serves it (a clone with its work tree on main) and reads the result back through `LocalGitForge`: a branch that passes is pushed and every commit verifies against the orchestrator's key; a forge whose work tree has the task branch checked out refuses the push, which returns `RefusedPush`, records `push_refused` after `push_intended`, asks the forge for no pull request, and is pushed by the next call once the forge's work tree is back on main; a forge whose `pre-receive` hook refuses the push and prints the forge's path gives `RefusedPush` with the same fixed reason, which never carries the hook's output; a ledger that refuses `push_refused` stops the push with `BranchNotPushed`.

## The pull request

`Plugin/Forge/Contract/ChangeOpening` has two methods, `refuseForeignChange(project, branch)` and `openOrUpdate(ProposedChange)`. `openOrUpdate` returns an `OpenedChange`: the `ChangeId` and its `Opening`, `Created` when this call created the change (`POST /pulls`) or updated an open one that Intakt's own App created (a retry after a push that stopped before its record), and `Updated` when it updated an open one someone else created; a `ProposedChange` is the project, the branch, the base branch (main) and the `ChangeText`. `Plugin/GitHubForge/Infrastructure/GitHubChangeOpener` implements it as the installation (the App): the title and body are scanned for secrets first (`ChangeTextHoldsSecret`, nothing written), then `GET /pulls?head=<owner>:<branch>&state=open` looks for the branch's open pull request, and `PATCH /pulls/<number>` updates its title, body and base, or `POST /pulls` opens one. An open pull request of the branch is updated only when this App opened it and every other open pull request of the branch too: GitHub allows several open pull requests from one head to different bases, and a push moves the head of each, so every listed pull request whose head is the branch is checked, and the first of them is the one updated, answered as `Created`. Each author (`user.login`, which GitHub alone sets) must be a bot account and this App's own one, `<slug>[bot]` without letter case, the slug read from GitHub's `GET /app` with the App's own JWT (`SteeringIdentities::isOwn()`), so a person named like the App does not count; when any of them was opened by another account, such as the existing loop, another App or a person, the call fails with `ForgeWriteFailed` (`An open pull request of branch <branch> was not opened by this App, so Intakt leaves it alone.`) and nothing is written; one without a `user.login` text (no `user`, a login that is no text, or an empty one) fails with `ForgeWriteFailed` (`GitHub answered an open pull request of branch <branch> without its author's login, so Intakt leaves it alone.`) and nothing is written too, so the GitHub opener never answers `Updated`. Both hold even when this App's own pull request is listed first (`GitHubChangeOpenerTest::testABranchWithAForeignOpenPullRequestToAnotherBaseListedAfterThisAppsOwnIsRefusedBeforeThePush`), and an owner that cannot be checked (the `GET /app` read fails) fails the same way before any write. The ownership check runs before the push: `ChangeOpening::refuseForeignChange(project, branch)` does the same `GET /pulls` look-up and the same check and writes nothing, and `PushBranch` calls it after the signatures verify and before `push_intended` is recorded and `git push` runs, so a branch that carries another account's open pull request gets no new commits (`PushBranchTest::testABranchWhoseOpenPullRequestAnotherAccountOpenedIsNeitherPushedNorRecorded`). `openOrUpdate` checks again, because a pull request can be opened between that first check and the write; a pull request that appears in between is refused at that point, after `push_intended`, `branch_pushed` and `change_intended` are recorded and the branch is pushed. The writes are never retried. An answer that is not JSON, a pull request without a number, a refused call and a call while GitHub's rate limit pauses the installation (`ForgeRateLimited`, turned into `ForgeWriteFailed` with its reset time, `GitHubChangeOpenerTest::testABranchIsRefusedBeforeThePushAsAFailedWriteWhileThePullRequestLookUpIsRateLimited`) are `ForgeWriteFailed`. A project without a `github` entry in its watch section now fails with `ForgeWriteFailed` in `refuseForeignChange`, before anything is recorded or pushed, so its branch is not pushed. The local git forge has no pull requests to open and does not implement it.

## What is not here

The pre-push check job (T51) runs before this use case is called, and `intakt:build:task` calls it as its push step ([Build task](build-task.md)). The workflow approval (T55) is not yet in that command's path: the command pushes without it. The merge itself (T62) and the build lane (T56) come later. GitHub does not show these commits as "Verified": it checks an SSH signature against a signing key registered on a user account whose verified email is the commit's committer email, a GitHub App's account holds no SSH signing keys, and the push keeps the builder's committer. The signatures verify with git itself against the orchestrator's public key (`gpg.ssh.allowedSignersFile` and `git log --format=%G?`), which is what step 3 checks.
