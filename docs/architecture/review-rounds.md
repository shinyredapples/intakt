## Review rounds

### In short

A round runs the reviewers of one panel on one change and keeps its state in the database. Each reviewer is a message on the `async` Messenger transport, which by default waits in the database, so a restarted worker resumes the round. Two state machines track progress: the round moves from collecting to complete to judged, and each reviewer from queued to running to a verdict, failed or blocked. The round completes only when every reviewer is in, in one locked step that also records the verdicts in the change's finding ledger.

Worth knowing:

- A running reviewer is held by its worker for at most one hour before it can be started again.
- After a second stop, a reviewer moves to blocked, so the round goes on without it.
- A message that fails for good blocks its reviewer instead of leaving the round waiting.
- The rounds of one change share a change name and take the next round number in turn.

The rest of this page is the detailed reference.

Plan task T9, part 2 (design: [Reviews](../design/05-architecture/07-reviews.md)). A round runs its reviewers in parallel and keeps its state in the database, so a restarted worker resumes. The two state machines are drawn by hand, with their guards and side effects, in [review-round.dot](review-round.dot) (Graphviz source); the round machine alone, as `bin/console workflow:dump review_round` generates it, is [review-round-machine.dot](review-round-machine.dot), and the reviewer machine, as `bin/console workflow:dump reviewer` generates it, is [reviewer-machine.dot](reviewer-machine.dot).

- **Start:** `UseCase/RunReviewRound/RunReviewRound` (a `Domain/ReviewTarget` of a `Domain/ReviewSubject`, which holds project, checkout directory and task, and the `VerdictIdentity`, see [Verdict identity](forge-contract.md#verdict-identity); the `Panel`; and the `change`, a name the caller chooses, such as the branch, that the rounds of one change share; `ReviewRound` is built from the same `ReviewTarget`) is handled on `command.bus` by `RunReviewRoundHandler`, which opens the round through `RoundOpening`. Through `ReviewRounds` that refuses a path that is no directory and an identity that does not describe the task and panel, takes the next round number of the change and the open findings of its ledger at that moment from its `change_findings` row, keyed by the change address in its canonical form (`Contract\ChangeAddress`: a GitHub pull-request address reduced to `https://github.com/<owner>/<repository>/pull/<number>` and lowercased, any other change name as written, see [One address per pull request](review-flow.md#one-address-per-pull-request)), under a write lock (`StoredFindings` takes it with an `UPDATE` of the row that changes nothing, then reads it with a pessimistic write lock, because on SQLite only a write takes the lock, and a stale snapshot then fails in that statement, where the transaction can start over, not in the ORM flush, which closes the entity manager; for a new change it first inserts the row in a savepoint, after a lookup without a lock because a lock on a missing row is a gap lock in MySQL that makes two such inserts deadlock, and ignores a unique constraint violation, so that two first rounds of one change opened at once both lock the one row and become rounds 1 and 2 instead of the later one rolling back; on SQLite a transaction that read before another round committed cannot write at all, so that one is retried as a whole, see below; `FindingsAcrossRoundsTest` forces that order with a DBAL middleware that lets another round commit the row right after the first lookup, on a WAL database), and stores one `ReviewRound` row (the subject is a Doctrine embeddable, columns `project`, `checkout_root`, `task`; the `Domain/ChangeRound` embeddable adds `change_ref`, `round_number` and `open_findings`, the open findings as JSON, nullable rather than defaulted because DBAL's MySQL platform leaves a default on a text column out of the column declaration, so a declared default would not reach the MySQL schema, and because a round stored before the ledger existed had none; migration `Version20261031150000`) and one `RoundReviewer` row per panel member (`review_round`, `round_reviewer`, migrations `Version20261030120000` and `Version20261031120000`; the ids are UUIDv7 at the clock's time; `ReviewRounds::open()` takes one per panel member, sorts them ascending and then hands them out in panel order, because a UUIDv7 made at an explicit time is not monotonic and a clock that goes back would give a later member an id that sorts first; `ReviewRound::reviewers()` reads the rows ordered by id, so a stored round lists its reviewers in panel order on every engine, `ReviewRoundReviewerOrderTest` and `ReviewerIdOrderTest`), then appends `review_started` to the ledger (JSON: `round`, `project`, `reviewers` as the count, `change` and `number`, the round's number in its change, then `task`, `repository` and `base` only when the round has a change source, and `quorum`, the panel's `QuorumPolicy` value, which `RoundOpening` passes to `RoundLedger::reviewStarted()` so the dashboard can decide the round's outcome) and dispatches one `ReviewWithReviewer` message (only the reviewer id) per reviewer, all in one transaction (`ReviewRounds::inOneTransaction`, the connection's `transactional` with a flush, not `wrapInTransaction`, which would close the entity manager a worker keeps; after a rollback the entity manager is cleared; a DBAL `RetryableException`, such as SQLite's `LockWaitTimeoutException` for a stale snapshot or a deadlock, runs the whole transaction again, at most three attempts, unless a caller's transaction is still open or the failure closed the entity manager (a failed ORM flush, such as a deadlock on MySQL or PostgreSQL), in which case the original failure is rethrown without a retry, never hidden behind `EntityManagerClosed`). With the Doctrine transport the messages are rows on the same connection, so a refused dispatch or a stopped process leaves no round, no ledger event and no message behind, never a round whose reviewers have no message. In the same transaction, right after the ledger event and before the reviewer messages, so that with fewer workers than reviewers it does not wait behind whole reviews, `RoundOpening` dispatches `Review\Contract\RoundOpened` (`round`, `project`) on the command bus, routed to `async` as well, which the dashboard's project filter handles in a worker (see Project filter in [Live updates](live-updates.md)); its queue row goes with the round, so a round that rolled back, also with a caller's enclosing transaction, is never announced. It returns the round id. The ids are UUIDv7 from the `ClockInterface`. Every start of a reviewer (`RoundReviewer::recordStart()`) gives it a new conversation id, a UUIDv7 from the start's moment in the `conversation_id` column (migration `Version20261031130000`), because the conversation store refuses an id that was already started and a reviewer started again after a stopped worker, a rate limit or a refused ledger event begins a new conversation.
- **Transport:** `config/packages/messenger.yaml` routes `ReviewWithReviewer` (and the round's `RoundOpened`, see Start) to `async`, whose DSN is `MESSENGER_TRANSPORT_DSN` (`doctrine://default` in `.env`, so a message waits in the database and survives a restart; `.env.test` uses `in-memory://`). The transport's `auto_setup` is off: its `messenger_messages` table comes from the migration `Version20261031120000` (or `messenger:setup-transports`), never from a first send, because a first send inside a round's transaction would create the table in that transaction and a rollback would take it with it while the transport remembers the setup as done; `schema_filter` keeps the table out of the mapping's diff. `redeliver_timeout` is 5400 seconds, above the one-hour hold on a running reviewer (below), so a message the transport hands out again finds the hold ended. `RunReviewRound` is handled in place. One `messenger:consume async` process handles one message at a time, so n workers review n reviewers at once.
- **Reviewer:** `ReviewWithReviewerHandler` takes the reviewer through `ReviewerLeases::take()`, which clears the entity manager (a worker keeps it between messages, and the stored row is the truth) and decides on the row loaded under a pessimistic write lock, in one transaction with the ledger event (`ReviewerMoves` applies each transition together with the event that reports it, so neither is stored without the other): a `queued` reviewer moves to `running` with `started_at` set to the clock's moment (ledger `reviewer_started`); a finished one is left alone; a `running` one is held by its worker until `started_at` plus `RoundReviewer::REVIEW_CEILING` (one hour), so inside the hold the handler throws `ReviewerStillHeld`, a `RecoverableMessageHandlingException` whose retry delay is the rest of the hold, rounded up to the next whole second (Messenger brings the message back then, not before, and never counts it against the retry limit), and after the hold the worker counts as stopped: the first time the reviewer is started again (`ReviewerMoves::restart()`: `requeue`, then `start` with a new `started_at`, ledger `reviewer_started`, and the `restarts` column of `round_reviewer`, migration `Version20261031130000`, goes up by one); the second time it moves to `blocked` with `the worker stopped twice before the reviewer had a verdict` (ledger `reviewer_blocked`). A `running` row without `started_at` (one that started before migration `Version20261031120000` added the column) has no hold, so `take()` counts its worker as stopped at once, even if that worker is still alive. Only a stopped worker uses the one retry, never a held hold or a rate limit. For a reviewer it took (left `running` by `take()`), the handler first announces the start through `LiveRoundProgress::publishStartOf()` (`RoundUpdates::reviewerStarted()`, then the round's latest `RoundProgress`, whose started and finished counts both come from the round state, see [Live updates](live-updates.md)), then builds the `ReviewBrief` from the round's task, its diff (stored in the `diff` column of `review_round`, set from `ChangeReviewRequest::$diff`, which `intakt:review` fills with the branch's patch) and the open findings stored with the round when it opened (`ReviewRounds::openFindingsOf()`, through `StoredFindings::openFor()`, which reads the round's `open_findings` with the `stored` serializer; none in round one or for a round stored without them) and the round's number (`ReviewBrief::$round`), so every reviewer of a round is told the same open findings whatever other round of the change completes meanwhile, and calls `Vendor::review()` and records the result through `ReviewerLeases`, which loads the row again under the lock and applies the move only while the stored state is still `running` with the attempt the worker took (`RoundReviewer::isSameAttemptAs()` compares the conversation id, which every start makes new; a worker whose reviewer another worker started again after the hold finds another conversation and leaves the row alone): a verdict (ledger `verdict_received`, with the decision, the count of findings and the project's `mode`, `reviewer-for-loop` or `live`, see [Mode per project](capability-tiers.md#mode-per-project), and for a `blocked` verdict Intakt gave its `reason` (`Verdict::blockedReason()`, left out for any other verdict); the verdict is stored as JSON, written by `ReviewerMoves` and read by `StoredVerdicts` through the `stored` serializer; the verdict of a reviewer stopped from the dashboard adds `reviewer_stopped`, see [Dashboard](dashboard.md)) or, when building the request or the vendor call throws any other exception than `ProviderRateLimited`, `VendorAccountBusy` and `VendorAccountOut`, which hand the reviewer back (below), and `NoProviderLeft`, which blocks it (see Substitute), so for example `ProviderFailedTransiently`, `UsageNotRecorded`, a provider's client error or a checkout that is gone, a failure (ledger `reviewer_failed`, with the exception class only, except a `VerdictUnreadable` with a key-safe reason, recorded in words; the handler does not rethrow). The hold is also the review's ceiling: a result recorded at or after `started_at` plus `REVIEW_CEILING` is dropped and the reviewer moves to `failed` with `the reviewer had no result within the review ceiling` (ledger `reviewer_failed`), whether or not another delivery came. A result that arrives after the reviewer was finished by another worker is dropped, so a verdict never overwrites `failed`, `blocked` or another verdict and a complete round never changes. When the vendor call throws `ProviderRateLimited`, the handler hands the reviewer back to `queued` (`ReviewerLeases::handBack()`, only while the stored row is still `running` with the worker's attempt; no ledger event, no restart counted), publishes the round's latest `RoundProgress` (`LiveRoundProgress::publishLatest()`, so the reviewer no longer counts as started) and throws `ReviewerRateLimited`, a `RecoverableMessageHandlingException` whose retry delay is `retryAfterSeconds` in milliseconds, so Messenger brings the message back after the provider's reset; without a reset the delay is null and the retry strategy of `async` decides (one second, doubling, with Messenger's default jitter of a tenth, at most one minute through `max_delay`). `VendorAccountBusy` (see [Vendor](vendor.md)) is handled the same way, with no delay, and so is `VendorAccountOut` (see [Vendor](vendor.md)), for which the handler throws `ReviewerMovesToAnotherAccount` with a delay of zero: the same reviewer starts again on another account of its vendor, in a new conversation, so no catch-up review is owed and no restart is counted. A recoverable exception is always retried, so the message waits as long as the provider limits it, but never more than one minute between two tries without a reset (`tests/Core/Review/UseCase/RunReviewRound/ReviewRetryWaitTest.php` reads the configured strategy). A ledger that refuses the end event raises `ReviewEventNotRecorded`; the move rolls back with it, and `ReviewerLeases` first stores the result again in a new transaction (at most three attempts in all, each loading the row under the lock afresh, so on SQLite it sees what another reviewer committed in between), without calling the reviewer again. When every attempt is refused (or the entity manager closed), the reviewer stays `running` and `ReviewerLeases` throws `ResultNotStored`, an `UnrecoverableMessageHandlingException` that holds the refusal, because a retry of the message would call a reviewer that already answered, and pay for it, again: Messenger does not retry it, and `BlockReviewerOfFailedMessage` (see Failure transport) blocks the reviewer and completes the round. `RunReviewRoundTest` covers a verdict refused once (one vendor call, one `verdict_received`), refused three times (left `running`, not retried, one vendor call also after a redelivery) and the failed message that blocks it; `ConcurrentVerdictStoreTest` lets a second worker on its own connection store its verdict between the first worker's read of its row and its write, on a WAL database, where SQLite refuses the first store with `LockWaitTimeoutException` and the next transaction stores it, with one vendor call per reviewer.
- **Round:** after every message, finished or not, `ReviewRounds::completeWhenEveryReviewerIsIn()` clears the entity manager and, in a transaction holding a pessimistic write lock on the round row, hands the round to `StoredFindings::completeWhenEveryReviewerIsIn()`, which applies `complete` (`RoundTransition::Complete`) when the workflow allows it and in the same step records every stored verdict of the round in the change's finding ledger under the round's number (on the locked `change_findings` row; a failed or blocked reviewer has no verdict and adds nothing), so a round reaches the ledger as one step, and the ids its verdicts name were open in the list stored with the round. That step returns one `ReportedFindings` per reviewer with a verdict (the ledger ids `FindingLedger::recordVerdict()` tracked its findings under, empty for a failed review, and `severities`, each of those ids with the severity this reviewer reported it at, set in `StoredFindings::reportedBy()`, because two reviewers may repeat one tracked finding at different severities), and `ReviewRounds` appends one `reviewer_findings_recorded` row for each (`RoundLedger::reviewerFindingsRecorded()`, payload `Contract\ReviewerFindingsRecorded`: `round`, `reviewer`, `findings`, `severities`, null on a row written before severities were recorded) in the same transaction (#2933, part 1 of #2863), so the dashboard can tell which reviewers reported each act entry; the ids are those of the round's reported findings, which its judge's act list and merges name, also for a round overtaken by a newer one, which leaves the change's stored finding ledger untouched but still appends its own rows (`R<n>-F<m>` ids from `FindingLedger::apartFor()`). A completion that finds the guard closed writes nothing, and a round completed before this change has no such row. Rounds of one change may overlap: a round whose number is lower than the `recorded_round` of the change completes but records nothing in the stored finding ledger (only its `reviewer_findings_recorded` rows), so an older round finishing last cannot close a finding a newer round repeated. The guard `HoldRoundUntilEveryReviewerFinished` (listener on `workflow.review_round.guard.complete`) blocks the move while a reviewer is `queued` or `running`; a round that is already `complete` has no `complete` transition, so a second finisher or a redelivered message does nothing. Whichever reviewer finishes last completes the round.
- **Restart:** the state is in the rows. A message redelivered for a `queued` reviewer runs it; for a finished reviewer it only tries to complete the round (the worker that finished it may have stopped before it did); for a `running` reviewer it waits for the hold to end (`ReviewerStillHeld`) and then, when the reviewer is still `running`, starts it again once and after a second stop moves it to `blocked`, which finishes it, so the round goes on; a worker killed mid-review costs its reviewer at most one hour plus the redelivery per stop.
- **Failure transport:** `config/packages/messenger.yaml` sets `failure_transport: failed`, a second Doctrine transport on the same DSN and table with `queue_name: failed`, and a `retry_strategy` on `async` (two retries, one second, doubling, at most one minute) for exceptions that are not recoverable; its `max_delay` also caps the wait of a recoverable one that names no delay. When a `ReviewWithReviewer` message will not be retried (`WorkerMessageFailedEvent::willRetry()` is false), `UseCase/RunReviewRound/BlockReviewerOfFailedMessage` (a listener whose `#[AsEventListener]` declares `after: SendFailedMessageForRetryListener::class`, which decides `willRetry()`, and `before: SendFailedMessageToFailureTransportListener::class`, which parks the message; it sets no priority, and `FailedMessageListenerOrderTest` reads the resulting order from the container) moves its reviewer to `blocked` through `ReviewerLeases::recordBlocked()` on the locked row (a finished reviewer is left as it is; ledger `reviewer_blocked`, reason `the review message failed for good`) and completes the round when every reviewer is in. When blocking fails for any reason (the ledger refuses the `reviewer_blocked` event with `ReviewEventNotRecorded`, the row is gone and `ReviewerNotFound` is thrown, a database error, a malformed id), the listener catches the `Throwable`, logs it at error level with the reviewer id and the exception, and returns, because Messenger's worker does not catch what a failure listener throws and would stop before parking the message; the reviewer stays as it was and the message is parked in `failed`, where `messenger:failed:retry` can run it again. `blocked` is a finished state (`ReviewerState::isFinished()`), reached by the `block` transition from `queued` or `running`. A `JudgeRound` message that will not be retried leaves its round unjudged, and `intakt:review` waiting on it ends as `blocked` with the reason `the judging failed` ([Review flow](review-flow.md#a-judging-that-failed-for-good)); for a `reviewer-for-loop` project, the `RecordFailedJudging` message of the judging's `DispatchOnFailureStamp` queues the publication of an `error` status for its head ([Publishing the verdict](capability-tiers.md)).
- **Workflow:** the `review_round` state machine is declared by the Workflow attributes of 8.2 on `Infrastructure/ReviewRoundStateMachine`: `#[AsWorkflow]` on the class (name, supported `ReviewRound`, marking store, initial place `collecting`, places from the `RoundState` enum) and one `#[Transition]` on each constant, whose value is a `RoundTransition` case (`complete`: collecting to complete; `judge`: complete to judged). The `reviewer` state machine is declared the same way on `Infrastructure/ReviewerStateMachine` (supported `RoundReviewer`, initial place `queued`, places from the `ReviewerState` enum, constant values from the `ReviewerTransition` enum: `start`: queued to running; `receive`: running to verdict; `fail`: running to failed; `requeue`: running to queued; `block`: queued or running to blocked). A transition of a state machine attribute has one input place, so `block` repeats `#[Transition]` once for each place it leaves, which gives the same two `block` transitions the configuration built before. Neither class uses `WorkflowTrait`, because their callers take the `WorkflowInterface` services `state_machine.review_round` and `state_machine.reviewer`. So the places and transitions have one home, and there is no `config/packages/workflow.php`. Their marking store, `Infrastructure/StateMarkingStore`, reads and writes the `state` column through `HasPlace` (Symfony's method marking store would need a public setter). The entities are in `Domain/`; `ReviewRound` has no readonly properties because the lazy proxy a reviewer holds for its round sets them again, and `ReviewerLeases` loads a row fresh after `clear()` instead of refreshing it for the same reason.
- **Substitute:** a verdict with a substitute is stored with it (`round_reviewer.substitute`, migration `Version20261101170000`; `RoundReviewer::owesCatchUp()`), and `ReviewerMoves::receive()` appends `catch_up_owed` (`substitute` is the provider value; `model` is the model of the tier's first substitute on that provider, as `TierResolver::substitutes()` lists them, left out when the tier names none there or does not resolve) in the same transaction as `verdict_received`; running the catch-up is not built yet. `NoProviderLeft` blocks the reviewer through `ReviewerLeases::recordOutage()` with its message as the reason (ledger `reviewer_blocked`), under the same attempt check as a verdict, and the round completes with it (`CrossProviderSubstituteTest.php` in the same folder).
- **Not yet:** The loop does not start a round yet; `intakt:review` is the only door (see Review command under [Verdict identity](forge-contract.md#verdict-identity)).
- **Tests:** `tests/Core/Review/UseCase/RunReviewRound/RunReviewRoundTest.php` (`persistence` group, SQLite by default) delivers the messages of a round of three in a chosen order (a data provider of four orders, never repetition) and asserts the round stays `collecting` until the last one; it also covers a failed reviewer, a reviewer's `blocked` with findings stored as `changes` (see [Review verdicts](review-verdicts.md)), a redelivery, a restarted worker (new handlers, cleared entity manager), a redelivery inside and after the hold, a verdict that arrives after the ceiling with no other delivery (the reviewer fails) and just inside it (the verdict lands), and a refused end event (stored on a new transaction when refused once; after three refusals the reviewer stays `running`, `ResultNotStored` is not retried and a redelivery does not call the reviewer again), and `RoundOpened` (dispatched once with the round and its project on the reviewers' bus, before any reviewer message; `DoctrineQueueTest.php` shows it queued with the reviewer messages and ahead of them, and gone with a round whose reviewer messages could not all be queued and with an enclosing transaction that rolls back). `DuplicateDeliveryTest.php` runs a second handler on its own connection and entity manager inside the first one's vendor call, with the order forced by the vendor double: inside the hold the round stays `collecting` and the first worker's verdict lands; after the hold the second worker starts the reviewer again, reviews it and the first worker's late verdict is dropped; and while the restarted attempt is still running, the first worker's late verdict leaves it `running` and its late rate limit does not hand it back to `queued`. `KilledWorkerTest.php` stops a worker right after it took its reviewer and moves the clock past the hold: the reviewer is started once more in a new conversation, the second stop makes it `blocked`, and a round whose last open reviewer is blocked is complete. `RateLimitedReviewerTest.php` covers the rate limit (delay from the reset, a new conversation on the retry, null without one, a busy account, and that a rate limit leaves the stopped worker's retry unused), `FailedMessageTest.php` the listener (blocked and round complete, a refused ledger event that is logged instead of thrown, a message that will be retried, a finished reviewer, another message class). `DoctrineQueueTest.php` runs the application's Doctrine transport (the test sets `MESSENGER_TRANSPORT_DSN` before booting): a first send never creates the table, the messages of a round roll back with it, and the queue takes the next round after a rollback. `FindingsAcrossRoundsTest.php` runs rounds of two reviewers on one change with a vendor double that answers per role: round one tells no reviewer of open findings, round two tells both the open findings under their ids, ids stay stable over three rounds while a resolved id closes and a repeat keeps its id, another change sees none, and of two overlapping rounds the older one finishing last cannot close a finding the newer one repeated, while the newer one finishing last is recorded; the two reviewers of one round are told the same open findings when another round of the change completes between them, whether that round is newer (it records a finding the older round's second reviewer must not see) or older (it resolves a finding the newer round's first reviewer was shown and repeated), and a round stored without open findings is told none; a retryable failure that closed the entity manager surfaces as itself after one attempt.
