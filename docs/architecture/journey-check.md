# Journey check

`bin/journey-check` walks user journeys in a real browser against a running Intakt and reports each one as passed or failed, with the step where it broke and a screenshot where one can be saved. It is a developer check run by hand: `bin/check` does not call it, and it is not the same as `bin/check --journeys` (see [Journeys](journeys.md)), which boots a fresh instance per journey and drives it over HTTP. How to run it is in the [user manual](../reference/user-manual.md#walking-user-journeys-with-the-journey-check).

## The runner

The script is Node.js (CommonJS) beside `bin/ui-check` and follows its contract: Playwright comes from `require('playwright')` on `NODE_PATH`, and `CHROME_PATH` names a Chrome or Chromium to launch in place of Playwright's own. It adds no PHP or npm dependency. `main(argv)` reads as its steps:

1. `parseAddress` parses the only argument with `new URL` (after `URL.canParse`), refuses anything but `http:` and `https:`, and clears `username`, `password`, `search` and `hash`, so a route appended to the address never lands in a query or fragment. Only that address is used from then on, for the requests, the browser and every line of output, so a user name or password given in the address never shows. A missing or unparsable address stops the check without echoing its text.
2. `expectAnswer` fetches `<address>/` with `signal: AbortSignal.timeout(STEP_TIMEOUT_MS)` (10 seconds) and without following redirects. Any HTTP status counts as an answer; a refused connection, or a server that accepts the connection and never answers, stops the check with `nothing answers at <address> within 10 s`.
3. Playwright is loaded and Chromium launched only after that, so the startup errors need no browser.
4. Each journey runs through `runJourney(browser, address, journey, folder, position)`, where `position` is its 1-based place in the run, in a new browser context (fresh cookies and storage), with `STEP_TIMEOUT_MS` as the page's default timeout. The steps run in order; the first one that throws ends the journey, and the first line of its error is kept (Playwright's call log follows on later lines).
5. `report` prints one line per journey and a count; `exitCode` gives 0 when every journey passed and 1 when one failed. Every error that escapes `main` (a startup failure, a missing Playwright, a browser that does not launch) prints `Journey check stopped: <reason>` and ends with exit code 2.

The journeys the check walks are the `JOURNEYS` list in the script, exported with the patterns below so the tests run the same journey.

## Journey 1: First run without a key

Its five steps, by the names the report prints:

| Step | Built from | Passes when |
|---|---|---|
| `open /setup and see the start` | `open('/setup?step=5')`, `seeRole('heading', 'See a real review')` | the last step of the setup wizard, where a fresh dashboard sends its visitor, loads and shows that heading |
| `press the button "Play the demo run"` | `press('button', 'Play the demo run')` | the button of the wizard's last step (`templates/dashboard/_setup_step_5.html.twig`, shown while a recording is ready) exists and is clicked; it posts to `POST /demo`, which redirects to `/demo?play=<id>` |
| `reach /demo and see the demo run` | `arrive('/demo')`, `seeRoleWhileAt('/demo', 'heading', 'The demo run')` | the press led the page to `/demo` on the checked address's origin and the answer there was a success, and the page shows that heading while it is still on `/demo`. The demo page follows the run to its review page (`assets/tour-caption.js`) as soon as the queue worker started it, which can be before the page is looked at: a page that already moved on passes this step without the heading only when it went to a review page, path `/reviews/<round>` (the `SHOW_REVIEW` route of `ShowReviewController`) on the checked address's origin; any other address fails the step with `the page left /demo for <origin and path>, not for a review page on <origin>`. A departure to the review page can end the race before the heading appeared, and the step then passes |
| `wait for the verdict of the demo run` | `seeRoleSince('/demo', 'heading', OUTCOME, VERDICT_TIMEOUT_MS)`, `seeRoleSince('/demo', 'heading', RECORDED_VERDICT)` | a visible heading matches `OUTCOME` within 180 seconds, then a visible heading is exactly `RECORDED_VERDICT` within the step timeout, and at the end of each wait the page is on a review page; from the arrival at `/demo` on, it was only on `/demo` and one review page of the checked address |
| `see the recorded finding on the review page` | `seeRoleSince('/demo', 'link', RECORDED_FINDING)` | a visible link's accessible name matches `RECORDED_FINDING` and the page is on the review page; from the arrival at `/demo` to the end of the journey, it was only on `/demo` and one review page of the checked address |

`OUTCOME` is `/^(Approved|Changes needed|Blocked: .+|Failed: .+|Checked, but the outcome was not recorded)$/`: every heading `templates/dashboard/_verdict_card.html.twig` can show, so the long wait ends on any verdict, including a judged pass without a recorded outcome, and never on another heading. `RECORDED_VERDICT` is `Changes needed`, the verdict `fixtures/demo/sample-change-review.json` records, so any other verdict fails step 4 within 10 seconds after the long wait ended. `RECORDED_FINDING` is `/^The check changed from amount >= 100 to amount > 100\.(\s|$)/`: the headline of finding F1 of `fixtures/demo/sample-change-review.json` as its row in the review page's to-fix list names it (the code spans lose their backticks, and the place, such as `src/discount.js:3`, follows after a space). It ends with the sentence's own period followed by white space or the end of the name, so a link reading `... to amount > 100.50.` does not match. Playwright ignores `exact` for a pattern, so both are anchored themselves.

The journey plays the demo run, so it needs an install where `/setup?step=5` offers **Play the demo run** (the compose demo with a recording ready), a queue worker that plays it and the Mercure hub for the live updates. After it played, `/setup?step=5` shows no button, and the next check fails at step 2 until `intakt:demo:remove` removes the run.

## Journeys and steps

A journey is `{ name, steps }`, and a step is `{ name, run(page, address) }`. The script exports the step builders, so a journey finds what a person sees and never a CSS class: a redesign keeps the journeys, while a renamed button fails the journey a person would also get stuck in.

| Builder | Step name | What it does |
|---|---|---|
| `open(path)` | `open <path>` | `page.goto(address + path)`; when no page was loaded (`goto` returns no response) the step fails with `no page was loaded for <path>`, and a response that is not a success fails it with `HTTP <status> for <path>` |
| `arrive(path)` | `arrive at <path>` | reads what the page's last `press` recorded and waits up to `STEP_TIMEOUT_MS` until one of the main frame's addresses since that press has the origin and the path of `address + path` and a response for that address with a 2xx status. So a button that leads elsewhere, to the same path on another origin or to a page that answers with an error fails here, even when the wrong page shows what a later step looks for, and a page that left the path again at once still passes. Its failure reads `the press did not lead to <path> with a success status within 10 s; it led to <origin and path> (HTTP <status>), then ...` (`no answer seen` in place of the status when no response for that address was seen, `no other address` when the page went nowhere); without a `press` before it, it fails with `no press came before the arrival at <path>` |
| `press(role, name)` | `press the <role> "<name>"` | starts recording before the click (`page.on('framenavigated')` for each address the main frame takes, with or without loading a new document, and `page.on('response')` for the status of each response to the main frame's requests, both without the fragment; a status of 400 or more kept for an address is never replaced, as the page's own fetch of that address answers for the main frame too), replacing the record of the page's earlier press, then `page.getByRole(role, { name, exact: true }).click()` |
| `see(text)` | `see "<text>"` | `page.getByText(text, { exact: true }).filter({ visible: true }).first().waitFor()`: waits for the first visible exact match, so a hidden match earlier in the page is skipped |
| `seeRole(role, name, timeout)` | `see the <role> "<name>"`, or `see the <role> matching <pattern>` for a pattern | `page.getByRole(role, { name, exact: true }).filter({ visible: true }).first().waitFor({ timeout })`, with `STEP_TIMEOUT_MS` when no timeout is given |
| `seeRoleWhileAt(path, role, name)` | `see the <role> "<name>" while at <path>` | when the page is at the origin and path of `address + path`, `seeRole(role, name)` races `page.waitForURL` (with `waitUntil: 'commit'`) for an address that is not there, and fails when the wait for the role loses; every address the page has been at since it reached that path must then be that path or a review page, otherwise the step fails naming only the origin and path of the first one that is neither. Those addresses are every one the press's trail holds from the first arrival at the path on (`addressesSince`), the address `waitForURL` saw and the page's own address, so a page that passed a review page and moved on to another page before this step looked fails too. A review page (`isReviewPage`) has the origin of `address` and the path `<address path>/reviews/<one segment>`, and the segment is judged after one `decodeURIComponent`, as the dashboard's router decodes the path before it matches: it must not be empty or hold a `/`, so `/reviews/r1%2Frecord` (the full record to the router) is refused and `/reviews/r1%252Frecord` (one segment to the router) is accepted, and a segment that cannot be decoded is refused. All review pages must be of one round (the decoded segment), otherwise the step fails with `the page went from the review page <origin and path> to the review page <origin and path> of another round` |
| `seeRoleSince(path, role, name, timeout)` | `see the <role> "<name>" on the review page reached from <path>` (a pattern as in `seeRole`) | `seeRole(role, name, timeout)`, and once it passed, the same address check as `seeRoleWhileAt` (`expectReviewPagesSince`, shared by both): every address the press's trail holds from the first arrival at the path on, and the page's own address, must be that path or a review page; the page's own address must be a review page, or the step fails with `the page shows it at <origin and path>, not on a review page` |
| `named(name, ...steps)` | `<name>` | runs the given steps in order as one step, so the report names the step a person would name; the first line of the inner step's error is kept |

`exact: true` keeps `press('button', 'Start')` from matching a button named "Start review".

## Output

The screenshots of one run go to `var/journey-check/<run>/`, where `<run>` is the run's start in UTC as `toISOString()` with `:` and `.` replaced by `-` followed by `-` and eight random hex digits (for example `2026-11-24T09-05-07-012Z-1a2b3c4d`). The random suffix keeps runs that start in the same millisecond apart in practice; nothing checks that the folder is new. `screenshotFile(folder, position, name)` names the file: the journey's position in the run, zero-padded to two digits, then `-` and the journey's name in lower case with every other run of characters turned into `-` (`01-start-a-review.png`), so two journeys whose names reduce to the same text (`Read a verdict` and `Read a verdict!`) still get their own screenshot. The folder is made only when a journey fails, so a passing run leaves none. When the folder cannot be created or `page.screenshot` fails, the journey keeps its failed step and exit code 1, and the report says `no screenshot: <reason>` instead of the path.

```
passed <journey>
failed <journey> at step "<step>": <first line of the error>
  screenshot: var/journey-check/<run>/<position>-<journey>.png
Journey check: <n> journeys, <passed> passed, <failed> failed.
```

## Tests

- `tests/Core/Dashboard/UseCase/journey-check.test.mjs` runs without a browser: the address parsing and its redaction, the startup deadline against a `node:http` server on port 7781 that never answers, the exit code 2 cases through the script itself, the run's name, the screenshot names of two journeys whose names reduce to the same text, the report, and a failed journey whose folder cannot be created or whose page cannot take a screenshot (a stand-in browser), `OUTCOME` against every verdict heading and against headings that only start like one, `RECORDED_FINDING` against the finding's sentence and against `... to amount > 100.50.`, and journey 1's name and step names.
- `tests/Core/Dashboard/UseCase/journey-check.browser.mjs` runs in Chromium, with its pages answered by Playwright's routing on each context the runner opens. A trivial journey proves the runner in four tests: a passing journey, a renamed button that fails its step with a screenshot, a fresh page for each journey, and a page where a hidden copy of the text comes first and `see` still passes on the visible copy that follows. Journey 1 runs against stand-in pages for `/setup`, `/demo` and a review page whose verdict and finding arrive after the page loads (every origin answers with the same pages), in twenty-five tests: it passes; it passes when the verdict arrives after more than a click's wait; it passes when `/demo` follows to the review in an inline script with no timer, before its heading; it passes when the button fetches `/demo` and pushes its address, as Turbo does, and the page follows at once; a renamed **Play the demo run** button on `/setup` fails it at `press the button "Play the demo run"` with `01-first-run-without-a-key.png`; a button that leads to another page than `/demo` fails it at step 3; a button that leads to `/demo` on another origin fails it at step 3; a `/demo` with no heading that leaves at once for `/elsewhere`, which shows the recorded verdict and finding, fails it at step 3; a `/demo` that leaves at once for `/reviews/r1` on another origin, or for `/reviews/r1/record`, fails it at step 3; a `/demo` that leaves at once for `/reviews/r1%2Frecord`, or for `/reviews/r1%E0%A4%A` (which cannot be decoded), fails it at step 3, while one that leaves for `/reviews/r1%252Frecord` passes; a `/demo` that went to `/elsewhere` and from there to `/reviews/r1` before the press returned fails it at step 3 naming `/elsewhere`; a `/demo` that went to `/reviews/r1` and from there to `/elsewhere`, which shows the recorded verdict and finding, before the press returned fails it at step 3 naming `/elsewhere`; a review page that leaves for `/elsewhere` after step 3 passed, and one that leaves after it showed the verdict, fail it at step 4 and at step 5 naming `/elsewhere`; a review page that leaves for another round after step 3 passed fails it at step 4; a `/demo` that shows the verdict and the finding itself and never follows fails it at step 4; a `/demo` that answers HTTP 500 and then fetches its own address with HTTP 200 fails it at step 3 naming HTTP 500; a `/demo` that stays and does not show its heading fails it at step 3; a missing `/demo` (404) fails it at step 3; the verdict "Approved" fails it at step 4; the heading "Checked, but the outcome was not recorded" ends the verdict wait and fails step 4 within two clicks' waits, far below 180 seconds; and a finding link reading `... to amount > 100.50.` fails it at step 5.

Both run by hand with `node --test` (see [Requirements](requirements.md)).
