# Model choice

Routing rules in the configuration pick the tier a build starts on. This page covers the rules and their reader (parts 1 and 2 of the model-choice task, T60: the default, label and sensitive path rules, and raising the tier after a setback) and part 3 (#1748), which turns the tier into a model and records the choice as a `model_chosen` ledger event.

**Facts.** `Core\Build\Contract\BuildFacts` holds the facts of a build: the tier a `model:` label names (`labelledTier`, null without one), the paths the build touches (`paths`, one `Git\Contract\Paths`) and the `Contract\Setback` of the earlier round (`setback`, null without one). `BuildFacts::fromLabels(Labels, Paths)` (the labels as one `Review\Contract\Labels`) reads a `model:<tier>` label with `Tier::tryFrom`, so a value that names a model or a vendor is ignored, and the last valid label wins. `Setback` has `failed-attempt` (an earlier attempt failed), `blocking-finding` (the round before had a P1) and `stall`; a round without a P1 is no setback, so the caller passes null. `escalation` holds the `Review\Contract\EscalationOutcome` of the review rounds on the head of the change's latest round (null without one), set by `BuildFacts::afterEscalation()`. The loop passes these from what it knows, never from builder output. The class has no field for anything the builder says, so a job cannot choose its own model; a test pins its fields.

**Rules.** `Domain\RoutingRules` holds the default tier, the sensitive path globs and the setbacks to escalate on (`escalateOn`). `Domain\ModelRouting::choose()` returns a `Contract\TierChoice` (tier and `TierReason`): a touched path matching a sensitive glob gives the strong tier (`sensitive-path`) whatever the label says, as the design's [label rules](../design/05-architecture/04-labels.md) require (safety rules beat labels); else a confirmed escalation of a recurring P1 gives the strong tier (`confirmed-escalation`, whatever `escalateOn` lists, see [The escalation review](review-flow.md#the-escalation-review)), also when the label already names strong; a rejected one changes nothing; else a setback listed in `escalateOn` gives the strong tier (`setback`), unless the label already names strong, which keeps reason `label`; else the label's tier (`label`); else the default tier (`default`). Globs are matched by `Review\Contract\PathGlob`, the same matcher the review rules use (see [Capability tiers per project](capability-tiers.md)).

**Configuration.** A project's `build` section (`Infrastructure\BuildRoutingConfiguration`, its own tree because the projects tree of the AI module refuses unknown keys) has `tier` (one of the `Tier` values, default `standard`) and `sensitive_paths` (a list of non-empty UTF-8 globs, default empty) and `escalate_on` (a list of `failed-attempt`, `blocking-finding` and `stall`, default all three; a shorter list turns triggers off); other keys, an unknown tier or setback and a map instead of a list are refused at boot. `config/packages/ai.php` lifts the section out of each project, gives every project the defaults when it has none, and sets the container parameter `BuildServices::ROUTING`. `Infrastructure\ConfiguredBuildRouting` implements `Contract\BuildRouting::tierFor($project, $facts)` over it and throws `BuildRoutingNotConfigured` for an unknown project.

**Door.** `UseCase\ShowBuildTier\ShowBuildTierCommand` (`intakt:build:tier <project> [--label=L ...] [--path=P ...] [--setback=S] [--change=C]`) prints `tier <tier>, reason <reason>` (an unknown `--setback` fails with a message), reads the configuration and, with `--change`, the escalation outcome of the review rounds on the head of that change's latest round (`Review\Contract\ChangeEscalations::outcomeAtLatestHead()`), and calls no model; while an escalation review of those rounds is still queued it fails with `EscalationStillPending`'s message instead of printing a tier. The first-build lane calls `BuildRouting` too: `UseCase\BuildTask\BuildTask` (`intakt:build:task`) asks `tierFor()` with the task's labels and no paths, setback or escalation, because a first build has no earlier round. No rework build calls the routing yet, so no build lane passes `--change`: the escalation outcome reaches a tier only through `intakt:build:tier` and `intakt:build:model`. Tests: `ModelRoutingTest`, `BuildFactsTest`, `BuildRoutingConfigurationTest`, `ConfiguredBuildRoutingTest`, `ShowBuildTierCommandTest`, and `tests/Application/ProjectTiersTest.php` (the container lifts a project's `build` section into `BuildServices::ROUTING` and gives a project without one the defaults).

**Choosing and recording.** `UseCase\ChooseBuildModel\ChooseBuildModel::chooseFor(BuildAttempt, BuildFacts): ChosenModel` asks `BuildRouting::tierFor()` for the tier and reason, resolves the tier to a provider and model with the Ai module's `TierResolver::resolve()` (the project's tier mapping), refuses a provider other than `claude_code` with `RunBuildJob\BuilderNotOnClaudeCode` before it records anything (a build runs the Claude Code CLI, and `RunBuildJob` refuses any other provider too), and appends one `LedgerEventKind::ModelChosen` (`model_chosen`) event whose JSON payload holds `project`, `task`, `attempt`, `tier`, `reason`, `provider` and `model`. A ledger that does not record the event fails the choice with `ModelChoiceNotRecorded`, so a build never runs on a model the ledger does not name. `BuildAttempt` is the project, the task and the attempt number (at least 1); its constructor throws an `InvalidArgumentException` for an empty project or task, a project or task that is not valid UTF-8 (the JSON payload cannot hold it) and an attempt below 1, and `BuildAttempt::refusalOf()` returns the same message without throwing. The inputs are the loop's `BuildFacts` only, and neither `BuildAttempt` nor `BuildFacts` has a field for the builder's output, so a job never picks its own model. `ChooseBuildModelCommand` (`intakt:build:model <project> <task> <attempt> [--label=L ...] [--path=P ...] [--setback=S] [--change=C]`, `--change` read as for `intakt:build:tier`) is its door: it prints `tier <tier>, reason <reason>, provider <provider>, model <model>`, records the event, calls no model, and fails with a message for an unknown setback, an empty project or task, a project or task that is not valid UTF-8, an attempt below 1 (all checked with `refusalOf()` before it builds the attempt, so nothing is recorded), an unconfigured project, a tier its provider cannot serve, a tier mapped to a provider other than `claude_code` or an event the ledger did not record. A rework after a round without a P1 passes no setback and so stays on the cheaper tier. Nothing in the build loop calls it yet. Tests: `ChooseBuildModelTest`, `ChooseBuildModelCommandTest`.
