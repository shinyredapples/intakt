## Live updates

Plan task T21, parts 1 to 3 (design: [Dashboard](../design/05-architecture/13-dashboard.md)). Reviewer progress and round state are published through the Mercure hub as Turbo Stream markup, and the review page listens to them; the stop button and the cancel of a running reviewer are described in [Dashboard](dashboard.md).

- **Port:** `Review\Contract\RoundUpdates` has `toolCalled()`, `textStreamed()`, `answerRead()`, `reviewerAskedAgain()`, `roundChanged()`, `summaryChanged()`, `reviewerStopped()` and `reviewerStarted()`; an implementation never throws. `ReviewWithReviewerHandler` calls `LiveRoundProgress::publishStartOf()`, which calls `reviewerStarted(round, reviewer)`, after `ReviewerLeases::take()` committed the reviewer as running (its first start, or its start again after a stopped worker), before the review; a message for a reviewer that already answered, or that another worker still holds, announces no start. `ReviewerRuns::reporting()` hands the agent's execution to `LiveProgress::reporting()` (which holds the `RoundUpdates`), which registers `onProgress()` on it and forwards a `Progress` whose payload is a `ToolCall` (in plain words with its path and search text, never by the tool's name, as the end of this bullet describes) or a streamed `TextDelta`, for a reviewer whose `ReviewerConversation` names a round, under its `reviewerId` (the `RoundReviewer` id the ledger and the dashboard use; the conversation `id` only when none is set), so the text of a review retried in a new conversation after the output limit stays on its reviewer. The verdict path reads the execution's result (`getResult()->getContent()`, or the verdict part of an answer in several parts), also when the call is streamed, and the strict verdict converter maps a streamed answer too (see Mapping in [Review verdicts](review-verdicts.md)), so with the production subscribers a stream's text deltas reach `LiveProgress`. The deltas are held per model turn in a `StreamedTextBatch` made by `LiveProgress::reporting()` (one per reviewer call): a turn's text reaches `textStreamed()` in one piece only when a tool call follows it (`StreamedTextBatch::release()`, right before that call's `toolCalled()`), because only then may it be narration; a turn whose text opens a JSON object with a key anywhere (`{`, optional whitespace, then `"`: an answer written before a tool call, also inside a fence, among prose with other braces, as a second object, with a syntax error or cut off) is dropped instead and never published, and so is narration that quotes a JSON object (for example `the config reads {"a":1}`), which is accepted because the rule fails closed; the text of the turn that ends the call is the answer, which is never published as text, also when the stream is cut off. The answer reaches the live updates only as read: `ReviewerAgent` hands the `Verdict` that `ReviewerPrompt::verdictIn()` read to `ReviewerRuns::answered()`, which `LiveProgress::answered()` publishes as `answerRead(round, reviewer, ReadAnswer)` for a reviewer in a round. `Review\Contract\ReadAnswer::of()` keeps the verdict and, per finding, a `ReadFinding` with its severity, file, line and title (the whole first line of the finding's text, ending at `\r\n`, `\n` or a bare `\r`, trimmed, since a finding has no title of its own; the live log reads its emphasis marks first and then cuts it to 160 visible characters with `…` as the last of them when it is longer, so a finding written as one long line still reads as a title and a cut never leaves a mark, see [dashboard.md](dashboard.md)); an answer that `verdictIn()` refuses as `VerdictUnreadable` is published as `ReadAnswer::unreadable()` (no verdict and no finding, `wasRead()` false), and the exception, whose message keeps the reason as before, is thrown on unchanged. A stopped reviewer, a lost review server, a reviewer still asking for tools at `ReviewerRuns::MAX_ROUNDS` and a cut stream publish no answer. The checks after reading (malformed tool calls, reserved failure ids from `Verdict::claimedFailureIds()`, unknown ids, a cut approval) still fail or block the review after its read answer was published. `MercureRoundUpdates::answerRead()` publishes the `answer_read` stream (#2252, see [dashboard.md](dashboard.md)) and `BoardHeadlineRoundUpdates` passes it on (#2251, part 1 of #2227). A retry of `SymfonyAiVendor` (see [Review flow](review-flow.md)) keeps the `reviewerId`, so its updates land after what the stopped or cut first try already published (its narration and tool calls); its `ReviewerConversation` carries `askedAgain`, and `LiveProgress::reporting()` then calls `reviewerAskedAgain(round, reviewer, try)` with the retry's conversation id as `try` before any of its progress. The page replaces the first try's text with one line saying the first try gave no usable answer (Publisher below), so the two answers are never read as one; the first try's tool calls stay in the list, because the live log shows what the reviewer did. `LiveProgress::reporting()` passes each tool call to `toolCalled()` in plain words, never by the tool's name: `Review\Contract\ReviewTool` (the reviewer's tools `read_file`, `list_directory` and `search_files`, the one home of their names, which `ReadFileTool::NAME`, `ListDirectoryTool::NAME`, `SearchFilesTool::NAME` and the in-process `#[AsTool]` names take) turns a call into words with `callInWords(ToolCall)`, which reads the call's arguments, after the review server's prefix (`ReviewerMcpToolboxFactory::TOOL_PREFIX`, `review_`) is taken off: `read src/discount.js`, `listed src/` (`listed the repository root` for `.`, `./` or no path), `searched for "discount" in src` (no ` in` part for the root). The arguments come from the model, so one that is not a non-blank string reads as the call without it (`read a file`, `searched the files`), and a tool that is none of the three reads `used a tool`.
- **Streaming and its fallback:** `ReviewerAgent` sets `stream` on the reviewer's call when the model's catalog entry (`getModelCatalog()->getModel()`) has `Capability::OUTPUT_STREAMING`, a fact read from plain code and never from model text. `TierRoutedPlatform` answers with `UnstreamedModelCatalog` for a provider whose `Provider::streams()` is false (the subscription CLIs `claude_code` and `codex`, whose bridges end a streamed run differently), so those calls stay unstreamed. A request the provider refuses (`BadRequestException` or `InvalidRequestException`, which a provider raises before its first delta) before it accepted a stream is repeated once without `stream` on the same stored conversation, and `ReviewerRuns::fellBackToUnstreamed()` hands it to `StreamingFallbacks::record()`, which appends a `streaming_fell_back` ledger event (`round`, `reviewer`, the same reviewer id) for a reviewer of a round; a failed append is logged, not thrown. `StreamAcceptance` watches the execution's `Progress`: once a delta or a tool call arrived, the provider accepted the stream, so a refusal in a later round of tool calls (a context grown too long, for example) stays an exception, is neither repeated nor recorded as a fallback. A stream cut off mid-answer is not a refusal either: it stays `IncompleteStreamException`, which `ReviewerAgent` does not repeat; `SymfonyAiVendor` runs the review once more without streaming instead, unless a provider outage caused the cut (see [Review flow](review-flow.md)). The usage of a streamed call is settled as Mapping describes.
- **Round state:** `RunReviewRound/LiveRoundProgress::publishLatest()` publishes `ReviewRound::progress()` (reviewers started, reviewers finished, reviewers, judged, all counted from the one round state in one pass: a reviewer has started once it is no longer `queued`, so a finished reviewer always counts as started; `LiveRoundProgress::publishStartOf()` publishes it after each reviewer's start and `RunReviewRound/PublishRoundStartHandler`, a second handler of `RoundOpened`, at the round's start, where it publishes the round's latest state (0 started and 0 finished of N, unless a reviewer on the same `async` transport started first); and `RoundProgress::$finished`: each finished reviewer's state by reviewer id as a `Review\Contract\FinishedState` (`verdict`, `failed` or `blocked`, the reviewer's own state, or `stopped`) with `stopped` for the reviewers `Review\Infrastructure\StopRequests::stoppedIn()` names, those whose last answer row in the ledger (`verdict_received`, `reviewer_failed`, `reviewer_blocked`, `reviewer_stopped`) is a `reviewer_stopped`; the whole ledger is read for it only when the round has a `reviewer_stopped` row). `ReviewWithReviewerHandler` calls it after a reviewer is recorded and the round was offered for completion, and after a review that throws handed its reviewer back to the queue (a rate limit, a busy or exhausted account, a refused ledger row), so the started count drops before the message comes back, and `JudgeRound/PublishJudgedRound`, a `RoundJudged` listener, after the judge's record is committed. One worker publishes a round at a time: a Lock per round (`review-round-progress-<round id>`), tried without waiting. The holder reads the progress under it, publishes it when it differs from what it last published, and reads again after the release, taking the lock again when the progress moved. A worker that finds the lock taken leaves its newer state to the holder, so the published states never go backwards ("1 of 2" after "2 of 2", or an unfinished round after "Checked").
- **Publisher:** `Dashboard\Infrastructure\MercureRoundUpdates` renders the template of a `RoundStream` case (`tool_called`, `text_streamed`, `answer_read`, `reviewer_asked_again`, `round_changed`, `round_judged`, `summary_changed`, `reviewer_stopped`; a test asserts each has its `templates/dashboard/stream/*.stream.html.twig` file) (autoescaped, so model text cannot close the `<template>`) and publishes it as a `LiveEvent` on the topic `review/rounds/<round id>` (`MercureRoundUpdates::topicOf()`, the only place that spells it) through `Dashboard\Contract\LiveUpdates` (below); A judged round publishes `round_judged` instead of `round_changed`, as the last update of the topic after its final summary: it includes `round_changed` (started and finished counts, reviewer rows, `Checked.`, the stop emptied, the in-review marker `round-<id>-now-runs` removed so the start of the next round shows) and also replaces the round head with the judged round's outcome chip (muted `Checked` with the title `Judged` when the round could not be read), the Now box's phase with `checked` and its "?" (`GlossaryTerm::Checked`) and its judge element `round-<id>-now-judge` (since #2342, part 2 of #2335, with `templates/dashboard/_now_judge.html.twig`: since #2461 (part 3 of #2450) it opens with the call itself, `p.now-call` holding `ReviewedRound::reviewOutcome()`'s value in `strong.now-outcome`, or "outcome not recorded" for a round without a recorded quorum, and the count of `ReviewedRound::actFindings()` in `span.now-to-fix`, "N findings to fix" or "1 finding to fix", the same findings the Now box's open findings then list, as in "Changes requested, 2 findings to fix.", followed by the muted link "See each finding in the round below." to `#round-<id>`, or "See the round below." when the count to fix is 0). Since #2286 (part 1 of #2242) it also carries the judge's call and the findings: `MercureRoundUpdates` reads the round as the page does (`LedgerReviewPages::reviewOf()`, the round of that id when it is judged, read from the starts and the rows that name that review's rounds and calls, never the whole ledger) and `round_judged` replaces `round-<id>-judged` with `templates/dashboard/_judged_round.html.twig`, the partial the page renders, `round-<id>-verdict` with `_round_verdict.html.twig` (passed `newest` when the round is the last of the review's rounds, so an approved newest round gets the bowing octopus a new load shows and an older round judged late gets none) and the Now box's open findings `round-<id>-now-findings` with that round's act findings, and the judge element states the call and the count of findings to fix and links to the findings below (above). Since #2367 (part 1 of #2198) `MercureRoundUpdates` also passes the `Review` of that read as `review`, and `round_judged` replaces the round's tokens and cost table `round-<id>-tokens` with `templates/dashboard/_round_tokens.html.twig`, the header totals `review-summary-tokens` and `review-summary-cost` with the `tokens` and `cost` macros of `templates/dashboard/_review_summary.html.twig`, and the session summary's `Review so far` cell `round-<id>-review-cost` with the `review_cost` macro of `_session_summary_parts.html.twig`, each the markup the page renders, so these figures show the judge's call too without a reload. A ledger that cannot be read is logged as the warning `The judged round was not read for its live update.` (round and exception) and swallowed; the judged state then goes out without the findings, the tokens and the totals, and the judge paragraph asks for a reload, as it does when the ledger does not hold the round as judged. `round_changed` and `round_judged` carry `outcomes` (the round's `ReviewerOutcome` list), read the same way (a failed read is logged as the warning `The round was not read for its live reviewer rows.` and the cells show the process word as muted text, never `verdict`), so a finished reviewer's cell and Now box line hold the outcome chip a reload renders. `reviewerStarted()` publishes nothing on the round's topic, because the review page places a reviewer from its first tool call or text. `MercureRoundUpdates` is the `RoundUpdates` service (`#[AsAlias]`), decorated by `BoardHeadlineRoundUpdates` (Board headline below). `LiveUpdates` which posts a private `Update` through `HubInterface`, the hub's HTTP endpoint, so Messenger consumers, the console and the web side use one path. `mercure_publish()` is not used. In the test environment the hub `mercure.hub.default` is decorated by the journeys' `RecordingHub`, which records each update to a file instead of posting it (see [Journeys](journeys.md)). A template that fails to render is logged as the warning `A live round update was not rendered.` (round, stream and exception) and nothing is published; a hub failure is logged and swallowed only by `MercureLiveUpdates`: a live update must not change a verdict or a round. Stream targets (`reviewer-<id>-activity`, `reviewer-<id>-text`, `round-<id>-state`, `round-<id>-started` (the Reviewers section's started count, replaced by `round_changed` from `templates/dashboard/_round_started.html.twig` with `RoundProgress::$reviewersStarted`, so it moves with the finished counts of the same update, #2351), `round-<round>-reviewer-<reviewer>-state` and `round-<round>-reviewer-<reviewer>-stop`, the reviewer table's body `round-<id>-reviewers`, the round's findings block `round-<id>-judged` (replaced by `round_judged`), the round's tokens and cost table `round-<id>-tokens` (replaced by `round_judged`), the verdict block `round-<id>-verdict` (the outcome paragraph, replaced by `round_judged` from `templates/dashboard/_round_verdict.html.twig`, the partial the page renders, and empty until the round is judged), the state chip `round-<id>-head-state` in the head of a round that is not judged yet (replaced by `round_judged`; a judged round's heading has none), and in the current state block `round-<id>-now-progress`, `round-<id>-now-phase`, `round-<id>-now-judge` (the owl beside its heading sits outside it, so it stays), `round-<id>-now-findings` (the open findings, replaced by `round_judged` from `templates/dashboard/_now_findings.html.twig` with the judged round's act findings), `round-<round>-now-reviewer-<reviewer>-state`, `round-<id>-now-reviewers` and `round-<id>-now-none`, in the page head `round-<id>-now-stop` (emptied by `round_judged`) and `round-<id>-now-runs` (removed by `round_judged`), the header totals `review-summary-tokens` and `review-summary-cost` (replaced by `round_judged`), and in the pinned session summary `round-<id>-summary-tools`, `round-<id>-summary-cost`, `round-<id>-summary-files`, `round-<id>-summary-findings` and `round-<id>-review-cost` (the `Review so far` cell, replaced by `round_judged`)) are elements of the review page.
- **Dashboard publisher:** `Dashboard\Contract\LiveUpdates::publish()` takes a `Dashboard\Contract\LiveEvent` (a `topic`, refused with `InvalidArgumentException` when empty or blank, and the `turboStream` markup the caller rendered) and never throws; it is the door for every pushed dashboard event, and has four callers today, `MercureRoundUpdates` above, the project filter and the board headline below, and the demo replay, which publishes a recording's captured round updates unchanged at the recorded pace ([The demo recording](demo-recording.md#replaying-the-ledger-events)); the Waiting on you count is planned to use it too. Callers get `Dashboard\Infrastructure\CapturingLiveUpdates`, which hands each event on and, while `INTAKT_LIVE_CAPTURE` names a capture file, also appends it there under one lock held across both steps ([The demo recording](demo-recording.md)). `Dashboard\Infrastructure\MercureLiveUpdates`, the implementation it decorates (`#[AsAlias]`), posts a private `Update` with the event's topic and markup through `HubInterface`. Any `Throwable` from the hub (an error status, a dropped or refused connection, a publisher token the hub cannot use) is logged as the warning `A live dashboard update was not published.` with `topic` and `exception`, and swallowed, so a request or a worker that publishes while the hub is down goes on unchanged.
- **Project filter (#1344, part 1 of #1249):** `RoundOpening::open()` dispatches `Review\Contract\RoundOpened` (`round`, `project`) on the command bus inside the transaction that stores the round, its `review_started` row and its reviewer messages, ahead of the reviewer messages so that with fewer workers than reviewers it does not wait behind whole reviews; `config/packages/messenger.yaml` routes it to the `async` (Doctrine) transport, so the queue row commits or rolls back with the round, also when a caller's enclosing transaction (the watcher's) rolls back after the opening's savepoint was released, and a worker handles it only after the outermost commit, when the ledger holds the new start. `Dashboard\Infrastructure\PublishProjectFilter`, its `#[AsCommandHandler]`, renders `templates/dashboard/stream/project_filter.stream.html.twig` (`PublishProjectFilter::TEMPLATE`) with the names of `FilterProjects::names()`, the same source and order as the filter the shell renders, and publishes it as a `LiveEvent` on `DashboardTopics::SHELL` through `LiveUpdates`. The stream is `<turbo-stream action="update" target="projfilter">` holding All projects (empty value) and one option per project, autoescaped: an `update` of the options, not a `replace` of the select, so the shell script's listeners on `#projfilter` stay bound. No option is marked selected, because the publisher cannot know each tab's choice; the shell script (`base.html.twig`, a `turbo:before-stream-render` listener on the document, since Turbo appends a stream to the document element) wraps the render of a stream whose target is `projfilter`, notes the tab's own choice, lets Turbo update the options, then selects the same project again, or All projects when the new list no longer names it, and filters the rows again. It never stores the choice (only the person's own pick is stored), and does nothing on a page without the select. The listener is bound once per document, not once per Turbo visit, and looks up `#projfilter` when a stream arrives, so it acts on the page currently shown. The stream's options come from the same `dashboard/components/_options.html.twig` as the layout's select. Without a hub or after a dropped connection no stream arrives and the filter works from the page alone. Only a project's first round publishes, since its start is the only row that publishes (a project whose build work comes first is listed at the next page load, because a build step publishes nothing) and every publication resets the select of a listening page: the handler first asks `FilterProjects::isFirstRoundOf(round, project)`, true when the oldest readable `review_started` of the project is this round, and publishes nothing otherwise (a round of a listed project, or one the ledger does not hold). A publication then holds the whole list. Two workers whose rounds open together could otherwise publish out of order and leave an older list, without the newer project, on every open page, so one worker publishes at a time, as for the round state: a Lock (`dashboard-project-filter`, one for the install), tried without waiting. The holder reads the names under it, publishes them when they differ from what it last published, and reads them again after the release, taking the lock again when they changed; a worker that finds the lock taken publishes nothing and leaves its newer list to the holder's re-read. A failure to take the lock, read the projects or render the template is logged as the warning `The project filter was not published.` with `round`, `project` and `exception`, and swallowed, because the round is already committed and an exception would send the `RoundOpened` message back to the queue; a hub that is down is handled by `MercureLiveUpdates` as above. A page loaded later renders the filter from the ledger as before.

- **Hub:** the `Caddyfile` runs FrankenPHP's built-in hub (1.13 and later) in modern mode: an `issuer` block with `publisher` and `subscriber` keys (`MERCURE_JWT_SECRET`, issuer `MERCURE_JWT_ISSUER`), the `bolt` transport (`MERCURE_BOLT_PATH`, `MERCURE_HISTORY_SIZE`, default 1000 events) so a client that reconnects with `Last-Event-ID`, or with `last_event_id` in the address as the dashboard does, receives what it missed, and `encode` applied to every path but `/.well-known/mercure`. `config/packages/mercure.yaml` (`symfony/mercure-bundle`) mints the publisher token from the same secret; `MERCURE_URL`, `MERCURE_PUBLIC_URL`, `MERCURE_JWT_SECRET` (empty in `.env`, set it in `.env.local`) and `MERCURE_JWT_ISSUER` are in `.env`. A subscriber asks with `match=<topic>` and a token that grants `subscribe`, as a bearer header or in the cookie `mercure_access_token` (`cookie_name` in the `Caddyfile` and in `config/packages/mercure.yaml`, prefix-less because the dashboard answers over plain http on localhost, where a `__Secure-` cookie is refused). FrankenPHP takes these values from its own environment and from the files given with `--envfile`, never from Symfony's `.env` loading; the first file that sets a variable wins, so `.env.local` goes before `.env`. The admin API listens on `localhost:2019` only (`CADDY_ADMIN` moves it), where `intakt:server:status` reads it.
- **Shell subscription:** `templates/dashboard/base.html.twig` prints, when the page was rendered with `live`, `importmap('app')` in the `importmap` block and one `turbo_stream_from([<shell topic>, ...topics], true)` at the top of the shell's `.main` column (a direct child of `.shell` would take a cell of its two-column grid and push the rail out of the first one), so every dashboard page (`/projects`, `/reviews`, `/reviews/<round>`, `/trends`) has one private `<turbo-mercure-stream-source>` and one subscriber cookie; a page's own topics come in the `topics` variable, so a page has one stream source. Before it, `mercure(null, {subscribe: listener_grants})` adds `LivePageRendering::listenerGrants()` to the same cookie (the bundle merges the grants of one response): the exact shell topic and the `urlpattern` grant `review/rounds/:round` (from `MercureRoundUpdates::topicOf(':round')`), the same on every page, because every tab shares the cookie (its path is the hub's) and a list page that granted less would leave a review tab, or one Turbo restores from its cache, reconnecting without its round's private updates; the review page's cookie also names its unjudged rounds that have not ended exactly, as `turbo_stream_from` grants what it listens to. The shell topic is `Dashboard\Contract\DashboardTopics::SHELL` (`dashboard/shell`), the only place that spells it, for the publishers of later parts to build their `LiveEvent` with. `Dashboard\Infrastructure\LivePageRendering::render()` renders a page with `live` and its topics and, when that throws (an empty `MERCURE_JWT_SECRET`), logs the warning `A dashboard page was rendered without live updates.` with the template and the exception, puts the flash lines back and renders again with `live` false (no stream source, and no import map except on the Trends page and the components page, which load it either way for the charts' `chart` controller); the page controllers use it. - **Summary updates:** `ReviewedRepository` (the review server) calls `RoundUpdates::summaryChanged()` after each tool call is recorded in `round_tool_call`, also a refused one, because the summary is computed from what is stored and would lag one call behind if announced earlier. `MercureRoundUpdates` recomputes it with `Review\Contract\SessionSummaries::ofRound()` and publishes `stream/summary_changed.stream.html.twig`: four `replace` actions, one per live part of the pinned summary (`round-<id>-summary-tools`, `-cost`, `-files`, `-findings`); `roundChanged()` publishes it too, because the findings and the cost move when a reviewer finishes, and before the round state. `Review so far` is not replaced by it, because the summary knows only the round; the judged round's update replaces it from the whole review (Publisher above). One worker at a time reads and publishes a round's summary, under the Symfony Lock `dashboard-session-summary-<round id>`. A tool call's publisher, and `roundChanged()` for an unjudged round, try it without waiting: a worker that finds it busy returns, and the holder reads the summary again after releasing it and publishes once more if the rendered stream changed, so an older read is never the last one published (`MercureRoundUpdatesTest` forces that order). That second read publishes nothing when the stream is unchanged. A judged round's state must stay the last update of its topic (the journeys' `RoundStreamCheck` refuses any update after it), so `roundChanged()` for a judged round waits for the lock (`acquire(true)`; the install's store is the semaphore store, which the system releases when a holder's process ends), then publishes the final summary and the judged state under it. `SessionSummary::$judged` carries the round's state with the summary, read in the same query, so a tool call's publisher that reads the summary of a judged round, under the lock or in the re-read after its release, publishes nothing: the judge committed before it published, so every read after the judged state sees the flag, and a read taken before it is published before the judge takes the lock. `MercureRoundUpdatesTest` forces both orders with fibers, the judge arriving while a tool call holds the lock (its lock store yields the fiber while it waits) and a tool call arriving while the judge holds it. When the lock cannot be taken, the judged state goes out anyway after the warning below. A round with no stored summary publishes nothing; a summary that cannot be computed or rendered, or a summary lock that cannot be taken or released, is logged as the warning `A live session summary was not published.` and swallowed. File names and finding text are escaped like the other streams. The page never polls for it.
- **Review page (part 2):** `symfony/ux-turbo` with `symfony/asset-mapper` and `symfony/stimulus-bundle` (which Turbo requires). `ShowReviewController` passes the topics of the rounds that are neither judged nor ended (`ReviewedRound::hasEnded()`: blocked with no outcome in time or because the judging failed) from `topicOf()` as the page's `topics` to the shell's single `turbo_stream_from` (above): a `<turbo-mercure-stream-source private>` whose address and subscriber cookie the Mercure bundle makes locally from `MERCURE_JWT_SECRET`, so rendering never calls the hub. A reviewer that starts after the page was loaded gets the same block from its first update: the tool-call and text streams begin with `stream/_reviewer_placed.stream.html.twig`, an `append` to `targets="#round-<id>-live:not(:has(#reviewer-<id>-text))"`, which matches nothing once the block exists, so a known reviewer keeps its text; the placed block is headed by the reviewer's role and model (`role (model)`, the same `ReviewerOutcome::modelAndLab()` the page uses, with the raw model id as the heading's `title` when one was recorded, #3274) from the `outcome` `MercureRoundUpdates` reads with `LedgerReviewPages::startedReviewerOf()` (from the rows that name the round alone, never every start in the ledger), or "A reviewer (role not read)" when that read fails. `reviewer_asked_again` begins the same way and, with the `update` action, replaces the content of `targets="#reviewer-<id>-text:not(:has(#reviewer-<id>-try-<try>))"` with `p.asked-again#reviewer-<id>-try-<try>` ("First try gave no usable answer, so the reviewer was asked again."), so the first try's text is gone and the retry's text follows that line, and a retry that reports its start twice (a streamed retry refused before its first delta and run again unstreamed) matches nothing the second time and keeps its own text. `tool_called` appends the call in plain words (see Port above) as an `li` of `reviewer-<id>-activity`. `LivePageRendering` renders the page again without the subscription and the script when the first render throws (an empty key, a token that cannot be made), as described above, so a hub problem never gives a `500`; when the hub is down the browser's `EventSource` fails, the shell's `connection` controller shows the reconnecting line and the Offline marker and opens a new `EventSource` every 5 s, asking with `last_event_id` for what the page missed (Connection state in [Dashboard](dashboard.md)), and the page stays as the ledger shows it, with no polling fallback. `mercure_publish()` is not used by the web side either: every process publishes through the hub endpoint. Turbo's JavaScript comes from `importmap.php` at pinned versions, each module with a sha384 integrity hash in the rendered import map (the import map settings under Dependencies in [Conventions](conventions.md)); `assets/vendor/` is not committed, `bin/console importmap:install` downloads it and the `Dockerfile` runs it with `asset-map:compile`. Updates are private, so a listener without the cookie gets `401` from the hub.
