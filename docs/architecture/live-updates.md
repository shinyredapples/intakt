## Live updates

Plan task T21, parts 1 to 3 (design: [Dashboard](../design/05-architecture/13-dashboard.md)). Reviewer progress and round state are published through the Mercure hub as Turbo Stream markup, and the review page listens to them; the stop button and the cancel of a running reviewer are described in [Dashboard](dashboard.md).

- **Port:** `Review\Contract\RoundUpdates` has `toolCalled()`, `textStreamed()`, `roundChanged()` and `reviewerStopped()`; an implementation never throws. `ReviewerRuns::reporting()` hands the agent's execution to `LiveProgress::reporting()` (which holds the `RoundUpdates` and the clock), which registers `onProgress()` on it and forwards a `Progress` whose payload is a `ToolCall` (its name only, never the arguments) or a streamed `TextDelta`, for a reviewer whose `ReviewerConversation` names a round, under its `reviewerId` (the `RoundReviewer` id the ledger and the dashboard use; the conversation `id` only when none is set), so the text of a review retried in a new conversation after the output limit stays on its reviewer. The verdict path reads the execution's result (`getResult()->getContent()`), also when the call is streamed, and the strict verdict converter maps a streamed answer too (see Mapping in [Review verdicts](review-verdicts.md)), so with the production subscribers a stream's text deltas reach `textStreamed()`. The deltas are batched per reviewer call in a `StreamedTextBatch` made by `LiveProgress::reporting()`: the first delta is published at once, later text is published at most every 250 milliseconds (by the injected clock), and the rest is flushed through `onResult()` when the answer ends, also when less than 250 milliseconds passed since the last publish (so a reviewer can see one more update in that second), so the published pieces joined in order equal the full answer.
- **Streaming and its fallback:** `ReviewerAgent` sets `stream` on the reviewer's call when the model's catalog entry (`getModelCatalog()->getModel()`) has `Capability::OUTPUT_STREAMING`, a fact read from plain code and never from model text. `TierRoutedPlatform` answers with `UnstreamedModelCatalog` for a provider whose `Provider::streams()` is false (the subscription CLIs `claude_code` and `codex`, whose bridges end a streamed run differently), so those calls stay unstreamed. A request the provider refuses (`BadRequestException` or `InvalidRequestException`, which a provider raises before its first delta) before it accepted a stream is repeated once without `stream` on the same stored conversation, and `ReviewerRuns::fellBackToUnstreamed()` hands it to `StreamingFallbacks::record()`, which appends a `streaming_fell_back` ledger event (`round`, `reviewer`, the same reviewer id) for a reviewer of a round; a failed append is logged, not thrown. `StreamAcceptance` watches the execution's `Progress`: once a delta or a tool call arrived, the provider accepted the stream, so a refusal in a later round of tool calls (a context grown too long, for example) stays an exception, is neither repeated nor recorded as a fallback. A stream cut off mid-answer is not a refusal either: it stays `IncompleteStreamException` and is never repeated. The usage of a streamed call is settled as Mapping describes.
- **Round state:** `RunReviewRound/LiveRoundProgress::publishLatest()` publishes `ReviewRound::progress()` (reviewers finished, reviewers, judged). `ReviewWithReviewerHandler` calls it after a reviewer is recorded and the round was offered for completion, and `JudgeRound/PublishJudgedRound`, a `RoundJudged` listener, after the judge's record is committed. One worker publishes a round at a time: a Lock per round (`review-round-progress-<round id>`), tried without waiting. The holder reads the progress under it, publishes it when it differs from what it last published, and reads again after the release, taking the lock again when the progress moved. A worker that finds the lock taken leaves its newer state to the holder, so the published states never go backwards ("1 of 2" after "2 of 2", or an unfinished round after "Judged").
- **Publisher:** `Dashboard\Infrastructure\MercureRoundUpdates` renders the template of a `RoundStream` case (`tool_called`, `text_streamed`, `round_changed`, `reviewer_stopped`; a test asserts each has its `templates/dashboard/stream/*.stream.html.twig` file) (autoescaped, so model text cannot close the `<template>`) and publishes a private `Update` on the topic `review/rounds/<round id>` (`MercureRoundUpdates::topicOf()`, the only place that spells it) through `HubInterface`, the hub's HTTP endpoint, so Messenger consumers, the console and the web side use one path. `mercure_publish()` is not used. In the test environment the hub `mercure.hub.default` is decorated by the journeys' `RecordingHub`, which records each update to a file instead of posting it (see [Journeys](journeys.md)). A failed publish is logged (round, stream and exception) and swallowed: a live update must not change a verdict or a round. Stream targets (`reviewer-<id>-activity`, `reviewer-<id>-text`, `round-<id>-state`, `round-<round>-reviewer-<reviewer>-state` and `round-<round>-reviewer-<reviewer>-stop`) are elements of the review page.
- **Hub:** the `Caddyfile` runs FrankenPHP's built-in hub (1.13 and later) in modern mode: an `issuer` block with `publisher` and `subscriber` keys (`MERCURE_JWT_SECRET`, issuer `MERCURE_JWT_ISSUER`), the `bolt` transport (`MERCURE_BOLT_PATH`, `MERCURE_HISTORY_SIZE`, default 1000 events) so a client that reconnects with `Last-Event-ID` receives what it missed, and `encode` applied to every path but `/.well-known/mercure`. `config/packages/mercure.yaml` (`symfony/mercure-bundle`) mints the publisher token from the same secret; `MERCURE_URL`, `MERCURE_PUBLIC_URL`, `MERCURE_JWT_SECRET` (empty in `.env`, set it in `.env.local`) and `MERCURE_JWT_ISSUER` are in `.env`. A subscriber asks with `match=<topic>` and a token that grants `subscribe`, as a bearer header or in the cookie `mercure_access_token` (`cookie_name` in the `Caddyfile` and in `config/packages/mercure.yaml`, prefix-less because the dashboard answers over plain http on localhost, where a `__Secure-` cookie is refused). FrankenPHP takes these values from its own environment and from the files given with `--envfile`, never from Symfony's `.env` loading; the first file that sets a variable wins, so `.env.local` goes before `.env`. The admin API listens on `localhost:2019` only (`CADDY_ADMIN` moves it), where `intakt:server:status` reads it.
- **Review page (part 2):** `symfony/ux-turbo` with `symfony/asset-mapper` and `symfony/stimulus-bundle` (which Turbo requires). `templates/dashboard/review.html.twig` fills the `importmap` block of `base.html.twig` with `importmap('app')` and, when a round of the page is not judged, prints one `turbo_stream_from(topics, true)` with the topics `ShowReviewController` takes from `topicOf()` for all of them, because the Mercure bundle sets the subscriber cookie once per response and throws on a second call: a `<turbo-mercure-stream-source private>` whose address and subscriber cookie the Mercure bundle makes locally from `MERCURE_JWT_SECRET`, so rendering never calls the hub. The page holds the elements the streams target: `round-<id>-state` (the same words the stream sends), and in `round-<id>-live` of an unjudged round, per started reviewer, `templates/dashboard/_live_reviewer.html.twig`: `reviewer-<id>-activity` (a list) and `reviewer-<id>-text`, where `<id>` is the reviewer id the publisher uses. A reviewer that starts after the page was loaded gets the same block from its first update: the tool-call and text streams begin with `stream/_reviewer_placed.stream.html.twig`, an `append` to `targets="#round-<id>-live:not(:has(#reviewer-<id>-text))"`, which matches nothing once the block exists, so a known reviewer keeps its text. `ShowReviewController` renders the page again without the subscription and the script when the first render throws (an empty key, a token that cannot be made), logs a warning with the round and the exception itself, and puts the one-time flash lines back, so a hub problem never gives a `500`; when the hub is down the browser's `EventSource` fails and the page stays as the ledger shows it, with no polling fallback. `mercure_publish()` is not used by the web side either: every process publishes through the hub endpoint. Turbo's JavaScript comes from `importmap.php` at pinned versions; `assets/vendor/` is not committed, `bin/console importmap:install` downloads it and the `Dockerfile` runs it with `asset-map:compile`. Updates are private, so a listener without the cookie gets `401` from the hub.
- **Tests:** `tests/Core/Dashboard/UseCase/ReviewPageLiveUpdatesTest.php` (subscription to the private topic with the cookie, one listener whose cookie names every unjudged round, none for a judged round, every stream target exists in the page, a reviewer started after the page loaded gets its block from its first update, the page renders fully while no hub runs; it writes empty stand-ins for the downloaded scripts (`DownloadedScriptStandIns`) into a folder per test worker under `assets/vendor/` and points the asset mapper there, so it runs with the test workers), `ReviewPageWithoutHubTest.php` (no key: the page renders fully from the ledger, keeps the flash line and logs a warning), `NoPollingTest.php` (no refresh tag, timer or request on any page, no script outside the review page but the inline theme script of the layout), `tests/Core/Dashboard/Infrastructure/MercureRoundUpdatesTest.php` (`MockHub`: topics, order, private, escaping, a failing hub), `tests/Core/Dashboard/Infrastructure/MercureHubTest.php` (group `hub`, a real `frankenphp run` on a free port with its admin API on another: events reach a subscriber in order, a reconnect with `Last-Event-ID` receives the missed ones, no token gets 401, the admin API reports the hub ready; skipped without `frankenphp`), `CaddyfileTest.php` beside it (group `hub`, `frankenphp adapt` with the documented env files: the issuer and key come from `.env.local` when it is first and not when `.env` is, the admin API listens on `localhost:2019`), `ReviewerVerdictTest` (tool calls, streamed text with the production subscribers, a streamed verdict mapped strictly), `LiveRoundProgressTest` (a worker that finishes while another publishes, a taken lock) and `JudgeRoundTest` (round state, a reviewer message delivered again after the judge).
