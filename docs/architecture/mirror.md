# Bare mirror

Intakt keeps one bare mirror per project at `var/mirrors/<project>.git` (the container parameter `intakt.git.mirrors_directory`, `Intakt\Core\Git\Contract\GitServices::MIRRORS_DIRECTORY`). The mirror is a cache of the remote: if it is lost, the next update clones it again. Deleted branch heads are not kept here but in a separate archive on the data volume ([Branch cleanup](branch-cleanup.md#archive)).

## Updating a mirror

`php bin/console intakt:mirror:update <project> <remote>` (`UpdateMirror` in `src/Core/Git/UseCase/UpdateMirror/`) keeps the mirror up to date in place: it first asks `git ls-remote --symref -- <remote> HEAD`, then fetches with `git --git-dir=<mirror> fetch --prune --quiet --no-write-fetch-head -- <remote> +refs/*:refs/*`, so a branch the remote's `HEAD` names already exists when the fetch runs and comes in with it, and then points the mirror's `HEAD` at what `ls-remote` advertised: the branch it names (`symbolic-ref`), or, when the remote's `HEAD` is detached and names no branch, the commit it advertises (`update-ref --no-deref`, a detached `HEAD`, as `git clone --mirror` leaves it). Before that `update-ref`, `git --git-dir=<mirror> fetch --quiet --no-write-fetch-head -- <remote> HEAD` fetches the advertised commit by name, because a detached `HEAD` may sit on a commit no branch or tag reaches, which the refs fetch leaves out; only a detached `HEAD` is fetched this way, since an empty remote advertises no `HEAD` and `fetch -- <remote> HEAD` fails there. Both fetches carry `--no-write-fetch-head`, because a fetch otherwise writes the remote's address into the mirror's `FETCH_HEAD` (`branch 'main' of <remote>`), and the mirror keeps no address; `clone --mirror` writes no `FETCH_HEAD`. The remote is named on every call, so a mirror never depends on a remote setting, and the mirror's config names no remote. `--git-dir` pins every call to the mirror, so git never looks upward into the install's own checkout.

- A mirror exists when the path holds `HEAD`, `objects/` and `refs/` and `git rev-parse --is-bare-repository` says `true`. It is fetched in place, so a branch the remote deleted disappears and a bare repository left without refs is filled.
- Anything else (no folder, an empty folder, a folder that is not a bare repository) gets a new mirror: `git clone --mirror --quiet -- <remote> <staging>` into a staging folder `var/mirrors/.<project>.git.<random>`, then renamed to `<project>.git`. The clone takes the remote's object format, so the mirror of a SHA-256 repository is a SHA-256 repository too (`git init --bare` would always make SHA-1, and a fetch from a SHA-256 remote into it fails). Each attempt of the clone gets a new, empty staging folder (`NetworkGit::runEachAttempt()`), so a retry never clones into what a killed attempt left. The clone saves the remote's address as `remote.origin.url` in the staging repository's `config`, and with it any credential in the URL, so `git config --remove-section remote.origin` drops that section before the staging folder is published: the mirror keeps no address and no credential, and a rotated token leaves nothing behind. Every staging folder is removed at the end, so an incomplete mirror is never published.
- The rename runs under the Symfony lock `git-mirror-<project>`, which checks the path again first: when another update published the mirror meanwhile, that mirror is kept, the staging folder is dropped, and the overtaken update then fetches into the published mirror once more (outside the lock, like every fetch), because the update that won may have fetched earlier and the mirror must be at least as fresh as the overtaken fetch. The fetches run outside the lock; git's own ref locks guard them.

Once `HEAD` is set, `git --git-dir=<mirror> --bare rev-parse --verify --quiet HEAD` checks that it resolves; when it does not (the remote deleted the branch between `ls-remote` and the fetch), the update throws `MirrorNotUpdated` naming the ref, and the next update repairs `HEAD`. An empty remote advertises no `HEAD`, so `HEAD` is neither set nor checked. A local git step that fails (`config --remove-section`, `symbolic-ref`, `update-ref`) or a rename that fails throws `MirrorNotUpdated`; the console command prints it and exits with 1.

Before it clones, fetches or makes any folder, the update checks the [disk floors](disk-floors.md) with `DiskSpace::holdAt()`, on the folder it will write to. It first asks, without writing, whether the mirror's path holds a valid mirror. A valid mirror is measured itself, because the fetch writes into it and it may be mounted on a disk of its own. Otherwise (no folder there yet, or a folder that is no mirror and will be replaced) the clone goes to a staging folder in the mirrors folder (`var/mirrors`), so the nearest folder that exists at or above the mirrors folder is measured, and a folder at the mirror's path that is no mirror is not. Below a floor it throws `MirrorNotUpdated` with the reason from `DiskHold::reason()` (`the disk of <folder> holds new work: <free> free bytes, below the floor of <minimum>`, or `inodes`), and a disk that cannot be read (`FreeSpaceUnreadable`, or an inode read that times out, named `df timed out after 10 seconds`) throws `MirrorNotUpdated` with its message; either way nothing is cloned or fetched, and the console command prints it and exits with 1. This holds a fetch into an existing mirror too. The next update above both floors goes ahead. `UpdateMirror::refresh()` is the same update without the check, for the pre-push check of a build that is already running ([build task](build-task.md)).

The project name becomes a folder name, so a name must start with a letter or a digit, hold only letters, digits, `.`, `_` and `-`, and not contain `..` (`Intakt\Core\Git\Domain\Mirrors::pathOf()`). Anything else is refused before git runs. The remote is passed after `--`, so it can never be read as an option. The remote is an argument because a project has no remote setting yet. A relative local path (no `/` at the start and no `:` before the first `/`, git's own rule for a local path) is resolved once against the mirrors folder (`Path::makeAbsolute()`), because git reads a relative path from its working directory, which is the mirrors folder for the clone but the mirror itself for a fetch: without that, the second update of `../repo` would name a repository the first one never cloned. An address with a scheme (`file://`, `https://`) or a host before the path (`host:repo`) is passed as it is.

All calls are built by `HardenedGit`: the calls in the mirror by `callInBareRepository()`, which pins the bare mirror with `--git-dir=<mirror> --bare` and takes no work tree, and `clone --mirror` by `call()` in the mirrors folder (a mirror clone uses no work tree). A folder whose config names a work tree (`core.worktree` beside `core.bare = false`) is refused by the bare call, so the check before an update counts it as no mirror and replaces it (`WorkTreeInBareRepository`). A check that is killed by a signal or hits its time limit gives no answer: it stops the update with the Process exception and the existing mirror stays as it is. A mirror that holds `info/attributes` is refused with `RepositoryAttributesRefused`, which is not caught as "no mirror" either, so the update stops and the mirror is not replaced. The bare call looks at the config when it is prepared, so a config changed between that look and the run of the call is not seen by it; the callers read objects and refs only. The network calls (`clone --mirror`, `fetch` of the refs, `fetch` of a detached `HEAD`, `ls-remote`) run through `NetworkGit`. `HardenedGit` allows no transport protocol, so `NetworkGit` overrides just two variables for its call: `GIT_ALLOW_PROTOCOL=file:https` and `GIT_TERMINAL_PROMPT=0` (git never asks for a password). The retries are described in [Retried network git calls](network-git.md).

The `clone --mirror` call alone carries no `--attr-source` and unsets `GIT_ATTR_SOURCE`. It runs in the mirrors folder, so `HardenedGit` would name SHA-1's empty tree as the attribute source, and a `file://` remote hands that on to its `upload-pack`, which refuses it in a SHA-256 repository (a plain path starts no `upload-pack`, which hides the problem). A bare mirror clone checks out nothing and reads no attributes, and `core.attributesFile=/dev/null` and `GIT_ATTR_NOSYSTEM` still apply. The fetches and `ls-remote` keep the full call, because they run inside the mirror, whose object format is the remote's.
