## Journeys

A journey walks one path a user takes through a freshly booted install and asserts what the user sees, so a break that no single change's evidence shows is caught. They live in `tests/Journeys/`, in the PHPUnit group `journeys`; the `application` suite of `phpunit.dist.xml` excludes that folder, so neither the `tests` gate nor `bin/check --fast` runs them, while its `journey harness` suite still runs the harness tests in `tests/Journeys/Support/`. A test in the group elsewhere under `tests/` runs in the `tests` gate like any other. Nothing here calls a model provider or a forge.

- **Run:** `bin/check --journeys` runs the `journeys` gate alone (it refuses `--fast`, `--only`, `--skip`, `--base` and `--test-merge`, and is not a gate that `--only` can name). For each `tests/Journeys/*JourneyTest.php` it starts `bin/instance` with PHPUnit as the command (`--no-configuration --group=journeys`, failing on skipped, risky, warning, notice, PHPUnit notice, deprecation and PHPUnit deprecation, as the `tests` gate does), so every journey gets its own instance and database, up to 240 seconds each (`INTAKT_INSTANCE_COMMAND_SECONDS`, set through `env`). Each run is contained like the gate runner's other contained runs (`ProcessRunner::runWithin()`: its own session, and a PID namespace where `unshare` allows one), so a process a journey leaves behind is killed with its run, and the whole tree is killed after 300 seconds; in process-group mode a process still running after the journey ends makes the run time out. A tree without a journey fails. A failing journey is one finding: its file and the line `journey "<name>" failed at step "<step>": <reason>` (the first line of the reason, the whole finding cut at 300 characters).
- **Harness:** `tests/Journeys/Support/JourneyTestCase` reads the instance address from `INTAKT_INSTANCE_URL`, drives pages with BrowserKit's `HttpBrowser` (`visit()`, which sends the `Host` the dashboard accepts, with the `DASHBOARD_PORT` of `.env.test`, which the instance reads too since it runs in the test environment) and the console with `bin/console` through Symfony Process (`console()`, with variables for that process only and a timeout of 60 seconds unless the caller gives one). `publishedUpdates()` reads what the instance's hub recorded (below). `step('<name>', <callable>)` runs a named step through `JourneySteps`, which turns any failure into `journey "<name>" failed at step "<step>": <reason>`. `JourneyStepsTest` and `tests/Gates/JourneysGateTest.php` (with a deliberately broken journey fixture) prove that a forced break names its journey and step, and `LiveReviewProgressBreakJourneyTest` proves it on the real live review progress journey (below). `address()` is a `final protected` accessor so that test reads the address from the one place.
- **Test vendor and recording hub:** `config/services.yaml` imports `tests/Journeys/services.yaml` in the test environment (skipped when `tests/` is missing), so every test-environment container, the one an instance from `bin/instance` builds included, has two stand-ins. `Support/JourneyVendor` is the `Plugin/Vendor/Contract/Vendor` service: every review approves with no findings and every judgement marks the blocking (P1 and P2) findings to act, without a model, a key or a network call. `Support/RecordingHub` decorates the Mercure hub `mercure.hub.default`: `publish()` appends the update's topics, data and private flag as one JSON line (under a file lock) to `journey-hub-updates.jsonl` in the kernel's share directory (`APP_SHARE_DIR` plus the environment), and posts nothing; the public URL, token factory, protocol version and cookie name stay the decorated hub's, so the review page authorizes its listener as before. The share directory, not the cache, because a journey's `cache:clear` would remove the recording. `RecordingHub::updatesIn()` reads the file under a shared lock, so it never sees a half-appended line. A journey reads the updates with `publishedUpdates()` of `JourneyTestCase`, which builds the test kernel only to ask its share directory, from the same `APP_SHARE_DIR` that `bin/instance` gives both the instance and the journey; a recorded line that is not an update fails the journey. `JourneyVendorTest`, `RecordingHubTest` (including a read while another process holds the write lock in the middle of a line) and `JourneyContainerTest` (the test container's vendor, and an update published through its hub read back by the journey side) cover them. `LiveReviewProgressJourneyTest` uses both.
- **Live round driver:** `liveRoundDriver()` of `JourneyTestCase` returns a `Support/LiveRoundDriver` that starts a review round on the sample project's pull request and steps it. `startOnSamplePullRequest(<repository>)` dispatches `StartReview` (project `sample`, branch `sample-change` against `main`, round 1) on the test container's message bus, the door the dashboard's start uses, from a kernel of the journey's own on the instance's database and share directory (shut down after the test), and returns the round id the handler queued. The journey's PHPUnit loads no Dotenv, so for that kernel's life `JourneyTestCase` puts the values of `.env` and `.env.test` that the process does not already have (in `$_ENV`, `$_SERVER` or its environment, as Dotenv decides) into `$_ENV` (without Dotenv's `SYMFONY_DOTENV_VARS`), and `MESSENGER_TRANSPORT_DSN=doctrine://default` over the `in-memory://` of `.env.test`, so the queue is the instance database's table, which the worker in another process reads too; after the test it puts `$_ENV` back, and a second call first shuts the earlier kernel down and puts `$_ENV` back. The sample project lives in the compiled container, so a journey rebuilds the cache after seeding and before starting the driver. `step()` runs `messenger:consume async --limit=1 --time-limit=5` through `console()` with the same shared queue, so one queued message (a reviewer or the judgement) is handled per step, and a step on an empty queue waits 5 seconds. `stepUntilEnded(<round>)` steps, after each step reads `publishedUpdates()` for the topic `review/rounds/<round>` (updates of other rounds are ignored) and returns them once an update carries the `Judged.` text of the `round_changed` stream; once 150 seconds of stepping have passed (measured on a `MonotonicClock`, each step's wait cut to the time left), well inside a journey's 240 seconds, it fails naming the round and the last update. Together: the test vendor approves without a model, the recording hub keeps what `RoundStream` would have sent, and the driver moves the round so the journey can read those updates between steps. `LiveRoundDriverTest` covers it with a stubbed bus, console and updates and a `MockClock` (including a round that never ends failing before the gate's journey limit, read from `JourneysGate`); `JourneyContainerTest` shows the accessor wires a driver from the test container, on a Doctrine queue, with the default settings, and leaves `$_ENV` as it found it.
- **Watcher start:** `watcherStart(<variables>)` of `JourneyTestCase` returns a `Support/WatcherStart` whose console calls get the journey's variables and the shared `doctrine://default` queue. `startOnSamplePullRequest(<repository>, <configuration>)` starts a round the way a user's pull request does, through one watcher tick, and never dispatches `StartReview` itself: it reads the `sample-change` head of the sample repository with git, writes `watcher-recording.json` beside the configuration (the format `tests/Core/Watcher/RecordedPullRequests` reads: pull request 1 at that head and one completed, successful `ci` run for it), adds a `watch` section (the repository, `main` and the sample task) to the sample project in the configuration the seed wrote, rebuilds the cache with `INTAKT_CONFIG` naming it, and runs `messenger:consume scheduler_watcher --limit=1` with `WATCHER_RECORDING` for that process only. A fresh worker sends its first tick one schedule interval after it starts (Symfony's `PeriodicalTrigger`), so the tick takes about a minute; its `--time-limit` is the interval of `WatcherSchedule` plus 30 seconds and its process timeout 30 seconds more. It reads `intakt:ledger:events` before the tick and again after it, and returns the round of the last `round_queued` entry for the sample project at that head among the entries the tick appended (an entry the ledger already held, even for the same head, does not count); no such entry fails naming the recording and the head, a `round_queued` entry that is not JSON or names no round fails too, and a configuration without the sample project fails naming the file. `WatcherStartTest` covers it with a stubbed console on a sample repository built from the fixtures.
- **First install and setup** (`FirstInstallJourneyTest`): creates the database (`doctrine:migrations:migrate`), opens `/projects` and reads that no project has started a review, rebuilds the container with a placeholder provider key as the container entrypoint does and seeds the sample project (`intakt:sample:seed`), seeds again and reads that both parts are kept, then opens `/reviews`.
- **Live review progress on the dashboard** (`LiveReviewProgressJourneyTest`): creates the database, rebuilds the container with a placeholder provider key and seeds the sample project, then starts a round on the sample pull request through the watcher with `watcherStart()->startOnSamplePullRequest()` (the variables it gets name the seeded configuration, and its rebuild after adding the watch section is what the worker that steps the round reads). It opens `/reviews/<round>` while the round runs and reads it `in progress` with `N of M reviewers finished.` in `#round-<round>-state`, steps the round with `liveRoundDriver()->stepUntilEnded()`, and checks the recorded updates against the page it opened while running with `Support/RoundStreamCheck::assertFitsThePage()`: every update on the topic `review/rounds/<round>` is made of `<turbo-stream>` elements with an action and a target, a single target names an element of that page or one an earlier update placed, the progress never goes back, and the last update, and only that one, shows `Judged.`. It then opens the page again and reads `Judged.` in `#round-<round>-state` and the round as `judged`. Every review and the judgement come from the test vendor, so no model is called. Open item: the live listener on the page is not asserted. The instance has no `MERCURE_JWT_SECRET`, so the review page renders without `turbo-mercure-stream-source`; the journey reads what the hub was sent and checks it against the page; whether the browser subscribes is covered by `ReviewPageLiveUpdatesTest`.
- **Forced break in the live review progress journey** (`LiveReviewProgressBreakJourneyTest`): runs `LiveReviewProgressJourneyTest` unchanged in a child PHPUnit process (`--no-configuration --group=journeys`, a timeout of 200 seconds) with `INTAKT_INSTANCE_URL` set to the instance address plus the path prefix `/forced-break`, which the dashboard does not serve. The first three steps use only the console and pass; `visit()` of `open the running round` then gets a 404. The test asserts that the child fails and that its output holds `journey "live review progress on the dashboard" failed at step "open the running round": GET /reviews/`, exactly one failed step, and neither the later step `step the round until the judge has ruled` nor another journey. It uses the same test vendor, so no model is called, and the journey's own file and behavior are not changed.

- **Alarm on a red run** (`bin/journey-alarm [--run=<link>] [<file>]`): reads the output of `bin/check --journeys` from the file, or from stdin without one, and turns a red run on main into one task. `Support/JourneyRun` reads the output's JSON lines: each finding of the `journeys` gate line that matches `<file>: journey "<name>" failed at step "<step>": <reason>` is a failing journey; with none, a `"result":"pass"` line means green, and anything else (no such finding and no pass, an empty output, a `no journey found` finding) is refused, so the command exits 1 with a message and calls nothing. A `journeys` gate line with `"ok":false` and no such finding is refused too, even beside a pass line. Green prints `no journey failed: nothing filed` and exits 0 without calling `gh`. Red: `Support/JourneyAlarm` takes a Symfony Lock (a file lock in the system's temporary directory, waited for) and holds it from the lookup to the create or edit, so two runs on one machine never both create. `Support/GitHubIssues` reads every page of the repository's open issues (`gh api repos/<owner>/<name>/issues?state=open&per_page=100 --paginate --slurp`, the answer validated as a list of pages of issues with a number and a body, empty bodies read as empty, pull requests skipped) and picks the oldest whose body holds the line `<!-- intakt:journey-alarm -->`. None: `gh issue create` with the labels `priority:urgent` and `ready` and the title `fix(journeys): journey "<name>" fails on main` (the name cut at 60 characters), or `fix(journeys): <N> journeys fail on main` for several; its answer must be a link ending in `/issues/<number>`. It then reads the open issues again: when a run on another machine filed an older marked task meanwhile, it closes its own (`gh issue close <number> --comment "Duplicate of #<older>"`) and edits the older one, so one task stays open. One: `gh issue edit <number>` replaces only its body, so its title and labels stay. The body (`Support/JourneyAlarmTask`) is the marker line, each failing journey with its file, step and reason, `Run: <link>` when `--run` gives an https link, and the last 40 lines of the output in a code block whose fence is longer than any backtick run in them; it stays under GitHub's 65536 characters by cutting the start of that tail (and, should the findings alone be longer, the body itself). Every `gh` call names the repository from `GITHUB_REPOSITORY` (`<owner>/<name>`, else exit 1 before any call), gets the body on stdin and a 60-second limit. Without a token in `GH_TOKEN` or `GITHUB_TOKEN` it exits 1 before any call, so `gh` never falls back to a stored login; `gh` reads that token, and the command reads no credential. A failing `gh` call exits 1 with its error. A file it cannot read, a second file, an unknown option or a `--run` that is not an https link exits 2. The classes live in `tests/Journeys/Support/` beside the harness, so the `journey harness` suite runs their tests: `JourneyRunTest` and `JourneyAlarmTaskTest` read `Support/Fixtures/one-broken-journey.out`, a saved output of the gate on the broken journey fixture of `tests/Gates/JourneysGateTest.php`, and `JourneyAlarmTest` runs the command with a fake `gh` first on `PATH` that records its calls and answers from an issues file it keeps, so a first red run creates exactly one issue and a second red run edits it and creates none; with listings made to wait for each other, two runs at the same time create one issue.

`.github/workflows/journeys.yml` ([CI](ci.md)) runs `bin/check --journeys` on main nightly and on demand, one run at a time, read-only, as `ci.yml` runs `bin/check`. A red run stays red, and its `alarm` job, the only one with `issues: write`, runs `bin/journey-alarm` on GitHub's `ubuntu-24.04`, whose `gh` it uses. The `journeys` job's limit of 40 minutes holds the image build plus each journey file's run in turn: the gate's 300 seconds cover one file's whole contained run (the instance's boot and stop and the PHPUnit run of that file), not each journey test in it. The journeys of a built and merged task and of an owner decision (#1051) are a separate task.

**Testing a PHPStan rule.** A rule's test class in `tests/Gates/` extends `PhpStanRuleTestCase` (built on PHPStan's `RuleTestCase`) and returns the rule from `ruleFor(string $root)`, built as `config/gates/phpstan.neon` wires it, with `$root` for `%currentWorkingDirectory%`. The three deprecation rules report together, so their test asks `tests/Gates/DeprecationRules.php`, which hands each node to every one of them whose node types match (PHPStan's `CompositeRule` takes rules of one node type only). Its fixtures are folders under `tests/Gates/Fixtures/`, where a file `*.php.fixture` is copied as `*.php`. In the rule test classes that do not use the one-run helper below, at most one rejected and one accepted case per rule run `bin/check --only=phpstan` on a sandbox copy (`assertRejectedBy('phpstan', ...)` and `assertAcceptedBy('phpstan', ...)` of the `UsesSandboxes` trait), so the rule's registration in `phpstan.neon` stays covered end to end; since the gate dumps the checked tree's container into the tree's own `var/cache/`, such a sandbox borrows this repository's `bin/console` through a link (`Sandbox::borrowKernel()`, which `StaticAnalysisGateTest` calls too) and gets this repository's container built in its own cache; these runs of one test class share one sandbox (`Sandbox::ownedBy()`, a folder named by a hash of the process id and the test class, so it holds no static state; the trait removes it in `setUpBeforeClass()` and `tearDownAfterClass()`; `tests/Gates/SandboxTest.php` covers it), whose fixture `Sandbox::replaceFixtureWith()` swaps while it keeps `var/`, so the container, which bakes in the folder it was dumped in, is built once per class and the later runs only warm it up; `NoMockOptOutRuleTest` has only a rejected case, and `ContainerRegistrationTest` runs none through `bin/check`. `ContainerUnknownGetIdRuleTest` (six cases) and `ContainerUnknownHasIdRuleTest` (five cases) judge more cases through `bin/check`, because in the in-process analysis their rules get a service map without services (`tests/Gates/NoServices.php`), so only a full run judges an id against the checked tree's dumped test container: ids in a union, the invalid-behavior argument named last and private services with the test container (`get()`), and a locator typed as `Psr\Container\ContainerInterface` (`has()`). Their cases that do not depend on the container (a single id left to phpstan-symfony, a locator's own keys, the container bag) run in-process. These two classes, `ContainerUnknownParameterRuleTest` and `ContainerDumpingGateTest` (a misspelled and a registered service id) make one `bin/check --only=phpstan` run per class for all such cases: their data provider hands each case's fixture and expected findings to `casesOfOnePhpstanRun()` of the `UsesSandboxes` trait, which copies each fixture into a folder of its name (`Sandbox::withFixturesInFolders()`), borrows the kernel, runs the gate once, removes the sandbox in a `finally` block and hands the run to every case, named as the test it replaced (for example `--filter 'testEachFixtureReportsItsFindingsUnderItsFolder@ReadingAMisspelledParameterNameFailsStaticAnalysis'`). `assertFindingsUnderItsFolder()` then expects exactly the case's findings under `<fixture>/`, none for a fixture that must pass, and fails every case of a run whose gate reported no result or a finding that names no file (such as a container that could not be dumped), so a broken run cannot pass the accepted cases. Every other case analyzes its sandbox in the test's own process with only that rule: `assertRuleRejects(<fixture>, <finding>)` expects the finding, `assertRuleAccepts(<fixture>)` expects none from this rule, and `ruleFindingsOf(<fixture>)` or `ruleFindingsIn(<sandbox>)` return the findings in the gate's form (`<path>:<line> <identifier> <message>`, the path relative to the sandbox). Like the gate, this analysis skips the folders listed under `excludePaths` in `config/gates/phpstan.neon` (read from that file): `vendor`, `var`, `upstream` and `tests/Gates/Fixtures`. PHPStan's test container finds a class only through an autoloader, so the base class registers one for the classes the sandbox's files declare. The container keeps every class it has reflected, and fixtures reuse class names, so each test starts from a new instance of the compiled container and analyzes one sandbox (`PhpStanRuleTestCaseTest` analyzes a deprecated `Legacy` and then a plain one). `StaticAnalysisGateTest`, which checks the gate's own configuration (strict, deprecation and cognitive complexity rules), runs `bin/check --only=phpstan` once over all its fixtures, each in a folder of its name (`Sandbox::withFixturesInFolders()`): its data provider makes that run (removing the sandbox in a `finally` block) and hands it to one case per fixture, so each case also runs alone when selected with `--filter` (for example `--filter 'testEachFixtureFailsStaticAnalysisWithItsOwnFinding@deprecated-call'`), and looks for its finding under its folder. Because PHPUnit calls data providers while it builds the suite, any `phpunit.gates.xml` run that loads this file, or a class that uses `casesOfOnePhpstanRun()`, makes the run, even when `--filter` selects other tests.
