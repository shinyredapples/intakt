## Journeys

A journey walks one path a user takes through a freshly booted install and asserts what the user sees, so a break that no single change's evidence shows is caught. They live in `tests/Journeys/`, in the PHPUnit group `journeys`; the `application` suite of `phpunit.dist.xml` excludes that folder, so neither the `tests` gate nor `bin/check --fast` runs them, while its `journey harness` suite still runs the harness tests in `tests/Journeys/Support/`. A test in the group elsewhere under `tests/` runs in the `tests` gate like any other. Nothing here calls a model provider or a forge.

- **Run:** `bin/check --journeys` runs the `journeys` gate alone (it refuses `--fast`, `--only`, `--skip`, `--base` and `--test-merge`, and is not a gate that `--only` can name). For each `tests/Journeys/*JourneyTest.php` it starts `bin/instance` with PHPUnit as the command (`--no-configuration --group=journeys`, failing on skipped, risky, warning, notice, PHPUnit notice, deprecation and PHPUnit deprecation, as the `tests` gate does), so every journey gets its own instance and database, up to 240 seconds each (`INTAKT_INSTANCE_COMMAND_SECONDS`, set through `env`). Each run is contained like the gate runner's other contained runs (`ProcessRunner::runWithin()`: its own session, and a PID namespace where `unshare` allows one), so a process a journey leaves behind is killed with its run, and the whole tree is killed after 300 seconds; in process-group mode a process still running after the journey ends makes the run time out. A tree without a journey fails. A failing journey is one finding: its file and the line `journey "<name>" failed at step "<step>": <reason>` (the first line of the reason, the whole finding cut at 300 characters).
- **Harness:** `tests/Journeys/Support/JourneyTestCase` reads the instance address from `INTAKT_INSTANCE_URL`, drives pages with BrowserKit's `HttpBrowser` (`visit()`, which sends the `Host` the dashboard accepts, with the `DASHBOARD_PORT` of `.env.test`, which the instance reads too since it runs in the test environment) and the console with `bin/console` through Symfony Process (`console()`, with variables for that process only and a timeout of 60 seconds unless the caller gives one). `publishedUpdates()` reads what the instance's hub recorded (below). `rebuildContainer(<variables>)` rebuilds the instance's container from the given variables through `Support/ContainerRebuild`: it removes only the container's loader file (the kernel's container class, named by the kernel through `ContainerRebuild::loaderOf()`, in its build directory) and runs `cache:warmup` with the variables, so that process compiles a new container into a new folder beside the one the instance's running worker still loads its services from. No other process compiles one while the loader is gone, because the instance boots a kernel only for a command or request the journey sends, and the journey waits for the warmup before it sends one. Not `cache:clear`, because it takes a container compiled in the second it starts for one it built itself and keeps it (so one the instance or an earlier command built without the key survived, and the seed found no provider key), and marks the service files the running worker still loads as old, so the next compile removes them (which answered the next page with a 500). `ContainerRebuildTest` runs real console processes: a container built without a key and stamped, inside each console process of the rebuild (a prepended PHP file), with that process's start time, then the rebuild with a key and the seed, which writes the sample project; the running worker's service files are all still there after a rebuild; and the loader is the file the kernel compiles into. `step('<name>', <callable>)` runs a named step through `JourneySteps`, which turns any failure into `journey "<name>" failed at step "<step>": <reason>`. `JourneyStepsTest` and `tests/Gates/JourneysGateTest.php` (with a deliberately broken journey fixture) prove that a forced break names its journey and step, and `LiveReviewProgressBreakJourneyTest` proves it on the real live review progress journey (below). `address()` is a `final protected` accessor so that test reads the address from the one place. `redirectOf(<path>)` sends a `GET` without following redirects and returns the `Location` of a `302` or `303` (anything else fails), because BrowserKit would follow it with the target's own host name, which the dashboard refuses. `redirectOfSubmit(<form>)` sends a form the same way through the HTTP client, with the browser's cookies and an encoded body, and keeps the cookies the answer sets, because `HttpBrowser` refuses any request body without `symfony/mime`, which Intakt does not need. `restartTheDashboard()` restarts the instance's FrankenPHP worker through its admin API (`POST <INTAKT_INSTANCE_ADMIN_URL>/frankenphp/workers/restart`, the address `bin/instance` sets in worker mode; nothing under the built-in server, which boots a kernel per request), as a restart of Intakt does, so a rebuilt container is the one the pages use.
- **Test vendor and recording hub:** `config/services.yaml` imports `tests/Journeys/services.yaml` in the test environment (skipped when `tests/` is missing), so every test-environment container, the one an instance from `bin/instance` builds included, has these stand-ins. `Support/ScriptedJourneyVendor` is the `Plugin/Vendor/Contract/Vendor` service. While `INTAKT_JOURNEY_SCRIPTS` is empty (its default) it answers with `Support/JourneyVendor`: every review approves with no findings and every judgement marks the blocking (P1 and P2) findings to act, and every tier counts as mapped (`mapsAModelTo()` answers true), without a model, a key or a network call. In a process whose `INTAKT_JOURNEY_SCRIPTS` names a script directory (below), it answers with `SymfonyAiVendor` itself, built only then (a service closure). `ScriptedJourneyVendor` wraps `SymfonyAiVendor` directly, so `AccountLimitedVendor` (account rotation and cooldowns) is not part of the concurrent consumer journey, while the account cap is (it lives in `SymfonyAiVendor`). `Support/ScriptedHttpClient` decorates `http_client` and passes every call to the real client while `INTAKT_JOURNEY_SCRIPTS` is empty. `Support/RecordingHub` decorates the Mercure hub `mercure.hub.default`: `publish()` appends the update's topics, data and private flag as one JSON line (under a file lock) to `journey-hub-updates.jsonl` in the kernel's share directory (`APP_SHARE_DIR` plus the environment), and posts nothing; the public URL, token factory, protocol version and cookie name stay the decorated hub's, so the review page authorizes its listener as before. The share directory, not the cache, because clearing the cache would remove the recording. `RecordingHub::updatesIn()` reads the file under a shared lock, so it never sees a half-appended line. A journey reads the updates with `publishedUpdates()` of `JourneyTestCase`, which builds the test kernel only to ask its share directory, from the same `APP_SHARE_DIR` that `bin/instance` gives both the instance and the journey; a recorded line that is not an update fails the journey. `Support/JourneyKeyCheck` is the `Plugin/Vendor/Contract/KeyCheck` service: it accepts every pasted key without a call, so a journey can paste a placeholder token into the first-run page's key form and no provider is asked. `JourneyKeyCheckTest`, `JourneyVendorTest`, `ScriptedJourneyVendorTest`, `RecordingHubTest` (including a read while another process holds the write lock in the middle of a line) and `JourneyContainerTest` (the test container's vendor and HTTP client, the vendor asking `SymfonyAiVendor` once `INTAKT_JOURNEY_SCRIPTS` is set, and an update published through its hub read back by the journey side) cover them. `LiveReviewProgressJourneyTest` uses both.
- **Live round driver:** `liveRoundDriver()` of `JourneyTestCase` returns a `Support/LiveRoundDriver` that starts a review round on the sample project's pull request and steps it. `startOnSamplePullRequest(<repository>)` dispatches `StartReview` (project `sample`, branch `sample-change` against `main`, round 1) on the test container's message bus, the door the dashboard's start uses, from a kernel of the journey's own on the instance's database and share directory (shut down after the test), and returns the round id the handler queued. The journey's PHPUnit loads no Dotenv, so for that kernel's life `JourneyTestCase` puts the values of `.env` and `.env.test` that the process does not already have (in `$_ENV`, `$_SERVER` or its environment, as Dotenv decides) into `$_ENV` (without Dotenv's `SYMFONY_DOTENV_VARS`), and `MESSENGER_TRANSPORT_DSN=doctrine://default` over the `in-memory://` of `.env.test`, so the queue is the instance database's table, which the worker in another process reads too; after the test it puts `$_ENV` back, and a second call first shuts the earlier kernel down and puts `$_ENV` back. The sample project lives in the compiled container, so a journey rebuilds the container after seeding and before starting the driver. `step()` runs `messenger:consume async --limit=1 --time-limit=5` through `console()` with the same shared queue, so one queued message (a reviewer or the judgement) is handled per step, and a step on an empty queue waits 5 seconds. `stepUntilEnded(<round>)` steps, after each step reads `publishedUpdates()` for the topic `review/rounds/<round>` (updates of other rounds are ignored) and returns them once an update carries the `Checked.` text of the `round_changed` stream (which `round_judged` includes); once 150 seconds of stepping have passed (measured on a `MonotonicClock`, each step's wait cut to the time left), well inside a journey's 240 seconds, it fails naming the round and the last update. Together: the test vendor approves without a model, the recording hub keeps what `RoundStream` would have sent, and the driver moves the round so the journey can read those updates between steps. `LiveRoundDriverTest` covers it with a stubbed bus, console and updates and a `MockClock` (including a round that never ends failing before the gate's journey limit, read from `JourneysGate`); `JourneyContainerTest` shows the accessor wires a driver from the test container, on a Doctrine queue, with the default settings, and leaves `$_ENV` as it found it.
- **Watcher start:** `watcherStart(<variables>)` of `JourneyTestCase` returns a `Support/WatcherStart` whose console calls get the journey's variables and the shared `doctrine://default` queue. `startOnSamplePullRequest(<repository>, <configuration>)` starts a round the way a user's pull request does, through one watcher tick, and never dispatches `StartReview` itself: it reads the `sample-change` head of the sample repository with git, writes `watcher-recording.json` beside the configuration (the format `tests/Core/Watcher/RecordedPullRequests` reads: pull request 1 at that head and one completed, successful `ci` run for it), adds a `watch` section (the repository, `main` and the sample task) to the sample project in the configuration the seed wrote, rebuilds the container through the `ContainerRebuild` it is given (`cache:warmup` after removing the loader, with `INTAKT_CONFIG` naming the configuration), and runs `messenger:consume scheduler_watcher --limit=1` with `WATCHER_RECORDING` for that process only. A fresh worker sends its first tick one schedule interval after it starts (Symfony's `PeriodicalTrigger`), so the tick takes about a minute; its `--time-limit` is the interval of `WatcherSchedule` plus 30 seconds and its process timeout 30 seconds more. It reads `intakt:ledger:events` before the tick and again after it, and returns the round of the last `round_queued` entry for the sample project at that head among the entries the tick appended (an entry the ledger already held, even for the same head, does not count); no such entry fails naming the recording and the head, a `round_queued` entry that is not JSON or names no round fails too, and a configuration without the sample project fails naming the file. `WatcherStartTest` covers it with a stubbed console on a sample repository built from the fixtures.
- **Concurrent consumer support** (for the `messenger:consume --concurrency` journey of #2723, which is not written yet): `Support/ScriptDirectory` is a folder a journey arms and every consumer worker records in. `arm(<weight>, <answers>)` writes `script.json` (the seconds each call is held and a list of answers, each a content type and a body); `script()` reads it and throws `ScriptNotArmed` for a missing file, a negative weight or no answers. `callStarted()` publishes `<n>.start` and `callEnded(<n>)` `<n>.end`, each a JSON record of the call number, the writer's PID, the writer's start time (clock ticks since boot, from `/proc/<pid>/stat`) and the clock's time: the JSON goes to a temporary file in the folder, `link()` gives it the record's name (which fails when the name exists, so `callStarted()` moves on to the next number and two workers never share one, and a second end throws `CallEndedTwice`), and the temporary file is removed, so a record appears whole or not at all. A `link()` that fails while the name is still free (no file and no link of that name) throws `RecordNotPublished` instead of trying the next number, so a filesystem error never keeps a worker retrying. A `link()` that reports success also throws `RecordNotPublished` unless the record's name now is the record itself (same device and inode, not a symbolic link), so a link someone put at the name after the scan never lets a call claim its number; since such a `link()` creates the symbolic link's target, every other name of the record in the folder is removed before it throws. `calls()` reads every start with its end and skips, instead of failing, an empty or partial `.start` file, a symbolic link, a start file whose name is not the plain spelling of a number (a zero-padded `01.start` or a number too large for an integer), and a record whose call number is not the one in its file name, so no call is listed twice. `Support/ScriptedHttpClient`, in a process with `INTAKT_JOURNEY_SCRIPTS`, answers every request itself, with the options given through `withOptions()` (a `base_uri`, say) applied as the real client would: it reads the script on its first call and keeps it in `Support/KeptScript` (a property marked `#[KeptForTheProcess]`), which every client `withOptions()` derives from it shares, so a worker answers all its calls from the script it read first even when the journey arms it again; its `reset()` (it takes over the `kernel.reset` tag of the `http_client` it decorates) is passed on to the real client and leaves the kept script alone; each call records its start, waits the weight on the clock, records its end and answers with the script's answer for its call number (counting round the list). `Support/ConsumerProcess::startedIn(<project directory>, <concurrency>, <variables>)` starts `php bin/console messenger:consume async --concurrency=<n> --memory-limit=256M --time-limit=3600 --quiet`, the options `docker/entrypoint.sh` gives its async consumer with the image's default memory ceiling; `signal()` sends it a signal, and `endedWithin(<seconds>)` polls until it ends and returns the seconds since the signal, or null (late) when the measured time is over the limit, also when the consumer exits between the last poll and the check, since the time is measured after the exit is seen. `isWorker(<pid>, <process start>)` tells whether the recorded worker (PID and start time from its call record) is still a descendant of the running consumer (at most four levels down, so a shell between the consumer and its worker still counts) with the same start time, with parents and start times read from `/proc/<pid>/stat` by `Support/ProcParents` (the worker's start time and parent come from one read, a `Support/ProcessEntry`, so a PID reused between two reads cannot pair the recorded worker's start time with another process's parent, and each ancestor on the way up must have started no later than its child, so a process that took a vanished shell's PID is no ancestor; an entry that cannot be read, such as one of a process that just ended, counts as no process, without a warning). The answer holds at the time of inspection only: a PID that was no longer the recorded worker at that moment, including one taken by a replacement worker of the same consumer, is no worker, but the system can still give the PID to another process between this check and the signal a teardown sends, so the journey's teardown has to handle that window itself. `--concurrency` above 1 needs the `amphp/parallel` package, which Intakt does not install yet, so the journey that runs such a consumer waits for it. `ScriptDirectoryTest` (including a hand-made empty and a partial `.start` file, a link that lands behind a symbolic link put at the name, and a symbolic link from one start name to the next), `ScriptedHttpClientTest`, `ConsumerProcessTest` (including an exit seen only after the deadline, forced by a stubbed process and a `MockClock`, a reused PID, a replacement worker with the recorded PID and one that takes the PID right after the first read) and `ProcParentsTest` (including an entry that is found but fails to read, through the `Fixtures/VanishedProcess` stream wrapper) cover them.

- **Alarm on a red run** (`bin/journey-alarm [--run=<link>] [<file>]`): reads the output of `bin/check --journeys` from the file, or from stdin without one, and turns a red run on main into one task. `Support/JourneyRun` reads the output's JSON lines: each finding of the `journeys` gate line that matches `<file>: journey "<name>" failed at step "<step>": <reason>` is a failing journey; with none, a `"result":"pass"` line means green, and anything else (no such finding and no pass, an empty output, a `no journey found` finding) is refused, so the command exits 1 with a message and calls nothing. A `journeys` gate line with `"ok":false` and no such finding is refused too, even beside a pass line. Green prints `no journey failed: nothing filed` and exits 0 without calling `gh`. Red: `Support/JourneyAlarm` takes a Symfony Lock (a file lock in the system's temporary directory, waited for) and holds it from the lookup to the create or edit, so two runs on one machine never both create. `Support/GitHubIssues` reads every page of the repository's open issues (`gh api repos/<owner>/<name>/issues?state=open&per_page=100 --paginate --slurp`, the answer validated as a list of pages of issues with a number and a body, empty bodies read as empty, pull requests skipped) and picks the oldest whose body holds the line `<!-- intakt:journey-alarm -->`. None: `gh issue create` with the labels `priority:urgent` and `ready` and the title `fix(journeys): journey "<name>" fails on main` (the name cut at 60 characters), or `fix(journeys): <N> journeys fail on main` for several; its answer must be a link ending in `/issues/<number>`. - **Alarm on a timed-out run** (`bin/journey-alarm --timed-out [--run=<link>] [<file>]`): the command builds the run and passes it to `Support/JourneyAlarm::raise()`.
  It uses `JourneyRun::timedOut()` with `--timed-out` and `JourneyRun::fromOutput()` without.
  With `--timed-out` the output is not parsed: the run counts as red whatever it holds, so a cut-off or empty output files or updates the task instead of being refused.
  Only without the flag is unreadable or empty output refused.
  The task's title is `fix(journeys): the journeys run timed out on main`.
  Its body says ``The journeys run on `main` timed out, so its output may be cut off.`` instead of ``The journeys failed on `main`.``, names no journey, and keeps the run link and the tail.
  An open marked task gets only its body replaced, so its title stays.
  `JourneyAlarmTest` starts the binary with `--timed-out` on a cut-off output, on an empty one, and with a marked task already open.

**Testing a PHPStan rule.** A rule's test class in `tests/Gates/` extends `PhpStanRuleTestCase` (built on PHPStan's `RuleTestCase`) and returns the rule from `ruleFor(string $root)`, built as `config/gates/phpstan.neon` wires it, with `$root` for `%currentWorkingDirectory%`. The three deprecation rules report together, so their test asks `tests/Gates/DeprecationRules.php`, which hands each node to every one of them whose node types match (PHPStan's `CompositeRule` takes rules of one node type only). Its fixtures are folders under `tests/Gates/Fixtures/`, where a file `*.php.fixture` is copied as `*.php`. Each rule test class judges a few of its cases, at least one rejected case, through `bin/check --only=phpstan` on a sandbox copy, in one run per class (the one-run helper below), so the rule's registration in `phpstan.neon` stays covered end to end; `ContainerRegistrationTest` runs none through `bin/check`. Since the gate dumps the checked tree's container into the tree's own `var/cache/`, such a sandbox borrows this repository's `bin/console` through a link (`Sandbox::borrowKernel()`, which `StaticAnalysisGateTest` calls too) and gets this repository's container built in its own cache. `assertRejectedBy('phpstan', ...)` and `assertAcceptedBy('phpstan', ...)` of the `UsesSandboxes` trait, which no rule test class calls (`CodingStandardsGateTest` calls the latter for its compliant class), run on a sandbox copy that the runs of one test class share (`Sandbox::ownedBy()`, a folder named by a hash of the process id and the test class, so it holds no static state; the trait removes it in `setUpBeforeClass()` and `tearDownAfterClass()`; `tests/Gates/SandboxTest.php` covers it), whose fixture `Sandbox::replaceFixtureWith()` swaps while it keeps `var/`, so the container, which bakes in the folder it was dumped in, is built once per class and the later runs only warm it up. `ContainerUnknownGetIdRuleTest` (six cases) and `ContainerUnknownHasIdRuleTest` (five cases) judge more cases through `bin/check`, because in the in-process analysis their rules get a service map without services (`tests/Gates/NoServices.php`), so only a full run judges an id against the checked tree's dumped test container: ids in a union, the invalid-behavior argument named last and private services with the test container (`get()`), and a locator typed as `Psr\Container\ContainerInterface` (`has()`). Their cases that do not depend on the container (a single id left to phpstan-symfony, a locator's own keys, the container bag) run in-process. These classes, `ContainerUnknownParameterRuleTest`, `ContainerDumpingGateTest` (a misspelled and a registered service id), `NoDeprecatedReferenceRuleTest`, `ClockOnlyRuleTest`, `NoMockOptOutRuleTest`, `ImportFormRuleTest`, `StatefulServiceResetRuleTest`, `NoNestedTryRuleTest`, `FlagParameterRuleTest`, `ReSpelledNameRuleTest`, `ParameterLimitRuleTest`, `FinalClassRuleTest` and `NoStaticPropertyRuleTest` make one `bin/check --only=phpstan` run per class for all such cases: their data provider hands each case's fixture and expected findings to `casesOfOnePhpstanRun()` of the `UsesSandboxes` trait, which copies each fixture into a folder of its name (`Sandbox::withFixturesInFoldersUnder()`), borrows the kernel, runs the gate once, removes the sandbox in a `finally` block and hands the run to every case, named as the test it replaced (for example `--filter 'testEachFixtureReportsItsFindingsUnderItsFolder@ReadingAMisspelledParameterNameFailsStaticAnalysis'`). `StatefulServiceResetRuleTest`, `ReSpelledNameRuleTest`, `FinalClassRuleTest` and `NoStaticPropertyRuleTest` pass `'src/'` as the parent of those folders, because their rules judge only files under the checked tree's `src/` (`ContainerRegistration`; `ReSpelledNameRule` also its `config/`; `FinalClassRule` and `NoStaticPropertyRule` also its `tests/`, `bin/` and `config/gates/src/`), so a fixture folder at the tree's root would pass unjudged; a fixture's `src/Mailer.php` lands at `src/<fixture>/src/Mailer.php` and its findings are expected under `src/<fixture>/`. `assertFindingsUnderItsFolder()` then expects exactly the case's findings under `<fixture>/`, none for a fixture that must pass, and fails every case of a run whose gate reported no result, a finding that names no file (such as a container that could not be dumped) or a nonzero `omitted` count (the gate shows at most its first findings, so an omitted one could belong to an accepted fixture), so a broken or truncated run cannot pass the accepted cases (`tests/Gates/OnePhpstanRunFindingsTest.php`). Every other case analyzes its sandbox in the test's own process with only that rule: `assertRuleRejects(<fixture>, <finding>)` expects the finding, `assertRuleAccepts(<fixture>)` expects none from this rule, and `ruleFindingsOf(<fixture>)` or `ruleFindingsIn(<sandbox>)` return the findings in the gate's form (`<path>:<line> <identifier> <message>`, the path relative to the sandbox). Like the gate, this analysis skips the folders listed under `excludePaths` in `config/gates/phpstan.neon` (read from that file): `vendor`, `var`, `upstream` and `tests/Gates/Fixtures`.
