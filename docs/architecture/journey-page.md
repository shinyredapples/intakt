# The journey page

`bin/journey` regenerates the numbers, tables and charts of `docs/journey.md` and draws its charts and timeline as SVG files in `docs/journey/`. The classes live in `tests/JourneyPage/` (namespace `Intakt\Tests\JourneyPage`), beside the tests that run them, like `bin/journey-alarm`; they are tooling, not application code.

## Inputs

- The GitHub API, read when the command runs: milestones, issues and pull requests of `GITHUB_REPOSITORY` (`<owner>/<name>`), each with `gh api repos/<owner>/<name>/<resource>?state=all&per_page=100 --paginate --slurp` (`GhCliApi`). `gh` takes its token from `GH_TOKEN` or `GITHUB_TOKEN`; without one the command exits 1 before any call. Pull requests are read from the pulls resource and skipped in the issues list. `GitHubReader` validates each answer (a list of pages of objects, a known state, a date that parses, an issue with a `created_at`, a closed issue with a `closed_at`) and refuses anything else with exit 1.
- `--recorded=<folder>` reads `milestones.json`, `issues.json` and `pulls.json` from a folder instead (`RecordedApi`): the same `--slurp` shape, no network and no credentials. The tests use `tests/JourneyPage/Fixtures/api/` and `tests/JourneyPage/Fixtures/api-later/`.
- `docs/journey/usage.jsonl`: JSON lines `{"day","vendor","account","lane","tokens","reserved"}`: `tokens` is what the providers' usage answers reported, `reserved` the reservations of steps that were killed before they reported usage, kept apart because one is measured and the other estimated. `UsageReader` refuses a line that does not hold exactly these six fields, in any order (so a limit, a reset time or a quota never passes through, and a line without `reserved` is never read as having none), `tokens` or `reserved` that is not a whole number of zero or more, an empty text field, a `day` that is not a real `YYYY-MM-DD` date, and a vendor (`claude`, `gpt`), account (`claude-1`, `claude-2`, `claude-api`, `gpt-1`) or lane (`build`, `review`) outside the backed enums `UsageVendor`, `UsageAccount` and `UsageLane`. An account is shown only by its `UsageAccount` name (Claude account 1, Claude account 2, Claude API key, GPT subscription), never by an email or a plan.
- The page's own Mermaid block that starts with `timeline` (`MermaidTimeline`): `title`, `section` and `<period> : <event> : <event>` lines, and lines starting with `:` that add events to the period above. Events are split at a colon with spaces around it, so `18:00` stays in one event. A page without exactly one such block, a period before the first section, or a line of another form refuses the whole run.

## Outputs

Only the lines between `<!-- journey:begin NAME -->` and `<!-- journey:end NAME -->` change (`MarkedRegions`); everything else on the page stays byte for byte, the Mermaid timeline block included. A name with no marker or more than one, or an end marker before its begin, refuses the whole run and writes nothing.

- `glance`: first merged pull request, pull requests merged (to today's date from the clock), issues closed (done, and dropped for closed as not planned or as a duplicate), busiest day by merges (the earliest on a tie) and tokens per merged pull request (the measured total, `Usage::total()`, divided by merged pull requests). Each figure is followed by its `FigureKind` marker through `Figures::marked()` (both in `Intakt\Core\Platform\Contract`): the merge and issue counts `counted`, the token figures `measured`, and tokens per merged pull request as `<ratio> measured (<total> measured tokens over <merges> counted merges)`, so the ratio of a measured to a counted figure never stands alone. When the usage file holds reserved tokens (`Usage::reserved()`), the parentheses end with `; not included: <reserved> estimated tokens reserved for killed steps`, so the estimated part stands beside the measured one and is never added to it. The table is followed by one line naming each kind's source (`FigureSource`): `Counted: from the pull requests and issues the GitHub API lists. Measured: ` and `TokenCharts::USAGE`, then, with reserved tokens, `Estimated: ` and `TokenCharts::RESERVED`. A first commit, a first release and first-pass approvals have no source among the inputs, so the table has no such rows.
- `milestones`: one row per milestone ordered by due date (none last): title, goal (its description), due date, the day of the last issue closed as done (`open` while an issue is open, `none` when no issue is open and none was closed as done), and done / open counts under the column `Done / open (counted)`. The table is followed by the line `Counted: from the issues the GitHub API lists, by each issue's milestone.` (`FigureSource`). Dates are `MM-DD`, with the year for any other than 2026. A title or goal is written as literal text, so text from the forge can open no comment, write no journey marker and add no Markdown: it is trimmed, each line break (`\r\n`, `\r` or `\n`) becomes one space, every ASCII punctuation character kramdown reads as Markdown (`` \ ` * _ { } [ ] ( ) # + - . ! : | " ' $ > ``) gets a backslash in one pass (the backslash itself included, so nothing is escaped twice), and then, in one more pass, `&` is written `&amp;` (so no entity in the text renders), `<` is written `&lt;` and `~` is written `&#126;` (so `~~` cannot strike text through).
- One region per chart (`ChartRegion`): the image `![<title> (<kind>)](journey/<name>.svg)`, then a line `<Kind>: <source>.` from the chart's `FigureSource` (its `FigureKind` and where its series come from, never `FigureKind::source()`, which names Intakt's ledger), then a `<details markdown="1">` block with the same numbers as a table (one row per day, `none` for a day without a value) whose series columns read `<series> (<kind>)`, so the chart never depends on color or sight alone.

| Region and file | Chart | Days | Series | Kind |
|---|---|---|---|---|
| `tokens-by-lane` | stacked bars (`StackedBarSvg`) | each day from the first to the last day in the usage file | measured tokens (the `tokens` field, never `reserved`) of each vendor and lane that has usage (`Claude, building`, `Claude, reviewing`, `GPT, building`, `GPT, reviewing`, in that order) | measured |
| `tokens-by-account` | stacked bars | the same | measured tokens of each account that has usage, in `UsageAccount` order | measured |
| `tokens-per-merge` | line (`LineSvg`) | the same | the day's measured tokens divided by the pull requests merged that day (UTC) as counted for this usage file, none on a day without a merge | measured (tokens over counted merges) |
| `issues-per-day` | grouped bars (`GroupedBarSvg`) | each day from the first issue created to the last issue created or closed | issues created and issues closed (done or dropped) that day | counted |
| `open-issues` | line | the same | issues created minus issues closed up to the end of the day | counted |

The merges per usage day are counted once for each version of the usage file (`CountedMerges`): the `tokens-per-merge` region ends with the line `<!-- merges counted for usage sha256:<SHA-256 of usage.jsonl>: <YYYY-MM-DD>=<merges> ... -->`, inside its markers, and while the SHA-256 of `usage.jsonl` matches that line, a rerun takes the counts from it instead of counting the merges again. A changed usage file, or a line that does not read as counts, counts them again from the API and writes the line anew. A count reads as one only as a whole number from 1 to 999,999,999 without a leading zero, so a line edited to a count of zero does not read as counts either. So with an unchanged `usage.jsonl` the token charts and their tables stay byte for byte the same, even after another merge on one of its days; the issue charts end on the last event, not on today, so a rerun on a later day draws the same charts.

The drawings follow the look of the charts first drawn by hand for the page (`ChartCanvas`): a 920 pixel wide surface `#fcfcfb`, four gridlines up to a round top (1, 2, 4, 5 or 10 times a power of ten, `YScale`), at most nine day labels, bars with a 4 pixel rounded top and a 2 pixel surface gap between stacked or neighboring bars (between grouped bars at most a quarter of a bar's share of the day, so a long chart keeps a width for each bar), a legend for two or more series, a 2 pixel line whose last value is labelled and whose values without a neighboring value are drawn as dots, and `role="img"` with an `aria-label` and a `<title>`, both the chart's title followed by its kind in parentheses (`DailyChart::caption()`), which the `<summary>` of its table uses too. Series colors come from the fixed order of `ChartPalette` (`#2a78d6`, `#eb6834`, `#1baf7a`, `#eda100`), given by the series' place in the chart and never cycled: a fifth series refuses the run. `ChartPaletteTest` checks that every two of these colors stay at least 8 apart in OKLab (times 100) for typical vision and for simulated protanopia, deuteranopia and tritanopia (the full-severity matrices of Machado, Oliveira and Fernandes, 2009). Coordinates are written with at most two decimals, so a rerun writes the same bytes.

`TimelineSvg` draws the Mermaid timeline as `docs/journey/timeline.svg` for GitHub Pages, whose Jekyll does not render Mermaid: the title, each section with a rule, and each period with one event per line. github.com keeps rendering the Mermaid block itself; `docs/journey.md` does not reference `timeline.svg`, only the Pages copy below does.

The command computes everything before it writes, then writes each SVG and last `docs/journey.md`, only the files whose content changed, and prints `<path> regenerated` for each. When nothing changed it prints `docs/journey.md and its drawings are current` and writes nothing, so a rerun with the same inputs leaves every file alone. A file it cannot write exits 1 with `cannot write <path>`, before the page is written.

## The Pages site

`bin/pages <folder> [--recorded=<folder>]` writes the Jekyll source of the whole GitHub Pages site into `<folder>` (made when missing). It runs `bin/highlights`, then `bin/journey` with the `--recorded` option passed through unchanged, each as `PHP_BINARY` with its output passed on; when one exits non-zero, `bin/pages` exits 1 without running the next and without writing into `<folder>`. Then it writes:

- `index.html` and `assets/<path>`: copies of `docs/pages/index.html`, the front page, and of every file under `docs/pages/assets/`, subfolders included, at the same relative path.
- `highlights/index.md`: `docs/highlights.md` with one line after its title that links the journey page relatively (`[the journey](../journey/)`), then, when `--recorded` holds a readable `issue-states.json`, the settled row statuses and the one-sentence rule ([The published highlights page](highlights-page.md)).
- `journey/index.md`: `docs/journey.md` with every `](journey/` turned into `](`, so the chart images resolve from `/journey/` (correct only because `docs/journey.md` links nothing under `journey/` except the `*.svg` drawings copied beside the page, which `PagesCommandTest` checks on the repository's page), and the Mermaid timeline block (matched by `MermaidTimeline::BLOCK`) replaced with `![Timeline](timeline.svg)`.
- `journey/<name>.svg`: a copy of every `docs/journey/*.svg`.

Like `bin/journey`, it writes only the files whose content changed, printing `<folder>/<path> written` for each, or `site is current` when nothing changed. It removes nothing: a drawing removed from `docs/journey/` stays in `<folder>/journey/` when the command runs again into the same folder; a build into a fresh folder is not affected. Before writing anything, it exits 1 when a source file cannot be read, naming the file, and when `<folder>` holds a root `index.md` from the old layout, which the front page replaces. Outside `<folder>` it writes only what `bin/highlights` and `bin/journey` regenerate under `docs/`. `tests/JourneyPage/PagesCommandTest.php` runs it on the recorded answers and the usage fixture. The `build` job of `.github/workflows/highlights.yml` runs `bin/journey-record _journey-api` on the runner with its own token (`issues: read`, `pull-requests: read`), then `bin/pages /page --recorded=/workspace/_journey-api` in the CI image, so the journey page is published at `/journey/` beside the highlights.

`bin/journey-record <folder>` is a POSIX `sh` script for the CI runner: the CI image has no `gh`, and the token stays out of the container. For `milestones`, `issues` and `pulls` (the cases of `JourneyResource`; `JourneyRecordCommandTest` checks that the script asks for each `JourneyResource::path()`) it runs `gh api repos/$GITHUB_REPOSITORY/<resource>?state=all&per_page=100 --paginate --slurp` into a hidden draft folder inside `<folder>`, and only after all three succeeded moves them to `<folder>/<resource>.json`, the files `RecordedApi` reads. An empty `GITHUB_REPOSITORY` exits 1 before any call; a failing `gh` exits 1 and the draft folder is removed, so no new file is left and earlier recordings stay as they were; a missing folder argument exits 2. After the move it removes any earlier `<folder>/issue-states.json` and writes a new one with `jq` (`[.[][] | objects | {number, state}]` over `issues.json`, through the draft folder) for the highlights statuses of `bin/pages` (`IssueStates::FILE`); a failing `jq` prints a warning, leaves no state file and still exits 0, so the journey page is never lost to it. It prints no environment value, the token included.
