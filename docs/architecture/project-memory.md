## Project memory

`Core/Memory` keeps what Intakt learned about a project and hands the part that concerns some files to a reviewer. Its `Contract/` has two interfaces, kept apart on purpose: `ProjectMemory::relevantTo(MemoryQuery)` is retrieval only and is what a reviewer is given, `ProjectMemory::settledOn(SettledQuery)` is its second read, and `MemoryIndex` writes and belongs to the orchestrator (`index(MemoryEntry)`, `settle(SettledFinding)`, `forget(SettledFinding)`). No Symfony AI type crosses the contract.

- **Entry:** `MemoryEntry` is the project it belongs to, a text and the repository-relative paths it describes (a `Git\Contract\Paths`, as are the files of a `MemoryQuery`). Indexing goes through the Store's `DocumentIndexer`: `MemoryDocuments` turns an entry into a `TextDocument` (the paths and the text are embedded together, the project is kept in the metadata; the id is the SHA-256 of the JSON of the project, the path list and the text, so indexing the same entry twice keeps one copy, the same note in two projects stays two entries, and path lists that join to the same text, such as `a b.php` and `a`, `b.php`, stay two entries).
- **Settled findings:** a second kind of entry, for a finding the judge or an escalation review rejected (written by `Core/Review`, see **Settling rejections** below). `SettledFinding` is the project, the finding text, the reason it was rejected and a `CodeSnapshot` (file, symbol, content hash; the symbol is empty for a whole file). The caller computes the hash, so Memory never reads git. `MemoryDocuments::toSettledDocument()` stores it with `kind` = `settled` in the metadata; a document without a kind is a resolved finding, so older rows keep working, and `ofProject()` (resolved) and `settledOfProject()` keep the two kinds apart: `relevantTo()` never returns a settled finding and `settledOn()` never returns a resolved one. The id is the SHA-256 of the JSON of the kind, project, file, symbol and text, without the hash and the reason, so `settle()` of the same finding after its code changed replaces the entry, and `forget()` needs no hash. `settle()` first embeds the new document with the `memory` vectorizer, so a failing embedder (`ProjectMemoryNeedsEmbeddingModel` without an embedding account, or a platform error) propagates and leaves the earlier entry untouched; only then does it add the embedded document to the store. The SQLite store replaces the row with that id inside its own transaction, so a failing insert keeps the earlier entry; only the in-memory store, which keeps a second copy under the same id, has the old id removed first.
- **Settled and stale:** `settledOn(SettledQuery)` takes the project and the current snapshot of each file and symbol on main that the caller asks about. `SettledMemory` holds `settled` (the stored hash equals the current one) and `stale` (it differs: main changed that code, so the entry is flagged and is not given as settled). An entry about a file and symbol not in the query is in neither list. With no snapshots the result is empty. Deleting is `MemoryIndex::forget()` through the Store's `remove()`; a deleted entry is not returned. A settled document missing its reason, file, symbol or hash throws `StoredMemoryIsMalformed`. `OptionalProjectMemory::settledOn()` turns a failed read into no settled entries, as for `relevantTo()`.
- **Projects kept apart:** one install serves several projects from one store, so every `MemoryQuery` names its project and `StoreProjectMemory` hands the `Retriever` the store's `filter` option with `MemoryDocuments::ofProject()`: only documents whose metadata names that project are ranked at all. A document without a project (written before entries had one) belongs to no project and is never retrieved.
- **Retrieval:** `StoreProjectMemory` asks the Store's `Retriever` with the file paths as the query, double quotes replaced by spaces: the SQLite store puts each term in an FTS5 phrase without escaping a quote, so a path such as `src/Quote"d.php` would make the query fail (`upstream/ai-sqlite-store-unescaped-fts-quote/`); FTS5 drops quotes when it indexes anyway. The store only ranks (a hybrid query, as the Retriever picks for a store with vectors), it does not decide relevance: plain code keeps the entries that describe at least one of the queried files. With no files the result is empty.
- **Cap:** `RelevantMemory::within()` takes the entries most relevant first and keeps them until the next one would pass `MemoryQuery::maxBytes`, counted in bytes of the entry text. It stops there, so a less relevant entry never fills the room a more relevant one did not fit. The most relevant entry is kept whole even when it alone passes the cap, so the caller can shorten it instead of getting nothing. The cap is applied by this code, not by the store's `maxItems`.
- **Store:** production uses `symfony/ai-sqlite-store` (SQLite FTS5 for text, vector similarity computed in PHP, needs only `pdo_sqlite`). It loads all vectors into PHP memory for each query and applies the project filter there, which is fine at the size of one install's memory. Tests use the in-memory store with a scripted embedding platform (`MockPlatformFactory`), and two tests in the `persistence` group run the same flow on the SQLite store: one on a store it builds itself, one through the container on the configured `memory` store and file, with the scripted platform set in place of `EmbeddingsNotConfigured` in the test container. `tests/Probe/SettledMemoryFlow.php` runs that settle, stale and forget flow through `bin/probe` on a booted instance and its memory file. A reranker is not used: no configured provider supports reranking.
- **Indexing resolved findings:** `Core/Review` is the only caller of `MemoryIndex`. `QueueIndexingOfCompletedRound` is an `AsCompletedListener` on the `complete` transition of `review_round`, so it runs once per round inside the completing transaction and queues `IndexResolvedFindings(roundId)` on the `async` transport (routed in `config/packages/messenger.yaml`); a second completion finds the guard closed and queues nothing. The resolved findings are fixed when the round completes, in the step that records its verdicts on the change's ledger under its lock: the ids the round's verdicts list as `resolved` (a failed review's verdict counts for nothing) that the ledger then holds as resolved are stored as JSON with the round (`review_round.resolved_findings`, migration `Version20261101130000`; none for a round completed before it), so a finding another reviewer reported again in the same round, which stays open, is not indexed, and a later round that reopens a finding before the worker runs cannot erase the earlier resolution. A round overtaken by a newer recorded round of the change (its number is below the change's `recorded_round` when it completes) keeps an empty list and indexes nothing, because its verdicts never reach the stored ledger, where the newer round may hold the finding open. `IndexResolvedFindingsHandler` runs in a worker, outside any transaction, and reads them back with `StoredFindings::resolvedBy()`. Each becomes one `MemoryEntry` of the round's project: the text is `Resolved finding: <text>`, then `Cause: <requirement>` and `Evidence: <probe>: <output>` when the finding has them, and the files are the finding's file (none when it has none). The text is stored as the reviewer wrote it and is fenced when a briefing puts it into a prompt (part 3). A redelivered message indexes the same entries again, which keeps one copy of each. No reviewer code (`Review/Infrastructure`, `Contract`, `Domain`) names `MemoryIndex`.
- **Settling rejections:** `UseCase\SettleRejectedFindings` (issue #3525) is the only writer of settled findings. `JudgeRoundHandler`, after `JudgedRounds::record()` committed the judging, asks `RejectedFindings::ofJudgement()` for one `SettleRejectedFinding` message per finding on `JudgedFindings::$rejected` (a P3 the judge marked `reject`; a P1 or P2 marked `reject` stays on the act list and is not settled), dispatches `RoundJudged` and then queues the messages on the `async` transport. The hash is read before `RoundJudged`, because a listener removes the round's checkout then. The reason is the judge's note for that finding, trimmed, or `RejectedFindings::JUDGE_GAVE_NO_REASON` when it gave none. For an escalation, `RecordRecurringP1s` puts the hash of the finding's file in the queued `EscalateRecurringP1` (`codeHash`, null when the recurrence belongs to another round than the one judged, whose checkout may be gone, or the file cannot be read; a message queued before the field existed reads null); after keeping a verdict, `EscalateRecurringP1Handler` reads the key's kept verdict again and, when it is `rejected`, queues the finding with that verdict's reasons. The message holds the project, the text (the symbol and `: ` before it when the finding names one), the reason, the file and the hash, all passed through the `Redactor`, because the checkout is gone by the time a worker runs it. `SettledCode` is the one home of the hash: SHA-256 of the whole file as `CheckedOutFile::contentBehindNoLinkOf()` reads it from the checkout, and the symbol is always empty (`SettledCode::WHOLE_FILE`), because a symbol cannot be cut out of every language reliably. A finding without a file, or whose file is deleted, a link or outside the checkout, is not settled. `SettleRejectedFindingHandler` calls `MemoryIndex::settle()`; a missing embedding model logs one `info` line with the project, as for resolved findings, and any other failure is thrown, so Messenger retries it. A message lost between keeping an escalation verdict and queuing its settling is not queued again, because a redelivered escalation finds its outcome recorded and does nothing.
- **Production wiring:** `config/packages/ai.php` configures the AI bundle's SQLite store (`var/memory_<environment>.db`, one file per kernel environment like `var/data_<environment>.db`; in the test environment `memory.db` in the kernel's cache directory, one per test worker; table `project_memory`, created by `bin/console ai:store:setup`), a vectorizer on `text-embedding-3-small` and the `memory` indexer; `config/services.yaml` points `DocumentIndexer` at that indexer and `MemoryIndex` at `StoreMemoryIndex`, which is also given the `memory` vectorizer and the store itself, for `settle()` and `forget()`. The embedding platform is the enabled OpenAI account; without one `EmbeddingsNotConfigured` stands in and throws `ProjectMemoryNeedsEmbeddingModel` from the indexing message, which `IndexResolvedFindingsHandler` treats as done: it logs the exception's message at `info` level with the project and no trace, once per message, and returns, so the message is neither retried nor sent to the failure transport. Any other indexing failure still propagates, so Messenger retries the message and then sends it to the failure transport. The same file configures the `memory` retriever over that store, and `config/services.yaml` points `Retriever` at it and `ProjectMemory` at `OptionalProjectMemory`, which wraps `StoreProjectMemory`. `EmbeddingsNotConfigured` throws `ProjectMemoryNeedsEmbeddingModel` (in Memory's `Contract/`, a `LogicException`). `OptionalProjectMemory` answers it with no entries and logs its message once per process at `info` level with the project and no trace, however many reviews read memory (a boolean property marked `#[KeptForTheProcess]` remembers it, and nothing resets it between messages); the default logger's minimum level is `warning`, so that line shows only when the level is lowered. Any other failure of the read still logs a `warning` with its trace on every call.
- **Briefing:** `ReviewerPrompt` is given `ReviewerMemory` (itself given `ProjectMemory`, `Fence`, `DiffPaths`, `PromptAssembly` and `SettledCode`) by the container; `messagesFor()` asks `ReviewerMemory::briefingOn()` with the brief, whose change's project and diff make the query, and the checkout of the head under review (`ReviewerAgent` passes the request's), and adds the user messages it returns (built by `PromptAssembly`), each as a message of its own after the diff (before the open findings); with no entries it adds nothing, and a `ReviewerPrompt` built without `ReviewerMemory` (an optional constructor argument) adds no briefing either. **Settled findings come first:** for each file of the diff that the checkout holds, `SettledCode` hashes it, and `ProjectMemory::settledOn()` with those snapshots returns the settled entries whose hash still matches; they are listed as `<file>: <text>` and `Reason: <reason>` in one `project memory` fence under the lead `Project memory, already settled, do not raise again unless this code changed: ...`, which also tells the reviewer to raise one again only to show its reason no longer holds, citing the entry (the judge then decides on that finding as on any other). The hash is of the head under review, main plus the change, so a change of that file on main, or by the change itself, makes the entry stale and it is not given. Without a checkout nothing is given as settled. The notes follow in a second message that gets the room the settled one leaves, so both together stay within the cap below; when less than the empty fence and the shortening marker is left, no notes are given. The system message stays the reviewer's instructions and role prompt, with or without notes: Symfony AI's `MemoryInputProcessor` is not used, because it puts a fixed preamble in front of the system prompt that tells the model the memory outweighs it. `DiffPaths` reads the files under review from the diff's file headers, outside the hunks: both paths of a `diff --git` header, `---` and `+++` paths (not `/dev/null`), and `rename`/`copy` `from`/`to` paths, so a renamed file finds the notes of its old path too; git-quoted paths are decoded and CRLF line ends accepted. A header path with spaces is read only when both sides name the same file. `ReviewerMemory` asks `ProjectMemory::relevantTo()` with a fixed cap of 4000 bytes (a constant, not an option) less the settled message and the notes' introduction and empty fence, so the entries it returns fit once wrapped, joins the entry texts and wraps them in one `project memory` fence under a one-line introduction; it drops the last entries until the whole message, separators, fence and introduction included, fits the room, and the two messages together are at most 4000 bytes; in either message a lone entry that is still too long is cut at a UTF-8 character boundary and ends with ` [note shortened]`. The reviewer is handed `ProjectMemory` only, never `MemoryIndex`, and no memory tool. `OptionalProjectMemory` turns a failed read into no entries (a missing embedding model logs the single info line described above; a store not set up or any other failure logs a warning that carries the project and the exception itself, class, message and trace in the log record), so a missing memory never fails a review. No reranker: no configured provider supports one.
