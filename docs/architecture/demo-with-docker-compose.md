## The demo with docker compose

Plan task T23, part 2. `compose.yaml` builds the image from the `Dockerfile` and runs it as the service `intakt` with the env file `.env.local` (`required: false`, so a clone with no file starts; `.env.dist` is its template: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `HF_TOKEN`, `APP_SECRET`, `MERCURE_JWT_SECRET`, and `MCP_OWNER_TOKEN`, all empty and all optional; `.dockerignore` keeps `.env.local` out of the image), the volume `intakt-data` at `/app/var/data`, the port `127.0.0.1:7781:7781` (loopback only by default), a `healthcheck` that runs `intakt-healthcheck` (`interval` 30s, `start_period` 60s, `start_interval` 2s, so `docker compose up -d --wait` returns soon after the seed and the dashboard are ready), `INTAKT_CONFIG=/app/var/data/intakt.yaml`, `INTAKT_SAMPLE_REPOSITORY=/app/var/data/sample-repository` and `INTAKT_COMPOSE_SERVICE=intakt` (the service's own name; `.env` sets it empty for every other install; `ComposeDemoTest` requires it on every service in `compose.yaml`, so a second service added later has to set it too).

On every start, before the migrations, `docker/entrypoint.sh` hands a non-empty `HF_TOKEN` to the `openai_compatible` provider: when neither `OPENAI_COMPATIBLE_BASE_URL` nor `OPENAI_COMPATIBLE_API_KEY` is set in the environment, it exports `OPENAI_COMPATIBLE_BASE_URL` set to the `router_url` of `config/sample-project.yaml` (`https://router.huggingface.co`, the Hugging Face router; without `/v1`, because the generic bridge appends `/v1/chat/completions`) and `OPENAI_COMPATIBLE_API_KEY` with the token's value. It reads that line with bash alone (`router_url` must stay one plain top-level line), by the path relative to the working directory `/app`; a file without the line, or no file, stops the start before the seed with `intakt: config/sample-project.yaml names no router_url, so HF_TOKEN cannot be used`. An endpoint the owner set in the environment wins, the token is not used and the file is not read. Either way `HF_TOKEN` is one of the held credentials redacted from the log ([conventions](conventions.md)). A token pasted on the first-run page and kept is served as the same two variables by the kept key's env var loader, with the same router URL (through `HuggingFaceDescriptor`) and the same rule, extended to the secrets vault ([AI providers](ai-providers.md)), so the next start's seed writes the sample project with it.

A new demo install opens on the first-run page: `/` answers `303` to `/setup` while the ledger holds no review, and the page opens with **See a real review**, which holds the **Play the demo run** button of the keyless tour when a recording is installed and otherwise says in plain words that the install has no recorded review (#2058), then **Use your own project** with three step cards, where a pasted key and the first review's start open the live review page ([Dashboard](dashboard.md), First-run page).

When `INTAKT_SAMPLE_REPOSITORY` is set, `docker/entrypoint.sh` requires `INTAKT_CONFIG` and, after the migrations, exports the owner's MCP settings (below), rebuilds the container (removes the kernel's cache and build folders as in [the container image](container-image.md), then `cache:warmup` in a new process, because the image's container was compiled at build time without keys or projects, and `cache:clear` kept it after the seed), runs `intakt:sample:seed "$INTAKT_SAMPLE_REPOSITORY" "$INTAKT_CONFIG"` and rebuilds the container again. Then, only when `INTAKT_COMPOSE_SERVICE` is set as well, it runs `intakt:demo:create`, which marks the demo project `demo-replay` as a replay ([The demo recording](demo-recording.md#the-demo-project)), the project `intakt:demo:replay` writes a recording's ledger events into, run by hand and refused without the same variable ([Replaying the ledger events](demo-recording.md#replaying-the-ledger-events)); a plain `docker run` with a sample repository, such as the CI smoke start, skips it. A failed seed or a failed `intakt:demo:create` stops the entrypoint before the server starts. Without the variable nothing of this runs. The dashboard's first-run page reads the same variable as the repository of the sample change it offers to review (First-review step in [Dashboard](dashboard.md)).

The `image` job of `.github/workflows/ci.yml` ([CI](ci.md)) runs `docker/verify-first-start.sh intakt:ci` on the image it built for the smoke test: the image on an empty volume with a placeholder key, then, once the admin API answers, `intakt:review:panel sample` in the running container. No model is called. It is a smoke check, because a stale container did not fail every start; `EntrypointSampleSeedTest` plants one before and after the seed and requires both removed.

`Core/Review/UseCase/SeedSampleProject/SeedSampleProjectCommand` (`intakt:sample:seed <repository> <configuration>`) holds the lock `review-sample-seed` (waited for) while it seeds, each part only when it does not exist yet:

- **The project:** `SampleProject` asks the Ai module's `Contract\EnabledAccounts` which of Anthropic, OpenAI and `openai_compatible` (in that order; the providers one key enables) have an enabled account; `openai_compatible` counts only when `OPENAI_COMPATIBLE_BASE_URL` is exactly the `router_url` of the sample project's data file (`https://router.huggingface.co`), because its seeded models are router models another endpoint would not know. With none it warns `Set ANTHROPIC_API_KEY or OPENAI_API_KEY or HF_TOKEN to seed the sample project; the next start with one writes it.` (names from `Provider::variables()`, with `HF_TOKEN` for `openai_compatible`), writes no file and goes on to the repository, and the command exits 0, so a start without a key still reaches the server and the health check; the file being absent, the first start with a key writes it. Otherwise it maps the tiers `strong` and `light` to the first keyed provider and `standard` to the last (one key: all three on it; two or three keys: `standard` on the last of them), each with the model the data file names for that provider and tier (shipped: `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`; `gpt-6.2-sol`, `gpt-6.1-terra`, `gpt-6-luna`; `moonshotai/Kimi-K3.1-Pro:deepinfra` for every router tier), except `standard` when `strong` is on the router too, which gets the file's `second_lab` (`deepseek-ai/DeepSeek-V4-Pro-0813:deepinfra`), so a panel on the token alone still has models of two AI labs. The file also gets a top-level `budget.price_date` and a `budget.prices` block with the data file's `price_date` and its list price of each of those models it names (see [Round cost](round-cost.md)), so the first review's cost is a figure.

The data file `config/sample-project.yaml` is the one home of these provider facts (decision D2 of #2328), so refreshing the five-minute start is an edit of that file: `router_url`, `price_date`, `models` (per provider and tier), `second_lab` and `prices` (per model, US dollars per million tokens). `Core/Review/Contract/SampleProjectData` reads it with Symfony Yaml on every call, found from its own folder (`SampleProjectData::SHIPPED`) because `config/packages/ai.php` builds the key catalog before the container exists; a missing entry, an empty text, a router URL that is no URI or a price that is not amounts by kind is a `LogicException` naming the file and the entry's path, and a missing or unreadable file is Symfony Yaml's `ParseException`. `price(model)` returns the amounts as one `Review\Contract\ModelPrice`, which iterates them by kind in the file's order. Three places read it: `SampleProject` (models, the second reviewer's model, prices, price date and router URL), the Hugging Face descriptor of the key check (the router URL, see [AI providers](ai-providers.md#provider-descriptors)) and `docker/entrypoint.sh` (the router URL, above). The router models name their router provider after the colon, because the router's default provider may refuse tools together with structured output (Groq and Cerebras did; DeepInfra accepted both for the seeded models). It builds the panel as Review's `Contract\Panel` (quorum `all`; `correctness` on `strong`, `security` on `standard`, budget 10 each, each on the provider its tier maps to) and writes project `sample` with `tiers` and `review` as YAML to the configuration file, which `config/packages/ai.php` then reads and validates like any project file. An existing file is kept as it is, whatever it holds.
- **The repository:** `SampleRepository` builds what `fixtures/sample-repository/README.md` describes (`main` from `base/`, `sample-change` adding `pull-request/`, `main` checked out) with `Core/Git/Contract/HardenedGit` calls (`init` names its own `--git-dir=.git`, because git refuses the pinned work tree without one), a fixed author, committer and date (`2026-11-01T00:00:00+00:00`), so every install builds the same commits. It builds in a sibling `<repository>.partial-<random>` directory and renames it into place, so an interrupted build leaves nothing a later start would keep. An existing directory is kept untouched.

The owner's MCP token is made by `docker/entrypoint.sh`, not by the command: in the demo branch (`INTAKT_SAMPLE_REPOSITORY` set) it exports `MCP_OWNER_ACCESS` (default `mcp_tool_write`, so a client can start a review) and `MCP_OWNER_TOKEN`. A token from `.env.local` wins; otherwise the file named by `MCP_OWNER_KEPT_FILE` (set by `compose.yaml` to `/app/var/data/mcp-owner-token` on the data volume, and the only place the name is written) is read, or made first: a draft from `mktemp` (mode 0600) gets 32 random bytes as hex (`od`, `tr`) and is hard-linked into place with `ln`, which fails when another start linked first, so starts at once on one volume all read the same complete token. The token is assigned before it is exported, so a failed write is not hidden; anything but 64 hex characters (the folder missing or read-only, the name taken by a folder) stops the start before the seed with `intakt: could not make or read the MCP owner token in <file>; set MCP_OWNER_TOKEN or make its folder writable`. `MCP_OWNER_KEPT_FILE` comes from compose's `environment:`, not from the entrypoint's exports, so a process started by `docker compose exec`, which never runs the entrypoint, sees it too. The exports come before the first container rebuild, so the seed, the web process and the workers see them, and the token does not change on a restart.

The two secrets use the same mechanism (`kept_secret`, shared with the token) before anything else: for `APP_SECRET` and `MERCURE_JWT_SECRET`, when the variable is empty, `export_secret` reads or makes `app-secret` and `mercure-jwt-secret` beside `INTAKT_CONFIG` (32 random bytes as hex, mode 0600, linked into place so starts at once agree) and exports it; a value from `.env.local` or `-e` wins and writes nothing; nothing is echoed to the log. Without a value and without `INTAKT_CONFIG` the start stops naming the variable, and anything but 64 hex characters stops it with `intakt: could not make or read <NAME> in <file>`. The `${NAME:?` guards stay after it, because the Caddyfile reads `MERCURE_JWT_SECRET` without a default.

The seed prints no review command, and neither does the start. In the demo branch the entrypoint removes `var/sample-ready` before anything else and touches it after the second container rebuild and the provider notes, so it exists only once the seed has run in this start; `docker/healthcheck.sh` (the image's `HEALTHCHECK` and compose's `healthcheck`) fails until the admin API's `/metrics`, the dashboard and that mark all answer, and without `INTAKT_SAMPLE_REPOSITORY` it needs the first two only. Once the web server and the workers are started, the entrypoint's one-second poll (the one that restarts ended consumers) also asks, until both answer, `/metrics` (`http://${CADDY_ADMIN:-localhost:2019}/metrics`) and then the dashboard (`http://localhost:${SERVER_PORT:-7781}/` with `Host: localhost:$DASHBOARD_PORT`) with `curl --fail --max-time 2`. On the first poll where both answer it prints `intakt: the dashboard is ready at http://localhost:$DASHBOARD_PORT` once and never asks again. Asking from the poll instead of waiting before it keeps crashed consumers restarting while the server comes up. Each `curl` call runs as a background job the script waits for (`as_job`: `"$@" &`, then `wait "$!"`), because bash runs the TERM trap only after a foreground command ends: a health check that took its two seconds would add its time to the stop's 8 second grace and pass Docker's 10 second stop timeout. `wait` returns at once on a trapped signal, and the stop ends the job with the other children, because it reads them from bash's job table (see `container-image.md`). The two seconds per `curl` call only keep a stuck server from holding the poll, and with it the restart of an ended consumer. A start without `INTAKT_SAMPLE_REPOSITORY` never asks.

`Core/Review/UseCase/ShowSampleReview/ShowSampleReviewCommand` (`intakt:sample:show <repository>`), its own use case beside the seed's, reads the seed's `SampleProject` and `SampleRepository` constants and prints one block between two lines of `=`: `Open the dashboard: http://localhost:<DASHBOARD_PORT>`, then the `intakt:review` command line for `sample-change` with the project, the repository, the base and the task `SampleProject::TASK`, as `php bin/console intakt:review ...`, preceded by `docker compose exec <service> ` when `INTAKT_COMPOSE_SERVICE` is not empty, so the compose demo's reader runs it from the host shell in the repository folder (when `SampleProject::isWritten()` finds no file at the project file path, the container parameter `intakt.review.project_file` that `config/packages/ai.php` sets to the file `INTAKT_CONFIG` names or `config/intakt.yaml`, as after a keyless start, it prints `No sample project yet: set <variables> and start again to write it, then run intakt:sample:show again.` in place of the review command, the variables from `SampleProject::keyVariables()` joined by ` or `), then the `claude mcp add` line for `<REVIEW_MCP_BASE_URL>/mcp/owner` with the token as a bearer header, or, when there is no token, one line `No MCP owner token found: set MCP_OWNER_TOKEN in .env.local ...` (built by `Core/Mcp/Contract/OwnerClientLine::setup()`, which `intakt:demo` uses too and which single-quotes a token or address the shell would expand; the token comes from `Core/Mcp/Contract/OwnerToken`, which returns `MCP_OWNER_TOKEN` when it is set and otherwise the content of `MCP_OWNER_KEPT_FILE` when that is 64 hex characters (a missing or unreadable file is no token, read through Symfony Filesystem's `readFile()`, so it gives the hint line and no PHP warning), so the line has the token the server accepts also under `docker compose exec`; the image sets `REVIEW_MCP_BASE_URL` to `http://localhost:7781`). Each line is printed whole, never wrapped, so it copies as one command. The entrypoint no longer runs it; the reader runs it by hand (`docker compose exec intakt php bin/console intakt:sample:show /app/var/data/sample-repository`), so the review command and the MCP line are not in the start log. The dashboard address line is the last thing the entrypoint prints: the consumers start with `--quiet`, so no consumer banner follows it (see `container-image.md`); request logs the server writes later can still follow it.

`intakt:demo` is the terminal fallback that runs the review itself: in the compose demo, `docker compose exec intakt php bin/console intakt:demo` reviews `sample-change` of the repository in `INTAKT_SAMPLE_REPOSITORY` for the project `sample` and prints the outcome, the act list, the review's dashboard address and the `claude mcp add` line, with `intakt:review`'s exit codes (see the demo command in [Forge contract](forge-contract.md)). Like `intakt:review`, it waits for the container's workers to review and judge.
