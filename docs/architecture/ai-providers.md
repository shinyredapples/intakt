## AI providers

`config/packages/ai.php` configures the AI Bundle platforms `anthropic`, `openai` and a generic endpoint named `openai_compatible` (packages `symfony/ai-anthropic-platform`, `symfony/ai-open-ai-platform` and `symfony/ai-generic-platform`, pinned like the other Symfony AI packages). Each provider is a case of the `Intakt\Core\Ai\Contract\Provider` enum, which lists the environment variables it needs (`ANTHROPIC_API_KEY`; `OPENAI_API_KEY`; `OPENAI_COMPATIBLE_BASE_URL` and `OPENAI_COMPATIBLE_API_KEY`; `CLAUDE_CODE_OAUTH_TOKEN`; none for `codex`, whose credential is a login file).

Hugging Face's Inference Providers reach Intakt through `openai_compatible`, with no package of their own: in the image, `docker/entrypoint.sh` sets its two variables from `HF_TOKEN` with the base URL `https://router.huggingface.co` (no `/v1`, because the generic bridge appends `/v1/chat/completions`), and the demo seed puts router models on it (see [the demo](demo-with-docker-compose.md)). The pinned generic bridge reads only `error.message` from a failed response, while the router writes `message` at the top level, so a refused call shows only the HTTP reason ("Bad Request"); symfony/ai#2849 reads both and arrives with the next Symfony AI release through the normal dependency update.

The fourth provider, `claude_code`, runs the `claude` CLI through `symfony/ai-claude-code-platform` (pinned like the other Symfony AI packages). The AI Bundle has no configuration for that bridge, so `Intakt\Core\Ai\Infrastructure\ClaudeCodePlatformFactory` builds its platform with the bundle's event dispatcher (the structured output subscribers hang on it), and `config/packages/ai.php` registers it as `intakt.ai.platform.claude_code` when the token is set. `IsolatedClaudeCodeCli` (the service `intakt.ai.claude_code.cli`) builds the bridge's client for every request, so a variable added to a long-running worker's environment is covered too, and runs the CLI in `var/claude-code/` (created on first use, also the CLI's `HOME`) with an environment in which only `PATH`, `HOME` and `CLAUDE_CODE_OAUTH_TOKEN` have a value: Symfony Process passes every inherited variable unless it is overridden by name, and the bridge takes only strings, so every other inherited variable is set to an empty string. `ConfinedClaudeCodeClient` wraps that client: it drops every option the agent passes (the bridge turns each into a CLI flag) except `Core\Ai\Contract\ReviewServerAccess::OPTION`, gives the CLI no built-in tool (`--tools ""` and `--disallowed-tools` naming each built-in), no settings (`--setting-sources ""`), no MCP server but the one it is given (`--strict-mcp-config`) and no saved session, and passes the response format's JSON schema (the `json_schema.schema` part of `PlatformSubscriber::RESPONSE_FORMAT`) as `--json-schema` instead of appending it to the system prompt, and refuses a response format without a schema with the platform's `InvalidArgumentException` before the CLI starts. The CLI holds its answer to that schema and returns it in the result event's `structured_output`; `FinishedProcessResult` puts that value, JSON-encoded, in place of the result's `result` text the bridge reads (the bridge maps no response format to `--json-schema` and ignores `structured_output`, see `upstream/ai-claude-code-platform-structured-output/`), and leaves `result` as it is when the field is absent or null, so the verdict parser still refuses a structured answer that is not a verdict (recordings `structured`, `structured-not-a-verdict` and `structured-null`). The judge's call on `claude_code` (the `light` tier, for example `haiku`) takes the same path: `JudgeAgent` sets `Judgement::class` as the response format, so the CLI gets the judgement's schema as `--json-schema`, and the marks are read from its structured output; an answer that maps to no `Judgement` gives `Judgement::everyBlockingFindingActs()`. The judge's call carries no `ReviewServerAccess::OPTION`, so the CLI gets the no-tool prompt line and no `--mcp-config`. `tests/Plugin/SymfonyAiVendor/ClaudeCodeJudgeTest.php` replays the recordings `judgement-structured` and `judgement-structured-not-a-judgement` through `SymfonyAiVendor::judge()`, checking the marks read, the schema passed and the usage settled once. `SymfonyAiVendor` sets that option on every call of a `claude_code` review whose conversation has a round, from `Review\Contract\ReviewServerAccesses` (`IssuedReviewServerAccesses`: the address, the parameter `ReviewServices::MCP_URL` set in `config/packages/mcp.yaml`, the round's `ReviewCredential` bearer and the names of the three read-only tools, read from their `#[McpTool]` attributes). `ConfinedClaudeCodeClient` passes the option on to `IsolatedClaudeCodeCli`, which writes `ReviewServerAccess::mcpConfiguration()` (only that server and its `Authorization` bearer header) to a file of its own in the CLI's directory (`review-server-*.json`, mode `0600`), passes its path as `--mcp-config` and removes it once the run has been read (`RemovedAfterRun`), or at once when the bridge's client throws before a run exists (the CLI is not on `PATH`, the process does not start): never inline JSON, because Symfony Process puts the command line into its timeout message, which is logged. When no access can be issued (an empty `APP_SECRET`, so `ReviewCredential` signs nothing), `IssuedReviewServerAccesses` throws `Review\Contract\NoReviewServerAccess` and `SymfonyAiVendor` does not start the CLI: it settles the call's reservation with no usage and returns `Verdict::noTools()`, the blocked verdict an API-key reviewer gets when its toolbox lists no tools. `ConfinedClaudeCodeClient` adds `--allowedTools` (`mcp__intakt-review__<tool>` for each of the three) and a prompt line that only those tools are available; without it the line says no tool is available. The allow-list is a second fence: the server's `ToolAccessVoter` still decides every call. The CLI never sees the checkout directly: its own file tools would bypass `Checkout` and `Fence`, so it reads only through the review server, which fences every answer itself (`ReviewedRepository`, see [MCP server](mcp-server.md)). `Provider::readsTheCheckout()` stays false for `claude_code`, because the provider alone gives the CLI no tool; `SymfonyAiVendor` (which resolves the tier through `TierResolver`) decides per call (part 2 of #1252): an `approve` counts when the provider reads the checkout or the call's options carry `ReviewServerAccess::OPTION` and one of the call's rounds reports a read through it (`Contract\ReviewServerReads`; see Codex reviewer below for `codex`). For `claude_code`, `FinishedProcessResult` implements it from the CLI's own stream events, never from the answer's text: a read is a `tool_use` block of an `assistant` event named as one of the access's tools (`ReviewServerAccess::mcpToolNames()`, `mcp__<server>__<tool>`, the same names `ConfinedClaudeCodeClient` allows beside `--strict-mcp-config` and the built-in denials) whose `tool_result` in a `user` event has that block's id and no `is_error: true`, so a refused call, a call without a result and a call to another server are none (#1894), and is otherwise turned into `Verdict::unreadApproval()`, a `blocked` verdict whose finding `unread-approval` gives the reason, as for a `claude_code` call without a round; its usage is settled as usual. The check runs inside each attempt, so a retry at the output limit is judged by its own options. `FinishedProcessResult` turns a run without its final result event into `IncompleteStreamException`, whether the CLI exited, was killed or timed out (a run that wrote its final result and failed stays a failure), and drops the `tool_calls` the bridge collects from the tools the CLI ran itself, so the agent never runs them again (both in `upstream/`); `SymfonyAiVendor` catches that one exception, leaves the call unsettled once and returns `Verdict::incompleteStream()`, a `blocked` verdict. Every other failure keeps its mapping. Without a structured output the CLI answers in prose around one fenced `json` block, so `StrictVerdictSubscriber` has `StrictVerdictConverter` read that block for `claude_code` and `codex` models ([review verdicts](review-verdicts.md)); `FencedVerdictTest` covers the cases and the recordings `fenced`, `two-blocks`, `prose-only` and `not-a-verdict` cover them end to end. `tests/Plugin/SymfonyAiVendor/ClaudeCodeReviewerTest.php` replays recorded streams (`tests/Plugin/SymfonyAiVendor/Fixtures/claude-code/`) through the bridge's own process result, and runs one review through `IsolatedClaudeCodeCli` and the bridge's client against a scripted `claude` on `PATH` to check its exact arguments and configuration file.

**Codex subscription login** (plan T39, part 1). `symfony/ai-codex-platform` is pinned like the other Symfony AI packages. `Infrastructure\CodexLogins` keeps each account's login in `var/codex/logins/<account>/auth.json` and refuses a name that does not match `Account::NAME_PATTERN`, since it becomes a path and a lock key. `handOver(account)` takes the `LockFactory` lock `intakt.codex.login.<account>` (`AiServices::CODEX_LOGIN_LOCK_PREFIX`, blocking), reads the login (`CodexLogin`: `tokens.id_token`, `access_token` and `refresh_token` as non-empty strings and `last_refresh` in RFC 3339, else `CodexLoginUnusable`; the file is handed over byte for byte, and a refresh changes only `tokens` and `last_refresh`, decoding objects as objects so an empty one stays `{}`), refreshes it when `last_refresh` is seven days old or more on the `ClockInterface` (`CodexTokenRefresh::refreshedIfDue()` posts the refresh token to the endpoint with the client id the Codex CLI uses; the answer must carry a non-empty `access_token`, an `id_token` or `refresh_token` replaces the old one only when present, a refusal with HTTP 401 is the lost login `CodexAccountFailure::LoginLost` (an `AuthenticationException`, so the call fails as it is sent, before the CLI runs, and `AccountPlatform` takes the account out as a rejected one, see "Rejected keys"), and anything else, another HTTP error included, is `CodexLoginUnusable`), writes the refreshed login back with mode 0600, writes a copy with mode 0400 to `var/codex/homes/<account>/auth.json`, releases the lock and returns that home; refresh and copy both happen under the lock, because a refresh replaces the refresh token. Every reviewer and judge call carries the output limit of its tier (`max_output`, see [Capability tiers](capability-tiers.md)) as `PlatformOptions::MAX_OUTPUT_TOKENS`, so a verdict is not cut off at a model's default, which raised `MaxOutputTokensException` on the strong tier; the subscription CLIs take none. A reviewer whose call still raises `MaxOutputTokensException` is retried once by `SymfonyAiVendor` with twice the tier's limit (`ResolvedModel::withMaxOutput()`) and fails with that exception when the retry stops too (see [Review flow](review-flow.md)); the judge is not retried.

When the container is built, a provider is included only if each of its variables has a value. This is decided at build time because an unset `%env()%` makes the service fail when it is first built. The key itself stays a `%env()%` reference, so no secret is written into the compiled container. The consequence is that a changed key needs a cache clear.

**Where a value comes from.** A variable counts when it is non-empty in `$_ENV`, `$_SERVER` or the process environment, or has a non-empty value in the Symfony secrets vault, or, last, is the variable of the key kept from the browser (see "The provider key typed in the browser" below). These are the sources of Symfony's env processor, which falls back to its env var loaders (the vault's, then the kept key's) for an empty variable. The kept key does not count for a variable the vault lists when revealing that secret throws (see "What counts as missing" below): the vault's loader throws the same way at run time, before the kept key's loader is asked.

**How the vault is read.**

- The directory is the framework's default, `config/secrets/<runtime environment>` (`APP_RUNTIME_ENV`, else the kernel environment).
- The decryption key is the framework's default: the value of `SYMFONY_DECRYPTION_SECRET` when it is set, else the vault's `decrypt.private.php`. The environment value overrides the file.
- The environment value is decoded by the framework's own `base64:` env processor (`EnvVarProcessor`, lenient and accepting the standard or URL-safe alphabet).
- `SodiumVault::list()` gives the names without decrypting. Only a needed variable that is empty in the environment and listed in the vault is revealed with `SodiumVault::reveal()`, as the framework's env loader does.
- The revealed values are used only for this check and are not written into the container.

**What counts as missing.** A secret that cannot be decrypted counts as missing, so a broken decryption key never aborts the boot:

- a wrong key returns null;
- a key of the wrong length throws `SodiumException`;
- no key at all (a secret that decodes to nothing and no key file in the vault) throws `RuntimeException`.

Both exceptions are caught.

**A kept key behind such a secret.** The build tells the two throwing cases apart from a vault that only returns nothing (`$vaultValue` in `config/packages/ai.php` returns `false` for the first and `null` for the second):

- when the vault lists the variable and `reveal()` throws, the kept key does not count: the provider stays disabled with its message, as it is without a kept key. Resolving the variable at run time would throw the same exception in the vault's loader (it reveals the one name lazily), and the env processor never reaches the kept key's loader. The vault's loader is neither wrapped nor reordered, so the vault keeps winning over the kept key;
- when the vault does not list the variable, holds an empty secret, or returns null (a wrong key of the right length, or a private key file missing beside the public one), the kept key counts, and it is the value the env processor resolves.

**A disabled provider.** A provider none of whose accounts (see "Accounts" below) has every variable set is left out, and the parameter `intakt.ai.disabled_providers` (provider name to message) records `Provider "<name>" is disabled: set <VARIABLE> to enable it.`, naming the first account's variables. A provider with at least one complete account stays on, and each incomplete account is listed in `intakt.ai.disabled_accounts` instead. `Intakt\Core\Ai\Infrastructure\DisabledProvidersWarning` writes each message to standard error on the `ConsoleCommandEvent` of `intakt:ai:tiers` and `intakt:vendor:probe` only (the application has no log handler that prints warnings yet), followed by the messages of `intakt.ai.disabled_accounts`. Other commands print no note, so a result such as the review's is not preceded by them. The demo entrypoint (`docker/entrypoint.sh`) runs `intakt:ai:tiers` after its last container rebuild with standard output discarded, so the start log holds the notes, and then writes the mark `provider-notes-shown` beside `INTAKT_CONFIG` on the data volume; a start that finds the mark skips the call, so only the first start on a volume prints them (a mark that cannot be written does not stop the start, the next start prints them again). A failed `intakt:ai:tiers` (for example, a project file it cannot read) does not stop the start either: the entrypoint prints `intakt: could not print the provider notes; the next start tries again` to standard error and writes no mark, so the next start calls it again.

**Accounts.** The top-level `accounts` key of Intakt's config file (validated by `ProjectsConfiguration`: per provider a list of at least one name matching `Contract\Account::NAME_PATTERN`, each listed once, default `[default]`) names each provider's accounts in the order they are tried. `Contract\Account` (provider and name) reads the provider's variables for `default` and the variables with `_<NAME>` appended for any other name; `key()` is `<provider>.<name>`, unambiguous because neither part can hold a dot. An account with a missing variable is left out with `Account "<name>" of provider "<provider>" is disabled: set <VARIABLE> to enable it.` in `intakt.ai.disabled_accounts`; the provider goes into `intakt.ai.disabled_providers` (with the first listed account's variables) only when none of its accounts is set. The parameter `intakt.ai.accounts` lists the enabled account names per provider. The default account keeps the bundle's platform (`ai.platform.anthropic`, `ai.platform.openai`, `ai.platform.generic.openai_compatible`, `intakt.ai.platform.claude_code`). The bundle configures one `anthropic` and one `openai` platform, so another account of those is built with the bridge's `Factory::createPlatform()` and the arguments the bundle passes; another `openai_compatible` account is the generic platform `openai_compatible_<name>`, and another `claude_code` account gets `intakt.ai.claude_code.cli.<name>` and `intakt.ai.platform.claude_code.<name>`, running in `var/claude-code-<name>/`. Every `codex` account gets `intakt.ai.codex.cli[.<name>]` and `intakt.ai.platform.codex[.<name>]` (no suffix for `default`); `codex` has no variables, so its listed accounts are all enabled when the `codex` section is set and the provider is left out of every parameter (not disabled) when it is not. Each enabled provider is the service `intakt.ai.accounts.<provider>`, an `Infrastructure\AccountFailoverPlatform` over its accounts' platforms in the listed order.

**Cooldowns and failover.** `AccountFailoverPlatform::invoke()` drops every account `Contract\AccountCooldowns` reports as cooling down, throws `Contract\EveryAccountCoolingDown` (with `secondsUntilAnAccountIsFree`) before any call when none is left (or the rejection, see "Rejected keys" below), logs at info level when the first listed account is skipped, and hands the call to a Symfony AI `FailoverPlatform` built for this call over the free accounts, each wrapped in `AccountPlatform`. That `FailoverPlatform` gets a `NullLogger`, because it logs the provider's exception message, which can echo a key; `AccountPlatform` logs each account error of its account (one it cools the account down for, below) at warning level instead, with the account key and the exception (`Account {account} failed.`), whose message the log redacts like every record. A new `FailoverPlatform` per call because it keys its rate limiter by platform class, which every account of a provider shares, and calls a platform that failed again on the next call (`upstream/ai-failover-platform-retries-a-failed-platform/`); its own limiter is a `no_limit` one, since the cooldowns decide. `AccountPlatform` cools its account down on a `RateLimitExceededException` (until `getRetryAfter()`) or another `RetryableExceptionInterface` (no reset), thrown when the call is sent, later through the `DeferredResult`'s `onError()` (a limit can arrive when the answer is read), or while a stream is read, through the `Infrastructure\AccountStreamFailures` listener's `onError(ErrorEvent)` that an `onConvert()` callback adds to a `StreamResult` (the `onError()` does not fire while a stream is read); an `IncompleteStreamException` is looked through to its previous exception, and `SendFailures::record()` reports a failure it already holds for that account, so each is logged and cooled down once. Any other exception, such as the refusal of an answer Intakt cannot read (`StrictVerdictConverter`'s `ValidationException`, `UnexpectedResultTypeException` or deserialization `RuntimeException`, [review verdicts](review-verdicts.md)), is no account error (issue #1831): `AccountPlatform::coolDownAfter()` matches no cooldown for it, so it is not recorded in `SendFailures`, not logged as a failed account and cools nothing down (`tests/Plugin/SymfonyAiVendor/ClaudeCodeReviewerTest.php` replays the unreadable `claude_code` recordings through an `AccountFailoverPlatform`, and `AccountFailoverPlatformTest.php` a failure read from the answer). A call that fails when it is sent with such an exception (the CLI crashing, a non-retryable bad request) is logged at warning level as `Account {account} could not send the call.` with the exception, redacted like the other record, because the `FailoverPlatform` logs nothing and chains no cause. `AccountPlatform` also puts the account key in the result's metadata (`Account::METADATA`). When `FailoverPlatform` fails with every account and all of them now cool down, the error becomes `EveryAccountCoolingDown`; when every account it sent the call to threw a transport error while sending, it becomes `EveryEndpointUnreachable` (see "Rejected keys" below). `Infrastructure\AccountCooldownWindows` implements `AccountCooldowns` with Symfony RateLimiter: a `fixed_window` limiter of one call per account key, anchored (`anchor_at`) at the end of the cooldown with a one-month interval (the shortest the RateLimiter anchors), in the cache pool `intakt.ai.account_cooldowns` (`config/packages/cache.yaml`: `cache.app` on this host's filesystem, so every worker shares it; an array pool in tests) with the application's `LockFactory`. A cooldown lasts the reset the provider sent, 60 seconds without one, at most 86400; a reset of zero or less starts none, and a second limit while one runs keeps the first. Each new cooldown appends `account_cooled_down` (`account` key and `until` in ATOM) to the ledger, written from the readonly payload class `Infrastructure\AccountCooledDown` through the `stored` serializer (`tests/Core/Ai/Infrastructure/AccountCooledDownTest.php`); a refused append is logged at error level and the cooldown still holds. `secondsUntilAnAccountIsFree(provider)` is zero while an account is free, else the shortest wait, at least one second. Tests: `tests/Core/Ai/Contract/AccountTest.php`, `tests/Core/Ai/Infrastructure/AccountCooldownWindowsTest.php`, `AccountFailoverPlatformTest.php` (`MockPlatformFactory` platforms, and `FailingWhenRead` for a limit read from the answer), `ProjectsConfigurationTest.php`, and `tests/Application/ProjectTiersTest.php` (a kernel with two accounts of one provider).

**Rejected keys.** `AccountPlatform` also cools its account down on a Platform `AuthenticationException` (a revoked or wrong key) through `AccountCooldowns::coolDownRejected()`: the same 60-second cooldown, plus a marker `account-cooldown-rejected-<account key>` in the same pool that expires with the running window, so `isRejected()` holds exactly while the account cools down after a rejection. A rejection is an account error only the owner can fix, so `coolDownRejected()` also reports it once: it first saves the pool item `account-cooldown-pending-<account key>`, then, while that item is there, takes the `LockFactory` lock `account-cooldown-reported-<account key>` without waiting, looks for the pending item again under the lock (a worker that paused between its look and the lock finds it gone when another worker reported the error meanwhile, and leaves without reporting it again), deletes it and, only while the pool holds no item of that name, it appends `account_error_reported` (`account` key and `reported_at` in ATOM, from the readonly payload class `Infrastructure\AccountErrorReported` through the `stored` serializer) and then saves the item with the report's moment and no expiry, so an error that outlasts its cooldown is not reported again on each retry. A busy lock leaves the pending item to the worker holding the lock (reporting the account or clearing its report): every holder looks for it again after it releases the lock, so an error that comes while a report is cleared is still reported, and one that comes while the same error is reported is not reported twice. A refused append is logged at error level (`An account error was not reported.`) and saves nothing, so the next error reports it again. Only an answer clears the item: `AccountPlatform` takes the `ClockInterface` of `AccountFailoverPlatform`, notes the moment it sends each call and, when the answer converts (a `StreamResult` only once it is read to its end, through the `Infrastructure\AccountStreamAnswered` listener's `onComplete()`), calls `AccountCooldowns::answered(account, sentAt)`, which deletes the item under the same lock (taken waiting) only when the report is strictly older than the call; an answer to a call sent before or at the report's moment, read after the error, keeps it, and an answer that fails to convert never clears it. Tests: `AccountCooldownWindowsTest.php` and `AccountFailoverPlatformTest.php` (a `MockClock` forces the order of send, report and answer), `tests/Core/Ai/Infrastructure/AccountErrorReportedTest.php`. Each `AccountPlatform` records the class of its account's account error, sent or read through `onError()` or the stream listener, in a per-call `Infrastructure\SendFailures` keyed by account. When every account of the provider rejected its key, in this call (`SendFailures::wasRejected()`) or in an earlier one it still cools down from (`isRejected()`), `Contract\EveryKeyRejected` is thrown instead of `EveryAccountCoolingDown`, since no wait brings a rejected key back; an account cooling down from a limit keeps it a wait. `EveryKeyRejected` is an `AuthenticationException` whose message names only the provider and which chains no previous exception, so the provider's error text, which can echo a key, never reaches a log (the judging's failure listener logs the exception it gets). The same rule holds before the call: when no account is free and every one cools down from an earlier rejection, `invoke()` sends nothing and throws `EveryKeyRejected`. `AccountCooldowns::isEveryAccountRejected(provider)` tells the same over the provider's configured accounts (false for a provider without any). For a key rejected as the answer is read, `AccountFailoverPlatform` returns a new `DeferredResult` whose `Infrastructure\TypedRejectionConverter` turns the `AuthenticationException` into `EveryKeyRejected` or `EveryAccountCoolingDown` by the same rule; with a free account left it becomes `Contract\KeyRejected`, an `AuthenticationException` that names only the account key and chains nothing, and the review starts again on it. A key rejected as the call is sent never surfaces at all: `FailoverPlatform` moves on to the next account, and its own error when every free account fails (`All platforms failed.`) chains no cause. With Symfony's HTTP client a failed name lookup, a refused connection or a timeout surfaces only when the answer is read, not when the call is sent, so no other account is tried: the `TransportExceptionInterface` reaches the vendor through the answer, which types it as `ProviderUnreachable` and asks the reviewer once more (see [Vendor](vendor.md); `tests/Plugin/SymfonyAiVendor/AnthropicUnreachableRetryTest.php` builds the Anthropic bridge with its own factory over a `MockHttpClient` whose response fails the lookup). The send-time path is only a guard for a platform that throws a `TransportExceptionInterface` while sending: `AccountPlatform` notes in the same `SendFailures` each account the call is sent to (`tried()`) and each that threw such an error as it was sent (`unreachable()`, which cools no account down); when every account the call was sent to was unreachable (`isEveryTriedUnreachable()`), `AccountFailoverPlatform` throws `Contract\EveryEndpointUnreachable` instead of the failover's error, judged over the accounts actually tried, so an account whose cooldown ended during the call does not hide it. `EveryEndpointUnreachable` is a `TransportExceptionInterface` whose message names only the provider and which chains nothing, so the transport error's text, which names the request's URL, never reaches a log, and the vendor retries the review like any unreachable endpoint. With one account unreachable and another failing otherwise, the failover's error stays. Tests: `AccountFailoverPlatformTest.php`, `tests/Plugin/SymfonyAiVendor/ReviewerRetryVendorTest.php`, `AnthropicUnreachableRetryTest.php`. The converter offers the account's `TokenUsageExtractor` only while the account's answer carries no usage, so an answer read through it holds its usage once, and one that failed to map still has it read from the raw answer.

### Provider key

`Intakt\Core\Ai\Contract\ProviderKey::recognise()` takes a key as typed, trims surrounding whitespace and names its kind from its form, as a `KeyKind`: `sk-ant-` followed by at least eight letters, digits, `_` or `-` is `Anthropic`; `sk-` (this includes `sk-proj-`, but not `sk-ant-`) with the same body is `OpenAi`; `hf_` followed by at least eight letters or digits is `HuggingFace`. The OpenAI form excludes the `sk-ant-` prefix, so an Anthropic key with too short a body (cut off when pasted) is refused instead of being taken for an OpenAI key. Any other form, including an empty one, throws `KeyNotRecognised`, whose message is fixed and never carries the input. `HuggingFace` is a key kind only; it is not a `Provider` case.

`ProviderKey` offers its `kind()` and its `configured()` state, a `ConfiguredKey` holding the kind and at most the last four characters (at most a quarter of the key, so a short key shows fewer). `ConfiguredKey` keeps only the last four characters of whatever it is given, so even a whole key passed to it shows no more. The key itself is kept in a `SensitiveParameterValue`, has no string conversion and no public getter except `secret()` (used by the key check, to write the kept file, to resolve the kept key and to redact it from logs), and arrives as a `#[SensitiveParameter]`, so `var_dump`, `print_r`, `var_export` and an exception trace do not show it. `Intakt\Core\Dashboard\UseCase\KeepProviderKey\KeepProviderKey::keep()` recognises a key, checks it through the vendor contract `Intakt\Plugin\Vendor\Contract\KeyCheck` and, only when the outcome is `Accepted`, keeps it through the Ai contract `KeptProviderKeys` before it returns the `ConfiguredKey` (a refused or unchecked key is never written); `configured()` reads the state back from the kept file. `Infrastructure\KeptProviderKeyFile` implements `KeptProviderKeys` and keeps the one key in `var/data/provider-key.json` (the data volume; the directory is the parameter `intakt.ai.kept_key_directory`, which `config/packages/ai.php` sets from `INTAKT_PROVIDER_KEY_DIR` when that is set, which only the tests do) as JSON with its kind and key. The write goes to a new file in the directory (mode 0600, the directory created with 0700 when missing) that is then renamed over the path, so the key is never readable by others and a link at the path is replaced, never followed. A write that fails removes its new file and throws `KeptProviderKeyNotWritten` (fixed message, no previous exception, because the failed call's arguments in its trace hold the key). `read()` treats the file as outside input: it rebuilds a `ProviderKey` through `recognise()`, so the configured state comes from the one rule in `ProviderKey::configured()`, returns `null` when no file exists, and throws `KeptProviderKeyUnreadable` (fixed message, no file content) for a file that cannot be read or parsed, whose key does not have a recognised form (a value too short for its form included) or whose form names another kind than the one stored. `KeyCheck::check()` returns a `KeyCheckOutcome` (`Accepted`, `Refused`, `NotChecked`) and never throws for a provider failure. `SymfonyAiKeyCheck` builds the key's own platform over the injected HTTP client (the Anthropic bridge, the OpenAI bridge, and the generic bridge on `https://router.huggingface.co` for a Hugging Face token) and makes one call with the constant prompt `Answer with the single word: ok`, the cheapest model of the kind (`claude-haiku-5-5`, `gpt-4.1-nano`, `meta-llama/Llama-3.2-1B-Instruct`) and the smallest answer cap its provider accepts: one token for Anthropic and Hugging Face, 16 for OpenAI, whose Responses API refuses a smaller `max_output_tokens`. The answer is read only to see that the call succeeded and is then dropped. An `AuthenticationException` is `Refused`; any other failure (unreachable, limited, a server error) is `NotChecked`, so a key is not called bad on a bad moment. `keep()` throws `KeyNotRecognised`, `KeyRefusedByProvider`, `KeyNotChecked` or `KeptProviderKeyNotWritten`; the messages are fixed and no exception keeps the provider's exception as its previous one, because a provider's text can echo the key, so the key reaches no log or message. Tests script the provider with Symfony's `MockHttpClient` under the real bridges, so each kind's endpoint, request body and refusal are pinned. `Infrastructure\KeptProviderKeyVariables` is a Symfony env var loader (`EnvVarLoaderInterface`, autoconfigured as `container.env_var_loader`): it returns the kept key as the variable of its kind (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `HF_TOKEN`) and an empty list when no file exists or the file is unreadable (it then logs only a fixed warning, never file content). Symfony's env processor asks its loaders only for a name the environment lacks (or holds empty) and takes the first loader's non-empty value in tag priority order; the class carries `#[AsTaggedItem(priority: -100)]`, below the vault's loader (`secrets.env_var_loader`, priority 0), so the order is: the environment (a value in `.env.local` included), the secrets vault, then the kept key; a kept key is used like the same variable in `.env.local`. `config/packages/ai.php` decides at build time whether a provider is enabled and counts the kept key as set last, in the same order, so a kept key enables its provider after the container is rebuilt (the cache cleared or the app restarted); an install with a value in the environment is unchanged. It does not count the kept key for a variable whose vault secret throws when revealed (see "A kept key behind such a secret" above), because the run-time lookup would throw in the vault's loader first. `HF_TOKEN` is held and redacted but turns on no platform, since Hugging Face is no `Provider`. `Platform\Infrastructure\HeldCredentials` also holds the kept key's value (through the Ai contract `KeptProviderKeys`; an unreadable file holds nothing, so the logger still writes), so `RedactedJsonFormatter` removes it from every log record. Tests: `KeptProviderKeyVariablesTest`, `HeldCredentialsTest` and the `AiProvidersTest` cases for a kept key, for the key the platform sends, for the environment and the vault winning, and for a kept key behind a vault secret that throws or returns nothing.

**The endpoint that keeps a key (#2258, part 2 of #2231, decision D2).** `dashboard_keep_provider_key` is `POST /setup/provider-key` (`Dashboard\UseCase\KeepProviderKey\KeepProviderKeyController`, under the `dashboard_` prefix, so `RefuseForeignHost` covers it); the dashboard has no login, so three guards stand in front of it. It checks the CSRF token of the id `dashboard_keep_provider_key` first (`400`, nothing kept, through `FormPress`). It then refuses while a key is configured: the kept file holds one (`KeepProviderKey::configured()`), or any provider has an enabled account (`EnabledAccounts::of()`, which counts a key from the environment, `.env.local` or the vault); an unreadable kept file refuses too, with its fixed message. The refusal is a flash line and a `303` back to `/setup`, so changing a key later stays an edit of `.env.local`. Only then does it read the form field `key` straight into `KeepProviderKey::keep()` (a `#[SensitiveParameter]`) and turn each outcome into a fixed flash line: kept (the kind and the last four characters only, and that a restart makes the provider enabled), not a recognised form, refused by the provider, not checked, or not written. No flash, redirect, exception message or log record carries the key. The key goes to the provider check and never into a prompt, so the fencing helper does not apply. The form that posts to it is not built yet (the next part of #2231). Tests: `KeepProviderKeyControllerTest` (a wrong token keeps nothing, a second key is refused beside a kept key or an enabled account and the kept key stays, a refused, unchecked or unrecognised key is not kept, an accepted key is kept and the response and every log record lack it).
