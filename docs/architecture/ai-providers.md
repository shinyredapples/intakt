## AI providers

### In short

This part connects Intakt to AI models through the Symfony AI Bundle. It knows five providers: `anthropic`, `openai`, a generic `openai_compatible` endpoint (which also serves Hugging Face's router), and the subscription CLIs `claude_code` and `codex`. A provider is included only when each of its variables has a value, from the environment, the Symfony secrets vault, or the key typed in the browser. `codex` needs no variable; its credential is a login file. Each provider can have several accounts, tried in order, and an account that is cooling down is skipped.

Worth knowing:

- Providers are chosen when the container is built, so a changed key needs a cache clear.
- A vault secret that cannot be decrypted counts as missing and never aborts the boot.
- A left-out provider gets a message in `intakt.ai.disabled_providers` that names the variable to set.
- When every account is cooling down, the call fails with `EveryAccountCoolingDown` before anything is sent.

The rest of this page is the detailed reference.

`config/packages/ai.php` configures the AI Bundle platforms `anthropic`, `openai` and a generic endpoint named `openai_compatible` (packages `symfony/ai-anthropic-platform`, `symfony/ai-open-ai-platform` and `symfony/ai-generic-platform`, pinned like the other Symfony AI packages). Each provider is a case of the `Intakt\Core\Ai\Contract\Provider` enum, which lists the environment variables it needs (`ANTHROPIC_API_KEY`; `OPENAI_API_KEY`; `OPENAI_COMPATIBLE_BASE_URL` and `OPENAI_COMPATIBLE_API_KEY`; `CLAUDE_CODE_OAUTH_TOKEN`; none for `codex`, whose credential is a login file).

Hugging Face's Inference Providers reach Intakt through `openai_compatible`, with no package of their own: in the image, `docker/entrypoint.sh` sets its two variables from `HF_TOKEN` with the base URL `https://router.huggingface.co` (no `/v1`, because the generic bridge appends `/v1/chat/completions`), a token kept from the setup wizard's AI account step is served as the same two variables (see the kept key below), and the demo seed puts router models on it (see [the demo](demo-with-docker-compose.md)). That URL, the seeded models and their prices with their date live in one data file, `config/sample-project.yaml`, so refreshing the demo is an edit of that file. Three files read it: `src/Core/Review/UseCase/SeedSampleProject/SampleProject.php` (models, the second reviewer's model, prices, price date, and the router URL that `OPENAI_COMPATIBLE_BASE_URL` must equal), `src/Plugin/SymfonyAiVendor/Infrastructure/HuggingFaceDescriptor.php` (the router URL the key check calls) and `docker/entrypoint.sh` (the router URL it exports); the two PHP readers go through `src/Core/Review/Contract/SampleProjectData.php`, the entrypoint reads the `router_url` line with bash. The pinned generic bridge reads only `error.message` from a failed response, while the router writes `message` at the top level, so a refused call shows only the HTTP reason ("Bad Request"); symfony/ai#2849 reads both and arrives with the next Symfony AI release through the normal dependency update.

On an install with a container engine a `claude_code` reviewer runs in a [review job](review-job.md) and reads its checkout with the CLI's own file tools; this section describes the CLI in Intakt's own process.

The fourth provider, `claude_code`, runs the `claude` CLI through `symfony/ai-claude-code-platform` (pinned like the other Symfony AI packages). The AI Bundle has no configuration for that bridge, so `Intakt\Core\Ai\Infrastructure\ClaudeCodePlatformFactory` builds its platform with the bundle's event dispatcher (the structured output subscribers hang on it), and `config/packages/ai.php` registers it as `intakt.ai.platform.claude_code` when the token is set. `IsolatedClaudeCodeCli` (the service `intakt.ai.claude_code.cli`) builds the bridge's client for every request, so a variable added to a long-running worker's environment is covered too, and runs the CLI in `var/claude-code/` (created on first use, also the CLI's `HOME`) with an environment in which only `PATH`, `HOME` and `CLAUDE_CODE_OAUTH_TOKEN` have a value: Symfony Process passes every inherited variable unless it is overridden by name, and the bridge takes only strings, so every other inherited variable is set to an empty string. `ConfinedClaudeCodeClient` wraps that client: it drops every option the agent passes (the bridge turns each into a CLI flag) except `Core\Ai\Contract\ReviewServerAccess::OPTION`, gives the CLI no built-in tool (`--tools ""` and `--disallowed-tools` naming each built-in), no settings (`--setting-sources ""`), no MCP server but the one it is given (`--strict-mcp-config`) and no saved session, and passes the response format's JSON schema (the `json_schema.schema` part of `PlatformSubscriber::RESPONSE_FORMAT`) as `--json-schema` instead of appending it to the system prompt, and refuses a response format without a schema with the platform's `InvalidArgumentException` before the CLI starts. The CLI holds its answer to that schema and returns it in the result event's `structured_output`; `FinishedProcessResult` puts that value, JSON-encoded, in place of the result's `result` text the bridge reads (the bridge maps no response format to `--json-schema` and ignores `structured_output`, see `upstream/ai-claude-code-platform-structured-output/`), and leaves `result` as it is when the field is absent or null, so the verdict parser still refuses a structured answer that is not a verdict (recordings `structured`, `structured-not-a-verdict` and `structured-null`). The judge's call on `claude_code` (the `light` tier, for example `haiku`) takes the same path: `JudgeAgent` sets `Judgement::class` as the response format, so the CLI gets the judgement's schema as `--json-schema`, and the marks are read from its structured output; an answer that maps to no `Judgement` gives `Judgement::everyBlockingFindingActs()`. The judge's call carries no `ReviewServerAccess::OPTION`, so the CLI gets the no-tool prompt line and no `--mcp-config`. `tests/Plugin/SymfonyAiVendor/ClaudeCodeJudgeTest.php` replays the recordings `judgement-structured`, `judgement-structured-not-a-judgement` and `judgement-structured-only-f1` through `SymfonyAiVendor::judge()`, checking the marks read, the schema passed, the usage settled once, and that an answer that is no judgement or leaves out a finding makes every blocking finding act. `SymfonyAiVendor` sets that option on every call of a `claude_code` review whose conversation has a round, from `Review\Contract\ReviewServerAccesses` (`IssuedReviewServerAccesses`: the address, the parameter `ReviewServices::MCP_URL` set in `config/packages/mcp.yaml`, the round's `ReviewCredential` bearer and the names of the three read-only tools, read from their `#[McpTool]` attributes). `ConfinedClaudeCodeClient` passes the option on to `IsolatedClaudeCodeCli`, which writes `ReviewServerAccess::mcpConfigurationJson()` (only that server and its `Authorization` bearer header) to a file of its own in the CLI's directory (`review-server-*.json`, mode `0600`), passes its path as `--mcp-config` and removes it once the run has been read (`RemovedAfterRun`), or at once when the bridge's client throws before a run exists (the CLI is not on `PATH`, the process does not start): never inline JSON, because Symfony Process puts the command line into its timeout message, which is logged. When no access can be issued (an empty `APP_SECRET`, so `ReviewCredential` signs nothing), `IssuedReviewServerAccesses` throws `Review\Contract\NoReviewServerAccess` and `SymfonyAiVendor` does not start the CLI: it settles the call's reservation with no usage and returns `Verdict::noTools()`, the blocked verdict an API-key reviewer gets when its toolbox lists no tools. `ConfinedClaudeCodeClient` adds `--allowedTools` (`mcp__intakt-review__<tool>` for each of the three) and a prompt line that only those tools are available; without it the line says no tool is available. The allow-list is a second fence: the server's `ToolAccessVoter` still decides every call. The CLI never sees the checkout directly: its own file tools would bypass `Checkout` and `Fence`, so it reads only through the review server, which fences every answer itself (`ReviewedRepository`, see [MCP server](mcp-server.md)). `Provider::readsTheCheckout()` stays false for `claude_code`, because the provider alone gives the CLI no tool; `SymfonyAiVendor` (which resolves the tier through `TierResolver`) decides per call (part 2 of #1252): an `approve`, or a `changes` of only P3 findings, which the quorum can count as approval (`Verdict::mayCountAsApproval()`; a reviewer's `blocked` with findings is judged as the `changes` it is recorded as), counts when the provider reads the checkout or the call's options carry `ReviewServerAccess::OPTION` and one of the call's rounds reports a read through it (`Contract\ReviewServerReads`; see Codex reviewer below for `codex`). For `claude_code`, `FinishedProcessResult` implements it from the CLI's own stream events, never from the answer's text (#1407): the `system` event of subtype `init` must list the access's server in its `mcp_servers` (each entry `{"name", "status"}`) with status `connected`, so a server that failed, is still pending or is not listed counts no read, and at least one read must follow. A read is a `tool_use` block of an `assistant` event named as one of the access's tools (`ReviewServerAccess::mcpToolNames()`, `mcp__<server>__<tool>`, the same names `ConfinedClaudeCodeClient` allows beside `--strict-mcp-config` and the built-in denials) whose `tool_result` in a `user` event has that block's id and no `is_error: true`, so a refused call, a call without a result and a call to another server are none (#1894), and is otherwise turned into `Verdict::unreadApproval()`, a `blocked` verdict whose finding `unread-approval` gives the reason, as for a `claude_code` call without a round; its usage is settled as usual. The check runs inside each attempt, so a retry at the output limit is judged by its own options. `FinishedProcessResult` turns a run without its final result event into `IncompleteStreamException`, whether the CLI exited, was killed or timed out (a run that wrote its final result and failed stays a failure), and drops the `tool_calls` the bridge collects from the tools the CLI ran itself, so the agent never runs them again (both in `upstream/`); `SymfonyAiVendor` catches that one exception, leaves the call unsettled once and returns `Verdict::incompleteStream()`, a `blocked` verdict. Every other failure keeps its mapping. Without a structured output the CLI answers in prose around one fenced `json` block, so `StrictVerdictSubscriber` has `StrictVerdictConverter` read that block for `claude_code` and `codex` models ([review verdicts](review-verdicts.md)); `FencedVerdictTest` covers the cases and the recordings `fenced`, `two-blocks`, `prose-only` and `not-a-verdict` cover them end to end. `tests/Plugin/SymfonyAiVendor/ClaudeCodeReviewerTest.php` replays recorded streams (`tests/Plugin/SymfonyAiVendor/Fixtures/claude-code/`) through the bridge's own process result, and runs one review through `IsolatedClaudeCodeCli` and the bridge's client against a scripted `claude` on `PATH` to check its exact arguments and configuration file.

**Codex subscription login** (plan T39, part 1). `symfony/ai-codex-platform` is pinned like the other Symfony AI packages. `Infrastructure\CodexLogins` keeps each account's login in `var/codex/logins/<account>/auth.json` and refuses a name that does not match `Account::NAME_PATTERN`, since it becomes a path and a lock key. `handOver(account)` takes the `LockFactory` lock `intakt.codex.login.<account>` (`AiServices::CODEX_LOGIN_LOCK_PREFIX`, blocking), reads the login (`CodexLogin`: `tokens.id_token`, `access_token` and `refresh_token` as non-empty strings and `last_refresh` in RFC 3339, else `CodexLoginUnusable`; the file is handed over byte for byte, and a refresh changes only `tokens` and `last_refresh`, decoding objects as objects so an empty one stays `{}`), refreshes it when `last_refresh` is seven days old or more on the `ClockInterface` (`CodexTokenRefresh::refreshedIfDue()` posts the refresh token to the endpoint with the client id the Codex CLI uses; the answer must carry a non-empty `access_token`, an `id_token` or `refresh_token` replaces the old one only when present, a refusal with HTTP 401 is the lost login `CodexAccountFailure::LoginLost` (an `AuthenticationException`, so the call fails as it is sent, before the CLI runs, and `AccountPlatform` takes the account out as a rejected one, see "Rejected keys"), and anything else, another HTTP error included, is `CodexLoginUnusable`), writes the refreshed login back with mode 0600, writes a copy with mode 0400 to `var/codex/homes/<account>/auth.json`, releases the lock and returns that home; refresh and copy both happen under the lock, because a refresh replaces the refresh token. Each write goes to a new file in the target directory that is then renamed over the path, and a home that is a link is removed first, so a link the call leaves for its home or its copy is replaced, never followed into another account's login. `IsolatedCodexCli` (a `ModelClientInterface`) calls `handOver()` on every request and runs the bridge's `ModelClient` in that home with `CODEX_HOME` and `HOME` set to it, `PATH` kept and every other inherited variable emptied, and with its confinement and `CodexSettings::options()` as its only options, since the bridge turns every option and every payload key into a flag (the caller's options are dropped except `ReviewServerAccess::OPTION`, which becomes the review server's settings, see "Codex reviewer" below, and of an array payload only `prompt` and `system_prompt` pass): `--sandbox read-only`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--skip-git-repo-check` (the home is no repository), `--disable` for each of `shell_tool`, `unified_exec`, `apps`, `plugins`, `browser_use`, `in_app_browser`, `computer_use`, `multi_agent`, `image_generation`, `view_image` and `hooks` (features the CLI enables by default; it refuses an unknown name, so a renamed feature fails the call), `--model <pinned>`, and `--config` with `web_search="disabled"` and `model_reasoning_effort="<effort>"`. `CodexSettings` comes from the optional `codex` section of `ProjectsConfiguration` (`model`, validated like a tier's, and `effort`, the backed enum `CodexEffort`), held in the parameter `intakt.ai.codex` (null without the section). `php bin/console intakt:codex:probe [account]` (`UseCase/ProbeCodexLogin`) makes one call with a fixed prompt and the bridge's `ResultConverter`. Tests: `tests/Core/Ai/Infrastructure/CodexLoginTest.php`, `CodexTokenRefreshTest.php` (`MockHttpClient`), `CodexLoginsTest.php` (an `InMemoryStore` lock, including that the refresh runs while the lock is held), `IsolatedCodexCliTest.php`, `tests/Core/Ai/UseCase/ProbeCodexLoginCommandTest.php` (a scripted `codex` on `PATH` that reports its arguments, environment and the copy's mode) and `tests/Application/ProjectTiersTest.php` (the container's probe shows the model of the owner's `codex` section).

**Codex reviewer** (plan T39, part 2). `Provider::Codex` (`codex`) has no variables and `readsTheCheckout()` false. `SymfonyAiVendor` sets `ReviewServerAccess::OPTION` on every call of a review whose provider does not read the checkout (`claude_code` and `codex`) and whose conversation has a round, and counts a `codex` `approve` (or a `changes` of only P3 findings) only for a call that had the option and whose rounds include a raw result implementing `Contract\ReviewServerReads` that reports a read through that access (#1835); otherwise it becomes `Verdict::unreadApproval()`. `CompletedCodexTurn` implements it from the CLI's own `item.completed` events, never from an agent message: a read is an `mcp_tool_call` item on the access's server, naming one of its tools, with status `completed`, no `error` and a `result` not marked `isError: true` (a failed call, a call the server refused or one to another server is none), and an access that cannot be issued gives `Verdict::noTools()` without starting the CLI. `ConfinedCodexClient` passes that option on to `IsolatedCodexCli`, which turns it into `--config` overrides naming the access's server as the CLI's one MCP server (`mcp_servers.<name>.url`, `bearer_token_env_var="INTAKT_REVIEW_SERVER_BEARER"`, `enabled_tools` with the access's three tools and `required=true`, so a server that cannot start fails the call) and sets that variable to the round's bearer in the CLI's environment, so the bearer is never on the command line, which the bridge logs and Symfony Process puts into its timeout message; `--ignore-user-config` still keeps every other server out. Each value is JSON-encoded, which the CLI parses as a TOML string or list. `ProjectModelCatalog` adds each mapped Codex model as the bridge's `Codex` class with the review capabilities (the bridge's own catalog lacks structured output). `ProjectsConfiguration` refuses a tier or substitute on `codex` whose model is not `codex.model`, so also one without the `codex` section. `config/packages/ai.php` registers the `CodexSettings` service `intakt.ai.codex.settings` from that section and, per account, an `IsolatedCodexCli` and a platform from `CodexPlatformFactory`, which builds the bridge's provider with the bundle's event dispatcher, the bridge's `ResultConverter` and a contract whose `CodexMessageBagNormalizer` replaces the bridge's normalizer, which keeps only the last user message (`upstream/ai-codex-platform-last-user-message/`): it joins the text of every user message, separated by a blank line, so the CLI's prompt holds the task, the diff, the memory briefing and the open findings. The provider's client is `ConfinedCodexClient`, which drops every option the agent passes (the bridge turns each into a CLI flag) except `ReviewServerAccess::OPTION` and passes only `prompt` and `system_prompt`: the agent's system prompt, a line that only the read-only tools of the named server are available and that the reviewer reads the files it needs through them before it gives a verdict (without the option: a line that no tool is available), and the verdict schema (the bridge prepends it to the prompt, since the CLI has no system prompt option). It wraps the answer in `CompletedCodexTurn`, which raises `IncompleteStreamException` when the bridge returns an agent message without the usage of `turn.completed` (`SymfonyAiVendor` turns that into `Verdict::incompleteStream()` and leaves the call unsettled once; `upstream/ai-codex-platform-cut-off-stream/`), drops the `tool_calls` the bridge collects from tools the CLI ran itself (`upstream/ai-codex-platform-cli-tool-calls/`), and, when a completed turn has no agent message, adds the usage of `turn.completed` from the process output, which the bridge drops (`upstream/ai-codex-platform-usage-without-answer/`): the bridge's converter still fails the reviewer, and the call is left unsettled with that usage. A complete stream is converted by `StrictVerdictConverter`, which reads the one fenced `json` block for a `Codex` model as it does for `claude_code` ([review verdicts](review-verdicts.md)), so text that is no verdict, a limit message included, is a `VerdictUnreadable` (asked once more, then a failed reviewer) with its usage settled, and `AccountPlatform` cools the account down only on the platform's typed limit and rejection exceptions, which the bridge never throws and `CompletedCodexTurn` throws only for the CLI's own account errors (below); a CLI that exits non-zero makes the bridge's `getData()` throw its `RuntimeException` before it reads the output, so `CompletedCodexTurn` catches that one exception and, when the output holds the usage of `turn.completed`, returns an `error` entry with the exception's message and that usage (the bridge's converter still fails the reviewer with it, and the extractor reads the usage on the unsettled row); without a reported usage it rethrows, which fails the reviewer with no usage row, unless the turn ended in an account error. **Codex account errors** (plan T39, issue #638). `codex exec --json` keeps only the message of an error event and drops its code, so the CLI's fixed messages stand for the codes: the closed set is the backed enum `CodexAccountFailure`, each case matched at the start of the message (`tests/Core/Ai/Infrastructure/CodexAccountFailureTest.php`). `usage_limit_reached` (a message starting `You’ve hit your usage limit`, with either apostrophe, or exactly `Quota exceeded. Check your plan and billing details.`) becomes a `RateLimitExceededException` without a reset, so `AccountCooldownWindows` cools the account down until the latest reset of a window its measured readings show spent (below), or for its default minute without one, and the vendor throws `ProviderRateLimited`; `model_not_in_plan` (`To use Codex with your ChatGPT plan, upgrade to Plus`, or a `400 Bad Request` whose detail says the model is not supported with a ChatGPT account) and `login_lost` (`Your access token could not be refreshed`, or `unexpected status 401 Unauthorized`) become an `AuthenticationException` naming the code, so the account is taken out as a rejected one (`coolDownRejected`) and the vendor throws `ProviderRejectedTheKey` (see [Vendor](vendor.md) for where each goes next). `CompletedCodexTurn` asks only of a turn without the usage of `turn.completed` (a non-zero exit, or an exit without an agent message) and reads only the `error` and `turn.failed` events, never an agent message, so a reviewer's own text, the exact message included, is never an account error; any other message still fails the reviewer, and the call is left unsettled once with no usage. Neither outcome is a failed review or a `changes` verdict. An account error (`model_not_in_plan`, `login_lost`, and a refresh the token endpoint refuses with 401) is reported to the owner once as `account_error_reported`, like any rejected account (see "Rejected keys"); a usage limit is not (issue #639). The usage of `turn.completed` (`input_tokens`, `cached_input_tokens`, `output_tokens`) reaches `UsageLedger` through the bridge's `TokenUsageExtractor` as one row naming the account (`codex.<name>`). `tests/Plugin/SymfonyAiVendor/CodexReviewerTest.php` replays recorded streams (`tests/Plugin/SymfonyAiVendor/Fixtures/codex/`) through a scripted `codex` on `PATH`, so each passes the login handoff, `IsolatedCodexCli` and the bridge's own process result; the script also records its arguments and the bearer variable, so the tests check the one MCP server, the pinned model and effort, and that the bearer is never an argument (`review-server-read.jsonl` holds a read through `intakt-review`, which counts; `tool-use.jsonl`, `review-server-read-failed.jsonl`, `review-server-read-refused.jsonl` and `other-server-read.jsonl` approve after a failed call on another server, a failed call on `intakt-review`, a completed call on `intakt-review` whose result is a tool error and a completed call on another server, which are each refused; so are `review-server-read-started.jsonl`, whose read through `intakt-review` appears only in an `item.started` event, and `review-server-read-in-text.jsonl`, whose agent message embeds such a read event as text). The `claude-code` fixtures `review-server-read.jsonl` (a read through `intakt-review` with its result, which counts), `review-server-read-failed.jsonl`, `review-server-read-unanswered.jsonl`, `other-server-read.jsonl` and `review-server-read-in-text.jsonl` (a result answered with `is_error: true`, a read without its result, a read through another server and the events only as answer text, each refused) check the same rule for `claude_code`, and `review-server-connected-unread.jsonl`, `review-server-not-connected.jsonl` and `review-server-read-without-status.jsonl` (the server connected but nothing read, a read whose server's status is `failed`, and a read from a stream whose `init` event lists no MCP servers, each refused) check its connection half.

Every reviewer and judge call carries the output limit of its tier (`max_output`, see [Capability tiers](capability-tiers.md)) as `PlatformOptions::MAX_OUTPUT_TOKENS`, so a verdict is not cut off at a model's default, which raised `MaxOutputTokensException` on the strong tier; the subscription CLIs take none. A reviewer whose call still raises `MaxOutputTokensException` is retried once by `SymfonyAiVendor` with twice the tier's limit (`ResolvedModel::withMaxOutput()`) and fails with that exception when the retry stops too (see [Review flow](review-flow.md)); the judge is not retried.

When the container is built, a provider is included only if each of its variables has a value. This is decided at build time because an unset `%env()%` makes the service fail when it is first built. The key itself stays a `%env()%` reference, so no secret is written into the compiled container. The consequence is that a changed key needs a cache clear.

**Where a value comes from.** `Intakt\Core\Ai\Infrastructure\ProviderKeySource` holds the rule and `config/packages/ai.php` only calls it (`environmentValue()`, `openVault()`, and `missing(Account)`, which lists the account's variables that `isSet()` finds without a value). The constructor's kept values are a `#[SensitiveParameter]`, so a trace never shows a kept key. A variable counts when it is non-empty in `$_ENV`, `$_SERVER` or the process environment, or has a non-empty value in the Symfony secrets vault, or, last, is the variable of the key kept from the browser (see "The provider key typed in the browser" below). These are the sources of Symfony's env processor, which falls back to its env var loaders (the vault's, then the kept key's) for an empty variable. The kept key does not count for a variable the vault lists when revealing that secret throws (see "What counts as missing" below): the vault's loader throws the same way at run time, before the kept key's loader is asked.

**How the vault is read.**

- The directory is the framework's default, `config/secrets/<runtime environment>` (`APP_RUNTIME_ENV`, else the kernel environment; kernel: `testAKeyStoredOnlyInTheSecretsVaultEnablesItsProvider`).
- The decryption key is the framework's default: the value of `SYMFONY_DECRYPTION_SECRET` when it is set, else the vault's `decrypt.private.php`. The environment value overrides the file.
- The environment value is decoded by the framework's own `base64:` env processor (`EnvVarProcessor`, lenient and accepting the standard or URL-safe alphabet; unit: `testAKeyInAVaultBehindAUrlSafeEncodedDecryptionSecretEnablesItsProvider`).
- `SodiumVault::list()` gives the names without decrypting. Only a needed variable that is empty in the environment and listed in the vault is revealed with `SodiumVault::reveal()`, as the framework's env loader does.
- The revealed values are used only for this check and are not written into the container.

**What counts as missing.** A secret that cannot be decrypted counts as missing, so a broken decryption key never aborts the boot:

- a wrong key returns null (kernel: `testAKeptKeyIsUsedBehindAVaultSecretThatAWrongKeyOfTheRightLengthCannotOpen`);
- a key of the wrong length throws `SodiumException` (unit: `testAKeyStoredOnlyInTheVaultBehindAMalformedDecryptionSecretCountsAsMissing`; kernel: `testAVaultSecretBehindADecryptionSecretOfTheWrongLengthDisablesItsProviderDespiteAKeptKey`);
- no key at all (a secret that decodes to nothing and no key file in the vault) throws a bare `RuntimeException`, the only class the vault catch lets through as "no key"; a subclass or any other exception passes (unit: `testAKeyStoredOnlyInAVaultWithoutAnyUsableDecryptionKeyCountsAsMissing`; kernel: `testAVaultSecretWithoutAnyUsableDecryptionKeyDisablesItsProviderDespiteAKeptKey`).

Both exceptions are caught.

**A kept key behind such a secret.** The build tells the two throwing cases apart from a vault that only returns nothing (`ProviderKeySource` returns `false` for the first and `null` for the second):

- when the vault lists the variable and `reveal()` throws, the kept key does not count: the provider stays disabled with its message, as it is without a kept key. Resolving the variable at run time would throw the same exception in the vault's loader (it reveals the one name lazily), and the env processor never reaches the kept key's loader. The vault's loader is neither wrapped nor reordered, so the vault keeps winning over the kept key (unit: `testAKeptKeyIsIgnoredBehindAVaultSecretThatCannotBeRevealed`; kernel: `testAVaultSecretBehindADecryptionSecretOfTheWrongLengthDisablesItsProviderDespiteAKeptKey` and `testAVaultSecretWithoutAnyUsableDecryptionKeyDisablesItsProviderDespiteAKeptKey`);
- when the vault does not list the variable, holds an empty secret, or returns null (a wrong key of the right length, or a private key file missing beside the public one), the kept key counts, and it is the value the env processor resolves (unit: `testAKeptKeyCountsWhenNeitherTheEnvironmentNorTheVaultHasOne`; kernel: `testAKeptKeyEnablesItsProviderWhenTheEnvironmentHasNone`, `testAKeptKeyIsUsedBesideAnEmptySecretInTheVault`, `testAKeptKeyIsUsedBehindAVaultSecretThatAWrongKeyOfTheRightLengthCannotOpen` and `testAKeptKeyIsUsedBehindAVaultSecretWhosePrivateKeyFileIsMissing`).

**A disabled provider.** A provider none of whose accounts (see "Accounts" below) has every variable set is left out, and the parameter `intakt.ai.disabled_providers` (provider name to message) records `Provider "<name>" is disabled: set <VARIABLE> to enable it.`, naming the first account's variables. A provider with at least one complete account stays on, and each incomplete account is listed in `intakt.ai.disabled_accounts` instead. `Intakt\Core\Ai\Infrastructure\DisabledProvidersWarning` writes each message to standard error on the `ConsoleCommandEvent` of `intakt:ai:tiers` and `intakt:vendor:probe` only (the application has no log handler that prints warnings yet), followed by the messages of `intakt.ai.disabled_accounts`. Other commands print no note, so a result such as the review's is not preceded by them. The demo entrypoint (`docker/entrypoint.sh`) runs `intakt:ai:tiers` after its last container rebuild with standard output discarded, so the start log holds the notes, and then writes the mark `provider-notes-shown` beside `INTAKT_CONFIG` on the data volume; a start that finds the mark skips the call, so only the first start on a volume prints them (a mark that cannot be written does not stop the start, the next start prints them again). A failed `intakt:ai:tiers` (for example, a project file it cannot read) does not stop the start either: the entrypoint prints `intakt: could not print the provider notes; the next start tries again` to standard error and writes no mark, so the next start calls it again.

**Accounts.** The top-level `accounts` key of Intakt's config file (validated by `ProjectsConfiguration`: per provider a list of at least one name matching `Contract\Account::NAME_PATTERN`, each listed once, default `[default]`) names each provider's accounts in the order they are tried. `Contract\Account` (provider and name) reads the provider's variables for `default` and the variables with `_<NAME>` appended for any other name; `key()` is `<provider>.<name>`, unambiguous because neither part can hold a dot. An account with a missing variable is left out with `Account "<name>" of provider "<provider>" is disabled: set <VARIABLE> to enable it.` in `intakt.ai.disabled_accounts`; the provider goes into `intakt.ai.disabled_providers` (with the first listed account's variables) only when none of its accounts is set. The parameter `intakt.ai.accounts` lists the enabled account names per provider (`Contract\EnabledAccounts`). The parameter `intakt.ai.listed_accounts` (`Contract\ListedAccounts`, read by the dashboard's team roster) lists every configured account name per provider, enabled or not, except for a provider with no enabled account that the file does not list under `accounts` (so it keeps only its implicit `[default]`; an explicit `[default]` stays listed), so a provider the owner never set up is not shown; `codex` accounts the file lists under `accounts` stay listed also without the `codex` section. `Contract\AccountCredentials::areSet()` (`Infrastructure\ConfiguredAccountCredentials`, read by the same roster) is true for an account among the enabled ones, and for a `codex` account only while its kept login file exists and parses the way a call reads it (`CodexLogins::hasLogin()`: a file a call would reject with `CodexLoginUnusable`, such as `{}` without tokens, counts as no login). The default account keeps the bundle's platform (`ai.platform.anthropic`, `ai.platform.openai`, `ai.platform.generic.openai_compatible`, `intakt.ai.platform.claude_code`). The bundle configures one `anthropic` and one `openai` platform, so another account of those is built with the bridge's `Factory::createPlatform()` and the arguments the bundle passes; another `openai_compatible` account is the generic platform `openai_compatible_<name>`, and another `claude_code` account gets `intakt.ai.claude_code.cli.<name>` and `intakt.ai.platform.claude_code.<name>`, running in `var/claude-code-<name>/`. Every `codex` account gets `intakt.ai.codex.cli[.<name>]` and `intakt.ai.platform.codex[.<name>]` (no suffix for `default`); `codex` has no variables, so its listed accounts are all enabled when the `codex` section is set and the provider is left out of every other parameter (not disabled) when it is not, keeping only the accounts the file lists for it in `intakt.ai.listed_accounts`. Each enabled provider is the service `intakt.ai.accounts.<provider>`, an `Infrastructure\AccountFailoverPlatform` over its accounts' platforms in the listed order.

**Cooldowns and failover.** `AccountFailoverPlatform::invoke()` reads once per account how long it waits (`Contract\AccountCooldowns::secondsUntilFree()`, and for a model id that pins a router provider the longer of that and the pin's own wait, see "Pinned provider cooldowns" below), drops every account whose wait is above zero, throws `Contract\EveryAccountCoolingDown` before any call when none is left (with `secondsUntilAnAccountIsFree`, the shortest of those same waits, so at least one second; the waits are never read a second time for it) (or the rejection, see "Rejected keys" below), logs at info level when the first listed account is skipped, and hands the call to a Symfony AI `FailoverPlatform` built for this call over the free accounts, each wrapped in `AccountPlatform`. Before each free account sends, the first one too, its `AccountPlatform` reads that account's wait again through the same `ModelWaits::ofAccount()`, because the scan that found it free went on to read the accounts after it, and another worker can cool it or its pin during that scan or while an earlier account is tried: a wait above zero sends nothing, records no cooldown and throws a `RateLimitExceededException` with that wait, so the failover moves on and, when no account is left, the `EveryAccountCoolingDown` carries the right wait. That read and the request are not atomic: a cooldown another worker writes between them is accepted, because closing that gap would need a lock held across the HTTP call. That `FailoverPlatform` gets a `NullLogger`, because it logs the provider's exception message, which can echo a key; `AccountPlatform` logs each account error of its account (one it cools the account down for, below) at warning level instead, with the account key and the exception (`Account {account} failed.`), whose message the log redacts like every record. A new `FailoverPlatform` per call because it keys its rate limiter by platform class, which every account of a provider shares, and calls a platform that failed again on the next call (`upstream/ai-failover-platform-retries-a-failed-platform/`); its own limiter is a `no_limit` one, since the cooldowns decide. `AccountPlatform` cools its account down on a `RateLimitExceededException` (until `getRetryAfter()`; when that is null, until the `Retry-After` header of the raw HTTP answer, pinned model or not, read as described under "Pinned provider cooldowns" below with the 60-second fallback and the one-day cap; or a subscription plan's measured reset when neither gives a wait, below) or another `RetryableExceptionInterface` (no reset), thrown when the call is sent, later through the `DeferredResult`'s `onError()` (a limit can arrive when the answer is read), or while a stream is read, through the `Infrastructure\AccountStreamFailures` listener's `onError(ErrorEvent)` that an `onConvert()` callback adds to a `StreamResult` (the `onError()` does not fire while a stream is read); an `IncompleteStreamException` is looked through to its previous exception, and `SendFailures::record()` reports a failure it already holds for that account, so each is logged and cooled down once. Any other exception, such as the refusal of an answer Intakt cannot read (`StrictVerdictConverter`'s `ValidationException`, `UnexpectedResultTypeException` or deserialization `RuntimeException`, [review verdicts](review-verdicts.md)), is no account error (issue #1831): `AccountPlatform::coolDownAfter()` matches no cooldown for it, so it is not recorded in `SendFailures`, not logged as a failed account and cools nothing down (`tests/Plugin/SymfonyAiVendor/ClaudeCodeReviewerTest.php` replays the unreadable `claude_code` recordings through an `AccountFailoverPlatform`, and `AccountFailoverPlatformTest.php` a failure read from the answer). A call that fails when it is sent with such an exception (the CLI crashing, a non-retryable bad request) is logged at warning level as `Account {account} could not send the call.` with the exception, redacted like the other record, because the `FailoverPlatform` logs nothing and chains no cause. `AccountPlatform` also puts the account key in the result's metadata (`Account::METADATA`). When `FailoverPlatform` fails with every account and all of them now cool down, the error becomes `EveryAccountCoolingDown`; when an account is free again and every account the call did send to failed with a limit (`SendFailures::isEveryTriedLimited()`), the outcome depends on which account is free (`AccountFailoverPlatform::typed()`). When a free account is one the call never sent to (skipped by its pre-send read, or not free when the call began; `freedUntried()`), it becomes `EveryAccountCoolingDown` with a wait of one second, so the vendor's retry reaches that account. Otherwise every free account was sent to and limited, so no window stands (a pin ended between its save and that read, or a store saved none; issue #3975): a pinned call becomes `EveryAccountCoolingDown` with the shortest wait its limited accounts named (per account the longer of what its limit still has to run, `SendFailures::limitedWait()`, and the window now stored for it, then the shortest over those and over the stored wait above zero of every account the call never sent to, as when no account is free, so the wait does not depend on whether a limited account's window was saved; `AccountPlatform::coolDownLimited()` records through `SendFailures::limitedUntil()` the time each limit ends, before it writes either store: the reset or the header's wait, at least one second, 60 seconds when neither names one, at most a day), so a pin that ended after its save waits the one-second minimum, a 120-second reset whose windows were not saved waits 120 seconds, and an account another worker extended is not retried early, never a flat second; an unpinned call keeps the failover's error. When an account the call sent to failed otherwise, the failover's error stays; when every account it sent the call to threw a transport error while sending, it becomes `EveryEndpointUnreachable` (see "Rejected keys" below). `Infrastructure\AccountCooldownWindows` implements `AccountCooldowns` with Symfony RateLimiter: a `fixed_window` limiter of one call per account key, anchored (`anchor_at`) at the end of the cooldown with a one-month interval (the shortest the RateLimiter anchors), in the cache pool `intakt.ai.account_cooldowns` (`config/packages/cache.yaml`: `cache.app` on this host's filesystem, so every worker shares it; an array pool in tests) with the application's `LockFactory`. A cooldown lasts the reset the provider sent; without one (`coolDown()` given `null`) it lasts 60 seconds. `AccountPlatform::coolDownLimited()` calls `coolDownUntilPlanResets()` instead for a `RateLimitExceededException` without a reset on an account whose provider `spendsAPlan()` (`claude_code`, `codex`; issue #1749: a spent Codex plan, `CodexAccountFailure::UsageLimitReached`, names no reset): it lasts until the latest `resetsAt` still ahead among the account's windows whose last reading through `Budget\Contract\MeasuredUse::of()` is at or above 100 percent, else 60 seconds; a read that throws is logged at warning level (`The measured readings of account {account} could not be read.`) and keeps the 60 seconds, so the provider's limit still reaches the caller. Only the demo's `Budget\UseCase\ReplayDay\DayReplay` records readings today, so outside the demo that cooldown is 60 seconds too. An outage or other retryable error without a reset keeps 60 seconds whatever the readings say (`tests/Core/Ai/Infrastructure/AccountPlatformCooldownTest.php`). At most 86400 seconds in every case. A rejected key (`coolDownRejected()`) always cools for 60 seconds; a reset of zero or less starts none in the store, so `AccountPlatform::coolDownLimited()` raises a limit's reset of zero or less to one second before it cools the account and the pin, and a second limit while one runs keeps the first. Each new cooldown appends `account_cooled_down` (`account` key and `until` in ATOM) to the ledger, written from the readonly payload class `Infrastructure\AccountCooledDown` through the `stored` serializer (`tests/Core/Ai/Infrastructure/AccountCooledDownTest.php`); a refused append is logged at error level and the cooldown still holds. `secondsUntilAnAccountIsFree(provider)` is zero while an account is free, else the shortest wait, at least one second. Tests: `tests/Core/Ai/Contract/AccountTest.php`, `tests/Core/Ai/Infrastructure/AccountCooldownWindowsTest.php`, `AccountFailoverPlatformTest.php` (`MockPlatformFactory` platforms, and `FailingWhenRead` for a limit read from the answer), `ProjectsConfigurationTest.php`, and `tests/Application/ProjectTiersTest.php` (a kernel with two accounts of one provider).

**Pinned provider cooldowns.** A model id that pins a router provider after its colon (`deepinfra` in `moonshotai/Kimi-K3.1-Pro:deepinfra`) is named by `Contract\PinnedProvider`: the `Account` the call runs on and the router provider name; `key()` is `<account key>:<router provider>`, unambiguous because an account key cannot hold a colon. `Contract\PinnedProviderCooldowns` has `coolDown(PinnedProvider, seconds)`, `isCoolingDown(PinnedProvider)` and `secondsUntilFree(PinnedProvider)` (zero once the window has ended, else the time left rounded up to a whole second, counted in microseconds), implemented by `Infrastructure\PinnedProviderCooldownWindows` (aliased with `#[AsAlias]`). It saves the window's end (`ClockInterface::now()` plus the seconds) as a `DateTimeImmutable` in the same pool `intakt.ai.account_cooldowns`, under `pinned-provider-cooldown-<xxh128 of the key>` (hashed, because a router provider name may hold characters PSR-6 reserves), so every worker shares it. The item has no expiry: `isCoolingDown()` is true only while the clock is before the saved end, so the clock alone decides, and a test clock forced past the end makes the provider usable again. A window of zero or fewer seconds saves nothing, and a longer one than `AccountCooldowns::LONGEST_SECONDS` (86400, the account windows' cap) is cut to it, so a pin never reads back more than a day. A window ending later than the running one extends it, and one ending earlier leaves the running one, because answers in flight arrive in any order and the provider is not usable before every window it named has ended; `coolDown()` reads the running end and writes the new one while holding a Symfony Lock on the item's key (the autowired `LockFactory` over file locks in `var/locks`, so every worker on the host takes the same lock). When the cache refuses the write, or the lock or the cache fails with an exception, `coolDown()` throws `Contract\PinnedProviderCooldownNotSaved` (with that exception as its cause) instead of returning, so the caller learns the window was not saved: `isCoolingDown()` still reports what the pool held before (usable when no earlier window runs), and the caller must not count on a cooldown it was told failed. Only a model id of exactly the router shape `owner/model:provider` pins: one slash, then one colon, each of the three parts only visible ASCII other than the slash and the colon (`\x21` to `\x7E`), matched up to the very end of the name (options after a `?` left out). A native id with colons (`ft:gpt-4o-mini:org:custom:id`), a tag without an owner (`llama3:8b`), a nested owner (`owner/group/model:router`), a name with a newline anywhere (`owner/model\n:router`, `owner/model:router\n`) or with any non-ASCII character (a no-break space U+00A0, a next-line U+0085) pins nothing; the parser lives in `Infrastructure\ModelWaits::routerProviderOf()`; `openai_compatible` serves routers and plain endpoints alike, so a namespaced tag on a plain endpoint (`team/llama3:8b`) counts as a pin named `8b` on that account, cooled for the same retry-after its account cools for. When such a call answers 429 (sent or read), `AccountPlatform` takes the wait from the exception's `getRetryAfter()`, or, only for a 429 on the read path (the only one that comes with a raw answer), when it has none, from the `Retry-After` header of the raw HTTP answer as RFC 9110 defines it: delta-seconds of any number of digits (leading zeros allowed), or an HTTP date in any of its three forms (IMF-fixdate, the obsolete RFC 850 form, asctime) judged against `ClockInterface`. A value with anything other than visible ASCII and spaces (a NUL byte, a non-ASCII character) is read as no header before any date is parsed, so reading it never throws and the provider's 429 reaches the caller unchanged. Runs of spaces are read as one, because asctime pads a one-digit day with a space (`Nov  9`), and a date counts only when it formats back to that value, so one PHP would read by normalizing it (minute `99`, a wrong weekday) does not parse. Either is capped at `AccountCooldowns::LONGEST_SECONDS` (a day), and a past date or `0` gives one second, like an exception's own reset of zero or less (Symfony AI's generic bridge drops the header when it builds its exception; symfony/ai#2913 is open for it, reproduced in `upstream/ai-failover-platform-deferred-rate-limit/GenericRetryAfterHeaderTest.php`). Without a header that parses, and for a 429 thrown while the call is sent without its own wait, the wait is 60 seconds (`AccountCooldowns::SECONDS_WITHOUT_RESET`). The same wait cools the account first, as for any limit, and then the pin, so a failing store of either never costs the other its window: an account write that throws is logged at warning level (`The cooldown of account {account} could not be saved.`), a pin write that fails likewise (`The cooldown of pinned provider {pinned} could not be saved.`), and in both cases the provider's own 429 reaches the caller unchanged. `AccountFailoverPlatform` reads each account's wait as the longer of its own window and its pin's, once per decision (`waits()`, through `Infrastructure\ModelWaits::perAccount()`), so an account window that outlasts its pin sets the wait; both the free accounts and the reported wait come from that one read, and the exception carries that wait to the vendor: a call that finds no account free reports the shortest of those waits, which is at least a second, so a window that ends or a pin that another worker extends between two reads can never turn a refused call into a wait of 0 (the cause of the earlier zero waits was a second read of the account store, kept in step with the pins, after the first read had refused every account). The account window a pinned 429 also writes is best effort: no wait rests on it, and when the cache refuses it (`AccountCooldownWindows` passes the limiter a `PoolRememberingItsSave`, built for that one cooldown, and takes the cache's own result of the save made under the limiter's lock, so no window is read back and a window another worker saved with the same end is never taken for its own; `AccountCooldownWindowsTest.php` forces that order) the refusal is logged at warning level with the same words, no `account_cooled_down` event is recorded, and the pin still carries the wait. While it runs, another router provider or a model without one on that account waits too. `TierPlatform` judges a model by the wait its provider platform reports for that model alone (`Infrastructure\ModelWaits::secondsUntilFree()`, the same class and the same per-account read of the account window and the pin `AccountFailoverPlatform` decides its calls by, reached through `AccountFailoverPlatform::modelWaits()`), and by `AccountCooldowns::secondsUntilAnAccountIsFree()` only for a platform that is not an `AccountFailoverPlatform`, so one read decides and an account window that ends while the platform is built never keeps the model out; a pin that outlasts its account window, because the account store kept a shorter running window or refused the write, still keeps the model out: a tier with substitutes moves to the first free one, and a tier without them reports the pin's wait. The outages are kept per provider and judged by the first model listed on it (the tier's own model, else its first substitute there), so a cooling pin never moves a tier to another router of the same provider, and the substitute model the ledger records for a provider (`RoundLedger`, the first substitute on it) is always the model that answered. `AccountLimitedVendor` uses the wait an `EveryAccountCoolingDown` in the cause chain of a `ProviderRateLimited` carries and reads `AccountCooldowns::secondsUntilAnAccountIsFree()` only when there is none, because the account windows alone know nothing of a pin. Tests: `tests/Core/Ai/Contract/PinnedProviderTest.php`, `tests/Core/Ai/Infrastructure/PinnedProviderCooldownWindowsTest.php` (`MockClock`, `ArrayAdapter`, two `FilesystemAdapter`s on one folder for two workers, `InMemoryStore` locks, a forced late write of an earlier end), `PinnedProviderRetryAfterHeaderTest.php` (a real 429 through the generic bridge over `MockHttpClient`, with `retry-after` as delta-seconds, as an HTTP date, missing or unreadable), `TierPlatformPinnedProviderTest.php` (tier selection with a cooling pin and a free account window, a pin that outlasts a running 10-second account window in a forced order, and a tier without substitutes reporting the pin's wait), `PinnedProviderCooldownTest.php` (scripted 429s from `MockPlatformFactory` and `FailingWhenRead`, a pinned account skipped without a request and used again after its window, every pin cooling giving the shortest pin's wait, and forced orders: a pin that ends between the reads of two accounts through `ClockMovingAfterARead`, the first free account's pin cooling during the scan through `PinCoolingAfterARead`, a fallback pin that cools while the first account is tried, one that ends again while the last account is tried, an account window the cache refuses while the pin is saved, a reset of zero whose pin the cache refuses, a one-second pin that ends between its save and the read after sending, an untried account's 5-second pin that sets the wait while the limited account's 3600-second reset is not saved, and the same refusal logged with no `account_cooled_down` event while the caller gets the provider's own 429), `tests/Plugin/SymfonyAiVendor/Infrastructure/AccountLimitedVendorTest.php` (the carried wait), and `PinnedProviderCooldownWindowsWiringTest.php` (the container's store, reached through the public test alias `test.intakt.pinned_provider_cooldowns` of `tests/Core/Ai/services.yaml`, on its own pool and pinned clock).

**Rejected keys.** `AccountPlatform` also cools its account down on a Platform `AuthenticationException` (a revoked or wrong key) through `AccountCooldowns::coolDownRejected()`: the same 60-second cooldown, plus a marker `account-cooldown-rejected-<account key>` in the same pool that expires with the running window, so `isRejected()` holds exactly while the account cools down after a rejection. A rejection is an account error only the owner can fix, so `coolDownRejected()` also reports it once: it first saves the pool item `account-cooldown-pending-<account key>`, then, while that item is there, takes the `LockFactory` lock `account-cooldown-reported-<account key>` without waiting, looks for the pending item again under the lock (a worker that paused between its look and the lock finds it gone when another worker reported the error meanwhile, and leaves without reporting it again), deletes it and, only while the pool holds no item of that name, it appends `account_error_reported` (`account` key and `reported_at` in ATOM, from the readonly payload class `Infrastructure\AccountErrorReported` through the `stored` serializer) and then saves the item with the report's moment and no expiry, so an error that outlasts its cooldown is not reported again on each retry. A busy lock leaves the pending item to the worker holding the lock (reporting the account or clearing its report): every holder looks for it again after it releases the lock, so an error that comes while a report is cleared is still reported, and one that comes while the same error is reported is not reported twice. A refused append is logged at error level (`An account error was not reported.`) and saves nothing, so the next error reports it again. Only an answer clears the item: `AccountPlatform` takes the `ClockInterface` of `AccountFailoverPlatform`, notes the moment it sends each call and, when the answer converts (a `StreamResult` only once it is read to its end, through the `Infrastructure\AccountStreamAnswered` listener's `onComplete()`), calls `AccountCooldowns::answered(account, sentAt)`, which deletes the item under the same lock (taken waiting) only when the report is strictly older than the call; an answer to a call sent before or at the report's moment, read after the error, keeps it, and an answer that fails to convert never clears it. Tests: `AccountCooldownWindowsTest.php` and `AccountFailoverPlatformTest.php` (a `MockClock` forces the order of send, report and answer), `tests/Core/Ai/Infrastructure/AccountErrorReportedTest.php`. Each `AccountPlatform` records the class of its account's account error, sent or read through `onError()` or the stream listener, in a per-call `Infrastructure\SendFailures` keyed by account. When every account of the provider rejected its key, in this call (`SendFailures::wasRejected()`) or in an earlier one it still cools down from (`isRejected()`), `Contract\EveryKeyRejected` is thrown instead of `EveryAccountCoolingDown`, since no wait brings a rejected key back; an account cooling down from a limit keeps it a wait. `EveryKeyRejected` is an `AuthenticationException` whose message names only the provider and which chains no previous exception, so the provider's error text, which can echo a key, never reaches a log (the judging's failure listener logs the exception it gets). The same rule holds before the call: when no account is free and every one cools down from an earlier rejection, `invoke()` sends nothing and throws `EveryKeyRejected`. `AccountCooldowns::isEveryAccountRejected(provider)` tells the same over the provider's configured accounts (false for a provider without any). For a key rejected as the answer is read, `AccountFailoverPlatform` returns a new `DeferredResult` whose `Infrastructure\TypedRejectionConverter` turns the `AuthenticationException` into `EveryKeyRejected` or `EveryAccountCoolingDown` by the same rule; with a free account left it becomes `Contract\KeyRejected`, an `AuthenticationException` that names only the account key and chains nothing, and the review starts again on it. A key rejected as the call is sent never surfaces at all: `FailoverPlatform` moves on to the next account, and its own error when every free account fails (`All platforms failed.`) chains no cause. With Symfony's HTTP client a failed name lookup, a refused connection or a timeout surfaces only when the answer is read, not when the call is sent, so no other account is tried: the `TransportExceptionInterface` reaches the vendor through the answer, which types it as `ProviderUnreachable` and asks the reviewer once more (see [Vendor](vendor.md); `tests/Plugin/SymfonyAiVendor/AnthropicUnreachableRetryTest.php` builds the Anthropic bridge with its own factory over a `MockHttpClient` whose response fails the lookup). The send-time path is only a guard for a platform that throws a `TransportExceptionInterface` while sending: `AccountPlatform` notes in the same `SendFailures` each account the call is sent to (`tried()`) and each that threw such an error as it was sent (`unreachable()`, which cools no account down); when every account the call was sent to was unreachable (`isEveryTriedUnreachable()`), `AccountFailoverPlatform` throws `Contract\EveryEndpointUnreachable` instead of the failover's error, judged over the accounts actually tried, so an account whose cooldown ended during the call does not hide it. `EveryEndpointUnreachable` is a `TransportExceptionInterface` whose message names only the provider and which chains nothing, so the transport error's text, which names the request's URL, never reaches a log, and the vendor retries the review like any unreachable endpoint. With one account unreachable and another failing otherwise, the failover's error stays. Tests: `AccountFailoverPlatformTest.php`, `tests/Plugin/SymfonyAiVendor/ReviewerRetryVendorTest.php`, `AnthropicUnreachableRetryTest.php`. The converter offers the account's `TokenUsageExtractor` only while the account's answer carries no usage, so an answer read through it holds its usage once, and one that failed to map still has it read from the raw answer.

It runs in the `serial` group, not in the parallel test workers, because a container another worker compiled while `config/secrets/` exists would keep the framework's vault loader ([conventions](conventions.md)), saving and restoring `$_SERVER`, `$_ENV` and the process environment. `tests/Core/Ai/Infrastructure/DisabledProvidersWarningTest.php` covers the warning, including that a console output gets it on its error output only. Tests that need a model answer use Symfony AI's `MockPlatformFactory` or a `MockHttpClient` under the real bridge, never a provider.

### Provider descriptors

The facts of each provider a key can belong to live outside Core, in `src/Plugin/SymfonyAiVendor/Infrastructure/`. The contract `Intakt\Plugin\Vendor\Contract\ProviderDescriptor` names them: `id()` (the provider id Core keeps: `anthropic`, `openai`, `huggingface`), `label()` (the name a refused key's message lists), `variables()` (an `EnvironmentVariables` of the Ai contract; the first one holds the key, so a kept key is served as that variable), `keyPattern()` (a regular expression anchored with the `D` modifier), `baseUrl()` (a `Uri\Rfc3986\Uri`), `tierProvider()` (the `Provider` the project tiers name the provider's models under), `checkModel()` (null takes the light tier's model, so no model id is in PHP) and `answerTokensAtLeast()` (the smallest answer cap the provider accepts). `SymfonyAiProvider` extends it with `platform(secret, model, http)`, which builds the Symfony AI bridge that speaks the provider's API with an `InMemoryModelCatalog` listing the check model with `INPUT_MESSAGES` and `OUTPUT_TEXT`, so a light-tier model the bridge's own catalog does not list is still called.

- `AnthropicDescriptor`: `sk-ant-` followed by at least eight letters, digits, `_` or `-`; the Anthropic bridge on `https://api.anthropic.com`; one token.
- `OpenAiDescriptor`: `sk-` with the same body, `sk-proj-` included but not `sk-ant-`, so an Anthropic key with too short a body (cut off when pasted) is refused instead of being taken for an OpenAI key; the Open Responses bridge (`symfony/ai-open-responses-platform`, which the OpenAI bridge builds on, pinned like the other Symfony AI packages) called at the descriptor's base URL `https://api.openai.com`, because the OpenAI bridge takes a region instead of a base URL; 16 tokens, because OpenAI's Responses API refuses a smaller `max_output_tokens`.
- `HuggingFaceDescriptor`: `hf_` followed by at least eight letters or digits; `HF_TOKEN`; the generic bridge on the `router_url` of `config/sample-project.yaml` (`https://router.huggingface.co`), read through `Review\Contract\SampleProjectData` when the base URL is asked; tier provider `openai_compatible`, where the image puts the router models; one token. `huggingface` is a provider id of the catalog only; it is not a `Provider` case.

The variables of the first two are read from the `Provider` enum, which still builds the accounts from them. Each descriptor takes its base URL as an optional constructor argument whose default is the URL above (for `HuggingFaceDescriptor` the argument is null by default and the data file's router URL is used), and its `platform()` sends to that URL, so `SymfonyAiKeyCheckTest` moves it to show that the call follows it, and checks that a Hugging Face key is called at the data file's router URL. `SymfonyAiProviderCatalog` implements the contract `ProviderCatalog` and is the one list of descriptors, in that order: `descriptors()` gives the list and `descriptor(id)` the one with that id, or null.

Model ids and provider hosts are written nowhere else under `src/`: the `phpstan` gate's `intakt.providerLiteral` reports one outside a class that implements `ProviderDescriptor`, except the hosts its shrink-only list `ratchet/provider-literals.neon` still holds for the Claude Code and Codex adapters ([quality gates](quality-gates.md)); the sample project's model ids live in `config/sample-project.yaml`.

**Adding a provider.** Write a descriptor class in `src/Plugin/SymfonyAiVendor/Infrastructure/` that implements `SymfonyAiProvider`, with a key pattern that no listed pattern also fits; add it to the default list of the `SymfonyAiProviderCatalog` constructor; add its keys to the cases of `tests/Plugin/SymfonyAiVendor/Infrastructure/SymfonyAiProviderCatalogTest.php` and `SymfonyAiKeyCheckTest.php`; and add its key variable to the `$names` of `HeldCredentials` in `config/services.yaml`, so logs redact it. A retired check model is replaced by editing the light tier in the owner's config, not PHP.

### Provider key

`Intakt\Core\Ai\Contract\ProviderKey::recognise()` takes a key as typed and a `ProviderCatalog`, trims surrounding whitespace and asks the catalog which provider the key belongs to: the key must fit the key pattern of exactly one listed descriptor, whose id the `ProviderKey` keeps, so a key two patterns fit is refused instead of going to whichever provider is listed first. Any other key, including an empty one, throws `KeyNotRecognised`, whose message lists only the labels of the listed providers (`The key has the form of no listed provider (Anthropic, OpenAI, Hugging Face).`) and never carries the input.

`ProviderKey` offers its `provider()` id and its `configured()` state, a `ConfiguredKey` holding the provider id and at most the last four characters (at most a quarter of the key, so a short key shows fewer, and a key under four characters shows none). `ConfiguredKey` keeps only the last four characters of whatever it is given, so even a whole key passed to it shows no more. The key itself is kept in a `SensitiveParameterValue`, has no string conversion and no public getter except `secret()` (used by the key check, to write the kept file, to resolve the kept key and to redact it from logs), and arrives as a `#[SensitiveParameter]`, so `var_dump`, `print_r`, `var_export` and an exception trace do not show it. `Intakt\Core\Dashboard\UseCase\KeepProviderKey\KeepProviderKey::keep()` recognises a key through the catalog, checks it through the vendor contract `Intakt\Plugin\Vendor\Contract\KeyCheck` and, only when the outcome is `Accepted`, keeps it through the Ai contract `KeptProviderKeys` before it returns the `ConfiguredKey` (a refused or unchecked key is never written); `configured()` reads the state back from the kept file. `Infrastructure\KeptProviderKeyFile` implements `KeptProviderKeys` and keeps the one key in `var/data/provider-key.json` (the data volume; the directory is the parameter `intakt.ai.kept_key_directory`, which `config/packages/ai.php` sets from `INTAKT_PROVIDER_KEY_DIR` when that is set in the test environment only; any other environment ignores the variable and keeps `var/data`, which `KeptKeyDirectoryConfigTest` shows for `prod` and `test`) as JSON with its provider id (`provider`, and the same id again as `kind`, the field earlier releases read, so a rollback still finds the key) and key. The write goes to a new file in the directory (mode 0600, the directory created with 0700 when missing) that is then hard-linked to the path and removed, so the key is never readable by others. A link fails when anything is at the path, and a symbolic link there (a dangling one included, which PHP may resolve before it links) is refused before the link is tried, so `keep()` never replaces a kept key and never writes through a link there: it throws `ProviderKeyAlreadyKept` (fixed message) instead, and of two requests that both found no key only the first to link keeps its key. A write that fails otherwise removes its new file and throws `KeptProviderKeyNotWritten` (fixed message, no previous exception, because the failed call's arguments in its trace hold the key). `read()` treats the file as outside input: it rebuilds a `ProviderKey` through `recognise()` with the catalog, so the configured state comes from the one rule in `ProviderKey::configured()`, returns `null` when no file exists, and throws `KeptProviderKeyUnreadable` (fixed message, no file content) for a file that cannot be read or parsed, that has no `provider` (a file kept by an earlier release, with only `kind`, reads its provider from `kind`, the ids being the same) or no `key`, whose key does not have a recognised form (a value too short for its form included) or whose form names another provider than the one stored. `KeyCheck::check()` returns a `KeyCheckOutcome` (`Accepted`, `Refused`, `NotChecked`) and never throws for a provider failure. `SymfonyAiKeyCheck` takes the key's descriptor from `SymfonyAiProviderCatalog`, builds its platform over the injected HTTP client and makes one call with the constant prompt `Answer with the single word: ok` (one user message built by `Review/Contract/PromptAssembly::notice()`), the check model and the descriptor's `answerTokensAtLeast()` as `PlatformOptions::MAX_OUTPUT_TOKENS`. The check model is the descriptor's `checkModel()` when it names one (no shipped descriptor does), else the light tier's own model (`TierResolver::configured()`) of the first project, in the order of the config file, whose light tier is on the descriptor's `tierProvider()`; a project whose light tier cannot be read is skipped. Without such a project, as on a fresh install, it is the light model `config/sample-project.yaml` gives that provider (`SampleProjectData::model()`), the one a fresh project gets. For a key whose provider the catalog does not list, the outcome is `NotChecked` and no call is made. The answer is read only to see that the call succeeded and is then dropped. An `AuthenticationException` is `Refused`; any other failure (unreachable, limited, a server error, a model the provider does not know) is `NotChecked`, so a key is not called bad on a bad moment, and logs the fixed warning `A provider key could not be checked.` with the context `provider` (the key's provider id) and `exception_class` (the failure's class), never the exception itself, its message or its chain, because the key being checked is not kept yet and so is no held credential the log redacts; a refused or accepted key logs nothing. `keep()` throws `KeyNotRecognised`, `KeyRefusedByProvider`, `KeyNotChecked`, `ProviderKeyAlreadyKept` or `KeptProviderKeyNotWritten`; the messages are fixed and no exception keeps the provider's exception as its previous one, because a provider's text can echo the key, so the key reaches no log or message. Tests script the provider with Symfony's `MockHttpClient` under the real bridges, so each provider's endpoint (its descriptor's base URL), request body (the light-tier model and the descriptor's token minimum) and refusal are pinned, and a stubbed `TierResolver` gives the light tiers. `Infrastructure\KeptProviderKeyVariables` is a Symfony env var loader (`EnvVarLoaderInterface`, autoconfigured as `container.env_var_loader`): it returns the kept key as the first variable of its provider's descriptor (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `HF_TOKEN`); for a descriptor whose `tierProvider()` is `openai_compatible` but whose variables are not that provider's (Hugging Face), it also returns `OPENAI_COMPATIBLE_BASE_URL` as the descriptor's `baseUrl()` and `OPENAI_COMPATIBLE_API_KEY` as the key, as `docker/entrypoint.sh` does for `HF_TOKEN`, unless the environment or any other env loader (the secrets vault's included, handed to it as `#[AutowireIterator('container.env_var_loader')]`, which leaves the loader itself out) sets either of them to a value, or lists one whose value cannot be read or fails to load at all (such a failure logs only the fixed warning `Another env loader failed, so its variable counts as set and the kept key does not stand in for it.` with the context `loader` (the failing loader's class) and `exception_class` (the failure's class), never the exception or its message, which can carry vault content; #2232, so a token pasted on the setup wizard's AI account step lets the seed write the sample project, and the token never goes to an endpoint the owner set in the vault nor the owner's key to the router; `config/packages/ai.php` hands it the vault when it reads the kept key at build time); and an empty list when no file exists, the catalog lists no descriptor of its provider, or the file is unreadable (it then logs only a fixed warning, never file content). `config/packages/ai.php` builds it, and the `KeptProviderKeyFile` it reads, with a `SymfonyAiProviderCatalog` of its own and the framework's fallback logger (`Symfony\Component\HttpKernel\Log\Logger` at level `warning`, on stderr), because the container is not built yet; so both warnings reach stderr when the container is built, as the message only, since that logger prints no context (`loader` and `exception_class` reach only the app's logger at run time; `KeptKeyBuildWarningTest` covers both warnings). Symfony's env processor asks its loaders only for a name the environment lacks (or holds empty) and takes the first loader's non-empty value in tag priority order; the class carries `#[AsTaggedItem(priority: -100)]`, below the vault's loader (`secrets.env_var_loader`, priority 0), so the order is: the environment (a value in `.env.local` included), the secrets vault, then the kept key; a kept key is used like the same variable in `.env.local`. `config/packages/ai.php` decides at build time whether a provider is enabled and counts the kept key as set last, in the same order, so a kept key enables its provider after the container is rebuilt (the cache cleared or the app restarted); an install with a value in the environment is unchanged. It does not count the kept key for a variable whose vault secret throws when revealed (see "A kept key behind such a secret" above), because the run-time lookup would throw in the vault's loader first. `HF_TOKEN` is held and redacted but turns on no platform by itself, since Hugging Face is no `Provider`; a kept Hugging Face token turns on `openai_compatible` through the two variables above. `Platform\Infrastructure\HeldCredentials` also holds the kept key's value (through the Ai contract `KeptProviderKeys`; an unreadable file holds nothing, so the logger still writes), so `RedactedJsonFormatter` removes it from every log record. Tests: `KeptProviderKeyVariablesTest` (with the vault's loader as `FixedEnvVars` beside it, through Symfony's `EnvVarProcessor`: a vault base URL or key alone keeps the stand-in off, an empty vault value does not, an unreadable vault value or a failing loader keeps it off), `KeptProviderKeyVariablesWiringTest` (the container hands the loader every other env loader but itself), `HeldCredentialsTest` and the `AiProvidersTest` cases for a kept key, for the key the platform sends, for the environment and the vault winning, and for a kept key behind a vault secret that throws or returns nothing.

**The endpoint that keeps a key (#2258, part 2 of #2231, decision D2).** `dashboard_keep_provider_key` is `POST /setup/provider-key` (`Dashboard\UseCase\KeepProviderKey\KeepProviderKeyController`, under the `dashboard_` prefix, so `RefuseForeignHost` covers it); the dashboard has no login, so three guards stand in front of it. It checks the CSRF token of the id `dashboard_keep_provider_key` first (`400`, nothing kept, through `FormPress`). It then refuses while a key is configured: the kept file holds one (`KeepProviderKey::configured()`), or any provider has an enabled account (`EnabledAccounts::of()`, which counts a key from the environment, `.env.local` or the vault); an unreadable kept file refuses too, with its fixed message. The refusal is a flash line and a `303` back to the setup wizard's AI account step, `/setup?step=3` (every answer of the form goes there), so changing a key later stays an edit of `.env.local`. The provider check runs between this guard and the write, so a second request can pass the guard while the first is still checked; the write itself then refuses (`ProviderKeyAlreadyKept`, see above) and the second request gets the same "already configured" line, so the first key stays. Only then does it read the form field `key` straight into `KeepProviderKey::keep()` (a `#[SensitiveParameter]`) and turn each outcome into a fixed flash line: kept (the provider id and the last four characters only, and that a restart makes the provider enabled), not a recognised form (the line is `KeyNotRecognised`'s message, which lists the catalog's labels), refused by the provider, not checked, or not written. No flash, redirect, exception message or log record carries the key. The key goes to the provider check and never into a prompt, so the fencing helper does not apply. The form that posts to it is on step 3, AI account, of the setup wizard (#2259, part 3 of #2231; #3751): `ProviderStep::offersKeyForm()` shows it only while no provider has an enabled account, no key is kept and the kept file is readable; `SetupSteps` reads `KeptProviderKeys::configured()` and hands the page only a `ConfiguredKey` (provider id and at most four characters) or a flag that the file is unreadable, never a key, and the catalog's provider labels for the field's label (`ProviderStep::$keyLabels`), so the page names no vendor of its own. The form has one `type=password` field `key` without a `value` (so a key is never sent back), `autocomplete=off`, and the token of the controller's `TOKEN_ID` through `constant()`. There is no provider select: the provider is recognised from the key's form through the catalog. A kept key reads "The <provider id> key ending in <last characters> is kept. Restart Intakt to use it."; an unreadable kept file is the step's error.
