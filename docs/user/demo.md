# The demo and the sample repository

The demo shows a review from start to end without a project of your own. `fixtures/sample-repository/` holds a small shop project with a change that carries deliberate issues, and `docker compose up` seeds it as a sample project you can review and play back in the dashboard.

## The sample repository

`fixtures/sample-repository/` holds a small shop project to try a review on. `base/` is the base commit and `pull-request/` holds the files the pull request branch adds or changes. The branch carries three deliberate issues (a bug, a new function without a test, and a command built from input), listed in `issues.json` so a later check can tell whether a review found them. The folder's `README.md` has the git commands that turn it into a repository with a `main` branch and a `sample-change` branch. The demo builds that repository for you (see below). The same folder holds `bench/`, eight small changes (three of them without any defect) with the defects planted in them, which measure how well reviewers find defects. `php bin/console intakt:bench:review <change> --project=<project>` reviews one of them (a folder name under `bench/`, for example `free-shipping`) with the project's review panel and prints, for each reviewer, the planted defects it caught or missed, its false alarms on a change without defects, the tokens and the time it used, and the judge's act list, with the Intakt version and a hash of the review prompts and of the bench files. **It calls your paid models**, so it runs only when you ask: nothing in `bin/check` or CI runs it. Start the workers first, as for `intakt:review`. It builds its own temporary repository for the run in the system's temporary folder and removes it afterwards. A reviewer that failed is shown with its harness failure, and its missed defects are not counted against it.

### The review bench

`php bin/console intakt:bench --project=<project>` reviews every bench change, one after the other in name order, the same way, except that it builds each checkout under `var/bench/checkouts/` and removes it after its review. Add `--repeat=<n>` to review each change `n` times (1 by default, at least 1), each time from a fresh checkout, to see how much the answers vary. The report comes in three parts:

1. **Failure causes**, before any figure: every missed defect with its cause (`reviewer`: the model missed it; `bench`: the expectation cannot hold), every false alarm on a change without defects with its place (cause `reviewer`), and every run where a reviewer failed (a provider or tool failure) with its reason. Those failed runs are left out of the defect counts.
2. **Figures**: one line per run of each change and per reviewer, then whether the runs of that change agreed: `runs agree` when every run reached the same decision and each reviewer caught the same defects and raised a false alarm or not in each, `runs disagree` otherwise, and `runs not comparable` when fewer than two runs are left after leaving out failed ones. This only tells you whether the runs agreed; it is not a statistical claim.
3. **Totals per reviewer and model** over every run: planted defects found out of planted, false alarms, failed runs left out, rounds and tokens.

Each reviewer is named by its role, tier and the model its calls ran on (for example `role-1 (standard, model big)`), so runs of one role answered by another model are counted apart. A reviewer that failed before any call has no model and is named `model not recorded` in its run's line; in the totals it joins the line of its role and tier when that role and tier has exactly one model line (for example `role-1 (standard, model big)`), and keeps its own `model not recorded` totals line when it has several model lines or none, since the model it would have used is then unknown. Every figure is labeled as measured. It also writes everything into one JSON file under `var/bench/`, named after the moment of the run in UTC (for example `var/bench/20261115T103000Z-1a2b3c.json`), and prints its path: the Intakt version, the hashes of the review prompts and of the bench files, and per change whether its runs agreed and, per run, the decision, the judge's act list and per reviewer its models, the caught and missed defects (each miss with its cause), the false alarms, the other findings, a harness failure, the tokens and the time. **It calls your paid models** for every change and every repeat, so it too runs only when you ask, and nothing in `bin/check` or CI runs it. When a review cannot run (for example the project maps no model to a tier its panel needs), it stops with the error, exits with 1 and writes no file. Comparing result files with each other comes later.

**What a run costs.** Each review of a bench change is one round of the project's panel: every reviewer reviews the change once, and the judge is called once when the reviewers raised at least one finding (with no finding the round is decided without it). A run reviews the eight changes `--repeat` times. On the demo panel of the project `sample` (two reviewers, `correctness` and `security`), `--repeat=3` makes 24 rounds: 48 reviewer reviews and at most 24 judge calls, all billed to your keys or token. A reviewer may send several model requests in one review while it reads the change through its tools. The report's `calls` is the number of usage reservations (one per started review call), not of single model requests, so the tokens of those requests are summed under one call and `calls` can be lower than the requests sent. The report and the result file count the reviewers' tokens only, not the judge's. Intakt prints no price for a bench run: multiply the reported tokens by your provider's prices for a figure in money.

**Reading a bench result.** Read the failure causes first: a `harness failure` means the run says nothing about the reviewer (the provider or a tool failed) and is left out of the defect, false alarm and agreement counts (its rounds, calls and tokens are still totaled), and a miss with cause `bench` points at the bench, not the model. Then, per reviewer, the totals line answers the three questions of [the bench page's table](../bench.md#review-bench):

- **Defects found**: `<n> of <m> planted defects found`. The bench plants five defects, so with `--repeat=3` a reviewer that ran without a failure has 15 to find.
- **False alarms**: `<n> false alarms`, findings on the three changes without any defect. A finding on a change with a planted defect that matches none of its defects is not counted as a false alarm; the result file lists it under `unmatched`.
- **Tokens per change**: the total tokens divided by the number of reviews (8 times `--repeat`, for example 24).

The review bench section of `docs/bench.md` also holds one sentence, `Each change ran 3 times.`, which tells the dashboard how many runs the published result covers. The dashboard reads the count only when that sentence appears exactly once in the section; if it appears twice or more, or the number is 0 or written with leading zeros, it shows the published totals without a run count. The command prints no row for the panel as a whole. Its panel row is worked out by hand from the result file: a planted defect counts as found by the panel in a run when at least one reviewer caught it there, and its false alarms and tokens are the reviewers' added together. Under the figures, `runs agree` means a change got the same outcome in every repeat, and `runs disagree` that the answers varied, so one run's figure for that change is a matter of luck. The result file is written inside the install: with docker compose it is in the container under `/app/var/bench/`, outside the data volume, so copy it out (for example `docker compose cp intakt:/app/var/bench ./bench-results`) before you remove the container.

A key checked and accepted from the browser is kept in the data volume, in `var/data/provider-key.json` (`/app/var/data/provider-key.json` in the container), a file only the app user can read (mode 0600). The page shows only that a key is configured, with its provider and at most its last four characters; the key itself is never shown again and never written to a log. The check is one short call to the key's provider with the model your config maps to the `light` tier on that provider (for a Hugging Face token, the `light` tier on `openai_compatible`), taken from the first project that has one; to check with another model, change that tier. A key the provider refuses, or that could not be checked (also when no project maps its `light` tier to that provider), is not kept. A value in `.env.local` (or the environment) or in the secrets vault wins over the kept key; the kept key is used for a provider only when there is no such value, and, as with `.env.local`, after the app is restarted or its cache cleared. One case keeps the provider switched off even with a kept key: the secrets vault holds a secret of the same name, and `SYMFONY_DECRYPTION_SECRET` decodes to a key of the wrong length, or there is no decryption key at all (it decodes to nothing and the vault has no key files). The vault is asked before the kept key and fails with an error there, so Intakt does not turn the provider on; repair the decryption key or remove that secret from the vault, then restart the app or clear its cache. An empty secret, or one a wrong key of the right length cannot open, does not stand in the way: the kept key is used. A kept file that cannot be read (damaged, or holding no key of a known form) is ignored, and standard error shows `The kept provider key could not be read, so it is not used.` when the configuration is built; remove the file (then keep a key again from the browser if you want one) and restart the app or clear its cache. A kept Hugging Face token is kept and hidden from logs but turns on no provider.

## The demo with docker compose

```
cp .env.dist .env.local   # optional: set one or two provider keys (or HF_TOKEN)
docker compose up -d --wait
```

No file needs editing to start: without `.env.local` the dashboard opens, and `docker compose up -d --wait` returns once the container reports healthy, which it does only when the dashboard answers and the sample is seeded. A review needs at least one of `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and `HF_TOKEN` in `.env.local` (copy `.env.dist`; every value in it is optional), or one key or token pasted on the first-run page (below). When `APP_SECRET` or `MERCURE_JWT_SECRET` is empty, the first start makes a random one (64 hex characters) and keeps it in the volume, in `/app/var/data/app-secret` and `/app/var/data/mercure-jwt-secret` (mode 0600, never printed), so a restart keeps it; a value you set in `.env.local` wins and no file is written for it. A start that cannot write the file stops with `intakt: could not make or read APP_SECRET in <file>; ...`. The image is built from the `Dockerfile`, the dashboard answers on `http://localhost:7781` (on this computer only), and the data lives in the volume `intakt-data`.

The first start seeds the demo, in the volume:

- the sample repository at `/app/var/data/sample-repository`, with the branch `sample-change` to review against `main`;
- the project `sample` in `/app/var/data/intakt.yaml`, with a panel of two reviewers (`correctness` and `security`) that must both approve. With one Anthropic or OpenAI key, both reviewers use that provider; with both keys, `correctness` uses Anthropic and `security` uses OpenAI. With `HF_TOKEN` beside one or both keys, `security` moves to Hugging Face, so the two reviewers use two providers; with `HF_TOKEN` alone, see [Running the demo on a Hugging Face token](#running-the-demo-on-a-hugging-face-token).

Open `http://localhost:7781`. While no review has run yet, `/` sends you to the first-run page (`http://localhost:7781/setup`), which opens with **See a real review**:

- **Watching a recorded review** needs no key. When the demo run can be played, **Play the demo run** sits under the title as the page's one main button, with "1 minute · no key" above it (see [Playing the demo run in the dashboard](#playing-the-demo-run-in-the-dashboard)); otherwise one plain line says that this install has no recorded review.
- **Running it live with your key**: under **Use your own project**, paste the key or token in the **Add a key here** card and keep it (while no provider has a key, the line under the title says to add one below; once one has, it says a live review can be started or opened from the cards below, or that no card can start one yet while Intakt waits for the restart), restart Intakt (`docker compose restart intakt`) so the sample project gets its reviewers, then press **Start the first review** in the **First review** card. It reviews the sample change, the same review as `intakt:demo` below, and opens its live review page, where each reviewer and then the verdict appear as they come in.

Between the two, three small pictures show what a review does: the reviewer (Read), the judge (Check) and the developer (To fix). Each of the three cards is marked Done, Missing or Not needed, and the first card with something left to do has an orange ring.

Once a review has run, `/` opens the board on a computer and Waiting on you on a phone, or the newest review when every card is Done, nothing is running and nothing waits on you (the board is then at `/?board=1`, which the Now entry of the menu opens), and the Projects page's **Set up Intakt** button leads to the first-run page. Connecting a repository, creating the GitHub App and adding an account in the browser are not on the page yet: they are done in configuration today (`config/intakt.yaml` or the file `INTAKT_CONFIG` names, `.env.local`, and [Intakt's GitHub App](README.md#intakts-github-app)).

Once the server answers its health check and the dashboard answers, every start ends its log with one line, `intakt: the dashboard is ready at http://localhost:7781`; with `docker compose up -d --wait` the same moment is when the command returns. The start no longer prints the review command. Print it, and the line that connects an MCP client, when you want them, in the repository folder:

```
docker compose exec intakt php bin/console intakt:sample:show /app/var/data/sample-repository
```

It prints the command that reviews the sample change, in the form your shell runs from the repository folder (it runs the console inside the container):

```
docker compose exec intakt php bin/console intakt:review sample-change --project=sample --repository=/app/var/data/sample-repository --base=main --task="Add a shipping cost by weight and a report of a customer's orders; a cart of 100 or more keeps its discount."
```

After a start without a key there is no sample project to review yet, so in place of that command it prints `No sample project yet: set ANTHROPIC_API_KEY or OPENAI_API_KEY or HF_TOKEN and start again to write it, then run intakt:sample:show again.`

Or let one short command run that same review for you, with the sample's values built in:

```
docker compose exec intakt php bin/console intakt:demo
```

It prints what `intakt:review` prints (the outcome, each reviewer, the act list, the tokens and the cost), then the address of this review in the dashboard (`Open the review: http://localhost:7781/reviews/<round id>`) and the line that connects an MCP client (below). It ends with the same exit codes as `intakt:review`: 0 for approve, 10 for changes, 11 for blocked, and 1 when it cannot start, for example `INTAKT_SAMPLE_REPOSITORY is not set` outside the compose demo or a project file without the `sample` project. Use `intakt:review` for your own projects.

The first start also makes the owner's MCP token, unless `MCP_OWNER_TOKEN` is set in `.env.local` (then yours is used), keeps it in `/app/var/data/mcp-owner-token` on the volume, and allows write tools for the demo (`MCP_OWNER_ACCESS` defaults to `mcp_tool_write` in the container). The `intakt:sample:show` command above also prints a line to connect an MCP client, after the review command, and so does `intakt:demo` after its review (both read the kept token file, so they print it also when run with `docker compose exec`; without any token they print one line saying to set `MCP_OWNER_TOKEN` in `.env.local`):

```
claude mcp add --transport http intakt http://localhost:7781/mcp/owner --header "Authorization: Bearer <the token>"
```

Run it, install the [`intakt-review` skill](../../skills/intakt-review/README.md) and say "intakt review the demo": for the sample project the skill uses the values below, and makes its fixes inside the container (a work tree of `sample-change` at `/app/var/data/sample-fixes`, through `docker compose exec intakt`, so run the agent in this folder), because the sample repository lives in the `intakt-data` volume, not on the host. Without the skill, ask your agent to start a review with the values of the review command above: project `sample`, change `sample-change`, base `main`, repository `/app/var/data/sample-repository` (the default `.` is not the sample) and the text after `--task=` as the task. A start that cannot make or read the token file stops before the seed with `intakt: could not make or read the MCP owner token in /app/var/data/mcp-owner-token`; two starts at once on one volume get the same token.

The token is a secret that sits in the volume and in what `intakt:sample:show` and `intakt:demo` print; `docker compose down -v` makes a new one. [Connecting an agent through MCP](mcp.md) says what the client can do.

Later starts keep both as they are once written (the log says `Kept`), also when you add a key. To seed again, for example after adding the second key, remove the volume with `docker compose down -v` (this also removes the database) or delete `/app/var/data/intakt.yaml` in the container and start again. Without any provider key the start goes on: it builds the sample repository, writes no project, warns `Set ANTHROPIC_API_KEY or OPENAI_API_KEY or HF_TOKEN to seed the sample project; the next start with one writes it.`, and still reports healthy once the dashboard answers. Add a key to `.env.local` and start again (`docker compose up -d --wait`) to write the project. An `openai_compatible` endpoint other than the Hugging Face router does not count for the seed, because the seeded models are router models.

### Running the demo on a Hugging Face token

`HF_TOKEN` lets you try the demo without an Anthropic or OpenAI key. The demo needs one provider key or one Hugging Face token, and its calls are billed to the key's or the token's owner. Create a fine-grained token on Hugging Face with only the permission "Make calls to Inference Providers". The container hands it to the `openai_compatible` provider, with `https://router.huggingface.co` (the `router_url` of `config/sample-project.yaml`) as the base URL, unless you set `OPENAI_COMPATIBLE_BASE_URL` or `OPENAI_COMPATIBLE_API_KEY` in the environment yourself (then yours win and the token is not used). A token pasted on the first-run page and kept is handed over the same way, after the restart, unless either variable is set in the environment or in the secrets vault.

The dashboard can also take one provider key at `POST /setup/provider-key` (the form for it is the first step of `/setup`: one field for an Anthropic key, an OpenAI key or a Hugging Face token, which Intakt recognizes from its form, and a button; the page shows the provider and at most the last four characters once a key is kept, and no field while one is configured). It accepts a key only while none is configured, from `.env.local`, the vault or an earlier key; it needs the form's token; it checks the key with one tiny call to its provider and keeps it only when the provider accepts it; and it never shows the key again, only its provider and last four characters. A key that has the form of no listed provider is refused with a line naming the providers it can take. When two keys are sent at the same time, the first one kept stays and the other is refused as already configured. Restart Intakt for the kept key to take effect. To change or replace a key later, edit `.env.local`: the dashboard has no login, so it does not change a key.

- With `HF_TOKEN` alone, the two reviewers run on models of two different AI labs through it: `correctness` on `moonshotai/Kimi-K3.1-Pro:deepinfra` and `security` on `deepseek-ai/DeepSeek-V4-Pro-0813:deepinfra`.
- With `HF_TOKEN` and `ANTHROPIC_API_KEY`, `correctness` stays on Anthropic and `security` runs on `moonshotai/Kimi-K3.1-Pro:deepinfra`. Two separate providers are the stronger setup: one token is one outage, one rate limit and one bill.

Two things to know when you set up Hugging Face yourself, for example as `openai_compatible` in your own configuration:

- The base URL is `https://router.huggingface.co`, without `/v1` at the end. Intakt adds `/v1/chat/completions` itself; with `/v1` in the base URL the call goes to `/v1/v1/chat/completions` and fails with a plain "Bad Request".
- Name the router provider after the model, as the seeded models do (`:deepinfra`). Every reviewer call uses tools together with structured output, and some router providers refuse that combination: Groq and Cerebras did. DeepInfra accepted it for `moonshotai/Kimi-K3.1-Pro` and `deepseek-ai/DeepSeek-V4-Pro-0813`. The router's default provider may be one that refuses, and the error then says only "Bad Request".
- A rate limit from the router provider you named (an answer of 429) pauses that router provider on that account until the reset time the answer gave (its `Retry-After` header, in seconds or as a date), or for one minute without one, and at most a day. Intakt sends it no call while the pause lasts, also from other workers on this computer, and calls it again once the pause has ended. When another account can take the call, the call goes there at once; when none can, a tier with substitutes moves to the first free substitute, and one without them waits until the first account is free again, never less. The account itself also pauses as for any rate limit, so while its own pause runs another router provider or a model without one on that account waits too. Moving on to another router provider instead of waiting comes in a later change. Intakt counts a model name as naming a router provider only in exactly the form `owner/model:provider`, made of plain ASCII letters, digits and punctuation with no space, line break or other character in it; a name such as `ft:gpt-4o-mini:org:custom:id`, `llama3:8b` or `owner/group/model:router` names none.

Project memory still needs an OpenAI key: a Hugging Face token alone gives no embeddings.

### Recording a review for the demo

A recording keeps one real review of a change in one file: its ledger events and the live updates the review page received, with the date the review started, the models it called and the Intakt version that wrote the file. `intakt:demo:replay` plays its ledger events and its live updates back into the demo project (see [The demo project](#the-demo-project) below). Intakt can already store that a project is a replay: each review started in such a project afterwards is stored as a replay too, and a review started before the project was marked stays live. A review stored as a replay never counts as a verdict, whatever its reviewers decided: the verdict reading gives none of its reviewers' verdicts as counting, `intakt:review` ends it as `blocked` with the reason `a replay never counts as a verdict: this round plays a recorded review back`, and a `reviewer-for-loop` project publishes no comment and only an `error` status for it. The only command that marks a project is `intakt:demo:create`, which marks the demo project `demo-replay` (see [The demo project](#the-demo-project) below). The board, the review page and the status command show the mark of each round: a card whose latest round is a replay carries a **Replay** label, the review page puts one beside each replay round (and says under the title that none of the verdicts count when every round is a replay), and `intakt:status` gives `mark` per project and per entry (see [The status document](dashboard.md#the-status-document) above).

1. Before the first round of the change, set `INTAKT_LIVE_CAPTURE` to a file (the recording takes every round of the change and is refused when one of them has no captured update), for example `INTAKT_LIVE_CAPTURE=/app/var/data/live-updates.jsonl` in `.env.local` for the compose demo, and run `docker compose up -d` so the container is made again with it. From then on every live update is also appended to that file, one line each. If the file cannot be written, the warning "A live dashboard update was not captured." is logged and the review goes on. The capture keeps the order the hub received the updates in, because each update is published and appended while holding one lock.
2. Run the review, for example both rounds of the sample change.
3. Write the recording: `php bin/console intakt:demo:record sample sample-change /app/var/data/sample-review.json` (in the compose demo, prefix `docker compose exec intakt`). It takes every round of that change in that project from the ledger and the captured updates of those rounds, and prints how many of each it wrote. In the compose demo, write it under `/app/var/data`, the data volume, so it survives when the container is made again, and copy it out with `docker compose cp intakt:/app/var/data/sample-review.json .`.
4. Set `INTAKT_LIVE_CAPTURE` empty again in `.env.local`, since the file keeps growing while it is set. Do it before the playback install of step 5 starts: both installs read the same `.env.local`, so otherwise the playback install appends to a capture file too.
5. Play the recording on another compose demo with a ledger of its own, not on this one: this ledger already holds the recording's rounds, so `intakt:demo:replay` and the `/demo` page refuse it here (see below). For example, stop this install with `docker compose down` (without `-v`, so its data stays), start a second one under its own project name, which gives it its own data volume, with `docker compose -p intakt-playback up -d --wait`, and copy the file in with `docker compose -p intakt-playback cp sample-review.json intakt:/app/var/data/sample-review.json`.
6. Play it on that install, keeping `-p intakt-playback` on every command: from the console with `docker compose -p intakt-playback exec intakt php bin/console intakt:demo:replay /app/var/data/sample-review.json --factor=10`, or in the dashboard by setting `INTAKT_DEMO_RECORDING=/app/var/data/sample-review.json` in `.env.local`, running `docker compose -p intakt-playback up -d` so the container is made again with it, and pressing **Play the demo run** on the `/demo` page. Both ways are described below.

The command writes nothing and exits 1 when the ledger has no round of that change in that project, when `INTAKT_LIVE_CAPTURE` is empty, when the capture file cannot be read, holds a line that is no captured update (the message names the line) or holds no update of one of those rounds (the message names the round, so a capture started after the first round is refused), or when the recording file cannot be written.

### The demo project

Recordings are played back into a project of their own, `demo-replay`, never into the `sample` project or one of yours. The project exists on the compose demo, marked as a replay, so every review in it is shown with the **Replay** label and never counts as a verdict. Each start of the compose demo creates it after the seed by running `php bin/console intakt:demo:create`, which prints `The demo project demo-replay is marked as a replay: its reviews never count as a verdict.` Running it again changes nothing.

The command refuses on any install that is not the compose demo, which it recognizes by `INTAKT_COMPOSE_SERVICE` (set only by `compose.yaml`): it prints `The demo project is created only on the compose demo, and INTAKT_COMPOSE_SERVICE is empty on this install.`, marks nothing and exits 1. A container started with `docker run` and a sample repository is not the compose demo either, so its start does not create the project.

To play a recording back, run `php bin/console intakt:demo:replay /app/var/data/sample-review.json` (in the compose demo, prefix `docker compose exec intakt`, or `docker compose -p intakt-playback exec intakt` on the playback install of [Recording a review for the demo](#recording-a-review-for-the-demo), and put the file where the container can read it, for example in `/app/var/data/`). It writes the recording's ledger events into the ledger one by one, in the recorded order and with the recorded time between them, counted from the start of the replay so a slow write does not stretch the rest, so the review unfolds as it did. `--factor=10` plays it ten times as fast (`--factor=0.5` at half speed); the default is 1. Each event is written as recorded, except that a project name equal to the recording's project becomes `demo-replay`, so the review shows up in the demo project with its **Replay** label, and the event that starts a review round also records the factor. Between the events it sends the live updates the review page received during the recorded review, each at its recorded time on the same pace and unchanged, so an open review page changes as it did during the real review; an update recorded at the same moment as an event is sent after that event is written. A page opened later reads the events when it loads. The review page shows the speed factor beside each replayed round's **Replay** label, for example "Played 10 times as fast as recorded"; a page that was already open shows it after a reload. It ends with `Replayed <n> ledger events and <n> live updates of change <change> into the demo project demo-replay, <factor> times as fast as recorded.`

It writes nothing and exits 1 on an install that is not the compose demo (`A recording is replayed only on the compose demo, and INTAKT_COMPOSE_SERVICE is empty on this install.`), for a factor that is not a number above 0, for a file that cannot be read or is not a recording, while another replay runs, when the demo project is not there (after `intakt:demo:remove`, until `intakt:demo:create` or the next start creates it again), and when the ledger already holds one of the recording's review rounds: a recording plays back once per install, since a second playback would mix into the first one's review pages. It also refuses when the ledger already holds one of the recording's model calls (by call id), so the replay's usage never mixes with another project's and removing the demo project never takes that project's usage with it. When writing an event fails, it stops there without sending the updates after it, exits 1 and says how many events it wrote. If the very first event failed, nothing was written: the message says so and asks you to replay the recording again, and earlier replays in the demo project stay as they are. Otherwise the events it wrote stay in the ledger, and once the start of a review round is among them the same recording is refused as a second playback; the message says the events stay and names the way out: run `intakt:demo:remove`, then `intakt:demo:create` (or start the compose demo again), before replaying it. `intakt:demo:remove` deletes every replay in the demo project, not only the stopped one.

To remove the demo project with everything played back into it, run `php bin/console intakt:demo:remove` (in the compose demo, prefix `docker compose exec intakt`). It deletes the recorded events of every review in `demo-replay` from the ledger, then the project's replay mark, and ends with `Removed the demo project demo-replay with its <n> ledger rows.` Your other projects, the `sample` project included, keep all their events. This is the only command that deletes events from the ledger, and only those of the demo project. Like the other demo commands it refuses and exits 1 on an install that is not the compose demo, and it also refuses while a replay runs. When `demo-replay` is not marked as a replay (for example after a removal) it prints `The project demo-replay is not marked as a replay, so nothing is removed.` and exits 0. Run `intakt:demo:create`, or start the compose demo again, before the next replay.

### Playing the demo run in the dashboard

The dashboard's `/demo` page (`http://localhost:7781/demo`) plays a recording without the console and without a provider key. `INTAKT_DEMO_RECORDING` names the recording file as the container sees it. Intakt ships one recording, a real one-round review of the sample change by two reviewers on Claude and GPT, at `/app/fixtures/demo/sample-change-review.json` in the container, and the image names it by default, so a fresh `docker compose up -d --wait` with no `.env.local` can play it. To play another one, written with `intakt:demo:record` (above), set the variable in `.env.local` (for example `INTAKT_DEMO_RECORDING=/app/var/data/sample-review.json`, with the file copied into the volume) and run `docker compose up -d` (`docker compose -p intakt-playback up -d` for the playback install) so the container is made again with it; setting it empty there offers no demo run. The page opens with one short line, two labels (**No key needed** and **Replay, not a verdict**) and four pictures of how a review works (the change, two reviewers from two AI labs, the judge checking every finding, To fix). Below the labels it says in one line what it can do:

- On an install that is not the compose demo: `The demo run plays only on the compose demo, and INTAKT_COMPOSE_SERVICE is empty on this install.`
- With `INTAKT_DEMO_RECORDING` empty or naming no file: `No demo recording is installed: set INTAKT_DEMO_RECORDING to a file written by intakt:demo:record.`
- Once a demo run is in the ledger: `The demo run is in the ledger. To play it again, remove it with intakt:demo:remove and start the compose demo again.`
- Otherwise it offers **Play the demo run**. The first-run page (`/setup`) offers the same button under its title **See a real review** while the run can be played.

The button plays the recording at one and a half times the recorded pace, as `intakt:demo:replay --factor=1.5` would, in a queue worker, so the page answers at once with `The demo run is starting: the caption at the bottom of each page names the stage it is in.` A recording that cannot be read or is refused (see the replay's refusals above) plays nothing, and the worker logs `The demo run was not played.` with the reason. The worker checks the compose demo again before it plays, so a press queued before the install stopped being the compose demo plays nothing either. Two quick presses can queue the run twice: the first plays it and the second is refused as a second playback, so that log line after a double click is harmless.

While the demo project holds a played run, every dashboard page except the error page shows a caption bar at its bottom, after the page's content, with the stage of the run (one dot per stage, the current one wider), one short sentence about it (at the two reviewer stages, followed by the reviewers' names as model and AI lab, such as Kimi K3.1 (Moonshot AI), with the raw model id in a tooltip; a model Intakt does not know is shown by its id alone) and a link to its review, and it rings the part of the review page that stage is about (the reviewers, the judge, the To fix list) when that page shows the round. There are five stages: the change arrives; the reviewers read it; findings arrive; the judge checks them; the round is done and To fix lists what still needs changing. A later round passes the same five stages again. A page that receives live updates moves the caption on as each recorded event is written. **Pause** (desktop only; the phone caption is one row without it) holds the caption at its stage until **Resume** (a page you open meanwhile shows the stage of that moment), and **Close** hides it in that browser tab until a later round starts. Right after you press **Play the demo run**, the demo page takes you to the review as soon as the first stage shows, unless you paused or closed the caption; opening the demo page later leaves you there. Eight seconds after the last stage shows, the caption closes by itself (a paused caption closes eight seconds after **Resume**). The caption never shows outside the compose demo.
