# Checks and tests for contributors

This page is for contributors to Intakt itself. It covers `bin/check` and its gates (what each finding means and how to fix it), running the tests, walking the user journeys, the release cooldown for dependencies, running a probe against an install, and looking inside a development install with Mate.

## Walking the user journeys

`bin/check --journeys` checks the product as a whole: for each journey in `tests/Journeys/` it boots a fresh instance with `bin/instance`, walks one path a user takes through the pages and the console, and checks what the user sees. The full list, with what each journey checks, is in [Journeys](../architecture/journeys.md); the main ones follow. First install and setup: the database is created, the board says "Nothing is running yet. Start the first review.", the projects page is empty, the sample project is seeded (a second seed keeps it), and the reviews page is empty. Live review progress on the dashboard: the watcher starts a review round on a recorded pull request of the sample project, the review page shows it in progress, every live update the round sends fits that page until the judge has ruled, the board headline sent once a reviewer started names the change and links to that round's review page, the page shows it judged, the page opened while the round ran, with those updates applied, shows the judge's call, the findings, the round's tokens and cost and the review's totals as that fresh load does, without any text asking for a reload, and the board then says "Nothing is running. Nothing needs you." (whether the browser subscribes to those updates is checked by a separate test). First run of the demo without a key: the demo starts without a key, `/` sends you to the first-run page, and the page opens on the recorded review, with the key form and no start button yet. First run of the demo with a key: the same start, then a placeholder Hugging Face token pasted on the first-run page is kept, a restart gives the sample project its reviewers, **Start the first review** opens the live review page with "Started round 1.", and once the round has run that page shows it judged with its outcome. Second start from the dashboard: once the first review is judged, **Start round 2** on its review page shows "Started round 2.", and pressing the same start again shows "Round 2 was asked for, but the next round of this change is round 3." and starts no further round. They need no network and no real keys. Each journey has up to 240 seconds, and anything it leaves running is stopped with its instance.

The option runs alone (`--fast`, `--only`, `--skip`, `--base` and `--test-merge` are refused with exit code 2), and neither `bin/check` nor `bin/check --fast` runs the journeys. A passing run ends with `{"result":"pass","failed":[],"report":"var/check/report-<16 hex digits>.json"}` (see [Reading the whole report of `bin/check`](#reading-the-whole-report-of-bincheck)); a failing journey is one finding that names its file, the journey, the step that broke and the first line of the reason, for example `FirstInstallJourneyTest.php: journey "first install and setup" failed at step "open the reviews page": Failed asserting that ...`. The plain-words guide is [Checking the whole product](../guide/checking-the-whole-product.md).

`bin/journey-alarm [--run=<https link>] [<file>]` reads that output (from the file, or from stdin) and, when journeys failed, files one task on the repository named by `GITHUB_REPOSITORY` through `gh` (labels `priority:urgent` and `ready`, the failing journeys, their steps and the last 40 lines of the output, and the run link when given). A later red run replaces the body of that task, found by the hidden line `<!-- intakt:journey-alarm -->` in it, instead of filing another. Two runs at the same time on one computer take turns, and a run that finds an older task filed meanwhile closes its own as a duplicate. A green run files nothing and exits 0; output with neither a failing journey nor a pass, or a failed journeys gate whose findings name no journey, exits 1 with a message, as does a failing `gh` call or a missing token; a file it cannot read, an unknown option or a `--run` that is not an https link exits 2. Set the token in `GH_TOKEN` or `GITHUB_TOKEN`: without one the command stops before calling `gh`, so a stored `gh` login is never used.

`bin/journey-alarm --timed-out [--run=<https link>] [<file>]` is for a run stopped at its time limit.
It skips parsing the output, so a cut-off or empty output files or updates the same task instead of exiting 1.
That task is titled `fix(journeys): the journeys run timed out on main` and says the run timed out instead of listing journeys.
Without `--timed-out`, the command behaves as described above.

Intakt's CI runs the journeys on every push to main, and on a pull request that changes more than `docs/`, `tests/` or `upstream/` or touches the journeys' test code (`tests/Journeys`, `tests/Support`, `tests/Core/Watcher/RecordedPullRequests.php`), as the `journeys` job of the `ci` workflow (`.github/workflows/ci.yml`). It also runs them on main every night and whenever someone starts the `journeys` workflow (`.github/workflows/journeys.yml`) by hand ("Run workflow", or `gh workflow run journeys.yml`). The two differ in what a failure does. When the `journeys` job of `ci.yml` fails, that pull request's or push's CI run fails, and no task is filed. Only a red nightly or hand-started `journeys.yml` run files one urgent task, or updates the one already open while the journeys stay red ([Running Intakt's CI on your own runner](self-hosted-ci.md)). The nightly run and its alarm stay for now; they are removed once the `journeys` job of `ci.yml` has been green on main for a week.

## Regenerating the journey page

`bin/journey` rewrites the "At a glance" table, the milestone table and the charts of `docs/journey.md` (the page that tells how Intakt was built) and leaves every other line of the page as it was. It draws five charts as SVG files in `docs/journey/` (tokens per day by lane and by account, tokens per merged pull request, issues created and closed per day, open issues per day) and puts each on the page with a table of the same numbers below it, folded away under the chart. Every figure it writes is followed by its kind, like the review report: the token figures `measured` (the providers' usage answers, the `tokens` field of `usage.jsonl`), the merges and issues `counted` (from the GitHub API), and the tokens reserved for steps that were killed before they reported usage `estimated` (the `reserved` field of `usage.jsonl`). Each chart names its kind in its title, in the picture's description and in the columns of its table, and a line under the drawing says where its numbers come from; the "At a glance" table and the milestone table (whose done and open issues are `counted`) end with such a line too. Tokens per merged pull request shows the measured tokens and the counted merges beside it, each with its own kind, and the estimated reserved tokens apart from them when there are any. The charts and every token total hold only measured tokens: a reservation is never added to them. The page shows no cost. It also draws the page's Mermaid timeline as `docs/journey/timeline.svg`, for GitHub Pages, which does not show Mermaid diagrams. Accounts appear only as Claude account 1, Claude account 2, Claude API key and GPT subscription. It reads the milestones, issues and pull requests of the repository named by `GITHUB_REPOSITORY` (`<owner>/<name>`) through `gh`, and the token counts in `docs/journey/usage.jsonl`, where every line holds both `tokens` and `reserved`. Set the token in `GH_TOKEN` or `GITHUB_TOKEN`: without one the command stops before calling `gh`. `bin/journey --recorded=<folder>` reads `milestones.json`, `issues.json` and `pulls.json` from that folder instead, with no network and no token. It prints `<file> regenerated` for each file it changed, or `docs/journey.md and its drawings are current` when nothing changed, and exits 0. The token charts change only when `usage.jsonl` does: the merges on its days are counted when it changes and kept on the page in a hidden comment below the tokens per merged pull request table, until it changes again. If that comment was edited so that it no longer reads as counts (a count of zero, for example), the merges are counted again and the comment is written anew. A missing marker pair, a page without exactly one Mermaid timeline, a timeline line it does not understand, a GitHub answer or usage line it does not accept (an unknown account, vendor or lane among them), a failing `gh` call or a missing token exits 1 with a message and writes nothing; a file it cannot write exits 1 before the page is written; an unknown option exits 2. The technical description is [The journey page](../architecture/journey-page.md).

`bin/pages <folder> [--recorded=<folder>]` builds the whole GitHub Pages site into a folder: it runs `bin/highlights` and `bin/journey` (passing `--recorded` on), then writes the highlights page as `index.md` with a link to the journey page, and the journey page as `journey/index.md` with its charts and the timeline drawing beside it, the timeline shown as that drawing because Pages does not show Mermaid diagrams. If either command fails, it exits 1 and writes nothing into the folder. A rerun with the same inputs changes nothing and prints `site is current`. It never deletes a file: a drawing removed from `docs/journey/` stays in the folder's `journey/` when you build into the same folder again, so build into a fresh folder to leave it out. Apart from the folder, it changes only what the two commands regenerate under `docs/`.

`bin/journey-record <folder>` saves the milestones, issues and pull requests of the repository named by `GITHUB_REPOSITORY` through `gh` as `milestones.json`, `issues.json` and `pulls.json` in the folder, ready for `--recorded`. It is meant for a machine that has `gh` and the token, such as the CI runner. It writes the three files only once all three answers arrived: a failing `gh` or an empty `GITHUB_REPOSITORY` exits 1 and leaves no new file. It never prints the token.

## Finding the slowest tests

When the `tests` gate of `bin/check` runs, its line also lists the ten slowest test files under `slowest`, slowest first, each with its `file` and its `seconds` (the times of all its tests added up, over all test passes, including the run of the `serial` tests). For example:

```
{"gate":"tests","ok":true,"findings":[],"omitted":0,"slowest":[{"file":"tests/Application/InstanceTest.php","seconds":45.722},...]}
```

The time of every test file, not only the ten slowest, is kept in `tests/durations.json` in the gates cache: the folder `INTAKT_GATES_CACHE` names, or `intakt-gates` in the system temp folder when it is not set. Each run replaces the file. A test file outside the project folder is left out of both the file and the `slowest` list, so no path of your machine shows up in them. The times never change whether the gate passes; when the cache folder cannot be written, the file is simply not written. The gates cache also holds file selections: the `rector` gate's list of the files it checks, in `rector-paths/` (a relative `INTAKT_GATES_CACHE` is taken from the folder you run `bin/check` in); a run that cannot write that list fails the `rector` gate.

In CI, the `check` job restores the analyser caches (PHPStan, PHP CS Fixer and Rector) from main's latest run, so the analysers check only what changed since then. Only runs on main save them; a pull request run uses them but never saves its own. A change to `composer.lock` or to anything under `config/gates/` starts from empty caches. The caches hold analysis results, test durations and the lists of files a Rector run checked, no secret and no token.

## The PHP profile and the environment gate

The profile of the PHP that builds, reviews and CI use is in the repository: `config.platform.php` and the `ext-*` entries under `require` in `composer.json`, and the ini settings in `config/gates/php/check.ini` (for example `zend.assertions=1`). Load the settings by adding `config/gates/php` to `PHP_INI_SCAN_DIR`, after the directories PHP already scans. A leading `:` keeps PHP's own directory first, so from the project folder:

```
PHP_INI_SCAN_DIR=":$(pwd)/config/gates/php" bin/check
```

`bin/check` runs the `environment` gate first in every run, the full one and `--fast` (not `--journeys`, which keeps its own selection). The gate (the `EnvironmentGate` class) checks the running PHP against that profile. `bin/check` neither restarts PHP nor changes its ini scan path, so a run without the profile loaded fails the `environment` gate as soon as your PHP differs from it. Each finding names one difference: a PHP older than the platform version, a missing extension, a setting that differs from the check ini (for example `PHP setting zend.assertions is -1 but config/gates/php/check.ini says 1`), or a setting in the check ini that the gate does not allow. When a setting differs, the gate also says how to load the profile.

## Running the tests in parallel

The `tests` gate runs the test files in several workers at once: one for each processor it may use, at most four, and no more than a CPU quota of its container allows (rounded up). Each worker takes the next file from one shared list, which starts with the files that have no recorded time yet (new ones), then the files that took longest in the last run (from `tests/durations.json` above). Set `INTAKT_TEST_WORKERS` to choose the number of workers yourself (from 1 to 127; any other value fails the gate); `INTAKT_TEST_WORKERS=1` runs each test pass in a single process, as before. A finding names the pass and the file it came from, for example `sqlite tests/Core/ReportTest.php: ReportTest::testRuns: ...`. A failing, skipped, risky or incomplete test, or a warning, notice or deprecation, fails the gate in any worker, as does a warning PHPUnit gives while it lists the test files (for example a test file without its class), and so does a file whose run crashes (`phpunit exited with code ...`) or takes longer than 600 seconds (`timed out after 600 seconds, last output: ...`). All files together get at most 3600 seconds: past that, the files still running are stopped and the ones not yet started never start, and each fails the gate with `timed out: the test pass reached its overall limit of 3600 seconds` (a stopped file also shows `, last output: ...` after it).

## Running the gates at the same time

`bin/check` runs the selected gates at the same time, as many at once as there are processors it may use (capped by a CPU quota of its container, rounded up), but fewer when its container has a memory limit (its own control group, each group above it and the top group it can see are all read): each test worker and each gate gets 2 GiB of it, the test workers first, because a gate such as `phpstan` may use that much (at least one gate runs). The gates that run your change's code (`tests`, `container`, `journeys`, and `phpstan`, which starts your change's kernel to dump the test container) start only after every other gate has finished, because a test could otherwise change the files or tools another gate is still checking. The other gates start first, in the usual gate order as earlier ones finish; then the `tests` gate starts first, so it never waits, and `phpstan` and `container` follow, in that order. Because the test workers need processors too, the `tests` gate counts for as many gates as it runs workers, but always leaves room for one other gate beside it. When the `tests` gate runs and more than one gate runs at once, the `phpstan` and `container` gates beside it run at the lowest processor priority, so they only use processor time the test workers leave idle; every other gate (and every gate with `--only=phpstan`, or `INTAKT_GATE_SLOTS=1`) keeps its usual priority. Set `INTAKT_GATE_SLOTS` to choose how many gates run at once (from 1 to 999); `INTAKT_GATE_SLOTS=1` runs them one after another. Any other value stops `bin/check` with exit code 2 before any gate starts. The lines, the result line and the exit code are the same however many run at once.

The `rector` gate starts at most 4 workers of its own, each allowed 300 s (`withParallel` in `config/gates/rector.php`), whatever the processor count. With Rector's defaults (a worker per core, 120 s), several `bin/check` runs at once on one machine starved each other's workers until they timed out, and the gate failed with `Child process timed out after 120 seconds` and no finding of its own. The gate hands Rector its files in a list file named by `INTAKT_RECTOR_PATHS_FILE`, not on the command line, because Rector's workers failed to start with `Argument list too long` once the list of every file passed 128 KiB. A list file that is missing or incomplete fails the gate; it never checks fewer files. To run Rector by hand, name the paths on its command line.

## Reading the whole report of `bin/check`

A gate's line shows at most its first ten findings, each cut to 300 characters. After the gate lines, `bin/check` writes everything into one report file and names it in its result line, so you never need to run the check again to see the rest:

```
{"result":"fail","failed":["dashes"],"report":"var/check/report-3f9c0a1b2d4e5f60.json"}
```

The file lies in the checked folder (`--root`, else the repository), under `var/check/`, with a new random name on every run, so an earlier report is never overwritten. It holds one JSON object: `gates` lists every gate's whole result in gate order (every finding, uncut). Each whole result is copied as the gate wrote it, with nothing decoded and written again. A gate whose whole result is not available is listed with its summary line instead; so is a gate that crashed, timed out or printed no valid line, so its line names why it stopped, even when it saved a result before that, and so is a gate whose saved result gives another verdict or other findings than its line, and `whole` is then `false` only if that line leaves something out (more than ten findings, or a finding cut or as long as the limit). Characters beyond ASCII are written as `\u` escapes. The file gets the permissions your umask gives. A `var/` or `var/check` that is a link is not followed: then there is no report. When no report can be written, the result line has no `report` key: when the system temp folder is missing or not writable (or lies inside the checked folder), so the gates cannot hand over their whole results, when `var/` or `var/check` is a link, the folder cannot be created or lies outside the checked folder, the file cannot be opened, or the write fails or stops short (the partly written file is removed). None of these prints a PHP warning between the JSON lines, and a scratch folder that cannot be removed afterwards is left in the system temp folder without changing the result. The report never changes the result, the `failed` list or the exit code. Intakt's own `.gitignore` leaves out `var/`. After writing its report, `bin/check` keeps only the 20 newest generated reports in `var/check/` (by modification time) and removes the older ones. The report it just wrote always stays, even when 19 others are dated in the future. Only files named exactly like the generated ones (`report-` plus 16 lowercase hex digits, `.json`, nothing more) are ever removed: a file you named yourself, such as `report-manual.json`, and links stay. When no report could be written, nothing is removed.

## Listing the static gates and the gate order

`bin/check --static-gates`, with no other argument, runs no gate. It prints one JSON line with two lists and exits with 0:

- `static`: the gates that do not run your change's code, so they can check a copy of the change on their own (every gate except `phpstan`, `tests` and `container`);
- `order`: every gate of a run without `--journeys`, in gate order (the order of the gate list in `bin/check`).

For example:

```
{"static":["cs","rector",...,"ratchet","workflows","left-undone"],"order":["cs","phpstan","rector",...,"container","ratchet","workflows","left-undone"]}
```

With any other argument beside it, `bin/check` runs no gate: it prints an `error` line with its usage and exits with 2. A normal `bin/check` run is unchanged: it still starts the static gates before the gates that run your change's code.

## When `bin/check` reports a missing tool

Before it runs any gate, `bin/check` checks that the programs the selected gates call are installed. When one is missing, it runs no gate, prints one line naming every missing program, such as `gitleaks not found, see docs/architecture/requirements.md`, and exits with 2. A Composer older than 2.11 is reported the same way, naming the version found, because it would ignore a release cooldown set in `composer.json`. It also needs PHP's `pcntl` and `posix` extensions, so that a Ctrl-C reaches the gates' processes; a missing one is named the same way (`PHP extension pcntl not found, ...`). Install the program or the extension (the [requirements](../architecture/requirements.md) name the version), point `INTAKT_GITLEAKS` at gitleaks if it is not on the path, or leave the gate that needs it out with `--skip=<gate>`. `bin/probe` reports a missing `unshare`, `sh` or `ip` the same way, with exit code 2, before it starts anything.

The `workflows` gate is the exception: it needs zizmor (the [requirements](../architecture/requirements.md) name the version), and without it only that gate fails, with `missing tool zizmor` in its own result line; `--skip=workflows` leaves it out.

`bin/check` looks for the programs on `PATH`. When `PATH` is not set at all, it looks where the system shell `/bin/sh` then looks, since the gates start their programs through that shell (on Debian and Ubuntu: `/usr/local/sbin`, `/usr/local/bin`, `/usr/sbin`, `/usr/bin`, `/sbin` and `/bin`); if the shell cannot run, it looks only in the project folder. A `PATH` that is set but empty (`PATH=`) is taken as it is: only the project folder is searched, so every other program is reported missing.

## When the `workflows` gate reports an ignore without a reason

A zizmor finding in a YAML file under `.github/` may only be silenced with a comment `# zizmor: ignore[<audit>]` followed by the reason on the same line, for example `# zizmor: ignore[artipacked] the job needs the token to push`. The `workflows` gate fails with `<file>:<line> zizmor ignore without a reason: # zizmor: ignore[...]` when the last ignore on a line has no words after it (blanks or punctuation do not count, and neither do words before it, for example in a quoted value that happens to contain such a comment), and with `<file> cannot be read for zizmor ignores` for a YAML file it cannot read. To resolve it, fix the finding the ignore silences, or write on the same line why the pattern is safe. A file with Windows (CR LF) or old Mac (CR) line endings is read line by line the same way.

## The release cooldown for dependencies

`composer.json` sets a release cooldown of 3 days: `composer update` leaves out a package version published less than 3 days ago and locks the newest older one. The `audit` gate of `bin/check` also fails when `composer.lock` holds a release inside that period. Wait until the release is 3 days old; do not shorten the period to make the gate pass. The only exception is a one-time decision of the owner: the `symfony/*` packages at version `8.2.0-BETA2` (released 2026-11-13) may be locked before they are 3 days old. It is written in `config.policy.cooldown.ignore` in `composer.json`, a passing `audit` gate names it in its note (`cooldown exceptions in force: symfony/* 8.2.0-BETA2`), and it is removed again once that release is older than 3 days. No other package has one. This needs Composer 2.11 or later (see above). Dependabot has its own cooldown, which only decides when its pull requests open: 7 days for the GitHub Actions the workflows use, 3 days for images and Composer packages. It also holds for the `FROM` images of `Dockerfile`, `.github/ci/Dockerfile` and `.github/ci/databases.Dockerfile` (the database images CI starts for the persistence tests), updated together in one pull request, with one exception: the images from GitHub's container registry, such as the gitleaks image. Dependabot cannot see there when a version was published, so an update of such an image can open with no wait.

The dashboard's JavaScript packages in `importmap.php` follow the same 3-day rule: `bin/console importmap:update` keeps a package at its pinned version while the newer one is less than 3 days old (the pin can also move to an older release that is old enough while the newest one is held back), and takes the newest version that is at least 3 days old once there is one. `bin/console importmap:outdated` lists a version it holds back in its "Withheld" column. Each module in the dashboard's import map also carries a sha384 integrity hash of the file Intakt serves, so the browser refuses to run a module whose bytes changed after the import map was computed (on a deployed install, after `asset-map:compile`). Both are set in `config/packages/asset_mapper.yaml`; do not shorten the age or remove the hash to get a fresh package in sooner.

## When `bin/check` reports a gate process that ended without a result line

`bin/check` runs each selected gate in a process of its own, several at the same time, and prints their lines in the usual gate order once all have finished, then the result line. A gate whose process crashes, runs longer than 3600 seconds, or prints anything but that gate's own result line fails with the finding `gate process ended with exit code <n> and no valid result line: ...`, followed by what the process wrote to its output and then to its error output; when that does not fit the finding's 300 characters, only its end is kept, after `...` (for a timeout, it ends with `... timed out after 3600 seconds`; for a process killed by a signal, with `... was killed by signal <n>`). When a gate's process ends or is stopped, or `bin/check` is interrupted (Ctrl-C), any program the gate started and left running is stopped with it. One exception: a program the gate started in a contained run of its own (such as a journey's instance) may keep running if the gate's process is killed outright (signal 9), because then it has no chance to stop it. Exit code 124 means it timed out, 255 usually a PHP fatal error, 128 plus the signal number a kill by that signal (137 for signal 9). Warnings and notices a gate's process gives appear on `bin/check`'s error output, not in its lines. To resolve it, read the quoted output, fix its cause, and run the gate alone with `bin/check --only=<gate>`.

## When `bin/check` reports a stateful service

Intakt keeps one process alive across many requests and messages, so a service that keeps a value in a property would carry it into the next request. The `phpstan` gate of `bin/check` therefore reports a finding `intakt.statefulService` for every concrete class under `src/` with a property which is not `readonly`, including properties from a parent class or a trait under `src/`, and static ones, because the container registers every class under `src/` as a service. A property a vendor base class declares, such as those of Symfony's `Command` or `AbstractController`, is framework wiring rather than request state and is not reported. A virtual property, a hooked property without a backing store such as one with only a `get` hook that computes its value from other properties, keeps no value and is not reported either; a hooked property with a backing store is. The finding names the property. To resolve it, do one of:

- make the property, or the whole class, `readonly`;
- implement `Symfony\Contracts\Service\ResetInterface` and clear the property in `reset()`, which Symfony calls between requests and messages;
- if the value must last the whole process on purpose (a notice logged once per start, for example), mark the property with `#[Intakt\Core\Platform\Contract\KeptForTheProcess]`; the marker exempts only the property it sits on, so a reviewer sees each such property, and an attribute of the same short name from another namespace does not count;
- if the class is a value object or a data transfer object rather than a service (a console input object for `#[MapInput]` included), mark it with Symfony's `#[Exclude]` attribute so the container does not register it. An `#[Argument]` or `#[Option]` property alone does not exempt a class, because the container still registers it.

Doctrine entities, embeddables, mapped superclasses and column types, and exceptions are not services and are never reported. Neither is the kernel, which performs the reset, nor any class outside `src/` (tests, gate code, scripts), which the container never registers.

## When `bin/check` reports a deprecated reference

Deprecated code is not used. The `phpstan` gate of `bin/check` already reports a call, a `new` or a signature type that uses a deprecated symbol, and reports a finding `intakt.deprecatedReference` for every place that names a deprecated class, interface or trait: a `use` import (also inside a group import such as `use Acme\{Legacy, Modern}`), an `instanceof`, a `catch` type, a `::class`, an attribute, a `new`, a type, and a type in any docblock tag (`@var`, `@param`, `@return`, `@property`, `@method`, a `@template` bound and the others) on a class, trait (also a trait no class uses, reported once from its own file), function, method, property, statement or closure, also inside a union such as `object|Legacy` or a constant type such as `Legacy::*`. Some places get both findings. A class is deprecated when it carries a `@deprecated` tag, or when its file calls the global `trigger_deprecation()` (in any letter case, also through a `use function` alias; a function of that name in the file's own namespace is not the global one) outside any class, function or closure (also inside an `if`), as some Symfony classes do to warn when they load; a first-class callable `trigger_deprecation(...)` is no call and deprecates nothing. The finding names the class. To resolve it, switch to the replacement the class names (its `@deprecated` text or its deprecation message says which); do not silence the finding. The `tests` gate also fails when a test (a gate test under `tests/Gates/` too), a helper under `tests/` or a class under `src/` causes a deprecation, including one that only loads a deprecated vendor class; only a deprecation that one vendor package causes by calling another is ignored.

## When `bin/check` reports a flag parameter

A boolean parameter that switches what a function does hides two behaviors behind one name, so the `phpstan` gate of `bin/check` reports a finding `intakt.flagParameter` for every parameter typed `bool`, `true` or `false` (also nullable or in a union) of a function, method, closure or constructor, except in `tests/`. The finding names the parameter. A `readonly` service is reported like any other. To resolve it, do one of:

- replace the boolean with a backed enum whose cases name the modes;
- split the method in two, one per behavior;
- if the boolean is data of a value object, make the class `readonly`, mark it with Symfony's `#[Exclude]` attribute (Doctrine entities, embeddables and mapped superclasses count as excluded too) and keep the boolean as it is, as a promoted constructor property or assigned unchanged to a property in the constructor body. Only such a constructor parameter passes, and only when the constructor body does nothing but assign variables to properties the class itself declares (as a property, a promoted constructor parameter or a property of a trait the class uses, since PHP counts a trait's property as declared by the class that uses the trait), one plain `$this->name = $variable;` per statement. An assignment to any other property (one the class never names, or one a parent class declares) is reported, since PHP hands an undeclared property or a parent's private one to `__set()`, which could read the boolean. A promoted boolean must appear nowhere in the body, and a stored one exactly once, as the variable of one of those assignments. Any other statement in the body (a condition, a call, `new`, `eval`, `include`, a `parent::__construct()` call) could read the boolean, so every boolean of that constructor is reported then, even in a value object, while the class's other methods may read the stored property, and the exemption follows the attribute, not the folder, so an unmarked `readonly` class under `bin/` or `config/gates/src/` is reported too.

## When `bin/check` reports a class that is not final

A class is closed for extension unless it is built to be extended, so the `phpstan` gate of `bin/check` reports a finding `intakt.finalClass` for every class declared neither `final` nor `abstract` in a file the gate analyzes under `src/`, `tests/`, `bin/` or `config/gates/src/`: the `.php` files there plus `bin/check`, `bin/instance` and `bin/probe`, but not the gate test fixtures under `tests/Gates/Fixtures/` or other files without an extension, such as `bin/console`. Services, `readonly` value objects, Doctrine entities and test classes are all reported alike. An abstract class is not reported, and neither is an anonymous class (`new class { ... }`), an interface, an enum or a trait. The finding names the class. To resolve it, add `final` to the declaration and keep everything else as it is (`final readonly class` stays readonly, a mutable service that implements `ResetInterface` becomes `final class`), or declare it `abstract` when it is meant to be extended.

## When `bin/check` reports a static property

Intakt keeps one process alive across many requests and messages, and a test run shares one process between many tests, so a value kept in a static property outlives the request or the test that set it. The `phpstan` gate of `bin/check` therefore reports a finding `intakt.noStaticProperty` for every static property declared in a class or a trait in a file the gate analyzes under `src/`, `tests/`, `bin/` or `config/gates/src/` (the same files as `intakt.finalClass` above), whatever its visibility, and one finding for each property when one declaration names several. Services, Doctrine entities and test classes are reported alike. Abstract classes and anonymous classes (`new class { ... }`) are exempt. Static methods, `static fn` closures, `static` variables inside a function and class constants are not static properties and are not reported. The finding names the class and the property. To resolve it, keep the value in an instance property, a service or a local variable; a test builds what it needs in `setUp()` and removes it in `tearDown()` instead of sharing it through `setUpBeforeClass()`.

## When `bin/check` reports a public setter

An object that can be changed after it is built can be seen half set up, and any caller can change it, so the `phpstan` gate of `bin/check` reports a finding `intakt.noPublicSetter` for every public method whose name is `set` or starts with `set` followed by an uppercase letter or an underscore (`setName()`, `set_name()`), in any letter case (`SetName()` too, since PHP matches method names case-insensitively), declared in a class, an interface, an enum or a trait in a file under `src/`, `tests/`, `bin/` or `config/gates/src/` (the same files as `intakt.finalClass` above). A trait's setter is reported once, in the trait. It is exempt only when at least one analyzed class uses the trait and the exemption below holds in every class that uses it (as `setUpBeforeClass()` of PHPUnit's `TestCase` in `tests/Gates/UsesSandboxes.php`); a trait no class uses has no exemption, and `#[Override]` makes no difference. This holds for an abstract trait setter too, which a vendor parent of the using class may implement. A class that renames a trait method to a public setter (`use Renames { rename as setName; }`), or makes a protected trait setter public (`use Titled { settitle as public; }`, judged by the name the class gets, `setTitle()`, whatever the letter case in the clause), is reported on that line, unless the class declares a method of the same name itself: PHP then uses the class's method, so that method is judged instead (a protected one passes, a public one is reported once). A trait that does so (`trait WrappedSetter { use Lookup { find as setLabel; } }`) is judged at the trait: the alias is reported once, under the trait's name, whether or not a class uses the trait, and without the exemption below; to override a vendor method through an alias, write the alias in the class that uses the trait, where the exemption applies. A `bin/check --fast` run skips the trait setters only when it analyzes fewer than all PHP files in scope, since the classes that use a trait may then be missing; a full `bin/check` and CI always judge them. Methods of an anonymous class declared inside a trait method are a known gap: the rule does not check them. Methods such as `settle()`, `setup()`, `settings()`, `Settings()` or `set2()` are not setters and are not reported, so a setter written all in lowercase (`setlabel()`) is not recognized either, and neither are private and protected setters. A setter that a vendor interface or parent class declares is exempt, since PHP does not let the class rename it: for example `setMarking()` of Symfony Workflow's `MarkingStoreInterface`, or an override of `setName()` of Symfony Console's `Command`. A setter that an interface or class of the repository itself declares is reported, both there and in every class that implements or extends it, so a subclass gets its own finding only when it redeclares the setter; a subclass that just inherits the method gets no extra finding. A parent or interface under `migrations/` grants no exemption either, so a class in the folders above that overrides its setter is reported, while the declaration under `migrations/` is outside the folders the rule checks and is not. The finding names the class and the method. To resolve it, pass the value to the constructor, or return a new instance from a `with*()` method (`clone()` with overrides).

## When `bin/check` reports a magic method

PHP calls a magic method implicitly, so what it does (a property or method that exists only at run time, a copy, a serialization) is invisible to static analysis, the IDE and readers. The `phpstan` gate of `bin/check` therefore reports a finding `intakt.noMagicMethod` for every method whose name starts with `__` (PHP reserves those names for magic methods), such as `__get()`, `__set()`, `__call()`, `__clone()`, `__destruct()` or `__serialize()`, whatever its visibility and in any letter case (PHP matches method names case-insensitively), declared in a class, an interface, an enum or a trait in the same files as `intakt.finalClass` above. A trait's magic method is reported once, in the trait, whether or not a class uses it, and a class that renames a trait method to a magic method (`use Lookups { find as __call; }`) is reported on that line. A trait that does so (`trait WrappedLookup { use Lookup { find as __get; } }`) is judged at the trait: the alias is reported once, under the trait's name, whether or not a class uses the trait. Methods of an anonymous class declared inside a trait method are a known gap: the rule does not check them. `__construct()` and `__invoke()` are allowed, and so is `__toString()`, which implements PHP's own `Stringable` interface. The finding names the class and the method. To resolve it, declare the property or the method, or give the class a named method for the lookup.

## When `bin/check` reports a re-spelled name

A container service id, a parameter name or a provider name is written once, so that renaming it cannot leave a second spelling behind. The `phpstan` gate of `bin/check` therefore reports a finding `intakt.reSpelledName` for a string literal in a PHP file under `src/` or `config/` (but not `config/gates/`) that starts with `intakt.` outside a module's ids class (a class, not a trait, interface or enum, ending in `Services` in a `Contract` namespace, such as `AiServices`), and for a literal equal to a provider's value (`codex`, `anthropic` and the others) outside the `Provider` enum. Only a whole literal counts: a message that mentions `codex` is not reported. A double-quoted string with a variable in it, such as `"intakt.ai.platform.{$name}"`, is reported when it starts with `intakt.`. Code in a trait is checked too, also when no class uses the trait, and so is code in an anonymous class (`new class { ... }`), which counts as part of the class it is written in. Tests, the gates' own code and the YAML of `config/intakt.yaml` are not checked. To resolve it, use the constant of the ids class (add one there for a new name), or derive the name from the case (`Provider::Codex->value`, or a `Provider` method such as `platformId()`).

## When `bin/check` reports a provider literal

A model id or a provider's host is written in one place, so that a retired model or a moved endpoint is one edit. The `phpstan` gate of `bin/check` therefore reports a finding `intakt.providerLiteral` for a string in a PHP file under `src/` that holds a model id (such as `claude-sonnet-5-5`, `gpt-6.1-terra`, `o4-mini`, `text-embedding-3-small`, `deepseek-chat` or `gemini-2.5-pro`, also inside a longer string such as a router id) or a provider host (`anthropic.com`, `claude.ai`, `claude.com`, `openai.com`, `chatgpt.com`, `huggingface.co` or a subdomain of one, also inside a URL), with the message `'claude-sonnet-5-5' names a model: name it in a provider descriptor of the catalog or in the demo data file, not in code.` Provider names and values such as `Anthropic`, `claude_code` or `codex` pass, and so does prose such as `o2 sensor` (a bare `o3` counts only where an id stands: as the whole string, in a router id such as `openai/o3`, `openai:o1` or `openai/o3:online` (also with text after it, as in `Use openai/o3 for this request.`), after `=` as in `--model=o3 --format=json`, or in quotes as in `{"model":"o3"}`). A class that implements `ProviderDescriptor` (the catalog in `src/Plugin/SymfonyAiVendor/Infrastructure/`) is not reported, and tests, `config/` and the demo data file `config/sample-project.yaml` are not checked. To resolve it, take the model from the project's tiers or the demo data file, or the host from the provider's descriptor. A few hosts of the Claude Code and Codex adapters are still listed in `ratchet/provider-literals.neon` until they move; that list may only get shorter (see [When `bin/check` reports a ratchet finding](#when-bincheck-reports-a-ratchet-finding)).

## When `bin/check` reports a bare serializer format

The JSON format of Symfony's serializer is named by its constant, so code never spells the format a second way. The `phpstan` gate of `bin/check` therefore reports a finding `intakt.bareSerializerFormat`, with the message `'json' as a serializer format is a magic string: pass JsonEncoder::FORMAT instead.`, when a PHP file passes the plain string `'json'` as the format to a serializer, normalizer, denormalizer, encoder or decoder of Symfony's Serializer component (`serialize()`, `deserialize()`, `normalize()`, `denormalize()`, `encode()`, `decode()`, their `supports...()` checks and `getSupportedTypes()`), also as a named argument (`format: 'json'`, or the name a class of your own gives that parameter), inside an unpacked array (`...[$data, 'json']`, read the way PHP passes it, so an entry a later key overwrites does not count) and in a call to the parent class (`parent::serialize($data, 'json')`). Only the format argument counts: stored JSON, a `'json'` array key or a method of another class with the same name pass. To resolve it, pass `JsonEncoder::FORMAT` (from `Symfony\Component\Serializer\Encoder\JsonEncoder`).

## When `bin/check` reports a highlights finding

`docs/highlights.md` lists the Symfony and Symfony AI features Intakt uses, and the `highlights` gate of `bin/check` checks its tables. The page is not in git and not edited by hand: `bin/highlights` builds it from `docs/highlights.d/` (run it to read the page locally), where `layout.md` holds the intro, the headings and the table headers, and each change adds one fragment named after its issue, such as `docs/highlights.d/1045-highlight-fragments.md`. A fragment holds only rows, each under the `## <section>` heading of its section in `layout.md`: table rows starting with `|`, or list items starting with `- ` in "PHP 8.5 in use". To change a row, add a fragment with the whole new row; it replaces the earlier row with the same first cell (or, for a list item, the same text before its closing status parenthesis such as `(done, T6)`, so an item can change its status) at its place, because fragments apply in the order they were merged, whatever their issue numbers: the order git added them to the branch, a fragment you have not committed yet last, and fragments added in the same commit (or outside git) in the natural order of their numbers (fragment 10 after fragment 2). The gate checks the page as `bin/highlights` would build it, so two changes never touch the same file, and a copy on disk that differs from that build fails. The order needs the full git history: in a shallow clone the gate fails until you run `git fetch --unshallow`. Each finding names the line: a fragment finding the line of the fragment, a table finding the line of the built page. To resolve it:

- **docs/highlights.md is committed:** the page was added to git (for example after a hand edit); run `git rm --cached docs/highlights.md` and put the change in a fragment;
- **docs/highlights.md is not the assembly of docs/highlights.d/:** your local copy was edited by hand or is older than the fragments; put any change in a fragment and run `bin/highlights`;
- **the history of docs/highlights.d/ is shallow:** run `git fetch --unshallow`;
- **cannot write docs/highlights.md** (from `bin/highlights`, which then exits with status 1): something else is in the way, such as a folder of that name or a read-only file; remove it or make it writable and run `bin/highlights` again;
- **a fragment is named `<issue>-<slug>.md`:** rename the file to its issue number, a hyphen and a slug in lowercase letters, digits and hyphens;
- **section is not a section of `layout.md`, or the line is outside a section:** put the rows under a `## ` heading spelled exactly as in `layout.md`; a new section is added to `layout.md` first;
- **section holds table rows (or list items), or the table header is in `layout.md`:** write only the rows of the section's kind; the header and its `---` line stay in `layout.md`;
- **row appears twice in this fragment:** keep one row per first cell (one list item per text before its status) in a fragment;
- **status is not one of planned, in progress, done:** write exactly one of those three words in the Status column, and move any remark (such as "optional") to another column;
- **Where cites a pull request:** name the task and its issue instead (`T9 (#14)`); a pull request number counts in every form (`PR #12`, `PR: #12`, `PR (#12)`, `PR12`, `pull request 12`, `pull/12`), while text inside backticks, such as a path `upstream/pr1-repro/`, does not (a span opened with two backticks ends only at the next two, so it may hold a single backtick, and a backtick written with a backslash before it, `` \` ``, is plain text that starts no span);
- **Where names a path which does not exist on the branch:** fix the path, add the file to git, or remove the backticks when the text is no path. Anything in backticks with a `/`, or ending in an extension like `.php` or `.md`, counts as a path and must be tracked by git; package names and commands with a `/` therefore go without backticks. A `|` in a path is written `\|` inside the table, and the gate checks it as `|`;
- **row is planned, but every path its Where names exists:** the change that built the row's feature left its status behind; set the Status to `in progress` (an open pull request) or `done` (on main). A planned row that names no path, or a path not built yet, gets no such finding;
- **Where cannot be checked, shorten the cell:** the cell is too long for the gate to read (usually a stray backtick before a very long text); close or remove the backtick, or split the text.

Tables inside a fenced code block (three or more backticks or tildes, indented at most three spaces) are examples and are skipped. The block ends at a line holding only a fence of the same character, at least as long as the opening one; a fence line with text after it stays inside the block. A block that is never closed runs to the end of the file.

A fragment may hold `{{` or `{%`, in a code span for example: the published page shows them as written.

## When `bin/check` reports a reproductions finding

Every folder directly under `upstream/` is a reproduction of a likely library bug, and the `reproductions` gate of `bin/check` checks that each one is listed. A finding such as `upstream/messenger-lost-message/ has no row in "Found in the beta" of docs/highlights.md` names the folder. To resolve it, add a row to the "Found in the beta" table of `docs/highlights.md` (through a fragment under `## Found in the beta` in `docs/highlights.d/`; the gate reads the page built from the fragments, see the highlights finding above) that names the folder in its text, for example `` `upstream/messenger-lost-message/` `` in the Where column. Only a row of a table in that section counts (a table needs its header and its `---` line, not indented four or more spaces, and it ends at the first line that is blank, has no `|`, or starts a heading, a list item, a blockquote or an HTML comment, even when that line holds a `|`; only the cells under the header's columns count). A line without a `|` ends the table even where GitHub would still show it as a row: this is stricter than GitHub and can only make the gate fail, never pass wrongly. A mention in its prose, on a line that merely starts with `|`, under a heading or in a list right after the table, in another section or inside a fenced code block does not, and neither does a longer path such as `docs/upstream/messenger-lost-message/`. A file directly under `upstream/` (such as its `README.md`) needs no row. The gate reads the folders git tracks or would add (ignored files do not count), and the working tree when there is no git repository.

The same gate checks the reports. A finding such as `upstream/a-bug/REPORT.md is ready to file but has no "Checked" line` or `... is older than 14 days` means the last `Decision` or `Status` line of `## Upstream status` says `ready to file` without a dated `Checked` line. The gate reads such a line however it is written: with any list marker or none, with or without backticks, in any case, and with more text after the phrase. Check the report against upstream again, add or update `- **Checked:** YYYY-MM-DD ...` (commits or tags, duplicate search, preferred form and target branch; see `upstream/README.md`), or change the status. A finding `... has no "Pull requests and commits" line` means the section does not say which upstream pull requests and commits the check found: add `- **Pull requests and commits:** ...` naming them (a `#` number, a URL or a commit hash), or `none found` with the date of the search as `YYYY-MM-DD`. A line that starts with `none`, `nothing` or `no` always needs that date, even when it names the searched pull requests or a search URL. A line that names none of these and holds no date, such as `none`, `-` or `No pull requests or commits found.`, gets `... names no pull request (#n), URL or commit hash and no date of the check as YYYY-MM-DD`. A finding `... has no "## Upstream status" section` means a `ready to file` line stands in a report whose status heading is not written exactly that way: fix the heading. A report has only one such section (`... has more than one Upstream status section`), and its status is a list item at the top level of that section: a line that says `ready to file` in another section, in a quote or indented four or more spaces gets `... write the status as a list item in the Upstream status section`.

## When `bin/check` reports a container finding

The `container` gate of `bin/check` runs `bin/console lint:container` for the `dev`, `test` and `prod` environments, also with `--fast`. It catches a wrongly wired service before the first request does: a service argument of the wrong type, or a reference to a service or parameter that does not exist. A finding names the environment and Symfony's message, for example `prod: Invalid definition for service "App\Mailer": argument 1 of "App\Mailer::__construct()" accepts "App\Transport", "App\Clock" passed.` To resolve it, fix the service definition or the constructor type it names, then run `php bin/console lint:container --env=<environment>` to see it pass. Environment variables are not resolved, so a missing API key does not fail the gate.

The `phpstan` gate of `bin/check` knows the service container too: before it analyzes the code it builds the `test` environment's container of the checked tree in that tree's own `var/cache/` folder, whatever `APP_CACHE_DIR` or `APP_BUILD_DIR` says (`php bin/console cache:warmup --env=test`, so a tree without `bin/console` fails the gate) and reads the service ids and parameter types from it. A `get()` with a service id the container does not define fails the gate, for example `src/Lookup.php:17 symfonyContainer.serviceNotFound Service "kernal" is not registered in the container.`, also when the id is picked from several fixed strings and only one is wrong, and so does a `get()` of a private service outside the test container, also when it is one of several fixed strings. A `has()` with such an id fails the same way (`intakt.containerUnknownHasId`), even when the id is picked from several fixed strings and only one is wrong, and so does a `getParameter()` with a parameter name the container does not define, for example `src/Settings.php:17 intakt.containerUnknownParameter Parameter "kernal.debug" is not defined in the container.` To resolve it, fix the id or name, or use the ids class constant that names it. A service locator's own keys and the parameter names asked of a container bag are not checked, as long as the locator is typed as `ServiceProviderInterface`: a locator typed as `Psr\Container\ContainerInterface` looks like the container itself, so its keys are checked as service ids. With `--fast`, a change to `config/`, `src/Kernel.php` or a `services.yaml` under `tests/` checks every PHP file, so removing a service in configuration alone still finds its callers. A test that sets a service during the test declares it `synthetic` in `tests/Support/services.yaml`; a test that boots a kernel with other settings reads that kernel's services through `tests/Support/RebuiltContainer`.

## When the `left-undone` gate reports a TODO comment, a skipped test or a not-implemented throw

The `left-undone` gate of `bin/check` (also with `--fast`) also fails when your change adds, under `tests/`, a `markTestSkipped()` or `markTestIncomplete()` call (in any letter case) without a message, a first-class callable of one such as `$this->markTestIncomplete(...)` (its later message cannot be checked, so call the method directly with its message), or a `#[Skip...]` or `#[Incomplete...]` attribute without one (also `#[\Vendor\SkipIf]`) (`tests/OrderTest.php:5: markTestSkipped call without a reason; ...`), or, under `src/`, a `throw new LogicException('Not implemented')`, a `throw new NotImplementedException()` or similar, also with the message as `message:` or built with `sprintf()` (`src/Order.php:5: not-implemented throw left in the change; ...`). To resolve it, give the skip a message naming the missing tool or outside condition on the same line as the call (`markTestSkipped('python3 is not on the PATH')`, also as `message: '...'` or `"needs $tool on the PATH"`), make the test run, or implement the code. A message of only escapes or nothing, such as `"\t"`, `'\n'` or `b''`, is no message. A not-implemented throw passes only with a comment on the same line that starts with `//` or `#`, then `TODO`, `FIXME` or `XXX` (any case), then `(#<issue>):` and a reason: `// TODO(#123): <reason>`, `# fixme(#123): <reason>` or `// XXX(#123): <reason>`. Reviewers judge whether the message names a real condition. The rest of this section describes the comment rule.

The gate fails when your change adds a PHP or Twig comment that starts with `TODO`, `FIXME` or `XXX`, for example `src/Order.php:5: TODO comment left in the change; finish the work, or open an issue and write TODO(#<issue>): <reason>` or `templates/order.html.twig:3: TODO comment left in the change; ...` for `{# TODO: show the total #}`. In a template, a Twig comment is `{# ... #}` (also `{#- ... -#}` and over several lines), a documentation comment that opens with `{##` and closes with `##}` or `#}` (`{## TODO explain the total #}` fails), or a `#` or `##` comment inside a `{{ }}` or `{% %}` tag (`{{ total ## TODO round it` fails too); plain template text, an HTML comment `<!-- TODO -->`, a string such as `{{ 'TODO' }}` and a `{% verbatim %}` block are not Twig comments and pass. An HTML comment does not hide a Twig comment inside it: `<!-- {# TODO finish this #} -->` fails. A marker behind nested comment syntax counts too: `// // TODO later`, `# # FIXME the total` and `/* // XXX breaks on empty orders */` all fail, while `// // TODO(#12): drop once the forge sends the total` passes like the form below. In a Twig comment, PHP or shell comment syntax is text, not Twig syntax, so `{# // TODO is the PHP syntax #}` passes, and so does `{# # TODO is shell syntax #}`: a hash after `{# ` and a space is text, not the `{##` opener; only a `*` followed by whitespace at the start of any Twig comment line is skipped, so a line ` * FIXME the total` inside a star-framed multi-line `{# ... #}` fails, and so do a one-line `{# * TODO show the total #}` and an inline `{{ total # * TODO round it` (a `#` comment runs to the end of its line, so the closing `}}` goes on the next line); a star right before the word is Markdown emphasis, so `{# *TODO* is shown in italics #}` passes. It reports only the lines your change adds against the target branch (committed or not, and every line of a new file git does not track yet); it reads each changed PHP or Twig file whole, to tell a comment from a string, but only an added line can fail. So a comment that was already there, or that only moved with a renamed file, is not reported. The same text inside a string is not a comment and passes. Markdown, files other than PHP and Twig, `tests/Fixtures/`, `fixtures/`, `tests/Gates/Fixtures/` and `upstream/` are not read. JavaScript files are not read yet either: a scanner for their comments exists, but the gate does not use it yet. To resolve it, finish the work, or open an issue and name it with a reason on the same line: `// TODO(#123): drop once the forge sends the total` passes this gate (it checks the form, not that the issue is open), and so does `{# TODO(#123): show the total once the forge sends it #}` in a template. The `comments` gate accepts the same form when the comment also gives a reason, with a word such as *because* or *needs*: `// TODO(#123): drop once the forge sends the total, because it is computed twice` gets a change through `bin/check`. Without a target branch the gate fails with `no base branch found, pass --base=<ref>`; a folder without git history skips it.

## When the `phpstan` gate reports a prompt message finding

Every message Intakt sends to a model is built by one class, `Intakt\Core\Review\Contract\PromptAssembly`, so no text from outside reaches a model unfenced. The `phpstan` gate of `bin/check` (also with `--fast`) fails when code under `src/`, `bin/` or `config/` builds a model message anywhere else: a call of `Message::ofUser()`, `Message::forSystem()` or `Message::ofAssistant()`, or `new UserMessage(...)` or `new SystemMessage(...)`. It also catches the less direct forms: a first-class callable such as `Message::ofUser(...)`, a call through an object or a class-name string (`$message::ofUser()`, `new $class(...)` with `$class` typed `class-string<SystemMessage>`) and a method name given as a known string (`Message::{'ofUser'}()`). It also refuses a literal callable of a factory: an array with exactly the keys `0` and `1` in any written order, `Message` at `0` and at `1` either a factory name or a method name known only at run time that may be a string (`[Message::class, 'ofUser']`, `[1 => 'ofUser', 0 => Message::class]`, `[Message::class, $method]` with `$method` typed `string` or `?string`; a known name that is not a factory passes), and a callable string such as `'Symfony\AI\Platform\Message\Message::ofUser'`; an array with other keys, such as `['class' => Message::class, 'method' => 'ofUser']`, passes. Code in a trait is judged by the file the trait is written in, so a trait under `src/` is judged even when only a class under `tests/` uses it. The finding names the call, for example `src/Sample/Report.php:13 intakt.rawPromptMessage Message::ofUser() builds a model message outside PromptAssembly: build it through Intakt\Core\Review\Contract\PromptAssembly, with Intakt's own text as a literal and untrusted text as a FencedText from Fence.` To resolve it, call a method of `PromptAssembly` instead: write Intakt's own instructions as literal strings, and wrap any text from a model, a forge or a user with `Fence::wrap()` (or `PromptCut::fenced()`) and pass the resulting `FencedText`. Code under `tests/` is not checked.

A second finding, `intakt.unprovenRolePrompt`, appears only in `ReviewWithReviewerHandler`: it means a `new ReviewerConversation(...)` there takes a role prompt that is not `$reviewer->rolePrompt()` of the round's `RoundReviewer`. To resolve it, pass that call as the role prompt (first argument, or the argument named `rolePrompt`), not a string, and unpack no argument in that call (not even after the role prompt), because the role prompt is the one text that enters the system message verbatim.

## When `bin/check` reports a ratchet finding

A new PHPStan rule can be switched on before the code is clean: the violations it finds that day go into a ratchet list, one file per rule outside `config/gates/`, included from `config/gates/phpstan.neon`. The `ratchet` gate of `bin/check` (also with `--fast`) makes sure such a list only gets shorter. It compares each list with the list on the target branch and fails when an entry was added, a `count` went up, or an entry's identifier, message pattern or path changed, for example `ratchet/loose-conditions.neon: count rose from 2 to 3: [...]`. To resolve it, fix the new violation in the code instead of listing it; deleting entries and lowering counts always pass. A list also needs a line `# Cleanup issue: #<number>` in its header, may hold nothing but `parameters:` with `ignoreErrors:` (`ignoreErrors: []` once its last entry is gone), and arrives only in the change that adds its include. A violation that is not on the list, or a list entry that no longer matches anything (for example after a fix or after moving the file), fails the `phpstan` gate: delete the entry in the same change as the fix. A tree without any list passes with the note `no ratchet lists`. The gate reads the includes of `config/gates/phpstan.neon` only as plain `- path` lines under an unindented `includes:` key (the lines may be indented or not); any other form, such as `includes: [...]` or a configuration file that is indented as a whole, fails with `cannot read the includes` rather than overlooking a list.

## GitHub's test merge and the `commits` gate

On a pull request, GitHub checks out a merge of the branch into the base branch, with a subject such as `Merge <sha> into <sha>`, which is not a Conventional Commit. CI names that merge and the pull request's head with `--test-merge=<merge>:<head>`, and the `commits` gate skips it when its second parent is the pull request's head and its first parent is on the base branch, also when the base branch moved after the pull request's last update. Every other commit, merges included, still needs a conforming subject.

## Running a probe against an install

`php bin/probe tests/Probe/NAME.php` boots the same scratch instance and runs one small PHPUnit test (a name ending in `Test.php`) or PHP script against it, with the network cut, so anything that reaches for the network fails. The script or test finds the instance's address in the environment variable `INTAKT_INSTANCE_URL`. Its output is printed, followed by a line `exit code: N`, and the command exits with that code. A probe still running after 60 seconds is stopped with exit code 124. The instance, its files and anything the probe started are removed afterwards. It needs Linux with `unshare` and `ip`, which cut the network for the run.

The instance and the probe do not inherit your whole environment, so a token you have set in your shell is not visible to them. They get only `PATH`, `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TZ` and `TMPDIR` (when you set them), the application variables `bin/instance` sets itself (`APP_*` and `DATABASE_URL`) and `INTAKT_INSTANCE_URL`; in worker mode also `INTAKT_INSTANCE_ADMIN_URL` (FrankenPHP's admin API) for the probe, and `XDG_DATA_HOME` and `XDG_CONFIG_HOME` (inside the scratch folder) for FrankenPHP. `PWD` is also present: the `sh -c` wrapper in `bin/instance` sets it, it is not taken from your environment. `APP_ENV` and `APP_SECRET` keep your value when it is set and not empty or `0`.

A caller that already runs `bin/probe` without network access and in its own process namespace (as the build loop's sandbox does) sets the environment variable `PROBE_ISOLATED=1`. `bin/probe` then starts the instance directly and needs neither `unshare` nor `ip`, but first checks that the run really is offline: when `/proc/net/dev` cannot be read or lists something unexpected, when it shows a network interface other than `lo`, or when `lo` is down, it prints the reason and exits with code 2 before anything starts. The caller is responsible for ending whatever the probe leaves running. Any other value, or no value, keeps the `unshare` way.

## Looking inside the development install with Mate

On a development install (`composer install` with the dev packages), `vendor/bin/mate` answers questions about the running app from its own container and environment files instead of from reading the code. It is not part of a production install: `composer install --no-dev` leaves it out.

- `vendor/bin/mate tools:list` lists the tools.
- `vendor/bin/mate tools:inspect TOOL` shows a tool's parameters.
- `vendor/bin/mate tools:call TOOL --PARAM=VALUE` runs one; add `--format=json` for machine-readable output.

The useful tools today are `symfony-services` and `symfony-service-detail` (which services the container holds and how one is wired), `symfony-dotenv-check` (which `.env*` file declares a variable and whether it resolves, with the value masked) and `server-info` (PHP version, system and extensions). The profiler tools `symfony-profiler-list` and `symfony-profiler-get` list and read the profiles Symfony's profiler saves.

The development install (`APP_ENV=dev`) saves a profile of every request, by default under `var/cache/dev/profiler/`, and names it in the response's `X-Debug-Token` header. In `test`, a request saves a profile only when its test calls `enableProfiler()` on the test client; two tests use it to pin what a request does: the number of database queries of the reviews page with three rounds, and the messages a press of the dashboard's start button dispatches. A production install has no profiler. A profile holds only what measures the request: the database queries, the messages dispatched, the time and the memory. Of the request itself it keeps the method (such as `GET`) and the URL without the part from the `?` or `#` on: the query string is cut off before the profile is saved, and a URL it cannot read (for example one with a raw space or a non-ASCII character in its path) is not saved at all. It keeps no headers, cookies, session, body or client IP address, and none of the environment variables, so no secret ends up in it. This holds also when the development install runs with `APP_DEBUG=0`. There is no profiler toolbar or `/_profiler` page; read profiles with the Mate tools above.

To read one request: start the install with `APP_ENV=dev`, send it a request at the address it listens on (with `php bin/instance`, the usual way to start one, that address is in `$INTAKT_INSTANCE_URL`, so the request is `curl -si "$INTAKT_INSTANCE_URL/"`), copy the `X-Debug-Token` header and run `vendor/bin/mate tools:call symfony-profiler-get --token=TOKEN --format=json`. The answer names the request and lists its collectors (`time`, `memory`, `db`, `messenger`). `symfony-profiler-list` lists the latest profiles when you have no token. With `bin/instance`, the profiles live in its scratch folder only while it runs, so run Mate as its command: `APP_ENV=dev php bin/instance -- sh -c 'curl -si "$INTAKT_INSTANCE_URL/"; vendor/bin/mate tools:call symfony-profiler-list --format=json'` (Mate looks where `APP_CACHE_DIR` points when it is set, as `bin/instance` sets it for its command). None of this is in the container image. No Mate extension is published for the other bundles Intakt uses (Doctrine, Messenger), so these six are all the tools there are. For the read-only console commands to use beside them, see "Tools for looking inside the app" in `AGENTS.md`.

If Mate stops with a PHP version mismatch, it was started with a PHP other than 8.5 (the version `mate/config.php` pins); run it with the PHP 8.5 the app uses. If a container tool reports "No compiled container found", run `bin/console cache:warmup` first so the dev container exists. If `tools:list` says "No tools found", check whether `vendor/` is a symlink: Mate then looks for its settings next to the folder the symlink points to and finds none, so it needs a real `vendor/` folder in the project. The other cause is missing package information: Mate finds its packages through `vendor/composer/installed.json`, so if that file is missing or does not list `symfony/ai-mate`, run `composer install` again with the dev packages (without `--no-dev`).

`vendor/bin/mate discover` writes files for coding agents: skill copies in `.agents/skills/` and `.claude/skills/`, and a `CLAUDE.md` in the project root; Git ignores all three. It also rewrites the committed `mate/extensions.php` and `mate/AGENT_INSTRUCTIONS.md`; do not commit those changes, and restore the files with `git checkout -- mate/extensions.php mate/AGENT_INSTRUCTIONS.md`.
