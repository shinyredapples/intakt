# Building tasks

Intakt builds a task in a job container of its own, checks what the build hands back and pushes an accepted build itself. This page covers job containers and images, what a builder is told, the build commands, the protected paths and the watchdog's rules for main, and how a risky CI change is scanned and held for your approval.

## Job containers

Intakt has the part that will run each build, check and review in a container of its own; the check before a push uses it ([below](#the-check-before-a-push)), and no build or review uses it yet. Each job gets a fresh container that is thrown away afterwards: its system files cannot be changed, it works in a scratch area that is gone when it ends (its home folder and caches live there too, so every job starts clean), the inputs it is given are read-only, and the only thing it can hand back is what it leaves in its own output folder, which no other job can see. It gets none of Intakt's keys or tokens, and has its own memory and CPU limit, so a job that runs out of memory is stopped alone. What a job hands back is bounded too: at most 1000 files and 16 MiB in total, so a job that writes more fails instead of exhausting Intakt's memory. An image that declares volumes is refused, because a job could write into them. The ledger records how each job ended (`job_ended`): `exited` with its exit code, `oom` when its memory limit stopped it, or `timed_out` when it ran past its time and was stopped (a job that runs out of memory just before it is stopped still counts as `oom`). A container that keeps running even after it was stopped fails the job: no end is recorded, and the container is removed.

A probe job has no network at all. A job that needs to download (the check before a push names the package registries; a build names the AI company's address and the package registries; a review job names the AI company's address alone) gets a short list of host names it may reach, and nothing else: it sits on a network of its own whose only way out is a proxy of its own, and the proxy lets through only `CONNECT` tunnels to port 443 of the hosts on the list; it does not check that what runs inside a tunnel is encrypted. Everything else is refused: another host, an address, plain HTTP or another port. The job cannot reach other services on the Docker machine either, except one published on port 443 at an address a listed host name resolves to; for the dashboard this is an accepted risk of the [threat model](../design/05-architecture/14-threat-model.md). The job starts only once its proxy is ready; a proxy that stops, reports itself unhealthy or is not ready within 30 seconds fails the run before the job starts. Each refused request is written to the ledger as `job_egress_refused` with the method and what was asked for (for example `CONNECT outside.example:443`), each one once and at most 20 per job. Host names on the list are exact and lowercase, without wildcards; a list with an address, a wildcard or a port is refused before the job starts.

Before its own command, every job checks that what it was told it can do works: it writes a small file into its output folder and its scratch area and reads it back, checks that each input it was given can be read, and, for a job with a host list, that each host on the list answers through its proxy (this needs `curl` in the job's image). Each check is written to the job's log with a mark that is new for every run, for example `intakt-start-check 3f9c…: input: /input/memory is not readable`. When a check fails, the job still runs, but in a reduced mode: its log says `reduced mode:` with the failed checks, the job itself finds them in `INTAKT_REDUCED_MODE`, and the ledger gets one `job_start_check_failed` event per failure with the check (`output`, `work`, `input`, `egress`, or `log` when the check's lines in the job's log are missing or damaged) and the reason, at most 20 per job. Intakt reads the result from the job's log before the job's container is removed, and only the lines with that run's mark up to the `full mode` or `reduced mode` line count. The job's command never sees the mark, so nothing the job writes or prints can turn a failed check into a passed one; if the check's own lines are lost (say Docker's log settings rotate them away while the job floods its log), the check counts as failed. A job whose output folder cannot be written is recorded as an `output` failure. The job image needs `/bin/sh`; its own entrypoint is not used.

The proxy comes from its own image, which you build once on the machine that runs Docker:

```
docker build -t intakt-egress-proxy docker/egress-proxy
```

It has not yet run against a real Docker Engine; it is first checked when jobs run on a machine with Docker. Use Docker Engine 25.0.5 or later: older engines answer DNS lookups for outside names even on a network without a way out.

Intakt needs the Docker Engine's socket at `/var/run/docker.sock` for this. Without it a job fails with `The Docker Engine is not reachable: there is no socket at /var/run/docker.sock.`

Containers are removed when their job ends, with the job's proxy and network. If Intakt itself crashed while jobs ran, their containers and networks are removed before the next job starts (`job_container_removed` and `job_network_removed` in the ledger). To clean up at once, run:

```
php bin/console intakt:job:sweep
```

It prints one line per container it removed and a count, for example `1 orphaned job containers removed.`, and leaves the containers of jobs that are still running alone. When the engine cannot be reached it prints the reason and exits with 1.

### Job images

The image a project's jobs will run in comes from the project's last commit (files you have not committed do not count), from the first of these it has:

1. `.devcontainer/devcontainer.json`: its `image`, or the Dockerfile its `build` names (comments and trailing commas are fine; a compose setup is not supported yet).
2. A `Dockerfile` at the top of the repository, used as it is.
3. Only `composer.json`: Intakt writes the Dockerfile itself, with the PHP from `config.platform.php` (a three-number version exactly; a two-number one such as `8.4` is a minor, and `require.php` then picks the patch by the rule below) or else the newest of PHP 8.5, 8.4, 8.3 and 8.2 that `require.php` allows (its latest patch only when `require.php` allows every patch from the newest one Intakt knows was released, such as 8.4.25, to the end of that version, otherwise the highest allowed patch up to that known release, or the lowest allowed one above it, so `8.4.1` gives 8.4.1 and `>=8.4.1 <8.4.20` gives 8.4.19; the same applies to a minor from `config.platform.php`, and for a minor with no known released patch it is the latest patch when the last allowed range runs to the end of that version, otherwise the highest allowed patch), Composer, every `ext-*` extension under `require` and `require-dev`, and fixed versions of the Claude Code and Codex command-line tools.

A job never gets another PHP: when `composer.json` names no PHP version at all, no image is built, whatever else the project has. The build itself is not network-free: steps that come from the project (its Dockerfile, or the base image a devcontainer names) run on the engine's host with the engine's default network, without Intakt's egress controls (see the [threat model](../design/05-architecture/14-threat-model.md#job-image-build-inputs)). After the build, when the project has a PHP profile, Intakt starts the image once without network and asks its PHP for its version and extensions; an image whose PHP does not match `composer.json`, or that lacks an extension, is refused with the version or the extension's name. An extension that cannot be installed fails the build with `missing PHP extension: <name>`.

```
php bin/console intakt:job:build-image path/to/checkout intakt-job/my-project:main
```

It prints where the image comes from, the build's output, and for example `Image intakt-job/my-project:main (sha256:...) built: PHP 8.5.12 with every required extension.`, with the id of the image this build made: the check ran in that image, even if another build has since given the tag to its own. To see where the image would come from and the Dockerfile Intakt would write, without building, run `php bin/console intakt:job:plan-image path/to/checkout`. On any failure both print the reason and exit with 1. What goes to the engine depends on where the image comes from. With your own Dockerfile (the one at the top of the repository, or the one a devcontainer's `build` names), the committed files go to the engine as an archive streamed from a temporary file, so a large repository needs disk space in the system temporary folder for the time of the upload, not memory. With a Dockerfile Intakt writes (the generated image, or a devcontainer that names an `image`), only that Dockerfile is sent, and the size of the repository does not matter. In both cases the temporary file is deleted as soon as the engine has received it, and also when the build fails. It needs the Docker Engine's socket like the jobs do, and the Docker machine must reach Docker Hub, Debian's package mirrors and the npm registry for a generated image. Nothing builds images on its own yet, and images are not rebuilt when the project changes.

A review job will run a reviewer's command-line tool, which your own Dockerfile or devcontainer image may not have. Add `--kind=review` to either command to get a review job's image: your Dockerfile (or the devcontainer's `image`) followed by Intakt's steps that install `curl`, `git`, Node.js and the Claude Code and Codex command-line tools with `apt-get` and `npm`, so the image's last stage must be Debian or Ubuntu based. A generated image has them already and stays as it is. A Dockerfile that sets `# escape=` to a backtick in its parser directives at the top (also after another directive such as `# check=skip=all; error=true`; an ordinary comment such as `# maintainer=Example Team` ends the directives, so a backtick line after it is a comment), or whose last line ends with a backslash that continues it (an escaped backslash, `\\`, does not), is refused with the reason.

Give each project the image its review jobs run in, in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names), and run `php bin/console cache:clear`:

```yaml
projects:
    alpha:
        review_job: { image: intakt-job/alpha:review }
```

A `review_job` section without an `image` stops Intakt from starting. A review job runs one reviewer on Claude Code (it may reach `api.anthropic.com` only) or Codex (`chatgpt.com` only), with 4 GiB of memory, 2 CPUs and 30 minutes; a reviewer on another provider, or a project without an image, gets no job. The job does not carry your subscription login yet, so it cannot sign in, and no review uses review jobs yet: reviews still run inside Intakt.

The script a review job runs, `docker/job/review.sh`, is not used by any review yet. Before it starts the reviewer's tool (Claude Code with file reads only, or Codex with its shell and other tools switched off), it checks that the reviewer gets exactly the commit under review and cannot change it: the checkout must be a real folder, not a link, every file and folder of it must be read-only, the checkout must be at that exact commit, with no changed, deleted or extra file (files your `.gitignore` ignores, such as `vendor/`, are fine), and with no repository setting or local attributes file beyond what a fresh clone writes. A folder the commit holds as a submodule must be empty, as a fresh clone leaves it, so nothing can hide there or run from there; a submodule whose path has a control character, a double quote or a backslash is refused. Files are compared byte for byte, so a project whose `.gitattributes` makes git rewrite files on checkout (`ident`, `eol=crlf`, `working-tree-encoding`, or a `filter` such as a Git LFS smudge filter) is refused even when nothing changed. No hook in the checkout's `.git/hooks` runs during the checks, and no attributes file outside the repository (in your home folder or the system's) is read. It also checks that the job has its proxy and host list and passed its start check, and makes sure nothing bypasses the proxy. The checks need git 2.40 or later in the review image: Debian 12 and Ubuntu 22.04 install an older git, so with one of them as your image's last stage every review is refused (`refused: the checkout checks need git 2.40 or later, found: git version 2.39.5`, say); Debian 13 and Ubuntu 24.04 are fine. If any check fails, the reviewer never starts, and the job's `review.log` says why, for example `refused: the checkout differs from the head`.

### The check before a push

Intakt never trusts a builder's own run of the checks. Before anything is pushed, it checks the bundle a build returned (as `intakt:hand-back:check` does, secret scan included, see [Hand-back checks](../architecture/hand-back.md); it takes no `--credential-env`, so it redacts no mounted credential, and no pull request text, so it neither scans one nor records a send-back or hand-over) and then runs the project's check on it in a job container:

```
php bin/console intakt:check:run var/mirrors/my-project.git my-task-branch build.bundle intakt-job/my-project:main
```

The arguments are the project's mirror, the task's branch, the bundle and the project's job image ([Job images](#job-images)). The job clones the mirror afresh and applies the bundle on the task's branch. The mirror need not belong to the job's user: the job trusts that one repository for its clone only, and passes that exception on git's command line only, never in a configuration file. When main (the commit the mirror's `HEAD` points to) has commits the branch lacks, the job then merges the branch into main inside its clone, as GitHub's CI merges a pull request, and checks that merge; the bundle stays as it is. That merge reads no git settings of the job image or the job's environment (merge options, signing, hooks, attributes outside the repository), as GitHub's merge reads none of yours; the repository's own `.gitattributes` still counts. The command uses the mirror as it is, so run `intakt:mirror:update` first to check against the latest main. A branch that conflicts with main (git reports a conflict) fails with `the branch conflicts with current main, so the check ran no step`, and a merge that fails without a reported conflict (git refuses it, for example for a branch with no history in common with main, its commit fails, or it leaves no merge commit) with `git refused to merge the branch with current main without a conflict, so the check ran no step`; neither runs a check. Then the job runs `composer install` and then `bin/check --fast` in that clone, with empty caches, so nothing from the build's own folder or downloads is reused. It may reach Packagist and GitHub's archives only. `--check-command="make check"` runs your own command instead (it then has to install what it needs itself). The result comes back only through the job's output folder; a job that leaves no clear result there, runs out of memory or runs out of time fails the check.

Intakt will later let checks of heads with the same `composer.json`, `composer.lock` and PHP version share one dependency install. No check does that yet, but the store that will keep those installs is in place: Intakt keeps them in `var/dependency-snapshots`, which only Intakt itself writes (no build gets it, and a check will get only its own install, read-only). It keeps the 10 installs used most recently (`intakt.hand_back.dependency_snapshot_count` in `config/services.yaml`, at least 1) and never removes one a check is using, so it can hold more while checks run and until the next time it saves or hands out an install after they end. If Intakt is stopped while it removes an install, no check ever gets the half-removed copy, and Intakt clears it, with any other leftover of that removal, the next time it saves an install or looks for one (even when it finds none). The rule for which projects may share one is in place too: a project may share an install only when its lock file pins every package's contents. A project is not allowed to share (it then installs for each check, and the check does not fail for this) when its lock holds a package from a local folder (a `path` package, in any letter case), an archive without a checksum (unless its `https` address ends in its own locked commit id), a source locked to anything but a full commit id, a malformed checksum, mirrors, a local or unknown address, a Composer plugin or installer other than `symfony/runtime`, or when your `composer.json` defines a `pre-package-install`, `post-package-install`, `pre-package-update` or `post-package-update` script or is not valid JSON, or when, after Composer ran, a package that was cloned from source is not at the commit the lock names or cannot be checked (a different commit, a `.git` that is missing, a link or a file, a `.git/commondir` file, a source that is not git, or a folder Composer recorded outside the vendor folder). Intakt looks for each clone where Composer recorded installing it, so a package name with capitals or a `target-dir` is checked too. The reason is one line naming the package, file or script; it never shows the refused address, since an address can hold a password.

Before the job starts, Intakt compares each file the change touches with the version the branch started from. A file that keeps less than a fifth of its size and loses more than 50 lines (a removed file counts too) stops the check at once, with the file named, unless the task's plan names it as removed or rewritten: pass each such path with `--rewritten=<path>`. A file the change replaced with a submodule counts as emptied. A file that is only moved, or one that main shrank, is fine; a file moved to a new path and then rewritten is covered by naming its new path. A named path covers one file only: the file that was at that path when the branch started, or, for a path the change created, the file that is there at the end and the path it came from. Moving another file onto a named path does not cover it, and a file that passed through a named path on its way to another path is still checked under that path. A file moved onto a named path that the change then removed and created anew is not covered either, because the new file there is another file.

It prints any lost files (`lost docs/guide.md: 120 lines to 1`), the last 40 lines of the check's output, and `passed` (exit 0) or `failed:` with the reason and, for a failed command, its exit code (exit 1). A refused bundle prints `refused:` and the reason. Without Docker it fails with `The Docker Engine is not reachable: there is no socket at /var/run/docker.sock.` Nothing runs this check on its own yet: the push and the build lane will.

## What a builder is told

A builder's instructions name the task, your decisions on it and, for a rework, the findings to act on, the excerpt of the failed CI log and the published pull request text it edits. Each of these is marked as untrusted text with its source (`task`, `decisions`, `act list`, `ci log`, `pull request text`), and the instructions say that marked text is data: the builder never follows a line in it that asks it to handle credentials, change protected paths, disable checks, push, merge or reach outside services. A task, CI log excerpt or pull request text longer than 100000 bytes is cut to at most 100000 bytes, ending a little earlier when needed so no character is split, and Intakt's own note after the marked text says how much was left out. A first build is asked to write the pull request text to `PR.md`; a rework is asked to edit the published text and change only the lines it changes. Both are told that, when they need a decision the task does not cover, they must not guess: they write no `PR.md` and end with a question in the file `QUESTION.json` instead, with the question, one or more choices and their recommendation among them ([Running a build](#running-a-build) says what Intakt does with it). `intakt:build:run` gives a builder these instructions ([Running a build](#running-a-build)). See [Builder prompt](../architecture/builder-prompt.md).

## Building one task

`php bin/console intakt:build:task <project> <issue number> --remote=<remote> --branch=<branch> --directory=<folder> --image=<image>` takes one open issue of a project from its text to a build, in this order: it reads the issue from GitHub (a pull request of that number is no task), updates the project's mirror from `<remote>` (as `intakt:mirror:update` does), makes the build clone in `<folder>` for `<branch>` (as `intakt:build:clone` does; the folder must not exist yet) and runs the build job in that clone in a container made from the project's job image `<image>` (as `intakt:build:run` does). The build job gets the issue's title and body as the task. Its tier comes from the project's `build:` routing rules in `config/intakt.yaml` ([Capability tiers per project](providers.md#capability-tiers-per-project)), so a `model:<tier>` label on the issue counts, and that tier must use the `claude_code` provider. The build job step passes when the builder made at least one commit on the branch, wrote `PR.md` and left no question (a question comes first, see [Running a build](#running-a-build)). A valid question parks the task instead: Intakt stores the question, its choices and its recommendation, records the build job step as `asked`, prints `build_job asked: the task is parked until its question is answered` (never the question itself), runs no later step and exits with 0; if the database does not store the question, the step fails with `Issue <n> of project "<project>" was not parked: the database did not store its question`. A question that breaks the question rule fails the step. Otherwise it fails with the reason `intakt:build:run` gives (for example `the build made no commit on the task's branch`). A project without a `build:` section also fails this step. Then it checks the bundle the build handed back against the project's mirror, as `intakt:hand-back:check` does for the bundle (secret scan included, so `gitleaks` must be installed; see [Hand-back checks](../architecture/hand-back.md)), but without the pull request text and without sending a refusal back to the builder. A refused bundle fails this step with the refusal's reason (for example `the bundle cannot be read as a git bundle`); an accepted one moves the branch of the build clone in `<folder>` to the checked commits, because the build job commits in a copy of its own inside the container (if the clone cannot take them, this step fails too). A git or gitleaks call that is killed or runs too long fails this step with fixed words such as `the hand-back check was killed by signal 15`. A bundle file that cannot be removed from `var/hand-backs` after the check fails this step with that error's message, also when the bundle was accepted. Then comes the pre-push check: it first updates the project's mirror from `<remote>` again, because main may have moved while the builder worked (an update that fails fails this step), then runs the project's checks on the same bundle in a check job of its own in a container made from `<image>`, as `intakt:check:run` does without `--check-command`, so for a PHP project the job runs `composer install` and `bin/check --fast` on a fresh clone of the mirror with the bundle applied ([Check job](../architecture/check-job.md)). When main moved since the branch last merged it, the job first merges the branch into current main inside its own clone, as CI merges a pull request, and runs the checks on that merge; the pushed branch stays as the build handed it back. A branch that conflicts with current main fails this step with `the branch conflicts with current main, so the check ran no step` and runs no check; a merge that fails without a reported conflict (git refuses it, for example for a branch with no history in common with main, its commit fails, or it leaves no merge commit) fails it with `git refused to merge the branch with current main without a conflict, so the check ran no step`. This step passes when the check passes; otherwise it fails with a fixed reason, for example `the check command failed (exit code 2)`, never with the check's log, because the log holds what the built code printed. A check job that runs out of its 30 minutes (`the job ran out of time`) or its memory, a bundle the check refuses again, a job the container runner refuses, and a call that is killed or runs too long (fixed words such as `the pre-push check was killed by signal 15`) fail it too. After a passed pre-push check the build clone in `<folder>` holds the checked commits on `<branch>`. Last comes the push: Intakt signs the checked commits with its own key and pushes `<branch>` to `<remote>`, as described in [Pushing an accepted build](#pushing-an-accepted-build), then opens the pull request of the branch on GitHub, or updates the open one, with the title from the first line of the builder's `PR.md` and the rest as its text. A `PR.md` whose first line is empty fails this step with `the pull request text has no title on its first line` and pushes nothing. A push the remote refuses fails it with the recorded reason (`the remote refused the push of <branch> (git push exited with <n>)`) and opens no pull request; a branch that conflicts with main fails it with `the branch conflicts with main, so nothing was pushed (conflicting paths: <n>)`, and is not sent back to the builder here; an unsigned commit, a title or text that trips the secret scan and a failed GitHub write fail it with their message. The first step finds the issue in the full list of the project's open issues, read page by page (100 issues a page, at most 10 pages), and fails with the reason when that list cannot be trusted to be complete: a page GitHub refuses, rate-limits or answers with anything but a whole page (for example `206 Partial Content`), a `Link` header that cannot be read, a short page that still names a next one, more than 10 pages, an issue listed on two pages, a page before the last that GitHub no longer confirms unchanged once the last page is read (an issue on it was edited, opened or closed meanwhile), a page before the last without a `Date` header or with one that is not an exact HTTP date (for example a weekday that does not match its day), an issue on such a page changed 5 seconds or less before GitHub served it, or an `ETag` that is not an entity tag (such as `*`). An issue the list lacks fails it too. Most of these come from issues changing while the list is read, and running the command again then gets past them ([Forge contract](../architecture/forge-contract.md)). It prints each step that passed (`task passed`, `mirror passed`, `clone passed`, `build_job passed`, `hand_back_check passed`, `pre_push_check passed`, `push passed`) and the issue's title (once it was read; a control character in the title is printed as `?`, because the title is text anyone who can open an issue writes). It stops at the first step that fails, prints that step and its reason, exits with 1 and runs no later step; nothing is retried. Each step is recorded in the ledger as a `build_step_ended` event with the step and whether it passed or failed, or `asked` for the build job of a parked task (`php bin/console intakt:ledger:events` shows it). An issue number that is not a whole number, a missing option, or a ledger that cannot record a step also fail with a message. A run whose steps all pass ends after the push and exits with 0. The bundle file is not kept (an accepted bundle's commits and their signed copies stay in the mirror, named by no branch, and the unsigned ones on the branch of the build clone), so use `intakt:build:run` when you need the bundle. The push writes its own ledger events (`push_intended`, `branch_pushed` or `push_refused`, `change_intended`, `change_opened`) before the push step's `build_step_ended`. Running the command again for the same issue is not refused yet. `intakt:status` shows the last step of each task and its outcome (see [The status document](dashboard.md#the-status-document)), and the dashboard's task page `/tasks/<project>/<issue number>` shows each step of the task's latest run (see [The dashboard](README.md#the-dashboard)). See [Build task](../architecture/build-task.md).

## Running a build

`php bin/console intakt:build:run <project> <clone> <branch> <task> <image> <bundle>` runs a first build of a task: the Claude Code command-line tool works on the task in a container of its own, made from the project's job image `<image>`, and hands back its commits and the pull request text. Git settings the tool leaves in its working copy (including files that tell git to read objects from elsewhere), or in a repository it makes around it, are not used to pack the commits: the job packs only its working copy, writes fresh settings there first, and when it cannot, it hands back no commits and says so in its log. `<clone>` is a copy made with `intakt:build:clone` for the same `<branch>`, and `<task>` is a file holding the task's text. Add `--decision="..."` once for each of your decisions on the task, in order. The model comes from the project's tiers in `config/intakt.yaml` ([Capability tiers per project](providers.md#capability-tiers-per-project)): `--tier=strong`, `standard` (the default) or `light`, and that tier must use the `claude_code` provider.

The builder gets the copy's branches, the [instructions](#what-a-builder-is-told), and a network that reaches only Anthropic's API and the package registries. A question comes first: a build that ended with a valid question exits with 0 and writes no bundle, whatever commits or `PR.md` it also left (see [the question paragraph](#a-build-that-ends-with-a-question)); only a job that ran out of memory or time, or whose output was too big, not plain files or not cleared, fails before its question is read. When it left no question, made at least one commit on the branch and wrote `PR.md`, the command writes the commits as a git bundle to `<bundle>`, prints `bundle <bundle>`, `pull request text:` and the text, and exits with 0. Check the bundle with `intakt:hand-back:check` before you trust it ([Checking what a build hands back](#checking-what-a-build-hands-back)). Otherwise (it accepted neither a valid question nor a complete change) it prints the end of the build's log and the reason (no commit, which is also what you see when the job could not prepare the copy of the branch, so check that the copy exists and holds the branch; no pull request text, out of memory, out of time after an hour, an output too big or not plain files, or files the builder put in the output folder itself that the job could not remove), writes no bundle and exits with 1. A second build of the same branch of the same project is refused while one runs.

<a id="a-build-that-ends-with-a-question"></a>When the builder ended with a question instead (the file `QUESTION.json`, see [What a builder is told](#what-a-builder-is-told)), the command prints `question: <the question>`, one `choice: <choice>` line per choice and `recommendation: <the recommended choice>`, writes no bundle and exits with 0, also when the builder made commits or wrote `PR.md` as well. In these texts, a line break or another control character, a format character (such as a zero-width space), a line or paragraph separator, a space other than the plain one, an unassigned or private-use code point and a character Unicode marks as default-ignorable (such as U+034F, a variation selector or a Hangul filler) is printed as its code point (a line break as `\u{A}`, a tab as `\u{9}`, U+034F as `\u{34F}`), and a backslash as `\\`. So each text stays on its own line, and two choices that differ only in such a character print differently. Letters that only look alike (a Latin and a Cyrillic "a", for example) are printed as they are. A `QUESTION.json` the branch already held when the build started counts only when the builder changed the file's bytes as they were checked out (the job compares a SHA-256 digest of the file's bytes taken before and after the session, which no git setting of the clone affects); when the file's bytes cannot be read and digested before or after the session (for example because the file cannot be read), the question does not count and the build's log says why. Keys other than these three are ignored. Intakt checks the question first: it must be a JSON object of at most 8192 bytes, with at most 7 arrays or objects nested in one another counting the question object itself (also under a key that is otherwise ignored; a deeper one refuses the question with `question refused: the question is not a JSON object`), with a non-empty `question` text, a non-empty list (a JSON array, not an object) of non-empty `choices` texts, no two of them the same once surrounding spaces are removed, and a `recommendation` that is one of the choices. A question that breaks this rule is refused: the command prints the end of the build's log, which then ends with `question refused: <the broken rule>` (for example `question refused: the recommendation is not one of the choices`), and `failed: the build ended with a question that breaks the question rule`, and exits with 1. In `intakt:build:task` a build that ends with a question fails the build job step with `the build ended with a question instead of a change`; parking the task and posting the question come later.

A build session gets at most 100 turns and 3000 seconds (50 minutes); these are fixed for now. When it reaches either limit, the session ends, but the commits it made before are kept: the build then ends as described above, with the bundle of those commits when the builder also wrote `PR.md` and left no question (a question it left comes first, and then no bundle is written). `build.log` then says `claude cut after 3000 seconds, its commits are kept` when the time ran out. The hour limit above is only a backstop for a job that hangs after the session: a job stopped by it hands back nothing.

Intakt works out how many gates the builder's `bin/check` may run at once: `max(2, processors / build slots)`, and never more than 8. The division rounds down to a whole number: 11 processors and 3 slots give 3. The processors are the online processors of the machine Intakt runs on. The build slots are the number of builds you let run at the same time on that machine: set `intakt.build.slots` under `parameters:` in `config/services.yaml` (a whole number of at least 1; 1 by default) and run `php bin/console cache:clear`. With 12 processors, 1 slot gives 8, 2 slots give 6 and 3 slots give 4; with 2 processors and 3 slots it is still 2. The number is a ceiling: the build job hands it to `bin/check` (as `INTAKT_GATE_SLOTS`) only when you set more than one slot and the number is lower than what `bin/check` picks by itself from the job's CPUs and memory ([Quality gates](../architecture/quality-gates.md)). It never raises that pick, because more gates at once than the job's memory holds could get the build killed. In every other case, and always with 1 slot, the job hands over nothing and `bin/check` picks as it always does (it still reads an `INTAKT_GATE_SLOTS` that the job image itself sets). Today every build job runs with 2 CPUs and 4 GiB of memory, where `bin/check` picks 1 gate at once, and the lowest number Intakt works out is 2. So for now `intakt.build.slots` does not change a build job's check: the job's CPU limit is what keeps builders on one machine apart. The setting starts to matter once build jobs get larger limits. The reason for the setting, measured on builders that ran without such limits: three builders on 12 processors that each ran 8 gates at once loaded the machine so much that one check took 7 to 9 minutes; checks that ran past the builder's 10-minute tool limit went to the background, and the builders spent most of their time waiting on their own checks.

Intakt also gives the build session a tool time limit: one command the builder runs (its `bin/check --fast`, for example) may run up to 1500 seconds (25 minutes) inside its own tool call. This is the time limit of the Claude Code command-line tool's Bash tool, not the session's watchdog (the 3000 seconds above): a command that runs past it does not end the session, but it no longer finishes inside the call that started it (in the measurement above, such commands went to the background). The build job sets both `BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` to that limit in milliseconds when it starts the session, so the builder gets that limit by default for a command and as the most one command may ask for. It exports them as environment variables and also passes them to the command-line tool as command-line settings (`--settings` with both values in its `env`), because Claude Code applies the `env` of the project's own `.claude/settings.json` and `.claude/settings.local.json` after it starts, and command-line settings rank above those files: a project cannot raise the limit that way, so the builder cannot ask for more. To change it, set `intakt.build.tool_time_limit_seconds` under `parameters:` in `config/services.yaml` (a whole number of seconds, at least 1 and below the session's 3000 seconds) and run `php bin/console cache:clear`; any other value, including one that is not a whole number such as `true`, stops a build before its job starts, with a message that names the rule. The reason is the same measurement as above: with three builders on 12 processors one `bin/check --fast` took 7 to 9 minutes, close to or past the tool's 10-minute default. Checks past it went to the background, and the builders then polled for them: over 12 builds they waited 146 minutes on their own checks and 15 minutes on the model.

It needs a Docker engine (see [Job containers](../architecture/job-containers.md)). The container does not get your Claude login yet, so a real build cannot sign in; running one is not possible until that part is built.

## Checking what a build hands back

A build returns its commits as a git bundle, and the text of its pull request. `php bin/console intakt:hand-back:check <repository> <branch> <bundle> <pull-request-text> [--merge-main] [--credential-env=<variable>]...` checks both before anything trusts them. `<repository>` is a bare repository whose `HEAD` names main, such as the project's mirror; `<branch>` is the task's branch; `<pull-request-text>` is a file holding the pull request text (one that cannot be read is an error and exits with 1). The bundle is refused when:

- it is not a git bundle Intakt can read (a missing file, a folder, another file, a broken pack, or a filtered bundle);
- it updates main;
- it names any ref other than the task's branch;
- it builds on a commit that is neither on the task's pushed branch nor on main (also when its header does not list that commit, or it names a commit another branch holds without carrying it);
- it leaves out a commit, folder or file its new commits need (one the repository holds on another branch counts as left out);
- it is not a fast-forward of the pushed branch, or, when the branch was not pushed yet, it does not start on main (any commit of main counts, so main moving while the build ran refuses nothing);
- it holds a merge commit. With `--merge-main` (the task asked for a merge of main), a merge whose other parents are all on main is allowed; a merge of anything else is still refused;
- one of its new commits is malformed, so git itself would not write it (for example a commit with no author);
- a file or file name it adds holds the value of a credential mounted into the build job (see `--credential-env` below), also when a later commit deletes it again;
- the secret scan (`gitleaks` with its built-in rules) finds a secret in anything it adds: a commit and its message, a folder listing or a file, also one a later commit deletes again. Scanner settings, ignore lists and inline allow comments the build committed are ignored, and so are `GITLEAKS_CONFIG` and `GITLEAKS_CONFIG_TOML`.

When the bundle passes, the pull request text is refused when it holds the value of a mounted credential, or when the same secret scan finds a secret in it. The text is refused, not cleaned, so the builder writes it again without the value.

A refusal is sent back to the builder once: it prints `refused, sent back to the builder:` and a fixed reason. When the task's previous hand-back was sent back too, the refusal hands the task over instead and prints `refused, handed over:` and the reason. An accepted hand-back, or a hand-over, starts the count again. Either way the command exits with 1, and the reason never holds a ref name, commit id, secret or other text from the bundle or the pull request text. Each outcome is recorded in the ledger (`hand_back_accepted`, `hand_back_sent_back` or `hand_back_handed_over`, with the repository, the branch and the reason or the accepted head; see `intakt:ledger:events`), and a task is counted by its repository and branch. A ledger that does not take the line is an error and exits with 1. Nothing yet passes the reason to a builder or the hand-over to the maintainer agent; the build lane will. A branch name git does not accept, a branch that is main, and a path that is no such repository are errors and exit with 1 as well. So is a secret scan that cannot run or fails: the bundle is then not accepted, and nothing is recorded, because that is no fault of the build. The scan runs the `gitleaks` that `INTAKT_GITLEAKS` names (`gitleaks` from the path when it is unset or empty), as before a review is posted.

Name each credential that was mounted into the build job with `--credential-env=<variable>`, the environment variable that holds its value (the value itself never goes on the command line, where other users of the machine could see it). Its value is replaced by `[redacted]` in every new commit's message and in its author and committer, which gives that commit a new id like a stripped one. A named variable that is unset or empty is an error and exits with 1.

An accepted bundle loses its attribution: from each new commit (main's own commits are left as they are) the `Co-authored-by:` trailers and the lines that start with `Generated with`, `Generated by` or `Generated-by:` (in any case, after an emoji or other mark) are removed. A message written with Windows line endings keeps them: the collapsed blank line and the final newline use the same ending as the rest of the message. A changed commit, and every new commit after it, gets a new id and no signature, because Intakt signs the commits itself before it pushes. The command prints `accepted <head>`, `base <commit>` (the pushed branch it checked against, or `base none` when the branch was not pushed yet) and `rewritten <count>`, and exits with 0. Nothing is pushed and no ref is changed: the commits are only added to the repository's objects. A refused bundle adds nothing, because its objects are kept apart until every check passed. An accepted bundle also adds its commits as the build wrote them (with attribution or a credential in the message) beside the rewritten ones, in the repository only: no branch names them, so nothing pushes them; that is also so when the bundle passes and only the pull request text is refused.

## Pushing an accepted build

Intakt pushes an accepted build's branch itself: [`intakt:build:task`](#building-one-task) does it as its last step; the build lane that will call it is not built yet. The push signs every new commit with Intakt's own SSH key (the file `/app/var/data/keys/signing_key`, on the volume you mount at `/app/var/data`, which `ssh-keygen` from OpenSSH reads; a build never sees it; it must be an ed25519 key, any other type stops the push) and checks that every commit of the branch carries a signature of that key alone, so a commit signed by another key, or not signed, stops the push. Before anything is pushed, main is merged into the branch in the repository's object store only; a real conflict pushes nothing. `intakt:build:task` records the push as failed with the number of conflicting files (never their names, which the builder chose) and ends the run; it does not send the branch back to the builder yet. The push is never forced: a remote branch that is not where the build was checked is refused. Intakt reads the branch on the remote every time, also for a build whose push is already in the ledger: when the branch has moved since (a later build was pushed, someone else moved the branch, or it is gone), that earlier build is refused, nothing is written to its pull request and no new ledger entry is made, so a late retry of an earlier build never replaces the title and text of the build that followed it. Before anything is pushed, Intakt asks GitHub for every open pull request of the branch, whatever branch it targets: when any of them was opened by someone other than Intakt's own GitHub App (a person, the earlier loop or another App), when GitHub does not name its author, or when its author cannot be checked against the App, the push stops with an error, nothing is pushed and no ledger entry is made, so Intakt does not move the head of a pull request that someone else had open when it asked. This is not a full guarantee, because GitHub cannot tie this question to the push: a pull request someone else opens of the branch after the question and before the push does have its head moved by the push; Intakt then asks again before it writes to GitHub, stops with an error and leaves that pull request's title and text alone. An open pull request that GitHub lists without its branch name, or with an empty one, stops the push the same way. A project without a `github` entry in its watch section stops at this point too, and so does a branch with 100 or more open pull requests, because GitHub's answer then may not list them all. A rate limit on that question stops the push the same way, and it can be tried again after the reset. Intakt then opens the pull request as the GitHub App with the builder's title and text, or updates its own open one of that branch to main (asking GitHub the same question again just before), and refuses text that trips the secret scan. Its own pull request of the branch to another branch is never retargeted: Intakt opens a new one to main instead, and stops with an error when GitHub lists its own pull request without the branch it targets. A rework that corrects only the title or the text and keeps the commits updates the pull request too: with `change_opened` the ledger keeps a digest of the text (never the text itself), and the pull request is neither looked up nor written again only when the commits and the text are the ones last recorded and no later write to GitHub was started. Before Intakt writes to GitHub it notes that in the ledger (`change_intended`), so a title or text that reached GitHub while its own record failed is never taken for the one recorded before it: the next push sends its text again. The phases are written to the ledger (`push_intended` before the push, `branch_pushed` after it, `change_intended` before the pull request is written, `change_opened` after it), so a crash neither pushes twice nor opens a second pull request. When the remote refuses the push (for example a local git forge repository that has the task branch checked out), the ledger gets `push_refused` with the reason (`the remote refused the push of <branch> (git push exited with <n>)`, never git's own message, which may name the remote's address), no pull request is written, and the next push of the same build tries again. A `git` call of the push may run for 10 minutes and an `ssh-keygen` call for one; a call that runs longer is stopped, and a call that is stopped, killed or cannot start ends the push with a reason that names the program and never the remote's address or the key's file (`The branch was not pushed: git push timed out after 600 seconds`). Intakt does not try such a call again on its own: the next push reads the branch on the remote first and pushes only when the stopped push did not arrive. GitHub does not show these commits as "Verified": GitHub only trusts a signing key registered on a user account whose email is the commit's committer, and the commits keep the builder as committer. Git itself verifies them against the public key of Intakt's signing key.

## Listing the protected paths a head touches

The files a change may only touch with an approval (a project's checks, its CI setup, its agents' instructions) are your list, kept in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names), never in the project's repository, so a change can never edit the list that judges it. Give each project a `protected_paths` list and run `php bin/console cache:clear`:

```yaml
projects:
    alpha:
        protected_paths: [bin/check, config/gates/, .github, AGENTS.md]
```

An entry names a file or a folder from the repository's root, and protects that file, or everything in that folder, at any depth; a trailing `/` changes nothing. Letters must match exactly, also in case, so `bin/check` does not protect `bin/checker` or `BIN/check`. An entry that starts with `/`, has an empty, `.` or `..` part, or is not text stops Intakt from starting and names the entry. `.gitmodules` at the root and every submodule are always protected, also without an entry; a project without a list protects only those.

`php bin/console intakt:protected:list <project> <head>` lists the protected paths the head (a full commit id) touches, read from the project's mirror (run `intakt:mirror:update` first), where main is the commit the branch the mirror's `HEAD` names points at when the check starts (a mirror update during the check does not change it). It reads the whole change from where the head left main to the head, and each commit the head has that main lacks, also those a merge brought in from another branch, so a protected file changed and changed back, or reverted or deleted by a merge made by hand, is still listed. What a merge of main brings in is main's own and is not listed: a file a commit leaves exactly as the current main has it is never listed for that commit, while a merge that sets a file back to an older main's version is. It prints `protected <path>` for each path, then `touches protected paths: yes` or `no`, and exits with 0. When it cannot read the change (no mirror, a mirror whose `HEAD` names no branch or a branch without a commit, a commit the mirror does not hold, an id that names an annotated tag, a shallow mirror, a missing object), it prints `unreadable` and the reason, and the head counts as touching protected paths. A head that is not a full commit id, such as a branch name, and a project name that breaks the rule above, are refused with exit 1. Holding a protected head for your approval is not built yet.

## The watchdog's rules for main

Intakt has the rules its watchdog will use to judge each new commit on main, and it can read main's commits and check their signatures. You can run the check by hand with `intakt:watchdog:check` (below), or with `intakt:watchdog:guard`, which also halts the project and gives you a card for each violation (see [Halting the project](#halting-the-project-and-clearing-your-card)); nothing runs either on its own yet. A merge Intakt recorded passes before any signature is looked at, and so do the commits that merge brought to main, also when main simply moved forward to the merged branch so that its commits sit on main one by one. A commit main already had before that merge is not covered by it. Any other commit passes only when it is signed with a key you registered. Owner keys are SSH public keys (one `<type> <base64>` line each, as in a `.pub` file; an Ed25519, RSA or ECDSA key, also one on a security key; a key that is cut short, of another type, an RSA key shorter than 1024 bits or, for ECDSA, not an uncompressed point on its curve is refused), and a signature counts only as an SSH signature that `ssh-keygen` verifies against those keys; a PGP signature, or a check that fails or times out, counts as a key you did not register. A commit without a signature, a commit signed with a key you did not register, and a rewrite of main's history (a force push) are violations. A recorded merge names its head and base as full commit ids; an abbreviated id or a branch name is refused. Main is read only from the repository itself: the top folder of a checkout, or the folder of a bare repository. A plain folder inside a checkout (not a checkout of its own, such as a linked work tree), a path that is a file, a shallow clone (one made with `--depth`, which lacks older commits) and a repository with a `.git/info/attributes` file are refused as unreadable, never judged clean or rewritten. The rules are in [Watchdog over main](../architecture/watchdog.md).

`php bin/console intakt:watchdog:check <repository> <last-seen-head> [--recorded-merge=<base>..<head> ...] [--owner-key=<key> ...]` checks the commits on the repository's `main` branch after `<last-seen-head>` (a full commit id). `--recorded-merge` names one merge Intakt recorded, its base and head as full commit ids with two dots between them, base first; it is optional and you can give it more than once. `--owner-key` is one of your SSH public keys (`<type> <base64>`, in quotes because of the space); it is optional and you can give it more than once. Without it, every signed commit counts as signed with a key you did not register. The command prints `main is clean` and exits with 0, or prints `violation <commit> <reason>` for each violating commit, oldest first (`unsigned`, `unknown_key` or `history_rewritten`), and exits with 1. When main cannot be read it prints the reason and exits with 1, never `main is clean`. A last seen head, recorded merge or owner key that breaks the rules above, an option without its value and a missing argument are refused with exit 2; a refused owner key is named by its position, never printed, and a refused run is not logged with its command line. A commit id must have the full length of the repository's ids (40 characters, or 64 in a SHA-256 repository), so a SHA-256 id cut to 40 characters is refused too. Control characters in a reason (a line break, or a Unicode one such as a next line or a direction override) are printed escaped.

### Halting the project and clearing your card

`php bin/console intakt:watchdog:guard <project> <repository> <last-seen-head> [--recorded-merge=<base>..<head> ...] [--owner-key=<key> ...]` checks main exactly like `intakt:watchdog:check`. Each violation then halts the project `<project>` (the name your card shows, such as `acme/shop`) with a card for you, kept in Intakt's ledger. The card names the commit and the reason (`unsigned`, `unknown_key` or `history_rewritten`). While any card stands, the decision that a step or a merge would ask answers `halted`, for every project: a start does not name its project yet, so one card halts every project until it does. No step or merge asks that decision yet (only `intakt:budget:replay` does, see [Cooldowns, pauses and outage notices](running.md#cooldowns-pauses-and-outage-notices)), so today a card blocks no live work on its own. The command prints each card of the project that still stands, also older ones, as `card <id> halts <project>: commit <commit> <reason>, raised <moment>`, and exits with 1. Without one it prints `<project> is not halted: no owner card stands` and exits with 0. A violation that already has a card gets no second one, also after you cleared it, since you already checked that commit. A rewrite is told apart by what replaced main too: a second force push over the same commit, to another commit, gets a new card, and so does a new commit on the rewritten main while you still give the old last seen head. When main moves while the command reads it, the command reads it again at the new head, so the card names what main holds now; when main moves during each of 3 reads, or main cannot be read, or the card cannot be recorded, the command prints the reason and exits with 1, never "not halted". An empty project name, and everything the check refuses, exits with 2.

Only you can clear a card, after you have checked its commit. Run `php bin/console intakt:watchdog:clear <card-id>`: it asks for your owner token, the `MCP_OWNER_TOKEN` your owner MCP endpoint uses, without showing what you type. A terminal that cannot hide what you type is refused instead of asking visibly, and so is an input that ends before you answer. With the right token it prints `card <id> cleared`, then the cards of that project that still stand, or `<project> is not halted`. Any other answer, or an install with no owner token set up, is refused with `Only the owner clears a halt` and exit 1, and the card stands. A card that is not standing (cleared already, or an unknown id) is refused too, and so is a second clear of the same card that runs while the first is still writing, so a card is cleared once. The token is asked, never given on the command line, so it does not show in the process list or your shell history. Clearing adds a line to the ledger; the card's own line stays.

## Scanning a workflow file for CI risk

A pull request runs the workflow of its own branch on your runners, so a change to a GitHub Actions workflow can run before anyone reviewed it. `php bin/console intakt:forge:workflow-risk <file>` reads one workflow file and lists everything in it beyond a GitHub-hosted runner with a read-only token and no secrets, one line each: `line <n>: <kind>: <what it found>`, where the kind is:

- `runner`: a job runs on a label that is not one of GitHub's standard hosted labels (such as `ubuntu-latest`, `ubuntu-24.04`, `windows-latest` or `macos-15`), or picks its runner by group;
- `permissions`: the token may write (a scope set to `write`, or `write-all`), or a job gets no `permissions` from itself or the workflow, so the repository's default applies, which may write;
- `secret`: the file reads a repository secret (`secrets.<NAME>` in any value, in any case, also inside a `|` or `>` block, or `secrets:` passed to another workflow); the job's own `secrets.GITHUB_TOKEN` is fine;
- `trigger`: an event other than `push`, `pull_request`, `workflow_dispatch`, `schedule` and `merge_group`, such as `pull_request_target`, `workflow_run` or `issue_comment`;
- `unreadable`: a form the scan does not read, such as an anchor or alias (`&name`, `*name`), a tag, a value over several lines that is not a `|` or `>` block, a block with an indentation number or a line indented less than its first line, a nested flow value (`[[...]]`, or `[...]` holding `${{ }}`), an escape in a double-quoted value, a key that appears twice, a tab in the indentation, a second document, text that is not UTF-8, a job that calls another workflow (`uses:`), a job without `runs-on`, or a workflow without `on` or `jobs`. A key the scan looks for by name (`on`, `jobs`, `permissions`, `runs-on`, `uses`, `secrets`) written in another case, such as `Permissions:` or `RUNS-ON:`, is `unreadable` on its line (each such spelling on its own line), with a detail that names the key and the spelling the scan expects: the scan does not guess whether GitHub reads it. A `runs-on` taken from an expression such as `${{ vars.CI_RUNS_ON }}` or `${{ matrix.os }}` is `unreadable` too, also as the `group` or `labels` of a runner picked by group: the scan never reads a variable's value, so it counts even while the variable is unset, because its value can change without a commit.

It then prints `risky: <count> findings` and exits with 1, or prints `no risk: hosted runners, a read-only token, no secrets` and exits with 0. A file it cannot open is refused with exit 2. This command reads only the file you name; `intakt:forge:ci-scan` (below) reads all the workflows of a change.

The files a workflow runs are part of the CI definition, so changing one is a CI change. A changed file counts when any workflow's text names its file name (or a longer trailing part of its path) as a whole word, in any case (accented letters too), whatever folder the workflow runs it from; so do everything under `.github/`, every Dockerfile, everything in the folder of a local action (`uses: ./tools/build`, folder in any case), and every file when a workflow cannot be read or is in a form the strict line reader does not read (such as an escaped key or value, which could spell a file name the text does not show). Files a workflow runs without naming them, such as Makefile targets or Composer scripts, are not found this way; your approval of the push decides those. `php bin/console intakt:forge:ci-paths <path>... --workflow=<file>` (repeat `--workflow` for each workflow) prints `ci <path>` for each changed path that counts, then `CI change: yes` or `no`, and exits with 0.

`php bin/console intakt:forge:ci-scan <repository> <head>` puts both together for a whole change. `<repository>` is a git directory: a project's bare mirror, where main is the branch its `HEAD` names (the remote's default branch), or the `.git` folder of a clone, where main is the branch checked out; `<head>` is a branch or commit in it. It reads the `.yml` and `.yaml` files directly in `.github/workflows/` of the head, of main and of the two merged (as git merges them, without a checkout), scans each, and prints each finding as `<head|main|merged> <file> line <n>: <kind>: <what it found>`. A workflow it cannot read counts as `unreadable` (at line 0): a symbolic link or submodule in that folder, a `.github` or `.github/workflows` that is a link, a submodule or a file instead of a folder, a failed git read, and the merged workflows when the head does not merge with main without a conflict. Then it prints `ci <path>` for each changed path that is part of the CI definition (every file where the head or the merge differs from main, so a file main changed after the head branched off counts too; with a conflict every such file counts), and `risky: yes|no`, `CI change: yes|no` and `push waits for the owner: yes|no`. A change waits for you when it is a CI change and any workflow on any side is risky; it then exits with 1, otherwise with 0. A repository whose `HEAD` names no branch, a head that names no commit, or a merge git cannot try (such as unrelated histories), is refused with exit 2. `intakt:forge:push-approval` (below) holds a push on this answer.

## Holding a risky CI change for your approval

A risky CI change stays local until you approve its push. `php bin/console intakt:forge:push-approval <repository> <head> --project=<project> --issue=<n>` takes the same `<repository>` and `<head>` as `intakt:forge:ci-scan`, resolves the head to one commit, scans it the same way and prints the findings and `ci <path>` lines. Then it prints one decision:

- `push: free (no risky CI change)`, exit 0: the change may be pushed without you, and GitHub is not asked.
- `push: approved by the owner for <sha>`, exit 0: the issue holds your comment `approve <sha>` for exactly this commit, posted after Intakt's request for it, and the change can still be shown in full.
- `push: held, the owner was asked on issue #<n> to approve <sha>`, exit 1: it posted one comment on the task's issue (`<n>`, in the GitHub repository of the project's `watch` section) that holds what the scan found, the complete diff from where the head left main to the head (every file; an image, a PNG, JPEG or GIF that is not executable, is named by its size at the base and at the head and by its two full blob ids on its `index` line instead of its bytes, which your approval of the full commit id pins), and the line to reply with.
- `push: held, still waiting for the owner's approve <sha> on issue #<n>`, exit 1: that comment is already there, so nothing is posted again.
- `push: held, the change cannot be shown in full and goes back to be split: <reason>`, exit 1: nothing is posted when the comment would be longer than 65536 characters (GitHub's limit), when the diff is not UTF-8 text or holds a NUL byte even with its images named (for example a text file with a byte that is not UTF-8, or any other binary file, such as a script with a NUL byte, which you would otherwise approve unseen), or when the secret scan finds a credential in it. A change is never shown to you as a file list or cut.
- `push: held, nothing was decided: <reason>`, exit 2: the head names no commit, the repository's `HEAD` names no branch, the head and main do not have exactly one merge base, GitHub could not be read or written, or another run is asking about the same head at that moment.

Only your own account counts. Set your GitHub login in `GITHUB_OWNER_LOGIN`; while it is empty, no approval counts and a risky change stays held. Your approval is a comment whose whole text is `approve ` followed by the full commit id (40 characters, or 64 in a SHA-256 repository); a short id does not count, since a builder can make a commit whose short id matches. An approval posted before Intakt's request for that commit does not count either, since you approve the diff the request shows: reply after the request. When someone edits Intakt's request, it no longer counts: Intakt posts the request again, and only an approval after the new one counts. A comment by another account or an App (also an App that posts in your name with your permission), a comment with other text around the line, and a comment that was edited (an admin or an App can edit your comment) do not count. Each new commit needs a new approval. Approving the push does not approve the merge: you are asked again before the change merges. Without the settings of [Intakt's GitHub App](README.md#intakts-github-app), a held change stops with the settings error and exit 1.
