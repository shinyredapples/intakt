# Providers and API keys

Intakt reaches models through five providers: Anthropic, OpenAI, any endpoint that speaks the OpenAI API, a Claude subscription and a Codex subscription. This page tells how to give Intakt their keys or logins, how to use more than one account of a provider, and how a project picks its models through capability tiers and its mode.

## Configuring providers and API keys

Intakt knows five providers: `anthropic`, `openai`, `openai_compatible` (any endpoint that speaks the OpenAI API), `claude_code` (a reviewer or the judge on a Claude subscription, see below) and `codex` (a reviewer on a Codex subscription, which uses a login file instead of a variable, see [A Codex subscription login](#a-codex-subscription-login)). Each of the first four reads its key from Symfony secrets (`php bin/console secrets:set ANTHROPIC_API_KEY`) or from the environment (`.env.local` or the real environment), never from a plain committed file; a non-empty environment value wins over the secret:

| Provider | Variables it needs |
|---|---|
| `anthropic` | `ANTHROPIC_API_KEY` |
| `openai` | `OPENAI_API_KEY` |
| `openai_compatible` | `OPENAI_COMPATIBLE_BASE_URL` and `OPENAI_COMPATIBLE_API_KEY` (for Hugging Face, see [Running the demo on a Hugging Face token](demo.md#running-the-demo-on-a-hugging-face-token)) |
| `claude_code` | `CLAUDE_CODE_OAUTH_TOKEN` |

A provider whose variables are not all set (empty counts as not set, and so does a secret Intakt cannot decrypt when the container is built), neither in the environment nor in the secrets, is switched off, and Intakt still starts. A provider with several accounts (see below) stays on as long as one of its accounts is fully set. `php bin/console intakt:ai:tiers` and `php bin/console intakt:vendor:probe` print a line on standard error for every switched-off provider, and the demo's first start prints them once in its log, not again on a restart with the same volume (when printing them fails, the start goes on with a one-line note and the next start tries again; other commands print none), for example `Provider "openai" is disabled: set OPENAI_API_KEY to enable it.` The same text is in the container parameter `intakt.ai.disabled_providers`. `php bin/console debug:config ai` lists the providers that are on, except `claude_code`, which is not part of the AI Bundle's configuration: `php bin/console debug:container intakt.ai.platform.claude_code` finds that service only when it is on. Whether a key is set is decided when the container is built, so after you add or remove a key, run `php bin/console cache:clear`. Without an enabled OpenAI account, project memory has no embedding model: reviews go on without memory, and the log says so once per start at `info` level, without a stack trace (the default log level, `warning`, hides it). Resolved findings are then not remembered either: each review round that resolves findings logs the same `info` line once, and nothing is retried or kept as a failed message.

### More than one account of a provider

A provider can have several accounts, for example a personal and a team API key. List them under `accounts:` in `config/intakt.yaml`, in the order Intakt tries them (see `config/intakt.example.yaml`):

```yaml
accounts:
    anthropic: [default, team]
```

The account `default` reads the variables in the table above. Any other account reads the same variables with its name in capitals appended: `team` reads `ANTHROPIC_API_KEY_TEAM` (for `openai_compatible`, `OPENAI_COMPATIBLE_BASE_URL_TEAM` and `OPENAI_COMPATIBLE_API_KEY_TEAM`; for `claude_code`, `CLAUDE_CODE_OAUTH_TOKEN_TEAM`, with its own folder `var/claude-code-team/`). A name starts with a lowercase letter and holds only lowercase letters, digits and underscores, and is listed once; anything else stops Intakt from starting. A provider you do not list has its `default` account only. An account whose variables are not all set is switched off with a line such as `Account "team" of provider "anthropic" is disabled: set ANTHROPIC_API_KEY_TEAM to enable it.`; the provider is switched off only when none of its accounts is set.

Intakt can tell the kind of a key from its form: `sk-ant-` is an Anthropic key, any other `sk-` an OpenAI key and `hf_` a Hugging Face token; any other form, including an Anthropic key cut off too short, is refused without echoing it, and a key that is shown as configured shows at most its last four characters. Intakt can also check a key with one small call to its provider (a one-word question with an answer of at most a few words: one token, or 16 for OpenAI, the least it accepts): a key the provider turns down is refused, and a key whose provider could not be reached is not kept as checked. The call and its refusals never print the key. Typing a key in the browser and keeping it are planned and not built yet: keep using the variables above.

When a provider limits a call (a rate limit or quota) or fails it with a temporary error, the account that made the call **cools down** until the reset time the provider sent, at most one day. When the provider sent none, the account cools down for one minute. The one exception is a subscription account (`claude_code` or `codex`) whose plan limit came without a reset time, as with a Codex plan whose usage limit is reached: it cools down until the latest reset of a usage window Intakt last measured as used up (100 percent or more) for that account, and for one minute when no such reading has a reset still ahead or the readings cannot be read. Today nothing outside the demo's replay records these readings, so on a real install that cooldown is one minute too. Every reviewer on that account waits out the same cooldown, also in other workers on this computer, and the reviewer starts again at once on the next free account of the same provider: it stays the same reviewer, so no catch-up review is owed. Only when no account of the provider can serve the model right now (each one either cooling down from its own limit or with the router provider the model names paused on it) does the reviewer wait, until the first account is free again; this holds for a temporary error too, so such a reviewer is not marked failed. A temporary error or a limit that arrives after a reviewer's streamed answer has started (its first text, thinking or tool call, not only the token counts a provider sends first) is different: the answer cannot be resumed and the account is cooling down, so the reviewer is not asked again and ends `blocked` with the finding `incomplete-stream` and the reason `The provider failed after the answer had started streaming.`, and the tokens the call spent are counted once. Every `incomplete-stream` finding carries evidence for finding out why: the provider and model of the call, what cut it (`platform` when the provider's stream ended early, `provider-failure-mid-stream` for such an error, `unfinished-answer` when the stream ended normally without a whole verdict), how many pieces the stream had sent and the last five of them (the first 80 characters of each piece of text). That failed answer still cools its account down, like any other account error: a limit, a rejected key or a temporary error that arrives while the answer is being read, before or after it has started, keeps the next review off that account (a rejected key cools it for a minute and counts as a rejection). A failed account is logged (`Account claude_code.default failed.`) with its name and the kind of error, never with the provider's error text, which can repeat a key. Only a limit, a rejected key or login, or a temporary error of the provider counts as an account error. An answer Intakt could not read (for example a reviewer's answer without one readable verdict) is not one: the account answered, so it is not logged as failed, does not cool down and takes the next call. Any other failure that stops a call from being sent is logged as `Account claude_code.default could not send the call.`, with the same redaction, and does not cool the account down. Each cooldown is recorded in the ledger as an `account_cooled_down` event with the account (`anthropic.team`) and its end, and each usage row names the account the call ran on. A rejected key or login is an account error only you can fix, so it is also reported to you once, as an `account_error_reported` event in the ledger with the account and the moment: the same error is not reported again while it lasts, however often the account is tried after its cooldown. Once the account answers a call sent after that report, its next error is reported again; an answer to a call sent before the report does not count. Cooldowns and these reports are kept in Symfony's cache, so `php bin/console cache:clear` ends them (an account error that lasts is then reported once more).

A key the provider rejects (revoked or wrong) puts its account into cooldown for a minute like a limit, so the call moves on to the next account of the provider; the reviewer ends `failed` when every account of the provider rejected its key (now or in a cooldown still running, also for a review that starts during that cooldown, without sending a call), and waits when another account is only cooling down from a limit.

**Substitutes.** A tier can list `substitutes` (a provider and a model each, see the commented line in `config/intakt.example.yaml`). Only when the tier's provider cannot answer (every account is cooling down or has paused the router provider the model names, every key was rejected, or the provider is disabled because its settings are not set) does a review go to the first substitute that can, in the order you listed. Only the first model you list on a provider counts for it: a substitute on the tier's own provider, or a second one on a provider listed before, is skipped. A tier without `substitutes` never leaves its provider: its reviewers wait as described above, and a tier on a disabled provider is refused. When the provider and every substitute are out, the review stops with a reason that names each provider and why it is out (disabled, keys rejected, or the wait in seconds). A call that failed (a refused request) never goes to a substitute. A review that went to a substitute stays on it to the end, counts against that provider's limit on parallel calls, and its approval counts only when that provider can read the project's checkout. A reviewer whose provider is not listed under `accounts:` (so it has its default account only) ends `failed` when that key is rejected and the tier has no substitutes. Because another provider reviewed, the ledger gets a `catch_up_owed` event with the reviewer's role, tier, the substitute and the substitute's model (the first substitute of the tier on that provider), and the reviewer's row keeps the substitute; the dashboard then names the reviewer by the substitute's model when the event names one, also in a row an open review page already shows, so the model and the substitute name the same provider (an event without a model leaves the model the reviewer started on); a move to another account of the same provider owes nothing. The catch-up review itself is planned. When every provider of the tier is out, the substitutes too, the reviewer ends `blocked` with the reason (`Every provider of the tier is out: anthropic disabled, openai keys rejected, openai_compatible for 60 s.`: a wait in seconds, or why no wait helps), shown in the `reviewer_blocked` event, and the round completes without waiting.

**Output limit.** Each tier has a `max_output` (a whole number of at least 1, the most tokens one answer may have), so a long verdict is not cut off by a model's or a provider's own default. When you leave it out, `strong` gets 16000, `standard` 8000 and `light` 4000; a substitute of a tier uses the tier's limit. Intakt sends it with every call of a reviewer or the judge on that tier, to Anthropic, OpenAI and OpenAI-compatible providers; the Claude Code and Codex subscription logins take no such limit, so none is sent there. When a provider stops a reviewer's answer at the limit, Intakt runs that reviewer once more with twice the limit (twice the default above when the tier sets none); when the answer is stopped again, the reviewer ends `failed`, and its `reviewer_failed` event names `MaxOutputTokensException`. Each of the two calls has its own usage row. The judge is not run again.

### A reviewer on a Claude subscription

Map a tier to `provider: claude_code` and a Claude Code model name (`opus`, `sonnet` or `haiku`) to run that reviewer through the `claude` command-line tool, which must be installed where Intakt runs. Create the login token with `claude setup-token` and store it as `CLAUDE_CODE_OAUTH_TOKEN`. The tool gets only that token, your `PATH` and its own folder `var/claude-code/` (where it runs and keeps its state); every other variable of Intakt's environment reaches it empty, so neither an API key nor any other secret does, and the subscription is used. It is given none of its own tools, only the read-only reading tools of the review's own server (file, directory and search), reached with a credential made for that one review; it can read the files of the head under review through those tools, and nothing of the checkout or of Intakt's files otherwise. Its `approve` counts like any other reviewer's when the tool's own report of that call shows the review's server connected and at least one read through it (one of its reading tools, on that server) that the server answered without an error. A call whose report does not show that server connected, or that read nothing through it (no tool call, only calls the server refused or never answered, or calls to another server) or that was started without the server (a review without a round) counts as not having read the change: when it answers `approve`, or `changes` with only P3 findings (which can count as approval, see [Reviewing a branch](README.md#reviewing-a-branch)), its verdict becomes `blocked` with the reason that it approved a change it could not read. When no credential can be made for the server (an empty `APP_SECRET`), the tool is not started and the reviewer is `blocked` for want of tools. Any other `changes` verdict from it stays `changes`. Intakt gives the tool the verdict's JSON schema, so the tool holds its answer to it, and reads the answer the tool returns held to that schema as the verdict (one that is not a verdict is refused like any unreadable answer, below). When the tool returns no such answer, Intakt reads its text instead: a few sentences and then one fenced `json` block holding the verdict; Intakt reads that block as the verdict when it is the only `json` fence opening anywhere in the answer (three or more backticks or tildes, then `json`; one that is indented, quoted, in a list or only mentioned in the prose counts too), it opens at the start of a line with exactly three backticks and `json`, it closes on a line of exactly three backticks, and it does not sit inside another fenced block. A block stays open until a fence line with the same prefix closes it (up to three spaces of indentation count as none): a quoted, listed or deeper indented fence line inside a block is content and closes nothing. A closed block of another language beside it, such as `php`, is fine. A bare JSON answer works too. An ambiguous answer is refused rather than guessed: one with no `json` block, with two or more openings, with the one block in another form or nested in another block, or with a block that is not a verdict is refused, asked for once more, and when the second answer cannot be read either, the reviewer fails because its answer could not be read as a verdict. Intakt reads the environment again for every call, so a variable added while Intakt runs also reaches the tool empty. Its usage is recorded in the ledger like any other call. If its output ends before the final result (the tool stopped, was killed or ran past its 300-second limit), the reviewer's verdict is `blocked` with that reason, and its usage is recorded once as unsettled.

The judge can run on the subscription too: map the `light` tier to `provider: claude_code` (for example `model: haiku`). The judge's call goes through the same tool with the same limits (no tools of its own, and no review server, since the judge reads no files). Intakt gives the tool the judgement's JSON schema and reads the marks from the answer the tool returns held to it. An answer that is not a judgement, or that does not mark each finding exactly once, is not used: every P1 and P2 finding stays on the act list and no P3 finding is added, as for any judge whose answer cannot be read. Its usage is recorded in the ledger like any other call.

Which plans may be used this way is the vendor's decision, not Intakt's. Anthropic's [Claude Code legal and compliance page](https://code.claude.com/docs/en/legal-and-compliance) says that Free, Pro and Max plans fall under the Consumer Terms of Service and that Team and Enterprise plans fall under the Commercial Terms of Service, that the subscription login is meant for ordinary use of Claude Code by the plan's own purchaser, and that routing requests through Free, Pro or Max credentials on behalf of other users is not permitted. Use your own plan for your own reviews, read those terms for your case, and use an API key (`anthropic`) when in doubt. Intakt does not check your plan.

To decrypt the secrets, Intakt reads `SYMFONY_DECRYPTION_SECRET` the way Symfony does: a base64 value, in the standard or the URL-safe alphabet (`-` and `_`). When it is not set, or decodes to nothing, the vault's own private key file in `config/secrets/<environment>/` is used. A secret that cannot be decrypted (a wrong key, or no key at all) counts as not set, so its provider is switched off and named on standard error as above. A key kept from the browser stands in for such a secret only when decrypting it fails quietly, not when the decryption key is of the wrong length or there is no key at all (see the kept key below, under the review bench). When the vault fails while Intakt builds its configuration (for example a decryption key of the wrong length), standard error shows `Another env loader failed, so its variable counts as set and the kept key does not stand in for it.`: the vault's variables count as set, so a kept key does not replace them. Repair the vault or its decryption key, then restart the app or clear its cache.

### A Codex subscription login

Codex has no long-lived token, so Intakt keeps each account's login file itself. Log in with the `codex` command-line tool, then copy its `auth.json` (in `~/.codex/`, or in `CODEX_HOME` when you set it) to `var/codex/logins/<account>/auth.json`, for example `var/codex/logins/default/auth.json`; the account name follows the same rule as above. Keep that file readable by Intakt's user only (`chmod 600`). Pin the model and the reasoning effort every call uses in `config/intakt.yaml`, both required once the section is there:

```yaml
codex: { model: gpt-6.2-sol, effort: high }
```

The effort is one of `minimal`, `low`, `medium`, `high` and `xhigh`; anything else stops Intakt from starting. Before each call Intakt refreshes the login when it was last refreshed seven days ago or more (the `codex` tool would do so itself after eight), writes the new login back to the same file, and then gives the call a read-only copy in the account's own folder `var/codex/homes/<account>/`, which is also the tool's home and working folder. Whatever the call writes there never reaches the kept login, and the next call gets a fresh copy. Like the Claude tool, it gets your `PATH`, its home folder (as `HOME` and `CODEX_HOME`) and, in a review with a round, the review server's credential (`INTAKT_REVIEW_SERVER_BEARER`); every other variable of Intakt's environment reaches it empty. A login that cannot be read or refreshed stops the call with a message saying so.

Every call runs the tool with its shell, web search, browsers, computer use, apps, plugins, other agents, image tools and hooks switched off, in its read-only sandbox, without a saved session and without reading a settings or rules file from its folder. These limits are fixed: neither a project nor a reviewer can lift them. The tool refuses a feature name it does not know, so a `codex` release that renames one makes every call fail with that message instead of leaving the feature on.

`php bin/console intakt:codex:probe <account>` (the account defaults to `default`) makes one such call and prints the account, the pinned model and effort, and the answer; it needs the `codex` tool where Intakt runs.

### A reviewer on a Codex subscription

Once the `codex` section is there, map a tier to `provider: codex` and the model you pinned to run that reviewer through the `codex` tool; a tier or substitute on `codex` that names another model, or one without the `codex` section, stops Intakt from starting, because every Codex call runs on the pinned model. List the accounts under `accounts:` as for the other providers (`codex: [default, team]`); each needs its login file, and an account without one fails its call with a message naming the file. Without the `codex` section Codex is simply left out, with no "disabled" line.

Like the reviewer on a Claude subscription, it reads the change through the review's own server: for that call only, the tool is started with that server as its one MCP server (its own settings, which could name others, are still not read), allowed just its read-only reading tools (file, directory and search) and given a credential made for that one review, which reaches it in its environment, never on its command line. The tool is told to read the files it needs through those tools before it gives a verdict; it reads nothing of the checkout or of Intakt's files otherwise. When the server cannot be started, the call fails instead of going on without it. Its `approve` counts like any other reviewer's when the tool's own report of that call shows at least one completed read through the review's server (one of its reading tools, on that server). A call that read nothing through it (no tool call, only failed ones or ones the server refused, or calls to another server) or that was started without the server (a review without a round) counts as not having read the change: when it answers `approve`, or `changes` with only P3 findings (which can count as approval, see [Reviewing a branch](README.md#reviewing-a-branch)), its verdict becomes `blocked` with the reason that it approved a change it could not read. When no credential can be made for the server (an empty `APP_SECRET`), the tool is not started and the reviewer is `blocked` for want of tools. Any other `changes` stays `changes`. Its answer is read as for the Claude subscription: bare JSON, or prose around exactly one fenced `json` block. Its answer must be a complete run of the tool: an answer that is not a valid verdict, including text that only says a limit was reached, is asked for once more and then fails the reviewer ("the reviewer's answer could not be read as a verdict"), never counts as a limit, and the account is not paused. A run that ends before the tool reported the turn complete is `blocked` (`incomplete-stream`). When the tool itself reports that the plan's usage limit is reached, the account is paused like any limited account (for one minute, because the tool's message gives no reset Intakt reads), and the review waits or moves to another account. When it reports that the plan does not include the model or that the login is lost (it could not be refreshed, or the service refused it), the account is taken out like one whose key was rejected; so is a login whose refresh the sign-in service refuses as unauthorized, before the tool runs. Neither is a failed review or `changes`, and only these reports of the tool count, never the reviewer's own text. Each of these account errors is reported to you once, as described for a rejected key under [Cooldowns, pauses and outage notices](running.md#cooldowns-pauses-and-outage-notices); a usage limit is not reported. Any other run the tool reports as failed fails the reviewer, and so does a run it reports complete without an answer. The use the tool reports (input, cached input and output tokens) is recorded once per review in the ledger, in a usage row that names the account it ran on (`codex.team`), also when a run without an answer fails the reviewer and when the tool reported the turn complete and then exited with an error. A failed run that never reported its turn complete records no use.

### Capability tiers per project

Each project maps three capability tiers (`strong`, `standard`, `light`) to a provider and a model. Copy `config/intakt.example.yaml` to `config/intakt.yaml` (or point `INTAKT_CONFIG` at another file), edit it, and run `php bin/console cache:clear`. Project names are kept exactly as written, dashes included, and a model must be a text value that is valid UTF-8 and not blank (a value made only of whitespace, including Unicode spaces such as a no-break space, counts as blank). A project can also carry a `watch` section (`repository`, `base` and `task`, all required text that is not blank, `github`, the project's `owner/name` on GitHub, which is required for the watch to read pull requests from GitHub, and the optional `eligibility_label`, the issue label that will let Intakt build a task from an issue (a blank value, also one made only of Unicode whitespace such as a no-break space, stops Intakt from starting; nothing reads the label yet); see `config/intakt.example.yaml`): Intakt then reads its open pull requests every minute (run `php bin/console messenger:consume scheduler_watcher` to keep the schedule going) and starts a review round for the head of a pull request once its CI has finished green. The round reviews exactly that commit, read from the local repository named by `repository`, so the commit must be there (fetched); until it is, the start fails and that head alone backs off, as does any head whose CI cannot be read or whose start failed, without holding back the other pull requests: the log gets an error with the cause, the ledger records `head_failed` (the cause, the failures in a row and the next try), and the head is tried again a minute later, then after twice as long each time, but never more than 30 minutes later. A head whose CI Intakt could not read because GitHub's hourly allowance is used up (see [Intakt's GitHub App](README.md#intakts-github-app)) is not failing: it is read again at the reset time GitHub named, with no `head_failed` line, no card and no count toward the hand-over. Only when Intakt cannot save that reset time (a database error) does the head count as failing and back off as described above; when even that back-off cannot be saved, the error is logged, nothing about the head changes, and the next tick tries it again, while the other pull requests go on either way. After four failures in a row the ledger records `head_handed_over` once (the maintainer agent that takes it over is planned); the head is still tried at those waits, so it starts its round once the cause is gone, without a new push. The latest failure of each head is shown as a card at the top of `/reviews`. Such a failure holds every account (a [failure back-off](running.md#cooldowns-pauses-and-outage-notices)) only when no single pull request causes it: GitHub refuses Intakt's credentials, the disk is full, a second pull request fails with the same error within an hour, or the hand-over itself cannot be recorded. One pull request that keeps failing never starts it. A head whose CI is still running starts nothing and is read again a minute later; a head whose CI failed is only recorded; a pull request closed before its CI finished is no longer read, and the ledger records `head_forgotten` for its queued head, which also takes its card off `/reviews`; a head gets one round, however often it is seen, also when two ticks run at once, except that a head that returns after its round was reported stale (the pull request moved to another head and back) gets a fresh round, because the old verdicts no longer count. The ledger records `round_queued` for each round; when the ledger cannot take that line, the round still starts, the tick reports the failure, and a later tick writes the line once. When a pull request gets a new head while an earlier round's verdicts exist, the ledger records `verdicts_stale` for that round once, also when a round was still starting as the head moved, unless the change cannot affect them (for example documentation only); when the ledger cannot take that line, a later tick checks the round again and records it. That check also reads the new head from the local repository: while its commit is not fetched, a head with running or failed CI is still recorded as such, but the check fails and that head alone backs off as described above: it is tried again once its next try has come (a minute later, then after twice as long each time; a head with failed CI is then read and recorded as failed again), and after four failures in a row it is handed over. The `task` text is given to every round of the project. Several projects can map the tiers differently; a tier you leave out is reported as not mapped. A model name the provider's built-in list does not know is added to it, so newer models work too. An invalid file stops Intakt from starting and names the bad key. `php bin/console intakt:ai:tiers` lists every project with the provider and model of each tier; a tier whose provider is switched off (see above) shows the reason instead of a model.

A tier you leave out has no model. Before a review round starts, Intakt checks that the project maps a model to every tier the round needs: each reviewer's tier and the judge's `light` tier. When one is missing, the round is refused before any reviewer starts, with `Project "<name>" maps no model to the "<tier>" tier, which this round needs: map a model to it in the project's tiers and review again.` (`intakt:review` prints it and ends with exit code `1`). So map every tier the project's reviewers and judge use. The check looks only at the mapping, so a tier whose provider is switched off still counts as mapped, even when no other provider stands in for it; such a round starts, and its call fails when it asks the provider.

A project can also carry a `review:` section that sets its review panel (see `config/intakt.example.yaml`): `quorum` is `all`, `majority` or `one-strong-plus-one`, and `reviewers` lists one or more reviewers, each with a `role`, a `tier` (`strong`, `standard`, `light`), a `provider` (`anthropic`, `openai`, `openai_compatible`, `claude_code`, `codex`), a `prompt` and a `budget` (a whole number of at least 1). Every field is required, and the panel comes from the file alone. A reviewer's `provider` must be the provider the project maps that `tier` to under `tiers:`. A panel of any size works, at least one reviewer (an empty list is refused), as long as its policy can be met when every reviewer approves: `one-strong-plus-one` needs at least two reviewers, one of them on the `strong` tier. An unknown policy, tier or provider, a missing, empty or blank field, a budget below 1, an empty reviewer list, reviewers written as a map instead of a list, a provider that differs from the tier's, or a policy the panel can never meet stops Intakt from starting and names the problem. A `projects:` value that is not a map of projects stops Intakt too. A project without a `review:` section has no panel yet.

A `review:` section can also hold `rules`, a list of extra reviewers for bigger or sensitive changes. Each rule has `min_lines` (a whole number of at least 1), `paths` (a list of path patterns) or both, and `reviewers` written like the core ones (the provider again must be the tier's). A rule without `min_lines` and `paths`, rules or paths written as a map instead of a list, or a path pattern that is not text (a number, `true`) or not valid UTF-8 stops Intakt from starting. The quorum policy must be reachable both by the core panel alone and with every rule added, otherwise Intakt does not start either. A rule applies when the change has at least `min_lines` changed lines or touches a path matching one of its patterns; in a pattern `*` stays inside one folder (`src/*` does not match `src/a/b.php`) and `**` crosses folders (`src/**`), any characters included; `/**/` also matches no folder (`src/**/Security/**` matches `src/Security/Door.php`), and a leading `**/` matches the top folder too (`**/Security/**` matches `Security/Door.php`); quote a pattern that starts with `*` (`'**/Security/**'`), since YAML reads a bare leading `*` as a reference. The reviewers of every matching rule join the core panel, which is never reduced, and the project's quorum policy stays. The label `review:full` applies every rule. The panel comes from the configuration alone.

### Reviewer-for-loop mode

A project with `mode: reviewer-for-loop` is one whose pull requests a build loop builds and merges, where Intakt's panel takes the place of the loop's own Claude reviewer. With a `watch` section, Intakt reviews every new head of the project's open pull requests once its CI is green, with the whole panel and judge, as for a live project. Its verdicts are recorded in the ledger with `"mode":"reviewer-for-loop"` and count like a live project's; the dashboard shows them without a mark. Once a round is judged, or its judging has failed for good (after the worker's retries, for example because the judge's tier has no model), Intakt publishes its verdict on that exact head under its GitHub App, and this is the whole contract with the loop:

- a commit status named `intakt/review` on the head: `success` when the panel approves, `failure` when it asks for changes with a finding to act on or when Intakt withdrew its review (see below), `error` when Intakt could not review the head (no quorum and no reviewer asking for changes with a finding on the act list, for example because reviewers failed, or the judging failed for good);
- for a review decision (`success`, or `failure` when the panel asks for changes), first one pull request comment; a withdrawal publishes its `failure` without a comment. The comment is in the shape of the loop's own reviewer comments: the heading `**Review by Intakt** (head <first 12 characters of the head>)`, one line `[P1] file:line: text` (or `[P2]`, `[P3]`) per finding on the act list, and a fenced `json` block `{"verdict":"approve"|"changes","head":"<the full head>","summary":"..."}`, followed only by an invisible marker `<!-- intakt-verdict: <round id> -->`, after the `json` block. An owner ask on a protected head of a pull request [handed to Intakt](running.md#pull-requests-handed-to-intakt) is not part of this comment: each of its parts is a comment of its own. A finding without a line shows only its file, one without a file shows `(no file)`, and line breaks in a finding become spaces. A `<!--` in a finding is written as `&lt;!--`, so it opens no hidden HTML comment that would hide the rest of the comment.

Without a GitHub App, that is with `GITHUB_APP_ID` empty as in the demo, Intakt publishes nothing to GitHub and does not try again; the review page and the MCP tools show the verdict, and Intakt notes this once per start at info level, below the warnings and errors the service output shows.

The status and the comment always tell the same verdict, as the loop reads it: the loop counts an open P1 or P2 as changes, so an approval whose act list still holds a P1 (for example from the reviewer who was outvoted) is published as changes, with `failure` and `"verdict":"changes"`; an approval with only P2 or P3 findings lists them under a `Follow-ups:` line, which the loop reads as an approval with follow-ups. A reviewer that asked for changes only with P3 findings the judge deferred or rejected counts as approving here too, so it is among the approvals the comment counts (`2 of 2 reviewers approve`).

Each finding line is redacted like a review, as a whole and on its own, so a redaction that runs to the end of its text (an unclosed credential header, for example, even one that starts in the file and ends in the text) ends at that line; the heading and the `json` block hold no reviewer text and are not redacted, so a posted comment always ends with its `json` block and the hidden marker after it. Then the comment is scanned with `gitleaks`; if the scan still finds a secret, no comment is posted and the status is `error` with the description "Intakt could not publish its review of this head." A review stored as a replay (see [Recording a review for the demo](demo.md#recording-a-review-for-the-demo)) gets no comment and the status `error` with the description "Intakt does not count a replay as a review of this head.", whatever its reviewers decided. A round of a local branch (not a GitHub pull request address) publishes nothing and logs a warning. When GitHub refuses or cannot be reached, the worker tries the publication again later; before posting the comment it reads the pull request's comments, and when one posted by Intakt's own GitHub App already ends with the round's marker (an earlier attempt posted it; a marker quoted inside a finding of another round's comment does not count) it posts only the status; a comment by anyone else that holds the marker does not count. Only one worker publishes a round at a time: a second one finds the round busy and tries again later. So each round leaves one comment. The App needs write access to commit statuses and to pull requests (`statuses:write` and `pull_requests:write` in `GITHUB_APP_PERMISSIONS` when you check the installation). Apart from this (and the owner ask on a protected head of a pull request [handed to Intakt](running.md#pull-requests-handed-to-intakt)), Intakt writes nothing to the forge in this mode: it never merges, pushes, labels or approves a head, and it posts no review. The loop keeps building, merging and asking you as before. To roll back, switch the loop back to its own Claude reviewer and set the project to `live` (which publishes nothing on the loop's own pull requests; a pull request [handed to Intakt](running.md#pull-requests-handed-to-intakt) still gets its verdict published in a `live` project). The watch reads the open pull requests and their CI from GitHub through the App identity, so it needs the GitHub App settings and a `github` repository in the `watch` section; without it the tick fails for that project with a clear message.

A round can be marked stale after it started, when its head is refused later because it no longer boots. The watcher boots a green head only when its pull request author is trusted (a person with write access, Intakt's own GitHub App or the maintainer); it boots that head again each time the listing names its pull request, and marks the round of a head that now fails to boot while main boots. Another author's head, or one whose trust check fails, is never booted, so its round is never marked stale this way: it is reviewed unbooted, and the ledger records `head_boot_skipped` with the cause `boot_skipped_untrusted_author`. The boot runs the head's `composer install` and `bin/instance` on the host as Intakt's user, not yet in an isolated job container (see above). Its verdicts then stop counting, also while the pull request is still at that head, and Intakt publishes the round again: the status on that head becomes `failure` with the description "Intakt withdrew its review: this head does not boot." and no comment, which replaces an approval already published, also when the mark lands while that approval is being posted. When the withdrawal cannot be recorded at once, the watcher keeps it owed and tries it again on the pull request's next check, also when the head boots by then, and starts no new round for that head before it succeeded. Intakt publishes the verdicts of one pull request one at a time (a publication that finds another one under way is tried again within a minute), so the last status on a commit is always the one of its latest round, withdrawn when that round was marked stale. A publication of a round is dropped when a later round of the same pull request that reviewed the same commit is already judged, because the later round's status is the one that commit stands at. A later round of another commit does not stop it: when a pull request moves from head A to head B and back to A, and A then fails to boot, A's old approval is still withdrawn.

### Project mode

A project can carry `mode: live`, the same as leaving the key out, or `mode: reviewer-for-loop` (see [above](#reviewer-for-loop-mode)). Any other value stops Intakt from starting and names the key; that includes `mode: shadow`, which is no longer a mode, so set such a project to `live` or `reviewer-for-loop`. Every reviewer's verdict is recorded in the ledger with the project's mode at that moment (`"mode":"reviewer-for-loop"` or `"mode":"live"`); a verdict recorded earlier with `"mode":"shadow"` stays in the ledger as it was written. The mark is a record only: it never stops a verdict from counting, and a round reviewed before a switch to `reviewer-for-loop` is published like any other. Intakt can post a review to GitHub, but in a live project only a pull request [handed to Intakt](running.md#pull-requests-handed-to-intakt) gets its verdict published; the loop's own pull requests get nothing, and nothing merges yet.

`budget.shadow_ceilings` is no longer a setting either; a configuration that still has it stops Intakt from starting and names the key, so remove it.

To see which panel a change gets, without calling any model, run `php bin/console intakt:review:panel <project> --lines=300 --path=src/Foo.php --label=review:full` (`--path` and `--label` can be repeated; all options are optional, and `--lines` must be zero or more). It prints the quorum and one line per reviewer with its tier, provider and budget. Intakt reads the configuration when it starts, so a changed file shows after the cache is cleared. An unknown project fails with a message. A path pattern Intakt cannot evaluate against a path (for example, one too complex for the pattern matcher) fails the same way, with a message that names the pattern. `intakt:review` takes the paths from the branch and no labels.

### Which tier a build starts on

A project can carry a `build:` section that sets the rules for the tier a build starts on. `tier` (`strong`, `standard` or `light`; default `standard`) is the tier for an ordinary build, `escalate_on` lists the setbacks that raise the next build to the strong tier (`failed-attempt`, `blocking-finding`, `stall`; all three by default, a shorter list turns triggers off, and an empty list or `escalate_on: ~` turns every escalation off), and `sensitive_paths` is a list of path patterns (same patterns as a review rule's `paths`) for the files that need the strong tier:

```yaml
projects:
    alpha:
        build:
            tier: standard
            sensitive_paths: [config/**, src/**/Security/**]
            escalate_on: [failed-attempt, blocking-finding, stall]
```

A build that touches a sensitive path starts on the strong tier, whatever its label says. Otherwise, after a listed setback (an earlier failed attempt, a blocking P1 finding or a stall) the build is raised to the strong tier; a rework after a round without a P1 stays on the cheaper tier. Otherwise a `model:<tier>` label (for example `model:strong`) sets the tier, and without either the build starts on `tier`. A `model:` value that names no tier, such as a model name, is ignored. The rules look only at the labels, the touched paths and the setback the loop passes, so a job can never choose its own model. A bad tier, an unknown setback, or sensitive paths or setbacks that are not a list, stop Intakt from starting and name the key.

To see the tier the rules choose, without calling any model, run `php bin/console intakt:build:tier <project> --label=model:strong --path=src/Foo.php --setback=stall` (`--label` and `--path` can be repeated; all options are optional). It prints the tier and why (`default`, `label`, `setback` or `sensitive-path`); an unknown project fails with a message. Starting a build on the chosen tier is not wired yet.

To choose the model of a build and record it, run `php bin/console intakt:build:model <project> <task> <attempt> [--label=...] [--path=...] [--setback=...]` (the attempt starts at 1). It applies the same rules, prints the tier, the reason, the provider and the model the project maps that tier to, and writes one `model_chosen` event to the ledger (`php bin/console intakt:ledger:events` shows it). It calls no model. An empty project or task, a project or task that is not valid UTF-8 and an attempt below 1 fail with a message and record nothing. A build runs the Claude Code CLI, so if the project maps the chosen tier to any other provider, the command fails and records nothing. If the ledger cannot record the event, the command fails and the choice does not count. A build never picks its own model: only the rules, your labels, the paths and the earlier round's setback decide.
