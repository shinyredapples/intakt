# Running and operating Intakt

This page covers running Intakt and keeping it healthy: the container image, the server status, the background workers, the boot check and the log. It also describes what Intakt keeps (project memory, the ledger, the measured use of subscription windows, a copy of each project's repository) and its GitHub App, releases, the weekly report and the check of a new Symfony AI release.

## Running the container image

The `Dockerfile` builds an image with Intakt on FrankenPHP in worker mode, with the live-update hub built in. To check an image you built, run `docker/smoke-test.sh <image>`: it starts the image with throwaway secrets and checks that the dashboard answers, that MCP requests go to their own worker, that the server runs as an unprivileged user and that the admin port stays inside the container, then removes what it started. CI builds the image and runs this check on main and on every pull request that changes more than `docs/`, `tests/` or `upstream/` (the `image` job in `.github/workflows/ci.yml`). Every release also publishes a checked image, `ghcr.io/shinyredapples/intakt:<version>` and `:latest` (see [Releasing](../releasing.md#the-container-image)); use it instead of `docker build` when you run a release. Between two requests the worker clears the signed-in user, the database entities it loaded and the other per-request state of Intakt's own services, so one browser never sees another's flash messages or data. Each request also starts with the file permission mask (`umask`), locale and environment variables the worker started with, whatever the request before changed. The same reset runs between two messages of a consumer, so a reviewer's model, tools and conversation stay with its own review: the next one connects to the review tools again and sends only its own model, tools and messages (checked by `tests/Application/SymfonyAiResetTest.php`). A test in the repository (`tests/Application/WorkerModeTest.php`) checks the rest, both as the image runs and with `FRANKENPHP_RESET_KERNEL=1` (a fresh copy of Intakt's kernel for each request). The image does not set it.

```
docker build -t intakt .
# fails if the base image's PHP is below 8.5.12
docker run -d --name intakt -p 127.0.0.1:7781:7781 -v intakt-data:/app/var/data \
  --env-file intakt.env intakt
```

- The secrets are never in the image. `intakt.env` (yours, not in the repository, and left out of the build like `.env.local` and `.env.local.php`) must set `APP_SECRET` and `MERCURE_JWT_SECRET` (at least 32 bytes); the container refuses to start without them, and names the one that is missing. Nothing else is required: the image sets defaults for `MERCURE_JWT_ISSUER` (`http://localhost:7781`), `SERVER_PORT`, `DASHBOARD_PORT` and the other values in its `ENV` lines. When you serve the dashboard from another address, set `MERCURE_JWT_ISSUER` and `MERCURE_PUBLIC_URL` to the address your browser uses. Before it starts the web server, the container asks FrankenPHP to check the Caddyfile and prints the reason when it is rejected.
- Publish the port on `127.0.0.1` only (`-p 127.0.0.1:7781:7781`): the dashboard has no login (whoever reaches the port can act), and a plain `-p 7781:7781` opens it to every network the host is on, where a client can send `Host: localhost:7781` itself. Keep the same port inside and outside: the dashboard answers only `localhost`, `127.0.0.1` or `[::1]` with its own port (see [the dashboard](README.md#the-dashboard)), and the image sets `DASHBOARD_PORT` and `SERVER_PORT` to 7781.
- The database (SQLite) and the hub's history live in `/app/var/data`. Mount a volume there (`-v intakt-data:/app/var/data`): the image declares none, so without it they are lost with the container. The container runs as the user with id 10001, so a bind-mounted folder must belong to that user. It applies the migrations on every start, then serves `/projects`.
- Keep the project file on that volume and name it with `INTAKT_CONFIG` in `intakt.env` (for example `INTAKT_CONFIG=/app/var/data/intakt.yaml`). The image was built without your projects, so the container builds its cache again on every start, after the migrations and before the web server and the workers. A change to the project file, or its removal, therefore applies at the next start (`docker restart intakt`), with no `cache:clear`. A project file the cache cannot be built from stops the start with the reason in the log. A file at `/app/config/intakt.yaml` is read the same way when `INTAKT_CONFIG` is not set, but it is lost with the container unless you mount it.
- Two worker pools serve requests: `app` for the dashboard, and `mcp` for `/mcp/*` with its own thread limits (`MCP_WORKERS`, `MCP_MAX_THREADS`), so a streamed MCP answer cannot take the dashboard's threads. `APP_WORKERS` sets the dashboard's pool, `MAX_WAIT_TIME` how long a request waits for a free thread.
- FrankenPHP's admin API listens on `localhost:2019` inside the container and nothing publishes it; read it with `docker exec intakt php bin/console intakt:server:status`.
- A worker is replaced after `FRANKENPHP_LOOP_MAX` requests (default 500) and when it holds more than `WORKER_MEMORY_CEILING_MB` megabytes (default 256) after a request; it finishes sending the answer first, so no request fails. A crash is restarted by FrankenPHP itself.
- The queue workers and the scheduler (see [Background work](#background-work)) run in the same container, beside the web server: `MESSENGER_CONSUMERS` workers (default 3, so the reviewers of a panel of three run at once) and one scheduler. When one of them stops, for any reason, it is started again a second later and the container logs `intakt: async ended with status 137, starting it again` (`scheduler_watcher` for the scheduler). A worker also ends on purpose after an hour or once it holds more than `WORKER_MEMORY_CEILING_MB` megabytes, between two messages, and is started again the same way. `docker stop` lets each worker finish the message it is on for up to 8 seconds, then stops what still runs; a message cut off is handed out again later.
- Start the container with `--restart unless-stopped`, so Docker starts it again after a crash or a reboot. When the web server itself stops, the container stops the workers and the scheduler and exits, so this restart brings all of them back. The image has a health check (`intakt-healthcheck`) that asks FrankenPHP's metrics endpoint and the dashboard every 30 seconds and, in the demo, also waits for the seed; read it with `docker inspect --format '{{.State.Health.Status}}' intakt` (`healthy` or `unhealthy`).

## Checking the server

When Intakt runs under FrankenPHP, `php bin/console intakt:server:status` reads FrankenPHP's admin API and prints how many worker threads are busy and idle, how many requests wait in the queue, how often workers were restarted, and whether the Mercure hub is healthy:

```
worker threads: 0 busy, 2 idle
queue depth: 0
worker restarts: 2
hub: healthy
```

Run it inside the container, because the admin API answers only there. It reads `FRANKENPHP_ADMIN_URL` (default `http://localhost:2019`), which must be plain `http` on `localhost`, `127.0.0.1` or `[::1]`; any other address is refused before anything is sent. A value that cannot be read shows `down` with the reason (the server did not answer, answered with an error status, or answered something Intakt cannot use), and the command then exits with a non-zero code. A thread that is starting or restarting counts as neither busy nor idle.

## Background work

Intakt has two internal message buses, one for commands and one for questions. Each bus accepts only its own kind of message: a question sent on the command bus, or a command sent on the question bus, is refused before any handler runs. This covers messages Intakt sends itself; a message a worker takes back from the queue is not checked again.

A review round sends one message per reviewer to a queue, and workers take them from it, so the reviewers of a round run at the same time. It also queues one message that has a worker send the dashboard's project filter again when the round is its project's first; a round that is undone before it is stored leaves none of these messages behind. The queue is a table in your database (`MESSENGER_TRANSPORT_DSN`, `doctrine://default` unless you change it in `.env.local`), created by `php bin/console doctrine:migrations:migrate` together with the other tables. Start as many workers as you want reviewers to run at once:

```
php bin/console messenger:consume async
```

The state of a round and of each reviewer is stored in the database, and so are the waiting messages. If a worker stops, start it again: the reviewers still waiting run, and a round whose last reviewer has finished is completed. A reviewer that was in the middle of its review when its worker stopped keeps its place for one hour from its start, so a message that reaches another worker in that hour (the same message is handed out again after ninety minutes) waits until the hour is over; then the reviewer is started again once. If its worker stops a second time, the reviewer is recorded as blocked (`reviewer_blocked` in the ledger, readable with `php bin/console intakt:ledger:events`) and the round goes on without it. A review that takes longer than that hour counts as failed too: an answer that arrives after the hour is dropped and the reviewer is recorded as failed, even when no other worker got the message. A reviewer whose call to the model fails for any reason is recorded as failed too, with the kind of failure (for example a refused key), and the round goes on. A reviewer whose result could not be written to the ledger goes back to the queue and is reviewed again. A reviewer whose call the provider limits (a rate limit or quota) goes back to the queue and its message comes back after the time the provider named, or, when it named none, after a wait that starts at about one second and doubles each time up to at most one minute; a failed attempt does not use up the one restart of a stopped worker. At most 3 calls run at the same time for one provider account (`intakt.vendor_account_parallel_calls` in `config/services.yaml`); a further reviewer waits in the queue the same way. While Messenger will still try a failed message again, its reviewer is left as it is and its next try can still give a verdict. A message that Messenger gives up on, once its tries are used up (it lands in the `failed` queue, shown by `php bin/console messenger:failed:show`), makes its reviewer blocked in the same step, before the message is parked, which counts as finished, so the round still completes. If the reviewer cannot be blocked for any reason (the ledger cannot store it, the reviewer is no longer in the database, the database fails), the worker logs an error naming the reviewer and keeps running; the message still lands in the `failed` queue, and `php bin/console messenger:failed:retry` runs it again. `php bin/console intakt:review` starts a round and waits for these workers (see [Reviewing a branch](README.md#reviewing-a-branch)).

## Checking that an install boots

After `composer install`, `php bin/instance` starts Intakt on a local port with a scratch SQLite database, checks that it answers, stops it and removes everything it created. Without `TMPDIR` it keeps its scratch files in `var/`; a `var/` folder that the run created is removed again when it is empty, and one that existed before is left in place. If it cannot create its scratch folder, the reason names the cause, for example `cannot create the scratch directory: mkdir(): Permission denied`, or `unknown reason` when the system gave none. It needs no network. Descriptor 3 receives one line, `{"status":"ready"}` or `{"status":"failed","reason":"..."}`, for example:

```
php bin/instance 3>&1 >/dev/null
```

The exit code is 0 only when the status is `ready`. The server log goes to standard output.

A failed boot's reason says what went wrong (`the server exited:`, `HTTP <code>:` for an answer of 500 or more, or `no answer within 30 seconds:`) followed by the first line of the server log that mentions an error or exception. When no line does, it is the last line of the log that is not empty, so a server that the system stops, for example with a bare `Out of memory`, reads `the server exited: Out of memory`. The built-in server's own lines (its start line and the lines it writes for each request) are skipped there, since they only restate the status code; when nothing else is in the log, the reason reads, for example, `HTTP 500: the server log names no reason`. A server that exits without writing anything reads `the server exited: the server log is empty`.

When `frankenphp` is on your `PATH` (as in the container image), `bin/instance` serves the app with FrankenPHP in worker mode instead of PHP's built-in web server, and the line says so: `{"status":"ready","mode":"worker"}` or `{"status":"failed","mode":"worker","reason":"..."}`. A line without `mode` means the built-in server.

Descriptor 3 can be a pipe, a file or a memfd (an anonymous in-memory file, as a supervising program may pass). A memfd named exactly `opcache_lock` is not accepted, because PHP's OPcache uses that name for its own lock; any other name works. When descriptor 3 is not open, or is not accepted, no line is written and the exit code is 1.

Intakt can boot a commit of a project's local repository the same way: in a scratch copy of the commit it runs `composer install` (without the commit's Composer scripts) and then `bin/instance`, taken from main for a pull request's head, so a head that changes `bin/instance` cannot pass its own check. Both get only basic environment variables (such as `PATH` and the proxy settings) and an empty scratch home instead of the install's `HOME` and Composer home, so neither Intakt's own keys and tokens nor the Composer `auth.json` of the install are handed to them. This is not a sandbox: the commit's code still runs as the same user on the same machine and can read its files on purpose; isolating it is a later part ([Boot step](../architecture/boot-step.md)). The result is booted, failed (with the reason `bin/instance` or Composer gave) or crashed (the boot step itself could not run, for example because the commit is missing); a crash never stops the review. Main's result is kept per project, main commit and tool fingerprint, so main is booted again only when its commit or the tools change, and the ledger records `boot_result_computed` each time it is computed, and once more, marked `read_from: store`, when a kept booted or failed result is answered and differs from what the board shows for the project (a crashed boot is kept only for 5 minutes: within them main's crash is answered without booting again, and after them main is booted again). The watcher boots a pull request head whose CI is green before its review starts, but only when the pull request's author is trusted: a person with write access, Intakt's own identity or the maintainer's identity. Any other author's head (also when the trust check fails or cannot answer) is never booted: its review still starts, and the ledger records `head_boot_skipped` with the cause `boot_skipped_untrusted_author` ([Boot step](../architecture/boot-step.md#in-the-watcher)). Be aware of the remaining risk: until reviews run in isolated job containers (a later part), a trusted author's head runs `composer install` (with the Composer plugins it allows) and `bin/instance` directly on your machine as Intakt's user, next to your install's home, keys and database. For a trusted author's head, a head goes back, like red CI, only when it fails while main boots: no review starts, the ledger records `head_red` with the cause `boot_failed` and the reason, and a review already made on that same head is withdrawn (its status on the forge becomes `failure`, see below), so an approved head that does not boot keeps no approval. When main does not boot (also when the project has no `bin/instance`) or the step crashes, the review goes ahead without the boot check, and when main itself fails to boot the ledger records one `main_boot_failed` alert for that main commit and tool fingerprint, so a tool change can raise another alert for the same commit (when the ledger cannot write it, or Intakt stops before it is written, the next time main's result is asked for, before a green head is reviewed, it tries again; a main whose failure was already kept before the alert existed gets it the next time main's result is asked for after `doctrine:migrations:migrate`) and the board shows a banner `Main of <project> does not boot` until a new main commit, or main after a tool change, boots (a crash raises no alert, because it is the boot step's fault and main is booted again after it), and a check that breaks never stops a review. The banner follows the current main: when main or the tools go back to a commit and tool pair whose result is already kept, the banner shows again if that pair failed and clears if it booted, while the alert stays one per pair (a pair whose alert was recorded raises none again).

## The log

Intakt writes its warnings and errors to the service output (the journal, or `docker logs`), one JSON line per record: `time`, `level`, `message` and `context`. The context names the item a failure belongs to (for example `reviewer`, `round`, `call`, `project` or `account`), and a failure carries the exception's `class`, `message`, the `at` line and the `trace` (the file, line and function of each call, never the values passed to it), with the earlier exception it wraps under `previous`. Before a line is written, the credentials Intakt holds, whether set in the environment or in Symfony secrets (`APP_SECRET`, `MERCURE_JWT_SECRET`, `MCP_OWNER_TOKEN`, `GITHUB_APP_PRIVATE_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENAI_COMPATIBLE_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `HF_TOKEN`, and the same names with an account name appended, such as `ANTHROPIC_API_KEY_TEAM`), the userinfo of a URL (`https://user:pass@host` is written `https://[redacted]@host`), the values of authorization and cookie headers, and secret-shaped strings are replaced with `[redacted]`. A held credential is found with or without its leading and trailing spaces or newlines, so a value saved with a newline at its end is still replaced where a line quotes it without that newline. This applies to context names too; when two names end up the same, the later one gets a number (`[redacted] 2`), so no value is lost from the line.

## Project memory

Intakt can keep short notes about a project, each tied to the files it explains, and look up the notes for the files a change touches within a size limit (in bytes). When a review round completes, every finding a reviewer marked resolved (and that stays resolved) is written as a note, with its cause and the file it concerns; a round that finishes after a newer round of the same change writes none, since its verdicts are left out of the list (see [Finding ids across review rounds](README.md#finding-ids-across-review-rounds)). This needs an OpenAI account for the embeddings (`OPENAI_API_KEY`); without one the note is not written and the message waits in the failed queue with the reason. Create the notes table once with `php bin/console ai:store:setup`. Notes belong to the project whose review wrote them: a review is only ever shown its own project's notes, even when another project on the same install has notes on a file with the same path. Each reviewer's briefing carries the notes for the files in the change's diff (for a renamed file, its old and new path), most relevant first, marked as untrusted text; the whole briefing is at most 4000 bytes. Less relevant notes that do not fit are left out; when the most relevant note alone is too long, it is cut to fit and ends with `[note shortened]`. It comes after the diff as a message of its own, and the reviewer is told the notes may be wrong and must be checked against the code. When the notes cannot be read (no OpenAI account, or the table was not created) the review goes on without them and a warning is logged. Reviewers can only read the notes, never change them.

## The ledger

Intakt has a ledger that can store review events (review started, reviewer started, verdict received, judge done, usage recorded) in one SQLite table, `ledger_event`, and read them back in the order they were stored, even if the system clock is set back in between. Each event gets an id that carries the time it was stored (a UUID version 7) and keeps the moment it was stored in UTC, and reads it back the same whatever time zone PHP is set to. A reviewer started event names the model the reviewer's tier pointed to when it started (none when the tier could not be resolved, and none in events stored before Intakt recorded it, which still read). So far the model calls of the vendor write to it (their token usage), and so do job containers (how each job ended, and containers removed after a crash; see below). Create the table with:

```
php bin/console doctrine:migrations:migrate
```

The same command also creates the tables where Intakt will keep what it read from a project's GitHub issues: the open issues and pull requests of the last full listing, a marker (the listing's entity tag) that lets Intakt reuse the stored listing when GitHub confirms it unchanged, while a changed listing is read again in full, and the reason a task failed for good. The reason stays stored after its issue is closed, so tasks that wait for it stay held. Intakt does not take work from GitHub issues by itself yet: the code that fills these tables from one full listing of the open issues exists, but nothing runs it so far, and the automatic intake is still planned. When it runs, a listing that GitHub answers only in part, or an issue that changes while Intakt reads who wrote and labeled it, changes nothing: no task is picked from it and no wait counts as finished, and the reason goes to the log as a warning. When two workers read the same project's listing at the same time, the first to save its listing wins: the other never overwrites it with an older one, and picks from the saved listing instead, after checking those issues against its own configured eligibility label. A worker whose saved listing was replaced again while it checked it picks nothing that round and logs a warning. A worker that finds the other one still saving picks nothing that round, logs a warning, and reads the saved listing on the next one.

### Choosing the database

Intakt uses SQLite unless you set `DATABASE_URL` (in `.env.local` or the real environment) to another database; MySQL, MariaDB and PostgreSQL are tested too, for example `DATABASE_URL="postgresql://intakt@localhost:5432/intakt"`. Intakt finds out the MySQL or MariaDB server version itself on the first connection. For PostgreSQL it does not ask the server and always uses its support for PostgreSQL 12 and later, the newest it has. The test environment appends `_test` to the database name, so tests against `intakt` use the database `intakt_test`. In CI, a pull request runs the tests on MySQL, MariaDB and PostgreSQL only when it touches persistence (the ledger, migrations, Doctrine's configuration, the Composer files or the CI definition under `.github/workflows/` and `.github/ci/`, or adds a line naming Doctrine in `src/`); when that check fails, the CI run fails rather than skipping them, and every push to main runs them. SQLite runs on every change.

Stored events cannot be changed or removed. Intakt refuses to update or delete one with a `LedgerEventsAreAppendOnly` error, and on SQLite the same migration adds database triggers that abort any `UPDATE` or `DELETE` on the table, and any insert that would replace a stored event (for example `INSERT OR REPLACE` with the position or id of an existing event), even from another tool. On other database engines only the refusal inside Intakt applies.

Read the events back, oldest first, with:

```
php bin/console intakt:ledger:events
```

It prints one line per event (the moment in UTC, the id, the kind and the payload) and ends with a count, for example `2 events`. The payload is printed exactly as stored, console color tags included. The ledger has no notion of a run yet, so the command lists every stored event of a known kind; rows of a removed kind stay stored but are not shown and are not counted.

### Pull requests handed to Intakt

While Intakt runs beside the earlier loop, the pull requests Intakt opens itself (as its GitHub App) are handed over to it: the loop leaves them. Each minute's look at a project's pull requests notes every open one that Intakt created with a `change_handed_to_intakt` event (the project, the pull request's address and its head), once per pull request, also when the pull request did not change since the last look. Intakt decides this from its own record of creating the pull request (the `change_opened` event of the push, with `opening` `created`) or from the author GitHub reports, never from the title, labels or branch GitHub shows, so a pull request someone else opened, the loop's included, is never noted, even with the same branch name or title, and even when an earlier version of Intakt's push updated its text (such a record says `updated`). Intakt now leaves such a pull request alone: a push for a branch that has an open pull request someone else opened stops with an error before anything is pushed (see [Pushing an accepted build](README.md#pushing-an-accepted-build)). Letter case in the repository name does not matter. For an open pull request Intakt has no record of opening, Intakt asks GitHub who created it, on each look only until GitHub gives a definite answer, which is then recorded, and notes it when that is Intakt's own App, so a push that stopped after GitHub created the pull request but before Intakt recorded it is still noted without another push, also when the branch moved since. A pull request someone else created, the loop's included, is not noted as handed over: it gets a `change_not_handed_to_intakt` event instead (the same fields), because the author GitHub sets never changes. So the author GitHub sets decides when no record of opening does, and a recorded answer, either way, means GitHub is not asked again about that pull request. A later push also finds Intakt's own pull request open with Intakt's own App as its author, records it as `created`, and goes on. When GitHub shows that open pull request without its author (or with an empty one), the push stops with an error and changes nothing, so it can be tried again. A pull request Intakt opened before this version has a `change_opened` event without `opening`; for such an open pull request, Intakt asks GitHub who created it, only until GitHub gives a definite answer, which is then recorded, and notes it when that is Intakt's own App. An answer without the author's name (or with an empty one) is no definite answer: nothing is recorded and the next look asks again. A pull request someone else created gets the `change_not_handed_to_intakt` event and GitHub is not asked again; while it is open, a push of its branch stops before anything is pushed (see [Pushing an accepted build](README.md#pushing-an-accepted-build)), so no push records it as `created`. A push of the same commits and text whose only record has no `opening` also asks GitHub again and records it. When GitHub cannot answer who created a pull request, nothing is recorded and that pull request alone waits for the next look (Intakt logs a warning), and the other pull requests are noted and looked at as usual; after a rate limit, no further author is asked on that look. The weekly report keeps covering the loop's own pull requests and is not changed by it. See [Pull requests handed to Intakt](../architecture/handed-to-intakt.md).

Intakt's review of a pull request handed to it counts, in any project mode (also `live`): once its round is judged, Intakt publishes the verdict on that head exactly as in [reviewer-for-loop mode](providers.md#reviewer-for-loop-mode), the comment ending with the round's marker `<!-- intakt-verdict: <round id> -->` (the round's one-time token, so a retry posts the comment once) and the commit status `intakt/review`. In a `live` project the loop's own pull requests still get nothing on the forge. When Intakt approves a handed-over head that touches a protected path of the project (`protected_paths`, see [Protected paths](../architecture/protected-paths.md)), or whose protected paths cannot be read (Intakt's copy of the repository does not hold that head, for example), Intakt asks you instead of approving on its own:

- after the review comment, Intakt posts a second comment with `**Waiting for the owner** (head <full head>)`, the line "This head touches protected paths, so it merges only once the owner has approved this head.", and either "Protected paths:" with one `- <code>path</code>` line for every path (a line break, a backtick, HTML or markdown in a file name is shown escaped) or, when the paths cannot be read, "Intakt could not read which paths this head changes, so it counts as protected." without the reason; when the list is too long for one GitHub comment, it goes on in further comments headed `**Waiting for the owner** (head <full head>), continued`;
- the status is `pending` with the description "Intakt approves this head; it touches protected paths and waits for the owner.", never `success`;
- the ledger gets one `owner_asked` event per head (project, pull request, head, round, the paths and the unreadable reason), also when the publication is tried again or a later round reviews the same head, and only once the ask is on the pull request: without a GitHub App nothing is posted and nothing is recorded.

A publication that is tried again posts only the comments that are not on the pull request yet; when the protected paths it finds differ from the earlier try's, it posts the new list as an ask of its own (the earlier ask stays), and that new list is the one the `owner_asked` event records. A protected file name that would show a secret is never posted: Intakt then posts no comment at all and the status is `error` with "Intakt could not publish its review of this head.". A pull request that is noted as handed over after the head it was noted at was already judged gets that head's review published then, shortly after the look that noted it; so does one noted as handed over by an earlier version of Intakt, once, on the first look after the upgrade. When several rounds judged the same head, the verdict published is the one of the round with the highest number of the pull request, not the one judged last by the clock, so a clock that went back does not pick an older round. The one exception is a pull request whose only judged round of that head was kept under another letter case of its address by an older version of Intakt: when no round of the pull request's one numbering judged that head, that round's verdict is published. A head Intakt asks changes for, or could not review, asks nothing. Merging a handed-over pull request, and reading your approval, are not built yet.

## Measured use of subscription windows

Intakt can keep, for each AI account, the latest use of its five-hour and weekly windows as the AI company measured it, with the time the window resets and how old the reading is. A reading belongs to its account only: another account, of the same company or another one, never sees it. A reading whose reset time has already passed, or lies further ahead than the window is long, is not kept, and the previous reading stays. The table is created with `php bin/console doctrine:migrations:migrate`.

From these readings Intakt can decide whether one more call may start on an account:

- No call starts while a window is at or above its ceiling. An old reading still counts until its window resets, since use only grows until then; once the reset time has passed, the reading no longer counts. A reading without a reset time stops counting once it is older than its window is long (five hours or a week).
- The weekly window is paced: the pace is the weekly ceiling times the share of the week that has passed, counting the current five hours as passed. While the weekly use is ahead of the pace, the five-hour ceiling shrinks in the same proportion (for example, a weekly use of twice the pace halves it).
- With no call running, one call starts below the ceilings, even with no reading or an old one.
- A second call at the same time needs a reading of both windows taken within the last 5 minutes, and both windows more than 10 points below their ceilings (at a ceiling of 90%, a use of 80% is not enough). Without a reading of both windows from the last 30 minutes, only one call runs at a time.
- Only the account's own readings count. Intakt's estimate of what a call will cost plays no part.

Set the ceilings, in percent from 1 to 100, in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names) and run `php bin/console cache:clear`:

```yaml
budget:
    ceilings:
        five-hour: 90
        weekly: 90
```

Both default to 90; a window you leave out keeps it. A value outside 1 to 100 (`.NaN` included), a window name other than `five-hour` and `weekly`, or another key under `budget` than `ceilings` and `prices` (such as the former `shadow_ceilings`, see [Project mode](providers.md#project-mode)) stops Intakt from starting and names the key. The ceilings apply to every account. Nothing records readings or asks this decision before a call yet: reading the windows from Claude and Codex and holding back new work by this decision come in later changes.

### Cooldowns, pauses and outage notices

Besides the ceilings, Intakt can hold work back in these ways (the tables are created by the same `doctrine:migrations:migrate`):

- **Cooldown of one account:** when the AI company answers that an account's usage limit is reached, that account gets no new call until the reset time the answer gave, even if that is days away. Other accounts, of the same company or another, keep working. An answer whose reset time has already passed, or lies more than a week ahead, cools nothing down.
- **Budget back-off:** no new call starts on any account, but pull requests that are already approved still merge, since merging calls no model.
- **Pause:** the same as a budget back-off: nothing new starts, approved pull requests still merge.
- **Failure back-off:** no new call starts on any account and nothing merges (once holds are checked, see below). Intakt starts it by itself for 15 minutes, and only for a fault no single item causes. Today these come from the pull requests Intakt watches: GitHub refuses Intakt's credentials (an answer of 401; a rate limit does not count), the disk is full, the lock store fails while a pull request is being locked or unlocked, two different pull requests fail with the same error within an hour, or handing a pull request over to the maintainer agent itself fails. The log gets an error naming the reason.
- **Drain:** nothing new starts and nothing merges, so work in progress can finish before an update.
- **Watchdog halt:** while any card of the watchdog stands, the decision answers `halted` for every start and every merge, of every project ([Halting the project](building.md#halting-the-project-and-clearing-your-card)). It does not end by itself: only you clear it.

When several are in effect, the strictest wins: a watchdog halt, then drain, then failure back-off, then pause, then budget back-off, then an account's cooldown, then the ceilings. Each one except the watchdog halt ends by itself at the time it was given.

When no usage reading of an account has arrived for 3 hours, Intakt writes one warning to its log, for example `No usage of account claude_code.main has been read since 2026-11-02T08:00:00+00:00, so only one call at a time runs on it.` It writes it once for that outage, also with several workers; if writing the warning fails, Intakt tries again at the next decision; after a new reading, a later outage gets its own warning. Intakt also records the outage as a notice, and the dashboard's Waiting on you page lists it until a newer reading of the account arrives (see [The dashboard](README.md#the-dashboard)). Intakt keeps the time of that reading as the end of the outage, so the outage stays off the page even if the reading is removed later. The reading and the end are saved together: if saving the end fails, the reading is not kept either, the outage stays on the page, and the next reading ends it. Only an outage that ended before Intakt kept these ends can show up again when its reading is removed. Sending these notices to your phone comes with the notifier.

Nothing places a cooldown, a budget back-off, a pause or a drain yet: the AI company answers and the admin controls that place them come in later changes. Nothing checks a hold before a call or a merge yet either, the failure back-off and a watchdog halt included: only `intakt:budget:replay` (below) reads them. The replay reads the cards that stand on your install now, not the ones the scripted day had, so while a card stands every start and merge of the replay answers `halted`.

To see what Intakt would decide over a day, write a script and replay it:

```
# one step per line: a UTC moment, then the step
2026-11-02T08:00 read claude_code.main five-hour 20 2026-11-02T13:00
2026-11-02T08:00 read claude_code.main weekly 10 2026-11-08T08:00
2026-11-02T08:00 start claude_code.main 0
2026-11-02T09:00 limit claude_code.main 2026-11-02T13:00
2026-11-02T09:00 start claude_code.main 0
2026-11-02T10:00 hold budget-back-off 2026-11-02T10:30
2026-11-02T10:00 merge
```

```bash
php bin/console intakt:budget:replay my-day.txt
```

It prints each line with its outcome (`recorded`, `cooling-down`, `start` and so on), and the outage warnings where they happen. The steps are `read <account> <window> <percent> <reset>`, `limit <account> <reset>`, `hold <drain|failure-back-off|pause|budget-back-off> <until>`, `start <account> <calls running>` and `merge`; an account is written as company and name, such as `claude_code.main`. The replay runs on your database and your ceilings with its own clock, starting at the first line, and undoes everything when it ends, so your install keeps nothing of it. A line it does not understand stops it with the reason. `tests/Core/Budget/UseCase/ReplayDay/scripted-day.txt` is a whole example day.

## Checking a new Symfony AI release against the known bugs

`php bin/console intakt:upstream:run` runs every reproduction in `upstream/` and prints the installed Symfony AI versions, then `passes` (the bug seems fixed) or `still fails` for each reproduction, and a count. Add `-v` to see why a reproduction fails. The exit code is 1 while any reproduction still fails. A reproduction counts as `passes` only when its PHPUnit tests ran and asserted something, or when its `reproduce.php` script exits with 0 and prints `REPRODUCTION PASSES` as its last line. One without tests or script, with a skipped or incomplete test, or that runs longer than 5 minutes is reported as `still fails`, and the other reproductions still run. A folder that does not exist, cannot be read or cannot be opened (no execute permission) is an error (exit code 2).

For a bug in Symfony AI, a reproduction folder can also hold a prepared fix for the owner to approve: `fix.patch` (one commit for `symfony/ai`) and `PR.md` (the pull request text as it will be posted), or `COMMENT.md` (a comment for an upstream pull request that already fixes the bug, or for an upstream issue that already covers it). A bug that needs a new upstream issue, in Symfony AI, Symfony or Doctrine, holds `ISSUE.md`: the issue text as it will be filed. The folder's `REPORT.md` says in `## Upstream status` whether a fix pull request is ready or only an issue is right, and why, and ends with a `Status` line after the owner's review (`not filed`, with the reason, for a report that is not sent). Intakt posts nothing upstream: the owner approves each one first. `intakt:upstream:run` ignores these files.

Before a new folder is made, the bug is checked against upstream (the order is in `upstream/README.md`, under "Before a new folder"): the folders already here, upstream's pull requests, the recent commits on upstream's development branch and the next release's changelog, then upstream's issues. Upstream often fixes a bug in a pull request or a commit with no issue. A bug upstream has already fixed gets no folder: the fixing pull request or commit and the first release that contains it are noted instead. The expected form of a report's `## Upstream status` names the pull requests and commits this check found, or "none found" with the date.

Some folders in `upstream/` are probes that pass: they check that Symfony AI and the MCP SDK behave where Intakt relies on them (two models and two MCP sessions in one worker without mixing, structured output cut mid-array, three parallel tool calls on one session). They stay as guards, so a later release that breaks one shows up as `still fails`.

Two probes check how Symfony AI behaves when a provider fails, and both still fail: a rate limit that the provider reports only when the answer is read does not move the call to the next account of a failover, and an agent whose streamed answer is cut off after a tool call reports no token usage for the run. Intakt does not depend on either: it moves to another account through its own cooldowns and reads the usage of each model call itself, so an interrupted call keeps the tokens it spent.

## Intakt's GitHub App

Intakt acts on GitHub as its own GitHub App, never with a personal token. Give it three values, the way you give it a provider key (Symfony secrets with `php bin/console secrets:set`, or `.env.local`, or the real environment): `GITHUB_APP_ID` (the App's id), `GITHUB_APP_INSTALLATION_ID` (the id of its installation on your account) and `GITHUB_APP_PRIVATE_KEY` (the App's private key, the whole PEM text). From the private key Intakt signs a proof of identity that lasts under ten minutes and exchanges it for an installation token that lasts an hour. It asks for a token for each call to GitHub and keeps one only while it has more than a minute to live; after that it asks GitHub for a new one. If the exchange fails (a wrong key or id, a removed installation, no network, an answer without a token or with an expiry date that does not exist, or a token that has expired or has less than a minute to live), the call fails with that reason and Intakt tries nothing else: no personal token, no `GITHUB_TOKEN`. The failure names the status or the kind of error, never the key or a token. When GitHub answers that Intakt used up its hourly allowance (a 403 with no calls left, or a 403 or 429 that says how long to wait, in seconds or as a date, or for GraphQL queries any answer with none left), Intakt makes no call of that kind with the installation's token until the reset time GitHub named, however far away it is (one minute when none was readable or the named time has already passed), and the call fails as rate limited with that time; a 429 is not retried. GitHub counts its ordinary (REST) calls and its GraphQL queries in separate pools, so each pause holds only calls of its own pool: the REST pause holds reading pull requests, posting reviews, publishing verdicts, the access checks of `intakt:forge:trust` and the repository list of `intakt:forge:installation`, and the GraphQL pause holds reading the history of an issue (who last edited it and who applied its labels), nothing else yet. When two answers of the same pool name different times, Intakt waits for the later one. Any other 403 is an ordinary refusal. Every REST answer's remaining allowance, hourly allowance and reset time are kept in the shared cache, so all workers see the latest reading; a GraphQL answer records none, because its pool is not the one the reserve below watches. Intakt keeps a reserve of the hourly allowance for the calls it cannot do without: 20% by default. To change it, set `reserve_percent` under `github:` in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names), a whole number from 0 (no reserve) to 100, and run `php bin/console cache:clear` (see `config/intakt.example.yaml`); any other value makes `cache:clear` fail with an error that names `intakt.github.reserve_percent`. While less than the reserve is left, Intakt reads each project's list of open pull requests once a minute on average: each listing makes the next one due a minute after this one was due or ran, whichever is later, and a listing that comes half a minute or more before its due time fails as rate limited with the reset time, without a call. Reading the CI of a head, reading a pull request, posting a review, publishing a verdict, the access checks and the installation check always go on. `/reviews` shows the installation's calls used and remaining this hour and whether the reserve is in force (see [The dashboard](README.md#the-dashboard)). While GitHub's own pause holds, a watched head whose CI could not be read waits for the reset time and is not counted as failing, unless Intakt cannot save that reset time, which counts as a failure of that head and backs it off (see [Watching pull requests](providers.md#capability-tiers-per-project)). To check the installation, also set `GITHUB_APP_PERMISSIONS` (the permissions the installation must hold, as `name:level` pairs separated by commas, for example `contents:write,pull_requests:write`; each permission at most once, a name given twice is refused) and `GITHUB_APP_REPOSITORIES` (the repositories it must cover, as `owner/name` separated by commas). `php bin/console intakt:forge:installation` reads the installation back from GitHub and compares it with both lists, exactly: a permission at another level, a missing or extra permission, and a missing or extra repository each make the command fail with a message that names the difference, and, through the check Intakt runs before its first call to GitHub, every read or write on GitHub is refused until the installation matches. When all match, it prints the permissions and repositories it read and exits with success. If GitHub cannot be reached, refuses the read, or lists fewer or more repositories than it counts, the check fails with the reason and tries nothing else. The messages and logs never hold the key or a token. Intakt also runs the same check by itself before its first call to GitHub: until the installation matches, every read or write on GitHub fails with the difference named, and nothing is read from or posted to a pull request.

`php bin/console intakt:forge:trust <owner/name> <login>` shows whether an account may steer Intakt on a repository. A person counts only with write access (the admin, maintain or write role; triage and read do not), which Intakt asks GitHub with its App's token on every check. A bot account (a login ending in `[bot]`, or one GitHub marks as a bot) never steers, whatever its permission, except two: Intakt's own App, whose name Intakt asks GitHub for, and the maintainer's App, whose slug you set in `GITHUB_MAINTAINER_APP_SLUG` (leave it empty while you run no maintainer App). Those two steer only while GitHub reports write access for them on the repository, asked with the App's token like a person's; without it they count as `non-writer`. The command prints `writer`, `non-writer`, `foreign-bot`, `own-identity` or `maintainer` and whether that steers. If the token exchange fails, the installation does not match, or GitHub refuses the read or answers something Intakt cannot use, the check fails with the reason and tries no other credential. No event is checked this way so far: Intakt reads who applied an issue's labels (an App is named with `[bot]`, as here), but nothing applies the rule to them yet.

To move Intakt from the co-existence Apps to the earlier loop's Apps at the takeover, and back, follow [Taking over from the earlier loop](takeover.md).

Set `GITHUB_OWNER_LOGIN` to your own GitHub login: while it is empty no approval counts and a held change stays held (see [Holding a risky CI change for your approval](README.md#holding-a-risky-ci-change-for-your-approval)).

Intakt reads a pull request from GitHub with that token: you name it by its web address (`https://github.com/<owner>/<repo>/pull/<number>`), and Intakt reads its head, its base (where the branch left the base branch), the diff, the changed files (a renamed file counts as the old path deleted and the new one added) and any file as it is at the head. GitHub lists at most 300 changed files, so a pull request that changes 300 files or more cannot be read yet. It can tell that the head moved during a review, and whether the new commits only added to the old head or replaced it; a merge of the base branch is always treated as new commits to review again, and new commits that change 300 files or more count as a replaced head, so earlier approvals do not carry over. A short failure at GitHub (a server error or a dropped connection) is tried again up to three times. Any other address, or a pull request GitHub does not know, is refused as not found.

Intakt posts the outcome of a review round as one review comment on the pull request, tied to the head it reviewed. The comment ends with the round's one-time token in a hidden HTML comment (`<!-- intakt-review-token: ... -->`), so Intakt can later tell that the review on GitHub is the one it counted. Just before posting, Intakt reads the pull request again: if the head moved during the round, the round is stale and nothing is posted. Before that, Intakt redacts the text: every credential value the job that wrote the text held (also when the text holds it JSON-encoded once or more, whatever the nesting, including line breaks, quotes and accented or other non-English letters written as escapes), the values of authorization, cookie and API key headers (in plain text, quoted, shell-quoted, in JSON at any depth, in `print_r` or `var_export` dumps including list values and lists inside lists, and Digest parameters; a list of header values that is the value of a quoted key in JSON or a `var_export` dump becomes one `[redacted]` and the fields after it on the same line stay, while any other value in brackets, like `Cookie: [a]; sid=...`, `Authorization: ['Bearer x'] ...` or a quoted key inside another header's value such as `Cookie: x; 'authorization': ["a"], sid=...`, is redacted whole, to the end of its line or quote), the user and password of a URL (`https://user:password@host`, also as JSON writes it, `https:\/\/user:password@host`), and strings shaped like secrets (GitHub and cloud tokens, bearer tokens, private key blocks) become `[redacted]`; when a header's end cannot be found, the rest of the text is redacted, and a header list in a `print_r` dump is redacted to the end of the text, because `print_r` does not quote values and its end cannot be told apart from a value (redacting too much is accepted, stopping too early is not). Then Intakt scans the text with `gitleaks` (which must be installed where Intakt runs, on the path or named by `INTAKT_GITLEAKS`, and needs several gigabytes of address space when it starts, so a tight memory limit makes every post fail): if the scan still finds something that looks like a key or password, nothing is posted. If the pull request cannot be read again, GitHub refuses the post or cannot be reached, or the scan cannot run, the post fails with the status or the kind of error. The post is never tried again, because GitHub may have stored a review it answered with an error, and a second try would post it twice. No review round uses this yet. Intakt does not fetch or push with git yet, so no git command uses the token so far.

## Releases

Releases normally come from the [release train](../releasing.md#the-release-train): twice a day it cuts a release from a green `main`, but only when a `feat` or `fix` commit landed since the previous tag. The owner cuts milestone versions by hand. Every release is a signed tag and a GitHub release marked pre-release before `v1.0.0`. `v0.1.0` has hand-written notes; every later release uses generated notes. A pull request from this repository (not from a fork) is labeled `feat`, `fix` or `docs` from the type in its title when it is opened, reopened or its title changes (a new push leaves the label alone, because the label follows the title), so the notes list it under Features, Fixes or Docs; anything else lands under "Other changes". A pull request whose labeling run failed, or that was retitled before this rule reached `main`, can still carry the label of an old title; the person preparing the release then corrects or adds the label by hand. No CHANGELOG file is kept. See [Releasing](../releasing.md).

## The weekly report: the loop's reviews and Intakt's

When Intakt reviews for the loop, the loop's GPT reviewer and Intakt both post their review on the same heads of a pull request. `php bin/console intakt:reviewer-for-loop:weekly-report <folder>` compares them, from recorded pull requests: the folder holds one JSON file per pull request with `pullRequest` (its number), `loop` (the loop's account), `intakt` (Intakt's App account) and `comments`, each with `author`, `head`, `postedAt` (a moment with its offset, as GitHub writes it, for example `2026-11-03T09:12:00Z`) and `body`; see `tests/Fixtures/ReviewerForLoop/weekly/`. Every file ending in `.json` is read, in name order; other files and subfolders are skipped. Nothing fetches the comments from GitHub yet, so the folder has to be recorded first.

The week is the seven days before `--until` (a moment with its offset; without it, now). Only reviews are compared: on the loop's side, a comment whose `Reviewer:` line names `gpt` (the loop's other reviewers and its ordinary messages are left out), and on Intakt's side, a comment with a verdict block (a JSON line or a json fence, even one that cannot be read). A head belongs to the week in which the last of these reviews on it was posted: a review posted exactly at the end of the week belongs to the next week. Comments by other accounts are ignored. Both sides are read with the rules for the loop's reviews above (Intakt publishes its review in the same shape). The command prints the week, then a table with one row per head (pull request, head, each side's decision per reviewer, the agreement, the matched findings, and the findings only the loop or only Intakt raised, by severity, file and line), then a summary line. The agreement is:

- `agree` when both sides ask for changes, or both approve;
- `disagree` when one side asks for changes and the other approves;
- `incomplete` when a side posted no review on the head, or one of its reviews could not be read, even when another of its reviews asks for changes. A review that cannot be read never counts as agreement.

Otherwise a side asks for changes when any of its reviews does. Findings are matched by file and line (same file, lines at most 3 apart, a spot several reviewers of one side raised counts once); a finding Intakt files under `Follow-ups:` in an approval still counts as a finding. A finding line without a file and line is not read. An end that is not such a moment, a folder that cannot be read, or a file in it that is not a recorded pull request, stops the command with an error that names it.

## Keeping a copy of a project's repository

`php bin/console intakt:mirror:update <project> <remote>` keeps one bare copy (a mirror) of a project's repository in `var/mirrors/<project>.git`. The first run copies the whole repository from `<remote>` (a path, a `file://` or an `https://` address; a relative path counts from the mirrors folder `var/mirrors`, not from where you run the command); later runs fetch what is new and drop branches the remote deleted. The mirror's `HEAD` follows the remote's, also when the remote's `HEAD` is a detached commit, even one on no branch or tag, and a SHA-256 repository gets a SHA-256 mirror. If the branch the remote's `HEAD` names is deleted during a run, so the mirror's `HEAD` would point at nothing, the run says so and exits with 1, and the next run sets `HEAD` again. A first copy is built in a hidden folder beside it and only takes the mirror's place once it is complete, so a copy that fails half-way never counts as a mirror; a folder at the mirror's place that is not a bare repository is replaced. The project name must start with a letter or digit and may hold letters, digits, `.`, `_` and `-`. If git cannot reach the remote, hangs past 10 minutes or is stopped, Intakt waits 10 seconds and tries again, waits 30 more seconds and tries a last time, logging each wait; then it prints git's message (or, for a call that hung or was stopped, the reason in Intakt's own words, never the command with a password that may be in the address) and exits with 1. The mirror keeps neither the remote's address nor a password that may be in it (you name the remote on every run). Delete the mirror and the next run copies it again.

`php bin/console intakt:build:clone <project> <branch> <directory>` makes the copy a build works in, from the project's mirror (run `intakt:mirror:update` first). The new folder `<directory>` holds main (the branch the mirror's `HEAD` names) and the task's `<branch>`, checked out, and nothing else: no other branch, no tag and no remote. A branch the mirror does not hold yet starts at main. The command refuses a `<directory>` where anything already is (a folder, a file or a link, also a folder another `intakt:build:clone` made a moment before, so two runs for the same folder never share it), a project name that breaks the rule above, a project without a mirror, a mirror whose `HEAD` names no branch, a branch name git does not accept and a branch that is main itself; if a step fails after it made the folder, it removes that folder; it prints the reason and exits with 1. On success it prints `clone <directory>`.

A task split from a bigger change can build on an earlier piece of work with a line of its own `Source: <branch>@<sha>` (the full commit id). Give the task's text as a file with `--task=<file>`. Add `--trusted-author` when the task's author has write access to the project: the command then checks in the mirror that the commit is on that branch and adds that one commit to the copy as `refs/source/<branch>`, not as a branch and without any later commit of that branch. A source branch git does not accept, a branch the mirror does not hold, a commit that is not on the branch, an id that names something other than a commit (an annotated tag, for example) and a task with two source lines are refused, and no copy is made. Without `--trusted-author` the source line is ignored: the command prints one line starting with `comment` that says so, and makes the copy without it. A sentence that only mentions a source line, a quoted or indented line, a line inside a fenced code example (between lines of three backticks or tildes), a line inside an `<!-- external -->` ... `<!-- /external -->` block (text copied from outside, which does not count even in a trusted task; a block that is never closed runs to the end of the text) and a short commit id are not source lines. A task file that cannot be read is refused.
