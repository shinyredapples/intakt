# Intakt user guide

For owners who run Intakt. Each feature gets a page here, written in the same change as the feature: what it does, how to set it up, and what to do when it goes wrong.

The path from a clone to a first verdict, in order:

1. **Set up:** `cp .env.dist .env.local`, set a provider key (or a Hugging Face token, `HF_TOKEN`) and the two secrets, and run `docker compose up` ([the demo](#the-demo-with-docker-compose)). Without Docker: `composer install`, `php bin/console doctrine:migrations:migrate`, and the keys as described in [Configuring providers and API keys](#configuring-providers-and-api-keys).
2. **Choose the panel:** copy `config/intakt.example.yaml` to `config/intakt.yaml` and set the project's tiers and its `review:` section ([Capability tiers per project](#capability-tiers-per-project)); `php bin/console intakt:review:panel <project>` shows the panel a change would get without calling a model.
3. **Start the workers:** `php bin/console messenger:consume async` ([Background work](#background-work)); the container already runs them.
4. **Review a branch:** `php bin/console intakt:review <branch> --project=<project> --task="..."` ([Reviewing a branch](#reviewing-a-branch)) and read the outcome ([Reading a verdict](#reading-a-verdict)).
5. **Watch or script it:** the [dashboard](#the-dashboard) shows each round; an agent starts and reads reviews through [MCP](mcp.md).

What the guide covers today, feature by feature; the parts marked planned arrive later:

- Running the demo with `docker compose up`: it seeds a sample project and a sample repository with a change to review (see [The demo](#the-demo-with-docker-compose)); the timed run to the first verdict has its record in the [README](../../README.md#timed-run), still to be filled in by the owner
- Choosing a review panel by the size or paths of a change, and the dry run `intakt:review:panel` (see below). A project's panel and its quorum policy (`all`: every reviewer approves; `majority`: more than half approve; `one-strong-plus-one`: at least two approve, one of them a strong reviewer) are set in the configuration file (see below), and `intakt:review` runs it (see [below](#reviewing-a-branch)).
- Reviewing a branch of a local repository with `intakt:review` (see [below](#reviewing-a-branch)); reviewing a pull request is planned
- Checking whether a verdict still counts for a branch of a local repository, with `intakt:verdict:identity` (see [below](#checking-whether-a-verdict-still-counts))
- Watching a project's open pull requests: the code that lists them with conditional requests and returns only those whose head or update time changed exists, as does the code that reads a head's CI state and decides to wait (CI running, or a run cancelled and not run again), skip (CI red) or review (CI green), and a `watch` section makes a tick run them every minute (see [Capability tiers per project](#capability-tiers-per-project)); the GitHub App identity reads the pull requests and CI from GitHub for a project whose `watch` section names its `github` repository
- Project mode per project: `live`, the default, or `reviewer-for-loop`; `mode: shadow` is no longer a mode and stops Intakt from starting (see [below](#project-mode))
- Reviewer-for-loop mode per project: a project set to `mode: reviewer-for-loop` has Intakt's panel review the existing loop's heads in place of the loop's Claude reviewer; its verdicts count, and the only thing it writes to the forge is its verdict on each head, as a commit status `intakt/review` and one pull request comment (see [below](#reviewer-for-loop-mode))
- Running a job in a fresh container of its own, with its own memory limit and a check at start that its folders and allowed hosts work, and cleaning up after a crash with `intakt:job:sweep`; `intakt:check:run` runs the check before a push in one, and no build or review runs in one yet (see [Job containers](#job-containers))
- Checking a build's bundle before a push with `intakt:check:run`: the project's check in a fresh clone with an empty dependency cache, and a stop for a file that lost most of its content (see [The check before a push](#the-check-before-a-push))
- Scanning one GitHub Actions workflow file for anything beyond a hosted runner with a read-only token and no secrets, with `intakt:forge:workflow-risk` (see [below](#scanning-a-workflow-file-for-ci-risk)), listing the changed files that are part of the CI definition with `intakt:forge:ci-paths`, and scanning the head's, main's and the merged workflows of a change with `intakt:forge:ci-scan`, and holding a risky CI change until your `approve <sha>` with `intakt:forge:push-approval`, which shows its complete diff on the task's issue; no build calls it yet, since Intakt does not push builds yet (see [below](#holding-a-risky-ci-change-for-your-approval))
- Building a project's job image with `intakt:job:build-image`, from its devcontainer, its Dockerfile or `composer.json`, and checking that it has the project's PHP and extensions; no job uses such an image yet (see [Job images](#job-images))
- Taking tasks from GitHub issues, with `Waits for #n` holding a task until the named issues are closed, is planned. Intakt will learn whether a waited-for issue is closed only from the one list of open issues it reads each round (a list that comes back incomplete releases no wait), never by reading each waited-for issue on its own, and a worker with no room for new work will ask GitHub nothing, so routine reads do not use up GitHub's hourly allowance (see the [design](../design/05-architecture/03-choosing-work.md)).
- Looking at projects, reviews and the page of one review in the browser (see [below](#the-dashboard)); the button that starts the next round of a change is described [below](#the-dashboard)
- Connecting an agent through MCP: the owner's server answers `list_projects`, `review_status`, `review_verdicts` and `review_act_list`, serves a round's findings, and starts a review of a branch with `start_review` when the owner's token is sent and writes are allowed (see [Connecting an agent through MCP](mcp.md)); starting a review of a pull request is planned

The highlights page (the Symfony and Symfony AI features Intakt uses) is assembled from small pieces and published from main at <https://shinyredapples.github.io/intakt/> ([how](../architecture/highlights-page.md)); `bin/highlights` builds it locally as `docs/highlights.md`.

For whoever maintains a copy of the Intakt repository: [Running Intakt's CI on your own runner](self-hosted-ci.md).

## Reading a change from a local repository

Intakt can treat a branch of a local git repository as a pull request: the branch is the change and the repository's base branch is what it is compared with. It reads the branch's latest commit, the diff against the point where the branch left the base, the list of changed files and any file as it was at that commit (by its exact name, even one starting with `:`), ignoring git's replacement refs (`git replace`) and graft file (`.git/info/grafts`), which could otherwise show other content under the same commit or hide commits. It reads the repository with its own git settings: the repository's configuration and attributes cannot run a program (a hook, a filter, a diff or signature tool, or a fetch from a remote the repository names for an object it lacks: such an object is an error, never fetched) or change what is read, every file in the diff is shown as text, and the git configuration of the user running Intakt (`~/.gitconfig`, even a broken one) is not read. A repository whose `.git/info/attributes` file exists cannot be read, because that file could hide a change and git offers no way to ignore it: remove it first. It notices when the branch has moved to a newer commit since it was read. A name that is not a valid branch name (such as `../tags/v1`) is treated like a branch that does not exist. It only reads; it never changes the repository. `php bin/console intakt:change:summarize <branch>` prints what it reads (see [Summarizing a branch](#summarizing-a-branch)); for an invalid name it prints the same error as for a missing branch and exits with 1.

## The dashboard

Intakt serves five pages in the browser, built from the ledger of review events (no model call) and, for the forge budget on `/reviews`, from the budget GitHub's own answers last reported (no forge call). The dashboard's own address (`/`, for example `http://localhost:7781` in the container) shows the board: its nine columns (Waiting on you, Backlog, Ready, Planned, Building, Checking, In review, Merging, Done) side by side, each with its name and the number of cards in it across all projects. Each change under review is one card, in In review while its latest round runs and in Done once that round is judged; the card shows the change's number, its project, "Review of" the change, its round (with the word's explanation when you point at it), the number of reviewers and the cost so far, and opens the review page of its latest round. A round from before Intakt recorded its change shows its round id instead. Waiting on you is pinned as the first column and is a little wider than the others; it shows what the Waiting on you page will list, and since Intakt records nothing that waits for you yet, it says "Nothing needs you" and counts 0. The other six columns say "Nothing here" until Intakt takes in and builds tasks. The project filter hides the cards of other projects; the counts stay the totals. A column with more than 12 cards shows its first 12 and a **Show 28 more** button (the number is the cards left) under them, which shows the rest; with a project chosen, the 12 and the number count only that project's cards, the button disappears when 12 or fewer are left, and choosing a project never folds an opened column back. A long title wraps to at most three lines and a long change number or project name on a card is cut short with "…"; pointing at the number or the project name shows it whole. Backlog and Done start collapsed, each to a 108 pixel strip with its name and count side by side; clicking the strip opens the column with its cards, and **Hide** in its heading collapses it again (each page load starts them collapsed). On a phone (narrower than 761 pixels) they are not collapsed: every column shows its cards. **Open the review list** leads to `/reviews`. From 1700 pixels of width every dashboard page and its top bar leave 48 pixels at the sides instead of 32; the board has no maximum width and grows with the window at every width. On a phone the word "Round" on a card, which the keyboard reaches on its own, is 44 pixels tall like every other control; the board passes the UI check (below) at every width in both themes.

Above the columns, the board shows **Who is working**, a closed strip that says "N working" (or "Nobody is working yet"). Opening it lists the lanes: the reviewers still running in the latest round of each review that the judge has not decided, newest review first, each with its role, tier, the time it started (UTC), its change, its project and its round. The project filter hides the lanes of other projects, but the "N working" count stays the total over all projects. Build slots are not part of it yet, so there is no idle count.

Above Who is working, the board shows one red banner for each pull request whose head failed in the watcher (the same heads as "Pull requests that failed" on `/reviews`): "Pull request 7 of alpha failed.", then how many failures in a row and the next try (UTC), or that it was handed over to the maintainer agent, and the cause, with any credential in it replaced by `[redacted]`. **See the failed pull requests** opens that section of `/reviews`. The project filter hides the banners of other projects. The board does not update them live: a banner goes away on the next load of the board after the watcher reads the head again, starts its round or forgets the pull request. Below 761 pixels a banner is one line with the pull request and project; tapping it shows the rest, also on a board without the live connection, and tapping it again closes it.

Every page sits in the same frame. On the left, the menu shows the Intakt logo, which opens the dashboard's address, and one entry per page that is built: today **Board** and **Projects**, each highlighted while you are on it (Waiting on you, Team, History and Settings join them as their pages are built). **Collapse** at its bottom narrows the menu to its icons; this browser remembers it. The bar along the top holds the search field, with the hint `Ctrl K` (`⌘K` on a Mac): clicking it, or pressing Ctrl K (Cmd K on a Mac) on any page, opens the search window over the page (see Search, below). Beside it, the moon or sun button switches between the light and the dark look and remembers the choice in this browser. Below 761 pixels of width (a phone) the menu becomes a 68 px bar at the bottom of the screen, each entry an icon over its name, and the top bar holds only the logo (it opens the dashboard's address), a **Search** button (it opens the search as a full-screen sheet, described under Search below) and the theme button; the project filter is hidden there, so every project is shown, and the choice comes back on a wider window. History and Settings, once built, go behind **More** at the end of the bar, which opens a sheet with them above it (tap beside it or press Escape to close it); until then More is not shown.

- `/components` shows each building block of the dashboard (buttons, a button with only an icon, segmented tabs, filter chips, cards, banners and the one-line phone banner, inputs, a number stepper, a command with a Copy button, usage bars including a dimmed "Last known" one, and so on) in the light and the dark look side by side, with a "Switch theme" button that flips the look and remembers it in this browser. It loads no font, style or script from another website. The segmented tabs, the filter chips, the stepper and the Copy button only show how they look for now: no page uses them yet, so pressing one changes nothing. Nothing links to it yet.
- `/projects` lists the projects that started a review, one row each with its name and a line such as "2 review rounds, 1 judged." (how many rounds it has had and how many of them the judge has decided), or says "No project has started a review yet."
- `/reviews` lists every round, newest first, in a table with its project, its number of reviewers, when it started (UTC) and its state as a small label: **Judged** (with a check) once the judge has decided it, **In progress** (with a green dot) before. `/reviews?project=<name>` chooses that project in the top bar's project filter (below); each project on the first page links there. Above the rounds, under "Pull requests that failed", a card for each watched pull request whose head failed last time it was tried names the pull request and whether it is backing off or was handed over to the maintainer agent ("Pull request 7: backing off"), shows the cause in red, then the failures in a row and the next try (UTC); the card goes once the head is read, its round is queued or its pull request is closed. The cause is redacted like a log line, so a configured key or token never appears on it. When a GitHub App installation is set (`GITHUB_APP_INSTALLATION_ID`), the section "Forge budget this hour" at the top lists it with its calls used and calls remaining this hour, from the latest answer GitHub sent, and marks the forge reserve **In force: routine reads wait** while less than the reserve is left (see [Intakt's GitHub App](#intakts-github-app)), else **Not in force**; before an answer of this hour reported the budget it says "No reading this hour". The section shows what was known when the page loaded; reload to see newer figures.
- `/search?q=<words>` answers the search window of the top bar: not a page but a piece of one, a list of results in groups, in this order: **Actions**, **Reviews** (each round as "Round <id>" with its project and state, linking to its review), **Projects** (each with its number of review rounds, linking to its reviews) and **Pages** (Reviews, Projects and Components). Words are separated by any white space, including a no-break space or an em space, and spaces of that kind at the start or end of what you typed are ignored. A result is found when every word you typed appears in its name, its line under the name or its group's name, in any case; each group shows at most 10. Every result names its project, or says "All projects". With no words it shows **Recent**, the 5 newest review rounds, then the actions. When nothing matches it says "No results for" your words, suggests what to try (a project of yours by name, a round id or a page), and offers **Clear the search**, which asks again with no words. The only action today is "Switch light or dark theme".
- **Search**: the search window opens over the page, which stays behind a dark veil and cannot be reached until the window closes. The cursor is in its field, which starts empty and shows Recent and the actions; every letter you type asks `/search` again and shows its groups. The first result is highlighted: the Up and Down arrows move the highlight (past the last result it starts again at the top), Enter opens the highlighted result (a review, a project's reviews or a page) or runs it ("Switch light or dark theme" switches the look and closes the window), and Escape, Ctrl K (Cmd K) again or a click beside the window closes it and puts the cursor back where it was. A click on a result does the same as Enter, and pressing the mouse on a result leaves the cursor in the field, so the arrows and Enter keep working after it. Until the results for what you just typed have arrived, the arrows and Enter do nothing, so Enter never opens a result for other words. If you type with an input method that composes text, such as Japanese, Chinese or Korean input, Enter and the arrows go to it while it composes, so Enter confirms your text instead of opening a result. Tab stays inside the window. When nothing matches, **Clear the search** empties the field and shows Recent again. If Intakt does not answer, the window says "Search did not answer."; typing again asks again. On a phone (narrower than 761 pixels) the window fills the whole screen, shows a **Cancel** button next to the field instead of the key hints, and has result rows at least 52 pixels tall; Cancel closes it like Escape does, and Tab then also stops on Cancel. Matching words are not highlighted in the results yet.
- `/reviews/<round id>`, linked from each round on `/reviews`, shows the whole review the round belongs to: every round of the same change in the same project, in round order. Under the title, a meta line names the project, the change (in full, never cut) and when the latest round started (UTC). While the latest round is not judged yet, a current state block, "Now: round N in review", shows how many of its reviewers finished, each reviewer's role, tier, state and verdict, the open findings (the findings the judge marked `act` in the newest judged round, each linking to its row in the timeline below; "No finding is open." before any round is judged) and that the judge has not judged the round yet; on a page the live updates reach, the finished count changes as reviewers answer, a stopped reviewer turns `stopped`, and once the judge decides the heading says "judged" and the block asks you to reload for the judge's call. Under "Timeline", every round the judge has decided is folded to one line (its outcome, or `outcome not recorded`, its number of findings, and the time it started and the time it was judged, in UTC), which you open with a click; a round judged before Intakt kept the findings says `findings not recorded` there instead of a count, with how many ids the judge marked (`2 marked by the judge`) when it marked any; the round still running stays open. While the latest round is not judged, a "Live log of round N" panel sits beside the timeline (under it on a screen 1100 pixels wide or narrower; on a phone, 760 pixels or narrower, a Timeline and Live log switch that stays under the top bar shows one of the two, the timeline first, and choosing a finding id brings the timeline back when the finding has an entry there (a finding of a round still running has none yet, so the live log stays); from 1500 pixels wide the page grows and the log scrolls within 520 pixels, and from 2200 pixels wide the session summary below becomes a column beside the log) with each started reviewer's tool calls and text; before any reviewer starts it says they will appear there, and once every round is judged the timeline takes the whole width. A session summary stays at the bottom of that panel while the log scrolls above it: the round's tool calls by kind with their total (just "No tool call yet." until there is one), the cost of the round and of the whole review so far, each file the reviewers read, and the findings this round (each open finding the round checks, marked `Checked, resolved` once the round resolved it or `Open`, and each other finding it reported, marked `Reported`; reported findings appear once every reviewer is in). Choosing a finding id there highlights that finding's entry in the timeline, opens its folded round and scrolls to it, moving the highlight off the earlier one, also on a page the live updates do not reach; a finding the judge has not marked yet has no entry, so nothing changes. The figures come from what Intakt recorded for the round, summed over its reviewers, kept up to date on a page the live updates reach: the tool calls, the cost of the round, the files read and the findings change as the reviewers work, without a reload (the cost of the whole review so far changes after a reload). Without the live updates the page shows them as of when you loaded it. A tool call whose record could not be saved is left out of those figures (the reviewer carries on and gets its answer as usual, and Intakt logs an error), so a total can be one short. A round Intakt holds no record of says so instead. For each round: its number with its state label beside it (as on `/reviews`), then its id and start; each reviewer that started, with its role, tier, state (`running`, `verdict`, `failed`, `blocked` or `stopped`), its verdict (shown without a mark, also one recorded while the project was in the former shadow mode) and number of findings, and why it failed or was blocked, or the substitute that answered for it (a failure in plain words, such as `stopped at its output limit`, never an error's class name); once the judge has decided, the round's outcome (`approve`, `changes` or `blocked`), decided by the panel's quorum policy over all its reviewers exactly as `intakt:review` decides it, with how many reviewers failed: a failed reviewer gives no approval, so a two-reviewer panel never quietly becomes a one-reviewer approval (a round started before Intakt recorded its quorum policy says so instead of an outcome, and the outcome appears when you load the page after the judge, not through the live updates); once the judge has decided, every finding with its id (`F1`, `F2`, ...), severity and text, and the judge's call on it (`act`, `follow-up`, or `rejected or unmarked`); and the tokens the round's model calls used (prompt, cache read, cache write, cached, completion and total, the same figures as the [token line](#reviewing-a-branch) of `intakt:review`). The top of the page gives the number of rounds, the tokens and the cost of all of them. Cost is the figure `intakt:review` prints for the round, at the prices in your settings; for a model with no price it says `unknown, no price for <model>`, and for a call whose provider reported no input tokens it says plain `unknown`, never 0 and never an estimate. A round judged before Intakt recorded the findings themselves says so and still lists the ids the judge marked `act` or `follow-up`, with `not recorded` for severity and text; it never claims the reviewers found nothing. A round started before Intakt recorded the change's name in the ledger is shown as a review of its own. A running reviewer in an unjudged round has a **Stop this reviewer** button: it asks the reviewer to stop, and the reviewer ends at its next progress update with the verdict `blocked` (the finding `reviewer-stopped`) and the state `stopped`, without a reload on a page the live updates reach (after a reload otherwise); a stopped reviewer has no button. While a reviewer of the unjudged latest round is running, a **Stop** button at the top right asks every reviewer of that round that is running at the press to stop, the same way; like **Stop this reviewer** it asks for a second click first ("Click again to stop the round"). A reviewer that has not started at the press is not asked, and starts as usual. On a page the live updates reach, the button appears without a reload when a reviewer that starts after the page loaded shows its first tool call or text, and goes away without a reload once every reviewer has finished or the judge decides (on a page the live updates reach). An unknown round id gets `404 Not Found`.

The pages answer only an address on the computer itself: `localhost`, `127.0.0.1` or `[::1]` with the dashboard's port, which is `DASHBOARD_PORT` (default 7780, set it to the port you publish on the host). Any other address in the request, or another port, gets `400 Bad Request` and no data, so a web page that points its own name at your computer cannot read them. Every page comes in a light and a dark theme: it follows the browser's light or dark setting (`prefers-color-scheme`) unless a theme was chosen and stored in the browser (`localStorage`, key `intakt-theme`) with the theme button in the top bar of every page or the "Switch theme" button on `/components`. The top bar also holds the project filter, a select of All projects and every project of `/projects` in name order: choosing a project hides the rows of every other project on `/projects` and `/reviews` and its failing-head cards, in the browser without reloading, and the browser stores the choice (key `intakt-project`) for every page; a stored project that is no longer listed counts as All projects. A `/reviews?project=<name>` address with the exact name of a listed project (`1` is not `01`) overrides and replaces the stored choice; choosing another project there removes `project` from the address, so a reload keeps the new choice. When a project starts its first review round, a worker (see [Background work](#background-work)) sends the filter's list again over the live connection (below), so an open page's filter lists the new project without a reload; a round of a project already listed sends nothing; the filter keeps the project you chose in that tab and the rows stay filtered by it, and shows All projects (with every row) only when the new list no longer names your project; the stored choice is never changed by a pushed list, and when the live connection is down the filter simply keeps working as before. On a phone every page is laid out at the phone's own width (`<meta name="viewport" content="width=device-width, initial-scale=1">`), so the phone layout of the building blocks (larger controls, one-line banners) applies. Its fonts (Outfit, Atkinson Hyperlegible Next, Atkinson Hyperlegible and JetBrains Mono, each with its license under `assets/fonts/`), styles and scripts are served by Intakt itself, so a page asks no other host for anything. The shared building blocks of the coming pages are built (buttons, chips, counts, cards, list and setting rows, inputs, bars, banners, sub-tabs, toasts with Undo, explained terms, loading, error and empty states): a danger button asks you to click again before it acts and forgets that after 4 seconds, a toast disappears after 5 seconds unless the pointer or focus is on it, and on a phone a banner shrinks to one line that opens when tapped. The `/components` page shows them all, light and dark side by side, with the hover, focus and pressed look of buttons, cards, inputs and tabs held on show (no other page does that), and gives every field, select and switch on it a name a screen reader reads out. `/projects`, `/reviews` and the review page use them: each opens with its title and a short line under it, projects are list rows, failed pull requests are cards, states are labels, tables have quiet headings and lines between rows (on a narrow screen a wide table scrolls sideways, and Tab stops on each table so the arrow keys scroll it), an empty list shows an empty state, the start button is a primary button and "Stop this reviewer" a danger button, which asks "Click again to stop" first, also on a page without the live connection. The list pages are plain HTML, apart from the small script in the page head that picks the theme, the one after the page that runs the menu, the theme button, the search hint and the project filter, the one in the page head that makes a danger button ask first and opens or collapses a board column and a phone banner and switches a review page between its timeline and live log on a phone (all only answer clicks) and runs the search window (it asks `/search` only while you search), and, when the live-update hub can authorize a listener, Turbo and Stimulus from the import map for the live connection (see below); they never refresh themselves: reload them to see newer rounds. The review page of a round that is not judged yet listens to the live-update hub and changes by itself (see below). On `/reviews`, two rounds of one change appear as two rows of the same project; both link to the same review page. On a review page, the button "Start the next round on the current head" starts the change's next round from the repository and base recorded when its latest round started, then returns to the page with a line naming the new round (or the reason it could not start). The button asks for the number after the latest round the page knows, so pressing it twice, or pressing it on a page opened before another round started, starts nothing and says that another round took the number. The repository is recorded as an absolute path, so a round started with `--repository=.` restarts from the same repository. Rounds started before Intakt recorded the repository, base and task show a note instead of the button. The round runs in the workers; the new round's page shows its progress live, and a reload always shows what the ledger holds. Its reviewers read a snapshot of the head in the system's temporary directory (`intakt-kept-review-*`), which Intakt removes once the round is judged; a round that is never judged keeps it, and `git worktree remove --force <path>` removes it. Until the owner login is built, anyone who can reach the dashboard's address on the computer can press the button. Each reviewer that is still running in a round that is not judged has a "Stop this reviewer" button in its row. Pressing it records a stop request in the ledger (`reviewer_stop_requested`, naming the round and the reviewer) and returns to the page with a line saying so; a reviewer that has already answered, failed or been blocked, or a judged round, has no button and a post for it is refused with `404`. The worker running that reviewer looks for the request each time the reviewer reports progress (a call to the model, a tool call, a piece of streamed text) and stops it at the next one; a stop pressed while the reviewer waits to be tried again, or before its call to the model starts, still lands at its next progress update. A model that reports nothing for a long time (one long answer that is not streamed) stops only once it reports progress or answers. The stopped reviewer's verdict is `blocked` with the reason `reviewer-stopped`, and the ledger records `reviewer_stopped` (round and reviewer); a stop request that was answered this way never stops a later run of that reviewer. The page then shows the reviewer's state as `stopped` with its verdict `blocked` and no button, live while it is open and after a reload; a reviewer that the model reports as stopped without your request is never shown as `stopped`. Like the start button, it needs no login until the owner login is built.

### Live updates (in progress)

While a review runs, Intakt sends each reviewer's tool calls, its text and each round's progress ("1 of 2 reviewers finished", "Judged") to the live-update hub built into FrankenPHP. A reviewer's text is sent as it is written, in pieces at most four times a second per reviewer, plus one last piece when the reviewer finishes its answer. The review page of a round that is not judged yet shows them without a reload: the round's "N of M reviewers finished" line, each finished reviewer's state ("verdict", "failed", "blocked" or "stopped") in the reviewer table and in the current state block, the same count in the block (and "judged" in its heading once the judge decides), and, in the live log beside the timeline, each started reviewer's tool calls and text. A reviewer that starts after you opened the page appears with its first tool call or text, under a heading that does not name its role until you reload, and gets a row in the current state block (`running`, or its state once it finishes or is stopped), named by its reviewer id instead of its role and tier until you reload. Every dashboard page (the project list, the review list and the review page) also opens one live connection that listens to the shell topic `dashboard/shell`, and gets the same permission on every page, which covers the shell topic and every round's updates, so opening a list does not stop a review page in another tab from updating; only the project filter's list is published on it so far (when a project starts its first review round); the filter gains the new project and keeps the project this browser tab chose, so the lists do not change by themselves, and the review list and the project list show only what the ledger holds, also when the hub is down. The page needs a browser with JavaScript for this; without it, or when the hub is not running or `MERCURE_JWT_SECRET` is not set, the page shows the same state as the ledger on every reload and nothing else breaks. When the page loses its connection to the hub, a line at the top of the page says "Reconnecting." with the time it was lost, and counts down to the next try, every 5 seconds (Try now tries at once; a try still waiting for the hub's answer is left to finish); the top bar shows "Offline" (not on a phone). After two minutes the line turns red and says "Can't reach Intakt." Both go away once the connection is back, and if the page had received an update before the drop, the updates sent in the meantime follow. While the line shows, it adds that actions wait until the connection is back: the buttons that change something (Start the next round, Stop, Stop this reviewer) are disabled, and enabled again once the connection is back; a button that was already disabled stays so. An elapsed time, such as "42 min", shows the time of the drop beside it ("42 min at 11:12") until then; no page but the components page shows one yet. To run the hub, set `MERCURE_JWT_SECRET` (at least 32 characters) in `.env.local` and start FrankenPHP from the repository with `frankenphp run --config Caddyfile --envfile .env.local --envfile .env`. FrankenPHP does not read the `.env` files on its own, and the first file that sets a value wins, so `.env.local` comes first. The same command also serves the dashboard in worker mode on port 7781 (`SERVER_PORT`), in the `dev` environment `.env` sets; because `.env` sets `DASHBOARD_PORT=7780`, its pages answer `400 Bad Request` there until `.env.local` sets `DASHBOARD_PORT=7781`. FrankenPHP's admin API answers on `localhost:2019` only, where `intakt:server:status` reads it. If the hub is not running, reviews are not affected: the update is dropped and a warning is logged. Intakt also has a general way to send updates to the other dashboard pages, which the project filter uses (the Waiting on you count is planned to); it works the same way: when the hub is not running or refuses the update, the update is dropped, the warning "A live dashboard update was not published." is logged, and the page or work that sent it carries on. A `docker build` or an install from the repository needs `php bin/console importmap:install` once, to download Turbo for the dashboard pages that listen for live updates.

### The status document (in progress)

Intakt can describe what it is doing as one JSON document, the status, which the owner's own dashboard reads until Intakt's dashboard replaces it. Its fields are documented in [status.schema.json](status.schema.json), a JSON Schema, and Intakt's tests check every document they build against that file. Print it with `php bin/console intakt:status --format=json` (JSON is also the format when `--format` is left out, and any other format is refused with an error): the command writes the document as one line and exits with 0. A local address that serves it comes next. The status is read from Intakt's database only, so it still answers while no worker runs; a stopped worker then shows as messages waiting in a queue.

- `generated_at`: when the status was read (UTC).
- `holds`: the install-wide holds in effect (`drain`, `failure-back-off`, `pause`, `budget-back-off`), the one that wins first. Only the name is given, never when it ends.
- `queues`: each background queue with the number of messages waiting for a worker (`async`, `failed`), or `null` for a queue that cannot count them.
- `projects`: one entry per project the watcher watches or the ledger names, by name. Each has:
  - `lanes.review`: the review rounds in progress, newest first, each with its change, round id and number, start, its number of reviewers and one step per reviewer a worker has started (role, tier and `running`, `verdict`, `failed`, `blocked` or `stopped`). Fewer steps than reviewers means the others still wait for a worker.
  - `guard_decisions`: the pull requests the watcher holds back: `pending` (CI still runs, with when it reads again), `red` (CI failed) or `failed` (the head could not be read, with the cause, the failures in a row and the next try).
  - `waiting_for_owner`: the changes on the board's Waiting on you column; empty for now, since Intakt places nothing there yet.
  - `needs_you`: the pull requests handed over after repeated failures, with the cause and the failures.
  - `last_outcomes`: the last judged round of each change, newest first, at most ten, with its outcome (`approve`, `changes`, `blocked`, or `null` for a round started before Intakt recorded its quorum policy) and when it was judged.

The status carries no secret: a failure cause is redacted like a log line, so a configured key or a token in it shows as `[redacted]`, and holds and back-offs carry no end time.

### Checking the pages with the UI check

`bin/ui-check` opens every dashboard page in a headless browser, in the light and the dark theme, at 1440, 1920 and 390 pixels wide: `/` (the board), `/components`, `/projects`, `/reviews`, the search window open on `/reviews`, and the page of the first round `/reviews` lists. For each it reports the accessibility violations axe finds, counted by impact (critical, serious, moderate, minor) with the first elements each one names, and at 390 wide every visible text under 15 px (the text typed into a field, or its placeholder, too) and every button, link, field, search result or other control under 44 px tall (a control counts its label's height; a link inside a sentence is not counted). It saves a full-page screenshot of each as `var/ui-check/<page>-<theme>-<width>.png`, replacing those of the last run. It ends with exit code 0 when nothing serious or critical, no floor finding and no page error (a page that did not answer with success, a script error, or the wrong theme) was found, 1 otherwise, and 2 when it could not run (no browser, nothing answering at the address, or no review round to open).

It needs Node.js 22 or later, Playwright and axe-core, and a running dashboard with at least one review round:

```sh
NODE_PATH="$(npm root --global)" bin/ui-check http://localhost:7780
```

The address defaults to `http://localhost:7780`. `CHROME_PATH` names a Chrome or Chromium to use in place of Playwright's own browser.

## Running the container image

The `Dockerfile` builds an image with Intakt on FrankenPHP in worker mode, with the live-update hub built in. To check an image you built, run `docker/smoke-test.sh <image>`: it starts the image with throwaway secrets and checks that the dashboard answers, that MCP requests go to their own worker, that the server runs as an unprivileged user and that the admin port stays inside the container, then removes what it started. CI builds the image and runs this check on main and on every pull request that changes more than `docs/`, `tests/` or `upstream/` (the `image` job in `.github/workflows/ci.yml`). Every release also publishes a checked image, `ghcr.io/shinyredapples/intakt:<version>` and `:latest` (see [Releasing](../releasing.md#the-container-image)); use it instead of `docker build` when you run a release. Between two requests the worker clears the signed-in user, the database entities it loaded and the other per-request state of Intakt's own services, so one browser never sees another's flash messages or data. Each request also starts with the file permission mask (`umask`), locale and environment variables the worker started with, whatever the request before changed. The same reset runs between two messages of a consumer, so a reviewer's model, tools and conversation stay with its own review: the next one connects to the review tools again and sends only its own model, tools and messages (checked by `tests/Application/SymfonyAiResetTest.php`). A test in the repository (`tests/Application/WorkerModeTest.php`) checks the rest, both as the image runs and with `FRANKENPHP_RESET_KERNEL=1` (a fresh copy of Intakt's kernel for each request). The image does not set it.

```
docker build -t intakt .
# fails if the base image's PHP is below 8.5.12
docker run -d --name intakt -p 127.0.0.1:7781:7781 -v intakt-data:/app/var/data \
  --env-file intakt.env intakt
```

- The secrets are never in the image. `intakt.env` (yours, not in the repository, and left out of the build like `.env.local` and `.env.local.php`) must set `APP_SECRET` and `MERCURE_JWT_SECRET` (at least 32 bytes); the container refuses to start without them, and names the one that is missing. Nothing else is required: the image sets defaults for `MERCURE_JWT_ISSUER` (`http://localhost:7781`), `SERVER_PORT`, `DASHBOARD_PORT` and the other values in its `ENV` lines. When you serve the dashboard from another address, set `MERCURE_JWT_ISSUER` and `MERCURE_PUBLIC_URL` to the address your browser uses. Before it starts the web server, the container asks FrankenPHP to check the Caddyfile and prints the reason when it is rejected.
- Publish the port on `127.0.0.1` only (`-p 127.0.0.1:7781:7781`): the dashboard has no login yet, and a plain `-p 7781:7781` opens it to every network the host is on, where a client can send `Host: localhost:7781` itself. Keep the same port inside and outside: the dashboard answers only `localhost`, `127.0.0.1` or `[::1]` with its own port (see [the dashboard](#the-dashboard)), and the image sets `DASHBOARD_PORT` and `SERVER_PORT` to 7781.
- The database (SQLite) and the hub's history live in `/app/var/data`. Mount a volume there (`-v intakt-data:/app/var/data`): the image declares none, so without it they are lost with the container. The container runs as the user with id 10001, so a bind-mounted folder must belong to that user. It applies the migrations on every start, then serves `/projects`.
- Two worker pools serve requests: `app` for the dashboard, and `mcp` for `/mcp/*` with its own thread limits (`MCP_WORKERS`, `MCP_MAX_THREADS`), so a streamed MCP answer cannot take the dashboard's threads. `APP_WORKERS` sets the dashboard's pool, `MAX_WAIT_TIME` how long a request waits for a free thread.
- FrankenPHP's admin API listens on `localhost:2019` inside the container and nothing publishes it; read it with `docker exec intakt php bin/console intakt:server:status`.
- A worker is replaced after `FRANKENPHP_LOOP_MAX` requests (default 500) and when it holds more than `WORKER_MEMORY_CEILING_MB` megabytes (default 256) after a request; it finishes sending the answer first, so no request fails. A crash is restarted by FrankenPHP itself.
- The queue workers and the scheduler (see [Background work](#background-work)) run in the same container, beside the web server: `MESSENGER_CONSUMERS` workers (default 3, so the reviewers of a panel of three run at once) and one scheduler. When one of them stops, for any reason, it is started again a second later and the container logs `intakt: async ended with status 137, starting it again` (`scheduler_watcher` for the scheduler). A worker also ends on purpose after an hour or once it holds more than `WORKER_MEMORY_CEILING_MB` megabytes, between two messages, and is started again the same way. `docker stop` lets each worker finish the message it is on for up to 8 seconds, then stops what still runs; a message cut off is handed out again later.
- Start the container with `--restart unless-stopped`, so Docker starts it again after a crash or a reboot. When the web server itself stops, the container stops the workers and the scheduler and exits, so this restart brings all of them back. The image has a health check that asks FrankenPHP's metrics endpoint every 30 seconds; read it with `docker inspect --format '{{.State.Health.Status}}' intakt` (`healthy` or `unhealthy`).

## Checking the server

When Intakt runs under FrankenPHP, `php bin/console intakt:server:status` reads FrankenPHP's admin API and prints how many worker threads are busy and idle, how many requests wait in the queue, how often workers were restarted, and whether the Mercure hub is healthy:

```
worker threads: 0 busy, 2 idle
queue depth: 0
worker restarts: 2
hub: healthy
```

Run it inside the container, because the admin API answers only there. It reads `FRANKENPHP_ADMIN_URL` (default `http://localhost:2019`), which must be plain `http` on `localhost`, `127.0.0.1` or `[::1]`; any other address is refused before anything is sent. A value that cannot be read shows `down` with the reason (the server did not answer, answered with an error status, or answered something Intakt cannot use), and the command then exits with a non-zero code. A thread that is starting or restarting counts as neither busy nor idle.

## Background work

Intakt has two internal message buses, one for commands and one for questions. A command handler cannot answer a question and the reverse.

A review round sends one message per reviewer to a queue, and workers take them from it, so the reviewers of a round run at the same time. It also queues one message that has a worker send the dashboard's project filter again when the round is its project's first; a round that is undone before it is stored leaves none of these messages behind. The queue is a table in your database (`MESSENGER_TRANSPORT_DSN`, `doctrine://default` unless you change it in `.env.local`), created by `php bin/console doctrine:migrations:migrate` together with the other tables. Start as many workers as you want reviewers to run at once:

```
php bin/console messenger:consume async
```

The state of a round and of each reviewer is stored in the database, and so are the waiting messages. If a worker stops, start it again: the reviewers still waiting run, and a round whose last reviewer has finished is completed. A reviewer that was in the middle of its review when its worker stopped keeps its place for one hour from its start, so a message that reaches another worker in that hour (the same message is handed out again after ninety minutes) waits until the hour is over; then the reviewer is started again once. If its worker stops a second time, the reviewer is recorded as blocked (`reviewer_blocked` in the ledger, readable with `php bin/console intakt:ledger:events`) and the round goes on without it. A review that takes longer than that hour counts as failed too: an answer that arrives after the hour is dropped and the reviewer is recorded as failed, even when no other worker got the message. A reviewer whose call to the model fails for any reason is recorded as failed too, with the kind of failure (for example a refused key), and the round goes on. A reviewer whose result could not be written to the ledger goes back to the queue and is reviewed again. A reviewer whose call the provider limits (a rate limit or quota) goes back to the queue and its message comes back after the time the provider named, or, when it named none, after a wait that starts at about one second and doubles each time up to at most one minute; a failed attempt does not use up the one restart of a stopped worker. At most 3 calls run at the same time for one provider account (`intakt.vendor_account_parallel_calls` in `config/services.yaml`); a further reviewer waits in the queue the same way. A message that Messenger gives up on (it lands in the `failed` queue, shown by `php bin/console messenger:failed:show`) makes its reviewer blocked, which counts as finished, so the round still completes. If the reviewer cannot be blocked for any reason (the ledger cannot store it, the reviewer is no longer in the database, the database fails), the worker logs an error naming the reviewer and keeps running; the message still lands in the `failed` queue, and `php bin/console messenger:failed:retry` runs it again. `php bin/console intakt:review` starts a round and waits for these workers (see [Reviewing a branch](#reviewing-a-branch)).

## Checking that an install boots

After `composer install`, `php bin/instance` starts Intakt on a local port with a scratch SQLite database, checks that it answers, stops it and removes everything it created. Without `TMPDIR` it keeps its scratch files in `var/`; a `var/` folder that the run created is removed again when it is empty, and one that existed before is left in place. If it cannot create its scratch folder, the reason names the cause, for example `cannot create the scratch directory: mkdir(): Permission denied`, or `unknown reason` when the system gave none. It needs no network. Descriptor 3 receives one line, `{"status":"ready"}` or `{"status":"failed","reason":"..."}`, for example:

```
php bin/instance 3>&1 >/dev/null
```

The exit code is 0 only when the status is `ready`. The server log goes to standard output.

When `frankenphp` is on your `PATH` (as in the container image), `bin/instance` serves the app with FrankenPHP in worker mode instead of PHP's built-in web server, and the line says so: `{"status":"ready","mode":"worker"}` or `{"status":"failed","mode":"worker","reason":"..."}`. A line without `mode` means the built-in server.

Descriptor 3 can be a pipe, a file or a memfd (an anonymous in-memory file, as a supervising program may pass). A memfd named exactly `opcache_lock` is not accepted, because PHP's OPcache uses that name for its own lock; any other name works. When descriptor 3 is not open, or is not accepted, no line is written and the exit code is 1.

Intakt can boot a commit of a project's local repository the same way: in a scratch copy of the commit it runs `composer install` (without the commit's Composer scripts) and then `bin/instance`, taken from main for a pull request's head, so a head that changes `bin/instance` cannot pass its own check. Both get only basic environment variables (such as `PATH` and the proxy settings) and an empty scratch home instead of the install's `HOME` and Composer home, so neither Intakt's own keys and tokens nor the Composer `auth.json` of the install are handed to them. This is not a sandbox: the commit's code still runs as the same user on the same machine and can read its files on purpose; isolating it is a later part ([Boot step](../architecture/boot-step.md)). The result is booted, failed (with the reason `bin/instance` or Composer gave) or crashed (the boot step itself could not run, for example because the commit is missing); a crash never stops the review. Main's result is kept per project, main commit and tool fingerprint, so main is booted again only when its commit or the tools change, and the ledger records `boot_result_computed` each time it is computed (a crashed boot is not kept, so it is tried again). Nothing runs this step before a review yet: that part of the boot gate comes later ([Boot step](../architecture/boot-step.md)).

## Walking the user journeys

`bin/check --journeys` checks the product as a whole: for each journey in `tests/Journeys/` it boots a fresh instance with `bin/instance`, walks one path a user takes through the pages and the console, and checks what the user sees. Today there are two journeys. First install and setup: the database is created, the projects page is empty, the sample project is seeded (a second seed keeps it), and the reviews page is empty. Live review progress on the dashboard: the watcher starts a review round on a recorded pull request of the sample project, the review page shows it in progress, every live update the round sends fits that page until the judge has ruled, and the page shows it judged (whether the browser subscribes to those updates is checked by a separate test). They need no network and no keys. Each journey has up to 240 seconds, and anything it leaves running is stopped with its instance.

The option runs alone (`--fast`, `--only`, `--skip`, `--base` and `--test-merge` are refused with exit code 2), and neither `bin/check` nor `bin/check --fast` runs the journeys. A passing run ends with `{"result":"pass","failed":[]}`; a failing journey is one finding that names its file, the journey, the step that broke and the first line of the reason, for example `FirstInstallJourneyTest.php: journey "first install and setup" failed at step "open the reviews page": Failed asserting that ...`. The plain-words guide is [Checking the whole product](../guide/checking-the-whole-product.md).

`bin/journey-alarm [--run=<https link>] [<file>]` reads that output (from the file, or from stdin) and, when journeys failed, files one task on the repository named by `GITHUB_REPOSITORY` through `gh` (labels `priority:urgent` and `ready`, the failing journeys, their steps and the last 40 lines of the output, and the run link when given). A later red run replaces the body of that task, found by the hidden line `<!-- intakt:journey-alarm -->` in it, instead of filing another. Two runs at the same time on one computer take turns, and a run that finds an older task filed meanwhile closes its own as a duplicate. A green run files nothing and exits 0; output with neither a failing journey nor a pass, or a failed journeys gate whose findings name no journey, exits 1 with a message, as does a failing `gh` call or a missing token; a file it cannot read, an unknown option or a `--run` that is not an https link exits 2. Set the token in `GH_TOKEN` or `GITHUB_TOKEN`: without one the command stops before calling `gh`, so a stored `gh` login is never used.

`bin/journey-alarm --timed-out [--run=<https link>] [<file>]` is for a run stopped at its time limit.
It skips parsing the output, so a cut-off or empty output files or updates the same task instead of exiting 1.
That task is titled `fix(journeys): the journeys run timed out on main` and says the run timed out instead of listing journeys.
Without `--timed-out`, the command behaves as described above.

Intakt's CI runs the journeys on main every night and whenever someone starts the `journeys` workflow by hand ("Run workflow", or `gh workflow run journeys.yml`), never on a pull request. A red run files one urgent task, or updates the one already open while the journeys stay red ([Running Intakt's CI on your own runner](self-hosted-ci.md)).

## Regenerating the journey page

`bin/journey` rewrites the "At a glance" and milestone tables of `docs/journey.md` (the page that tells how Intakt was built) and leaves every other line of the page as it was. It reads the milestones, issues and pull requests of the repository named by `GITHUB_REPOSITORY` (`<owner>/<name>`) through `gh`, and the token counts in `docs/journey/usage.jsonl`. Set the token in `GH_TOKEN` or `GITHUB_TOKEN`: without one the command stops before calling `gh`. `bin/journey --recorded=<folder>` reads `milestones.json`, `issues.json` and `pulls.json` from that folder instead, with no network and no token. It prints `docs/journey.md regenerated`, or `docs/journey.md is current` when nothing changed, and exits 0. A missing marker pair, a GitHub answer or usage line it does not accept, a failing `gh` call or a missing token exits 1 with a message and writes nothing; an unknown option exits 2. The technical description is [The journey page](../architecture/journey-page.md).

## The log

Intakt writes its warnings and errors to the service output (the journal, or `docker logs`), one JSON line per record: `time`, `level`, `message` and `context`. The context names the item a failure belongs to (for example `reviewer`, `round`, `call`, `project` or `account`), and a failure carries the exception's `class`, `message`, the `at` line and the `trace` (the file, line and function of each call, never the values passed to it), with the earlier exception it wraps under `previous`. Before a line is written, the credentials Intakt holds, whether set in the environment or in Symfony secrets (`APP_SECRET`, `MERCURE_JWT_SECRET`, `MCP_OWNER_TOKEN`, `GITHUB_APP_PRIVATE_KEY`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENAI_COMPATIBLE_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `HF_TOKEN`, and the same names with an account name appended, such as `ANTHROPIC_API_KEY_TEAM`), the userinfo of a URL (`https://user:pass@host` is written `https://[redacted]@host`), the values of authorization and cookie headers, and secret-shaped strings are replaced with `[redacted]`. This applies to context names too; when two names end up the same, the later one gets a number (`[redacted] 2`), so no value is lost from the line.

## Finding the slowest tests

When the `tests` gate of `bin/check` runs, its line also lists the ten slowest test files under `slowest`, slowest first, each with its `file` and its `seconds` (the times of all its tests added up, over all test passes, including the run of the `serial` tests). For example:

```
{"gate":"tests","ok":true,"findings":[],"omitted":0,"slowest":[{"file":"tests/Application/InstanceTest.php","seconds":45.722},...]}
```

The time of every test file, not only the ten slowest, is kept in `tests/durations.json` in the gates cache: the folder `INTAKT_GATES_CACHE` names, or `intakt-gates` in the system temp folder when it is not set. Each run replaces the file. A test file outside the project folder is left out of both the file and the `slowest` list, so no path of your machine shows up in them. The times never change whether the gate passes; when the cache folder cannot be written, the file is simply not written.

## The PHP profile and the environment gate

The profile of the PHP that builds, reviews and CI use is in the repository: `config.platform.php` and the `ext-*` entries under `require` in `composer.json`, and the ini settings in `config/gates/php/check.ini` (for example `zend.assertions=1`). Load the settings by adding `config/gates/php` to `PHP_INI_SCAN_DIR`, after the directories PHP already scans. A leading `:` keeps PHP's own directory first, so from the project folder:

```
PHP_INI_SCAN_DIR=":$(pwd)/config/gates/php" bin/check
```

`bin/check` runs the `environment` gate first in every run, the full one and `--fast` (not `--journeys`, which keeps its own selection). The gate (the `EnvironmentGate` class) checks the running PHP against that profile. `bin/check` neither restarts PHP nor changes its ini scan path, so a run without the profile loaded fails the `environment` gate as soon as your PHP differs from it. Each finding names one difference: a PHP older than the platform version, a missing extension, a setting that differs from the check ini (for example `PHP setting zend.assertions is -1 but config/gates/php/check.ini says 1`), or a setting in the check ini that the gate does not allow. When a setting differs, the gate also says how to load the profile.

## Running the tests in parallel

The `tests` gate runs the test files in several workers at once: one for each processor it may use, at most four, and no more than a CPU quota of its container allows (rounded up). Each worker takes the next file from one shared list, which starts with the files that have no recorded time yet (new ones), then the files that took longest in the last run (from `tests/durations.json` above). Set `INTAKT_TEST_WORKERS` to choose the number of workers yourself (from 1 to 127; any other value fails the gate); `INTAKT_TEST_WORKERS=1` runs each test pass in a single process, as before. A finding names the pass and the file it came from, for example `sqlite tests/Core/ReportTest.php: ReportTest::testRuns: ...`. A failing, skipped, risky or incomplete test, or a warning, notice or deprecation, fails the gate in any worker, as does a warning PHPUnit gives while it lists the test files (for example a test file without its class), and so does a file whose run crashes (`phpunit exited with code ...`) or takes longer than 600 seconds (`timed out after 600 seconds, last output: ...`). All files together get at most 3600 seconds: past that, the files still running are stopped and the ones not yet started never start, and each fails the gate with `timed out: the test pass reached its overall limit of 3600 seconds` (a stopped file also shows `, last output: ...` after it).

## Running the gates at the same time

`bin/check` runs the selected gates at the same time, as many at once as there are processors it may use (capped by a CPU quota of its container, rounded up), but fewer when its container has a memory limit (its own control group, each group above it and the top group it can see are all read): each test worker and each gate gets 2 GiB of it, the test workers first, because a gate such as `phpstan` may use that much (at least one gate runs). The gates that run your change's code (`tests`, `container`, `journeys`, and `phpstan`, which starts your change's kernel to dump the test container) start only after every other gate has finished, because a test could otherwise change the files or tools another gate is still checking. The other gates start first, in the usual gate order as earlier ones finish; then the `tests` gate starts first, so it never waits, and `phpstan` and `container` follow, in that order. Because the test workers need processors too, the `tests` gate counts for as many gates as it runs workers, but always leaves room for one other gate beside it. When the `tests` gate runs and more than one gate runs at once, the `phpstan` and `container` gates beside it run at the lowest processor priority, so they only use processor time the test workers leave idle; every other gate (and every gate with `--only=phpstan`, or `INTAKT_GATE_SLOTS=1`) keeps its usual priority. Set `INTAKT_GATE_SLOTS` to choose how many gates run at once (from 1 to 999); `INTAKT_GATE_SLOTS=1` runs them one after another. Any other value stops `bin/check` with exit code 2 before any gate starts. The lines, the result line and the exit code are the same however many run at once.

The `rector` gate starts at most 4 workers of its own, each allowed 300 s (`withParallel` in `config/gates/rector.php`), whatever the processor count. With Rector's defaults (a worker per core, 120 s), several `bin/check` runs at once on one machine starved each other's workers until they timed out, and the gate failed with `Child process timed out after 120 seconds` and no finding of its own.

## Listing the static gates and the gate order

`bin/check --static-gates`, with no other argument, runs no gate. It prints one JSON line with two lists and exits with 0:

- `static`: the gates that do not run your change's code, so they can check a copy of the change on their own (every gate except `phpstan`, `tests` and `container`);
- `order`: every gate of a run without `--journeys`, in gate order (the order of the gate list in `bin/check`).

For example:

```
{"static":["cs","rector",...,"ratchet","workflows"],"order":["cs","phpstan","rector",...,"container","ratchet","workflows"]}
```

With any other argument beside it, `bin/check` runs no gate: it prints an `error` line with its usage and exits with 2. A normal `bin/check` run is unchanged: it still starts the static gates before the gates that run your change's code.

## When `bin/check` reports a missing tool

Before it runs any gate, `bin/check` checks that the programs the selected gates call are installed. When one is missing, it runs no gate, prints one line naming every missing program, such as `gitleaks not found, see docs/architecture/requirements.md`, and exits with 2. A Composer older than 2.11 is reported the same way, naming the version found, because it would ignore a release cooldown set in `composer.json`. It also needs PHP's `pcntl` and `posix` extensions, so that a Ctrl-C reaches the gates' processes; a missing one is named the same way (`PHP extension pcntl not found, ...`). Install the program or the extension (the [requirements](../architecture/requirements.md) name the version), point `INTAKT_GITLEAKS` at gitleaks if it is not on the path, or leave the gate that needs it out with `--skip=<gate>`. `bin/probe` reports a missing `unshare`, `sh` or `ip` the same way, with exit code 2, before it starts anything.

The `workflows` gate is the exception: it needs zizmor (the [requirements](../architecture/requirements.md) name the version), and without it only that gate fails, with `missing tool zizmor` in its own result line; `--skip=workflows` leaves it out.

`bin/check` looks for the programs on `PATH`. When `PATH` is not set at all, it looks where the system shell `/bin/sh` then looks, since the gates start their programs through that shell (on Debian and Ubuntu: `/usr/local/sbin`, `/usr/local/bin`, `/usr/sbin`, `/usr/bin`, `/sbin` and `/bin`); if the shell cannot run, it looks only in the project folder. A `PATH` that is set but empty (`PATH=`) is taken as it is: only the project folder is searched, so every other program is reported missing.

## When the `workflows` gate reports an ignore without a reason

A zizmor finding in a YAML file under `.github/` may only be silenced with a comment `# zizmor: ignore[<audit>]` followed by the reason on the same line, for example `# zizmor: ignore[artipacked] the job needs the token to push`. The `workflows` gate fails with `<file>:<line> zizmor ignore without a reason: # zizmor: ignore[...]` when the last ignore on a line has no words after it (blanks or punctuation do not count, and neither do words before it, for example in a quoted value that happens to contain such a comment), and with `<file> cannot be read for zizmor ignores` for a YAML file it cannot read. To resolve it, fix the finding the ignore silences, or write on the same line why the pattern is safe. A file with Windows (CR LF) or old Mac (CR) line endings is read line by line the same way.

## The release cooldown for dependencies

`composer.json` sets a release cooldown of 3 days: `composer update` leaves out a package version published less than 3 days ago and locks the newest older one. The `audit` gate of `bin/check` also fails when `composer.lock` holds a release inside that period. Wait until the release is 3 days old; do not shorten the period to make the gate pass. This needs Composer 2.11 or later (see above). Dependabot has its own cooldown, which only decides when its pull requests open: 7 days for the GitHub Actions the workflows use, 3 days for images and Composer packages. It also holds for the `FROM` images of `Dockerfile`, `.github/ci/Dockerfile` and `.github/ci/databases.Dockerfile` (the database images CI starts for the persistence tests), updated together in one pull request, with one exception: the images from GitHub's container registry, such as the gitleaks image. Dependabot cannot see there when a version was published, so an update of such an image can open with no wait.

## When `bin/check` reports a gate process that ended without a result line

`bin/check` runs each selected gate in a process of its own, several at the same time, and prints their lines in the usual gate order once all have finished, then the result line. A gate whose process crashes, runs longer than 3600 seconds, or prints anything but that gate's own result line fails with the finding `gate process ended with exit code <n> and no valid result line: ...`, followed by what the process wrote to its output and then to its error output; when that does not fit the finding's 300 characters, only its end is kept, after `...` (for a timeout, it ends with `... timed out after 3600 seconds`; for a process killed by a signal, with `... was killed by signal <n>`). When a gate's process ends or is stopped, or `bin/check` is interrupted (Ctrl-C), any program the gate started and left running is stopped with it. One exception: a program the gate started in a contained run of its own (such as a journey's instance) may keep running if the gate's process is killed outright (signal 9), because then it has no chance to stop it. Exit code 124 means it timed out, 255 usually a PHP fatal error, 128 plus the signal number a kill by that signal (137 for signal 9). Warnings and notices a gate's process gives appear on `bin/check`'s error output, not in its lines. To resolve it, read the quoted output, fix its cause, and run the gate alone with `bin/check --only=<gate>`.

## When `bin/check` reports a stateful service

Intakt keeps one process alive across many requests and messages, so a service that keeps a value in a property would carry it into the next request. The `phpstan` gate of `bin/check` therefore reports a finding `intakt.statefulService` for every concrete class under `src/` with a property which is not `readonly`, including properties from a parent class or a trait under `src/`, and static ones, because the container registers every class under `src/` as a service. A property a vendor base class declares, such as those of Symfony's `Command` or `AbstractController`, is framework wiring rather than request state and is not reported. A virtual property, a hooked property without a backing store such as one with only a `get` hook that computes its value from other properties, keeps no value and is not reported either; a hooked property with a backing store is. The finding names the property. To resolve it, do one of:

- make the property, or the whole class, `readonly`;
- implement `Symfony\Contracts\Service\ResetInterface` and clear the property in `reset()`, which Symfony calls between requests and messages;
- if the class is a value object or a data transfer object rather than a service (a console input object for `#[MapInput]` included), mark it with Symfony's `#[Exclude]` attribute so the container does not register it. An `#[Argument]` or `#[Option]` property alone does not exempt a class, because the container still registers it.

Doctrine entities, embeddables, mapped superclasses and column types, and exceptions are not services and are never reported. Neither is the kernel, which performs the reset, nor any class outside `src/` (tests, gate code, scripts), which the container never registers.

## When `bin/check` reports a deprecated reference

Deprecated code is not used. The `phpstan` gate of `bin/check` already reports a call, a `new` or a signature type that uses a deprecated symbol, and reports a finding `intakt.deprecatedReference` for every place that names a deprecated class, interface or trait: a `use` import (also inside a group import such as `use Acme\{Legacy, Modern}`), an `instanceof`, a `catch` type, a `::class`, an attribute, a `new`, a type, and a type in any docblock tag (`@var`, `@param`, `@return`, `@property`, `@method`, a `@template` bound and the others) on a class, trait (also a trait no class uses, reported once from its own file), function, method, property, statement or closure, also inside a union such as `object|Legacy` or a constant type such as `Legacy::*`. Some places get both findings. A class is deprecated when it carries a `@deprecated` tag, or when its file calls the global `trigger_deprecation()` (in any letter case, also through a `use function` alias; a function of that name in the file's own namespace is not the global one) outside any class, function or closure (also inside an `if`), as some Symfony classes do to warn when they load; a first-class callable `trigger_deprecation(...)` is no call and deprecates nothing. The finding names the class. To resolve it, switch to the replacement the class names (its `@deprecated` text or its deprecation message says which); do not silence the finding. The `tests` gate also fails when a test (a gate test under `tests/Gates/` too), a helper under `tests/` or a class under `src/` causes a deprecation, including one that only loads a deprecated vendor class; only a deprecation that one vendor package causes by calling another is ignored.

## When `bin/check` reports a flag parameter

A boolean parameter that switches what a function does hides two behaviors behind one name, so the `phpstan` gate of `bin/check` reports a finding `intakt.flagParameter` for every parameter typed `bool`, `true` or `false` (also nullable or in a union) of a function, method, closure or constructor, except in `tests/`. The finding names the parameter. A `readonly` service is reported like any other. To resolve it, do one of:

- replace the boolean with a backed enum whose cases name the modes;
- split the method in two, one per behavior;
- if the boolean is data of a value object, make the class `readonly`, mark it with Symfony's `#[Exclude]` attribute (Doctrine entities, embeddables and mapped superclasses count as excluded too) and keep the boolean as it is, as a promoted constructor property or assigned unchanged to a property in the constructor body. Only such a constructor parameter passes, and only when the constructor body does nothing but assign variables to properties the class itself declares (as a property, a promoted constructor parameter or a property of a trait the class uses, since PHP counts a trait's property as declared by the class that uses the trait), one plain `$this->name = $variable;` per statement. An assignment to any other property (one the class never names, or one a parent class declares) is reported, since PHP hands an undeclared property or a parent's private one to `__set()`, which could read the boolean. A promoted boolean must appear nowhere in the body, and a stored one exactly once, as the variable of one of those assignments. Any other statement in the body (a condition, a call, `new`, `eval`, `include`, a `parent::__construct()` call) could read the boolean, so every boolean of that constructor is reported then, even in a value object, while the class's other methods may read the stored property, and the exemption follows the attribute, not the folder, so an unmarked `readonly` class under `bin/` or `config/gates/src/` is reported too.

## When `bin/check` reports a re-spelled name

A container service id, a parameter name or a provider name is written once, so that renaming it cannot leave a second spelling behind. The `phpstan` gate of `bin/check` therefore reports a finding `intakt.reSpelledName` for a string literal in a PHP file under `src/` or `config/` (but not `config/gates/`) that starts with `intakt.` outside a module's ids class (a class, not a trait, interface or enum, ending in `Services` in a `Contract` namespace, such as `AiServices`), and for a literal equal to a provider's value (`codex`, `anthropic` and the others) outside the `Provider` enum. Only a whole literal counts: a message that mentions `codex` is not reported. A double-quoted string with a variable in it, such as `"intakt.ai.platform.{$name}"`, is reported when it starts with `intakt.`. Code in a trait is checked too, also when no class uses the trait, and so is code in an anonymous class (`new class { ... }`), which counts as part of the class it is written in. Tests, the gates' own code and the YAML of `config/intakt.yaml` are not checked. To resolve it, use the constant of the ids class (add one there for a new name), or derive the name from the case (`Provider::Codex->value`, or a `Provider` method such as `platformId()`).

## When `bin/check` reports a highlights finding

`docs/highlights.md` lists the Symfony and Symfony AI features Intakt uses, and the `highlights` gate of `bin/check` checks its tables. The page is not in git and not edited by hand: `bin/highlights` builds it from `docs/highlights.d/` (run it to read the page locally), where `layout.md` holds the intro, the headings and the table headers, and each change adds one fragment named after its issue, such as `docs/highlights.d/1045-highlight-fragments.md`. A fragment holds only rows, each under the `## <section>` heading of its section in `layout.md`: table rows starting with `|`, or list items starting with `- ` in "PHP 8.5 in use". To change a row, add a fragment with the whole new row; it replaces the earlier row with the same first cell (or, for a list item, the same text before its closing status parenthesis such as `(done, T6)`, so an item can change its status) at its place, because fragments apply in the order they were merged, whatever their issue numbers: the order git added them to the branch, a fragment you have not committed yet last, and fragments added in the same commit (or outside git) in the natural order of their numbers (fragment 10 after fragment 2). The gate checks the page as `bin/highlights` would build it, so two changes never touch the same file, and a copy on disk that differs from that build fails. The order needs the full git history: in a shallow clone the gate fails until you run `git fetch --unshallow`. Each finding names the line: a fragment finding the line of the fragment, a table finding the line of the built page. To resolve it:

- **docs/highlights.md is committed:** the page was added to git (for example after a hand edit); run `git rm --cached docs/highlights.md` and put the change in a fragment;
- **docs/highlights.md is not the assembly of docs/highlights.d/:** your local copy was edited by hand or is older than the fragments; put any change in a fragment and run `bin/highlights`;
- **the history of docs/highlights.d/ is shallow:** run `git fetch --unshallow`;
- **cannot write docs/highlights.md** (from `bin/highlights`, which then exits with status 1): something else is in the way, such as a folder of that name or a read-only file; remove it or make it writable and run `bin/highlights` again;
- **a fragment is named `<issue>-<slug>.md`:** rename the file to its issue number, a hyphen and a slug in lowercase letters, digits and hyphens;
- **section is not a section of `layout.md`, or the line is outside a section:** put the rows under a `## ` heading spelled exactly as in `layout.md`; a new section is added to `layout.md` first;
- **section holds table rows (or list items), or the table header is in `layout.md`:** write only the rows of the section's kind; the header and its `---` line stay in `layout.md`;
- **row appears twice in this fragment:** keep one row per first cell (one list item per text before its status) in a fragment;
- **status is not one of planned, in progress, done:** write exactly one of those three words in the Status column, and move any remark (such as "optional") to another column;
- **Where cites a pull request:** name the task and its issue instead (`T9 (#14)`); a pull request number counts in every form (`PR #12`, `PR: #12`, `PR (#12)`, `PR12`, `pull request 12`, `pull/12`), while text inside backticks, such as a path `upstream/pr1-repro/`, does not (a span opened with two backticks ends only at the next two, so it may hold a single backtick, and a backtick written with a backslash before it, `` \` ``, is plain text that starts no span);
- **Where names a path which does not exist on the branch:** fix the path, add the file to git, or remove the backticks when the text is no path. Anything in backticks with a `/`, or ending in an extension like `.php` or `.md`, counts as a path and must be tracked by git; package names and commands with a `/` therefore go without backticks. A `|` in a path is written `\|` inside the table, and the gate checks it as `|`;
- **row is planned, but every path its Where names exists:** the change that built the row's feature left its status behind; set the Status to `in progress` (an open pull request) or `done` (on main). A planned row that names no path, or a path not built yet, gets no such finding;
- **Where cannot be checked, shorten the cell:** the cell is too long for the gate to read (usually a stray backtick before a very long text); close or remove the backtick, or split the text.

Tables inside a fenced code block (three or more backticks or tildes, indented at most three spaces) are examples and are skipped. The block ends at a line holding only a fence of the same character, at least as long as the opening one; a fence line with text after it stays inside the block. A block that is never closed runs to the end of the file.

## When `bin/check` reports a reproductions finding

Every folder directly under `upstream/` is a reproduction of a likely library bug, and the `reproductions` gate of `bin/check` checks that each one is listed. A finding such as `upstream/messenger-lost-message/ has no row in "Found in the beta" of docs/highlights.md` names the folder. To resolve it, add a row to the "Found in the beta" table of `docs/highlights.md` (through a fragment under `## Found in the beta` in `docs/highlights.d/`; the gate reads the page built from the fragments, see the highlights finding above) that names the folder in its text, for example `` `upstream/messenger-lost-message/` `` in the Where column. Only a row of a table in that section counts (a table needs its header and its `---` line, not indented four or more spaces, and it ends at the first line that is blank, has no `|`, or starts a heading, a list item, a blockquote or an HTML comment, even when that line holds a `|`; only the cells under the header's columns count). A line without a `|` ends the table even where GitHub would still show it as a row: this is stricter than GitHub and can only make the gate fail, never pass wrongly. A mention in its prose, on a line that merely starts with `|`, under a heading or in a list right after the table, in another section or inside a fenced code block does not, and neither does a longer path such as `docs/upstream/messenger-lost-message/`. A file directly under `upstream/` (such as its `README.md`) needs no row. The gate reads the folders git tracks or would add (ignored files do not count), and the working tree when there is no git repository.

The same gate checks the reports. A finding such as `upstream/a-bug/REPORT.md is ready to file but has no "Checked" line` or `... is older than 14 days` means the last `Decision` or `Status` line of `## Upstream status` says `ready to file` without a dated `Checked` line. The gate reads such a line however it is written: with any list marker or none, with or without backticks, in any case, and with more text after the phrase. Check the report against upstream again, add or update `- **Checked:** YYYY-MM-DD ...` (commits or tags, duplicate search, preferred form and target branch; see `upstream/README.md`), or change the status. A finding `... has no "## Upstream status" section` means a `ready to file` line stands in a report whose status heading is not written exactly that way: fix the heading. A report has only one such section (`... has more than one Upstream status section`), and its status is a list item at the top level of that section: a line that says `ready to file` in another section, in a quote or indented four or more spaces gets `... write the status as a list item in the Upstream status section`.

## When `bin/check` reports a container finding

The `container` gate of `bin/check` runs `bin/console lint:container` for the `dev`, `test` and `prod` environments, also with `--fast`. It catches a wrongly wired service before the first request does: a service argument of the wrong type, or a reference to a service or parameter that does not exist. A finding names the environment and Symfony's message, for example `prod: Invalid definition for service "App\Mailer": argument 1 of "App\Mailer::__construct()" accepts "App\Transport", "App\Clock" passed.` To resolve it, fix the service definition or the constructor type it names, then run `php bin/console lint:container --env=<environment>` to see it pass. Environment variables are not resolved, so a missing API key does not fail the gate.

The `phpstan` gate of `bin/check` knows the service container too: before it analyzes the code it builds the `test` environment's container of the checked tree in that tree's own `var/cache/` folder, whatever `APP_CACHE_DIR` or `APP_BUILD_DIR` says (`php bin/console cache:warmup --env=test`, so a tree without `bin/console` fails the gate) and reads the service ids and parameter types from it. A `get()` with a service id the container does not define fails the gate, for example `src/Lookup.php:17 symfonyContainer.serviceNotFound Service "kernal" is not registered in the container.`, also when the id is picked from several fixed strings and only one is wrong, and so does a `get()` of a private service outside the test container, also when it is one of several fixed strings. A `has()` with such an id fails the same way (`intakt.containerUnknownHasId`), even when the id is picked from several fixed strings and only one is wrong, and so does a `getParameter()` with a parameter name the container does not define, for example `src/Settings.php:17 intakt.containerUnknownParameter Parameter "kernal.debug" is not defined in the container.` To resolve it, fix the id or name, or use the ids class constant that names it. A service locator's own keys and the parameter names asked of a container bag are not checked, as long as the locator is typed as `ServiceProviderInterface`: a locator typed as `Psr\Container\ContainerInterface` looks like the container itself, so its keys are checked as service ids. With `--fast`, a change to `config/`, `src/Kernel.php` or a `services.yaml` under `tests/` checks every PHP file, so removing a service in configuration alone still finds its callers. A test that sets a service during the test declares it `synthetic` in `tests/Support/services.yaml`; a test that boots a kernel with other settings reads that kernel's services through `tests/Support/RebuiltContainer`.

## When `bin/check` reports a ratchet finding

A new PHPStan rule can be switched on before the code is clean: the violations it finds that day go into a ratchet list, one file per rule outside `config/gates/`, included from `config/gates/phpstan.neon`. The `ratchet` gate of `bin/check` (also with `--fast`) makes sure such a list only gets shorter. It compares each list with the list on the target branch and fails when an entry was added, a `count` went up, or an entry's identifier, message pattern or path changed, for example `ratchet/loose-conditions.neon: count rose from 2 to 3: [...]`. To resolve it, fix the new violation in the code instead of listing it; deleting entries and lowering counts always pass. A list also needs a line `# Cleanup issue: #<number>` in its header, may hold nothing but `parameters:` with `ignoreErrors:` (`ignoreErrors: []` once its last entry is gone), and arrives only in the change that adds its include. A violation that is not on the list, or a list entry that no longer matches anything (for example after a fix or after moving the file), fails the `phpstan` gate: delete the entry in the same change as the fix. A tree without any list passes with the note `no ratchet lists`. The gate reads the includes of `config/gates/phpstan.neon` only as plain `- path` lines under an unindented `includes:` key (the lines may be indented or not); any other form, such as `includes: [...]` or a configuration file that is indented as a whole, fails with `cannot read the includes` rather than overlooking a list.

## GitHub's test merge and the `commits` gate

On a pull request, GitHub checks out a merge of the branch into the base branch, with a subject such as `Merge <sha> into <sha>`, which is not a Conventional Commit. CI names that merge and the pull request's head with `--test-merge=<merge>:<head>`, and the `commits` gate skips it when its second parent is the pull request's head and its first parent is on the base branch, also when the base branch moved after the pull request's last update. Every other commit, merges included, still needs a conforming subject.

## Running a probe against an install

`php bin/probe tests/Probe/NAME.php` boots the same scratch instance and runs one small PHPUnit test (a name ending in `Test.php`) or PHP script against it, with the network cut, so anything that reaches for the network fails. The script or test finds the instance's address in the environment variable `INTAKT_INSTANCE_URL`. Its output is printed, followed by a line `exit code: N`, and the command exits with that code. A probe still running after 60 seconds is stopped with exit code 124. The instance, its files and anything the probe started are removed afterwards. It needs Linux with `unshare` and `ip`, which cut the network for the run.

The instance and the probe do not inherit your whole environment, so a token you have set in your shell is not visible to them. They get only `PATH`, `HOME`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TZ` and `TMPDIR` (when you set them), the application variables `bin/instance` sets itself (`APP_*` and `DATABASE_URL`) and `INTAKT_INSTANCE_URL`; in worker mode also `INTAKT_INSTANCE_ADMIN_URL` (FrankenPHP's admin API) for the probe, and `XDG_DATA_HOME` and `XDG_CONFIG_HOME` (inside the scratch folder) for FrankenPHP. `PWD` is also present: the `sh -c` wrapper in `bin/instance` sets it, it is not taken from your environment. `APP_ENV` and `APP_SECRET` keep your value when it is set and not empty or `0`.

A caller that already runs `bin/probe` without network access and in its own process namespace (as the build loop's sandbox does) sets the environment variable `PROBE_ISOLATED=1`. `bin/probe` then starts the instance directly and needs neither `unshare` nor `ip`, but first checks that the run really is offline: when `/proc/net/dev` cannot be read or lists something unexpected, when it shows a network interface other than `lo`, or when `lo` is down, it prints the reason and exits with code 2 before anything starts. The caller is responsible for ending whatever the probe leaves running. Any other value, or no value, keeps the `unshare` way.

## Configuring providers and API keys

Intakt knows five providers: `anthropic`, `openai`, `openai_compatible` (any endpoint that speaks the OpenAI API), `claude_code` (a reviewer on a Claude subscription, see below) and `codex` (a reviewer on a Codex subscription, which uses a login file instead of a variable, see [A Codex subscription login](#a-codex-subscription-login)). Each of the first four reads its key from Symfony secrets (`php bin/console secrets:set ANTHROPIC_API_KEY`) or from the environment (`.env.local` or the real environment), never from a plain committed file; a non-empty environment value wins over the secret:

| Provider | Variables it needs |
|---|---|
| `anthropic` | `ANTHROPIC_API_KEY` |
| `openai` | `OPENAI_API_KEY` |
| `openai_compatible` | `OPENAI_COMPATIBLE_BASE_URL` and `OPENAI_COMPATIBLE_API_KEY` (for Hugging Face, see [Running the demo on a Hugging Face token](#running-the-demo-on-a-hugging-face-token)) |
| `claude_code` | `CLAUDE_CODE_OAUTH_TOKEN` |

A provider whose variables are not all set (empty counts as not set, and so does a secret Intakt cannot decrypt when the container is built), neither in the environment nor in the secrets, is switched off, and Intakt still starts. A provider with several accounts (see below) stays on as long as one of its accounts is fully set. `php bin/console intakt:ai:tiers` and `php bin/console intakt:vendor:probe` print a line on standard error for every switched-off provider, and the demo's first start prints them once in its log, not again on a restart with the same volume (other commands print none), for example `Provider "openai" is disabled: set OPENAI_API_KEY to enable it.` The same text is in the container parameter `intakt.ai.disabled_providers`. `php bin/console debug:config ai` lists the providers that are on, except `claude_code`, which is not part of the AI Bundle's configuration: `php bin/console debug:container intakt.ai.platform.claude_code` finds that service only when it is on. Whether a key is set is decided when the container is built, so after you add or remove a key, run `php bin/console cache:clear`.

### More than one account of a provider

A provider can have several accounts, for example a personal and a team API key. List them under `accounts:` in `config/intakt.yaml`, in the order Intakt tries them (see `config/intakt.example.yaml`):

```yaml
accounts:
    anthropic: [default, team]
```

The account `default` reads the variables in the table above. Any other account reads the same variables with its name in capitals appended: `team` reads `ANTHROPIC_API_KEY_TEAM` (for `openai_compatible`, `OPENAI_COMPATIBLE_BASE_URL_TEAM` and `OPENAI_COMPATIBLE_API_KEY_TEAM`; for `claude_code`, `CLAUDE_CODE_OAUTH_TOKEN_TEAM`, with its own folder `var/claude-code-team/`). A name starts with a lowercase letter and holds only lowercase letters, digits and underscores, and is listed once; anything else stops Intakt from starting. A provider you do not list has its `default` account only. An account whose variables are not all set is switched off with a line such as `Account "team" of provider "anthropic" is disabled: set ANTHROPIC_API_KEY_TEAM to enable it.`; the provider is switched off only when none of its accounts is set.

When a provider limits a call (a rate limit or quota) or fails it with a temporary error, the account that made the call **cools down** until the reset time the provider sent (one minute when it sent none, at most one day). Every reviewer on that account waits out the same cooldown, also in other workers on this computer, and the reviewer starts again at once on the next free account of the same provider: it stays the same reviewer, so no catch-up review is owed. Only when every account of the provider is cooling down does the reviewer wait, until the first account is free again; this holds for a temporary error too, so such a reviewer is not marked failed. A temporary error or a limit that arrives after a reviewer's streamed answer has started (its first text, thinking or tool call, not only the token counts a provider sends first) is different: the answer cannot be resumed and the account is cooling down, so the reviewer is not asked again and ends `blocked` with the finding `incomplete-stream` and the reason `The provider failed after the answer had started streaming.`, and the tokens the call spent are counted once. That failed answer still cools its account down, like any other failure: a limit, a rejected key or a temporary error that arrives while the answer is being read, before or after it has started, keeps the next review off that account (a rejected key cools it for a minute and counts as a rejection). A failed account is logged with its name and the kind of error, never with the provider's error text, which can repeat a key. Each cooldown is recorded in the ledger as an `account_cooled_down` event with the account (`anthropic.team`) and its end, and each usage row names the account the call ran on. A rejected key or login is an account error only you can fix, so it is also reported to you once, as an `account_error_reported` event in the ledger with the account and the moment: the same error is not reported again while it lasts, however often the account is tried after its cooldown. Once the account answers a call sent after that report, its next error is reported again; an answer to a call sent before the report does not count. Cooldowns and these reports are kept in Symfony's cache, so `php bin/console cache:clear` ends them (an account error that lasts is then reported once more).

A key the provider rejects (revoked or wrong) puts its account into cooldown for a minute like a limit, so the call moves on to the next account of the provider; the reviewer ends `failed` when every account of the provider rejected its key (now or in a cooldown still running, also for a review that starts during that cooldown, without sending a call), and waits when another account is only cooling down from a limit.

**Substitutes.** A tier can list `substitutes` (a provider and a model each, see the commented line in `config/intakt.example.yaml`). Only when the tier's provider cannot answer (every account is cooling down, every key was rejected, or the provider is disabled because its settings are not set) does a review go to the first substitute that can, in the order you listed. A tier without `substitutes` never leaves its provider: its reviewers wait as described above, and a tier on a disabled provider is refused. When the provider and every substitute are out, the review stops with a reason that names each provider and why it is out (disabled, keys rejected, or the wait in seconds). A call that failed (a refused request) never goes to a substitute. A review that went to a substitute stays on it to the end, counts against that provider's limit on parallel calls, and its approval counts only when that provider can read the project's checkout. A reviewer whose provider is not listed under `accounts:` (so it has its default account only) ends `failed` when that key is rejected and the tier has no substitutes. Because another provider reviewed, the ledger gets a `catch_up_owed` event with the reviewer's role, tier and the substitute, and the reviewer's row keeps the substitute; a move to another account of the same provider owes nothing. The catch-up review itself is planned. When every provider of the tier is out, the substitutes too, the reviewer ends `blocked` with the reason (`Every provider of the tier is out: anthropic disabled, openai keys rejected, openai_compatible for 60 s.`: a wait in seconds, or why no wait helps), shown in the `reviewer_blocked` event, and the round completes without waiting.

**Output limit.** Each tier has a `max_output` (a whole number of at least 1, the most tokens one answer may have), so a long verdict is not cut off by a model's or a provider's own default. When you leave it out, `strong` gets 16000, `standard` 8000 and `light` 4000; a substitute of a tier uses the tier's limit. Intakt sends it with every call of a reviewer or the judge on that tier, to Anthropic, OpenAI and OpenAI-compatible providers; the Claude Code and Codex subscription logins take no such limit, so none is sent there. When a provider stops a reviewer's answer at the limit, Intakt runs that reviewer once more with twice the limit (twice the default above when the tier sets none); when the answer is stopped again, the reviewer ends `failed`, and its `reviewer_failed` event names `MaxOutputTokensException`. Each of the two calls has its own usage row. The judge is not run again.

### A reviewer on a Claude subscription

Map a tier to `provider: claude_code` and a Claude Code model name (`opus`, `sonnet` or `haiku`) to run that reviewer through the `claude` command-line tool, which must be installed where Intakt runs. Create the login token with `claude setup-token` and store it as `CLAUDE_CODE_OAUTH_TOKEN`. The tool gets only that token, your `PATH` and its own folder `var/claude-code/` (where it runs and keeps its state); every other variable of Intakt's environment reaches it empty, so neither an API key nor any other secret does, and the subscription is used. It is given none of its own tools, only the read-only reading tools of the review's own server (file, directory and search), reached with a credential made for that one review; it can read the files of the head under review through those tools, and nothing of the checkout or of Intakt's files otherwise. Its `approve` counts like any other reviewer's when the review's server was given to it for that call. A call started without the server (a review without a round) counts as not having read the change: when it answers `approve`, its verdict becomes `blocked` with the reason that it approved a change it could not read. When no credential can be made for the server (an empty `APP_SECRET`), the tool is not started and the reviewer is `blocked` for want of tools. A `changes` verdict from it stays `changes`. The tool answers with a few sentences and then one fenced `json` block holding the verdict; Intakt reads that block as the verdict when it is the only `json` fence opening anywhere in the answer (three or more backticks or tildes, then `json`; one that is indented, quoted, in a list or only mentioned in the prose counts too), it opens at the start of a line with exactly three backticks and `json`, it closes on a line of exactly three backticks, and it does not sit inside another fenced block. A block stays open until a fence line with the same prefix closes it (up to three spaces of indentation count as none): a quoted, listed or deeper indented fence line inside a block is content and closes nothing. A closed block of another language beside it, such as `php`, is fine. A bare JSON answer works too. An ambiguous answer is refused rather than guessed: one with no `json` block, with two or more openings, with the one block in another form or nested in another block, or with a block that is not a verdict is refused as invalid output, and the review records the `invalid-output` finding. Intakt reads the environment again for every call, so a variable added while Intakt runs also reaches the tool empty. Its usage is recorded in the ledger like any other call. If its output ends before the final result (the tool stopped, was killed or ran past its 300-second limit), the reviewer's verdict is `blocked` with that reason, and its usage is recorded once as unsettled.

Which plans may be used this way is the vendor's decision, not Intakt's. Anthropic's [Claude Code legal and compliance page](https://code.claude.com/docs/en/legal-and-compliance) says that Free, Pro and Max plans fall under the Consumer Terms of Service and that Team and Enterprise plans fall under the Commercial Terms of Service, that the subscription login is meant for ordinary use of Claude Code by the plan's own purchaser, and that routing requests through Free, Pro or Max credentials on behalf of other users is not permitted. Use your own plan for your own reviews, read those terms for your case, and use an API key (`anthropic`) when in doubt. Intakt does not check your plan.

To decrypt the secrets, Intakt reads `SYMFONY_DECRYPTION_SECRET` the way Symfony does: a base64 value, in the standard or the URL-safe alphabet (`-` and `_`). When it is not set, or decodes to nothing, the vault's own private key file in `config/secrets/<environment>/` is used. A secret that cannot be decrypted (a wrong key, or no key at all) counts as not set, so its provider is switched off and named on standard error as above.

### A Codex subscription login

Codex has no long-lived token, so Intakt keeps each account's login file itself. Log in with the `codex` command-line tool, then copy its `auth.json` (in `~/.codex/`, or in `CODEX_HOME` when you set it) to `var/codex/logins/<account>/auth.json`, for example `var/codex/logins/default/auth.json`; the account name follows the same rule as above. Keep that file readable by Intakt's user only (`chmod 600`). Pin the model and the reasoning effort every call uses in `config/intakt.yaml`, both required once the section is there:

```yaml
codex: { model: gpt-5.3-codex, effort: high }
```

The effort is one of `minimal`, `low`, `medium`, `high` and `xhigh`; anything else stops Intakt from starting. Before each call Intakt refreshes the login when it was last refreshed seven days ago or more (the `codex` tool would do so itself after eight), writes the new login back to the same file, and then gives the call a read-only copy in the account's own folder `var/codex/homes/<account>/`, which is also the tool's home and working folder. Whatever the call writes there never reaches the kept login, and the next call gets a fresh copy. Like the Claude tool, it gets your `PATH`, its home folder (as `HOME` and `CODEX_HOME`) and, in a review with a round, the review server's credential (`INTAKT_REVIEW_SERVER_BEARER`); every other variable of Intakt's environment reaches it empty. A login that cannot be read or refreshed stops the call with a message saying so.

Every call runs the tool with its shell, web search, browsers, computer use, apps, plugins, other agents, image tools and hooks switched off, in its read-only sandbox, without a saved session and without reading a settings or rules file from its folder. These limits are fixed: neither a project nor a reviewer can lift them. The tool refuses a feature name it does not know, so a `codex` release that renames one makes every call fail with that message instead of leaving the feature on.

`php bin/console intakt:codex:probe <account>` (the account defaults to `default`) makes one such call and prints the account, the pinned model and effort, and the answer; it needs the `codex` tool where Intakt runs.

### A reviewer on a Codex subscription

Once the `codex` section is there, map a tier to `provider: codex` and the model you pinned to run that reviewer through the `codex` tool; a tier or substitute on `codex` that names another model, or one without the `codex` section, stops Intakt from starting, because every Codex call runs on the pinned model. List the accounts under `accounts:` as for the other providers (`codex: [default, team]`); each needs its login file, and an account without one fails its call with a message naming the file. Without the `codex` section Codex is simply left out, with no "disabled" line.

Like the reviewer on a Claude subscription, it reads the change through the review's own server: for that call only, the tool is started with that server as its one MCP server (its own settings, which could name others, are still not read), allowed just its read-only reading tools (file, directory and search) and given a credential made for that one review, which reaches it in its environment, never on its command line. The tool is told to read the files it needs through those tools before it gives a verdict; it reads nothing of the checkout or of Intakt's files otherwise. When the server cannot be started, the call fails instead of going on without it. Its `approve` counts like any other reviewer's when the tool's own report of that call shows at least one completed read through the review's server (one of its reading tools, on that server). A call that read nothing through it (no tool call, only failed ones or ones the server refused, or calls to another server) or that was started without the server (a review without a round) counts as not having read the change: when it answers `approve`, its verdict becomes `blocked` with the reason that it approved a change it could not read. When no credential can be made for the server (an empty `APP_SECRET`), the tool is not started and the reviewer is `blocked` for want of tools. A `changes` stays `changes`. Its answer is read as for the Claude subscription: bare JSON, or prose around exactly one fenced `json` block. Its answer must be a complete run of the tool: an answer that is not a valid verdict, including text that only says a limit was reached, counts as a failed review (`changes` with the finding `invalid-output`), never as a limit, and the account is not paused. A run that ends before the tool reported the turn complete is `blocked` (`incomplete-stream`). When the tool itself reports that the plan's usage limit is reached, the account is paused like any limited account (for one minute, because the tool's message gives no reset Intakt reads), and the review waits or moves to another account. When it reports that the plan does not include the model or that the login is lost (it could not be refreshed, or the service refused it), the account is taken out like one whose key was rejected; so is a login whose refresh the sign-in service refuses as unauthorized, before the tool runs. Neither is a failed review or `changes`, and only these reports of the tool count, never the reviewer's own text. Each of these account errors is reported to you once, as described for a rejected key under [Cooldowns, pauses and outage notices](#cooldowns-pauses-and-outage-notices); a usage limit is not reported. Any other run the tool reports as failed fails the reviewer, and so does a run it reports complete without an answer. The use the tool reports (input, cached input and output tokens) is recorded once per review in the ledger, in a usage row that names the account it ran on (`codex.team`), also when a run without an answer fails the reviewer and when the tool reported the turn complete and then exited with an error. A failed run that never reported its turn complete records no use.

### Capability tiers per project

Each project maps three capability tiers (`strong`, `standard`, `light`) to a provider and a model. Copy `config/intakt.example.yaml` to `config/intakt.yaml` (or point `INTAKT_CONFIG` at another file), edit it, and run `php bin/console cache:clear`. Project names are kept exactly as written, dashes included, and a model must be a text value that is valid UTF-8 and not blank (a value made only of whitespace, including Unicode spaces such as a no-break space, counts as blank). A project can also carry a `watch` section (`repository`, `base` and `task`, all required text that is not blank, and `github`, the project's `owner/name` on GitHub, which is required for the watch to read pull requests from GitHub; see `config/intakt.example.yaml`): Intakt then reads its open pull requests every minute (run `php bin/console messenger:consume scheduler_watcher` to keep the schedule going) and starts a review round for the head of a pull request once its CI has finished green. The round reviews exactly that commit, read from the local repository named by `repository`, so the commit must be there (fetched); until it is, the start fails and that head alone backs off, as does any head whose CI cannot be read or whose start failed, without holding back the other pull requests: the log gets an error with the cause, the ledger records `head_failed` (the cause, the failures in a row and the next try), and the head is tried again a minute later, then after twice as long each time, but never more than 30 minutes later. A head whose CI Intakt could not read because GitHub's hourly allowance is used up (see [Intakt's GitHub App](#intakts-github-app)) is not failing: it is read again at the reset time GitHub named, with no `head_failed` line, no card and no count toward the hand-over. After four failures in a row the ledger records `head_handed_over` once (the maintainer agent that takes it over is planned); the head is still tried at those waits, so it starts its round once the cause is gone, without a new push. The latest failure of each head is shown as a card at the top of `/reviews`. Such a failure holds every account (a [failure back-off](#cooldowns-pauses-and-outage-notices)) only when no single pull request causes it: GitHub refuses Intakt's credentials, the disk is full, a second pull request fails with the same error within an hour, or the hand-over itself cannot be recorded. One pull request that keeps failing never starts it. A head whose CI is still running starts nothing and is read again a minute later; a head whose CI failed is only recorded; a pull request closed before its CI finished is no longer read, and the ledger records `head_forgotten` for its queued head, which also takes its card off `/reviews`; a head gets one round, however often it is seen, also when two ticks run at once, except that a head that returns after its round was reported stale (the pull request moved to another head and back) gets a fresh round, because the old verdicts no longer count. The ledger records `round_queued` for each round; when the ledger cannot take that line, the round still starts, the tick reports the failure, and a later tick writes the line once. When a pull request gets a new head while an earlier round's verdicts exist, the ledger records `verdicts_stale` for that round once, also when a round was still starting as the head moved, unless the change cannot affect them (for example documentation only); when the ledger cannot take that line, a later tick checks the round again and records it. That check also reads the new head from the local repository: while its commit is not fetched, a head with running or failed CI is still recorded as such, but the check fails and that head alone backs off as described above: it is tried again once its next try has come (a minute later, then after twice as long each time; a head with failed CI is then read and recorded as failed again), and after four failures in a row it is handed over. The `task` text is given to every round of the project. Several projects can map the tiers differently; a tier you leave out is reported as not mapped. A model name the provider's built-in list does not know is added to it, so newer models work too. An invalid file stops Intakt from starting and names the bad key. `php bin/console intakt:ai:tiers` lists every project with the provider and model of each tier; a tier whose provider is switched off (see above) shows the reason instead of a model.

A project can also carry a `review:` section that sets its review panel (see `config/intakt.example.yaml`): `quorum` is `all`, `majority` or `one-strong-plus-one`, and `reviewers` lists one or more reviewers, each with a `role`, a `tier` (`strong`, `standard`, `light`), a `provider` (`anthropic`, `openai`, `openai_compatible`, `claude_code`, `codex`), a `prompt` and a `budget` (a whole number of at least 1). Every field is required, and the panel comes from the file alone. A reviewer's `provider` must be the provider the project maps that `tier` to under `tiers:`. A panel of any size works, at least one reviewer (an empty list is refused), as long as its policy can be met when every reviewer approves: `one-strong-plus-one` needs at least two reviewers, one of them on the `strong` tier. An unknown policy, tier or provider, a missing, empty or blank field, a budget below 1, an empty reviewer list, reviewers written as a map instead of a list, a provider that differs from the tier's, or a policy the panel can never meet stops Intakt from starting and names the problem. A `projects:` value that is not a map of projects stops Intakt too. A project without a `review:` section has no panel yet.

A `review:` section can also hold `rules`, a list of extra reviewers for bigger or sensitive changes. Each rule has `min_lines` (a whole number of at least 1), `paths` (a list of path patterns) or both, and `reviewers` written like the core ones (the provider again must be the tier's). A rule without `min_lines` and `paths`, rules or paths written as a map instead of a list, or a path pattern that is not text (a number, `true`) or not valid UTF-8 stops Intakt from starting. The quorum policy must be reachable both by the core panel alone and with every rule added, otherwise Intakt does not start either. A rule applies when the change has at least `min_lines` changed lines or touches a path matching one of its patterns; in a pattern `*` stays inside one folder (`src/*` does not match `src/a/b.php`) and `**` crosses folders (`src/**`), any characters included; `/**/` also matches no folder (`src/**/Security/**` matches `src/Security/Door.php`), and a leading `**/` matches the top folder too (`**/Security/**` matches `Security/Door.php`); quote a pattern that starts with `*` (`'**/Security/**'`), since YAML reads a bare leading `*` as a reference. The reviewers of every matching rule join the core panel, which is never reduced, and the project's quorum policy stays. The label `review:full` applies every rule. The panel comes from the configuration alone.

### Reviewer-for-loop mode

A project with `mode: reviewer-for-loop` is one whose pull requests an existing loop builds and merges, where Intakt's panel takes the place of the loop's own Claude reviewer. With a `watch` section, Intakt reviews every new head of the project's open pull requests once its CI is green, with the whole panel and judge, as for a live project. Its verdicts are recorded in the ledger with `"mode":"reviewer-for-loop"` and count like a live project's; the dashboard shows them without a mark. Once a round is judged, or its judging has failed for good (after the worker's retries, for example because the judge's tier has no model), Intakt publishes its verdict on that exact head under its GitHub App, and this is the whole contract with the loop:

- a commit status named `intakt/review` on the head: `success` when the panel approves, `failure` when it asks for changes or when Intakt withdrew its review (see below), `error` when Intakt could not review the head (no quorum and no reviewer asking for changes, for example because reviewers failed, or the judging failed for good);
- for a review decision (`success`, or `failure` when the panel asks for changes), first one pull request comment; a withdrawal publishes its `failure` without a comment. The comment is in the shape of the loop's own reviewer comments: the heading `**Review by Intakt** (head <first 12 characters of the head>)`, one line `[P1] file:line: text` (or `[P2]`, `[P3]`) per finding on the act list, and a fenced `json` block `{"verdict":"approve"|"changes","head":"<the full head>","summary":"..."}`, followed only by an invisible marker `<!-- intakt-verdict: <round id> -->`. A finding without a line shows only its file, one without a file shows `(no file)`, and line breaks in a finding become spaces.

The status and the comment always tell the same verdict, as the loop reads it: the loop counts an open P1 or P2 as changes, so an approval whose act list still holds a P1 (for example from the reviewer who was outvoted) is published as changes, with `failure` and `"verdict":"changes"`; an approval with only P2 or P3 findings lists them under a `Follow-ups:` line, which the loop reads as an approval with follow-ups.

Each finding line is redacted like a review, as a whole and on its own, so a redaction that runs to the end of its text (an unclosed credential header, for example, even one that starts in the file and ends in the text) ends at that line; the heading and the `json` block hold no reviewer text and are not redacted, so a posted comment always ends with its `json` block. Then the comment is scanned with `gitleaks`; if the scan still finds a secret, no comment is posted and the status is `error` with the description "Intakt could not publish its review of this head." A round of a local branch (not a GitHub pull request address) publishes nothing and logs a warning. When GitHub refuses or cannot be reached, the worker tries the publication again later; before posting the comment it reads the pull request's comments, and when one posted by Intakt's own GitHub App already holds the round's marker (an earlier attempt posted it) it posts only the status; a comment by anyone else that holds the marker does not count. Only one worker publishes a round at a time: a second one finds the round busy and tries again later. So each round leaves one comment. The App needs write access to commit statuses and to pull requests (`statuses:write` and `pull_requests:write` in `GITHUB_APP_PERMISSIONS` when you check the installation). Apart from this, Intakt writes nothing to the forge in this mode: it never merges, pushes, labels or approves a head, and it posts no review. The loop keeps building, merging and asking you as before. To roll back, switch the loop back to its own Claude reviewer and set the project to `live` (which publishes nothing). The watch reads the open pull requests and their CI from GitHub through the App identity, so it needs the GitHub App settings and a `github` repository in the `watch` section; without it the tick fails for that project with a clear message.

A round can be marked stale after it started, when its head is refused later because it no longer boots (nothing sends this mark yet: the boot check before a review that will send it is planned). Its verdicts then stop counting, also while the pull request is still at that head, and Intakt publishes the round again: the status on that head becomes `failure` with the description "Intakt withdrew its review: this head does not boot." and no comment, which replaces an approval already published, also when the mark lands while that approval is being posted. Intakt publishes the verdicts of one pull request one at a time (a publication that finds another one under way is tried again shortly), so the last status on a commit is always the one of its latest round, withdrawn when that round was marked stale. A publication of a round is dropped when a later round of the same pull request that reviewed the same commit is already judged, because the later round's status is the one that commit stands at. A later round of another commit does not stop it: when a pull request moves from head A to head B and back to A, and A then fails to boot, A's old approval is still withdrawn.

### Project mode

A project can carry `mode: live`, the same as leaving the key out, or `mode: reviewer-for-loop` (see [above](#reviewer-for-loop-mode)). Any other value stops Intakt from starting and names the key; that includes `mode: shadow`, which is no longer a mode, so set such a project to `live` or `reviewer-for-loop`. Every reviewer's verdict is recorded in the ledger with the project's mode at that moment (`"mode":"reviewer-for-loop"` or `"mode":"live"`); a verdict recorded earlier with `"mode":"shadow"` stays in the ledger as it was written. The mark is a record only: it never stops a verdict from counting, and a round reviewed before a switch to `reviewer-for-loop` is published like any other. Intakt can post a review to GitHub, but no review round of a live project posts its outcome yet and nothing merges yet.

`budget.shadow_ceilings` is no longer a setting either; a configuration that still has it stops Intakt from starting and names the key, so remove it.

To see which panel a change gets, without calling any model, run `php bin/console intakt:review:panel <project> --lines=300 --path=src/Foo.php --label=review:full` (`--path` and `--label` can be repeated; all options are optional, and `--lines` must be zero or more). It prints the quorum and one line per reviewer with its tier, provider and budget. Intakt reads the configuration when it starts, so a changed file shows after the cache is cleared. An unknown project fails with a message. A path pattern Intakt cannot evaluate against a path (for example, one too complex for the pattern matcher) fails the same way, with a message that names the pattern. `intakt:review` takes the paths from the branch and no labels.

### Which tier a build starts on

A project can carry a `build:` section that sets the rules for the tier a build starts on. `tier` (`strong`, `standard` or `light`; default `standard`) is the tier for an ordinary build, `escalate_on` lists the setbacks that raise the next build to the strong tier (`failed-attempt`, `blocking-finding`, `stall`; all three by default, a shorter list turns triggers off, and an empty list or `escalate_on: ~` turns every escalation off), and `sensitive_paths` is a list of path patterns (same patterns as a review rule's `paths`) for the files that need the strong tier:

```yaml
projects:
    alpha:
        build:
            tier: standard
            sensitive_paths: [config/**, src/**/Security/**]
            escalate_on: [failed-attempt, blocking-finding, stall]
```

A build that touches a sensitive path starts on the strong tier, whatever its label says. Otherwise, after a listed setback (an earlier failed attempt, a blocking P1 finding or a stall) the build is raised to the strong tier; a rework after a round without a P1 stays on the cheaper tier. Otherwise a `model:<tier>` label (for example `model:strong`) sets the tier, and without either the build starts on `tier`. A `model:` value that names no tier, such as a model name, is ignored. The rules look only at the labels, the touched paths and the setback the loop passes, so a job can never choose its own model. A bad tier, an unknown setback, or sensitive paths or setbacks that are not a list, stop Intakt from starting and name the key.

To see the tier the rules choose, without calling any model, run `php bin/console intakt:build:tier <project> --label=model:strong --path=src/Foo.php --setback=stall` (`--label` and `--path` can be repeated; all options are optional). It prints the tier and why (`default`, `label`, `setback` or `sensitive-path`); an unknown project fails with a message. Starting a build on the chosen tier is not wired yet.

To choose the model of a build and record it, run `php bin/console intakt:build:model <project> <task> <attempt> [--label=...] [--path=...] [--setback=...]` (the attempt starts at 1). It applies the same rules, prints the tier, the reason, the provider and the model the project maps that tier to, and writes one `model_chosen` event to the ledger (`php bin/console intakt:ledger:events` shows it). It calls no model. A build runs the Claude Code CLI, so if the project maps the chosen tier to any other provider, the command fails and records nothing. If the ledger cannot record the event, the command fails and the choice does not count. A build never picks its own model: only the rules, your labels, the paths and the earlier round's setback decide.

## Looking inside the development install with Mate

On a development install (`composer install` with the dev packages), `vendor/bin/mate` answers questions about the running app from its own container and environment files instead of from reading the code. It is not part of a production install: `composer install --no-dev` leaves it out.

- `vendor/bin/mate tools:list` lists the tools.
- `vendor/bin/mate tools:inspect TOOL` shows a tool's parameters.
- `vendor/bin/mate tools:call TOOL --PARAM=VALUE` runs one; add `--format=json` for machine-readable output.

The useful tools today are `symfony-services` and `symfony-service-detail` (which services the container holds and how one is wired), `symfony-dotenv-check` (which `.env*` file declares a variable and whether it resolves, with the value masked) and `server-info` (PHP version, system and extensions). The profiler tools are listed too, but Intakt does not turn on Symfony's profiler, so they find no profiles.

If Mate stops with a PHP version mismatch, it was started with a PHP other than 8.5 (the version `mate/config.php` pins); run it with the PHP 8.5 the app uses. If a container tool reports "No compiled container found", run `bin/console cache:warmup` first so the dev container exists. If `tools:list` says "No tools found", check whether `vendor/` is a symlink: Mate then looks for its settings next to the folder the symlink points to and finds none, so it needs a real `vendor/` folder in the project. The other cause is missing package information: Mate finds its packages through `vendor/composer/installed.json`, so if that file is missing or does not list `symfony/ai-mate`, run `composer install` again with the dev packages (without `--no-dev`).

`vendor/bin/mate discover` writes files for coding agents: skill copies in `.agents/skills/` and `.claude/skills/`, and a `CLAUDE.md` in the project root; Git ignores all three. It also rewrites the committed `mate/extensions.php` and `mate/AGENT_INSTRUCTIONS.md`; do not commit those changes, and restore the files with `git checkout -- mate/extensions.php mate/AGENT_INSTRUCTIONS.md`.

## Project memory

Intakt can keep short notes about a project, each tied to the files it explains, and look up the notes for the files a change touches within a size limit (in bytes). When a review round completes, every finding a reviewer marked resolved (and that stays resolved) is written as a note, with its cause and the file it concerns; a round that finishes after a newer round of the same change writes none, since its verdicts are left out of the list (see [Finding ids across review rounds](#finding-ids-across-review-rounds)). This needs an OpenAI account for the embeddings (`OPENAI_API_KEY`); without one the note is not written and the message waits in the failed queue with the reason. Create the notes table once with `php bin/console ai:store:setup`. Notes belong to the project whose review wrote them: a review is only ever shown its own project's notes, even when another project on the same install has notes on a file with the same path. Each reviewer's briefing carries the notes for the files in the change's diff (for a renamed file, its old and new path), most relevant first, marked as untrusted text; the whole briefing is at most 4000 bytes. Less relevant notes that do not fit are left out; when the most relevant note alone is too long, it is cut to fit and ends with `[note shortened]`. It comes after the diff as a message of its own, and the reviewer is told the notes may be wrong and must be checked against the code. When the notes cannot be read (no OpenAI account, or the table was not created) the review goes on without them and a warning is logged. Reviewers can only read the notes, never change them.

## The ledger

Intakt has a ledger that can store review events (review started, reviewer started, verdict received, judge done, usage recorded) in one SQLite table, `ledger_event`, and read them back in the order they were stored, even if the system clock is set back in between. Each event gets an id that carries the time it was stored (a UUID version 7) and keeps the moment it was stored in UTC, and reads it back the same whatever time zone PHP is set to. So far the model calls of the vendor write to it (their token usage), and so do job containers (how each job ended, and containers removed after a crash; see below). Create the table with:

```
php bin/console doctrine:migrations:migrate
```

### Choosing the database

Intakt uses SQLite unless you set `DATABASE_URL` (in `.env.local` or the real environment) to another database; MySQL, MariaDB and PostgreSQL are tested too, for example `DATABASE_URL="postgresql://intakt@localhost:5432/intakt"`. Intakt finds out the MySQL or MariaDB server version itself on the first connection. For PostgreSQL it does not ask the server and always uses its support for PostgreSQL 12 and later, the newest it has. The test environment appends `_test` to the database name, so tests against `intakt` use the database `intakt_test`. In CI, a pull request runs the tests on MySQL, MariaDB and PostgreSQL only when it touches persistence (the ledger, migrations, Doctrine's configuration, the Composer files or the CI definition under `.github/workflows/` and `.github/ci/`, or adds a line naming Doctrine in `src/`); when that check fails, the CI run fails rather than skipping them, and every push to main runs them. SQLite runs on every change.

Stored events cannot be changed or removed. Intakt refuses to update or delete one with a `LedgerEventsAreAppendOnly` error, and on SQLite the same migration adds database triggers that abort any `UPDATE` or `DELETE` on the table, and any insert that would replace a stored event (for example `INSERT OR REPLACE` with the position or id of an existing event), even from another tool. On other database engines only the refusal inside Intakt applies.

Read the events back, oldest first, with:

```
php bin/console intakt:ledger:events
```

It prints one line per event (the moment in UTC, the id, the kind and the payload) and ends with a count, for example `2 events`. The payload is printed exactly as stored, console color tags included. The ledger has no notion of a run yet, so the command lists every stored event of a known kind; rows of a removed kind stay stored but are not shown and are not counted.

## Job containers

Intakt has the part that will run each build, check and review in a container of its own; the check before a push uses it ([below](#the-check-before-a-push)), and no build or review uses it yet. Each job gets a fresh container that is thrown away afterwards: its system files cannot be changed, it works in a scratch area that is gone when it ends (its home folder and caches live there too, so every job starts clean), the inputs it is given are read-only, and the only thing it can hand back is what it leaves in its own output folder, which no other job can see. It gets none of Intakt's keys or tokens, and has its own memory and CPU limit, so a job that runs out of memory is stopped alone. What a job hands back is bounded too: at most 1000 files and 16 MiB in total, so a job that writes more fails instead of exhausting Intakt's memory. An image that declares volumes is refused, because a job could write into them. The ledger records how each job ended (`job_ended`): `exited` with its exit code, `oom` when its memory limit stopped it, or `timed_out` when it ran past its time and was stopped (a job that runs out of memory just before it is stopped still counts as `oom`). A container that keeps running even after it was stopped fails the job: no end is recorded, and the container is removed.

A probe job has no network at all. A job that needs to download (the check before a push names the package registries; a build or a review will name the AI company's address and the package registries) gets a short list of host names it may reach, and nothing else: it sits on a network of its own whose only way out is a proxy of its own, and the proxy lets through only encrypted connections (port 443) to the hosts on the list. Everything else is refused: another host, an address, plain HTTP or another port. The job cannot reach services on the Docker machine itself either. The job starts only once its proxy is ready; a proxy that stops, reports itself unhealthy or is not ready within 30 seconds fails the run before the job starts. Each refused request is written to the ledger as `job_egress_refused` with the method and what was asked for (for example `CONNECT outside.example:443`), each one once and at most 20 per job. Host names on the list are exact and lowercase, without wildcards; a list with an address, a wildcard or a port is refused before the job starts.

Before its own command, every job checks that what it was told it can do works: it writes a small file into its output folder and its scratch area and reads it back, checks that each input it was given can be read, and, for a job with a host list, that each host on the list answers through its proxy (this needs `curl` in the job's image). Each check is written to the job's log, for example `intakt-start-check: input: /input/memory is not readable`. When a check fails, the job still runs, but in a reduced mode: its log says `intakt-start-check: reduced mode:` with the failed checks, the job itself finds them in `INTAKT_REDUCED_MODE`, and the ledger gets one `job_start_check_failed` event per failure with the check (`output`, `work`, `input`, `egress`, or `report` when the check's own report is damaged) and the reason, at most 20 per job. A job whose output folder cannot be written is recorded as an `output` failure. The job image needs `/bin/sh`; its own entrypoint is not used.

The proxy comes from its own image, which you build once on the machine that runs Docker:

```
docker build -t intakt-egress-proxy docker/egress-proxy
```

It has not yet run against a real Docker Engine; it is first checked when jobs run on a machine with Docker. Use Docker Engine 25.0.5 or later: older engines answer DNS lookups for outside names even on a network without a way out.

Intakt needs the Docker Engine's socket at `/var/run/docker.sock` for this. Without it a job fails with `The Docker Engine is not reachable: there is no socket at /var/run/docker.sock.`

Containers are removed when their job ends, with the job's proxy and network. If Intakt itself crashed while jobs ran, their containers and networks are removed before the next job starts (`job_container_removed` and `job_network_removed` in the ledger). To clean up at once, run:

```
php bin/console intakt:job:sweep
```

It prints one line per container it removed and a count, for example `1 orphaned job containers removed.`, and leaves the containers of jobs that are still running alone. When the engine cannot be reached it prints the reason and exits with 1.

### Job images

The image a project's jobs will run in comes from the project's last commit (files you have not committed do not count), from the first of these it has:

1. `.devcontainer/devcontainer.json`: its `image`, or the Dockerfile its `build` names (comments and trailing commas are fine; a compose setup is not supported yet).
2. A `Dockerfile` at the top of the repository, used as it is.
3. Only `composer.json`: Intakt writes the Dockerfile itself, with the PHP from `config.platform.php` (exactly that version) or else the newest of PHP 8.5, 8.4, 8.3 and 8.2 that `require.php` allows (its latest patch, or the lowest patch `require.php` allows when it stops inside that version, as `8.4.1` does), Composer, every `ext-*` extension under `require` and `require-dev`, and fixed versions of the Claude Code and Codex command-line tools.

A job never gets another PHP: when `composer.json` names no PHP version at all, no image is built, whatever else the project has. After the build, Intakt starts the image once without network and asks its PHP for its version and extensions; an image whose PHP does not match `composer.json`, or that lacks an extension, is refused with the version or the extension's name. An extension that cannot be installed fails the build with `missing PHP extension: <name>`.

```
php bin/console intakt:job:build-image path/to/checkout intakt-job/my-project:main
```

It prints where the image comes from, the build's output, and for example `Image intakt-job/my-project:main (sha256:...) built: PHP 8.5.12 with every required extension.`, with the id of the image this build made: the check ran in that image, even if another build has since given the tag to its own. To see where the image would come from and the Dockerfile Intakt would write, without building, run `php bin/console intakt:job:plan-image path/to/checkout`. On any failure both print the reason and exit with 1. It needs the Docker Engine's socket like the jobs do, and the Docker machine must reach Docker Hub, Debian's package mirrors and the npm registry for a generated image. Nothing builds images on its own yet, and images are not rebuilt when the project changes.

### The check before a push

Intakt never trusts a builder's own run of the checks. Before anything is pushed, it checks the bundle a build returned (as `intakt:hand-back:check` does, secret scan included, see [Hand-back checks](../architecture/hand-back.md); it takes no `--credential-env`, so it redacts no mounted credential, and no pull request text, so it neither scans one nor records a send-back or hand-over) and then runs the project's check on it in a job container:

```
php bin/console intakt:check:run var/mirrors/my-project.git my-task-branch build.bundle intakt-job/my-project:main
```

The arguments are the project's mirror, the task's branch, the bundle and the project's job image ([Job images](#job-images)). The job clones the mirror afresh, applies the bundle on the task's branch, and runs `composer install` and then `bin/check --fast` in that clone, with empty caches, so nothing from the build's own folder or downloads is reused. It may reach Packagist and GitHub's archives only. `--check-command="make check"` runs your own command instead (it then has to install what it needs itself). The result comes back only through the job's output folder; a job that leaves no clear result there, runs out of memory or runs out of time fails the check.

Before the job starts, Intakt compares each file the change touches with the version the branch started from. A file that keeps less than a fifth of its size and loses more than 50 lines (a removed file counts too) stops the check at once, with the file named, unless the task's plan names it as removed or rewritten: pass each such path with `--rewritten=<path>`. A file the change replaced with a submodule counts as emptied. A file that is only moved, or one that main shrank, is fine; a file moved to a new path and then rewritten is covered by naming its new path. A named path covers one file only: the file that was at that path when the branch started, or, for a path the change created, the file that is there at the end and the path it came from. Moving another file onto a named path does not cover it, and a file that passed through a named path on its way to another path is still checked under that path. A file moved onto a named path that the change then removed and created anew is not covered either, because the new file there is another file.

It prints any lost files (`lost docs/guide.md: 120 lines to 1`), the last 40 lines of the check's output, and `passed` (exit 0) or `failed:` with the reason and, for a failed command, its exit code (exit 1). A refused bundle prints `refused:` and the reason. Without Docker it fails with `The Docker Engine is not reachable: there is no socket at /var/run/docker.sock.` Nothing runs this check on its own yet: the push and the build lane will.

## Measured use of subscription windows

Intakt can keep, for each AI account, the latest use of its five-hour and weekly windows as the AI company measured it, with the time the window resets and how old the reading is. A reading belongs to its account only: another account, of the same company or another one, never sees it. A reading whose reset time has already passed, or lies further ahead than the window is long, is not kept, and the previous reading stays. The table is created with `php bin/console doctrine:migrations:migrate`.

From these readings Intakt can decide whether one more call may start on an account:

- No call starts while a window is at or above its ceiling. An old reading still counts until its window resets, since use only grows until then; once the reset time has passed, the reading no longer counts. A reading without a reset time stops counting once it is older than its window is long (five hours or a week).
- The weekly window is paced: the pace is the weekly ceiling times the share of the week that has passed, counting the current five hours as passed. While the weekly use is ahead of the pace, the five-hour ceiling shrinks in the same proportion (for example, a weekly use of twice the pace halves it).
- With no call running, one call starts below the ceilings, even with no reading or an old one.
- A second call at the same time needs a reading of both windows taken within the last 5 minutes, and both windows more than 10 points below their ceilings (at a ceiling of 90%, a use of 80% is not enough). Without a reading of both windows from the last 30 minutes, only one call runs at a time.
- Only the account's own readings count. Intakt's estimate of what a call will cost plays no part.

Set the ceilings, in percent from 1 to 100, in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names) and run `php bin/console cache:clear`:

```yaml
budget:
    ceilings:
        five-hour: 90
        weekly: 90
```

Both default to 90; a window you leave out keeps it. A value outside 1 to 100 (`.NaN` included), a window name other than `five-hour` and `weekly`, or another key under `budget` than `ceilings` and `prices` (such as the former `shadow_ceilings`, see [Project mode](#project-mode)) stops Intakt from starting and names the key. The ceilings apply to every account. Nothing records readings or asks this decision before a call yet: reading the windows from Claude and Codex and holding back new work by this decision come in later changes.

### Cooldowns, pauses and outage notices

Besides the ceilings, Intakt can hold work back in these ways (the tables are created by the same `doctrine:migrations:migrate`):

- **Cooldown of one account:** when the AI company answers that an account's usage limit is reached, that account gets no new call until the reset time the answer gave, even if that is days away. Other accounts, of the same company or another, keep working. An answer whose reset time has already passed, or lies more than a week ahead, cools nothing down.
- **Budget back-off:** no new call starts on any account, but pull requests that are already approved still merge, since merging calls no model.
- **Pause:** the same as a budget back-off: nothing new starts, approved pull requests still merge.
- **Failure back-off:** no new call starts on any account and nothing merges (once holds are checked, see below). Intakt starts it by itself for 15 minutes, and only for a fault no single item causes. Today these come from the pull requests Intakt watches: GitHub refuses Intakt's credentials (an answer of 401; a rate limit does not count), the disk is full, the lock store fails while a pull request is being locked or unlocked, two different pull requests fail with the same error within an hour, or handing a pull request over to the maintainer agent itself fails. The log gets an error naming the reason.
- **Drain:** nothing new starts and nothing merges, so work in progress can finish before an update.

When several are in effect, the strictest wins: drain, then failure back-off, then pause, then budget back-off, then an account's cooldown, then the ceilings. Each one ends by itself at the time it was given.

When no usage reading of an account has arrived for 3 hours, Intakt writes one warning to its log, for example `No usage of account claude_code.main has been read since 2026-11-02T08:00:00+00:00, so only one call at a time runs on it.` It writes it once for that outage, also with several workers; if writing the warning fails, Intakt tries again at the next decision; after a new reading, a later outage gets its own warning. Sending these notices to your phone comes with the notifier.

Nothing places a cooldown, a budget back-off, a pause or a drain yet: the AI company answers and the admin controls that place them come in later changes. Nothing checks a hold before a call or a merge yet either, the failure back-off included: only `intakt:budget:replay` (below) reads them.

To see what Intakt would decide over a day, write a script and replay it:

```
# one step per line: a UTC moment, then the step
2026-11-02T08:00 read claude_code.main five-hour 20 2026-11-02T13:00
2026-11-02T08:00 read claude_code.main weekly 10 2026-11-08T08:00
2026-11-02T08:00 start claude_code.main 0
2026-11-02T09:00 limit claude_code.main 2026-11-02T13:00
2026-11-02T09:00 start claude_code.main 0
2026-11-02T10:00 hold budget-back-off 2026-11-02T10:30
2026-11-02T10:00 merge
```

```bash
php bin/console intakt:budget:replay my-day.txt
```

It prints each line with its outcome (`recorded`, `cooling-down`, `start` and so on), and the outage warnings where they happen. The steps are `read <account> <window> <percent> <reset>`, `limit <account> <reset>`, `hold <drain|failure-back-off|pause|budget-back-off> <until>`, `start <account> <calls running>` and `merge`; an account is written as company and name, such as `claude_code.main`. The replay runs on your database and your ceilings with its own clock, starting at the first line, and undoes everything when it ends, so your install keeps nothing of it. A line it does not understand stops it with the reason. `tests/Core/Budget/UseCase/ReplayDay/scripted-day.txt` is a whole example day.

## Summarizing a branch

`php bin/console intakt:change:summarize <branch> [--repository=.] [--base=main]` prints the change summary of a branch of a local repository against its base branch: the short base and head commits, the number of changed files with the added and removed lines, and one line per file (`added`, `modified` or `deleted`). A control character in a file name is shown in a visible form such as `\x1b`, and a backslash as `\\`. A `--repository` that is not a directory, an empty branch or `--base`, a branch the repository does not have, a repository git cannot read, or a repository whose `.git/info/attributes` file exists, prints an error and exits with 1. The summary is what the branch has gained since it was cut from the base branch, not what the base branch gained afterwards.

## Checking whether a verdict still counts

A reviewer's verdict counts only for what it reviewed: the branch's latest commit, the commit it was compared with, the task, the check command and the project's review panel. `php bin/console intakt:verdict:identity <project> <branch> <task> <check-command> [--repository=.] [--base=main]` prints that identity as one line, `identity` followed by five parts separated by dots (the two commits, then fingerprints of the task text, the check command and the panel). The task text and the command are not shown, only their fingerprints.

Pass a printed identity back with `--reviewed=<identity>` to see whether a verdict given on it still counts:

- `current`: nothing changed.
- `stale: head changed` (or any other changed parts): the verdict no longer counts. A new task text, check command or panel always makes it stale, and so does a new commit, unless one of the two cases below applies.
- `kept-for-untouched-parts: ...`: the verdict still counts for everything the change left alone, and each `review again <path>` line names a file to review again. This happens when the base branch was merged into the branch and git merged it by itself (no conflict to resolve, no other edit in the merge commit), or when the new commits touch only files in the repository's `docs/` folder and the base did not move.

A project without a review panel, a `--repository` that is not a directory, a branch the repository does not have, or an identity that is not in the printed form prints an error and exits with 1. Every review round remembers the identity it was started on, and reading its verdicts applies the same rules: a stale round's verdicts no longer count. Nothing reads stored rounds that way yet. `intakt:review` does not read an older round: its own round reviews a snapshot of the branch's head instead (see [Reviewing a branch](#reviewing-a-branch)).

## Checking a new Symfony AI release against the known bugs

`php bin/console intakt:upstream:run` runs every reproduction in `upstream/` and prints the installed Symfony AI versions, then `passes` (the bug seems fixed) or `still fails` for each reproduction, and a count. Add `-v` to see why a reproduction fails. The exit code is 1 while any reproduction still fails. A reproduction counts as `passes` only when its PHPUnit tests ran and asserted something, or when its `reproduce.php` script exits with 0 and prints `REPRODUCTION PASSES` as its last line. One without tests or script, with a skipped or incomplete test, or that runs longer than 5 minutes is reported as `still fails`, and the other reproductions still run. A folder that does not exist, cannot be read or cannot be opened (no execute permission) is an error (exit code 2).

For a bug in Symfony AI, a reproduction folder can also hold a prepared fix for the owner to approve: `fix.patch` (one commit for `symfony/ai`) and `PR.md` (the pull request text as it will be posted), or `COMMENT.md` (a comment for an upstream pull request that already fixes the bug, or for an upstream issue that already covers it). A bug that needs a new upstream issue, in Symfony AI, Symfony or Doctrine, holds `ISSUE.md`: the issue text as it will be filed. The folder's `REPORT.md` says in `## Upstream status` whether a fix pull request is ready or only an issue is right, and why, and ends with a `Status` line after the owner's review (`not filed`, with the reason, for a report that is not sent). Intakt posts nothing upstream: the owner approves each one first. `intakt:upstream:run` ignores these files.

Some folders in `upstream/` are probes that pass: they check that Symfony AI and the MCP SDK behave where Intakt relies on them (two models and two MCP sessions in one worker without mixing, structured output cut mid-array, three parallel tool calls on one session). They stay as guards, so a later release that breaks one shows up as `still fails`.

Two probes check how Symfony AI behaves when a provider fails, and both still fail: a rate limit that the provider reports only when the answer is read does not move the call to the next account of a failover, and an agent whose streamed answer is cut off after a tool call reports no token usage for the run. Intakt does not depend on either: it moves to another account through its own cooldowns and reads the usage of each model call itself, so an interrupted call keeps the tokens it spent.

## Asking a model for a verdict

Inside Intakt, the vendor asks the model of a project's capability tier to review a change and gets back a verdict: an approve, changes or blocked decision with findings. The model is a reviewer agent: it gets a role prompt, the task, the diff of the change (what it adds, edits and deletes) and the rules of how code reads, and it may read the files of the head under review with the tools described below before it answers. Each finding names the rule it breaks. The task text, the diff and everything the tools return are marked as untrusted data in the prompt, so text in a task or in the code under review cannot give the reviewer orders. A fence ends only at a closing marker that repeats its own boundary, so a fake closing marker in a file stays data. A reviewer that keeps asking for tools without answering (30 rounds of requests, however many files one round asks for), that makes a malformed tool request (a missing argument, a path that is not text, or a tool that does not exist), or that answers with something that is not a verdict counts as changes; one that answers `changes` without naming a finding is asked once more, and fails when it does so again; a reviewer stopped from the dashboard still counts as stopped after a malformed request. Only the reviewer's final answer is read as its verdict: the text it writes before a tool request is not, and a final answer written beside the model's thinking (as Anthropic models answer, streamed or not, also after tool requests) is read like any other. A final answer split into two separate pieces of text counts as changes, because which piece is the verdict would be a guess; so does one with no text at all, unless it was streamed, which fails like an answer cut off. A task, a diff or a tool answer longer than 100000 bytes is cut to that size, with a note from Intakt after it that says how much was left out; when anything in a review was cut, an `approve` from the reviewer becomes `blocked` with the reason `cut-approval` (a `changes` stays `changes`), so split a change that big or review it yourself. There is no command for it yet; the review loop will use it.

Each reviewer keeps its conversation of a review round (the prompt, the model's answers, the tool calls and what they returned) in the database table `reviewer_conversation`, one conversation per reviewer and round (a reviewer that is started again, after a stopped worker or a rate limit, begins a new one), so a reviewer never sees what another one was told or answered; a review that would reuse a conversation already started is refused before the model is asked. `php bin/console doctrine:migrations:migrate` creates it with the ledger table. Prompt caching is on for Anthropic models (the five-minute window), so a round that follows another in a review pays less for the part of the conversation the provider already holds.

Every such review is recorded in the ledger as `usage_recorded` events: one when it starts, and one when it ends, either with the tokens it used in all its rounds (one entry per model call, because the reviewer may call tools between answers) (prompt, completion, cached and the others the provider reports, plus the remaining-token figures) or marked unsettled when the call failed, with the tokens of the rounds that had answered before it failed. Both carry the same call id, so a call is counted once. An answer that is not a valid verdict still records the tokens it used. If the tokens of an answer cannot be read, the call is marked unsettled and a warning is logged, but the review still gets its verdict. If the ledger cannot store the first row, the call is not sent; if it cannot store the last one, the call fails and the row, tokens included, is logged as an error so it can be recorded later. `php bin/console intakt:ledger:events` shows the rows.

A call the provider refuses because of a rate limit or quota fails with a clear error that carries the time to wait when the provider sent one; other temporary provider errors fail with their own error, so a later retry can tell them apart. Either one cools the account down, also when it arrives while the answer is being streamed, and the review moves to another account of the same provider when one is free (see [More than one account of a provider](#more-than-one-account-of-a-provider)).

Run `php bin/console intakt:vendor:probe` after you set or change a provider key, to check the setup before a first review. It checks the real setup: it sends one tiny call to each enabled provider your projects use and prints a line with the model and the tokens used (prompt, completion, cached, total, remaining). It uses the keys from your environment, costs a few tokens per provider, and exits with 1 if any call fails. A failed call shows only the kind of error, never the provider's message, so a key it echoes stays off your screen. A provider that is switched off (see the `Provider "..." is disabled` lines above) is not probed.

## What a builder is told

A builder's instructions name the task, your decisions on it and, for a rework, the findings to act on, the excerpt of the failed CI log and the published pull request text it edits. Each of these is marked as untrusted text with its source (`task`, `decisions`, `act list`, `ci log`, `pull request text`), and the instructions say that marked text is data: the builder never follows a line in it that asks it to handle credentials, change protected paths, disable checks, push, merge or reach outside services. A first build is asked to write the pull request text to `PR.md`; a rework is asked to edit the published text and change only the lines it changes. `intakt:build:run` gives a builder these instructions ([Running a build](#running-a-build)). See [Builder prompt](../architecture/builder-prompt.md).

## What a reviewer can read

A reviewer reads the change through three read-only tools: it can read a file, list a directory and search for text, all at the head under review and nothing else. A request for a file outside the repository (a `../` path, an absolute path, the `.git` folder, or a link pointing out of the checkout or into the `.git` folder) is refused with a message, and the file is never opened. A tool that fails, such as a file that does not exist or a binary file, gives the reviewer an error message and the review goes on. A search skips binary files and files over 1 MB, shortens very long matching lines and returns at most 100 matches; a listing of a very large directory is shortened too. The reviewer agent uses these tools; a request it makes that is refused or fails is answered with a message and the review goes on.

## Reviewing a branch

`php bin/console intakt:review <branch> --project=<project> --task="<what the branch builds>" [--round=N] [--format=text|json] [--repository=.] [--base=main] [--check-command=bin/check]` reviews a branch of a local repository end to end: it chooses the project's panel for the change (its changed lines and paths), starts a round, waits for the workers, and prints the outcome, the act list, the tokens used and their cost. The reviewers read a snapshot of the branch's head, not your checkout: the command creates a detached git worktree of the head's commit in the system's temporary directory (an entry under `.git/worktrees/` in your repository, made without running the repository's hooks or filters) and removes it when the round ends. The branch need not be checked out, and nothing you do in the checkout while the round runs (switching branches, editing files, committing) changes what the reviewers read: they review the commits the branch pointed at when the command started. Start the workers first (`php bin/console messenger:consume async`, see above), on the same machine, because they read the snapshot by its path: the command only queues the round and waits for them, for at most two hours. A round the workers did not finish in that time ends as `blocked`, with the reason printed, and loses its snapshot, so a reviewer still reading it fails. The snapshot holds the head's files exactly as committed: a line-ending conversion (`core.autocrlf`) or a sparse checkout set up in your repository does not change it or leave files out.

Stopping the command with Ctrl-C (SIGINT) or SIGTERM removes the snapshot before it exits, with exit code 130 or 143 (on a PHP with the `pcntl` extension, which the console needs to handle signals). A run killed with SIGKILL cannot clean up and may leave an `intakt-review-*` worktree behind: `git worktree list` shows it, and `git worktree remove --force <path>` removes it.

The outcome comes from plain code, never from what a reviewer wrote: `approve` when the project's quorum policy is met, otherwise `changes` when a reviewer asked for changes, otherwise `blocked` (a reviewer that failed or was blocked gives no approval). The act list is the findings the judge marked `act`. The tokens are the prompt, completion and total tokens (the prompt includes cached input, and the cache read, cache write and cached parts appear beside it when they are not 0) of the model calls made for this round, that is each reviewer's calls and the judge's call (as recorded in the ledger, including calls that failed after spending tokens); each of these calls is recorded with the round it was made for, so another round of the same project running at the same time is not counted. The cost prices each of those calls by its model, from the prices you set (see [The cost of a round](#the-cost-of-a-round)).

Exit codes: `0` approve, `10` changes, `11` blocked, `1` wrong input or configuration (a missing `--project` or `--task`, a `--round` below 1, a `--repository` that is not a directory, an empty branch or `--base`, an unknown project, a branch the repository does not have, a repository git cannot read, or a `--round` that is not the change's next round), with the reason printed. Any other error is a bug in Intakt: the command does not print it as a reason, so it reaches the console, which shows it as an error block naming the exception's file and line, adds the trace only with `-v`, and exits with the exception's code, or `1` when that code is 0 or negative; a code above 255 is capped at 255. An exit code of `1` alone therefore does not tell a wrong input from a bug; the printed message does. `--round` is optional: the next round of a change is numbered by Intakt (1, then 2, and so on), and `--round=N` makes the command refuse to start when the next round would not be N, so a script can tell that another round started meanwhile; the number is checked as the round is opened, so a round started by someone else a moment earlier is caught too.

`--format=json` prints one JSON document instead of the text: `round_id`, `round`, `decision`, `exit_code`, `verdicts` (tier, decision and finding count per reviewer), `act_list`, `tokens`, `cost` (`usd`, the cost in US dollars or `null` when it is unknown, and `unpriced`, the models without a price) and `reasons`. Each `act_list` row is a finding with only the fields the schema lists (`id`, `severity`, `file`, `line`, `symbol`, `text` and `fixable_by`); what Intakt keeps about a finding for its own use, such as the evidence or the requirement a reviewer named, is left out. Intakt writes the document with the Symfony Serializer, and its tests check it against [review-output.schema.json](review-output.schema.json), the document's JSON Schema, so a script can rely on that file.

### Reading a verdict

`intakt:review` ends with the outcome on the first line and an exit code a script can test. The shape is below (an illustration of the format `ReviewReport` prints, not a recorded run; ids, files and numbers differ in every review):

```
changes (round 1)
strong reviewer: changes, 2 findings
standard reviewer: approve, 0 findings
act list: 2 findings
F1 P1 src/Cart.php:42: the discount is applied twice
F2 P2 src/Report.php:10: a new function has no test
tokens: 5 calls, 18000 prompt (15000 cache read, 2000 cache write), 1200 completion, 19200 total
cost: 0.0567 USD
```

- **The token line** counts every model call of the round, its judge call included. The prompt holds all input tokens, also the ones the provider read from its prompt cache (`cache read`) or wrote to it (`cache write`); those two are named in parentheses when the provider reports them, or as one `cached` figure when it does not tell them apart (Claude Code). A streamed call keeps the input and cache figures the provider reported when the stream began (Anthropic reports them first and only the output tokens at the end), so its prompt is not lost; a figure the provider never reported stays unknown, never 0. The total is always the prompt plus the completion. The dashboard's review page shows the same figures.
- **The cost line** is what the round's calls cost at the prices you set, in US dollars, to four decimals (`less than 0.0001 USD` when it is above 0 but too small for that). When a call used a model you set no price for, also a call that failed before the provider reported any tokens, the line says `cost: unknown, no price for <model>` (naming each such model once) instead of a partial sum or 0. When a call's provider reported no input tokens for it, the line says `cost: unknown` instead of the cost of the output tokens alone (with `, no price for <model>` added when a model also has no price). The dashboard's review page shows the same figure for each round, in its tokens table, and the sum of the rounds in the summary line, with the same `unknown, no price for <model>` wording.

- **The decision** is `approve` when the project's quorum policy is met, `changes` when a reviewer asked for changes, otherwise `blocked` (a reviewer that failed or was blocked gives no approval). Plain code decides it, never a reviewer's wording. The exit code is `0` for approve, `10` for changes, `11` for blocked and `1` for wrong input or configuration.
- **One line per reviewer** names its tier, its decision and how many findings it reported. A `reason:` line follows when a reviewer was blocked, with why. A reviewer that failed is named there in plain words, for example `reason: correctness reviewer failed, stopped at its output limit`, or `reason: correctness reviewer failed, asked for changes without naming a finding`; it counts as a blocked vote, so a failed reviewer never turns a two-reviewer panel into a one-reviewer approval.
- **The act list** holds the findings the judge marked to fix now. Each line has the finding's id (`F1`, ...; the same problem keeps its id in every later round), its severity (`P1` must be fixed, `P2` should be, `P3` is a small remark), the file and line, and the text. When two reviewers report the same file and line and the judge marks both to fix, the list holds one line for that place (the highest severity and the first reviewer's text), and its id names each finding it stands for, joined with `+` (`F1+F2`). A finding the judge deferred becomes a follow-up and one it rejected is dropped; neither is on the list. `php bin/console intakt:review ... --format=json` prints the same as one JSON document ([schema](review-output.schema.json)); a merged line shows only its first id there, and the JSON will show the merged ids in a later change.
- **A verdict that asks for changes names at least one finding.** A reviewer that answers `changes` without any finding is asked once more at once; when it answers that way again, it is a failed reviewer with the `reason:` line above, so a `changes` line with 0 findings never reaches the judge or the decision.
- **A reviewer whose answer breaks off is asked once more without streaming.** When the stream of a reviewer's answer ends before the answer is complete, the same reviewer is asked once more at once, from the start and without streaming, and its answer counts as usual. When that answer breaks off too, the reviewer is `blocked` with the reason of the first break, as it was before. Any other failure of the second try counts as that failure: a rate limit or a temporary provider error is handled as one. A rate limit or temporary error that itself breaks off the streamed answer is not asked again: the reviewer is `blocked` at once (see [More than one account of a provider](#more-than-one-account-of-a-provider)). Each try has its own pair of `usage_recorded` rows, so both are counted. A reviewer on a Claude or Codex subscription never streams, so it is not asked again.
- **A failed review** shows as `changes` with a finding `invalid-output` (the model's answer was not a valid verdict), or `blocked` with a finding such as `reviewer-stopped` or `cut-approval`, or with a `reason:` line; fix the cause (a key, a tier, a change split in smaller parts) and start the next round. See [Asking a model for a verdict](#asking-a-model-for-a-verdict).
- **The review page** (`/reviews/<round id>` in the [dashboard](#the-dashboard)) shows every reviewer's state and verdict (a failed reviewer in the same plain words as the `reason:` line), the round's decision once judged, every finding with the judge's call (`act`, `follow-up` or `rejected or unmarked`) and the tokens used. A meta line under its title names the project, the change and the latest round's start; while the latest round runs, a current state block at the top sums up its reviewers, the open (`act`) findings of the last judged round and the judge's call still to come; judged rounds fold to one line each in the timeline.

### The cost of a round

Set the price of each model under `budget.prices` in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names), keyed by the model name exactly as a tier names it, in US dollars per million tokens, and run `php bin/console cache:clear`:

```yaml
budget:
    prices:
        claude-opus-5-5: { input: 5, output: 25, cache_read: 0.5, cache_write: 6.25 }
        gpt-5: { input: 1.25, output: 10 }
```

`input` and `output` are required; `cache_read` and `cache_write` default to the `input` price. For a subscription account, use the list price: the figure is an equivalent, not a bill. A price must be a number of 0 or more; a missing `input` or `output`, a negative price, text or `.NaN` stops Intakt from starting and names the key. A call is priced as: uncached input tokens at `input`, cache reads at `cache_read`, cache writes at `cache_write`, completion tokens at `output`; cached tokens the provider does not split into reads and writes (Claude Code) count at the `input` price. Each call is priced by the model its tier names (or its substitute's model when a substitute answered), not by the name the provider's answer gives, so `gpt-5` in the config also prices an answer that reports itself as `gpt-5-2025-08-07`, and Claude Code calls, whose answers name no model, are priced too. A call recorded before Intakt kept the tier's model counts as the model `(no model)`, which has no price. With no `prices` set, every round's cost is unknown.

The demo's sample project brings its own prices: the first start writes a `budget.prices` block into the seeded file, one entry for each model of its panel and judge (the models of the providers you gave keys for), so the first review shows a cost figure. They are list prices read on 2026-11-13, not a bill, and you can edit them in that file. A model without a price, for example one you add to a tier later, still gives `cost: unknown, no price for <model>`. A demo that was seeded before this change keeps its file, since a seeded file is never rewritten, so add the prices by hand.

## Finding ids across review rounds

Intakt keeps a list of the findings of a change across its review rounds. Each new finding gets an id (`F1`, `F2`, ... in the order they first appear), and a finding reported again under that id in a later round keeps it, so the same problem has the same id in every round. When several reviewers report the same existing id in one round, it stays one finding. A finding marked resolved is closed: later rounds are not shown it, cannot mark it as a repeat, and the same problem reported again gets a new id. From round two on, every reviewer of a round is shown the open findings as they were when the round started, with their ids (marked as untrusted text in the prompt), lists the ids it finds fixed as resolved, and marks a finding that is still there as a repeat under the same id; any other finding gets a new id. A verdict that resolves or repeats an id that was not open, or marks the same id both resolved and repeat, counts as changes, like any answer that is not a valid verdict. The list is kept in the database for each change and updated once every reviewer of a round is in; when one reviewer finds a finding fixed and another reports it again in the same round, it stays open. From round two on, a new finding that is P1 or P2 is lowered to P3 before the reviewer's verdict is stored, so the panel's decision and the list both see P3, unless the reviewer marked it a regression (the change broke something that worked before) or named a requirement it breaks; a finding reported again under its id keeps the severity it was first stored with, and round one is never lowered. A review that failed (an answer that was not a valid verdict, a cut-off answer, or an approval from a reviewer that could not read the change) adds nothing to the list: it is the reviewer's fault, not the change's. When two rounds of one change run at the same time, the reviewers of a round still all see the list from their round's start, even when the other round finishes between them; a round that was shown a finding as open can still mark it as a repeat after the other round resolved it, and then it is open again. When the older round finishes last, its verdicts are left out of the list, so they cannot reopen or close what the newer round decided.

Each reviewer's verdict, the findings of a round and this list are kept in the database as JSON with snake_case field names (such as `fixable_by` and `follow_ups`). Verdicts and findings stored by an earlier version of Intakt use the same fields and read back unchanged, so updating Intakt needs no step to convert them.

## Sorting findings with the judge

The judge is a small model call (on the `light` tier of the project) that reads the task and the findings of the reviewers and marks each finding `act` (fix it now), `defer` (real, but not part of this task) or `reject` (wrong, taste, or against a non-goal of the task). The task and the findings reach it as fenced data, never as instructions. It only marks findings: it never changes a reviewer's verdict. When its answer is invalid (not the expected shape, an id it was not given, a finding left unmarked, a mark that is not one of the three, or a stream cut off), every P1 and P2 finding is marked `act` and P3 findings get no mark. When every reviewer of a round has finished, Intakt queues one judge call for the round, run by a worker outside the round's lock. The judge sees the round's findings under the ids Intakt gave them (`F1`, `F2`, ...), so two reviewers that both call a different finding `F1` do not hide one of them. These findings are kept with the round when its last reviewer finishes, so a later round of the same change, or one that finished first, does not change what the judge of this round sees. A new finding of a round that finished after a newer round of the same change gets an id with the round's number in front (`R1-F2`), so it never shares an id with a finding of a later round. A round whose reviewers reported no findings is recorded as judged without a model call. When the provider limits the call or the account is busy, the call is tried again later instead of being given up. When the call fails for another reason and its retries run out, Intakt logs an error that names the round, and the round stays unjudged. A round is judged once: the round then moves to `judged`, and a judge call delivered again asks the model nothing and records nothing. The builder's list holds only the `act` findings; each `defer` finding becomes a follow-up; a `reject` finding (and a P3 finding left unmarked after an invalid answer) is on neither. After an invalid answer every P1 and P2 finding is on the builder's list and no follow-up is made. The result is recorded as a `judge_done` event in the ledger with the ids on the act list, the ids of the follow-ups, and every finding the judge was given (id, severity and text), which the review page shows. Follow-ups are not stored anywhere else yet, and `intakt:review` prints the act list.

## Intakt's GitHub App

Intakt acts on GitHub as its own GitHub App, never with a personal token. Give it three values, the way you give it a provider key (Symfony secrets with `php bin/console secrets:set`, or `.env.local`, or the real environment): `GITHUB_APP_ID` (the App's id), `GITHUB_APP_INSTALLATION_ID` (the id of its installation on your account) and `GITHUB_APP_PRIVATE_KEY` (the App's private key, the whole PEM text). From the private key Intakt signs a proof of identity that lasts under ten minutes and exchanges it for an installation token that lasts an hour. It asks for a token for each call to GitHub and keeps one only while it has more than a minute to live; after that it asks GitHub for a new one. If the exchange fails (a wrong key or id, a removed installation, no network, an answer without a token or with an expiry date that does not exist, or a token that has expired or has less than a minute to live), the call fails with that reason and Intakt tries nothing else: no personal token, no `GITHUB_TOKEN`. The failure names the status or the kind of error, never the key or a token. When GitHub answers that Intakt used up its hourly allowance (a 403 with no calls left, or a 403 or 429 that says how long to wait, in seconds or as a date, or for GraphQL queries any answer with none left), Intakt makes no call of that kind with the installation's token until the reset time GitHub named, however far away it is (one minute when none was readable or the named time has already passed), and the call fails as rate limited with that time; a 429 is not retried. GitHub counts its ordinary (REST) calls and its GraphQL queries in separate pools, so each pause holds only calls of its own pool: the REST pause holds reading pull requests, posting reviews, publishing verdicts, the access checks of `intakt:forge:trust` and the repository list of `intakt:forge:installation`, and the GraphQL pause holds reading the history of an issue (who last edited it and who applied its labels), nothing else yet. When two answers of the same pool name different times, Intakt waits for the later one. Any other 403 is an ordinary refusal. Every REST answer's remaining allowance, hourly allowance and reset time are kept in the shared cache, so all workers see the latest reading; a GraphQL answer records none, because its pool is not the one the reserve below watches. Intakt keeps a reserve of the hourly allowance for the calls it cannot do without: 20% by default, set as `intakt.github.reserve_percent` in `config/services.yaml` (from 0, no reserve, to 100). While less than the reserve is left, Intakt reads each project's list of open pull requests once a minute on average: each listing makes the next one due a minute after this one was due or ran, whichever is later, and a listing that comes half a minute or more before its due time fails as rate limited with the reset time, without a call. Reading the CI of a head, reading a pull request, posting a review, publishing a verdict, the access checks and the installation check always go on. `/reviews` shows the installation's calls used and remaining this hour and whether the reserve is in force (see [The dashboard](#the-dashboard)). While GitHub's own pause holds, a watched head whose CI could not be read waits for the reset time and is not counted as failing (see [Watching pull requests](#capability-tiers-per-project)). To check the installation, also set `GITHUB_APP_PERMISSIONS` (the permissions the installation must hold, as `name:level` pairs separated by commas, for example `contents:write,pull_requests:write`; each permission at most once, a name given twice is refused) and `GITHUB_APP_REPOSITORIES` (the repositories it must cover, as `owner/name` separated by commas). `php bin/console intakt:forge:installation` reads the installation back from GitHub and compares it with both lists, exactly: a permission at another level, a missing or extra permission, and a missing or extra repository each make the command fail with a message that names the difference, and, through the check Intakt runs before its first call to GitHub, every read or write on GitHub is refused until the installation matches. When all match, it prints the permissions and repositories it read and exits with success. If GitHub cannot be reached, refuses the read, or lists fewer or more repositories than it counts, the check fails with the reason and tries nothing else. The messages and logs never hold the key or a token. Intakt also runs the same check by itself before its first call to GitHub: until the installation matches, every read or write on GitHub fails with the difference named, and nothing is read from or posted to a pull request.

`php bin/console intakt:forge:trust <owner/name> <login>` shows whether an account may steer Intakt on a repository. A person counts only with write access (the admin, maintain or write role; triage and read do not), which Intakt asks GitHub with its App's token on every check. A bot account (a login ending in `[bot]`, or one GitHub marks as a bot) never steers, whatever its permission, except two: Intakt's own App, whose name Intakt asks GitHub for, and the maintainer's App, whose slug you set in `GITHUB_MAINTAINER_APP_SLUG` (leave it empty while you run no maintainer App). Those two steer only while GitHub reports write access for them on the repository, asked with the App's token like a person's; without it they count as `non-writer`. The command prints `writer`, `non-writer`, `foreign-bot`, `own-identity` or `maintainer` and whether that steers. If the token exchange fails, the installation does not match, or GitHub refuses the read or answers something Intakt cannot use, the check fails with the reason and tries no other credential. No event is checked this way so far: Intakt reads who applied an issue's labels (an App is named with `[bot]`, as here), but nothing applies the rule to them yet.

Intakt reads a pull request from GitHub with that token: you name it by its web address (`https://github.com/<owner>/<repo>/pull/<number>`), and Intakt reads its head, its base (where the branch left the base branch), the diff, the changed files (a renamed file counts as the old path deleted and the new one added) and any file as it is at the head. GitHub lists at most 300 changed files, so a pull request that changes 300 files or more cannot be read yet. It can tell that the head moved during a review, and whether the new commits only added to the old head or replaced it; a merge of the base branch is always treated as new commits to review again, and new commits that change 300 files or more count as a replaced head, so earlier approvals do not carry over. A short failure at GitHub (a server error or a dropped connection) is tried again up to three times. Any other address, or a pull request GitHub does not know, is refused as not found.

Intakt posts the outcome of a review round as one review comment on the pull request, tied to the head it reviewed. The comment ends with the round's one-time token in a hidden HTML comment (`<!-- intakt-review-token: ... -->`), so Intakt can later tell that the review on GitHub is the one it counted. Just before posting, Intakt reads the pull request again: if the head moved during the round, the round is stale and nothing is posted. Before that, Intakt redacts the text: every credential value the job that wrote the text held (also when the text holds it JSON-encoded once or more, whatever the nesting, including line breaks, quotes and accented or other non-English letters written as escapes), the values of authorization, cookie and API key headers (in plain text, quoted, shell-quoted, in JSON at any depth, in `print_r` or `var_export` dumps including list values and lists inside lists, and Digest parameters; a list of header values that is the value of a quoted key in JSON or a `var_export` dump becomes one `[redacted]` and the fields after it on the same line stay, while any other value in brackets, like `Cookie: [a]; sid=...`, `Authorization: ['Bearer x'] ...` or a quoted key inside another header's value such as `Cookie: x; 'authorization': ["a"], sid=...`, is redacted whole, to the end of its line or quote), the user and password of a URL (`https://user:password@host`, also as JSON writes it, `https:\/\/user:password@host`), and strings shaped like secrets (GitHub and cloud tokens, bearer tokens, private key blocks) become `[redacted]`; when a header's end cannot be found, the rest of the text is redacted, and a header list in a `print_r` dump is redacted to the end of the text, because `print_r` does not quote values and its end cannot be told apart from a value (redacting too much is accepted, stopping too early is not). Then Intakt scans the text with `gitleaks` (which must be installed where Intakt runs, on the path or named by `INTAKT_GITLEAKS`, and needs several gigabytes of address space when it starts, so a tight memory limit makes every post fail): if the scan still finds something that looks like a key or password, nothing is posted. If the pull request cannot be read again, GitHub refuses the post or cannot be reached, or the scan cannot run, the post fails with the status or the kind of error. The post is never tried again, because GitHub may have stored a review it answered with an error, and a second try would post it twice. No review round uses this yet. Intakt does not fetch or push with git yet, so no git command uses the token so far.

## Releases

Releases normally come from the [release train](../releasing.md#the-release-train): twice a day it cuts a release from a green `main`, but only when a `feat` or `fix` commit landed since the previous tag. The owner cuts milestone versions by hand. Every release is a signed tag and a GitHub release marked pre-release before `v1.0.0`. `v0.1.0` has hand-written notes; every later release uses generated notes. A pull request is labeled `feat`, `fix` or `docs` from the type in its title, so the notes list it under Features, Fixes or Docs; anything else lands under "Other changes". No CHANGELOG file is kept. See [Releasing](../releasing.md).

## The weekly report: the loop's reviews and Intakt's

When Intakt reviews for the loop, the loop's GPT reviewer and Intakt both post their review on the same heads of a pull request. `php bin/console intakt:reviewer-for-loop:weekly-report <folder>` compares them, from recorded pull requests: the folder holds one JSON file per pull request with `pullRequest` (its number), `loop` (the loop's account), `intakt` (Intakt's App account) and `comments`, each with `author`, `head`, `postedAt` (a moment with its offset, as GitHub writes it, for example `2026-11-03T09:12:00Z`) and `body`; see `tests/Fixtures/ReviewerForLoop/weekly/`. Every file ending in `.json` is read, in name order; other files and subfolders are skipped. Nothing fetches the comments from GitHub yet, so the folder has to be recorded first.

The week is the seven days before `--until` (a moment with its offset; without it, now). Only reviews are compared: on the loop's side, a comment whose `Reviewer:` line names `gpt` (the loop's other reviewers and its ordinary messages are left out), and on Intakt's side, a comment with a verdict block (a JSON line or a json fence, even one that cannot be read). A head belongs to the week in which the last of these reviews on it was posted: a review posted exactly at the end of the week belongs to the next week. Comments by other accounts are ignored. Both sides are read with the rules for the loop's reviews above (Intakt publishes its review in the same shape). The command prints the week, then a table with one row per head (pull request, head, each side's decision per reviewer, the agreement, the matched findings, and the findings only the loop or only Intakt raised, by severity, file and line), then a summary line. The agreement is:

- `agree` when both sides ask for changes, or both approve;
- `disagree` when one side asks for changes and the other approves;
- `incomplete` when a side posted no review on the head, or one of its reviews could not be read, even when another of its reviews asks for changes. A review that cannot be read never counts as agreement.

Otherwise a side asks for changes when any of its reviews does. Findings are matched by file and line (same file, lines at most 3 apart, a spot several reviewers of one side raised counts once); a finding Intakt files under `Follow-ups:` in an approval still counts as a finding. A finding line without a file and line is not read. An end that is not such a moment, a folder that cannot be read, or a file in it that is not a recorded pull request, stops the command with an error that names it.

## The sample repository

`fixtures/sample-repository/` holds a small shop project to try a review on. `base/` is the base commit and `pull-request/` holds the files the pull request branch adds or changes. The branch carries three deliberate issues (a bug, a new function without a test, and a command built from input), listed in `issues.json` so a later check can tell whether a review found them. The folder's `README.md` has the git commands that turn it into a repository with a `main` branch and a `sample-change` branch. The demo builds that repository for you (see below).

## The demo with docker compose

```
cp .env.dist .env.local   # fill in one or two provider keys (or HF_TOKEN) and the two secrets
docker compose up
```

`.env.local` needs at least one of `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and `HF_TOKEN`, and `APP_SECRET` and `MERCURE_JWT_SECRET` (generate each with `openssl rand -hex 32`). The image is built from the `Dockerfile`, the dashboard answers on `http://localhost:7781` (on this computer only), and the data lives in the volume `intakt-data`.

The first start seeds the demo, in the volume:

- the sample repository at `/app/var/data/sample-repository`, with the branch `sample-change` to review against `main`;
- the project `sample` in `/app/var/data/intakt.yaml`, with a panel of two reviewers (`correctness` and `security`) that must both approve. With one Anthropic or OpenAI key, both reviewers use that provider; with both keys, `correctness` uses Anthropic and `security` uses OpenAI. With `HF_TOKEN` beside one or both keys, `security` moves to Hugging Face, so the two reviewers use two providers; with `HF_TOKEN` alone, see [Running the demo on a Hugging Face token](#running-the-demo-on-a-hugging-face-token).

The log then shows the command that reviews the sample change, in the form your shell runs from the repository folder (it runs the console inside the container). Copy it as printed:

```
docker compose exec intakt php bin/console intakt:review sample-change --project=sample --repository=/app/var/data/sample-repository --base=main --task="Add a shipping cost by weight and a report of a customer's orders; a cart of 100 or more keeps its discount."
```

The first start also makes the owner's MCP token, unless `MCP_OWNER_TOKEN` is set in `.env.local` (then yours is used), keeps it in `/app/var/data/mcp-owner-token` on the volume, and allows write tools for the demo (`MCP_OWNER_ACCESS` defaults to `mcp_tool_write` in the container). The log prints, after the review command, a line to connect an MCP client:

```
claude mcp add --transport http intakt http://localhost:7781/mcp/owner --header "Authorization: Bearer <the token>"
```

Run it, then ask your agent to start a review with the values of the review command above: project `sample`, change `sample-change`, base `main`, repository `/app/var/data/sample-repository` (the default `.` is not the sample) and the text after `--task=` as the task. A start that cannot make or read the token file stops before the seed with `intakt: could not make or read the MCP owner token in /app/var/data/mcp-owner-token`; two starts at once on one volume get the same token.

The token is a secret that sits in the log (`docker compose logs intakt`) and in the volume; `docker compose down -v` makes a new one. [Connecting an agent through MCP](mcp.md) says what the client can do.

Later starts keep both as they are (the log says `Kept`), also when you add a key. To seed again, for example after adding the second key, remove the volume with `docker compose down -v` (this also removes the database) or delete `/app/var/data/intakt.yaml` in the container and start again. Without any provider key the first start stops with `Set ANTHROPIC_API_KEY or OPENAI_API_KEY or HF_TOKEN to seed the sample project.`; an `openai_compatible` endpoint other than the Hugging Face router does not count for the seed, because the seeded models are router models. Without one of the secrets it stops naming the missing one.

### Running the demo on a Hugging Face token

`HF_TOKEN` lets you try the demo without an Anthropic or OpenAI key. The demo needs one provider key or one Hugging Face token, and its calls are billed to the key's or the token's owner. Create a fine-grained token on Hugging Face with only the permission "Make calls to Inference Providers". The container hands it to the `openai_compatible` provider, with `https://router.huggingface.co` as the base URL, unless you set `OPENAI_COMPATIBLE_BASE_URL` or `OPENAI_COMPATIBLE_API_KEY` in the environment yourself (then yours win and the token is not used).

- With `HF_TOKEN` alone, the two reviewers run on models of two different makers through it: `correctness` on `moonshotai/Kimi-K3:deepinfra` and `security` on `openai/gpt-oss-120b:novita`.
- With `HF_TOKEN` and `ANTHROPIC_API_KEY`, `correctness` stays on Anthropic and `security` runs on `moonshotai/Kimi-K3:deepinfra`. Two separate providers are the stronger setup: one token is one outage, one rate limit and one bill.

Two things to know when you set up Hugging Face yourself, for example as `openai_compatible` in your own configuration:

- The base URL is `https://router.huggingface.co`, without `/v1` at the end. Intakt adds `/v1/chat/completions` itself; with `/v1` in the base URL the call goes to `/v1/v1/chat/completions` and fails with a plain "Bad Request".
- Name the router provider after the model, as the seeded models do (`:deepinfra`, `:novita`). Every reviewer call uses tools together with structured output, and some router providers refuse that combination: Groq and Cerebras did. DeepInfra and Baseten (for `moonshotai/Kimi-K3`), Novita (for `openai/gpt-oss-120b`) and DeepInfra (for `deepseek-ai/DeepSeek-V4.1-Flash`) accepted it. The router's default provider may be one that refuses, and the error then says only "Bad Request".

Project memory still needs an OpenAI key: a Hugging Face token alone gives no embeddings.

## Keeping a copy of a project's repository

`php bin/console intakt:mirror:update <project> <remote>` keeps one bare copy (a mirror) of a project's repository in `var/mirrors/<project>.git`. The first run copies the whole repository from `<remote>` (a path, a `file://` or an `https://` address; a relative path counts from the mirrors folder `var/mirrors`, not from where you run the command); later runs fetch what is new and drop branches the remote deleted. The mirror's `HEAD` follows the remote's, also when the remote's `HEAD` is a detached commit, even one on no branch or tag, and a SHA-256 repository gets a SHA-256 mirror. If the branch the remote's `HEAD` names is deleted during a run, so the mirror's `HEAD` would point at nothing, the run says so and exits with 1, and the next run sets `HEAD` again. A first copy is built in a hidden folder beside it and only takes the mirror's place once it is complete, so a copy that fails half-way never counts as a mirror; a folder at the mirror's place that is not a bare repository is replaced. The project name must start with a letter or digit and may hold letters, digits, `.`, `_` and `-`. If git cannot reach the remote, hangs past 10 minutes or is stopped, Intakt waits 10 seconds and tries again, waits 30 more seconds and tries a last time, logging each wait; then it prints git's message (or, for a call that hung or was stopped, the reason in Intakt's own words, never the command with a password that may be in the address) and exits with 1. The mirror keeps neither the remote's address nor a password that may be in it (you name the remote on every run). Delete the mirror and the next run copies it again.

`php bin/console intakt:build:clone <project> <branch> <directory>` makes the copy a build works in, from the project's mirror (run `intakt:mirror:update` first). The new folder `<directory>` holds main (the branch the mirror's `HEAD` names) and the task's `<branch>`, checked out, and nothing else: no other branch, no tag and no remote. A branch the mirror does not hold yet starts at main. The command refuses a `<directory>` where anything already is (a folder, a file or a link, also a folder another `intakt:build:clone` made a moment before, so two runs for the same folder never share it), a project name that breaks the rule above, a project without a mirror, a mirror whose `HEAD` names no branch, a branch name git does not accept and a branch that is main itself; if a step fails after it made the folder, it removes that folder; it prints the reason and exits with 1. On success it prints `clone <directory>`.

A task split from a bigger change can build on an earlier piece of work with a line of its own `Source: <branch>@<sha>` (the full commit id). Give the task's text as a file with `--task=<file>`. Add `--trusted-author` when the task's author has write access to the project: the command then checks in the mirror that the commit is on that branch and adds that one commit to the copy as `refs/source/<branch>`, not as a branch and without any later commit of that branch. A source branch git does not accept, a branch the mirror does not hold, a commit that is not on the branch, an id that names something other than a commit (an annotated tag, for example) and a task with two source lines are refused, and no copy is made. Without `--trusted-author` the source line is ignored: the command prints one line starting with `comment` that says so, and makes the copy without it. A sentence that only mentions a source line, a quoted or indented line, a line inside a fenced code example (between lines of three backticks or tildes), a line inside an `<!-- external -->` ... `<!-- /external -->` block (text copied from outside, which does not count even in a trusted task; a block that is never closed runs to the end of the text) and a short commit id are not source lines. A task file that cannot be read is refused.

## Running a build

`php bin/console intakt:build:run <project> <clone> <branch> <task> <image> <bundle>` runs a first build of a task: the Claude Code command-line tool works on the task in a container of its own, made from the project's job image `<image>`, and hands back its commits and the pull request text. `<clone>` is a copy made with `intakt:build:clone` for the same `<branch>`, and `<task>` is a file holding the task's text. Add `--decision="..."` once for each of your decisions on the task, in order. The model comes from the project's tiers in `config/intakt.yaml` ([Capability tiers per project](#capability-tiers-per-project)): `--tier=strong`, `standard` (the default) or `light`, and that tier must use the `claude_code` provider.

The builder gets the copy's branches, the [instructions](#what-a-builder-is-told), and a network that reaches only Anthropic's API and the package registries. When it made at least one commit on the branch and wrote `PR.md`, the command writes the commits as a git bundle to `<bundle>`, prints `bundle <bundle>`, `pull request text:` and the text, and exits with 0. Check the bundle with `intakt:hand-back:check` before you trust it ([Checking what a build hands back](#checking-what-a-build-hands-back)). Otherwise it prints the end of the build's log and the reason (no commit, which is also what you see when the job could not prepare the copy of the branch, so check that the copy exists and holds the branch; no pull request text, out of memory, out of time after an hour, an output too big or not plain files, or files the builder put in the output folder itself that the job could not remove), writes no bundle and exits with 1. A second build of the same branch of the same project is refused while one runs.

A build session gets at most 100 turns and 3000 seconds (50 minutes); these are fixed for now. When it reaches either limit, the session ends, but the commits it made before are kept: the build then ends as described above, with the bundle of those commits when the builder also wrote `PR.md`. `build.log` then says `claude cut after 3000 seconds, its commits are kept` when the time ran out. The hour limit above is only a backstop for a job that hangs after the session: a job stopped by it hands back nothing.

It needs a Docker engine (see [Job containers](../architecture/job-containers.md)). The container does not get your Claude login yet, so a real build cannot sign in; running one is not possible until that part is built.

## Checking what a build hands back

A build returns its commits as a git bundle, and the text of its pull request. `php bin/console intakt:hand-back:check <repository> <branch> <bundle> <pull-request-text> [--merge-main] [--credential-env=<variable>]...` checks both before anything trusts them. `<repository>` is a bare repository whose `HEAD` names main, such as the project's mirror; `<branch>` is the task's branch; `<pull-request-text>` is a file holding the pull request text (one that cannot be read is an error and exits with 1). The bundle is refused when:

- it is not a git bundle Intakt can read (a missing file, a folder, another file, a broken pack, or a filtered bundle);
- it updates main;
- it names any ref other than the task's branch;
- it builds on a commit that is neither on the task's pushed branch nor on main (also when its header does not list that commit, or it names a commit another branch holds without carrying it);
- it leaves out a commit, folder or file its new commits need (one the repository holds on another branch counts as left out);
- it is not a fast-forward of the pushed branch, or, when the branch was not pushed yet, it does not start on main (any commit of main counts, so main moving while the build ran refuses nothing);
- it holds a merge commit. With `--merge-main` (the task asked for a merge of main), a merge whose other parents are all on main is allowed; a merge of anything else is still refused;
- one of its new commits is malformed, so git itself would not write it (for example a commit with no author);
- a file or file name it adds holds the value of a credential mounted into the build job (see `--credential-env` below), also when a later commit deletes it again;
- the secret scan (`gitleaks` with its built-in rules) finds a secret in anything it adds: a commit and its message, a folder listing or a file, also one a later commit deletes again. Scanner settings, ignore lists and inline allow comments the build committed are ignored, and so are `GITLEAKS_CONFIG` and `GITLEAKS_CONFIG_TOML`.

When the bundle passes, the pull request text is refused when it holds the value of a mounted credential, or when the same secret scan finds a secret in it. The text is refused, not cleaned, so the builder writes it again without the value.

A refusal is sent back to the builder once: it prints `refused, sent back to the builder:` and a fixed reason. When the task's previous hand-back was sent back too, the refusal hands the task over instead and prints `refused, handed over:` and the reason. An accepted hand-back, or a hand-over, starts the count again. Either way the command exits with 1, and the reason never holds a ref name, commit id, secret or other text from the bundle or the pull request text. Each outcome is recorded in the ledger (`hand_back_accepted`, `hand_back_sent_back` or `hand_back_handed_over`, with the repository, the branch and the reason or the accepted head; see `intakt:ledger:events`), and a task is counted by its repository and branch. A ledger that does not take the line is an error and exits with 1. Nothing yet passes the reason to a builder or the hand-over to the maintainer agent; the build lane will. A branch name git does not accept, a branch that is main, and a path that is no such repository are errors and exit with 1 as well. So is a secret scan that cannot run or fails: the bundle is then not accepted, and nothing is recorded, because that is no fault of the build. The scan runs the `gitleaks` that `INTAKT_GITLEAKS` names (`gitleaks` from the path when it is unset or empty), as before a review is posted.

Name each credential that was mounted into the build job with `--credential-env=<variable>`, the environment variable that holds its value (the value itself never goes on the command line, where other users of the machine could see it). Its value is replaced by `[redacted]` in every new commit's message and in its author and committer, which gives that commit a new id like a stripped one. A named variable that is unset or empty is an error and exits with 1.

An accepted bundle loses its attribution: from each new commit (main's own commits are left as they are) the `Co-authored-by:` trailers and the lines that start with `Generated with`, `Generated by` or `Generated-by:` (in any case, after an emoji or other mark) are removed. A changed commit, and every new commit after it, gets a new id and no signature, because Intakt signs the commits itself before it pushes. The command prints `accepted <head>`, `base <commit>` (the pushed branch it checked against, or `base none` when the branch was not pushed yet) and `rewritten <count>`, and exits with 0. Nothing is pushed and no ref is changed: the commits are only added to the repository's objects. A refused bundle adds nothing, because its objects are kept apart until every check passed. An accepted bundle also adds its commits as the build wrote them (with attribution or a credential in the message) beside the rewritten ones, in the repository only: no branch names them, so nothing pushes them; that is also so when the bundle passes and only the pull request text is refused.

## Listing the protected paths a head touches

The files a change may only touch with an approval (a project's checks, its CI setup, its agents' instructions) are your list, kept in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names), never in the project's repository, so a change can never edit the list that judges it. Give each project a `protected_paths` list and run `php bin/console cache:clear`:

```yaml
projects:
    alpha:
        protected_paths: [bin/check, config/gates/, .github, AGENTS.md]
```

An entry names a file or a folder from the repository's root, and protects that file, or everything in that folder, at any depth; a trailing `/` changes nothing. Letters must match exactly, also in case, so `bin/check` does not protect `bin/checker` or `BIN/check`. An entry that starts with `/`, has an empty, `.` or `..` part, or is not text stops Intakt from starting and names the entry. `.gitmodules` at the root and every submodule are always protected, also without an entry; a project without a list protects only those.

`php bin/console intakt:protected:list <project> <head>` lists the protected paths the head (a full commit id) touches, read from the project's mirror (run `intakt:mirror:update` first), where main is the commit the branch the mirror's `HEAD` names points at when the check starts (a mirror update during the check does not change it). It reads the whole change from where the head left main to the head, and each commit the head has that main lacks, also those a merge brought in from another branch, so a protected file changed and changed back, or reverted or deleted by a merge made by hand, is still listed. What a merge of main brings in is main's own and is not listed: a file a commit leaves exactly as the current main has it is never listed for that commit, while a merge that sets a file back to an older main's version is. It prints `protected <path>` for each path, then `touches protected paths: yes` or `no`, and exits with 0. When it cannot read the change (no mirror, a mirror whose `HEAD` names no branch or a branch without a commit, a commit the mirror does not hold, an id that names an annotated tag, a shallow mirror, a missing object), it prints `unreadable` and the reason, and the head counts as touching protected paths. A head that is not a full commit id, such as a branch name, and a project name that breaks the rule above, are refused with exit 1. Holding a protected head for your approval is not built yet.

## Scanning a workflow file for CI risk

A pull request runs the workflow of its own branch on your runners, so a change to a GitHub Actions workflow can run before anyone reviewed it. `php bin/console intakt:forge:workflow-risk <file>` reads one workflow file and lists everything in it beyond a GitHub-hosted runner with a read-only token and no secrets, one line each: `line <n>: <kind>: <what it found>`, where the kind is:

- `runner`: a job runs on a label that is not one of GitHub's standard hosted labels (such as `ubuntu-latest`, `ubuntu-24.04`, `windows-latest` or `macos-15`), or picks its runner by group;
- `permissions`: the token may write (a scope set to `write`, or `write-all`), or a job gets no `permissions` from itself or the workflow, so the repository's default applies, which may write;
- `secret`: the file reads a repository secret (`secrets.<NAME>` in any value, in any case, also inside a `|` or `>` block, or `secrets:` passed to another workflow); the job's own `secrets.GITHUB_TOKEN` is fine;
- `trigger`: an event other than `push`, `pull_request`, `workflow_dispatch`, `schedule` and `merge_group`, such as `pull_request_target`, `workflow_run` or `issue_comment`;
- `unreadable`: a form the scan does not read, such as an anchor or alias (`&name`, `*name`), a tag, a value over several lines that is not a `|` or `>` block, a block with an indentation number or a line indented less than its first line, a nested flow value (`[[...]]`, or `[...]` holding `${{ }}`), an escape in a double-quoted value, a key that appears twice, a tab in the indentation, a second document, text that is not UTF-8, a job that calls another workflow (`uses:`), a job without `runs-on`, or a workflow without `on` or `jobs`. A `runs-on` taken from an expression such as `${{ vars.CI_RUNS_ON }}` or `${{ matrix.os }}` is `unreadable` too, also as the `group` or `labels` of a runner picked by group: the scan never reads a variable's value, so it counts even while the variable is unset, because its value can change without a commit.

It then prints `risky: <count> findings` and exits with 1, or prints `no risk: hosted runners, a read-only token, no secrets` and exits with 0. A file it cannot open is refused with exit 2. This command reads only the file you name; `intakt:forge:ci-scan` (below) reads all the workflows of a change.

The files a workflow runs are part of the CI definition, so changing one is a CI change. A changed file counts when any workflow's text names its file name (or a longer trailing part of its path) as a whole word, in any case (accented letters too), whatever folder the workflow runs it from; so do everything under `.github/`, every Dockerfile, everything in the folder of a local action (`uses: ./tools/build`, folder in any case), and every file when a workflow cannot be read or is in a form the strict line reader does not read (such as an escaped key or value, which could spell a file name the text does not show). Files a workflow runs without naming them, such as Makefile targets or Composer scripts, are not found this way; your approval of the push decides those. `php bin/console intakt:forge:ci-paths <path>... --workflow=<file>` (repeat `--workflow` for each workflow) prints `ci <path>` for each changed path that counts, then `CI change: yes` or `no`, and exits with 0.

`php bin/console intakt:forge:ci-scan <repository> <head>` puts both together for a whole change. `<repository>` is a git directory: a project's bare mirror, where main is the branch its `HEAD` names (the remote's default branch), or the `.git` folder of a clone, where main is the branch checked out; `<head>` is a branch or commit in it. It reads the `.yml` and `.yaml` files directly in `.github/workflows/` of the head, of main and of the two merged (as git merges them, without a checkout), scans each, and prints each finding as `<head|main|merged> <file> line <n>: <kind>: <what it found>`. A workflow it cannot read counts as `unreadable` (at line 0): a symbolic link or submodule in that folder, a `.github` or `.github/workflows` that is a link, a submodule or a file instead of a folder, a failed git read, and the merged workflows when the head does not merge with main without a conflict. Then it prints `ci <path>` for each changed path that is part of the CI definition (every file where the head or the merge differs from main, so a file main changed after the head branched off counts too; with a conflict every such file counts), and `risky: yes|no`, `CI change: yes|no` and `push waits for the owner: yes|no`. A change waits for you when it is a CI change and any workflow on any side is risky; it then exits with 1, otherwise with 0. A repository whose `HEAD` names no branch, a head that names no commit, or a merge git cannot try (such as unrelated histories), is refused with exit 2. `intakt:forge:push-approval` (below) holds a push on this answer.

## Holding a risky CI change for your approval

A risky CI change stays local until you approve its push. `php bin/console intakt:forge:push-approval <repository> <head> --project=<project> --issue=<n>` takes the same `<repository>` and `<head>` as `intakt:forge:ci-scan`, resolves the head to one commit, scans it the same way and prints the findings and `ci <path>` lines. Then it prints one decision:

- `push: free (no risky CI change)`, exit 0: the change may be pushed without you, and GitHub is not asked.
- `push: approved by the owner for <sha>`, exit 0: the issue holds your comment `approve <sha>` for exactly this commit, posted after Intakt's request for it, and the change can still be shown in full.
- `push: held, the owner was asked on issue #<n> to approve <sha>`, exit 1: it posted one comment on the task's issue (`<n>`, in the GitHub repository of the project's `watch` section) that holds what the scan found, the complete diff from where the head left main to the head (every file, binary files as text), and the line to reply with.
- `push: held, still waiting for the owner's approve <sha> on issue #<n>`, exit 1: that comment is already there, so nothing is posted again.
- `push: held, the change cannot be shown in full and goes back to be split: <reason>`, exit 1: nothing is posted when the comment would be longer than 65536 characters (GitHub's limit), when the diff is not UTF-8 text or holds a NUL byte, or when the secret scan finds a credential in it. A change is never shown to you as a file list or cut.
- `push: held, nothing was decided: <reason>`, exit 2: the head names no commit, the repository's `HEAD` names no branch, the head and main do not have exactly one merge base, GitHub could not be read or written, or another run is asking about the same head at that moment.

Only your own account counts. Set your GitHub login in `GITHUB_OWNER_LOGIN`; while it is empty, no approval counts and a risky change stays held. Your approval is a comment whose whole text is `approve ` followed by the full commit id (40 characters, or 64 in a SHA-256 repository); a short id does not count, since a builder can make a commit whose short id matches. An approval posted before Intakt's request for that commit does not count either, since you approve the diff the request shows: reply after the request. When someone edits Intakt's request, it no longer counts: Intakt posts the request again, and only an approval after the new one counts. A comment by another account or an App (also an App that posts in your name with your permission), a comment with other text around the line, and a comment that was edited (an admin or an App can edit your comment) do not count. Each new commit needs a new approval. Approving the push does not approve the merge: you are asked again before the change merges. Without the settings of [Intakt's GitHub App](#intakts-github-app), a held change stops with the settings error and exit 1.
