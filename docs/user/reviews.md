# Reviews from the command line

Intakt reviews a branch of a local git repository from the command line, the same way it will review a pull request. This page covers how it reads the change and summarizes a branch, how a model is asked for a verdict and what a reviewer can read, the `intakt:review` command and its output, and how findings keep their ids and are sorted by the judge.

## Reading a change from a local repository

Intakt can treat a branch of a local git repository as a pull request: the branch is the change and the repository's base branch is what it is compared with. It reads the branch's latest commit, the diff against the point where the branch left the base, the list of changed files and any file as it was at that commit (by its exact name, even one starting with `:`; a binary file only by its size), ignoring git's replacement refs (`git replace`) and graft file (`.git/info/grafts`), which could otherwise show other content under the same commit or hide commits. It reads the repository with its own git settings: the repository's configuration and attributes cannot run a program (a hook, a filter, a diff or signature tool, or a fetch from a remote the repository names for an object it lacks: such an object is an error, never fetched) or change what is read, every file in the diff is shown as text except a binary file (one with a NUL byte anywhere, before or after the change), which the diff names as binary with its size at the base and at the head instead of showing its bytes (in a text file, a byte that is not valid UTF-8 is shown escaped, such as `�{E9}`; a branch that adds, changes or deletes a file whose name is not valid UTF-8 cannot be read, and the error names the file with such escapes; a file whose permissions alone changed shows only its old and new mode, never as binary), and the git configuration of the user running Intakt (`~/.gitconfig`, even a broken one) is not read. A repository whose `.git/info/attributes` file exists cannot be read, because that file could hide a change and git offers no way to ignore it: remove it first. It notices when the branch has moved to a newer commit since it was read. A name that is not a valid branch name (such as `../tags/v1`) is treated like a branch that does not exist. It only reads; it never changes the repository. `php bin/console intakt:change:summarize <branch>` prints what it reads (see [Summarizing a branch](#summarizing-a-branch)); for an invalid name it prints the same error as for a missing branch and exits with 1.

## Summarizing a branch

`php bin/console intakt:change:summarize <branch> [--repository=.] [--base=main]` prints the change summary of a branch of a local repository against its base branch: the short base and head commits, the number of changed files with the added and removed lines, and one line per file (`added`, `modified` or `deleted`). A control character in a file name is shown in a visible form such as `\x1b`, and a backslash as `\\`. A `--repository` that is not a directory, an empty branch or `--base`, a branch the repository does not have, a repository git cannot read, or a repository whose `.git/info/attributes` file exists, prints an error and exits with 1. The summary is what the branch has gained since it was cut from the base branch, not what the base branch gained afterwards.

## Checking whether a verdict still counts

A reviewer's verdict counts only for what it reviewed: the branch's latest commit, the commit it was compared with, the task, the check command and the project's review panel. `php bin/console intakt:verdict:identity <project> <branch> <task> <check-command> [--repository=.] [--base=main]` prints that identity as one line, `identity` followed by five parts separated by dots (the two commits, then fingerprints of the task text, the check command and the panel). The task text and the command are not shown, only their fingerprints.

Pass a printed identity back with `--reviewed=<identity>` to see whether a verdict given on it still counts:

- `current`: nothing changed.
- `stale: head changed` (or any other changed parts): the verdict no longer counts. A new task text, check command or panel always makes it stale, and so does a new commit, unless one of the two cases below applies.
- `kept-for-untouched-parts: ...`: the verdict still counts for everything the change left alone, and each `review again <path>` line names a file to review again. This happens when the base branch was merged into the branch and git merged it by itself (no conflict to resolve, no other edit in the merge commit), or when the new commits touch only files in the repository's `docs/` folder and the base did not move.

A project without a review panel, a `--repository` that is not a directory, a branch the repository does not have, or an identity that is not in the printed form prints an error and exits with 1. Every review round remembers the identity it was started on, and reading its verdicts applies the same rules: a stale round's verdicts no longer count. Nothing reads stored rounds that way yet. `intakt:review` does not read an older round: its own round reviews a snapshot of the branch's head instead (see [Reviewing a branch](#reviewing-a-branch)).

## Asking a model for a verdict

Inside Intakt, the vendor asks the model of a project's capability tier to review a change and gets back a verdict: an approve or changes decision with findings. The reviewer is asked for `approve` or `changes` only; a problem that must stop the change is a finding of severity P1, not a verdict of its own. A reviewer that still answers `blocked` and names at least one finding is recorded as `changes` with those findings (see [Reviewing a branch](#reviewing-a-branch)); `blocked` stays for the cases where Intakt itself holds a review back. The model is a reviewer agent: it gets a role prompt, the task, the diff of the change (what it adds, edits and deletes) and the rules of how code reads, and it may read the files of the head under review with the tools described below before it answers. Each finding names the rule it breaks. The task text, the diff and everything the tools return are marked as untrusted data in the prompt, so text in a task or in the code under review cannot give the reviewer orders. A fence ends only at a closing marker that repeats its own boundary, so a fake closing marker in a file stays data. A reviewer that keeps asking for tools without answering (30 rounds of requests, however many files one round asks for), that makes a malformed tool request (a missing argument, a path that is not text, or a tool that does not exist), or that answers with something that is not a verdict (also a verdict that names finding ids that were not open, marks one id both fixed and repeated, or gives a finding one of the ids Intakt keeps for its own failed reviews, such as `no-tools` or `reviewer-stopped`) gave an answer Intakt cannot read as a verdict. Intakt asks it once more, in a new conversation with twice the output room, as it does for a call stopped by its output limit; when the second answer cannot be read either, the reviewer fails with the reason "the reviewer's answer could not be read as a verdict". When Intakt can say why in its own words without repeating the model's text (a malformed tool request, the limit of tool rounds, finding ids that look like Intakt's ids but were not open, finding ids kept for failed reviews, a blank field or a line number below 1), the reason goes on after a colon, for example "the reviewer's answer could not be read as a verdict: the verdict names ids that were not open: F9."; text from the model's answer is never shown, because it could hold a key. Such an answer never counts as changes or as approval, and it never reaches the judge. One that answers `changes` or `blocked` without naming a finding is asked once more at once, and fails when it does so again. A reviewer stopped from the dashboard still counts as stopped after a malformed request. Only the reviewer's final answer is read as its verdict: the text it writes before a tool request is not, and a final answer written beside the model's thinking (as Anthropic models answer, streamed or not, also after tool requests) is read like any other. A final answer split into two separate pieces of text cannot be read as a verdict, because which piece is the verdict would be a guess; neither can one with no text at all, unless it was streamed, which fails like an answer cut off. A task, a diff or a tool answer longer than 100000 bytes is cut to that size, with a note from Intakt after it that says how much was left out; when anything in a review was cut, an `approve` from the reviewer, or a `changes` with only P3 findings (which can count as approval), becomes `blocked` with the reason `cut-approval` (any other `changes` stays `changes`), so split a change that big or review it yourself. There is no command for it yet; the review loop will use it.

Each reviewer keeps its conversation of a review round (the prompt, the model's answers, the tool calls and what they returned) in the database table `reviewer_conversation`, one conversation per reviewer and round (a reviewer that is started again, after a stopped worker or a rate limit, begins a new one), so a reviewer never sees what another one was told or answered; a review that would reuse a conversation already started is refused before the model is asked. `php bin/console doctrine:migrations:migrate` creates it with the ledger table. Prompt caching is on for Anthropic models (the five-minute window), so a round that follows another in a review pays less for the part of the conversation the provider already holds.

Every such review is recorded in the ledger as `usage_recorded` events: one when it starts, and one when it ends, either with the tokens it used in all its rounds (one entry per model call, because the reviewer may call tools between answers) (prompt, completion, cached and the others the provider reports, plus the remaining-token figures) or marked unsettled when the call failed, with the tokens of every round whose tokens could be read; a round whose tokens cannot be read is left out of the row and a warning is logged for it. Both carry the same call id, so a call is counted once. An answer that is not a valid verdict still records the tokens it used, and so does the call that asks again. If the tokens of an answer cannot be read, the call is marked unsettled with the tokens of its other rounds and one warning is logged for that round, but the review still gets its verdict. If the ledger cannot store the first row, the call is not sent; if it cannot store the last one, the call fails and the row, tokens included, is logged as an error so it can be recorded later. `php bin/console intakt:ledger:events` shows the rows.

A call the provider refuses because of a rate limit or quota fails with a clear error that carries the time to wait when the provider sent one; other temporary provider errors fail with their own error, so a later retry can tell them apart. Either one cools the account down, also when it arrives while the answer is being streamed, and the review moves to another account of the same provider when one is free (see [More than one account of a provider](providers.md#more-than-one-account-of-a-provider)).

Run `php bin/console intakt:vendor:probe` after you set or change a provider key, to check the setup before a first review. It checks the real setup: it sends one tiny call to each enabled provider your projects use and prints a line with the model and the tokens used (prompt, completion, cached, total, remaining). It uses the keys from your environment, costs a few tokens per provider, and exits with 1 if any call fails. It checks only the providers your projects' tiers use, so a provider none of them uses is not called (the provider of an account the Waiting on you page names may be one of them), and it does not tell whether Intakt reads an account's usage again. A failed call shows only the kind of error, never the provider's message, so a key it echoes stays off your screen. A provider that is switched off (see the `Provider "..." is disabled` lines above) is not probed.

## What a reviewer can read

A reviewer reads the change through three read-only tools: it can read a file, list a directory and search for text, all at the head under review and nothing else. A request for a file outside the repository (a `../` path, an absolute path, the `.git` folder, or a link pointing out of the checkout or into the `.git` folder) is refused with a message, and the file is never opened. Reading a binary file (one with a NUL byte anywhere, such as a PNG image) gives the reviewer only `Binary file, not shown: <size> bytes`, never the file's bytes. A tool that fails, such as a file that does not exist or a text file that is not valid UTF-8, gives the reviewer an error message and the review goes on. A search skips binary files and files over 1 MB, shortens very long matching lines and returns at most 100 matches; a listing of a very large directory is shortened too. The reviewer agent uses these tools; a request it makes that is refused or fails is answered with a message and the review goes on.

## Reviewing a branch

`php bin/console intakt:review <branch> --project=<project> --task="<what the branch builds>" [--round=N] [--format=text|json] [--repository=.] [--base=main] [--check-command=bin/check]` reviews a branch of a local repository end to end: it chooses the project's panel for the change (its changed lines and paths), starts a round, waits for the workers, and prints the outcome, the act list, the tokens used and their cost. The reviewers read a snapshot of the branch's head, not your checkout: the command creates a detached git worktree of the head's commit in the system's temporary directory (an entry under `.git/worktrees/` in your repository, made without running the repository's hooks or filters) and removes it when the round ends. The branch need not be checked out, and nothing you do in the checkout while the round runs (switching branches, editing files, committing) changes what the reviewers read: they review the commits the branch pointed at when the command started. Start the workers first (`php bin/console messenger:consume async`, see above), on the same machine, because they read the snapshot by its path: the command only queues the round and waits for them, for at most its upper wait: one hour for each reviewer of the panel plus one hour for the judge (three hours for a panel of two), long enough for one worker to run the reviewers one after another. A round with no outcome by then, for whatever cause (no worker running, a provider that keeps limiting the calls), ends as `blocked` with the reason "no outcome in time", and loses its snapshot, so a reviewer still reading it fails. A round whose judging failed for good (the judge's message failed after the worker's retries and the failure was recorded in the ledger as `judging_failed`) ends the command at once as `blocked` with the line `reason: the judging failed`; the round stays unjudged. The snapshot holds the head's files exactly as committed: a line-ending conversion (`core.autocrlf`) or a sparse checkout set up in your repository does not change it or leave files out.

To see the states a round moves through (collecting, complete and judged) and the steps between them (complete, judge), open the diagram in [`docs/architecture/review-round-machine.dot`](../architecture/review-round-machine.dot). It is generated from the code: `php bin/console workflow:dump review_round | dot -Tsvg > review-round.svg` (needs Graphviz) draws the current machine. Each reviewer of a round has its own states (queued, running, verdict, failed and blocked) and steps (start, receive, fail, requeue, block), drawn in [`docs/architecture/reviewer-machine.dot`](../architecture/reviewer-machine.dot) and generated the same way with `php bin/console workflow:dump reviewer`.

Stopping the command with Ctrl-C (SIGINT) or SIGTERM removes the snapshot before it exits, with exit code 130 or 143 (on a PHP with the `pcntl` extension, which the console needs to handle signals). A run killed with SIGKILL cannot clean up and may leave an `intakt-review-*` worktree behind: `git worktree list` shows it, and `git worktree remove --force <path>` removes it.

The outcome comes from plain code, never from what a reviewer wrote: `approve` when the project's quorum policy is met, otherwise `changes` when a reviewer asked for changes with a finding on the act list, otherwise `blocked` (a reviewer that failed or was blocked gives no approval). A reviewer that asked for changes only with P3 findings, all of which the judge deferred or rejected, counts as approving: the deferred findings become follow-ups and the rejected ones are dropped, so no reviewer holds the review at `changes` only for findings the judge deferred or rejected. A reviewer that asked for changes with no finding on the act list in any other way (its findings quote code the change does not hold, so the judge never saw them; the judge's answer could not be read, so its P3 findings got no mark; or its answer uses one of the finding ids Intakt keeps for a failed review, such as `no-tools`, whose findings are never recorded) counts as `blocked`, so a review judged with counted votes that ends as `changes` always names something to act on (a round judged before votes were counted keeps the verdicts as given, see [Reading a verdict](#reading-a-verdict)). The dashboard's review page shows the same outcome. The verdict published for a loop differs in one case: an approval whose act list still holds a P1 (the quorum was met beside a reviewer's P1) is published as `changes`. The act list is every P1 and P2 finding that passed the quote check plus the P3 findings the judge marked `act`. The tokens are the prompt, completion and total tokens (the prompt includes cached input, and the cache read, cache write and cached parts appear beside it when they are not 0) of the model calls made for this round, that is each reviewer's calls and the judge's call (as recorded in the ledger, including calls that failed after spending tokens); each of these calls is recorded with the round it was made for, so another round of the same project running at the same time is not counted. The cost prices each of those calls by its model, from the prices you set (see [The cost of a round](#the-cost-of-a-round)).

Exit codes: `0` approve, `10` changes, `11` blocked (also a round with no outcome at the command's upper wait, with the reason "no outcome in time", and a round whose judging failed for good, with the reason "the judging failed"), `1` wrong input or configuration (a missing `--project` or `--task`, a `--round` below 1, a `--repository` that is not a directory, an empty branch or `--base`, an unknown project, a branch the repository does not have, a repository git cannot read, a `--round` that is not the change's next round, or a project that maps no model to a tier the round needs, such as `Project "intakt" maps no model to the "light" tier, which this round needs: ...`, see [Capability tiers per project](providers.md#capability-tiers-per-project)), with the reason printed. Any other error is a bug in Intakt: the command does not print it as a reason, so it reaches the console, which shows it as an error block naming the exception's file and line, adds the trace only with `-v`, and exits with the exception's code, or `1` when that code is 0 or negative; a code above 255 is capped at 255. An exit code of `1` alone therefore does not tell a wrong input from a bug; the printed message does. `--round` is optional: the next round of a change is numbered by Intakt (1, then 2, and so on), and `--round=N` makes the command refuse to start when the next round would not be N, so a script can tell that another round started meanwhile; the number is checked as the round is opened, so a round started by someone else a moment earlier is caught too.

`--format=json` prints one JSON document instead of the text: `round_id`, `round`, `decision`, `exit_code`, `verdicts` (tier, decision and finding count per reviewer), `act_list`, `tokens`, `cost` (`usd`, the cost in US dollars or `null` when it is unknown, `unpriced`, the models without a price, and `price_date`, the day of your price list, or `null` when you gave none, when the cost is unknown, and for a round that made no model call), `reasons` and `kinds` (the kind of the figures: `round`, `findings` (each verdict's finding count) and `calls` (`tokens.calls`) are `counted`, `tokens` (the other figures in `tokens`) is `measured`, `cost` is `estimated`). Each `act_list` row is a finding with only the fields the schema lists (`id`, `severity`, `file`, `line`, `symbol`, `text`, `fixable_by`, `merged`, the ids of the other findings the row stands for, empty when it stands for one, and `judge_note`, the judge's note: the row's own note, or, when the row has none, the first note of a finding it merged, and no key when neither has one); what Intakt keeps about a finding for its own use, such as the evidence or the requirement a reviewer named, is left out. Intakt writes the document with the Symfony Serializer, and its tests check it against [review-output.schema.json](review-output.schema.json), the document's JSON Schema, so a script can rely on that file.

### Reading a verdict

`intakt:review` ends with the outcome on the first line and an exit code a script can test. The shape is below (an illustration of the format `ReviewReport` prints, not a recorded run; ids, files and numbers differ in every review):

```
changes (round 1 counted)
strong reviewer: changes, 2 findings counted
standard reviewer: approve, 0 findings counted
act list: 2 findings counted
F1 P1 src/Cart.php:42: the discount is applied twice
judge: the second call only runs for a coupon that is already rejected
F2 P2 src/Report.php:10: a new function has no test
tokens: 5 calls counted, 18000 prompt (15000 cache read, 2000 cache write), 1200 completion, 19200 total measured
cost: 0.0567 USD estimated, prices of 2026-11-13
```

- **Every figure says how it came to be.** A short word follows it: `measured` for token counts, which the provider reported; `counted` for the round number, the finding counts and the number of calls, which Intakt counts in its own records; `estimated` for the cost, which is worked out from your price list. On the token line, `counted` follows the calls and `measured` follows the token figures. The review never adds figures of different kinds into one total: the tokens and the cost stay on their own lines, side by side. The JSON names the same kinds under `kinds` (`round`, `findings` and `calls` are `counted`, `tokens` is `measured`, `cost` is `estimated`).

- **The token line** counts every model call of the round, its judge call included. The prompt holds all input tokens, also the ones the provider read from its prompt cache (`cache read`) or wrote to it (`cache write`); those two are named in parentheses when the provider reports them, or as one `cached` figure when it does not tell them apart (Claude Code). A streamed call keeps the input and cache figures the provider reported when the stream began (Anthropic reports them first and only the output tokens at the end), so its prompt is not lost; a figure the provider never reported stays unknown, never 0. The total is always the prompt plus the completion. The dashboard's review page shows the same figures.
- **The cost line** is what the round's calls cost at the prices you set, in US dollars, to four decimals (`less than 0.0001 USD` when it is above 0 but too small for that), followed by `estimated` and the day of your price list (`prices of 2026-11-13`, or `price date unknown` when you set no `price_date`, and also for a round that made no model call, since nothing was priced). An unknown cost shows no figure, so it carries no `estimated`. When a call used a model you set no price for, also a call that failed before the provider reported any tokens, the line says `cost: unknown, no price for <model>` (naming each such model once) instead of a partial sum or 0. When a call's provider reported no input tokens for it, the line says `cost: unknown` instead of the cost of the output tokens alone (with `, no price for <model>` added when a model also has no price). The dashboard's review page shows the same figure for each round, in its tokens table, and the sum of the rounds in the summary line, with the same `unknown, no price for <model>` wording. On the page, a cost with a figure has the same `prices of 2026-11-13` or `price date unknown` after it, also the round's and the review's cost in the session summary of a running round; the review's cost in the summary line and the "Cost" head of each token table whose cost has a figure carry a small `estimated` label (hover over it to read that it comes from your price list). The page shows the tokens and the cost side by side and never adds them into one total.

- **The decision** is `approve` when the project's quorum policy is met, `changes` when a reviewer's request for changes has a finding on the act list, otherwise `blocked` (a reviewer that failed or was blocked gives no approval). Plain code decides it, never a reviewer's wording. A reviewer's `changes` counts as changes only when one of its findings is on the act list; it counts as an approval with follow-ups when all its findings are P3 and the judge deferred or rejected every one; otherwise it counts as `blocked` (a `changes` with no finding at all never reaches this point, see below). So a round judged with counted votes that ends as `changes` always names something to fix. A round judged before votes were counted has no votes stored: its verdicts count as given, so it can still read `changes` with an empty act list. The reviewer's own line still reads `changes`; only its vote for the quorum differs. The console, the JSON and the review page show the same outcome (see the paragraph above for the cases, and [Reviewer-for-loop mode](providers.md#reviewer-for-loop-mode) for the one case where the published verdict differs). The exit code is `0` for approve, `10` for changes, `11` for blocked and `1` for wrong input or configuration. A project that maps no model to a tier the round needs (a reviewer's tier or the judge's `light` tier) gets no verdict at all: the round is refused before any reviewer starts, the message names the project and the tier, and the exit code is `1`.
- **A judging that failed for good** ends the review as `blocked`, exit code `11`, with the line `reason: the judging failed` (in the JSON, `"the judging failed"` first in `reasons`) and an empty act list, whatever the reviewers decided. The command stops waiting as soon as the failure is recorded in the ledger (event `judging_failed`), after the worker's retries; a judging that was parked in the failure transport also ends the wait; the round stays unjudged and, for a project in `reviewer-for-loop` mode with the forge publication configured, its head still gets the status for a round Intakt could not review, once: a judging that comes back after a worker restart, or one queued before an upgrade, publishes nothing twice and loses nothing. The workers' log names the round (`The judging of round ... failed for good; ...`).
- **A replay** ends the review as `blocked`, exit code `11`, with the line `reason: a replay never counts as a verdict: this round plays a recorded review back` (in the JSON, for a judged round, the same text first in `reasons`), whatever the reviewers decided, when the round was opened in a project stored as a replay (see [Recording a review for the demo](demo.md#recording-a-review-for-the-demo)). The verdicts and the act list are still listed.
- **No outcome in time** ends the review as `blocked`, exit code `11`, when the round is neither judged nor failed in its judging at the command's upper wait (one hour for each reviewer plus one for the judge), whatever held it up. The line reads `reason: no outcome in time: the round did not end within 10800 seconds; if no worker runs, start one with "messenger:consume async", then review again` (the seconds are the upper wait of the panel; in the JSON, the same text first in `reasons`). The act list is empty; the verdicts the reviewers did give are still listed.
- **One line per reviewer** names its tier, its decision and how many findings it reported. A `reason:` line follows when a reviewer was blocked, with why: a reviewer that did not deliver a usable review (no provider left, a cut stream, a refused approval, a stopped worker) is named as blocked, for example `reason: correctness reviewer blocked, Every provider of the tier is out: anthropic for 300 s, openai for 300 s.` or `reason: correctness reviewer blocked, The reviewer had no tools to read the change ...`, and the review page shows **Blocked** with the same reason in its line in the Now box and its row in the round's Reviewers table. For a blocked verdict recorded by an older version of Intakt, which did not keep the reason, the page says `Reason not recorded` instead. A reviewer that failed is named there in plain words, for example `reason: correctness reviewer failed, stopped at its output limit`, `reason: correctness reviewer failed, gave no approval without naming a finding`, or `reason: correctness reviewer failed, the model endpoint could not be reached`; the MCP `start_review` tool gives the same reasons. It counts as a blocked vote, so a failed reviewer never turns a two-reviewer panel into a one-reviewer approval.
- **A reviewer that answers `blocked` with findings asks for changes.** Reviewers are asked for `approve` or `changes` only, and a problem that must stop the change is a P1 finding. When a reviewer still answers `blocked` and names at least one finding, Intakt records its verdict as `changes` with those findings: its line here reads `changes`, and on the review page its line in the Now box and its row in the round's Reviewers table read **Changes requested**, and the quorum policy counts it as any `changes` answer (see the decision above). Only the live log shows the model's own word, `blocked`. A `blocked` with no finding is asked once more as below, and the blocked verdicts Intakt gives itself (a stopped reviewer, a cut stream, a refused approval, a reviewer without tools) stay `blocked`. What keeps a verdict `blocked` is that Intakt gave it, not the finding's id: a reviewer whose answer (`approve`, `changes` or `blocked`, also on a diff Intakt had to cut) names a finding like one of Intakt's (for example `no-tools`) gave an answer that could not be read, so it is asked once more and then fails, as below.
- **The act list** holds every P1 and P2 finding that passed the quote check (see [Sorting findings with the judge](#sorting-findings-with-the-judge); the judge cannot remove one) and the P3 findings the judge marked to fix now. Each line has the finding's id (`F1`, ...; the same problem keeps its id in every later round), its severity (`P1` must be fixed, `P2` should be, `P3` is a small remark), the file and line, and the text. When two reviewers report the same file and line and both findings are on the list, the list holds one line for that place (the highest severity and the first reviewer's text), and its id names each finding it stands for, joined with `+` (`F1+F2`). The same holds for two findings the judge says have one cause (for example one changed comparison flagged at lines 12 and 14) when both are in the same changed part (hunk) of the same file and at most five lines apart; the judge only names the cause, and findings in different hunks, in other files or further apart stay separate lines. A finding at the line of one already merged joins the same line, whichever of them was reported first. The whole line stays within five lines of one file: when the judge's links would chain findings further (for example lines 3, 8 and 13), the link that would stretch it is not used, so the finding at line 13 keeps its own line and text. The JSON row has the first id under `id` and the others under `merged` (`"id": "F1", "merged": ["F2"]`), and the review page shows the same single row with one finding number, `F1`, and `Also reported as F2` below it. A P3 finding the judge deferred becomes a follow-up and a P3 it rejected is dropped; neither is on the list, and a reviewer whose findings are all such P3s counts as approving. When the judge marked a P1 or P2 finding defer or reject, the line after it reads `judge:` and the judge's one-sentence reason (in the JSON, `judge_note` on that row). A line that merged other findings shows its own note, or, when it has none, the first note of a finding it merged, so a reason given for a finding reported second at a place is not lost; a line carries at most one note, and has no such line or key only when neither it nor any finding it merged has a note. A finding on a rule that a passing gate enforces is not a reason to send the change back; a case the gate misses becomes a gate issue instead. `php bin/console intakt:review ... --format=json` prints the same as one JSON document ([schema](review-output.schema.json)).
- **A verdict that does not approve names at least one finding.** A reviewer that answers `changes` or `blocked` without any finding is asked once more at once, from the start, told that its earlier answer's list of findings was empty, shown one complete example finding (its id, severity, file, line, text, rule and the other fields), and asked to name each finding that must change or to approve. When the second answer names nothing either, the reviewer fails with `gave no approval without naming a finding` on the `reason:` line above, so a `changes` or `blocked` line with 0 findings never reaches the judge or the decision. On the dashboard such a reviewer reads `Failed` with no answer, whichever of the two it answered.
- **A reviewer whose model endpoint cannot be reached is asked once more.** When a reviewer's call fails because the model endpoint could not be reached (a failed name lookup, a refused or dropped connection, a timeout), the same reviewer is asked once more at once, and its answer counts as usual. When the second call cannot reach the endpoint either, the reviewer fails with `the model endpoint could not be reached`. Both calls count against the review's budget, each with its own pair of `usage_recorded` rows.
- **A reviewer whose answer breaks off is asked once more without streaming.** When the stream of a reviewer's answer ends before the answer is complete, the same reviewer is asked once more at once, from the start and without streaming, and its answer counts as usual. When that answer breaks off too, the reviewer is `blocked` with the reason of the first break, as it was before. A rate limit or a temporary provider error on the second try is handled as one. The second try is not asked again in turn: when it is stopped at its output limit, the reviewer fails at once with `stopped at its output limit` (there is no third try with more room), and when it gives no approval without naming a finding, or its answer cannot be read as a verdict, the reviewer fails at once with that reason. A rate limit or temporary error that itself breaks off the streamed answer is not asked again: the reviewer is `blocked` at once (see [More than one account of a provider](providers.md#more-than-one-account-of-a-provider)). Each try has its own pair of `usage_recorded` rows, so both are counted. A reviewer on a Claude or Codex subscription never streams, so it is not asked again.
- **A failed review** never shows as `changes`: it shows as `blocked` with a finding such as `reviewer-stopped` or `cut-approval`, or as a failed reviewer with a `reason:` line, for example `reason: correctness reviewer failed, the reviewer's answer could not be read as a verdict` when the model's answer was not a valid verdict twice in a row (the JSON output has the same text in `reasons`). With a panel of one that makes the round `blocked`; with more reviewers the quorum policy decides, and the failed reviewer never counts as an approval. One exception comes from older rounds: a verdict stored as `changes` with such a reserved finding id before Intakt refused those ids still reads `changes` on its line, while the finding ledger skips that verdict's own findings and resolutions. When its round was judged after votes were counted, none of its findings can be on the act list, so it counts as a `blocked` vote: with a panel of one or under `all` the panel decides `blocked` (or `changes` when another reviewer's finding is on the act list), never `changes` with nothing to fix; under `majority` or `one-strong-plus-one` enough approvals beside it still make the panel decide `approve`. The findings of the other reviewers stay listed, and the published verdict follows the act list as for any round: an approving panel whose act list still holds a P1 from another reviewer is published as `changes` (see [Reviewer-for-loop mode](providers.md#reviewer-for-loop-mode)). A round judged before votes were counted has none stored, so there the verdict counts as the old `changes` vote. Fix the cause (a key, a tier, a change split in smaller parts) and start the next round. See [Asking a model for a verdict](#asking-a-model-for-a-verdict).
- **The review page** (`/reviews/<round id>` in the [dashboard](README.md#the-dashboard)) shows every reviewer's state and verdict (a failed or blocked reviewer with the same plain words as the `reason:` line, in the Now box and in the round's Reviewers table), the round's decision once judged, every finding with the judge's call in plain words (`Fix now`, `Dropped: deferred to a follow-up issue` or `Dropped: rejected or not marked by the judge`; findings merged into one act list line are one card with that line's first number, `F1`, and the others below it, `Also reported as F2`) and the tokens used. Under its title, the task sentence, then a meta line naming the project, the change, the number of rounds, their tokens and cost, and the latest round's start; while the latest round runs, a current state block at the top sums up its reviewers, the open (`act`) findings of the last judged round and the judge's call still to come; in the timeline only the newest round of the review starts open, and only when it is judged; every other judged round folds to one line, so while a newer round is still in review every judged round starts folded; a round that ended without the judge's call shows **Blocked** with its reason, as in the two blocked ends above.

### The cost of a round

Set the price of each model under `budget.prices` in `config/intakt.yaml` (or the file `INTAKT_CONFIG` names), keyed by the model name exactly as a tier names it, in US dollars per million tokens, and run `php bin/console cache:clear`:

```yaml
budget:
    price_date: '2026-11-17'
    prices:
        claude-opus-5-5: { input: 5, output: 25, cache_read: 0.5, cache_write: 6.25 }
        gpt-6.2-sol: { input: 2, output: 10 }
```

`budget.price_date` is optional: the day you read the prices, written `YYYY-MM-DD` in quotes (`'2026-11-17'`). The review, on the console and on the dashboard's review page, shows it beside the estimated cost; anything else than such a day stops Intakt from starting, also a date without quotes, because YAML reads an unquoted date as a point in time and moves a day that does not exist, such as `2026-02-30`, into the next month.

`input` and `output` are required; `cache_read` and `cache_write` default to the `input` price. For a subscription account, use the list price: the figure is an equivalent, not a bill. A price must be a number of 0 or more; a missing `input` or `output`, a negative price, text or `.NaN` stops Intakt from starting and names the key. A call is priced as: uncached input tokens at `input`, cache reads at `cache_read`, cache writes at `cache_write`, completion tokens at `output`; cached tokens the provider does not split into reads and writes (Claude Code) count at the `input` price. Each call is priced by the model its tier names (or its substitute's model when a substitute answered), not by the name the provider's answer gives, so `gpt-6.2-sol` in the config also prices an answer that reports itself under a dated name, and Claude Code calls, whose answers name no model, are priced too. A call recorded before Intakt kept the tier's model counts as the model `(no model)`, which has no price. With no `prices` set, every round's cost is unknown.

The demo's sample project brings its own prices: the first start writes a `budget.price_date` of 2026-11-18 and a `budget.prices` block into the seeded file, one entry for each model of its panel and judge (the models of the providers you gave keys for), so the first review shows a cost figure. They are list prices, not a bill: the table is dated 2026-11-18, and the Hugging Face router prices of Kimi-K3.1-Pro and DeepSeek-V4-Pro-0813 on DeepInfra were read from the router on that day (the Anthropic and OpenAI prices were not refreshed then), and you can edit them in that file. The demo takes its models, these prices and their date from `config/sample-project.yaml` in the image, so a release that refreshes them changes only that file; a demo already seeded keeps its own file. A model without a price, for example one you add to a tier later, still gives `cost: unknown, no price for <model>`. A demo that was seeded before this change keeps its file, since a seeded file is never rewritten, so add the prices by hand.

## Finding ids across review rounds

Intakt keeps a list of the findings of a change across its review rounds. Each new finding gets an id (`F1`, `F2`, ... in the order they first appear), and a finding reported again under that id in a later round keeps it, so the same problem has the same id in every round. When several reviewers report the same existing id in one round, it stays one finding. A finding marked resolved is closed: later rounds are not shown it, cannot mark it as a repeat, and the same problem reported again gets a new id. From round two on, every reviewer of a round is shown the open findings as they were when the round started, with their ids (marked as untrusted text in the prompt), lists the ids it finds fixed as resolved, and marks a finding that is still there as a repeat under the same id; any other finding gets a new id. A verdict that resolves or repeats an id that was not open, marks the same id both resolved and repeat, or names a finding with an id Intakt keeps for its own failed reviews, cannot be read as a verdict, like any answer that is not a valid verdict: it is asked for once more and then fails the reviewer. The list is kept in the database for each change and updated once every reviewer of a round is in; when one reviewer finds a finding fixed and another reports it again in the same round, it stays open. From round two on, a new finding that is P1 or P2 is lowered to P3 before the reviewer's verdict is stored, so the panel's decision and the list both see P3, unless the reviewer marked it a regression (the change broke something that worked before) or named a requirement it breaks; a finding reported again under its id keeps the severity it was first stored with, and round one is never lowered. A review that failed (an answer that was not a valid verdict, a cut-off answer, or an approval from a reviewer that could not read the change) adds nothing to the list: it is the reviewer's fault, not the change's. When two rounds of one change run at the same time, the reviewers of a round still all see the list from their round's start, even when the other round finishes between them; a round that was shown a finding as open can still mark it as a repeat after the other round resolved it, and then it is open again. When the older round finishes last, its verdicts are left out of the list, so they cannot reopen or close what the newer round decided.

Each reviewer's verdict, the findings of a round and this list are kept in the database as JSON with snake_case field names (such as `fixable_by` and `follow_ups`). Verdicts and findings stored by an earlier version of Intakt use the same fields and read back unchanged, so updating Intakt needs no step to convert them.

## Sorting findings with the judge

The judge is a small model call (on the `light` tier of the project) that reads the task, the list of files the change touches and the findings of the reviewers and marks each finding `act` (fix it now), `defer` (real, but it needs its own design or tests, or files outside the change; a small local edit in a file the change already touches, such as wording, a name, a comment or a missing test case, is `act`) or `reject` (wrong, taste, or against a non-goal of the task). The judge can also mark a P1 or P2 finding `defer` or `reject` and give its reason, when it disagrees with or doubts the finding, but that mark does not remove it: a P1 or P2 finding stays on the builder's list whatever its mark, and only a P3 finding is deferred or rejected by its mark. The task, the findings and the list of files the change touches (one path per line, each written as a JSON string so a path with a newline or a quote stays on one line) reach it as fenced data, never as instructions. It never changes a reviewer's verdict as shown, but its marks decide how a reviewer's `changes` counts for the quorum: a reviewer whose findings are all P3s it deferred or rejected counts as approving, with follow-ups (see [Reading a verdict](#reading-a-verdict)). When its answer is invalid (not the expected shape, an id it was not given, a finding left unmarked, a mark that is not one of the three, or a stream cut off), every P1 and P2 finding is marked `act` and P3 findings get no mark. When every reviewer of a round has finished, Intakt queues one judge call for the round, run by a worker outside the round's lock. The judge sees the round's findings under the ids Intakt gave them (`F1`, `F2`, ...), so two reviewers that both call a different finding `F1` do not hide one of them. These findings are kept with the round when its last reviewer finishes, so a later round of the same change, or one that finished first, does not change what the judge of this round sees. A new finding of a round that finished after a newer round of the same change gets an id with the round's number in front (`R1-F2`), so it never shares an id with a finding of a later round. A round whose reviewers reported no findings is recorded as judged without a model call. When the provider limits the call or the account is busy, the call is tried again later instead of being given up. When the call fails for another reason and its retries run out, Intakt logs an error that names the round, and the round stays unjudged; `intakt:review` waiting on that round ends as `blocked` with the reason "the judging failed". A round is judged once: the round then moves to `judged`, and a judge call delivered again asks the model nothing and records nothing. The builder's list holds every P1 and P2 finding and the P3 findings marked `act`; each deferred P3 finding becomes a follow-up; a rejected P3 finding (and a P3 finding left unmarked) is on neither. After an invalid answer every P1 and P2 finding is on the builder's list and no follow-up is made. The result is recorded as a `judge_done` event in the ledger with the ids on the act list, the ids of the follow-ups, and every finding the judge was given (id, severity and text), which the review page shows. When the judge defers or rejects a P1 or P2 finding and gives a reason, the reason is kept with that finding in the event, with a credential this install holds, or text shaped like a key or token, replaced by `[redacted]`; the finding stays on the builder's list. Follow-ups are not stored anywhere else yet, and `intakt:review` prints the act list.

Before the judge is asked, plain code (no model) runs a quote check on each finding. It reads the code a finding quotes inline between backticks (such as `` `grepName` ``) and looks for the names in it in the change: the diff and the files the diff touches, as they are in the reviewed checkout. A finding is dropped when it quotes code and none of its quotes is found there, so a finding about a name nobody wrote ("`grepName` is not defined" on a change that only uses `customerName`) never reaches the judge, or the builder's list (the review page lists it apart, with its reason), and a real finding at the same file and line is never merged under it. A quote counts as found when any name in it is found as a whole name. Two backticks on each side may have spaces inside them (``` `` customerName `` ```). Backticks the check cannot read for sure (a space right inside single backticks, three or more backticks within a line, a different number of backticks on each side, or two or more backticks on each side around code that holds fewer backticks, such as ```` ``` customerName + `suffix` ``` ````) can only keep a finding: it stays when a name between them is found, and they never cause a drop. Fenced code blocks, quoted paths and file names, and quoted numbers are not checked. A line that starts with three backticks opens a fenced block only when no other backtick follows on that line, as in Markdown, so a line starting with an inline quote in three backticks (```` ```grepName``` is not defined ````) is read as a quote and the lines after it are still checked. The finding's symbol is never checked, because it is a place like the file and line, so a finding without a quote goes to the judge whatever its symbol. A round whose every finding is dropped is recorded as judged without a model call. Each dropped finding is recorded with the round in the ledger, with the reason it was dropped (such as "none of its 1 quoted code fragments is in the change"), in the round's `judge_done` event, which `bin/console intakt:ledger:events` prints. The MCP tool `review_status` returns them, with their reasons, under `dropped` once the round is judged (see [Connecting an agent through MCP](mcp.md)). The review page lists them under the judged findings, each card marked "Quote not found in the code", with a closed **Quoted code** disclosure that opens on the quotes the check counted (as many as the reason names; fenced suggested-fix blocks are not listed), under each quote the changed lines recorded as closest to it (see below), each with its file and line number, the fixed line "File names, numbers and suggested-fix blocks are not checked." and the recorded reason after `Dropped before the judge:`; when the check counted no quote, the disclosure holds only the recorded reason. A round whose every finding was dropped does not say the reviewers reported none; `intakt:review` does not show them yet.

With each dropped finding, in the same `judge_done` event, Intakt records for each quote up to three lines the change adds that come closest to the quote, each with its file and line number: a line comes close when its names share at least half of the quote's name parts (`reasonForDrop` and `reasonToDrop` share "reason" and "drop"), and the lines sharing the most come first. Each line is cut to 160 characters, every quote of the finding gets its lines (a quote written twice gets them once), and a quote with no close line gets none. Credentials in a recorded line or quote are replaced with `[redacted]`, as in the logs; that mark is not counted as a name, so a line is never recorded only because a credential was hidden in it. Intakt reads each line from the file as it is checked out for the review and looks for credentials in the whole file, so a private key is recognized by its `BEGIN` line wherever that line is. When a credential runs over several lines of a file, as a private key does, no line of that file is recorded. No line is recorded from a file Intakt cannot read in the checkout (deleted, outside it, or the checkout is gone), nor from a symbolic link or a file under a linked folder (the link may point at a file the change does not touch), nor from a file that was swapped for a link or another file while Intakt read it, nor from a file whose path holds a credential; lines of other files can take their place. The review page shows these lines in the closed **Quoted code** disclosure, under the quote they were recorded for. A quote with no recorded lines shows alone, and so does every quote of a finding dropped before Intakt kept these lines. A quote that had a credential hidden when it was recorded shows no lines either, because the page matches the lines to the quote exactly.

### A P1 that comes back on the next head

When the judge is done, Intakt gives each P1 finding of the round a key and records the keys under `p1_keys` in the round's `judge_done` event (finding id to key), which `bin/console intakt:ledger:events` prints. The key is a hash of the finding's text and of every file it names, as that file is in the reviewed checkout, so the same finding on unchanged files gets the same key and an edit of any file it names gives another one. A finding names a file in its file field (taken exactly as written), in a span between backticks (read whole, so a path with a space or any other character works there, with or without a trailing line number such as `:12`), or as a word of its text that names a file of the checkout. A path with a directory is read from the top of the checkout. A name without a directory (such as `B.php:12`, `Makefile` or `Dockerfile`) stands for the file of the checkout with that name, wherever it is. Spacing in the text counts only between backticks or double quotes. A P1 gets no key (`null`) when it names no regular file of the checkout, when its file field is not a regular file of the checkout, when a path with a directory and a file extension it names is not a regular file of the checkout, when a path it names is not there while the folder it points into is (a file cited with something after its name, such as `src/B.php::run()`, `src/B.php#L12` or `src/B.php(12)`), when a name without a directory starts with the name of a file of the checkout and goes on with a character that is no letter or digit (`B.php::run()`), when a word of its text names a file of the checkout that cannot be read, when a folder of the checkout cannot be listed, when a name without a directory belongs to several files of the checkout, or when a word is the first part of a file or folder name with a space, wherever that file or folder is (a path or name with a space written without backticks, such as docs/Release Notes.md or Release Notes.md, gives no key); such a finding is judged again. A word with a `/` that points into no folder of the checkout (and/or) is not a file and changes nothing. A finding that mentions the name of a checkout file anywhere outside a citation the key could read (such as Core/B.php::run(), file=B.php or @B.php) gets no key either. When a P1 with a key comes back on another head of the same change (another commit was reviewed), Intakt records a `recurring_p1_found` event in the ledger, which `bin/console intakt:ledger:events` prints, with the round that flagged it again, its finding id there, the key and the first round that flagged it. Each round that flags it again on another head than the first one gets one such event, also when the rounds are judged out of order, and a round on the same head as the first one gets none. A round's event waits while an earlier round of the change has all its reviews in and waits for the judge, because that earlier round might be the one that flagged it first. An earlier round still waiting for a reviewer, a round whose judging failed, and a round completed by an older version of Intakt, which was never sent to the judge, do not hold it up; when a judging fails for good, the events it held up are recorded with the failure (or at the next judging of the change, if the failure could not be recorded). So on heads A, B and A, rounds judged in any order give one event, for the round on B, as long as no earlier round is still waiting for a reviewer. If an earlier round was still waiting for a reviewer and is judged later, the events recorded before stay and its judging adds its own, so A, B and A can then give two. A P1 without a key never counts as recurring. The round itself is still judged as usual. When Intakt already keeps an escalation verdict for that P1 (the separate verdict of an escalation review, kept per finding under the same key), it records the reuse of that verdict instead of asking for an escalation review again: an `escalation_verdict_reused` event after the `recurring_p1_found` one, naming the verdict's outcome (`confirmed` or `rejected`) and the round that gave it. The reuse asks no model, and edited files give another key, so nothing is reused on changed code. A P1 that names no regular file has no key and is judged again. Without a kept verdict, Intakt queues an escalation review of that P1 (see below).

The escalation review of a P1 that comes back shows the stronger review the one finding and the diff, with the diff of every file the finding cites first and whole, and cuts only the rest of the diff when it is long. A cited file is a path or a name with an extension in the finding's text. If none of those files is in the diff, or they alone are too long, Intakt builds no prompt and gives its own reason.

A queue worker runs the escalation review after the round is judged.
It asks the project's strong tier, with no tools, whether the one finding is real (`confirmed`) or not (`rejected`), and why.
The reasons are redacted, so a secret the model quotes is not kept.
It fails with Intakt's own reason, and gives no verdict, when the project maps no model to the strong tier, when the finding's code would be cut from the prompt, or when the answer cannot be read: anything but `confirmed` or `rejected`, reasons that are empty or only spaces, or a field the answer must not have.
A provider error (a rate limit, a rejected key, an outage) is not a failed escalation: it stays an error, so the call can be tried again.
The worker's log and a parked message then name the failure in Intakt's words, never in the provider's, because a provider's message can repeat a key.
Intakt keeps the verdict for the finding's key and records an `escalation_reviewed` event with the round, the finding id, the key, the outcome and the redacted reasons, which `bin/console intakt:ledger:events` prints.
A later round with the same P1 on unchanged files reuses the kept verdict (`escalation_verdict_reused`) and asks no model.
A failed escalation records `escalation_failed` with Intakt's reason and keeps no verdict, so a later round of the same P1 is reviewed again.
The review runs once per round and finding: a message delivered again asks no model and records nothing more.
When two rounds of the same P1 are reviewed at once, only the first verdict is kept, and the other round records its reuse.
