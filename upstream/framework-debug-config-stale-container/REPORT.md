# `debug:config` fails when the cached container is stale

Found while building #2901: `bin/console debug:config framework asset_mapper` failed with `Can not change config enabled because it has already been read.` (`FrameworkExtension.php:757`).

## What happens

`ConfigDebugCommand::compileContainer()` clones the kernel and boots the copy. When the cached container is stale, `boot()` builds the container, which loads every bundle extension; the command then calls `buildContainer()` on the same copy, so the same extension instances are loaded again and `FrameworkExtension::load()` throws in `writeConfigEnabled()`. It is not about AssetMapper: any `debug:config <name>` fails, with or without a path.

On 8.2 the cache is stale now and then without any change, since symfony/symfony 73784a8d00 ("[Config] Detect changes made in the same second as a cache was built"): in Intakt the first run after a fresh install (no `config/reference.php`) failed, later runs passed. On the 8.2.0-BETA2 skeleton, `rm -rf var config/reference.php && bin/console debug:config framework secrets` failed in 5 of 10 and 2 of 10 runs (two batches). Forced in one process (boot the kernel on an empty `var/`, give `config/services.yaml` the mtime of the cached container without changing its content, run the command with that kernel) it failed 3 of 3 times on 8.2.0-BETA2 and exited 0 on 8.1.11; 73784a8d00 is in v8.2.0-BETA1 and later only.

## Reproduction

`reproduce.php` dates `config/services.yaml` one minute in the future, runs `debug:config framework secret` and restores the mtime. Not yet run through `intakt:upstream:run`; the same steps were run by hand on the skeletons below.

Measured on fresh `symfony/skeleton` apps with `symfony/asset-mapper` (PHP 8.5.12, Docker `composer:2` on CT 135), after `touch -d '+1 hour' config/services.yaml`: 6.4.50 (framework-bundle 6.4.49), 7.4.23, 8.1.11, 8.2.0-BETA2 and `8.2.x-dev` (framework-bundle d1f6bdf) exit 1 with the message for `debug:config framework`, `framework secrets` and `framework asset_mapper`. With a fresh cache all exit 0. On 8.2.0-BETA2, `rm -rf var config/reference.php` before `debug:config framework secrets` failed in 1 of 3 runs. Rerun on 2026-11-20 (PHP 8.5.12) with `reproduce.php` on a skeleton at framework-bundle 8.2.0-BETA2: exit 1 without the fix; with the `ConfigDebugCommand` change of `fix.patch` it passes, and the cold-cache and forced same-second cases above exit 0 (10 of 10, 3 of 3).

`fix.patch` (against 6.4 d3ef71457a): initialize the bundles of the copy again after booting it, and `testDumpWhenTheCachedContainerIsStale`, which fails without the fix and passes with it; `ConfigDebugCommandTest` (41) and `ConfigDumpReferenceCommandTest` (16) pass. Merged up to 7.4 (c8778bb100), 8.1 (46cb370c72) and 8.2 (2894e4eeea), with a context conflict in the test only (`#[TestWith]` attributes): the new test fails without the fix and passes with it on each, and the two test classes pass (44 and 20 on 7.4 and 8.1, 52 and 21 on 8.2). FrameworkBundle low-deps and high-deps for 6.4, set up as Symfony's `unit-tests.yml` (`build-packages.php`, `COMPOSER_ROOT_VERSION=6.4.x-dev`, flex `SYMFONY_REQUIRE`), PHP 8.4.27: 1461 tests OK with `--prefer-lowest --prefer-stable` (the new test also fails there without the fix), 1398 OK with the highest dependencies. php-cs-fixer 3.95.32 with the repository config: nothing to fix in the two files on all four branches. The earlier low-deps attempt broke because `COMPOSER_ROOT_VERSION` was unset: the root package is then 1.0.0 and `symfony/twig-bundle` conflicts with it. The pull request text is prepared outside the repository.
