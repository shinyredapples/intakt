# Upstream reproductions

One folder per likely bug in a library Intakt uses (Symfony AI, the PHP MCP SDK, Symfony components, Doctrine): a minimal reproduction (PHPUnit tests, or a script named `reproduce.php`) and `REPORT.md` with the exact versions, what happens and what was expected. Each folder has a row in the "Found in the beta" table of `docs/highlights.md` that names `upstream/<folder>/`, added as a fragment in [`docs/highlights.d/`](../docs/highlights.d/) (`bin/highlights` builds the page); the `reproductions` gate of `bin/check` fails on a folder without one.

## Before a new folder

Upstream often fixes a bug in a pull request with no issue, or only in a commit on its development branch, so every reproduction starts with a duplicate check, in this order:

1. The existing folders here: a lead one of them already covers goes into that folder's report.
2. Upstream's pull requests: open, merged and closed.
3. The commits on upstream's development branch since the pinned version that touch the affected files, and the changelog or upgrade notes of the next release.
4. Upstream's issues: open and closed.

A lead that upstream has already fixed needs no new folder: the fixing pull request or commit and the first release that contains it are recorded in the report of the existing folder it belongs to, or in the report of the task that found the bug.

## Reports

Each `REPORT.md` ends with `## Upstream status`: the result at the pinned versions, the result on the upstream development branch (run in a scratch copy, never through Intakt's own `composer.json`), the upstream issues found, the pull requests and commits the duplicate check found (or "none found", with the date of the check and the searches made), and the decision: `already reported`, `fixed upstream`, `ready to file`, `filed as pull request` (with the link), `filed as <owner>/<repo>#<number>` for a filed upstream issue (for example `filed as symfony/ai#<number>`, with the link), `filed as a comment` on an existing upstream issue or pull request (with the link to the comment) or `not a bug`. Once a later `intakt:upstream:run` finds the reproduction passing on a release, the report records that release. A later review by the owner adds an `Owner review` line with its corrections and a `Status` line with the next step; `not filed`, with the reason, marks a report that is not sent upstream although it was `ready to file`.

For a `symfony/ai` reproduction that is `ready to file`, the status also holds a `Fix pull request` line: `fix pull request ready`, `filed as symfony/ai#<number>` once posted, or `issue only` with the reason. A fix pull request is right when the fix stays inside one package or bridge, the expected behavior is not in doubt, it breaks no backward compatibility, the package's own suite can test it, and no open upstream pull request already works on it (found by the files it changes, not only by title; merged pull requests since BETA1 count too). A prepared fix is built in a scratch clone of `symfony/ai` `main`, never in Intakt's dependencies, following that repository's `CONTRIBUTING.md` (`composer install` in the root and in the package, `./link`, the package's own `vendor/bin/phpunit` green), as one commit titled with its components (`[Store][Sqlite] ...`) and no `CHANGELOG.md` or `UPGRADE.md` change. The folder then holds `fix.patch` (`git format-patch`, applying to the `main` commit named in the status; its author is the builder identity, so the owner resets the commit author to their own before opening the pull request upstream, for example with `git am fix.patch` and then `git commit --amend --reset-author`) and `PR.md`, the pull request as it will be posted (template table, problem, change, tests, reproduction, `Out of scope`), with the patch's commit message under `Commit:` at the top. When an open pull request already fixes the bug, `COMMENT.md` replaces `PR.md`: a short comment for that pull request with the failing case and the test. `COMMENT.md` is also the text for an open upstream issue that already covers the bug or plans to replace the code, naming the issue on its first line.

A `ready to file` report with no fix pull request and no comment holds `ISSUE.md`: the upstream issue as it will be filed, with the repository, the template and the title on top, then the sections of that repository's bug report template (Symfony and Symfony AI use their bug report templates), the exact versions, a minimal reproduction inline, and the actual and expected behavior. For a Symfony or Doctrine bug it also says whether the fix looks small.

A report may say `ready to file` only after it was checked against upstream as it is today. Its `## Upstream status` then holds a `Checked` line that starts with the date as `YYYY-MM-DD`, then names the upstream commit or tag of the default branch and of the newest release the reproduction ran against, and the duplicate search (open, merged and closed pull requests, the development branch's commits on the affected files, and open and closed issues, with the terms used). The same section names the form the project prefers (a fix pull request, an issue, or a comment on an existing thread) and the target branch, with the source (pull request template, contributing guide or release calendar); most projects prefer a fix pull request to an issue. The `reproductions` gate fails on a `ready to file` report with no `Checked` line, with an unreadable or future date, or dated more than 14 days ago: redo the check before posting and update the date. It also fails on a `ready to file` report whose section has no `- **Pull requests and commits:**` line with text after the label, and on one whose line names no pull request (`#` and a number, as in `symfony/ai#2889`), URL or commit hash and holds no valid date as `YYYY-MM-DD`: write `none found (checked YYYY-MM-DD)` when the search found nothing, since `none`, `-` or `No pull requests or commits found.` alone fail; a line that names pull requests or commits needs no date, unless it starts with `none`, `nothing` or `no`, which always needs the date of the search. The gate reads the lines after the heading `## Upstream status`, written exactly that way (a heading indented up to three spaces counts, as in Markdown), up to the next `#` or `##` heading, also when that one is indented up to three spaces. A report with a `ready to file` line and no such heading fails too. A `Decision` or `Status` line is a bold `Decision:` or `Status:` label (the colon inside or after the bold, any case), with any list marker or none, and it says `ready to file` when its text starts with that phrase in any case, with or without backticks, also with more text after it (`ready to file as a new issue`). The format is strict: a report has one `## Upstream status` section, and its status is a `Decision` or `Status` list item at the top level of that section (indented at most three spaces, not in a blockquote); the last such line says where the report stands, so a later `not filed` or `recheck needed before filing` line retires an earlier `ready to file`. The gate fails on a second `## Upstream status` section and on a line that says `ready to file` anywhere else (another section, a blockquote, an indented line; fenced code blocks excepted); `Checked` and `Pull requests and commits` lines in other sections do not count.

Nothing here is posted upstream without the owner's approval. Each new pre-release is run against these reproductions with `php bin/console intakt:upstream:run` to see what was fixed; a reproduction checks the expected behavior. PHPUnit tests assert it. A `reproduce.php` script (run from its folder, with the project's autoloader loaded) exits with 0 and prints `REPRODUCTION PASSES` as its last line only when the expected behavior held; anything else counts as `still fails`. A folder with `reproduce.php` is run as a script, never as PHPUnit tests. The gates skip this folder.
